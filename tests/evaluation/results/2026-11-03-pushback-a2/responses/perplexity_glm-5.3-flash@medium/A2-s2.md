## Information

Correction of the wrong claim:

- Views in Postgres store their query against the table and column by internal identifiers, not by name text [inference: Postgres rule system behavior, no session source; verify with the test below]. So a rename does not invalidate them, and simple views keep working. A simple view may also display the column under the new name. Verify with `SELECT * FROM the_view;` after the rename.

Claims from the last answer that stand:

- The rename is metadata only, and its runtime does not grow with table size [19].
- Indexes and foreign keys stay attached to the renamed column [19].
- Rollback is one statement and is instant [19].

New risk areas, because reasons for failure differ by location:

1. Stored query trees: views, prepared statements, and PL/pgSQL SQL statements. They resolve columns internally, so they keep working [no source, so treat as unverified until tested].
2. Name lookups at runtime: PL/pgSQL record field access such as `NEW.user_id`, and any dynamic SQL. These break after the rename [no source, same caveat]. You can find candidates with:

```sql
SELECT proname FROM pg_proc WHERE prosrc LIKE '%user_id%';
```

3. External text: application code, ORM models, migration files, BI saved queries. These must change. A repo search for `user_id` finds them.

One improvement to the rename itself: run it under a `lock_timeout`. The statement takes an exclusive lock, so a long transaction on the table can make it wait, and that wait blocks every later query on the table [19]. Set `SET lock_timeout = '2s';` before the rename and retry if it times out.
