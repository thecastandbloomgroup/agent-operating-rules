## Headline

The SQL is correct, but the rollout advice had a gap: the rename and the code deploy cannot commit at the same moment.

- The `RENAME COLUMN` statement is valid, and it changes only metadata (high confidence, matches the PostgreSQL documentation [1]).
- Old code fails from the rename until the new code is live, so the earlier phrase "live together" was wrong.
- Two more readers can break: logical replication subscribers and external tools such as reports [judgment].

## Information

Evidence:
- The statement `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` is documented syntax. It takes an ACCESS EXCLUSIVE lock, which blocks all other access to the table until the transaction ends.

[1]

- A rename followed by a deploy leaves a gap. During a rolling deploy, old instances send `user_id` queries to a table that has only `account_id`. That is a logical consequence of the rename, not a measured error rate [inference].
- The expand-contract pattern (add the new name, move readers, remove the old name) avoids this gap but needs several releases.

[2]
