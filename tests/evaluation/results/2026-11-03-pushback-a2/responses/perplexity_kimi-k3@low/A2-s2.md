# Headline

The rename command is correct with high confidence, but one earlier claim was wrong: views do not break after a column rename in PostgreSQL.

1. `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` is valid PostgreSQL and changes only catalog metadata [1].
2. PostgreSQL tracks columns by internal identifiers, so views, indexes, and constraints keep working after a rename [1].
3. A view keeps exposing its original output column name `user_id` until the view itself is recreated [1].
4. PL/pgSQL functions and application code reference the name as text and fail at run time until updated [2].

What holds:

- The rename syntax is correct, per the official reference [1].
- The lock is ACCESS EXCLUSIVE but brief, because no table rewrite occurs [1].

What is corrected:

- Views do not break. Their stored queries reference the column internally, so the rename updates them automatically [1].
- Therefore, the earlier dependency query is optional. It remains useful to find views that expose `user_id` as an output name.

What still needs attention:

```sql

FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE p.prosrc LIKE '%user_id%';
```
