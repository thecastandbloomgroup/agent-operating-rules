# Headline

The rename command is correct, but one supporting claim was wrong: views do not break when a column is renamed in PostgreSQL.

- The command syntax, the brief lock, and the automatic handling of indexes, constraints, and foreign keys stand as stated [1].
- Views survive a rename because the rule system stores column references by internal attribute number, not by name [1].
- Application code and stored function bodies name columns as text, so they still break and still need updates.

## Background

The previous reply gave a four-step plan to rename orders.user_id to account_id before a flight. This reply re-verifies each claim and corrects the one that fails.

## Relevance

## Information

What stands, high confidence, documented behavior:

- The lock is a brief ACCESS EXCLUSIVE and no table data moves, so the statement finishes in milliseconds [1].
- Indexes, constraints, and foreign keys follow the rename automatically; only their display names keep the old text, which is cosmetic [1].
- The statement is transactional in Postgres, so a rollback restores the old name inside the transaction [1].

The correction:

- PostgreSQL rewrites the stored view definition so the view keeps its old output column name, for example `account_id AS user_id` [1]. Therefore views, and callers of views, keep working. The earlier Step 1 check on information_schema.views tested the wrong object.

What still breaks:

- Function bodies are stored as text and parsed at execution, so a body that names user_id fails at runtime [judgment]. Check them with:

```sql
SELECT pronamespace::regnamespace AS schema, proname
FROM pg_proc
WHERE prosrc ILIKE '%user_id%';
```

- Application SQL that references orders.user_id directly fails after the rename [judgment].

A1. Application SQL is the only direct reader of orders.user_id besides views and functions. Why not measured: the material does not state it. Validate by: grep the codebase and ask the analytics team about saved queries. If wrong: update those queries in the same window or postpone.

**Alternative considered:** keep the original claim and postpone if any view names user_id. It loses because documented rule-system behavior contradicts it, so the check would block a safe operation for no reason [1].
