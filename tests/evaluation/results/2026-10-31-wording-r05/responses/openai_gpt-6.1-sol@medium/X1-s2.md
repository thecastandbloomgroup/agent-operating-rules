## Background

Agents report that summaries are “sometimes wrong,” but the team has no metrics. [1] That report identifies a problem, but not its frequency, cause, or impact.

## Relevance

A prompt change alone gives no evidence that accuracy improves. [judgment] Therefore, the first improvement should create both a safety check and a repeatable test. [judgment]

## Information

### Define the error before selecting the fix

Use these separate labels. A summary can receive more than one label.

| Label | Definition | Example |
|---|---|---|
| Unsupported statement | The source does not support a claim. | The summary invents a refund promise. |
| Contradiction | A claim conflicts with the source. | The summary says an unresolved case is resolved. |
| Essential omission | The summary excludes a fact needed for the next action. | It omits an agreed callback. |
| Presentation defect | The facts remain correct, but the text is hard to use. | Repeated details hide the next action. |

These definitions are proposed product criteria, not measured findings. [judgment]

Add a separate **severe error** flag for mistakes that change money, access, safety, or a customer commitment. [judgment]

### Use three initial measures

1. **Material error rate:** summaries with an unsupported statement or contradiction, divided by summaries reviewed.
2. **Essential omission rate:** summaries missing an agreed required fact, divided by summaries reviewed.
3. **Severe error count:** summaries containing at least one severe error.

Keep agent edits and rejection reasons as secondary signals. An edit alone does not prove a factual error. [judgment]

Record the ticket snapshot, supplied model input, model version, prompt version, output, and review labels. This enables comparison between source failures and model failures. [judgment]

### Diagnose before changing

- If the model never receives a required message, fix input selection.
- If it receives stale status data, fix the source snapshot.
- If it invents details despite complete evidence, test stricter source constraints.
- If facts are correct but hard to use, test a shorter, fixed format.

These are diagnostic branches, not findings about this system. [judgment]

### 1. Protect use and capture evidence

**Test first, deterministic:** Given a generated summary, when an agent uses it, then approval and versioned source records exist.

**Increment:** Add an approval gate and restricted records for one support queue during one work session.

**Blocker removed:** Unreviewed summaries and untraceable errors. [judgment]

**Domain:** Clear, because approval and record checks have fixed pass conditions.

If approval already exists, retain it. Store only policy-approved data, with restricted access and a retention limit.

### 2. Create a small reference set

**Test first, deterministic:** Given each test ticket, when reviewers inspect its reference record, then every required fact has a source location.

**Increment:** Prepare 25 closed tickets: five reported failures and 20 randomly selected eligible tickets.

Use two agents to agree required facts, source locations, and severe-error labels. Resolve differences before accepting each reference record.

**Blocker removed:** No shared definition of a correct summary. [judgment]

**Domain:** Complicated, because source comparison requires support expertise.

Step 2 MUST follow Step 1. Keep the failure set separate from the random set when reporting results.

### 3. Run one targeted, repeatable comparison

**Acceptance test first, stochastic:**

- **Baseline:** The current version on the frozen ticket inputs.
- **Candidate:** One change selected from the observed error pattern.
- **Sample:** Two outputs per version per ticket, giving 50 outputs per version.
- **Pass:** At least 30% lower material error rate on the random-ticket set.
- **Safeguards:** No severe errors, no higher essential omission rate, and no regression on the five reported failures.

If the baseline produces fewer than five material errors on the random set, extend the test before accepting improvement.

**Increment:** Run a four-hour, offline comparison with reviewers unaware of each output’s version.

**Blocker removed:** No evidence that a proposed fix improves accuracy. [judgment]

**Domain:** Complex, because the change’s effect requires observation; its benefit remains a guess.

Step 3 MUST wait until Step 2 passes. Stop at four hours or upon a severe candidate error.

Report counts beside percentages. If the session ends before review finishes, record “incomplete,” not “passed.”

### 4. Enable only a reviewed pilot

**Test first, deterministic:** Given a passing candidate, when its pilot fails a safety check, then the prior version remains available.

**Increment:** Configure one reviewed queue with version labels, error reports, and a tested rollback control.

**Blocker removed:** No controlled path from offline evidence to real use. [judgment]

**Domain:** Clear, because release controls have fixed checks.

Step 4 MUST NOT start unless Step 3 passes. Keep agent approval mandatory.

Stop the pilot after any severe error. Review the next 25 summaries before expanding beyond that queue.
