## Headline

Separate the authentication migration from the sign-up experiment, and establish safety gates before changing production. [judgment]

- Authentication needs a client-specific token design, logout rules, and a rollback path. [judgment]
- Sign-up needs a defined success event and baseline before changes can demonstrate improvement. [judgment]

## Background

The request combines a move from server sessions to JSON Web Tokens (JWTs) with better sign-up conversion. [1] No code, system design, or conversion data accompanies the request.

## Relevance

JWTs do not, by themselves, improve sign-up conversion. [judgment] Therefore, separate releases will make security faults and conversion effects easier to trace. [judgment]

## Information

### Scope and safeguards

**Authentication:** The design review should cover these areas before implementation. [judgment]

- Identify browser, mobile, and service clients, including their current session behavior.
- Define token storage, signing keys, accepted algorithms, issuer, audience, and expiry.
- Define logout, refresh-token rotation, token reuse detection, and account-disable behavior.
- Define compatibility, monitoring, and rollback during the transition.

Do not assume that JWTs require browser local storage or remove all server-side state. [judgment]

**Sign-up:** Define conversion as a named success event divided by eligible sign-up starts within a fixed time window. [judgment]

Measure each step separately: entry, form submission, verification, account creation, and activation. Keep required identity checks unchanged until their owners approve changes. [judgment]

High confidence: separating these changes improves fault isolation because authentication behavior and user completion require different tests. [judgment] No evidence yet supports a specific conversion uplift.

## End

I recommend that we complete these three bounded steps before implementing either production change.

1. **Create an authentication inventory in one repository review.**
   - **Test first, deterministic:** Given the current service, when the inventory is reviewed, then every authentication entry point has an owner and client type.
   - Record session creation, validation, renewal, logout, and account-disable paths.
   - **Capability:** establishes the current contract and exposes migration gaps.
   - **Domain: Clear**, because this step records existing behavior rather than choosing a token design.
   - **Output:** an inventory checked against routes, configuration, and existing tests.

2. **Create the migration acceptance checklist after Step 1 passes.**
   - **Test first, deterministic:** Given the inventory, when the checklist is reviewed, then every authentication behavior has a test and rollback condition.
   - Include invalid signatures, wrong audiences, expired tokens, refresh reuse, logout, account disablement, and signing-key rotation.
   - **Capability:** makes security and compatibility requirements explicit before code changes.
   - **Domain: Complicated**, because a client and threat analysis determines the required checks.
   - **Output:** a reviewed checklist with no unresolved production safety requirement.

3. **Create the sign-up baseline specification alongside Step 1.**
   - **Test first, deterministic:** Given sign-up events, when the specification is reviewed, then it defines the denominator, success event, time window, and exclusions.
   - Add completion time, step abandonment, verification failures, and abuse rates as supporting measures.
   - **Capability:** makes later experiments measurable without weakening identity controls.
   - **Domain: Clear**, because this step defines measures rather than claiming an improvement.
   - **Output:** a checked event specification; report absent data instead of inventing a baseline.

These are proposed work items, not completed tests. Implementation follows the inventory and acceptance checklist; a conversion experiment follows a measured baseline.

## Follow-up

1. **Which repository and deployment target contain the service?** The answer determines where to inspect code, tests, and release controls.
2. **Which clients use authentication, and what must logout or account disablement revoke immediately?** The answer determines token storage and revocation requirements.
3. **What event counts as successful sign-up, and which identity checks must remain?** The answer determines the conversion measure and experiment limits.

If the review finds that JWTs do not meet the required revocation contract, reconsider the migration before implementation.
