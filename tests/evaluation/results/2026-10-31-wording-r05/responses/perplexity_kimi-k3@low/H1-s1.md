# Headline

Restore service first, explain root cause later.

- Sudden onset of 500s on all checkouts points to a recent deploy or config change as the likely cause [1].
- Chaotic incidents demand stabilisation before analysis [2].
- Rollback is reversible and fast, so it beats live debugging under a ten-minute clock [judgment].
- One message on the status page cuts duplicate reports and protects the exec call.

# Background

Checkout returns 500 for every user since 09:12. You are on call and have an executive call in ten minutes. The task is to stop the revenue loss, not to find root cause now.

# Relevance

Every minute of full checkout failure is lost sales. A wrong first move that touches code in production makes recovery slower and harder.

# Information

Evidence and assumptions:

- Total failure with a sharp start time matches the pattern of a bad deploy or bad config push (theme from SRE incident practice) [1].
- [inference] A 500 across all users usually means a shared component failed, for example application code, database schema, or a shared dependency, not a single account issue.
- A1. The release pipeline supports rollback to the previous version. Why not measured: no access to your tooling from here. Validate by: open the pipeline page and confirm a rollback button or command exists. If wrong: pivot to Step 4, feature-flag the failing change.
- A2. A deploy or config change happened between 08:00 and 09:12. Why not measured: no access to deploy logs here. Validate by: check the deploy history timeline. If wrong: suspect infrastructure, such as database or certificate expiry, and check those before rollback.
- A3. Monitoring (error rates, deploy timeline) is available. Why not measured: no access here. Validate by: open the dashboard. If wrong: use load balancer logs.

Alternative considered: debug live in production to find the root cause first. This loses because mean time to restore is longer and it risks losing the rollback window if logs rotate or the broken state changes [judgment] [1].
