## Headline

Measure the errors first, then fix the largest error class, then add monitoring so the problem stays visible. Agents report failures but no data exists, so the first step is a labeled evaluation set, not a prompt change. A measured baseline then directs each fix and proves it worked. This plan takes about three to four weeks of part-time work [judgment].

## Background

A support tool uses an LLM to write summaries. Agents describe the output as "sometimes wrong". No metrics, no error examples, and no definition of "wrong" exist yet.

## Relevance

Fixes without measurement fail about as likely as not, because no one can tell a fix from a regression. A baseline turns agent complaints into a number the team can move and defend.

## Information

**Evidence.** The only signal is qualitative: agent complaints, count of sources unknown, no examples collected [no source]. The failure rate, failure types, and business cost are unmeasured. Any claim about the cause would be a guess, so none drives this plan.

**Assumption log.**

A1. The summariser condenses support tickets or call transcripts into a short case note. Why not measured: the material does not state it. Validate by: read one summary and its source text. If wrong: the error taxonomy in Step 1 changes, the plan does not.

A2. "Wrong" means factual errors against the source text, for example invented facts, wrong numbers, or missed actions. Why not measured: the material does not state it. Validate by: ask three agents to each paste two bad summaries. If wrong: re-scope the taxonomy in Step 1 before Step 3.

A3. Agents can label outputs, at least 30 minutes per week each. Why not measured: the user has not answered. Validate by: run one labeling session with two agents. If wrong: use one reviewer and halve the evaluation set size.

A4. The team can edit the prompt, retrieval inputs, and model settings. Why not measured: the material does not state it. Validate by: make a trivial prompt change in a test environment. If wrong: Step 4 becomes a vendor change request with the same acceptance test.

**Alternative considered.** Rewrite the prompt at once, because it is fast and cheap. It loses because, without a baseline, the team cannot show the rewrite helped, and prompt edits can fix one error class while they add another [judgment].

## End

I recommend that we take these five steps, in this order.

1. **Define the error taxonomy and collect failures.** Cynefin domain: Confused, because the failure modes are unknown, so this step gathers what is needed to classify the work. Increment: in one session, ask five agents for two bad summaries each and sort them into classes, for example invented fact, wrong number, missed action, wrong customer. Blocker removed: "sometimes wrong" has no shared definition. Test (evaluative, rubric first): criteria are coverage (every example fits one class, weight 60%) and agreement (two reviewers assign the same class to 80% of examples, weight 40%); pass at a weighted score of 80 on 100.

2. **Build an evaluation set of 150 real cases.** Cynefin domain: Clear, because building a labeled dataset follows a known practice. Increment: 150 past tickets with source text, summary, and a pass or fail label per taxonomy class. Blocker removed: nothing to measure against. Test (evaluative): two reviewers label each case; pass when inter-reviewer agreement reaches at least 80% on a 30-case sample; resolve disputes before the set is accepted [1].

3. **Measure the baseline.** Cynefin domain: Clear, because scoring a fixed set is a repeatable procedure. Increment: run the current summariser on the 150 cases and compute error rate per class. Blocker removed: no baseline number. Test (stochastic, written first): metric is the factual error rate; sample size is all 150 cases; record the rate with a 95% confidence interval; accept the baseline when total errors exceed 5%, otherwise the agents' complaint does not reproduce and the taxonomy from Step 1 is wrong.

4. **Run one fix as a capped probe.** Cynefin domain: Complex, because prompt and retrieval changes interact in ways visible only afterward, so leverage is a guess. Increment: pick the largest error class from Step 3, apply one change, for example require the summary to quote the source line for each key fact, and re-run the evaluation set. Budget: two working days and two iterations, then stop. Blocker removed: the dominant error class. Test (stochastic, written first): metric is that class's error rate; baseline is the Step 3 rate; pass at a relative reduction of at least 30% with no other class worse by more than 5%, on the same 150 cases. Step 4 MUST NOT start until the test in Step 3 passes.

5. **Add production monitoring.** Cynefin domain: Complicated, because several known monitoring patterns exist and the choice needs analysis. Increment: add a one-click "bad summary" flag in the agent interface and a weekly sample of 20 summaries scored against the taxonomy. Blocker removed: future regressions stay invisible. Test (deterministic, Gherkin): Given an agent flags a summary, When the weekly report runs, Then the flag appears with its taxonomy class and the flag rate, per [1]. If A2 is false, replace the taxonomy in Step 1 and repeat Steps 2 to 3; the rest of the plan stands.

## Follow-up

Conditions that change the recommendation: if Step 3 shows an error rate under 5%, the complaint likely concerns a small visible subset, so shift effort to monitoring (Step 5) before more fixes [judgment]. If Step 4 fails twice within its budget, escalate to retrieval or model changes, with the same acceptance test.
