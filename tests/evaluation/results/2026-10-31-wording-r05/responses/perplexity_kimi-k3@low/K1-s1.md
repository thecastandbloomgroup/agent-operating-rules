# Headline

Rollback or hotfix the db.yaml pool settings in release 2026.10.21: the pool of 8 connections cannot serve 32 workers, and the 5 second acquire timeout turns queuing into errors and latency.

- db.pool.acquire p95 rose from 3 ms to 690 ms while query times stayed flat [1][2].
- Pool max_size fell from 50 to 8 for a workload with 32 concurrent workers [2].
- acquire_timeout_s fell from 30 to 5, which converts pool queueing into 503 responses [2][1].
- The ORM and cache changes are secondary contributors: the eager load adds one query per request, and the TTL cut raised the miss rate from 12% to 31% [2].

# Background

After release 2026.10.21, API p95 rose from 120 ms to 900 ms. The release changed the ORM query, the cache TTL, and the connection pool. Logs, traces, and the diff are attached.

# Relevance

The service now emits 1,800 to 2,400 pool exhaustion warnings per hour and a 0.40% error rate, 20 times baseline [1][2]. Each PoolTimeout is a failed customer request after 5 seconds of waiting.

# Information

**Quantitative evidence**

- database.pool.acquire dominates the regression: p50 1 to 140 ms, p95 3 to 690 ms [2].
- Query spans are flat: orders p95 52 to 58 ms, order_lines p95 30 to 26 ms [2]. N+1 logic per request is not the cause.
- Load is unchanged: peak 410 rps in window A, 405 in window B [2]. The regression is config, not traffic.
- DB server is healthy: peak CPU 38% to 41% [2]. Bottleneck is client-side pool queuing.
- Capacity math: 4 pods x 8 workers = 32 concurrent requests possible, but 6 idle workers per pod because max_size is 8 [2]. Requests that find the pool full wait; at 5 s they fail.
- Cache TTL 300 to 60 s cut warm-window hits: miss rate 12% to 31% [2]. That raises DB demand, but query spans show the DB absorbs it; pool queuing remains the binding limit.
- selectinload(Order.lines) adds one extra query per miss [2]. It holds each connection slightly longer, which worsens queueing under an 8-connection pool.
