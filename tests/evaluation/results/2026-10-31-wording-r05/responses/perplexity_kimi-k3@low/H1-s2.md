# Headline

Roll back the last checkout change first, because a rollback is the fastest stabiliser and diagnosis comes after.

1. A full 500 on every user for 58 minutes points to the last deploy, not gradual failure [judgment].
2. Rollback takes minutes to attempt; root cause analysis takes much longer [judgment].
3. The exec call needs one message: impact, action, time of next update [judgment].

## Background

Checkout returns 500 for all users since 09:12. You are on-call and join an exec call in ten minutes. No logs, dashboards, or deploy records are in the material.

## Relevance

Revenue stops while checkout fails, and the exec call needs facts and a plan now. Stabilising beats explaining during an active outage [judgment].

## Information

Evidence available: uniform 500s across all users and a sudden start at 09:12. Both fit a bad deploy or a failed shared dependency, such as a payment token service or database [judgment]. Cause and effect are not visible, so this is the Chaotic Cynefin domain: act to stabilise before analysing [1].

Assumption log:
- A1. A deploy or config change occurred near 09:12. Why not measured: logs are not in the material. Validate by: check the deploy timeline (1 look). If wrong: skip rollback, go to the dependency check.
- A2. A rollback path exists and restores a working version. Why not measured: no deploy records given. Validate by: the rollback command completing and returning 200. If wrong: fail over or scale up instead.

Alternative considered: investigate logs first, then fix. It loses because it trades minutes of certainty for minutes of continued total outage [judgment].

## End

I recommend that we:

1. Announce the incident in one message now: "Checkout down since 09:12, all users, rollback in progress, next update in 15 minutes." This removes the comms blocker before the exec call. Test: Given the message, When the exec call starts, Then you can paste it from drafts. Deterministic, Chaotic because it stabilises the human system like the rollback stabilises the technical one.
2. Check the deploy timeline and error logs for changes after 09:00 (1 glance, no edits). This confirms or kills A1. Test: Given the timeline, When viewed, Then the newest change before 09:12 is named. Deterministic, Chaotic because it feeds the stabilising act and stays under 2 minutes.
3. Roll back the newest checkout change to the last known good version. This removes the largest single probable cause. Test: Given the rollback completes, When a real checkout request runs, Then it returns a non-500 status. Deterministic, Chaotic because restoration comes first whatever the cause [1].
4. If the 500s persist 3 minutes after rollback, shift traffic away or scale the failing tier, and page the service owner of the top error dependency. This is the fallback stabiliser. Test: Given 3 minutes of 500s after rollback, When failover completes, Then error rate falls below 1%. Deterministic fallback, biased to act because downtime is total [judgment].
5. After checkout recovers, run a 30-minute incident review with the deploy diff and logs. This converts the guess into a root cause and a prevention item. Test: Given the incident data, When the review ends, Then one root cause and one prevention action are recorded. Evaluative and later, Complicated because analysis picks among competing causes.

Steps 1 to 3 run in sequence. Step 4 starts only if the test in Step 3 fails. Step 5 MUST NOT start until checkout returns 200s.

If A1 is false, replace Step 3 with a check of external dependencies named in the top error line.

## Follow-up
