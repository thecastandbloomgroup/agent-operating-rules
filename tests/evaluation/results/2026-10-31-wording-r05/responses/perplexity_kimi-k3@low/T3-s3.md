# Headline

Do not bundle these two changes: ship the JWT migration first as reversible work behind a running sessions path, then treat sign-up conversion as a separate measured experiment.

- The auth migration and the conversion goal have different owners, risks, and tests, so coupling them multiplies failure modes.
- The migration should dual-run tokens and cookies so a rollback is one config flag, not an incident.
- Conversion work should start with funnel data, because changing the form before measuring it removes the baseline.
- Three missing facts change the sequencing; they are answered below as assumptions if not confirmed.

# Background

The auth service issues server-side sessions today and should move to JWT (JSON Web Tokens, signed tokens the client presents with each request). At the same time, sign-up conversion should improve. These requests arrived together but are independent problems [judgment].

# Relevance

A session migration touches every request path, so a mistake breaks login for all users at once. A conversion change made during the same deploy window makes it impossible to attribute funnel movement [judgment].

# Information

The two efforts differ in kind and in evidence base, so they are analyzed separately.

**Migration risk.** Session removal forces simultaneous changes in logout, revocation, and token refresh [judgment]. JWT makes logout semantically harder: a stateless token stays valid until expiry, so revocation needs a denylist or short token lifetimes [1]. Dual-running both auth methods during rollout is the standard way to keep rollback cheap [2]. If there are existing mobile clients, they pin old behavior in the field, which raises rollout cost [judgment].

**Conversion.** "Better" has no number attached. Without a funnel baseline (visits, form starts, completions, drop-off by step), any form change ships blind and cannot be evaluated [3]. Analytics must be in place before the form changes, or the change is unmeasurable [3].

**Sequencing logic.** Mixing both in one release makes attribution and rollback unclear, so they are decoupled, auth first. This ordering also protects revenue: a broken signup form during an auth outage compounds the damage [judgment].

**Assumption log**

A1. Stack is a conventional web backend with a database, one deployable auth service. Why not measured: the material does not state it. Validate by: read the service's config and deploy list in one session. If wrong: Step 2's dual-run design still applies, but Step 1 changes.

A2. No third-party identity provider (SSO) exists today. Why not measured: the material does not state it. Validate by: check the login handler for external redirects. If wrong: the migration plan adds an OAuth/OpenID Connect track before Step 2.

A3. Sign-up funnel analytics exist or can be added this week. Why not measured: measuring costs waiting for an answer. Validate by: query the events table or the analytics tool for a `signup_completed` event. If wrong: Step 4 becomes Step 1 of the conversion track and the first experiment is delayed by one week.

**Alternative considered.** Ship both changes in one release to save calendar time. It loses because a conversion regression and an auth regression cannot be distinguished under one deploy, and the rollback for auth would also revert the form work [judgment].

# End

I recommend that we run the following steps in order.

1. **Inventory auth touchpoints.** List every endpoint, middleware, and client that reads the session cookie, in one working session. Blocker removed: unknown blast radius. Test (evaluative, deterministic criteria): Given the service source and deploy configs, When the inventory is reviewed by one engineer who did not write it, Then every consumer of the session cookie appears in the list with an owner. Cynefin: Clear, because enumeration of known consumers is a best-practice checklist task.

2. **Add JWT issuance alongside sessions.** Issue both a session cookie and a JWT at login, and make middleware accept either, with a config flag. Blocker removed: rollback risk. Test (deterministic): Given a valid login, When the flag is on, Then the response carries both credentials and a request with either one passes. Cynefin: Complex, because dual-running two auth modes can produce unanticipated edge behavior, so it ships first to an internal cohort as a safe-to-fail probe with a stop condition of auth error rate above 0.5% for one hour [2]. Step 2 MUST NOT merge until Step 1 is complete.

3. **Migrate consumers, short token lifetime, then sessions off.** Move consumers one by one to JWT, set access token expiry to 15 minutes with refresh tokens, add a refresh-token revoke table for logout, then remove session issuance [1]. Blocker removed: logout and revocation semantics. Test (deterministic): Given a revoked refresh token, When the user calls a protected route, Then every request fails within one access-token lifetime. Cynefin: Complicated, because the right pattern is known but must be fitted to this codebase. Step 3 is the only step with a hard security review gate.

4. **Instrument the sign-up funnel.** Add events: page view, form start, field errors, completion, in one session [3]. Blocker removed: no baseline. Test (stochastic): metric `signup_completed` count matches the user table inserts within 2% over three days of traffic. Cynefin: Clear, because adding standard funnel events is routine analytics work. Step 4 MUST NOT start until Step 3 is stable for one week, to keep attribution clean.

5. **Run one conversion experiment.** Change one form variable (for example, reduce required fields) behind an A/B split. Blocker removed: unmeasured changes. Test (stochastic): conversion rate lift, baseline from Step 4, pass threshold +5% relative, 90% confidence, sample sized by baseline rate. Cynefin: Complex, because user behavior is only visible after the fact, so this is a capped experiment with a stop condition of any drop exceeding 2% [4].

If A2 is false, insert an SSO integration step before Step 2 and reorder accordingly.
