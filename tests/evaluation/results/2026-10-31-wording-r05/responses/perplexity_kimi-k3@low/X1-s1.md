## Headline

The summariser cannot be improved until "sometimes wrong" is measured, so the first step is to define error types and measure them on real cases.

- Unmeasured quality complaints cannot be fixed; they can only be converted into metrics first.
- LLM output is stochastic, so acceptance requires a metric, baseline, threshold, and sample size.
- A small, tested evaluation set is the cheapest path from complaint to fix.

## Background

A support tool gained an LLM summariser. Agents report it is "sometimes wrong", but no metrics, error taxonomy, or test data exist. The request is to improve it.

## Relevance

Trust determines adoption. Unverified errors in agent-facing summaries can reach customers and create rework.

## Information

Evidence here is thin by design: the complaint is one qualitative statement from one group (agents), with no numbers. Confidence that an evaluation-first approach fits is high, based on practice: stochastic systems require metric-first acceptance [1]. Which error type dominates (omission, fabrication, wrong tone) is unknown. That gap drives the recommendation order.

**Assumption log:**

A1. The summariser output can be logged and re-run offline. Why not measured: the material does not state it. Validate by: check the pipeline for input/output logging. If wrong: Step 1 must add logging first.

A2. Around 100 recent real cases are available for labelling. Why not measured: the material does not state it. Validate by: query the case store. If wrong: reduce the labelling sample to 50 and state the wider error bars.

A3. Agents or leads can label errors at roughly 5 minutes per case. Why not measured: not stated. Validate by: time 5 labels. If wrong: use a smaller set per shift.

**Alternative considered:** tune the prompt or change the model immediately. This loses because without a baseline there is no way to tell improvement from noise [judgment].

## End

I recommend that we take these steps.

1. **Define error types and write the acceptance test first.** Increment: a one-page taxonomy (omission, fabrication, wrong action, tone) plus target. Test (stochastic): metric = % summaries with any factual error; baseline = to be measured in Step 2; pass threshold = 5% or less; sample size = 100 labelled cases. Cynefin: Clear; the best practice (define then measure) is known.
2. **Build a 100-case labelled set and measure the baseline.** Test (deterministic): Given 100 logged real cases, When two labellers score each against the taxonomy, Then every case has error labels and at least 85% inter-labeller agreement. Removes the blocker: no truth data. Cynefin: Complicated; labelling needs judgment and the rubric from Step 1. Step 2 MUST NOT start until the taxonomy in Step 1 exists.
3. **Fix the single dominant error type.** Runs only after Step 2 identifies it. Use a prompt, retrieval, or schema change sized to one session [inference]. Test (stochastic): same metric and sample as Step 1; accept only if the error rate drops below the threshold on the labelled set, then on 25 fresh cases. Cynefin: Complex; cause and effect show up after the probe, so cap the change at one variable.
4. **Add a per-summary feedback button with the taxonomy as options.** Increment: a one-click "wrong" button plus error-type picklist. Test (deterministic): Given an agent views a summary, When they click "wrong" and pick a type, Then the label and summary ID are stored. Cynefin: Clear. This runs in parallel with Steps 2 to 3.

## Follow-up

Conditions that change the plan: if A1 fails, add a logging step before Step 2. If no error type dominates after Step 2, raise the labelling sample before Step 3.
