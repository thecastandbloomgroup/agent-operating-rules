# Headline

The latency rise comes from the pool shrink in release 2026.10.21; roll back the pool config, restore the cache TTL, then review the ORM change.

- `db.pool.acquire` p95 rose from 3 ms to 690 ms while query times stayed flat, so queuing at the pool is the bottleneck [3].
- The pool fell from 50 to 8 per pod while 32 workers can demand 32 concurrent connections, so waiting became systemic [2], [3].
- The cache TTL cut from 300 s to 60 s pushed the miss rate from 12% to 31%, which raised connection demand [2], [3].

# Background

Release 2026.10.21 changed the connection pool, the cache TTL, and the ORM load strategy. After deploy, p95 latency rose from 120 ms to 900 ms. PoolTimeout errors now cause 96% of all errors [3].

# Relevance

PoolTimeouts already produce 503 responses at a 0.40% error rate, up from 0.02% [3]. Each day of delay extends customer-facing failures and possible 5 s stalls on normal requests [1].

# Information

Evidence, ranked by contribution:

1. Pool config. `max_size: 50 to 8`, `acquire_timeout_s: 30 to 5` [2]. Pool acquire p95: 3 ms to 690 ms [3]. "Pool exhausted" warnings: none on 2026-10-20, 1,800 to 2,400 per hour on 2026-10-22 [1]. Active DB connections from this service fell from 31 to 8 [3].
2. Cache TTL. `default_ttl_s: 300 to 60` [2]. Miss rate: 12% to 31% [3]. Misses force DB queries, which hold the scarce connections.
3. ORM change. The new `selectinload` adds an `order_lines` query, but that span runs at 9 ms p50 and 26 ms p95, against 11 ms and 30 ms before [2], [3]. DB CPU barely moved: 38% to 41% peak [3]. This change is not the driver.
4. Load. Peak throughput is unchanged: 410 versus 405 requests per second [3]. The rise is not a traffic effect.

Validate by: read ticket OPS-412 or the DB max_connections setting. If wrong: cap total pool at the stated limit and add worker or query-reuse limits instead.
- A2. Each of the 4 pods enforces its own pool of 8. Why not measured: the material does not state pool scope. Validate by: check the pool client configuration. If wrong: the same fix applies, sized to the shared scope.
- A3. Rollback of db.yaml and cache.yaml alone does not depend on the ORM change. Why not measured: no coupled migration appears in the diff. Validate by: confirm the diff contains no schema change. If wrong: stage the rollback with the migration plan.

Alternative considered: keep the small pool and only restore the cache TTL. This loses because miss rate was already 12% before, and 12% of 410 requests per second still exceeds what an 8-connection pool serves at 20 to 60 ms query times [inference from 3].
