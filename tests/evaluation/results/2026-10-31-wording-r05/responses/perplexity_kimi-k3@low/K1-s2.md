## Headline

The latency regression comes from one change: the pool was cut from 50 to 8 connections while the service runs 32 workers, so requests queue on pool acquisition.

- Traces show pool acquire p95 rose from 3 ms to 690 ms; query times stayed flat [1].
- Logs show pool exhaustion on all 4 pods and PoolTimeout errors, absent before the release [2].
- The ORM and cache changes raised DB load slightly but cannot explain a 7× latency jump.
- Revert the pool to 50, then re-apply the OPS-412 limit with a size that fits 32 workers.

## Background

P95 latency for the orders endpoint rose from 120 ms to 900 ms after release 2026.10.21. That release changed the pool config, the cache TTL, and one ORM query [1], [2], [3].

## Relevance

Customers now see 900 ms responses and 0.40% errors, versus 0.02% before [3]. The cause is in the attached diff, so a config revert restores service in one deployment.

## Information

Evidence, split by the three changes:

1. Pool size 50 to 8, timeout 30 s to 5 s. The service has 4 pods with 8 workers, that is 32 concurrent workers, now capped at 8 connections total [3]. Trace data: db.pool.acquire p95 went from 3 ms to 690 ms, which accounts for most of the 780 ms regression [1]. Active DB connections peaked at 8 in window B, exactly the new cap [1]. Logs show 1,800 to 2,400 pool-exhausted warnings per hour after the release and zero before [2]. Therefore the pool dominates.
2. Cache TTL 300 s to 60 s. Miss rate rose from 12% to 31% [1]. This adds DB queries, and each query now waits up to 690 ms to start. It is a secondary amplifier, not the root cause.
3. ORM selectinload. It replaced N+1 per-line queries with one extra query, and query spans stayed flat (orders p95: 52 to 58 ms; order_lines is a single 26 ms span) [1]. DB CPU rose only 38% to 41% [1]. This change is not a driver.

Assumption log:

- A1. OPS-412 imposes a real per-service DB connection limit. Why not measured: the ticket is not attached. Validate by: read ticket OPS-412. If wrong: keep max_size 50 permanently.
- A2. The database accepts 50 connections from this service. Why not measured: the DB connection limit is not in the material. Validate by: check max_connections on orders-db.internal. If wrong: use a size below the limit that still fits 32 workers, for example 32.

Alternative considered: raise the pool to 32 instead of 50 to honor OPS-412 in one step. It loses because the ticket scope is unverified (A1), and a revert to the last known good config is the fastest tested path back to 120 ms.

## End

1. Revert config/db.yaml to max_size 50 and acquire_timeout_s 30, and deploy. Blocker removed: pool queueing, the dominant cause (largest leverage).
