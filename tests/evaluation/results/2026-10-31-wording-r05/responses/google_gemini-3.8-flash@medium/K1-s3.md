### Headline

Revert the connection pool size reduction and restore the cache time-to-live to eliminate pool contention.
First, pool acquire latency accounts for 687 ms of the 780 ms p95 latency increase [3].
Second, lower cache time-to-live increased cache miss rate from 12% to 31% [3].
Third, the object-relational mapping query changes did not degrade database execution duration [3].

### Background

The API p95 latency increased from 120 ms to 900 ms after the deployment on 2026-10-21 [3].
The release lowered database pool size from 50 to 8, decreased pool acquire timeout from 30 s to 5 s, and lowered cache expiration from 300 s to 60 s [2].
The release also added eager loading for order lines in the orders query [2].

### Relevance

High latency harms customer experience and causes HTTP 503 errors on 0.40% of requests [3].
This issue requires prompt resolution because connection timeouts currently drop valid customer traffic [1].

### Information

First, trace data reveals that connection pool queueing caused the latency increase [3].
The `db.pool.acquire` span p95 rose from 3 ms in Window A to 690 ms in Window B [3].
This change represents 88% of the total 780 ms p95 increase [3].
In contrast, total database query duration remained stable [3].
Orders query p95 changed from 52 ms to 58 ms [3].
Order lines query p95 dropped from 30 ms to 26 ms [3].
Therefore, the eager loading query change in `app/orm/orders.py` did not cause the latency spike [3].

Next, the configuration changes caused the pool exhaustion [2].
The commit for `config/db.yaml` decreased `max_size` per pod from 50 to 8 [2].
Four API pods run eight worker threads each, creating 32 total workers [2].
At peak, active connections across the service dropped from 31 down to 8 [3].
Meanwhile, cache `default_ttl_s` dropped from 300 s to 60 s [2].
Because cached entries expired five times faster, cache miss rate jumped from 12% to 31% [3].
The higher miss rate sent 2.58 times more read traffic to the database [3].
Consequently, pods saturated their eight connections and logged between 1,800 and 2,400 pool exhaustion warnings per hour [1].
Furthermore, lowering `acquire_timeout_s` from 30 s to 5 s caused connection acquire timeouts [2].
Pool timeouts caused 96% of the errors in Window B [3].
Confidence in this root cause is high based on matching metrics across logs, traces, and diffs [judgment].
