### Headline

Database connection pool contention causes 88% of the latency increase [1].
A lower cache time-to-live increased database query traffic by 158% [1], [2].
Simultaneously, a configuration change cut the database pool size per pod from 50 to 8 [2].
Reverting the cache expiration and adjusting pool settings will restore latency to baseline [judgment].

### Background

Release 2026.10.21 altered the object-relational mapping code, the cache configuration, and the database pool settings [2].
After deployment, API p95 latency rose from 120 ms to 900 ms [1].
The user provided application logs, configuration diffs, and distributed traces to identify corrective actions [1], [2], [3].

### Relevance

High latency harms customer experience and causes request timeouts [1].
Furthermore, pool acquisition timeouts now generate HTTP 503 errors on 0.40% of customer order requests [1], [3].

### Information

The trace data indicates that `db.pool.acquire` p95 latency rose from 3 ms to 690 ms [1].
This single span accounts for 687 ms of the 780 ms total p95 latency increase [1].
In contrast, database query execution times remained stable across the two releases [1].
The query span for orders changed from 52 ms to 58 ms at p95 [1].
The query span for order lines dropped from 30 ms to 26 ms at p95 due to eager loading [1], [2].

Two changes combined to create this connection starvation.
First, `default_ttl_s` in `config/cache.yaml` decreased from 300 seconds to 60 seconds [2].
Because cache entries expired faster, the cache miss rate rose from 12% to 31% [1].
This change increased database read attempts by 158% under identical traffic volume [1].

Second, `max_size` in `config/db.yaml` fell from 50 connections to 8 connections per pod [2].
Each of the 4 API pods runs 8 worker threads [2].
When all 8 threads on a pod execute database queries simultaneously, the pool saturates [3].
Logs record between 1,800 and 2,400 pool exhaustion events per hour in the new release [3].
Additionally, `acquire_timeout_s` dropped from 30 seconds to 5 seconds [2].
Therefore, queued workers time out after 5 seconds, causing 96% of observed HTTP 503 errors [1], [3].
