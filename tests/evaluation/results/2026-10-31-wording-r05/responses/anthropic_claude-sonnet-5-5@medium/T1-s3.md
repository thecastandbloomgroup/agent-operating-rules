## Headline

Stop debating style by hand: pick one style in one time-boxed session, then let a tool enforce it.

- The root cause is that people judge style by taste, so every review reopens the argument.
- A formatter that runs in CI (the automated build check) removes style from human review.
- A single decision step with a written rubric ends the debate without a vote.
- A four-week trial measures whether the friction falls.

## Background

The team has no shared SQL format. Reviewers and authors disagree in every review. The request is to fix this as a culture problem.

## Relevance

Each style comment costs review time and creates conflict. The cost repeats with every pull request, so the fix pays back quickly.

## Information

**Evidence**

- SQLFluff is an open-source SQL linter and formatter. It has a `fix` command and supports many SQL dialects (variants of SQL) [1].
- Style disputes persist because no rule exists that all parties accept as neutral. [judgment]
- A tool applies the same rule to every author, so no person acts as the judge. [judgment]
- Cynefin sorts work by how cause and effect relate. It says a people system with unclear causes needs small probes, not a full rollout [2].
- Confidence that a CI formatter cuts format comments: likely (66 to 100%), based on the mechanism above and no team data yet.

**Assumption log**

A1. The team uses one main SQL dialect and has CI. Why not measured: the material does not state it. Validate by: read the repository and CI config. If wrong: replace Step 2 with a pre-commit hook.

A2. One person has the right to settle a tie. Why not measured: the user has not answered. Validate by: ask the team lead in one message. If wrong: the group picks a tie-breaker in Step 1.

A3. Most format comments in reviews are about layout, such as case, indent, and commas. Why not measured: no review data was provided. Validate by: count comments in the last 20 merged pull requests. If wrong: the formatter removes less friction, and Step 4 shows it.

**Alternative considered**

A written style guide with a team vote is the strongest alternative. It loses because people still apply a guide by hand, so the argument returns in each review. [judgment]

## End

I recommend that we take these steps in order:

1. **Choose the style in one 45-minute session.**
   - Blocker removed: no agreed style exists, so no tool can be configured.
   - Kind: evaluative. Cynefin: Complicated, because several good styles exist and analysis picks one.
   - Test, written first: a rubric with four criteria. Match to existing code (30). Tool support for the dialect (30). Diff readability (25). Short config (15). Pass threshold: 70 of 100, with a score for each option backed by a sample query. If no option passes, the tie-breaker from A2 picks the top score.
   - Step 2 MUST NOT start until the style is written down.

2. **Add the formatter to CI with the chosen config.**
   - Blocker removed: style depends on people, not on a rule.
   - Kind: deterministic. Cynefin: Clear, because automated formatting is an established practice.
   - Test, written first:
     - Given a SQL file that breaks the config
     - When the CI check runs
     - Then the check fails and names the rule
   - Step 3 MUST NOT start until this test passes.

3. **Reformat the whole repository in one commit.**
   - Blocker removed: old files would fail the new check.
   - Kind: deterministic. Cynefin: Clear, because the tool does the work and the result is known.
   - Test, written first:
     - Given the reformatted repository
     - When the CI check runs
     - Then it passes, and query results on a sample set are unchanged
   - Add the commit to the blame-ignore list (the file that hides bulk commits from `git blame`).

4. **Run a four-week probe on a new review rule: reviewers do not comment on layout.**
   - Capability added: reviews focus on logic. Start this in parallel with Step 3.
   - Kind: stochastic. Cynefin: Complex, because team response is visible only afterward. Leverage here is a guess.
   - Test, written first:
     - Metric: share of review comments about layout.
     - Baseline: the count from the last 20 merged pull requests (A3).
     - Pass threshold: at most 5%, or half the baseline if that is lower.
     - Sample: 20 pull requests.
   - Budget: two hours of total team time. Stop condition: three pull requests blocked by formatter errors that the config cannot fix.

5. **Hold a 20-minute review of the probe result.**
   - Blocker removed: the team has no data on whether the culture changed.
   - Kind: evaluative. Cynefin: Complicated, because the data supports analysis.
   - Test, written first: a rubric with criteria "metric met" (60) and "no stop condition hit" (40). Pass threshold: 100.
   - If the probe fails, replace Step 4 with a pairing session on the top three disputed rules.
