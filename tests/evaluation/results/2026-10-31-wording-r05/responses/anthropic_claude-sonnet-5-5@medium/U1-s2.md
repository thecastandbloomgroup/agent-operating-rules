## Headline

Measure the failure rate first, then quarantine the worst test, then fix its cause.

- No data on the failures exists yet, so a fix now would be a guess.
- A flaky build is one that passes and fails on the same code, and a rerun log shows the pattern.
- Quarantine of the top offender restores trust in the build within one session.
- A capped probe on the root cause avoids a large rewrite.

## End

I recommend that we take these steps in order:

1. **Measure the failure rate.** Rerun one commit 20 times and save the log of each failed step. This removes the lack of data. Kind: stochastic. Test: the metric is failure rate per job, the baseline is the result itself, the threshold is a complete log for all 20 runs, and the sample size is 20. Domain: Confused, because the cause class is unknown, so this step gathers what the next steps need.

2. **Group the failures by cause.** Label each failure as test, environment, or dependency. Name the top failing test. Step 2 MUST NOT start until Step 1 passes. Kind: evaluative. Rubric: frequency of failure (weight 50%), cost to fix (30%), strength of log evidence (20%). The pass threshold is a weighted score of 3 out of 5 for the chosen cause, with a log line as evidence for each score. Domain: Complicated, because analysis of the logs picks the practice.

3. **Quarantine the top failing test.** Move it to a separate job that does not block the build. This removes the noise that hides real defects. Step 3 MUST NOT start until Step 2 names the test. Kind: deterministic. Test, in Gherkin form [14]:
   - Given a test is listed in quarantine
   - When the main build runs
   - Then the build ignores its result and reports it in the separate job

   Domain: Clear, because quarantine is an established practice.

4. **Run a probe on the root cause.** Fix the cause of the quarantined test, for example by removing a shared state or a fixed wait. Budget: one working session. Stop condition: stop when the budget ends or when 3 fixes fail. Step 4 MUST NOT start until Step 2 is done, but it runs in parallel with Step 3. Kind: stochastic. Test: the metric is failures in repeated runs, the baseline is the rate from Step 1, the threshold is zero failures, and the sample size is 50 runs. Domain: Complex [18], because the cause shows only after the change. The leverage of this step is a guess.

5. **Return the test to the main build.** Do this only after Step 4 meets its threshold. Kind: deterministic. Test: Given the test is back in the main build, When the build runs 50 times, Then every run passes. Domain: Clear, because the move reverses Step 3.

If A3 is false, replace Step 3 and Step 4 with a pinned runner image and a pinned dependency list.
