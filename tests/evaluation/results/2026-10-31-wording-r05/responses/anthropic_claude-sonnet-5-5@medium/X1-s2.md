## Headline

Measure the summariser first, then change it, because the team cannot improve what it cannot count.

- No data exists today, so capture agent feedback and logs first.
- A labelled sample shows which error types occur.
- A fixed test set gives every later change a number.
- Prompt changes reach agents only after they beat the baseline on that set.

## Background

The team added a summariser to its support tool. It uses a large language model (LLM). Agents say it is "sometimes wrong". No metric exists. The request is to make it better.

## Relevance

A wrong summary costs agent time. It can also lead to a wrong reply to a customer. Without a baseline, no change can be shown to help.

## Information

Evidence:

- Agents report "sometimes wrong" (per the request). One source group, no detail on the error type, no dissent. Confidence is low on cause and high that a problem exists.
- Automatic summary metrics agree only weakly with human judgment, so human labels are the baseline. [1]
- Abstractive summaries often contain content that the source text does not support. [2]
- Most errors are likely invented or wrong facts, not style [judgment].

Assumption log:

A1. The system stores or can log each ticket text and its summary. Why not measured: the material does not state it. Validate by: query the database for stored pairs. If wrong: Step 1 must add logging before any feedback is useful.

A2. Most "wrong" reports are about facts (invented or missing), not tone. Why not measured: no metrics exist. Validate by: the Step 2 labels. If wrong: change the rubric weights in Step 2.

A3. The team can edit the prompt and choose the model version. Why not measured: the material does not state it. Validate by: ask the engineer who owns the integration. If wrong: replace Step 4 with a vendor request.

Alternative considered: switch to a larger model now. It loses because there is no baseline to show a gain, the cause of the errors is unknown, and cost rises [judgment].

## End

I recommend that we take these five steps, in this order:

1. **Log and collect feedback.** Increment: add a "wrong summary" button with reason codes. Log ticket text, summary, model version, and prompt version. Blocker removed: no data. Kind: deterministic. Domain: Clear, because the practice is well known.
   - Test: Given an agent views a summary, When the agent clicks "wrong" and picks a reason, Then one record stores the ticket, summary, versions, and reason.

2. **Label 100 recent summaries.** Increment: two reviewers score the summaries in one session. Blocker removed: unknown error types. Kind: evaluative. Domain: Complicated, because analysis of the labels picks the fix.
   - Rubric criteria and weights: faithfulness 40, coverage of issue and status 30, next action stated 15, length of 80 words or fewer 15.
   - Evidence: compare each claim in the summary with the ticket text.
   - Pass threshold: score of 80 or more and full marks on faithfulness.
   - Reviewers both score 20 of the 100. Agreement must reach 80% before the rest are scored.
   - The pass rate is the baseline.

3. **Build an automatic check and a golden set.** Increment: keep the 100 labelled tickets as a fixed test set. Add a check that every order number, amount, and date in a summary appears in its ticket. Blocker removed: no repeatable test. Kind: deterministic. Domain: Clear, because the check is a fixed rule.
   - Test: Given a summary with an amount absent from the ticket, When the check runs, Then it fails the summary and names the amount.
   - Step 3 MUST NOT start until Step 2 is complete.

4. **Probe prompt changes.** Increment: test up to three prompt variants on the golden set. Blocker removed: unknown fix. Kind: stochastic. Domain: Complex, because the effect of a prompt is visible only after a run. Leverage is a guess.
   - Metric: share of summaries that fail faithfulness.
   - Baseline: the Step 2 result.
   - Pass threshold: a 30% relative cut.
   - Sample: 100 tickets, 3 runs each.
   - Budget: 2 working days. Stop when the threshold is met or the budget ends.
   - Step 4 MUST NOT start until the test in Step 3 passes.

5. **Run a limited rollout.** Increment: enable the best variant for 10% of agents for two weeks. Blocker removed: no field evidence. Kind: stochastic. Domain: Complex, because agent behavior is unpredictable.
   - Metric: "wrong" flags per 100 summaries.
   - Baseline: the Step 1 data.
   - Pass threshold: 20% lower than baseline.
   - Sample: 500 summaries.
   - Stop condition: flags rise 10% above baseline.
   - Step 5 MUST NOT start until Step 4 meets its threshold.
   - If A2 is false, change the Step 2 weights, then repeat Step 4 against the new rubric.
