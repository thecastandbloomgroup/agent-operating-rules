## Headline

Replace the style debate with a rule: one formatter, one config, one enforced check, and a trial of a "no style comments" review norm.

- A formatter removes the choice, so no person has to win the argument.
- A CI check (an automated job that runs on each pull request) enforces the rule without reviewer effort.
- A short trial with a measure shows whether the friction falls.
- A named tie-break owner prevents the choice of formatter from becoming a new debate.

## Background

The team has no shared SQL format. Every code review contains style disputes. The request is to fix the cause, which the requester calls a culture problem.

## Relevance

Each style comment costs reviewer time and adds tension. The cost recurs on every pull request until a rule replaces opinion.

## Information

Evidence:

- Black, a Python formatter, states that its fixed style makes reviews faster and removes style discussion from them. [judgment] This transfers to SQL, because the mechanism is the same: a tool decides, not a person. Source:
  - Black documentation, "The Black Code Style" [1]

- Prettier, a formatter for web code, states the same aim: end debates over style. Source:
  - Prettier documentation, "Rationale" [2]

- SQLFluff is a SQL linter and formatter with a config file. It supports many SQL dialects. Source:
  - SQLFluff documentation [3]

- Two independent tool projects (Black, Prettier) use the same approach. Confidence: medium, because both sources are vendor documentation and neither measures SQL teams. Both are secondary sources.

A2. The SQL lives in version-controlled files in one dialect. Why not measured: the material does not state it. Validate by: list the file extensions in the repository. If wrong: pick a formatter per dialect in Step 1.

Alternative considered: a team workshop to write a style guide by consensus. It loses because a written guide still needs people to enforce it in review, so the friction remains. [judgment]

## End

I recommend that we take these four actions, in this order:

1. **Choose the formatter and config (Step 1).**
   - Increment: score SQLFluff, sqlfmt, and one other candidate in a Pugh matrix [4]. Use a one-hour meeting. The team lead breaks ties.
   - Blocker removed: the open choice that fuels the dispute.
   - Kind: evaluative. Rubric first. Criteria and weights: dialect support 40%, config rules 30%, CI speed 20%, setup effort 10%. Pass threshold: the top tool scores at least 70 of 100 and beats the baseline of "no tool". Evidence: run each tool on 10 real files.
   - Cynefin: Complicated. Analysis of the tools picks among several good options [5].

2. **Format the repository once (Step 2).**
   - Increment: commit the config. Run the formatter on all SQL files in one commit. List that commit in `.git-blame-ignore-revs`.
   - Blocker removed: old files that would fail the check.
   - Kind: deterministic. Test first:
     ```gherkin
     Feature: Repository SQL format
       Scenario: All files conform
         Given the committed formatter config
         When the formatter runs in check mode on all SQL files
         Then it reports zero violations
     ```
   - Cynefin: Clear. The tool applies a known best practice.
   - Step 2 MUST NOT start until Step 1 names a tool.

3. **Enforce the format in CI (Step 3).**
   - Increment: add one CI job that runs the formatter check on each pull request.
   - Blocker removed: reviewers who enforce style by hand.
   - Kind: deterministic. Test first:
     ```gherkin
     Feature: CI format check
       Scenario: Unformatted SQL is rejected
         Given a pull request with one badly formatted SQL file
         When the CI job runs
         Then the job fails and names the file
     ```
   - Cynefin: Clear. CI checks are a standard practice.
   - Step 3 MUST NOT start until the test in Step 2 passes.

4. **Trial the "no style comments" norm for two weeks (Step 4).**
   - Increment: count style comments in the last 30 reviews for the baseline. Then agree that reviewers do not comment on format, because CI does.
   - Blocker removed: the habit of arguing style in review.
   - Kind: stochastic. Test first. Metric: share of review comments about style. Baseline: the count from the 30 past reviews. Pass threshold: at most half the baseline share. Sample size: 20 reviews in the trial. Stop condition: end the trial early if review time per pull request rises. Budget: two weeks.
   - Cynefin: Complex. Team behavior shows its response only after the change, so leverage is a guess.
   - Run Step 4 in parallel with Steps 2 and 3. Start the baseline count now.

Condition that changes this: if A1 is false, replace Step 3 with a pre-commit hook. If the trial fails the threshold, interview reviewers to find the remaining cause.
