## Headline

Split this into two tracks: migrate to JWT with no change to the sign-up UX, and test conversion changes separately.

- The two goals have different test types: the migration is deterministic, and the conversion work is stochastic.
- A combined release hides the cause of any conversion change, because an auth change can also move sign-up numbers.
- JWT removes instant session revocation, so the design must replace it.
- The baseline conversion rate does not exist yet, so measure it first.

## Background

The request has two parts: replace server-side sessions with JSON Web Tokens (JWT, signed tokens that carry user claims), and raise sign-up conversion. The conversation contains no code, metrics, or architecture notes. This answer therefore rests on the assumptions in the log.

## Relevance

A bundled change gives no clean result. If conversion drops after release, the team cannot tell whether the cause is the token change or the form change.

## Information

**Evidence**

- A JWT is a signed token that the server verifies without a session lookup [1].

- Safe use needs a fixed list of allowed signing algorithms and short expiry [2].

- A stateless token stays valid until it expires. Instant logout therefore needs server state, such as a deny list or refresh token rotation [inference].

- A 20% baseline and a goal of +2 points need about 6,400 users per arm, at 80% power and a 5% significance level. This comes from the two-proportion formula n = 16·p(1-p)/d² [judgment].

**Assumption log**

A1. The service has browser clients and a server-side session store. Why not measured: the material does not state it. Validate by: read the auth config. If wrong: replace Step 3 with a design for the actual client types.

A2. Sign-up runs through the same auth service. Why not measured: no tool can reach the code. Validate by: trace one sign-up request. If wrong: the two tracks are independent, so skip the stratification in Step 4.

A3. Baseline sign-up completion is 20% and traffic gives 6,400 users per arm within the budget. Why not measured: the material has no analytics. Validate by: run Step 1 for one week. If wrong: recompute the sample size and the budget in Step 4.

A4. "Conversion" means completed sign-ups divided by started sign-ups. Why not measured: the user has not answered. Validate by: ask the product owner. If wrong: change the metric in Step 1 and Step 4.

**Alternative considered**

Keep sessions and fix only conversion. This loses because the request names the migration explicitly. It would also remove the revocation risk, so keep it as the fallback if Step 2 fails.

## End

I recommend that we do these four steps in order:

1. **Instrument the sign-up funnel.**
   - Increment: add events for "started" and "completed" sign-up, then run for one week.
   - Removes the blocker: no baseline exists.
   - Kind: deterministic.
   - Test: Given a user opens the sign-up form, When the user submits valid data, Then one "started" and one "completed" event appear with the same user key.
   - Domain: Clear, because event tracking has a known best practice.

2. **Write the JWT design and score it.**
   - Increment: one page that sets token lifetime, refresh rotation, revocation, and signing algorithm [2].
   - Removes the blocker: the revocation gap.
   - Kind: evaluative.
   - Rubric, scored against the draft: revocation delay (weight 40%), security per [2] (30%), client change effort (20%), latency (10%). The pass threshold is 80 of 100, and each criterion needs a test result or a cited rule as evidence.
   - Domain: Complicated, because expert analysis picks among known practices.
   - Step 3 MUST NOT start until the design scores 80 or more.

3. **Run both auth paths behind a flag.**
   - Increment: the service accepts a session cookie or a JWT for one endpoint, with no sign-up UX change.
   - Adds the capability: a reversible rollout.
   - Kind: deterministic.
   - Test: Given a user holds a valid JWT, When the user calls the endpoint, Then the service returns 200. Given the JWT is expired or revoked, Then the service returns 401.
   - Write the test, make it pass, then refactor.
   - Domain: Complicated, because the design in Step 2 fixes the cause and effect.

4. **Run one capped A/B probe on the sign-up form.**
   - Increment: change one form element, for example remove one optional field.
   - Kind: stochastic.
   - Metric: completion rate from Step 1.
   - Baseline: the Step 1 result.
   - Threshold: +2 points.
   - Sample size: 6,400 per arm.
   - Stop condition: stop early if the completion rate falls 3 points below baseline.
   - Budget: two weeks.
   - Run both arms on the session path, so the auth change does not distort the result.
   - Accept the change only when the threshold is met at that sample size.
   - Domain: Complex, because user behavior shows cause and effect only afterward. Its leverage is a guess.
   - Run Step 4 in parallel with Steps 2 and 3, but it MUST NOT start until Step 1 gives the baseline.

If A3 is false, replace the 6,400 figure with the recomputed size, and cut the probe if it exceeds the budget.
