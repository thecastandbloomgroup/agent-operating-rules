## Headline

Measure the summariser first, then change it, because "sometimes wrong" gives no target to fix.

- No error rate exists today, so no change can be proven to help.
- The error types are unknown, so the right fix (prompt, input, or model) is unknown.
- A feedback button and a labelled test set give the team a baseline within days.
- Small prompt probes, each checked against the baseline, then improve quality at low cost.

## Background

The team added a summariser based on a large language model (LLM) to a support tool. Agents report that it is "sometimes wrong" [1]. The team has no metrics and asks for a better summariser.

## Relevance

Agents who distrust a summary reread the full ticket, so the tool adds cost and no speed. Wrong summaries can also cause wrong replies to customers. [judgment]

## Information

**Evidence**

- One source reports the problem: the request itself, which gives no rate, no error type, and no count of agents [1].
- Without a rate, the baseline is unknown. Every claim below that depends on a rate is marked [judgment].
- Common error types in LLM summaries are invented facts, missed key facts, and wrong emphasis. [judgment]
- The domain is Confused because the error types are not known (Section 6.5 rule). The first action therefore gathers data [18].

**Assumption log**

A1. The summariser summarises support tickets or chats. Why not measured: the material does not state it. Validate by: ask the tool owner. If wrong: change the rubric terms in Action 1.

A2. The team can read stored inputs and summaries. Why not measured: no tool can reach the system. Validate by: export 10 rows. If wrong: Action 1 starts with logging.

A3. Agents can label 100 summaries within two working days. Why not measured: the user has not answered. Validate by: ask two agents for a time estimate. If wrong: cut the sample to 50 and widen the error range.

A4. The team can edit the prompt and settings. Why not measured: the material does not state it. Validate by: open the config. If wrong: Action 4 becomes a vendor request.

**Alternative considered**

Switch to a larger model or fine-tune now. It loses because no baseline exists to show a gain, and the cost is higher than a prompt change. [judgment]

## End

I recommend that we take these four actions in this order:

1. **Label a sample (Confused, because the error types are unknown).** Evaluative.
   - Increment: pull 100 random summaries with their source tickets. Two agents label each one.
   - Blocker removed: no error rate and no error types.
   - Test, written first: a rubric with four criteria.
     - Factual accuracy: weight 40%.
     - Coverage of key facts: weight 30%.
     - Next-step correctness: weight 20%.
     - Brevity: weight 10%.
   - Each criterion is scored 0 to 2 against the source ticket text. A summary passes at 80% of the weighted total with no factual score of 0.
   - Output: the pass rate and a count of errors per type.
   - Step 2 MUST NOT start its tuning until this output exists.

2. **Add a feedback button (Clear, because the pattern is standard).** Deterministic.
   - Increment: add "wrong summary" and "good summary" buttons, with a reason list built from the Action 1 types.
   - Blocker removed: no ongoing signal from agents.
   - Test, written first:
     - Given an agent views a summary
     - When the agent presses "wrong summary" and picks a reason
     - Then the system stores the ticket ID, summary ID, reason, and time.
   - Run it in parallel with Action 1. The reason list waits for Action 1 output.

3. **Freeze a golden set (Complicated, because expert analysis picks the cases).** Evaluative.
   - A golden set is a fixed group of labelled cases used to compare versions.
   - Increment: keep the 100 labelled tickets from Action 1 and add 20 hard cases from the button reports.
   - Blocker removed: no repeatable way to compare versions.
   - Test, written first: the set passes review if each error type has at least 5 cases and two labellers agree on at least 80% of them.
   - Action 4 MUST NOT start until this test passes.

4. **Probe one prompt change (Complex, because the effect is visible only after a trial).** Stochastic.
   - Increment: change the prompt to require that every claim comes from the ticket text and that missing facts are marked "not stated". The budget is one working session.
   - Blocker removed: the most common error type from Action 1.
   - Test, written first:
     - Metric: pass rate on the golden set.
     - Baseline: the Action 1 pass rate.
     - Threshold: a gain of at least 10 percentage points, with no drop in coverage. [judgment]
     - Sample size: the 120 golden cases, run three times each.
   - Stop condition: if the gain is below the threshold, revert and try one other change. Stop after three probes.
   - Leverage of this probe is a guess.

If A2 is false, add a logging step before Action 1. If Action 1 shows a pass rate above 95%, replace Action 4 with agent training on summary limits.
