## Headline

Measure the summariser first, then change it. Without a baseline, no change can prove it helps.

- No one knows how often or why the summaries fail, so the first step is to label a sample.
- Agents need a one-click way to flag bad summaries, so the data keeps coming.
- A fixed test set turns each future change into a pass or fail result.
- A small, capped trial of prompt changes then tests whether quality improves.

## Background

The support tool has a summariser built on a large language model (LLM), a model that writes text from text. Agents say it is "sometimes wrong". The team has no metrics, and the request is to improve it.

## Relevance

An agent who trusts a wrong summary may give a customer wrong information. An agent who distrusts the summary stops using it. Both outcomes remove the value of the feature.

## Information

Evidence:

- Agent reports are the only signal today. They come from the request, and they have no count, no examples, and no error types [no source].
- LLM output varies from run to run, so one test run proves little. A sample is required [inference].
- Likely (66 to 100%) that the main errors are missing facts and invented facts [judgment]. This must be checked in Step 1.
- The Cynefin framework separates work by how cause and effect relate [1]. Here the cause of the errors is unknown, so the first action is to gather data and classify.
- The Gherkin format (Given, When, Then) fixes the test for deterministic work [2].

Assumption log:

A1. Agents can open the ticket text beside the summary. Why not measured: the material does not state it. Validate by: ask one agent to compare one pair. If wrong: Step 1 needs an export of ticket text first.

A2. The tool can store each summary with its source ticket. Why not measured: no tool can reach the system design. Validate by: check the database for a summary field. If wrong: add logging before Step 2.

A3. Ten agent-hours are available this week for labeling. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: cut the sample in Step 1 from 100 to 50 and lower confidence.

Alternative considered: switch to a larger model now. It loses because no baseline exists, so no one could show that the new model is better or worth its cost [judgment].

## End

I recommend that we take these steps in order:

1. **Label a baseline sample.** Increment: two agents score 100 random recent summaries against their tickets in one session. Blocker removed: no one knows the error rate or error types. Kind: evaluative. Test, written first: a rubric with four criteria. Accuracy has weight 40. Completeness of issue, steps taken, and status has weight 30. Correct next step has weight 15. Brevity has weight 15. A summary passes at 80 of 100 or more. Each score needs a quoted line from the ticket as evidence. Output: the pass rate and a count per error type. Cynefin: Confused, because the cause of the errors is unknown, so this step gathers data to classify.

2. **Add a "wrong summary" button with a reason list.** Increment: one button and four reasons (missing fact, invented fact, wrong status, other), stored with the ticket ID. Blocker removed: no ongoing signal. Kind: deterministic. Test, written first: Given an agent views a summary, When the agent clicks "wrong summary" and picks a reason, Then the system stores the ticket ID, summary text, reason, and time. Cynefin: Clear, because a known pattern exists for feedback buttons. Step 2 MUST NOT start until Step 1 shows which reasons to list.

3. **Build a fixed test set.** Increment: copy the 100 labeled tickets from Step 1 into a test set, with a script that scores any summariser version. Blocker removed: no repeatable comparison. Kind: deterministic. Test, written first: Given the labeled test set, When the script runs on the current summariser, Then it reports a pass rate equal to the Step 1 result within 5 points. Cynefin: Complicated, because expertise picks the scoring method. Step 3 MUST NOT start until Step 1 is complete.

4. **Run one capped prompt trial.** Increment: change the prompt to require only facts found in the ticket, and rerun the test set. Blocker removed: no evidence on what improves quality. Kind: stochastic. Test, written first: the metric is the pass rate from Step 3. The baseline is the Step 1 pass rate. The threshold is the baseline plus 10 points. The sample is 100 tickets, run three times. Accept only if all three runs meet the threshold. Cynefin: Complex, because the effect of a prompt change shows only after the run. Budget: one working day. Stop condition: two failed variants. Leverage is a guess. This step runs in parallel with Steps 2 and 3, but its result counts only after Step 3 passes.

If A1 is false, replace Step 1 with a ticket export task. If Step 1 shows a pass rate of 95% or more, drop Step 4 and keep Steps 2 and 3 as monitoring.
