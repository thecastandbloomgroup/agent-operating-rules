## Headline

Migrate in a staged, reversible way, and measure sign-up conversion before you change it.

- The migration and the conversion work are two separate jobs, so split them and test each one on its own.
- Conversion has no baseline in the material, so measure it first.
- Run the sign-up experiment and the auth cutover in different time windows, so one does not distort the other.
- A JWT cannot be revoked before it expires unless the server keeps state, so design revocation before you build.

## Background

The request has two goals: replace server sessions with JSON Web Tokens (JWT), and raise sign-up conversion. The material gives no code, traffic data, or current conversion rate. Sign-up creates the first login, so a change to auth can change the sign-up flow.

## Relevance

A bad cutover logs users out or lets revoked users stay in. A change to the sign-up flow during the cutover makes the conversion result impossible to read.

## Information

**Evidence**

- A JWT is a signed set of claims, and the `exp` claim sets its expiry time [1].
- Best-practice guidance says to validate the signing algorithm and to check issuer, audience, and expiry on every token [2].
- A signed token stays valid until `exp` unless the server checks a deny list or a stored refresh token. [inference]
- The sample size below comes from the standard two-proportion formula (alpha 0.05, power 0.8). [inference]
- Baseline 20%, target 22%, about 6,500 sign-up starts per arm. [inference]

**Assumption log**

A1. One web service with first-party clients only. Why not measured: the material does not state it. Validate by: list the token consumers. If wrong: add an audience and key plan per client in Step 2.

A2. The sign-up flow has no funnel events today. Why not measured: no tool can reach the code. Validate by: search the codebase for sign-up events. If wrong: skip the instrumentation part of Step 1.

A3. Current sign-up completion is 20%. Why not measured: the material does not state it. Validate by: run Step 1. If wrong: recompute the sample size.

A4. Traffic gives at least 13,000 sign-up starts in two weeks. Why not measured: the material does not state it. Validate by: count last month's starts. If wrong: lengthen the window or pick a larger change.

**Alternative considered**

Keep sessions and fix conversion only. It loses because the request names the migration. [judgment]

A second option is one long-lived JWT with no server state. It loses because it cannot revoke access. [inference]

## End

I recommend that we:

1. **Measure the sign-up funnel baseline.**
   - Increment: add events for start, submit, and success. Report 7 days of data.
   - Blocker removed: no baseline exists, so no conversion change can be judged (A2, A3).
   - Test (deterministic), Gherkin [3]: Given a visitor opens sign-up, When the visitor submits a valid form, Then one "start" and one "success" event are stored.
   - Domain: Clear, because the work is plain event counting [4].

2. **Choose the token design.**
   - Increment: score two designs in one session. Design A is a short-lived access JWT plus a rotating refresh token stored on the server. Design B is a JWT with a deny list.
   - Blocker removed: revocation and logout rules are undefined.
   - Test (evaluative): a Pugh matrix [5] with baseline "current sessions". Criteria and weights: revocation speed 30, security checks from [2] 30, rollback ease 25, latency 15. Pass threshold: a weighted score above the baseline. Evidence: a short prototype and the checklist in [2].
   - Domain: Complicated, because expert analysis picks among known practices.
   - Step 3 MUST NOT start until Step 2 passes.

3. **Build dual-mode auth behind a flag.**
   - Increment: the service accepts a session or a JWT, and issues JWTs only for the 5% flagged group.
   - Blocker removed: no safe path exists from sessions to JWT.
   - Test (deterministic), Gherkin: Given a user holds a revoked refresh token, When the user asks for a new access token, Then the service returns 401. Add one case for an expired token and one for a wrong signing algorithm.
   - Domain: Complicated, because the design from Step 2 sets known behavior.
   - Raise the flag to 100% only after the error rate stays at or below the session baseline for 7 days. Remove the session store after that.

4. **Run one sign-up probe.**
   - Increment: test one change, for example remove one form field. Do not combine changes.
   - Capability added: evidence on what moves conversion.
   - Test (stochastic): metric is sign-up completion. Baseline is the Step 1 value, assumed 20%. Pass threshold: at least +2 points. Sample: 6,500 starts per arm. Stop condition: a drop of 3 points or more, or a two-week budget. Accept only at the full sample.
   - Domain: Complex, because user response shows only after the change. The leverage of this probe is a guess.
   - Step 4 MUST NOT start until Step 1 passes. Run it in parallel with Steps 2 and 3. Do not raise the flag in Step 3 during the probe window.

If A4 is false, replace Step 4 with a usability review of five sign-up sessions.
