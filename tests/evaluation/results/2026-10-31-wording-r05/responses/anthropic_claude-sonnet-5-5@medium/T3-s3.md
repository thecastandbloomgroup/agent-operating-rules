## Headline

Split the request into two tracks: a tested auth migration, and a measured sign-up experiment that starts only after a baseline exists.

- The migration is deterministic work, so a written test decides when it is done.
- Conversion is stochastic work, so an experiment with a sample size decides what works.
- The two tracks share users, so the experiment must not overlap the auth cutover.
- No funnel data was provided, so the first step is to measure it.

## Background

The request has two goals. First, replace server-side sessions with JWT (JSON Web Token, a signed token that carries user claims) [1]. Second, raise sign-up conversion (the share of visitors who finish sign-up). The material includes no code, no funnel data, and no stack description.

## Relevance

Both goals change the sign-up and login path. A change to both at once makes any conversion shift impossible to attribute. [judgment]

## Information

**Evidence**

- A JWT is verified without a server lookup, so revoking one before expiry needs extra state [1]. This is the main cost of the migration.
- The JWT best-practice document sets rules for algorithm choice, validation, and short lifetimes [2].
- Conversion work is Complex in the Cynefin sense: cause and effect show only after a trial [3]. This is the basis for a capped probe.
- Sample size for a baseline of 10% and a target of 12% (two-sided alpha 0.05, power 80%) is about 3,840 visitors per arm. This is my calculation with the standard two-proportion formula. [inference]
- Token lifetimes of 15 minutes for access and 7 days for refresh are common defaults. [judgment]

**Assumption log**

A1. The service uses a server-side session store and a web client. Why not measured: the material does not state it. Validate by: read the auth module config. If wrong: Step 3 changes to fit the real client type.

A2. Sign-up is an email and password form. Why not measured: the material does not state it. Validate by: open the sign-up page. If wrong: the Step 4 probe changes.

A3. Baseline conversion is 10%. Why not measured: no tool can reach the analytics data. Validate by: Step 1. If wrong: Step 4 sample size changes.

A4. No rule forces a token storage location. Why not measured: the user has not answered. Validate by: ask the security owner. If wrong: Step 2 criteria change.

**Alternative considered**

Keep sessions and work only on conversion. Sessions revoke instantly and need less new code. This loses because the user asked for the migration, which has precedence. [judgment] Step 2 keeps a server-side refresh record to recover instant revocation.

## End

I recommend that we take these steps in order:

1. **Instrument the sign-up funnel and record the baseline.**
   - Increment: add events for form view, form start, and submit success, then collect one week of data.
   - Blocker removed: no baseline exists, so no conversion claim can be tested.
   - Kind: deterministic. Domain: Confused, because the drop-off point is unknown.
   - Test:
     ```gherkin
     Given a visitor opens the sign-up page
     When the visitor submits a valid form
     Then the events form_view, form_start, and signup_success are stored once each
     ```

2. **Write the auth design note and score it.**
   - Increment: one page that sets token lifetimes, storage, signing algorithm, and the revocation method.
   - Blocker removed: unsafe token choices are costly to undo after release.
   - Kind: evaluative. Domain: Complicated, because experts can analyze the options.
   - Rubric (pass at 80 of 100, each criterion needs a cited rule or a written test case):

     | Criterion | Weight | Evidence |
     |---|---|---|
     | Revocation works within 1 minute | 30 | Test case |
     | Meets validation rules [2] | 30 | Checklist |
     | Lifetimes are short | 20 | Config value |
     | Rollback path exists | 20 | Written steps |

   - Step 3 MUST NOT start until the score reaches 80.

3. **Build JWT login behind a feature flag, with sessions still active.**
   - Increment: the login endpoint issues and verifies an access token and a refresh token for flagged users.
   - Capability added: a reversible path to JWT.
   - Kind: deterministic. Domain: Complicated, because known good practices exist [2].
   - Test:
     ```gherkin
     Given the jwt flag is on for a user
     When the user logs in and later calls a protected route with the access token
     Then the route returns 200
     And a revoked refresh token returns 401 within 1 minute
     ```
   - Write the test first. Then make it pass. Then refactor.

4. **Run one sign-up probe, capped at three weeks.**
   - Increment: remove one optional field from the form for half of the visitors.
   - Capability added: evidence of which change moves conversion. The leverage of this probe is a guess.
   - Kind: stochastic. Domain: Complex, because the effect shows only after the trial.
   - Acceptance test, written first:
     - Metric: sign-up completion rate.
     - Baseline: the Step 1 value, assumed 10% in A3.
     - Pass: at least 12%.
     - Sample: about 3,840 visitors per arm.
   - Stop early if completion drops 2 points below baseline in either arm.
   - Step 4 MUST NOT start until Step 1 has a baseline. It MUST NOT run during the Step 3 rollout to users, so that the two changes do not mix.
   - Run the probe in parallel with Steps 2 and 3 until the rollout begins.

If A3 is false, replace the sample size in Step 4 with a new calculation from the measured baseline. If A4 is false, add the mandated storage rule as a criterion in Step 2.
