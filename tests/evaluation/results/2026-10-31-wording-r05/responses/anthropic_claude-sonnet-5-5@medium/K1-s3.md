## Headline

Raise the database connection pool back toward its old size, because the pool limit of 8 causes most of the latency rise.

- The wait for a pool connection is 690 ms of the 900 ms p95 (95th percentile latency), so the pool is the main cause.
- Query time did not change, so the database and the ORM change are not the cause.
- The shorter cache lifetime adds load, so it is a smaller second cause.

## Background

Release 2026.10.21 cut the pool size per pod from 50 to 8 and the acquire timeout from 30 s to 5 s. It also cut the cache lifetime (TTL) from 300 s to 60 s and added `selectinload` to the orders query. The p95 latency of `GET /customers/{id}/orders` rose from 120 ms to 900 ms. The error rate rose from 0.02% to 0.40%.

## Relevance

Each pool timeout returns a 503 error to a customer. The error rate is 20 times higher than before. The release note says the change follows ticket OPS-412 (a database connection limit), so a plain rollback may break that limit.
