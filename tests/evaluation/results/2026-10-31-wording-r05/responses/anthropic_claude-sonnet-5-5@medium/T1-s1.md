## Headline

Remove style from human review: pick one format once, let a tool enforce it, and measure the result.

- **Decision:** The team needs one choice made by a fixed rule, not by repeated debate.
- **Enforcement:** A formatter and a CI check (an automated gate on each pull request) end style comments in review.
- **Proof:** A baseline count and a trial show whether friction falls.

## Background

The team has no shared SQL format. Each review repeats the same style argument. The request is to fix the cause, not the symptoms.

## Relevance

Each style comment costs reviewer time and delays merges. It also hides review comments about logic errors. Tool-enforced format removes the argument without a long culture program. [judgment]

## End

I recommend that we take these steps in order:

1. **Count style comments in the last 30 merged pull requests.**
   - Increment: one count, about 30 minutes.
   - Blocker removed: no baseline, so no proof of progress.
   - Kind: deterministic. Cynefin: Clear, because counting has one known method.
   - Test: Given the last 30 merged pull requests, When we tag each comment as style or other, Then the report shows style comments per pull request.
2. **Hold one 45-minute session to choose the format.**
   - Increment: one session with a written decision.
   - Blocker removed: no agreed format and no tie-break rule.
   - Kind: evaluative. Cynefin: Complicated, because the options are known and scoring picks one.
   - Options: A, SQLFluff defaults. B, another formatter with defaults. C, a written guide only.
   - Rubric, with the pass threshold at 70 of 100 points:

     | Criterion | Weight | Evidence |
     |---|---|---|
     | Tool enforces it | 40 | Demo on 3 real files |
     | Diffs stay readable | 30 | Diff of one past pull request |
     | Few overrides | 20 | Count of config lines |
     | Dialect support | 10 | Tool docs |

   - Rule: the tech lead breaks a tie. The team accepts the tool defaults except for at most five overrides.
   - Step 2 MUST NOT start until Step 1 gives the baseline.
3. **Add the chosen config and format all SQL files in one commit.**
   - Increment: one commit with config and formatted files.
   - Blocker removed: old files carry the old styles.
   - Kind: deterministic. Cynefin: Clear, because the tool applies a known procedure.
   - Test: Given the repo with the agreed config, When we run `sqlfluff fix` and then `sqlfluff lint`, Then lint reports zero violations and all data model tests pass.
   - Step 3 MUST NOT start until Step 2 records the decision.
4. **Add a CI check that fails on unformatted SQL.**
   - Increment: one CI job.
   - Blocker removed: no gate, so style drifts back.
   - Kind: deterministic. Cynefin: Clear, because CI checks are a standard practice.
   - Test: Given a pull request with an unformatted SQL file, When CI runs, Then the check fails and names the file.
   - Step 4 MUST NOT start until the test in Step 3 passes.
5. **Run a two-week trial and compare with the baseline.**
   - Increment: one probe over the next 20 pull requests.
   - Capability added: evidence on whether the culture problem is gone.
   - Kind: stochastic. Cynefin: Complex, because team behavior shows its effect only afterward. Leverage is a guess.
   - Test: Given the Step 1 baseline, When 20 pull requests merge, Then style comments per pull request fall by at least 80% [judgment].
   - Stop condition: after 10 pull requests, if the fall is under 50%, hold a retro on the rules.
   - Budget: two weeks. Step 5 runs in parallel with Steps 3 and 4 once Step 2 ends. It uses the pull requests that merge after Step 4.
