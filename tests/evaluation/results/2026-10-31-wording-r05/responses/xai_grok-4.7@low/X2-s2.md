Headline

Make each retrospective deliver one owned action, then check it next time.

- One action with an owner and a date turns talk into a commitment.
- A check at the next meeting shows whether the action was done.
- Reserved time stops new work from crowding out the action.
- A new format does not replace an owner, a date, or a check.

Background

A retrospective is a meeting where the team inspects recent work and picks a change. The team still holds these meetings, and people attend, but the way of work does not shift. The request asks what to do so the meeting produces a change.

Relevance

An unchanged meeting leaves the same blockers in the next cycle. Therefore the next cycle repeats the last delay.

Information

This section covers evidence, assumptions, and the alternative.

The Scrum Guide says the team addresses the most useful improvements as soon as possible. Those improvements may enter the Sprint Backlog, the work list for the next short cycle.
[1]

In the same way, Derby and Larsen describe five phases in the meeting. The phase "decide what to do" is the point where the team picks a change. A meeting that ends at insight does not finish that phase.
[2]

The request gives no count of actions that reached done. Therefore the follow-through gap is not measured yet.
[judgment]

The failure class is about as likely as not to be follow-through. Basis: the request states attendance and no action results.

A1. The team can change some of its own process. Why not measured: the material does not state it. Validate by: ask if the team may change a working agreement without outside approval. If wrong: escalate the constraint before the meeting design changes.

A2. The gap is follow-through, not a lack of ideas. Why not measured: the material does not include the action log. Validate by: score the last three notes for owner, date, and done state. If wrong: inspect whether finished actions missed the real constraint.

A3. People can name a problem in the room. Why not measured: the material does not state it. Validate by: count people who name a problem in one meeting. If wrong: use a written prompt before any new tracker.

Alternative considered: Run a different retrospective game each meeting. This loses because a new game adds no owner, no date, and no time to do the work.
[judgment]

End

I recommend that we take these four steps.

1. Classify the failure from the last three notes in one session. This removes the unknown cause, so later steps match the notes. Domain: Confused. Confused means the cause is not yet visible, so the first act is to classify it.

Test first. This action is evaluative. Rubric: owner present has weight 30. Date present has weight 20. Done state has weight 30. Team control has weight 20. Pass threshold: mean score of 70 or more. Evidence: the written notes from three meetings. Given those notes, when the rubric is applied, then record one class. The class is weak commitment, no review, no time, or done with no effect.

2. Install a close rule at the next retrospective. The meeting ends with one action, one owner, and one date. This removes the gap between talk and a commitment. See the Scrum Guide point in Information. The limit of one action is a judgment, not a quoted rule. Domain: Clear. Clear means the cause is known and one known practice applies. Step 2 MUST NOT start until Step 1 records a class other than done with no effect.

Test first. This action is deterministic. Given an open retrospective, when the close phase ends, then the notes show one action, one owner, and one date.

3. Open the next retrospective with a check of that action. Use the first five minutes, before any new topic. This removes the pattern of forgotten actions. Domain: Clear, because the check is one known step. Step 3 MUST NOT start until the test in Step 2 passes.

Test first. This action is deterministic. Given the prior action record, when the next retrospective opens, then the team marks it done, not done, or blocked.

4. Run one written probe in parallel with Steps 2 and 3. Budget: one meeting, then stop. Each person writes one blocker that the group has not said aloud. This tests whether silence, not follow-through, is the cause. Domain: Complex. Complex means the cause appears only after a small probe, so leverage is a guess. Stop if fewer than two people write a new blocker. Also stop if every note matches the spoken list.

Test first. This action is stochastic. Metric: count of written blockers absent from the spoken list. Baseline: the spoken list in the same meeting. Pass threshold: two or more new blockers. Sample size: one meeting with the people who attend.

If A2 is false, skip Steps 2 and 3. Replace them with one review of a finished action that did not change the cycle. That review is Complicated, because analysis can find the missed constraint. Step 4 still runs, because silence can hide the constraint.

Follow-up

If A1 is false, replace Step 2 with a short note to the person who controls the change. If A3 is false, stop Steps 2 and 3 and keep Step 4 only.
