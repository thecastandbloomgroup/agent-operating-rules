Headline

Measure failures on a fixed sample before any model change.

- A four-class rubric turns the complaint into counts.
- A fifty-case score creates the baseline the team lacks.
- One prompt change ships only if that baseline improves.

Background

The support tool added a large language model (LLM) that writes case summaries. Agents say some summaries are wrong, and the team has no metrics. The request is to make that summariser better.

Relevance

Agents read these summaries while they handle live cases. Therefore a wrong line can steer the next reply, and a change without a baseline can hide a new error.

Information

This section covers the evidence, the assumptions, and the alternative.

The request states two facts: summaries are sometimes wrong, and no metrics exist.
[1]

A model swap cannot prove a gain when the start rate is unknown. [judgment]

Agent remarks are qualitative evidence. Therefore group them into themes and count how often each theme appears.
[2]

The 40 percent share and the 10 percentage point drop are decision cuts, not measured rates. [judgment]

Confidence in the top error class is low, because no scored sample exists yet.

A1. The summarised object is a support case with source text the agent can check. Why not measured: the material does not state it. Validate by: open one production summary and its source. If wrong: score against the real source, not a case.

A2. "Wrong" means a fact error, a missing key fact, or a claim the source does not support. Why not measured: the material does not state it. Validate by: a 30-minute review with two agents. If wrong: change the rubric categories before the sample.

A3. Fifty recent cases can be exported in one session. Why not measured: the material does not state it. Validate by: export fifty case identifiers. If wrong: use twenty cases and keep the same rubric.

Alternative considered: replace the model first. It loses because no baseline exists, so the team cannot tell if errors fell. [judgment]

End

I recommend that we take these four steps.

Step 1, evaluative. Test first: two agents label the same ten summaries, and the rubric passes when they match on eight of ten. Criteria are fact error, missing key fact, unsupported claim, and other, each with weight 25. Evidence is the source text plus the summary. Then write that one-page rubric in one session. This removes the undefined complaint. Domain: Confused, because the dominant failure is not known yet, so this step classifies it.

Step 2, evaluative. Test first: the same rubric passes when fifty cases have a label and one class holds at least 40 percent of failures. Evidence is each source, summary, and label. Then score fifty recent cases in one session. This removes the missing baseline. Domain: Complicated, because the counts plus a short review can show which class dominates. Step 2 MUST NOT start until the Step 1 test passes.

Step 3, stochastic. Test first: metric is fact-error share on the same fifty cases. Baseline is the Step 2 rate. Pass mark is a drop of at least 10 percentage points. Sample size is 50. Then change one prompt rule on a copy and run each case once. Budget is one session, and stop if the rate does not fall. This probes a fix for the top class. Domain: Complex, because the effect shows only after the run, so the gain is a guess. Step 3 MUST NOT start until Step 2 names the top class.

Step 4, deterministic. Test first: Given a passed Step 3 result, When the copy is compared with production, Then the table shows the pass mark was met. Then ship that one rule and store the before and after rates. This removes an untested change. Domain: Clear, because the pass rule is already fixed and the team applies it. Step 4 MUST NOT start until the Step 3 test passes.

Follow-up

If A2 is false, replace fact-error share in Step 3 with the top class from Step 2. If A3 is false, use twenty cases and keep the same pass rule. If Step 2 shows no class at 40 percent, do not start Step 3, and split the rubric instead.
