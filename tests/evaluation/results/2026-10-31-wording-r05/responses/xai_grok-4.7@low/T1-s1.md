Headline
One automatic formatter ends the SQL layout dispute.
First, measure whether reviews argue about layout or about query meaning.
Second, give layout to one tool and one config file.

Background
The team does not share one format for Structured Query Language (SQL).
Each review opens the same layout debate.
The request is to remove that friction, not to choose one indent style.

Relevance
Review time goes to taste instead of defects.
A tool-owned rule stops the repeat argument in the next review cycle.

Information
Bacchelli and Bird report that review comments often cover style and maintainability, not only defects [1].
Therefore the SQL layout dispute matches a known review pattern.
The request has no count of this team's comments.
So the style share here stays unknown until a sample exists [judgment].

A1. Reviews mix layout comments with logic comments. Why not measured: the material does not state it. Validate by: tag 10 recent SQL review threads. If wrong: a formatter does not remove the friction, and the probe stops.

A2. A formatter can parse the dialect in use. Why not measured: the material does not state the dialect. Validate by: format 20 recent queries with one tool. If wrong: limit the rule to SQL the tool parses.

A3. No person can impose a style today. Why not measured: the material does not state governance. Validate by: name the person who can approve a repository rule. If wrong: publish the rule under that person.

The strongest alternative is a committee style guide that reviewers enforce by hand.
It loses because taste does not converge, and a document still needs a human judge [judgment].

A drop in layout comments is likely, in the 66 to 100% band.
The basis is the review pattern in [1] and the stable output of a formatter [judgment].

End
I recommend that we take these five steps.

1. Classify the friction before any format choice. Domain: Confused, because the cause is not named yet.
This step is evaluative.
Write the rubric first.
Criterion: share of comments that concern only layout.
Weight: 100%.
Pass threshold: at least 40% of tagged comments are layout-only [judgment].
Evidence: 10 merged SQL reviews from the last 30 days.
Two people tag each comment.
Then record the share.
This step removes the blocker that the dispute type is unknown.
Step 2 MUST NOT start until this score exists.
If the share is under 40%, stop.
The problem is not format.

2. Select one formatter and one config. Domain: Complicated, because several tools can work and a short trial picks one.
This step is deterministic.
Write the test first.
Given 20 repository queries, when the formatter runs twice, then the second run changes no file.
Both runs exit with code 0.
Run that test on at most two tools.
Keep the tool that passes.
Commit the config in one working session.
This removes the blocker that no shared rule exists.

3. Enforce format in continuous integration (CI). Domain: Clear, because a failing check is standard once the tool is chosen.
CI means the build that runs on each change.
This step is deterministic.
Write the test first.
Given a change with bad layout, when CI runs, then the check fails.

Add that check to one repository.
Step 3 MUST NOT start until the test in Step 2 passes.

4. Publish the review rule in that repository. Domain: Clear, because the rule is one sentence and the check already exists.
This step is deterministic.
Write the test first.
Given the contributing note, when a reader searches for SQL style, then the note marks layout comments out of scope.
The note points to the format command.
Add that sentence in one edit.
Step 4 MUST NOT start until the test in Step 3 passes.
This stops repeat layout comments in review.

5. Probe for 10 working days on that one repository. Domain: Complex, because compliance shows up only after the change.
This step is stochastic.
Write the test first.

Baseline: the share from Step 1.
Pass threshold: the rate falls by half versus that baseline.
Sample size: all SQL reviews in those 10 days, with at least 8 reviews.
Budget: one repository and no other team.
Stop if CI fails more than one in five changes because the tool cannot parse the SQL.
Step 5 MUST NOT start until Step 4 is in place.
Leverage of this probe is a guess.
If the threshold is met, copy the same config to the next repository.
