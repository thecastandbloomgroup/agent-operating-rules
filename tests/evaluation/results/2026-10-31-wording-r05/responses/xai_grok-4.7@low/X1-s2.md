Headline

Do not change the summariser until a scored sample shows what "wrong" means.
Agents do not name the failed fact, so a model swap can miss the cause.
A scored set of real tickets gives a baseline and a ranked failure list.
The first change should hit the largest failure and pass a written test before release.

Background

The support tool now writes a summary with a large language model (LLM).
Agents say that some summaries are wrong.
The current request states that the team has no metrics for that claim [1].

Relevance

Agents still use these summaries in live support work.
A change with no baseline can leave the same errors in place.

Information

The only quality signal is the phrase "sometimes wrong" [1].
That phrase has no rate, no error class, and no sample size.
A fix chosen from that phrase cannot show a gain [judgment].
Cause and effect are not visible from the phrase, so the work starts as Confused [2].
Low confidence on which error is largest, because no scored sample exists.

Three classes cover a wrong summary [judgment].
The classes are an added fact, a missing fact, and a change in meaning.
These three do not overlap, and together they cover the fault [judgment].
A fourth label, other, catches a note that does not fit.

A1. The LLM reads one support ticket and writes a short summary for a human agent. Why not measured: the material does not state the input or the reader. Validate by: open the prompt and one live example. If wrong: rewrite the rubric for the real task.

A2. The team can export 50 ticket and summary pairs from the last 30 days. Why not measured: the material does not state that logs exist. Validate by: ask the tool owner for that export. If wrong: start logging and wait for 50 pairs before any score.

A3. Wrong means an added fact, a missing needed fact, or a change in meaning. Why not measured: the material does not define wrong. Validate by: code 10 agent notes into those classes. If wrong: add the new class and score again.

A4. Two people can score the same 30 pairs. Why not measured: the material does not state team size. Validate by: name two scorers before Step 2. If wrong: one person scores twice, on two days, and agreement is between those passes.

Alternative considered

The strongest alternative is to rewrite the prompt or switch the model this week.
It loses because there is no baseline, so a later score cannot show a gain [judgment].

End

I recommend that we follow the four steps below.

Step 1. Domain: Confused, because cause and effect are not visible yet [2].
This step is evaluative, that is, the output is a judgment.
The test comes first.
Three criteria have equal weight.
A case passes when 2 of 3 criteria are true.
Criterion 1 needs the ticket text and the summary text.
Criterion 2 needs the agent words for what was wrong.
Criterion 3 needs one class: added fact, missing fact, changed meaning, or other.
The pass threshold is 8 of 10 cases [judgment].
In one session, label 10 recent bad summaries with that rubric.
This removes the blocker that the failure domain is unknown.
Step 2 MUST NOT start until this test passes.

Step 2. Domain: Complicated, because cause and effect need the scores [2].
This step is evaluative.
The test comes first.

Step 4. Domain: Complex, because the effect shows up only after the trial [2].
This step is a safe-to-fail probe.
Leverage is a guess.
This step is stochastic, that is, the LLM output can vary from run to run [judgment].
