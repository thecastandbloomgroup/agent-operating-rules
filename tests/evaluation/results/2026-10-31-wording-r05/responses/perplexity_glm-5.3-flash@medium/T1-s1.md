## Headline

Automate SQL formatting with one enforced tool config, so that style disputes leave human reviews.

1. A formatter tool applies one style mechanically. Humans stop judging style.
2. The team argues once, in a config file, not repeatedly in reviews.
3. CI enforcement makes compliance a check, not a negotiation.
4. Culture changes because the disputed question becomes unaskable in reviews.

## Background

The team disagrees on SQL format rules. Each review reopens the same debate, which costs time and creates resentment. The request names this a culture problem.

## Relevance

Review friction scales with every new pull request and every new team member. Removing the cause now stops a daily cost, not a single incident.

## Information

Evidence:

- SQLFluff is a configurable SQL linter that formats and autofixes SQL across dialects [S]. One config file holds every style decision, which makes it the single source of truth.
- The EditorConfig standard lets one file fix whitespace and line endings across editors, which covers issues formatters miss [P].
- Qualitative theme, from engineering practice: teams that move style checks to tools report fewer style arguments in review. One known source supports this theme; a counterexample is a team that adopts a tool but lets reviewers still comment on style, which restores the debate [inference].
- Baseline for the friction: today every review can contain style comments. Success means zero style comments over two weeks [judgment].

Assumption log:

- A1. The team uses pull request reviews in a shared repository. Why not measured: the material does not state it. Validate by: check one repository for a review history. If wrong: use local pre-commit hooks only, and the recommendation still holds.
- A2. The team uses one SQL dialect, for example PostgreSQL. Why not measured: the material does not state it. Validate by: list dialects in the codebase, one grep. If wrong: configure per-dialect overrides in the same config, which is supported [S].
- A3. A CI system exists. Why not measured: the material does not state it. Validate by: check for a pipeline config file. If wrong: enforce at pre-commit only, weaker but workable.

Alternative considered: a written style guide with human enforcement. It loses because people must remember the rules, and each forgetful review restarts the dispute. Tool configs do not forget [judgment].

## End

I recommend that we retire style from human review and enforce it with tooling. Steps, in order:

1. **Pick the config.** Increment: one 30-minute session, output is one decision list (dialect, indent, casing, comma position), scored with a Pugh matrix against two candidate styles. Blocker: it ends the era of undeclared preferences. Test: rubric first, criteria are readability, autofix support, and diff size, weights agreed before scoring. Criterion scores need one code sample per candidate. Cynefin: Complicated, because analysis by the group, not habit, must pick the style.
2. **Commit the config and a formatting rule file.** Increment: one commit with the tool config plus an EditorConfig file. Blocker: it removes "what is our style" as a discussion topic. Dependent on Step 1. Test (written first):

   ```gherkin
   Given the committed config in the repository
   When the linter runs on any SQL file
   Then the exit status is 0
   ```

   Cynefin: Clear, because the tool documents the check existentially and the test proves it [S].
3. **Reformat all existing SQL in one batch.** Increment: one autofix commit, no other changes in it, so diffs stay reviewable. Blocker: it removes old files from debates, so new rules feel universal, not selective. Dependent on Step 2. Test:

   ```gherkin
   Given the full codebase after the autofix commit
   When the linter runs on every SQL file
   Then the exit status is 0
   ```

   Cynefin: Clear, because the fix command is deterministic [S].
4. **Block unformatted SQL in CI.** Increment: one pipeline job that lints changed SQL files. Blocker: it converts compliance from peer policing into a mechanical gate, which is the culture change. Dependent on Step 3. Test:

   ```gherkin
   Given a pull request that adds SQL which fails the linter
   When the pipeline runs
   Then the check fails and review cannot start
   ```

   Cynefin: Clear, because the gate either passes or fails with no judgment [S].
5. **Probe the effect on review friction.** Increment: a two-week measure of style comments per review, budget one hour to tally. Measure: count of review comments that mention formatting; baseline is the current count, which today is above zero [judgment]. Stop condition: if the count is not zero after two weeks, run one retro on the cause. Cynefin: Complex, because human reaction is visible only afterward, so this stays a capped probe and shares no leverage claim.
