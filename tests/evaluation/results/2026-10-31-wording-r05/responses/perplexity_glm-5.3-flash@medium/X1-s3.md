# Headline

Add measurement before change: capture real agent feedback, build a small labeled test set, then improve the prompt against it. Support: first, agents' "sometimes wrong" is not specific enough to act on, so tag the error types. Second, the tool logs no data now, so instrument it to capture summaries and agent edits. Third, a 50-case labeled set turns opinions into a fail-rate metric you can re-run.

# Background

The team added an LLM summariser to a support tool. Agents report it is "sometimes wrong" [user report]. The team has no metrics for summary quality.

# Relevance

Without a metric, every change to the prompt is a guess. A small evaluation loop finds the real error types and shows whether each change helps.

# Information

## Evidence

Meaningful evaluation is feasible with a small sample. Evaluation with 50 to 100 cases gives a usable signal; the standard error of a fail rate at n=50 is about 7 percentage points at p=0.5 [judgment, from the binomial formula]. Wait for more data only if the real fail rate stands far from 50%.

"Sometimes wrong" is unverifiable until you measure the base rate. The complaint gives no number, so the current fail rate is unknown. A likely range is 10 to 40% as wrong or missing key facts [judgment]. Treat the first measurement, not this range, as the baseline.

Agent edits and discards are the cheapest quality signal. This follows qualitative practice: collect actual cases, group them into themes, and count support per theme [3], [5].

## Assumption log

A1. The summariser reads full ticket threads. Why not measured: the material does not state the input. Validate by: read the integration config. If wrong: missing-context errors need prompt changes that surface older messages.

A2. No log captures summary output or agent actions today. Why not measured: the material states "no metrics", which implies no logging. Validate by: ask the tool admin for existing logs. If wrong: skip the instrumentation step and reuse the log.

A3. Agents can spare 30 to 60 minutes to label cases. Why not measured: no tool can reach agent availability. Validate by: ask two agents directly. If wrong: label the set from past tickets instead of live work.

A4. The summariser is one prompt and one model, not a chain. Why not measured: the material does not state the architecture. Validate by: read the source. If wrong: budget per change doubles with each extra step.

## Alternative considered

Fix complaints case by case as agents report them. It loses because the base rate and the error mix stay unknown, so a change that fixes one case can break others with no way to detect it.

# End

I recommend that we run these four steps. Step 1 comes first because its output classifies the domain of the remaining work.

1. **Instrument the tool.** Log every summary, its source tickets, and each agent edit or discard, with timestamps. This removes the blocker of having no data.
   - Kind: deterministic. Cynefin: Clear, because cause and effect are known: log events, then events exist.
   - Test (write first, then build): Given a ticket with a generated summary, When an agent edits it, Then the log holds the summary text, the edited text, and one timestamp per event.
2. **Tag the error types.** Pull 50 recent summaries. Two agents tag each case: wrong fact, missing fact, too long, wrong tone, other. Total weakly over 50, so ties cost nothing.
   - Kind: evaluative. Cynefin: Confused, because the error mix and the right next action are unknown until this runs.
   - Rubric first: category list above, weight 1 per case, pass threshold 80% tagger agreement on 10 overlap cases, evidence is the summary text with its source tickets.
3. **Build the golden test set.** Freeze the 50 tagged cases as a labeled set with expected facts per case.
   - Kind: deterministic. Cynefin: Clear, tagging follows the written category rules from Step 2.
   - Test (write first): Given the frozen case list, When a reviewer checks each entry, Then every entry holds its ticket ID, its expected facts, and its categories.
4. **Probe prompt changes against the test set.** Make one small change per run, for example add "quote every named date as written". Score the fail rate on the 50 cases before and after.
   - Kind: stochastic. Cynefin: Complex, because the effect of a prompt change is visible only after the run.
   - Acceptance test (write first): metric is the percent of cases with a wrong or missing fact. Baseline: the Step 2 measured rate. Pass: 5 percentage points lower at n=50. Budget: two probe runs, then stop and re-tag a fresh 20 cases if neither run passes. Stop condition: any run that raises the rate ends that probe.

Step 1 frees Step 2 from manual pulls. Steps 2 and 3 MUST finish before Step 4 starts, because the test set defines its metric.

If A2 is false and logs exist, replace Step 1 with a log audit and run Step 2 against the log in the same session.

# Follow-up

Condition that changes the recommendation: if A4 is false and the summariser is a multi-step chain, isolate one step per probe. The per-step budget halves the probe count.
