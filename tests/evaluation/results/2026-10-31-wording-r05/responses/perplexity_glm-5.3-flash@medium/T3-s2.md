# Headline

Migrate the auth service to short-lived access tokens backed by revocable refresh tokens behind a feature flag, and measure the sign-up funnel before changing it. Supporting points:

1. Instrument the sign-up funnel first, because "conversion is bad" has no known cause yet.
2. Ship JWT issuance with server-side refresh token storage, so logout and revocation still work.
3. Roll out as a dual-run probe with a stop condition, not a big-bang switch.
4. Cut over only after the error-rate test passes at the sample size.

# Background

The request covers two tasks: replace session-based auth in the auth service with JWT, and raise sign-up conversion. No stack, codebase, or funnel data has been provided. The plan therefore assumes a generic web service and states each unknown.

# Relevance

A token migration touches every request path, so a wrong design is costly to reverse after launch. The funnel change is cheap to reverse, so it can wait for data.

# Information

## Evidence

Key sources for the design decisions:

1. JWT is a standard format for carrying verified claims between parties, per the JWT specification [R1].
2. Token lifetimes must be limited and refresh tokens should be scope-limited and revocable, per the OAuth 2.0 security best practice [R2].
3. Session management guidance recommends renewal and explicit expiry controls for session state, per OWASP [R3].
4. Stateless access tokens alone break instant logout and account lockout; this is a known trade-off between revocation and statelessness [R3] [judgment].
5. Sign-up conversion fixes depend on which step drops users; no funnel data exists in the conversation, so the cause is unclassified [no source].

## Assumption log

A1. The auth service is a web backend with a session store and a standard login form. Why not measured: the material does not state the stack. Validate by: read the repository and the deploy config. If wrong: the plan names stay the same; only the middleware names change.

A2. Instant session revocation (logout everywhere, account lockout) is required at or near real time. Why not measured: the material does not state a revocation policy. Validate by: ask the security owner for the policy. If wrong: tokens can be fully stateless and Step 2 gets simpler.

A3. The sign-up funnel is not instrumented per step today. Why not measured: no tool result or document shows funnel data. Validate by: query the analytics service for signup_page_view counts. If wrong: skip Step 1 and go straight to the A/B probe.

A4. Current baseline is 0 auth failures of any severity class from the session flow. Why not measured: no dataset is in the session. Validate by: pull the auth error rate for the last 7 days today. If wrong: replace the baseline in the Step 3 test with the measured number.

## Alternative considered

Keep sessions and change nothing about tokens. This loses because per-request session lookups couple service scaling to one store, and the request names cross-service token use; the cost of the change is one well-tested middleware (A3, [judgment]).
