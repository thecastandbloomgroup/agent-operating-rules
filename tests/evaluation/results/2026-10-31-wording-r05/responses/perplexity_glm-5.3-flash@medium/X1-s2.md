### Headline

Label a sample of summaries to measure the errors, fix the prompt behind a flag, and gate future changes on the labeled set.

- Labeling 50 summaries shows the error types and their rates.
- A prompt limited to the case transcript targets summaries that contradict the source.
- One-click disagreement capture keeps error reports coming after the first fix.
- A regression gate makes every future prompt or model change prove itself on the labeled set.

### Background

The support tool adds a summary of each case, generated by an LLM, a large language model. Agents report that the summaries are sometimes wrong, and no numbers exist for the error types or rates.

### Relevance

Agents use summaries to decide how to reply, so a wrong fact can reach a customer [judgment, A1]. Measurement is therefore the blocker: without a rate, no change can be shown to work.

### Information

**Evidence**

- "Sometimes wrong" is a report theme without a count. The accepted method is to code a sample into themes and count the sources for each theme [5].
- A sample of 50 gives a 95% confidence interval of about plus or minus 8 percentage points around a pass rate of 90% [inference].

**Assumption log**

A1. Agents read the summary before the full case, so wrong facts reach customers. Why not measured: the material does not state the workflow. Validate by: watch two agents use the tool. If wrong: the plan holds; the feedback loop gains weight instead.

A2. "Wrong" includes summaries that contradict the transcript. Why not measured: agent reports are not collected. Validate by: the labels from Step 1. If wrong: drop the contradiction gate in Step 2 and target omissions instead.

A3. The tool generates enough summaries to draw 50 recent cases. Why not measured: volume is not stated. Validate by: count the runs of the last week. If wrong: extend the draw window or label all available cases.

**Alternative considered**

Fix the prompt now, with no baseline. It loses because, without labels and a measured rate, any improvement claim rests on a guess.

### End

I recommend that we run four steps in this order. Each step names its increment, its blocker or new capability, its test, and its Cynefin domain, which describes how cause and effect behave in that kind of work [18].

1. **Rubric and labels.** I recommend that we write a rubric with four error classes: contradicts the transcript, omits a fact from the transcript, wrong emphasis, too long. Each class has a weight, a pass threshold, and the evidence it needs, per the rubric layout in [15]. Two reviewers then label 50 recent summaries. The increment fits two short sessions. Blocker removed: the team gains the error types and rates that every later step needs. Test written first (evaluative): the rubric states criteria, weights, pass threshold, and required evidence; reviewers must agree beyond chance, at kappa 0.70 or more, before the labels count as a baseline [judgment]. Domain: Confused, because the first work gathers what is needed to classify the problem [18].

2. **Prompt fix on a flag.** I recommend that we change the prompt so the summary uses only facts from the case transcript, quotes customer numbers exactly, and stays within five sentences. Deploy it behind a feature flag for the 50 eval cases. The increment fits one session. Capability added: the prompt gains a rule that ties output facts to the source. Test written first (stochastic): metric, rubric pass rate; baseline, the rate from Step 1; pass threshold, 90% or above at a sample size of 50, with zero summaries that contradict the transcript [judgment]; run the trials and accept only at threshold. Domain: Complex, because the effect of a prompt change shows only after the run; cap the probe at one prompt revision and 50 eval runs, and stop it if the pass rate stays below the baseline. Step 2 MUST NOT start before the labels from Step 1 exist.

3. **Disagreement capture.** I recommend that we add one button per summary that stores the case id, the error class the agent selects, and a note. Until it ships, use a shared form with the same fields. The increment fits one session. Capability added: error reports arrive continuously instead of one at a time. Test written first (deterministic), in Gherkin [14]:

```gherkin
Given a generated summary
When an agent selects an error class and saves
Then the system stores the case id, the class, and the note
```

Domain: Clear, because write on click is a known practice with one correct step [18]. Steps 2 and 3 run in parallel once Step 1 is done.

4. **Regression gate and rollout.** I recommend that we keep the 50 labeled cases with their transcripts as a regression set, and require each future prompt or model change to pass the Step 2 threshold at n = 50 before full rollout. The increment fits one session. Blocker removed: future changes gain a repeatable pass or fail test. Test written first (deterministic), in Gherkin:

```gherkin
Given an eval run of a prompt or model change at n = 50
When the pass rate meets the Step 2 threshold
Then rollout proceeds
```

Full rollout MUST NOT start until the gate passes. Domain: Complicated, because the analysis that compares eval runs picks the practice [18].

If A2 is false, replace the contradiction gate in Step 2 with an omission threshold.

### Follow-up

Open questions: none. Conditions that change the recommendation: A1 to A3 in the assumption log; A3 has the cheapest test.
