# Headline

Roll back to the last known good release now, verify checkout with a test request, and walk into the exec call with a three-line status update.

1. A change that went out near 09:12 is the most likely cause, and rollback is the fastest fix. [judgment]
2. Capture two minutes of evidence first, so the rollback is not blind.
3. If rollback is not possible, revert config and feature flags from the same window.
4. The exec call needs scope, start time, actions, and next update time, not a diagnosis.

# Background

Checkout returns HTTP 500 for every user since 09:12, about one hour before this message. The on-call engineer has ten minutes before an exec call and needs an order of work, not an analysis.

# Relevance

Every minute of outage is full customer impact on revenue, and the exec call fixes the reporting window. The order of the next ten minutes decides both the recovery time and the quality of the update.

# Information

**Evidence.**

1. Tracked incidents most often trace to a recent change, so rollback of the last change is the standard first move in incident response [19].
2. A total failure (100% of users) with a fixed start time points to a deployment, config change, or dependency event at that minute, not to a slow resource leak [inference].
3. Theme from incident practice: "stabilize first, diagnose after" appears in operational runbooks and postmortem guides as the dominant pattern, with no major source in this literature disagreeing (2 sources support: [19], [20]).

**Assumption log.**

- `A1. A deploy or config change went out near 09:12 and caused the failure. Why not measured: the material does not state the deploy history. Validate by: run the deploy log command in Step 1. If wrong: rollback is a no-op, so move to Step 3 and triage the error stack.`
- `A2. A rollback path exists and completes within minutes. Why not measured: the material does not state the release tooling. Validate by: open the release tooling page. If wrong: use the flag revert in Step 3, or shift traffic to the last known good instances.`

**Alternative considered.** Debug forward in place: read stack traces and fix the root cause live. It loses because diagnosis time is unknown while rollback time is known and short [judgment].

# End

I recommend that we run these four steps, in this order:

1. **Stabilize: roll back to the last known good release.** The increment is one rollback command plus a deploy log check, done in one session. This removes the blocker, which is the bad release serving traffic. Chaos domain [18]: cause and effect are not yet visible [inference], so the action is stabilize first, act, then assess. Test (write it before the run): `Given a test cart with one item, When the checkout request is sent, Then the response code is 200 and the order is recorded.` This step MUST NOT wait on any other step.
2. **Verify: confirm recovery with a real test request.** The increment is one scripted request plus a check of the error-rate graph for two minutes. This adds the capability to prove recovery, not assume it. Clear domain: a known check with a known answer applies. Test: `Given the rollback from Step 1 is complete, When the test request runs three times over two minutes, Then all three responses are 200.`
3. **Fallback: revert config and feature flags from the 09:00 to 09:15 window.** The increment is one diff review plus flag reverts, one session. This removes the blocker for the case where A1 is false or A2 is wrong. Clear domain: a best practice exists, apply it, because flag and config changes deploy without a release. Test: `Given the flags from the listed window are reverted, When the test request runs, Then the response code is 200.` This step waits until Step 1 is complete or proven impossible.
4. **Communicate: post the exec update before the call.** The increment is a five-line status note, one session. This removes the blocker of an exec call with no facts. Clear domain: a fixed template applies. Test: `Given the exec call starts, When the update is read, Then it states scope, start time 09:12, actions taken, current owner, and next update time.` Dependency: steps 1 to 3 send only facts already observed, so step 4 can run while step 3 waits.

If the deploy log in Step 1 shows no change in the 48 hours before 09:12, drop the rollback plan and replace Step 3 with error-stack triage against the top failing dependency. [inference]
