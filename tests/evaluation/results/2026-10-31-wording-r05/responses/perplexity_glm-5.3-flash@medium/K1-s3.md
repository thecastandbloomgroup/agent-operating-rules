# Headline

Roll the pool settings back first, then the cache TTL: the pool shrink from 50 to 8 connections is the root cause. The evidence in order of weight:

1. db.pool.acquire p95 went from 3 ms to 690 ms [1], so the acquire wait holds 88% of the 780 ms total latency increase (687 of 780 ms) ([inference], from the span table).
2. Errors rose to 0.40% of requests [1], and 96% of them are "PoolTimeout: acquire timed out after 5 s" [1].
3. The release cut pool max_size from 50 to 8 and acquire_timeout_s from 30 to 5 s [2].
4. The query spans barely moved (orders: 52 to 58 ms, order lines: 30 to 26 ms) [1], so the ORM change is not the driver.

# Background

The service serves 405 requests per second at peak through 4 pods with 8 worker threads each, so 32 workers share the pool space [2]. The release changed the pool size, the acquire timeout, the cache TTL, and one ORM query [2]. Since the release, each pod logs "pool exhausted: 8 of 8 connections in use" at a rate of 1,800 to 2,400 per hour, against none before it [3].

# Relevance

The pool is exhausted across all 4 pods, so every request that misses the cache queues for a connection. Each day at this error rate sends 0.40% of orders traffic a 5 second timeout and a 503 response [1].

# Information

**Evidence, quantitative.** The traces give paired windows of 10,000 sampled requests each: window A before the release, window B after it [1]. Total p95: 120 ms to 900 ms [1]. db.pool.acquire p95: 3 ms to 690 ms [1]. Cache miss rate: 12% to 31% [1]. Database CPU at peak: 38% to 41%, so the database has headroom [1]. Active connections from this service at peak: 31 at 38% CPU in window A [1]. This number matters for sizing: the old peak of 31 connections ran at low CPU, so a pool of 32 connections or more is safe on the database side ([inference], from the CPU and connection counts).

**Why the pool change dominates.** The logs show the 8 connection limit applies per pod, because each pod reports "8 of 8" separately [3]. Therefore 32 worker threads per service now compete within pods of 8 connections, and waiters of 9 to 14 queue behind each pod's 8 [3]. So each cache miss turns into a query that waits for a connection.

**Why the cache change matters but is secondary.** The TTL cut from 300 s to 60 s [2] raised the miss rate from 12% to 31% [1], which is about 2.6 times the misses per request ([inference], from the two rates). Each miss adds a query and a pool acquire. However, the acquire wait grew 230 times (3 ms to 690 ms) [1], therefore the pool, not the miss rate, is the binding constraint.
