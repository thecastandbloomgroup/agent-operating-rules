# Headline

Make a tool, not the team, decide how we format SQL, and the culture problem loses its cause.

- A committed config file holds every format rule in one place, so the team stops debating them.
- An automated check rejects SQL that does not match the config before a human reviews it.
- Reviewers then see only logic changes, so the format debate has nothing to feed on.
- One capped 30-day probe confirms the friction drops; if not, the plan changes.

## Background

The team disagrees on how to format SQL. Every code review now includes a style side-debate, and the team calls this a culture problem. The request: remove the friction.

## Relevance

Each review pays the debate cost today. A tool-based fix removes the cause in one sprint, and it requires no persuasion.

## Information

**Root cause.** The debate is about taste, so round-table agreement cannot produce a stable answer. The theme from the sources: people argue longest about small taste issues, and a fixed mechanical rule ends the argument. Three sources support this theme, and none disagree:

Because the debate continues in every review, the working rule "everyone agrees first, then we format" has already failed. Therefore the stable fix removes the format decision from humans [judgment]. Confidence in this mechanism: high confidence, because the three sources and the reported pattern in the request agree.

**Assumption log.**

A1. The team uses one SQL dialect for most code. Why not measured: the material does not state the dialect. Validate by: set the dialect in the config from A1 and run one lint pass over the repo; parse errors reveal the dialect. If wrong: change one line in the config and rerun; cost is under one hour.
A2. The code lives in one repository that runs automated checks on merge. Why not measured: the material does not describe the repo layout. Validate by: check whether merge requests already run any automated step. If wrong: replace the pipeline gate in Step 3 with a pre-commit hook; the rest of the plan is unchanged.
A3. No formatter config exists in the repo today. Why not measured: the material does not mention one. Validate by: search the repo for `.sqlfluff`, `.editorconfig`, or similar files. If wrong: review and update the existing config instead of creating one.

**Alternative considered.** A written style guide, enforced by reviewers. It loses because a guide still leaves each case to human judgment, and that judgment is the friction source [judgment].

## End

I recommend that we run the four steps below, in order.

**Step 1. Add the config and record the baseline.** (deterministic)
Install sqlfluff, an open-source SQL formatter and linter, meaning a tool that checks and fixes code style [1]. Commit a `.sqlfluff` file with the dialect, indent width, and comma style. In the same session, count style-only comments in the last 10 closed reviews to record the baseline. Capability added: one source of truth for format, so human choice is capped. Test, written before the work [4]:
```
Given the repository contains a .sqlfluff file with the dialect set
When the team runs "sqlfluff lint" on one sample file
Then the sample file passes with no format errors
```
Cynefin: Clear, because the step is known and one scripted tool does it.

**Step 2. Reformat the codebase in one merge request.** (deterministic)
The request changes SQL layout only, with no logic changes. Capability added: it removes the backlog of mixed formats, so later reviews show a stable format. This step MUST NOT start until the test in Step 1 passes. Test, written before the work:
```
Given the reformat merge request with changes to SQL statements only
When the team compares the parsed statements before and after
Then each statement parses the same and only the layout changes
```
Cynefin: Clear, because a formatter applies rules mechanically.

**Step 3. Add the pipeline gate.** (deterministic)
Add one pipeline step that runs `sqlfluff lint` and fails the merge request on any format error [1]. This step MUST NOT start until Step 2 is merged; otherwise the gate fails for every open request. Blocker removed: reviewers no longer enforce format, so the human friction path closes. Test, written before the work:
```
Given a merge request with SQL that does not match the config
When the pipeline runs the lint step
Then the pipeline fails with the message "run sqlfluff fix"
```
Cynefin: Clear, because the check is a scripted rule with a known outcome.

**Step 4. Probe the culture result for 30 days.** (stochastic)
Run a safe-to-fail probe: it changes no code, so a wrong guess costs nothing. Metric: style-only comment threads per review. Baseline: the count from Step 1. Pass threshold: fewer than 1 style thread per 10 reviews [judgment]. Sample size: 10 reviews after rollout. Stop condition and budget: 30 days and 2 hours; therefore if the threshold is not met at that sample size, hold one team vote on the whole config, freeze the result, and re-probe once. Cynefin: Complex, because team behavior shows cause and effect only after the run.

## Follow-up

Conditions that change the recommendation:

- If the repo has no pipeline (A2 false), use a pre-commit hook in Step 3 for the same gate.
- If the repo truly mixes dialects beyond A1, apply the config per directory with the dialect set for each.

Open questions: none.
