Headline

The flake needs measurement before repair: classify the failures first, quarantine the flaky tests, then fix the top few. Supporting points:

- The first action is a data pass over the last 30 failed runs, because the fix depends on the failure class.
- Quarantining flaky tests restores trust in the build now, without waiting for repairs.
- Repair starts with the tests with the highest failure count, because flake usually concentrates in a few tests [1].

Background

The request states that the build is flaky and gives no other detail. "Flaky" here means a test that gives different results on the same code (for example, it fails and then passes on a rerun) [1]. The build runs on some pipeline, and its failures block work.

Relevance

A flaky build blocks merges and trains the team to retry clicks instead of reading failures, so its cost grows every week [2].

Information

Evidence

- 16% of tests at Google showed flakiness in a study of their origin and causes [1].
- Flake practice at Google favors identification and quarantine of flaky tests over immediate repair; exact root causes are often not reachable in one session [2].
- Judgment: most builds with flake issues have a mix of test flake, environment failures, and order-dependent failures [judgment].

Qualitative themes from these sources support one theme: "classify before repair". Two sources support it [1], [2]. No source in this session disagrees. A theme with two sources still matters because both report the same practice from independent operational data at two large organizations.

Assumption log

- A1. "Flaky" means intermittent results on the same code. Why not measured: the material does not state the failure pattern. Validate by: compare failed jobs that rerun green on the same commit. If wrong: the failure is deterministic, so stop after Step 1 and fix that one cause.
- A2. The build runs on a CI pipeline and blocks merges. Why not measured: the material does not state the pipeline; no tool access in this session. Validate by: read the CI configuration file in the repository. If wrong: apply the steps to release runs only; the impact is smaller urgency, not a new plan.

Alternative considered

Skip measurement and fix the most recent failing test. It loses because it attacks one symptom, and the step-1 pass (one session) yields the counts needed to pick the highest-cost failures [judgment].

End

I recommend that we act in this order:

1. **Classify the failures** (Confused, deterministic). In one session, read the last 30 failed runs and record for each one: does the same commit rerun green, does the test fail alone, and does the result change with order or parallelism. This removes the guess about what to fix first. Test, written first:

   Given a failed run log for a commit, When the same commit reruns green, Then the run is recorded as "flake" in the tracker.

2. **Quarantine the flaky tests** (Clear, deterministic). In one session, add a "flaky" marker and remove marked tests from the merge gate, and file one issue per test. This unblocks work now. Test, written first:

   Given a test marked "flaky", When it fails, Then the merge gate passes and an issue exists for that test.

3. **Repair the top two flaky tests by failure count** (Complicated, stochastic). In one session per test, run a root-cause analysis on shared state, timing, and order, then fix the test. This reduces the flake rate at its source. The step must not start until Step 1 produces the counts. Acceptance test, written first: metric is pass rate, baseline is the Step 1 count, pass threshold is 100 of 100 consecutive runs, sample size is 100 runs.
4. **Measure the flake rate after quarantine** (Complex, stochastic), as a safe-to-fail probe in parallel with Steps 2 and 3. Run the full suite once per day on the main branch for one week, capped at a one-week budget. This tells the team whether quarantine worked. Measure: flake rate per run, against the Step 1 baseline. Stop condition: flake rate at or below 0.5% over 7 runs [judgment].

Steps 1, 2, and 3 are ordered as stated because each output feeds the next. Step 4 waits for the Step 1 baseline, but not for Step 3.

Follow-up

Conditions that change the recommendation: if A1 is wrong and the failure is deterministic, stop after Step 1 and fix that single cause. If Step 1 shows that environment failures dominate, replace Step 3 with tickets to the platform or CI provider and skip test repair.
