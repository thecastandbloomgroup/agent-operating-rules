# Headline

Convert each retrospective into one owned experiment with a review date, and stop treating the meeting as discussion only.

1. Retrospectives stop producing change when their output items have no owner, no date, and no follow-up review.
2. One experiment per retrospective creates a visible link between the meeting and a change in the work.
3. Reviewing the previous experiment at the start of the next retrospective closes the feedback loop.

## Background

The team attends retrospectives but no workflow change follows. The request asks for a way to restore change output. The material does not state the team size, the retro format, or whether past action items exist in written form.

## Relevance

Each retrospective costs about 60 minutes per member, so a meeting with zero change output wastes that time every cycle [judgment]. Unconverted discussion erodes trust in the process, so attendance and candor drop next [judgment].

## Information

**Evidence.** Two themes emerge from practitioner sources, grouped with the method in [3].

Theme 1: action items without owners, dates, or follow-up is the most cited cause of retro failure. Two sources support this theme, [1], [2]. No disagreeing source was found. Confidence is high, two independent practitioner sources.

Theme 2: a retro needs a closed loop, meaning the next meeting reviews what the previous one produced. One source states this directly: follow-up on actions is part of the retro method itself [1]. Confidence is high, one main source plus its confirmed status as the base method text.

Theme 1 and Theme 2 agree, so confidence in the recommendation basis rises.

**Assumption log.**

- A1. The retrospectives are facilitated meetings with written notes. Why not measured: the material does not state it. Validate by: check the notes of the last three retrospectives. If wrong: change the recommendation to start written output first.
- A2. Some action items already exist in recorded form after each meeting. Why not measured: the material does not state it. Validate by: count them against Step 1 in the End section. If wrong: start a backlog from zero; the recommendation holds.
- A3. The team holds authority to change parts of its own workflow. Why not measured: the user has not answered. Validate by: ask the team lead which decisions the team may change alone. If wrong: this becomes an escalation problem first, at team-management level.

**Alternative considered.** Change only the format, for example a new exercise or a new facilitator. This loses because format changes do not create ownership or follow-up, and Theme 1 identifies the missing follow-through as the blocker [1], [2].

## End

I recommend that we run the following steps.

1. **Audit the last three retrospectives. Count every action item and record its owner, date, and status today.** This removes the blocker of an unknown baseline. Classification: deterministic. Cynefin: Clear, because the rule is simple counting with a known method. Test:

```gherkin
Given the notes of the last three retrospectives
When each recorded action item is checked
Then the audit lists owner, date, and status for every item
```

2. **Create a standing experiment backlog. Each retrospective selects exactly one experiment, one owner, and one review date within two weeks.** This adds the capability to convert discussion into change. Classification: deterministic. Cynefin: Clear, because applying the known rule of owned, dated actions directly follows Theme 1. Test:

```gherkin
Given a completed retrospective
When the team selects its experiment for the period
Then the backlog stores one owner, one experiment, and one review date
```

3. **Open each retrospective with a review of the previous experiment result, then select the next one.** Step 3 cannot start before the first experiment from Step 2 has reached its review date. This removes the blocker of a missing feedback loop. Classification: deterministic. Cynefin: Clear, because the step applies the loop rule stated in [1]. Test:

```gherkin
Given the start of a retrospective
When the previous experiment reaches its review date
Then the team records the result before the discussion begins
```

4. **Run one meta-retropective on the retro process itself. Sort each issue into "team may change it here" or "needs management support", and escalate the second group the same week.** Step 4 can run in parallel with Steps 2 and 3. This removes the blocker of hidden blockers outside the team, per assumption A3. Classification: evaluative. Cynefin: Complicated, because analysis of the team's authority scope picks the route for each issue. Rubric: three criteria with weights and a pass threshold of 2.5 of 3 scored against recorded retro notes.

| Criterion | Weight | Pass needs evidence of |
|---|---|---|
| Issue clarity | 1 | The issue is written with an example |
| Authority scope | 1 | The decided owner for this issue is named |
| Straightforward | 1 | The issue applies to the last three cycles |

Expect the first visible workflow change about two weeks after the first owned experiment starts, because that is the review date set in Step 2 [judgment].

## Follow-up

Condition that changes the recommendation: if A3 is false, replace Step 4 with an escalation meeting and run no Step 2 for issues outside the team's authority.

Condition: if A1 is false, add a step to produce written output before Step 2.
