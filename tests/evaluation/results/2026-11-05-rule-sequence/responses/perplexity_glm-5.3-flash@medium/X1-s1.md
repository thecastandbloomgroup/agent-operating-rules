## Headline

Add a measurement loop first, then change the prompt; do not change the summariser today.

- Agents' "sometimes wrong" hides several failure types, so we must define and count them.
- A flag button and a log format turn agent opinion into a metric within two weeks.
- A weighted rubric scores faithfulness, completeness, and tone against the ticket.
- Prompt changes then run as small trials with a baseline, threshold, and sample size.

## Background

A support tool uses an LLM (large language model) summariser. Agents report errors: "sometimes wrong". No metric, log, or error count exists. The request is to make the summariser better.

## Relevance

Without a metric, any prompt change is a guess, and nobody can confirm it worked. An agent trusting a wrong summary answers a customer badly, so the risk now sits on the customer, not the tool [judgment].

## Information

A careful reviewer asks four things, and the material answers none of them: what "wrong" means, how often errors occur, whether we can add logging, and how many summaries the tool produces.

Assumption log:

A1. "Wrong" means one of four failure types: a wrong fact, a missing point, a wrong tone, or an unclear sentence. Why not measured: the material does not state it. Validate by: ask two agents for three example summaries. If wrong: prompt tests target the wrong failure type.

A2. The tool can accept a logging hook and a flag button. Why not measured: the material does not state the architecture. Validate by: ask the tool owner. If wrong: replace Step 3 with a weekly manual export of 50 summaries.

A3. The tool produces at least 50 summaries per week. Why not measured: the material does not state the volume. Validate by: ask the tool owner. Validate cost: one question, so below the decision value. If wrong: extend the sampling window.

However, each failure type needs different fixes, so counting types comes before prompt work. The recommended end state follows from A1 to A3.

Alternative considered: replace the LLM with a fixed rule template. Reason it loses: rule templates cannot compress mixed-topic tickets, so the top complaint (missing or wrong content) likely persists [judgment].

## End

I recommend that we run this sequence. Step 2 MUST NOT start until Step 1 collects 100 marked summaries.

**Step 1, mark the failures (evaluative, Confused).** Increment: in one working session, pull 100 summaries from the last 30 days and mark each with one failure type and the ticket text. Blocker removed: "sometimes wrong" becomes four counted error types. Test (rubric written first): the four-type rubric from A1, cut-off: two raters agree on the type for 8 of 10 randomly checked summaries. Domain reason: Confused, because the failure types decide the next step, so this action classifies the work.

**Step 2, score with a weighted rubric (evaluative, Complicated).** Increment: in one working session, extend the rubric with weights and a pass bar: faithfulness 50%, completeness 30%, tone 20%, pass at 8 of 10 [judgment]. Blocker removed: trials get a number to compare against. Test: score 20 pairs from Step 1; cross-check agreement as in Step 1; then compute the baseline pass share over all 100. Domain reason: Complicated, deduction from standard weighted-criteria analysis [15]; the pattern breaks if raters disagree, so the cross-check runs first.

**Step 3, add the flag button and log (deterministic, Clear).** Increment: in one working session, add a "Wrong" button next to each summary and store the text plus a failure type. Blocker removed: the metric keeps growing after the study ends. Test, in Gherkin [14]:

```gherkin
Given an agent reads a summary
When the agent clicks "Wrong" and picks a failure type
Then the tool stores the summary text, the ticket ID, and the failure type
```

Domain reason: Clear, one known step, so apply it directly.

**Step 4, run one prompt trial (stochastic, Complex).** Increment: change one prompt element, for example "list every open question in the ticket", in one working session. Blocker removed: the largest error type from Step 1 gets a targeted fix. Acceptance test first: metric = pass share on the rubric; baseline = Step 2 baseline; pass threshold = baseline plus 20 percentage points; sample size = 50 summaries [judgment]. Stop condition: revert the change if the first 20 summaries score below the baseline. Domain reason: Complex, cause and effect show only after the run, so the probe stays small and capped at 50 summaries; leverage is a guess.

Conditions that change the recommendation: if A2 is false, replace Step 3 with a weekly manual export; if A1 is wrong and agents name a fifth failure type, add it to the Step 1 rubric before Step 2.
