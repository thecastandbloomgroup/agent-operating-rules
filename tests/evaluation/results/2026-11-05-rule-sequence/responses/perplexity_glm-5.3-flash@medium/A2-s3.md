## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` inside the same deploy that ships the code change, because the rename alone makes old queries fail. The statement is atomic and takes milliseconds, so timing with the app release is the only real risk. Postgres keeps views, indexes, and foreign keys valid through the rename [19]. Any application code that still sends `user_id` fails the moment the column is gone [inference].

## Background

The request is a rename of one column in one Postgres table, given while boarding a plane. Time for action is short.

## Relevance

The SQL is one line, but running it without the matching app change causes errors in production. Order and pairing decide the outcome.

## Information

**A1.** The rename must align with an app release that uses `account_id`. Why not measured: the conversation does not state the deploy state. Validate by: git search for `user_id` in release code. If wrong: the column rename forces a same-session code hotfix.

**A2.** No dynamic SQL, stored function, or analytics job reads `user_id` by name. Why not measured: no tool access to the codebase in this session. Validate by: search the codebase for `user_id`. If wrong: add a view alias or a two-step rename plan.

Views and foreign keys survive a `RENAME COLUMN` because Postgres stores their references by column number, not by name [19]. Indexes are unaffected [19].

**Alternative considered:** a new column with data copy and dual writes. It loses because the rename is atomic, instant, and requires no backfill [19].
