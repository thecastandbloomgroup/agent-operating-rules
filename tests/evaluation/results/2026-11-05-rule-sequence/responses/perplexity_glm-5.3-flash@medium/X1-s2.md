Headline

Do not tune the summarizer yet: build the metric first. Label a sample of real summaries to find which errors dominate. Agree a weighted accuracy rubric with agents. Then test prompt or model variants against that rubric.

Supporting points:

- "Sometimes wrong" is not actionable; a labeled sample converts it into error types with frequencies.
- The rubric defines "correct" so any change can be accepted or rejected by a threshold.
- Variants are cheap to test once the rubric exists; they are expensive to test without one.

Background

The support tool now produces LLM summaries for support cases. Agents report the summaries are sometimes wrong. The team has no metrics, no error log, and no baseline for accuracy.

Relevance

Without a baseline, every change is a guess and a failed rollout repeats. A one-week metric build makes each later change testable and cheap to reverse.

Information

Evidence

Theme 1: "Sometimes wrong" is a frequency claim that needs counts, not a polarity fix. No sources in the session support any frequency; the data does not yet exist [judgment].

Theme 2: Summary accuracy needs human or rubric-based review, because token-overlap scores miss factual errors. The ROUGE package measures n-gram overlap only [1]. Later work shows such scores track factual consistency poorly, so rubric-graded review is the accepted method [2], [3].

Theme 3: Multi-step design, probe, review is the standard loop for LLM output quality; the pattern is documented as process and rubric definition before measurement [3].

Assumption log

A1. Summaries are agent-facing text on a case view, not sent to customers. Why not measured: the material does not state the audience. Validate by: open the agent view and check where the summary renders. If wrong: the accuracy bar and thresholds stay the same, but the rollout adds a review gate before any customer sees it.

A2. Agents can open the full ticket, so a reviewer can check each summary against its source. Why not measured: the material does not state tool permissions. Validate by: confirm one agent session next to a reviewer. If wrong: the whole plan stops until ticket access exists, because there is no ground truth.

A3. Case volume supports a 50-case sample from recent weeks. Why not measured: volume data is not in the material. Validate by: query the ticket count for the last 30 days. If wrong: sample 20 cases over 60 days; power drops, so thresholds loosen by about 10 percentage points [judgment].

Alternative considered

Skip the review and improve the prompt now. It loses because no error distribution exists, so there is no reason to pick one fix over another and no way to know if it worked. The first week of labeling is the cheapest path to both [judgment].

End

I recommend that we run the following four steps, in this order.

Step 1. Label a failure-mode sample.

- Increment: two reviewers label 50 recent summaries with categories: wrong fact, missing key detail, extra noise, wrong tone. Two working sessions.
- Blocker it removes: "sometimes wrong" becomes a ranked list of error types with counts.
- Test (evaluative, rubric written first): criteria are category fit and sample representativeness, weights 0.8 and 0.2, pass threshold is rater agreement of 0.6 or higher (Cohen's kappa), evidence is the double-labeled sheet.
- Cynefin: Confused. The domain of the errors cannot be named yet, so this step gathers the counts that classify them. Its output decides the rest, so it is first [5].

Step 2. Agree a weighted accuracy rubric.

- Increment: with agents, set criteria and weights, for example factual accuracy 0.5, key-detail coverage 0.3, brevity and tone 0.2. Pass threshold: 90 percent of sampled summaries score 4 of 5 or higher on accuracy. One working session.
- Blocker it removes: it defines "correct", so every later variant gets an accept or reject decision.
- Test (evaluative, Kepner-Tregoe form): each criterion scored against the same 50 labeled summaries; pass if the weighted score of the current config is reproducible within 5 points by a second scorer.
- Cynefin: Complicated. The rubric follows from analysis of the step 1 counts, and leverage estimates become reliable after that analysis.
- Dependency: Step 2 MUST NOT start until the agreement threshold in Step 1 is met.

Step 3. Probe one or two variants against the rubric.

- Increment: run the current config and one changed prompt or model on the same cases. Two working sessions. Budget cap: 2 days and 60 summaries; stop early if the variant scores worse at n = 30.
- Blocker it removes: it separates real gains from taste, because the rubric decides instead of opinion.
- Test (stochastic, acceptance test written first): metric is accuracy pass rate per the step 2 rubric; baseline is the current config's pass rate; pass threshold is 15 percentage points or more above baseline at n = 30 per arm.
- Cynefin: Complex. Cause and effect between prompt changes and error counts show only afterward, so the action is a safe-to-fail probe with a capped budget; its leverage is a guess and is not used for ordering [5].
- Dependency: Step 3 MUST NOT start until the test in Step 2 passes.

Step 4. Ship the winner behind a flag and capture agent feedback.

- Increment: enable the better config on a subset of agents; add a Wrong-flag button on the summary view that stores the case ID and summary text. One working session.
- Blocker it removes: it ends the metric gap, because the failure log that was missing becomes continuous.
- Test (deterministic, Gherkin, written first):

```gherkin
Given a summary on an open case
When the agent clicks the Wrong flag
Then the system stores the case ID, summary text, and timestamp
```

- Cynefin: Clear. Storing a click and a filing choice are known rules with one best practice; the action is one step and its leverage is reliable [5].
- Dependency: Step 4 runs in parallel with Step 3 only for the flag work; the config switch itself waits for a Step 3 pass at the stated threshold.

If Step 1 shows the dominant error is missing key detail rather than wrong facts, replace the step 3 probe with a coverage-focused rubric check before any prompt change.

Follow-up

Conditions that change the recommendation:

- If summaries reach customers (A1 false), add a mandatory human review gate before enabling the switch.
- If agents lack full ticket access (A2 false), pause the plan and create ground truth first.
- If case volume is under 20 summaries per 60 days (A3 false), reduce n to 20 and state the power loss in the acceptance test.

Open questions: none asked this turn; the three conditions above cover the decision-relevant unknowns.
