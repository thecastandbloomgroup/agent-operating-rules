## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` now, inside a transaction; it takes milliseconds and is reversible. Then update every query that still says `user_id`, because the rename will break them the moment you commit.

- The rename itself is safe: Postgres changes only the catalog, so it does not rewrite table data [1].
- The risk is downstream: application code, views, and saved queries that use `user_id` start failing at runtime.
- A compatibility view can keep old queries working while you finish the code change.

## Background

The request is a column rename in the `orders` table of a live Postgres database. The user is about to board a plane and asked for a fast answer.

## Relevance

A rename commits in one command, so the window to prevent breakage is the time between commit and the next deploy. Deciding the order now avoids an outage later.

## Information

**Evidence.** Postgres documentation: `ALTER TABLE ... RENAME` changes the column name and does not rewrite stored data [1]. Renaming a column also updates the definitions of dependent views; `DROP` does not behave this way [1]. Therefore the breakage risk sits in application code and external clients, not in the database objects [judgment].

**Assumption log.**

A1. The application references the column by name in code or reports. Why not measured: the code is not in this conversation. Validate by: grep the codebase for `user_id` near `orders`. If wrong: the fix ends at Step 1.

A2. No reporting or BI tool queries this column through saved SQL. Why not measured: no tool can reach the reporting stack from here. Validate by: ask the on-call analyst. If wrong: those dashboards fail until their SQL is edited.

**Alternative considered.** Keep `user_id` and add a generated `account_id` column. It loses because it leaves two names for one value, doubles the cleanup work, and delays the goal of the rename [judgment].

## End

I recommend that we execute these three steps, in this order.

1. **Rename in a transaction.** Increment: open a transaction, run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;`, verify, then `COMMIT`. Blocker removed: the schema now matches the target name. Test (write it first, deterministic):

   ```gherkin
   Given the orders table has a column user_id
   When I run "ALTER TABLE orders RENAME COLUMN user_id TO account_id"
   Then a query selecting account_id returns rows
   And a query selecting user_id fails with "column does not exist"
   ```

   Domain: Clear. A known rule covers a known effect, so the step is one command.

2. **Find and fix named references.** Increment: phase 1, grep the codebase for `user_id` in files that touch `orders`. Phase 2, edit each match to `account_id` and open a pull request. Blocker removed: invisible call sites stop being a surprise. Test (evaluative, write the rubric before scoring): criterion "no match for `user_id` in orders code paths", weight 100%, pass threshold zero matches, evidence is the grep output. Domain: Complicated. Analysis (the grep) picks the work items; the fix follows from that analysis. Step 2 depends on Step 1, because the old name fails only after the rename exists.

3. **Smoke test the live paths.** Increment: exercise the main order pages against a staging database with the renamed column. Budget: 30 minutes. Measure: zero 500 errors on the order pages. Stop condition: any error on the order path, roll the rename back with the reverse `RENAME` command. Blocker removed: unknown runtime failures become known before production. Domain: Complex. Cause and effect (which query paths fail) show up only after the run; the budget and stop condition cap the damage. Step 3 MUST NOT start until Step 1 has passed its test.

Condition that changes this: if A2 is true, deploy a compatibility view instead of editing every report first: `CREATE VIEW orders_old AS SELECT account_id AS user_id, * FROM orders;` decrees the old name keeps working [1].

- After landing: paste the grep results, and the plan in Step 2 becomes concrete.
