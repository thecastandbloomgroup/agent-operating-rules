## Headline

Pin the versions now, with a lock file behind the pinned file.

- The two broken builds came from floating installs: an unpinned file lets pip resolve to a newer release at install time [judgment].
- Exact pins reproduce the old, working install, which turns an upgrade into a tested event instead of a surprise [judgment].
- A separate upgrade procedure keeps the pins fresh, so the fix does not freeze the project.

## Background

The project uses requirements.txt with no version pins. Upstream library updates broke the build twice last month. The request asks whether to pin.

## Relevance

Unpinned installs make the build depend on the release calendar of every dependency. Pinning moves that risk to a controlled, scheduled change.

## Information

**Evidence**

- The material reports two build failures last month after a library update. That baseline shows install-time resolution is unstable in this project. [1, from the user's message]
- Pinning tools exist to keep a base file readable and a lock file exact: pip-tools generates a lock from pinned or ranged input [S]. [2]
- The Python Packaging User Guide recommends pinning exact versions for application deployments, because it makes installs reproducible [S]. [3]
- Pinning only top-level entries is not enough in itself: transitive dependencies still float at install time unless the lock file pins them too [judgment].

**Assumption log**

- A1. The build installs with pip from requirements.txt. Why not measured: the material does not state the install tool. Validate by: read the CI and Dockerfiles for the pip call. If wrong: apply the same pin plus lock idea with that tool's lock format.
- A2. The repo has no lock file today. Why not measured: the material does not mention one. Validate by: list the repo root and CI files. If wrong: keep the existing lock file and add the upgrade step only.

**Why not just pin top-level entries**

The strongest alternative is pinning only the direct dependencies with == and leaving transitive versions open. It loses because a transitive update can still break the build, and the failure mode of last month fits that pattern as well as a direct update [judgment].
