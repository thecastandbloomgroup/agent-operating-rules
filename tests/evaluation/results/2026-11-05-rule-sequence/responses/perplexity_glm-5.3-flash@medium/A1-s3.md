## Headline

Pin all versions: yes, the project should use exact pins in requirements.txt and add a generated lock file. Three supporting points:
1. An unpinned requirement lets every new upstream release enter an unreviewed build, so two breaks in one month is the expected result, not bad luck [1].
2. Exact pins with `==` make each install reproducible, and the pin file then documents a tested set of versions [1].
3. A lock file covers transitive dependencies, which unpinned direct versions do not control.

## BRIEF

**Background**: The project installs Python libraries from requirements.txt. Nothing is pinned, and library updates broke the build twice last month.

**Relevance**: Each unpinned install accepts whatever the current newest release is [1]. Therefore the same file can produce different builds on different days, and the next update can break the build again at any time.

**Information**

Evidence:
- The pip requirements file format defines exact pins with `==` and treats an unpinned name as a bare requirement with no version constraint [1].
- The pip-tools documentation states that `pip-compile` resolves and pins the full tree, including transitive dependencies, into one file [2].
- User report from this conversation: two build failures in one month, both after a library update.
- [inference] The pinning principle applies to any pip-based project, so the fix is tool independent.

Assumptions:
- A1. The project installs dependencies with pip from requirements.txt. Why not measured: the user has not answered. Validate by: read the build script or container file. If wrong: the pin syntax changes, but the principle holds.
- A2. Some breakage came from transitive dependencies, not only direct ones. Why not measured: no error logs in the conversation. Validate by: read the two build logs and the diff of changed versions. If wrong: pinning direct dependencies still fixes the direct path, and the lock file in Step 2 fixes the transitive path.

Alternative considered: looser pins with an upper bound, for example `package>=2.0,<3`. This loses because new patch releases still enter the build without review, and review effort then lands on unplanned build failures instead of planned upgrades [2].

**End**

I recommend that we pin every version and gate the build on an exact match. Actions, in order:

1. Pin each direct dependency with `==` and the exact version in requirements.txt.
   - Increment: one edited file, one session. Blocker removed: unknown, varying versions on each install.
   - Test, kind deterministic, write first:
     ```gherkin
     Given a clean virtual Python environment
     When the build runs pip install -r requirements.txt, then pip freeze
     Then every frozen line matches a line in requirements.txt
     ```
   - Cynefin domain: Clear. Reason: pip defines the pin rule, so we deduce the fix from that rule [1].

2. Generate a fully pinned lock file with `pip-compile` from the direct pins [2].
   - Increment: one generated file plus one command in the build. Blocker removed: uncontrolled transitive dependencies.
   - Test, deterministic:
     ```gherkin
     Given a clean environment built from the lock file
     When a second clean environment installs the same file
     Then both pip freeze outputs match line for line
     ```
   - Cynefin domain: Complicated. Reason: more than one good lock tool exists, so analysis picks one; a wrong tool choice, not the method, is the breakable part.

3. Add a CI job that builds from requirements.txt in a clean environment on every merge.
   - Increment: one pipeline job. Blocker removed: silent version drift entering the main branch.
   - Test, deterministic:
     ```gherkin
     Given a merge request with changed dependencies
     When CI runs the clean-environment build and the test suite
     Then the merge fails when the build or the suite fails
     ```
   - Cynefin domain: Clear. Deduction from rule: an exact-match gate blocks unreviewed updates.
   - Step 3 MUST NOT start until the file edits in Steps 1 and 2 pass their tests.

4. Upgrade pins on a monthly schedule with `pip-compile --upgrade`, run the full test suite, and revert on failure.
   - Increment: one upgrade session per month, capped at one hour. Blocker removed: pins growing stale.
   - Test, deterministic:
     ```gherkin
     Given the upgraded lock file
     When the full test suite runs in a clean environment
     Then the upgrade merges only when the suite passes, and the team reverts otherwise
     ```
   - Cynefin domain: Complex. Reason: which upstream version breaks the build shows only after a probe, so each upgrade is a safe-to-fail trial with a stop condition and a time budget [18]. Leverage here is a guess.

**Follow-up**

Conditions that change the recommendation: if installs come from a pre-built container image or a fully frozen cache, pinning requirements.txt adds little on its own; pin the image or cache instead. No further questions.
