**Headline**
Build the measurement first, then fix the failure mode with the highest rate under a controlled test.
- The report "sometimes wrong" names no failure type, so it cannot guide a change to the prompt or the model.
- A log of generated summaries beside agent-final texts creates a quality baseline within 10 working days.
- Changes without a baseline cannot be verified, so the log must come before any fix.

**Background**
The support tool produces a summary of each case with a language model. Agents report that some summaries are wrong, but the reports do not say which kind of wrong. The team has no error metrics and no baseline.

**Relevance**
Every prompt change is unverifiable until a baseline exists. A measured fix also restores agent trust, because each report becomes a counted error instead of an opinion.

**Information**

Analysis. The first blocker is the absence of data, not the model itself [inference]. Summariser errors fall into a small set of classes [judgment]: factual error (the summary states a fact the record does not support), omission (the summary drops a load-bearing item, for example a promised callback), and wrong focus (the summary covers trivia and skips the blocker). These three classes do not overlap, and each pair gets one main label, so the set coverage is complete.

Assumption log.
- A1. Agents are a reliable judge of summary quality. Why not measured: the material gives no calibration data. Validate by: compare downvotes against edit distance in Step 1. If wrong: replace agent labels with a sampled manual review.
- A2. The tool handles at least 50 cases in 10 working days with a summary and an agent edit. Why not measured: the user gave no volume. Validate by: query the case count once logging starts. If wrong: extend the window to 20 days.
- A3. The three error classes above cover most failures. Why not measured: no taxonomy exists in the material. Validate by: Step 2 labeling, with an "other" box. If wrong: expand the taxonomy before Step 4.

Alternative considered. Remove the summariser and return to manual summaries. It loses because agents pay back the writing time on every case, and the error rate is unknown, so removal has no supporting evidence [inference].

**I recommend that we** run the following four steps in order.

1. **Log real pairs (Confusion domain, so data decides the rest).** Instrument the tool so it stores, for each case, the generated summary, the agent's final text, the edit distance, and a timestamp. Increment: logger live in one working session. Blocker removed: no data exists, so no claim about quality can be tested. Test first, in Gherkin form [14]:
   Given a case with a generated summary,
   When the agent saves the final text,
   Then the log stores the pair with the case number and the timestamp.
   Run this step for 10 working days to collect at least 50 pairs.

2. **Label the pairs with a rubric (Complicated: analysis and skill pick the labels, because the taxonomy does not yet exist).** Increment: score 50 pairs in one working session. Blocker removed: the unclassified error reports become a ranked list of failure types. Rubric first: criteria are factual accuracy (weight 0.5), completeness (weight 0.3), and focus (weight 0.2); pass threshold is a total score of 0.8; evidence is one pass mark per item on every pair, reviewed by a second person on a 10-pair sample. Step 2 MUST NOT start before the log in Step 1 holds 50 pairs.

3. **Define the metrics and the acceptance threshold (Clear: a known rule, compute the rate over labeled pairs).** Increment: a one-page metric sheet in one working session. Blocker removed: quality becomes a number, so agents' reports can be confirmed or rejected. Test first:
   Given the labeled pairs from Step 2,
   When the pipeline computes the metrics,
   Then it reports the factual error rate, the omission rate, and the focus error rate, each with the sample size.
   Baseline: the rates from Step 2, measured per error type; the goal state is the factual error rate near 0 [judgment for the target].

4. **Probe a fix for the top failure mode (Complex: cause and effect become visible only after the run, so this is a safe-to-fail probe with a cap).** Increment: one prompt change, tested on the next 50 logged pairs. Blocker removed: the highest-rate error type shrinks. Test first (stochastic): metric, factual error rate from Step 3; baseline, the Step 2 rate; pass threshold, at most half the baseline error count at a sample of 50 pairs [judgment for the threshold]. Budget: two prompt iterations over two weeks. Stop condition: no improvement after two iterations, then re-classify the error type instead of another prompt change. Step 4 MUST NOT start before Step 2 ends.

**Follow-up**
Condition that changes the recommendation: if A1 fails and agent edits do not track agent reports, replace agent labels with a sampled manual review in Step 2 and re-run it monthly.
Condition that changes the recommendation: if A2 fails and 50 pairs need more than 20 days, shorten the metric sheet to the two error types with the highest counts.
Condition that changes the recommendation: if the factual error rate is already below 0.05 per summary after Step 2, the feature is in tolerable shape, so ship Step 5 as agent-facing feedback buttons instead of prompt work.
