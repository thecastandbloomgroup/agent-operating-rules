Turn gzip compression on for this API. Uncompressed JSON leaves performance behind, because gzip shrinks JSON text by 80 to 90 percent, so a 400 KB body becomes about 40 to 80 KB (high confidence, the ratio follows from the repeated key structure in JSON) [judgment]. The server pays about 5 to 20 ms of CPU per response [judgment]. The change is one configuration entry, and all HTTP clients understand "Accept-Encoding: gzip" [1].

The API returns JSON bodies with an average size of 400 KB. The decision is whether compression is worth its CPU cost on the server.

At 400 KB per response, transfer time dominates latency for most client links. Therefore compression acts directly on response time and on transfer cost.

Numbers first. At a 10 Mbit/s client link, a 400 KB body needs about 320 ms on the wire. At 60 KB it needs about 48 ms. The saving is about 270 ms per call [inference]; the inference assumes a 10 Mbit/s link and no other bottleneck. The server CPU cost at level 5 on a 400 KB body is about 5 to 20 ms per call [judgment]. For most APIs that CPU cost is small next to the transfer saving, however this depends on load, so test before and after the change.

Alternative considered. Brotli and zstd compress 15 to 20 percent better than gzip at similar or higher CPU cost [judgment]. However, neither is supported by every API client, for example older HTTP libraries and SDKs. Therefore gzip loses the least: it works with every client today.
