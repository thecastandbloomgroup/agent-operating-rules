## Headline

Measure what happens to retrospective actions, then change the meeting so it ends with one owned action, and review that action weekly.

1. The symptom shows a break in the chain from meeting to change, so five minutes of counting shows which part fails.
2. The chain has three parts: a recorded action, a named owner, and a weekly review; one broken part makes the meeting end with nothing.
3. One owned action per meeting beats a list of five, because a list splits ownership until it vanishes [judgment].
4. If the data shows the three parts work, the discussion format itself becomes the target for a small probe.

## Background

The team holds regular retrospectives. People attend, but the output does not become change. The request asks for a remedy.

## Relevance

Meetings that produce no change cost time and hide real problems. A fix here is testable within one working session.

## Information

**Evidence.** The Scrum Guide requires the retrospective to identify the most helpful changes and to create a plan for them [1]. A meeting that ends with unowned notes does not meet that bar, so the baseline is the plan requirement, and the current state falls short of it [1]. Derby and Larsen state that a retrospective produces value through specific follow-up items that get done [2]. The most common failure in this cycle is follow-through, not the quality of discussion [judgment]. Because the stated symptom matches that pattern, the completion rate of past action items is likely (66 to 100%) below 80 percent [judgment].

**Assumption log.**

- A1. The team records who owns each action. Why not measured: the message does not state the recording practice. Validate by: check notes of the last three retrospectives. If wrong: add recording to Stage 2; the rest of the sequence holds.
- A2. The team can change its own meeting format without approval. Why not measured: no tool can reach the team charter. Validate by: ask the team lead for the decision rule. If wrong: insert one approval step; timing shifts by one cycle.
- A3. Attendance is stable across meetings. Why not measured: measuring the count costs more than this decision needs. Validate by: check attendance of the last three meetings. If wrong: run Stage 4 first, because low attendance hides quiet disagreement.

**Alternative considered.** Change the format or facilitator now, without the data step. It loses because the new format hides the true break, and the symptom returns one cycle later [judgment]. A second option, a shared change board instead of the meeting, loses because the meeting is the team's only structured place to surface cross-work issues [judgment].

## End

I recommend that we run four stages in numbered order.

1. **Stage 1 (Confused, deterministic).** Increment: in one session, read the notes of the last five retrospectives and count actions raised, owned, and done. Blocker removed: judging the meeting without data. Test written first (deterministic):
   - Given the notes of the last five retrospectives
   - When each action is checked for owner and status
   - Then a table shows the counts with less than 10 percent unknown status
   Domain: Confused, because the failure point is unknown, so this step gathers what is needed to Classify. Reason: acting first would guess.

2. **Stage 2 (Clear, deterministic).** Increment: change the agenda so the meeting ends with one action, one owner, and one due date, written on a visible board. Blocker removed: unowned item lists. Test written first:
   - Given a finished retrospective
   - When the team checks the board
   - Then exactly one action shows one owner and one date
   Domain: Clear, because a best practice with known cause and effect applies to meeting endings [2]. Stage 2 MUST NOT start before Stage 1 produces the table.

3. **Stage 3 (Clear, deterministic).** Increment: add a five-minute review of the board to one existing weekly meeting. Blocker removed: actions that die after the meeting ends. Test written first:
   - Given one week past a retrospective
   - When the team reviews the board
   - Then each action moves to done, gets a new date, or leaves the board with a recorded reason
   Domain: Clear, because cause and effect of a weekly check are known to everyone. Stage 3 MUST NOT start before Stage 2 completes.

4. **Stage 4 (Complex, stochastic).** Run Stage 4 only if the Stage 1 table shows owned actions with completion at or above 80 percent. Increment: for two meetings, collect written input before the meeting and keep every other part unchanged. Blocker removed: issues that people will not raise aloud. Acceptance test written first (stochastic): metric is the count of raised issues per meeting; baseline is the Stage 1 table; pass threshold is at least one more issue per meeting than baseline; sample size is two meetings; budget is two meetings; stop condition is a completion rate that drops below baseline. Domain: Complex, because cause and effect in discussion behavior appear only after the trial [3]. Reason: the pattern could break if written input stays as quiet as spoken input.

If Stage 1 shows items raised but never owned, Stage 2 carries the fix and Stage 3 follows as written. If one lead owns most past actions, add owner rotation to Stage 2.

## Follow-up

**Conditions that change the recommendation.** A1 or A2 false: add the approval or recording step, and keep the stage order. Stage 1 completion above 80 percent with no change from Stage 2: the problem sits in the discussion itself, so escalate Stage 4 with a second condition, such as anonymous scoring of past actions.
