# Headline

Pin the versions. Every dependency gets an exact version with `==`, plus a locked transitive dependency file, and updates happen only through a tested upgrade step. Supporting points:

1. Pinning makes each build reproducible, so a third-party release cannot break it without your action [1].
2. Pinning does not stop updates; it moves them into a deliberate, tested step [2].
3. The two breaks last month are the direct cost of the current setup [1].

# Background

The project keeps a `requirements.txt` with no version pins. A library update broke the build twice last month [1]. The request is a decision on pinning policy.

# Relevance

Unpinned installs pull the newest compatible release at build time [3]. Therefore every fresh environment today carries a risk of another silent break.

# Information

**Evidence.** Two build failures followed a third-party library update, per the request [1]. The twelve-factor method says to declare and isolate dependencies explicitly, so the code pauses when a dependency changes [2]. That matches the failure mode: the change arrived at install time, not through your own change process. Semantic versioning lets the library authors add changes without a coordinated release on your side, unpinned only if you allow it [4]. [judgment] The unpinned setup shifts the release risk of the library onto your build, for no keeping-up benefit, because upgrades still flow through a tested step under a pinning policy.

**Assumption log.**

- A1. The project installs dependencies with pip and a plain `requirements.txt`. Why not measured: the request states `requirements.txt`, and I do not know the wider tool chain. Validate by: check the repository for `pyproject.toml`, a lock file, or a CI config. If wrong: the same policy applies to the equivalent file in your tool.
- A2. The build runs the test suite or at least an import check. Why not measured: the request does not say. Validate by: read the CI configuration. If wrong: add a smoke test before Step 3 can detect bad upgrades.
- A3. The team wants to keep up with new releases. Why not measured: the request only states the failure. Validate by: ask the maintainer. If wrong: freeze the pins for the project lifetime, and Step 3 becomes optional.

**Alternative considered.** Use compatible ranges (`~=`) with a CI test run. This loses because the breaks landed before any test could catch them, in fresh environments that CI did not read the same way [1] [judgment].

# End

I recommend that we adopt exact pins with a deliberate upgrade step. Actions, in order:

1. **Pin top-level dependencies.** Step 1 small, one working session, A. Increment: add `==` versions of every top-level package, taken from the last working build, to `requirements.txt`. Blocker removed: the build stops depending on future third-party releases [2]. Test, write it first:
   ```gherkin
   Given a clean environment with Python 3.11
   When pip install -r requirements.txt runs
   Then each installed version equals the pinned version in the file
   ```
   Kind: deterministic. Cynefin: Clear, because the rule "pin for reproducibility" is known and applies in one step [2].
2. **Lock transitive dependencies.** Wait for Step 1 to pass. Increment: generate a lock or constraints file with pip-tools from the pinned top-level set [5]. Blocker removed: transitive packages can still drift and break the build even with pinned top-level entries [judgment]. Test, written first:
   ```gherkin
   Given the locked file from a passing build
   When pip installs from the join of both files
   Then the total package set equals that build
   ```
   Kind: deterministic. Cynefin: Clear.
3. **Add an upgrade runbook with a tested cadence.** Wait for Step 2. Increment: a short guide that runs `pip-compile`, then the test suite, then a commit, each month. Blocker removed: pinning removes the risk of silent updates and adds the task of scheduled ones [2]. Acceptance test first: metric, upgrade steps completed per month; baseline, 0 now; threshold, at least 1 per month; sample size, 2 months of runs. Kind: stochastic, because each future upgrade run escapes a different release and its result varies. Cynefin: Complex, because each upgrade's effect is visible only after the test run, so the cap is one upgrade session per month with a stop rule of "revert on test failure" [judgment].

If A2 is wrong, replace the test suite part of Step 3 with a minimal smoke test: import every app entry point and exit after normalizing errors. If A3 is wrong, drop Step 3 and keep Steps 1 and 2 permanent.

# Follow-up

**Conditions that change the recommendation.** If this project is a library published for others to install, pin only your dev and build dependencies, and publish compatible ranges instead, because your consumers need to resolve their own versions [4] [judgment]. If your tool is Poetry, uv, or conda, run the same policy in that tool's file (A1).
