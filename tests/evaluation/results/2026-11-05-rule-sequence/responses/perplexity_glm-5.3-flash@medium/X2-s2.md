## Headline

Treat each retrospective as a checkpoint that ships at most one small change with one owner and a test, and first run a diagnostic session to pick the cause.

- The failure has one of three causes: no item leaves with an owner, people hold back the real problem, or each item is too large for one increment. These cover the space and do not overlap.
- The fix differs by cause, therefore diagnose before changing the format.
- Measure the output, which is changes shipped per cycle, not participation in the room.

## Background

Retrospective meetings still run, but they no longer produce changes. The request asks what the team should do. The only material is the request.

## Relevance

Each cycle spends team hours on discussion without results, so the cost repeats at every cycle. A stalled retro also signals to the team that raising problems leads nowhere.

## Information

**Analysis.** Three causes are possible, and they do not overlap:

1. Output gap: the session ends with no change card, no owner, no test, and no due date. The practice literature states that a retro should end with experimental changes for the next cycle [1].
2. Input gap: people hold back, so the real problem never reaches the board. Team learning depends on the safety to raise interpersonal and process risks [2].
3. Scope gap: each item is a decision larger than one increment, so every session reopens it.

The numbers and the themes agree on the baseline: the current rate of shipped changes is 0 per cycle [inference from the request]. Qualitative grouping of retro notes, with a count per theme and one source that disagrees with each theme, follows the six-step thematic method [3]. Confidence is high for this method because it requires counts and a counterexample per theme, so it limits support from one loud voice.

**Assumption log.**

- A1. Past retros produced changes. Why not measured: the request does not state it. Validate by: review the last 10 retro outputs. If wrong: start with the output contract before the diagnostic.
- A2. Retros run on a fixed cadence. Why not measured: the request does not state it. Validate by: check the calendar. If wrong: a cadence decision comes first, because probes need cycles.
- A3. All attendees are team members. Why not measured: the request does not state it. Validate by: compare the invite list to reported attendance. If wrong: manager presence reduces candor [2], and the input cause gains weight.

**Alternative considered.** Pause retros for one cycle and restart later. It loses because it costs a full cycle to learn nothing, and it removes the standing forum without testing any cause [judgment].

## End

I recommend that we run the steps below. Steps 2 and 3 run in parallel after Step 1. Step 4 starts with Step 2.

1. **Diagnostic session** (evaluative, Confused). Increment: one 45-minute session. Blocker removed: it classifies the cause, so the rest is not a guess. Cynefin: Confused, because the counts from the session decide which cause holds. Rubric written before the work: criteria are the count of problems per theme (output, input, scope), each with weight 1; evidence is retro notes from the last 3 cycles plus one 5-minute anonymized ballot; pass threshold is one theme carrying more than 50 percent of the count.

2. **Output contract** (deterministic, Clear). Increment: one change per session, one owner, one test, due next cycle. Blocker removed: items can no longer leave without an owner. Cynefin: Clear, deduction from a known best practice [1]. Test written first:

   ```gherkin
   Given a retro session with 5 or more participants
   When the session ends
   Then exactly one change card exists with one owner, one test, and a due date in the next cycle
   ```

3. **Two-cycle probe** (stochastic, Complex). Increment: run the new format for 2 cycles. Blocker removed: it tests both the format and the diagnosed cause. Cynefin: Complex, because the pattern of behavior shows only after runs. Acceptance test written first: metric is changes shipped per cycle; baseline is 0; pass threshold is 1 shipped change in each cycle; sample size is 2 cycles with the full team. Budget is capped at 2 cycles, stop condition: if 0 changes ship in both cycles, replace this step with a scope split rule and rerun. Leverage is a guess here and is not trusted until the cycles report.

4. **Blocked-item escalation** (deterministic, Complicated). Increment: one escalation rule. Blocker removed: items that stall twice stop hiding in the wall of discussion. Cynefin: Complicated, deduction from the rule "blocked in two cycles means raise it", with the analysis that a repeat stall signals an external dependency. Test written first:

   ```gherkin
   Given a change card from a past cycle
   When two consecutive cycles end without it shipped
   Then the owner raises one specific help request to the team lead in the next session
   ```

Step 1 MUST NOT be skipped, because its output decides the inputs to Steps 2 and 3.

## Follow-up

Conditions that change the recommendation: if the diagnostic shows the input cause above 50 percent, put an anonymized ballot and a candor check [2] in front of the Step 3 probe. If A2 is false, decide the cadence first. If A1 is false, start at Step 2.
