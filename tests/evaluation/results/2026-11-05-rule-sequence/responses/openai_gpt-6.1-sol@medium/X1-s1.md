## Headline

Make the summariser better by measuring its errors, testing one targeted change, and keeping agents in control.
- First, limit harm while the error rate remains unknown. [judgment]
- Next, turn “sometimes wrong” into scored examples and a repeatable test. [judgment]
- Finally, compare one change against the current version before release. [judgment]

## Background

## Relevance

## Information

### What to measure

Use these proposed measures for each summary. Thresholds below are pilot choices, not established service requirements. [judgment]

| Measure | Definition | Purpose |
|---|---|---|
| Factual error rate | Summaries containing an unsupported or contradicted claim, divided by summaries reviewed | Detect false statements |
| Required-fact omission rate | Summaries missing a required fact, divided by summaries reviewed | Detect incomplete summaries |
| Severe error count | Errors involving sensitive disclosure, money, account access, or false action status | Identify high-harm failures |
| Agent correction time | Seconds needed to make a summary usable | Check practical value |

A summary can fail several measures; report each separately. Do not hide severe errors inside an average score. [judgment]

For each required fact, record its supporting ticket passage. Score an uncertain claim as requiring review, rather than silently accepting it. [judgment]

### Assumptions

A1. Agents can review summaries before use. Why not measured: The material does not state it. Validate by: Inspect one agent workflow. If wrong: Add a review gate first.

A2. Authorised staff can access resolved tickets for evaluation. Why not measured: The material does not state it. Validate by: Confirm access and data policy. If wrong: Use approved, redacted examples.

A3. The summary should preserve the issue, actions, current status, and next step. Why not measured: The material does not state it. Validate by: Review five tickets with an experienced agent. If wrong: Revise required facts.

**Kind:** Deterministic, meaning fixed checks have fixed expected results.

### 2. Create a small, reusable evaluation set

**Kind:** Deterministic.

**Test first:**

Given 30 authorised, resolved tickets  
When an experienced agent labels each ticket  
Then every ticket has required facts, source passages, and severe-error labels

**Work:** Randomly select 20 ordinary tickets. Add 10 reported failures, or difficult tickets if reported examples are unavailable.

Use the difficult tickets to diagnose problems. Reserve the ordinary tickets for comparison; do not tune against their expected answers.

**Capability:** This creates a baseline test set rather than relying on recollection. [judgment]

**Domain:** Clear, deduction from the fixed label requirements above.

**Completion:** Deliver the labelled set and a worksheet that calculates the four measures.

The 30-ticket size is a low-cost pilot choice, not a representative reliability estimate. [judgment]

**Dependency:** Step 2 MUST NOT start until authorised access is confirmed.

### 3. Measure the current version

**Kind:** Stochastic, meaning repeated runs can produce different outputs.

**Acceptance test first:**
- **Metric:** Evaluation completeness, plus the four quality measures.
- **Baseline:** Zero scored outputs available in this request.
- **Sample:** Two outputs per ticket, giving 60 outputs.
- **Pass threshold:** All 60 outputs receive scores, with severe errors reviewed by a second agent.

**Work:** Run the current version without changing its instructions, model, or inputs. Record their versions.

Group observed errors by cause: absent source context, misuse of available context, or an unclear summary requirement. Mark unresolved causes separately.

**Capability:** This identifies a measured baseline and evidence for the first change. [judgment]

**Domain:** Complex, induction from repeated outputs. Different ticket types or later model changes can break the observed pattern.

**Budget and stop:** Cap the probe at three staff-hours and 60 outputs. Stop on unauthorised data exposure.

**Dependency:** Step 3 MUST NOT start until Step 2 passes.

### 4. Test one targeted change against the baseline

**Kind:** Stochastic.

**Acceptance test first:**
- **Metrics:** Severe errors, factual errors, required-fact omissions, and correction time.
- **Baseline:** Step 3 results on the 20 reserved tickets.
- **Sample:** Two candidate outputs per reserved ticket, giving 40 outputs.
- **Pass threshold:** Zero observed severe errors; fewer factual failures; no increase in omissions or median correction time.

These thresholds favour factual safety over stylistic improvement. [judgment]

**Work:** Select one change using the diagnostic examples. Restore missing source context, tighten unsupported-claim instructions, or revise required facts, according to the observed cause.

Compare candidate and baseline outputs without showing reviewers which version produced them.

**Capability:** This tests whether the change improves results rather than merely changing their style. [judgment]

**Domain:** Complex, induction from a controlled comparison. Rare failures and different ticket types can break the pattern.

**Budget and stop:** Cap the probe at three staff-hours and 40 outputs. Reject the candidate if any acceptance condition fails.

**Dependency:** Step 4 MUST NOT start until Step 3 passes. Keep agent review even if the candidate passes.
