# Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;`, ideally inside a transaction after a quick dependency check.

- The rename is one deterministic statement, but views, triggers, and code referencing `user_id` will break silently.
- A 30-second lookup query finds every database object that still uses the old name.
- Boarding a plane suggests low network reliability, so run the check first, not the rename first.

## Background

The request is to rename `user_id` to `account_id` in `orders` on Postgres. Time is short because the user is about to board a plane.

## Relevance

A column rename in Postgres locks the table briefly and invalidates dependent views and rules. A missed dependency shows up later as a runtime error.

## Information

The rename command [judgment]:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Dependency check to run first [1]:

```sql
SELECT schemaname, viewname
FROM pg_catalog.pg_views
WHERE definition ILIKE '%user_id%';
```

Postgres updates dependent views' stored definitions on column rename in most cases, but foreign code (app queries, ORMs) is not updated [1]. Therefore the 70% likely failure mode is application code, not the database itself [judgment].

A1. No concurrent traffic constraints or large-table downtime concern for `orders`. Why not measured: the material does not state it. Validate by: check table size with `pg_total_relation_size('orders')`. If wrong: run during low traffic instead.

A2. Application code will be updated separately. Why not measured: not stated. Validate by: ask the team after landing. If wrong: add a compatibility view named with the old column.

Alternative considered: create a view `user_id` aliasing `account_id` for zero-downtime migration [judgment]. It loses here because it adds schema debt for a change the user wants done now; use it only if app deploy lag exists.
