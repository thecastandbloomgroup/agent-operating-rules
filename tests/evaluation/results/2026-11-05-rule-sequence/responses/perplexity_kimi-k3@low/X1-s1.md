# Headline

Build a labeled evaluation set and measure error types before changing anything, because "sometimes wrong" has unknown causes and fixes differ by cause.

- Without a baseline, no change can be proven to help [judgment].
- Errors split into MECE types: factual, omission, tone, and format; each has a different fix [judgment].
- The fastest path is: measure, classify, then tune prompt or retrieval for the dominant error type.

# Background

The support tool added an LLM-based summarizer. Agents report it is "sometimes wrong," and there are no metrics. The request is to improve it.

# Relevance

A wrong summary can send an agent toward a wrong reply, which costs customer trust. Acting without a baseline risks spending effort on the wrong fix.

# Information

## Assumption log

`A1. Errors mainly mean factual inaccuracies, not tone or format. Why not measured: the material does not state it. Validate by: agent review of 100 summaries. If wrong: the fix in Step 4 targets the wrong category.`

`A2. Ticket volume supports sampling 100 recent summaries. Why not measured: the material does not state it. Validate by: count tickets in the last two weeks. If wrong: extend the sampling window.`

`A3. The summarizer input includes the full ticket text. Why not measured: no tool can reach the system. Validate by: inspect the summarizer call. If wrong: add a retrieval step before tuning.`

## Alternative considered

Rewrite the prompt immediately. It loses because no baseline exists, so the rewrite cannot be verified and can regress other cases [judgment].

# End

I recommend that we take these actions in order:

1. **Sample and export 100 recent ticket-plus-summary pairs** (stochastic, Complex domain: induction from trials; pattern breaks if ticket mix shifts seasonally). Blocker removed: no data to measure. Acceptance test: metric = export completeness, baseline = 0, threshold = 100 pairs with fields ticket_id, full_text, summary, sample size = 100. Budget: half a working session.
2. **Score each pair with agents on four error types: factual, omission, tone, format** (evaluative, Complicated domain: analysis of cause and effect from rubric scores). Use a rubric: factual accuracy weight 50%, completeness 30%, format 20%; pass threshold = 90 of 100 summaries scoring "acceptable" overall; evidence = agent label plus quoted text span. Two agents label each item; record disagreement rate.
3. **Compute the error-rate baseline per category** (deterministic, Clear domain: a known counting rule applies). Test, written first:
   - Given 100 labeled pairs,
   - When the script counts labels per category,
   - Then it outputs one percentage per category and a top category, verified against 10 hand-counted rows.
   Step 4 MUST NOT start until this test passes.
4. **Fix the dominant category with one targeted change** (stochastic, Complex domain: safe-to-fail probe; stop condition = no improvement after 50 new samples; budget = two working sessions). For factual errors: constrain the prompt to quote only ticket text. For omissions: add a checklist of required fields to the prompt. Acceptance test: metric = category error rate, baseline = Step 3 value, threshold = 50% relative reduction, sample size = 50 held-out pairs.
5. **Add the evaluation to a weekly run so regressions surface** (deterministic, Clear domain: standard pipeline practice). Test, written first:
   - Given a fixed golden set of 50 scored pairs,
   - When the weekly job runs,
   - Then overall pass rate is reported and any drop over 5 points opens an alert.
   Depends on the prompt version from Step 4.

# Follow-up

Confidence: moderate. Basis: assumed error distribution (A1) drives Step 4; Steps 1 to 3 replace that guess with data. If A1 is false, Step 4 shifts to format or tone fixes, and Steps 1 to 3 still apply unchanged.
