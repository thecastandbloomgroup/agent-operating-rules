# Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` to rename the column.

- One DDL statement renames the column. Postgres keeps data, type, and indexes [1].
- The rename takes an ACCESS EXCLUSIVE lock. It is fast but blocks reads and writes during the millisecond it runs [1].
- Views, foreign keys, and application code that reference `user_id` will break until you update them [2].

# Relevance

# Information

The statement is one line of DDL:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Key facts with evidence:

- `ALTER TABLE ... RENAME COLUMN` rewrites no data. It changes only catalog metadata, so it completes in milliseconds regardless of table size [1].
- The statement takes an ACCESS EXCLUSIVE lock. Concurrent queries wait until it commits [1].
- Indexes on the column survive the rename [1]. Constraints whose name contains `user_id` keep working but keep the old name.
- Views, stored procedures, and foreign keys that name `user_id` fail after the rename [2]. Check them first:
  ```sql
  SELECT * FROM information_schema.view_column_usage
  WHERE table_name = 'orders' AND column_name = 'user_id';

  SELECT * FROM information_schema.constraint_column_usage
  WHERE table_name = 'orders' AND column_name = 'user_id';
  ```
- Side-by-side deployments (old and new app code live at once) break. Old code references the old name [judgment].
