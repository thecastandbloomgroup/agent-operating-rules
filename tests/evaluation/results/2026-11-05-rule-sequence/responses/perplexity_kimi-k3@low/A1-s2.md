# Headline

Yes, pin all versions in requirements.txt. Two build failures last month came from unpinned updates [1]. Pinning makes builds reproducible, which removes that failure class. A separate update step keeps you on maintained releases.

# Background

Your requirements.txt has no pinned versions. Two builds broke last month after library updates [1]. The question is whether to pin every dependency to an exact version.

# Relevance

Each unpinned dependency can change at build time without any code change from your team. Pinning stops unplanned breakage while a scheduled update step still controls security patches.

# Information

The two failures share one cause: an upstream release changed between builds [1]. This matches the known failure pattern that version pins prevent [2]. Pip supports exact pins with `==` [3]. Hash checking with `--require-hashes` adds integrity, so a tampered or corrupt package fails the build [3].

A separate tool such as Dependabot or pip-tools proposes updates on a schedule, so pinning does not freeze you out of security fixes [4]. The cost is a small, regular update review.
