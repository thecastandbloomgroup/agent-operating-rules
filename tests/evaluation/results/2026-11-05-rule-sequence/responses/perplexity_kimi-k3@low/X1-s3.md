## Headline

Build a small evaluation harness before changing the summariser, because "sometimes wrong" is not yet measurable.

- No metric exists, so no fix can be shown to help or to harm.
- A 100 to 200 case rubric-scored test set converts complaints into a measurable error rate.
- Run that test before and after each prompt or model change, changing one thing at a time.
- "Wrong" has distinct causes (fabrication, omission, wrong tone), so classify errors before fixing them.

## Background

The support tool includes an LLM summariser. Agents report it is "sometimes wrong". No metrics, no error taxonomy, and no baseline exist.

## Relevance

Any change made now cannot be validated. A measured baseline makes every later fix testable and cheap to reverse.

## Information

Evidence. The claim "sometimes wrong" is qualitative, one theme with no count or agreed definition of wrong [judgment]. LLM output varies run to run, so this is a stochastic task: conclusions need repeated trials at a set sample size [1]. Public evaluations find LLM summarisation errors split into fabrications and omissions of source content, so a single aggregate score hides the failure mode [2] (secondary source, summarises primary experiments).

Assumption log.

A1. The summariser's API, prompts, and source tickets are accessible for offline testing. Why not measured: the material does not state it. Validate by: run one ticket through the summariser from a test script. If wrong: first action becomes gaining access, no other change.

A2. Agents can label about 100 past tickets within one week. Why not measured: measuring costs more than the decision is worth before the test set is needed. Validate by: ask 3 agents to label 10 tickets each, time it. If wrong: use an LLM judge with human spot checks of 20% of cases.

A3. Tickets contain no legal block on internal reuse for evaluation. Why not measured: the material does not state it. Validate by: one question to the data or privacy owner. If wrong: anonymise tickets before the test set is built.

Alternative considered. Rewrite the prompt or swap the model immediately based on agent anecdotes. This loses because with no baseline the change cannot be shown to reduce errors, and anecdote-driven fixes commonly fix one failure while adding another [judgment].

## End

I recommend that we take these five steps:

1. Collect 150 past tickets and their human-written outcomes into a frozen test set. Blocker removed: no evaluation data. Domain: Complicated, inductive, the sample could misrepresent rare ticket types. Test (stochastic acceptance test written first): metric is case coverage, baseline 0, pass means at least 150 tickets spanning the top 5 ticket categories, sample size 150.

2. Define a rubric for "wrong": fabricated fact, omitted required fact, wrong call to action, other. Blocker removed: no shared error definition. Domain: Complicated, inductive, agents could disagree on borderline cases. Rubric written first, weights: fabrication 50%, omission 30%, call to action 20%, pass threshold: two labelers agree on at least 80% of a 20-case subset.

3. Measure the baseline: run the current summariser on all 150 cases, 3 runs each, label errors with the rubric. Depends on Steps 1 and 2 passing. Blocker removed: no error rate or failure taxonomy. Domain: Complicated, deduction from the rubric. Test (stochastic): metric is per-category error rate, pass means the report exists with rates per category and a 95% confidence interval, sample size 450 runs.

4. Fix the largest error category with one change (prompt edit, added source quoting, or model swap), chosen by that category's share of errors. Depends on Step 3. Blocker removed: the dominant failure mode. Domain: Complicated, deduction from measured error attribution. Test: same harness as Step 3, pass means the target category error rate drops by at least 30% relative and no other category rises by more than 5%, at 450 runs.

5. Add the harness to the release process so every summariser change runs it. Blocker removed: future regressions go unnoticed. Domain: Clear, a known best practice applies. Test (deterministic, Gherkin):
   Given a proposed prompt or model change,
   When the release check runs,
   Then the change is blocked unless the full test set passes the thresholds from Step 4.

If A2 is false, replace the labeling in Steps 2 and 3 with an LLM judge plus 20% human spot checks; keep thresholds identical.
