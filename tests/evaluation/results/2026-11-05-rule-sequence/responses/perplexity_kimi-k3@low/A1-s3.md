## Headline

Pin every direct and transitive dependency in requirements.txt, because unpinned versions caused two build failures last month, and pinning removes the cause while a weekly refresh job keeps versions current. This applies because the failures trace to upstream library updates [judgment]. The risk is stale dependencies, which a scheduled update job controls.

## Background

Your Python project keeps a requirements.txt with no version pins. The build broke twice last month after upstream library releases. The question is whether to pin versions.

## Relevance

Two broken builds in one month cost debugging time and block delivery. Pinning stops this class of failure at once.

## Information

**Evidence**

- Reproducible builds require identical dependency versions across runs [1].
- Python packaging guidance supports exact pins for applications, distinguishing them from libraries [2].
- Two failures last month both followed library updates (user report, above).
- Security counterpoint: frozen pins collect known vulnerabilities over time [3].

**Assumption log**

A1. The project is an application, not a published library. Why not measured: the material does not state it. Validate by: check whether setup.py or pyproject.toml marks it for PyPI. If wrong: pin in a lock file (for example, requirements.lock) and keep flexible ranges in requirements.txt instead.

A2. The CI pipeline runs the same install command that broke. Why not measured: the material does not state it. Validate by: read the CI config. If wrong: apply pinning to both pip calls.

**Alternative considered**

Using loose upper bounds (for example, `requests>=2,<3`) instead of exact pins. It loses because upper bounds still admit the breaking minor and patch updates that caused both failures [judgment], and bounds rot quietly as APIs change.
