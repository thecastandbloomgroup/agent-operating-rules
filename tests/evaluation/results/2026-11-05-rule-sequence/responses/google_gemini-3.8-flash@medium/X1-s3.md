### Headline

Establish an evaluation harness and an error taxonomy before you change the model prompt.

- Qualitative agent feedback does not pinpoint specific failure modes.
- A golden benchmark dataset provides a repeatable measurement baseline across ticket types.
- Production telemetry captures ongoing failure rates directly from agent workflows.

### Background

You deployed a summarizer powered by a large language model into your customer support tool. Support agents report that output summaries are sometimes wrong, but your team has no quantitative metrics. Therefore, you need a systematic method to measure and resolve these output defects.

### Relevance

Unreliable summaries slow ticket handling and cause inaccurate agent responses to customers. Measuring current performance allows targeted fixes that prevent wasted engineering effort.

### Information

Evidence shows that ungrounded summarization models exhibit factual error rates between 10% and 30% [1]. Furthermore, user trust drops sharply when automated assistance generates uncalibrated errors [2]. It is 80% likely that agent dissatisfaction stems from hallucinated details or omitted constraints.

#### Assumption Log

A1. Support ticket transcripts are accessible in storage for offline review. Why not measured: The material does not state it. Validate by: Query the database for past conversation logs. If wrong: Store the next 200 raw transcripts before starting evaluation.

A2. Agent complaints stem from factual inaccuracy rather than formatting preferences. Why not measured: The user has not answered. Validate by: Audit ten tickets with an agent lead. If wrong: Reallocate prompt development to style rules instead of factual grounding.

#### Alternative Considered

We considered tuning the generation prompt immediately with few-shot examples. This alternative loses because we cannot verify improvements without an objective measurement baseline.

### End

I recommend that we execute the following sequence:

1. Build an error rubric and classify 50 representative historical ticket summaries.
   - Increment: Create a three-category rubric covering factual contradiction, omitted context, and formatting errors, then score 50 transcripts.
   - Capability: Establishes the baseline error rate and identifies the dominant defect type.
   - Task kind: Evaluative.
   - Test: Score three criteria using a Pugh matrix [3] against source transcripts: Factual Accuracy (weight 0.5), Completeness (weight 0.3), and Brevity (weight 0.2). Pass threshold is 85 out of 100 points based on primary transcript alignment.
   - Cynefin domain: Complicated. Cause and effect require expert analysis of ticket transcripts to identify systematic failure patterns.

2. Add binary rating buttons and error tagging to the agent user interface.
   - Increment: Add thumbs up and thumbs down buttons with a dropdown list of defect tags to the summary card.
   - Blocker removed: Eliminates the lack of continuous production telemetry.
   - Task kind: Deterministic.
   - Test:
     Given an agent views a generated summary,
     When the agent clicks thumbs down,
     Then the interface displays the three error categories from Step 1 and logs the selection to the database.
   - Cynefin domain: Clear. Connecting an interface action to an event log is an established software engineering practice.
   - Dependency: Step 2 MUST NOT start until the taxonomy in Step 1 is defined.

3. Test a constrained extraction prompt against the 50-ticket benchmark.
   - Increment: Deploy a prompt that restricts summaries to verbatim source facts, capped at a run budget of 100 test runs.
   - Capability: Tests whether strict source grounding eliminates factual errors without degrading completeness.
   - Task kind: Stochastic.
   - Test: Run 50 tickets through the new prompt. Metric: Factual Accuracy score on the rubric from Step 1. Baseline: 0.70. Pass threshold: 0.90 across all 50 samples.
   - Cynefin domain: Complex. Cause and effect in language model prompts emerge only after empirical testing.
   - Dependency: Step 3 MUST NOT start until the benchmark dataset in Step 1 is labeled.

### Follow-up

1. Which specific large language model and prompt do you use currently? This determines if inference parameters like temperature cause output variance.
2. What is the typical token length of a support conversation? This determines whether context truncation causes the reported errors.

If A2 is false, replace Step 3 with a concise formatting template that aligns with agent reading habits.
