### Headline

Do not execute an immediate in-place rename on a live production table.
An immediate rename takes an access exclusive lock and breaks running application queries [1].
A safe column migration requires an expandable transition with dual-writing or a generated column [judgment].
This phased sequence preserves uptime and allows applications to deploy changes safely [judgment].

### Background

You requested an immediate rename of the `user_id` column to `account_id` in the `orders` PostgreSQL table.
Executing a direct database schema change right before travel introduces operational risk without monitoring [judgment].
A standard column rename in PostgreSQL requires careful coordination across database clients [1].

### Relevance

A direct rename breaks any active services that run queries against `user_id` [judgment].
Therefore, adopting a zero-downtime migration pattern prevents production outages while you are offline [judgment].

### Information

PostgreSQL supports direct column renaming with the `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` command [1].
However, that statement acquires an `ACCESS EXCLUSIVE` lock on the relation [1].
This lock blocks all concurrent reads and writes for its duration [1].
Furthermore, any running application code that references `user_id` fails immediately after execution [judgment].

Because immediate execution causes downtime, teams use multi-phase rollouts [2].
The expand-and-contract pattern adds the new column first and backfills data [2].
In PostgreSQL 12 and later versions, teams can also add a generated column or create an updatable view to bridge the change [1].
