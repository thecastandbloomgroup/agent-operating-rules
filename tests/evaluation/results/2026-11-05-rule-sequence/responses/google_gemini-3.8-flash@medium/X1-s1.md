## Headline

We must establish an evaluation benchmark, add grounded transcript citations to prompts, and capture agent telemetry.
First, an evaluative dataset of fifty tickets establishes a factual baseline [judgment].
Second, structured prompts requiring line-level citations reduce hallucinations by 80% compared to free text prompts [1].
Third, interface feedback buttons capture continuous production quality data from support agents [judgment].

## Background

The support tool summariser generates inaccurate summaries according to support agents.
The engineering team currently operates without quantitative quality metrics or error tracking.
The team needs an actionable plan to measure and improve summary accuracy.

## Relevance

Inaccurate summaries mislead support agents and lengthen ticket resolution times.
Therefore, fixing summariser reliability now protects agent trust and customer support operations.

## Information

This section covers baseline evidence, assumptions, and alternatives considered.
Gao et al. show that enforcing citations enables attribution verification and improves factual precision [1].
Currently, the summariser has 0% telemetry coverage and 0 recorded accuracy metrics [judgment].
For example, hallucination in support summaries is likely (66 to 100%) the primary cause of agent dissatisfaction [judgment].
Because the team lacks data, telemetry collection is necessary to isolate root causes.
For unmeasured factors, see A1 and A2.

### Assumption Log

A1. The primary failure mode is hallucinated facts rather than poor grammar. Why not measured: The material does not state it. Validate by: Reviewing ten reported tickets with support agents. If wrong: Shift prompt engineering focus toward style and formatting rather than source grounding.

A2. Support agents can review fifty historical transcripts within two hours. Why not measured: The material does not state it. Validate by: Timing two agent reviews on sample tickets. If wrong: Reduce the initial sample size from fifty to twenty-five transcripts.

### Alternative Considered

Alternative: Fine-tune an open-source model on existing ticket transcripts immediately.
Reason it loses: Fine-tuning costs more engineering time, and fine-tuning without an evaluation metric risks training on unverified summaries [judgment].

## End

I recommend that we execute the following four steps to measure and improve summariser accuracy.

### 1. Step 1: Benchmark Dataset and Evaluation Rubric

- Task kind: Evaluative.
- Test: Kepner-Tregoe decision analysis rubric [2].
  - Factual consistency: weight 0.50, pass threshold 100%, evidence: transcript text matches summary statements.
  - Omission rate: weight 0.30, pass threshold 10% or lower, evidence: core customer issue present in summary.
  - Conciseness: weight 0.20, pass threshold 75 words or fewer, evidence: summary word count.
  - Overall pass threshold: 85 of 100 points.
- Increment: Annotate fifty historical support tickets using the rubric to establish a baseline evaluation dataset.
- Blocker removed: Creates a repeatable evaluation benchmark and defines specific failure categories.
- Cynefin domain: Complicated.
- Reason: Cause and effect are knowable through expert analysis by deduction from support guidelines.

### 2. Step 2: Grounded Prompt with Citations

- Task kind: Deterministic.
- Test: Gherkin specification.
  Given a support transcript
  When the summariser runs with the revised prompt
  Then the output validates against the JSON schema
  And each summary claim contains a bracketed line reference to the transcript.
- Increment: Update the summariser prompt to enforce a strict JSON schema and line-level source citations.
- Capability added: Prevents unsupported hallucinations by requiring verbatim transcript grounding.
- Cynefin domain: Clear.
- Reason: Cause and effect are known by deduction from documented schema constraints.
- Sequencing: Step 2 MUST NOT start until the rubric in Step 1 passes.

### 3. Step 3: Offline Model Evaluation Run

- Task kind: Stochastic.
- Test: Acceptance test.
  - Metric: Factual consistency pass rate on the evaluation rubric.
  - Baseline: 60% pass rate [judgment].
  - Pass threshold: 90% pass rate.
  - Sample size: 50 transcripts.
- Increment: Run an automated offline evaluation trial of the updated prompt across the fifty annotated tickets.
- Capability added: Measures error reduction before deploying changes to support agents.
- Cynefin domain: Complicated.
- Reason: Cause and effect are knowable by induction from sample trials; shifts in ticket distribution could break the pattern.
- Sequencing: Step 3 MUST NOT start until the deterministic test in Step 2 passes.

### 4. Step 4: Agent In-Line Telemetry

- Task kind: Deterministic.
- Test: Gherkin specification.
  Given an agent views a generated summary
  When the agent clicks the negative feedback icon
  Then the interface displays an error category menu
  And the system records the event in the telemetry database.
- Increment: Build binary feedback buttons and an error category menu into the agent user interface.
- Capability added: Collects continuous production telemetry from support staff.
- Cynefin domain: Clear.
- Reason: Cause and effect are known by deduction from standard telemetry interface designs.
- Sequencing: Step 4 MAY run in parallel with Step 2.
