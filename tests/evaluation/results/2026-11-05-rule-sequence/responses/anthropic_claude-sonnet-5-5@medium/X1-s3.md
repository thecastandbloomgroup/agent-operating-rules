## Headline

Build a way to measure the summariser first, then fix its most common error with a tested change.

- Data: the team has no error counts, so every fix is a guess until errors are logged.
- Diagnosis: a small labelled test set shows which error type is most common.
- Fix: one targeted prompt change, scored on that test set, tests the cause.
- Safeguard: links from each summary line to its source message let agents check facts in seconds.

## Background

The support tool shows an LLM (large language model) summary of each ticket. Agents report that the summary is "sometimes wrong". The team has no metrics, so the error rate, the error types, and the cost of errors are unknown.

## Relevance

Agents who distrust the summary will skip it or reread whole tickets. That removes the time saving that justified the feature.

## Information

**Evidence**

- Agents report errors. This is one source (the request), with no number and no dissent. Confidence is low, basis: one unquantified statement.
- Abstractive summarisers often add content that the source text does not support [1].
- The strongest cause is therefore invented or wrong facts. This is [inference], and step 2 tests it.
- A 60-ticket test set takes about 3 hours per labeller at 3 minutes per summary [judgment].

**Assumption log**

A1. Agents read the summary inside the ticket and act on it. Why not measured: the material does not state it. Validate by: watch two agents handle five tickets. If wrong: drop step 4 and redesign the display.

A2. The team may use real ticket text for labelling. Why not measured: the material does not state it. Validate by: ask the data owner. If wrong: use redacted tickets in step 2.

A3. Invented or wrong facts are the main error type. Why not measured: no error data exists. Validate by: tally error types in step 2. If wrong: aim step 3 at the top error type.

A4. The team can edit the prompt and rerun the model. Why not measured: the material does not state it. Validate by: run one edited prompt in staging. If wrong: replace step 3 with a vendor request.

**Alternative considered**

Switch to a larger model or fine-tune now. It loses because without a baseline nobody can show it helps. It also costs more than a prompt change [judgment].

## End

I recommend that we take four actions, in this order. Cynefin domains follow the framework in [2].

1. **Log agent flags.** Kind: deterministic. Domain: Clear, because a known practice applies (a feedback button with logging, by deduction from a known rule).
   - Increment: add a "Wrong" button with a reason list: invented fact, wrong fact, missing key point, other.
   - Blocker removed: no error data exists.
   - Test, in Gherkin form [3], written first:

   Given an agent views the summary of a ticket
   
   When the agent clicks "Wrong" and picks "Invented fact"
   
   Then the system stores ticket ID, summary ID, model version, reason, and time

2. **Build the test set and score the baseline.** Kind: evaluative. Domain: Complicated, because analysis of labelled cases picks the practice (deduction from analysis).
   - Increment: two agents label 60 recent tickets and score each current summary.
   - Blocker removed: no baseline and no known error types.
   - Test: write the rubric first. Score each criterion against the ticket text.

   | Criterion | Weight | Evidence needed |
   |---|---|---|
   | Every stated fact appears in the ticket | 50 | Matching ticket sentence |
   | Customer request, status, next step present | 30 | Ticket text |
   | Length under 100 words, neutral tone | 20 | Word count |

   - Pass: score of 80 or more and no unsupported fact. Record the share of passing summaries as the baseline.
   - Two labellers score each summary. Report how often they agree.

3. **Probe one prompt change.** Kind: stochastic. Domain: Complex, because the effect is visible only after trials (induction from trials). The pattern breaks if errors come from the ticket data, not the prompt.
   - Increment: change the prompt so each statement must rest on a quoted ticket sentence. Leverage is a guess.
   - Blocker removed: the most common error type, found in step 2.
   - Test, written first: metric is the share of summaries with an unsupported fact. Baseline comes from step 2. Pass: at least one third lower. Sample: the same 60 tickets, three runs each.
   - Budget: one working day. Stop after three prompt variants without a pass.
   - Step 3 MUST NOT start until step 2 produces a baseline.

4. **Link summary lines to sources.** Kind: deterministic. Domain: Complicated, because engineering analysis picks the design (deduction from analysis).
   - Increment: clicking a summary line opens the supporting ticket message.
   - Blocker removed: agents cannot check a fact quickly.
   - Test:

   Given a summary line that states a fact
   
   When the agent clicks the line
   
   Then the ticket scrolls to the message that supports it

   - Step 4 MUST NOT start until the step 3 test passes, because the quotes come from the new prompt.

## Follow-up

Open questions: none.

Conditions that change the recommendation:

- If A3 is false, aim step 3 at the top error type from step 2.
- If the step 3 probe fails, repeat it for the next most common error type.
- When labelling cost becomes a limit, test an LLM judge against the human labels. One study reports over 80% agreement with humans [4].
