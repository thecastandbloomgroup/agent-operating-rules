## Headline

Measure the summariser's errors first, then fix the most common error type and test the fix against a baseline.

- No metric exists today, so no change can be shown to help.
- Agent feedback and a labelled sample will show which error types occur most.
- A fixed test set will let the team check every later change automatically.
- A capped trial on the top error type will show whether a fix works.

## Background

The support tool has a summariser built on a large language model (LLM). Agents report that it is "sometimes wrong" [1]. The team has no metrics, and the error types, error rates, and causes are unknown.

## Relevance

Agents read these summaries while they handle live tickets. An unnoticed error can send a wrong reply to a customer. Agents who stop trusting the tool will also stop using it.

## Information

**Evidence.** The only evidence is the agents' report [1]. It gives no number, so the error rate is unknown. The tag for this source is [U] because it is second-hand.

Free-text complaints do not say what "wrong" means. For example, "wrong" can mean an invented fact, a missed fact, or a poor tone. Each type needs a different fix. This is a [judgment].

Errors are likely (66 to 100%) to cluster in two or three types. The basis is [judgment] from common LLM summary faults, and the sample in Step 1 will test it.

**Assumption log.**

A1. The tool stores each ticket text and its summary. Why not measured: the material does not state it. Validate by: query the database for ten recent tickets. If wrong: add logging before Step 1.

A2. Agents can review 50 summaries in one working session. Why not measured: the user has not answered. Validate by: time five reviews. If wrong: cut the sample to 30.

A3. Agents will click a feedback button if it takes one click. Why not measured: no tool can reach agent behavior yet. Validate by: count clicks in the first week. If wrong: sample summaries for review instead.

**Alternative considered.** Swap to a larger model or rewrite the prompt now. It loses because, without a baseline, the team cannot tell whether the change helped. It could also add cost without fixing the main error type. This is a [judgment].

**Domain labels.** Each action carries a Cynefin label [2]. Cynefin sorts work by how cause and effect relate.

## End

I recommend that we take these four steps in order:

1. **Label 50 recent summaries to find the error types.**
   - Increment: two agents review 50 random summaries in one session. Each error gets one type: invented fact, missed fact, wrong order, or tone.
   - Blocker removed: nobody knows what "wrong" means.
   - Kind: evaluative. Rubric written first. Criteria and weights: faithfulness to the ticket (50), coverage of key facts (30), usefulness to the agent (20). Pass threshold: 80 of 100 per summary. Evidence: the ticket text beside the summary.
   - Domain: Confused. The error types are unknown, so this step gathers what is needed to classify the rest.
   - Step 4 MUST NOT start until this step ends.

2. **Add a one-click "Wrong" button with an error-type menu.**
   - Increment: the button and a log table, shipped to a test group.
   - Blocker removed: no ongoing metric exists.
   - Kind: deterministic. Test written first:

   ```gherkin
   Given an agent views the summary of a ticket
   When the agent clicks "Wrong" and picks an error type
   Then the system stores the ticket id, summary id, error type, and time
   ```

   - Domain: Clear. The practice is known, and deduction from a known rule applies.

3. **Build a fixed test set from the 50 labelled cases.**
   - Increment: a script that scores stored summaries against the labels.
   - Blocker removed: no way to compare a change with the baseline.
   - Kind: deterministic. Test written first:

   ```gherkin
   Given the 50 labelled cases and one set of stored summaries
   When the script runs twice
   Then both runs give the same score
   ```

   - Domain: Complicated. Analysis picks the scoring method, so the work uses deduction from known practice.
   - Step 3 MUST NOT start until Step 1 ends.

4. **Run a capped trial of one fix for the top error type.**
   - Increment: one prompt change, for example a rule to quote only facts found in the ticket. Run it on 100 new tickets.
   - Blocker removed: no evidence that any fix works.
   - Kind: stochastic. Acceptance test written first:
     - Metric: share of summaries rated correct by the Step 1 rubric.
     - Baseline: the Step 1 rate.
     - Pass threshold: baseline plus 15 percentage points. This value is a [judgment].
     - Sample size: 100 summaries.
   - Budget: two working days. Stop condition: the score drops below baseline on any 20 summaries in a row.
   - Domain: Complex. The effect of a prompt change shows only after a trial, so this is induction from trials. The pattern could break if the top error type differs by ticket category. Leverage is a guess.
   - Step 4 MUST NOT start until Steps 1 and 3 end.

If A1 is false, add logging of ticket text and summaries before Step 1.
