## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;`, but only after you check the application code, and not while you cannot watch it.

- The command is one line and fast, because it changes only the catalog [1].
- The database updates indexes, foreign keys, and views itself [1].
- Application queries that name `user_id` fail the moment the rename commits.
- You cannot fix a failure from a plane.

## Background

The request is to rename one column in the `orders` table of a Postgres database. The user boards a plane soon. The material does not say whether the database is in production or whether code reads `user_id`.

## Relevance

The rename takes seconds, but a missed reference breaks live queries. A break during the flight has no owner to fix it.

## Information

Evidence:

- `RENAME COLUMN` does not rewrite table data [1].
- It takes an ACCESS EXCLUSIVE lock, so it waits behind running queries and blocks new ones while it waits [1].
- Views, indexes, and constraints that use the column follow the new name [1].
- Application code, ORM models, reports, and ETL jobs do not follow. [judgment]
