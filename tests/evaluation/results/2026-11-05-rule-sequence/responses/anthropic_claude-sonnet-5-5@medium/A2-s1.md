## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` only when the application code is ready, which is likely after you land.

- The database change is fast: it edits metadata and does not rewrite rows.
- The risk sits outside the database: any query that names `user_id` fails after the rename.
- A short lock timeout makes the change safe on a busy table.

## Background

You asked to rename `user_id` to `account_id` in the `orders` table of a Postgres database. You board a plane soon, so you cannot watch the change or fix a failure.

## Relevance

A rename that lands before the application update breaks every query that uses the old name. You would be offline during that outage.

## Information

**Evidence**

- A column rename changes the catalog entry only. It does not rewrite the table.

  Source: PostgreSQL documentation, ALTER TABLE [1].

- The command takes an ACCESS EXCLUSIVE lock. Other sessions wait until it finishes.

  Source: PostgreSQL documentation, Explicit Locking [2].

- Views, indexes, and foreign keys refer to a column by number, so they follow the rename. [judgment]
- Function bodies and application SQL store the name as text, so they do not follow it. [judgment]
- Logical replication subscribers must also rename the column. [judgment]

A2. No logical replication or external reader uses `orders.user_id`. Why not measured: no tool can reach it. Validate by: run `SELECT * FROM pg_publication_tables WHERE tablename='orders';`. If wrong: rename the column on the subscriber first.

**Alternative considered**
