## Headline

Measure the summariser first, then fix the most common error type with a tested change.

- Measure: no metric exists, so no change can be shown to help.
- Contain: agents need a fast way to check each summary against the ticket.
- Improve: change the prompt only after the baseline error rate and error types are known.

## Background

The team added an LLM summariser to the support tool. Agents say it is "sometimes wrong" [1]. The team has no metrics, so the error rate, the error types, and the cost of each error are unknown.

## Relevance

Agents who distrust the summary stop using it, or they act on wrong facts. Both outcomes cost time and customer trust. [judgment]

## Information

**Evidence**

- Agents report that errors occur. This is one qualitative theme from one source. It has no disagreeing source and no numbers. Confidence is low, based on one statement.

  Source: the user request [1].

- LLM summaries are known to contain content that the source does not support.

  Source: a survey of hallucination in text generation [2].

- A sample of 100 summaries estimates an error rate within about 10 points at 95% confidence. [inference] The worst-case formula gives n = 1.96² × 0.25 / 0.10² ≈ 96.

- Two reviewers should agree on labels. Use Cohen's kappa and require at least 0.6. The method is defined in [3]. The 0.6 threshold is [judgment].

**Assumption log**

A1. Most errors are unsupported or missing facts, not display bugs. Why not measured: the material does not state it. Validate by: read 20 flagged summaries against their tickets. If wrong: Step 4 targets a different fix.

A2. The team can edit the prompt and log summaries. Why not measured: the material does not state it. Validate by: check access to the prompt and the database. If wrong: Step 4 becomes a request to the vendor.

A3. The tool produces at least 100 summaries per week, and policy allows review of them. Why not measured: the material does not state it. Validate by: count last week's summaries. If wrong: use a smaller sample and report a wider interval.

**Alternative considered**

Switch to a larger model now. It loses because no baseline exists, so the team cannot tell whether it helps. It also adds cost. [judgment]

## End

I recommend that we:

1. **Add a "Wrong" flag and a log.**
   - Increment: one button with a reason list, and a table that stores ticket ID, summary text, model version, reason, and time.
   - Blocker removed: no data exists.
   - Kind: deterministic. Domain: Clear. Reason: deduction from a known best practice, so one step applies.
   - Test, written first:

   ```gherkin
   Given an agent views a summary
   When the agent selects "Wrong" and a reason
   Then the log stores the ticket ID, summary text, model version, reason, and time
   ```

2. **Label a baseline of 100 summaries.** Step 2 MUST NOT start until Step 1 logs summaries.
   - Increment: two agents score 100 recent summaries. Twenty of them overlap, to compute kappa.
   - Blocker removed: the error rate and error types are unknown.
   - Kind: evaluative. Domain: Complicated. Reason: analysis of the labels picks the fix.
   - Rubric, written first:

   | Criterion | Weight | Evidence needed |
   |---|---|---|
   | Faithfulness: every claim appears in the ticket | 50% | Ticket and summary side by side |
   | Completeness: issue, status, next step present | 30% | Same pair |
   | Brevity: at most 5 sentences | 20% | Summary text |

   - Pass threshold: a summary passes at a weighted score of 80 or more, and it MUST pass Faithfulness. Kappa MUST reach 0.6 or more. Otherwise, rewrite the rubric wording and relabel the overlap.
   - Output: a baseline failure rate and a ranked list of error types.

3. **Show the source next to the summary.** Step 3 MUST NOT start until Step 2 ranks the error types.
   - Increment: show the summary beside the source thread, with a one-click link to each message used.
   - Blocker removed: agents cannot check a summary cheaply.
   - Kind: deterministic. Domain: Complicated. Reason: analysis of Step 2 picks the display that fits the top error type.
   - Test, written first:

   ```gherkin
   Given a ticket with 6 messages and a stored summary
   When an agent opens the summary
   Then the source thread is visible within one click
   And the summary shows the count and time of messages used
   ```

4. **Run a capped prompt probe.** Step 4 MUST NOT start until Step 2 gives the baseline. It runs in parallel with Step 3.
   - Increment: rewrite the prompt to target the top error type from Step 2. For example, "use only facts in the ticket" and a fixed layout of issue, status, next step.
   - Blocker removed: the error rate has no tested fix.
   - Kind: stochastic. Domain: Complex. Reason: induction from trials, because the prompt effect is visible only afterward. The pattern could break on new ticket types.
   - Leverage is a guess. Cap: two prompt variants and one working day.
   - Acceptance test, written first: metric is the Step 2 failure rate on the same 100 tickets. Baseline is the Step 2 result. Pass is a drop of at least 10 points, with Faithfulness never worse. Sample size is 100.
   - Stop: if neither variant passes, keep the old prompt and revisit A1.
