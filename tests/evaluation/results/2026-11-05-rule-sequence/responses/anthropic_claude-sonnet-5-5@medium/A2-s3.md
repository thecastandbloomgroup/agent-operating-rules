## Headline

Rename the column in one short transaction, but run it only when someone can deploy the matching app change.

- The SQL is one statement and changes only the catalog, not the stored rows [1].
- Code that still reads `user_id` fails the moment the rename commits.
- Check dependents first, because functions with text bodies do not update on their own.

## Background

The request is to rename `user_id` to `account_id` in the `orders` table of a Postgres database. The user boards a plane soon. The material does not name the environment, the schema, or the apps that use the column.

## Relevance

A rename is quick to run but not quick to undo while traffic flows. If the change lands in production while the user is offline, nobody can fix a break.

## Information

Evidence:

- `ALTER TABLE ... RENAME COLUMN` changes the name only. It takes a brief exclusive lock on the table [1].
- Views and foreign keys follow the new name, because Postgres links them by column position, not by name [judgment].
- Any app query, report, or function body that spells `user_id` breaks after the commit [inference].
