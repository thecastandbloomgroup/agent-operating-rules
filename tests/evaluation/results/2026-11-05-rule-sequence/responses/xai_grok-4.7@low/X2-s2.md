Headline
Retrospectives (meetings that inspect the team's way of work) change the work when the team reviews old actions and sets one owned next step.
Review old actions before any new topic.
End the meeting with one action, one owner, and one date.
Place that action on the board the team already uses.
Wait to change the meeting format until this loop holds for three cycles.

Background
The team still holds retrospectives, and people attend.
The work does not change after those meetings.
The request asks for a next step that restores that link.

Relevance
The next retrospective will either repeat the pattern or break it.
Therefore a meeting with no later change spends team time and lowers trust in the practice.

Information
The Scrum Guide says the team plans the most helpful changes and addresses them as soon as possible [1].
Derby and Larsen end the retrospective in a decision about what to do, and they treat that decision as the point of the meeting [2].
A retrospective that never reviews those decisions repeats the same topics [judgment].

A1. Prior actions exist, but the next retrospective does not review them. Why not measured: the material does not state it. Validate by: read the last three retrospective notes. If wrong: use the safety check in the End section instead of the review loop.
A2. The team has a shared work board. Why not measured: the material does not state it. Validate by: open the board before the next retrospective. If wrong: store the action in a shared note with an owner and a date.

The strongest alternative is a new set of retrospective activities.
It loses because a new activity does not finish actions the team already leaves open [judgment].

End
I recommend that we run three steps in order.

Step 1. Domain: Confused. The cause is not yet known, so this step gathers the facts that classify it. The inference waits on the count.
Test:
Given the notes from the last three retrospectives,
When a reviewer marks each action done or open,
Then one line records the done count and the open count.
Increment: one sitting that reads only those notes.
Blocker: an unknown cause.
Later steps use this line.

Step 2. This step MUST NOT start until the line in Step 1 exists. Domain: Clear. Apply the known rule that the team checks prior commitments before new topics. The inference is deduction from that rule.
Test:
Given the agenda for the next retrospective,
When the meeting starts,
Then the team states the status of each open action before any new topic.
Increment: the first ten minutes of one meeting.
Blocker: actions that nobody reviews.

Step 3. This step MUST NOT start until Step 2 is on the agenda. Domain: Clear. Apply the limit of one action so the team can finish it. The inference is deduction from that limit.
Test:
Given the close of that same retrospective,
When the facilitator ends the meeting,
Then the record shows one action, one owner, and one date, and that action is on the team board.
Increment: one board item added in that meeting.
Blocker: a list too long to finish.

If the Step 1 line shows that prior actions were done, replace Step 2 and Step 3 with a safety check.
Each person answers one private question on whether they can name a problem.
Use that result before any change to the meeting format.

Follow-up
If A1 is false, use the safety check above.
If A2 is false, store the action in a shared note with an owner and a date.
