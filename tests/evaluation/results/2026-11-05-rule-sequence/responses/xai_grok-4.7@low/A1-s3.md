Headline
Pin exact versions in requirements.txt before the next install.
Unpinned names let each install select a release at that moment.
Two breaks last month followed a library update.
Exact versions make the next install match a known good set.

Background
The project lists Python libraries in requirements.txt.
None of those lines pin a version.
A pin is an exact version on the library line.
The build broke twice last month after a library update.
The request asks if those versions should be pinned.

Relevance
An unpinned file can change the installed set with no code change.
Therefore the same commit can pass on one day and fail on the next.

Information
This section covers the evidence, the assumptions, and the alternative.
Per the request, the build failed twice in one month after a library update.
[1]
The baseline is zero unexpected library failures in a month.
Therefore two failures sit above that baseline.
[judgment]
PEP 508 is the dependency specification for Python packages.
A dependency may omit the version specifier.
[2]
A version specifier is the version constraint after the library name.
Without a specifier, the line does not name one release.
[judgment]
Therefore exact versions remove install-time release changes.
[judgment]
Confidence: high confidence, two observed breaks and the PEP 508 rule.
The assumption log follows.

A2. The last green build log still stores resolved versions. Why not measured: the material does not state log retention. Validate by: open the last green build log. If wrong: copy versions from a local build that passes.
The strongest alternative is a lock file before any edit to requirements.txt.
