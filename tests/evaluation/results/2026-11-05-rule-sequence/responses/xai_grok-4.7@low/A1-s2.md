Headline

Pin the full install in a lock file, and keep direct dependencies in a separate source file.

An open requirements line lets the installer select a new release on each run.
Two breaks last month followed library updates, so the open file did not hold the build.
A lock file records every installed version, including packages the source file does not name.
The source file stays short, so each update is a chosen change.

Background

The project installs from a requirements.txt file, and no line pins a version.
A library update broke the build twice last month.
The request asks whether those versions should be pinned.

Relevance

The next library release can change the build before any local code change.
A recorded install set closes that path for the versions that work today.

Information

This section covers the evidence, the assumptions, and the alternative.

The request reports two build breaks in one month after a library update [1].
Therefore the open file already failed to keep the build stable.
The file is likely (66 to 100%) an application install [judgment].

The packaging guide says to pin dependency versions in a requirements file, not in library metadata [2].
A version specifier is the version rule on a requirements line.
When a line has no version specifier, it does not limit the version [3].
Therefore a later release can enter the next install.
[inference] The installer then chooses one allowed release.

[judgment] Two breaks in one month are enough to treat the open file as the main blocker.
The basis is the count in the request, not a wider sample.

A1. The file installs an application or a service, not a library that other projects depend on. Why not measured: the material does not state it. Validate by: check whether other projects install this package from an index. If wrong: keep exact pins out of published package metadata.

A2. The two breaks came from version changes that the open file allowed. Why not measured: the material does not include the failure logs. Validate by: compare installed versions in the two build logs. If wrong: repair the local defect before the update probe.

Alternative considered: add exact pins by hand in the current requirements.txt. This loses because a hand list often omits packages pulled in by other packages, and the next edit can drift from the set that built.
