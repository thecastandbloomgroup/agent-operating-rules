## Headline

**Measure the errors first, then fix the most common error type with a tested prompt change.**

- Nobody knows the error rate today, so any change is a guess.
- Agent flags and a small expert review will give a baseline within days.
- A frozen test set will show whether each later change helps or hurts.

## Background

The team added a summariser built on a large language model (LLM). An LLM is a program that writes text from a prompt. Agents report that it is "sometimes wrong" (user message, [1]). The team has no metrics.

## Relevance

Agents who distrust the summaries will reread each ticket, which removes the time the tool should save. Without a baseline, the team cannot show that any fix works.

## Information

**Evidence**

- One theme appears: agents see wrong output. One source (the user message) supports it, and it gives no error type or rate [1]. Confidence in the cause is low, because there is one source.
- It is likely (66 to 100%) that two or three error types cause most errors, such as invented facts or missing key facts [judgment].
- A review of 50 summaries gives a 95% interval of about ±14 percentage points at a 50% error rate [inference]. That is enough to rank error types. It is not enough to prove a small gain.

**Assumption log**

A1. Tickets and summaries can be logged. Why not measured: the material does not describe the tool. Validate by: ask the tool owner to export ten pairs. If wrong: Step 1 grows to include logging work.

A2. Agents will click a "Wrong" button. Why not measured: the user has not answered. Validate by: count clicks in the first three days. If wrong: sample summaries at random in Step 2 only.

A3. The team can edit the prompt. Why not measured: the material does not state it. Validate by: read the tool configuration. If wrong: replace Step 3 with a vendor request.

A4. About 50 tickets per week are enough to label. Why not measured: the material gives no volume. Validate by: count tickets for one day. If wrong: shrink the sample sizes.

**Alternative considered:** Switch to a larger model now. It loses because there is no baseline to show a gain, and the cost rises [judgment].

## End

I recommend that we take these four actions in this order.

1. **Add an error flag and a log.**
   - Increment: one "Wrong" button with a reason list, and a log record. Complete it in one session.
   - Blocker removed: no data exists on errors.
   - Kind: deterministic. Cynefin domain: Clear. Reason: logging is a known practice, so we apply deduction from a known rule.
   - Test, written first:

   ```gherkin
   Given an agent views the summary of ticket 123
   When the agent clicks "Wrong" and picks a reason
   Then the log stores ticket id, summary, reason, prompt version, and model version
   ```

2. **Score a baseline sample.** Step 2 MUST NOT start until the test in Step 1 passes.
   - Increment: two reviewers score 50 random logged summaries against the ticket text.
   - Blocker removed: the error rate and the top error types are unknown.
   - Kind: evaluative. Cynefin domain: Complicated. Reason: expert analysis of the cases picks the error types, so we use deduction from analysis.
   - Rubric, written first: faithfulness (weight 40), missing key facts (30), wrong names or numbers (20), length (10). Each criterion needs the ticket text as evidence. A summary passes at 80 of 100 or more. Reviewers resolve differences by discussion.

3. **Run one capped prompt probe.** Step 3 MUST NOT start until Step 2 names the top error type.
   - Increment: change the prompt to target the top error type. Run it on 100 new tickets.
   - Blocker removed: no fix is tested.
   - Kind: stochastic. Cynefin domain: Complex. Reason: induction from trials; new ticket types could break the pattern. Leverage is a guess.
   - Acceptance test, written first: the metric is the faithfulness error rate. The baseline comes from Step 2. The threshold is a cut of at least 30% (relative) with no rise in the missing-fact rate. The sample is 100 tickets.
   - Budget: one working day. Stop if the first 30 tickets show no cut.

4. **Freeze a regression set.** Step 4 MUST NOT start until Step 2 is done.
   - Increment: store the labelled tickets from Step 2 and a script that scores any new prompt.
   - Blocker removed: later changes could silently make output worse.
   - Kind: deterministic. Cynefin domain: Clear. Reason: regression sets are standard practice, so we apply deduction from a known rule.
   - Test, written first:

   ```gherkin
   Given the regression set of labelled tickets
   When the team runs the set against a new prompt
   Then the report shows the error rate and lists each summary that got worse
   ```

If A3 is false, replace Step 3 with a written request to the vendor that includes the Step 2 findings.
