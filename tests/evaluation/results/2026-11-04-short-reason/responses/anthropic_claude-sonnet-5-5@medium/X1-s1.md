## Headline

Measure the summariser first, then fix its largest error type, because today nobody knows what "sometimes wrong" means.

- Evidence is missing: agents report errors, but no metric, baseline, or error list exists [1].
- Summary models can add facts that the source text does not support [2], so faithfulness is the first thing to check.
- A fix counts only if it beats a measured baseline on a fixed test set.
- Each step below fits one working session.

## Background

The team added a large language model (LLM) summariser to its support tool. Agents say its output is "sometimes wrong" [1]. The team has no metrics, no error categories, and no baseline.

## Relevance

An agent who trusts a wrong summary may give a wrong answer to a customer. An agent who distrusts it loses the time the tool should save.

## Information

**Evidence**

- The user message states the complaint and the lack of metrics [1].
- Research on abstractive summaries reports content that the source does not support [2]. This is a secondary source, so it shows a known risk, not your error rate.
- Confidence that unsupported facts are the main error type: low confidence, zero measurements on your data.
- A sample of 100 tickets gives a 95% interval of about plus or minus 6 points at a 90% pass rate (1.96 × √(0.9 × 0.1 / 100)) [inference].
- LLM judges can agree with human raters at over 80% in a published test [3]. Use human labels first, then check any automatic judge against them.

**Assumption log**

A1. Agents can see the source ticket next to the summary. Why not measured: the material does not state it. Validate by: ask one agent to demo the screen. If wrong: add a source link before any other work.

A2. Most "wrong" cases are unsupported or missing facts. Why not measured: no metrics exist. Validate by: Step 1 labels. If wrong: the probe in Step 4 targets the largest category found.

A3. The team may review real tickets under its data policy. Why not measured: the material does not state it. Validate by: ask the data owner. If wrong: redact tickets before Step 1.

A4. The team controls the prompt and the model version. Why not measured: the material does not state it. Validate by: read the tool's configuration. If wrong: Step 4 changes only the inputs sent to the vendor.

**Alternative considered**

Switch now to a larger model or fine-tune. It loses because there is no baseline to prove a gain, and the cost is high [judgment]. Removing the tool also loses: it discards the time savings with no evidence of net harm [judgment].

## End

I recommend that we do these five steps in order:

1. **Label 100 summaries.** This step is Confused, so it comes first.
   - Increment: re-run the summariser on 100 recent tickets. Two reviewers score each summary with the rubric below.
   - Blocker removed: no one knows the error types or rate.
   - Kind: evaluative. Write the rubric before the scoring.
   - Domain: Confused, because the cause of the errors is unknown and the first need is data to classify [4].

   | Criterion | Weight | Evidence needed |
   |---|---|---|
   | Faithfulness: no unsupported claim | 40 | Quote from the ticket for each claim |
   | Completeness: issue, request, status present | 30 | Checklist of the three items |
   | Correct names, numbers, dates | 20 | Match against the ticket text |
   | Brevity and clarity | 10 | Word count and reviewer note |

   Pass threshold: score of 80 or more, and no faithfulness failure. Record the pass rate and the count per error type. Step 3 MUST NOT start until both reviewers finish.

2. **Add a "wrong" flag and logging.** Run this in parallel with Step 1.
   - Increment: one button with a reason list. Log ticket ID, summary, prompt version, and model version.
   - Blocker removed: no ongoing signal from agents.
   - Kind: deterministic. Test first:
     - Given an agent views a summary
     - When the agent clicks "wrong" and picks a reason
     - Then one record is stored with the ticket ID, reason, and versions [5]
   - Domain: Clear, because logging a user action is a known practice.

3. **Freeze a golden set and set the target.**
   - Increment: pick 200 labelled tickets, including those from Step 1. Fix them as the test set.
   - Blocker removed: no baseline to compare changes against.
   - Kind: stochastic. Acceptance test first: the metric is the pass rate under the rubric, the baseline is the Step 1 rate, the threshold is a gain of 5 points, and the sample is 200 tickets.
   - Domain: Complicated, because analysis of the Step 1 error counts sets the target.

4. **Probe a fix for the largest error type.**
   - Increment: change one thing, for example the prompt to quote the ticket, or add a source check. Run it on the golden set.
   - Blocker removed: the largest error category.
   - Kind: stochastic. Accept only if the pass rate rises 5 points over baseline on 200 tickets, with no drop in other criteria.
   - Domain: Complex. Cause and effect show only after the trial. Induction from trials could break if golden tickets differ from live tickets.
   - Budget: two working days. Stop if two variants gain under 2 points. Leverage is a guess [judgment].
   - Step 5 MUST NOT start until this test passes.

5. **Release to a pilot group.**
   - Increment: enable the best variant for 10 agents for one week.
   - Blocker removed: no proof that the gain holds on live work.
   - Kind: stochastic. Acceptance test first: the "wrong" flag rate from Step 2 falls below its pre-change level over at least 200 summaries.
   - Domain: Complicated, because rollout practice is known and the Step 2 data guides it.

If A2 is false, Step 4 targets the largest category from Step 1, not faithfulness.
