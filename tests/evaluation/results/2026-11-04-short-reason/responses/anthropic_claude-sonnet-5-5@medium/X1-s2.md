## Headline

Measure the summariser first, then fix its top error type with small, capped trials.

- No metrics exist, so no change can be shown to help.
- Agent reports give themes but no error rate, so a labelled sample is needed.
- A feedback button in the tool supplies data on every ticket.
- Each fix runs as a trial against the baseline from the labelled sample.

## Background

The support tool has an LLM-based summariser (a language model that condenses a ticket thread). Agents say it is "sometimes wrong", per the user's message. The team has no metrics. The request is to make it better.

## Relevance

The team cannot improve what it cannot measure. Agents who distrust the summary may stop using it, or may act on a wrong summary.

## Information

**Evidence**

- "Sometimes wrong" is one qualitative statement. It gives no count, no error type, and no source count. [no source]
- Agent comments should be grouped into themes (for example: missing facts, invented facts, wrong tone). Count the agents behind each theme. [1]
- A sample of 100 labelled summaries gives about a 10-point margin at 95% confidence on an error rate near 50%. [inference]
- The pass threshold of 5% serious errors is a starting target. [judgment]

**Assumption log**

A1. Agents can name the error types when shown examples. Why not measured: the material does not state it. Validate by: ask three agents to label 10 summaries each. If wrong: replace Step 1 with a review by a senior agent.

A2. Ticket text and past summaries are stored and can be exported. Why not measured: no tool can reach the system. Validate by: export 10 records. If wrong: Step 1 starts with logging.

A3. The model and prompt can be changed by the team. Why not measured: the material does not state it. Validate by: ask the owner. If wrong: Step 4 becomes a vendor request.

**Alternative considered**

Switch to a larger model now. It loses because the error type is unknown, and a change without a baseline cannot be judged. [judgment]

## End

I recommend that we take these steps in order.

1. **Classify the problem (Confused: the error types are unknown, so gather data first, by induction from samples).**
   - Increment: one session. Export 100 recent tickets with summaries. Three agents label each summary as correct, missing a key fact, or containing an invented fact.
   - Blocker removed: no error taxonomy and no baseline.
   - Kind: evaluative. Rubric written first. Criteria: factual accuracy (weight 50%), coverage of key facts (30%), usefulness to the agent (20%). Evidence: the ticket text. Pass threshold: a weighted score of 80% per summary. Two labellers must agree on 90% of labels.

2. **Add a feedback control (Clear: a known pattern, applied by deduction from a rule).**
   - Increment: one thumbs-up/down button with a reason list on each summary, stored with the ticket ID.
   - Blocker removed: no ongoing data.
   - Kind: deterministic. Test first, in Gherkin form [2]:

     Given an agent views a summary
     When the agent selects "wrong" and a reason
     Then the tool stores the rating, reason, ticket ID, and summary version

   - Step 2 MAY run in parallel with Step 1.

3. **Set the baseline (Complicated: analysis of the Step 1 labels picks the metric, by deduction).**
   - Increment: compute the serious-error rate and its top error type from the Step 1 labels.
   - Blocker removed: no number to beat.
   - Kind: stochastic. Acceptance test first. Metric: share of summaries with a serious error. Baseline: the Step 1 result. Threshold: under 5%. Sample size: 100 held-out tickets.
   - Step 3 MUST NOT start until Step 1 passes its agreement check.

4. **Run one fix as a probe (Complex: effects show only after trials, so use induction; a change in ticket mix could break the pattern).**
   - Increment: change one thing aimed at the top error type, for example a prompt rule that bans facts absent from the ticket. Run it on the 100 held-out tickets.
   - Blocker removed: the top error type.
   - Kind: stochastic. Metric: serious-error rate. Baseline: Step 3. Threshold: at most half the baseline. Sample size: 100. Budget: one working day. Stop if the rate does not fall after two prompt versions.
   - Step 4 MUST NOT start until Step 3 records the baseline.
   - If A3 is false, replace Step 4 with a written request to the vendor.

Leverage for Step 4 is a guess. [judgment]
