# Headline

Measure the errors first, then fix the largest error class, and keep a live agent feedback loop.

1. No metrics exist, so step one is a labeled sample that classifies the errors.
2. A fixed evaluation set of 100 pairs gives numbers that track every later change.
3. Prompt and grounding fixes are cheap probes that this set can measure.

## Background

The team added an LLM-based summariser to a support tool. Agents report that it is sometimes wrong, in the team's words, from this session's query. No metrics exist, so the errors have no measured size or class.

## Relevance

Without a baseline, each prompt change is a guess, and no one can prove progress. A labeled sample costs about one working session [judgment].

## Information

**Evidence**

- The current measurement count is 0 runs, against a target of 1 baseline study. The source is the team's own report in this session.
- The current signal is agent anecdotes. Anecdotes show that errors exist, but they cannot give a rate or a class [judgment].
- LLM judges are an option if labeling cost is too high for a second pass. G-Eval reached higher agreement with human raters than earlier automatic metrics on summarisation tasks [19].

**Assumption log**

A1. "Sometimes wrong" means factual errors or omissions, not speed or tone. Why not measured: the material does not state it. Validate by: the error classes in Step 1. If wrong: run a latency or tone evaluation instead.

A2. About 100 reviewable ticket and summary pairs exist in the past 30 days. Why not measured: no ticket volume is given. Validate by: query the ticket store for the date range. If wrong: use a 40-pair sample and accept wider intervals.

A3. The team can change the prompt but not the model weights. Why not measured: the tool setup is not stated. Validate by: ask the tool admin. If wrong: score two vendors on the same evaluation set.

**Alternative considered**

Swap the model or fine-tune it now. It loses because a change without a baseline cannot show gain, and it costs more money sooner [judgment].

## End

I recommend that we run these steps, in this order.

1. **Label a sample.** Take 100 ticket and summary pairs from the past 30 days. Two agents read each pair and record one class: hallucination, omission, wrong emphasis, or no error. Write the rubric first: four classes with one equal-weight criterion, pair agreement above 80 percent as the pass threshold at a sample size of 100. Test: when 100 pairs are scored by two agents, at least 80 pairs get the same class from both. Kind: evaluative. Cynefin: Confused, because the error distribution decides which fix comes next.
2. **Publish the baseline.** Compute one error rate per class from the sample. Report each rate with a 95 percent interval; the half-width stays near 10 percentage points at this sample size [judgment]. Test: when 100 labeled pairs are totalled, every class has a reported rate and interval. Kind: stochastic. Cynefin: Complicated, because simple analysis of known counts gives the rates.
3. **Probe a fix** on the top error class. If hallucination leads, pass the full transcript to the model and require a facts-only section. If omission leads, add a coverage checklist to the prompt. Write the acceptance test first: metric is the class rate from Step 2, baseline is that number, threshold is a fall of 5 percentage points or more, sample size is 30 pairs. Budget: two prompt revisions. Stop when the rate does not fall across a run of 30 pairs. Kind: stochastic. Cynefin: Complex, because the effect appears only after a run, so this is a safe-to-fail probe with a cap.
4. **Add agent feedback.** Ship a one-click thumbs up and thumbs down control with three fixed reasons: wrong facts, missing facts, wrong emphasis. Kind: deterministic. Cynefin: Clear, because a best practice exists for in-tool feedback controls. Test:

   ```gherkin
   Given an open ticket with a summary
   When the agent clicks a rating and one reason
   Then the tool stores the rating, the reason, and the ticket ID
   ```

5. **Re-measure.** Rerun the same evaluation set after two weeks and compare each class rate with Step 2. Kind: stochastic. Cynefin: Complicated, for the same analysis reason as Step 2.

Sequence: Steps 3 and 4 run in parallel after Step 2. Step 5 MUST NOT start until Step 2 produces the baseline and Step 3 has run for two weeks [18]. Confidence: high that a labeled sample beats agent anecdotes as the driving signal, because a rubric gives measurable agreement between two agents [judgment].

Condition that changes this plan: if A3 is false, replace Step 3 with a vendor comparison scored on the same evaluation set.
