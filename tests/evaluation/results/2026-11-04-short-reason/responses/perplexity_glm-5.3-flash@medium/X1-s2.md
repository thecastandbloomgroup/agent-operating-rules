# Headline

Measure before you change: build a labeled baseline of real errors, then run one capped improvement probe against it.

1. Label what "wrong" means, because agents have not agreed on one error type.
2. Freeze an eval set of real tickets, then score the current output on it as a baseline.
3. Run one small probe, for example a prompt change, and accept it only when the baseline drops.
4. Keep a per-summary feedback button so the metric stays alive after this project.

Confidence in the direction: high, because the blocker is measured (no baseline at all). Confidence in the final fix: low, one probe will not settle it [judgment].

# Background

A support tool now uses a model that writes ticket summaries [1]. Agents report that the output is sometimes wrong [1]. No error metric, no baseline, and no labeled data exist today [1].

# Relevance

Without a baseline, no change can be tested, so any prompt edit or vendor fix is a guess. Measurement is cheap and it unblocks every later step.

# End

I recommend that we take the four actions below, in this order.

**Step 1. Classify failures.**

Kind: evaluative. Write the rubric first:

| Criterion | Weight | Evidence needed | Pass threshold |
|---|---|---|---|
| Factuality | 0.5 | Summary claim matches the ticket text | 90% of summaries with no factual error |
| Completeness | 0.3 | All key issues and commitments present | 80% of summaries with nothing missing |
| Tone and length | 0.2 | Fit for the support tool's summary format | 80% pass rate |

Then label the most recent 50 summaries against this rubric, with one agent per summary and one overlap set of 10 to check agreement. The output is the error taxonomy, which tells us which fix domain we are in.

Cynefin: Confused. The error type is unknown, so this gathering step classifies the problem before any fix is chosen.

**Step 2. Freeze the eval set and score the baseline.**

Kind: deterministic. Take the 50 labeled summaries, or 100 if volume allows (see A3), as a frozen set with source tickets and labels. Test:

```gherkin
Given a frozen eval set of 50 summaries with labels
When the scorer runs twice on the same set
Then both runs give the same score to two decimal places
```

Record the baseline: factual error rate, omission rate, and rubric mean score, with units of errors per summary.

Cynefin: Clear. Applying a fixed set and a fixed scorer is one known step, so leverage is easy to state.

**Step 3. Run one improvement probe. MUST NOT start until Step 2 is done.**

Kind: stochastic. Acceptance test written first:

```gherkin
Given the baseline factual error rate from Step 2
When the changed prompt runs on 50 eval-set summaries
Then the rate falls by at least 30% relative to baseline
```

Metric: factual error rate per summary. Baseline: Step 2 value. Threshold: 30% relative reduction at a sample size of 50. Budget: one changed prompt per week, capped at two versions before a stop. Change one thing only, for example the prompt or the input guard on long tickets, so the result is readable.

Cynefin: Complex. Cause and effect in prompt changes show only after a run, so this is a safe-to-fail probe, and its stop condition is the unmet threshold at week two.

**Step 4. Wire permanent feedback. CAN start in parallel after Step 2 passes its test.**

Kind: deterministic. Add a thumbs-down field on each summary that stores the error category from the Step 1 rubric, plus a weekly report of counts. Test:

```gherkin
Given a summary displayed to an agent
When the agent submits a thumbs-down with a category
Then the report shows one count for that category within 24 hours
```

Cynefin: Clear. This is one standard build step, so the leverage estimate is reliable.
