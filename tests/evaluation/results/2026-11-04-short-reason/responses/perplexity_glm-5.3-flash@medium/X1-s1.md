## Headline

Measure the failures first, then fix the largest failure mode and re-test against the baseline.

1. "Sometimes wrong" is a report, not a metric, so the first step classifies failures.
2. The fix target is the failure class with the highest count, not the loudest report.
3. Two cheap changes reduce harm now: stricter grounding and passive agent feedback.
4. Each change is tested against the same baseline, so the effect is visible.

## Background

An LLM-based summariser runs inside a support tool. Agents report that it is "sometimes wrong", with no definition of "wrong". No metrics exist, so this response builds a measurement loop and a first fix. The request is "make it better".

## Relevance

Unmeasured output erodes agent trust, and agents may then bypass the summariser or miss errors in it. A baseline makes every later change testable. [judgment]

## Information

Failure reports without data are qualitative evidence. A single theme exists: summaries lose agent trust. One source group (agents) supports it, so the confidence is low. [judgment] Thematic analysis of agent reports is the standard method for exactly this state [3] [5]. Because the failure distribution is unknown, the state is Confused: cause and effect cannot yet be classified [18].

Three metrics cover the failure space, adapted from the software quality model [17]:

- Grounding: share of summary claims present in the ticket text.
- Completeness: share of key ticket facts present in the summary.
- Acceptance: share of summaries agents keep without edits.

Assumption log:

- A1. "Wrong" means the summary states facts absent from the ticket, or misses key facts. Why not measured: the material does not state it. Validate by: tag 30 flagged summaries with a failure taxonomy. If wrong: the fix targets the wrong failure mode, and step 1 output redirects all later steps.
- A2. The ticket text contains the facts the summary needs. Why not measured: the material does not state it. Validate by: check 20 resolved tickets for facts that live only in attachments or internal notes. If wrong: grounding must include attachments, and step 2 changes scope.
- A3. Agents can tag failures in under one minute per ticket. Why not measured: the material does not state it. Validate by: ask two agents to tag for one day and measure the time. If wrong: replace tagging with passive edit-diff capture.

Alternative considered: build an automated evaluation suite first. It loses because no labelled failures or ground truth exist yet, so its scores would not predict agent trust. [judgment]

## End

I recommend that we:

**Step 1. Run a two-week failure log.** Agents tag each summary with one reason: false claim, missing fact, wrong emphasis, or too long. Increment: one shared sheet and a one-line tagging guide, set up in one session. Blocker removed: the unknown failure distribution.

- Kind: evaluative. Rubric first: criteria are tag accuracy and coverage, weights 60 and 40, pass threshold is 80% agreement when one agent re-tags 20 summaries from another, evidence is the tagged sheet.
- Cynefin: Confused. Reason: the tag counts decide which failure mode step 2 targets, so no analysis can classify the cause yet.

**Step 2. Score a baseline of 50 summaries.** The score uses the three metrics in the Information section. Increment: one session of manual scoring. Blocker removed: missing baseline for all later tests. This step must wait for step 1 data, because the key-fact checklist comes from the tag distribution.

- Kind: evaluative. Rubric first: the three metrics above, weights 50, 30, 20, pass threshold set as the number to beat by 20 relative points, evidence is the scored sheet plus the ticket text.
- Cynefin: Clear. Reason: scoring is one known procedure applied to a fixed sample.

**Step 3. Change the summariser prompt in parallel with step 2.** The prompt instructs the model to ground every sentence in ticket text and to state "no summary possible" when the ticket text is thin. Increment: one prompt edit plus 20 test tickets, done in one session. Blocker removed: the largest share of false claims, expected to be false-claim tags in step 1. [judgment]

- Kind: stochastic. Acceptance test first: metric is false claims per 100 summaries; baseline is the step 2 score; pass threshold is a 50 relative reduction from baseline; sample size is 50 summaries; budget is 200 summaries or two weeks, whichever stops first.
- Cynefin: Complex. Reason: prompt effects are visible only after runs, so this is a safe-to-fail probe with a stop condition and cap [18].

**Step 4. Add passive feedback to the tool.** Every summary gets a keep-or-edit signal, captured without extra agent work. Increment: one UI control plus one log line, one session. Blocker removed: the cost of step 1 style tagging, so measurement continues at low cost.

- Kind: deterministic. Test: given a summary the agent has viewed, when the agent edits or keeps it, then the tool logs one event with the summary id and the edit diff.

Step 3 MUST NOT stop before its threshold is met at the stated sample size. If A1 fails, add attachments to the grounding input before step 3 and re-baseline with step 2. If A3 fails, drop agent tagging and start from step 2 with edit diffs as the only signal.

## Follow-up

- Condition that changes the recommendation: A1. If the top failure class is "wrong emphasis" rather than false claims, step 3 replaces grounding rules with an emphasis rubric.
- Condition: A2. If key facts live in attachments, step 2 scores against the full ticket record, not the body text alone.
- Open question (1 of 3): how many summaries per agent per day exist now, because this sets the sample size for step 2 and the probe budget for step 3.
