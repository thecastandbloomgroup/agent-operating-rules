## Headline

Stop running another retrospective; the loop between the meeting and the work is broken, so fix the follow-through first.

- Most retrospective meetings produce usable actions; the actions die because no one owns them, tracks them, or re-reviews them.
- Carry exactly one action per retrospective into the team's own work tracker, with a named owner.
- Open every retrospective by reviewing the previous action, and measure the completion rate over three cycles.
- Run a parallel diagnosis, because a broken loop is the most common cause but not the only one.

## Background

A team holds regular retrospectives. Attendance continues, yet no behavior or process changes afterward. The request is an intervention plan.

## Relevance

Every retrospective costs the team a working hour without output today. Each untracked action also teaches the team that speaking up changes nothing, so participation decays next.

## Information

**Evidence.**

Qualitative themes from method sources [1] [2]:

1. Theme: change fails when the loop stops after the meeting. Sources agree that retrospective output must live in tracked work, not in a meeting note. The Scrum Guide rules that the agreed improvement becomes an item in the Sprint Backlog and moves to Done [3]. This contradicts the current pattern, so the strongest hypothesis sits at the hand-off.
2. Theme: withheld concerns produce hollow actions. Teams without psychological safety hide problems and avoid risks, so retro content stays shallow [4]. One source, so treat as a secondary hypothesis. The diagnosis in Step 1 tests it.
3. Baseline comparison [judgment]: untracked retro actions in most teams complete near a 0% rate, because no mechanism forces a review. Completion of backlog items, by contrast, has a review point every cycle. The gap is the failure point.

**Assumption log.**

- A1. The retros produce action items and attendees do not complete them. Why not measured: the material does not state it. Validate by: read the last three retro notes and count finished actions. If wrong: refocus on facilitation, not follow-through.
- A2. The team already has a work tracker or board. Why not measured: the material does not state it. Validate by: inspect the team's tool. If wrong: track in a shared document with the same fields.
- A3. Dissenters are absent rather than silent, so overload is rare. Why not measured: no tool can reach team belief. Validate by: the Step 1 survey. If wrong: add a capacity cap to Step 2.

**Alternative considered.**

Cancel the retrospectives and switch to continuous improvement. It loses because the hand-off, not the meeting, is the broken link [judgment]; the meeting still supplies the raw ideas that the fixed loop needs. [3]

## End

I recommend that we run the following four actions. Step 1 and Step 2 start at the next retrospective. Step 3 runs from the cycle after that, and it MUST NOT start until Step 2 has produced one tracked action.

**Step 1. Diagnose the cause first.** Increment: a 10-minute anonymous survey at the next retrospective with four options: no capacity, actions were unclear, no owner, low safety. This is the Confused action, because the true cause is unknown and this output classifies the rest. Test (evaluative, rubric first): metric is the top cause; pass when one option reaches more than half of respondents; sample is the full team; fail means treat causes as tied and run both Step 2 and a safety session.

**Step 2. Track one action per retrospective.** Increment: at the next retrospective, write one action only, with a named owner and a place on the team board. Blocker removed: actions without a home and a name. Cynefin: Clear, because the rule is public practice from the Scrum Guide [3]. Test (deterministic, written first, TDD order: test, then run it at the next retro):

```gherkin
Given the last retrospective agreed one action
When the team opens the board on the next retrospective day
Then the board shows that action with an owner and a Done field
```

If A2 is false and no board exists, replace "board" with a shared document in the test.

**Step 3. Probe the completion rate.** Increment: measure completed retro actions over three cycles. Blocker removed: no feedback signal on whether the fix works. Cynefin: Complex, because cause and effect in team habits show only after the runs. Leverage is a guess; the probe is capped at three retrospective cycles. Test (stochastic, acceptance first): metric is the completion rate of retro actions; baseline is 0%; pass threshold is 30% complete at a sample of three cycles; if the pass threshold fails, stop the probe and run a safety session based on [4], then re-measure once.

**Step 4. Close the review loop.** Increment: each retrospective opens with the previous action's status, in two minutes. Blocker removed: actions that no one re-reviews. Cynefin: Complicated, because the two-minute review is a known practice, and analysis picks where it sits; open instead of close reduces interference with new topics. Depends on Step 2: the review reads the board, so it MUST NOT start before Step 2 passes its test.

## Follow-up

Trigger for change: if the Step 1 survey names low safety or no capacity, replace Step 3 with a safety or capacity intervention and re-baseline the completion rate.
