### What to measure

Use these separate error categories. They describe proposed review rules, not observed failures. [judgment]

| Category | Definition | Example |
|---|---|---|
| Unsupported claim | The source does not support a summary claim | Invented refund approval |
| Contradiction | The summary conflicts with the source | “Resolved” when the customer still needs help |
| Missing information | The summary omits a required fact | Missing next action or deadline |
| Presentation defect | Facts remain correct, but the format fails requirements | Summary exceeds the length limit |

Mark an error **severe** when it changes the agent’s next action or misstates a financial, privacy, or account decision. [judgment]

Track:

- **Error rate:** summaries with any factual error divided by summaries reviewed.
- **Severe-error rate:** summaries with any severe error divided by summaries reviewed.
- **Required-fact coverage:** required facts present divided by required facts identified.
- **Review time:** seconds agents spend checking and correcting each summary.

These measures separate factual quality, completeness, and agent effort. [judgment]

| Criterion | Weight | Evidence needed |

| Factual accuracy | 60% | Each summary claim checked against the exact model input |
| Required-fact coverage | 30% | A support lead’s list of necessary facts |
| Format compliance | 10% | The agreed summary format and length limit |

Score each criterion from 0 to 100. Pass at a weighted score of 90, with no severe error. These are initial review thresholds. [judgment]

### 2. Add minimum safeguards

**Kind: Deterministic. Test first:**

```gherkin

Given a generated summary
When the agent opens it
Then the tool shows the source ticket and requires agent approval before use
```

**Work:** Add these two controls and run both tests. Keep the output labelled as a draft.

**Deliverable:** Tested controls that block empty-source summaries and preserve human review. These controls limit exposure; they do not prove factual accuracy. [judgment]

**Domain: Clear.** Deduction from explicit workflow rules determines whether both controls pass.

**Dependency:** Step 2 MUST follow the access and workflow checks in Step 1.

### 3. Test one fix against the current version

**Kind: Stochastic. Acceptance test first:**

- **Sample:** 20 unseen tickets, with one current-version output and one candidate output per ticket.
- **Baseline:** Current-version error rate, required-fact coverage, and median review time on those same tickets.
- **Pass threshold:** At least 30% fewer summaries with factual errors, with zero severe candidate errors.
- **Additional gates:** Required-fact coverage and median review time must not worsen.
- **Budget:** Four hours and 40 generated summaries; stop when either limit is reached.

These are pilot decision rules, not statistically proven release thresholds. [judgment]

**Work:** Change one component based on Step 1:

- If necessary facts never reach the model, repair source selection.
- If supplied facts become incorrect, test source-constrained instructions.
- If required facts disappear, test an explicit summary structure.

Have reviewers assess outputs without version labels. Record the metric differences before accepting the candidate.

If the baseline has zero factual errors, require a larger test rather than claim an improvement. [judgment]

**Deliverable:** A measured candidate decision, not an automatic production release.

**Domain: Complex.** Induction from trials guides the choice; rare cases or different ticket types can break the observed pattern.

**Dependency:** Step 3 MUST NOT start until Step 1 identifies a target and Step 2 passes.
