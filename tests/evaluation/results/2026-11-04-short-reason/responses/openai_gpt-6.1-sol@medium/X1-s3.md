## Headline

Measure the errors first, then test one targeted fix before expanding use. [judgment]

- First, keep agents responsible for checking summaries against the source conversation. [judgment]
- Next, separate factual errors, missing facts, and unclear text through a small review. [judgment]
- Finally, compare one fix against the current version using separate test cases. [judgment]

## Background

Agents report that the summariser is “sometimes wrong,” but no metrics exist. [1] That report identifies a problem, not its cause or frequency. [inference]

## Relevance

Without a baseline, a new prompt can appear better while introducing different errors. [judgment] Therefore, the first change should create evidence and limit harm, rather than assume a cause. [judgment]

## Information

### What the evidence supports

The available evidence contains one report of errors and no measured results. [1] Confidence in any specific cause is low because no source conversations or summaries are available.

Review these distinct failure types:

| Failure type | Definition | Example |
|---|---|---|
| Incorrect content | The summary contradicts or invents a fact | It says a refund happened when someone only requested it |
| Missing content | The summary excludes a required fact | It omits an unresolved customer request |
| Unclear text | The facts appear, but agents cannot use them reliably | It mixes completed actions with proposed actions |

These categories are a proposed review framework, not observed findings. [judgment]

### Assumptions

A1. Agents can check summaries before relying on them. Why not measured: The material does not state it. Validate by: Inspect one agent workflow. If wrong: Pause summary use until review exists.

A2. Authorized reviewers can access source conversations and generated summaries. Why not measured: The material does not state it. Validate by: Retrieve one approved pair. If wrong: Establish approved access before the review.

### Alternative considered

Change the prompt immediately using agent complaints. This takes less initial effort, but provides no reliable comparison or protection against new errors. [judgment]

## End

I recommend that we complete these four steps, with each increment limited to one working session.

### 1. Require source checks before agents rely on summaries

**Kind:** Deterministic.  
**Test first:**

```gherkin
Given a generated support summary
When an agent opens the summary
Then the source conversation and an unverified label are visible
```

**Increment:** Add the label and source link through the simplest available configuration. State that agents must verify facts before action.

**Blocker removed:** Agents can distinguish generated text from verified facts. [judgment]

**Domain:** Clear. Deduction from a known rule: unverified summaries require source checks.

If this test fails, pause summary use rather than imply that review protection exists.

### 2. Review 50 recent cases and identify the largest error group

**Kind:** Evaluative.  
**Rubric first:** Use this weighted rubric for each summary.

| Criterion | Weight | Evidence required |
|---|---:|---|
| Facts match the source | 50% | Source support for each factual claim |
| Required facts appear | 30% | Reviewer’s source-based list of required facts |
| Text supports the agent’s task | 20% | Clear requests, completed actions, and unresolved issues |

Score each criterion as 0, 0.5, or 1, then apply its weight. The proposed pass threshold is 90%. [judgment]

A harmful error fails regardless of score. Examples include the wrong customer, wrong financial action, or invented authorization. [judgment]

**Increment:** Review 40 randomly selected recent cases and 10 reported failures. Keep their results separate to avoid inflating the baseline.

Record the rubric scores, failure type, source evidence, and agent correction. Have a second reviewer check disputed labels.

**Blocker removed:** This replaces “sometimes wrong” with measured failure rates and examples. [judgment]

**Domain:** Complicated. Source comparison and error analysis identify the best target for a fix.

Step 2 follows Step 1. No scores exist yet; report them only after the review.

### 3. Test one fix against the current version

**Kind:** Stochastic, meaning results can vary between runs.

**Acceptance test first:**

- **Sample:** 100 separate conversations, excluded from Step 2.
- **Baseline:** Current-version results on those same conversations.
- **Primary metric:** Percentage of summaries with incorrect content.
- **Pass threshold:** At least 50% fewer incorrect summaries, with zero harmful errors.
- **Coverage constraint:** The percentage containing every required fact must not decrease.
- **Review:** Hide version names and vary presentation order.

These sample sizes and thresholds are proposed pilot settings, not established safety limits. [judgment]

**Increment:** After Step 2, change only the component linked to the largest error group.

Examples include source selection, instructions, or output format. Inspect the actual model input before choosing the change.

**Capability added:** A controlled comparison tests whether the targeted change improves results. [judgment]

**Domain:** Complex. Induction from trials tests improvement; different ticket types or model variation can break the pattern.

Treat this as a small, reversible trial. Cap it at 200 generated summaries and four reviewer-hours. Stop when either budget expires.

Do not accept the change unless the full sample passes. If the baseline has zero incorrect summaries, this test cannot establish error reduction.

### 4. Preserve the evidence and prevent repeat failures

**Kind:** Deterministic.  
**Test first:**

```gherkin
Given reviewed cases with required facts and prohibited claims
When the candidate version runs through the evaluation
Then the report shows each failure and the candidate version
```

**Increment:** Save the reviewed cases and create a repeatable evaluation report.

Record the model version, prompt version, source references, reviewer labels, and agent corrections under existing access and retention rules.

**Blocker removed:** Future changes gain a stable comparison instead of relying only on complaints. [judgment]

**Domain:** Complicated. Analysis converts reviewed failures into explicit checks and a repeatable report.

Step 4 follows Step 2 and can run alongside Step 3. Do not expand use based solely on this pilot. [judgment]
