## Headline

"Agents say it is sometimes wrong" is not an actionable problem, so the first step is to measure errors before changing the model or prompt. Once measured, fix the largest error class first with retrieval grounding, because unsupported content is the most common cause of wrong summaries [judgment]. Then add a continuous quality loop so improvements do not regress.

## Background

The team added a large language model (LLM) summariser to a support tool. Agents report vague errors, and no metrics exist. The request is to improve quality without a baseline.

## Relevance

A wrong summary can send an agent toward the wrong fix and erode trust in the tool. Measurement must come first, because prompt or model changes without a baseline cannot be shown to help.

## Information

**Evidence.** LLM summaries can contain content not present in the source (hallucination). This is a documented failure mode [1] (tertiary source; no primary study is in this session). Claim of specific rates for this deployment: no data exists, so 50% likely the dominant class is unsupported content [judgment].

**Assumption log.**

A1. Ticket text and agent-edited or accepted summaries can be logged. Why not measured: the material does not state it. Validate by: inspect one day of tool logs. If wrong: Step 1 requires a small logging change first.

A2. The summariser output is stochastic (LLM output varies run to run). Why not measured: model config not given. Validate by: run the same ticket twice and diff. If wrong: tests switch to deterministic Gherkin form.

**Alternative considered.** Switch to a different model first. It loses because there is no metric to show the new model is better, so the change is unverifiable.

## End

I recommend that we:

1. (Stochastic, Confused domain, classify first.) Define the error taxonomy and label 200 past summaries. Fields: unsupported content, missing key fact, wrong priority, other. Test (written first): metric = share of summaries with at least one error; baseline = unknown; pass = two annotators agree on 80%+ of labels (Cohen's kappa above 0.7); sample size n = 200. Why Confused: the output of this step decides every later step.

2. (Deterministic, Clear domain.) Add logging of source ticket, summary, and agent accept or edit action. Test (Gherkin):
   - Given a summarised ticket,
   - When an agent accepts or edits the summary,
   - Then the store holds source, summary, and action with a timestamp.
   Why Clear: standard instrumentation, best practice exists.

3. (Stochastic, Complicated domain.) Fix the largest error class from Step 1 with retrieval grounding, that is, pass the source text into the prompt and require the summary to cite source lines. Test: metric = error rate on the labeled set; baseline = Step 1 result; pass = error rate drops by 30% relative; sample size n = 200. Depends on Step 1 finishing. Why Complicated: prompt-design trade-offs are knowable by analysis of the Step 1 labels.

4. (Stochastic, Complex domain, capped probe.) Add an agent feedback control (thumbs up or down plus one-line reason) in the tool. Probe budget: two weeks, 5% of tickets. Stop condition: fewer than 30 responses in two weeks. Why Complex: agent adoption behavior is visible only after release, so leverage is a guess.

Step 2 and Step 4 can run in parallel. Step 3 MUST NOT start until Step 1 passes.

## Follow-up

Condition that changes the recommendation: if A1 is false, add a logging step before Step 1. If Step 1 shows the dominant class is missing facts rather than unsupported content, Step 3 changes from grounding to including the missing field in the prompt.
