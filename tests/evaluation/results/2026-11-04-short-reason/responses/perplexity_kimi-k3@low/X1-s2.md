# Headline

The fix is to measure failures first, then improve the summariser against a rubric, because "sometimes wrong" without metrics cannot be corrected. First, build a small scored test set from real tickets. Next, measure the current error rate and types. Then improve prompts or context where the errors cluster. Finally, add a continuous check so regressions surface.

# Background

An LLM summariser inside a support tool produces summaries that agents call "sometimes wrong". No baseline, error taxonomy, or target exists. The request is to make it better.

# Relevance

An unmeasured summariser erodes agent trust and can pass wrong facts to customers. A measured error rate turns a vague complaint into an engineering task with a pass threshold.

# Information

LLM summarisation errors concentrate in three classes: factual errors relative to the source, omissions of key content, and misread user intent [1].

Evaluation research shows prompt and context changes can shift accuracy by tens of percentage points, so changes must be tested, not assumed [inference].

**Assumption log**

A1. The tool stores or can log tickets with their generated summaries. Why not measured: the material does not state it. Validate by: check the data store for one day of summaries. If wrong: start with 50 tickets collected manually from agents.

A2. Ticket language is mainly English. Why not measured: the material does not state it. Validate by: sample 50 tickets and record the language. If wrong: add a language check before scoping the test set.

A3. Agents will rate summaries when given a 3 question form. Why not measured: the user has not answered. Validate by: ask two agents to rate 10 summaries each. If wrong: use automated reference checks instead of human ratings.

A4. "Sometimes wrong" means between 5% and 40% of summaries contain at least one material error. Why not measured: no metrics exist. Validate by: the baseline run in Step 1. If wrong: adjust the pass threshold, not the plan.

**Alternative considered**

Rebuild the summariser with a larger model now. This loses to measure first: without a baseline, a new model can cost more and still fail the same cases [judgment, supported by evaluation practice in 1].

# End

I recommend that we take four actions, tested in this order:

1. **Build the gold set and baseline the error rate.** Stochastic. Complex; cause and effect between prompt and accuracy are visible only after trials. Increment: sample 50 real tickets per ticket category, cap 200 total, generate summaries, and have agents score them against the rubric in the Follow-up section. Budget: two working sessions. Stop condition: 200 summaries scored. Test: metric is material-error rate, baseline to be measured, target below 5% material errors at n=200, blockers removed are the missing baseline and the error taxonomy.

2. **Classify errors, then fix the top class with a prompt and context change.** Deterministic in the mapping step, stochastic in the re-test. Complicated for selection, because the taxonomy must be analysed to pick the fix. Increment: rewrite the prompt for the dominant error class, which is factual errors or omissions per the theme in 1. Test, written before the change:
   Given the 200 ticket gold set,
   When the new prompt summarises all 200,
   Then the material-error rate drops below the Step 1 baseline by at least 30% at the same sample size.

3. **Add a streaming check.** Stochastic. Clear once the rubric exists, because a known practice of sampled review applies. Increment: flag 10% of live summaries each day, score with the same rubric, and alert when the weekly error rate passes 10%. This adds regression detection.

4. **Tune grounding and output length for the remaining errors.** Evaluative. Complicated; choice of fix follows the Step 2 analysis. Increment: score two grounding options, source quote requirements and length caps, with a rubric of accuracy weight 0.6, completeness 0.3, readability 0.1, pass at 80 of 100. Step 4 MUST NOT start until the test in Step 2 passes.

# Follow-up

**Rubric for all steps, written before the baseline run:**
- Factual accuracy: 0.5. Every claim in the summary must trace to the ticket.
- Completeness: 0.3. The summary must state the issue, the resolution state, and the next action.
- Concision: 0.2. Under 120 words.
- Pass: a summary scores 80 or more. A material error is any false claim about the issue or its state.

If A3 is false, replace human scoring in Steps 1 and 2 with automated checks against stored ticket fields and lower confidence accordingly. Confidence in the plan is likely to hold, because it follows established evaluation practice [1], but one source only supports it, so confidence is stated as likely, not near certain.

Open questions, at most three:
1. Can ticket and summary data leave the support system for offline scoring? The answer decides where Step 1 runs.
2. Which ticket categories exist today? The answer sets the stratified sample in Step 1.
