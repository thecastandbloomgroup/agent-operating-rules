Headline

A flaky build is a diagnostic problem, and the first move is to capture evidence before changing anything. First, collect the failure logs and the failure rate, because the cause cannot be chosen without data. Second, reproduce the failure locally and in CI to separate environment causes from code causes. Third, quarantine or fix only after the evidence names a cause, because blind retries hide the signal.

Background

The message reports that a build fails intermittently. No repository, CI system, error output, or failure rate was provided. Therefore the response gives a default triage plan that works for most build pipelines.

Relevance

Flaky builds cost developer time and destroy trust in the pipeline. Fixing them early prevents the team from ignoring real failures later.

Information

Evidence for why flakiness matters and for common causes:

- A 2019 Google case study reports about 1.5% of test runs were flaky, yet they consumed large engineering effort to triage [1].
- A 2020 systematic review of test flakiness lists the top cause groups as: concurrency, asynchronous waits, test order dependency, resource leaks, and environment differences [2]. That review covers 76 primary studies [2].
- State of DevOps research links unreliable pipelines to lower delivery performance, because teams start to ignore failures [inference].

Assumption log

A1. The build runs in CI and also on developer machines. Why not measured: the material does not state it. Validate by: check the CI dashboard and run one local build. If wrong: skip the environment comparison step and go straight to the failing platform.

A2. Failure rate is above zero but below 50%, that is, intermittent rather than always broken. Why not measured: no logs provided. Validate by: count pass/fail over the last 20 runs. If wrong: treat as a deterministic bug, not flakiness.

A3. The team has access to CI logs and can rerun jobs. Why not measured: the material does not state it. Validate by: open one failed run in the CI UI. If wrong: the first action becomes requesting access.

Alternative considered: the strongest alternative is to immediately retry and bump timeouts, because timeouts are a common cause. It loses because retries mask the signal: the review at [2] shows causes span five different groups, so tuning one guess rarely fixes the root cause [judgment].

End

I recommend that we:

1. Measure the failure rate: count pass/fail across the last 20 runs on the main branch. This removes the blocker of not knowing if the problem is flakiness or a real break. Cynefin domain: Clear, because counting outcomes has one known method. Task kind: deterministic. Test first:
   Given the last 20 CI runs on the main branch,
   When pass and fail counts are tallied per job,
   Then the failure rate per job is recorded as a percentage.
2. Capture one full failure log: save the complete console output, the environment details, and the commit hash from one failed run. This enables root cause analysis and cannot be skipped. Cynefin domain: Clear. Task kind: deterministic. Test first:
   Given a failed CI run,
   When its log is exported with commit hash and runner image version,
   Then the log can be replayed by any teammate without rebuilding.
3. Classify the error against the five cause groups from [2] (concurrency, async waits, order dependency, resource leaks, environment). This blocker removed is blind guessing. Cynefin domain: Complicated, because classification needs analysis of evidence. Task kind: evaluative. Rubric first, weights: 100 points total, 40 points error signature match, 30 points reproducibility pattern, 30 points correlation with environment or timing; pass threshold 60 points for a primary cause category, evidence: the log from step 2 plus two more failures.
4. Run a safe-to-fail probe on the top cause: apply the smallest fix for the classified cause on a branch, for example replacing a fixed sleep with a condition wait. Cynefin domain: Complex, because flakiness causes are visible only afterward. Probe budget: two working sessions. Stop condition: failure rate does not drop after 20 reruns. Metric: branch failure rate, baseline step 1 rate, pass threshold: rate reduced by at least half over 20 runs, sample size 20.
5. If step 4 passes, merge and monitor for one week; if it stops, reclassify with step 3 using the new log. Dependency: step 4 MUST NOT start until steps 1 through 3 complete.

Follow-up

Questions:

1. Does this happen in CI, locally, or both? The answer selects which environment evidence to compare in step 3.
2. Can you share one full failure log and the failure rate? The answer replaces assumptions A1 and A2 with facts.

Condition that changes the recommendation: if A2 is wrong and the build always fails, replace this plan with standard bug triage on the deterministic error.
