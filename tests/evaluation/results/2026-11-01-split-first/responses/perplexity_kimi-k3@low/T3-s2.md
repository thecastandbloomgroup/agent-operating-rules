## Headline

Treat this as two projects: a deterministic auth migration to JWT (JSON Web Tokens) and an evaluative conversion effort, each with its own tests. The migration has known cause and effect and can start now. The conversion goal has no baseline in the material, so its first step must measure the funnel. Cost of failure is much higher on auth, so auth gets the tighter controls.

## Background

The request bundles a session-to-JWT migration with a sign-up conversion improvement. No codebase, traffic, or funnel data was provided. These two goals differ in kind and risk.

## Relevance

Auth changes can lock out every user at once, so a staged rollout limits that risk. Conversion work without a baseline cannot prove it helped, so measurement must come first.

## Information

Evidence and facts:

- JWT is a signed token standard, RFC 7519 [1]. It removes server-side session storage but adds token revocation and key rotation problems that sessions do not have [judgment].
- JWTs cannot be invalidated server-side before expiry without extra state. Short expiry plus a refresh token is the common mitigation [1] [inference].
- No sign-up funnel metrics exist in the material. A conversion rate needs a baseline before any change [judgment].
- Mixing the two changes in one deploy makes rollback hard. If sign-ups drop or logins fail, you cannot tell which change caused it [judgment].

Assumption log:

`A1. The service is a web API with a login endpoint and server-side sessions today. Why not measured: the material does not state it. Validate by: list session store usage in the code. If wrong: adjust Step 2 scope.`

`A2. Session tokens are not used for anything beyond auth (no data stored in sessions). Why not measured: the material does not state it. Validate by: grep for session reads outside auth. If wrong: add a data migration step before Step 3.`

`A3. Sign-up conversion has an analytics tool available. Why not measured: the material does not state it. Validate by: check for an analytics SDK in the frontend. If wrong: add event logging before any funnel analysis.`

Alternative considered: use a token bucket or one combined release, shipping JWT auth and funnel changes together. It loses because a failure would be attributable to either change and a full revert would undo both [judgment].

## End

I recommend that we:

1. Write dual-auth acceptance tests for the login flow. Deterministic, Clear domain: a session and a JWT test both exist as known practice.
   - Given a registered user, When they log in, Then the server issues both a session cookie and a JWT access token with a 15 minute expiry.
   - Test first: write the tests before any migration code.

2. Add a JWT issuing path alongside sessions, with a refresh token and a signing key in a secrets store. Removes the session-store dependency one client at a time. Deterministic, Clear domain: key issuance follows RFC 7519 [1].
   - Given a valid refresh token, When the access token expires, Then a new access token is issued without re-login.
   - Step 3 MUST NOT start until every client type sends the JWT header.

3. Flip the auth check to JWT-first with session fallback, then remove sessions after two weeks with no fallback errors. Removes the dual-stacks risk. Deterministic, Complicated domain: the cutoff decision needs log analysis of fallback usage.
   - Given a request with no JWT, When sessions are removed, Then the server returns 401 and the error rate stays under 0.1% of requests.

4. Instrument the sign-up funnel as events: page view, form start, submit, verification, first login. Adds the measurement capability that A3 requires. Stochastic probe, Complex domain: which step loses users is only visible after data arrives. Budget: one working session for instrumentation, then measure for two weeks.
   - Acceptance test: funnel events land in analytics for at least 95% of sign-up sessions, sample of 500 sessions, versus a manual count baseline.

5. Change one funnel step per release, starting with the step that the data in Step 4 shows as the biggest drop. Evaluative, Complicated domain: pick the step by rubric, not preference. Rubric: drop-off rate (weight 0.5), effort to fix (weight 0.3), risk to auth (weight 0.2); pass threshold: chosen step scores highest with documented evidence.
   - Acceptance test per change: step conversion improves by at least 3 percentage points over 1,000 visits at the baseline from Step 4.
