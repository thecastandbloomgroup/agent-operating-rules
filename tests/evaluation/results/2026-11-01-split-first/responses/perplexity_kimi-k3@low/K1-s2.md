# Headline

The latency regression comes from the DB pool shrink in `config/db.yaml`: `max_size` dropped from 50 to 8 while the service still runs 32 workers, so pool waits (p95 690 ms) dominate request time [1]. Supporting points:

1. Pool acquire p95 rose from 3 ms to 690 ms, while query times stayed flat, so the bottleneck is waiting for connections, not the database [1].
2. The cache TTL drop from 300 s to 60 s raised the miss rate from 12% to 31%, which increases demand for connections [1][2].
3. The ORM `selectinload` change is not the cause; the `order_lines` query times did not regress (p95 30 ms to 26 ms) [1][3].

# Background

The p95 latency of `GET /customers/{id}/orders` rose from 120 ms to 900 ms after release 2026.10.21 [1]. The release changed the pool config, the cache TTL, and the ORM query [3].

# Relevance

Error rate rose from 0.02% to 0.40%, and 96% of the new errors are `PoolTimeout` [1]. Reverting the right change restores latency now without a prolonged investigation.

# Information

**Evidence**

- `db.pool.acquire` p95: 3 ms (window A) vs 690 ms (window B) [1]; the total p95 delta is 780 ms, and the acquire delta alone is 687 ms.
- Config: `max_size` 50 → 8, `acquire_timeout_s` 30 → 5, against 4 pods × 8 workers = 32 concurrent workers [3]. Peak DB connections from this service: 31 (A) vs 8 (B) [1].
- "Pool exhausted" warnings: 0 per hour on 2026-10-20 vs 1,800 to 2,400 per hour on 2026-10-22 [2].
- Cache miss rate: 12% vs 31% after TTL 300 s → 60 s [1][3].
- ORM query spans: `orders` p95 52 → 58 ms, `order_lines` p95 30 → 26 ms [1]. No regression there.

**Assumption log**

`A1. The new DB connection limit from ticket OPS-412 permits a per-pod pool larger than 8. Why not measured: the material does not state the limit value. Validate by: check OPS-412 and the DB's max_connections setting. If wrong: keep max_size 8 and instead raise acquire_timeout_s to 15 s and TTL to 300 s, which removes most queueing errors but leaves some queueing latency.`

`A2. The cache TTL change to 60 s is not a functional requirement. Why not measured: the diff gives no rationale for cache.yaml. Validate by: ask the cache.yaml author or check the change ticket. If wrong: keep TTL 60 s and rely on the pool fix alone.`

**Alternative considered**

The strongest alternative is to keep pool size 8 and only increase the acquire timeout. It loses because the pool is the measured constraint: 32 workers share 8 connections, so waiters grow regardless of timeout, while the capacity fix directly removes the queue [1][3].
