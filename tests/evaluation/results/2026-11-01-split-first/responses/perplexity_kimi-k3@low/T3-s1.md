## Headline

Split this into two projects: complete the JWT migration first, then run sign-up conversion as a measured experiment, because a combined change makes conversion results uninterpretable. First, JWT migration is a deterministic refactor with known risks, while conversion is stochastic and needs controlled trials. Second, shipping both at once confounds the conversion metric, so a drop cannot be attributed. Third, the migration alone removes the session store dependency, which is the larger technical blocker.

## Background

The request combines two goals: migrating the auth service from server-side sessions to JWT, and improving sign-up conversion. No architecture, traffic, or baseline data was provided.

## Relevance

Coupling a security-critical infrastructure change to a growth metric creates a rollback dilemma: a conversion bug could force a rollback of the token layer. Decoupling the two protects both.

**Alternative considered**

Do both changes in one release to save time. It loses because a conversion regression would be confounded across two changes, and a token bug would risk a sign-up outage. Two independent changes dominate one coupled change [judgment].

**Evidence basis**

The claim that paired changes confound metrics is a standard experiment-design rule [1]. JWT statelessness trades server lookup for token invalidation difficulty, a documented property [2]. Both driving claims rest on secondary sources.
