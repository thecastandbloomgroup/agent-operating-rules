## Headline
Build a measurement loop first, then change the summariser against that loop. The complaint “sometimes wrong” has three separable causes: fact errors, missing key facts, and wrong tone for support. The first release should score errors before it changes prompts, models, or retrieval. Target: cut severe factual errors while keeping agent edit time acceptable.

## Background
The support tool added a language model summariser. A language model is software that predicts text from context. Agents report wrong summaries, but no baseline, error classes, or pass threshold exist.

## Relevance
Without metrics, prompt changes can trade one failure for another. A small labeled set turns agent complaints into counts that guide the next change.

## Information
Evidence is thin, so the driving claims are judgment. Agents are primary witnesses for perceived failures, but their reports are not yet sampled or coded [1]. Three error themes cover most support-summary risk: wrong fact, missing fact, and unsafe or rude wording [judgment]. A useful first baseline is 200 recent conversations, because it fits one working session and gives error counts by class [judgment].

Assumptions:
A1. Summaries are shown to agents before customers see them. Why not measured: the material does not state it. Validate by: inspect one production ticket flow. If wrong: add customer-facing risk controls before auto-send.
A2. Source conversation text is available to the summariser and to reviewers. Why not measured: the material does not state it. Validate by: open one summary and trace each sentence to transcript lines. If wrong: add retrieval before quality scoring.
A3. Agents can spare 20 minutes per day for labels. Why not measured: the user has not answered. Validate by: run a one day pilot with five agents. If wrong: use reviewer labels from ticket edits instead of a new task.

Alternative considered: switch models first. It loses because no baseline shows whether the model, prompt, retrieval, or task definition causes the errors [judgment].

## End
I recommend that we run a two week measurement and correction cycle:

1. Create a 200 conversation gold set.
   Increment: export 200 recent tickets with summary, transcript, and agent edit.
   Blocker removed: no baseline.
   Test: evaluative rubric; criteria are factual accuracy 50%, coverage 30%, support tone 20%; pass threshold is 85% weighted score; evidence is transcript line references.
   Cynefin: Confused, because the domain is unknown until errors are classified.
2. Label failures by class and severity.
   Increment: two reviewers label each summary as wrong fact, missing fact, tone risk, or acceptable; severe means a customer can act on a false statement.
   Blocker removed: “sometimes wrong” is not countable.
   Test: deterministic acceptance. Given 200 labeled summaries, When two reviewers disagree, Then a third reviewer resolves and inter-rater agreement is recorded as percent agreement.
   Cynefin: Complicated, because trained reviewers can separate known error types.
3. Add transcript-grounded output rules.
   Increment: require every summary sentence to cite transcript line IDs and refuse when evidence is missing.
   Blocker removed: unsupported claims.
   Test: deterministic Gherkin. Given a summary sentence, When it has no transcript line ID, Then the system marks it invalid and asks for a narrower summary.
   Cynefin: Clear, because citation presence is directly checkable.
4. Run a stochastic quality gate before wider release.
   Increment: score 100 new summaries after the change against the same rubric.
   Blocker removed: regression risk from prompt or model edits.
   Test: acceptance metric; baseline is week one severe error rate; pass threshold is 50% relative reduction and no more than 10% agent major-edit rate; sample size is 100 summaries.
   Cynefin: Complex, because language output varies and needs capped trials.
