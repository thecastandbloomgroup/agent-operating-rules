# Headline

Build a small evaluation harness before changing anything, because "sometimes wrong" has four distinct causes and each needs a different fix.
First, sample 200 past summaries and label their error type by hand.
Second, pick the top error type and fix only that one.
Third, gate every future change on a measured score, not agent opinion.

## Background

A support tool now summarizes tickets with an LLM. Agents report errors. No metrics, no error taxonomy, and no ground truth exist.

## Relevance

Prompt and model changes without measurement trade one error type for another. A labeled baseline turns complaints into a ranked fix list within days.

## Information

Evidence for the plan:

- LLM summary errors fall into known classes: hallucination, omission, wrong priority, tone, and format [1]. This is secondary evidence.
- Agent complaints are qualitative. One theme ("sometimes wrong") appears with an unstated count of sources. This tells nothing about frequency [no source].
- Without a labeled sample, fix effort cannot be aimed [judgment].

Assumption log:

A1. Ticket texts, agent replies, and past summaries are stored and readable. Why not measured: the material does not state it. Validate by: query the ticket store for one ticket. If wrong: collect 50 live tickets with agent labels instead of a historical sample.

A2. Agents can spend 3 hours total on labels. Why not measured: the material does not state it. Validate by: ask the support lead. If wrong: label a 100-ticket sample instead of 200.

A3. Errors cluster. One or two types explain most complaints, 70% likely. Why not measured: no data exists. Validate by: the label distribution from Step 1. If wrong: fix the harness and input data before tuning the prompt.

Alternative considered: tune the prompt directly from agent anecdotes. This loses because anecdotes have no counts. Hallucination fixes (stricter prompt) often raise omission rates, and without a score the regression stays invisible [judgment].

## End

I recommend that we run four actions in order:

1. **Classify the domain.** Pull one ticket with its summary. Confirm access and tooling. Cynefin: Confused, because the failure mode is unknown, so this step gathers what classifies the rest. Increment: one working query returning real ticket data. Test (deterministic):
   - Given a ticket identifier from last week,
   - When the script fetches the record,
   - Then it returns the ticket text, the generated summary, and the final agent reply.

2. **Label a baseline sample.** Two agents independently label 200 sampled summaries against source tickets. Record error type per summary. Depend on Step 1. Cynefin: Complicated, because taxonomy design needs one analysis pass and then a known method applies. Increment: 200 labeled rows in a sheet. Test (stochastic): metric is inter-rater agreement (Cohen's kappa). Baseline is none. Pass threshold is kappa above 0.6. Sample size is 200 summaries. If below, sharpen label definitions and relabel 50.

3. **Fix the top error type only.** Change the prompt, the context window content, or the post-processor whichever matches the dominant type. Depend on Step 2. Cynefin: Complex, because prompt effects appear only after the change, so treat it as a probe. Budget: two working sessions. Stop condition: no score gain after two variants. Increment: one candidate change behind a feature flag. Test (stochastic): metric is error rate on the labeled 200-summary set. Baseline is the Step 2 rate for the dominant type. Pass threshold is a 20% relative drop with no other type rising. Sample size is 200.

4. **Add a standing quality gate.** Run a 50-summary labeled holdout on every prompt or model change. Depend on Step 3's harness. Cynefin: Clear, because the harness already exists and regression testing is a known practice. Increment: one script a developer runs before merge. Test (deterministic):
   - Given the 50-summary holdout and a candidate prompt,
   - When the gate script runs,
   - Then it fails the change if the error rate exceeds the Step 3 baseline.

## Follow-up

Condition that changes the plan: if A3 fails and errors are spread evenly, replace Step 3 with input-data fixes (missing ticket fields, noisy threads) and repeat Step 2 after that change.
