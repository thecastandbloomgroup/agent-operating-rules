## Headline

You cannot improve the summariser until you can measure it, so the first move is a small labeled set and an automated score. "Sometimes wrong" hides at least three failure types: wrong facts, missing facts, and wrong tone [judgment]. Each type has a different fix, so measurement decides the repair.

## Background

A support tool generates case summaries with an LLM. Agents report errors, but no metric exists. The request is to improve summary quality.

## Relevance

Without a score, every change is a guess, and quality can fall while prompt edits look like progress. A baseline makes each fix provable.

## Information

**Evidence.** LLM summarisation errors cluster into hallucination, omission, and instruction-following failure [judgment]. Grounding the summary in the source text with citations reduces unsupported claims, per general retrieval-augmented practice [1]. Typical actionable baselines: factuality score on 30 to 50 agent-labeled cases, target pass rate set by the team [no source].

**Assumption log.**

`A1. The raw ticket text is available to the evaluation pipeline. Why not measured: the material does not state it. Validate by: inspect one stored ticket record. If wrong: Step 2 changes to capture transcripts at request time.`

`A2. Agents can spend 20 minutes labeling 30 cases. Why not measured: the material does not state it. Validate by: ask the support lead. If wrong: label with the engineering team instead.`

**Alternative considered.** Replace the LLM with extractive rules. It loses because extractive text reads poorly for long tickets [judgment], and it cannot merge facts across messages, which is the main value of the summariser.

## End

1. **Build a 30-case golden set from real tickets.** Blocker removed: nothing to measure. Domain: Complicated, because picking representative cases takes analysis.
