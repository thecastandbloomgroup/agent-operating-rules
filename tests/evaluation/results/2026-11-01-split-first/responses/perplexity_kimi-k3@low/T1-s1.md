## Headline

The fix is process, not culture: one automated formatter, one ratified configuration, automated checks, and a measured review.

- Style disputes persist because style authority is ambiguous; an automated formatter with a team-owned configuration removes that ambiguity.
- A short working agreement moves residual disagreements into configuration pull requests, so the norm changes without a culture program.
- A CI (continuous integration) check rejects rule-breaking SQL, so style comments leave the review [judgment].
- A count of formatting comments before and after adoption shows whether the friction fell.

## Background

The team writes SQL without a shared standard, and format debates recur in review. Formatting is deterministic, so a tool can own it. The request names culture; the workable target is the process that keeps the argument running.

## Relevance

Review time spent on formatting delays merges and taxes every reviewer [judgment]. Disputes over small matters absorb effort out of proportion to their impact [1].

## Information

**Evidence.**

- SQLFluff checks style rules and auto-formats SQL across many dialects [2].
- sqlfmt applies one fixed style by design, which removes most room for configuration debate [3].
- dbt Labs publishes a written SQL style guide, so a written standard has precedent [4].
- A pre-commit hook (a script that runs before a commit is saved) can run the formatter on every commit [5].
- Git can hide one chosen commit from blame output, so the one-time reformat keeps history readable [6].
- Mechanism: automation plus a written agreement removes the trigger of style debate [judgment]. Confidence: high; basis is the documented tool capability above plus published precedent.

**Uncertainty.** Whether part of the friction is personal conduct is about as likely as not [judgment]. Step 1 supplies the data that settles it.

**Assumptions.**

A1. The team stores SQL in a shared Git repository with pull request review. Why not measured: the material does not state it. Validate by: open the repository and pipeline settings. If wrong: add a version control step before Step 2.

A2. CI exists, or local hooks are acceptable meanwhile. Why not measured: the material does not state it. Validate by: check the pipeline configuration. If wrong: run the formatter locally until CI exists.

A3. The friction concerns style, not conduct or correctness. Why not measured: the material does not state it. Validate by: the Step 1 tally. If wrong: replace Steps 2 to 4 with a facilitated session on conduct.

A4. The team uses one or two SQL dialects. Why not measured: the material does not state it. Validate by: check the warehouse connection settings. If wrong: raise the dialect weight in Step 2.

**Alternative considered.** Hold norms workshops without tooling. It loses because the trigger, ambiguous style authority, stays in place [judgment]. Workshops also cost several sessions versus one configuration pull request [judgment].

## End

I recommend that we take five steps in order.

1. **Baseline tally.**
   - Increment: two reviewers label each comment on the last 20 merged SQL pull requests. Half a session.
   - Blocker removed: no shared evidence about the friction; tests A3.
   - Kind: evaluative. Write the rubric first. Categories: formatting, logic, performance, naming, with equal weight. Evidence: the comment text. Pass threshold: 80 percent agreement between the two raters [judgment]. Then each rater scores each comment.
   - Cynefin: Complicated, because the data exists and analysis reveals it [7].

2. **Select one formatter.**
   - Increment: score SQLFluff and sqlfmt in a Pugh matrix (a weighted table that compares options) in one session [8].
   - Criteria and weights [judgment]: dialect support 30 percent; rule control 25 percent; editor and CI integration 20 percent; setup time 15 percent; maintenance activity 10 percent.
   - Evidence: the tool documentation cited in Information. Pass threshold: the winner leads by at least 10 points out of 100.
   - Blocker removed: no agreed engine for the standard.
   - Kind: evaluative. Cynefin: Complicated, because several good tools exist and the matrix picks one (domain source: see Step 1).
   - Dependency: start after Step 1, so the weights reflect the measured friction.

3. **Ratify a one-page working agreement.**
   - Increment: draft the agreement in one session. Then ratify it by lazy consensus (the proposal stands unless someone objects) over five working days.
   - Content: the formatter configuration is the style guide. Reviewers do not comment on style. Style changes go through a configuration pull request with a five-day window.
   - Blocker removed: ambiguous style authority and no change path. This step is the culture fix, because the norm moves from individuals to a shared artifact.
   - Kind: deterministic. The artifact is a document with fixed acceptance criteria. Write the test first [9]:
     - Given a draft agreement and configuration in a pull request
     - When five working days pass without a blocking review
     - Then the agreement merges and governs every SQL file
   - Cynefin: Clear, because a ratified written standard is a known best practice.
   - Dependency: Step 3 MUST NOT start until Step 2 names the formatter.

4. **Automate the check.**
   - Increment: add the formatter to the pre-commit hook and to CI. Then reformat every SQL file in one commit, and record that commit in .git-blame-ignore-revs. One session.
   - Blocker removed: reviewers carrying style checks by hand.
   - Kind: deterministic. Write the test first:
     - Given a pull request whose SQL violates the configuration
     - When the CI job runs
     - Then the check fails and prints the rule identifier
   - Also verify history: run git blame on a reformatted file and confirm the reformat commit is hidden (see Information).
   - Cynefin: Clear, because formatter-in-CI is a documented standard practice (see Information).
   - Dependency: Step 4 MUST NOT start until the test in Step 3 passes.

5. **Re-measure as a capped probe.**
   - Increment: in week four after Step 4, repeat the Step 1 tally. Budget: one 45-minute retro.
   - Kind: stochastic, because team behavior varies. Write the acceptance test first:
     - Metric: formatting comments per merged SQL pull request.
     - Baseline: the Step 1 number.
     - Pass threshold: a drop of at least 50 percent [judgment].
     - Sample: every SQL pull request merged in week four, minimum five; extend one week if fewer [judgment].
   - Stop condition: the count does not fall by half, or someone reverts the configuration without discussion. Response: pause the check and hold a facilitated session on the real conflict.
   - Blocker removed: not knowing whether the fix worked.
   - Cynefin: Complex, because the team response is visible only afterward; leverage here is a guess (domain source: see Step 1).
   - Dependency: Step 5 MUST NOT start until Step 4 passes. It then runs in parallel with normal work, capped at the retro budget.

## Follow-up

Conditions that change the recommendation: if Step 1 falsifies A3, replace Steps 2 to 4 with a facilitated session on conduct before any tooling [judgment]. If A2 fails, do Step 4 with local hooks only (see Information).

No open questions; the fallbacks above cover the unknowns.
