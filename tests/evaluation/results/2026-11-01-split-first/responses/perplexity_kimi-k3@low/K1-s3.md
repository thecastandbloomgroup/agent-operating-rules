## Background

Release 2026.10.21 changed three things: pool config, cache TTL, and an ORM query. After it, p95 latency rose from 120 ms to 900 ms, and errors rose from 0.02% to 0.40% [3].

## Relevance

About 96% of the errors are PoolTimeout, so customers now get 503s. The longer the config stays, the more requests fail at peak load [1], [3].

## Information

Evidence (all primary, from the attached files):

- Pool capacity: 4 pods × 8 workers = 32 workers, but only 8 connections exist in total, one per pod pair... that is, 8 per pod shared by 8 workers per pod [2]. Waiters reach 14 per pod [1].
- Latency budget: db.pool.acquire p95 went 3 ms → 690 ms. Query and serialize spans stayed flat [3].
- Connections: active DB connections fell from 31 (peak) to 8, so the database is not the bottleneck (CPU 38% → 41%) [3].
- Errors: 96% of Window B errors are PoolTimeout after 5 s [3].
- Cache: miss rate 12% → 31% after TTL 300 s → 60 s [2], [3]. This adds DB load, so it amplifies the pool problem but did not cause it.
- ORM: orders query p95 52 → 58 ms, lines 30 → 26 ms. No regression [3].

Alternative considered: raise pool size only partially (for example, 16). This loses because peak demand needs about 31 connections per service (Window A baseline [3]) and the prior 50 carried the same traffic at p95 120 ms.

Confidence: high. Span timing, config diff, and waiters all point to the same cause [1], [2], [3].
