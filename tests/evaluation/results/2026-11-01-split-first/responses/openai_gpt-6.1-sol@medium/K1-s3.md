## Headline

Treat connection acquisition as the main bottleneck; verify the connection budget, then test a cache-only rollback before changing pool capacity.

- Pool-acquisition p95 rises from 3 ms to 690 ms while request p95 rises from 120 ms to 900 ms. [1]
- The release reduces pool capacity and cache lifetime together, so both changes deserve investigation. [2]
- Do not restore the old pool size blindly: its reduction reflects a new database connection limit. [2]

## Background

The supplied traces compare 10,000 requests before and after release 2026.10.21. [1]  
The files show pool timeouts, more cache misses, and little change in individual query latency. [1]

## Relevance

Errors rise from 0.02% to 0.40%, and pool timeouts account for 96% of post-release errors. [1]

### Resolve the connection-scope discrepancy

The deployment has four pods, but reported service-wide peak connections fall to eight. [1]  
If each pod owns one eight-connection pool, nominal capacity totals 32 connections, not eight. [inference]

Check pool ownership, effective configuration, metric scope, and any database proxy limit before changing capacity. [judgment]  
Also measure connection hold time and queries per request; individual query spans do not settle the ORM change’s total cost. [judgment]
