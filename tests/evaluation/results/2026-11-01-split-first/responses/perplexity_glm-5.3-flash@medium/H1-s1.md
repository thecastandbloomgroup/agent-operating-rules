## Background

Checkout returns a 500 error for every user since 09:12. The on-call engineer has ten minutes before an executive call and asks for the first actions [judgment, from the request].

## Relevance

A total checkout outage loses revenue per minute and damages trust. The order of actions decides whether recovery happens inside the ten minute window [judgment].

Analysis: a total failure for all users, with a sharp start time, fits a change event (deploy, config, outage of a shared dependency) more than a load or data issue, because partial issues show gradual onset [inference].

**Assumption log.**

- A1. A deploy, config change, or infrastructure change landed in the 09:00 to 09:12 window. Why not measured: the material does not state it. Validate by: open the deploy and change log for that window (one minute). If wrong: treat a dependency outage instead and route around it (Step 5).
- A2. The newest deploy contains no irreversible data migration. Why not measured: the material does not state it. Validate by: scan the migration list for the newest deploy (two minutes). If wrong: do not roll back the database; roll back code only and keep the schema.

**Alternative considered.** Diagnose the root cause in code before touching the service. This loses because diagnosis of a 500 can take longer than ten minutes, while a rollback is a known path with a fixed duration [judgment].

## End

I recommend that we execute the four steps below in order.

1. **Stabilize first (Chaotic):** Roll back the newest checkout deploy to the previous version, or switch off the newest change with a flag. Cause and effect are not yet visible, so stabilization comes first [18]. Blocker removed: total purchase loss. Write the test first:

Step 1 MUST start before any diagnosis. Steps 3 and 4 MUST NOT consume the minutes reserved for Step 2 [judgment].
