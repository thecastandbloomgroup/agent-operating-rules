# Headline

Root cause: the release cut the DB pool from 50 connections to 8, while the API's request rate needs about 10 per pod at peak [1]. Therefore connection acquisition is the bottleneck, not the queries.

1. Pool acquisition takes 690 ms at p95, versus 3 ms before, and it is 77% of the 900 ms total [2].
2. The 503 errors are the same failure: acquire timeouts after 5 s [1], [3].
3. The cache TTL and ORM changes add load, however their query cost is under 90 ms at p95 [2].

# Background

Release 2026.10.21 changed three settings: pool size and timeout, cache TTL, ORM prefetch [1]. The API's p95 rose from 120 ms to 900 ms, and the error rate rose from 0.02% to 0.40% [2]. Logs show heavy pool exhaustion after the release [3].

# Relevance

The 503 errors reach customers today, with a 5 s wait before failure [3]. The pool fix restores both latency and error rate with a config change.

# Information

## Evidence

- Pool: max_size 8, acquire_timeout_s 5, versus 50 and 30 s before the release [1]. The commit cites ticket OPS-412 for the DB limit [1].
- Workload: 32 worker threads across 4 pods, unchanged in the release [1]. Traffic is flat: 410 versus 405 rps at peak [2].
- Pool warnings: 0 per hour before, 1,800 to 2,400 per hour after [3].
- Peak active DB connections: 31 under the old pool size, 8 under the new one [2]. Therefore the pool cap now binds before the DB does.
- DB capacity: CPU peak is 41% versus 38% before [2]. So the DB has spare room.
- Demand analysis [judgment]: at p95 a request holds a connection for about 100 ms (queries 58 + 26 ms, serialize 15 ms) [2]. At 405 rps over 4 pods, that gives 101 rps × 0.10 s ≈ 10 connections per pod. Therefore 8 per pod is short of demand, so requests queue and time out.
- Cache: default_ttl_s (time to live) fell from 300 s to 60 s [1]. The miss rate rose from 12% to 31% [2]. Each miss adds a DB query and so lengthens connection hold time. Because the cache.get span itself stayed at 2 to 5 ms p95, the cache change adds DB load, not cache latency [2].
- ORM: selectinload (an eager-load option in the ORM) was added [1]. The lines query got faster, 30 to 26 ms at p95, and the full query cost is 84 ms, or 9% of 900 ms [2]. This change is not the driver.

Confidence: high. Three independent signals agree: warning counts [3], the acquire span [2], and the active-connection count [2].

## Assumption log

A1. pool.max_size applies per pod, shared by that pod's 8 worker threads. Why not measured: the engine setup code is not attached. Validate by: read the ORM engine creation. If wrong: resize at the real pool level instead, keeping the total under the OPS-412 limit.
A2. The OPS-412 limit allows at least 32 service connections. Why not measured: the ticket text is not attached. Validate by: read the ticket and the DB max_connections value. If wrong: keep a smaller cap and complete Step 3 plus the timeout change only.
A3. Connection hold time at p95 is about 100 ms. Why not measured: no hold-time span exists in the attached traces. Validate by: add a connection-held span in the APM. If wrong: raise max_size above 16.

## Alternative considered

Reverting the ORM selectinload change as the cause. It loses: the lines query p95 fell from 30 to 26 ms, and the total query cost is 9% of the latency [2].
