## Headline

The connection pool reduction causes the latency rise, so revert the pool and cache config and keep the ORM change.

- The pool dropped from 50 to 8 connections, while the service still runs 32 worker threads [2].
- Pool acquire adds 690 ms of the 780 ms p95 increase, from 3 ms to 690 ms [3].
- Pool exhausted warnings rose from 0 to 1,800 to 2,400 per hour, and 96% of errors are PoolTimeout [1][3].
- Query and cache read times are flat against baseline, so the ORM and TTL are not the main cost [3].

## Background

API p95 latency rose from 120 ms to 900 ms after release 2026.10.21 [3]. The release changed the pool config, the cache TTL, and the ORM loader [2]. Logs, traces, and the diff are attached and agree with each other.

## Relevance

The error rate is 20 times baseline, from 0.02% to 0.40%, and those errors return HTTP 503 (service unavailable) to customers [3]. The fix is a config change, so the cost is one deploy per step, not a rebuild.

## Information

Terms: p95 is the 95th percentile, the value 95% of requests fall below. Pool is a set of reusable database connections. TTL is time to live, how long a cache entry stays valid.

Evidence, compared against window A (2026-10-14 release) as baseline [3]:

1. **Pool starvation.** db.pool.acquire p95 went from 3 ms to 690 ms, which is 88% of the total p95 increase (3/780 ≈ 88%, therefore the pool dominates). Active connections peak at 8 in window B, which equals the new max_size, so the pool serves all 32 workers with 8 connections [2][3]. BASeline peak was 31 connections at max_size 50 [3]. One connection now serves about 4 threads at peak, so most requests wait.
2. **Cache pressure.** Miss rate went from 12% to 31%, because TTL fell from 300 s to 60 s [2][3]. cache.get time is flat (2 to 5 ms), so cache reads do not add latency. The extra misses add database load, which raises pressure on the starved pool.
3. **ORM change.** The diff adds selectinload(Order.lines), which loads order lines with one extra query [2]. db.query order_lines is 9 to 26 ms in window B versus 11 to 30 ms in window A, therefore no added cost is visible [3].

Theme counts across the three sources [5]: theme 1 has three supporting sources, none disagreeing. Theme 2 has two. Theme 3 has one, so it matters only if you revert it without measure. The three themes agree with the log timings, so confidence is high.
