## Headline

Eliminate the SQL formatting debate by making a machine apply the style, so the standard is a fact and not an opinion in review.

- Choose the formatter once, with a weighted comparison, then stop debating it.
- Reformat the whole repository with one pinned config, in one commit.
- Enforce the style with a required CI check, so reviewers stop enforcing it.
- Measure style comments in reviews to confirm the debate has ended.

## Background

The team argues about SQL format in every code review. The request is to fix the culture problem behind those arguments.

## Relevance

Style arguments consume review time and create resentment between reviewers. Removing the human step removes both costs. [judgment]

## Information

The problem is not any single format rule. The problem is that each person applies the rules by hand, so each review enforces a personal variant. This produces repeat comments and repeat arguments. [judgment] The fix replaces the manual step with three machine steps: a tool formats, a config pins the rules, and a check blocks non-conforming code. After that, style has one answer and reviews cover only logic.

Assumption log

- A1. The team stores SQL as text in version control. Why not measured: the material does not state it. Validate by: search the repositories for SQL files and inline query strings. If wrong: retarget the tool to the query-builder layer and change the enforcement point.
- A2. The review platform can run a required CI check. Why not measured: the material does not state it. Validate by: list the current required checks on one repository. If wrong: enforcement moves to a pre-commit hook, which is weaker because developers can skip hooks.
- A3. The existing SQL volume fits one reformat session, one working day or less. Why not measured: the material does not state the volume. Validate by: count SQL files and lines. If wrong: split the reformat by schema, one commit per schema.
- A4. No pinned formatter config exists today. Why not measured: the material does not state it. Validate by: search the repositories for formatter config keys. If wrong: review the existing config first instead of writing a new one.

Alternative considered: vote on a hand-written style guide. It loses because a guide still requires people to apply it by hand, so the same arguments return on every edge case. A formatter turns style into tested output. [judgment]

## End

I recommend that we take these four steps, in this order.

**Step 1. Pick the formatter by a scored comparison.**
Increment: run two or three candidate tools on three real queries from the repository, in one session. Blocker removed: no agreed candidate standard. Candidate names such as sqlfmt and sqlformat are starting points to verify, not verified facts. [no source]
Kind: Evaluative. Domain: Complicated, because analysis among options picks the practice.
Rubric (pass threshold: winner scores 60 of 100 or more):

| Criterion | Weight | Evidence needed |
|---|---|---|
| Dialect match | 40% | The tool parses all three queries without errors |
| Determinism | 25% | Two runs on the same file give identical output |
| Committed config | 20% | All rules live in one config file in the repository |
| Diff noise | 15% | The reformat of one old file changes only whitespace and layout |

**Step 2. Pin the config and reformat all SQL in one commit.** This step waits on Step 1. [18]
Increment: commit the winning config, then run the format command across the whole repository. Blocker removed: mixed formats, which would make every later diff noisy.
Kind: Deterministic. Domain: Clear, because the best practice exists: format once, then keep it formatted. Test, written before the work:

```gherkin
Given the pinned config committed in the repository
When the format command runs on every SQL file
Then the working tree stays clean
```

**Step 3. Add a required CI check on every pull request.** This step waits on Step 2, because the check needs the pinned config.
Increment: a check job that runs the formatter in check mode. Blocker removed: enforcement that depends on each reviewer's memory and patience.
Kind: Deterministic. Domain: Clear, for the same reason as Step 2. Test, written before the work:

```gherkin
Given an open pull request with a changed SQL file
When the check runs the formatter in check mode
Then it passes only when the file produces zero diff
```

Add one rule to the review guide at the same time: "it does not match the formatter" is not a review comment, because the CI check already covers it. [judgment]

**Step 4. Run a probe to confirm the debate ended.** Step 4 runs in parallel with Step 3, after Step 2 completes.
Increment: count style-only comments on SQL reviews for two sprints before and two sprints after the change, then compare. Blocker removed: no baseline proves the change worked, so the team cannot defend it later.
Kind: Stochastic. Domain: Complex, because behavior change shows its cause and effect only afterward, so the work runs as a capped probe, not a full commitment. Acceptance test, written before the run: metric = count of style-only comments per SQL review; baseline = the count over the two sprints before the change; pass = at least 50% fewer comments in the after period; sample = at least 20 SQL-touching reviews. Budget: two hours of setup. Stop condition: if the baseline count is below five comments in total, stop the probe, because the measure cannot show a change. Leverage here is a guess. [judgment]
