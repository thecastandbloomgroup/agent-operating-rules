## Headline

The latency rise comes from connection pool starvation, not from the database server or the ORM queries. The release set pool max_size to 8 connections for 32 worker threads, and the cache TTL cut tripled the DB query rate behind those 8 connections.

1. Wait time to acquire a connection rose from 3 ms to 690 ms p95 and is 77% of the 900 ms total [1].
2. Pool exhaustion warnings went from none per hour on 2026-10-20 to 1,800 to 2,400 per hour on 2026-10-22 [2].
3. The release is the only change set: it cut max_size 50 to 8, the acquire timeout 30 s to 5 s, and the cache TTL 300 s to 60 s [3].

## Background

The p95 latency of GET /customers/{id}/orders rose from 120 ms to 900 ms after the 2026-10-21 release. The release touched the ORM layer, the cache config, and the connection pool, per the attached diff [3]. Logs, traces, and the diff are attached for this hour of analysis.

## Relevance

96% of the current errors are "PoolTimeout: acquire timed out after 5 s" [1]. The fix is two config lines, so the cost to restore service is low.

1. **Restore the cache TTL and deploy that one line.**
   - Increase: set default_ttl_s from 60 to 300 in cache.yaml, and deploy the one-line change.
   - Blocker: this cuts the DB query rate by about 60% (31% to 12% miss rate), which removes the overload on the pool of 8.
   - Test (deterministic, written first):
     ```

2. **Confirm the OPS-412 limit and size the pool against it.**
   - Increase: read OPS-412, then set pool max_size to one quarter of the confirmed limit per pod, minimum 8.
   - Blocker: this sets the connection capacity against the hard DB limit, so acquire waits end at peak.
   - Test (deterministic, written first):
     ```
     Given max_size is set to one quarter of the confirmed OPS-412 limit per pod
     When the pool runs at the 405 requests per second peak for one hour
     Then db.pool.acquire p95 is 10 ms or lower and no pool exhausted warning is logged
     ```
   - Domain: Complicated, because the ticket and a capacity model must pick the value before the config line.

3. **Restore the acquire timeout as a safety net.** Step 3 MUST NOT deploy before Step 1 is live, because a longer deadline on a starved pool turns fast 503 failures into long waits.

   - Blocker: this removes the 5 s acquire deadline behind 96% of the 503 errors [1].
   - Test (deterministic, written first):

     When any request runs in the next 24 hours
     Then no response returns 503 with a PoolTimeout error
     ```
   - Domain: Clear, because one config line removes a known failure path.

   - Increase: deploy the build without the selectinload option to one pod for one hour.

   - Test (stochastic, acceptance written first): metric is db.pool.acquire p95 and session hold p50 on the canary pod; baseline is the three unchanged pods in the same hour; pass threshold is equal or lower; sample size is one hour of peak traffic.
