## Headline

The Q3 report most likely (66 to 100%) [judgment] carries one of four error types: bad source data, wrong aggregation, period boundary drift, or unlogged manual edits. Because the report is not attached, the cause is unclassified until the data is in hand. The first step is therefore a figure inventory, not a fix.

## Background

The request states that the numbers in the Q3 report are off. The report file and its source data are not in this conversation [no source]. The message gives no figure, no baseline, and no expected value to compare against.

## Relevance

Wrong report numbers flow into budget and forecast decisions within days [judgment]. Each week of delay extends the correction cost into Q4 planning, because later periods restate from the same source lines.

Evidence and analysis:

- No material is available to test, so no number can be verified today [no source].
- Four cause groups cover this space without overlap: source data, aggregation, period boundaries, manual edits. That is, data in, calculation, data window, and data changed after export [judgment], [no source].
- "Variance" below means the difference between a reported number and its recomputed value from source lines.
- Confidence in the group order is low (below 66%) until Step 1 runs, because no figure has been seen [judgment].

Assumption log:

A1. The report has a source system behind it, and its data can be exported. Why not measured: the material does not state it. Validate by: request the file and its export, then run Step 1. If wrong: replace Step 2 with a design review of the report formulas.
A2. The four cause groups cover the whole fault space. Why not measured: no data exists yet. Validate by: the Step 1 inventory, whose unmatched flags either fill a group or expose a fifth group. If wrong: extend the check to report templates and formulas in Step 3.
A3. Each report number rests on one source system, not on merged systems. Why not measured: the user has not answered. Validate by: read the data section of the report. If wrong: add a cross system check to Step 3.

Alternative considered: fix the figure that looks most wrong first. That loses because a single figure can share a cause with all others, and one wrong correction costs more rework than the full inventory [judgment].

## End

I recommend that we run four steps in order, each within one working session, and write each test before the work it tests.

1. Build a figure inventory.
   - Increment: a table that maps each report figure to exactly one source line, with a status of match or unmatched.
   - Blocker removed: unknown error location, because the inventory classifies the fault before any fix (see A2).
   - Task kind and test, written first:
     ```gherkin
     Given the Q3 report file and each source export,
     When the inventory is built,
     Then each report figure maps to exactly one source line with one status
       and each unmatched figure is listed with its value.
     ```
   - Cynefin domain: Confused, because the fault type is not knowable until this data exists.
2. Recompute each reported total from its source lines. Step 2 MUST NOT start until the Step 1 test passes.
   - Increment: a line by line comparison of reported totals against recomputed totals, with variance values.
   - Blocker removed: unverified aggregates, because it replaces trust in the report with arithmetic.
   - Task kind and test, written first:
     ```gherkin
     Given the mapped source lines from Step 1,
     When each reported total is recomputed from those lines,
     Then each recomputed total equals the reported total
       or the variance is logged as a number with its source lines.
     ```
   - Cynefin domain: Clear, because the arithmetic rule is the same for every figure and needs no expert judgment.
3. Check period boundaries and units. Step 3 runs after Step 1 and can run in parallel with Step 2.
   - Increment: a list of date range, currency, and unit mismatches per figure.
   - Blocker removed: silent definition drift, because Q3 cutoffs and units often differ between systems [judgment].
   - Task kind and test, written first:
     ```gherkin
     Given two or more source systems in the inventory,
     When the date range, currency, and unit of each figure are compared,
     Then each mismatch is logged with the field name and both values.
     ```
   - Cynefin domain: Clear, because the comparison is a fixed rule applied per field.
4. Probe manual edits, in parallel with Steps 2 and 3, capped at one session.
   - Increment: a list of every edit applied after the system export, with its value.
   - Blocker removed: edits that are invisible inside totals, because the probe measures their share of the variance.
   - Task kind: stochastic. Metric: share of the reported variance explained by the listed edits. Baseline: 0%. Pass threshold: any share above 0% is a signal. Sample size: the full set of edits in the period, so the probe reads the complete population. Stop condition: stop when the edits explain the full variance, or when the session budget ends, whichever comes first.
   - Cynefin domain: Complex, because the effect of each edit is visible only after the check. Leverage here is a guess and is capped by the session budget.

## Follow-up

- If A1 fails and no source export exists, replace Step 2 with a formula review of the report file itself.
