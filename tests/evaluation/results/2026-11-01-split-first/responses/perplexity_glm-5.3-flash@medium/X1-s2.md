## Headline

Build a measured baseline first, then make the summariser quote its source ticket text, then re-test with a fixed pass threshold. Supporting points:

- Agents say "sometimes wrong" but report no categories, so fixes cannot be ranked.
- A labeled sample of 50 flagged summaries defines the error set and the baseline cost.
- A summary sentence that cites ticket text is easy to verify, which cuts the main failure class.
- A re-test against the baseline decides keep, tune, or revert.

## Background

The support tool includes an LLM summariser. Agents report "sometimes wrong" with no detail, and the team has no metrics.

## Relevance

The summariser shapes what agents tell customers, so bad output carries sales and trust risk. Until a baseline exists, no change to the summariser can be judged as better or worse.

## Information

**Reviewer questions.** A reviewer would ask: what does "wrong" mean (invented facts, missing facts, wrong emphasis, wrong status)? Who annotates? Can we edit the prompt and pipeline? Assumption A1 to A3 cover these.

Define terms here. Hallucination: a summary claim with no basis in the ticket text. Rubric: a fixed list of criteria with weights and a pass threshold.

**Assumption log.**

- A1. Hallucination or omission dominates the complaints. Why not measured: the material does not state it. Validate by: the 50-item tagging in Step 1. If wrong: the Step 3 fix targets the wrong class and the Step 2 rubric reweights.
- A2. Two agents can spare about 4 hours total for tagging and scoring. Why not measured: the material does not state staffing. Validate by: ask the team lead. If wrong: cut the sample to 30 and extend the calendar by 1 week.
- A3. The team can edit the prompt and add an output check. Why not measured: the material does not state pipeline ownership. Validate by: confirm with the tool owner. If wrong: replace Step 3 with a filter that shortens the summary.
- A4. At least 100 summaries per week exist in the tool. Why not measured: the material does not state volume. Validate by: query the tool's ticket count. If wrong: extend the sampling window proportionally.

**Confidence.** High confidence in the sequence, because each step consumes the output of the step before it. The guess in A1 is about as likely as not (50 percent) until Step 1 tests it.

**Alternative considered.** Tune the prompts now and watch complaints. It loses: with no error categories, a drop in complaints is unverifiable, so a failed fix costs a second full cycle [judgment]. Full commercial evaluation tooling was rejected; its cost exceeds the decision value for the first iteration.

## End

I recommend that we run five steps in the order below. Numbers classify each step: deterministic (same input, same output), evaluative (a judgment), or stochastic (varies run to run).

1. **Tag the errors.** Increment: 2 agents tag the same 50 flagged summaries with categories (hallucination, omission, wrong emphasis, wrong status, other) and merge overlaps. Blocker removed: no shared language for errors, so no fix can be ranked. Test, written first (evaluative rubric): criterion is category agreement, weight 1 per item, pass threshold: the same category on 80 percent of items, evidence: summary plus full ticket text. Stop rule: if agreement stays below 80 percent after 1 recalibration pass, merge categories and re-tag. Domain: Complex, because the real error mix is visible only after tagging; the probe is capped at 50 items and 4 agent hours [18].

2. **Record the baseline.** Step 2 MUST NOT start until the Step 1 test passes. Increment: both agents score 100 random summaries with the rubric. Blocker removed: no numbers, so changes cannot be judged. Test, written first (evaluative rubric): criteria and weights: hallucination-free 0.4, completeness 0.3, correct emphasis 0.3; pass threshold: none, this run records the baseline; evidence: summary plus ticket text. Domain: Complicated, because trained annotators must analyse the sample to produce trustworthy scores.

3. **Ground the output.** Steps 3 and 5 can start in parallel with Steps 1 and 2. Increment: a prompt rule that requires each summary sentence to cite ticket line IDs, plus an output check that rejects any uncited or dangling citation. Blocker removed: unverifiable claims, so agents cannot trust or check the summary. Test, written first (deterministic, Gherkin [14]):

   ```gherkin
   Given a ticket with at least 20 turns
   When the summariser produces a summary
   Then every summary sentence cites at least one ticket line ID
     and every cited ID resolves to text in that ticket
   ```

   Domain: Clear, because source citation plus output checking is a known practice for this failure class [judgment].

4. **Re-test against the baseline.** Step 4 MUST NOT start until Step 2 is recorded and the Step 3 test passes. Increment: both agents score 100 fresh summaries with the same rubric. Blocker removed: the keep versus revert decision has no evidence. Acceptance test, written first (stochastic): metric: share of summaries with a critical error; baseline: the Step 2 value; pass threshold: at least a 50 percent relative cut; sample size: 100 summaries. Domain: Complicated, because trained annotators can measure the effect reliably.

5. **Add the feedback loop.** Increment: a thumbs-down control with a 3-option reason menu, routed to the error list from Step 1. Blocker removed: post-launch errors stay invisible, so regressions return unnoticed. Acceptance test, written first (stochastic): metric: usable labeled feedback items per week; baseline: 0, because no feedback path exists; pass threshold: at least 10 items per week; sample size: 4 weeks; budget: 1 engineer day. Stop rule: below 5 items per week, replace the control with a monthly manual audit of 20 summaries. Domain: Complex, because live failure modes appear only over time [18].

Condition that changes this plan: if A1 fails and wrong status is the top error, add a freshness rule (summary must re-read status fields at generation time) before or instead of Step 3 [inference].

## Follow-up

Open question (1 of 3): can you edit the summariser prompt and add an output check? Use: the answer decides whether Step 3 is a prompt rule or an external filter that rewrites the summary.

If A3 is false, replace the Step 3 method with a filter, and move Step 5 to last.
