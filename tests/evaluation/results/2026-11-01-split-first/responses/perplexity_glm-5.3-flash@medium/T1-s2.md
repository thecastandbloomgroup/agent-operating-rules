# Headline

Stop debating SQL format in reviews and give ownership of format to a formatter. The friction comes from un-owned taste decisions, not from the people. One pinned formatter with one config removes the debate. A CI check keeps it removed. A small probe confirms that reviewers stop writing format comments.

# Background

The team disagrees on SQL formatting, and disputes show up in code review. The request is to fix this "culture problem". The material names no dialect, no tool chain, and no team size.

# Relevance

Every review that carries format comments spends review attention on style instead of design. The dispute repeats on every PR until a machine owns the decision.

# Information

## Evidence

Reviewers find real defects, but style comments crowd out defect comments in review load [2]. Format rules are deterministic, so tools can check them without judgment [1]. Existing format guides for SQL exist and are public, so the team does not need to invent rules [3]. The disagreement is about ownership of a decision, not about team values: the current reviews show the manual approach already failed [judgment].

## Assumptions

A1. The team writes one SQL dialect, most likely PostgreSQL. Why not measured: the material does not name it. Validate by: list the SQL files and their executor in the repo. If wrong: set the `dialect` key in the config; the rest of the plan stays the same.
A2. The repository runs a CI pipeline on pull requests. Why not measured: the material does not name one. Validate by: open the PR settings. If wrong: use a pre-commit hook first and add CI when it exists; see the condition in Follow-up.
A3. No formatter is pinned in the repo today. Why not measured: a dispute on every review implies no common tool. Validate by: search the repo for `.sqlfluff` or `formatter` config. If wrong: the reformat step shrinks to a diff review only.
A4. Review friction is measurable as format-only comments. Why not measured: the material does not state the review load number. Validate by: count format-only comments in the last 10 PRs before the change. If wrong: keep the probe but also measure review time per PR.

## Alternative considered

A manual style guide with human enforcement. It loses because human enforcement is the current state, and the current state is the reported failure [judgment].

# End

I recommend that we hand format ownership to a pinned formatter and automate the check. Order the actions by leverage; the blocked work is review attention.

1. Pin the formatter. Add `sqlfluff` with a pinned version, the `dialect` from A1, and a checked-in `.sqlfluff` config to the default branch [1]. Increment: one working session per Step 6.1. Blocker removed: no single source of format truth now exists. Test, written before the work (deterministic; Cynefin domain Clear, because a documented best practice exists [18], note also [3]):

   ```gherkin
   Given the repo contains a pinned formatter and a .sqlfluff config
   When a contributor runs the lint command on every tracked SQL file
   Then each file with tool-approved format exits with code 0
   ```

2. Reformat the codebase. Run the formatter over all SQL files and merge the result as one dedicated commit [1]. Increment: one working session. Blocker removed: the baseline now matches the tool, so future diffs show logic only. Test (deterministic; Clear):

   ```gherkin
   Given the tool prints the reformat for each file
   When the merge diff is compared against the tool output
   Then the diff contains no change outside tool output
   ```

3. Enforce at the gate. Add a CI step that runs the lint command and fails the PR on violation (deterministic; Clear, one documented step). Blocker removed: format violations can no longer reach review. Test:

   ```gherkin
   Given a PR contains SQL that fails the lint command
   When the CI pipeline runs
   Then the PR fails with the rule name and the file path in the log
   ```

4. Measure the culture change (stochastic; Cynefin domain Complex, because reviewer behavior shows its effect only afterward). Probe: count format-only comments per PR in the next 10 PRs. Metric: format-only comments. Baseline: the same count in the 10 PRs before Step 2, from review logs per A4. Pass threshold: the count trends to zero by the tenth PR. Sample size: 10 PRs. Stop condition and budget: stop early if the count is zero for 5 PRs in a row; budget is 4 weeks. This step MUST NOT start until the test in Step 3 passes.

Step 2 waits for Step 1. Step 3 waits for Step 2. Step 4 runs after Step 3 and in parallel with normal work.

# Follow-up

Conditions that change this plan: if A2 is false, ship the pre-commit hook from Step 3 first and add the CI step when a pipeline exists. If A1 is wrong, change only the `dialect` key and rerun Steps 1 and 2. If the Step 4 probe shows no fall in format comments by the tenth PR, the cause is outside format, and the next step is a review-load audit.

Usage note: `sqlfluff` is one deterministic tool choice; `sqlfmt` is a smaller alternative with fewer rules [1].
