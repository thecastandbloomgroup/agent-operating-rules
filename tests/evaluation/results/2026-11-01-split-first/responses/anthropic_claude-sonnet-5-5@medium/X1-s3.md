## Headline

Measure the summariser first, then fix its most common error with a tested change.

- No metric exists, so no one can say whether a change helps (per the user message).
- A labelled sample of real tickets gives a baseline and shows which errors matter most.
- A small, capped trial on that sample tests each fix before agents see it.
- A staged rollout with a live "wrong" flag confirms the gain in daily use.

## Background

The support tool has a summariser built on a large language model (LLM), a text-generation system. Agents report that it is "sometimes wrong". The team has no metrics. The request is to improve it.

## Relevance

Without a metric, each prompt or model change is a guess. Wrong summaries can also lead agents to give wrong answers to customers.

## Information

**Evidence**

- Research on neural summarisers finds that they add content that the source text does not support. [1] [S]
- An LLM can act as a judge. Strong LLM judges agreed with human raters on over 80% of comparisons. [2] [S]
- This result covers chat answers, not support tickets. Validate any LLM judge against human labels before use. [inference]
- A sample of 200 tickets gives a 95% margin of about 7 points on a pass rate. That is 1.96 × sqrt(0.25 / 200). [judgment]
- Prompt changes alone reach the target in about as likely as not (33 to 66%) of cases. [judgment]

**Assumption log**

A1. The tool stores tickets and summaries, and an engineer can add a button. Why not measured: the material does not state it. Validate by: ask an engineer for a one-hour check. If wrong: Step 1 becomes a data export from the vendor.

A2. Most errors are wrong or invented facts, not style. Why not measured: no data exists. Validate by: read 30 summaries that agents flag. If wrong: change the rubric weights in Step 2.

A3. Two reviewers can label 200 summaries in about 7 hours each. Why not measured: measuring costs more than the decision is worth. Validate by: time the first 20 labels. If wrong: use 100 tickets and accept a margin of about 10 points.

A4. Policy allows reviewers to read ticket text. Why not measured: the user has not answered. Validate by: ask the data owner. If wrong: mask personal data before Step 2.

**Alternative considered**

Switch to a larger model now. It loses because there is no baseline to show a gain, and the cost rises with each call. Step 3 tests it as one variant.

## End

I recommend that we take these four actions, in this order:

1. **Log every summary and add a "Wrong" button.**
   - Increment: one working session. The button records a reason from a short list.
   - Blocker removed: no data exists on errors.
   - Kind: deterministic.
   - Domain: Clear, because logging is a known practice. [4]
   - Test:
     - Given an agent views a ticket with a summary
     - When the agent clicks "Wrong" and picks a reason
     - Then the log stores ticket ID, summary, model version, prompt version, reason, and time

2. **Label 200 logged summaries and compute the baseline pass rate.**
   - Step 2 MUST NOT start until the test in Step 1 passes.
   - Increment: two reviewers score the summaries against the rubric. The output is a pass rate and a ranked list of error types, which is the gold set.
   - Blocker removed: no baseline and no known top error.
   - Kind: evaluative.
   - Domain: Complicated, because expert analysis of the sample gives the answer.
   - Rubric, written first:
     - Factual accuracy, weight 50. Evidence: each claim matches the ticket text.
     - Coverage of the issue, steps tried, and customer request, weight 30. Evidence: all three appear.
     - Brevity and clarity, weight 20. Evidence: the summary is under 80 words and reads clearly.
     - Pass threshold: a score of 80 or more, with no factual error.
     - Reviewers MUST agree on at least 80% of summaries. They resolve the rest by discussion.

3. **Trial two fixes for the top error type on the gold set.**
   - Step 3 MUST NOT start until Step 2 gives the baseline.
   - Increment: two variants, for example "use only facts in the ticket and write 'not stated' for gaps", and a larger model.
   - Blocker removed: the top error type.
   - Kind: stochastic.
   - Domain: Complex, because the effect of a prompt change shows only after a run. Leverage here is a guess.
   - Budget: two working days. Stop when both variants miss the threshold.
   - Test, written first:
     - Metric: pass rate from Step 2.
     - Baseline: the Step 2 result.
     - Threshold: baseline plus 10 points.
     - Sample: the same 200 tickets.
     - Accept a variant only if it meets the threshold.

4. **Release the best variant to 10% of agents.**
   - Step 4 MUST NOT start until a variant is accepted in Step 3.
   - Increment: a feature flag and a weekly report of "Wrong" clicks per 100 summaries viewed.
   - Blocker removed: lab gains may not hold in daily use.
   - Kind: stochastic.
   - Domain: Complex, because agent behaviour is not predictable.
   - Budget: two weeks.
   - Stop condition: roll back if the flag rate exceeds baseline for two days.
   - Test, written first:
     - Metric: "Wrong" clicks per 100 summaries viewed.
     - Baseline: the Step 1 rate over one week.
     - Threshold: a relative drop of at least 20%.
     - Sample: at least 500 summaries per group.

Step 1 runs first. Steps 3 and 4 are capped probes.

If A2 is false, replace the factual-accuracy focus in Step 3 with the top error type from Step 2.
