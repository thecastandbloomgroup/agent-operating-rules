Roll back the newest change now, then give the executives three facts, and diagnose only if the rollback fails.

## Background

Checkout returns HTTP 500 for every user since 09:12. You are the on-call engineer. The executive call starts in ten minutes.

## Relevance

A total failure of one revenue path grows in cost each minute. The call is also a deadline for a clear status.

## Information

**Evidence**
- Checkout fails for 100% of users since 09:12 (your report, per the query). 
- A sudden total failure at a fixed time is likely (66 to 100%) linked to a change near 09:12. [judgment]
- Incident practice says to mitigate first and find the root cause later. See [1].
- The Cynefin framework puts work with no visible cause and effect in the Chaotic domain, and says to stabilise first. See [2].

**Assumption log**

A1. A deploy or config change happened shortly before 09:12. Why not measured: the material does not state it. Validate by: read the deploy log for the last 60 minutes. If wrong: skip Step 1 rollback and go to Step 3 now.

A2. A rollback or feature-flag switch exists for that change. Why not measured: no tool can reach it. Validate by: check the deploy tool for a previous version. If wrong: use a failover or maintenance page.

**Alternative considered**

Debug the root cause first. It loses because the cause is unknown and the time is ten minutes. A rollback takes minutes and is reversible. [judgment]

## End

I recommend that we take these steps in order:

1. **Stabilise (Chaotic: no cause is visible yet).** Roll back the newest change from A1, or switch its flag off. This removes the blocker, a failing checkout. The increment is one rollback. Step 2 MUST NOT start until the rollback finishes or fails. Kind: deterministic.
   - Given the newest change is identified
   - When the rollback completes
   - Then a test checkout returns HTTP 200

2. **Brief the call (Clear: a status template exists).** Write three lines: impact, action taken, next update time. This removes the risk of guesses on the call. Kind: deterministic.
   - Given the result of Step 1 is known
   - When the three lines are written
   - Then each line holds a fact, a time, and no unverified cause

3. **Diagnose if Step 1 fails or no change exists (Complicated: analysis finds the cause).** Read the first 500 error in the checkout logs. Check the database and the payment provider status. The increment is one named failing component. Step 4 MUST NOT start until Step 3 names a component. Kind: deterministic.
   - Given the checkout logs since 09:12
   - When errors are grouped by message
   - Then the most frequent error and its component are named

4. **Confirm recovery (Clear: a synthetic check gives a known answer).** Watch the 500 rate for 10 minutes. Declare recovery only at 0 errors for 10 minutes. Kind: deterministic.
   - Given the fix or rollback is live
   - When 10 minutes of checkout traffic pass
   - Then the 500 rate is 0%
