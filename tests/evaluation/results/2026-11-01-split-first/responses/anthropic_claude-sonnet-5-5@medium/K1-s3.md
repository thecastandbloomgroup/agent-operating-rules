## Headline

The pool limit cut in release 2026.10.21 causes the latency rise, so raise the pool size and restore the cache time-to-live (TTL).

- The pool cut from 50 to 8 connections makes requests wait for a free connection.
- The database itself is not slower, so the ORM change is not the main cause.
- The shorter cache TTL adds load but is a secondary cause.

## Background

p95 latency on GET /customers/{id}/orders rose from 120 ms to 900 ms after release 2026.10.21. The release changed the pool, the cache, and one ORM query. Logs, traces, and the diff are attached.

## Relevance

The error rate is 20 times higher (0.02% to 0.40%). Each pool timeout returns a 503 error to a customer after 5 s.

## Information

Evidence:

- Pool wait p95 rose from 3 ms to 690 ms. That is 687 of the 780 ms increase. See traces.txt, span table.
  [3]
- Query spans did not change: db.query orders p95 was 52 ms and is now 58 ms.
  [3]
- Database CPU peak rose only from 38% to 41%, so the database is not the limit.
  [3]
- 96% of the errors in window B are PoolTimeout. The log shows "8 of 8 connections in use" with 6 to 14 waiters.
  [1]
- The diff cut max_size from 50 to 8 and acquire_timeout_s from 30 to 5.
  [2]
- Pool warnings went from none on 2026-10-20 to 1,800 to 2,400 per hour on 2026-10-22.
  [1]
- The cache miss rate rose from 12% to 31% after the TTL change from 300 s to 60 s. More misses mean more database work, so pool demand rises [inference].
  [3]
- Each pod has 8 workers, and the log shows up to 14 waiters on one pod. That is more waiters than workers, and no source explains it [no source].
  [2]
- The selectinload change replaces per-row line loads with one extra query. The order_lines span is unchanged (p95 30 ms to 26 ms), so it is not the cause.
  [3]

Confidence that the pool change is the main cause: high confidence, three independent measurements (span timing, error type, database CPU).

Assumption log:

A1. The pool size of 8 applies per pod, and the OPS-412 limit allows at least 16 connections per pod. Why not measured: the material does not state the limit. Validate by: ask the OPS-412 owner for the limit. If wrong: set max_size to the real limit divided by 4, or add a connection pooler.

A2. The extra waiters come from more concurrent threads than the 8 workers, or from requests that hold two connections. Why not measured: no tool can reach per-thread pool data in the material. Validate by: log the pool holder per request on one pod. If wrong: Step 5 finds another cause.

Alternative considered: revert the whole release. It loses because the config files hold the cause, and a revert also drops the ORM change, which shows no cost in the traces. [judgment]
