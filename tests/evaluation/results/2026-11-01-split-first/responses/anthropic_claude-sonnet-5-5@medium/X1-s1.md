## Headline

Measure the errors first, then fix the most common error type with a tested prompt change.

- Agents report errors, but no data shows which errors occur or how often.
- A flag button and a labelled test set turn "sometimes wrong" into a number.
- A small prompt change aimed at the top error type is the cheapest fix to try.

## Background

The support tool shows an LLM (large language model) summary of each ticket. Agents say the summary is "sometimes wrong". The team has no metrics, so nobody knows how often it fails or how.

## Relevance

An agent who trusts a wrong summary may give a wrong answer to a customer. An agent who distrusts all summaries gets no value from the feature. Both cases cost support time now.

## Information

**Evidence**

- The team has 0 quality metrics (per the user's message). So any claim about the error rate is unsupported today.
- Factual accuracy is a standard software quality: ISO/IEC 25010 names "functional correctness" as part of functional suitability.

- The team does not yet know the problem type. The cause of the errors is unknown, so the work starts in the Cynefin Confused domain.

- Agent comments are qualitative data. Group them into themes and count the sources per theme.

[4]

- Errors likely cluster in two or three types, such as invented facts or missed details. Likelihood: 70% [judgment]. Confidence is low, because 0 cases have been counted.

**Assumption log**

A1. Agents see the full ticket beside the summary. Why not measured: the material does not state it. Validate by: ask one agent to open a ticket. If wrong: agents cannot check summaries, so add a source link first.

A2. The tool stores the ticket text and the summary text. Why not measured: no tool can reach the system from here. Validate by: query the log for one ticket. If wrong: add logging in Step 2 before Step 1 can finish.

A3. Two agents can give 2 hours in total this week. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: cut the sample in Step 1 to 15 cases.

**Alternative considered**

Switch to a larger model, or fine-tune now. It loses because 0 metrics exist to show any gain, and the cost is higher than a prompt change [judgment].

## End

I recommend that we take these four actions in order:

1. **Classify the errors (Confused: the cause of the errors is unknown).**
   - Increment: two agents review 30 flagged or recent summaries in one session. They label each with one error type.
   - Blocker removed: nobody knows what "wrong" means.
   - Kind: evaluative. Rubric, written first:
     - Coverage (40 points): 30 summaries each have one label.
     - Agreement (30 points): the two agents give the same label on at least 24 of 30.
     - Actionability (30 points): the top three types explain at least 60% of the cases.
   - Pass threshold: 70 of 100 points. Evidence: the labelled sheet.
   - Step 3 MUST NOT start until this rubric passes.

2. **Add a "Wrong summary" button with reason codes (Clear: a standard logging feature).**
   - Increment: one button, five reason codes taken from Step 1, one log table.
   - Blocker removed: no continuous data on errors.
   - Kind: deterministic. Run this step in parallel with Step 1, then align the codes. Test, written first:

```gherkin
Given an agent views the summary on ticket 123
When the agent clicks "Wrong summary" and picks the reason "invented fact"
Then the log stores the ticket id, the summary id, the reason, and the time
```

3. **Build a test set and measure the baseline (Complicated: analysis of the Step 1 labels picks the metric).**
   - Increment: 100 past tickets, each with a reference check by two agents, and 3 runs of the current prompt.
   - Blocker removed: no baseline to compare any change against.
   - Kind: stochastic. Acceptance test, written first:
     - Metric: share of summaries with at least one factual error.
     - Baseline: the current prompt on this set.
     - Threshold: the spread across 3 runs is 5 points or less.
     - Sample size: 100 tickets per run.
   - Accept the baseline only when the threshold is met.

4. **Probe one prompt fix for the top error type (Complex: the effect shows only after a trial).**
   - Increment: one prompt change in one session. For example, "write only facts that appear in the ticket".
   - Blocker removed: the top error type.
   - Kind: stochastic. Acceptance test, written first:
     - Metric: the same error share as in Step 3.
     - Baseline: the Step 3 result.
     - Threshold: a relative drop of 30% or more.
     - Sample size: 100 tickets, 3 runs.
   - Stop condition: stop after 2 prompt versions, or when the error share falls below 10%.
   - Budget: one working session per version. The leverage of this step is a guess.
   - Step 4 MUST NOT start until Step 3 passes.

The acceptance tests use Gherkin form for Step 2.
