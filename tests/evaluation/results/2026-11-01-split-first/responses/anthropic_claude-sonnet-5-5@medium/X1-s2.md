## Headline

Measure the summariser's errors first, then change it against a fixed test set.

- The team has no baseline, so no change can be shown to help.
- Agents report errors but give no type, so the fix cannot be chosen yet.
- A labeled test set turns each later change into a measured result.

## Background

The support tool has a summariser built on a large language model (LLM). Agents say it is "sometimes wrong" (per the request message). The team has no metrics and asks for a better summariser.

## Relevance

A wrong summary can send an agent to the wrong action on a ticket. Without data, each prompt or model change is a guess.

## Information

**Evidence**

- One source reports the problem: the request message. It gives no error rate and no error type. Confidence in any cause is low (one source, no numbers).
- A sample of 100 cases gives a 95% interval of about ±8 points at a 20% error rate. [inference, from the standard error formula]
- One error type is likely (66 to 100%) to cause most errors. [judgment]

**Assumption log**

A1. Most errors are invented or missing facts, not tone. Why not measured: the material does not state it. Validate by: label 100 summaries (Step 1). If wrong: Step 4 targets the real top type.

A2. The tool can store ticket text, summary, and model version. Why not measured: no tool can reach the system design. Validate by: ask engineering to log one test ticket. If wrong: store ticket ids and fetch text on demand.

A3. Two agents can give about two hours each for labeling. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: label 50 cases and widen the interval.

**Alternative considered**

Switch to a larger model now. It loses because no baseline exists to show a gain, and cost and delay rise first. [judgment]

## End

I recommend that we take these steps, in this order:

1. **Label a sample of current summaries.** The problem domain is Confused: the error types are unknown, so this step gathers what is needed to classify them [1].
   - Increment: two agents score 100 recent summaries in one session.
   - Blocker removed: no baseline and no error types.
   - Kind: evaluative.
   - Rubric: accuracy (weight 50%), completeness of key facts (30%), usefulness to the next agent (20%).
   - Evidence: the ticket text beside the summary.
   - Pass threshold: a summary passes at 80% or higher.
   - Output: the baseline pass rate and a count of errors by type.

2. **Add a "Wrong" button with a reason list.** Domain: Clear, because logging feedback is a known practice.
   - Increment: one button, one reason list, one stored record.
   - Blocker removed: no continuous error data.
   - Kind: deterministic. Write this test first [2]:

   Given an agent views a summary on a ticket
   When the agent clicks "Wrong" and picks a reason
   Then the system stores the ticket id, summary text, model version, reason, and time

3. **Build a fixed test set and a scoring script from the Step 1 labels.** Domain: Complicated, because experts can analyze the labeled errors to pick the metric. Step 3 MUST NOT start until Step 1 is done.
   - Increment: the 100 labeled cases and one script.
   - Blocker removed: no repeatable measure.
   - Kind: deterministic. Write this test first:

   Given the 100 labeled cases and one summariser version
   When the script runs twice
   Then both runs print the same pass rate and the same error counts by type

4. **Run a capped probe of three prompt variants against the top error type.** Domain: Complex, because the effect of a prompt change shows only after a run. Step 4 MUST NOT start until the Step 3 test passes.
   - Increment: three variants, three runs each, one day of budget.
   - Blocker removed: no evidence on what reduces errors.
   - Kind: stochastic.
   - Metric: pass rate on the test set.
   - Baseline: the Step 1 pass rate.
   - Threshold: baseline plus 15 points.
   - Sample size: 100 cases, 3 runs per variant.
   - Stop condition: end the probe after the day, or when no variant gains 5 points after its first run.
   - Leverage is a guess. Ship a variant only when it meets the threshold.

## Follow-up

**Conditions that change the recommendation**

- If A1 is false, aim Step 4 at the error type that Step 1 finds.
- If A2 is false, replace the stored text in Step 2 with ticket ids.
