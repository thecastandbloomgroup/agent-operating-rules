### Information

First, we analyze the trace spans.

The `db.pool.acquire` span grew by 687 ms, from 3 ms to 690 ms [traces.txt].

Next, we identify the root causes from the configuration diff.
The cache time-to-live dropped from 300 s to 60 s in `config/cache.yaml` [release.diff].
Because of this drop, the cache miss rate increased from 12% to 31% [traces.txt].
This higher miss rate sent 2.58 times more read traffic to the database pool [traces.txt].
Simultaneously, `config/db.yaml` reduced `max_size` from 50 to 8 connections per pod [release.diff].
With 8 worker threads per pod, 8 connections create head-of-line blocking under burst traffic [release.diff, logs.txt].
Furthermore, `acquire_timeout_s` was reduced from 30 s to 5 s [release.diff].
This reduction caused 96% of the 0.40% error rate via pool timeout errors [traces.txt].

The ORM change added `selectinload(Order.lines)` [release.diff].
However, traces confirm query execution times stayed stable: orders query p95 moved from 52 ms to 58 ms, and lines query p95 dropped from 30 ms to 26 ms [traces.txt].
Database CPU utilization rose only from 38% to 41% [traces.txt].
Therefore, the database instance is not CPU-bound [traces.txt].
