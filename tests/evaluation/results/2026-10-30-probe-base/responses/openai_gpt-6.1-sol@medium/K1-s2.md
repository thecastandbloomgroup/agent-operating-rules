## Headline

Treat connection acquisition as the main bottleneck, but do not restore the old pool size before confirming the database connection budget.

- Pool-acquire p95 rises from 3 ms to 690 ms, while query times remain close to baseline. [1]
- Pool timeouts account for 96% of post-release errors. [1]
- The shorter cache lifetime increases database demand, while the pool reduction follows an explicit connection-limit requirement. [3]

## Background

The release changes the connection pool, cache lifetime, and ORM data load. API p95 rises from 120 ms to 900 ms across two windows, each containing 10,000 sampled requests. [1]

## Relevance

The immediate goal is to reduce connection waits without exceeding the database limit. A full rollback would restore 50 connections per pool despite the new limit described in OPS-412. [3]

## Information

### Diagnosis

**High confidence: connection acquisition is the main observed bottleneck.** The trace comparison and timeout logs support this conclusion. [1]

- Pool-acquire p95 increases by 687 ms, compared with a 780 ms increase in request p95. [1]
- Pool warnings increase from none to 1,800 to 2,400 per hour. [2]
- Error rate increases from 0.02% to 0.40%, a 20-fold increase. [1]

However, these percentiles do not identify the same requests. Therefore, do not interpret their difference as an exact latency breakdown. [judgment]

**Moderate confidence: reduced connection capacity and increased cache misses jointly drive saturation.** Both change with the release, but the evidence does not isolate their effects. [judgment]

**The pool topology needs verification.** Four pods with eight worker threads each do not establish how many pools exist. [3]

Meanwhile, reported service-wide peak connections fall from 31 to 8, despite exhausted eight-connection pools on several pods. [1]

This discrepancy warrants runtime inspection, not an assumption that the service has 32 usable connections. [judgment]

**The ORM change is not the first rollback target.** Order-query p95 changes from 52 to 58 ms; order-line p95 improves from 30 to 26 ms. [1]

However, these spans do not establish connection hold duration or query count per request. Therefore, inspect both before excluding the ORM change. [judgment]
