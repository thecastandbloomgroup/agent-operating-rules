## Headline

Restore the connection pool settings from before release 2026.10.21, because the pool change causes the latency rise and the 503 errors.

- `db.pool.acquire` p95 rose from 3 ms to 690 ms and 96% of errors are pool timeouts [1].
- The pool max_size fell from 50 to 8 connections and the acquire timeout fell from 30 s to 5 s [3].
- The database has spare capacity: CPU peak is 41% and the pool change, not database load, causes the wait [1].
- The ORM change and the cache TTL change are secondary causes; neither explains the timeouts.

## Background

The API p95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed the connection pool, the cache TTL, and the ORM query loading [3].

## Relevance

The error rate grew 20 times to 0.40%, and 96% of errors are 5 second timeouts that return HTTP 503 to customers [1]. The fix is a small config change.

## Information

**Evidence.** The traces show where the time goes:

- In window B, `db.pool.acquire` adds p50 140 ms and p95 690 ms, against a window A baseline of p50 1 ms and p95 3 ms [1]. No other span rose by more than 5 ms [1].
- The error rate rose from 0.02% to 0.40%. 96% of errors in window B are `PoolTimeout: acquire timed out after 5 s` [1].
- The logs show 1,800 to 2,400 "pool exhausted" warnings per hour in window B, against none per hour in window A [2]. Since 20 October saw none, the release on 21 October is the change point [2].
- The diff shows the pool change: `max_size` 50 to 8, `acquire_timeout_s` 30 to 5 [3].
- The deployment note gives the scale: 4 pods with 8 worker threads each, 32 workers in total, so 8 workers share one pool of 8 [3]. Log lines show pool use of 8 of 8 with up to 14 waiters per pod [2].
- The cache shows the second cause. `default_ttl_s` fell from 300 to 60 [3], and the miss rate rose from 12% to 31% [1]. The rate is 405 requests per second, near the window A peak of 410, so load did not rise [1].
- The database rejects the load explanation. Database CPU peak rose only from 38% to 41% [1]. Active connections from this service fell from a peak of 31 to 8 [1]. Window A ran 31 connections without timeouts, so the constraint is the pool config, not the database.
- What changed in the ORM is not at fault. The `selectinload` change splits one query into two, but `db.query orders` p95 moved 52 to 58 ms and `db.query order_lines` p95 moved 30 to 26 ms [1]. Both stayed fast.

**Assumption log.**

- A1. The pool is per pod, so the service runs 4 pools of 8. Why not measured: the diff does not state the pool scope. Validate by: read the pool config loader for one pod. If wrong: the service runs one pool of 8 for 32 workers, the rollback still applies.
- A2. The OPS-412 database connection limit per service is at least 32. Why not measured: the ticket is not attached. Validate by: ask the database owner for the limit. If wrong: the final pool sizing must use limit divided by pod count.
- A3. 8 concurrent requests can hold all 8 connections, so bursts queue. Why not measured: no trace span covers connection hold time. Validate by: add a hold time span and sample 100 requests. If wrong: reduce the queue estimate; the rollback still removes the timeouts.

**Alternative considered.** The ORM `selectinload` change causes the slow query and extra load. It loses: its two spans stayed fast (p95 58 ms and 26 ms), database CPU rose only 3 percentage points, and the cache miss rise explains the extra rows read [1].
