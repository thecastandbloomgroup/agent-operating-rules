## Headline

Restore the database connection pool size: the release cut it from 50 to 8 per pod, and pool waits now add about 690 ms at p95.

- The traces show db.pool.acquire p95 rose from 3 ms to 690 ms, while query latencies stayed flat ([3]).
- Pool-exhausted warnings went from none to 1,800 to 2,400 per hour ([1]).
- Database CPU stayed at 38 to 41 percent under the same request rate, so the database has capacity ([3]).
- The cache TTL and ORM changes are secondary; the ORM loader change works as intended ([3], [inference]).

## Background

API p95 latency rose from 120 ms to 900 ms after release 2026.10.21, deployed 2026-10-21 14:05 UTC. The release changed the DB pool config, the cache TTL, and the ORM loader. Logs, traces, and the diff are attached ([1], [2], [3]).

## Relevance

The error rate rose from 0.02% to 0.40%, and 96% of errors are PoolTimeout after 5 s ([3]). Requests fail for users now, so the fix belongs in the next deploy window.

## Information

The pool change is the cause, and three lines of evidence agree.

1. Acquisition dominates the request path. Pool acquire p95 went from 3 ms to 690 ms, and total p95 from 120 ms to 900 ms against the window A baseline ([3]).
2. Supply fell, demand did not. Window A peaked at 31 active connections from this service at 410 rps ([3]). Window B caps the pool at 8 per pod ([2]). Demand now exceeds supply by close to 4 to 1.
3. The database is not the limit. Server CPU stayed at 38% to 41%, and per-query latencies stayed flat at p95 52 to 58 ms ([3]). However, exhausted-pool warnings rose from none to over 1,800 per hour within 24 hours ([1]).

Secondary findings:

- The cache TTL cut from 300 s to 60 s raised the miss rate from 12% to 31% ([2], [3]). Per-query latency stayed flat, so this adds load, not per-query delay ([inference]). Treat it as secondary.
- The selectinload change in orders.py adds one extra query for order lines. The order_lines span appeared with p95 30 ms to 26 ms, so the change works as planned ([3]). Keep it.

**Assumption log**

- A1. The OPS-412 connection limit allows at least 32 connections from this service. Why not measured: the material does not state the limit. Validate by: read OPS-412 and the DB max_connections setting. If wrong: keep a small pool and add PgBouncer in transaction mode.
- A2. max_size: 8 applies per pod, per the "8 of 8" lines in the logs ([1]). Why not measured: the material does not state the config scope. Validate by: check one pod's connection count under load. If wrong: set the pool per worker instead of per pod.

**Alternative considered**

Revert the selectinload change as a suspected N+1 query. It loses: the order_lines query p95 fell from 30 ms to 26 ms, and pool acquire, not queries, carries 77% of the added latency ([3]).

## End

1. Size the pool from the OPS-412 limit and apply it. Increment: in one session, read the limit, then set per-pod max_size so that 4 pods stay under it; candidate 16 per pod, 64 total. Blocker: it removes the queueing that produces 690 ms p95 waits. Test:

Acceptance test: metric is cache miss rate, baseline 12%, pass threshold at or below 15%, sample size 30 minutes at about 400 rps.    Cynefin domain: Clear.

Steps 1 and 2 ship together. Step 4 has no dependency and can run in parallel.

Condition that changes this plan: if A1 is false, replace Steps 1 and 2 with a measured small pool plus PgBouncer in transaction mode.
