## Headline

Measure the flake rate and the failure causes first, then quarantine the worst tests and probe one fix.

- The cause is unknown, so the first step is data from past runs.
- Test-level causes are the most common, so tests are the first place to look.
- Quarantine protects the team now, and a fix probe finds the real cause.

## Background

The request says the build is flaky. A flaky build passes and fails on the same code. The message names no project, tool, or logs. The next action does not depend on a missing answer, so this response assumes and proceeds.

## Relevance

Each false failure costs a rerun and weakens trust in the signal. Teams then ignore real failures.

## Information

**Evidence**

- Google found that 1.5% of all test runs were flaky. Almost 16% of its tests showed some flakiness [1].
- A study of 201 fix commits in 51 open-source projects found three main causes [2]:
  - async wait, 45%
  - concurrency, 20%
  - test order dependency, 12%
- It is likely (66 to 100%) that the cause sits in tests and not in the build tool [judgment]. The basis is the two studies above, which are not about this build.

**Assumption log**

A1. The CI system keeps logs of the last 50 runs. Why not measured: the material does not state it. Validate by: open the CI history page. If wrong: Step 1 starts with 20 new runs instead.

A2. The flakes come from tests, not from the CI hardware or network. Why not measured: no tool can reach the build. Validate by: check whether failures cluster on one test or one runner. If wrong: replace Step 2 with a runner audit.

A3. Tests can be tagged or skipped by name. Why not measured: the material does not state the test framework. Validate by: read the framework docs for skip or tag support. If wrong: move the flaky tests to a separate job.

**Alternative considered**

The alternative is to retry the whole build on failure. It loses because it hides the cause and raises build time on every flake [judgment].

## End

I recommend that we take these four actions:

1. **Classify past failures.** Export the last 50 runs and group failures by test name and error text. This removes the blocker of an unknown cause. Domain: Complicated, because analysis of the logs reveals the cause. Kind: deterministic. Test:
   ```gherkin
   Given an export of 50 runs with known failures
   When the grouping script runs
   Then it lists each failing test with its failure count
   ```
2. **Quarantine the top flaky tests.** Move tests that failed on passing commits into a separate non-blocking job. This stops false failures at once. Step 2 MUST NOT start until Step 1 passes. Domain: Clear, because quarantine is a known best practice. Kind: deterministic. Test:
   ```gherkin
   Given a test listed as flaky in Step 1
   When the main build runs
   Then the main build does not run that test
   And the quarantine job runs it
   ```
3. **Measure the baseline flake rate.** Rerun one passing commit 30 times. This gives a number to compare every fix against. Domain: Complicated, because the measurement method is known. Kind: stochastic. Test: the metric is the failure rate per run. The baseline is the rate from Step 1. The pass threshold is a rate below 2% after quarantine. The sample size is 30 runs.
4. **Probe one fix.** Pick the top cause from Step 1. For example, replace a fixed sleep with a wait on a condition. Apply it to one test only. Run it in parallel with Steps 2 and 3. Domain: Complex, because the cause shows only after the change. Kind: stochastic. Test: the metric is the failure rate of that test. The baseline is its rate from Step 1. The pass threshold is zero failures in 50 runs. The budget is one working session. Stop the probe if the rate does not fall after 50 runs.

Condition that changes this: if A2 is false, replace Step 2 with a runner audit.
