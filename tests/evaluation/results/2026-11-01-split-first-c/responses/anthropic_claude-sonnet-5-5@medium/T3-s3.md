## Headline

Split the request in two: migrate to JWT first with the sign-up flow unchanged, and run sign-up improvements as measured experiments.

- The two goals have different test types: the migration is deterministic, and conversion is stochastic.
- Conversion has no baseline today, so the first step is to measure the funnel.
- Randomized experiments keep the migration from distorting the conversion result.
- Each step is small enough to finish in one working session.

## Background

The request has two goals: replace server-side sessions with JSON Web Tokens (JWT) in the auth service, and raise sign-up conversion. The material gives no funnel data, no client list, and no traffic figures. JWT is a signed token format defined in RFC 7519 [1].

## Relevance

A migration that ships together with sign-up changes makes any conversion shift impossible to attribute. A failed token design also locks users out, so it is costly to reverse.

## Information

Evidence:

- A JWT cannot be revoked on its own, because the server holds no state. Short expiry plus server-side refresh-token tracking restores revocation [judgment].
- Pin the signing algorithm and validate every claim, per the JWT best-practice guidance.

  Source: [2]

- The two goals need different tests (Section 6.4 of the operating rules). A migration has fixed pass criteria. A conversion change has a random outcome.
- No conversion baseline exists in the material, so no change can be called an improvement yet [no source].
- Sign-up changes and the migration touch different steps of the user path. Random assignment of users to variants spreads any migration effect across both arms [inference].

Assumption log:

A1. Clients are first-party web and mobile apps that we control. Why not measured: the material does not state it. Validate by: list the clients that call the auth service. If wrong: add a token-handling step for third-party clients.

A2. Funnel analytics for sign-up do not exist yet. Why not measured: no tool can reach our analytics. Validate by: check for sign-up start and sign-up complete events. If wrong: skip Step 1 and use the existing baseline.

A3. Sign-up traffic reaches the needed sample in two weeks. Why not measured: the material does not state traffic. Validate by: compute the sample size from the Step 1 baseline. If wrong: extend the probe budget or test a larger change.

Confidence that A3 holds: about as likely as not, because traffic is unknown.

Alternative considered: keep sessions and work only on conversion. It loses because the request names the migration explicitly, and a session store can be kept as a fallback during rollout instead.

Cynefin classification [3] drives the action forms below. The migration is Complicated, because expertise picks the token design. Conversion is Complex, because user response is visible only after a trial.

## End

I recommend that we do the following steps in order.

1. Instrument the sign-up funnel and record a two-week baseline. This removes the missing baseline that blocks Step 4. Domain: Clear, because event tracking is a known practice. Kind: deterministic.
   Test:
   - Given a new visitor opens the sign-up page
   - When the visitor submits the form
   - Then a "signup_started" event and a "signup_completed" event appear once each in the log

2. Add JWT issue and verify beside sessions, behind a feature flag. Use 15-minute access tokens, rotating refresh tokens, a pinned algorithm, and a server-side revocation list. This adds the migration capability. Domain: Complicated, because a design analysis picks storage and revocation. Kind: deterministic. Write the design note before the code.
   Test:
   - Given a user with a valid refresh token
   - When the token is revoked and the user requests a new access token
   - Then the service returns 401 and the revoked token is rejected

3. Move clients to JWT in cohorts, then retire sessions. Step 3 MUST NOT start until the test in Step 2 passes. Start with 5% of logins. This removes the session store. Domain: Complicated, because the rollout order follows known risk analysis. Kind: deterministic.
   Test:
   - Given 5% of logins use JWT
   - When the login error rate is compared with the session baseline
   - Then the JWT error rate is not higher than the baseline

4. Run one sign-up probe: remove one form field, split users 50/50. This tests a conversion lever, and its leverage is a guess. Domain: Complex, because the user response is visible only afterward. Kind: stochastic. Run it in parallel with Steps 2 and 3, and start it after Step 1 ends.
   - Metric: sign-up completion rate.
   - Baseline: the Step 1 result.
   - Pass threshold: a relative gain of 10% or more [judgment].
   - Sample size: set by a power calculation at 80% power from the Step 1 baseline.
   - Stop condition: a relative drop of 5% or more, or the budget ends.
   - Budget: two weeks.
   - Guardrail: the login success rate in each arm.

   If A3 is false, replace Step 4 with a larger change.
