## Headline

Split this into two projects, migrate to JSON Web Tokens (JWT) first with a safe cut-over, and test sign-up changes separately.

- The migration is deterministic work, and the conversion work is an experiment, so each needs its own test.
- JWT does not raise conversion by itself, so a combined release hides which change caused any movement.
- Stateless tokens cannot be revoked before they expire, so the design needs a short token life and a server-side refresh record.
- A funnel baseline must exist before any conversion claim can pass a test.

## Background

The request has two goals: replace server sessions with JWT in the auth service, and raise sign-up conversion. The material gives no details on the current stack, the clients, or the current conversion rate. This response plans both goals and keeps their releases apart.

## Relevance

A bundled release makes a conversion change impossible to attribute. A weak token design also creates a security gap that sessions do not have.

## Information

Evidence:

Assumption log:

A1. The service has one web client and a database-backed session store. Why not measured: the material does not state it. Validate by: read the service configuration. If wrong: Step 2 grows to cover more clients.

A2. Immediate revocation is required for logout and account bans. Why not measured: the user has not answered. Validate by: ask the security owner. If wrong: Step 2 can drop the refresh record.

A3. A funnel baseline can be pulled from existing analytics. Why not measured: no tool can reach it. Validate by: query the last 30 days of sign-up events. If wrong: Step 1 must first add event tracking.

Alternative considered: keep sessions and work only on conversion. It loses because the user asked for the migration. It also stays valid if A2 holds and the team has no scaling need for stateless tokens. [judgment]

## End

I recommend that we take these four steps, in this order:

1. **Capture the sign-up funnel baseline.**
   - Increment: one query or dashboard of visits, form starts, and completed sign-ups for 30 days.
   - Blocker removed: no conversion claim can pass a test without a baseline.
   - Kind: deterministic. Domain: Clear, because funnel counting is a known practice.
   - Test:
     - Given 30 days of sign-up events
     - When the funnel query runs
     - Then it returns one conversion rate that matches the raw event count

2. **Build JWT auth in dual-run mode behind a flag.**
   - Increment: a 15-minute access token and a rotating refresh token stored on the server, following [2]. The service accepts both sessions and JWT.
   - Blocker removed: the migration risk of a hard switch and the revocation gap.
   - Kind: deterministic. Domain: Complicated, because expert analysis picks the token design. Name that analysis in a short design note first.
   - Test:
     - Given a user with a valid refresh token
     - When an admin revokes that user
     - Then the next refresh request returns 401, and the old session path still works for session users
   - Step 4 MUST NOT start until this test passes in production for 30 days.

3. **Run one sign-up experiment.**
   - Increment: one A/B test (random split of visitors into two groups) on the sign-up form, for example fewer required fields.
   - Blocker removed: the lack of evidence on which change moves conversion.
   - Kind: stochastic. Domain: Complex, because user response is visible only afterward. Leverage is a guess.
   - Probe limits: stop on a drop of 1 point or more in sign-up completion. Budget is one form change and four weeks.
   - Acceptance test: the metric is the completion rate from Step 1. The baseline is the Step 1 rate. The pass threshold is a gain of 1.5 points, absolute. The sample size is about 6,700 per group at a 10% baseline, 80% power, and 5% significance. [inference] Recompute with the real baseline.
   - Step 3 MUST NOT ship in the same release as Step 2. It MAY run in parallel with Step 2 work.

4. **Retire sessions.**
   - Increment: remove the session code path and store.
   - Blocker removed: two live auth systems double the attack surface.
   - Kind: deterministic. Domain: Clear, because removal after zero use is standard practice.
   - Test:
     - Given 30 days with zero session logins
     - When the session path is removed
     - Then all login tests pass and no request touches the session store

## Follow-up

Conditions that change the recommendation:

- If A2 is false, drop the refresh record in Step 2.
- If A3 is false, add event tracking to Step 1 before the query.
- If traffic is too low for 6,700 visitors per group in four weeks, replace Step 3 with five user interviews.
