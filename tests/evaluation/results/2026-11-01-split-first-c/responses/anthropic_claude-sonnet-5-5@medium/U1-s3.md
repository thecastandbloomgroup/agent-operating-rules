## Headline

Measure the flakiness first, then fix the largest cause, because a retry or a guess hides the real problem.

- A flaky build passes and fails on the same code, so the first need is a failure rate per test.
- Most flaky tests share a few known causes, so classifying failures narrows the fix.
- A quarantine keeps the build usable while the fix is in progress.

## Background

The request says the build is flaky. It gives no logs, no tool, and no history. This response assumes a continuous integration (CI) build that fails at random on unchanged code.

## Relevance

A flaky build teaches the team to ignore red results. Real defects then pass unnoticed.

## End

I recommend that we take these steps in order:

1. **Measure the failure rate per test.**
   - Increment: rerun one commit 20 times and record each test result in a table.
   - Blocker removed: no data shows which tests fail.
   - Kind: deterministic.
   - Domain: Clear, because rerun and log is a known practice.
   - Test:
     - Given a commit with no code change
     - When the build runs 20 times
     - Then a table lists each failed test with its failure count

2. **Quarantine the test with the highest failure count.**
   - Step 2 MUST NOT start until the test in Step 1 passes.
   - Increment: move that one test to a non-blocking job.
   - Blocker removed: red builds hide real defects.
   - Kind: deterministic.
   - Domain: Clear, because quarantine is a standard practice.
   - Test:
     - Given the quarantined test fails
     - When the blocking build runs

3. **Classify the failures of the top three tests.**
   - Step 3 MUST NOT start until the test in Step 1 passes.
   - Increment: label each failure as async wait, concurrency, order dependence, or infrastructure.
   - Blocker removed: the fix is unknown.
   - Kind: evaluative.
   - Domain: Complicated, because analysis of the logs finds the cause.
   - Rubric: pass at a weighted score of 70 out of 100.

     - Sample size: 100 runs.
