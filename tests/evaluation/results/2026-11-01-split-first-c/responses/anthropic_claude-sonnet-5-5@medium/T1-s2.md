## Headline

Replace the style debate with one decided standard that a tool enforces, so reviews stop carrying style comments.

- A decision rule ends the disagreement, because no one has to win the argument.
- A formatter and a CI check move style out of human review.
- A measured trial shows whether the friction falls.

## Background

The team has no shared SQL format. Each review includes style arguments. The request is to fix this as a culture problem.

## Relevance

Every review that debates style delays merges and wears down trust. The cost repeats with each pull request.

## Information

**Evidence**
- Large engineering organisations enforce style with automated formatters, so reviewers focus on logic [1].
- The SQL linter and formatter sqlfluff supports many dialects and a shared config file [2].
- Disagreement over style comes from a missing decision rule, not from bad faith [judgment].
- It is likely (66 to 100%) that an enforced formatter cuts style comments, based on one secondary source and [judgment]. Confidence is moderate.

**Assumption log**

A1. The team reviews SQL in pull requests in a Git host. Why not measured: the material does not state it. Validate by: ask in the team channel. If wrong: replace the CI check in Step 3 with a pre-share script.

A2. The team uses one SQL dialect. Why not measured: the material does not state it. Validate by: list the dialects in the repo. If wrong: add one config per dialect in Step 2.

A3. The team accepts one tie-break owner. Why not measured: the user has not answered. Validate by: ask for a yes or no in the Step 1 meeting. If wrong: use a majority vote with a time limit.

A4. About 20 recent reviews exist as a baseline. Why not measured: no tool can reach the repo from here. Validate by: count them in the Git host. If wrong: use the next 20 reviews as the baseline.

**Alternative considered**

Write a long style guide and enforce it by review. It loses because humans apply it unevenly, so the friction stays [judgment].

## End

I recommend that we take these steps, in this order:

1. **Decide the standard in one 45-minute meeting.** This removes the blocker: no agreed rule. Name a tie-break owner first. Compare two or three candidate styles in a Pugh matrix. Task kind: evaluative. Cynefin: Complicated, because expert analysis can pick among several good practices.
   - Criteria and weights: tool support 40%, diff readability 30%, match with existing code 30%.
   - Pass threshold: the top style scores at least 60% of the maximum.
   - Evidence: a sqlfluff run on 5 sample files per style, plus a vote on readability.
   - If no style passes, the tie-break owner picks the top scorer.

2. **Format the repo in one commit.** Step 2 MUST NOT start until Step 1 ends. This adds a single baseline for all files. Task kind: deterministic. Cynefin: Clear, because a known tool applies a known rule.
   - Given the chosen sqlfluff config is committed
   - When the formatter runs on all SQL files
   - Then a second run changes zero files

3. **Add a CI check that fails on style violations.** Step 3 MUST NOT start until the test in Step 2 passes. This removes style from human review. Task kind: deterministic. Cynefin: Clear, because CI checks are standard.
   - Given a pull request with an unformatted SQL file
   - When the CI pipeline runs
   - Then the style check fails and names the file

4. **Run a two-week trial as a safe-to-fail probe.** Start the baseline count now, in parallel with Steps 1 to 3. Task kind: stochastic. Cynefin: Complex, because team reaction is visible only afterward. Leverage is a guess.
   - Metric: style comments per review.
   - Baseline: the mean over the last 20 reviews (A4).
   - Pass threshold: a drop of at least 50% over the next 20 reviews.
   - Budget: one hour per week. Stop early if the count rises for 5 reviews in a row.
   - If the test fails, hold a 30-minute retrospective and revise the config.

## Follow-up

Conditions that change the recommendation:
- If A1 is false, replace Step 3 with a pre-share script.
- If A2 is false, run Steps 1 and 2 once per dialect.
