## Headline

**Do the migration and the conversion work as two separate changes, and measure conversion before you change anything.**

- The two goals have different test types: the migration is deterministic, and the conversion work is stochastic.
- A signed token cannot be recalled before it expires, so the design must handle logout and revocation.
- Both sign-up arms share one auth path, so the migration does not distort the conversion result.

## Background

The request has two goals: replace server sessions with JWT (JSON Web Token, a signed token that carries user claims), and raise sign-up conversion. The conversion rate is the share of visitors who start sign-up and finish it. The material gives no stack, no client list, and no current conversion rate.

## Relevance

Auth changes touch every user, so a failed cutover locks people out. A conversion test run during a migration gives results that no one can read.

## Information

**Evidence**

- A JWT is a signed claim set that a server verifies without a database lookup [1].

- Current guidance says to check the algorithm, issuer, and expiry on every token [2].

- A signed token stays valid until it expires. Logout therefore needs a short expiry or a server-side revoke list [inference].

- Sign-up conversion has no baseline in the material. Any lift target is a [judgment] until Step 1 yields a number.

**Assumption log**

A1. The service has one backend and first-party web and mobile clients. Why not measured: the material does not state it. Validate by: list the client apps in the repository. If wrong: add a token storage step per extra client type.

A2. Sign-up funnel events are not tracked today. Why not measured: no tool can reach the analytics data. Validate by: query analytics for sign-up event counts. If wrong: shorten Step 1 to a check.

A3. Baseline conversion is 20%, and a lift to 23% is worth detecting. Why not measured: the material does not state it. Validate by: Step 1 output. If wrong: recompute the sample size in Step 4.

Sample size for A3, at 5% significance and 80% power, is about 2,940 sign-up starts per arm [inference, standard two-proportion formula].

**Alternative considered**

The strongest alternative is to keep sessions and fix only conversion. It loses if you need stateless scaling across services. That need is not in the material, so confirm it before Step 3 (see A1).

## End

I recommend that we take these four actions in this order:

1. **Instrument the sign-up funnel.**
   - Increment: add four events (view, start, submit, success) to the sign-up flow.
   - Blocker removed: no baseline exists for conversion.
   - Domain: Clear, because event tracking is a known practice.
   - Kind: deterministic. Test, written first:
     - Given a new visitor opens the sign-up page
     - When the visitor completes sign-up
     - Then the four events appear once each in analytics

2. **Choose the token design with a Pugh matrix [3].**
   - Increment: one page that scores "short-lived access token plus rotating refresh token" against "keep sessions".
   - Blocker removed: the logout and revocation risk.
   - Domain: Complicated, because analysis picks among good practices.
   - Kind: evaluative. Rubric, written first:
     - Criteria: revocation speed (weight 3), client effort (2), scaling need (2), security per [2] (3).
     - Pass threshold: the winner scores at least 20% above the baseline option.
     - Evidence for each criterion: a repository check or a written spec.

3. **Run JWT beside sessions.**
   - Step 3 MUST NOT start until the Step 2 page passes its rubric.
   - Increment: the service issues and accepts both credentials on the login endpoint only.
   - Blocker removed: a one-step cutover that can lock users out.
   - Domain: Complicated, because the expert analysis in Step 2 sets the design.
   - Kind: deterministic. Test, written first:
     - Given a user with a valid password
     - When the user logs in
     - Then the response holds a JWT with a 15-minute expiry, and a token with a wrong signature gets a 401 status

4. **Probe one sign-up change.**
   - Increment: remove one form field for half of new visitors, on the same auth path for both arms.
   - Step 4 MUST NOT start until Step 1 reports a baseline.
   - It runs in parallel with Step 3.
   - Capability added: a measured lift, not a guess.
   - Domain: Complex, because user response shows only after the change. Its leverage is a guess.
   - Kind: stochastic. Acceptance test, written first:
     - Metric: sign-up completion rate.
     - Baseline: the Step 1 value (A3 assumes 20%).
     - Pass threshold: an absolute lift of at least 3 points.
     - Sample size: about 2,940 starts per arm.
   - Budget: two weeks of traffic.
   - Stop condition: halt if completion in the test arm falls 3 points below the baseline.

If A3 is false, recompute the sample size in Step 4 from the Step 1 baseline. If scaling across services is not needed, replace Step 3 with "keep sessions".
