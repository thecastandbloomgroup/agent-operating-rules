## Headline

Roll back the latest change now, then diagnose only if the rollback fails, and brief the executives with facts.

- Most outages follow a change, so the change history is the fastest lead.
- A rollback is faster and safer than a live fix under time pressure.
- The executive call needs a short status, not a root cause.

## Background

Checkout returns HTTP 500 for every user since 09:12 (per the user's message). The user is the on-call engineer. The executive call starts in ten minutes.

## Relevance

Every minute of downtime blocks all revenue from checkout. The next ten minutes decide whether the call opens with a fix underway or with no data.

## Information

Evidence:

- Google reports that about 70% of outages come from changes to a live system. [1]
- The failure began at one exact time and affects all users. That pattern points to a shared cause, such as a deploy, a config change, or a dependency. [judgment]
- A total outage with an unknown cause is a Chaotic situation, so stabilise before analysis. [2]

A1. A deploy or config change happened near 09:12. Why not measured: the material does not state it. Validate by: read the deploy log for 09:00 to 09:12. If wrong: skip to Step 2.

A2. A tested rollback path exists and takes under five minutes. Why not measured: no tool can reach the pipeline. Validate by: check the last rollback in the deploy log. If wrong: disable the change with a feature flag instead.

A3. A checkout test order can run in production. Why not measured: the material does not state it. Validate by: run one test order now. If wrong: use the error-rate dashboard as the pass signal.

Alternative considered: debug the live system first. It loses because diagnosis takes longer than ten minutes in most cases, and a rollback reverses cheaply if it does not help. [judgment]

## End

I recommend that we take these actions in this order:

1. **Roll back the last change in the 09:00 to 09:12 window (about 5 minutes).** This removes the outage if a change caused it. Domain: Chaotic, because no cause is known and the system must stabilise first. Kind: deterministic. Test, written first:
   - Given checkout returns 500 for every user
   - When the last change is rolled back
   - Then a test order returns 200 and the 500 rate falls to the pre-09:12 baseline within five minutes

2. **Check three suspects only if Step 1 fails: database, payment provider, cache (about 5 minutes).** This finds the failing dependency. Step 2 MUST NOT start until the Step 1 test fails or no change exists. Domain: Complicated, because expert analysis can find the cause. Kind: evaluative. Rubric, written first:
   - Criteria and weights: error in logs matches the 09:12 start time (50%), health check of the dependency fails (30%), dependency status page shows an incident (20%).
   - Pass threshold: a suspect scores 70% or more.
   - Evidence: log lines, health check output, status page text.

3. **Write a three-line status for the executive call (2 minutes, start at minute 7).** This gives the call facts. Step 3 MAY run while Step 1 waits for the deploy. Domain: Clear, because the format is a known practice. [1] Kind: deterministic. Test, written first:
   - Given the call starts in three minutes
   - When the status is posted
   - Then it states impact, current action, and the time of the next update

If A1 is false, replace Step 1 with Step 2.
