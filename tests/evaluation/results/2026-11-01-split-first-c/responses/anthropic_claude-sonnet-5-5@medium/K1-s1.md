## Headline

Raise the database connection pool, which the release cut from 50 to 8, and restore the cache TTL (time to live).

- The pool cut explains most of the latency rise: 88% of the p95 increase is time spent waiting for a connection.
- The shorter cache TTL is a smaller second cause: it raises cache misses and so adds database load.
- The ORM (object-relational mapper) change does not explain the slowdown, because query times did not change.
- The database server is not the bottleneck, because its CPU rose only 3 points.

## Background

The API p95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed the pool, the cache TTL, and one ORM query. The attached logs, diff, and traces cover the change.

## Relevance

The error rate is now 0.40%, up from 0.02%. Each error is a 503 after a 5 s wait. The problem grows with traffic.

## Information

**Evidence**

- Pool wait is the main cause. The p95 of `db.pool.acquire` rose from 3 ms to 690 ms. That is 687 of the 780 ms total rise, or 88%.
  - See traces.txt, span table. [3]
- The diff cut `max_size` from 50 to 8 and `acquire_timeout_s` from 30 to 5.
  - See release.diff, config/db.yaml. [2]
- Of the errors, 96% are `PoolTimeout`. Logs show "pool exhausted" 1,800 to 2,400 times per hour on 2026-10-22, against none on 2026-10-20.
  - See logs.txt, note. [1]
- The cache miss rate rose from 12% to 31%. The TTL fell from 300 s to 60 s.
  - See traces.txt, cache row. [3]
  - See release.diff, config/cache.yaml. [2]
- The ORM change adds `selectinload`, which loads order lines in a second query. The `db.query orders` p95 moved from 52 ms to 58 ms. The `order_lines` p95 fell from 30 ms to 26 ms.
  - See traces.txt, query rows. [3]
- Database CPU at peak rose from 38% to 41%. Peak load stayed flat: 410 requests per second (rps) before, 405 rps after.
  - See traces.txt, last section. [3]
- Confidence that the pool is the main cause: high confidence, three independent sources agree (diff, logs, traces).

**Assumption log**

A1. The limit of 8 connections is shared by the whole service, so 32 workers share 8 connections. Why not measured: the material does not state it. Validate by: count connections by application name in `pg_stat_activity`. If wrong: the limit is per pod, and the fix is the same but smaller.

A2. The database connection limit in OPS-412 allows at least 32 connections for this service. Why not measured: the material does not state the limit. Validate by: ask the OPS-412 owner for the number. If wrong: add an external connection pooler, or lower the worker count.

A3. No product need requires the 60 s TTL. Why not measured: the user has not answered. Validate by: ask the product owner about data staleness. If wrong: keep 60 s and size the pool for the higher miss rate.

Two facts conflict. Logs show "8 of 8" on every pod, and waiter counts reach 14, above the 8 threads per pod. Traces show only 8 connections service-wide. [inference] A1 fits the traces better.

**Alternative considered**

Revert the `selectinload` change first. It loses because query times did not change, so the expected gain is under 6 ms at p95. [judgment]
