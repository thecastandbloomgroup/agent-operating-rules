## Headline

Replace the style debate with one automated formatter that the team adopts by a short, timeboxed decision.

- The friction comes from taste, and taste has no tie-breaker. [judgment]
- A tool that rewrites code to one layout removes the topic from review.
- A written rule makes the tool, not the reviewer, the authority.
- A measured trial shows whether the friction fell.

## Background

The team disagrees on SQL layout. Each pull request (PR, a proposed change that others review) draws style comments. The request is to end this friction.

## Relevance

Every style comment costs reviewer time and adds tension. Both effects repeat on each PR until someone sets a rule.

## Information

**Evidence**
- A formatter is a tool that rewrites code into a fixed layout. SQLFluff is one such tool for SQL, and it also checks rules [1].
- No team data was provided. The size of the style problem is unmeasured. [no source]
- Style debates persist when no one owns the decision. [judgment]
- Confidence that a formatter cuts style comments by 80% or more: 70% likely, based on [judgment] and no local data.

**Assumption log**

A1. The team uses git, PRs, and a continuous integration (CI, a server that runs checks on each change) system. Why not measured: the material does not state it. Validate by: ask one developer. If wrong: replace Step 3 with a local script.

A2. The team writes one SQL dialect, such as PostgreSQL. Why not measured: the material does not state it. Validate by: scan the repository for dialect keywords. If wrong: set a dialect per folder in Step 2.

A3. Members accept any consistent style over their own preference. Why not measured: the user has not answered. Validate by: the vote in Step 1. If wrong: the lead decides, and Step 4 records the decision.

**Alternative considered**

Write a long style guide and enforce it in review. It loses because humans apply rules unevenly, and the debate returns on every PR. [judgment]

## End

I recommend that we take these five steps. Domains follow Snowden and Boone [2].

1. **Choose one formatter in a 30-minute session.**
   - Increment: test three candidates (SQLFluff, sqlfmt, pgFormatter) on five real files.
   - Blocker removed: no agreed decision exists.
   - Kind: evaluative. Write the rubric first. Criteria and weights: dialect support 40, matches existing code 20, CI and pre-commit support 20, auto-fix mode 20. Pass threshold: 70 of 100. Evidence: output on the five files.
   - Domain: Complicated, because analysis of the tools picks the best practice.
   - Rule: if two tools tie, the lead picks one. The team MUST accept the result.

2. **Commit the formatter config and one reformat of the repository.**
   - Increment: one commit with the config and the reformatted files.
   - Blocker removed: old code would show format noise in later diffs.
   - Kind: deterministic. Test in Gherkin form [3]:
     - Given the config is committed
     - When the formatter runs on any SQL file
     - Then the file does not change on a second run
   - Domain: Clear, because the formatter docs give a known procedure.
   - Step 2 MUST NOT start until Step 1 meets the threshold.

3. **Add a pre-commit hook (a script that runs before a commit is saved) and a CI check.**
   - Increment: one hook file and one CI job.
   - Blocker removed: people can skip the formatter by accident.
   - Kind: deterministic. Test:
     - Given a SQL file with wrong layout
     - When a developer opens a PR with it
     - Then the CI check fails and names the file
   - Domain: Clear, because hook and CI setup is a standard practice.
   - Step 3 MUST NOT start until the test in Step 2 passes.

4. **Publish a one-page rule: the tool decides layout.**
   - Increment: a page in the repository that states: "Reviewers MUST NOT comment on layout. Change the config by PR."
   - Blocker removed: reviewers still raise taste points.
   - Kind: deterministic. Test:
     - Given the page is merged
     - When a reviewer reads the page
     - Then it names who changes the config and how
   - Domain: Clear, because the rule applies to a known tool.

5. **Run a two-week probe on the effect.** It runs in parallel with Steps 2 to 4 and is a Complex probe.
   - Increment: count layout comments per PR.
   - Blocker removed: no evidence exists that the change works.
   - Kind: stochastic. Metric: layout comments per PR. Baseline: the last 20 merged SQL PRs. Pass threshold: a drop of 80% or more. Sample size: 20 PRs after adoption.
   - Budget: 2 hours of counting. Stop condition: stop and review if two members say the rule hurts their work.
   - Domain: Complex, because team reaction shows only after the change. The leverage claim is a guess.

If A3 is false, the lead picks the formatter in Step 1 without a vote.
