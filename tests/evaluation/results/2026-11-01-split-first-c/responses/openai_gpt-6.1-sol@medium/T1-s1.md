## End

I recommend that we take these three steps:

### 1. Publish a one-page review agreement

**Test first, deterministic:**

```gherkin
Given a disagreement about SQL format
When the team applies the agreement
Then it identifies the default, decision owner, exception route, and policy-change route
```

In one 30-minute meeting, approve a draft with these rules:

- The formatter controls supported format choices.
- Reviewers do not block changes over personal format preferences.
- Anyone can raise concerns about query behavior or clarity.
- One named maintainer resolves uncovered format choices after hearing objections.
- Anyone can propose a policy change with an example and a reason.
- Existing files change only when edited, unless the team approves separate cleanup.

This removes uncertainty about decision rights. [judgment]

**Domain: Clear**, because the document has fixed acceptance checks; its effect on team behavior remains untested.

### 2. Add a small, tested format check

**Test first, deterministic:**

```gherkin
Given representative queries in the team's SQL dialect
When the selected formatter runs twice
Then the second run makes no further changes
And the formatted queries pass the existing query checks
```

After Step 1 passes, spend one work session checking dialect support and repository compatibility. Select the tool through that analysis.

Pin its version and configuration. Add one local command and the same check to continuous integration, the automated repository checks.

Avoid a repository-wide rewrite during this session. This adds a repeatable default without mixing format changes with query changes. [judgment]

**Domain: Complicated**, because tool compatibility requires analysis, but tests can establish its behavior.

If A2 fails, use the written convention during the pilot rather than forcing an incompatible tool.

### 3. Run a capped review-culture pilot

**Acceptance test first, stochastic:** measure format-only discussion threads per SQL review.

- **Baseline:** the latest 10 SQL reviews before the pilot.
- **Sample:** the first 10 SQL reviews during the pilot.
- **Pass threshold:** at least 50% fewer format-only threads per review.
- **Safety condition:** no unresolved report that the agreement suppresses a substantive concern.
- **Budget:** two weeks, plus one 20-minute team review.
- **Stop condition:** pause the affected rule if the tool changes query behavior or the agreement silences substantive review.

Start only after Step 1 passes and Step 2 establishes a usable default. At the team review, ask which rules helped and which caused friction.

Run the trial before accepting the policy. If fewer than 10 reviews occur, report insufficient evidence rather than declaring success.

**Domain: Complex**, because the team’s response becomes visible only through use. This is a safe-to-fail probe; its expected benefit is a guess. [judgment]
