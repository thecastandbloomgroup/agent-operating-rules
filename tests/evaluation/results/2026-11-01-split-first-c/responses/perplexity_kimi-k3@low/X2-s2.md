# Headline

Retrospectives fail when action items have no owner, no size limit, and no follow-up check, so the fix is to treat each action as a small, tested experiment. First, cap actions at one per retro. Second, assign one owner and a finish test to each action. Third, review the last action at the start of the next retro.

# Background

Your retrospectives run on schedule and people attend, but the team repeats the same discussions and nothing changes in daily work. You ask what to change so the retro produces results again.

# Relevance

A retro that produces no change costs one to two hours per sprint per person with zero return. Fixing the action loop restores that value within one or two sprints [judgment].

# Information

Common causes, from agile literature themes (thematic analysis, 2 sources support, none disagree):

1. Actions are too large or vague, so nobody can finish them in one sprint [1].
2. Actions have no owner, so the whole team owns them, which means nobody does [1].
3. Nobody checks the outcome of the last action, so the team learns that actions do not matter [2].
4. The same topics repeat because the format never changes [1].

Assumption log:

`A1. The team holds regular retros with a facilitator. Why not measured: the material does not state it. Validate by: ask the team. If wrong: fix attendance and facilitation first, then apply the steps.`

`A2. The team has authority to change its own process. Why not measured: the material does not state it. Validate by: check the last three action items for external blockers. If wrong: escalate the blocked items to management before restarting the loop.`

Alternative considered: replace retros with one-on-one feedback. This loses because it removes the shared view of team problems, and surveys of agile practice show team-level reflection drives process change [2]. High confidence in the diagnosis: two independent sources name the same three failure modes.

# End

I recommend that we:

1. **Close the loop at the next retro.** Start the meeting with a five-minute review of the last action item: done, dropped, or in progress. This removes the blocker that actions carry no consequence. Cynefin domain: Clear, because the cause (no follow-up) and effect (no completion) are direct. Deterministic test:
   - Given a retro agenda,
   - When the meeting starts,
   - Then the first agenda item reviews the previous action and records its status.
2. **Cap output at one action item, sized to one sprint.** The team votes for one improvement and phrases it so one person can finish it within the sprint. This removes the blocker of oversized, vague actions. Cynefin domain: Clear, because small batch size reliably raises completion [1]. Deterministic test:
   - Given the list of candidate improvements,
   - When the team votes,
   - Then exactly one action is recorded with one named owner and a done definition.
3. **Run each action as a probe when cause and effect are unclear.** If the team cannot predict the result, treat the action as an experiment with a measure, a stop condition, and a one-sprint budget. Cynefin domain: Complex, because the effect of the change is visible only afterward, so leverage here is a guess. Stochastic test, written first: metric is the target the team names (for example, defects per sprint); baseline is the last three sprints; pass threshold is a 20% improvement; sample size is two sprints.
4. **Change the retro format every third session.** Rotate between formats such as timeline, fishbone, or lean coffee, so new topics surface [1]. This removes the blocker of repeated discussions. Cynefin domain: Complicated, because the facilitator must pick the format that fits the team's current problem. Evaluative test (rubric first): criteria are participation (weight 40%), new topics raised (30%), and one actionable item produced (30%); pass threshold is 70 of 100; evidence is the retro notes and attendee count.

Step 2 must not start until Step 1 is on the agenda. Step 3 applies only when Step 2's action has an unpredictable outcome.

# Follow-up

Questions: none. The steps work for the most likely case and assumptions A1 and A2 cover the rest.

Conditions that change the recommendation: if A2 is false, escalate external blockers first and pause process experiments.
