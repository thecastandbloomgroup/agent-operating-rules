# Headline

The pool size cut (50 to 8) is the cause of the latency rise, so restore a pool of about 50 and rebuild cache TTL to 300 s as a fast mitigation.

- Pool acquire time rose from 3 ms to 690 ms at p95, which matches the p95 jump from 120 ms to 900 ms.
- Query times are unchanged, so the ORM change is not the cause.
- The cache TTL cut raised the miss rate from 12% to 31%, which adds load but is secondary.
- 96% of errors are pool acquire timeouts, which ties the errors to the same cause.

# Background

p95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed the pool config, the cache config, and the ORM query. Logs, traces, and the diff are attached.

# Relevance

The service now returns 503s to real users at a 0.40% error rate. Each day with the 8-connection pool risks more timeouts at peak traffic.

# Information

## Evidence

First, the pool. Max connections dropped from 50 to 8 per pod, and acquire timeout dropped from 30 s to 5 s (release.diff, config/db.yaml). Pool acquire p95 rose from 3 ms to 690 ms [1]. Active DB connections peaked at 8, versus 31 before [1]. The service runs 32 workers in total, but 4 pods at 8 connections give 32 connections only when nothing queues. DB CPU stayed near 40%, so the database has spare capacity.

Second, the queries. Orders and order-lines query times are stable at p95 (52 to 58 ms, 30 to 26 ms) [1]. Therefore the selectinload change did not slow the database work.

Third, the cache. TTL dropped from 300 s to 60 s (release.diff, config/cache.yaml). Cache miss rate rose from 12% to 31% [1], and logs show repeated misses on the miss path. Each miss holds a connection longer because more requests reach the database at once, so the cache change amplifies the pool problem. It is not the root cause, because acquire waits dominate the added latency (690 ms of 780 ms added at p95) [1].

Errors: 96% of the 0.40% error rate is PoolTimeout [1]. Logs confirm 1,800 to 2,400 "pool exhausted" warnings per hour on 2026-10-22, versus none on 2026-10-20.

The OPS-412 commit says the limit is per service. However, 4 pods at 50 each is 200 connections, which conflicts with a "per service" limit. Whether the new DB limit is 200 or 32 connections total is not stated in the material.

## Assumption log

A1. The new DB connection limit from OPS-412 is per pod or higher than 32, not 32 per service. Why not measured: the material does not state the limit value. Validate by: read ticket OPS-412 or ask the DBA. If wrong: keep pool at 32 total, set max_size to 8 but raise acquire_timeout to 30 s, and fix the cache TTL first.

A2. Redis can hold the extra keys at 300 s TTL within max_entries 200,000. Why not measured: current key count is not in the material. Validate by: check dbsize and evictions in Redis. If wrong: raise max_entries or set TTL to 120 s.

## Alternative considered

Keep the pool at 8 and only restore cache TTL to 300 s. This loses because misses were already 12% before the release, and 32 workers can still demand more than 32 connections at once [judgment]. The 690 ms acquire wait cannot come from cache misses alone.
