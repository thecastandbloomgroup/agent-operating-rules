# Relevance

Flaky builds erode trust in signals, so real failures get ignored and releases slow down. Acting now limits that damage [1], [3].

# Information

**Evidence.** A study of 4.6 million tests at Google found about 1.5% of test runs and 16% of tests show some flakiness [1]. An analysis of open-source projects found asynchronous waits, test-order dependence, and resource leaks are leading causes [2]. These support a "measure, then fix by frequency" strategy.

**Assumption log.**

A1. The build runs in a CI system that logs per-test results. Why not measured: the material does not state it. Validate by: check the CI dashboard once. If wrong: run the triage on local build logs instead.

A2. Flakiness comes from tests, not infrastructure. Why not measured: no evidence supplied. Validate by: compare failure signatures; identical errors on identical code point to infrastructure. If wrong: swap Step 3 for an infrastructure fix.

A3. The team can change test code and CI config. Why not measured: no permission stated. Validate by: open one quarantine pull request. If wrong: escalate to the pipeline owner.

**Alternative considered.** Re-run the build until it passes and change nothing. It loses because flakes compound: each ignored failure raises the chance a real defect ships [3].
