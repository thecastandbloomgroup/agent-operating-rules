## Headline

The fix starts with measuring which tests fail, not with guessing causes.

1. Flaky builds have three MECE causes: test issues, environment issues, or code race conditions.
2. Data from recent runs must classify the cause before any fix.
3. A rerun flag is a stopgap, not a fix, so quarantine beats retries as first aid.

## Background

The request reports a flaky build. No logs, tool, or repo were provided. The team and pipeline details are unknown.

## Relevance

Flaky builds erode trust in the pipeline. Developers then ignore real failures, which slows every release.

## Information

Three known cause classes cover flakiness [1]:

- Test causes: timing dependence, random data, order dependence.
- Environment causes: shared state, clock drift, network calls, resource limits.
- Code causes: concurrency bugs, retries, hidden global state.

The evidence needed is quantitative: failure rate per test over the last 30 runs, and which stage fails. Without it, cause is about as likely as not to be test timing [judgment].

A2. The build uses an automated test suite in CI. Why not measured: the material does not state it. Validate by: list the CI job definition. If wrong: rerun and quarantine advice still applies.

A3. Failure logs of recent runs exist somewhere. Why not measured: the material does not state it. Validate by: open the last failed run. If wrong: add logging first, then measure.

Alternative considered: add automatic retries to flaky tests. It loses because retries hide the defect and let the failure rate grow [1]. It also lengthens every run by the retry cost.

## End

I recommend that we:

1. Collect the last 30 run results and compute per-test failure rate. This removes the Confused state by giving the data that classifies the cause. Confused domain, because the problem type is not yet known.
   - Given the CI run history for 30 runs,
   - When failure rate is grouped by test,
   - Then the worst offender and its stage appear in a ranked list.
2. Rerun the top failing test 20 times in isolation on one machine. This separates test causes from environment causes. Complicated, because the analysis method is known.
   - Given the ranked list from Step 1,
   - When the top test runs 20 times alone,
   - Then pass or failure pattern shows if the test is the source.
3. Quarantine confirmed flaky tests and fix one per session, starting with the highest failure rate. This restores trust in the main signal while fixes land. Clear, because the best practice exists [1].
4. Remove external calls and shared state from tests, one test per change. This blocks recurrence. Complicated, because each test needs its own analysis.

Step 3 MUST NOT start until the test in Step 2 identifies confirmed flaky tests.
