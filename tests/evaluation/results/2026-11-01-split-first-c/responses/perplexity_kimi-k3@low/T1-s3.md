## Headline

Ship a semantics-preserving formatter and make it automatic, so the culture problem becomes a non-event in review.

- The formatter only rewrites whitespace and keyword case, so semantics and secrets stay byte-identical in token text.
- The team keyword list comes from your own corpus, so nobody argues taste, the code votes.
- The team is small (4 to 8 people) and the file count is not stated, so automation beats negotiation.
- Largest risk is a semantic change; the plan gates every step on an equivalence check before rollout.

## Background

Review friction over SQL style is the trigger. The environment is constrained: pure Lua, large files (about 600 lines), secrets inside text, no network or LSP. Documents W1 (style825 rules) and W2 (team keyword file) are assumed available; see the assumption log.

## Relevance

Every review cycle burns time on style until a machine owns style. Fixing this once removes the recurring conflict, and protects secrets while doing it.

## Information

**Evidence**

- Whitespace between SQL tokens carries no meaning in the lexical grammar, so whitespace-only rewrite is safe [1].
- Keyword case carries no meaning in the SQL grammar, so case-folding keywords is safe [1].
- Secret safety reduces to one rule: never modify text inside string literals, quoted identifiers, or comments [judgment].
- A tokeniser that copies every token byte-for-byte makes semantic change impossible by construction [judgment].
- Four to eight people cannot converge on taste faster than a script can; style guides resolve this class of conflict at industry scale [2].

**Assumption log**

- A1. The corpus is one SQL dialect. Why not measured: the material does not state it. Validate by: scan top keyword frequencies for dialect markers. If wrong: extend the tokeniser for the second dialect.
- A2. Secrets appear only inside string literals, not in comments or identifiers. Why not measured: the material does not state it. Validate by: grep top literals and comment text for secret patterns on three sample files. If wrong: add a rule that comments also pass through untouched, which is already the design.
- A3. Team editors support a format-on-save hook calling a local script. Why not measured: the material does not state it. Validate by: configure one editor. If wrong: use a pre-commit hook instead.
- A4. W1 defines style825 indentation and case rules precisely enough to implement. Why not measured: the material does not state it. Validate by: hand-format one 100-line file against W1 and compare. If wrong: encode the observed team style instead.

**Alternative considered**

The alternative is a team meeting to agree on style by consensus. It loses because consensus across 4 to 8 people on 600-line legacy files does not survive the next merge, while an automated check enforces itself [judgment].

## End

I recommend that we take these steps in order.

1. **Extract the team keyword list from the corpus.** Increment: one Lua script that tokenises all files, counts keyword candidates, and writes the top list for review. Blocker removed: argument about which words are keywords. Cynefin: Complicated, because dialect analysis picks the right token set. Task kind: deterministic. Test first:
   - Given a corpus of the team SQL files,
   - When the scanner runs,
   - Then every emitted keyword appears as a whole word in at least one file, and no string-literal text appears in the list.
2. **Build the token-preserving formatter in Lua.** Increment: tokeniser plus emitter that uppercases listed keywords and applies style825 indentation, copying all other token bytes unchanged. Blocker removed: any possibility of semantic or secret drift. Cynefin: Complicated, because the lexical rules are knowable and testable. Task kind: deterministic. Test first:
   - Given 20 representative files including ones with secrets and comments,
   - When the formatter runs,
   - Then the token stream before and after is identical except keyword case, and reformatting a second time changes nothing.
3. **Wire format-on-save for every team editor, or a pre-commit hook where A3 fails.** Increment: configuration for one editor, then replication. Blocker removed: reliance on memory. Cynefin: Clear, because each editor has a documented hook mechanism. Task kind: deterministic. Test first:
   - Given a developer edits a file and saves,
   - When the save completes,
   - Then the file on disk satisfies the formatter with zero diff.
4. **Add a check that fails a pull request on unformatted SQL.** Increment: one job running the formatter in check mode. Blocker removed: style comments in review. Cynefin: Clear, because check-mode tooling is a known pattern. Task kind: deterministic. Test first:
   - Given a pull request with one badly formatted line,
   - When the check runs,
   - Then the check fails and names the file and line.
5. **Run the formatter once over the full corpus and measure review threads.** Increment: one bulk commit, then four weeks of observation. Blocker removed: legacy drift that would otherwise poison every diff. Cynefin: Complex, because the effect on team behaviour appears only afterward; leverage is a guess. Test first: metric is style-only comments per review, baseline is the last four weeks, pass threshold is a drop of 80% over a sample of at least 20 reviews.

Step 3 MUST NOT start until the test in Step 2 passes. Step 4 SHOULD start after Step 3. Step 4 runs in parallel with Step 3.
