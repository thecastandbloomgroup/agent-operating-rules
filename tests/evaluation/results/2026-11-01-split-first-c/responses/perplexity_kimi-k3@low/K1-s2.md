## Background

## Relevance

PoolTimeout errors now cause 96% of a 0.40% error rate, so customers see 503 responses, not only slow ones [3]. The cause is visible in the diff, so the fix is quick.

## Information

Evidence from the traces [3]:

- db.pool.acquire p95: 3 ms in Window A, 690 ms in Window B.
- db.query orders p95: 52 ms to 58 ms. db.query order_lines p95: 30 ms to 26 ms.
- Cache miss rate: 12% to 31%. Matches the TTL cut 300 s to 60 s in the diff [2].
- Active DB connections peak: 31 in A, 8 in B. Matches pool max_size 50 to 8 [2].
- DB CPU peak: 38% to 41%. The database is not the bottleneck [3].

Analysis [judgment]: 32 workers share 8 connections per pod of 8, so about 8 connections serve 8 workers per pod. Any request holding a connection during two queries blocks others. The logs confirm this: 1,800 to 2,400 "pool exhausted" warnings per hour, versus none before [1]. The selectinload change replaces lazy loading with one extra eager query. Query spans show no regression, so the ORM change is neutral here [3].

Alternative considered: keep pool size 8 and remove the selectinload to shorten connection hold time. It loses because query spans total about 78 ms p95 while acquire waits are 690 ms p95; shrinking hold time cannot close a gap that size with 8 connections against 32 workers [3].
