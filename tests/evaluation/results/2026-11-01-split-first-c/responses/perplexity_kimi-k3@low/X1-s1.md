## Headline

Build a small evaluation set first, measure the failure modes, then fix the dominant one and guard it with regression tests.

1. Fix blindly a second time because the first failure pattern is unmeasured.
2. A labeled sample of 100 to 200 real cases turns "sometimes wrong" into measured failure types.
3. Fixes ordered by failure frequency remove the most agent frustration per unit of work.

## Background

The support tool uses a language model to summarize cases or threads. Agents report errors with no metric, no labeled data, and no failure taxonomy. The task is stochastic: summarizer output varies across runs and inputs.

## Relevance

Without a baseline, any change is unverifiable and regressions will go unnoticed. A measured failure breakdown shows which error type dominates, so the cheapest fix lands first.

## Information

Evidence and assumptions:

- No metrics or labeled data exist, so the current error rate and error mix are unknown [from the request].
- Vague quality reports of this kind usually split into a few failure types: wrong facts, missing key facts, wrong tone or action, and format violations [judgment].
- A1. Agents will flag and save at least 100 real cases within one week. Why not measured: the material does not state ticket volume. Validate by: add the flag button and count flags after three days. If wrong: extend the collection window or seed the set from recent closed tickets.
- A2. The summarizer is prompt-based and its prompt and model settings are editable. Why not measured: the material does not describe the implementation. Validate by: open the summarizer code or config. If wrong: replace Step 2 with an upstream fix (better input to the summarizer) and re-plan.

Alternative considered: rewrite the prompt based on agent anecdotes alone. It loses because anecdotes cannot rank failure types or detect regressions, and this judgment matches the absence of any baseline data [judgment].

## End

I recommend that we execute four actions in this order.

1. **Add a flag-and-save control in the agent view.** Increment: one button plus a free-text reason, shipped in one session, storing the input thread and the summary. Blocker removed: no data collection. Test (deterministic): Given an agent views a summary, When the agent flags it with a reason, Then the thread, summary, and reason are stored and queryable. Domain: Clear, the cause and effect of logging flags are known.

2. **Label 100 to 200 flagged or sampled summaries.** Increment: one labeling session with two reviewers and a four-category rubric (wrong fact, missing fact, wrong action, format), each weighted equally, a case fails on one or more criteria (Kepner-Tregoe style classification, evaluative). Blocker removed: unknown failure mix. Test: the rubric, written before labeling. Domain: Complicated, the error taxonomy is knowable by analysis. Step 2 MUST NOT start until Step 1 passes.

3. **Fix the top failure category.** Increment: one change, for example a prompt constraint or a post-check, sized to one session. Blocker removed: the dominant error type. Test (stochastic, written first): rerun the summarizer on the 200 labeled cases; metric is pass rate on the target category; baseline is the measured rate from Step 2; pass threshold is a 20-point absolute gain, or 50% relative reduction if the baseline is under 20 points; sample size is the full 200-case set. Domain: Complicated, the fix maps to a known failure once Step 2 lands. Step 3 MUST NOT start until Step 2 reports the failure mix.

4. **Add the labeled set as a regression gate, run as a capped probe for overall quality.** Increment: a repeatable evaluation script wired into deployment. Blocker removed: silent regressions. Test (stochastic, written first): metric is overall pass rate; baseline is the Step 3 result; pass threshold is no drop of more than 2 points on 200 cases per release. Domain: Complex, overall agent satisfaction emerges after release, so treat it as a safe-to-fail probe with a stop condition (revert on regression) and a one-release budget.

## Follow-up

Conditions that change the recommendation: if A2 is false, replace Step 2's fix lever with upstream input cleanup. If a labeled set larger than 200 exists after one week, raise sample sizes to match.
