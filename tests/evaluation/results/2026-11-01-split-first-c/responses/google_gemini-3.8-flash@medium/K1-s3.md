# Background

The application programming interface (API) 95th percentile (p95) latency increased from 120 ms to 900 ms after the October 21 release [1].
The release modified the cache configuration, the connection pool, and the object-relational mapping (ORM) query [2].
The user requested instructions to resolve this performance regression [judgment].

# Relevance

The latency increase degrades user experience and raises HTTP 503 error rates from 0.02% to 0.40% [1].
Therefore, the team must resolve connection starvation to restore service stability [judgment].

# Information

This section covers performance evidence, logged assumptions, and alternatives considered.

Database pool acquire time drove the latency regression [1].
Specifically, pool acquire p95 latency rose from 3 ms to 690 ms between Window A and Window B [1].
In contrast, database query execution times stayed flat [1].
Orders query p95 changed from 52 ms to 58 ms, while line items query p95 dropped from 30 ms to 26 ms [1].
Therefore, the ORM query update did not cause the regression [inference].
Database central processing unit (CPU) usage remained low at 41% peak [1].

Connection contention increased because cache misses rose [1].
The release reduced cache time to live (TTL) from 300 s to 60 s [2].
Consequently, cache miss rate jumped from 12% to 31% [1].
Higher cache misses produced more concurrent queries against the database [inference].
However, the release lowered pool maximum size from 50 to 8 connections per pod [3].
The service runs 4 pods with 8 worker threads each, creating 32 competing threads [4].

Contention caused pool exhaustion warnings to jump from zero to between 1,800 and 2,400 per hour [5].
Furthermore, the release reduced acquire timeout from 30 s to 5 s [3].
Because waiting requests could not get connections within 5 s, HTTP 503 errors rose twenty-fold [1].
Pool timeouts caused 96% of all recorded errors [1].
Confidence is high based on trace metrics and application logs [judgment].

A1. Ticket OPS-412 permits at least 12 database connections per pod across the 4 pods. Why not measured: The material does not state it. Validate by: inspect ticket OPS-412 in the issue tracker. If wrong: keep pool size at 8 and deploy an external connection pool proxy.

A2. Redis cache memory can support a 300 s TTL for 200,000 entries. Why not measured: The material does not state it. Validate by: run memory inspection on the cache host. If wrong: set TTL to 180 s instead of 300 s.

Alternative considered: Roll back the entire release including the ORM query changes.
This alternative loses because the ORM changes improved line item query latency from 30 ms to 26 ms [1].
A full rollback would remove that query improvement without targeting the actual bottleneck [judgment].
