## Headline

Run the JWT migration as a staged cutover with short-lived access tokens and rotating refresh tokens, and treat sign-up conversion as measured probes instead of a redesign.

1. Keep sessions and tokens live in parallel for an overlap window, so a bad cutover cannot lock users out.
2. Use short access tokens with refresh rotation, because a long-lived bearer token cannot be revoked after a leak.
3. Instrument the sign-up funnel before changing it, so every change has a baseline.
4. Run conversion changes one at a time with a stop condition, because user behavior shows cause and effect only after the change.

## Background

The request has two tasks: replace server-side sessions with JWT in the auth service, and lift sign-up completion. [inference: from the request] These tasks differ in kind. The migration is deterministic engineering work; conversion is stochastic user behavior.

## Relevance

Design choices made now are hard to reverse. A long-lived token with no revocation path is costly to fix after the first leak. Conversion changes without a baseline produce numbers with no meaning.

## Information

**Evidence**

1. JWT is a signed bearer token standard. Whoever holds a valid token gains access until expiry, so leaked or stolen tokens stay usable. [1]
2. The OAuth 2.0 framework defines refresh tokens for renewed access without a new login. Rotation with reuse detection is a recognized control against stolen refresh tokens. [2]
3. NIST SP 800-63B requires verifiers to set an upper bound on the time between reauthentication events. Short access-token lifetimes align with this control. [3]
4. Reduction of form fields raises completion rates; the size of the effect varies by audience. [judgment]

**Assumption log**

- A1. The auth service is a browser-facing HTTP API, and sessions live in a shared store. Why not measured: the material does not state it. Validate by: reply to Follow-up Q1. If wrong: the middleware implementation target changes; the plan shape stays.
- A2. No requirement exists for instant global revocation, such as "log out everywhere" for a banned account. Why not measured: the material does not state it. Validate by: check the security requirements list with the security owner. If wrong: keep a server-side token denylist; each request then needs one extra lookup.
- A3. The sign-up funnel has no complete step-level analytics baseline. Why not measured: the material does not state it. Validate by: check the analytics tool for sign-up step events. If wrong: skip the instrumentation step and use the existing baseline.

**Alternative considered**

Long-lived JWTs with no refresh tokens. It loses because the revocation gap equals the token lifetime, and 7 to 30 days of validity per stolen token exceeds the risk tolerance of most services. [judgment]

## End

I recommend that we execute this plan in five steps.

1. **Design the token lifecycle.** Increment: a one-page design plus a token-issuance module with 15-minute access tokens and rotating refresh tokens, completed in one session. Blocker removed: without this, no migration step has a target. Kind: deterministic. Test (write first):

   ```gherkin
   Given a refresh token that was already rotated
   When the client presents it for renewal
   Then the service rejects the request and revokes the token family
   ```

   Domain: Complicated, because analysis such as the alternative comparison above picks one practice from several good ones. So this step comes first.

2. **Add dual acceptance behind a flag.** Increment: middleware that accepts a session cookie or a JWT, plus JWT issuance at login, behind an environment flag. Blocker removed: the lockout risk at cutover. Kind: deterministic. Test:

   ```gherkin
   Given a request that carries a valid session cookie and no token
   When the request reaches a protected route
   Then authentication passes and the response is unaffected by the flag
   ```

   Domain: Clear, because a parallel-run is a known best practice for auth cutovers. Step 3 MUST NOT start until this test passes.

3. **Cutover and retire sessions.** Increment: new logins receive tokens only; active sessions stay valid for a 30-day overlap; then the session store is switched off. Blocker removed: the legacy session dependency. Kind: deterministic. Test:

   ```gherkin
   Given the overlap window has expired
   When a request arrives with a session cookie
   Then the service returns an unauthorized response and the store shows no growth
   ```

   Domain: Clear, because the cause and effect are known: flag off, sessions fail closed.

4. **Instrument the sign-up funnel.** Increment: events for page view, form start, submit, verification, and first login, plus a 2-week baseline report. Blocker removed: change decisions without a baseline. Kind: stochastic. Acceptance test: metric is step-through rate per step; baseline is the 2-week report; pass threshold is a complete baseline, not a target lift; sample size is at least 1,000 unique visitors per step. [judgment] Domain: Clear, because instrumentation is a known practice; the behavior behind it stays unexplained until Step 5.

5. **Run one conversion probe.** Increment: a 2-day change, ranked after the Step 4 baseline; the default first probe is a form reduced to email and password, with profile fields deferred. Blocker removed: unknown cause of drop-off. Kind: stochastic. Acceptance test: metric is form-start to account-created rate; baseline is the Step 4 report; pass threshold is at least a 5% relative lift; sample size is 1,000 visitors per arm; stop condition is 2 weeks or a negative trend after 3 days. Domain: Complex, because user behavior reveals cause and effect only after the change, so this runs as a capped probe and not a committed redesign.

Step 5 runs in parallel with Step 4 only if an existing baseline exists (per A3). Otherwise Step 5 waits for the Step 4 baseline.

## Follow-up

Questions (each answer changes a step):

1. Which language, framework, and session store does the auth service use? Answer decides the concrete token library and middleware target in Step 2.
2. Do you require instant revocation, such as "log out everywhere" or account bans? Answer decides whether Step 1 adds a server-side denylist (per A2).
3. Do you have step-level sign-up analytics today, and if so, where does drop-off concentrate? Answer decides whether Step 4 is needed and which probe Step 5 runs first.

Conditions that change the recommendation: if A2 is false, replace the refresh-rotation-only design in Step 1 with refresh rotation plus a token denylist. If the service has native mobile clients, add a token-refresh path with a longer refresh lifetime for silent reauth.
