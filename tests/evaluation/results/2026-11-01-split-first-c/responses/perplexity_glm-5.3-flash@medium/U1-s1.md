## Headline

Quarantine the flaky test today, then gather run data and reproduce in isolation before anyone fixes code.

- Quarantine removes the blocker now and keeps the main pipeline green.
- A table of 20 past run logs classifies where and how the build fails.
- 30 isolated reruns of the suspect test either reproduce the failure or rule out test code.
- A scoring rubric picks one root cause, so the fix targets a single cause family.

## Background

The build fails intermittently; no logs, pipeline name, or failing step is given in this request. Flaky here means a test or step that fails on one run and passes on the same code.

## Relevance

A flaky build slows every merge because no one can trust a red run [inference]. Data-first steps avoid a fix based on guesswork.

## Information

### Evidence

Luo et al. group flaky causes into a small set of families, and test order dependence and timing waits are major groups in their study [1].

Micco documents the same practice at Google: keep the main pipeline green, and run suspect tests in a separate job [2].

Theme, quarantine plus data-first classification: two sources support it; no disagreeing source appears in this set.

Baseline: the pipeline now fails intermittently. After Step 1 the run ends green by definition [judgment].

Confidence: high for the process, because two independent industry sources agree. Low for the specific cause, because there is no run data in this session.

### Assumption log

A1. A CI pipeline runs automated tests on each commit. Why not measured: the material does not state it. Validate by: read the pipeline config file. If wrong: replace Step 1 with a local repro script.

A2. Failures recur on unchanged code. Why not measured: no run history in this session. Validate by: map each failed run to its commit. If wrong: bisect the last change first.

A3. The cause sits in test code or its environment, not in production logic. Why not measured: no log data in this session. Validate by: run the suspect test on the last green commit. If wrong: drop the rubric path and debug the production change.

### Alternative considered

Automatic retry of failed steps. It loses because retries keep flakiness in the loop and mask real defects on the main path [inference].

## End

I recommend that we quarantine, collect, reproduce, and classify before any code fix.

Step 1. Put the failing test or step on the quarantine list, and run the pipeline once. This removes the immediate blocker: main returns green. Test:

Given the suspect test is on the quarantine list,
When the next pipeline run starts,
Then the run ends green and the suspect test reports in a separate job.

Kind: deterministic, test written first. Domain: Clear, because cause and effect are known [3].

Step 2. Collect a table of the last 20 pipeline runs. Columns: run id, commit, failed step, error text. This adds the data that cause selection needs. Test:

Given 20 saved run logs,
When each log maps to one failed step and one error mode,
Then no row in the table lacks both labels.

Kind: deterministic. Domain: Clear, because the log shows the failing step directly [3].

Step 3. Run the suspect test 30 times in isolation on a clean checkout, in parallel with Step 2 and capped by the budget. This probe reproduces or rules out test-side causes. Acceptance test written before the trials:

Metric: failure count. Baseline: zero failures in a single run. Threshold: at least one failure in the 30 runs. Sample size: 30 runs. Budget and stop condition: 1 hour, or zero reproduction.

Kind: stochastic. Domain: Complex, because the cause shows only after the probe runs, and leverage is a guess [3]. Do not fix code inside this probe.

Step 4. Score the cause candidates with a rubric, and write the fix only for the top cause. Step 4 MUST NOT start until Step 3 ends by reproduction or budget. Candidate families: test order dependence; wait and timing; shared fixture state; external service timeout [1]. Rubric:

- Evidence fit to the error text, weight 3, evidence: the Step 2 table.
- Reproduction under the Step 3 isolation run, weight 3, evidence: isolation log.
- Frequency in the 20 run table, weight 2, evidence: the Step 2 table.
- Low fix cost, weight 2, evidence: a one line fix estimate.

Pass threshold: the top total wins when its lead over the runner-up is 2 or more points. Kind: evaluative, rubric first. Domain: Complicated, because analysis must pick one practice among several [3].

## Follow-up

Conditions that change the recommendation:

- If Step 2 shows every failure after one commit, A2 is wrong; stop the probe and bisect that commit instead.
- If Step 4 names order dependence, fix test state before timing, because order dependence is a separate family [1].
- If there is no quarantine mechanism, A1 is wrong; skip Step 1 and start with local runs under Step 2.

Open questions: none; the assumption log covers the unknowns.
