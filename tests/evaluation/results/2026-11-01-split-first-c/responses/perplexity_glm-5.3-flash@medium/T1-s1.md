## Headline

Stop debating style in reviews: pin one lint config in the repository, block merges on it, and declare style remarks out of scope for reviews. This removes the friction at its source, because humans stop enforcing rules a machine can enforce [1] [judgment]. The plan has three parts: a formatter, an enforcement rule, and a short measurement of reviewer behavior after the change.

## Background

The team reviews SQL in code reviews. Reviewers disagree on SQL style, and the disagreement appears in every review. The request asks to fix the culture problem behind this friction.

## Relevance

Each review now costs extra rounds, so the cost recurs on every pull request. A mechanical fix removes the cause instead of mediating each dispute.

## Information

**Evidence.** A dedicated linter exists for this job. Sqlfluff supports many SQL dialects and reads its style rules from one config file in the repository, so every contributor and every check sees the same rules [1]. The current friction has no measured baseline; this rests on the user report alone [judgment]. The current failure mode is human enforcement of style, which invites debate because each reviewer applies a personal standard [judgment].

**Assumption log.**

- A1. The repository runs a check system (CI or pre-commit) that can block a merge. Why not measured: the material does not state it. Validate by: open the repository settings and list its existing checks. If wrong: the enforcement step moves to the check system available there, so the steps keep their order.
- A2. The dialect and layout rules for the team's SQL are decidable with one 60-minute session. Why not measured: the material does not state it. Validate by: run the linter's diff on five existing SQL files and confirm the result is acceptable to two reviewers. If wrong: add one extra session to the config work before Step 2.
- A3. No lint config exists today. Why not measured: the material does not state it. Validate by: search the repository for the config file name with a grep command. If wrong: the first step becomes a diff review of the existing config instead of a new one.

**Alternative considered.** The strongest alternative is a written style guide that reviewers enforce by hand. It loses because human enforcement of style is the current failure mode [judgment]; the guide adds a document, not a mechanism, per the enforcement evidence above.

## End

I recommend that we adopt a tool-owned solution with the following steps.

**Step 1.** Add a SQL linter to the repository with one pinned config file: dialect, layout rules, and rule severities [1]. Increment: one commit plus a dry-run diff on five SQL files, done in one session. Blocker it removes: the absence of a single shared standard. Test (deterministic, written first):

```gherkin
Given a repository with a SQL file
When a contributor runs the lint command
Then the command exits with status 0 if and only if the file matches the pinned config
```

Cynefin: Clear, because cause and effect are known to everyone and the tool output is one step. Step 2 MUST NOT start until this test passes.

**Step 2.** Wire the lint command into the merge-blocking check, and add one sentence to the review checklist: "style remarks are not required; the check owns style" [1]. Increment: one configuration change plus one checklist line, done in one session. Blocker it removes: the practice of reviewers defending personal style standards. Test (deterministic, written first):

```gherkin
Given a pull request whose SQL does not match the config
When a reviewer opens the pull request
Then the check fails and merge stays blocked until the contributor applies the formatter
```

Cynefin: Clear, because the check is mechanical and the rule is one step. This depends on A1; if A1 is false, run this step against the check system that A1 finds instead.

**Step 3.** Measure reviewer behavior for one sprint and decide whether the config needs edits. Increment: count style-related review comments per pull request across 20 pull requests, then review the counts in one session. Blocker it removes: the unknown of whether the new rule actually ended the disputes. Acceptance test (stochastic, written first): metric = median style comments per pull request; baseline = the median measured in week 0 [judgment, because no baseline exists yet]; pass threshold = median of 0 style comments; sample size = 20 pull requests. Budget: one sprint and one 60-minute review session. Stop condition: if 3 or more of the 20 pull requests still draw style disputes, open a config-change proposal instead of more discussion. Cynefin: Complex, because reviewer behavior shows its cause and effect only afterward, so this is a safe-to-fail probe with Leverage treated as a guess. Run it in parallel with Step 2; its budget caps its cost.

Uncertainty statement: the config in Step 1 satisfies about as likely as not exactly what each reviewer wants without one edit pass (33 to 66%), because style preferences vary by person [judgment]. Therefore Step 3 exists to catch that.
