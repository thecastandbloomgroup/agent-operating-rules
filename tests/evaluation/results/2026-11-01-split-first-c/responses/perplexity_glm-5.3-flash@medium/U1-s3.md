## Headline

Stabilize first, then measure, then remove causes one class at a time.

- Quarantine the flaky parts today so the pipeline blocks only on real failures.
- Measure which tests fail and how often, because the fix depends on the cause class.
- Diagnose one class at a time, then run capped fix probes against the measured rate.

## Background

The request states that the build is flaky. Flaky means a build or test that fails on one run and passes on the next with no code change. The message gives no system name, no failure data, and no history.

## Relevance

An unstable build blocks merges and hides real defects. Each red build lowers trust in every green one, so work loses its gate. [judgment]

## Information

**Evidence**

E1. [judgment] Nondeterministic failures fall into four classes: unordered shared state, timeouts, external dependencies, and real defects. Each class needs a different fix, so diagnosis comes before repair.

E2. [judgment] Quarantine removes the failing parts from the blocking path. This restores the pipeline's signal while diagnosis proceeds.

E3. [judgment] Automatic retries without diagnosis hide the symptom and raise run time. Retries rank below quarantine plus cause work.

**Assumption log**

A1. The failures are nondeterministic, not a new code defect. Why not measured: the request does not state failure data. Validate by: rerun the failed jobs on the same commit. If wrong: replace Steps 3 and 4 with normal defect triage.

A2. "Build" means the automated compile and test pipeline on each commit. Why not measured: the request does not name the system. Validate by: read the CI configuration in the repository. If wrong: ask which job fails and redirect Step 1 to its logs.

A3. CI stores logs for past runs that a script can read. Why not measured: the request does not name the system. Validate by: check log retention in the CI settings. If wrong: add log capture as a new Step 0, then reorder.

**Alternative considered**

The strongest alternative is to enable automatic retries on all failures. It loses because it hides the sign, raises run time, and leaves the cause in place (E3).

## End

I recommend that we run these four steps, in this order.

**Step 1. Measure the failure pattern.** [Cynefin: Confused, because the data decides how to classify the causes] [deterministic; test written first]
- Increment (one session): add a script that reads the logs of the last 100 CI runs and prints failures per test with counts.
- Blocker removed: the team cannot aim a fix without knowing which parts fail.

```gherkin
Given one hundred saved CI run logs
When the script runs
Then it prints each failed test with its failure count
```

**Step 2. Quarantine the flaky parts.** [Cynefin: Clear, because moving nondeterministic failures out of the blocking path is an established best practice] [deterministic; test written first]
- Increment (one session): move the parts that Step 1 flags into a separate, non-blocking suite.
- Blocker removed: merges stop being blocked by unstable parts.
- Sequence: wait until Step 1 prints its first report, because the quarantine list comes from it.

```gherkin
Given a test listed in the quarantine file
When the CI pipeline finishes
Then the pipeline result ignores that test's status
```

**Step 3. Classify the causes.** [Cynefin: Complicated, because an expert picks the fix after analysis of the run records] [deterministic; test written first]
- Increment (one session): rerun each quarantined part in isolation, alone, on its original commit, ten times, and record the error type per run.
- Blocker removed: the team can sort each failure into one class from E1 and pick the matching fix.

```gherkin
Given a quarantined test and its commit
When the test runs alone ten times
Then the record shows a pass count and an error class per run
```

**Step 4. Fix one cause class at a time with a capped probe.** [Cynefin: Complex, because the effect shows only after the fix runs in CI, so the work is a safe-to-fail probe, not a full commit] [stochastic; acceptance test written first]
- Increment (one session per class): apply one fix for one class on a branch, then watch CI.
- Blocker removed: one class of failures leaves the build, and the evidence shows whether it stayed out.
- Acceptance test: metric is failures per run for that test; baseline is the Step 1 count per 100 runs; pass threshold is zero failures; sample size is 30 runs.
- Budget and stop condition: one session per class. If two probes fail for one class, stop, re-enable the retry there, and file an issue to track it.

## Follow-up

- If the CI logs lack the data for Step 1, add log capture first and put it before Step 1.
