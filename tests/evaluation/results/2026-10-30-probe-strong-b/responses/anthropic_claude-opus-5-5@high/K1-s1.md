# Headline

The connection pool cut causes the rise, so resize the pool within the OPS-412 limit and restore the old cache setting.

1. The p95 (95th percentile) wait for a connection from the pool of shared database connections rose from 3 ms to 690 ms.
2. The cache TTL (time to live) fell from 300 s to 60 s, so 2.6 times more requests need the database.
3. The ORM (object-relational mapping) change is not the cause, because the query spans (timed steps) changed by 6 ms or less.
4. The safe pool size depends on the OPS-412 connection limit, and the attached files do not state that limit.

# Background

Release 2026.10.21 was deployed on 2026-10-21 at 14:05 UTC. It changed the connection pool, the cache TTL, and one ORM query. Since then, p95 latency for GET /customers/{id}/orders rose from 120 ms to 900 ms.

# Relevance

The error rate rose from 0.02% to 0.40%, and 96% of these errors are pool timeouts after 5 s, per traces.txt [1]. Until the pool is fixed, users of this endpoint get slow responses or 503 errors.

# Information

**Evidence**

Window A is 2026-10-20, 09:00 to 17:00 UTC, on release 2026.10.14. Window B is the same hours on 2026-10-22, on release 2026.10.21.

- Peak load was 410 requests per second in A and 405 in B [1].

- Peak database server CPU was 38% in A and 41% in B [1].

**Analysis**

1. Pool waits cause the rise. At p95, the acquire span grew by 687 ms of the 780 ms total rise (see table). Percentiles do not add, so this split is an estimate [inference]. Every other span changed by 6 ms or less. Confidence: high confidence, because the acquire span is the only span that moved more than 6 ms in 10,000 sampled requests per window.
2. The pool cut removed the margin. Total pool capacity fell from 200 to 32 connections, that is 4 pods times 50, then 4 pods times 8 [inference]. Window A peaked at 31 active connections, so 32 leaves one spare connection at peak (see Evidence).
3. The TTL cut raised demand. Requests that reach the database rose from about 49 to about 126 per second at peak [inference: peak rate times miss rate]. That is 2.6 times the old demand, on a pool that is 6.25 times smaller per pod.
4. The ORM change is neutral. The orders span rose by 6 ms, and the order_lines span fell by 4 ms (see table). So the selectinload change does not explain the rise [inference].
5. The database server has spare capacity. Peak CPU rose by 3 points, from 38% to 41% (see Evidence). Therefore the constraint is the connection count, not database load [inference].
6. The 5 s timeout converts long waits into 503 errors. Keep it [judgment]. A longer timeout holds worker threads and slows every request on the pod [judgment].

**Conflicts in the material**

- C1. traces.txt reports a peak of 8 active connections from the service in Window B [1].
- However, logs.txt shows api-1, api-2, and api-4 each at 8 of 8 within 7 s [3].
- If those intervals overlap, the service holds at least 24 connections [inference]. One explanation is a cap of 8 for the whole service at the database. That explanation is about as likely as not [judgment]. Step 1 resolves C1.
- C2. Waiters reach 14 on api-2, per logs.txt [3].
- The deployment note gives 8 worker threads per pod [2].
- So a request makes more than one checkout (it takes a pool connection), or more than 8 requests run at once on a pod [inference]. Step 4 tests the first cause.

**Assumption log**

A1. The OPS-412 limit applies to the whole service, not to each pod. Why not measured: the material does not state the limit or its scope. Validate by: read ticket OPS-412. If wrong: Step 3 sets max_size to the per-pod limit, with no division by pod count.

A2. No data freshness need drove the TTL cut from 300 s to 60 s. Why not measured: the material gives no commit message for config/cache.yaml. Validate by: read that commit and ask its author. If wrong: drop Step 2, and Step 3 must cover about 126 database requests per second, not 49.

A3. The database is PostgreSQL. Why not measured: the material gives only port 5432. Validate by: run SELECT version() on orders-db.internal. If wrong: Step 1 uses the session view of that database, not pg_stat_activity.

**Alternative considered**

Revert the full release to 2026.10.14. It restores 50 connections per pod (200 in total), and that total breaks OPS-412 if the limit is below 200 [judgment]. It also reverts the ORM change, which is neutral (see Analysis 4), and it hides which change caused the rise.
