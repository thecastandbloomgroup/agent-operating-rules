## Headline

Measure the errors first, then test one targeted change against the current summariser. [judgment]

- Define “wrong” through a short review of real support cases. [judgment]
- Compare both versions on the same unseen cases. [judgment]

## Background

Agents report that summaries are “sometimes wrong,” but no metrics exist. [1] The available evidence does not identify the errors, their frequency, or their impact.

## Relevance

A single accuracy score can hide rare errors that change an agent’s next action. [judgment] Therefore, measure error severity alongside frequency.

## Information

### What to measure

Use these definitions for the first review. Treat the thresholds below as proposed operating choices, not established benchmarks. [judgment]

| Measure | Definition | Purpose |
|---|---|---|
| Material error rate | Percentage of summaries with at least one major or critical error | Main quality measure |
| Critical error count | Errors that could cause unsafe action, financial harm, or data disclosure | Release gate |
| Agent correction time | Seconds spent correcting a summary | Workflow cost |
| Response time and cost | Seconds and currency per summary | Operational limits |

Classify each error once by its main cause:

1. **Unsupported addition:** the summary states something absent from the source.
2. **Contradiction:** the summary conflicts with the source.
3. **Omission:** the summary excludes information needed for the next action.
4. **Presentation:** the content is accurate and complete, but its form impedes use.

Separately, assign severity:

- **Critical:** the error creates one of the harms defined above.
- **Major:** the error changes the agent’s understanding or next action.
- **Minor:** the error does neither.

These categories are a proposed review scheme. [judgment] Record secondary effects in notes rather than counting the same error twice.

Do not estimate the overall error rate from deliberately selected failures.

### 2. Establish the baseline and choose one repair

**Kind:** Evaluative.  
**Domain:** Complicated, because source comparison and error analysis determine the repair.

**Rubric first:** Use this weighted decision scorecard, following the Kepner-Tregoe approach. [2]

| Criterion | Weight | Required evidence |
|---|---:|---|
| Factual agreement | 50% | Source passages supporting each claim |
| Required detail | 30% | Source passages for the issue, actions, status, and stated next step |
| Agent usability | 20% | Agent assessment and measured correction time |

Score each criterion **2** for no defect, **1** for minor defects, or **0** for a major or critical defect.

Calculate the weighted score out of 100. Proposed pass threshold: **90**, with **no material errors**. [judgment]

**Work:** After Step 1 passes, review the 30 diagnosis cases in one session.

- Compare each summary against the exact input the model received.
- Compare that input against the ticket to detect missing source content.
- Score every criterion and record supporting passages.
- Have a second reviewer assess five cases independently.
- Resolve severity disagreements before calculating the baseline.

No scores are available yet; the trial must produce them.

Choose one repair for the largest observed error group. [judgment] For example, repair input truncation before changing the prompt when required messages never reach the model.

This removes uncertainty about which defect to address. Report sampled results separately from any production-wide estimate.

### 3. Run a capped comparison

**Kind:** Stochastic, because generated summaries can vary between runs.  
**Domain:** Complex, because the effect of the change requires observation.

**Acceptance test first:**

- **Sample:** 30 reserved cases, two runs per case, for each version.
- **Total:** 120 summaries, comprising 60 current-version and 60 challenger summaries.
- **Baseline:** The current version’s results on these same reserved cases.
- **Main threshold:** At least 50% lower material error rate, with at least three fewer erroneous summaries.
- **Safety threshold:** Zero critical errors in the challenger.
- **Workflow threshold:** No increase in median correction time.
- **Operational threshold:** No more than 20% higher median response time or cost.

These thresholds are proposed pilot gates. [judgment]

**Work:** After Step 2 selects the repair, test that single change in one capped session.

Hide version names from reviewers. Randomise review order. Use the same inputs and review rubric for both versions.

**Budget:** At most 120 generations and four reviewer-hours.

**Stop condition:** Stop for a critical error, a data-control breach, or the budget limit.

If all gates pass, accept the change for a limited agent-reviewed pilot. Otherwise, retain the current version and use the results to select the next repair.

The expected benefit remains a guess until measured. [judgment] Repeated runs share cases, so this small trial does not establish production safety. [judgment]

## Follow-up

If the current version produces no material errors on the reserved cases, do not claim improvement. Collect more representative cases instead.

If summaries trigger actions without agent review, restrict that path before the trial. [judgment]
