## Headline

Treat SQL style as a shared tool setting, not a test of competence or taste. [judgment]

- Give one person authority to settle defaults after a short consultation. [judgment]
- Automate those defaults so reviewers can focus on correctness. [judgment]
- Preserve respectful dissent through a separate process for changes to the rules. [judgment]

## Background

Your team disagrees about SQL format, and those disputes create friction in every review. [1] The immediate task is to remove that repeated negotiation without silencing concerns.

## Relevance

A formatter addresses consistency, but the team also needs agreement about who decides and how people challenge decisions. [judgment] Therefore, address both the tool and the review process.

## Information

**Working diagnosis:** the team lacks a shared way to settle style disputes. That does not establish that anyone has a bad attitude. [inference]

Research links psychological safety, or safety to take interpersonal risks, with team learning behavior. [2] Therefore, stop repeated style debates without banning questions or dissent. [judgment]

**Confidence:** moderate, because the account establishes repeated friction but provides no review examples or team perspectives.

## End

I recommend that we adopt three small changes, in this order.

### 1. Establish a decision rule in one 20-minute session

**Kind:** Deterministic, because the output is a written rule with fixed acceptance criteria.

**Test first:**
```gherkin
Given two reviewers prefer different SQL layouts
When neither preference affects behavior or tool compatibility
Then the written rule identifies one default and one decision owner
```

**Action:** Adopt this policy, with a named maintainer:

> SQL format follows the repository’s formatter configuration. Until that exists, preserve the surrounding file’s style.
>
> The maintainer decides unresolved defaults after a short, written comment period. Agreement is welcome; unanimity is not required.
>
> Formatting preferences do not block approval. Concerns about correctness, security, performance, or comprehension still receive review.
>
> Propose changes to formatting rules separately from feature reviews.

**Blocker removed:** each review no longer needs to settle the same style dispute. [judgment]

**Domain:** Clear, because a named owner and an explicit rule settle procedural ambiguity.

### 2. Prepare one automated format check in a 60-minute session

Step 2 starts after Step 1 passes.

**Kind:** Deterministic, because the check compares SQL files against a fixed configuration.

**Test first:**
```gherkin
Given representative SQL files and a pinned formatter configuration
When the format check runs on correctly formatted files
Then it passes without changes

Given a file that violates the format configuration
When the format check runs
Then it fails and reports the correction command
```

**Action:** First, compare available formatters against the actual SQL dialect, template syntax, and editor support. Select one configuration and test representative files.

Then add the correction command and automated check to the repository. Keep any bulk format change separate from functional changes.

**Blocker removed:** reviewers no longer need to enforce spaces, capitalization, or line breaks manually. [judgment]

**Domain:** Complicated, because compatibility analysis must precede tool selection.

**Stop condition:** if compatibility remains unresolved after 60 minutes, retain Step 1’s temporary rule. Do not enforce an untested formatter.

### 3. Adopt a review agreement in one 20-minute session

Step 3 can follow Step 1 while Step 2 proceeds.

**Kind:** Deterministic, because the output is a documented review agreement and a scheduled check.

**Test first:**
```gherkin
Given a proposed review agreement
When the team checks its contents
Then it distinguishes blocking concerns from preferences
And it provides a route to challenge the rules
And it names an owner and date for a follow-up
```

**Action:** Adopt these review phrases:

- **Blocking:** “This changes the result because…”
- **Question:** “What constraint requires this layout?”
- **Preference:** “This is a preference, so it does not block approval.”

Use the maintainer to resolve disputed categories. Do not use “preference” to dismiss a concrete comprehension problem.

Schedule a 15-minute check after two weeks. Review format-only disputes, formatter failures, and whether people can challenge decisions without personal criticism.

**Capability added:** people can disagree without reopening every formatting choice. [judgment]

**Domain:** Clear, because this action establishes a repeatable process rather than predicting team behavior.
