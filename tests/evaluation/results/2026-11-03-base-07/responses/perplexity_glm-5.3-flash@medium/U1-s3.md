## Headline

Measure the flake rate first, quarantine the repeat offenders, and then fix causes in order of frequency. Three points: (1) Without pass and fail history per test, fix attempts are guesses. (2) Studies show flake causes cluster in a small set of categories, so one classification pass targets the effort. (3) Quarantine restores a trusted build signal while fixes run in parallel.

## Background

The build is flaky: the same code sometimes passes and sometimes fails. The message gives no system names, no failing test names, and no history. The request asks for a plan to stop flaky builds.

## Relevance

A flaky build hides real defects and wastes team time. Each red build without a cause costs a full investigation cycle.

## Information

**Evidence.** One large-sample study found more than 1,600 flaky tests across 91 open-source Java projects. Asynchronous waits was the largest root cause category, ahead of concurrency and test order dependence [1]. Google handles this pattern with result history: record all test outcomes, flag fail-then-pass results on one commit as flaky, and quarantine repeat offenders [2]. So the category analysis is backed by data, and the quarantine practice is backed by a large production deployment. The small set of causes holds as [judgment]: timing, shared state, order dependence, and external dependencies appear in both sources.

**Assumption log.**

- A1. The build runs on a CI system that records per-test results or accepts a result collector. Why not measured: the material does not name the system. Validate by: inspect the pipeline config. If wrong: rerun scripts replace the collector, and the cost of Step 1 rises.
- A2. "Flaky" means the same commit sometimes passes and sometimes fails. Why not measured: the user has not answered. Validate by: search CI history for a fail-then-pass result on one commit. If wrong: the failures are intermittent infrastructure faults, and the plan shifts to runner and network isolation.
- A3. The flaky tests are unit or integration tests inside the build. Why not measured: the material does not state the test type. Validate by: read one failing run's log. If wrong: the plan extends to build-time network and artifact checks.

**Alternative considered.** Fix the most suspected cause now, without measurements. It loses: [1] shows causes spread across several categories, so a fix without data chases the wrong test. The measurement step costs one day.
