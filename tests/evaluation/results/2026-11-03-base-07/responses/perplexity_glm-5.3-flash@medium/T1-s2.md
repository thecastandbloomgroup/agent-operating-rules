# Headline

Stop treating this as a culture debate: pin one machine-enforced SQL formatter, block merges on it, reformat the codebase once, and measure the result.

1. A pinned formatter config turns each style dispute into a one-line tool run. [judgment]
2. CI enforcement applies the standard to every commit, so reviews stop carrying the debate. [2]
3. One bulk reformat commit clears old diffs without per-file arguments. [judgment]
4. A comment count over two weeks shows whether the friction actually dropped. [judgment]

## Background

Nobody on the team agrees on SQL formatting. Each review repeats the same style debate. The request asks for a fix at the team level.

## Relevance

Every pull request pays this cost today. A one-time setup removes a recurring delay.

## Information

**Evidence**

Google's code review guidance tells reviewers to let tooling decide style questions and to skip such comments. [2]

SQLFluff is a SQL linter and formatter. It supports many dialects and reads a config file that pins the rules. [1]

pre-commit runs repo-level checks at commit time from a config file in the repository. [3]

Theme: "tooling, not voting, decides style". One source supports it [2]. One source is few, but it is the written practice of a team that reviews at high volume, and it agrees with the mechanical nature of the problem here. [judgment]

The friction has a mechanical root, so a mechanical fix addresses it. Confidence: 80% likely, based on [2] and the tool capabilities in [1] and [3].

**Assumption log**

A1. The team merges through pull requests with a CI pipeline. Why not measured: the material does not state the stack. Validate by: read the repository workflow config. If wrong: enforce at commit time with the hook only; the rest of the plan stands.

A2. The SQL lives in files or migrations that SQLFluff can parse. Why not measured: the material does not state the stack. Validate by: run SQLFluff parse on one recent commit. If wrong: format query strings where the host language allows, and leave the rest.

A3. The codebase reformat fits in one working session. Why not measured: the material does not state the size. Validate by: run the formatter on a fork and time it. If wrong: split the reformat per directory, one commit each.

**Alternative considered**

Write a style guide and hold a team vote. It loses because a vote settles one round, not the next commit. A machine verifies every commit at zero review cost. [judgment]

## End

I recommend that we fix this with enforcement, in four steps.

**Step 1. Pin the standard.** Increment: add SQLFluff plus a repo config file that sets one dialect and one rule set, capped at one session. Blocker: removes the absence of a single authority. Test, before any work:
```gherkin
Given a repo with SQLFluff configured
When the team runs "sqlfluff lint" on one SQL file
Then the output lists rule violations in a stable form
```
Cynefin: Clear, because a known practice exists for lint configs. [4]

**Step 2. Enforce it.** Increment: add a CI job and a pre-commit hook that fail on formatter diffs. Blocker: removes the need for reviewers to spot style by memory. Test, before any work:
```gherkin
Given a pull request that contains SQL formatted against the config
When CI runs the lint job
Then the job fails and blocks the merge
```
Cynefin: Clear, because CI linting is an established practice. [4]

**Step 3 must not start until Step 2 passes.**

**Step 3. Reformat once.** Increment: run the formatter across the whole codebase in one commit, capped at one session. Blocker: removes the old diff backlog that would otherwise send format noise into feature reviews. Test, before any work:
```gherkin
Given enforcement from Step 2
When the reformat commit is merged
Then CI passes with no manual edits and no feature changes
```
Cynefin: Clear.

**Step 4. Probe the culture change.** Increment: count review comments that mention formatting for two weeks, next to a one-week baseline before enforcement. Blocker: tests whether the friction claim was right. Acceptance test: metric = share of review comments about formatting; baseline = the pre-enforcement week; pass threshold = at most 10%; sample = all pull requests in the two weeks. Stop condition: if the rate stays above 10% after two weeks, revisit the config and rerun the probe. Cynefin: Complex, because behavior shows cause and effect only after the run, so this is a capped probe and its leverage is a guess. [4]

**Follow-up**

Conditions that change the recommendation: if A2 is false, Step 1 changes to a partial-language formatting setup and Step 4 measures only the covered files. If A1 is false, Step 2 becomes the hook alone.
