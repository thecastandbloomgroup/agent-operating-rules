## Headline

Adopt an automated SQL formatter as the single owner of style, enforce it in CI, and measure review friction for two weeks. Supporting points: (1) open style choices in SQL cause every review dispute, (2) a tool plus one committed config removes the decision surface, (3) CI plus pre-commit hooks stop debates before humans read the diff, (4) a two-week probe with friction data decides keep or change.

## Background

The team disagrees on SQL formatting. Every code review reopens the dispute, so reviewers spend time on layout instead of logic. The request is to remove the friction.

## Relevance

Each pull request pays the cost again until the team closes the choice. A mechanical rule closes it once.

## Information

**Evidence.** SQL leaves case, indenting, and keyword layout open, so each reviewer defaults to personal habit. No source in this session measures your team's review time; claims below carry labels.

- Formatters such as SQLFluff and sqlformat map one SQL file to one output, so format has one answer per config [1]. A source describes a linter as the standard that keeps team members consistent [1].
- Reviewers cannot focus on substance while they check layout. A source recommends automation for details so reviewers focus on the hard parts [1]. A paper on code review reaches the same conclusion: without automation, reviewers waste effort on minor problems and miss the important ones [2].

**Assumption log.**

A1. The team uses one or few SQL dialects. Why not measured: the material does not state it. Validate by: list dialects in use in 10 minutes. If wrong: set the dialect list in the config before Step 1.

A2. The repo has CI on pull requests. Why not measured: the material does not state it. Validate by: check for a CI config file in the repo root. If wrong: run the check on a maintainer's local machine first and add CI later.

A3. Reviews happen on pull requests in one repo. Why not measured: the material does not state it. Validate by: confirm the review workflow in 10 minutes. If wrong: point the hook at the SQL files in each repo the team uses.

**Alternative considered.** A facilitated workshop so the team agrees a style by discussion. It loses because agreement reached by talk still needs human enforcement, the exact step that produced the friction [2]. A tool replaces enforcement with an automated check.

## End

I recommend that we remove the decision surface, because a tool that owns format leaves style with no vote to contest.

1. **Settle the config (evaluative, Complicated).** Increment: in one 30-minute session, vote on the SQLFluff config options and commit one `.sqlfluff` file. Blocker removed: the team has no single source of style truth. Test (rubric first): criteria are dialect match (weight 3), rule count under 30 (weight 2), no team veto (weight 1), pass threshold 6 of 6 points, evidence is the committed config [15]. Cynefin: Complicated, because expert analysis of the config options picks the practice. Depends on A1.
2. **Automate enforcement (deterministic, Clear).** Increment: add `sqlfluff lint` to CI and a pre-commit hook in one session. Blocker removed: formatted SQL becomes a machine check, so reviews stop re-litigating layout. Test:


   Cynefin: Clear, because the check is one known step with a binary result [18]. Depends on Step 1.
