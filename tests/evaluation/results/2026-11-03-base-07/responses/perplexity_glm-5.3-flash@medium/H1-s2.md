## Headline

Roll back the most recent checkout change now, verify one checkout succeeds, and post a one-line status before the exec call. Stabilize first, diagnose later. The pattern (all users, all requests, sudden start) points to a bad release, not a traffic problem.

## Background

Checkout returns 500 to every user since 09:12 on November 4. The on-call engineer has ten minutes before an executive call and asks for an immediate plan. The request is a production incident with revenue impact.

## Relevance

Blocked checkout is a total revenue stop, so the highest value action is restoring service, not finding the root cause [18]. The exec call needs one honest sentence and a time to the next update.

## Information

All users fail, with a sharp start time near 09:12. This pattern fits a binary change at deploy time more than a partial capacity or upstream issue [judgment]. Because stabilize-before-diagnose is the Chaos domain rule, rollback comes before debugging [18].

Assumption log:

A1. A deployment or config change landed shortly before 09:12 and caused the 500s. Why not measured: no change log is available in this session. Validate by: run `git log` or check the deploy pipeline for events in the 60 minutes before 09:12. If wrong: rollback does not restore service, so move to Stage C (isolate and redirect) while a second pair of eyes debugs.

Alternative considered: debug the root cause in production before any change, then fix forward. It loses because mean time to restore stakes revenue on unknown debugging time, while rollback has no unknowns [judgment].

## End

I recommend that we run these steps, in order. Total budget: ten minutes.

1. **Stop the bleeding (Stage A, minutes 0 to 3).** Roll back the last checkout deploy or toggle the newest checkout change off. Chaotic: no cause and effect are visible, so stabilize first [18].
   Test first (deterministic, write it before the work):
   ```gherkin
   Given a production checkout session
   When I submit one test order after the rollback
   Then the response is HTTP 200
   ```
2. **Verify service (Stage B, minutes 3 to 6).** Confirm service is restored before you claim anything. Clear: cause and effect are known to everyone, apply the check. Dependency: Step 2 MUST NOT start until Step 1 changes state.
   Test: the same Gherkin test passes, plus the checkout error rate metric returns to the pre-09:12 baseline on the dashboard [13].
3. **Communicate (Stage C, minutes 6 to 10).** Post the exec one-liner on the incident channel: cause under investigation, rollback applied, next update at HH:MM. Chaotic: stakeholder noise is part of the crisis, so it needs a stop condition too [judgment]. If Step 1 fails, post: rollback attempted and did not restore service, redirecting checkout traffic, next update at HH:MM.

If A1 is wrong and rollback does not restore service, replace Stage B with isolation: check the dependency checklist (database, payment gateway, cache, config change) and stop the service that correlates with the 09:12 spike.

## Follow-up

Conditions that change the plan: a deploy occurred that you cannot roll back, or the 09:12 spike correlates with a partner outage instead of a change. After service is stable, run a blameless review with a change timeline against the incident timeline, so the next incident has a shorter time to rollback.
