## Headline

Build a measured quality loop first, then change the summariser one variable at a time. A 100-ticket gold set gives a numeric error rate within one week. A rubric written with agents turns "sometimes wrong" into scored criteria. One prompt change per run keeps cause and effect visible. A weekly sample with a rollback rule stops silent decay.

## Background

We added an LLM-based summariser to a support tool. Agents report that it is "sometimes wrong". No metrics exist today, so this report has no error type, no rate, and no trend.

## Relevance

Without a baseline, every prompt change is a guess. A tested loop replaces the guess with a number, a fix, and a check.

## Information

**Evidence and analysis**

- "Sometimes wrong" has no error type, no rate, and no sample. [judgment, from the request]
- A definition of "correct" is missing. Working definition: a summary is correct when it states every key ticket fact and states no non-fact. [judgment]
- Ground truth is cheap to build, because the ticket thread and the final reply already hold the facts. [judgment]
- A sample of 100 bounds the measured error rate to about plus or minus 10 percentage points. [judgment]
- Confidence in the loop design: high, based on standard QA practice with acceptance tests. [judgment]. Error cause is uncertain: about as likely as not (33 to 66%) that omissions, not wrong facts, drive the complaints. [judgment]

**Assumption log**

- A1. Most complaints are about facts, not tone. Why not measured: the material does not state it. Validate by: a 30-minute agent interview. If wrong: the rubric adds criteria for completeness or wording.
- A2. Weekly ticket volume is at least 100. Why not measured: tool data is not reachable in this session. Validate by: count tickets for the last week. If wrong: collect the gold set over 4 weeks and shift Steps 3 to 5 by 3 weeks.
- A3. Agents can spare about 2 hours to write reference summaries. Why not measured: agent workload is not in this session. Validate by: ask one team lead. If wrong: use 50 tickets for a wider interval.
- A4. The tool can export ticket thread text for scoring. Why not measured: no tool reach in this session. Validate by: export 10 tickets once. If wrong: work on exported copies.

**Alternative considered**

Tune the prompt now and ship. It loses because, without a baseline, no one can tell whether the change helps or hurts. The error rate stays unmeasured. [judgment]

## End

I recommend that we take these actions, with steps 1 and 2 in parallel:

**Step 1. Write the quality rubric (evaluative, Complicated).**
- Increment: a 60-minute workshop with three agents produces a one-page rubric.
- Blocker removed: the missing definition of "correct"; all later tests use the rubric.
- Test, written before the workshop: the rubric states each criterion, its weight, the pass threshold, and the evidence each criterion needs [1].
- Domain: Complicated, because agent analysis must pick the criteria.

**Step 2. Build the gold set (deterministic, Clear).**
- Increment: sample 100 closed tickets; one agent writes a reference summary for each; the job stores the pair.
- Blocker removed: the absence of ground truth.
- Test, written first, in Gherkin form [2]:
  - Given a sampled closed ticket
  - When a reference summary is entered
  - Then the tool stores the ticket, the reference summary, and the agent ID.
- Domain: Clear, because it is one known applied step.

**Step 3. Measure the baseline (stochastic, Complicated).**
- Increment: two scorers rate the 100 LLM summaries against the rubric; a third scorer resolves disagreements.
- Blocker removed: no number exists today.
- Test, written first: metric is factual errors per summary and missing key facts per summary; sample size is 100; scorer agreement threshold is 90% or higher; the first run sets the baseline.
- Domain: Complicated, because scorer calibration needs analysis; the interval is about plus or minus 10 percentage points. [judgment]

**Step 4. Change one prompt variable (stochastic, Complex).**
- Increment: add one rule, for example "use only facts stated in the ticket thread", then measure a fresh set of 50.
- Blocker removed: untested output changes.
- Test, written first: metric is the Step 3 error rate; baseline is the Step 3 value; pass threshold is a relative drop of 20% or more [judgment]; sample size is 50; budget is one working session; stop condition is no drop, then revert.
- Domain: Complex, because the effect shows only after the run, so this is a capped safe-to-fail probe [3].

**Step 5. Monitor and roll back (stochastic, Clear).**
- Increment: a weekly sample of 50 scored against the rubric, plus a rollback rule in the runbook.
- Blocker removed: silent decay after model or data changes.
- Test, written first:
  - Given a scored weekly sample of 50
  - When the error rate is above the Step 3 baseline for 2 weeks in a row
  - Then the last prompt change is reverted.
- Domain: Clear, because it is one known applied step.

Sequencing: Step 3 waits on Steps 1 and 2. Step 4 waits on Step 3. Step 5 starts when Step 3 passes its test.

Conditions: If A1 is false, Step 4 tests a coverage rule, for example "list every confirmed fact", instead of the grounding rule. If A2 is false, Step 2 runs for 4 weeks and Steps 3 to 5 shift by 3 weeks.
