Headline

Measure the summary error rate with agent labels first, then fix the summariser with one tested change at a time.

1. A sample of 100 labeled summaries gives a baseline error rate in about two working sessions [judgment].
2. A rating control with reason codes turns every future ticket into a new label.
3. The first fix, likely (66 to 100%) to help, is grounding: each summary sentence must quote a line from the ticket [judgment].

Background

The support tool now shows a summary of each ticket, written by a large language model (LLM). Agents report errors, but at an unknown rate. No metrics exist.

Relevance

Without a baseline, any change to the summariser is a guess. The steps below produce numbers within one week and a tested fix within two.

Information

Evidence

- The agent complaint is one qualitative theme from one source. It supports "errors exist" but gives no rate [judgment].
- Human labels are the accepted ground truth for text quality checks [judgment].
- One label takes about two minutes, so 100 labels cost about 3.5 hours of agent time [judgment].

Assumption log

A1. "Wrong" means the summary states facts absent from the ticket, or omits key facts. Why not measured: agents used an undefined phrase. Validate by: the reason codes from Step 1. If wrong: rewrite the Step 2 rubric before labeling.
A2. Volume is below 1,000 tickets per week. Why not measured: the material does not state volume. Validate by: query the ticket count. If wrong: switch to a weekly random sample of 100.
A3. Agents can edit the summary in the tool. Why not measured: the material does not state the UI. Validate by: check the summary screen. If wrong: use an accept button only, and drop the edit-diff metric.
A4. One agent session covers 50 labels. Why not measured: the estimate costs more than the decision is worth. Validate by: time the first labeling run. If wrong: cut the sample to 50 and state a wider error range.

Alternative considered

Use an LLM-as-judge to score summaries automatically. It loses because the judge's own error rate is also unmeasured, so it adds a second unknown [judgment]. A human-labeled sample is cheaper to trust first.

End

I recommend that we take these steps in order.

**Step 1 (Confused).** Ship a rating control with fixed reason codes next to every summary. Reason codes: "added fact", "omitted fact", "wrong tone", "too long". Increment: one working session. Blocker: removes the missing data and classifies the errors. Cynefin: Confused, because we cannot yet tell which fix matters [1].
Test (written first, deterministic [2]):
Given an agent views a summary
When the agent selects "wrong" and one reason code
Then the ticket record stores the rating and the code

**Step 2 (Complicated).** Label 100 sampled summaries against their tickets with a rubric adapted from the ISO/IEC 25010 quality categories [3]. This step waits on one day of ratings from Step 1, so the codes can confirm A1. Increment: two half-day sessions. Blocker: produces the baseline error rate and the largest error type. Cynefin: Complicated, because the coded errors pick the fix [1]. Rubric (evaluative kind): faithful (weight 0.5), complete (0.3), tone and structure (0.2). Pass needs two agents to agree on 80 of 100 labels. Evidence: each label cites the ticket line it checks.

**Step 3 (Complex).** Change the prompt so that each summary sentence quotes one ticket line. This step MUST NOT start until the Step 2 labels are complete. Increment: one prompt change. Blocker: removes the largest error type found in Step 2. Cynefin: Complex, because prompt changes act with delay and the effect is visible only after a run [1]. Probe, with a cap: metric, the share of sampled summaries with at least one unfaithful sentence; baseline, the Step 2 rate; pass, the share halves at a sample of 100 [judgment]; budget, two review sessions, then stop or keep.

**Step 4 (Clear).** Show every summary as a draft with its quoted ticket lines visible, until the agent accepts or edits it. This step runs only after the Step 1 control is live, and it runs in parallel with Step 3. Increment: one working session. Blocker: keeps unfaithful text from reaching customers before the prompt fix lands. Cynefin: Clear, because source display is a known practice for LLM output shown to operators [judgment].
Test (written first, deterministic [2]):
Given a summary with quoted ticket lines
When the agent has not accepted it
Then the ticket shows the summary as a draft

Keep the weekly "wrong" rating rate from Step 1 as the standing metric after all steps land. Treat it as the stop-or-continue signal for further prompt changes.

Follow-up

Conditions that change the recommendation: if A1 is wrong, rewrite the Step 2 rubric before any labeling. If A2 is wrong, sample weekly instead of labeling all output. If A3 is wrong, Step 4 becomes an accept button only.
