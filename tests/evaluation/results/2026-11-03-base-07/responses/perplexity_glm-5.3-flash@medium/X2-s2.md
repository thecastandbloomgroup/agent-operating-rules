Headline

Stop treating retrospectives as discussion meetings. Make each one produce a single owned action, close the loop on the past actions first, and run changes as short experiments.

Supporting points:

- Actions die after the meeting because nobody tracks them to closure. Therefore, review old actions before generating new ones.
- Cap the output at one action with one owner, one date, and one check. A list that everyone owns is a list that no one owns.
- Treat each change as a two-sprint probe with one metric and a stop condition, because in a team system cause and effect show up late [18].

Background

The team's retrospectives produce no process changes. Attendance continues, so people show up, but the outcomes do not shift behavior. The request asks what the team should do.

Relevance

A retro that produces no change costs hours per sprint and erodes trust in the practice. The fix is a process change, not a new meeting format to buy or a tool, so the team can start at the next retro.

Information

Evidence:

- The standard practice in retrospective guidance is a short list of improvement items, each with an owner and a follow-up in the next cycle [19].
- Vague suggestions with no owner do not get done. One or two concrete items per retrospective is the recommended norm [19].
- In teams, cause and effect between a change and an improvement is obscure in advance, so changes fit the safe-to-fail probe pattern: small, measured, with a stop condition [18].
- Small, explicit experiments with a target condition and a check cycle beat large process overhauls for sustained improvement [21].

Baseline for "nothing shifts": the described ratio of retro actions to closed actions is effectively 0 to many [no source]. Confidence that a closure loop fixes it: likely (66 to 100%), based on the pattern match to the described symptoms [judgment]. Confidence for the probe approach is separate: high for the need to measure, because the baseline is unknown.

End

I recommend that we:

1. Step 1 (Clear: a best practice exists, so apply it): at the next retro, spend the first half on the last three retros' actions. Mark each as closed or not, with dates, and adopt the follow-up habit from retrospectives guidance [19]. Deterministic. This removes the missing feedback loop on past work. Test, written before the work:
   Given the notes of the last three retros,
   When the team reviews each recorded action,
   Then every action has a status of closed or re-owned, with an owner and a date.
2. Step 2 (Clear: one step, known practice): at that same retro, end with at most one action, one owner, one date, and one check question [19]. Deterministic. This blocker: replaces unowned lists with a single owned change. Test:
   Given a retro ends,
   When the facilitator writes the record,
   Then the record contains one action with an owner, a date, and a check question, and no unowned item.
3. Step 3 (Complex: cause and effect appear only afterward, so run it as a capped probe [18]): run the single action as a two-sprint experiment with one metric. Stochastic. Metric: count of retro actions closed per sprint. Baseline: 0 per sprint, from the described state [no source]. Threshold: 1 closed action per sprint. Sample size: 2 sprints. Stop condition: no closed action after sprint 1, so stop and re-diagnose per A2. This adds the capability to learn which changes work. Test:
   Given two sprints run with one owned action each,
   When the count of closed actions is recorded,
   Then the count is at least 1 per sprint at the sample size of 2 sprints.
4. Step 4 (Complicated, depends on Step 1 data): if A1 fails and the chosen action sits outside team control, escalate that single action to the decision owner with the data from Step 1. Do not start this step until the Step 1 review produces the status list. Deterministic. This removes the authority blocker. Test:
   Given an action outside team control,
   When the team sends it to the decision owner,
   Then the message contains the action, the owner requested, a date, and the Step 1 data.

Follow-up

Conditions that change this recommendation: if Step 1 shows most past actions closed yet outcomes still fail to shift, then the gap is analysis quality or low safety, not tracking. Then switch to Step 3 with the retro format itself as the experiment, and add a safety check to the retro.
