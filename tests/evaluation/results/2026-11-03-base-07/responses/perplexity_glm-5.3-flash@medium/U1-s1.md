## Headline

Treat the flaky build as a Confused problem: the first action is data gathering, not a fix.

- First, extract the failure history from the CI logs and classify each failure by stage.
- Second, quarantine tests that fail on rerun, so the main suite stays usable.
- Third, fix the cause class with the largest failure count.
- Fourth, run a capped retry probe in parallel. Do not commit the full increment to it.

## Background

The message "The build is flaky" gives no pipeline, no logs, and no failure counts. The plan below assumes a CI system that keeps logs and pass/fail history per run. "Flaky" here means: the same commit sometimes passes and sometimes fails.

## Relevance

Intermittent failures block merges and mask real bugs. A data-first step decides which fix removes the most failures, before any work is spent on code changes.

## Information

Cause classes, with no overlap:

1. Test flakiness: timing, test order, or shared state between tests.
2. Environment contention: parallel runners, network, or container limits.
3. Non-hermetic build: cache, timestamps, or external data sources.
4. Infrastructure failure: runner crashes, disk, or quota limits.

## End

I recommend that we do the following, in this order:

1. **Extract and classify the failure history.**
   - Increment: one script that reads the last 50 CI runs and counts failures per stage and per test name.
   - Blocker removed: no knowledge of which cause class dominates.
   - Kind: deterministic. Test, written first:
     ```gherkin
     Given the CI log archive for the last 50 runs
     When the script processes each run and tags each failure
     Then the report shows a count per stage and per test name
     ```
   - Domain: Confused. The cause is not yet classifiable, so this action decides the rest.
2. **Quarantine the flaky tests.** This step MUST NOT start until the report from Step 1 exists.
   - Increment: move every test with 3 or more failures in 50 runs to a separate suite.
   - Blocker removed: intermittent failures stop blocking merges.
   - Kind: deterministic. Test, written first:
     ```gherkin
     Given the failure report from Step 1
     When the pipeline moves each named test to quarantine
     Then the main suite contains no test with 3 or more failures in 50 runs
     ```
   - Domain: Clear. A known practice exists: quarantine, then rerun out-of-band [1].
3. **Fix the top cause class.** This step waits on the report from Step 1.
   - Increment: one hermetic fix for the cause class with the largest count (for example: sleep removal or test isolation).
   - Blocker removed: the dominant failure source.
   - Kind: deterministic. Test, written first:
     ```gherkin
     Given the cause class with the largest failure count
     When the fix is in place
     Then 0 failures occur in 50 reruns of the affected tests
     ```
   - Domain: Complicated. Analysis from Step 1 picks the practice, so leverage is reliable after that analysis.
4. **Run a capped retry probe, in parallel with Steps 2 and 3.**
   - Increment: rerun a failed suite once, on a branch, for 2 calendar days.
   - Capability added: a measure of whether retries alone reduce the visible flake rate.
   - Kind: stochastic. Acceptance test first: metric is failures visible per 50 runs; baseline is the rate in the Step 1 report; pass threshold is a drop of at least 1 failure per 50 runs; sample size is 50 runs. Stop condition: remove the retry when the drop is smaller than the threshold. Budget: 2 calendar days. Leverage is a guess, because retries also hide real bugs [1].
   - Domain: Complex. Cause and effect show up only after the runs, so this is a safe-to-fail probe, capped by budget.

## Follow-up

Conditions that change the recommendation:

1. If the build is local-only (A1 false), replace Step 1 with 20 scripted local runs, and skip quarantine.
2. If the same commit fails every run (A2 false), the build is broken, not flaky. Stabilize first; treat this as Chaotic.
3. If the CI has no per-test logs, quarantine applies at the stage level, not the test level.
