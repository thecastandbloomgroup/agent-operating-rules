## Headline

Measure first: classify the errors, rate live summaries, and test every change on a fixed eval set. A two-agent review of 60 samples shows which error type dominates. A one-click rating on each summary turns "sometimes wrong" into weekly counts. A 50-case eval set gives each prompt or model change a pass or fail score. A grounding rule that limits the summarizer to facts in the ticket removes false claims directly.

## Background

The support tool gained an LLM-based summarizer for tickets. Agents report "sometimes wrong" with no numbers or error types. The task is to improve it The task is to make the summary quality measurable and then improve it.

## Relevance

Without metrics, each prompt change is a guess and agent trust keeps falling. A measurement setup costs a few days and turns feedback into ranked fixes.

## Information

**Evidence.** The only evidence today is one qualitative theme: agents judge the output as sometimes wrong. One source group supports it, so it carries low weight [no source]. Thematic analysis of agent comments is the method for this stage [3], [5]. No baseline numbers exist, so the first action must create them [judgment].

**Error taxonomy (MECE).** Summarizer errors separate into four classes [judgment]:

1. False claim: a statement not present in the ticket.
2. Missing fact: a needed statement absent from the summary.
3. Wrong emphasis: facts present, but order or priority misleads.
4. Unusable form: length, format, or language blocks use.

**Assumption log.**

- A1. The summarizer reads support conversation text. Why not measured: the request does not state the input. Validate by: read one summary next to its ticket. If wrong: the sample plan in Step 1 changes, the rest holds.
- A2. Agents read the summary before they act on a ticket. Why not measured: the tool workflow is not stated. Validate by: review the workflow during Step 1. If wrong: the rating in Step 2 becomes a weekly audit of closed tickets.
- A3. The tool stores summaries with their ticket IDs. Why not measured: the request does not state it. Validate by: check the log store during Step 1. If wrong: Step 1 must sample live output for one week before labeling.

**Alternative considered.** Drop the LLM summarizer and use a rule-based template from ticket fields. It loses because it cannot compress the middle of a long conversation, where agents lose the most time [judgment].

## End

I recommend that we run the following five steps. Step 1 goes first because its output decides every later choice.

1. **Label 60 sampled summaries** with the four-class taxonomy, two agents per case. Blocker removed: "wrong" has no definition. Kind: evaluative. Rubric: one criterion, primary error type, weight 1.0, threshold: the two agents agree on the primary label for 70% of cases [judgment], evidence per case: summary plus ticket text. Domain: Confused, because no data exists yet to classify the failure mode.
2. **Add one-click rating to the summary view.** The agent taps one of: no error, false claim, missing fact, wrong emphasis, unusable form. Blocker removed: agent judgment stays invisible. Test first:

```gherkin
Given an agent opens a summary in the tool,
When the agent taps one error-type button,
Then the tool stores ticket ID, summary ID, label, and timestamp in one record.
```

Kind: deterministic. Domain: Clear, a standard UI and write path.
3. **Collect ratings for one week.** Budget: 1 dev-day for reads and a count report. Stop if agents rate under 20% of summaries [judgment]. Blocker removed: no live defect rate exists. Kind: stochastic, acceptance test: metric is rated share of opened summaries, baseline is 0%, threshold 20%, sample: the week's full log. Domain: Complex, because adoption depends on agent behavior, so this runs as a capped safe-to-fail probe.
4. **Build a 50-case eval set**: 50 tickets, each with an agent-approved reference summary. Blocker removed: changes have nothing to compare against. Test first:

```gherkin
Given 50 tickets with agent-approved reference summaries,
When the eval script runs a summarizer version on all 50,
Then it writes one score file with per-case false-claim, missing-fact, and emphasis scores.
```

Kind: deterministic. Domain: Clear, a fixed dataset with known answers.
5. **Ground the prompt, then re-score.** The prompt rule: the summarizer uses only facts from the ticket text. Run the eval script per Step 4 and compare with the Step 1 samples as the baseline. Acceptance test: metric is the faithful-claim share, baseline is the measured rate on the Step 1 samples, pass at 95% over all claims, sample size 50 [judgment thresholds]. Blocker removed: false claims, the error class with the most direct fix. Kind: stochastic, because LLM output varies between runs. Domain: Complicated, because the score comparison picks between prompt rules, model swap, or a post-check.

Dependencies: Step 3 waits for Step 2. Step 5 does not start before Step 4's test passes. Run Step 3 and Steps 4 to 5 in parallel after their inputs exist.
