## Headline

Replace the format debate with one agreed rule set that a tool enforces, so reviews stop covering style.

- Decision: the team picks one style in a single timed session, with a named tie-breaker.
- Enforcement: a formatter and a CI check apply the style, so no person has to.
- Measurement: a short probe checks whether format comments drop in reviews.

## Background

The team has no shared SQL format. Each review includes arguments about style. The request is to end this friction.

## Relevance

Every review that debates format takes time away from review of logic and correctness. The cost repeats with every pull request until a rule and a tool exist.

## End

I recommend that we take these five actions in this order.

1. **Pick the style in one 45-minute session.**
   - Increment: choose among at most three candidate styles. Examples are the default of the chosen formatter, the current majority style, and one team proposal.
   - Blocker removed: no agreed rule exists.
   - Kind: evaluative. Write the rubric first.
     - Criteria and weights: automatable by a tool (40), readability on three real queries (35), size of the diff against current code (25).
     - Pass threshold: 70 of 100.
     - Evidence: the three queries formatted under each candidate, the line count changed, and a named tool that enforces the style.
   - Layout: a Pugh matrix [3]. The tie-breaker from A2 decides ties. The decision stays closed for 90 days.
   - Domain: Complicated, because several good practices exist and analysis picks one.

2. **Write the formatter config for the chosen style.**
   - Increment: one config file in the repository.
   - Blocker removed: the rule exists only in words.
   - Kind: deterministic.
   - Test, written first:
     - Given a SQL file with mixed keyword case
     - When the formatter runs with the team config
     - Then all keywords use the agreed case
   - Domain: Clear, because formatter config is a known best practice.
   - Step 2 MUST NOT start until Step 1 records a decision.

3. **Add a pre-commit hook and a CI check on changed files.**
   - Increment: one CI job and one hook.
   - Blocker removed: nobody enforces the rule.
   - Kind: deterministic.
   - Test, written first:
     - Given a pull request with an unformatted SQL file
     - When the CI format check runs
     - Then the check fails and names the file
   - Domain: Clear, because the practice is standard.
   - Step 3 MUST NOT start until the test in Step 2 passes.

4. **Reformat the existing SQL in one isolated commit.**
   - Increment: one commit with no logic changes. List it in a blame-ignore file.
   - Blocker removed: old files fail the new check.
   - Kind: deterministic.
   - Test, written first:
     - Given the repository after the bulk commit
     - When the formatter runs on all SQL files
     - Then it reports zero changes
   - Domain: Clear, because the steps are known.
   - Step 4 MUST NOT start until the test in Step 3 passes.

5. **Run a two-week probe on review behavior. Start it in parallel with Step 2.**
   - Increment: count format comments in reviews. Add one team rule: reviewers do not comment on format, and the CI check decides.
   - Blocker removed: no evidence shows whether the culture changed.
   - Kind: stochastic.
   - Acceptance test, written first:
     - Metric: share of review comments about format.
     - Baseline: the last 20 reviews before the change.
     - Threshold: a drop of at least 80% (judgment).
     - Sample: the first 20 reviews after Step 4.
   - Stop condition: end at two weeks or 20 reviews, whichever comes first.
   - Budget: 30 minutes of setup and 30 minutes of counting.
   - Domain: Complex, because team behavior shows its effect only afterward. Leverage here is a guess.

If A1 is false, replace Step 3 with an editor-level setting and keep the other steps.
