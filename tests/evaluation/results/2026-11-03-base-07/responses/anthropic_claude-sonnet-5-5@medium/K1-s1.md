## Headline

Raise the database pool to the new connection limit and restore the cache TTL (time to live) first, because pool exhaustion causes most of the delay.

- The pool setting causes the wait: `db.pool.acquire` p95 rose from 3 ms to 690 ms, which is 77% of the 900 ms total.
- The cache change adds load: the miss rate rose from 12% to 31%.
- The ORM change has no measured effect on query time, so it ranks last.
- The database server is not the limit: CPU rose only from 38% to 41%.

## Background

The API p95 latency for `GET /customers/{id}/orders` rose from 120 ms to 900 ms after release 2026.10.21. The release cut the pool size from 50 to 8, cut the cache TTL from 300 s to 60 s, and added `selectinload` to the orders query. The request asks for a course of action.

## Relevance

The error rate is now 0.40%, up from 0.02%. Users get 503 errors after a 5 s wait. The load stays at about 405 requests per second, so the problem will not clear on its own.

## Information

Confidence that the pool size is the main cause: very likely (90 to 100%). Basis: the trace spans, the error mix, and the log warnings agree.

Open anomaly: logs show up to 14 waiters on a pod with 8 worker threads [1]. Threads alone cannot explain this, so some code path may open more than one connection per request. This is [inference].

Assumption log:

A2. The trace figure "8 active connections" is a per-pod peak. Why not measured: the trace summary does not name its scope. Validate by: query the pool metric per pod for one hour. If wrong: the service total is below 32 and the pool is not the only limit.

Alternative considered: roll back the whole release. It loses because a rollback restores a pool of 50, which breaks the new database limit in OPS-412 [judgment]. It also reverts the ORM change, which has no measured fault.

## End

1. **Set `max_size` to the highest value the OPS-412 limit allows per pod.**
   - Increment: one config change, deployed to one canary pod.
   - Blocker removed: pool wait, 690 ms of the 900 ms p95.
   - Kind: deterministic. Domain: Complicated, because the limit is knowable by analysis of the ticket and the database settings.

2. **Restore `default_ttl_s` to 300.**
   - Increment: one config change, deployed to the canary pod.
   - Blocker removed: the extra database load from a 31% miss rate.
   - Kind: deterministic. Domain: Clear, because this is a known revert.
   - Test, written first:

3. **Set `acquire_timeout_s` to 15 after Step 1 passes.**
   - Increment: one config change, deployed to the canary pod.
   - Blocker removed: 503 errors after a 5 s wait during short bursts.
   - Kind: deterministic. Domain: Clear, because the 5 s value came from this release only.
   - Test, written first:
     - Given the canary pod runs a 2x burst for 60 s
     - When the burst ends
     - Then the error rate is at most 0.05%

4. **Run a probe on connection use per request, in parallel with Steps 1 to 3.**
   - Increment: one canary pod with `selectinload` on, one with it off, 10,000 requests each.
   - Capability added: the cause of waiters above the thread count, and the effect of `selectinload`.
   - Kind: stochastic. Domain: Complex, because the cause appears only after the probe. Leverage is a guess.
   - Budget: one working session. Stop when both runs finish or the error rate on a canary exceeds 1%.
   - Test, written first: metric is p95 latency. Baseline is 120 ms. Pass threshold is at most 150 ms. Sample size is 10,000 requests per arm. Keep `selectinload` only if its arm passes.

Condition that changes this plan: if A1 is false and the limit is below 32 in total, replace Step 1 with a cut in worker threads per pod to match the limit.
