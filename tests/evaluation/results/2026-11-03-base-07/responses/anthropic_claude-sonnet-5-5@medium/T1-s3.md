## Headline

Remove formatting from human judgment: pick one style once, then let a tool enforce it.

- A format dispute is a missing default, not a character flaw, so one decision ends the debate.
- A formatter (a program that rewrites code to a fixed style) removes the topic from reviews.
- A review rule keeps the topic closed after the tool is in place.
- A measured trial shows whether the culture changed.

## Background

The team writes SQL (Structured Query Language) and disagrees on its format. Each code review repeats the same argument. The request is to end this friction.

## Relevance

Every review that debates style delays merges and tires reviewers. The cost grows with each new pull request (a proposed change that reviewers check).

## Information

**Evidence**

- Style guides work best when tools enforce them, so people do not argue each rule by hand.
  - Software Engineering at Google, on style guides and rules [1]
- SQLFluff is a linter (a program that flags rule violations). It also formats SQL and reads rules from a config file in the repository.
  - SQLFluff documentation [2]
- Format comments in reviews carry no information when a tool can decide them. [judgment]
- The team has no measured count of format comments yet. Action 4 collects it.

**Assumption log**

A1. The team uses git with pull request reviews. Why not measured: the material does not state it. Validate by: ask one teammate. If wrong: replace the CI check in Step 3 with a pre-commit hook only.

A2. All SQL uses one dialect (for example PostgreSQL). Why not measured: the material does not state it. Validate by: list the dialects in the repository. If wrong: Step 2 needs one config per dialect.

A3. The team may choose its own tool and style. Why not measured: the user has not answered. Validate by: check with the team lead. If wrong: Step 1 must adopt the organization's existing standard.

A4. The conflict is about taste, not about a real technical need. Why not measured: no tool can reach the team's opinions. Validate by: collect objections in Step 1. If wrong: add the need to the rubric.

**Alternative considered**

Write a long style guide and enforce it in review. It loses because humans apply rules unevenly, and that keeps the friction. [judgment]

## End

I recommend that we:

1. **Decide the style in one 45-minute session.**
   - Increment: the team scores three candidates, and one named decider records the winner in the repository.
   - Blocker removed: no default exists, so every choice is open to debate.
   - Kind: evaluative. Test written first, as a Pugh matrix [3].
     - Criteria and weights: readability 3, diff noise 3, tool support 2, effort to adopt 1.
     - Evidence: one sample query formatted under each candidate.
     - Pass threshold: the winner beats the baseline of the current mixed style by a total of at least +3.
   - Cynefin: Complicated, because analysis picks among several good practices.
   - Rule: the decider MUST break any tie. Nobody reopens the choice for 90 days.

2. **Format the whole codebase in one commit.**
   - Increment: add the tool config, run the formatter once, and merge.
   - Blocker removed: old files would otherwise show style changes in future diffs.
   - Kind: deterministic. Test written first:
     - Given the committed config and the existing SQL files
     - When the formatter runs in check mode
     - Then it reports zero violations and the query results are unchanged
   - Cynefin: Clear, because a known tool applies a known practice.
   - Step 2 MUST NOT start until Step 1 records the decision.

3. **Enforce the style in automation.**
   - Increment: add a pre-commit hook and a CI (continuous integration, automatic checks on each change) job.
   - Blocker removed: without enforcement, the style decays.
   - Kind: deterministic. Test written first:
     - Given a pull request with a badly formatted query
     - When the CI job runs
     - Then the job fails and names the file and line
   - Cynefin: Clear, because the setup is standard.
   - Step 3 MUST NOT start until Step 2 is merged.

4. **Run a four-week trial of a review rule.**
   - Increment: reviewers do not comment on format the tool accepts. Style changes go through a config pull request.
   - Blocker removed: old habits can bring the argument back.
   - Kind: stochastic. Test written first:
     - Metric: share of review comments about format.
     - Baseline: count from the last 20 merged pull requests, before the trial.
     - Pass threshold: at most one-third of the baseline share.
     - Sample size: at least 20 pull requests in the trial.
   - Cynefin: Complex, because team behavior shows its response only afterward. Leverage is a guess.
   - Budget: 30 minutes to count the baseline, 15 minutes a week to track.
   - Stop condition: end the trial early if reviewers skip real defects. Run it in parallel with Steps 2 and 3.

## Follow-up

**Conditions that change the recommendation**

- If A3 is false, replace Step 1 with adoption of the organization's standard.
- If the trial in Step 4 fails the threshold, hold a retrospective to find the remaining friction. Add its themes to the rubric.
