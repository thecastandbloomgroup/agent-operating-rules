## Headline

I recommend that we measure the flake rate and group the failures before we fix anything, because the cause is not yet known.

- The request gives no failure data, so the first step is to collect it.
- A rubric can rank the causes once the data exists.
- A capped probe can reduce the pain while the analysis runs.

## Background

The request states that the build is flaky. A flaky build passes and fails on the same code. The request does not name the project, the CI system, the failing step, or the failure rate.

## Relevance

Each false failure blocks a merge and wastes a rerun. Teams also learn to ignore red builds, so real failures get missed.

## Information

**Evidence**

- At Google, about 1.5% of all test runs showed flaky results. Almost 16% of tests had some flakiness. [1]
- In a study of 201 fixed flaky tests, async wait was the largest cause, at about 45%. Concurrency and test order followed. [2]
- Test-level causes are 70% likely here, based on the study above. [2] This is a [judgment] about the transfer to this project.

**Assumption log**

A1. The build is a CI build, and failures are intermittent on unchanged code. Why not measured: the material states only "flaky". Validate by: rerun one commit 10 times. If wrong: a rate of 0% or 100% means the failure is deterministic, so bisect the commits instead.

A2. CI logs for the last 30 days are readable. Why not measured: no tool can reach the CI system. Validate by: open the run list. If wrong: Step 1 uses new runs collected over two weeks.

**Alternative considered**

The alternative is to add automatic retries to every job now. It loses because retries hide the cause and raise CI cost, and the flake rate stays unmeasured [judgment].
