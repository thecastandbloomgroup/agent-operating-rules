## Headline

Measure the summariser's errors first, then fix the most common error type with a tested change.

- The team has no metrics, so no one can show that any change helps.
- "Sometimes wrong" covers several different failures, and each needs a different fix.
- A fixed test set of real tickets lets the team compare every change against one baseline.
- Agent feedback inside the tool keeps the measurement running after launch.

## Background

The support tool now has an LLM-based summariser (a model that writes a short summary of a ticket). Agents report that it is "sometimes wrong" (per the user's message). The team has no metrics and asks for a better summariser.

## Relevance

Agents who distrust a summary reread the full ticket, so the feature adds work instead of saving it [judgment]. A wrong summary can also send a customer an incorrect answer.

## Information

**Evidence**

- Evidence of the problem is one statement from agents, relayed in the user's message. It has no count, no error type, and no rate [judgment: single source, low confidence].
- No baseline exists. Section A1 and A2 below explain how the plan creates one.
- The Cynefin framework sorts work by how clear cause and effect are [1]. The error causes here are unknown, so the first action gathers data to classify them.

**Assumption log**

A1. Ticket text and stored summaries are available for export. Why not measured: the material does not state it. Validate by: ask an engineer to export 20 rows. If wrong: Step 1 starts from live samples instead, which adds about one day.

A2. Agents can label 100 summaries in one session. Why not measured: the user has not answered. Validate by: time five labels. If wrong: cut the sample to 50 and widen the error margin.

A3. Most errors fall into a small set of types. Why not measured: no error data exists. Validate by: Step 1 results. If wrong: Step 4 targets a different cause, or splits into several probes.

A4. The model and prompt can be changed by the team. Why not measured: the material does not state it. Validate by: check the configuration. If wrong: Step 4 becomes a request to the vendor.

**Alternative considered**

Switch to a larger model now. It loses because without a baseline the team cannot tell whether it helps, and it raises cost [judgment].

## End

I recommend that we take these steps in order.

1. **Label 100 real summaries and classify the errors.**
   - Increment: one session where agents mark 100 recent summaries as correct or wrong, with one error type each.
   - Blocker removed: no one knows what "wrong" means.
   - Kind: evaluative. Rubric written first. Criteria and weights: factual accuracy 50%, no missing key facts 30%, no invented content 20%. Pass mark: a summary scores at least 80 of 100. Evidence: the ticket text beside the summary. Error types: invented fact, distorted fact, missing key fact, other.
   - Cynefin: Confused, because the cause of the errors is unknown. This step gathers what is needed to classify the rest.

2. **Add a "wrong summary" button that logs the ticket and summary.**
   - Increment: one button and one log table.
   - Blocker removed: no ongoing metric exists.
   - Kind: deterministic. Test first:
     - Given an agent views a summary
     - When the agent clicks "Wrong summary" and picks an error type
     - Then the log stores the ticket ID, summary text, error type, and time
   - Cynefin: Clear, because logging a click is a known practice.
   - Step 2 MUST NOT start until Step 1 fixes the error type list.

3. **Freeze the 100 labelled tickets as a test set with a scoring script.**
   - Increment: one script that runs the summariser on the 100 tickets and reports the error rate.
   - Blocker removed: no baseline to compare changes against.
   - Kind: stochastic. Acceptance test first. Metric: tickets with at least one factual error, out of 100. Baseline: the Step 1 result. Pass threshold: 10 fewer error tickets than baseline on the same set [judgment]. Sample size: 100, run three times per version to see run-to-run spread.
   - Cynefin: Complicated, because a good scoring method exists but needs analysis to choose.
   - Step 3 MUST NOT start until Step 1 is complete.

4. **Run one capped probe on the top error type.**
   - Increment: one prompt change aimed at the most common error from Step 1. Example: for invented facts, require the summary to use only ticket text.
   - Blocker removed: no evidence yet on which fix works.
   - Kind: stochastic. Use the Step 3 test. Budget: two working days and one prompt change per run. Stop condition: stop after three versions, or when the threshold is met.
   - Cynefin: Complex, because the effect of a prompt change shows only after the run. The leverage of this probe is a guess.
   - Step 4 MUST NOT start until the Step 3 script passes a dry run on the baseline prompt. It may run in parallel with Step 2.

## Follow-up

**Open questions:** none. Section A1 to A4 hold the assumptions.

**Conditions that change the recommendation:**

- If A3 is false, replace Step 4 with one probe per error type, each with its own budget.
- If Step 1 shows an error rate below 5%, drop Step 4 and keep Steps 2 and 3 as monitoring.
