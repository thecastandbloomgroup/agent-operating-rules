## Headline

Measure the errors first, then change the prompt only against a labeled test set.

- No one knows the error rate or the error types today, so any change is a guess.
- A labeled sample of 100 summaries gives a baseline and an error list in one session.
- A feedback button keeps the signal alive after the first fix.
- Prompt changes run as capped experiments, scored on the same test set.

## Background

The team added a summariser to the support tool. It uses a large language model (LLM), which is an AI model that generates text. Agents say the summaries are "sometimes wrong". The team has no metrics [1].

## Relevance

Agents read the summary instead of the full ticket. Therefore a wrong summary leads to a wrong reply or to lost time [judgment].

## Information

**Evidence**

- E1. The only signal is the agent comment "sometimes wrong". There is no rate and no error type.

  [1]

- E2. LLM summaries can contain facts that are not in the source text. Surveys call this hallucination.

  [2]

- E3. A sample of 100 summaries at an 80% error-free rate gives a 95% margin of about 8 points. A sample of 200 gives about 5.5 points. [inference] (normal approximation of the binomial)
- E4. Theme: errors cluster in a few types, such as invented fact, missing fact, and wrong ticket status. Support: one source group (agents), no dissent found. Confidence: low, one source. It is likely (66 to 100%) that this holds [judgment].

**Assumption log**

A1. Summaries and their source tickets are stored. Why not measured: the material does not state it. Validate by: query the last 100 pairs. If wrong: swap Step 1 and Step 2, then collect data for one week.

A2. Four agents can label 25 summaries each in one session. Why not measured: the user has not answered. Validate by: time five labels. If wrong: label 50 summaries and accept a wider margin.

A3. The team can change the prompt and the model settings. Why not measured: the material does not state it. Validate by: check access to the configuration. If wrong: limit Step 4 to checks on the output.

**Alternative considered**

The strongest alternative is to switch to a larger model now. It loses because there is no baseline to show a gain, and the cost per summary rises [judgment].

## End

I recommend that we take these four actions. Domains follow the Cynefin framework.

   [3]

1. **Sample and label (evaluative, Confused).** The domain is Confused because the cause of the errors is unknown.
   - Increment: pull the last 100 ticket and summary pairs. Four agents label each summary as correct or wrong. They tag each error as invented fact, missing fact, wrong status, or other.
   - Blocker removed: no baseline and no error types.
   - Rubric, written first: coverage (weight 40): 100 of 100 labeled. Agreement (weight 30): 20 double-labeled, at least 80% match. Taxonomy fit (weight 30): at least 90% of errors fit the first three types.
   - Pass threshold: 70 of 100 points, and the agreement criterion is met. Evidence: the label sheet, the double-label sheet, and a count table.
2. **Add a feedback button (deterministic, Clear).** The domain is Clear because this is a standard feature with a known method.
   - Increment: add a "Wrong summary" button with a reason list. Store the result.
   - Blocker removed: no ongoing signal after Step 1.
   - Test, in Gherkin form [4]:

     Given an agent views the summary for ticket 123

     When the agent clicks "Wrong summary" and picks "missing fact"

     Then the system stores the ticket ID, the summary text, the reason, and the time
   - Step 2 MAY run while Step 1 runs.
3. **Build the test set and the metric (stochastic, Complicated).** The domain is Complicated because the error types from Step 1 pick the metric.
   - Increment: extend the labeled set to 200 tickets. Define the metric: error-free rate, which is the share of summaries with no wrong label.
   - Blocker removed: no fixed way to compare versions.
   - Acceptance test, written first: run the current summariser three times on the 200 tickets. Metric: error-free rate. Baseline: the Step 1 rate. Threshold: the three runs differ by at most 5 points. Sample size: 200.
   - Step 3 MUST NOT start until the test in Step 1 passes.
4. **Probe a structured prompt (stochastic, Complex).** The domain is Complex because model behavior shows only after a trial. Leverage here is a guess.
   - Increment: change the prompt. Require three fields (issue, status, next step). Require a quoted ticket line for each fact.
   - Blocker removed: the main error type found in Step 1.
   - Acceptance test, written first: metric is the error-free rate. Baseline is the Step 3 rate. Threshold is a gain of at least 10 points. Sample size is 200 tickets.
   - Budget: two working days and three prompt variants. Stop condition: no variant gains 5 points.
   - Step 4 MUST NOT start until the test in Step 3 passes.

## Follow-up

Conditions that change the recommendation:

- If A1 is false, swap Step 1 and Step 2 and wait one week for data.
- If Step 1 shows an error-free rate above 95%, stop at Step 2 and track the button data.
- If Step 4 fails its stop condition, test a larger model on the same 200 tickets.
