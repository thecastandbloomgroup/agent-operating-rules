## Headline

Measure the failure rate and find the failing step first, then contain the flaky part, then fix its cause.

- The cause is unknown, because the request gives no logs or failure counts.
- A flaky build (one that fails and then passes on the same code) needs a measured failure rate before any fix.
- Containment protects the team now, and a root-cause fix removes the problem.

## Background

The request says "The build is flaky." It gives no logs, no tool names, and no failure counts. This response assumes an automated build and test run on a continuous integration (CI) server.

## Relevance

A flaky build makes the team distrust failures. Real defects then pass as "just a flake".

## Information

**Evidence**

- Flaky tests have common causes. In a study of 201 fixed flaky tests, async wait was the top cause at 45%, concurrency 20%, and test order dependency 12% [1]. This is secondary evidence from open-source projects, so it is a prior and not a diagnosis.
- A rerun of one unchanged commit 30 times detects a 10% failure rate with 96% probability (1 - 0.9^30). [judgment, simple probability]
- Automatic retries hide the failure and do not remove it. [judgment]

**Assumption log**

A1. The build runs on a CI server, and "flaky" means the same commit both passes and fails. Why not measured: the request does not state it. Validate by: rerun one commit five times. If wrong: Step 1 re-scopes to the real symptom.

A2. The cause is in the tests or the environment, not in the product code. Why not measured: no tool can reach the logs. Validate by: the grouping in Step 1. If wrong: Steps 3 and 4 move to the product code.

A3. The CI history holds at least 50 readable runs. Why not measured: no tool can reach the CI server. Validate by: export the history. If wrong: run Step 2 first and use its results as the baseline.

**Alternative considered**

The strongest alternative is to retry failed jobs automatically. It loses because it hides the failure rate and adds build time. [judgment]

## End

I recommend that we do these steps in order:

1. **Group the failures from the last 50 runs.**
   - Increment: export the runs and group failures by job and error text.
   - Blocker removed: nobody knows where the failures come from.
   - Kind: deterministic.
   - Domain: Confused, because the cause could sit in tests, environment, or dependencies.
   - Test, written first:
     ```text
     Given the CI history holds the last 50 runs
     When we export the runs and group failures by job and error text
     Then each failed run appears in exactly one group
     And the top three groups are listed by count
     ```

2. **Measure the baseline failure rate.**
   - Increment: rerun one unchanged commit 30 times and record the failures.
   - Blocker removed: no number exists to judge a fix.
   - Kind: stochastic.
   - Domain: Clear, because the method is a rerun and a count.
   - Test, written first: the metric is the failure rate. The baseline is the Step 1 rate (failed runs divided by 50). The sample is 30 runs. Accept only when all 30 runs finish and the rate is recorded.
   - Step 2 MUST NOT start until the test in Step 1 passes.

3. **Contain the top failing test.**
   - Increment: move the test from Step 1's top group into a non-blocking job.
   - Blocker removed: the flaky test stops blocking the team's merges.
   - Kind: stochastic.
   - Domain: Complicated, because choosing the quarantine method needs analysis of the top group.
   - Test, written first: the metric is the pass rate of the blocking build. The baseline is the Step 2 rate. The threshold is at least 95%. The sample is 30 runs.
   - Step 3 MUST NOT start until the test in Step 2 passes.

4. **Probe one root-cause hypothesis for the top group.**
   - Increment: apply one fix for the top Step 1 group. For example, replace a fixed sleep with an explicit wait.
   - Capability added: a test of the cause, not only the symptom.
   - Kind: stochastic.
   - Domain: Complex, because the cause shows only after the change. Leverage is a guess.
   - Test, written first: the metric is failures in 30 reruns. The threshold is 0 failures, which bounds the rate below about 10% at 95% confidence. The budget is one working session. Stop and revert if two hypotheses fail.
   - Step 4 MUST NOT start until the test in Step 1 passes. It runs in parallel with Steps 2 and 3.

If A2 is false, replace Step 4 with a code review of the product change that matches the top failure group.
