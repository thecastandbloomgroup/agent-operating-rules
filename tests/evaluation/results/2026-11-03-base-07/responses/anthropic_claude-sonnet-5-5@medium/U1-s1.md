## Headline

Measure the failure rate first, then group the failures by cause, then isolate the top cause.

- The cause of the flakiness is unknown, so a fix now is a guess.
- A flaky build is one that passes and fails on the same code with no change.
- Grouping failures into causes shows where the largest share of failures sits.
- A quarantine keeps the main branch usable while the fix is built.

## Background

The report states that the build is flaky. It gives no logs, failure counts, or build tool. This response assumes the build runs on an automated build server and fails at random on unchanged code.

## Relevance

Each random failure costs a rerun and hides real defects behind noise. Teams then start to ignore red builds [judgment].

## Information

**Evidence**

1. The material holds no failure data, so the failure rate is unknown. See A1 and A2.
2. Cause groups used in Step 2 cover the whole space and do not overlap [judgment]:
   - Shared state between tests, including test order.
   - Timing and asynchronous waits.
   - External services and network.
   - Build machine resources, such as memory, disk, and parallel jobs.
3. A run of n builds with zero failures shows a failure rate below 3/n with 95% confidence [inference]. For a 10% failure rate, n is 30.
4. Domain labels in the End section follow the Cynefin framework [1].

**Assumption log**

A1. The build fails on unchanged code at a rate of 10% or higher. Why not measured: the material does not state it. Validate by: rerun one commit 30 times. If wrong: raise the sample size in Step 4 to 3 divided by the measured rate.

A2. The build server keeps logs for each run. Why not measured: no tool can reach it. Validate by: open the last failed run. If wrong: Step 1 adds log capture before the reruns.

A3. One cause group explains most failures. Why not measured: the material does not state it. Validate by: the grouping in Step 2. If wrong: Step 4 runs one probe per group.

**Alternative considered**

Add automatic retries to the build. This loses because retries hide real failures and raise build time [judgment]. They also leave the cause in place.

## End

I recommend that we take these steps in order.

1. **Measure the failure rate.** Rerun the latest main commit 30 times and save each log.
   - Blocker removed: the failure rate and failing steps are unknown.
   - Kind: stochastic. Metric: share of failed runs. Baseline: 0%, because the code does not change. Pass threshold: all 30 runs finish and each failure has a log. Sample size: 30.
   - Domain: Confused, because the cause is unknown and this step gathers what is needed to classify the work.

2. **Group the failures by cause.** Place each failure in one of the four groups in the Information section.
   - Step 2 MUST NOT start until Step 1 passes.
   - Blocker removed: no one knows which cause to fix first.
   - Kind: evaluative. Rubric: criteria are failure count (weight 60%) and log evidence for the cause (weight 40%). Pass threshold: at least 80% of failures grouped, each with one log line as evidence.
   - Domain: Complicated, because analysis of the logs picks the practice.

3. **Quarantine the top failing test.** Move it to a separate job that does not block merges.
   - Step 3 MUST NOT start until Step 2 names the top test.
   - Blocker removed: random red builds stop blocking merges.
   - Kind: deterministic. The test follows the Gherkin form [2]:

     Given the top failing test is tagged as quarantined

     When the main build runs

     Then the main build passes without that test

     And the quarantined job still runs and reports its result
   - Domain: Clear, because quarantine is an established practice.

4. **Run one fix probe on a branch.** Change one thing that targets the top cause group, such as isolated temp directories for shared state.
   - Run this probe in parallel with Step 3. Cap it at two hours. Stop it when 30 runs show no drop in failure rate.
   - Capability added: evidence of whether the top cause is the real cause.
   - Kind: stochastic. Metric: failure rate. Baseline: the rate from Step 1. Pass threshold: zero failures in the sample. Sample size: 3 divided by the Step 1 rate, and at least 30.
   - Domain: Complex, because the effect of the change shows only after the runs. The leverage of this probe is a guess.
