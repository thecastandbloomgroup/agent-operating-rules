## Headline

**Measure the summariser's errors first, then change the prompt against that baseline.**

- No metric exists today, so no change can be shown to help.
- A labelled sample of 50 summaries will show which error types occur.
- A flag button will give a continuing error rate from live use.
- One prompt change and one small live trial will test the fix.

## Background

The team added a summariser built on a large language model (LLM) to the support tool. Agents report that it is "sometimes wrong" (per the user's message). The team has no metrics, so the size, type, and cause of the errors are unknown.

## Relevance

Agents who distrust the summary re-read the full ticket, so the feature adds work instead of saving it [judgment]. Each unmeasured change risks making errors worse without anyone noticing.

## Information

**Evidence**

1. LLM summarisers are known to produce content that the source text does not support. This is called hallucination.

   Survey of the field:

   [1]

2. Agent feedback is one theme from one source group: "sometimes wrong". Zero sources disagree. Zero sources give a count or an example. Confidence in any cause is low, based on one unquantified statement.
3. The top error type is unknown. It is likely (66 to 100%) that omission or unsupported content leads, but this is [judgment].
4. A prompt change alone is about as likely as not (33 to 66%) to reach the Step 3 threshold [judgment].
5. A sample of 50 gives a 95% interval of about plus or minus 14 percentage points at a 50% error rate. This follows from the normal approximation for a proportion. Only large improvements will show.
6. This plan sorts each action by Cynefin domain. Cynefin is a framework that classifies work by how cause and effect relate.

   Framework source:

   [2]

7. Tests in Gherkin form use Given, When, Then lines.

   Format source:

   [3]

**Assumption log**

A1. Ticket text is stored and linked to each summary. Why not measured: the material does not state it. Validate by: open five recent tickets. If wrong: capture ticket text before Step 1.

A2. The team can add a button to the agent screen. Why not measured: the material does not state it. Validate by: ask the tool developer. If wrong: use a shared form for Step 2.

A3. The model and prompt version are logged per summary. Why not measured: the material does not state it. Validate by: read the logs for one day. If wrong: Step 2 adds version logging.

A4. Two people can label 50 summaries in one session. Why not measured: measuring costs more than the decision is worth. Validate by: time the first five. If wrong: cut to 30 and accept a wider interval.

**Alternative considered**

The strongest alternative is to switch to a larger model or fine-tune now. It loses because no baseline exists, so no one can show that it works. It also costs more than a prompt change [judgment].

## End

I recommend that we take these four actions, in this order:

1. **Label a sample of 50 recent summaries against their tickets.**
   - Kind: evaluative. Domain: Confused, because we cannot yet say what "wrong" means.
   - Increment: one session, two reviewers, 50 summaries.
   - Blocker removed: no baseline and no error types.
   - Rubric, written first:
     - Factual accuracy, weight 40.
     - No invented facts, weight 30.
     - Key facts present (issue, status, next step), weight 20.
     - Length fits the screen, weight 10.
   - Pass threshold: a score of 80 or more and zero invented facts.
   - Evidence per criterion: the quoted ticket lines.
   - Output: the baseline failure rate and a count per error type.

2. **Add a "Wrong summary" button that logs each flag.**
   - Kind: deterministic. Domain: Clear, because feedback logging is standard practice.
   - Increment: one button, one reason list, one log table.
   - Blocker removed: no continuing error measure.
   - Step 2 MAY run in parallel with Step 1.
   - Test, written first:

     Given an agent views the summary of ticket 123

     When the agent presses "Wrong summary" and picks a reason

     Then the tool stores the ticket id, summary id, reason, model version, and prompt version

3. **Change the prompt to target the top error type from Step 1.**
   - Kind: stochastic. Domain: Complicated, because the Step 1 analysis picks the practice.
   - Increment: one prompt change, tested on the labelled tickets.
   - Blocker removed: the largest error type.
   - Step 3 MUST NOT start until Step 1 is complete.
   - Acceptance test, written first:
     - Metric: share of summaries scoring below 80 on the Step 1 rubric.
     - Baseline: the Step 1 result.
     - Threshold: at least 30% relative drop [judgment], and no new invented facts.
     - Sample: the same 50 tickets, 3 runs each, 150 outputs.
     - Accept only when the mean of the 3 runs meets the threshold.

4. **Run a live probe with one agent team for 10 working days.**
   - Kind: stochastic. Domain: Complex, because we cannot predict how agents react. Its leverage is a guess.
   - Increment: one team sees the Step 3 prompt. The other teams keep the old one.
   - Blocker removed: no proof that the lab gain holds in live use.
   - Step 4 MUST NOT start until Step 2 has logged flags for 5 working days and Step 3 has passed.
   - Acceptance test, written first:
     - Metric: flags per 100 summaries.
     - Baseline: the Step 2 rate.
     - Threshold: at least 30% lower [judgment].
     - Sample: at least 200 summaries per group.
     - Stop condition: the flag rate exceeds baseline by 10 points after 100 summaries.
     - Budget: one team, 10 working days.

## Follow-up

**Conditions that change the recommendation**

- If A1 is false, add a step to capture ticket text before Step 1.
- If Step 1 shows an error rate below 5%, drop Steps 3 and 4 and keep the flag button.
- If Step 3 misses its threshold, test the larger-model alternative on the same 50 tickets.
