## Headline

Replace the style debate with a tool and a rule, because a team can accept a tool's output more easily than a colleague's taste.

- The friction comes from humans enforcing style in review, so move enforcement to an automatic check.
- One time-boxed decision on the tool ends the open argument.
- A measured trial shows whether the friction falls.

## Background

The team has no shared SQL (Structured Query Language) format. Each review repeats the argument. The request is to fix the cause, not only the symptom.

## Relevance

Every review that debates style delays the merge and strains trust. The cost repeats with each change.

## Information

**Evidence**

- Formatters such as SQLFluff check and fix SQL style by rule, and support named SQL dialects [1].
- Style debates in review are a people problem when the rule is a matter of taste. [judgment]
- A check that runs in CI (continuous integration, which runs checks on each change automatically) removes the human enforcer. [judgment]
- No review data was provided, so the size of the friction is unknown. See A2.

**Assumption log**

A1. The team writes one SQL dialect, in git, reviewed by pull request (a proposed change that peers review). Why not measured: the material does not state it. Validate by: list the dialects in the repository. If wrong: the formatter choice in Step 1 changes.

A2. Formatting comments are a large share of review friction. Why not measured: the material has no review data. Validate by: count formatting comments in the last 20 merged reviews. If wrong: Steps 2 and 3 fix only a minor cause, so search for other causes.

A3. The team accepts a style that a tool decides. Why not measured: the user has not answered. Validate by: the Step 1 session. If wrong: name one owner who decides the style.

**Alternative considered**

The alternative is a written style guide that reviewers enforce by hand. It loses because the debate stays in each review and reviewers spend time on it. [judgment]

## End

I recommend that we take these steps in order:

1. **Choose the formatter in one 30-minute session.**
   - Increment: score three candidates (for example SQLFluff, sql-formatter, pgFormatter) and pick one.
   - Blocker removed: no agreed decision exists.
   - Kind: evaluative. Cynefin domain: Complicated [2], because analysis of known options picks the practice.
   - Test, written first: score each criterion from 0 to 5 with evidence. The pass threshold is a weighted total of 70 of 100 or more. The winner must pass.

   | Criterion | Weight | Evidence needed |
   |---|---|---|
   | Supports our dialect | 30 | Dialect named in the tool's documentation |
   | Works with default settings | 25 | Run on 5 existing files, count the failures |
   | Runs in CI | 25 | Documented command with an exit code |
   | Fixes files automatically | 20 | Run the fix command, then a re-check passes |

2. **Commit the config and reformat all existing SQL in one commit.**
   - Increment: one config file and one commit that changes only format.
   - Blocker removed: old files cause noisy diffs.
   - Kind: deterministic. Cynefin domain: Clear, because automated formatting is a known best practice.
   - Step 2 MUST NOT start until Step 1 passes.
   - Test, written first [3]:

     Given the config file is in the repository
     When the formatter check runs on the whole repository
     Then it reports zero violations

3. **Add the format check to CI.**
   - Increment: one CI job that runs the check command.
   - Blocker removed: humans enforce style by hand.
   - Kind: deterministic. Cynefin domain: Clear, because the job is a standard CI step.
   - Step 3 MUST NOT start until the test in Step 2 passes.
   - Test, written first:

     Given a pull request with a badly formatted SQL file
     When CI runs
     Then the format job fails and names the file

4. **Run a 4-week probe on review friction. Start the baseline count now, in parallel with Steps 1 to 3.**
   - Increment: count formatting comments per review for the last 20 merged reviews, then for the next 20.
   - Capability added: evidence that the culture changed.
   - Kind: stochastic. Cynefin domain: Complex, because team behavior shows its effect only afterward. Any leverage claim is a guess.
   - Budget: 1 hour per week. Stop condition: stop at 4 weeks, or earlier if the share rises above the baseline for 10 reviews.
   - Test, written first: the metric is the share of review comments about format. The baseline is the count from the last 20 reviews. The pass threshold is a drop of at least half. The sample is 20 reviews after Step 3.

If A2 is false, replace Step 4 with a search for the real cause of the friction.
