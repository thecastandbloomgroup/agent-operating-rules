## Headline

The pool size cut from 50 to 8 caused the latency rise, so restore it within the database limit, and revert the cache TTL (time to live).

- Pool wait explains 687 ms of the 780 ms p95 increase (88%) [1][2].
- The cache TTL cut adds load but is a minor cause.
- The ORM change shows no cost in the traces.
- The database server is not the bottleneck.

## Background

p95 latency on `GET /customers/{id}/orders` rose from 120 ms to 900 ms after release 2026.10.21. The release cut the pool size, the pool acquire timeout, the cache TTL, and added `selectinload` to the order query. The logs, diff, and traces are attached.

## Relevance

The error rate is 0.40%, up from 0.02%. Of those errors, 96% are pool timeouts that return HTTP 503 after 5 s.

## Information

**Evidence**

- `db.pool.acquire` p95 rose from 3 ms to 690 ms. Total p95 rose from 120 ms to 900 ms (traces.txt, table) [1].
- Query spans did not change. `db.query orders` p95 is 52 ms before and 58 ms after. `db.query order_lines` p95 is 30 ms before and 26 ms after (traces.txt, table) [1].
- Load is equal: peak 410 requests per second before, 405 after (traces.txt) [1].
- The pool `max_size` fell from 50 to 8, and `acquire_timeout_s` fell from 30 to 5 (release.diff, db.yaml) [2].
- Active connections peaked at 31 before and 8 after. The 8-connection cap is below the earlier peak of 31 (traces.txt) [1].
- The logs show "8 of 8 connections in use" with 6 to 14 waiters on all four pods (logs.txt) [3].
- Pool exhaustion warnings: none on 2026-10-20, and 1,800 to 2,400 per hour on 2026-10-22 (logs.txt, note) [3].
- Database CPU peaked at 38% before and 41% after. The database has spare capacity (traces.txt) [1].
- The cache miss rate rose from 12% to 31% after the TTL fell from 300 s to 60 s. `cache.get` latency is unchanged (traces.txt, release.diff) [1][2]. This adds database load, but the effect is small next to pool wait. Confidence: high, based on three agreeing sources (traces, logs, diff).
- The `selectinload` change shows no cost. [inference] It may add a second query per request, which raises pool demand.

A2. The "8" in the connection metric is per pod, or the pool is shared. Why not measured: traces.txt does not state the metric scope. Validate by: query the metric per pod. If wrong: the size target in Step 2 changes.

**Alternative considered**

Roll back the whole release. It restores service fastest. It loses because the diff shows only the pool change as the main cause [1][2], and a rollback may break the OPS-412 limit [judgment].
