Connection acquisition wait time caused 687 ms of the 780 ms latency increase [logs.txt, traces.txt].

### Background

Release 2026.10.21 changed the connection pool size, the cache duration, and the order query loader [release.diff].
After deployment, API 95th percentile latency increased from 120 ms to 900 ms [traces.txt].
The engineering team requested an analysis of the logs, diffs, and traces to restore latency [query].

### Relevance

The API currently breaches latency service level targets and drops 0.40% of customer requests via timeouts [traces.txt].
Resolving pool starvation will immediately restore response times and prevent customer-facing HTTP 503 errors [traces.txt].

### Information

Traces show that `db.pool.acquire` latency rose from 3 ms to 690 ms at the 95th percentile [traces.txt].
This acquisition delay accounts for 88% of the total 780 ms latency regression [traces.txt].
During the same period, database server CPU rose by only 3% from 38% to 41% [traces.txt].
Individual database query times remained stable: order queries increased by 6 ms, while line queries improved by 4 ms [traces.txt].
Therefore, slow database execution did not cause the regression [traces.txt].

The regression stems from two interacting configuration changes [release.diff].
First, `default_ttl_s` dropped from 300 s to 60 s in `config/cache.yaml` [release.diff].
This reduction increased the cache miss rate by 19 percentage points, from 12% to 31% [traces.txt].
Second, `max_size` dropped from 50 to 8 connections per pod in `config/db.yaml` [release.diff].
Each pod runs 8 worker threads, so 8 connections allow zero buffer during traffic spikes [release.diff].
Because cache misses rose, concurrent database demand exceeded pool capacity and triggered queue timeouts [logs.txt].

A1. Ticket OPS-412 permits at least 16 connections per pod. Why not measured: The material does not state it. Validate by: Check ticket OPS-412 in the issue tracker. If wrong: Keep pool size at 8 and increase cache TTL to 600 s.

Strongest alternative: Roll back all three files in release 2026.10.21.
This alternative loses because the Object-Relational Mapping change reduced order line query latency from 30 ms to 26 ms [traces.txt].
