# Headline

Revert the connection pool reduction and the cache time-to-live drop to restore latency.
The connection acquisition delay accounts for 687 ms of the 780 ms increase in 95th percentile latency [1].
Cache misses increased from 12% to 31% because cache time-to-live dropped from 300 seconds to 60 seconds [1], [2].
Each application pod has eight worker threads that exhaust the eight-connection pool during cache misses [1], [3].

# Background

Last week release 2026.10.21 changed the object-relational mapping query, reduced cache time-to-live, and reduced database pool capacity [2].
After deployment, 95th percentile API latency increased from 120 ms to 900 ms, while error rate rose from 0.02% to 0.40% [1].
You requested instructions to resolve this performance degradation.

# Relevance

Database pool timeouts cause 503 errors and violate the service latency target for customers now [1], [3].
Immediate rollback of the configuration changes removes client errors without database instability [1].

# Information

In release 2026.10.21, `config/db.yaml` decreased `max_size` from 50 to 8 and `acquire_timeout_s` from 30 to 5 [2].
At the same time, `config/cache.yaml` lowered `default_ttl_s` from 300 to 60 [2].
Traces show total 95th percentile latency rose by 780 ms, from 120 ms to 900 ms [1].
The `db.pool.acquire` span explains 88% of this rise, climbing from 3 ms to 690 ms [1].
Database execution time did not drive the regression: `orders` query 95th percentile increased by only 6 ms, while `order_lines` query 95th percentile dropped by 4 ms [1].
Peak database CPU remained low, moving from 38% to 41% [1].
However, the cache miss rate rose by 158%, from 12% to 31%, because time-to-live dropped [1], [2].
Because misses increased, more requests hit the database [1].
Each pod runs eight worker threads [2].
When all eight threads request database connections simultaneously, the eight-connection pool becomes exhausted [2], [3].
Logs record 1,800 to 2,400 pool exhaustion events per hour and timeouts after five seconds [3].
Pool timeouts cause 96% of the 503 errors in Window B [1], [3].
OPS-412 mentions a new database connection limit per service [2].
Peak connections across all pods reached only 8 in Window B, while Window A used 31 [1].
Therefore, the database can accept at least 31 connections without CPU strain [1].

## Assumption log

Validate by: inspect ticket OPS-412 in the issue tracker. If wrong: pool size must be set to the OPS-412 cap divided by four pods, and cache time-to-live must rise to 600 seconds to compensate.

A2. Reverting cache time-to-live to 300 seconds does not violate data freshness constraints. Why not measured: The material does not state product freshness requirements. Validate by: check cache invalidation logic for customer orders. If wrong: keep time-to-live at 60 seconds and scale connection pools to absorb higher read traffic.

## Alternative considered

Increase the database connection acquire timeout from 5 seconds to 30 seconds without changing pool size.
This alternative loses because it masks starvation, keeps 95th percentile latency high, and fails to stop connection queuing.
