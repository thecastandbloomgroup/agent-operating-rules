# Headline

Build an evaluation harness to measure accuracy before changing model prompts or architectures.

- User feedback without metrics prevents targeted model engineering.
- An annotated sample establishes a quantitative baseline for summary quality.
- Targeted prompt constraints reduce factual errors found during review.

# Background

Your team integrated an LLM-based summariser into a support workflow without tracking performance data. Support agents report that the summaries contain factual errors at an unknown rate [judgment]. You requested a strategy to improve summariser accuracy.

# Relevance

Without quantitative baselines, prompt changes risk degrading summary quality further. Establishing measurement now directs engineering effort toward proven failure modes.

# Information

Support agents report that summaries are "sometimes wrong" [judgment]. Because no logging exists, the error rate and failure modes remain unmeasured [judgment]. LLM evaluation literature shows that grounded summary evaluations require reference datasets [1].

## Assumption log

A1. Support ticket conversation logs and their summaries are accessible for review. Why not measured: The material does not state it. Validate by: Query the support database for 50 paired records. If wrong: Build data export pipelines before doing summary evaluation.

A2. Factual inconsistency, rather than poor grammar, causes agent complaints. Why not measured: The user has not answered. Validate by: Categorise 30 agent feedback reports into error classes. If wrong: Reallocate prompt development from fact grounding to text formatting.

A3. Five minutes per ticket is acceptable for internal human evaluation. Why not measured: The material does not state it. Validate by: Time two agents grading five summaries each. If wrong: Reduce the evaluation sample size from 100 to 50 tickets.

## Alternative considered

The alternative is prompt modification using zero-shot few-shot examples without a baseline dataset. This alternative loses because you cannot verify if changes fix hallucinations or introduce regressions [judgment].

# End

I recommend that we:

1. Step 1: Collect a gold-standard dataset of 100 closed support conversations and write reference summaries.
   - Increment: Export 100 recent support tickets and create expert summaries in one session.
   - Capability added: Provides the ground-truth reference needed for model evaluation.
   - Cynefin domain: Complicated, because domain expertise is needed to write accurate summaries.
   - Evaluative rubric:
     - Criterion 1 (Weight 0.5): Factual consistency with ticket content. Score 1 to 5.
     - Criterion 2 (Weight 0.3): Key customer issue identified. Score 1 to 5.
     - Criterion 3 (Weight 0.2): Resolution step stated accurately. Score 1 to 5.
     - Pass threshold: Average weighted score >= 4.0 across 100 tickets.

2. Step 2: Implement an automated factual consistency check using an LLM-as-a-judge metric.
   - Dependency: Step 2 MUST NOT start until the dataset in Step 1 is ready.
   - Increment: Deploy an open-source evaluation script against the Step 1 dataset.
   - Capability added: Detects unsupported claims in generated summaries.
   - Cynefin domain: Complicated, because calibrating judge prompts requires statistical validation.
   - Stochastic acceptance test:
     - Metric: Agreement rate (Cohen's kappa) with human ratings.
     - Baseline: 0.0 (no automated test exists).
     - Pass threshold: Cohen's kappa >= 0.70 [judgment].
     - Sample size: 100 ticket summaries.

3. Step 3: Run a safe-to-fail prompt experiment with source-quote constraints.
   - Dependency: Step 3 MUST NOT start until the metric in Step 2 is operational.
   - Increment: Update the summariser system prompt to require extracting direct ticket citations before generating summary text.
   - Blocker removed: Stops the model from inventing non-existent support actions.
   - Cynefin domain: Complex, because prompt variations produce unpredictable shifts in summary conciseness and fidelity.
   - Stochastic acceptance test:
     - Metric: Hallucination rate measured by the automated judge from Step 2.
     - Baseline: Current prompt hallucination rate on the 100-ticket set.
     - Pass threshold: 30% relative reduction in hallucinated claims with sample budget capped at 100 tickets.
     - Sample size: 100 tickets.

4. Step 4: Add an agent feedback button inside the support interface to record binary satisfaction.
   - Increment: Insert thumbs-up and thumbs-down buttons with a comment box next to the summary UI.
   - Capability added: Creates continuous production monitoring.
   - Cynefin domain: Clear, because best practices for UI telemetry are known.
   - Deterministic test:
     Given an agent views a generated summary,
     When the agent clicks the thumbs-down button,
     Then the database stores the ticket identifier, summary text, and timestamp.
