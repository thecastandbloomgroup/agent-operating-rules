# Headline

Adopt one automated SQL formatter and enforce it in CI (continuous integration, the automated check on each pull request), because the friction is a tooling gap, not a culture flaw.

1. The debate survives because formatting stays a human decision in review, so remove the decision, not the people [judgment].
2. A formatter applies one deterministic style to every file, so no one's taste wins or loses [1].
3. Hooks and CI checks enforce the style before review, so reviewers stop policing whitespace [5].
4. Precedent exists: Go ended its style debates when its formatter shipped with the language [3].

# Background

The team disagrees on SQL formatting, and the dispute consumes time in every review. The request is to fix the culture. Recurring style argument in review is a symptom of missing automation, not a symptom of damaged trust [judgment].

# Relevance

Every review pays this tax now, and every new file raises the cost of a later cleanup. A tool-enforced standard ends the tax within one sprint.

# Information

**Evidence**

- sqlfmt ships near-zero configuration by design, so it removes the options that teams argue about [1].
- SQLFluff supports many dialects and both checks and fixes SQL, so it fits teams with mixed warehouses [2].
- Go's experience shows that a tool-enforced style ends debate even when nobody loves the style [3].
- A one-time reformat commit can be hidden from git blame, so history stays readable [4].
- Pre-commit hooks run the formatter locally before code reaches review [5].
- The current level of friction is unmeasured; the baseline must come from review data (see A4).

**Assumption log**

A1. The team uses git with a CI service. Why not measured: the material does not state it. Validate by: list the files in .github/workflows or the equivalent directory. If wrong: keep Steps 2 and 4, and enforce through editor plugins instead of CI.

A2. SQL lives in the repository as files in one main dialect. Why not measured: the material does not state it. Validate by: count files by extension, then run the tool's parser on the 20 largest. If wrong: the rubric in Step 1 picks the tool with the right dialect coverage.

A3. No formatter config or style guide exists in the repository today. Why not measured: the material does not state it. Validate by: search the repository for sqlfluff, sqlfmt, or style config files. If wrong: adopt the existing config and skip the choice in Step 1.

A4. The friction is visible as formatting comments in reviews. Why not measured: the material does not state it. Validate by: count formatting comments in the last 20 reviews. If wrong: Step 4 measures review cycle time instead.

**Alternative considered**

Write a house style guide and keep human enforcement. This loses because it keeps formatting a human decision, which is the source of the friction [judgment]. Go's experience indicates that guides alone do not end style debate; tools do [3].

# End

I recommend that we delete the style decision and enforce one formatter with tools, in four steps.

**Step 1. Choose the formatter with a weighted rubric.** Complicated domain, because analysis of the dialect and codebase selects the right option, and more than one good option exists.

- Increment: one session; one engineer scores two or three candidates with a Pugh matrix (a weighted scoring table) [6].
- Blocker removed: the "whose style wins" debate, because the rubric decides before taste enters.
- Rubric first. Dialect parses our SQL: 40 points, evidence is a clean parse of the 20 largest files. Deterministic output: 25 points, evidence is two runs with byte-identical results. Small config surface, 10 options or fewer: 15 points, evidence is the options count in the docs. Active maintenance: 10 points, evidence is a release in the last 6 months. Editor and CI integration: 10 points, evidence is official plugin docs.
- Pass threshold: the winner scores 80 of 100 or more and leads by 10 points.

**Step 2. Reformat the repository in one commit.** Clear domain, because a known best practice exists and the action is one step. Step 2 MUST NOT start until Step 1 passes.

- Increment: one session; run the formatter on every SQL file, then commit once.
- Blocker removed: mixed-style files that restart the debate on every edit.
- Test first, in Gherkin form (a Given, When, Then format):

Given the main branch and the formatter from Step 1
When the formatter runs over every SQL file two times
Then the second run shows no changes and the existing test suite still passes

- Add the reformat commit hash to .git-blame-ignore-revs so blame stays useful [4].

**Step 3. Enforce the format in pre-commit and CI.** Clear domain, because the practice is standard and the action is one step. Step 3 MUST NOT merge before Step 2, or every open pull request fails the new check.

- Increment: one session; add one pre-commit hook and one CI job [5].
- Blocker removed: the reviewer's role as style police, because the pipeline rejects unformatted SQL before review.
- Test first, in Gherkin form:

Given a pull request that contains one unformatted SQL file
When the CI job runs
Then the job fails and prints the file name and the fix command

Given a pull request that contains formatted SQL only
When the CI job runs
Then the job passes

**Step 4. Pilot the new review norm for 20 reviews.** Complex domain, because team behavior shows cause and effect only afterward, so this is a probe with a measure and a stop condition; its leverage is a guess. Run it in parallel with Steps 2 and 3.

- Norm: reviewers write no style comments on SQL. A style change request becomes a config pull request. Otherwise the tool decides.
- Increment: post the norm in the review guide; tally comments for 15 minutes per week.
- Blocker removed: social pressure to re-litigate style in review.
- Test first, stochastic form. Metric: formatting comments per SQL review. Baseline: the count from the last 20 reviews (A4). Pass threshold: a drop of 80 percent or more over the next 20 reviews. Sample size: 20 reviews.
- Stop condition and budget: if the drop is under 50 percent after 20 reviews, hold a 30-minute retro and adjust the config or the norm. Cap effort at 15 minutes per week.

# Follow-up

**Open questions**

1. Which CI service and which SQL dialect does the team use? The answer names the exact config file in Step 3 and the dialect flag in Step 1.
2. How many SQL files and how many reviews per week? The answer sizes Step 2 and sets how fast Step 4 reaches 20 reviews.

**Conditions that change the recommendation**

- If A2 fails and no tool parses the dialect, scope Step 2 to the files that parse and track the rest as manual exceptions.
- If A1 fails, enforce through editor plugins and local hooks instead of CI.
