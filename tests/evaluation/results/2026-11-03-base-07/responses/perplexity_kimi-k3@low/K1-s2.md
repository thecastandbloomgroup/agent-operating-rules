# Headline

Restore the connection pool size to 50 and the cache TTL to 300 seconds; the pool shrink in release 2026.10.21 causes the latency, not the ORM change. First, the trace shows pool.acquire p95 rose from 3 ms to 690 ms while query times stayed flat. Second, pool exhaustion warnings rose from zero per day to about 2,000 per hour after deploy. Third, database CPU stayed near 40 percent, so the database is not the bottleneck.

# Background

Release 2026.10.21 changed three things: pool max_size 50 to 8, acquire timeout 30 s to 5 s, and cache TTL 300 s to 60 s. It also added selectinload for order lines. API p95 latency rose from 120 ms to 900 ms, and error rate rose from 0.02% to 0.40%.

# Relevance

The 503 errors and 5-second timeouts hit customers now. Every hour of delay costs failed requests, so the fix should ship today.

# Information

Evidence:

- db.pool.acquire p95: 3 ms in window A, 690 ms in window B [1]. The gap explains 687 ms of the 780 ms p95 regression [judgment].
- Active DB connections peaked at 8 in window B, down from 31 in window A [1]. Demand is about 4 times the new cap of 32 pooled connections across 4 pods [1].
- Errors are 96% PoolTimeout [1]. This matches the 8-of-8-in-use warnings in the logs [2].
- Cache miss rate rose from 12% to 31% [1]. The TTL cut from 300 s to 60 s adds load to the small pool and makes it worse [2].
- Query spans stayed flat: orders p95 52 ms to 58 ms, order_lines 30 ms to 26 ms [1]. The selectinload change is not the cause.
- Database CPU peaked at 41% [1]. The database has headroom for 50 connections per pod unless OPS-412 says otherwise.

Confidence: high, because span data, logs, and config diff agree from two independent sources [1], [2].
