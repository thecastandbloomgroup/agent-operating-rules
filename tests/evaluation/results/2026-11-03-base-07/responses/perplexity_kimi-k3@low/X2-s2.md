# Headline

Retrospectives stall when actions lack owners, deadlines, and proof of completion [judgment].

- Add a written action log with one owner and one date per action [judgment].
- Open each meeting by checking last actions before new topics [judgment].
- Run a small experiment on one process per cycle, with a stop condition [1].
- The strongest alternative, replacing retro format alone, fails because format changes do not fix missing follow-through [judgment].

# Background

Your team holds retrospectives. People attend. No change follows. You want steps that convert talk into shifts in how the team works.

# Relevance

An unfixed retro loop costs meeting time with zero return. A two-week cycle produces roughly 25 retro hours per person per year. That time is recoverable.

# Information

Common failure causes, from agile literature and retrospectives practice [2][3]:

1. Actions have no owner. The task belongs to "the team", so nobody does it.
2. Actions are too large. "Improve communication" is not a task.
3. Actions are never reviewed. The next retro starts fresh.
4. Too many actions per cycle. Teams complete zero of five more often than one of one [judgment].
5. The same problem recurs. That signals the action treated the symptom, not the cause.

Assumption log:

A1. Your team follows a two-week cycle. Why not measured: the material does not state it. Validate by: ask the team lead. If wrong: adjust the cycle counts only. The steps do not change.

A2. The team has authority to change its own process. Why not measured: the material does not state it. Validate by: pick one action this cycle and see whether the team can do it without approval. If wrong: add a step that asks the manager for a defined mandate.

Alternative considered: switch the retro format (for example, start/stop/continue to sailboat). This loses because evidence in retrospectives practice points to follow-through, not format, as the cause [3]. A new format delays the same problem by one or two cycles [judgment].

# End

I recommend that we:

1. **Create a visible action log today.** One page. Columns: action, owner, date, status. This removes the "team owns it" blocker. Clear domain: a known practice applies. Test (deterministic):
   - Given the last retro's notes,
   - When the log is created,
   - Then each action has exactly one owner and one date, and the log is visible where the team works.
2. **Open the next retro with a 10-minute action review.** This closes the feedback loop. Depends on Step 1. Clear domain. Test (deterministic):
   - Given the action log from Step 1,
   - When the next retro starts,
   - Then the first agenda item is the status of each prior action, and incomplete actions get a vote: continue, change, or drop.
3. **Limit each retro to one action, sized for one cycle.** This removes overload. Depends on Step 1. Clear domain. Test (deterministic):
   - Given the issues raised in one retro,
   - When the team selects actions,
   - Then only one action enters the log, and it fits inside one cycle.
4. **Run one action as a probe with a stop condition.** Treat the chosen change as a test: metric, baseline, threshold, end date. Budget: one cycle. Complex domain: the effect of a process change is visible only afterward, so cap the exposure. Test (stochastic): pick the metric the action targets. Record the baseline this cycle. Accept the change only if the metric moves past the threshold after one cycle across all team members. Otherwise revert.

Step 2 and Step 3 MUST NOT start until Step 1 is complete.

# Follow-up

Conditions that change this recommendation:

- If the team lacks authority to change its process (A2 is false), add a Step 0: ask the manager for a written mandate that names two or three process areas the team controls.
- If attendance is passive and silent, that is a psychological safety problem, not a follow-through problem. The fix differs [2].
