# Headline

Revert the connection pool settings in `config/db.yaml`: `max_size` of 8 starves 32 workers, and that single change causes the latency regression.

- Traces show `db.pool.acquire` grew from p95 3 ms to 690 ms, which explains about 570 ms of the 780 ms p95 increase [1].
- 32 workers against 8 connections lets at most 25% of workers hold a connection; 75% queue [2].
- The smaller cache TTL (300 s to 60 s) raised the cache miss rate from 12% to 31%, so more requests hit the starved pool [1][2].
- The ORM eager load is not the cause: both database queries stayed fast (52 ms and 30 ms at p95 in Window A) [1].

## Background

After release 2026.10.21, p95 latency rose from 120 ms to 900 ms and the error rate rose from 0.02% to 0.40%. The release changed three things: pool config, cache TTL, and an ORM query.

## Relevance

The service now returns 503 errors on pool timeouts. Each PoolTimeout wastes 5 s of a worker before it fails [3].

## Information

**Evidence, ranked by contribution:**

1. Pool starvation, primary cause. `db.pool.acquire` p95 went 3 ms to 690 ms, a 229x rise [1]. Peak active connections fell from 31 to 8 [1]. Logs show "pool exhausted: 8 of 8" 1,800 to 2,400 times per hour, versus zero on 2026-10-20 [3]. The commit message cites a new DB connection limit (OPS-412), but the observed peak was 31, so the limit is not binding at 50 [2][1].
2. Cache TTL, amplifier. Miss rate rose 12% to 31% [1]. Each miss now contends for a scarce connection, so the effect multiplies [inference].
3. ORM `selectinload`, not a cause. `order_lines` query p95 fell 30 ms to 26 ms [1]. It holds each connection slightly longer, a minor amplifier [inference].
4. Ruled out: traffic (peak 410 to 405 req/s) and DB server load (38% to 41% CPU) stayed flat [1].

**Assumption log**

- A1. The OPS-412 limit permits at least 50 connections per service. Why not measured: the ticket is not in the material. Validate by: check OPS-412 or query `pg_stat_activity` for the limit. If wrong: set `max_size` to the real limit, keep step 2.
- A2. Database headroom absorbs a rise from 8 to 50 connections. Why not measured: only peak CPU is given (41%). Validate by: watch DB CPU for one hour after revert. If wrong: keep pool at 8 and add a query queue instead.

**Alternative considered**

Keep `max_size: 8` and reduce workers to match. It loses because it cuts throughput or forces a deployment redesign, and it is unnecessary if the OPS-412 limit is not binding (peak was 31) [1] [judgment].

## End

I recommend that we:

1. **Revert the pool settings** in `config/db.yaml` (`max_size: 50`, `acquire_timeout_s: 30`) and redeploy. This removes the largest blocker: acquire contention. Domain: Clear, because the diff shows the exact values that worked before and the fix restores them.
   - Given release 2026.10.21 config, When the revert deploys, Then `db.pool.acquire` p95 falls below 10 ms in traces.
2. **Confirm the OPS-412 limit** in parallel. If the limit is below 50, set `max_size` to that limit instead. This guards against the stated reason for the change. Domain: Complicated, because reading one ticket answers it.
   - Given ticket OPS-412, When we read the limit, Then `max_size` equals min(50, limit) in config.
3. **Restore cache TTL to 300 s** after step 1 passes, unless a data freshness rule requires 60 s. This removes the amplifier. Domain: Clear, because the earlier value worked.
   - Given TTL restored, When one hour passes, Then cache miss rate falls below 15% [1].
4. **Add a pool saturation alert** (waiters above 0 for 60 s). This prevents recurrence. Domain: Clear, because the metric and threshold come from the logs.
   - Given an injected pool constraint in staging, When waiters appear for 60 s, Then the alert fires.
5. **Keep the ORM eager load, but measure it**. It is a safe-to-fail probe. Domain: Complex, because its effect on connection hold time appears only after deployment. Stop condition: hold time p95 above 100 ms; budget: two hours of observation.
   - Metric: `db.connection.hold_time` p95. Baseline: Window A (acquire 3 ms implies short holds). Threshold: under 100 ms over 10,000 sampled requests. If breached, revert the eager load [1].

Step 3 MUST NOT start until the test in step 1 passes. Step 2 informs the final value of step 1 but does not block the revert deploy.

## Follow-up

Conditions that change this plan: if A1 is false, keep the limit from OPS-412 and skip step 4's threshold tune. If A2 is false, replace step 1 with a request queue in front of the pool.
