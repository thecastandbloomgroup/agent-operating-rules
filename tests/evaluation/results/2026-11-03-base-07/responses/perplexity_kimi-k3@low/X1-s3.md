# Headline

Measure the errors before changing anything, then fix the largest error class with tested, reversible probes.

- No baseline exists, so no prompt or model change can be shown to help or to harm.
- A short logging and coding step turns "sometimes wrong" into counted, ranked error classes.
- LLM output varies run to run, so each fix must pass a fixed 200-case test before release.
- A review label and a weekly error chart limit harm while fixes are proven.

# Background

The support tool drafts ticket summaries with a large language model (LLM). Agents report the output is "sometimes wrong". There are no logs, error counts, or acceptance checks.

# Relevance

Without a baseline, every change is a guess and regressions stay invisible. Therefore, two weeks of measurement turns a vague complaint into a ranked defect list.

# Information

**Evidence**

- No metrics exist, so the team cannot tell improvement from regression; measure first [judgment].
- LLM output is stochastic: the same input can give different text, so single examples cannot prove a fix [inference].
- A 200-case sample estimates a 10% error rate within ±4 percentage points at 95% confidence [inference].
- A 100-case sample gives ±6 points, so low volume still supports a baseline [inference].
- Zheng et al. report agreement above 80% between a strong LLM judge (a second model that grades text against the rubric) and human labels [1].
- That level supports machine scoring at scale, with a human audit on a 10% subsample [inference].
- Themes from 50 to 100 coded summaries define the error classes and the scoring guide (rubric) [2].
- Two or three classes are likely (66 to 100%) to account for most errors; basis: defect counts in support tools skew heavily [judgment].

**Assumption log**

A1. "Wrong" means factual errors or missing key facts in the summary, not speed or tone. Why not measured: the material does not state it. Validate by: read 50 flagged summaries in Step 1. If wrong: Step 2 adds classes; the harness still applies.

A2. Weekly volume is at least 200 summaries. Why not measured: the material does not state it. Validate by: one count query on tool logs. If wrong: shrink the eval set (a fixed sample of past summaries used only for testing) to 100 cases and accept ±6 points.

A3. Agents see each summary before it is used. Why not measured: the material does not state it. Validate by: one walkthrough of the agent screen. If wrong: Step 5 adds a review step before any probe ships.

A4. The model and provider stay fixed during the study. Why not measured: the user has not answered. Validate by: confirm at the next planning session. If wrong: re-run the Step 3 baseline after any model change.

**Alternative considered**

Replace the model first. This loses because no baseline exists to detect the gain, so the change buys cost without evidence [judgment].

# End

I recommend that we run five steps: instrument, classify, baseline, probe, and guard.

**Step 1: instrument the tool.**
- Increment: one session. Log every summary with ticket id and agent action (accept, edit, reject). Add a one-click error flag. Add the on-screen label "AI draft: check facts before use".
- Blocker removed: there is no data.
- Test (deterministic, written first):
Given a ticket with a generated summary
When the agent accepts, edits, rejects, or flags the summary
Then one log row stores the summary text, the action, and the ticket id.
- Domain: Confused, because the failure type is unknown and this step gathers the data that classifies the rest.

**Step 2: build the error rubric.**
- Increment: one workshop. Two coders code 50 flagged summaries by theme. Output: 3 to 5 error classes with definitions and one example each.
- Blocker removed: "wrong" has no shared definition.
- Test (evaluative, rubric written first). Criteria: the error classes. Weights: wrong action or invented fact = 3, missing key fact = 2, wording = 1. Pass threshold for one summary: no weight-3 error, and weighted total at most 2. Evidence: the source ticket text. Gate: two coders label the same 20 summaries; agreement must reach 80% before wider use [2].
- Domain: Complicated, because the classes are knowable by analysis of a fixed sample.
- Dependency: Step 2 starts when Step 1 yields 50 flags; if flags run short, coders sample random summaries.

**Step 3: measure the baseline.**
- Increment: one session. Score a frozen eval set of 200 past summaries against the rubric. Use an LLM judge for scale after the gate passes.
- Blocker removed: there is no baseline.
- Test (evaluative, written first). Judge gate: at least 80% agreement with human labels on 30 cases, before the judge scores the rest [1].
- Output: per-class error rate with 95% intervals.
- Domain: Complicated, because scoring against a fixed rubric is analysis with a known method.
- Dependency: Step 3 MUST NOT start until the Step 2 coder gate passes.

**Step 4: probe the top error class.**
- Increment: one prompt or context change per probe. Each probe runs on the 200 frozen cases in one session.
- Blocker removed: the top error class has no proven fix.
- Acceptance test (stochastic, written first). Metric: top-class error count on the eval set. Baseline: the Step 3 count. Threshold: the count falls to 70% of baseline or less. Fixes outnumber new errors at least 2 to 1. No other class rises more than 2 points. Sample: all 200 cases. A human audits every relabeled case.
- Domain: Complex, because a prompt change shows its effect only after the run. Budget: three probe rounds. Stop rule: stop when the threshold passes or the budget ends; on failure, escalate to a model change.
- Dependency: probes start after Step 3; a variant ships only when the threshold passes.

**Step 5: add the weekly monitor.**
- Increment: one session. Build a weekly chart of per-class error rates. Alert level: the baseline rate plus 4 points, the width of the 95% interval at n=200 [inference].
- Blocker removed: regressions stay invisible after release.
- Test (deterministic, written first):
Given the weekly log data
When the weekly job runs
Then the chart shows each class rate and raises an alert above the baseline plus 4 points.
- Domain: Clear, because a known best practice (dashboard plus alert) applies.
- Run Step 5 in parallel with Step 4; both wait on Step 3.

# Follow-up

- Open questions: none. Assumptions A1 to A4 carry the unknowns, and each lists its cheapest check.
- Conditions that change the plan: if A2 fails, shrink the eval set to 100 cases. If three probes fail, re-baseline and test a different model through the same harness.
