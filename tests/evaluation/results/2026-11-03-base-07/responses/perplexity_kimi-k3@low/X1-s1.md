## Headline

Measure the errors first, then fix the largest type with one bounded experiment.

- No metric exists today, so no change can be shown to help.
- A set of 100 labelled ticket-summary pairs, sorted into four error types, makes "sometimes wrong" countable.
- One capped prompt experiment then targets the top error type.
- A regression gate on every later change keeps the gains.

## Background

The support tool uses a large language model (LLM) to summarise tickets for agents. Agents report the summaries are "sometimes wrong". No metric, baseline, or error definition exists yet.

## Relevance

Unverified summaries can produce wrong replies to customers. Without a baseline (the error rate before any change), each prompt edit is a guess no one can verify.

## Information

**Evidence**

- The material holds one quality theme: "sometimes wrong", from an unstated number of agents [no source].
- A single-source theme still matters, because it is the only reported defect signal.
- No baseline exists, per the request.
- The plan uses a rubric, that is, a fixed scoring rule with criteria.
- Cohen's kappa, a statistic for labeller agreement, checks that the rubric is applied the same way by both labellers [1].
- A pass bar of 0.7 for kappa is a judgement [judgment].
- A set of 100 labelled pairs bounds a 10% error rate within about ±6 points at 95% confidence [inference].
- An LLM judge (an LLM that scores summaries) can score at scale [2].
- However, it must match human labels on a 30-pair subset first, or its scores do not count [2].
- Prompt edits are the cheapest first fix, because they need no new data or systems [judgment].
- Confidence: high for the measurement steps, because they use standard practice; the Step 4 gain is a guess until the probe runs [4].

**Assumptions**

- A1. Summaries go to agents, not directly to customers. Why not measured: the request does not say. Validate by: watch one agent close one ticket. If wrong: add Step 0 that requires agent approval before any customer send.
- A2. Two agents can each spare about two hours to label pairs (100 pairs, about one minute per pair). Why not measured: the request does not state staffing. Validate by: confirm with the team lead before Step 1. If wrong: cut the set to 60 pairs; the interval widens to about ±8 points [inference].
- A3. The summariser is a prompt plus a hosted model, so prompt edits are cheap and reversible. Why not measured: the request does not describe the stack. Validate by: open the summariser config once. If wrong: replace the Step 4 probe with a retrieval or fine-tune probe at higher cost.
- A4. Ticket text can be logged under the current privacy policy. Why not measured: the request does not state the policy. Validate by: read the policy once. If wrong: label and log only anonymised tickets.

**Alternative considered**

Tune the prompt now from agent anecdotes and skip measurement. It loses because no baseline exists, so no edit can be verified and regressions stay invisible [judgment].

## End

I recommend that we run these five steps in order.

1. **Build the labelled test set** (evaluative; Complicated, because agreement between labellers is knowable and the rubric fixes the practice).
   - Test first: two labellers apply the rubric to 100 recent ticket-summary pairs.
   - The rubric defines four types with one example each.
   - They are hallucination (a fact not in the ticket), omission (a needed fact missing), wrong fact (a ticket fact misstated), and format (the agreed structure broken).
   - Pass: 100 labelled pairs, and kappa at or above 0.7 [1].
   - Increment: one session for two agents.
   - Blocker removed: "sometimes wrong" is not countable today.

2. **Log every outcome** (deterministic; Clear, because event logging is a known best practice).
   - Test first (Gherkin, a plain-language test format [3]):
     - Given a summariser run finishes,
     - When the agent clicks a state,
     - Then the log stores the ticket text, the summary, the model, the prompt version, and the click.
   - Increment: add one log record per summary and one button with three states: accept, edit, reject.
   - Blocker removed: no summary data accrues for later tests.
   - Dependency: none; run it in the same session as Step 1.

3. **Measure the baseline** (stochastic; Complicated, because the method to score comes from the Step 1 analysis).
   - Test first: metric is the error rate per type; sample size is 100 pairs.
   - The scorer is the LLM judge, calibrated to at least 80% agreement with human labels on a 30-pair subset [2] [judgment].
   - Pass: a baseline report lists an error rate per type.
   - Increment: run the scorer once; one session.
   - Blocker removed: no number exists to beat.
   - Dependency: Step 3 MUST NOT start until the test in Step 1 passes.

4. **Probe one prompt fix for the top error type** (stochastic; Complex, because prompt effects show only after a run [4]).
   - Run it as a safe-to-fail probe, that is, a small trial with a budget and a stop condition.
   - Test first: metric is the top-type error rate; baseline is the Step 3 rate; sample is 100 pairs with the judge plus 20% human spot checks.
   - Pass: the top-type rate falls at least 30% relative, and no other type rises more than 2 points.
   - Increment: write one prompt variant for the top type; budget one session and two variants.
   - For omission, require the summary to list open questions and promised actions.
   - For hallucination, require a quoted ticket line for each claim.
   - Stop after two failed variants and reassess.
   - Blocker removed: the largest measured error source.
   - Dependency: Step 4 MUST NOT start until the Step 3 test passes.

5. **Add a regression gate** (deterministic; Clear, because a gate on changes is standard practice).
   - Test first (Gherkin [3]):
     - Given a prompt or model change is proposed,
     - When the 100-pair test runs,
     - Then the deploy stops if the total error rate rises more than 2 points over the stored baseline.
   - Increment: add one script to the deploy flow; one session.
   - Blocker removed: silent regressions after later edits.
   - Dependency: Step 5 uses the Step 3 baseline, so it starts after Step 3 passes.

Steps 1 to 3 run first because they remove the largest blocker: nothing is measured. The Complex probe follows Step 3 because the baseline cuts its uncertainty. If A1 is false, insert Step 0 before all steps: require agent approval before any summary reaches a customer.
