## Headline

Measure the failures first, fix the worst one, then add guardrails: that order turns a flaky build into a tracked, shrinking problem.

- First, Step 1 collects 30 days of continuous integration (CI) results, because a fix without data aims at the wrong target.
- Next, Steps 2 to 4 reproduce and fix the top offender, targeting the causes behind 77% of fixed flakes in one study [1].
- Last, Step 5 adds quarantine and reporting, so new flakes stay visible instead of hidden.

## Background

The request states that the build is flaky. Here, flaky means the same code passes sometimes and fails sometimes, with no code change between runs. The request names no pipeline, test suite, or failure rate, so this plan assumes a standard CI setup (see A1 to A3).

## Relevance

Flaky builds teach a team to ignore red results, so real defects pass review. Even Google reports that almost 16% of its tests show flakiness, which makes this a common, measurable problem [2].

## Information

**Evidence**

- Root causes: a study of 201 fixed flaky tests in Apache projects ranks async wait first at 45%. Async wait means a test sleeps, then checks a result too early. Concurrency follows at 20%, and test order dependency at 12% [1].
- Scale: Google reports almost 16% of its tests show some flakiness, and it detects flakes by re-runs, not by closing them silently [2].
- Baseline: a stable test fails 0% of runs on one commit, so any repeat failure on identical code marks a flake [judgment].
- Confidence in this plan: high, two independent sources agree on the same top causes and on detection by re-runs.

**Assumption log**

A1. "The build" means a CI pipeline with automated tests. Why not measured: the material does not state it. Validate by: open the CI dashboard and list the jobs. If wrong: apply Steps 1 to 3 to build steps such as dependency downloads.

A2. Flaky means intermittent on the same commit. Why not measured: the material does not state it. Validate by: re-run one green commit twice. If wrong: if failures repeat identically, treat this as a broken build and skip to a direct fix.

A3. CI logs for the last 30 days exist. Why not measured: no tool can reach the CI system from here. Validate by: open the job history. If wrong: enable result retention, then start Step 1 after 7 days of data.

**Alternative considered**

Alternative: add retry-until-pass to every job now. It loses because retries hide the root cause and multiply CI minutes per failure, so the flake count keeps growing [judgment]. Google uses re-runs to detect flakes, not to close them [2].

## End

I recommend that we:

1. **Export the last 30 days of CI results and group failures by test name and error message.** This removes the blocker: no one can say which test fails most. Kind: deterministic. Domain: Confused, because the current data cannot classify the fault, so this step gathers what classification needs. Write this test first:

   Given the CI results for the last 30 days
   When the report groups failures by test name and error message
   Then it lists each failing test with a failure count and a failure rate in percent

2. **Score the failing tests with the rubric below and pick the first fix target.** This adds the capability: a defensible priority. Kind: evaluative, scored with a Kepner-Tregoe layout. Domain: Complicated, because analysis of the Step 1 data picks the practice. Step 2 MUST NOT start until the test in Step 1 passes.

   | Criterion | Weight | Evidence needed |
   |---|---|---|
   | Failure rate from Step 1 | 50% | Step 1 report |
   | Pipelines blocked per week | 30% | CI job graph |
   | Fix effort, scored in reverse (1 = one line, 5 = redesign) | 20% | Read of the test code |

   Pass threshold: the highest weighted score wins, and ties split by failure rate.

3. **Reproduce the chosen test on one commit: run it 100 times.** This is a capped probe, not a full commitment. Kind: stochastic. Metric: failures per 100 runs. Baseline: 0% for a stable test. Pass threshold: at least 3 failures, which confirms the flake. Budget: stop after 2 hours or 100 runs, whichever comes first. Domain: Complex, because timing faults reveal cause only after the probe, so leverage here is a guess.

4. **Fix the confirmed root cause in the one chosen test: replace fixed sleeps with condition waits, or isolate shared state.** This removes the blocker: the top source of red builds. Kind: deterministic. Domain: Complicated, because the Step 3 evidence selects which known practice applies. Step 4 MUST NOT start until Step 3 confirms the flake. Write this test first:

   Given the fixed test on one commit
   When it runs 100 times in CI
   Then the failure rate is 0% and total suite time grows by less than 2%

5. **Add two guardrails: a quarantine rule and a weekly flake report.** Quarantine means the test still runs but does not block the build. This adds the capability: new flakes get caught within a week. Kind: deterministic. Domain: Clear, because quarantine plus reporting is an accepted best practice [2]. Step 5 MAY run in parallel with Steps 3 and 4. Write this test first:

   Given a test fails at least 2 of 10 runs on one commit
   When the pipeline finishes
   Then the test moves to quarantine and the weekly report lists it
