## Headline

Build an evaluation set first, then improve the summariser against measured scores.

1. "Sometimes wrong" is not actionable; a labelled sample of summaries turns it into error rates by type.
2. The first action is instrumentation and a golden dataset, not prompt changes.
3. Prompt and guardrail fixes follow, each gated by a measured pass threshold.
4. This works because summariser quality is a stochastic judgment, so rubric-scored sampling is the correct test.

## Background

A support tool now includes an LLM summariser. Agents report it is "sometimes wrong", and there are no metrics, no labelled examples, and no way to tell if a change helps or harms.

## Relevance

Without a baseline, any prompt change risks trading one failure type for another. A small evaluation set converts vague complaints into a regression test for every future change.

## Information

**Evidence**

- Summary errors in support tools cluster into omission of resolution steps, wrong entity or ticket state, and hallucinated facts [judgment].
- LLM output varies per run, so a single example cannot validate a fix [judgment].
- Faithfulness errors of 2 to 10% are typical for summarisation without grounding checks [no source], treat as a planning prior.

**Assumption log**

A1. Each summary links to a source conversation. Why not measured: the material does not state it. Validate by: inspect 20 summaries. If wrong: add source capture first.

A2. ~50 conversations per week can be reviewed by an agent lead. Why not measured: no staffing data. Validate by: confirm with the team lead. If wrong: cut sample size and extend the build window.

**Alternative considered**

Replace the LLM summariser with extractive snippets. It loses because it cannot produce a coherent case narrative, and no evidence says extraction beats corrected generation for this use case [judgment].

## End

I recommend that we run these five steps in order.

1. **Instrument and enable feedback.** Add a thumbs-up/down plus one-line comment control on each summary, and log prompt, source text, and summary. Blocker removed: no data on what "wrong" means. Cynefin: Confused, this classifies the problem.

   Given an agent views a summary in the tool
   When the agent selects thumbs-down and enters a comment
   Then the rating, comment, source text, and summary are stored with a shared identifier

2. **Build a 100-item golden set (depends on Step 1 passing for one week).** Sample 100 conversations; an agent lead labels each summary "correct" or assigns an error type (omission, entity error, hallucination, style). Blocker removed: no baseline. Cynefin: Complex, behaviour is visible only after trials, so cap budget at two working sessions.

   Rubric (weights): factuality 50%, completeness of resolution 30%, correct entities 20%. Pass threshold: 90% correct overall. Evidence per criterion: the labelled conversation it applies to.

3. **Classify errors and fix the dominant type with prompt and grounding changes.** Example fixes: quote the resolution step, list ticket state verbatim, ban unsupported claims. Cynefin: Complicated, cause is knowable from the error classes in Step 2. Step 3 MUST NOT start until Step 2 reaches 100 labelled items.

   Test (stochastic): metric = rubric score from Step 2; baseline = Step 2 result; pass threshold = greater than or equal to 90% correct; sample size = 100 items, scored by double review on 20%.

4. **Add an automatic faithfulness check before display.** Flag summaries stating facts absent from the source; show flagged ones with a warning. Cynefin: Complicated, the rule (supported versus unsupported) is deducible.

   Given a summary containing a claim absent from the source conversation
   When the check runs before display
   Then the summary is flagged and the agent sees a verification warning

5. **Set a gate and weekly regression run.** Every prompt change runs the golden set; ship only on threshold pass. Cynefin: Clear, this is a known regression-test practice.

   Given a proposed prompt change
   When the golden set is re-scored
   Then the change ships only if the score meets the 90% threshold

If A1 is false, insert a step to record source conversations with each summary before Step 1.

## Follow-up

**Open questions** (at most three):

1. Does each summary link to its full source conversation? The answer decides whether Step 3 can ground claims in verifiable text.
2. How many distinct support topics exist? The answer sets how the golden set is stratified.
3. Can an agent lead review about 10 conversations per day? The answer sets the Step 2 timeline.

**Condition that changes the recommendation**: if Step 2 shows hallucination under 5% and omission over 15%, replace the prompt emphasis in Step 3 from faithfulness to completeness.
