## Background

A support tool now uses an LLM to summarise tickets. Agents report occasional errors, and there is no measurement. The request is to improve accuracy.

## Relevance

Every change without a baseline is unverifiable, so the first investment is measurement, not a new prompt model swap [judgment].

## Information

Error taxonomy for LLM summaries, per the literature, falls into four disjoint classes: fabrication, omission, contradiction of source, and instruction failure [no source]. A sample of 200 summaries, scored by agents, gives a per-class error rate with roughly ±7% margin at 95% confidence [judgment]. Typical reported fabrication rates for single-pass LLM summaries range 3 to 20% depending on task [no source]; treat as uncertain until measured.

Assumptions:

A1. Agent feedback of "wrong" covers all four error classes. Why not measured: no rubric exists yet. Validate by: run the 200-sample labeling. If wrong: taxonomy gains a class, rubric expands.
A2. The summariser sees the full ticket text. Why not measured: no tool access to the system. Validate by: inspect one prompt payload. If wrong: truncation becomes the top fix.
A3. Agents can label 200 summaries within one week. Why not measured: the user has not answered. Validate by: ask the support lead. If wrong: cut sample to 100, wider confidence interval accepted.

Alternative considered: swap to a newer model immediately. It loses because nothing proves the model is the failure point, and there is no test to show improvement [judgment].

## End

I recommend that we:

1. **Build the labeling harness.** Write a four-class rubric (accuracy 40%, completeness 30%, faithfulness 20%, instruction compliance 10%; pass: total error rate ≤10%). Collect 200 recent summaries with agent labels. Kind: evaluative. Cynefin: Confused, because the error mix is unknown and this step classifies everything else.
2. **Classify the errors.** Score the sample with the rubric. Blocker removed: unknown error mix. Test: each class reported with count and confidence interval. Kind: evaluative. Cynefin: Complicated, deduction from labeled data. Step 2 MUST NOT start until 200 labels exist.
3. **Add an automated faithfulness check.** Run a secondary LLM judge that compares summary claims against ticket text; test: Given a fabricated claim, when the judge runs, then it flags it; target ≥85% agreement with human labels on 50 cases. Kind: stochastic. Cynefin: Complex probe, induction from trial agreement; the pattern breaks if tickets change domain. Budget: half a session.
4. **Fix the top error class.** Fabrication first: constrain the prompt to quote ticket sentences, then cite them. Acceptance test: fabrication rate ≤2% on 100 new summaries, baseline from Step 2, met for two consecutive runs. Kind: stochastic. Cynefin: Complicated once the class is known. Step 4 MUST NOT start until Step 2 passes.
5. **Measure continuously.** Log judge scores and agent thumbs-down per summary. Test: dashboard updates per ticket. Kind: deterministic. Cynefin: Clear, best practice exists.

Run Steps 3 and 4 in parallel after Step 2, each within its budget. If A2 fails, insert a truncation fix as the new Step 4.
