### What to measure

Use these definitions consistently across the current version and each candidate. These are proposed measures, not observed results. [judgment]

| Measure | Definition | Purpose |
|---|---|---|
| Material error rate | Percentage of summaries containing a false statement or omission that changes an agent’s next action | Main quality measure |
| Critical error count | Number of summaries exposing another customer’s data or inventing a completed consequential action | Safety gate |
| Unsupported claim rate | Percentage of summaries containing any claim without support in the ticket | Detect invented facts |
| Review time | Median seconds agents need to verify and correct a summary | Check practical benefit |

Treat a wrong refund status as a material error. Treat an invented completed refund as a critical error. [judgment]

Record the model version, prompt version, input truncation, and source ticket for every test output. These records help separate input defects from model defects. [judgment]

### 3. Run one bounded, offline comparison

**Kind:** Stochastic, meaning results can vary between runs.

**Acceptance test first:**

- **Sample:** Run the current version and one candidate three times on each benchmark ticket: 300 summaries per version.
- **Baseline:** Measure the current version before changing it.
- **Quality threshold:** Require at least a 50% relative reduction in material error rate on the random-ticket subset.
- **Zero-baseline rule:** If that subset has no baseline material errors, require no new material errors.
- **Safety threshold:** Require zero critical errors across all candidate outputs.
- **Effort threshold:** Require median agent review time no higher than the baseline.

These are initial decision thresholds, not established product requirements. [judgment]

**Work:** First inspect baseline failures. Then change only the largest supported cause. [judgment]

For example, restore missing ticket content when truncation causes omissions. Require source passages when outputs contain unsupported claims. Do not change the prompt and model together. [judgment]

Have reviewers assess outputs without seeing which version produced them. Record material errors, critical errors, unsupported claims, and review time.

**Capability:** Identify whether one specific change improves measured quality. [judgment]

**Domain:** Complex, through induction from trials; new ticket types can break the observed pattern.

**Budget:** One candidate and 600 total outputs, with no live automatic actions. Stop on a critical error or an exhausted budget.

Step 3 MUST NOT start until Step 2 passes. Accept the candidate only after all thresholds pass; otherwise retain the current version behind the safeguard.
