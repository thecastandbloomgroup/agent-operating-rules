## Headline

Measure the summariser first, then change it, because no one can improve an error rate that no one has counted.

- Agents report "sometimes wrong", but the error types and the error rate are unknown.
- A labelled sample and an agent feedback button create the first metrics within days.
- A fixed test set lets every later change be scored against a baseline.
- Prompt changes (the instructions sent to the LLM) are experiments, so run them as small, capped probes.

## Background

Your support tool uses a large language model (LLM) to summarise tickets. Agents say the summaries are "sometimes wrong". You have no metrics, and you ask for a better summariser.

## Relevance

Without a baseline, each change is a guess. A wrong summary can also send an agent to give a customer the wrong answer.

## Information

**Evidence**

- The only evidence now is agent opinion: "sometimes wrong". It has no count, no category, and no source. [judgment]
- Reply-quality studies show agreement between reviewers must be checked. A kappa score (agreement beyond chance) of 0.61 to 0.80 counts as substantial agreement [1].
- A sample of 100 summaries gives a 95% confidence interval of about plus or minus 10 points at worst case (1.96 x sqrt(0.25/100) = 0.098). This is a calculation, not a source.
- Cynefin is a framework that sorts work by how cause and effect relate [2]. The cause of the errors is not yet known, so the first step is Confused: gather data to classify.

**Assumption log**

A1. Agents can see the original ticket next to the summary. Why not measured: the material does not state it. Validate by: open one ticket in the tool. If wrong: add the ticket link to Step 2.

A2. The tool stores ticket text and summaries for at least 100 recent tickets. Why not measured: no tool can reach your data. Validate by: query the database for the last 30 days. If wrong: log new summaries for one week before Step 1.

A3. Two agents can give 2 hours each for labelling. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: cut the sample to 60 and accept a wider interval (about plus or minus 13 points).

A4. You can change the prompt and the model setting. Why not measured: the material does not state it. Validate by: check who owns the integration. If wrong: Step 4 becomes a request to the vendor.

**Alternative considered**

Switch to a larger model now. It loses because the error type is unknown. A larger model costs more and may not fix omissions or wrong ticket data. [judgment]

## End

I recommend that we take these four steps in order.

1. **Label a sample of 100 recent summaries.**
   - Increment: two agents label 100 random summaries in one session each.
   - Blocker removed: no one knows the error types or rate.
   - Kind: evaluative. Cynefin: Confused. The first action must gather data to classify the problem. Reason: acting on the opinion "sometimes wrong" is a guess.
   - Test, written first. The rubric has three criteria:
     - Factual accuracy, weight 50.
     - Missing key facts, weight 30.
     - Wrong customer status or next step, weight 20.
   - Each criterion needs the ticket text and the summary as evidence. The pass threshold is a kappa of at least 0.61 between the two labellers. Below that, rewrite the criteria and relabel 20 summaries.
   - Output: an error rate and a count per error type.

2. **Add a "wrong summary" button with a reason list.**
   - Increment: one button and four reasons (wrong fact, missing fact, wrong status, other), stored with the ticket ID.
   - Blocker removed: no ongoing metric exists.
   - Kind: deterministic. Cynefin: Clear. Reason: a known pattern applies, so deduction from a rule is enough.
   - Test, written first:

   ```gherkin
   Given an agent views a ticket with a summary
   When the agent presses "wrong summary" and selects "missing fact"
   Then the tool stores the ticket ID, summary ID, reason, and time
   ```

   Step 2 MAY run in parallel with Step 1.

3. **Build a fixed test set and a baseline score.**
   - Increment: take 50 of the labelled tickets from Step 1 and write a correct summary for each.
   - Blocker removed: no way to compare one change with another.
   - Kind: stochastic, because LLM output varies by run. Cynefin: Complicated. Reason: expert analysis picks the metric, so use deduction.
   - Test, written first: the metric is the share of summaries with no factual error, judged by the Step 1 rubric. The baseline is the Step 1 rate. Run each ticket 3 times to show run-to-run spread. Record the baseline as the pass bar for Step 4.

4. **Probe two prompt changes against the test set.**
   - Increment: change one instruction per probe. Probe A: "use only facts in the ticket". Probe B: "list the customer status and next step in fixed fields".
   - Blocker removed: the cause of the errors.
   - Kind: stochastic. Cynefin: Complex. Reason: induction from trials, because the effect of a prompt change is visible only after a run. The pattern could break on ticket types the test set lacks. Leverage is a guess.
   - Test, written first:
     - Metric: share of summaries with no factual error.
     - Baseline: the Step 3 score.
     - Pass threshold: at least 10 points above baseline.
     - Sample size: 50 tickets x 3 runs.
   - Budget: 1 working day per probe. Stop a probe if it scores below baseline.
   - Step 4 MUST NOT start until Step 3 records a baseline.
   - Ship a probe only after it passes. Then watch the Step 2 button rate for two weeks.

## Follow-up

Open questions: none. A1 to A4 carry the unknowns.

Conditions that change the recommendation:
- If Step 1 shows an error rate under 5%, stop at Step 2 and monitor.
- If most errors are in one ticket type, make that type the first probe in Step 4.
- If A4 is false, replace Step 4 with a vendor request that includes the Step 3 test set.
