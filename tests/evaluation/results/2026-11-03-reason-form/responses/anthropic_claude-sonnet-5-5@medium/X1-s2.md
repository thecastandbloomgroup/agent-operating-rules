## Headline

Measure the errors first, then change the summariser against a fixed test set.

- No metric exists, so "better" has no definition yet.
- Agent feedback and a labeled sample will show which errors occur and how often.
- A small, scored test set lets each prompt change be accepted or rejected on data.
- Each change ships only if it beats the baseline at a stated sample size.

## Background

The support tool uses a large language model (LLM) to summarise tickets. Per the query, agents report that summaries are "sometimes wrong". The team has no metrics and no definition of "wrong".

## Relevance

An agent who reads a wrong summary can give a wrong answer to a customer. Without a baseline, any change is a guess, and the team cannot tell if it helped.

## Information

Evidence:

- Agents report errors, but no count, rate, or error type exists (per the query). Confidence in any cause is low, since no data exists.
- Summary errors usually fall into a few kinds, for example invented facts, missed facts, and wrong customer intent [judgment].

The work splits into three parts that do not overlap: define the error, measure the error, and reduce the error. The plan follows that order.

Assumption log:

A1. The tool stores the original ticket and the summary text. Why not measured: the material does not state it. Validate by: query ten recent tickets. If wrong: add storage first (new Step 0).

A2. Agents can label 50 summaries in one working session. Why not measured: the user has not answered. Validate by: ask two agents to label five summaries and time them. If wrong: cut the sample to 25.

A3. A 100-ticket test set is enough to detect a large change. Why not measured: measuring costs more than the decision is worth. Validate by: check the confidence interval after Step 3. If wrong: raise the sample size.

Alternative considered: switch to a larger model now. It loses because the error type is unknown. A larger model costs more and may not fix the main error [judgment].

## End

I recommend that we do these steps in order:

1. **Classify the errors from a sample (Confused).**
   - Increment: two agents label 50 recent summaries as correct, or wrong with an error type.
   - Blocker removed: no one knows what "wrong" means.
   - Kind: evaluative. Test first: the rubric has two criteria. Label completeness has weight 50%. Agreement between agents has weight 50%. Pass is 90% of summaries labeled and 70% agreement, with the labeled sheet as evidence [judgment].
   - Domain reason: the domain is unclear, so this step gathers data to classify the rest.
   - Step 3 MUST NOT start until this rubric passes.

2. **Log agent feedback in the tool (Clear).**
   - Increment: add a "correct / wrong" button and an error-type choice beside each summary.
   - Blocker removed: no ongoing metric exists.
   - Kind: deterministic. Test first:
     - Given an agent views a summary
     - When the agent presses "wrong" and picks "invented fact"
     - Then the system stores the ticket ID, summary ID, and error type
   - Domain reason: a known best practice applies, by deduction from a known rule.

3. **Build the test set and baseline (Complicated).**
   - Increment: take 100 labeled tickets, with reference summaries, and score the current summariser.
   - Blocker removed: no baseline exists.
   - Kind: stochastic. Test first: metric is the share of summaries with a severe error. Baseline is the Step 3 result. Pass threshold is a drop of at least 50% relative to baseline. Sample size is 100 tickets, and 3 runs per ticket [judgment].
   - Domain reason: expert analysis of the Step 1 themes picks the scoring method, by deduction from the labeled data.
   - Step 4 MUST NOT start until the baseline exists.

4. **Probe one prompt change aimed at the top error type (Complex).**
   - Increment: change the prompt, for example "use only facts in the ticket", and score it on the test set.
   - Blocker removed: the top error type.
   - Kind: stochastic. Test first: same metric, baseline, and threshold as Step 3. Stop after 3 prompt variants or one working session each. Leverage is a guess, since the effect shows only after the run.
   - Domain reason: induction from trials. The pattern could break if the test set differs from live tickets. Compare the Step 2 live feedback rate with the test result.
   - Ship only if the threshold is met at 100 tickets.

If A1 is false, add a storage step before Step 1. If Step 1 shows most errors come from missing ticket data, replace Step 4 with a fix to the input pipeline.
