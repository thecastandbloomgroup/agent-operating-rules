## Headline

Measure the summariser first, then fix the error types that the data shows.

- No metric exists, so no change can be called an improvement today.

- A labeled sample of 100 summaries gives a baseline within about 8 points.

## Background

The support tool has an LLM summariser (a model that condenses a ticket into a short text). Agents report that it is "sometimes wrong". The team has no metrics and asks for a better summariser.

## Relevance

Agents who distrust a summary re-read the full ticket, so the feature saves no time. A wrong summary can also send a customer an incorrect answer.

1. **Log every summary.** Store ticket ID, summary, model version, prompt version, and time.
   - Blocker removed: no data exists to classify the problem.
   - Kind: deterministic.
   - Domain: Confused. The failure types are unknown, so this step gathers what the team needs to classify them.
   - Test, written first:
     ```gherkin

     Then a log record holds the ticket ID, summary, model version, prompt version, and time
     ```
2. **Add a "Wrong" button with five reasons.** The reasons are: invented fact, missing fact, wrong customer issue, wrong tone, other.
   - Blocker removed: agent reports have no type.
   - Kind: deterministic.
   - Domain: Clear. Feedback buttons are a known best practice.
   - Test, written first:
     ```gherkin
     Given an agent views a summary
     When the agent presses "Wrong" and picks a reason
     Then the log record for that summary stores the reason
     ```
   - Step 2 MUST NOT start until the test in Step 1 passes.
3. **Label 100 random summaries from the log.** Two reviewers score each one. Build an error list from the results.
   - Blocker removed: no baseline error rate.
   - Kind: evaluative.
   - Domain: Complicated. Analysis of the sample picks the error types.
   - Rubric, written first:

     | Criterion | Weight | Evidence needed |
     |---|---|---|
     | No invented fact | 40% | Each claim found in the ticket |
     | No missing key fact | 30% | Issue, product, and request present |
     | Right customer issue | 20% | Matches the final resolution |
     | Readable in 10 seconds | 10% | Under 60 words |

   - Pass threshold for one summary: 80 points and no invented fact.
   - Reviewers MUST agree on at least 80% of items. If not, refine the rubric and relabel.
   - Step 3 MUST NOT start until Step 1 has 100 logged summaries.
4. **Run capped trials of fixes.** Try three changes: a stricter prompt, a "quote the ticket" rule, and a second-pass check. Use the top error type from Step 3.
   - Blocker removed: the errors themselves.
   - Kind: stochastic.
   - Domain: Complex. Effects show only after the trial, so the leverage of each fix is a guess.
   - Run it in parallel with Step 2. Budget: three working days. Stop after three variants without gain.
   - Acceptance test, written first:
     - Metric: share of summaries that fail the Step 3 rubric.
     - Baseline: the rate from Step 3.
     - Pass threshold: at least a 50% relative cut.
     - Sample size: 200 new summaries per variant.
   - Step 4 MUST NOT start until the baseline from Step 3 exists.

If A3 is false and the error rate is below 5%, replace Step 4 with a monitor that alerts when the "Wrong" rate doubles.
