**Headline**

Measure "wrong" first. Until a labeled sample exists, every change to the summariser is a guess [judgment].

1. The complaint has no rate and no error type, so it cannot anchor any change.
2. One session of labels over 20 to 30 recent summaries produces a pass rate and a ranked error list.
3. A one-click error report keeps that rate live with no extra reviewer work.
4. Every later fix runs as one measured probe against that baseline.

**Background**

A language model (a machine text generator) writes a summary on each support ticket. Agents report that it is "sometimes wrong", and no metric exists. The request is to make the tool better.

**Relevance**

Wrong summaries can lead agents to write wrong replies to customers [judgment]. A baseline is the entry condition for every later improvement, so it comes before prompt work (the prompt is the instruction text sent to the model).

**Information**

Evidence:

- There is no metric; the only signal is agent speech. [no source]
- A change without a baseline cannot show its effect. [judgment]
- Error reports form themes. Count the sources per theme and keep any dissenting report [5].
- Decision analysis sets the criteria, the weights, and the pass threshold before the judgment work starts [15].

Assumption log:

- A1. Most reported errors are mismatches between the summary and the ticket facts. Why not measured: the material does not state an error type. Validate by: the labels from the sample. If wrong: rebuild the rubric weights around the real top type.
- A2. Two agents can spare about 30 minutes each for the labels. Why not measured: agent time costs more than this decision is worth. Validate by: ask at the sample kickoff. If wrong: one reviewer labels the reports after the fact.
- A3. The ticket store can produce 20 to 30 recent tickets in one session. Why not measured: no tool in this session can reach the ticket store. Validate by: export the count first. If wrong: widen the period to 30 days.

Alternative considered:

- Change the prompt or the model now. It loses because, with no base rate, the change cannot show an effect [judgment], and it can add an error type that nobody catches.

**End**

I recommend that we work in this order. It follows Cynefin [18]: confused work first, then clear and complicated work, then one capped complex probe.

1. **Label a sample of 30 summaries. Kind: evaluative. Cynefin: Confused.**
   Increment: in one session, pull 30 recent tickets, write the rubric, and have two agents label each summary.
   Blocker removed: "sometimes wrong" becomes a pass rate and a ranked error list.
   Test, written first (rubric):
   - Fact match against the ticket thread, weight 5, evidence: the thread.
   - Next action named, weight 3, evidence: the agent's account.
   - Length and plain terms, weight 2, evidence: word count.
   Pass threshold: 8 of 10 total, and each criterion at half of its weight or better.
   Reason: cause and effect cannot be classified before the labels exist, so this output decides the rest.

2. **Add a one-click error report to every summary. Kind: deterministic. Cynefin: Clear.**
   Increment: a button with a fixed error type list, storing the rater, the ticket ID, and the summary version.
   Blocker removed: the rate updates daily with no extra reviewer work.
   Test, written first in Gherkin [14]:
   ```text
   Given a summary shown on a ticket
   When the rater selects "Numbers do not match"
   Then the log stores the rater, the ticket ID, the summary version, and the error type
   ```
   Reason: event storage has one known rule, so the answer comes by deduction.

3. **Run the top fix as one capped probe. Kind: stochastic. Cynefin: Complex.**
   Increment: for the top error type from Step 1, make one change only, for example feed the raw ticket fields into the prompt.
   Blocker removed: it tests whether the top error type falls.
   Test, written first: metric is the pass rate; baseline is the Step 1 rate; pass threshold is 15 percentage points above the baseline; sample size is 50 new summaries. Budget: one session. Stop condition: with no gain after 50 summaries, stop, revert, and log the result.
   Reason: the effect is visible only after the run, so this is a safe-to-fail probe, and the leverage is a guess.

4. **Keep a golden set with every change. Kind: deterministic. Cynefin: Complicated.**
   Increment: from the Step 1 sample, keep 20 tickets with agreed summaries as a golden set, that is, a fixed list for regression tests. Re-run the set after each prompt or model change.
   Blocker removed: a fix for one error type no longer breaks another type in silence.
   Test, written first:
   ```text
   Given the golden set of 20 tickets
   When a new prompt runs on it
   Then its pass rate is not lower than the rate of the current prompt
   ```
   Reason: expert analysis picks the set, and that analysis makes the leverage reliable.

Sequencing: Step 3 MUST NOT start until Step 1 produces the baseline and the top error type. Step 4 also waits on Step 1. Step 2 runs in parallel with Step 1.

**Follow-up**

Conditions that change the recommendation:

- If the Step 1 pass rate reaches 90% or better, replace the Step 3 target with zero factual errors on 50 summaries, because the baseline leaves little room for a 15 point gain.
- If agents refuse the label work, run Step 2 first and build the sample from the logged reports instead.
