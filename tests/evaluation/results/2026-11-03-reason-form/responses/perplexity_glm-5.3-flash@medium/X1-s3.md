## Headline

Measure agent failures at the point of use, then score the summariser against a rubric and a golden set, and only then change the model or flow.

Supporting points:
1. "Sometimes wrong" is a signal without a rate or a category, so capture it first.
2. A rubric with weights makes the judgement of "wrong" repeatable across agents.
3. A golden set of scored tickets gives a baseline error rate.
4. Changes are then tested one at a time against that baseline.

## Background

A support tool includes an LLM-based summariser. Agents report that it is "sometimes wrong". No metrics exist for correctness, usage, or failure type. The task is to make the summariser better.

## Relevance

Unmeasured LLM output erodes trust, and agents then stop reading summaries. Measurement converts an opinion into a target, so each change can be judged against evidence.

## Information

**What the evidence says.** The only evidence is the agent report "sometimes wrong". One theme spans it: output correctness, supported by one source [inference]. The theme has few sources, but it matters because it comes from the daily users of the output [3], [5]. The numbers are absent: no error rate, no failure categories, no volume. When numbers and themes disagree, say so; here the numbers do not exist yet, so the theme carries the case alone. Therefore the first step must create numbers, not change the model [judgment].

**Assumptions.**

- `A1. "Wrong" means factual errors or missing details more often than style. Why not measured: the agent comment names no category. Validate by: read 20 logged rejections after Step 1. If wrong: reweight the rubric in Step 2.`
- `A2. Ticket volume supports a sample of about 60 closed tickets. Why not measured: the material states no volume. Validate by: count one week of closed tickets. If wrong: cut the sample to 30.`
- `A3. The tool adds a rating control within one working session. Why not measured: the codebase is not in this session. Validate by: inspect the summary endpoint. If wrong: log ratings server-side behind a flag.`

**Alternative considered.** Replace the summariser with a fixed template over ticket fields. It loses because support tickets vary in form, so a template would drop or misplace details; the failure that agents already report would persist [judgment]. Also, this alternative skips measurement, so the team cannot tell whether the new design is better.

## End

I recommend that we execute these steps in order. Each increment fits one working session.

**Step 1. Capture failure evidence.** Add a two-button rating (correct, incorrect) and one required reason code (wrong fact, missing fact, wrong tone, too long) next to each summary.
- Kind: deterministic. Test (written first, Gherkin form [14]):
  - Given an agent views a summary
  - When the agent clicks incorrect and picks wrong fact
  - Then the system stores the rating, the code, and the summary text on the ticket
- Cynefin: Confused [18]. We cannot tell how cause and effect work in this failure, so the first action gathers what is needed to classify. Leverage is a guess.

**Step 2. Define the quality rubric.** Write criteria with weights: faithfulness 0.5, completeness 0.3, length 0.2. Faithfulness means every claim in the summary appears in the ticket. Pass threshold: two raters agree on the chosen category. Evidence per criterion: the ticket text itself, in the style of ISO/IEC 25010 quality characteristics [17].
- Kind: evaluative. Test: two raters score the same 10 summaries; if agreement is below 80%, revise the rubric wording and repeat.
- Cynefin: Complicated [18]. Analysis of failure codes from Step 1 picks the weights. Leverage estimates are reliable after that analysis.
- Dependency on A1: if the codes show style dominates, reweight before Step 3.

**Step 3. Build a golden set.** Sample 60 closed tickets, stratified by type. Two humans write reference summaries for each.
- Kind: deterministic. Test:
  - Given the sample is drawn by ticket ID
  - When two humans write reference summaries for the same 10 tickets
  - Then the raters reach the agreement threshold from Step 2 before scaling to 60
- Cynefin: Complicated [18]. Known sampling procedure, applied by rule.
- Dependency: Step 2 MUST pass its test before this step scales to 60.

**Step 4. Measure the baseline.** Score the summariser against the golden set with the rubric.
- Kind: stochastic. Acceptance test (written first): metric, faithfulness error rate per 100 summaries; baseline, the value from this run; sample size, 60; pass threshold, the baseline is recorded and cannot change without a new run [judgment].
- Cynefin: Complicated [18], because scoring by rubric is knowable with the agreed criteria.
- Dependency: MUST NOT start until Step 3 has 60 scored tickets.

**Step 5. Probe one change at a time.** Try one revision, such as grounding the summary in the ticket text, or a prompt change. Cap each trial at 10 golden-set tickets and two weeks. Stop a change if two trials fail to beat the baseline at that sample size.
- Kind: stochastic, with the same acceptance-test form as Step 4.
- Cynefin: Complex [18]. Effect is visible only after the trial, so this is a safe-to-fail probe, not a full commitment. Leverage is a guess.
- Dependency: MUST NOT start until Step 4 records the baseline.

Sequencing: Steps 2, 3, and 4 are the critical path. Step 5 runs one probe at a time. Condition that changes the plan: if Step 1 shows zero ratings after two weeks, the blocker is workflow fit, not model quality, so redesign the rating step before Step 2.

- A2 proves false: shrink the golden set to 30 tickets.
