## Headline

Add a measured feedback loop before changing the summariser: label agent-flagged errors, score them on a fixed test set, then fix the top error class.
- Agents already detect failures, so their flags give free labels.
- No baseline exists, so no change can be judged as better.
- Fixing the largest error class first targets the real problem, not a guessed one.

## Background

The team added an LLM-based summariser to the support tool. Agents call it "sometimes wrong" [user report]. The team has no metrics [user report]. The request is to make it better.

## Relevance

Without labels and a test set, every prompt change is a guess and failures repeat. A small feedback loop gives a baseline within two weeks [judgment, from standard evaluation practice].

## Information

**Evidence.** The only data is the agent statement "sometimes wrong" [user report]. Three error classes are typical for LLM summaries: wrong detail, missing context, and wrong reading of the ticket [judgment]. Which class dominates here is unknown. Thematic grouping of flagged cases can resolve this: count sources per theme and look for disagreement [3], [5].

**Confidence.** High confidence that labeling flags first beats direct fixes; basis: no labels exist, so no fix can be verified today. The step 4 gain estimate is a guess; the domain check in the End section says so.

**Assumption log.**

- A1. "Wrong" means wrong facts or missing context, not style. Why not measured: the user has not answered. Validate by: the error taxonomy from agents. If wrong: step 4 becomes a length or style constraint change.
- A2. Roughly 100 ticket-summary pairs can be reviewed in one session. Why not measured: ticket volume is not in the material. Validate by: count weekly tickets. If wrong: use a 50-case set; thresholds stay at 80% of the stated values.
- A3. Summaries and ticket text are stored, so they can be sampled later. Why not measured: no tool access in this session. Validate by: check log retention with the tool owner. If wrong: step 1 must also add logging; add one session.

**Alternative considered.** Rewrite the prompt now and ask agents again. It loses because without a baseline there is no way to tell improvement from noise, and the real error class stays unknown.

## End

I recommend that we build the feedback loop below, then fix the largest error class. Review the plan if two reviewers disagree with the assumption log.

1. **Add a flag action with an error taxonomy to the tool.** Categories: wrong detail, missing context, missed turn, style. This removes the blocker: failures cannot be counted. Test (deterministic, written first):
   ```
   Given an open ticket with a summary
   When the agent selects "flag summary" and picks a category
   Then the ticket, summary, and category are saved as one record
   ```
   Domain: Confused, because the records decide which later steps apply; classification, not analysis, is the next inference.
2. **Collect 50 flags and label their themes.** Metric: share of flags that receive one taxonomy label. Baseline: 0%. Threshold: 90% or more. Sample: 50 flags. This adds the capability to rank error classes. Domain: Complex, run as a capped probe because the pattern is visible only after labeling [18]. Budget: two weeks, stop if fewer than 20 flags arrive; then sample 50 summaries and review them directly. What could break the pattern: agents flag only extreme cases [judgment]. Step 2 MUST NOT start until the test in Step 1 passes.
3. **Build a test set of 100 ticket-summary pairs** (all flags plus a random sample) and write the scoring rubric first. Criteria and weights: faithfulness 0.5, coverage 0.3, action-readiness 0.2 [judgment]. Pass threshold: weighted score 4 of 5. Evidence per criterion: ticket text, agent-facing turn list. This removes the blocker: prompt changes cannot be judged without a fixed set. Layout: Kepner-Tregoe [15]. Domain: Complicated, because analysis selects the scoring practice. Class: evaluative. Step 3 MAY start once Step 2 has its first 20 records.
4. **Ground the summary in ticket text only** (prompt replacement or retrieval over turn text), then score it on the test set. Metric: faithfulness failures per 100 pairs. Baseline: from Step 3. Threshold: 30% relative drop. Sample: 100. This removes the dominant error class. Domain: Complex, safe-to-fail probe with budget one session; cause and effect with prompt changes are visible only after the run [18]. Stop condition: no drop after two tries; then swOp to a model or tool change review. Step 4 MUST NOT start until the threshold in Step 2 is met and the test set in Step 3 is scored.

Condition that changes the plan: if A1 is false and style errors dominate, replace Step 4 with a length and format constraint change on the same test set.
