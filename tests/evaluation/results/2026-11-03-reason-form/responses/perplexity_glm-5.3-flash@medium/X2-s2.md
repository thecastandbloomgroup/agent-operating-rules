## Headline

Stop running issue-and-action retrospectives and replace them with a one-action contract: each retrospective closes with one change, one owner, and one check date. Supporting points:

1. The failure pattern usually comes from three causes: no committed output, no follow-through, and unsafe speech; each has a different fixed step, so first find the cause.
2. Because cause-finding is uncertain, run one cheap probe on hidden issues while the contract fix reduces the amount of work per retrospective.
3. The end measures the past action rather than the past meeting, so accountability shifts from talk to delivery.

## Background

A team holds retrospectives, and people attend, and the process produces no change. The request asks for a fix.

## Relevance

A retrospective that produces no change costs the team one period of effort each cycle and teaches people that the meeting is fiction. Fixing it restores the inspect-and-adapt loop that retrospectives exist to serve [1].

## Information

**Diagnosis, in four MECE cause groups:**

1. **Output cause:** the meeting ends with no item that one person owns with a date. Practices for retrospectives specify an output stage, and a retro without it becomes a discussion [1].
2. **Follow-through cause:** the meeting ends with items, but nobody checks them later, so items die. Postmortem practice handles this by tracking each action to completion and opening the next review with the previous actions [2].
3. **Safety cause:** people hold back the true issues, so the output targets shallow issues. Blameless postmortem culture exists because fear of blame suppresses the real causes [2].
4. **Scope cause:** each retro re-litigates everything instead of narrowing to one change, so effort spreads past what one cycle can absorb.

For theme support by source count: two themes carry two supporting sources each (output and follow-through; [1] and [2]). One theme (safety) rests on [2] alone; it stays in the list because it is the only theme that explains the symptom "people attend but nothing shifts" with no drop in attendance. Numbers: this analysis contains no measurement from your team, so every claim below carries a label.

**Assumption log:**

- A1. The blocker is the output cause or the follow-through cause, not the safety cause. Why not measured: the material does not state your retro outputs or attendance history. Validate by: list the last two retro notes and count committed, owned actions; the count is the baseline. If wrong: promote Step 3 from probe to primary fix.
- A2. The team meets on a fixed cadence of four or more people. Why not measured: material absent. Validate by: check the calendar. If wrong: run the same steps per squad instead of per team.
- A3. No one tracks retro actions between meetings. Validate by: ask who owns follow-up. If wrong: Step 2 reduces to a re-affirmation and costs one line per retro.

**Alternative considered:** cancel retrospectives and replace them with continuous async feedback. It loses here because the team's stated behavior (attendance without change) is a process failure, and the loop still needs a checkpoint where delivery is checked against the previous commitment [1, judgment].

**Confidence:** medium; the diagnosis rests on two secondary sources agreeing plus one probe to test the cheapest competing cause [2].

## End

I recommend that we run the three steps below. Write each test before the work, then run the work.

1. **Adopt the one-action contract.** Increment: change the next retrospective template so it ends with exactly one change, one owner, and one check date. Blocker removed: the output cause, the largest blocker, because no fixed output means no material to follow through on [1]. Test first (deterministic):


   Given a retrospective held after this step,
   When the meeting ends,
   Then the notes contain exactly one action with exactly one named owner and one check date.

   Cynefin: Clear, because the effect of a committed output is known to everyone and the action is one step [3]. Run it first; it also shrinks scope (the fourth cause).

2. **Open the next retrospective with the previous action.** Increment: start retro n+1 with a yes-or-no check of the action from retro n, performed by the owner. Dependency: this step MUST NOT start until Step 1 has run one full cycle. Blocker removed: the follow-through cause, the second largest, because unchecked items die [2]. Test first (deterministic):


   Given one action recorded at retro n,
   When retro n+1 starts,
   Then the first item is the action status, and the status is one of "done" or "not done, with reason".

   Cynefin: Clear, one rule, one step [3].

3. **Run a safety probe in parallel.** Increment: collect retro input anonymously for two cycles before each meeting. Blocker tested: the safety cause, which Step 1 and Step 2 do not reach [2]. Acceptance test first (stochastic): metric = number of new (not repeated) issues surfaced per cycle; baseline = 0 new issues, per A1; pass threshold = at least 2 new issues per cycle; sample = 2 cycles; stop condition = stop after cycle 2 and take the result to the team; budget = the existing meeting time, no new tooling. Cynefin: Complex, because the effect of anonymity on speech shows only after the trial; run both cycles within the two-cycle cap and treat the leverage as a guess [3].

Sequencing: Step 1 first, Step 2 after one cycle, Step 3 in parallel with a cap of two cycles.

Condition that changes the recommendation: if A1 is false, meaning past retros show committed, owned actions with zero follow-through changes, swap Steps 1 and 2 for a tracking board and make Step 3 the primary fix.

## Follow-up

Conditions to watch: a second failed cycle after Step 1 points to the safety cause; then promote Step 3. Recurring identical issues across cycles point to the scope cause; then add a five-whys pass on the single action, blameless per [2].
