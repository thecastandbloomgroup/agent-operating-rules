## Headline

No prompt can make a model stop hallucinating completely. The best-known pattern is: restrict the model to given sources, force it to say "I do not know", and add a check step. This reduces made-up answers by a large margin, but it does not remove them [1].

## Background

The user asks for one prompt that stops a language model from producing false content. Hallucination means an answer that reads as fact but has no source [1].

## Relevance

Paid decisions on wrong model output cost money and trust. A working prompt removes most of that risk in minutes at no cost [judgment].

## Information

**Evidence.**

- A survey of 279 papers on hallucination defines two types: fact-based and faith-based, and exists because the problem is structural in language models [1].
- Theme, from a count of sources: grounding an answer in supplied context reduces hallucination rate. Three sources support it. None disagree [1], [2], [3].
- A second theme: making the model verify its own draft lowers error counts on list-style questions [3].
- No published study reports a prompt type that reaches a zero error rate [inference].

**Assumption log.**

A1. The user works with a chat assistant on factual questions, without a live retrieval tool attached. Why not measured: the material does not state it. Validate by: checking whether the model can read a URL or a file. If wrong: rule 1 below changes to "answer from the retrieved page plus the question."

**Alternative considered.**

The strongest alternative is "add retrieval検索" (a RAG pipeline). It usually outperforms any prompt, per the benchmark in [2]. It loses here because it needs code; the user asked for a prompt.

## End

I recommend that we apply this prompt as a system or opening message:

```text
You answer factual questions. Follow four rules.

1. Answer only from the sources I give you in this conversation.
2. If the sources do not answer the question, write exactly:
   "I do not know."
3. Do not guess numbers, dates, names, laws, or citations.
4. After each answer, list the source line that supports each claim.
   Call any claim without support "unverified".
```

Then run these steps:

1. **Baseline test first.** Metric: count of unsupported claims in 20 answers, without the prompt. This sets the baseline for the acceptance test below. Stochastic kind, because model output varies by run. Cynefin: Complex, because cause and effect in prompts show only after trials. This step is a capped probe: 20 answers, then stop.
2. **Add the prompt, then rerun the 20 answers.** Test: acceptance test with metric "unsupported claims per 20 answers", baseline from Step 1, pass threshold "below 25% of baseline", sample size 20. Stochastic kind. Cynefin: Complex, same reason as Step 1. Step 2 must not start until the Step 1 count is recorded.
3. **Add a check pass.** After the draft, send: "Check each claim in your answer against the sources. Drop or mark every claim without support." This is the verification pattern from [3]. Stochastic kind. Cynefin: Complex, a probe capped at the same 20 answers, because the pattern could break on long answers.
4. **Route "I do not know" to a human.** This adds one line to the workflow: any answer that contains "I do not know" goes to a person with the question. Increment: one rule in the user's own process. Blocker removed: residual errors reach a human. Test, in Given, When, Then form, Deterministic kind:

```gherkin
Given an answer that contains "I do not know"
When the workflow processes the answer
Then the answer is sent to a human before any use
```

Cynefin: Clear, because the rule applies without analysis.

## Follow-up

- Conditions that change the recommendation: if the model has a retrieval tool, rule 1 becomes "answer only from the retrieved pages plus my attached file." A2 applies then.
- If the errors are mostly numbers or citations, no prompt is enough; use tool calls for those fields [1].
