Headline
Classify why actions stall, then finish or drop one before the team adds another.

- A retrospective is meant to end in a small experiment, not a stored list.
- The cause is not known, so classification comes before a new format.
- An action needs one owner and a date inside 7 days.
- A capped one-week probe tests the class without a large bet.

Background
People attend the retrospective. Nothing in the way of work changes after it. The request asks for a next step that creates one change in the work.

Relevance
Each meeting with no closed action makes the next meeting weaker. Therefore a rule this week can show whether follow-through is the gap.

Information
This section covers the evidence, the assumptions, and the alternative.

Scrum requires the team to handle the most useful improvements as soon as possible [1].

Derby and Larsen end the retrospective with a small experiment the team will try [2].

Therefore a meeting that only stores ideas fails that purpose. [inference]

Confidence is low. The basis is that the material has no action log. [judgment]

A1. The team already meets on a regular cadence. Why not measured: The material does not state it. Validate by: Check the last three calendar invites. If wrong: Hold one facilitated session before you add a cadence rule.

A2. Past actions exist and are not reviewed at the start. Why not measured: The material does not state it. Validate by: Open the last notes and count open items. If wrong: Skip the review rule and test topic quality instead.

A3. One team member can finish a small change without new budget. Why not measured: The material does not state authority. Validate by: Ask which past action needed a manager. If wrong: Send systemic items to a manager forum.

The strongest alternative is to drop the meeting and keep only an improvement column.

It loses because the team still needs shared data before it picks one change [2].

End
I recommend that we take these four steps. Step 1 comes first. Run Step 4 in parallel with Step 2, inside its budget. Step 3 MUST NOT start until Step 1 names a primary cause.

1. Evaluative. Test first. Rubric: five causes, weight 20 each. Evidence: one note per action. Pass threshold: 3 of 3 actions have one primary cause. Increment: one 15 minute block in the next meeting. List the last three actions. Mark each as no owner, too large, blocked outside the team, unsafe to name, or forgotten. Blocker removed: unknown cause. Domain: Confused. The reason is deduction: no practice is valid until the cause class is known.

2. Deterministic. Test first.
Given the notes from the previous retrospective,
When the facilitator starts the meeting,
Then each open action has a status before any new topic.
Increment: one agenda change in that same meeting. Put the last actions first. Mark each one done, dropped, or still open. Blocker removed: new topics hide old promises. Domain: Clear. The reason is deduction from the Scrum rule that improvements start as soon as possible [1].

3. Deterministic. Test first.
Given the team adds a new action,
When the notes are saved,
Then they show one owner, one outcome, and a date within 7 days.
Increment: one saved note in that meeting. Keep one new action. Park the rest. Blocker removed: a list too large to finish. Domain: Clear. The reason is deduction from the practice of one small experiment [2].

4. Stochastic. Test first. Metric: the action is done or dropped. Baseline: no completed change, per A2. Pass threshold: 1 done or dropped action. Sample size: 1 trial of 7 days. Increment: one change one person can finish in 7 days. Cap team time at 2 hours. Stop if the change needs a person outside the team. Blocker removed: no proof that a class of fix works. Domain: Complex. The reason is induction from one trial. A manager veto can break the pattern. Leverage is a guess.

Follow-up
If A2 is false, skip Step 2 and test topic quality instead. If Step 1 marks unsafe to name, do not add a public action. Use an anonymous note first. If Step 1 marks blocked outside the team, stop Step 4. Write a one page request to the manager.
