## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` but not on production until the code that reads `user_id` is ready.

- The rename itself is a metadata change that finishes in milliseconds [1].
- The risk is in the code that still uses the old name, because the database does not update it.
- You are boarding, so a staging run now and a watched production run later is the safe split.

## Background

You asked for a rename of the column `user_id` to `account_id` in the `orders` table of a Postgres database. The statement is short. Application queries, stored functions, and reports that use `user_id` fail after the rename.

## Relevance

You are offline soon. A production change that breaks the application cannot be fixed from a plane.

## Information

Evidence:
- `RENAME COLUMN` changes the catalog entry only. It does not rewrite table data [1].
- Indexes, constraints, and views that use the column follow the new name automatically [1].
- Index and constraint names do not change. For example, `orders_user_id_idx` keeps its old name [1].
- The statement takes an exclusive lock on the table. Queries wait if a long transaction holds the table [1].
- Function bodies written in PL/pgSQL (Postgres procedural language) are stored as text. They break at call time [inference].

Assumption: The application is live and its code uses `user_id`. Why not measured: the material does not state it. Validate by: search the code base for `user_id`. If wrong: run the rename in production at once.

Assumption: No logical replication or external reader depends on the column name. Why not measured: no tool can reach it. Validate by: query `pg_publication_tables` for `orders`. If wrong: update subscribers first.

Assumption: The table is `public.orders`. Why not measured: the material does not state the schema. Validate by: run `\d orders`. If wrong: add the schema name to the statement.

Alternative considered: add `account_id`, copy the data, and drop `user_id` later. This path avoids downtime for old code. It loses here because it needs several deploys and the request is a plain rename [judgment].
