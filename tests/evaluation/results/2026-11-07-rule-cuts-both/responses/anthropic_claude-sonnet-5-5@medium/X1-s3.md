## Headline

Measure the errors first, then fix the most common error type, because no change can be judged without a baseline.

- Agents report errors, but no data shows which errors occur or how often.
- A labeled sample of 100 summaries gives a baseline within one working session.
- A feedback button turns each agent complaint into a data point.
- A regression check stops later changes from making the summaries worse.

## Background

The support tool has an LLM summariser (a model that shortens a ticket thread into a few lines). Agents say it is "sometimes wrong". The team has no metrics. The request is to improve it.

## Relevance

Agents who distrust the summary read the full thread anyway. Then the summariser saves no time. Without a measure, every prompt or model change is a guess.

## Information

Evidence:
- Summarisers often add content that the source does not support. This is a known failure type called hallucination [1]. This claim rests on a secondary source.
- It is likely (66 to 100%) that two or three error types cause most agent complaints [judgment]. This is why Step 3 targets one type.
- Another LLM can score summaries, and in one study it agreed with human raters over 80% of the time [2]. This supports automating the check later.

Assumption log:
- Assumption: the tool stores the ticket text and the summary text. Why not measured: the material does not state it. Validate by: query 10 recent tickets. If wrong: add logging before Step 1.
- Assumption: two agents can give 2 hours each this week. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: reduce the sample to 50 and widen the error margin.
- Assumption: "wrong" means unfaithful or incomplete, not slow or badly formatted. Why not measured: the material does not state it. Validate by: Step 1 labels include an "other" category. If wrong: add a criterion to the rubric.

Alternative considered: switch to a larger model or fine-tune now. It loses because no baseline exists to show a gain, and the cost is higher [judgment].

## End

I recommend that we:

1. **Label a baseline sample.** Increment: two agents label 100 recent summaries, each against its ticket. Blocker removed: no one knows the error rate or error types. Kind: evaluative. Test, written first, as a rubric:
   - Criteria and weights: faithfulness 50%, completeness 30%, usability 20%. Score each 0 to 2.
   - Pass threshold: a summary passes at a weighted score of 80% or more, and faithfulness must score 2.
   - Evidence: the ticket text beside the summary, plus one error-type tag from a fixed list (invented fact, missing key fact, wrong customer or product, other).
   - Output: the pass rate and a count per error type.
   - Cynefin: Confused. The error causes are unknown, so this step gathers data to classify them. Deduction is not yet possible.

2. **Add a feedback button.** Step 2 MAY start now, in parallel with Step 1. Increment: a thumbs up or down with a reason code on each summary. Blocker removed: no ongoing signal. Kind: deterministic. Test, written first:
   - Given an agent views a summary
   - When the agent clicks thumbs down and picks "invented fact"
   - Then the system stores the ticket ID, summary ID, prompt version, model version, reason, and time
   - Cynefin: Clear. Event logging is a known best practice, applied by deduction from that rule.

3. **Run one capped probe on the top error type.** Step 3 MUST NOT start until Step 1 finishes. Increment: change the prompt or add a rule that targets the most common error type. For example, tell the model to list only facts found in the ticket. Blocker removed: the main source of agent distrust. Kind: stochastic. Test, written first:
   - Metric: pass rate by the Step 1 rubric.
   - Baseline: the Step 1 pass rate.
   - Threshold: at least 10 points above baseline.
   - Sample size: 200 new tickets, not used before.
   - Budget: one working session and at most three prompt variants. Stop if none meets the threshold.
   - Cynefin: Complex. The effect of a prompt change shows only after trials, so this is induction from trials. The pattern could break if ticket types shift. The leverage estimate is a guess.

4. **Add a regression check.** Step 4 MUST NOT start until Step 1 gives a labeled set. Increment: a script that runs the 100 labeled tickets through the current prompt and reports the pass rate. Blocker removed: later changes could silently lower quality. Kind: deterministic. Test, written first:
   - Given the labeled set and a prompt version
   - When the script runs
   - Then it prints the pass rate and fails if the rate is below the Step 1 baseline minus 5 points
   - Cynefin: Complicated. Choosing the score method needs analysis, for example human labels first and LLM judge later [2]. The reasoning is deduction from that analysis.
