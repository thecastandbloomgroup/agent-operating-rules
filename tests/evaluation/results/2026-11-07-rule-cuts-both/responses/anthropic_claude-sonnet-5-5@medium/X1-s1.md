## Headline

We should measure the summariser first, then fix the most common error type, because no one can improve what no one counts.

- Agents report "sometimes wrong", but no one knows how often or in what way.
- Summaries that add facts absent from the source are a known failure of this technology [2].
- A fixed labelled test set lets us compare any change against today's baseline.
- Small, capped trials on the top error type limit the risk to agents.

## Background

The team added a summariser based on a large language model (LLM) to the support tool. An LLM is a text model that writes summaries. Agents say it is "sometimes wrong" [1]. The team has no metrics, so the error rate and the error types are unknown.

## Relevance

Agents who distrust the summary will reread the full ticket, so the tool saves no time. An agent who trusts a wrong summary may give a customer wrong advice.

## Information

Evidence:
- Abstractive summarisers often add content that the source does not support. Studies call this a faithfulness failure.

  Source:
  [2]

- A model can act as a judge of text quality. Reported agreement with human raters is above 80% on chat tasks.

  Source:
  [3]

- The judge result applies to chat tasks, not support tickets, so we must validate it locally before use. [inference]
- Prompt changes alone fix the top error type: about as likely as not (33 to 66%). [judgment]

## End

I recommend that we take these four actions in order:

1. **Label 100 recent summaries and rank the error types.**
   - Increment: two agents score the same random sample in one session.
   - Blocker removed: we do not know the error rate or error types.
   - Kind: evaluative. Write the rubric first.
     - Criteria and weights: faithfulness to the ticket 50%, coverage of key facts 30%, correct next step 20%.
     - Pass threshold: the labelling is valid when the two agents agree at kappa 0.6 or higher. Kappa is a score of agreement beyond chance.
     - Evidence: the summary, the full ticket, and one error tag per flaw.
   - Domain: Confused. The failure causes are unknown, so this step gathers what we need to classify the rest. It comes first.

2. **Add a "wrong summary" button with a reason list.** Step 3 MUST NOT start until this test passes.
   - Increment: one button, one log record.
   - Blocker removed: no ongoing signal exists.
   - Kind: deterministic. Test:

     Given an agent views a summary
     
     When the agent presses "wrong" and picks a reason
     
     Then the log stores the summary, ticket ID, reason, and prompt version

   - Domain: Clear. Logging feedback is a known practice, so we apply it by deduction.

3. **Freeze the 100 labelled summaries as a regression test set.**
   - Increment: a script that runs the current prompt on the set and reports the rate.
   - Blocker removed: no baseline exists.
   - Kind: stochastic. Write the acceptance test first.
     - Metric: share of summaries with no faithfulness error.
     - Baseline: the rate from Step 1.
     - Threshold: a change passes if it gains 10 points or more with no loss on coverage. [judgment]
     - Sample size: 100 summaries, run three times per prompt.
   - Domain: Complicated. Analysis of the Step 1 data picks the metric. Step 3 MUST NOT start until Step 1 ends.

4. **Run one prompt trial on the top error type.**
   - Increment: one prompt change, shown to 10% of agents for one week.
   - Blocker removed: the top error type.
   - Kind: stochastic. The Step 3 test applies. It adds a live check: the "wrong" button rate must fall against the control group.
   - Domain: Complex. Cause and effect show only after the trial, so leverage is a guess. This is a safe-to-fail probe.
     - Budget: one prompt author for two days.
     - Stop condition: stop at once if the "wrong" rate rises 5 points or more over control.
     - What could break the pattern: ticket mix changes between weeks.
   - Step 4 MUST NOT start until the test in Step 3 runs.

If the database does not store source tickets, replace Step 1 with logging work from Step 2.
