## Headline

Yes, pin the versions, and pin the full dependency tree, not only the top-level libraries.

- Unpinned installs pick the newest release on every build, so any upstream update can break the build.
- The two breaks last month match this failure pattern (per the user message).
- A pinned file makes builds repeatable, and a scheduled update job keeps the pins current.

## Background

The project has a requirements.txt with no pinned versions. The build broke twice last month after a library update. The question is whether to pin.

## Relevance

Each break blocks the team until someone finds the bad release. At two breaks per month, the cost recurs until the cause is removed.

## Information

Evidence:

- Pinning a version with `==` makes pip install the same release each time.

  [1]

- A pin on a top-level library does not fix the versions of the libraries it needs. These are transitive dependencies.

  [1]

- The tool pip-compile reads a short list of direct dependencies. It writes a file with exact versions for every package, including transitive ones.

  [2]

- Pinning very likely stops update-caused breaks (90 to 100%). [judgment] Breaks from a changed Python version or operating system remain possible.

Assumption: The last successful build is a good source for the versions. Why not measured: no tool can reach the build logs. Validate by: run the current main branch build once. If wrong: pin the versions from the oldest passing build instead.

Assumption: Both breaks came from library updates, as the user states. Why not measured: the material gives no logs. Validate by: read the two failed build logs for version changes. If wrong: the pins fix fewer breaks, and Step 4 gives the data to see it.
