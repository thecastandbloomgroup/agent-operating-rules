## Headline

Yes, pin exact versions in requirements.txt today.

- Unpinned files let every install pick the newest allowed version, so builds change without a decision.
- Exact pins make every build use the same library versions, including the ones that break [1].
- After pinning, version updates become deliberate, tested changes instead of surprise.
- A monthly update step keeps the pins current without risk to daily builds.

## Background

The team has a requirements.txt with no version numbers. Two builds broke last month after a library update [1]. The request asks whether to pin versions.

## Relevance

Version pins need one working session to add. They remove the repeat breakage the team saw last month [1].

## Information

**Evidence.** The pip documentation states that a requirement line with `==` and a version number installs exactly that version [2]. Therefore an unpinned file takes the newest release that satisfies any range, and the team controls nothing [2]. The two failed builds in one month came from this behavior per the team report [1].

**Assumption log.**

Assumption: installs from the file use pip. Why not measured: the message does not state the tool. Validate by: read one line of the project install config. If wrong: keep the pin method and change the syntax for the tool in use, for example npm or uv.

Assumption: a test suite exists that can check updates. Why not measured: the message does not state it. Validate by: run the build and the test command once. If wrong: Step 3 moves later, because a suite must exist to test updates.

**Alternative considered.** Use version ranges like `>=1.0,<2.0` instead of exact pins. It loses because ranges still allow a new patch or minor version on each install, so the same repeat breakage returns [2].

## End

I recommend that we do the following:

1. **Pin all libraries to exact versions in requirements.txt.** Increment: add `==` and a version number to every line. It removes the blocker: silent version changes in builds. Test:

   ```gherkin
   Given requirements.txt lists every library with an exact version
   When a clean machine installs from it and runs the build
   Then the install succeeds and the build reports the pinned versions
   ```

   Kind: deterministic. Domain: Clear, by deduction from the pip rule that `==` installs an exact version [2].

2. **Capture transitive libraries with pip freeze.** Increment: run `pip freeze > requirements-pinned.txt` and commit the result, after Step 1 passes. It removes the blocker: a dependent library (a library a pinned library needs) can still change under you. For example, one pinned library can pull in a newer dependent library. Test:

   ```gherkin
   Given every line in requirements-pinned.txt has an exact version
   When pip installs from the pinned file on a clean machine
   Then no install step downloads a version not named in the file
   ```

   Kind: deterministic. Domain: Complicated, because the analysis must pick which file is the source of truth for installs. The freeze output decides.

3. **Add a monthly update probe.** Increment: once a month, bump one library, run the full build and test suite, and merge only on pass. Step 3 MUST NOT start until the test suite exists and Step 2 passes. It adds the capability: up-to-date libraries with tested changes. Acceptance test (stochastic): metric is the suite result; baseline is the suite passing today [assumption]; threshold is 100 percent pass; sample size is one full suite run per update, once per month. Domain: Complex, because a new version's effect is visible only after the run. Budget: one hour per month. Stop condition: any failure. Failure pattern: the update goes back to the last pinned version.

A phased alternative, like pinning only direct libraries, is covered under "Alternative considered" above and loses [2].

## Follow-up

Conditions that change the recommendation: a security advisory for a pinned version needs an immediate bump, so the monthly cycle should not block it.
