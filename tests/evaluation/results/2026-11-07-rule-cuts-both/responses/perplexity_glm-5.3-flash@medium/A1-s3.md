# Headline

Yes. Pin every direct dependency to an exact version, and commit a resolved lock file for the indirect ones.

- Pinning fixes the cause: pip installs new versions when no pin exists.
- Exact pins give reproducible builds: the same input gives the same output.
- A lock file extends the pin to indirect packages, so build differences between machines disappear.
- Release cost stays low because a tested update job refreshes the pins on a schedule.

# Background

A Python project uses requirements.txt with no pinned versions. Two builds failed last month after a library update. The question is whether to pin.

# Relevance

The next pip install can pull a new version today, so the failure can repeat. Pinning costs one working session and reverses with one commit.

# Information

The request states that both breaks followed a library update [1]. Because nothing is pinned, pip resolves each install to the newest allowed release. That resolution is the entry point for those updates [judgment]. One session fixes the direct packages; the lock file fixes the rest of the graph.

Assumption: the project uses pip with a plain requirements.txt, not Poetry, uv, or Conda. Why not measured: the request does not state the tool. Validate by: read the build files in the repository. If wrong: replace steps 1 and 2 with the tool's own lock command.

Alternative considered: pin only the direct dependencies and skip the lock file. It loses because indirect packages still float, and silent indirect upgrades are the usual cause of surprise breakage [judgment].

# End

I recommend that we:

1. **Pin the direct dependencies.** Increment: in one session, set an exact version for every package without one in requirements.txt. Blocker removed: silent upgrades of the packages the code imports. Test, written first:

   ```gherkin
   Given a clean virtual environment
   When the team runs pip install -r requirements.txt
   Then pip uses only the exact versions in the file
   ```

   Kind: deterministic. Cynefin: Clear, because installation from an exact list follows a known rule by deduction, and leverage estimates for it are reliable.

2. **Generate the lock file.** Increment: create requirements.in from the current file, run pip-compile, and commit its output as requirements.txt. Blocker removed: unpinned indirect packages, the usual source of surprise updates. Test, written first:

   ```gherkin
   Given requirements.in with the pinned direct dependencies
   When the team runs pip-compile
   Then requirements.txt records every indirect package with an exact version
   ```

   Kind: deterministic. Cynefin: Clear, because pip-sync and pip-compile are the documented workflow for this lock pattern [2]. Step 2 MUST NOT start until the test in Step 1 passes.

3. **Add a build gate.** Increment: add one CI step that installs from requirements.txt and fails when a committed pin does not match requirements.in. Blocker removed: untested upgrades reaching the build from a neglected regen. Test, written first:

   ```gherkin
   Given the CI pipeline with the gate step
   When a commit changes requirements.in without a new pip-compile run
   Then the pipeline fails and names the first mismatched package
   ```

   Kind: deterministic. Cynefin: Clear, same known rule as Step 1. Step 3 MUST NOT start until the lock file from Step 2 exists.

4. **Run a monthly update probe.** Increment: in one trial per month, refresh all pins and run the test suite; cap each trial at 2 engineer hours; after 4 trials, adopt the job only if the threshold holds. Blocker removed: stale pins that push the team back to unmanaged installs. Acceptance test, written first: metric is the share of trials where the suite passes after the refresh; baseline is last month, where 2 of 2 library updates broke the build [1]; threshold is 3 of 4 trials pass at a sample of 4 monthly trials. Stop condition: if 2 of the first 4 trials fail the suite, pause the schedule and merge updates one package at a time with review. Kind: stochastic, because the output of an upstream release varies from run to run. Cynefin: Complex, because the effect of an upstream change is visible only after a trial; the pattern can break when a maintainer publishes a bad release, so it is a safe-to-fail probe with a stated measure, stop condition, and budget. Step 4 runs in parallel with nothing and MUST NOT start until Step 3 passes.

Condition that changes the plan: if the assumption about pip is wrong, replace Steps 1 and 2 with the installed tool's own pin and lock commands, and keep Steps 3 and 4.
