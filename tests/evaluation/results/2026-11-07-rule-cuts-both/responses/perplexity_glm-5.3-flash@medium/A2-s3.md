# Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` in the target database, then update every view and query that still reads `user_id`.

- The rename is metadata-only in Postgres, so it finishes in under a second.
- Postgres does not rewrite dependent views, so they break at first use after the rename.
- The rename takes a brief ACCESS EXCLUSIVE lock, so it needs a gap in long-running writes.

# Background

The request is a column rename from `user_id` to `account_id` in the `orders` table of a Postgres database. The user is boarding a plane and asks for a quick action.

# Relevance

Dependent views and application code keep the old name, because Postgres does not update them on a rename. A rename without a follow-up search can stop reports and the app at the next query.

# Information

First, the command. It is one statement and it does not touch table data [1]:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Next, the lock. Postgres holds an ACCESS EXCLUSIVE lock on `orders` for the duration of the statement. Concurrent queries on `orders` queue behind it and are themselves blocked until the rename ends. So run it outside peak write windows or in a maintenance gap [1].

Then, the dependents. Postgres does not rewrite the text of views, functions, or prepared statements when a column is renamed. A view that selects `user_id` fails with "column does not exist" after the rename [1]. Therefore run this check before and after:

- `grep -rn "user_id" app/` for application code [judgment].
- `\dv+ orders*` plus review of any view definitions that read `orders` [1].

Also note: hot tip for speed, add `SET lock_timeout = '5s';` before the rename. MySQL-style tricks are not needed here; this is a plain Postgres rename.

Assumption: no view or scheduled job reads `orders.user_id` at this moment. Why not measured: the material does not name the schema's dependents and no catalog access tool is present. Validate by: query `pg_depend` or run `\df`, `\dv` on the database before the rename. If wrong: one dependent view or job fails on its next run, so run the grep and catalog check at step 2 first.

Alternative considered: add `account_id`, copy data with `UPDATE`, drop `user_id`. It loses because the rename is instant and rewrites no rows, so the copy adds minutes of risk with no benefit [judgment].
