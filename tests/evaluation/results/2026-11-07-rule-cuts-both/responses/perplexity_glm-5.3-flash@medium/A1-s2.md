## Headline

Pin every dependency to an exact version, and accept updates only through a controlled upgrade step.

- Unpinned builds fetch the newest release at install time, so two builds with the same file can differ.
- Your report of two build failures last month after a library update shows this risk is active, not theoretical [1].
- Exact pins make every build install the same packages, so a build break points to code, not to a silent update.
- A separate, scheduled upgrade step lets updates in one at a time, with a test as the gate.

## Background

The project builds from requirements.txt, and the file contains no version pins. Two builds failed last month after a library released a new version [1]. The question asks whether to pin versions.

## Relevance

Every build today depends on what other projects publish. Pinning turns that outside factor into a fixed input, so the team regains control of release timing [judgment].

## Information

There are two pinning levels [judgment]:

1. Pin only the direct dependencies. Inner dependencies still float, so builds can still drift.
2. Pin the full environment with a lock file, produced by pip freeze or pip compile. Every package in every build is then fixed.

Level 2 removes the drift that caused the failures [1]. Level 1 leaves part of it open.

Assumption: The project uses pip and installs from requirements.txt alone, with no lock tool. Why not measured: the material does not state the toolchain. Validate by: read the deploy script or Dockerfile. If wrong: replace the tool in Step 2 with Poetry, uv, or the team's lock format; the pin decision itself still stands.

Alternative considered: keep loose ranges (>=) with a constraints file. It loses because the constraints file still requires writing and maintaining pins, and the drift risk remains until someone maintains it [judgment].

## End

I recommend that we take four steps.

Step 1. Pin all direct dependencies with exact versions in requirements.txt. Increment: add == pins to one file in one session. Blocker removed: builds no longer fetch unknown new releases. Kind: deterministic. Test:

```gherkin
Given requirements.txt with exact pins
When a fresh pip install runs
Then pip resolves every package to the pinned version and the app imports
```

Domain: Clear. Cause and effect are known to everyone; this is a standard practice.

Step 2. Generate a full lock file and commit it. Increment: run pip freeze or pip compile once, commit the output, and point the build at it. Blocker removed: inner dependencies no longer drift between builds. This step waits on Step 1, because the lock must start from the pinned file. Kind: deterministic. Test:

```gherkin
Given a committed lock file
When the build installs from the lock file on a clean machine
Then the installed package set matches the lock file exactly
```

Domain: Clear. The tool produces the file; the check is a direct comparison.

Step 3. Add a continuous integration job that installs from the lock file and runs the test suite before merge. Increment: one CI job with install plus tests. Blocker removed: a broken pin reaches production only if tests pass first. Kind: deterministic. Test:

```gherkin
Given a merge request with a changed lock file
When the CI job installs from the lock file and runs the tests
Then the merge is blocked when any test fails
```

Domain: Clear. The pass or fail rule is fully defined by the test suite.

Step 4. Run a scheduled upgrade session each month that bumps pins one library at a time. Increment: one session, ten or fewer bumps, each bump immediately followed by the test suite. Blocker removed: dependencies no longer age without review. Kind: stochastic, because the outcome of a new release varies. Acceptance test, written before the session: each bump must pass the full suite on the CI job of Step 3, with a baseline of the previous passing run, a threshold of zero failures, and a sample of one install per bump. Domain: Complex. The effect of an upgrade is visible only after the run, so each bump is a safe-to-fail probe with a stop condition: revert on any failure [judgment].
