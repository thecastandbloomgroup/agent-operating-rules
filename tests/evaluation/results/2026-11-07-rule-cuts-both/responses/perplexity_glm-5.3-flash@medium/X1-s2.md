# Headline

Measure the error rate first, then fix the top error type with one tested change. Support: agents label 60 real summaries against a shared error list, so the word "wrong" becomes counts. The counts set a baseline for factual errors and missing facts. One prompt constraint targets the top error type, and 100 fresh tickets test whether the rate drops. A weekly sample review keeps the measure current after release.

## Background

A support tool produces summaries with a large language model (LLM). Agents report that the output is sometimes wrong. No measures exist. The request is to make the summariser better.

## Relevance

Without a measured error rate, no change can show real effect. The first step is therefore to label a sample, not to edit the prompt.

## Information

An LLM can state facts that its source text does not contain [1]. So factual errors are one known failure class to test for [1]. The plan below rests on one testable judgment: agent labels on a 60 summary sample give a usable error rate [judgment].

**Assumptions:**

- Assumption: factual errors, not style, cause most complaints. Why not measured: the user has not answered. Validate by: the counts from Step 1. If wrong: pick the top error type from the Step 2 table instead.
- Assumption: the tool stores the full ticket text next to each summary. Why not measured: the material does not state it. Validate by: pull one week of records. If wrong: add one logging release before Step 1.
- Assumption: agents can give about 4 hours of label time. Why not measured: the material does not state it. Validate by: confirm one working session with the team lead. If wrong: drop double labels and keep the 10 summary overlap only.

**Alternative considered:** edit the prompt now without a baseline. It loses because, with no baseline, we cannot tell effect from noise [judgment].

- If the top error type belongs to the prompt, Steps 3 and 4 need no change.
