# Headline

Retrospectives fail when they produce feelings but not committed, tracked experiments, so the fix is to shrink the output to one owned, testable change per session.

- Retros fail most often because action items lack an owner, a deadline, and a follow-up check [judgment].
- Symptom "people attend but nothing shifts" suggests engagement survives, so the problem is the commitment mechanism, not facilitation quality [judgment].
- The remedy is a hard rule: maximum one or two actions per retro, each with an owner and a test, reviewed first at the next retro.

# Background

A team's retrospectives run on schedule and attendance is fine, but they produce no visible change. The request is what to do about it.

# Relevance

A retrospective that produces nothing still costs the team's time, roughly one to two hours per session [no source]. Worse, repeated empty retros teach the team that speaking up changes nothing, which erodes the habit itself.

# Information

Evidence for the common failure modes:

1. No owner: actions recorded as "we should" never get done because nobody is accountable [judgment].
2. Too many actions: lists of five or more items dilute effort so none finish [judgment].
3. Vague actions: "communicate better" has no test, so nobody can tell if it happened [judgment].
4. No follow-up: the next retro does not check the last retro's actions, so inaction is costless [judgment].
5. Same format every time: repeat formats surface repeat topics, which produces boredom, not insight [judgment].

Assumption log:

`Assumption: this is a software or knowledge-work team running recurring retros. Why not measured: the material does not state it. Validate by: ask the team lead once. If wrong: the same mechanism still applies, only the format changes.`

`Assumption: a facilitator or lead exists who can change the format. Why not measured: the material does not state it. Validate by: confirm with the user. If wrong: adds a step to appoint a rotating facilitator.`

Alternative considered: replace retros with continuous feedback (one-on-ones, async channels). This loses [judgment] because it removes the one forum where the whole team sees a problem at once; the forum is fine, the output mechanism is broken.

# End

I recommend that we run four actions, ordered by leverage:

1. **Start every retro with a review of the last retro's actions.** Increment: add a standing five-minute first agenda item, done in the next session. Blocker removed: inaction is currently costless. Kind: deterministic. Domain: Complicated (analysis: inspect whether prior actions finished; deduction from the rule "unchecked work does not get done"). Test, written first:

   Given the previous retro's action list,
   When the retro opens,
   Then each action is marked done, dropped, or carried with a reason, in under five minutes.

2. **Cap actions at one, with one named owner, one deadline, and one observable test.** Increment: a one-line template on the retro board. Blocker removed: vague, ownerless actions. Kind: deterministic. Domain: Clear (best practice exists: single owner plus deadline). Test, written first:

   Given a proposed retro action,
   When the team accepts it,
   Then it names one owner, one date, and one sentence describing what "done" looks like, or it is rejected.

3. **Install a parking lot for everything beyond the one action.** Increment: a visible list reviewed monthly. Blocker removed: fear that capping actions loses good ideas. Kind: deterministic. Domain: Clear. Test:

   Given an idea that does not make the single action,
   When the retro ends,
   Then it is recorded in the parking lot with a review date.

4. **Rotate the retro format monthly.** Increment: pick the next format from a short list (for example: start/stop/continue, sailboat, four Ls) at the end of each retro. Blocker removed: format fatigue. Kind: stochastic (attendance and energy vary). Domain: Complex (cause and effect on engagement visible only afterward; safe-to-fail probe, capped at three months). Acceptance test, written first: metric is "at least one actionable finding per retro"; baseline is current zero completed actions; pass threshold is one completed action per retro over three consecutive retros. Stop condition: if fewer than half the sessions produce a completed action after three months, replace the facilitator or survey the team on whether the retro itself should continue.

Steps 2 to 4 MUST NOT start until Step 1 runs once, because Step 1 supplies the data on whether the cap and parking lot work.

# Follow-up

Conditions that change the recommendation:

- If attendance is forced or hostile rather than merely passive, run a one-question anonymous survey first ("what would make this meeting worth your time?") before Step 1.
- If no facilitator exists, add Step 0.5: appoint a rotating facilitator before Step 1.
