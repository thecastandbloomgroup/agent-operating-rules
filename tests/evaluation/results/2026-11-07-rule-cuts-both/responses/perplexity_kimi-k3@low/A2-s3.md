## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` to rename the column in Postgres.

- The command is metadata-only. It finishes in milliseconds because it does not rewrite table data [1].
- It requires an ACCESS EXCLUSIVE lock, so it waits for open transactions on orders and blocks new ones while it waits.
- Indexes, constraints, and views that reference user_id keep working for indexes and constraints. Views that name the column break [judgment].
- Application code that reads or writes user_id fails the moment the rename commits. Deploy code and rename in a coordinated step.

## Background

You asked for the SQL to rename the column user_id to account_id in the orders table of a Postgres database. You are boarding a plane, so this gives the command plus the two risks that matter before you run it.

## Relevance

A rename is instant in the database but it breaks every dependent object and every query that still says user_id. Knowing the blast radius now avoids a failed deploy or an outage from the air.

## Information

The command:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Evidence and risks:

1. Rename is a catalog change only. The docs state it changes no data, so runtime is constant regardless of table size [1].
2. The lock is ACCESS EXCLUSIVE. On a busy orders table, queue the rename inside a short transaction with a lock timeout so it fails fast instead of blocking writes:

```sql
BEGIN;
SET lock_timeout = '2s';
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
COMMIT;
```

3. Postgres updates stored index and constraint definitions automatically, but view definitions store column names and invalid views error on next use [judgment]. Check dependencies first:

```sql
SELECT DISTINCT dependent_rel.relname
FROM pg_depend d
JOIN pg_rewrite r ON r.oid = d.objid
JOIN pg_class dependent_rel ON dependent_rel.oid = r.ev_class
JOIN pg_attribute a ON a.attrelid = d.refobjid AND a.attnum = d.refobjsubid
WHERE d.refobjid = 'orders'::regclass AND a.attname = 'user_id';
```

4. Application queries, ORM models, and migration files that use user_id fail with "column does not exist" after the rename. For zero-downtime, the standard pattern is: add account_id as a new column, backfill, dual-write, then drop user_id. That is a bigger change than you asked for.

Assumption: the app can be deployed in step with the rename or tolerate brief errors on user_id queries. Why not measured: the material does not state it. Validate by: check whether code and rename deploy together. If wrong: use the add-column, backfill, drop pattern instead of a rename.

Alternative considered: adding a new column and copying data avoids downtime, but it takes table-size-proportional time and a multi-step migration. It loses here because you asked for a rename and the metadata-only command is the cheapest correct move if a brief deploy window is acceptable [judgment].
