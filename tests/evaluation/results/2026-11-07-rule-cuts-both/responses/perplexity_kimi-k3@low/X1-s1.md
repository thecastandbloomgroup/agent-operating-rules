Headline

Measure the summariser first, then fix the largest error class, because "sometimes wrong" gives no direction for a fix without data. Four points support this. Agent complaints do not identify which edits matter [judgment]. A labelled sample of summaries is the cheapest reliable signal. Prompt and model changes are high-variance without a baseline. A standing test set prevents regressions after each change.

Background

The support tool has an LLM summariser. Agents report it is sometimes wrong. No metrics, test set, or error taxonomy exists.

Relevance

Every change is a guess until errors are counted by type. Without a baseline, a fix can make quality worse and go unnoticed.

Information

LLM summary quality varies run to run, so acceptance tests need a metric, a baseline, a threshold, and a sample size [judgment]. Common error classes in this setting are: factual errors (hallucinated facts), omissions (missing key details), and staleness (outdated info quoted) [judgment]. There is no public benchmark for this specific summariser, so a labelled internal sample is the only usable evidence [no source].

Assumption: Support tickets are stored and reusable as test input. Why not measured: The material does not state it. Validate by: query the ticket store for 100 closed tickets. If wrong: build test set from live tickets instead.
Assumption: A small team can review summaries at roughly 30 per hour. Why not measured: Measuring costs more than the decision is worth. Validate by: time the first 20 reviews. If wrong: reduce sample to 100 and extend later.

Alternative considered: swap the model or rewrite the prompt immediately based on agent anecdotes. This loses because it has no baseline, so improvement cannot be confirmed and regression is undetectable [judgment].

1. Build the test set. Select 150 closed tickets at random. Write the acceptance test first: metric is agent-rated accuracy per summary, baseline is none yet, pass threshold is set after baseline, sample size is 150.
