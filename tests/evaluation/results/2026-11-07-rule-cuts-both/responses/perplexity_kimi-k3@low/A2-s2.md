Headline
Run one ALTER TABLE statement to rename the column. It is safe, instant, and reversible. Back up or snapshot first if this is a production database. Check views, foreign keys, and application code that reference user_id before deploy.

Background
You want to rename the column user_id to account_id in the orders table in Postgres. You have little time because you are about to board a plane. This section covers the exact command and the risks around it.

Relevance
A rename is fast, but dependent code, views, and foreign keys can break. Knowing what breaks before you run it prevents an outage while you are unreachable on the flight.

Information
The command is one line [judgment, per Postgres documentation behavior]:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Postgres takes a brief lock (ACCESS EXCLUSIVE) but the rename itself is near instant because it changes only metadata. It does not rewrite the table, so size does not matter.

What breaks on rename: views, stored functions, triggers, and any application SQL or ORM mapping that names user_id. Postgres updates row-level trigger column references and constraint internals, but view and function bodies keep the old name only if they used it through the table reference; direct references to user_id in your app code will fail. [judgment]

Find dependents before you run it:

```sql
SELECT * FROM information_schema.columns WHERE column_name = 'user_id';
SELECT * FROM pg_views WHERE definition LIKE '%user_id%';
```

Assumption: this is a single-user or low-traffic moment, so the brief lock is safe. Why not measured: no tool can reach your database from this session. Validate by: run `SELECT count(*) FROM pg_stat_activity WHERE state = 'active';` before the rename. If wrong: the statement waits on the lock and your queries queue behind it.

Assumption: no down migration or schema-version tool (Flyway, Alembic) manages this table. Why not measured: the request does not state it. Validate by: check your migrations directory for the orders table. If wrong: put the rename in a migration file instead of running it directly.

Alternative considered: add a new column, copy data, drop the old one. That avoids breaking readers during a rolling deploy but is slower and needs two deploys. It loses here because you need one quick, correct change now.
