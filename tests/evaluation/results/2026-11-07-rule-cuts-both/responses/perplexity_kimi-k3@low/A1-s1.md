# Headline

Yes, pin every version in the requirements file, and add hashes when the project is deployed rather than shared as a library.

1. Two build failures last month trace directly to unpinned dependencies, so the cause is identified.
2. Pins make each install reproduce the same environment, therefore the failure mode is removed.
3. Pins do not block updates, because a scheduled update run still moves versions forward under test.

# Background

The project installs dependencies from a requirements.txt file with no version pins. The build broke twice in the past month when upstream libraries released new versions.

# Relevance

Unpinned files re-resolve to whatever is newest at install time. Therefore every build is a new, untested dependency set, and this is the direct cause of the two breakages.

# Information

**Evidence**

- No version is pinned in the requirements file, so `pip install` selects the latest candidate for each package [1].
- Two build failures occurred last month after library updates ([no source], user report).
- The pip documentation provides `pip freeze` for capturing exact installed versions and the `--require-hashes` option for hash checking [2].
- PEP 440 defines the version specifiers, including the exact match operator `==` [3].

**Assumption log**

`Assumption: this project is a deployable application, not a library published for others to install. Why not measured: the material does not state it. Validate by: check whether the package is published to an index. If wrong: pin only in a lock file and keep the install_requires ranges open, per the alternative below.`

**Alternative considered**

Keeping ranges (for example `requests>=2,<3`) preserves flexibility for library consumers. It loses here because builds already broke twice under that approach, and the project needs reproducibility more than consumer flexibility [judgment].

# End

I recommend that we:

1. Run `pip install` in a clean environment, verify the app passes its test suite, then run `pip freeze > requirements.lock` to capture exact versions.
   - Blocker removed: no record exists of the last known-good dependency set.
   - Test: Given a clean virtual environment, When the lock file is generated and the test suite runs, Then every dependency appears with an exact `==` version and all tests pass.
   - Kind: deterministic. Cynefin: Clear. A standard practice (freeze) exists, so this is deduction from a known rule.
2. Replace requirements.txt with the pinned versions from Step 1, using the `==` operator.
   - Blocker removed: installs re-resolve to new versions.
   - Test: Given a clean environment, When `pip install -r requirements.txt` runs, Then it is repeatable and resolves the identical versions on a second run.
   - Kind: deterministic. Cynefin: Clear. Deduction from standard tooling behavior. Step 2 MUST NOT start until the test in Step 1 passes.
3. Add hashes to the file with `pip hashes` or a tool such as pip-tools, and require hashes at install time.
   - Capability added: a tampered or corrupted package fails the install.
   - Test: Given a pinned file with hashes, When one hash is changed, Then the install fails with a hash mismatch error.
   - Kind: deterministic. Cynefin: Clear. Deduction from documented pip behavior [2]. Step 3 SHOULD start only after Step 2 is merged.
4. Add a weekly job that runs the full update on a branch, installs fresh, and runs the test suite.
   - Capability added: updates arrive in a controlled, tested way instead of silently.
   - Metric and threshold: the suite passes on the updated branch before merge; baseline is the current build failure count of 2 per month; target is 0 surprise breakages over the next 2 months.
   - Kind: stochastic (dependency releases vary). Cynefin: Complicated. Several update tools exist, so analysis of the toolchain picks one; this step is induction from trials, and the pattern breaks if the test suite misses an update-related defect.
