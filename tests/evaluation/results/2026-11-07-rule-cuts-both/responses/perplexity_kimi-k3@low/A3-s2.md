Headline

Turn on gzip only when the client asks for it, the response is large enough, and the route does not echo secrets.  
Average JSON responses of 400 KB are large enough to compress on most API paths.  
CPU-cost and response-reflection risk are the two blockers that gate rollout.

Background

The API returns JSON, which this answer treats as JavaScript Object Notation text. The average response is about 400 KB before compression. The question is whether the server should enable gzip, a common HTTP content-coding format.

Relevance

Large text responses spend cost on network egress and client wait time. gzip can cut bytes for repetitive JSON, but the gain falls when links are fast or CPU is saturated.

JSON at 400 KB usually has repeated keys and nested structure, so gzip commonly reduces transfer size by a large margin [judgment]. The main tradeoff is CPU for compression against bandwidth and latency savings [judgment]. HTTP already lets the client advertise support through Accept-Encoding, so negotiated gzip avoids sending compressed bytes to clients that cannot read them [judgment]. Security risk rises when a response compresses attacker-controlled text in the same body as a secret, because size changes can aid guessing attacks [judgment].

The strongest alternative is to leave compression off to save CPU. It loses for 400 KB text responses because negotiated gzip is standard, reversible per response, and easy to limit by route and size [judgment]. A second alternative is Brotli, another HTTP content-coding format. It can compress better at higher cost, however gzip is the safer first step for broad client support [judgment].
