```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Quick notes before you fly:

- The rename takes an `ACCESS EXCLUSIVE` lock, but only for a moment since it's metadata-only. It will wait behind any open transactions touching `orders`, so check `pg_stat_activity` if it hangs.
- Indexes on the column follow the rename automatically (the index name stays as-is, e.g. `orders_user_id_idx`, unless you rename it too).
- Views that reference the column also follow the rename in Postgres, but stored query text in application code, ORMs (e.g. Rails `foreign_key:`, SQLAlchemy models), and raw SQL strings do not. Update those before or right after deploy, or queries will fail with `column "user_id" does not exist`.
- Foreign keys pointing to this column are unaffected (a rename doesn't break the constraint).
- Wrap it in a migration with a rollback (`RENAME COLUMN account_id TO user_id`) if your team uses migration tooling.

If zero downtime matters on a hot table, the safer path is: add `account_id` column, backfill, dual-write, then drop `user_id`. But if the app is down or traffic is low, the one-liner is fine.
