Headline

Close each retrospective with one owned change, then check that change at the next meeting.

First, score the last three meetings so the real failure is known.
Second, put one small action on the work board before people leave.
Third, start the next meeting with the status of that action.
Fourth, keep only changes the team can finish itself.

Background

A retrospective is a team meeting that reviews recent work and chooses a change. People still attend these meetings. Nothing in the work changes afterward. The request is for a way to make the meetings produce change.

Relevance

Each meeting that ends without a tracked change spends time and weakens trust. A closed loop can show a result in the next work cycle.

Information

Derby and Larsen end a retrospective when the team decides what to do [1].

Kerth requires safety before people name real problems [2].

An action with no owner and no date does not enter the next cycle [judgment].

Teams that skip the prior-action check repeat the same topics [judgment].

Assumption: actions are discussed but not tracked into the next cycle. Why not measured: The material does not state it. Validate by: read the last three action lists. If wrong: replace the board step with the safety probe.

Alternative considered: Stop retrospectives and improve only inside daily work. This loses because one tracked action can still change the next cycle [judgment].

End

I recommend that we take these steps.

1. In one session, score the last three retrospectives with the rubric below. This removes the unknown cause. The test comes first. Criteria and weights: owner named (30%), date named (20%), team can do it (30%), status checked later (20%). Pass threshold: 70 points. Evidence: the written action list from each meeting. Score each meeting, then name the failed criterion. Domain: Confused. Reason: the scores are needed before the cause can be classed. This step uses deduction from those scores.

2. Before the current meeting ends, add one action to the work board. This removes the gap between talk and work. The test comes first.
Given an open retrospective,
When the team agrees one change,
Then the board shows one owner, one due date, and a task small enough for one cycle.
Domain: Clear. Reason: the rule is known, so apply it. Step 2 MUST NOT start until Step 1 names the failed criterion. If Step 1 shows missing safety instead of missing tracking, skip Step 2 and run Step 4 first.

3. Open the next retrospective with the status of that board item. This removes repeat talk with no result. The test comes first.
Given the next retrospective has started,
When the facilitator asks for status,
Then the owner states done, not done, or blocked in one minute.
Domain: Clear. Reason: the check rule is known. Step 3 MUST NOT start until the test in Step 2 passes.

4. Spend 10 minutes on one safety probe in the same meeting as Step 2. This tests whether people can name real problems. The test comes first. Metric: mean score on "I can name a real problem here," scale 1 to 5. Baseline: no prior score. Pass threshold: mean at least 4. Sample size: every person present, one round. Stop if the mean is below 3, and do not push for harder topics. Budget: 10 minutes. Domain: Complex. Reason: trust shows its effect only afterward, so this is a small probe, and one bad question can break the pattern. Leverage is a guess. Run Step 4 in parallel with Step 2, inside the 10-minute cap.

Follow-up

If Step 1 shows the actions were owned and checked, replace Step 2 with a scope cut: one change the team controls.
If the safety mean stays below 3 for two meetings, stop topic votes and use an outside facilitator.
