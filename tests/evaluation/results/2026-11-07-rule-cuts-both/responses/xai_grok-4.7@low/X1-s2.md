Headline
Measure error types on real tickets before any model change, because an unmeasured edit cannot show a gain.

- A small labeled set turns "sometimes wrong" into a rate you can compare.
- The first fix follows the largest error class, not a guessed prompt rewrite.
- A change ships only when that rate falls on tickets the team did not use to tune it.
- Human labels stay the check, because automatic scores miss unsupported claims.

Background
Agents use a large language model (LLM) summariser in the support tool. They say summaries are sometimes wrong, and the team has no metrics. The request is to make the summariser better.

Relevance
Agents act on these summaries before they reply. A wrong summary can hide a constraint or invent a promise. Therefore the next change must cut a counted error, not a felt one.

Information
Neural abstractive summaries often include content the source does not support.
[1]

Automatic scores such as ROUGE also track human judgments of consistency only weakly, so a score rise is not proof of fewer wrong summaries.
[2]

Four error classes cover most agent complaints in support summaries: a missing required fact, an added fact, a swapped entity, and an unsafe next step [judgment]. The largest class is unknown here, so the first measurement must name it.

Assumption: "Wrong" means a claim the ticket text does not support. Why not measured: the material does not state the failure mode. Validate by: ask three agents to mark five bad summaries each. If wrong: replace the faithfulness rubric with the class they mark.

Assumption: no labeled set exists. Why not measured: the material says there are no metrics and does not mention labels. Validate by: search the tool repo and the annotation store for a gold file. If wrong: skip the new sample and score that set first.

Assumption: forty recent tickets can be labeled in one working session. Why not measured: ticket volume is not stated. Validate by: time ten labels, then scale. If wrong: label every ticket from the last seven days instead of a sample of forty.

Assumption: the summary is shown before the agent sends a reply. Why not measured: the material does not state the screen flow. Validate by: one walkthrough of the agent screen. If wrong: measure errors on the stored summary, not on the live decision.

Alternative considered: rewrite the prompt or swap the model now. That loses because there is no baseline, so the team cannot tell a real drop in errors from noise [judgment].

End
I recommend that we take these steps in order.

1. Write this rubric before any labels. Criteria and weights: faithfulness 50 percent (each claim has a ticket quote), coverage 30 percent (issue, impact, customer ask, and status), action safety 20 percent (the next step does not contradict the ticket). Pass for one summary: faithfulness is full and at least three coverage fields are present. Evidence: the ticket text plus one agent mark. Then label forty recent summaries in one session. This removes the blocker that "sometimes wrong" has no rate. Domain: Confused, because the error class is not known, so this step gathers what classifies the rest. Step 2 MUST NOT start until these forty labels exist.

2. Write a decision table before the choice. Options: tighten the prompt, force a quote for each claim, or extract fields then summarise. Musts: the option targets the largest class from Step 1, and one person can build it in one session. Score each option on fit to that class (weight 70) and build time (weight 30). Pick the highest score that meets both musts. This removes the blocker of an unchosen fix. Domain: Complicated, because cause and effect need this analysis, and more than one good practice exists. The inference is deduction from the Step 1 counts.

3. Write the acceptance test before the trial. Metric: share of summaries that fail faithfulness. Baseline: the Step 1 rate. Pass: the rate is at least 10 percentage points lower. Sample: thirty new tickets, one summary each, temperature fixed. Then run one safe-to-fail probe of the Step 2 option, with a stop if the gap is under 10 points, and a budget of one session. This adds a measured drop, not a hoped one. Domain: Complex, because the effect shows only after the trial. Leverage is a guess. Step 3 MUST NOT start until Step 2 names one option.

4. Write this check before you store the gate. Given a new weekly batch of twenty labeled tickets, When the faithfulness fail rate is computed, Then the batch fails if the rate is above the Step 3 pass rate. Then save the rubric, the labels, and that gate in the tool repo. This removes the blocker of a one-time win with no repeat check. Domain: Clear, because the rule is now known and the action is to apply it. Step 4 MUST NOT start until Step 3 meets its threshold.

Follow-up
If agents mark tone or policy breaks instead of unsupported claims, replace the faithfulness criterion in Step 1 and rerun the sequence. If fewer than forty tickets exist, label all of them and lower the Step 3 sample to fifteen. If the Step 1 rate is already under 5 percent, stop and treat the complaint as a display or trust problem, not a summary defect.
