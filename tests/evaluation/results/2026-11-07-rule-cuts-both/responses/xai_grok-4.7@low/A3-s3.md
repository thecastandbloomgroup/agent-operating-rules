The API returns JSON. The average body is 400 KB. The question is whether gzip should be on.

This size is past the point where compression pays. Callers on mobile and distant links wait on the transfer. A mid gzip level costs only a few milliseconds of CPU for a body of this size [judgment].

Compress only when the client accepts gzip. Skip bodies under 1 KB, because the framing cost can exceed the gain [judgment]. Skip data that is already compressed. Images and zip files are examples.

HTTPS adds one risk. A secret next to attacker-chosen text can leak through compression. Gluck, Harris, and Prado named this BREACH in 2013 [1]. Keep secrets off those routes, or skip compression there.

Assumption: the 400 KB figure is uncompressed JSON, and gzip is not already on. Why not measured: the material does not state it. Validate by: read Content-Encoding on ten live responses. If wrong: do not add a second compression pass.

The strongest alternative is to leave compression off and save CPU. That loses at this size, because network time dominates on a normal API path [judgment].
