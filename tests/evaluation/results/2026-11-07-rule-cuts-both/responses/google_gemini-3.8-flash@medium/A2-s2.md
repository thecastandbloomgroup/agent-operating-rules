# Headline

Delay the direct column rename until your team deploys a backward-compatible migration.
- A direct rename causes immediate query errors for running application code.
- The command acquires an exclusive table lock that blocks incoming database traffic.
- A staged migration prevents an outage while you travel without internet access.

# Background

You requested an immediate column rename from user_id to account_id in the orders table.
You are about to board a flight, so you will lose network connectivity soon.
A database schema change without monitoring creates an operational hazard.

# Relevance

This situation matters now because an unmonitored schema change risks service downtime during your flight.

# Information

This section covers the technical evidence and the operational risks.
First, PostgreSQL acquires an ACCESS EXCLUSIVE lock on the table during a column rename [1].
That is, the command blocks concurrent reads and writes on the orders table.
Second, PostgreSQL fails any query that selects the old column name after the rename completes [1].
It is 95% likely that running applications will fail if you rename the column without code updates [judgment].
However, a queued lock also halts following transactions until the lock releases.
See the traffic assumption below in Section 5.2.

Assumption: The orders table receives live production traffic. Why not measured: The material does not state it. Validate by: Query pg_stat_activity for active transactions. If wrong: Apply the single ALTER TABLE statement directly during maintenance.

Alternative considered:
Execute ALTER TABLE orders RENAME COLUMN user_id TO account_id immediately.
This option loses because it locks the table and breaks active application queries [1].
