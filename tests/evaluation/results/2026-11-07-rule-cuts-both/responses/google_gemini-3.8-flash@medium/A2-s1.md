### Headline

Do not execute a raw column rename in production before your flight departs.
First, a direct rename breaks all running application queries that reference the old column name [1].
Second, a zero-downtime migration requires an expand-and-contract phase with a temporary view or column alias [judgment].
Third, applying this change safely requires deployment coordination across both database and application code [2].

### Information

PostgreSQL supports the `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` command [1].
However, this operation immediately invalidates prepared statements, views, and application queries that read `user_id` [1].
The standard industry pattern for this change is the expand-and-contract pattern [2].
First, the database adds an alias view or a generated column [judgment].
Next, application services deploy code to use the new name [judgment].
Finally, the database drops the old reference after validation [2].
