## Headline

First measure errors against the source tickets, then test one targeted fix before release.

- Keep agents in control while the error rate remains unknown. [judgment]
- Separate factual errors, missing facts, and style complaints because each needs a different fix. [judgment]
- Compare the current summariser with a candidate on the same unseen cases. [judgment]

## Background

Agents report that the summariser is “sometimes wrong,” but you have no metrics. [1]
That report does not establish the error rate or identify the causes. [inference]

## Relevance

A prompt change alone cannot show whether summaries improve without a baseline and a repeatable test. [judgment]
Therefore, the first deliverable should combine a safety control with a small evaluation set. [judgment]

## Information

### What to measure

Use the ticket information available **when the summary was generated**, not facts added later. [judgment]

| Measure | Definition |
|---|---|
| Unsupported claim rate | Percentage of summaries containing a claim that the source does not support. |
| Contradiction rate | Percentage containing a claim that conflicts with the source. |
| Required-fact omission rate | Percentage missing a required fact that appears in the source. |
| Severe-error count | Errors that change the required action, customer commitment, or safety outcome. |
| Agent correction rate | Percentage that agents change because of a factual error or required-fact omission. |
| Response time | Time from summary request to completed summary. |

Treat style edits separately from factual corrections. Otherwise, the correction rate mixes preference with accuracy. [judgment]

## End

I recommend that we complete these four increments in order, with each increment capped at one working session.

### 1. Require agent approval before a summary drives customer-facing action

**Kind:** Deterministic.  
**Domain:** Clear, deduction from the known approval rule.

**Test first:**
```gherkin
Given a generated summary without agent approval
When an agent attempts to send it or trigger an action from it

```

**Work:** Add an “AI draft: verify against ticket” label and an approval gate wherever the summary triggers customer-facing action.

**Capability:** This prevents unreviewed use, but does not establish accuracy. [judgment]

**Budget:** One engineering session. Finish with a passing workflow test.

### 2. Create a traceable evaluation set and correction record

**Dependency:** Step 2 MUST NOT start until Step 1 passes.

**Kind:** Deterministic.  
**Domain:** Complicated, deduction from an analysis of the summary’s data path.

**Test first:**
```gherkin
Given 100 sampled summary requests
When the evaluation export completes
Then every record contains the exact source input, summary, and generation settings
```

**Work:** First inspect where the tool constructs the summary input. Then export 100 recent cases through approved internal access.

Include ticket identifier, model version, prompt version, and response time. Remove unnecessary personal data.

Randomly split the cases into 50 diagnosis cases and 50 unseen comparison cases. Keep the comparison cases separate from prompt development.

Add correction reasons: unsupported claim, contradiction, omitted fact, and style.

**Capability:** This creates a reproducible test and links future complaints to evidence. [judgment]

**Budget:** One engineering session. Finish with an export that passes the completeness test.

### 3. Establish the baseline and choose one failure to address

**Dependency:** Step 3 MUST NOT start until Step 2 passes.

**Kind:** Stochastic, because summary quality varies across requests.  
**Domain:** Complex, induction from sampled cases; rare ticket types can break the observed pattern.

**Acceptance test first:**

- **Metrics:** All six measures in the Information section.
- **Baseline:** Current summaries on the 50 diagnosis cases.
- **Sample size:** 50 cases, with two reviewers independently assessing 10.
- **Pass threshold:** Score every case; require at least 90% reviewer agreement on error categories.
- **Stop condition:** Stop interpretation if agreement fails; clarify the definitions before proceeding.

**Work:** Score each summary against its source. Mark required facts before assessing omissions: customer issue, current status, unresolved request, and next action, where present.

Resolve reviewer disagreements against the source. Then count errors by category and identify the most frequent category.

**Capability:** This replaces “sometimes wrong” with a measured failure pattern. [judgment]

**Budget:** One review session. Treat the pattern as a pilot finding, not a production-wide estimate.

### 4. Test one targeted candidate against the current version

**Dependency:** Step 4 MUST NOT start until Step 3 passes.

**Kind:** Stochastic.  
**Domain:** Complex, induction from paired trials; different ticket types or model changes can break the result.

**Acceptance test first:**

- **Metric:** Percentage of summaries with any unsupported claim, contradiction, or required-fact omission.
- **Baseline:** Current version on the 50 unseen cases.
- **Sample size:** 50 paired cases, producing 100 summaries.
- **Pass threshold:** At least 30% fewer erroneous summaries, with zero severe errors in candidate outputs.
- **Additional limits:** No increase in omission rate; response time no more than 20% above baseline.
- **Stop condition:** Reject the candidate if any limit fails.

**Work:** Select one change based on Step 3:

- For unsupported claims, require source-linked facts and explicit “not stated” fields.
- For contradictions, preserve speaker, chronology, and unresolved status in the input.
- For omissions, use fixed fields for the required facts.

Run both versions on identical inputs. Hide version names from reviewers.

**Capability:** This tests a specific repair without combining changes that obscure the cause. [judgment]

**Budget:** One implementation-and-trial session. Accept only after the full sample passes; otherwise retain the current version and approval gate.
