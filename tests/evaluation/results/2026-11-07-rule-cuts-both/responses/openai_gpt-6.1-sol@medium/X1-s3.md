## Headline

Measure the errors first, then test one targeted change before any wider release.

- Turn “sometimes wrong” into specific error types and measured rates.
- Compare changes against the current summariser on the same tickets.
- Keep experimental drafts away from customers until human review supports a limited pilot.

## Background

Your support tool includes an LLM-based summariser, and agents report that it is “sometimes wrong.” You have no metrics. [1]

No ticket examples or summary outputs accompany the request, so the evidence does not establish an error rate or cause.

## Relevance

A fluent summary can still misstate a customer’s problem, invent an action, or omit a needed next step. [judgment] Therefore, measure factual accuracy separately from readability. [judgment]

## Information

**First, define an error.** Use these categories:

- **Unsupported fact:** the summary states something the approved sources do not support.
- **Contradiction:** the summary conflicts with those sources.
- **Omission:** the summary leaves out information an agent needs.
- **Severe error:** an error changes the customer, payment, security, or promised action.

These categories provide a practical first review scheme, not a validated standard. [judgment]

**Next, test a narrow hypothesis:** requiring source support and explicit uncertainty reduces unsupported claims. This is a test proposal, not a claim of improvement. [judgment]

**Assumption:** An internal pilot is acceptable. **Why not measured:** The material does not state it. **Validate by:** Obtain the tool owner’s approval. **If wrong:** Stop before the experiment.

**Alternative considered:** Replace the model immediately. This loses because no evidence yet separates model errors from missing context, source conflicts, or prompt defects. [judgment]

The sample sizes, time limits, and thresholds below are proposed pilot controls. They are not established performance standards. [judgment]

## End

I recommend that we complete these three steps in order:

### 1. Create a traceable review set

**Kind:** Deterministic.  
**Domain:** **Confused**, because the available evidence cannot distinguish the causes; gather records before classifying the failure.

**Test first:**

```gherkin
Given 30 approved, recent support tickets
When the review set is exported
Then each record contains the exact summariser input and output
Then each record identifies the model and prompt version
Then 10 records form the development set and 20 form the held-out set
```

**Work:** In one session, capture those records through approved internal systems.

Select consecutive eligible tickets, rather than only complaints, to reduce selection bias. [judgment] Link known complaints separately for diagnosis.

**Capability added:** Reviewers can trace each claim to the input the summariser actually received.

Keep the held-out set separate; do not use it to revise the prompt.

### 2. Establish the baseline and choose one defect to address

Step 2 MUST NOT start until Step 1 passes.

**Kind:** Evaluative.  
**Domain:** **Complicated**, because expert review can identify errors through source comparison and deductive analysis.

**Rubric first:** Use a weighted decision matrix.

| Criterion | Weight | Evidence required |
|---|---:|---|
| Factual accuracy | 50% | Each factual claim matches an input passage |
| Completeness | 30% | Summary includes the request, current status, and next action when available |
| Usability | 20% | Agent can understand the summary without rewriting it |

Score each criterion as 0, 0.5, or 1: failed, partly met, or fully met. Multiply by its weight.

**Pass threshold:** At least 90%, with no unsupported fact, contradiction, or severe error.

**Work:** In a two-hour session, have an experienced agent score the 30 baseline summaries against their inputs.

For each score, record the supporting passage or missing fact. Have a second reviewer check severe errors and disputed scores.

Record:

- Summaries with any factual error, divided by summaries reviewed.
- Summaries with a severe error, divided by summaries reviewed.
- Summaries with an omission, divided by summaries reviewed.
- Mean rubric score.

Then choose the most frequent error category from the development set. Record its count, examples, and proposed cause.

**Blocker removed:** “Wrong” becomes a measured defect with evidence.

If the session ends before review finishes, record the incomplete sample and pause Step 3.

### 3. Run one capped, internal experiment

Step 3 MUST NOT start until Step 2 produces the baseline and a target defect.

**Kind:** Stochastic, because model outputs vary.  
**Domain:** **Complex**, because improvement requires trials; new ticket types can break the observed pattern.

**Acceptance test first:**

- **Sample:** The same 20 held-out tickets, with one candidate summary per ticket.
- **Baseline:** Current summaries for those tickets, scored in Step 2.
- **Primary metric:** Number of summaries with a factual error.
- **Pass threshold:** Fewer factual-error summaries than baseline.
- **Guardrails:** Zero severe errors, no increase in omissions, and no decrease in mean rubric score.

**Work:** Change one prompt rule aimed at the chosen defect. Keep the model, input selection, and output format fixed.

For unsupported claims, require the summariser to omit claims without source support. Require it to mark missing information as “not stated.”

Have reviewers score candidate and baseline summaries without seeing which version produced each output.

**Budget:** One candidate, 20 generations, and two reviewer-hours. Keep candidate drafts internal.

**Stop condition:** Stop on a severe error or exhausted budget. Reject the candidate if any acceptance condition fails.

**Capability added:** Evidence for accepting or rejecting one change.

Leverage remains a guess until the trial finishes. Passing supports a larger internal trial, not a claim of production reliability. [judgment]

## Follow-up

If errors come from missing or conflicting inputs, replace the prompt experiment with a source-selection experiment. [judgment]

If payment, security, or promised-action errors dominate, require specialist review before further trials. [judgment]
