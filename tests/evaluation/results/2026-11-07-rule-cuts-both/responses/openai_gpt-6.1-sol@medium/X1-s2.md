### 2. Measure the current summariser

### 3. Test one targeted candidate

Step 3 MUST NOT start until Step 2 passes.

**Kind:** Stochastic.  
**Domain:** Complex, because a change can fix one error while creating another.

**Acceptance test first:**

Compare both versions on the 30 held-out tickets, with two runs per ticket.

Use these provisional release thresholds: [judgment]

- False-claim rate falls by at least 30% relative to the baseline.
- Serious-error count equals zero.
- Missing-fact rate does not increase.
- Median review burden does not increase.
- Mean response time and cost increase by no more than 10%.

If the baseline false-claim rate equals zero, require zero candidate false claims instead.

**Work:** Change only the instruction linked to the main development-set failure.

For example, prohibit unsupported resolution claims if the baseline invents successful outcomes. Require an explicit “not stated” value when the source lacks the requested fact. [judgment]

**Increment:** One candidate prompt and a matched comparison, capped at 80 model calls and four reviewer hours.

**Stop condition:** Reject the candidate after any serious error.

**Capability added:** A measured basis to retain or reject the change. [judgment]

This probe’s leverage remains unproven until the comparison passes. [judgment] Treat a pass as grounds for an agent-reviewed pilot, not proof of rare-error safety. [judgment]
