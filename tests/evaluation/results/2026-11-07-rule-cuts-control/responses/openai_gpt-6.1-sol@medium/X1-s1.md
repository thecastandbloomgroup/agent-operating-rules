## Headline

Make the summariser measurable first, then test one targeted fix before release. [judgment]

- Keep agents responsible for checking summaries while error rates remain unknown. [judgment]
- Build a small benchmark that separates wrong facts, missing facts, and unsupported claims. [judgment]
- Release a change only when it passes a fixed comparison against the current version. [judgment]

## Background

Agents report that the summariser is “sometimes wrong,” but you have no metrics. [1] This supports an investigation, not a diagnosis.

## Relevance

A fluent summary can still contain false information, so fluency alone cannot establish quality. [2] Therefore, the next step should produce evidence rather than another prompt revision. [judgment]

## Information

### Define “wrong”

Use these separate error classes. Count each error once, under its best match. [judgment]

| Error class | Definition | Example |
|---|---|---|
| Incorrect fact | Contradicts information available to the summariser | Says a refund succeeded when it failed |
| Unsupported claim | Adds information absent from that input | Invents a promised callback |
| Missing fact | Leaves out information needed for the next support action | Omits an unresolved payment failure |
| Presentation defect | Facts remain correct, but the format impedes use | Buries the next action in repeated text |

Mark an error **material** when it can change the agent’s next action or a customer commitment. [judgment]

Also separate two causes: required information never reached the model, or the model mishandled information it received. The fixes differ. [judgment]

### Measures

Use these pilot measures, with the current version as the baseline. All thresholds below are proposed acceptance rules, not measured results. [judgment]

- **Material-error rate:** summaries with at least one material error divided by summaries reviewed.
- **Required-fact coverage:** required facts correctly included divided by required facts in the reference.
- **Review time:** seconds an agent needs to check and correct each summary.
- **Generation time:** seconds from request to completed summary.

Record error classes separately. Otherwise, fewer invented facts can conceal more missing facts. [judgment]

**Confidence:** Low confidence about the cause, because no examples, model inputs, or measured outputs appear in the request.

**Assumption:** Authorized staff can access recent tickets and exact model inputs. **Why not measured:** The material does not state it. **Validate by:** Retrieve one permitted example. **If wrong:** Start with access approval or synthetic cases; defer production-quality claims.

**Alternative considered:** Rewrite the prompt immediately. It loses because no baseline exists to distinguish improvement from a change in error type. [judgment]

## End

I recommend that we complete these three actions, each within one working session.

### 1. Create a protected pilot benchmark

**Kind:** Deterministic. **Domain:** Confused, because the available evidence does not identify the failure source.

**Test first:**

```gherkin
Given recent tickets and the summariser's exact inputs
When the pilot benchmark is checked
Then every case has a source-backed reference and an error rubric
```

**Work:** Create 30 cases: 15 randomly selected recent tickets and 15 agent-reported failures. Record selection method for each case. [judgment]

Include required facts, source passages, actual model input, current output, and a material-error definition. Keep the random and reported-failure results separate.

Use only approved data access. If summaries trigger customer messages or ticket changes, require agent approval during the pilot. [judgment]

**Increment and blocker:** A checked benchmark replaces vague complaints with reproducible cases.

**Budget:** One session, capped at four staff-hours. If incomplete, reduce the case count and record the limit. [judgment]

### 2. Measure the current version

Step 2 MUST NOT start until Step 1 passes.

**Kind:** Stochastic, because model outputs can vary.  
**Domain:** Complicated, because source comparison and error analysis can identify specific defects.

**Acceptance test first:**

- **Metric:** Review completion.
- **Baseline:** Zero reviewed pilot outputs.
- **Pass threshold:** Every planned output has an error label, coverage score, and time measurement.
- **Sample:** Three runs for each benchmark case, or 90 outputs for 30 cases. [judgment]

**Work:** Run the current version without changing its settings. Have an agent compare each output with the reference.

Have a second agent check every material-error label. Resolve disagreements against the ticket evidence.

For each material error, check whether the necessary evidence reached the model. Then rank error classes by affected summaries. [judgment]

**Increment and blocker:** A completed baseline identifies the largest observed defect and prevents unsupported claims of improvement.

**Budget:** One session, capped at four staff-hours. No release decision follows from incomplete review. [judgment]

### 3. Test one targeted change

Step 3 MUST NOT start until Step 2 passes.

**Kind:** Stochastic.  
**Domain:** Complex, because trials establish the effect; different ticket types can break the observed pattern.

**Acceptance test first:**

- **Baseline:** Step 2 results on the same cases.
- **Sample:** Three runs per case with the candidate version.
- **Pass threshold:** At least 50% fewer material-error summaries.
- **Additional gates:** No lower required-fact coverage; no higher median review time.
- **Speed gate:** Median generation time stays within 20% of baseline. [judgment]

Score random cases and reported failures separately. Both groups must pass. If baseline material errors equal zero, expand the benchmark instead of claiming improvement. [judgment]

**Work:** Change only the component linked to the largest observed defect:

- Missing source evidence: correct input selection.
- Misread available evidence: revise instructions or summary structure.
- Unsupported claims: require source-linked facts and explicit “not stated” responses.
- Presentation defects only: revise the output format.

**Increment and blocker:** One measured candidate tests a specific cause without committing a full release.

**Budget and stop condition:** Cap the probe at four staff-hours and one candidate. Stop if any acceptance gate fails. [judgment]

Even after a pass, retain agent review. This small pilot does not establish a production-wide error rate. [judgment]

## Follow-up

If different agents disagree about required facts, settle that reference before testing model changes. [judgment]

If the candidate passes, test it on fresh tickets before expanding use. Otherwise, repeated use of the same cases can favor benchmark-specific changes. [judgment]
