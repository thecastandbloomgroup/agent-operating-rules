### Headline

Build an evaluation set from recent support tickets before changing the summarizer prompt.
- Establish an error baseline by auditing 50 support summaries with agents.
- Add an in-tool agent feedback widget to track daily accuracy metrics.
- Refactor the system prompt with grounding constraints to eliminate factual errors.

### Background

Your team deployed a large language model summarizer to your support tool. Support agents report that the generated summary is sometimes incorrect. The system currently operates without error metrics, accuracy tracking, or test benchmarks.

### Relevance

You cannot fix the summarizer without knowing how and when it fails. Developing measurable baselines now prevents repeated prompt changes that cause new errors.

### Information

Support agents state that summaries contain factual mistakes [judgment]. Because no logging exists, the exact failure rate remains unmeasured [judgment]. Research demonstrates that unsupported model summaries often stem from ungrounded prompts [19]. 

Assumption: Agent error reports stem primarily from source hallucination rather than missing context. Why not measured: The material does not state it. Validate by: Audit 50 flagged summaries with agents. If wrong: Shift focus from grounding rules to context window expansion.

Alternative considered: Fine-tuning a smaller open-source model on historical tickets. That alternative loses because it requires labeled data that does not exist yet and costs more engineering time.

### End

I recommend that we take the following three actions.

1. Categorize error types from historical tickets.
   - Increment: Review 50 agent-flagged summaries in one collaborative workshop session.
   - Blocker removed: Removes the lack of error taxonomy and baseline data.
   - Test (evaluative):
     - Rubric criteria: Factual accuracy (40%), omission of key issue (30%), formatting compliance (30%).
     - Pass threshold: 100% of reviewed samples categorized with supporting transcript quotes.
     - Evidence: A recorded spreadsheet with agent notes and assigned error categories.
   - Cynefin domain: Confused. The domain is confused because you cannot classify the causes of failure until you gather structured agent observations.

2. Add a binary feedback widget to the agent interface.
   - Dependency: Step 2 MAY run in parallel with Step 1.
   - Increment: Insert thumbs-up and thumbs-down buttons with a text field beside each summary.
   - Capability added: Adds continuous metric collection directly from daily agent workflows.
   - Test (deterministic):
     Given an agent views a generated summary
     When the agent clicks the thumbs-down button
     Then the system stores the ticket identifier, the summary text, and the timestamp in the database.
   - Cynefin domain: Clear. Deduction from known software engineering standards confirms this user interface pattern captures feedback reliably.

3. Refactor the summarizer prompt with strict source-grounding constraints.
   - Dependency: Step 3 MUST NOT start until the test in Step 1 passes.
   - Increment: Update the system prompt to instruct the model to cite transcript lines and refuse unstated claims.
   - Capability added: Prevents unsupported claims and reduces agent correction time.
   - Test (stochastic):
     - Metric: Summary error rate.
     - Baseline: Error rate measured in Step 1 (assumed at 20%).
     - Pass threshold: Less than 5% error rate.
     - Sample size: 50 held-out evaluation tickets.
   - Cynefin domain: Complicated. Cause and effect require prompt engineering expertise and systematic trial analysis.
