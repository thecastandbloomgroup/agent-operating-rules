Headline

Close the action loop before you change the retrospective format.

Past notes show whether each change had an owner and a done check.
One small change per cycle is easier to finish than a long list.
The next meeting must score the last change before new talk starts.
A new format helps only after this loop already works.

Background

A retrospective is a regular meeting where the team looks for better ways to work.
The team still holds these meetings, and people still attend.
The team reports that nothing shifts after them [1].

Relevance

A meeting with no later change trains the team to stay silent.
Therefore the next retrospective is the cheapest test of a fix.

Information

This section covers evidence, then the assumption, then the alternative.

The Scrum Guide states that the team addresses the top improvements as soon as possible [2].
The same guide states that these improvements can enter the sprint backlog, that is, the work list for the next cycle [2].
Derby and Larsen describe the retrospective as a path to one concrete experiment [3].
Therefore the useful output is a change in the next work plan, not a longer discussion [judgment].

One theme covers the request: people attend, but work does not change [1].
The Scrum Guide supports a loop of choose, do, and check [2].
Derby and Larsen support that same loop [3].
No source in this material disagrees.
The theme still sets the first fix, because an open loop blocks every later format change [judgment].
Confidence is low, basis: one team report and no action log [1].

Assumption: follow-through is the main gap, not safety or format.
Why not measured: the material does not state it.
Validate by: review the last four notes for owner, date, and done status.
If wrong: use an outcome metric when changes were done, or fix safety when notes lack issues.

The strongest alternative is a new meeting design and a new facilitator.
It loses because people already attend, so the agenda is not the first blocker [judgment].
See the assumption above if that judgment is false.

Snowden and Boone state that an unclear domain calls for more information before a response [4].
Therefore the first step gathers facts before a format change.

End

I recommend that we take four steps.

Step 1 comes first because the failure mode is not known yet.
Kind: deterministic.
Given the last four retrospective notes,
When each change is marked for owner, date, and done status,
Then the record shows one result: no owner, not done, or done with no effect.
Do this review in one working session.
Blocker removed: an unknown cause.
Domain: Confused, because cause and effect are not visible yet, so the team gathers facts first.
The inference is deduction from the unclear-domain rule [4].

Step 2 runs in the same session as Step 1 and does not wait on its result.
Kind: stochastic.
Metric: count of work issues on paper that speech did not name.
Baseline: issues named in the spoken part of the same meeting.
Pass threshold: at least three such issues.
Sample size: one meeting and every person present.
Ask each person to write one issue the group does not say aloud.
Budget: 15 minutes and one meeting.
Stop if the group will not write.
Blocker checked: hidden issues that speech does not show.
Domain: Complex, because cause and effect show up only after the probe.
The inference is induction from one trial, and a silent group can break the pattern.
Leverage is a guess.

Step 3 MUST NOT start until Step 1 shows no owner or not done.
Kind: deterministic.
Given one change from the last retrospective,
When the team adds it to the next work plan with one owner and a date in this cycle,
Then the plan shows that owner and that date before the cycle starts.
Do this in one planning session.
Blocker removed: changes that never enter the work plan.
Domain: Clear, because a known rule says to address the top change in the next cycle [2].
The inference is deduction from that rule.

Step 4 MUST NOT start until the Step 3 test passes.
Kind: deterministic.
Given the owned change from Step 3,
When the next retrospective starts,
Then the team scores that change done or not done before any new topic.
Use the first ten minutes of that retrospective.
Blocker removed: no check on the last change.
Domain: Clear, because the same rule requires a later check of the improvement [2].
The inference is deduction from that rule.

Follow-up

If Step 1 shows done with no effect, replace Step 3 with one outcome metric for one cycle.
If Step 2 yields fewer than three new issues, pause Steps 3 and 4 and repair safety first.
No open question remains, because the notes review answers the branch.
