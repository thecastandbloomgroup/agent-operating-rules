## Headline

Retrospectives stop producing change when actions lack owners, tracking, and a follow-up loop. Make each meeting deliver one owned action, put it in the team backlog, and review it first at the next meeting.

- Unowned actions die the same day, because no one carries them past the meeting.
- Actions outside the backlog lose to planned work, because the board is where the team looks each morning.
- Facilitators who accept five actions at once get zero completed actions.
- No review of the last action means no cost for breaking a commitment.

## Background

The team holds retrospectives, people attend, and the output does not change any practice. The request asks for a way to make the meetings produce executed changes.

## Relevance

A retro that changes nothing consumes roughly 1 hour per person per cycle and teaches the team that commitments are optional. That habit spreads to other ceremonies because it is visible to everyone.

## Information

**Evidence.** Derby and Larsen state that a retrospective should end with experimental actions, tried for a limited time, with a planned check on the result [1]. The common failure pattern is actions recorded on a wall or in a document that no one reads again. Kua states that visible follow-through on retrospective actions decides whether the team treats the meeting as real work [2]. Both sources agree on the mechanism: the output must be small, owned, and reviewed. The claim that this team generates more actions than it completes rests on the description above [judgment].

Validate by: ask the scrum master or look at the board. If wrong: use a separate one-line action list that the facilitator reads aloud at the start of each retro.`

`Assumption: Retro actions currently have no owner or due date. Why not measured: the material does not state how actions are recorded. Validate by: read the notes from the last three retros. If wrong: ownership exists, and the blocker is scheduling, so give the action a slot in the sprint like any task.`

`Assumption: The baseline action completion rate is near 0. Why not measured: no data exists in the material. Validate by: count completed actions from the last three retro notes. If wrong: some actions complete, so the fix is to protect and grow that count instead of starting from scratch.`

**Alternative considered.** Change the retro format: new activity, new facilitator, rotating structure. This loses because format churn does not create ownership or a review loop. The two sources above [1], [2] point at follow-through as the mechanism, not at the meeting activity.

## End

I recommend that we make each retrospective deliver one owned action, tracked in the backlog, and reviewed at the start of the next meeting.

1. **Limit the output.** Increment: end each retro with at most one action, one named owner, and one due date. Blocker removed: action overload, so nothing gets carried. Test, write before the meeting and check at the close:
   ```gherkin
   Given a retro has ended
   When the facilitator closes the meeting
   Then the notes show one action with an owner and a due date
       Or the notes show "no action this time" with a reason
   ```
   Owns the test as zero-cost observation of each meeting close. Kind: deterministic. Domain: Clear, because the rule is known to everyone and the action is one step.

2. **Put the action on the board.** Increment: create a card for the action in the team backlog, same as a work item, before the retro ends. Blocker removed: actions outside the backlog get no scheduling. Test:
   ```gherkin
   Given the team recorded one retro action
   When the team plans the next cycle
   Then the action card appears in the backlog
       And it gets a slot like a work item
   ```
   Works only if the backlog assumption holds; otherwise use the fallback in the log. Kind: deterministic. Domain: Clear, deduction from the tracking rule [1].

3. **Open the next retro with a review.** Increment: spend the first 5 minutes on the previous action: done, not done, or dropped with a stated reason. Blocker removed: no cost for breaking a commitment, so commitments stay optional. Dependency: the test in Step 1 must pass first, because Step 3 needs an action to review. Test:
   ```gherkin
   Given a new retro starts
       And the previous retro recorded an action
   When the facilitator opens the meeting
   Then the team states the action status: done, not done, or dropped
       And a dropped action carries a written reason
   ```
   Kind: deterministic. Domain: Clear, one known step, leverage comes from making the loop visible (higher leverage than Step 2, because it closes the cycle).

4. **Run a capped probe on why actions die.** Increment: after each of the next 4 retros, ask one anonymous question: "What stopped the last action?" Metric: action completion rate per retro. Baseline: 0%, from the assumption log [judgment]. Pass threshold: 50% at 4 retros. Sample size: 4 meetings, one question each, so the budget is under 30 minutes of team time. Stop condition: stop asking if two consecutive retros reach the threshold. Leverage is a guess here. Kind: stochastic. Domain: Complex, because the cause of stalled actions is visible only after the data arrives; the probe induction could break if people answer in order to please the facilitator, so anonymity is the control.

Steps 1 to 3 are ordered by leverage and start at the next retro. Step 4 runs in parallel, capped at its 4-meeting budget.

**Condition that changes this recommendation.** If the last three retro notes already show owners and due dates, skip Steps 1 and 2 and start with Step 3 plus a probe into scheduling pressure.
