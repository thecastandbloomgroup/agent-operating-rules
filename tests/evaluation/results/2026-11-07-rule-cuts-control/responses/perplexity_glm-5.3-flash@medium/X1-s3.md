## Headline

Measure before you fix: label a sample of summaries, compute error rates per type, then fix the top error type and retest.

1. "Sometimes wrong" gives no target until agents label about 100 summaries against the ticket transcript.
2. Label each bad summary in one of three types: wrong or invented content, missing key content, wrong size or tone.
3. Fix the largest error type with prompt guards, then verify with a fresh labeled sample of 100.
4. Add a vote button on every summary so the error rate becomes trackable over time.

## Background

An LLM-based summarizer now runs inside a support tool. Agents report intermittent errors. No metrics exist, so the severity is unknown and any prompt change cannot be verified.

## Relevance

Without a baseline error rate, every fix is a guess and agents lose trust in the tool. One labeled sample turns the report "sometimes wrong" into numbers per error type.

1. Factuality is a known weakness of abstractive summarizers. A peer-reviewed evaluation study reports factual non-consistency as a core flaw, and it built human labeling plus automatic metrics to measure it [1].
2. Therefore the expected dominant error is factual invention, likely (66 to 100 percent), basis: the study above [1]. Verify this in Step 1; the tool may behave differently [judgment].
3. No other evidence exists because the conversation supplied no data and no sample.
