# Headline

Make the summariser better by measuring first: audit a sample of summaries to define "wrong", publish a baseline, change the prompt as a capped probe, and let agents flag errors from the tool.

1. No metrics exist, so no change can be proven; a graded sample creates the baseline. [inference]
2. "Sometimes wrong" is an anecdote; a sample of 40 summaries turns it into counts. [judgment]
3. A prompt change is a probe in a Complex domain, so it needs a stop condition and a budget. [inference]

# Background

A support tool now generates ticket summaries with an LLM. Agents report that summaries are wrong at times. No measurement exists, so the error rate and the error types are unknown.

# Relevance

Agents use summaries to answer tickets, so a false fact can reach a customer as a claim. A baseline also decides whether every future prompt edit helps or hurts.

# Information

Error classes decompose into three parts that do not overlap and cover the whole: false facts that the ticket does not contain, true facts that the summary drops, and wrong emphasis between facts. Each reported error fits one class. [judgment]

Thematic analysis of graded samples supports this split; published guidance for grouping qualitative data comes from Braun and Clarke [3]. Contextual design methods support grading output inside the real work of agents [4].

Assumption log:

- Assumption: "Wrong" means a false fact, a missing fact, or a wrong emphasis. Why not measured: the user has not answered. Validate by: the audit in Step 1. If wrong: rebuild the rubric before Step 2.
- Assumption: past summaries and ticket texts are stored, so a sample exists. Why not measured: the material does not state it. Validate by: query the store for one week of tickets. If wrong: grade new summaries for one week to build the sample.
- Assumption: one agent can grade 40 summaries in one session. Why not measured: measuring costs more than the decision is worth. Validate by: time one agent grading 10 summaries. If wrong: cut the sample to 20 and widen the interval between tests.

Alternative considered: an LLM judge evaluates summaries automatically. It loses because a judge needs human labels for calibration, and those labels do not exist before the sample audit. [judgment]

# End

I recommend that we take these four actions in order:

1.
 Audit 40 sampled summaries from the last week. Blocker removed: "wrong" has no definition. Test: a rubric with three criteria, factual accuracy (weight 0.6), completeness (weight 0.3), emphasis (weight 0.1), pass threshold 90% of summaries score zero on false facts, evidence per criterion is the ticket text next to the summary. Domain: Confused [18], because the error type is unknown, so the action gathers materials for classification through the rubric itself. Output: counts per error class and the worst cases.

2.
 Publish the baseline metric from the audit counts. Blocker removed: no number to compare against. Test in Gherkin [14]:

```gherkin
Given 40 labeled summaries
When an auditor applies the counting rules from Step 1
Then the report shows the false fact rate, missing fact rate, and emphasis rate with exact numbers
```

Domain: Clear, because Step 1 has produced known rules, so this applies them. This step MUST NOT start until Step 1 produces the counts.

3.
 Change the prompt as a probe. The new prompt orders the model to use only facts from the ticket, to skip unknown facts, and to link each line to the ticket text. Blocker removed: the main false fact path. Test, written first, stochastic: metric is the false fact count per 40 summaries, baseline is the Step 1 count, pass threshold is at least 50% fewer, sample size is 40 new summaries, stop condition is a rising count, budget is one working session plus a revert. Domain: Complex [18], because prompt changes show effects only after trials, so this runs as a safe to fail probe, and the leverage claim is a guess. This step MUST NOT start until Step 2 sets the baseline.

4.
 Add an agent flag, one click for "wrong" and one for "missing", into the summary view. Blocker removed: feedback ends after the manual audit. Component added: a growing labeled set. Test in Gherkin [14]:

```gherkin
Given an open ticket with a generated summary
When an agent clicks "wrong" or "missing"
Then the flag, ticket ID, and summary text are stored with a timestamp
```

Domain: Clear, because it is one known step with a fixed rule.

Order: Step 1 first, because it is Confused and its output decides the rest. Step 2 and Step 3 follow Step 1. Step 4 runs in parallel from day one. Condition that changes this plan: if the audit shows all false facts occur in tickets longer than 20 messages, replace Step 3 with a prompt rule that limits summary length.

# Follow-up

Conditions that change the recommendation:

- The assumption about the meaning of "wrong" is false; the rubric changes first.
- Stored samples do not exist; the audit waits one week to collect data.
- Agents grade fewer than 20 summaries per week; the pass threshold stays at 50% but the interval between tests widens.
