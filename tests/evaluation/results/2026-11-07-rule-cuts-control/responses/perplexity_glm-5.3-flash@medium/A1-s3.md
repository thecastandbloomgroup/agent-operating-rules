## Headline

Pin the versions. Unpinned requirements let any install pull the newest release, so an upstream change breaks the build without a code change [1]. Two breakages in one month match that behavior [judgment, see the assumption log]. Pin each direct dependency to an exact version, and lock the full dependency tree beside it [2].

## Background

The project has a requirements.txt with no version pins. Two builds failed last month after a library update. The question is whether to pin versions in requirements.txt.

## Relevance

The build fails today, and it will fail again on the next upstream release. A pin change is a small, low-risk edit that removes repeat breakage [1].

## Information

**Evidence.** The pip requirements file format supports exact specifications of the form `package==version` [1]. The pip installer selects the newest version that satisfies each unpinned requirement [1]. The Twelve-Factor App guides developers to declare dependencies explicitly so that builds are reproducible across machines [2]. Because unpinned installs fetch new releases, the failure pattern in both breakages fits silent upstream changes [judgment].

**Assumption log.**

- Assumption: both failures came from an install pulling a newer library version, not from a code change. Why not measured: the material does not state the cause. Validate by: run `pip freeze` in the last working build and in the broken build, then diff the outputs. If wrong: pinning will not fix the cause, so the fix depends on the diff result.
- Assumption: dependency updates enter through ordinary installs, not through a cron job or script that upgrades packages on purpose. Why not measured: the material does not describe the update path. Validate by: read the build and deploy scripts for `pip install -U` or similar upgrade flags. If wrong: pinning also blocks that script, so review it in the same change.

**Alternative considered.** Pin with ranges of the form `>=x.y` instead of exact versions. This loses because a range still admits new releases, so it only slows the breakage pattern instead of stopping it [judgment: ranges admit newer versions by definition, per the specification in [1]].

Confidence in the recommendation is high, because the pip rules are documented [1] and both failures followed a library update.

## End

I recommend that we pin and lock the dependencies, then add a build gate. Steps run in this order.

1. **Pin direct dependencies.** Increment: edit requirements.txt in one session and add an exact `==` version to every direct dependency. Blocker removed: installs stop pulling new releases of those packages. Test, written first [1]:
```gherkin
Given requirements.txt lists <package> with "<version>" pinned
When pip install runs in a fresh venv
Then pip freezes <package> at the pinned version
```
Kind: deterministic. Cynefin: Clear, because the rule "exact pin stops upgrades" is a documented best practice [1]; deduction from a known rule.

2. **Lock the transitive tree.** Increment: run a dependency lock tool such as pip-compile in one session, then commit the generated lock file. Blocker removed: upgrades of dependencies of dependencies, which Step 1 cannot stop. Test, written first:
```gherkin
Given the committed lock file
When pip install runs in a fresh venv
Then every installed package matches a version in the lock file
```
Kind: deterministic. Cynefin: Complicated, because more than one lock tool exists, so a short analysis must pick one; induction from a trial run names what could break the pattern, a tool that misses the full tree. Step 2 MUST NOT start before Step 1 finishes.

3. **Gate the build in CI.** Increment: add one CI job, in one session, that installs from the lock file in a fresh environment and runs the test suite on every merge request. Blocker removed: installs that succeed but fail at import time or at test time. Test, written first:
```gherkin
Given the lock file and the existing test suite
When CI installs from the lock and runs the suite
Then the job fails when any test fails, and passes only on green
```
Kind: deterministic. Cynefin: Complicated, because the CI platform choice needs analysis; deduction from the platform's own test rules after that analysis. Step 3 MUST NOT start before the lock file in Step 2 is committed.

Upgrades do not stop; they become explicit. Because versions now stay fixed, schedule a deliberate bump and test cycle, for example monthly, so the pins do not rot.

**Conditions that change the recommendation.** If the diff shows a code change caused a failure, treat that failure separately; the pinning steps stay unchanged. If the project moves to Poetry or uv, replace pip-compile with that tool's own lock command.
