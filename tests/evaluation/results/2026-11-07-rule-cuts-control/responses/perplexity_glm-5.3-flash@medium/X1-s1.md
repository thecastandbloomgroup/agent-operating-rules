# Headline

Agent feedback is unusable for tuning until "wrong" is turned into named error types with counts. Build a labeled sample, measure the error rate, fix the top error type, and keep a weekly check in place.

- First, label a sample of summaries against their source tickets and classify the errors.
- Then, measure how often each error type occurs and set a pass threshold.
- Then, change one variable at a time and re-run the same test on the same sample.
- Finally, add source links to each summary line and a weekly spot check.

# Background

A support tool uses an LLM (a large language model) as a summariser. Agents report that the summaries are "sometimes wrong". The team has no metrics, so no one can say how often wrong happens or in what way.

# Relevance

Without a measure, any prompt or model change is a guess. A change can fix one error type and cause another [judgment].

# Information

**Analysis.** An LLM summariser is a stochastic system: the same ticket can give a different summary on each run. So the work needs a labeled test set and a metric, not one-off review. This is the acceptance-first rule for stochastic systems: metric, baseline, threshold, and sample size before the trials [14], [15].

Common error types for LLM summaries fall into three groups [inference, based on the taxonomy of fact errors in text generation]:

1. Hallucination: a summary line states a fact that is not in the ticket.
2. Omission: a fact that the ticket states is absent from the summary.
3. Misattribution: a fact is present but linked to the wrong person, ticket, or date.

Thematic analysis supports building such a taxonomy from worker comments: group statements into themes and count the sources for each theme [3], [5]. Apply that method to agent reports. Count how many agents describe each theme. A theme with few agents can still matter when the label set shows the same pattern [3].

The counts from the labeled sample are the baseline. Baseline comparison turns "sometimes" into a number [15].

**Assumption log.**

1. `Assumption: agents can point to a wrong line in a summary while the ticket text is visible. Why not measured: the material does not state it. Validate by: ask two agents to label 10 summaries. If wrong: use one trained reviewer instead of agent labels.`
2. `Assumption: 100 recent summaries with their ticket text can be sampled for a test set. Why not measured: no tool access in this session. Validate by: export attempt on 10 tickets. If wrong: build the set until it reaches 50 cases and note the smaller sample size in the threshold.`
3. `Assumption: label agreement between two people on the same 20 cases reaches 90%. Why not measured: measuring costs annotation time before the plan starts. Validate by: the agreement test in Step 1. If wrong: refine the error definitions and rerun before baseline.`

**Alternative considered.** Replace the summariser with rule-based templates. This loses for three reasons: a rule set cannot handle the variety of free text in tickets, the rewrite costs more engineer-days than the probe plan, and it removes value in cases where the model is already right [judgment].

# End

I recommend that we take the steps below. Order follows Section 6: the Confused step first, then the Complicated baseline, then Complex probes, with the Clear steps run in parallel.

**Step 1: Classify the errors (Confused).**

- Increment: label 100 recent summaries against their ticket text. Record the error type per summary, plus "no error".
- Blocker it removes: "sometimes wrong" becomes countable data. This step gathers what the rest of the plan needs.
- Kind: evaluative. Rubric first, per the Kepner-Tregoe layout [15]:
  - Criteria and weights: error type identified (0.5), line in the summary located (0.3), severity noted, high or low (0.2).
  - Pass threshold: two people label the same 20 cases and agree on 90% of labels.
  - Evidence per criterion: the marked summary and the ticket text side by side.
- Domain: Confused. The first action gathers the data needed to classify, because no rule or prior analysis exists [18]. The inference is acting to learn: the labels show the true distribution of failure.

**Step 2: Set the baseline (Complicated).**

- Increment: count the error rate per type on the same 100-case set. Example output: "hallucination in 12 of 100, omission in 20 of 100, misattribution in 5 of 100."
- Blocker it removes: a baseline that every later change is tested against.
- Kind: evaluative. Rubric: criteria are the three error types plus "no error" (weight 0.25 each). Pass threshold: agreement test from Step 1 already passed. Evidence: the label counts and the agreement score.
- Domain: Complicated. Cause and effect are knowable by analysis: count labels, compare the counts [18]. The inference is deduction from the labeling rule.
- Dependency: Step 2 uses the labels from Step 1. Step 2 MUST NOT start until the agreement test in Step 1 passes.

**Step 3: Fix the top error type with capped probes (Complex).**

- Increment: for the top error type, change one variable at a time: the prompt instruction, the ticket data passed to the model, or the model. One probe per cycle.
- Blocker it removes: the largest error type.
- Kind: stochastic. Acceptance test first: metric is the error rate for that type on the same 100 cases; baseline is the Step 2 rate; pass threshold is a 40% relative drop at a sample size of 100 cases. Example: 20 of 100 drops to 12 of 100 or less.
- Probe controls: stop after two failed probes and review the model choice instead. Budget: cap each probe at 2 engineer-days.
- Domain: Complex. Cause and effect in prompt behaviour are visible only after a run [18]. Leverage is a guess; the cap and the shared test set limit the loss.
- Dependency: Step 3 waits on the baseline from Step 2. Run probes one at a time so the result stays attributable.

**Step 4: Add source links to summary lines (Clear), run in parallel with Step 3.**

- Increment: change the summariser output so that each line links to the ticket text it came from.
- Blocker it removes: agents can verify a claim in seconds, so wrong lines get reported with their location.
- Kind: deterministic. Test written first, in Gherkin form [14]:

  ```gherkin
  Given a summary with 5 lines
  When an agent opens the summary
  Then each line shows a link to its source ticket text
  ```

- Domain: Clear. The rule "link a claim to its source" is known to everyone [18]. The inference is deduction from the rule.

**Step 5: Keep the metric alive (Clear), run in parallel with Step 3.**

- Increment: each week, label 30 new summaries with the Step 1 rubric and record the rates.
- Blocker it removes: drift, because model or ticket-mix changes can raise the error rate again.
- Kind: evaluative. Rubric: same criteria and weights as Step 1. Pass threshold: three consecutive weeks within 1.5 times the Step 2 rate. Evidence: the weekly label counts.
- Domain: Clear. It applies the same known labeling rule to new cases [18].

**Condition that changes the recommendation.** If the Step 1 agreement test stays under 90% after one round of definition fixes, replace Step 2 with a review by one domain expert, and use that expert's labels as the baseline.

# Follow-up

**Open questions:**

1. Can the team export summaries with their ticket text? This answer sets the sample size in Assumption 2.

**Conditions that change the recommendation:**

1. The expert-review substitute in the End section applies when label agreement fails.
2. If the sample falls under 50 cases, raise the pass threshold in Step 3 to 50% and state the smaller sample in every report.
