## Headline

Pin the versions now, and move future updates behind a tested process.

- Pin every direct dependency at a version that the last passing build used.
- Add a lock file so that transitive dependencies also stay at fixed versions.
- Move upgrades to a scheduled, tested job instead of letting installs resolve versions.

## Background

Nothing in `requirements.txt` is pinned. Two builds last month failed after a library update. The request asks for a decision on pinning.

## Relevance

Every deploy between code fixes can repeat the same failure, because unpinned installs resolve to the newest releases at install time [1]. Pinning stops repeat breaks now. The process change stops silent drift later.

## Information

1. An unpinned line such as `flask` installs the newest release at each run [1]. So an upstream update reaches a build without any code change and without a test.
2. Baseline: 2 broken builds in one month from dependency updates, versus 0 intended upgrades in that period [judgment, from the user's report]. The break cost came from untested change, not from old versions.
3. A common practice is a locked set: pin direct dependencies in `requirements.txt`, and pin the transitive set in a lock file that `pip-compile` manages [2]. Then only a deliberate edit to the lock file can change what installs [2].
4. Because the installed set becomes reproducible, this change removes the observed failure class. Confidence: high, since a fixed resolved set is the direct counter to install-time drift [inference].

Alternative considered: leave versions unpinned and add tests only. That loses because a test covers one resolved set, while each deploy resolves a different set [inference]. The next deploy gets no protection.

## End

I recommend that we pin the current versions, add a lock file, and schedule upgrades inside a tested job.

1. **Pin the direct dependencies.** Kind: deterministic. Domain: Clear, because a fixed version installs identically each run and the rule is known to everyone; deduction. Increment: add `==` versions for each direct dependency in one session. Blocker removed: repeat install-time drift. Test first:
```gherkin
Given a pinned requirements.txt
When install runs and the smoke tests run
Then the build passes with the resolved set equal to the pin set
```
2. **Add a lock file for transitive dependencies.** Kind: deterministic. Domain: Complicated, because more than one good tool exists and a small analysis picks one; deduction after that analysis. Increment: run `pip-compile` once and commit the output, in one session. Blocker removed: transitive drift. Step 2 MUST NOT start until the test in step 1 passes. Test first:
```gherkin
Given a committed lock file
When pip-compile runs in a clean environment
Then the resolved set matches the committed lock
```
3. **Schedule upgrades as tested jobs.** Kind: stochastic. Domain: Complex, because each future upgrade interacts with the build in ways that show only after running; each cycle is a safe-to-fail probe, and its leverage is a guess. Increment: a monthly job that bumps the lock file, runs the full suite, and merges only on green. Blocker removed: upgrades reach production untested. Step 3 MUST NOT start until the test in step 2 passes. Acceptance test first, then run the cycles:
   - Metric: share of upgrade jobs that end as a merged, green build.
   - Baseline: 0 of 2 upgrade-driven deploys last month [judgment, from the user's report].
   - Pass threshold: 3 of 3.
   - Sample size: 3 monthly cycles.
   - Budget: 2 engineer-hours per cycle.
   - Stop condition: 2 failing cycles in a row, then switch to manual review before merge.

Hedge, per the assumption log: if the deploy check shows a lock already exists, replace step 2 with a refresh rule. If no test suite exists, the step 1 session adds a smoke test before the pin.
