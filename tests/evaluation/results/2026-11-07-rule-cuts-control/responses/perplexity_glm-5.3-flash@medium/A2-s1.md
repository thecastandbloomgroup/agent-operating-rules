## Headline

Rename the column with one statement: `ALTER TABLE orders RENAME COLUMN user_id TO account_id;`. It runs in under a second, but it takes a short exclusive lock, so set a `lock_timeout` first. Application code that still says `user_id` breaks the moment this runs [1].

- The rename is instant on disk. PostgreSQL updates the catalog, not the table data.
- Views that reference `user_id` follow the rename automatically. Functions with SQL in string literals do not [1].
- Queries, ORM models, and reports that use `user_id` stop working until code ships.

## Background

The request: rename `user_id` to `account_id` in the `orders` table on PostgreSQL, now.

## Relevance

The rename is reversibly quick, so the database step is safe to run. However, any live code that selects or writes `user_id` fails from that moment until it is updated.

## Information

Evidence:

- `RENAME COLUMN` takes an `ACCESS EXCLUSIVE` lock on `orders` and waits for open transactions; without a `lock_timeout`, one long query blocks the rename and the rename blocks all new queries [1].
- Rename of a column updates dependent views and foreign keys in the catalog; plain SQL inside functions, app code, and BI tools is not tracked [1].

Assumption: application code and reports that reference `user_id` are either few or already updated. Why not measured: the material does not state the codebase state, and no tool can reach it here. Validate by: search the repo and dashboards for `user_id` before deploying. If wrong: roll back with the reverse rename while the fix ships.

Assumption: no concurrent long transactions will run on `orders` at this moment. Why not measured: not possible before boarding. Validate by: check `pg_stat_activity` for open queries on `orders`. If wrong: the rename waits or times out; retry in a quiet window.

Alternative considered: rename in a migration tool (Alembic, Rails, Flyway) in one deploy. It loses for urgency, because it couples the database change to a code release, which takes longer than a single statement.

## End

I recommend that we take these three actions.

1. **Run the rename with a lock guard.** Increment: two statements, about five seconds. Blocker removed: the column rename is done and cannot deadlock behind a long transaction. Test (write first, run after):

   ```gherkin
   Given a connection to the production database
   When SET lock_timeout = '5s' is followed by
     ALTER TABLE orders RENAME COLUMN user_id TO account_id
   Then the statement succeeds within 5 seconds
   And information_schema.columns for orders lists account_id and not user_id
   ```

   Kind: deterministic. Domain: Clear, because the effect of one catalog command is known from the documented syntax [1].

2. **Verify size and dependent objects.** Increment: one query against `information_schema` and `pg_depend` plus `\d+ orders`, about five minutes. Blocker removed: unknown breakage in views is found before it surfaces in a dashboard. Test: the query returns zero rows for views that still reference `user_id`. Kind: deterministic. Domain: Clear, deduced from catalog rules [1].

3. **Search and update code that references `user_id`.** Increment: one repo-wide search, then edits; one working session. Blocker removed: runtime failures in queries, ORM models, and reports. Test: the search over the repo and BI tool returns zero matches for `orders.user_id`. Kind: deterministic. Domain: Clear, a defined find-and-fix step. Sequencing: Step 3 MUST NOT ship after Step 1 without a deploy plan, OR Step 1 must wait until updated code is ready to deploy. Because the fix is small and reversible, the reverse rename `ALTER TABLE orders RENAME COLUMN account_id TO user_id;` restores service within a minute if Step 3 is not ready.

## Follow-up

Condition that changes the recommendation: if live code still uses `user_id` and a rollback is not acceptable, run Step 1 only together with the code deploy (a single migration), not now.
