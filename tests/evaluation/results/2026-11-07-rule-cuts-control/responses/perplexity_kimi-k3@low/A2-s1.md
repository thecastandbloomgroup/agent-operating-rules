# Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` and update dependent code and views at the same time.

- The rename takes a full table lock for a short time.
- Views, functions, and app queries that use `user_id` break immediately.
- Concurrent index and constraint definitions keep working unchanged.

## Background

A Postgres schema change is needed before a flight. The change is one column rename in `orders`.

## Relevance

Renames break dependent objects without warning, so a quick deploy can cause an outage if dependents are ignored.

## Information

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Evidence and risks:

- The command takes an `ACCESS EXCLUSIVE` lock. It usually finishes in milliseconds, per PostgreSQL documentation [1]. It waits behind open transactions, so it can block the table if a long transaction is open.
- Postgres updates stored view and rule definitions automatically. It does not update application code or external queries [1].
- Indexes and constraints keep their names but stay valid [1].

Assumption: `orders` exists in the `public` schema and no migration tool is used. Why not measured: the user has not answered. Validate by: `\d orders` in psql. If wrong: prepend the schema, for example `ALTER TABLE myschema.orders ...`, or add the rename to the migration tool.

Alternative considered: add `account_id` as a copy and backfill, then drop `user_id` later. It avoids downtime but is slow on large tables and unneeded for a simple rename, because the rename itself is metadata-only [1].

## End

I recommend that we:

1. Check for long open transactions first. Blocker removed: lock waits. Test (deterministic):
   Given a psql session, When `SELECT pid, now() - xact_start AS age FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY age DESC;` runs, Then no row shows an age above 1 minute. Cynefin: Clear, a best practice applies.
2. Run the rename. Capability added: new column name. Test (deterministic):
   Given the rename has run, When `\d orders` runs, Then the table shows `account_id` and no `user_id`. Cynefin: Clear, metadata change with known effect.
3. Update application queries that reference `user_id`. Blocker removed: runtime errors. Test (deterministic):
   Given the updated code, When the search for `user_id` runs on the repository, Then only historical migration files match. Cynefin: Complicated, analysis finds all references.
4. Re-point any views or reports that expected the old name. Test (deterministic):
   Given dependent views, When each is queried, Then each returns rows without error. Cynefin: Complicated.

Step 2 SHOULD run in the same maintenance window as step 3, or app queries fail between them.

## Follow-up

If the table is write-heavy and even a short lock is unacceptable, say so before running step 2, and the copy-and-backfill path applies instead.
