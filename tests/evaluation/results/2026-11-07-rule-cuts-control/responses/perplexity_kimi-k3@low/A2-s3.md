# Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` and it takes effect instantly in Postgres.

- Postgres updates only the catalog, so the rename is fast and safe for the operation itself [1].
- Views, indexes, constraints, and stored functions that name the column are updated automatically [1].
- Application code, ORMs (object-relational mappers), and triggers written in external tools still reference `user_id` and will fail until updated [judgment].

# Background

A rename of one column in the orders table is requested before a flight. This section gives the exact SQL and the checks that prevent breakage.

# Relevance

Postgres holds a brief access-exclusive lock on the table during the rename, so on a live system the statement can queue behind long transactions [1].

# Information

The command:

```
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Indexes, check constraints, and foreign keys on the column keep working because Postgres stores them by internal identifier, not name [1]. However, application queries using the old name fail immediately. If zero downtime matters, the common alternative is a transitional view or a dual-write migration, but for a single rename before boarding, the direct command is the right call [judgment].

Assumption: no concurrent long transactions block the table lock. Why not measured: no access to the database from here. Validate by: run `SELECT pid, now() - query_start AS age FROM pg_stat_activity WHERE state = 'active';` first. If wrong: the ALTER queues until those transactions finish [1].

Alternative considered: add a new column and copy data with dual writes. It loses because it takes hours of code changes where a zero-copy catalog rename takes milliseconds, and downtime risk stays low on a quiet table [1].
