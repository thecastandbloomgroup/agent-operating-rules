Headline
Build a measurement loop before tuning the summariser, because "sometimes wrong" is not actionable.
- First, collect a sample of summaries and score their errors, so the failure modes become visible.
- Second, define one accuracy metric with a pass threshold, so "better" becomes a number.
- Third, fix the dominant failure mode with one targeted change, then re-measure.

Background
A support tool now uses an LLM to summarise cases. Agents report that it is "sometimes wrong", and no metrics exist. Improving quality requires knowing what "wrong" means and how often it happens.

Relevance
Without a baseline, any change cannot be shown to help or harm. A one-time error audit costs hours and focuses all later effort on the failure mode that matters most.

Information
Evidence: LLM summarisation errors usually fall into three types: omission of key facts, hallucination of facts not in the source, and wrong priority or tone [judgment]. This pattern is reported across practitioner and research literature [1], [2]. A theme across two source types (papers and practitioners) supports it; no strong disagreement found. High confidence.

Assumption: each support case is short enough that a human can verify a summary in under 5 minutes. Why not measured: the material does not state it. Validate by: time the audit of 10 summaries. If wrong: sample fewer cases or audit only flagged ones.

Assumption: a labeled set of 50 to 100 recent cases is accessible. Why not measured: the material does not state it. Validate by: query the ticket database once. If wrong: have agents label tickets as they work for two weeks.

Alternative considered: swap to a different model or vendor first. It loses because without an error baseline, the swap cannot be shown to improve anything, and it may trade omission errors for hallucinations [judgment].

End
I recommend that we take these steps:

1. Build the error taxonomy from a sample of 50 recent summaries. Class: evaluative. Write a rubric first: three criteria (fact completeness, fact accuracy, correct priority), equal weights, pass at 90% of summaries clean on all three; evidence is the source ticket. Blocker removed: unknown failure modes. Cynefin: Complicated, because analysis of known error types works; the inference is deduction from established classifications [2]. Rubric: score each summary 0 or 1 per criterion against the ticket, note which criterion fails.

2. Instrument the tool to log every summary with its source ticket and agent edits. Class: deterministic. Blocker removed: no ongoing metric. Cynefin: Clear, logging is a known best practice.

3. Run a stochastic acceptance test on the current model as the baseline. Metric: error-free rate per the rubric. Baseline: unknown, measured here. Pass threshold: to be set after the baseline. Sample size: 100 summaries. Blocker removed: no reproducible number. Cynefin: Complex probe with a budget of one sprint, because agent editing behaviour feeds back into the data; a stop condition is 100 samples.

4. Apply one targeted fix to the dominant failure mode found in Step 1. For omissions, add a checklist prompt of required fields. For hallucinations, require the model to quote supporting ticket text per claim. Class: deterministic (prompt change). Blocker removed: the largest error source.

Follow-up
Conditions that change the recommendation: if the audit shows most errors come from bad source tickets rather than the LLM, replace Step 4 with a ticket-quality fix.
