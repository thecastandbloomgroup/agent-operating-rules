# Background

Your requirements.txt has no version pins. Last month a library update broke the build twice. The question is whether to pin.

# Relevance

Each broken build costs developer time and blocks releases. Pinning removes the most common cause: unplanned upstream changes.

# Information

**Evidence**

- Two breakage events in 30 days, both traced to a library update, per your report [1]. Rate without pins: 2 failures per month. Baseline with pins: upstream changes enter only when the team chooses, so expected failure rate from this cause is near 0 per month [judgment].
- Python packaging guidance recommends exact pins (`==`) for applications and recommends a lock file with hashes for reproducible installs [2].

**Assumptions**

`Assumption: The project is a deployable application, not a published library. Why not measured: The material does not state it. Validate by: Check whether the package is uploaded to PyPI. If wrong: Keep loose lower bounds in the package metadata and pin only in the lock file.`

`Assumption: The team can run pip-tools or uv. Why not measured: The material does not state it. Validate by: Check for pip-tools or uv on one developer machine (5 minutes). If wrong: Use plain `pip freeze` with `pip install --require-hashes`, no extra tooling.`

**Alternative considered**

The strongest alternative is lower bounds only (`package>=1.2`). It loses because it still installs untested new versions, which caused both failures [judgment]. Pinning without hashes also loses to pins with hashes, because hashes catch tampered or corrupted artifacts at near zero cost [2].
