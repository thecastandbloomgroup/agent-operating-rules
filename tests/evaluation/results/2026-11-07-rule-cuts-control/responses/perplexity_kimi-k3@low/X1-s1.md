# Headline

"Sometimes wrong" is unmeasurable, so the first step is to define and measure error before changing anything.

- The complaint has no defined error type, rate, or severity baseline, so no fix can be verified [judgment].
- Measurement of a per-agent labeled sample converts the complaint into a defect rate by type.
- An LLM summariser is a stochastic system, so improvement needs acceptance tests with sample sizes, not single checks.
- Prompt and input fixes close most defect types once the dominant type is known [judgment].

## Background

A support tool now includes an LLM summariser. Agents report it is "sometimes wrong". No metrics exist on output correctness.

## Relevance

Without a measured error rate by type, any change is unverifiable and can make quality worse while looking better. A labeled sample gives a baseline and directs effort to the dominant defect.

## Information

Evidence: no metrics exist in the material, so every quality claim is [judgment]. "Sometimes wrong" for summarisation typically means three disjoint defect types: factual error (hallucination), omission of a key fact, and format or tone failure. ## End

I recommend that we do the following, in order.

1. **Classify the problem.** Collect 10 labeled examples of "wrong" outputs from agents and classify cause and effect visibility. Domain: Confused, because the domain cannot be classified from the complaint; this step gathers what is needed. Kind: evaluative. Rubric first: each example gets a defect type (factual error, omission, format), with a weight per business impact, pass threshold "type assigned to 10 of 10", evidence is the ticket plus agent note. This removes the blocker that no work can be targeted.

2. **Build a labeled baseline set.** Label 100 production summaries against their tickets, one working session with 2 to 3 agents. Domain: Complicated, because classification is knowable with the rubric from Step 1. Kind: evaluative. Rubric: same three defect types, weights 50/30/20, evidence is the source ticket. Output: defect rate per type with counts. This removes the absence of a baseline. Step 2 MUST NOT start until Step 1 produces a usable rubric.

3. **Fix the dominant defect type.** Write one targeted change, that is a prompt constraint, an input-completeness check, or an output template, aimed at the top defect type from Step 2. Domain: Complicated, analysis from Step 2 picks the practice. Kind: stochastic. Acceptance test first: metric is the dominant defect rate, baseline from Step 2, pass threshold a relative reduction of at least 30%, sample size 100 new summaries. Run the trials; accept only at threshold.

4. **Add continuous sampling.** Sample 20 summaries per week for labeling, tracked in a spreadsheet. Domain: Clear, sampling is a known practice. Kind: deterministic.
