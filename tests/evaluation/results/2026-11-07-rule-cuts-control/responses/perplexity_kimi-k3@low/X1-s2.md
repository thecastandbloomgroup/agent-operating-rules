## Headline

Make the summariser measurable before tuning it: define quality, capture evidence, compare one candidate with the current version, and gate release.

- Error type and severity turn agent complaints into counted defects.
- A fixed test set keeps before-and-after comparisons stable.
- A candidate gate and a small release reduce the chance of regression.

## Background

A large language model (LLM) summariser now runs in the support tool. Agents say it is “sometimes wrong,” and no metrics exist [1]. The request is to improve it.

## Relevance

A prompt or model change can fix one error type and worsen another. So a measured baseline must come before wider release.

## Information

### Evidence

- Agents report wrong summaries, but the report has no count, severity, or example [1].
- The supplied material contains no denominator, scored sample, version, or baseline [1].
- Therefore, the current defect rate cannot be calculated from the supplied data [inference].
- Separate measures are needed because a fluent summary can omit or invent a key fact [judgment].

### Initial quality rubric

| Criterion | Weight | Evidence needed |
|---|---:|---|
| Factuality | 40 | Source quote supports each claim |
| Completeness | 30 | Required facts checklist is covered |
| Action guidance | 15 | Next step and status match the ticket |
| Safety and compliance | 10 | No unsupported commitment or policy breach |
| Concision | 5 | No repeated or irrelevant content |

Use these severity levels. Assign the highest applicable level [judgment].

- S4: privacy, safety, legal, or financial breach.
- S3: wrong action, customer, order, amount, date, or unsupported result.
- S2: minor factual error with no action effect.
- S1: style or format issue only.
- S0: no defect.

Track three measures [judgment].

- Severe defect rate: S3 and S4 summaries divided by scored summaries.
- Weighted quality score: rubric score from 0 to 100.
- Agent correction rate: edited or rejected summaries divided by all decisions.

### Assumption log

Assumption: Agents review summaries. Why not measured: Material omits workflow. Validate by: Check the user path. If wrong: Block customer-visible output first.

Assumption: Evaluation has approval to use tickets and edits. Why not measured: Material omits data rules. Validate by: Check privacy approval. If wrong: Use synthetic or redacted tickets.

Assumption: The tool can emit model, instruction, output, and decision events. Why not measured: Material omits telemetry. Validate by: Inspect the event schema. If wrong: Add logging first.

### Alternative considered

Strongest alternative: Replace the model immediately.

Reason it loses: The failure mix and baseline are absent [1].

Attribution would remain impossible without those two measures [inference].

## End

I recommend that we complete these five steps before a wider release.

1. **Calibrate the rubric.**
   - Test first, evaluative: Use the stated criteria and weights. Pass when two reviewers reach at least 80% item-level agreement on 30 summaries after adjudication [judgment]. Evidence is the label, severity, and source quote.
   - Increment: Select 30 recent summaries and score them in one review session.
   - Blocker removed: “Wrong” gains a shared operational meaning.
   - Domain: Complicated. Reviewers use source analysis, and disagreement exposes missing criteria.

2. **Add production evidence capture.**
   - Test first, deterministic:  
     Given a completed support summary  
     When the agent accepts, edits, or rejects it  
     Then the tool stores ticket ID, output record ID, instruction version, model, action, and timestamp
   - Increment: Add the event schema and a daily random-sample export.
   - Blocker removed: No denominator or agent feedback exists.
   - Domain: Clear. Event logging has a known cause-and-effect rule.

3. **Freeze the fixed test set, called the benchmark.**
   - Test first, deterministic:  
     Given 90 days of eligible support tickets and a fixed snapshot  
     When the sampler runs twice with one seed  
     Then it returns the same 50 ticket IDs and the same channel, language, type, and length counts
   - Increment: Build the sampler and export each thread, summary, and final resolution.
   - Blocker removed: Data drift cannot be separated from model change.
   - Domain: Clear. Fixed-seed sampling is deterministic.

4. **Test one candidate against the current version.**
   - Test first, stochastic: Metrics are quality score and severe defect rate. The baseline is the current version on the same 50 tickets. The pass threshold is at least 5 score points, a 30% relative drop in severe defect rate, no S4 defect, and 50 summaries per arm [judgment].
   - Increment: Change only the model instruction or source text input for the top two defects. Then generate and score both versions.
   - Blocker removed: Candidate value has no measured evidence.
   - Domain: Complex. The effect is inductive from trials. A different ticket mix can break that pattern.
   - Probe limit: Stop after one candidate, two generation runs, or any S4 defect.

5. **Prepare a small traffic release, called a canary.**
   - Test first, deterministic:  
     Given the Step 4 candidate has passed  
     When a 5% route is enabled  
     Then the dashboard shows version and decision events, and the rollback flag routes the next summary to the current version
   - Increment: Configure the 5% route, dashboard, S4 alert, and rollback flag. Set the edit/reject alert at 10 percentage points over baseline [judgment].
   - Blocker removed: No controlled release path exists.
   - Domain: Clear. Version routing and rollback are deterministic controls.

Steps 2 and 3 can run in parallel after Step 1. Step 4 MUST NOT start until Steps 1 and 3 pass. Step 5 MUST NOT start until Step 4 passes.

## Follow-up

Canary decision rule: Compare the first 50 candidate decisions with 50 matched current-version decisions. Promote only when the candidate has no S4 defect and an edit/reject rate no more than 2 percentage points above baseline; otherwise roll back [judgment].

Condition that changes the plan: If summaries are customer-visible without agent review, block that path first and require human approval.

Open questions: none.
