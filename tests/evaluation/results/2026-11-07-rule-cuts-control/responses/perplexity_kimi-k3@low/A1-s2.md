## Headline

Yes, pin the versions in requirements.txt.

- Two broken builds in one month show that un-pinned dependencies cause real harm [judgment].
- Pinning removes this cause at near-zero cost.
- An automated update tool keeps pinned versions current, so pinning does not mean stale dependencies.

## Background

The project's requirements.txt lists dependencies without version pins. The build broke twice last month because a library published a new version.

## Relevance

Each break costs developer time and delays delivery. A small change to the dependency process prevents the next break.

## Information

Un-pinned installs resolve to the latest release at install time, so the same requirements.txt can produce different environments on different days [1]. That is the direct cause of the two breaks [judgment]. The standard fix is to pin exact versions and update them on a schedule through a tool such as Dependabot or Renovate, which opens a pull request per update [2].

Assumption: builds run pip install from requirements.txt in a clean environment. Why not measured: the material does not state the build setup. Validate by: check the build script once. If wrong: pinning still applies, but to the actual install source.

Alternative considered: use compatible ranges (for example, `lib>=2,<3`) instead of exact pins. This loses because a minor release can still change behavior, and the team has already been burned twice [judgment].

## End

I recommend that we take these steps.

1. Freeze the current environment into pinned requirements. Run `pip freeze > requirements.txt` from a known-good environment. This removes the immediate cause of broken builds. Complicated domain: deduce the good state from a working install. Deterministic test: Given a clean virtual environment, When `pip install -r requirements.txt` runs and the test suite runs, Then the install succeeds and all tests pass.
2. Add a hash check. Use `pip-compile --generate-hashes` or `pip install --require-hashes` so installs verify package hashes [1]. This adds supply-chain protection. Clear domain: the tool's documented behavior applies directly. Deterministic test: Given a requirements file with hashes, When an install runs with hash checking, Then a tampered or mismatched package fails the install.
3. Enable an update tool. Configure Dependabot or Renovate to open weekly update pull requests [2]. This keeps versions current without surprise breaks. Complicated domain: pick the tool that matches the repository host by checking the host's documentation. Deterministic test: Given the tool's config file in the repository, When the next scheduled run occurs, Then a pull request appears for any outdated pinned dependency.
4. Gate updates on the build. Require continuous integration to pass before an update pull request merges. This stops a bad update from reaching the main branch. Clear domain: branch protection is a known best practice. Deterministic test: Given an update pull request with a failing build, When a merge is attempted, Then the merge is blocked.

Step 2 and Step 1 run in the same session. Step 3 MUST NOT merge updates automatically until Step 4 is in place.
