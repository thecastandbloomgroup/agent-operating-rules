## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` to rename the column without data loss.

- This is a metadata-only operation that completes in milliseconds and holds a brief lock.
- Code, views, and indexes that reference `user_id` will break until updated.
- Application code should be deployed to use `account_id` at the same time.

## Background

You asked for the SQL to rename `user_id` to `account_id` in the `orders` table in Postgres, before boarding a plane. The shortest safe path is below.

## Relevance

A rename is fast, but any query still using `user_id` fails immediately after. Do this only if dependent code is already updated or will be before users hit it.

## Information

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

- The rename updates catalog metadata only. No table rewrite, so it finishes in milliseconds even on large tables [1].
- It takes an `ACCESS EXCLUSIVE` lock for a fraction of a second. Queued queries wait briefly [1].
- Foreign keys and indexes on the column keep working. Their names do not change, only the column name [1].
- Views, stored procedures, and application queries referencing `user_id` break at once [judgment].
- The undo command is `ALTER TABLE orders RENAME COLUMN account_id TO user_id;`.

Assumption: Application code already uses `account_id`, or downtime from stale queries is acceptable. Why not measured: the material does not state it. Validate by: search the codebase for `user_id` before running. If wrong: delay the rename until code is deployed, or the app errors on reads and writes.

Alternative considered: create a new column, backfill, dual-write, then drop the old one. It avoids the breaking change, but takes multiple deployments. It loses because the request is a quick rename and code alignment appears done.
