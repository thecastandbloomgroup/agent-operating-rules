## Headline

The retrospectives fail because insights never become owned actions, so cap discussion time and end every session with one tested change. First, cause one: actions lack owners and tests. Second, cause two: too many issues dilute focus. Third, cause three: no check that prior actions happened.

## Background

The team holds retrospectives, attends them, and sees no change in how work runs. The request asks what to change in the retrospective process.

## Relevance

A retrospective that produces no change costs meeting hours and teaches the team that raising problems is pointless. That second effect is the larger loss.

## Information

The pattern described matches a known failure mode: discussion without committed, verified follow-through [judgment]. Three common causes fit the symptom. First, action items have no single owner, so no one acts. Second, the team raises many topics, so no topic gets enough depth to fix. Third, no one reviews last session's actions, so skipping actions carries no cost. Each of these is a theme supported by standard agile facilitation practice [1].

Assumption: The team holds regular retrospectives and can change their own format. Why not measured: The material does not state it. Validate by: Ask the facilitator. If wrong: Get permission from the process owner before Step 1.

Assumption: Attendance is real participation, not silent presence. Why not measured: The material does not state it. Validate by: Count speakers in the next session. If wrong: Add Step 0, a five-minute anonymous written round to surface topics.

Alternative considered: Replace retrospectives with incident postmortems. It loses because the failure is follow-through, not topic generation; postmortems with the same follow-through gap would decay the same way [judgment].

## End

I recommend that we run this sequence:

1. **Start the next retrospective with a review of the last session's actions** (Clear: the practice is known and repeatable). This removes the "no cost for skipping" blocker. Task kind: deterministic. Test, written first:
   - Given the previous retrospective produced action items,
   - When the new session opens,
   - Then each prior action is read aloud and marked done, dropped, or carried with a reason.

2. **Limit the session to one改进 topic, chosen by vote** (Clear). This removes the dilution blocker. Task kind: deterministic. Test:
   - Given a list of raised topics,
   - When the team votes,
   - Then only the top topic is discussed for the rest of the session.

3. **Convert the chosen topic into one action with one named owner and a visible change** (Complicated: the facilitator analyzes which practice fixes that topic). This adds the missing link from insight to change. Task kind: deterministic. Test:
   - Given the chosen topic,
   - When the session ends,
   - Then the action names one owner, one observable change, and one date within two weeks.

4. **Probe: run a fishbowl or silent-writing round in one session** (Complex, so capped: one session, stop condition is no new topics surfaced, budget is 15 minutes). Cause and effect on participation are only visible afterward. Task kind: stochastic. Acceptance test, written first: metric is number of distinct topics raised; baseline is the average of the last three sessions; pass threshold is baseline plus two; sample is one session, then confirm over the next two.

Step 3 MUST NOT start until Step 2's vote completes. Step 4 MAY run in parallel.

## Follow-up

If participation turns out to be the real blocker (silent presence), Steps 1 to 3 stay, and Step 4 becomes the primary fix.
