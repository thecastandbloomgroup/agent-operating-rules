## Headline

Measure the errors first, then fix the most common error type, because no one can improve what no one counts.

- Agents say "sometimes wrong", but the error types and the error rate are unknown.
- A labeled sample and a feedback button give a baseline within one week.
- Changes to the prompt or model need a pass threshold set before the change.
- Agent feedback keeps the metric alive after the first fix.

## Background

The support tool has an LLM summariser (a model that shortens a ticket thread into a few lines). Agents report that it is "sometimes wrong". The team has no metrics, so the request "make it better" has no target yet.

## Relevance

Agents who distrust the summary reread the full thread. That removes the time the tool should save. A wrong summary can also send a customer a wrong answer.

## Information

Evidence:

- Abstractive summarisers are known to state facts that the source does not support. Studies of factual consistency show this failure.
  
  [1]

- LLM judges can score summaries at scale. In one study, strong judges matched human raters on over 80% of comparisons. Check any judge against human labels first.

  [2]

- Cynefin sorts the work by how cause and effect relate. Here the error causes are unknown, so the first action must classify them.

  [3]

- The current error rate and the error types are not known. [no source]
- The top error type is likely to be a missing detail or an invented detail. [judgment]
- A sample of 60 summaries gives a margin of about 13 points at 95% confidence for a rate near 50%. [inference]

Assumption log:

`Assumption: the tool stores ticket threads and summaries. Why not measured: the material does not state it. Validate by: ask an engineer to pull 60 rows. If wrong: add a logging step before Step 1.`

`Assumption: one reviewer can label 60 summaries in one session. Why not measured: the material does not state label time. Validate by: time the first 10 labels. If wrong: cut the sample to 30 and widen the margin.`

`Assumption: agents will click a feedback button. Why not measured: no tool can reach agent habits. Validate by: count clicks in the first week. If wrong: sample summaries for review instead.`

Alternative considered: switch to a larger model now. It loses because the error types are unknown, so the team cannot show that the switch helps. It also adds cost and latency. [judgment]

## End

I recommend that we take these steps, in this order:

1. **Label a sample of summaries to classify the errors.**
   - Increment: one reviewer labels 60 recent summaries in one session. The labels are: correct, missing key fact, invented fact, wrong tone, other.
   - Blocker removed: nobody knows the error types or the error rate.
   - Kind: evaluative. Rubric written first: criteria are factual accuracy (weight 50%), coverage of the customer request (30%), and action items (20%). Evidence for each is the source thread. Pass threshold: a summary scores at least 80% and has no invented fact.
   - Cynefin: Confused. We cannot yet tell the cause of the errors, so this step gathers what is needed to classify them.

2. **Add a feedback control to each summary.** This step may run in parallel with Step 1.
   - Increment: one thumbs-down button with a reason list, and a log row for each click.
   - Blocker removed: no ongoing signal from agents.
   - Kind: deterministic. Test written first:
     - Given an agent views a summary
     - When the agent clicks thumbs-down and picks "invented fact"
     - Then the log stores the summary ID, the reason, and the time
   - Cynefin: Clear. A known pattern applies, and deduction from it is enough.

3. **Set a baseline on a fixed test set.** Step 3 MUST NOT start until Step 1 ends.
   - Increment: copy the 60 labeled cases into a test set and write a script that scores new summaries on the Step 1 rubric.
   - Blocker removed: no way to compare a change with today's output.
   - Kind: stochastic. Test written first: metric is the share of summaries with no invented fact. Baseline is the Step 1 rate. Pass threshold is the baseline plus 10 points. Sample is 60 cases, run 3 times each.
   - Cynefin: Complicated. Analysis picks the scoring method. If an LLM judge scores, check it against the human labels first [2].

4. **Probe a prompt fix for the top error type.** Step 4 MUST NOT start until the baseline from Step 3 exists.
   - Increment: change the prompt to target the most common error type, for example "quote the customer's request and list only facts in the thread".
   - Blocker removed: the largest error source.
   - Kind: stochastic. Test written first: the Step 3 metric, threshold, and sample. Accept only when the threshold is met.
   - Cynefin: Complex. Induction from trials; the pattern can break if the error type changes with ticket category. Leverage is a guess. Budget: two working days. Stop condition: three prompt variants with no gain.

If Step 1 shows that most errors come from truncated or missing thread text, replace Step 4 with a fix to the input data.

Conditions that change the recommendation:

- If the rate is above 40%, pause the tool for high-risk tickets while Step 4 runs.
