## Headline

Yes, pin the versions, because unpinned installs let new releases change your build without a code change.

- Pinning makes every build install the same versions, so a library update cannot break a build on its own.
- Pinning moves upgrades to a planned step with a test, instead of a surprise in the build.
- The cost is small: one lock file and one upgrade routine.

## Background

The project lists its libraries in requirements.txt without version numbers. The build broke twice last month after a library update, per the user's message. The question is whether to pin versions.

## Relevance

Each break stops the team until someone finds the changed library. Without pins, the next break is likely (66 to 100%) to repeat this pattern. Basis: two breaks in one month, both tied to updates.

## Information

**Evidence**

- Pip installs the newest release that matches the requirement. With no version given, any new release matches [1]. This explains the two breaks.

- Transitive dependencies (libraries that your libraries need) also move. Pinning only the top-level libraries leaves them open. [judgment]
- Two breaks per month is the baseline. The target is zero breaks caused by updates.
