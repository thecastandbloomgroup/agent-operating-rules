## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` only when the application code that reads the column ships in the same window.

- The statement changes metadata only, so it finishes fast.
- Queries that still use `user_id` fail after the rename.
- The statement needs a short exclusive lock on the table.

## Background

The request is to rename one column in the `orders` table of a Postgres database. The requester boards a plane soon and cannot watch the change.

## Relevance

A rename in production breaks any query that uses the old name. A failure while the requester is in the air has no quick fix.

## Information

Evidence:
- The rename changes the column name and does not rewrite stored data.

  [1]
- `ALTER TABLE` takes an `ACCESS EXCLUSIVE` lock, which blocks reads and writes until the transaction ends.

  [1]
- Indexes and constraints follow the new name. [inference]
- Application code, ORM mappings, and function bodies stored as text keep the old name. [inference]

Assumption log:
- `Assumption: orders is in the public schema and has no logical replication. Why not measured: the material does not state it. Validate by: run \d orders and check pg_publication_tables. If wrong: add the same rename on the subscriber first.`
- `Assumption: application code uses user_id and needs a change. Why not measured: no tool can reach the code. Validate by: run grep -r user_id in the repository. If wrong: skip Step 1 code changes.`

Alternative considered: add `account_id` as a new column and copy data, then drop `user_id` later. It is safer for old code, but it needs several deploys and a backfill. That cost is too high for a one-column rename. [judgment]

## End

I recommend that we:

1. Find every dependent of `user_id`. Run `grep -r user_id` on the code and query `pg_depend` for views and functions. This removes the risk of a hidden break.
   - Kind: deterministic.
   - Cynefin: Complicated, because analysis of the dependents picks the fix.
   - Test:
     ```
     Given the repository and the production schema
     When the dependency search runs
     Then the output lists every file, view, and function that names user_id
     ```
2. Rename the column in a staging copy and run the application tests. This proves the code change works before production.
   - Kind: deterministic.
   - Cynefin: Clear, because the rename is a known best practice.
   - Test:
     ```
     Given a staging copy of orders and the updated code
     When the rename runs and the test suite runs
     Then all tests pass and no query names user_id
     ```
   - Step 2 MUST NOT start until Step 1 finds no unfixed dependents.
3. Run the rename in production, in one transaction, with a lock limit. Use `BEGIN; SET LOCAL lock_timeout = '3s'; ALTER TABLE orders RENAME COLUMN user_id TO account_id; COMMIT;`. Deploy the code in the same window.
   - Kind: deterministic.
   - Cynefin: Clear, because the statement and its lock rule are documented.
   - Test:
     ```
     Given production orders has a column user_id
     When the transaction runs
     Then orders has account_id and has no user_id
     ```
   - Step 3 MUST NOT start until the test in Step 2 passes and someone who stays on the ground can watch it.
4. Check live traffic for five minutes after the change. Query `pg_stat_database` for rollbacks and read the application error log.
   - Kind: deterministic.
   - Cynefin: Clear, because the checks are known.
   - Test:
     ```
     Given the rename has committed
     When the error log is read for five minutes
     Then no "column user_id does not exist" error appears
     ```

If the code change cannot ship in the same window, replace Step 3 with a wait until after landing.

## Follow-up

Open questions: none.

Conditions that change the recommendation:
- Logical replication exists: rename on the subscriber first.
- A person on the ground cannot watch Step 4: delay Step 3.
