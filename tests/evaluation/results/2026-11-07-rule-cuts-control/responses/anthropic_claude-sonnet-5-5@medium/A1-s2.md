## Headline

Pin every version in requirements.txt, including indirect dependencies, and update the pins on a planned schedule.

- An unpinned install takes the newest allowed release at build time, so a library update can break a build without any code change.
- A pinned file makes every build install the same versions, so a failure points to your change.
- Updates still happen, but they move into a tested, reviewed step instead of a surprise.

## Background

The project lists dependencies in requirements.txt with no pinned versions. The build broke twice last month after a library update. The question is whether to pin the versions.

## Relevance

Each unplanned break stops the team until someone finds the cause. Pins remove that cause at low cost.

## Information

Evidence:

- The user reports two build breaks last month, both after a library update (user message). The baseline is 2 breaks per month.
- A requirements file accepts exact pins in the form `package==1.2.3` [1].

- The tool pip-tools compiles a full list of pinned versions, including indirect dependencies, from a short input file [2].

- An unpinned line lets pip choose the newest matching release at install time [inference].
- Confidence that pinning removes this failure type: high confidence, because the mechanism matches both reported breaks.
