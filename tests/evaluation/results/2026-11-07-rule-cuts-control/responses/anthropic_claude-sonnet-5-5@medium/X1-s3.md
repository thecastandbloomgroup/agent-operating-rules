## Headline

Measure the error rate first, then fix the largest error type, because "sometimes wrong" cannot guide any change.

- No baseline exists, so any change today cannot be shown to help.
- A labeled sample of summaries gives the baseline and the error types.
- A feedback button in the tool gives ongoing data.
- One targeted change, tested on the same sample, shows whether the fix works.

## Background

The team added an LLM summariser (a model that writes short text from longer text) to a support tool. Agents say it is "sometimes wrong". No metrics exist (per the user's query). The request is to make it better.

## Relevance

Agents who distrust the summary will reread each ticket, so the tool adds cost instead of saving time [judgment]. Without a baseline, the next change is a guess.

## Information

**Evidence**

- Agents report errors, but give no rate and no error types (per the user's query). Confidence in any cause: low, one qualitative statement and no measurement.
- Next, the theme method applies. Group agent comments into error themes and count the summaries behind each theme [1].
- A sample of 100 summaries gives a 95% interval of about ±10 percentage points at worst case [inference]. That is enough to find the top error type. It is not enough to show a small gain.
- A paired test on the same 100 inputs removes input variation between the two runs [judgment].

**Assumption log**

`Assumption: agents can see the source ticket next to the summary. Why not measured: the material does not state it. Validate by: ask one agent to open a ticket. If wrong: Step 1 needs a source-text export.`

`Assumption: the team can log events in the support tool and edit the prompt. Why not measured: the material does not state it. Validate by: ask one engineer, 10 minutes. If wrong: Step 2 becomes a shared spreadsheet.`

`Assumption: two agents can each give one hour for labeling. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: Step 1 uses one reviewer and a smaller sample.`

`Assumption: one error type causes most major errors. Why not measured: no data exists yet. Validate by: Step 1 counts. If wrong: Step 3 targets the two largest types.`

**Alternative considered**

Switch to a larger model now. It loses because no baseline exists to show a gain. Cost also rises for every ticket [judgment].

## End

I recommend that we take these steps in order:

1. **Audit 100 recent summaries.**
   - Increment: two agents label each summary as correct, minor error, or major error. They tag the error type: omission, invented fact, wrong name or number, or wrong priority.
   - Blocker removed: no baseline and no error types.
   - Kind: evaluative. Cynefin domain: Confused, because the error causes are unknown. This step gathers what is needed to classify the rest [2].
   - Test (rubric, written first). Pass threshold: 80 of 100 points.
     - Sample is random across ticket types. Weight 40. Evidence: sampling list.
     - Two reviewers agree on at least 80% of labels. Weight 30. Evidence: label sheet.
     - The error taxonomy covers at least 90% of errors found. Weight 30. Evidence: count of "other" tags.

2. **Add a "Wrong" button with a reason list beside each summary.**
   - Increment: one button, one reason menu, one stored record.
   - Blocker removed: no ongoing data.
   - Kind: deterministic. Cynefin domain: Clear, because logging a click is a known practice (deduction from a known rule).
   - Step 2 MAY run in parallel with Step 1.
   - Test (Gherkin form [3]):

```gherkin
Given an agent views a summary for a ticket
When the agent clicks "Wrong" and selects a reason
Then the system stores the ticket id, summary id, model version, reason, and time
```

3. **Run one probe: change the prompt to target the top error type from Step 1.**
   - Step 3 MUST NOT start until Step 1 passes its rubric.
   - Increment: one prompt change, such as "quote names and numbers only from the ticket text". Rerun on the same 100 tickets.
   - Blocker removed: the largest error type.
   - Kind: stochastic. Cynefin domain: Complex, because the effect of a prompt change shows only after a trial (induction from trials). The pattern could break on ticket types not in the sample. Leverage is a guess.
   - Budget: one working session. Stop condition: the major-error rate rises on any ticket type.
   - Test (written first). Metric: major-error rate. Baseline: the Step 1 rate. Threshold: at least 30% lower in relative terms. Sample size: the same 100 tickets. Accept only when all three hold. Otherwise revert the prompt.

4. **Set a weekly target from live feedback.**
   - Step 4 MUST NOT start until Step 2 has run for 5 working days.
   - Increment: one table of "Wrong" clicks per 100 summaries, by reason. Set the target against the Step 1 rate.
   - Blocker removed: no way to see drift after launch.
   - Kind: evaluative. Cynefin domain: Complicated, because analysis of the click data picks the target (deduction from analysis).
   - Test (rubric, written first). Pass threshold: 70 of 100 points.
     - The click rate and the audit rate are within 10 points of each other. Weight 50. Evidence: both tables.
     - Each reason maps to a Step 1 error type. Weight 50. Evidence: mapping sheet.

If the Step 1 sample shows fewer than 5 major errors in 100, replace Step 3 with a review of agent expectations.
