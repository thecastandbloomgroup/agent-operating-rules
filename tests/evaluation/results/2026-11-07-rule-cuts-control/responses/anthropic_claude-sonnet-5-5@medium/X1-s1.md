## Headline

Measure the summariser first, then fix the errors you can name, because no one can improve a quality that nobody measures.

- Agents hold the best evidence today, so capture their judgment as labeled data.
- Wrong facts, such as order numbers and names, are likely the largest error class, and code can check them.
- Prompt or model changes come last, and a fixed test set must approve each one.

## Background

The support tool has an LLM summariser (a model that shortens a ticket thread). Agents report that it is "sometimes wrong" [1]. The team has no metrics, so "wrong" has no definition and no baseline.

## Relevance

An agent who reads a wrong summary may give a wrong answer to a customer. The cost grows with every ticket. Without a metric, no change can show that it helps.

## Information

**Evidence**

- Research on abstractive summaries (summaries written in new words) reports that models often add content the source does not support [2].
- Summary quality has several parts, such as consistency, coverage, and fluency. One score does not capture them [3].
- Agent complaints are one source, so confidence in any error type is low until labeled samples exist [1].
- Wrong facts are the largest error class. This is likely, but it is [judgment].

**Assumption log**

Assumption: The tool stores the source ticket text and the summary text. Why not measured: the material does not state it. Validate by: ask an engineer to pull ten records. If wrong: add logging first, then start Step 1.

Assumption: Agents can label 50 summaries in one working session. Why not measured: the user has not answered. Validate by: time five labels with one agent. If wrong: cut the sample to 30 and widen the uncertainty.

Assumption: The team can change the prompt and test it offline. Why not measured: the material does not state it. Validate by: run one prompt on one stored ticket. If wrong: Step 4 needs a test copy of the tool.

**Alternative considered**

Switch to a larger model now. It loses because without a baseline nobody can tell whether it helps, and it raises cost per ticket [judgment].

## End

I recommend that we take these four actions in order:

1. **Define "wrong" from real cases (Confused, evaluative).** The domain is Confused because the error types are unknown. Deduction and induction both lack data, so this step gathers it.
   - Increment: 3 agents label 50 random summaries against the source tickets in one session.
   - Blocker removed: no definition and no baseline.
   - Rubric, written first:
     - Criteria and weights: faithfulness to the ticket 40%, missing key facts 30%, wrong identifiers 20%, format and tone 10%.
     - Pass threshold: a summary passes when its weighted score is at least 80%.
     - Evidence: each score cites the ticket sentence that supports or contradicts the summary.
   - Output: the baseline pass rate and a ranked list of error types.

2. **Add a feedback control (Clear, deterministic).** A best practice exists: a thumbs-up or thumbs-down with a reason code.
   - Increment: one button pair and four reason codes taken from Step 1.
   - Blocker removed: no ongoing signal.
   - Test, written first:
     ```gherkin
     Given an agent views a summary
     When the agent selects thumbs-down and the reason "wrong order number"
     Then the tool stores the ticket id, summary id, and reason code
     ```
   - Step 2 MUST NOT start until Step 1 names the reason codes.

3. **Add an identifier check (Complicated, deterministic).** An analysis of Step 1 picks the check. Deduction from the ranked error list gives the rule. If wrong facts are not the top error, replace this step with a check for the top error.
   - Increment: a script that flags any order number, date, or name in the summary that is absent from the ticket.
   - Blocker removed: wrong identifiers reach agents unflagged.
   - Test, written first:
     ```gherkin
     Given a ticket that contains order number 48213
     And a summary that states order number 48231
     When the identifier check runs
     Then the summary is flagged "identifier not in source"
     ```

4. **Probe one prompt change (Complex, stochastic).** The domain is Complex because model behavior shows itself only after trials. Induction from trials applies. The pattern could break if ticket types differ from the Step 1 sample.
   - Increment: one revised prompt that says "use only facts in the ticket", run offline on the 50 labeled tickets plus 50 new ones.
   - Blocker removed: no evidence that a change helps.
   - Acceptance test, written first:
     - Metric: share of summaries that pass the Step 1 rubric.
     - Baseline: the Step 1 pass rate.
     - Threshold: at least 10 points above baseline, and no rise in flagged identifiers from Step 3.
     - Sample size: 100 tickets.
   - Budget: one working day. Stop condition: stop after two prompt revisions that miss the threshold.
   - Step 4 MUST NOT start until Steps 1 and 3 are complete. Leverage is a guess.
