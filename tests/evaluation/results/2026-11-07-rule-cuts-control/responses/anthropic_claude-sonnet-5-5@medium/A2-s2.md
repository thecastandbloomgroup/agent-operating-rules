## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;`, but only after you confirm that no application code still reads `user_id`.

- The rename changes metadata only, so it finishes in milliseconds [1].
- Application queries that name `user_id` fail the moment the rename commits.
- Do not run it right before a flight, because you cannot roll back from the air.

## Background

The `orders` table in a Postgres database has a column `user_id`. The request is to rename it to `account_id`. The material does not state the schema, the Postgres version, or which services read the column.

## Relevance

The SQL takes seconds. The risk is in the callers. A failed deploy while you are offline costs more than a delayed rename.

## Information

Evidence:
- `RENAME COLUMN` changes the catalog entry and does not rewrite table data [1]. High confidence, one primary-style vendor document.
- Indexes and foreign key constraints that use the column follow the rename. Their names keep the old text, for example `orders_user_id_idx`. [judgment]
- The command takes a short exclusive lock on the table. A long open transaction on `orders` blocks it, so set `lock_timeout`. [judgment]

Assumption log:
- `Assumption: the table is public.orders. Why not measured: the material does not state it. Validate by: run \d orders. If wrong: change the schema name in the SQL.`
- `Assumption: application code and reports still use user_id. Why not measured: no tool can reach the code. Validate by: grep the repositories for user_id. If wrong: the rename is safe to run at once.`

SQL to run:

```sql
BEGIN;
SET LOCAL lock_timeout = '5s';
ALTER TABLE public.orders RENAME COLUMN user_id TO account_id;
COMMIT;
```

Rollback is the same command with the names swapped.

Alternative considered: add `account_id` as a new column, copy data, then drop `user_id`. It allows a gradual migration. It loses because it needs a table rewrite and dual writes, which cost more than one rename plus a coordinated deploy. [judgment]
