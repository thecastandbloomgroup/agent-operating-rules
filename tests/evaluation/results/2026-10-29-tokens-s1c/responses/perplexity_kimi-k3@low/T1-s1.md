## Headline

You cannot fix a culture problem directly; you fix it by removing the decision from people and giving it to a tool, then agreeing once, briefly, on what the tool cannot decide.

- Automated formatting turns a recurring taste dispute into a one-time configuration decision.
- The real agreement needed is small: pick a tool and accept its defaults with at most a few overrides.
- A short, time-boxed vote ends the debate; consensus-seeking restarts it.
- Style arguments in reviews stop when a formatter owns style, so reviewers discuss logic instead.

## Background

Your team argues about SQL formatting in every code review. The disagreements are personal taste, not correctness. You asked for a fix to the culture problem.

## Relevance

Each review spent on style wastes reviewer time and builds resentment. One tooling decision, made this week, removes the recurring conflict at its source.

## Information

- Formatters for SQL exist and run in editors and CI, for example sqlfluff, sqlfmt, and pgFormatter [1][2][3].
- Pre-commit and CI enforcement is standard practice for settled style questions; the same pattern works for SQL [4].
- Theme count: three independent formatter projects all assume teams should not hand-format SQL; no source disagrees.
- Confidence: high. The tooling exists and the pattern is proven in other languages [judgment].

**Assumption log**

A1. The team uses one main SQL dialect. Why not measured: the request does not state it. Validate by: ask one teammate or check the connection config. If wrong: pick the formatter that supports both dialects.
A2. A CI system exists to run checks. Why not measured: the request does not state it. Validate by: check the repository for a CI config file. If wrong: run the formatter as a pre-commit hook instead.
A3. The friction is about style, not deeper trust problems. Why not measured: the request gives no evidence of wider conflict. Validate by: notice whether argument in reviews stops after Step 3. If wrong: the tooling will fix formatting but not the culture; see the hedge in End.

**Alternative considered**

Hold a workshop to write a shared SQL style guide by consensus. It loses because style guides die without enforcement, and consensus-seeking on taste invites the same debate the request wants to end [judgment].

## End

I recommend that we:

1. **Pick a formatter by time-boxed vote** (Evaluative, Complicated). Rubric: dialect support 40%, CI and editor integration 30%, configurability 20%, active maintenance 10%. Pass threshold: one tool scores highest on evidence from docs; vote only if scores tie. Blocker removed: no shared standard exists. One working session.
2. **Adopt defaults with at most five overrides** (Deterministic, Clear). Test first, in Gherkin: Given the team list of style preferences, When the config file is written, Then it contains at most five overrides and the formatter runs clean on one sample file. Blocker removed: endless taste debate. One working session.
3. **Reformat the existing SQL in one commit and enforce in CI or pre-commit** (Deterministic, Clear). Test first: Given a pull request whose SQL fails the formatter, When CI runs, Then the check fails and blocks the merge. Blocker removed: style comments in reviews. One working session. Step 3 MUST NOT start until Step 2 passes.
4. **Move one review conversation to logic only** (Stochastic, Complex, probe). Acceptance: over the next ten reviews, zero comments are about formatting. Baseline: unknown, assumed nonzero. Budget: two weeks. Stop condition: if formatting comments persist, find and close the enforcement gap. Run in parallel with Steps 2 and 3.

Hedge: if formatting comments stop but review conflict moves to other topics, the problem is team trust, not style. In that case the next step is a facilitated retrospective, not more tooling.

## Follow-up

Conditions that change the recommendation: a second SQL dialect (see A1) or conflict that survives tooling (see the hedge in End).
