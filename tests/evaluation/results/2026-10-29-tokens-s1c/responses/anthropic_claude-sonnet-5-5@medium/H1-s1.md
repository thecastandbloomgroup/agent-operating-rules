## Headline

Roll back the newest change now, and brief the execs with three facts instead of a cause.

- Stop the harm first, because a full checkout outage costs more with each minute than a rollback does.
- Add a second responder, so one person fixes while the other communicates.
- Diagnose the cause only if the rollback fails.
- Give the exec call impact, action, and next update time.

## Background

Checkout returns a 500 error (a server failure) for every user since 09:12. You are the only on-call engineer. The exec call starts in ten minutes.

## Relevance

Every user fails, so revenue from checkout is zero until you fix it. The exec call needs facts from you, not a guess at the cause.

## Information

Evidence:

- 100% of users fail from one start time. This pattern points to one shared cause, such as a change or a shared dependency [inference].
- Incident guidance says to mitigate first and find the root cause later.

  Source: Google SRE book, "Managing Incidents" [1].
- A rollback is faster than a root-cause search for a fresh outage [judgment].
- The Cynefin framework assigns an outage with unknown cause to the Chaotic domain, where you stabilise first [2].

Assumption log:

A1. A deploy or config change happened near 09:12. Why not measured: the material does not state it. Validate by: check the deploy log for changes after 09:00. If wrong: skip Step 1 and start Step 3.

A2. The last change can roll back without data loss. Why not measured: no tool can reach the release notes from here. Validate by: check the change for a database migration. If wrong: use a feature flag or failover instead.

A3. A second engineer or manager is reachable. Why not measured: the user has not answered. Validate by: send one page and wait two minutes. If wrong: skip Step 2 and send the Step 4 message yourself.

Alternative considered: find the root cause before any action. It loses because the outage is total and each minute costs revenue [judgment]. A rollback is also reversible.

## End

I recommend that we take these steps in order:

1. **Roll back the newest change.**
   - Increment: one rollback of the last deploy or config change, about 5 minutes.
   - Blocker removed: the outage.
   - Domain: Chaotic. Kind: deterministic.
   - Test, written first: Given the last change is reverted, When a test user submits checkout, Then the response is 200 and the error rate falls below 1% within 3 minutes.
2. **Page a second responder and open one incident channel.**
   - Increment: one page and one channel with a pinned status line, about 2 minutes. Run it in parallel with Step 1.
   - Capability added: a person who writes updates while you fix.
   - Domain: Clear. Kind: deterministic.
   - Test, written first: Given the page is sent, When 2 minutes pass, Then one person confirms in the channel.
3. **Diagnose the error logs, only if the Step 1 test fails.** Step 3 MUST NOT start until the Step 1 test fails.
   - Increment: read the top error message for the 09:12 window and name one failing dependency, about 5 minutes.
   - Blocker removed: no known cause.
   - Domain: Complicated. Kind: evaluative.
   - Rubric, written first: criteria are timing match with 09:12 (weight 50%) and error count share (weight 50%). Pass is a score of 70% or more, with evidence from the logs.
4. **Send the exec brief before the call.**
   - Increment: one message of at most 5 lines, about 2 minutes.
   - Blocker removed: no facts for the call.
   - Domain: Clear. Kind: deterministic.
   - Test, written first: Given the message is sent, When an exec reads it, Then it states impact (100% of checkout since 09:12), current action, and the time of the next update.
