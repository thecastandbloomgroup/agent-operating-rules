## Headline

Measure the errors first, then change the summariser, because you cannot improve what you cannot count.

- Agents report errors, but no data shows which errors, how often, or how bad.
- A low-cost review of 50 summaries gives a baseline within one session.
- A feedback button then gives a continuous error signal.
- Prompt or model changes come last, as capped trials against that baseline.

## Background

Your support tool now has a summariser built on a large language model (LLM). Agents say it is "sometimes wrong". You have no metrics, so the size and type of the problem are unknown.

## Relevance

Agents who distrust a summary re-read the full ticket. That removes the time the tool should save. Without a measure, any change you make is a guess.

## Information

Evidence:
- Agents report errors. This is one statement from your query, with no count. Confidence in any error rate is low (one unquantified source). [judgment]
- Summary errors usually fall into three types: wrong fact, missing key action, invented content. [judgment]

Assumption log:

A1. The tool stores each ticket text and its summary. Why not measured: the material does not state it. Validate by: pull 20 records from the database. If wrong: add logging before Step 1.

A2. Most errors fit the three types above. Why not measured: no error sample exists yet. Validate by: label 50 summaries in Step 1. If wrong: add new types to the rubric.

A3. Agents will click a feedback button if it takes under five seconds. Why not measured: the user has not answered. Validate by: track the click rate for one week. If wrong: sample tickets for review instead.

Alternative considered: change the model or prompt now. It loses because without a baseline you cannot show the change helped. [judgment]

## End

I recommend that we:

1. **Label a sample of 50 summaries.** Increment: two reviewers score 50 recent summaries in one session. Blocker removed: no baseline error data. Kind: evaluative. Domain: Confused, so this step gathers what we need to classify the problem [1]. Rubric (written first): criteria are factual accuracy (weight 50%), missing key action (30%), invented content (20%). Pass threshold for the rubric itself: reviewers agree on at least 80% of labels. Evidence needed: the ticket text next to each summary.

2. **Add a "Wrong" button with a reason list to each summary.** Increment: one button, one reason menu, one log table. Blocker removed: no ongoing error signal. Kind: deterministic. Domain: Clear. Test (written first) [2]:
   - Given an agent views a summary
   - When the agent clicks "Wrong" and picks a reason
   - Then the system stores the ticket ID, summary ID, reason, and time

   Step 2 runs in parallel with Step 1.

3. **Freeze the labelled sample as a test set and record the baseline.** Increment: score the current summariser on the Step 1 data. Blocker removed: no way to compare versions. Kind: deterministic. Domain: Clear. Test (written first):
   - Given the labelled set of 50 summaries
   - When the scoring script runs twice
   - Then both runs give the same error rate

   Step 3 MUST NOT start until Step 1 ends.

4. **Run one capped trial of a prompt change aimed at the top error type.** Increment: one prompt variant. Blocker removed: the most common error. Kind: stochastic. Domain: Complex, so this is a safe-to-fail probe, and its leverage is a guess. Acceptance test (written first):
   - Metric: share of summaries with zero factual errors under the Step 1 rubric
   - Baseline: the Step 3 result
   - Pass threshold: baseline plus 10 percentage points [judgment]
   - Sample size: 200 new tickets
   - Budget: one week and two variants
   - Stop condition: no gain after two variants

   Step 4 MUST NOT start until the baseline in Step 3 exists. If A2 is false, replace the target in Step 4 with the most common new error type.
