## Headline

I split this into two jobs: migrate to JSON Web Tokens (JWT) in small, tested steps, and treat sign-up conversion as a separate experiment.

- The migration is a known engineering task, so analysis and tests control its risk.
- Conversion has no baseline in the material, so we measure first and then run capped probes.
- The two jobs share the sign-up path, so we keep their changes apart to read the results.

## Background

The request has two parts. The first part moves the auth service from server-side sessions to JWT. The second part raises sign-up conversion, that is, the share of visitors who finish sign-up. The material gives no funnel data, no client list, and no logout rules.

## Relevance

If both changes ship together, a drop in conversion has two possible causes and we cannot tell them apart. A bad token design also creates a security gap that is costly to fix after release.

## Information

**Evidence**

- A JWT is valid until its `exp` claim passes, so the server cannot cancel it early without extra state [1].
- Best-practice rules for JWT cover algorithm choice, claim checks, and short lifetimes [2].
- At a 10% baseline (A1), a +1 point lift at 80% power and 5% significance needs about 15,000 visitors per arm. [judgment] The figure comes from the standard two-proportion formula.
- Conversion work is Complex: cause and effect show only after a trial [3].

**Assumption log**

A1. Current sign-up conversion is about 10%. Why not measured: the material does not state it. Validate by: query the last 30 days of funnel events. If wrong: change the sample size in Step 4.

A2. Clients are browsers and one mobile app, and one backend issues tokens. Why not measured: the material does not state it. Validate by: list the clients that call the auth service. If wrong: Step 2 adds a token-storage design per client.

A3. Users need logout and password-reset revocation within 15 minutes. Why not measured: the user has not answered. Validate by: ask the security owner. If wrong: the access-token lifetime in Step 2 changes.

**Alternative considered**

Keep server sessions and fix only the sign-up flow. This option removes revocation risk and costs less. It loses only if you need stateless scaling or mobile clients, which the request implies. [judgment]
