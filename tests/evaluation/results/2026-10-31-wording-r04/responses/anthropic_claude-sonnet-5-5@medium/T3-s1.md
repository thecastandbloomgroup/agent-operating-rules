## Headline

Split this into two workstreams, and migrate to JWT (JSON Web Token) only if a short design check passes.

- The migration is a deterministic change, so a test can prove it.
- The conversion work is an experiment, so a sample-size test must prove it.
- Run both at once only with separate user cohorts, because two changes at once hide the cause of any shift in conversion.

## Background

You asked for two changes: move the auth service from server-side sessions to JWT, and raise sign-up conversion. Conversion is the share of visitors who finish sign-up. The request gives no stack, traffic, or current conversion rate.

## Relevance

Both changes touch the sign-up path. If they ship together, you cannot tell which change moved conversion or caused a failure.

## Information

## End

I recommend that we take these steps in order:

1. **Instrument the sign-up funnel and record the baseline.**
   - Kind: deterministic. Domain: Clear.
   - Increment: add one event per funnel step and one dashboard.
   - Blocker removed: no baseline exists for A2.
   - Test: Given a visitor completes sign-up, When the funnel report runs, Then each step count is within 1% of the database count.

2. **Score JWT against sessions before any build.**
   - Kind: evaluative. Domain: Complicated.
   - Increment: list every service that reads a session, then fill one Pugh matrix [judgment].
   - Blocker removed: the revocation and logout risk is unknown.
   - Rubric, with sessions as the baseline and scores of -1, 0, or +1:
     - Revocation (weight 30).
     - Fit with the JWT security guidance (weight 20).
     - Migration effort (weight 20).
     - Operating cost (weight 15).
     - Client compatibility (weight 15).
   - Evidence per criterion: one config file, log, or client list.
   - Pass threshold: weighted sum of +20 or more. Below it, keep sessions and skip Step 3.

3. **Build JWT behind a flag, with sessions still accepted.**
   - Kind: deterministic. Domain: Complicated.
   - Step 3 MUST NOT start until Step 2 passes.
   - Increment: issue and validate tokens for one internal user group.
   - Blocker removed: no working JWT path exists.
   - Test: Given a token signed with algorithm "none", When the API receives it, Then the API returns 401.
   - Test: Given an expired token, When the API receives it, Then the API returns 401.
   - Test: Given a valid token, When the API receives it, Then the API returns 200.
   - Sessions MUST remain valid until a rollback test passes.

4. **Run one capped sign-up experiment on a single form change.**
   - Kind: stochastic. Domain: Complex. Leverage is a guess.
   - Step 4 MUST NOT start until the baseline in Step 1 exists.
   - Increment: change one element, for example remove one optional field.
   - Blocker removed: the cause of drop-off is unknown.
   - Metric: sign-up completion rate. Baseline: Step 1 value (A2: 10%).
   - Pass threshold: a gain of at least 1 point, with 5% significance.
   - Sample size: 14,700 visitors per arm.
   - Budget: four weeks. Stop condition: stop if the variant trails the baseline by 2 points at half the sample.
   - Run it only on users who are not in the Step 3 cohort.

Step 4 MAY run in parallel with Steps 2 and 3 once Step 1 passes.

If A3 is false, replace the 1-point target in Step 4 with a 2-point target and recompute the sample size.

## Follow-up

Conditions that change the recommendation:

- If Step 2 scores below +20, keep sessions and drop Step 3.
- If the baseline in Step 1 differs from 10%, recompute the Step 4 sample size.
