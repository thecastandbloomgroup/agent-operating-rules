## Headline

Measure the errors first, because the tool has no metrics and so no change can be shown to help.

- Agents say "sometimes wrong", but no one knows how often or in what way.
- A small labeled sample turns that feeling into an error rate and error types.
- A fixed test set then lets you compare each change with a baseline.
- Only after that should you change the prompt or model.

## Background

Your team added an LLM summariser to a support tool. Agents report that summaries are "sometimes wrong". You have no metrics, and you ask for a better summariser.

## Relevance

Agents who distrust the summary will reread the full ticket. That removes the time saving the tool was built to give. Without a metric, a change can make the tool worse and no one will see it.

## Information

**Evidence**

- No usage, error, or feedback data was supplied. [no source]
- LLM summaries can contain invented facts and omissions. Surveys call the first kind "hallucination". [1]
- Agent comments should be grouped into themes, with a count of supporting sources per theme. [2]
- The likely error types are invented facts, missed key facts, and wrong customer status. [judgment] Confidence is low, because no sample has been read yet.
- The work is Confused in the Cynefin sense, because the failure mode is unknown. [3]

**Assumption log**

A1. The summary shows to agents inside the ticket view, and agents can read the source ticket. Why not measured: the material does not state it. Validate by: open five tickets. If wrong: Step 2 changes to fit the real interface.

A2. You can export tickets with their summaries. Why not measured: no tool can reach your system. Validate by: request a 50-ticket export. If wrong: Step 1 waits for log access.

A3. "Wrong" covers invented facts, missed facts, and wrong status. Why not measured: the user has not answered. Validate by: ask three agents for their last wrong summary. If wrong: Step 1 adds new error types.

A4. Two agents can spend two hours each on labeling. Why not measured: measuring costs more than the decision is worth. Validate by: ask the team lead. If wrong: cut the sample to 30.

**Alternative considered**

The strongest alternative is to switch to a larger model now. It loses because you cannot measure the gain, and the cost is higher. Errors from missing input, such as a truncated ticket, would not change. [judgment]

## End

I recommend that we take these four actions in order.

1. **Classify the errors (Confused, evaluative).**
   - Increment: two agents read 50 random summaries against their tickets and label each error. Finish this in one session.
   - Blocker removed: no one knows the failure mode.
   - Test, written first: a rubric. Criteria and weights: error present (40%), error type (30%), severity for the customer (30%). Pass threshold: both agents agree on at least 80% of labels. Evidence: the ticket text and the summary.
   - Step 2 MUST NOT start until this test passes.

2. **Add a feedback button and log (Clear, deterministic).**
   - Increment: one "wrong summary" button with an error-type choice, saved with the ticket ID and summary text.
   - Blocker removed: no ongoing signal.
   - Test, written first:
     - Given an agent views a summary
     - When the agent presses "wrong" and picks "invented fact"
     - Then the log holds the ticket ID, summary text, error type, and time.

3. **Build the test set and baseline (Complicated, evaluative).**
   - Increment: 100 labeled tickets with reference facts, taken from Step 1 and the Step 2 log. Score the current summariser on them.
   - Blocker removed: no way to compare changes.
   - Test, written first: a rubric. Criteria: facts correct (50%), key facts present (30%), length fit (20%). Pass threshold: the baseline error rate is recorded and two reviewers agree on 80% of labels. Evidence: the reference facts.
   - Step 4 MUST NOT start until this test passes.

4. **Probe one fix for the top error type (Complex, stochastic).**
   - Increment: change the prompt to target the most common error from Step 1. For example, require every fact to come from the ticket text. Run it on the test set.
   - Blocker removed: the cause of the errors is unknown. The leverage of this fix is a guess.
   - Test, written first: the metric is the share of summaries with at least one error. The baseline comes from Step 3. Pass: a relative drop of at least 30% on all 100 tickets, with no rise in missed key facts. Budget: one day. Stop condition: two prompt variants fail. Then review the input side, such as ticket truncation.
   - The 100-ticket sample detects only large gains. Treat a smaller gain as unproven.

If A2 is false, replace Step 1 with a manual review of 30 tickets that agents flag by hand.

## Follow-up

Open questions: none.

Conditions that change the recommendation:

- If Step 1 shows most errors come from truncated input, fix input handling before any prompt change.
- If the error rate in Step 3 is below 5%, stop and keep the tool.
