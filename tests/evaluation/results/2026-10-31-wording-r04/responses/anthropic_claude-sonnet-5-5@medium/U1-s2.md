## Headline

Measure the failures first, then fix the most common cause and prove the fix with repeated runs.

- The request has no logs or build details, so the cause is unknown.
- Published studies show a few causes explain most flaky tests, so a failure table narrows the search fast.
- Quarantine of the worst test limits the damage while the fix is built.
- A rerun count, not one green build, shows that the fix works.

## Background

The build passes and fails on the same code. You gave no logs, stack, or failure rate. This response assumes a continuous integration (CI) build with automated tests.

## Relevance

A flaky build wastes reruns and hides real failures. Each ignored red build makes the next real defect easier to miss.

Google reported that about 1.5% of its test runs showed a flaky result [2].

Both sources describe tests in other projects. They set a baseline, not a diagnosis of your build. [judgment]
