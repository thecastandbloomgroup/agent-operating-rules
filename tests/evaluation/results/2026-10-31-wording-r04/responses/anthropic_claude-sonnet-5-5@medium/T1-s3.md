## Headline

I decide that the team needs one named decider, one automated formatter, and one review rule: the tool settles format, not people.

- The friction comes from a missing decision rule, not from the style itself.
- A formatter in continuous integration (CI, the automatic check that runs on every change) removes format from review.
- A short trial with a stop condition shows whether the habit holds.

## Background

Your team does not agree on SQL (Structured Query Language) format. Every review includes this argument [1]. You asked for a fix to the culture problem.

## Relevance

Each format comment costs review time and adds friction. The cost repeats on every change until the team has a rule.

## Information

**Evidence**

- Google's review guide says the style guide is the final authority. For points the guide does not cover, the author's choice stands if it stays consistent [2]. This supports a rule where a written guide ends the debate.
- SQLFluff is an open source SQL linter and formatter. It reads rules from a config file and can fix many violations automatically [3]. This is a vendor source about its own product, so no independent test backs it.
- Cynefin is a framework that sorts work by how clear cause and effect are [4]. Format taste is a people problem with no known fix, so Step 4 is a probe, not a commitment.
- The claim that a formatter removes most style comments is likely (66 to 100%). [judgment] No source measures it for your team. Step 4 measures it.

**Assumption log**

A1. The team writes SQL in a shared repository with pull-request review. Why not measured: the material does not state it. Validate by: ask one teammate. If wrong: replace Step 2 with a pre-commit hook or editor setting.

A2. Nobody holds authority to settle style, and that is why the debate repeats. Why not measured: the material does not state it. Validate by: ask who decided the last format dispute. If wrong: skip the decider part of Step 1.

A3. The team can run a formatter in CI. Why not measured: no tool can reach your pipeline. Validate by: run SQLFluff locally on one file. If wrong: Step 2 uses a local script, and the Step 2 test uses that script.

**Alternative considered**

The alternative is a team vote on style. It loses because a vote gives no authority for future disputes, and the losing side keeps raising the issue [judgment].

## End

I recommend that we:

1. **Choose a base style and a decider.**
   - Increment: in one 45-minute session, list two or three public SQL style guides plus the SQLFluff defaults. Score them with a rubric. The criteria are readability (weight 40%), tool support (40%), and match to current code (20%). The pass threshold is 70 of 100, with evidence for each score. Name one decider for later disputes.
   - Blocker removed: no one has authority to end the debate.
   - Test: the rubric is written before scoring, and every score cites evidence.
   - Kind: evaluative. Cynefin domain: Complicated. The scoring picks among several good practices.

2. **Encode the choice in a formatter config and run it in CI.**
   - Increment: one config file and one CI job.
   - Blocker removed: people enforce style by hand.
   - Test, in Gherkin form:
     - Given a SQL file with a lowercase keyword where the guide requires uppercase,
     - When the CI job runs,
     - Then the job fails and names the line.
   - A second scenario shows a compliant file passes.
   - Step 2 MUST NOT start until Step 1 names the style.
   - Kind: deterministic. Cynefin domain: Clear. The practice is known.

3. **Reformat the existing SQL in one commit.**
   - Increment: one commit that only changes format.
   - Blocker removed: old files would fail the CI job from Step 2.
   - Test:
     - Given the reformatted repository,
     - When the CI job and the existing query tests run,
     - Then both pass.
   - Step 3 MUST NOT start until both Step 2 scenarios pass.
   - Kind: deterministic. Cynefin domain: Clear.

4. **Run a four-week trial of the rule "the tool decides format; reviewers do not comment on it."**
   - Increment: count format comments in the last 20 reviews now, as the baseline. Then count them again in the first 20 reviews after Step 3.
   - Blocker removed: the habit of arguing in review.
   - Test:
     - The metric is format comments per review.
     - The pass threshold is a drop of at least 80% from the baseline, at a sample size of 20 reviews.
     - The stop condition is two team members asking to end the trial.
     - The budget is 30 minutes of counting.
   - Start the baseline count now. Run the trial in parallel with Steps 2 and 3. The measured count after Step 3 decides the result. Leverage here is a guess.
   - Kind: stochastic. Cynefin domain: Complex. This is a safe-to-fail probe.
