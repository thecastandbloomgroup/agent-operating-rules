## Headline

I recommend that we measure first, then change the summariser, because no one can improve an error that the team has not counted.

- The team has no error rate, so no change can be shown to help.
- Agent comments are the only evidence now, and they do not say what "wrong" means.
- A labelled sample and a fixed test set turn "sometimes wrong" into a number.
- Prompt changes come last, as capped trials against that number.

## Background

The support tool shows an LLM-generated summary to agents. Agents report that it is "sometimes wrong". The team has no metrics, and the request is to make it better.

## Relevance

Agents who distrust a summary reread the full ticket. That removes the time the tool should save. A wrong summary that an agent trusts can also cause a wrong reply to a customer.

## Information

**Evidence**
- Agent reports are the only data. The count of reports, the error types, and the error rate are unknown [no source].
- Errors in LLM summaries usually fall into a few types, such as invented facts, missing facts, and wrong tone. This is likely (66 to 100%) [judgment].
- Thematic analysis groups free-text comments into themes and counts the sources behind each theme. This is the method for Step 1.
  
  [1] Braun and Clarke, 2006

**Assumption log**

A1. The summaries cover support tickets or chat threads that agents can reread. Why not measured: the material does not state it. Validate by: ask one agent for an example. If wrong: Step 3 needs another source of reference facts.

A2. The team can edit the prompt and the model settings. Why not measured: the material does not state it. Validate by: check the repository for the prompt file. If wrong: replace Step 4 with a vendor request.

A3. The tool produces at least 100 summaries per week. Why not measured: no log was provided. Validate by: count rows in the summary table. If wrong: lower the sample size and widen the stop margin in Step 4.

A4. Agents will flag a wrong summary when the flag takes one click. Why not measured: the user has not answered. Validate by: count flags in the first three days. If wrong: sample summaries by hand instead.

**Alternative considered:** switch to a larger model now. It loses because there is no baseline to show a gain, and the cost per summary rises [judgment].

## End

I recommend that we take these four actions, in this order:

1. **Classify the errors (Confused, evaluative).**
   - Increment: pull 50 summaries that agents called wrong. Two people label each error.
   - Blocker removed: no one knows what "wrong" means.
   - Test, written first. Rubric: coverage of the labelled errors by the categories (weight 50%, pass at 80% or more). Agreement between the two raters (weight 30%, pass at 70% or more). Each category names a fix the team can try (weight 20%, pass when every category does). Pass threshold: total score of 80 out of 100. Evidence: the 50 labelled rows.
   - Cynefin: Confused. This step gathers what the team needs to classify the rest [2].

2. **Add a one-click "wrong" flag with a reason code (Clear, deterministic).**
   - Increment: one button and one log table.
   - Blocker removed: no ongoing data.
   - Test, written first [3]:
     - Given an agent views a summary
     - When the agent clicks "wrong" and picks a reason
     - Then the log stores the summary ID, the reason, and the time
   - Cynefin: Clear.
   - Step 2 MUST NOT wait for Step 1. The reason codes use the Step 1 categories when they exist.

3. **Build a test set of 100 tickets (Complicated, stochastic).**
   - Increment: agents write the key facts for 100 tickets. A script checks each summary against them.
   - Blocker removed: no baseline.
   - Test, written first. Metric: share of summaries with no wrong fact and no missing key fact. Baseline: measured on the current summariser. Threshold: set after the baseline run, with a gain of at least 10 points. Sample size: 100 tickets, run 3 times.
   - Cynefin: Complicated. Step 1 supplies the analysis that picks the checks.
   - Step 3 MUST NOT start until the Step 1 rubric passes.

4. **Run one prompt trial (Complex, stochastic probe).**
   - Increment: change the prompt to require a fixed template, with one quoted line from the ticket for each fact.
   - Blocker removed: the cause of the top error type from Step 1.
   - Test, written first. Metric: the Step 3 score. Baseline: the Step 3 baseline. Pass: a gain of at least 10 points on 100 tickets in 3 runs. Budget: two working days. Stop condition: stop at the budget, or when two runs show no gain.
   - Cynefin: Complex. The leverage is a guess.
   - Step 4 MUST NOT ship until Step 3 gives a baseline. Step 4 MAY run in parallel with Step 2.

If A2 is false, replace Step 4 with a written request to the vendor that includes the Step 1 categories.
