Headline
Move browser login to a short-lived JSON Web Token (JWT) in a secure cookie, and test one signup cut before any wider redesign.
The cookie keeps the token away from page script, so a cross-site script attack cannot read it.
A JWT still helps when services must check a caller without a shared session store.
Signup completion needs one measured field cut, because a joint release hides which change moved the rate.

Background
The request asks to leave server sessions for JWT and to raise signup conversion.
The material has no code, no traffic counts, and no list of signup fields.
Therefore this plan treats the client as a browser app with cookie sessions and a server form.

Relevance
A weak token store can leak accounts after one script bug.
A signup change can also cut completion, so each change needs its own pass test.

Information
RFC 7519 defines a JWT as a compact, signed set of claims [1].
Page script can read local storage, but it cannot read an HttpOnly cookie [2].
HttpOnly means the browser hides the cookie from script.
SameSite=Lax means the browser sends the cookie on same-site requests and on top-level navigations.
The field cut is about as likely as not to raise completion, because no baseline rate is in the material.

A1. The client is a browser app that uses server sessions in cookies. Why not measured: The material does not state it. Validate by: Read the auth code and one login Set-Cookie header. If wrong: Replace Step 2 with a bearer token for the native client only.
A2. Signup conversion means the share of starts that finish account creation. Why not measured: The material does not state it. Validate by: Read the start and complete event names. If wrong: Change the Step 4 metric before the probe.
A3. No rule forces a shared-nothing token this week. Why not measured: The material does not state it. Validate by: Read the security requirements page. If wrong: Do the service JWT before the browser cookie change.

The strongest alternative is a bearer JWT in local storage.
It loses because page script can copy that token, and logout cannot end it without new server state [judgment].

End
I recommend that we take these four actions.

1. Confused. Evaluative.
Test: Rubric. Session store exists, weight 40. Cookie flags documented, weight 30. Client is browser, native, or both, weight 30. Pass at 70. Evidence is the auth code and one login trace.
Increment: one session to score that rubric.
Blocker: the domain is unknown, so later leverage is not trusted.
Step 2 MUST NOT start until this score is recorded.

2. Complicated. Deterministic.
Test: Given a test user, When login succeeds, Then Set-Cookie has HttpOnly, Secure, and SameSite=Lax.
The response body has no access token.
Increment: change only the login response in one service.
Blocker: script-readable tokens.
This step waits on Step 1, because that score picks a cookie or a bearer token.

3. Clear. Deterministic.
Test: Given the signup form source, When the list is written, Then each field has a required or optional mark and a source line.
Increment: one field table from the current form.
Blocker: unknown friction before any copy change.
This step can run in parallel with Step 2.

4. Complex. Stochastic.
Test: Metric is signup completion rate. Baseline is the prior 14 days. Pass is a rise of 2 percentage points. Sample is 1,000 starts or 14 days, whichever comes first. Stop if the rate falls by 2 points.
Increment: remove one required field that Step 3 marks as unused for account creation, behind a flag, with a 14 day budget.
Blocker: an unmeasured drop in completion.
Step 4 MUST NOT start until the Step 3 list exists.
Run it in parallel with Step 2, and do not grow the change inside the budget.

Follow-up
If A1 is false, replace Step 2 with a bearer JWT for the native client only.
If A3 is false, issue the service JWT before the browser cookie change.
