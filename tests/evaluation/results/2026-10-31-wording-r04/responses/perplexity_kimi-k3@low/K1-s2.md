## Headline

Cut the connection pool back to its old size: the release capped it at 8 while 32 workers compete for connections, and 690 ms of the 900 ms p95 is pool wait. The trace data isolates `db.pool.acquire` as the dominant new latency [3]. The ORM change and the cache TTL change are secondary, but the TTL change also raises load and needs a rollback.

## Background

The p95 for `GET /customers/{id}/orders` rose from 120 ms to 900 ms after release 2026.10.21 [3]. The release changed the pool config, the cache TTL, and one ORM query [2]. Logs record 1,800 to 2,400 "pool exhausted" warnings per hour on 2026-10-22, against zero on 2026-10-20 [1].

## Relevance

The 5 s acquire timeout now converts queueing into 503 errors. The error rate rose from 0.02% to 0.40%, and 96% of those errors are PoolTimeout [3]. Latency and availability both degrade until the pool recovers.

## Information

**Evidence, causes ranked:**

1. **Pool size cut, primary cause.** `max_size` fell from 50 to 8 and `acquire_timeout_s` fell from 30 to 5 [2]. The service runs 32 workers across 4 pods [2]. Trace B shows `db.pool.acquire` p95 at 690 ms, versus 3 ms in window A [3]. That is about 77% of the 900 ms total. Peak DB connections from this service fell from 31 to 8 [3].
2. **Cache TTL cut, secondary cause.** `default_ttl_s` fell from 300 to 60 [2]. The miss rate rose from 12% to 31% [3]. Misses add DB work, which holds pool connections longer, so this amplifies cause 1.
3. **ORM change, exonerated.** `selectinload(Order.lines)` adds a second query [2]. Yet `db.query order_lines` p95 fell from 30 ms to 26 ms, and total query spans are flat [3]. The new query pattern does not drive the regression.

DB CPU is flat (38% to 41% peak), so the database is not saturated [3]. Requests per second are flat (410 vs 405), so traffic did not change [3]. The bottleneck is the client-side pool cap, not the server. High confidence: the acquire-span number, the connection count, the flat traffic, and the flat DB CPU all point the same way.

**Assumption log:**

A1. The ticket OPS-412 connection limit refers to the DB side and permits 50 per pod or can be renegotiated. Why not measured: the material states the ticket but not the new limit. Validate by: ask OPS for the limit value in OPS-412 before redeploying. If wrong: set `max_size` to the limit divided by pod count, and reduce timeouts accordingly.

A2. No other read replica or failover event occurred in window B. Why not measured: the traces show DB CPU and query times flat, which argues against it, but the material has no DB admin log. Validate by: check DB admin logs for 2026-10-22. If wrong: revisit cause ranking after the rollback, using the metric in Step 3.

**Alternative considered:** keep the pool at 8 and instead cut DB load (raise TTL, cache more, add indexes). It loses because query spans are flat and the acquire span alone accounts for 690 ms of the regression [3]. Load reduction cannot fix a 4-to-1 worker-to-connection ratio.

## End

I recommend that we take four actions, in this order.

1. **Restore `max_size: 50` and `acquire_timeout_s: 30` in `config/db.yaml` and redeploy.** This removes the queueing blocker for 32 workers. Kind: deterministic, Cynefin domain: Clear (best practice exists: undo the regression). Test first: Given release 2026.10.21 config in staging, When the rollback config deploys, Then 500 sequential requests complete with acquire p95 under 10 ms and zero PoolTimeout errors.
2. **Restore `default_ttl_s: 300` in `config/cache.yaml` and redeploy.** This cuts the miss rate back toward 12% [3]. Kind: deterministic, domain: Clear. Test first: Given the rolled-back cache config, When a fixed 10,000-request replay runs, Then the miss rate is at or below 15%. This step may deploy with Step 1 as one release.
3. **Verify with production metrics for 30 minutes after the deploy.** Metric: p95 of `http.request` and `db.pool.acquire`, error rate. Baseline: window A values [3]. Pass threshold: p95 total at or below 150 ms, error rate at or below 0.05%. Kind: stochastic, sample size: at least 10,000 requests. Domain: Complicated (read production telemetry).
4. **Fix the intake process: add a config review check that compares pool size to worker count.** The bug shipped because 8 connections were approved for 32 workers [2]. Rubric: the check fails a release when `max_size` is below the worker count per pod. Pass threshold: the check blocks a synthetic replay of release 2026.10.21. Kind: evaluative, domain: Clear. Step 4 MUST NOT start until the test in Step 3 passes, so the page quiets first.

If A1 is false and OPS-412 caps connections below 50 per pod, replace Step 1 with `max_size` equal to the cap divided by pod count, and keep Step 2 as the offsetting lever.
