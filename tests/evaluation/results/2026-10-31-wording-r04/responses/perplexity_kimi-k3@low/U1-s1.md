## Headline

The fix is a three-step triage loop: reproduce the failure pattern, then isolate the cause class, then remove it. The plan below covers the most common cause of flakiness, which is nondeterminism in tests or dependencies [judgment].

## Background

The build fails intermittently without a stated error or environment. No logs, CI configuration, or failure rate were provided.

## Relevance

Flaky builds block merges and hide real defects. Team confidence in the pipeline drops fast, so the payoff from fixing this compounds.

## Information

Common flake classes, in rough order of frequency in CI systems [judgment]:

1. Test nondeterminism: time, randomness, ordering, shared state.
2. External dependencies: network calls, package registries, third-party services.
3. Resource issues: parallel jobs, timeouts, disk or memory limits.
4. Unpinned tools or dependencies that resolve differently per run.

A quantitative bucket supports this: Google reported that about 1.5% of its test runs were flaky, and flakiness clustered in time-of-day and parallelism effects [1]. That source is a blog post about Google's own system, so treat it as secondary evidence that the pattern generalizes, not as a basis for your numbers.

## End

I recommend that we:

1. **Measure the pattern** (Clear, deterministic). Pull the last 50 CI runs and record failure rate, failed step, time of day, and agent. This removes the blocker of not knowing where the flake lives. Test: *Given* 50 recent runs, *when* I tabulate failures by step and time, *then* every failure has a recorded step, timestamp, and error message.
2. **Reproduce it** (Complicated, deterministic). Run the most-failing step 20 times on one machine, with Step 3 blocked until this loop completes. This isolates the cause class from A2. Test: *Given* the failing step, *when* I run it 20 times, *then* at least one failure occurs or I accept it as environment-specific and move to Step 3.
3. **Classify the cause** (Clear, evaluative). Score the observed failures against the four classes above. Rubric: a class passes if at least one failure traces to it, weighed by count; threshold is one or more passing classes. Evidence: the logs from Steps 1 and 2.
4. **Fix the top class with a capped probe** (Complex). Apply the smallest change for the leading class, for example freeze time in the one suspect test. Measure: rerun the step 30 times; pass threshold: zero failures out of 30. Stop condition and budget: stop if still failing after three change attempts, then escalate to a human pairing session.
5. **Add a temporary retry with alerting** (Clear, deterministic). Gate flaky steps at two retries and log each retry. This buys headroom while Step 4 runs but MUST NOT close the issue. Test: *Given* a forced failure in a test branch, *when* the pipeline runs, *then* exactly two retries occur and each is logged.

Step 3 MUST NOT start until Step 2 finishes. Step 5 MAY start immediately in parallel.
