# Headline

Migrate the auth service to JWT with a short rollout that keeps sessions running in parallel, and treat sign-up conversion as a separate workstream with its own conversion baseline first. Security migration and conversion optimization have different failure modes, so they MUST NOT ship as one change. Both workstreams start with measurement before any code changes.

- JWT migration runs in four steps: dual-issue tokens, validate both, cut over, remove sessions, with a rollback at each step.
- Conversion work runs independently: define the funnel metric first, then run one capped experiment.
- The strongest coupling point is the sign-up flow touching auth code, so sequencing, not merging, is the control.

# Background

The request contains two goals: replace session-based auth with JSON Web Tokens (JWT), and improve sign-up conversion. No stack, traffic level, or current conversion rate was supplied. The plan therefore uses assumptions and validates each one cheaply before committing.

# Relevance

A failed auth migration can lock out every user, so rollback design matters more than speed. Conversion changes alter sign-up behavior, so an untracked change cannot be attributed.

# Information

**Evidence**

- JWT is a stateless token standard, so token verification removes server-side session storage, but token revocation becomes harder [2].
- JWT forgery incidents often trace to weak algorithm and key handling, so pinning the algorithm (for example RS256 or EdDSA) is standard guidance [1].
- Conversion improvements require an attribution baseline; Nielsen Norman Group practice is to instrument the funnel before changing it [3].
- The claim that merging both changes into one deploy raises rollback risk is [judgment], based on standard release practice.

**Alternative considered**

Alternative: convert everything to JWT in one deploy and bundle conversion tweaks into the new sign-up page. It loses because a single deploy removes the rollback path and makes conversion change unattributable (A2, [3]).

# End

I recommend that we proceed in two parallel workstreams, sequenced as follows.

1. **Define acceptance and baseline first (Complicated, evaluative).** Write the funnel rubric: metric = completed sign-ups per started sign-up, baseline = last 7 days, weight = 100% on this metric, pass threshold for later changes = +5% relative at n ≥ 1,000 starts per arm [3]. Increment: one dashboard query. Blocker removed: no attribution possible. Test: rubric written and baseline number recorded.
2. **Dual-issue JWT alongside sessions (Complicated, deterministic).** Issue a signed JWT (RS256, 15-minute expiry, refresh token in an HTTP-only cookie) at login, while sessions still work [1][2]. Depends on Step 1 completing. Blocker removed: zero end-to-end JWT path exists. Test: Given valid credentials, When login succeeds, Then both a session and a verifiable JWT are returned, and an endpoint accepts either.
3. **Cut validation to JWT, keep sessions as fallback for one week (Complicated, deterministic).** Depends on Step 2 passing. Test: Given a request with only a valid JWT, When it hits a protected route, Then access is granted; Given an expired JWT, Then a 401 with refresh flow is returned. Monitor error rates daily.
4. **Remove session code (Clear, deterministic).** Depends on 7 clean days in Step 3 (stop condition: auth error rate above 0.1% rolls back). Test: Given no session store running, When the full auth test suite runs, Then all tests pass.
5. **Run one capped conversion probe (Complex, stochastic).** Change one element of the sign-up form (for example, fewer fields), A/B test it. Metric and baseline from Step 1; accept at +5% relative, n ≥ 1,000 per arm, stop after 14 days regardless. Budget capped at one variant. Leverage is a guess because user behavior is only visible after the probe.
