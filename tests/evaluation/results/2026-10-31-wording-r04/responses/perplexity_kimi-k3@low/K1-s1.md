# Headline

The pool config change in release 2026.10.21 caused the latency regression. Revert `max_size` and `acquire_timeout_s`, then restore cache TTL.

- Trace data shows `db.pool.acquire` grew from 3 ms to 690 ms at p95. Queries stayed flat [1].
- The diff cut `max_size` from 50 to 8 and `acquire_timeout_s` from 30 to 5 [2].
- The cache TTL cut raised the miss rate from 12% to 31%. This adds load to the same starved pool [1][3].
- The ORM change adds one query. Its spans are unchanged, so it is not the cause [1].

## Background

p95 latency on `GET /customers/{id}/orders` rose from 120 ms to 900 ms after release 2026.10.21. The release changed the ORM, the cache config, and the pool config. Logs, traces, and the diff are attached.

## Relevance

Errors rose from 0.02% to 0.40%, and 96% of errors are pool timeouts [1]. Under higher load, waiters will grow and 503s will rise further. A fix restores error rate and removes a failure mode that worse traffic will amplify.

## Information

**Evidence.** In Window B, `db.pool.acquire` is the dominant span: p50 140 ms, p95 690 ms [1]. Query spans are flat. `orders` went 52 to 58 ms at p95. `order_lines` went 30 to 26 ms [1]. Therefore the database answers fast. Requests wait on connections.

Peak active DB connections from this service fell from 31 to 8 [1]. The service runs 4 pods with 8 workers each, so 32 workers compete for 8 connections per the new limit [2]. The old config gave 50 connections per pod. Logs confirm this: zero "pool exhausted" warnings on 2026-10-20, versus 1,800 to 2,400 per hour on 2026-10-22 [3]. Pool timeouts occur at 8 in use with 12 to 14 waiters [3].

The cache TTL cut from 300 s to 60 s raised the miss rate from 12% to 31% [1][2]. Each miss needs a DB round trip, so it holds a connection longer in queue pressure. This is a secondary contributor, likely adding tens of milliseconds of extra wait [judgment].

The `selectinload` adds one extra query per request. That query runs 9 to 26 ms and holds a connection briefly [1]. Under the small pool, this lengthens hold time slightly. The `pool.acquire` span accounts for roughly 690 of the 780 ms p95 increase, so queuing dominates [inference: 900 minus 120 equals 780; acquire rose 687 ms].

**Assumption log.**

A1. The new DB connection limit in ticket OPS-412 is per service, not per pod. Why not measured: the material quotes the ticket but not its text. Validate by: read OPS-412 or ask the DBA. If wrong: the allowed pool size changes, but revert-then-right-size still holds as sequence.

A2. Traffic on 2026-10-22 matched 2026-10-20. Why not measured: only peak RPS is given (410 vs 405). Validate by: compare hourly request counts. If wrong: the pool still saturates at 8 connections, so the recommendation stands.

**Alternative considered.** Raise `max_size` above 8 while keeping the new DB limit. This loses because A1 says the limit may cap the service at 50 total. Exceeding a DB-side limit risks connection rejections. The revert restores a known-good state first. Right-size after, against the real limit.

## End

I recommend that we:

1. **Revert `config/db.yaml` pool settings** (`max_size: 50`, `acquire_timeout_s: 30`) and deploy. This removes the queueing blocker. Deterministic, Clear domain. Test first, Gherkin: Given the reverted config is deployed, When 1,000 requests run at 400 RPS against `/customers/{id}/orders`, Then `db.pool.acquire` p95 is under 10 ms and error rate is under 0.05%.

2. **Restore `default_ttl_s: 300` in `config/cache.yaml`** and deploy with Step 1. This cuts the cache miss rate back to about 12%, so it removes load from the pool. Deterministic, Clear domain. Test first, Gherkin: Given the restored TTL, When 10,000 requests are sampled, Then cache miss rate is at or below 15%.

3. **Confirm end-to-end latency.** Evaluative, Clear domain. Rubric written first: `http.request` p95 at or below 150 ms for one hour at peak RPS (weight 70), error rate at or below 0.05% (weight 30). Pass threshold: both criteria met on production telemetry.

4. **Right-size the pool against OPS-412 later.** Read the ticket, compute the per-pod limit (service limit divided by pods), and set `max_size` to that value. Complicated domain, since analysis picks the value. This step MUST NOT start until the test in Step 3 passes. Evaluative. Pugh matrix: compare candidate sizes on p95 acquire time, timeout count, and DB connection count against the limit. Tests written as acceptance thresholds before load tests.

5. **Keep the `selectinload` change** unless Step 3 fails. It removed the per-line lazy-load pattern at no measured cost [1]. If A1 proves false and the limit is per pod, replace Step 4 with a transparent 200-connection ceiling discussion with the DBA.

## Follow-up

**Conditions that change the recommendation.** If OPS-412 mandates lower than 50 total, set `max_size` to (limit / 4 pods) in Step 1 instead of 50, and expect p95 to settle between 120 and 200 ms.
