## Headline

Baselining the summariser's errors before changing anything is the fastest path to "better", because "sometimes wrong" has no measurable target without it. First measure error type and rate on real tickets. Then fix the dominant error type with the cheapest change. Then set a release threshold so the fix cannot regress.

## Background

A support tool now uses an LLM summariser. Agents report it is sometimes wrong. No metrics or error taxonomy exist. The request is to improve it without a stated quality target.

## Relevance

Without a baseline, any change is a guess and improvement cannot be proven. Because agent reports are anecdotal, the first measurable step decides all later work. Guessing wrong costs weeks [judgment].

## Information

Evidence available: one qualitative theme, "sometimes wrong", from agents (one source group, no count, no examples). Confidence: low, because no quantitative data exists. Typical LLM summariser error classes are hallucination (facts not in the source), omission (dropped key facts), and misattribution (wrong actor or cause) [no source, judgment]. The Cynefin domain is Confused until errors are classified, because cause and effect are not yet visible [18].

Assumption log:

A1. Ticket text and summaries can be sampled and reviewed by staff. Why not measured: the material does not state it. Validate by: confirm access with the tool admin. If wrong: use exported logs or synthetic tickets instead.

A2. A wrong summary costs agent time but not safety or money. Why not measured: the material does not state it. Validate by: ask one support lead. If wrong: add a human-review gate before summaries are shown.

A3. The underlying model and prompt can be changed. Why not measured: the material does not state it. Validate by: check the integration config. If wrong: shift fixes to post-processing and UI warnings.

Alternative considered: tuning the prompt immediately based on agent complaints. It loses because untested prompt edits trade one error type for another with no way to detect the trade [judgment].

## End

I recommend that we take these four actions, in this order.

1. Build a 100-summary evaluation set from real tickets and score each as correct or wrong by type (hallucination, omission, misattribution). Blocker removed: no baseline. Kind: evaluative. Test first: a rubric with the three error classes weighted equally, pass threshold defined as a measured error rate below 10%, scored against full ticket text as evidence. Domain: Confused, because this classification enables all later steps. Step 2 MUST NOT start until this scoring is complete.

2. Fix the dominant error class with the cheapest change, that is a prompt or context fix. Blocker: the known largest cause of wrongness. Kind: deterministic for the change itself. Test first (Gherkin): Given a ticket from the failing class, When the summariser runs, Then the summary contains no unsupported facts and keeps all key facts per the rubric. Run against the evaluation set from Step 1. Domain: Complicated, because the analysis from Step 1 picks the practice.

3. Measure the fix with a stochastic acceptance test. Metric: rubric pass rate. Baseline: the rate from Step 1. Pass threshold: error rate under 10% or a 50% relative reduction, whichever is stricter. Sample size: 100 new unseen tickets. Budget: two working sessions. Stop condition: rate does not improve after two prompt iterations, escalate to a model or retrieval change. Domain: Complex, so this is a capped probe; leverage is a guess at this point.

4. Add a release check that reruns the evaluation set on every prompt or model change. Blocker: silent regression. Kind: deterministic. Test first (Gherkin): Given a proposed prompt change, When the harness runs, Then deployment is blocked if the error rate exceeds the Step 3 threshold. Domain: Clear.

## Follow-up

Conditions that change the recommendation: if A2 is false, insert a human-review gate before Step 2. If A1 is false, use synthetic tickets for Step 1 at lower confidence.
