# Headline

Split this into two workstreams: migrate to JWT with dual verification so existing sessions do not break, and measure sign-up conversion before you change it.

- JWT first, because auth underpins every request and a failed rollout affects all users.
- Conversion second, because no baseline exists, so "better" is not yet measurable.
- Run a small conversion probe in parallel once its budget and metric are fixed.

# Background

The request has two parts: replace session-based auth with JSON Web Tokens (JWT, a signed, self-contained token format), and improve sign-up conversion. No baseline conversion rate, funnel analytics, or JWT configuration exists in the material.

# Relevance

A failed auth migration can log out every active user at once. A change to sign-up without a baseline cannot show whether it helped.

# Information

Evidence and reasoning:

- Dual verification (accept session cookie and JWT during a transition window) is a standard phased-migration pattern. [judgment]
- JWT is a stated standard for compact signed tokens: RFC 7519 [1]. Signing algorithms and claim validation follow that spec.
- JWT cannot be revoked server-side without extra state, unlike sessions. [judgment] Therefore, short token lifetimes plus refresh tokens are needed.
- No conversion baseline is given. Therefore, no target is stated here. Assumption A1 records the assumed metric.

Assumptions:

- A1. Conversion means the share of visitors who finish sign-up. Why not measured: the material does not state it. Validate by: user confirmation. If wrong: retarget Step 4, migration unchanged.
- A2. Auth code is in one repo with session middleware in one module. Why not measured: no repo access. Validate by: list middleware files. If wrong: the audit in Step 1 takes longer.
- A3. A user drop-off for one deploy is unacceptable. Why not measured: no policy stated. Validate by: user confirmation. If wrong: dual verification can be skipped.

Alternative considered: big-bang cutover to JWT on release day. It loses because one bad claim validation logs out all users [judgment], and rollback needs a new deploy rather than a flag.

# End

I recommend that we:

1. **Audit and classify** (Confused, evaluative). Catalog every session read/write and every client sending credentials. Test written first, a rubric: 100% of endpoints mapped, each with its consumer, pass threshold 100%, evidence is the endpoint list. Removes the blocker of unknown blast radius.
2. **Implement dual verification** (Complicated, deterministic). Write the test first. Given a valid session cookie or a valid JWT, when a request arrives, then auth succeeds with the same user record. Grows the capability to accept both during transition. Depends on Step 1 passing.
3. **Issuance and rollout** (Clear, deterministic). Write the test first. Given correct credentials at login, when the feature flag is on, then the response sets a 15 minute access token plus refresh token, and zero login failures occur at flag rates of 1%, 10%, 50%, 100%. Step 3 MUST NOT start until Step 2 passes. Removes the risk of mass logout.
4. **Conversion probe** (Complex, stochastic, run parallel with Steps 2 and 3, budget one week). Instrument the funnel first, then change one step: remove optional fields from the sign-up form. Acceptance test written first: metric is completion rate, sample size 400 sign-ups per arm, threshold is the treatment arm exceeding baseline with a test interval. This is a safe-to-fail probe, because no drop-off data exists and effect sizes are guesses. Step 4 MUST NOT start until a baseline week is recorded.

Sequencing: 1, then 2, then 3. Step 4 runs parallel after instrumentation.

# Follow-up

If A3 is false, replace the flag rollout in Step 3 with a direct cutover. If A1 is false, Step 4's metric changes while Steps 1 to 3 are unchanged.
