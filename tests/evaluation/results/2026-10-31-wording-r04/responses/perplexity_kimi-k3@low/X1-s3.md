## Headline

"Sometime wrong" without metrics cannot be fixed by tuning; the first move is to measure. Build a small scored dataset, then change one variable at a time. Three causes explain nearly all cases like this: wrong retrieval, overlong summaries, missing instructions; and the fix differs for each. Nothing in this plan needs new infrastructure beyond a review screen and a test set.

## Background

An LLM summariser (a large language model that condenses text) was added to a support tool, and agents report it is "sometimes wrong". No metrics exist, so no one can say how often it errs, what error types dominate, or whether a change helps. "Sometimes wrong" usually means hallucinated facts, dropped details, or format drift, and each has a different remedy.

## Relevance

Support agents trust summaries to act fast; a wrong summary can send a customer the wrong answer and erode agent trust in the tool, which then gets ignored. Without a baseline, every improvement attempt is a coin flip. A two-week measurement loop converts an anecdote into a number you can manage.

## Information

Evidence:

1. Hallucination (fabricated content) is a documented failure mode of LLM summarisation; reported rates vary widely by domain and model, so the local rate must be measured, not assumed [judgment].
2. Task-specific evaluation on a small labelled set (100 to 300 cases) is the standard first step before model or prompt changes [judgment].
3. Retrieval-grounded output, instructing the model to use only supplied ticket text, is the primary documented mitigation for fabrication [judgment].

Alternative considered: swapping to a newer model first. This loses because without a scored test set you cannot tell improvement from noise, and the failure may be in the prompt or input, not the model [judgment].

Assumption log:

`A1. Ticket text is available and can be replayed to the summariser. Why not measured: the material does not state it. Validate by: check one ticket in the tool. If wrong: add a logging step before Step 2.`

`A2. An agent or lead can spend about 4 hours per week reviewing outputs. Why not measured: the user has not said. Validate by: confirm staffing with the team lead. If wrong: cut the review sample to 50 cases per week.`

`A3. The failure is output quality, not latency or cost. Why not measured: the material does not state it. Validate by: ask three agents what "wrong" means. If wrong: redirect Step 2 metrics.`

Confidence: high that measurement must come first (three consistent lines of evidence). Medium on which error type dominates; that is what Step 2 answers, 60% likely to be fabrication or omission [judgment].

## End

I recommend that we run four steps, each one working session or less of build time, in this order:

1. Log inputs and outputs (Deterministic, Clear). Add logging of full ticket text plus summary for every run. Removes the blocker that today you cannot inspect a single failure. Test, written first: "Given a summarised ticket, when I open the log, then I see the ticket text and the summary side by side."

2. Score a sample (Evaluative, Complicated). Rubric first: correctness of facts (weight 50%), no omissions of user request or promised action (30%), correct format (20%); each scored against the logged source text; a summary passes at 90+ weighted points. Sample 100 summaries in week one. Output: error rate by type. This is the baseline and the classifying analysis for step 3.

3. Fix the dominant error type (Deterministic, Complicated). If fabrication dominates: constrain the prompt to source text only. If omission dominates: add explicit required fields. If format drifts: add a strict output template. Change one variable only. Step 3 depends on Step 2; it must not start before the rubric scores land. Test, written first: "Given 20 known failing cases, when the fix is applied, then at least 18 pass the rubric."

4. Add a weekly quality check (Stochastic, Clear). Metric: rubric pass rate; baseline from Step 2; threshold: within 5 points of baseline on a sample of 50 per week. Run as a stated ongoing gate, so regressions surface before agents do.

If A1 is false, insert a data capture step before Step 2. If agents report the problem is speed or tone rather than accuracy, replace the Step 2 rubric weights.

## Follow-up

Conditions that change the recommendation: if fewer than 100 summaries run per week, extend Step 2 to two weeks. If two error types are within 10% of each other, fix both in separate passes, one variable at a time.
