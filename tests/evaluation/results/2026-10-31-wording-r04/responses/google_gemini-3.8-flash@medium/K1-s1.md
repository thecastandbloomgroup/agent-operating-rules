### Headline

Revert the connection pool size reduction and restore the cache time-to-live setting immediately to eliminate database connection starvation.

- Database connection wait time accounts for 687 ms of the 780 ms latency increase [1].
- Lowering the cache time-to-live from 300 s to 60 s increased the cache miss rate from 12% to 31% [1], [2].
- Reducing the connection pool limit from 50 to 8 per pod caused connection exhaustion under peak traffic [1], [2], [3].

### Background

Last week, release 2026.10.21 updated the object-relational mapping code, the cache configuration, and the database pool settings [2]. Following deployment, the 95th percentile application programming interface latency increased from 120 ms to 900 ms [1]. The error rate increased twenty-fold, dominated by connection pool acquisition timeouts [1], [3].

### Relevance

The latency increase degrades user experience and breaches service latency targets. Furthermore, 0.40% of requests now fail with HTTP 503 errors during traffic peaks [1].

### Information

This section covers the evidence, assumptions, and alternatives.

The trace data shows that total request 95th percentile latency rose by 780 ms, from 120 ms to 900 ms [1]. In that same window, database pool acquire latency rose by 687 ms, from 3 ms to 690 ms [1]. Therefore, connection acquisition delay accounts for 88% of the total latency increase [judgment]. Database query execution times remained stable at 58 ms for orders and 26 ms for order lines [1]. Database server central processing unit utilization rose only from 38% to 41% [1].

In `config/cache.yaml`, the default time-to-live dropped from 300 s to 60 s [2]. Because cached items expired five times faster, the cache miss rate rose from 12% to 31% [1]. This increase generated 2.58 times more database requests [judgment].

In `config/db.yaml`, the maximum pool size per pod dropped from 50 to 8 [2]. Each of the 4 pods runs 8 worker threads [2]. When all 8 connections are busy, incoming worker threads must wait [3]. Consequently, logs recorded 1,800 to 2,400 pool exhaustion events per hour [3].

#### Assumption log

A1. The total database connection ceiling permits at least 64 concurrent connections across all pods. Why not measured: ticket OPS-412 details are absent from the provided files. Validate by: inspect ticket OPS-412 or run `SHOW max_connections` on the database. If wrong: tune pod count and per-pod pool sizes to stay within the database connection limit.

#### Alternative considered

Revert the `selectinload` code in `app/orm/orders.py`. This alternative loses because query durations did not rise, while connection wait times caused 88% of the latency spike [1].
