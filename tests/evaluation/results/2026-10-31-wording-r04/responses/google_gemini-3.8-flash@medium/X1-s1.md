### Headline

Establish an evaluation benchmark from agent-flagged tickets before you change prompt instructions or model settings.
First, collect a sample of fifty flagged summaries to classify error modes into factual errors or missing details.
Next, create a deterministic rubric to score summaries against ticket ground truth.
Finally, run prompt iterations against this benchmark to reach an agreed accuracy threshold.

### Background

Your team deployed a large language model summarizer into a customer support tool. Support agents report that the generated summaries are sometimes wrong [judgment]. The system lacks error tracking, reference datasets, and performance metrics [judgment].

### Relevance

You cannot fix summary accuracy until you measure current failure modes. Modifying prompts without metrics risks silent regressions that degrade agent trust further [judgment].

### Information

This section covers the error baseline, assumption log, and alternative options.

To measure summarization quality, teams track factual consistency and completeness [1]. Without metrics, perceived inaccuracy often stems from hallucinations or omitted customer intents [judgment]. A standard evaluation uses an annotated dataset of customer conversations paired with human-verified summaries [2].

#### Assumptions

A1. Your support platform stores conversation transcripts and agent feedback. Why not measured: The material does not state it. Validate by: Check platform database logs. If wrong: Build an export pipeline before creating the evaluation set.

A2. Hallucinations and omissions cause most agent complaints. Why not measured: The material does not state it. Validate by: Review the first twenty flagged tickets with two agents. If wrong: Re-align the scoring rubric to agent workflow preferences.

#### Alternative Considered

Prompt tuning via direct trial and error in production was considered. It loses because it lacks regression tests and wastes agent time during live customer interactions [judgment].

### End

I recommend that we:

1. Step 1: Create an evaluation rubric and sample dataset.
   - Domain: Complicated [3].
   - Kind: Evaluative.
   - Test: The rubric passes when two reviewers agree on eighty percent of ten test cases:
     - Criterion 1 (Weight 0.5): Factual consistency with transcript (no false claims).
     - Criterion 2 (Weight 0.3): Key issue identified (primary intent captured).
     - Criterion 3 (Weight 0.2): Resolution or pending action noted.
     - Threshold: Score of 0.85 out of 1.0.
   - Increment: Extract fifty recent support transcripts with agent complaints and score them against the rubric.
   - Capability: This removes the lack of baseline metrics and establishes your ground truth.

2. Step 2: Add an in-tool binary feedback widget for agents.
   - Domain: Clear [3].
   - Kind: Deterministic.
   - Test:
     - Given an agent views a generated summary,
     - When the agent clicks thumbs-down,
     - Then the system saves the transcript, summary, and timestamp to an audit table.
   - Increment: Deploy a two-button feedback component next to the summary pane.
   - Capability: This removes manual reporting overhead and continuously gathers failure cases. Step 2 MAY run in parallel with Step 1.

3. Step 3: Test structured prompt instructions as a safe-to-fail probe.
   - Domain: Complex [3].
   - Kind: Stochastic.
   - Test: Acceptance requires factual consistency above ninety percent on the fifty-ticket sample (baseline is current model score, sample size fifty runs).
   - Increment: Constrain the prompt to extract only stated facts and run it on the Step 1 dataset.
   - Capability: This tests whether constrained prompting eliminates hallucinations without requiring model fine-tuning. Step 3 MUST NOT start until Step 1 passes.

### Follow-up

If assumption A1 is false, replace Step 1 with a manual logging task across five senior agents for three days.
