# Relevance

# Information

Evidence shows that connection starvation drives the latency increase [2].
First, 95th percentile `db.pool.acquire` duration rose from 3 ms to 690 ms [2].
This span explains 88 percent of the 780 ms latency increase [2].
In contrast, total query execution time remained flat at 84 ms compared to 82 ms prior to release [2].

Second, lowering cache time-to-live (TTL) from 300 s to 60 s increased cache miss rates from 12% to 31% [1], [2].
Therefore, database request rate increased by a factor of 2.58 [2].

Third, pool size per pod dropped from 50 to 8 connections [1].
With 4 pods and 8 workers per pod, 32 worker threads compete for connections [1].
Database CPU utilization peaked at 41 percent during window B [2].
Therefore, the database server can handle more connections [judgment].
High confidence, trace and log metrics confirm connection queueing as the primary bottleneck [2], [3].
