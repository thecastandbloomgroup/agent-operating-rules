### Headline

Revert the cache time-to-live reduction and increase the database connection acquire timeout to restore API latency.
The connection pool queue causes 687 ms of the 780 ms latency increase [1].
Lowering cache duration from 300 seconds to 60 seconds increased database query volume by 158% [1], [2].

Database CPU utilization remains healthy at 41%, which shows that the database server is not overloaded [1].

### Background

API p95 latency rose from 120 ms to 900 ms after release 2026.10.21 deployed on 2026-10-21 [1], [2].
The release changed object-relational mapping queries, reduced cache expiration, and shrank database connection pools [2].
You requested an action plan to resolve this degradation based on attached logs, diffs, and traces.

### Relevance

The latency increase slows response times for customers by 650% [1].
Furthermore, pool timeouts now generate HTTP 503 errors on 0.38% of user requests [1].

### Information

Traces show that `db.pool.acquire` p95 rose from 3 ms to 690 ms [1].
Therefore, connection wait time accounts for 88% of the total latency rise [judgment].
Individual query times did not increase materially [1].
Specifically, orders query p95 changed from 52 ms to 58 ms, while order lines query p95 dropped from 30 ms to 26 ms [1].
Database server peak CPU only rose from 38% to 41% [1].
Consequently, query execution at the storage layer is not the root cause [inference].

The latency surge comes from connection starvation caused by two interacting configuration changes [2].
First, `config/cache.yaml` reduced `default_ttl_s` from 300 to 60 [2].
This change caused the cache miss rate to jump from 12% to 31% [1].
Because cache misses rose by a factor of 2.58, the service sent 158% more queries to the database [judgment].
Second, `config/db.yaml` decreased `max_size` from 50 to 8 per pod [2].
The API runs 4 pods with 8 worker threads each, totaling 32 workers [2].
When cache misses occur concurrently, all 8 connections per pod saturate [3].
Workers then queue for connections and frequently exceed the new 5-second acquire timeout [1], [2].
