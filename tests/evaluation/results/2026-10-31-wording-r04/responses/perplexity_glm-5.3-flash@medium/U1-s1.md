## Headline

Run a data-first triage: capture every failure signature, measure reruns, then quarantine. Supporting points:
1. Capture and count before you fix, because the fix follows from the category.
2. Reruns separate infrastructure flakes from test defects, per Google practice [2].
3. Quarantine keeps the main branch usable while fixes proceed.

## Background

The report is a single sentence: the build is flaky. Flaky means the build or its tests pass and fail with no input change. No build system, language, or error log was supplied.

## Relevance

A red or random build blocks every merge on the path that uses it [judgment]. Teams then retry instead of fixing, so wasted minutes grow each week.

## Information

**Evidence.** Failure themes that recur in reported cases [judgment]:
1. Shared state between tests (tests touch the same file, database, or global variable).
2. Timing or network races (a step waits on an external service with a fixed timeout).
3. Resource limits in CI runners (memory or parallelism near the cap).

These themes count as qualitative labels [3]. I have no source here that disagrees with them.

Google reports that reruns, test-first orders, and isolation keep flaky tests out of required gates [2]. Active reruns on every run: rerun-on-recommit catches most flakes within runs in practice [S].

**Assumption log.**
- `A1. The build runs in a CI system that the user controls. Why not measured: the material does not state it. Validate by: inspect the CI configuration with the user. If wrong: reruns run locally instead.`
- `A2. The flakiness is not a new code regression. Why not measured: no error log was supplied. Validate by: run the last known green commit. If wrong: revert first, then triage.`
- `A3. CI keeps logs for at least the last 10 builds. Why not measured: no system was named. Validate by: open a failed build older than one week. If wrong: collect new data for a week first.`

**Alternative considered.** Ask clarifying questions before any action. It loses because signature capture and reruns produce useful data on any stack; the answers would only change tooling, not the order.

## End

I recommend that we follow four steps. Step 3 MUST NOT start until the sample in Step 2 reaches 10 reruns.

1. **Capture.** Add a failure log step to the CI pipeline. Blocker it removes: no trustworthy data. Test (deterministic): 
   ```gherkin
   Given a pipeline with one failing job
   When the job finishes
   Then the log contains the job ID, the commit hash, and the first error line
   ```
   Cynefin: Confused, because Step 1 gathers the data that classifies the failure domain.
2. **Rerun.** Rerun each failed job 10 times on a separate branch. Blocker it removes: one no sample size. Test (stochastic): metric is rerun failure rate; baseline is 1 of 10 skips fixed; sample size is 10 reruns per failed job; pass threshold for "flaky, not broken" is a failure rate below 100%. Budget: 2 hours of compute. Stop condition: 0 of 10 reruns fail, because then the cause is in the environment of the first run. Cynefin: Complex probe, so do not commit the full fix yet.
3. **Quarantine.** Label each test that fails in at least 1 of 10 reruns, and remove it from the required merge gate. Blocker it removes: blocked merges. Test (deterministic):
   ```gherkin
   Given a test labeled flaky with 1 failure in 10 reruns
   When a pull request runs
   Then the gate result does not include that test
   ```
   Cynefin: Clear, one rule applies.
4. **Fix by category.** Count the labels per theme above, then fix the largest group first, starting with the shared-state group. Blocker it removes: the highest-frequency failure cause. Test (deterministic, test first): write the isolated test, then make it pass, then refactor. Cynefin: Complicated, because analysis picks the practice; trust the ordering only after Step 2's counts exist.

## Follow-up

Open questions (each states its use):
1. Which CI system and which test stack? The answer sets the exact Step 1 configuration.
2. Which error messages have the last three failed builds shown? The answer can skip Step 2 for a known cause.
3. Is CI compute capped, so 10 reruns per job fit the budget? A smaller sample changes the Step 2 threshold.

Condition that changes the recommendation: if A2 is false and the failure is a regression, revert before Step 2.
