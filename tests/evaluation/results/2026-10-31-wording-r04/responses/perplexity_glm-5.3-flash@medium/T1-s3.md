## Headline

Automate SQL formatting with one tool and one config file, so no human arbitrates style anymore.
- The friction comes from style being decided by people in review; a committed formatter config makes the file the only source of style truth.
- A CI check that rejects unformatted SQL removes style comments from reviews before they are written.
- Style disagreements then become config changes, which are diffable and testable instead of opinion fights.

## Background

The team disagrees on SQL format, and each pull request review reopens the argument. The request is to fix this friction, described as a culture problem.

## Relevance

Every review day without a rule repeats the argument and slows merges. A fix this week ends recurring friction at low cost.

## Information

**Evidence.** SQLFluff is an open-source SQL linter and formatter that applies a committed project config, with a dialect setting and a `fix` command [1]. This is a tool-enforced standard, so output is deterministic: the same input and config give the same file. The Cynefin framework places settled best practices in the Clear domain, where one step, applied directly, works [2]. **Assumption log.**
A1. The team uses a shared repository with CI. Why not measured: the material does not state it. Validate by: check the repo for a CI config. If wrong: use a pre-commit hook instead of CI, same test shape.
A2. The team writes one main SQL dialect. Why not measured: the material does not state it. Validate by: list the engines the team queries. If wrong: set the SQLFluff dialect per directory [1].
A3. The friction is about format, not only labeled as format. Why not measured: past review threads were not sampled. Validate by: read 10 closed review threads. If wrong: the Step 4 probe will surface the real cause.

**Alternative considered.** A written style guide enforced by reviewers loses: it keeps humans as the enforcement point, so each review depends on memory and goodwill [judgment].

## End

I recommend that we remove style from human review by machine-enforcing one format:

1. Add SQLFluff with a committed config file set to the majority's current style. Increment: one working session to commit `.sqlfluff` and one automated `fix` pass. Blocker removed: the absence of a single style authority. Test (deterministic, write first): Given a repository with `.sqlfluff` committed, When a contributor runs `sqlfluff lint sql/`, Then the exit code is 0 on the tree as committed. Cynefin: Clear.
2. Add a CI job that runs the linter and fails the build on any unformatted file. This step MUST NOT start until the test in Step 1 passes. Increment: one session. Blocker removed: reliance on reviewers to catch style. Test (deterministic): Given an open pull request with one re-spaced query, When CI runs `sqlfluff lint`, Then the build fails and lists the file. Cynefin: Clear.
3. Adopt one review rule: reviewers comment on logic, schema, and correctness, and close any style comment with a pointer to a config change. Increment: one session to agree the rule in one paragraph. Blocker removed: ambiguity about what style debate is in scope. Test (evaluative, rubric first): score 10 new review threads against a two-criterion rubric (style comments present or absent, weight 0.8; rule stated, weight 0.2), pass threshold 8 of 10. Cynefin: Complicated.
4. Run a two-week probe comparing friction before and after. Increment: count review cycles per pull request and style comments for two weeks, capped at 15 pull requests. Blocker removed: no measure exists to confirm the fix works. Test (stochastic): metric is style comments per pull request, baseline is the prior 30 days, pass threshold is a reduction to under one per five pull requests, sample is 15 pull requests. Stop if the count does not fall; treat that as evidence that the conflict is about more than format and reopen the analysis. Cynefin: Complex, leverage estimate appears only after measurement.
