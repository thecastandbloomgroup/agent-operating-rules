Headline
The build flakiness needs a data-first triage: measure which tests fail on retry, quarantine those tests, then fix the worst ones.

1. Real builds fail once and stay red. Flaky builds fail, pass on retry, and stay red again later.
2. Triage starts with numbers, not with guesses about causes.
3. Quarantine keeps the gate green while the fixes land, in order of flake rate.
4. This plan assumes the cause sits in tests, not in infrastructure. A1 covers this.

Background
The build fails in a pattern that the team calls flaky. The message gives no CI system, no error logs, and no failure rate, so the steps below aim to produce those numbers first.

Relevance
A red-then-green gate hides real defects and trains developers to re-run until green. That habit costs more than any single test fix [judgment].

Information
Evidence
- On the same commit, runs stack in three groups: pass, fail-then-pass on retry, and fail-stay-red. Only the second group marks flakiness [judgment].
- The mainstream practice is to quarantine flaky tests: run them, report them, and block the gate only on the rest [7].
- Over the last 30 runs, the second group gives a direct flake rate per test [judgment].
- Infrastructure noise (network, agent load) and test bugs (races, order dependence, shared data) look alike in logs. Only the retry split above separates them [judgment].

Assumptions
- A1. The flakiness comes from tests, not from failed infrastructure agents. Why not measured: the material does not state it. Validate by: diff the fail-then-pass group from the fail-stay-red group over the last 30 runs. If wrong: replace Steps 3 and 4 with an infrastructure audit that compares agent types, load graphs, and vendors against failure time stamps.
- A2. The build runs more than one test. Why not measured: the material does not state it. Validate by: count test cases in one CI report. If wrong: the plan shrinks to one step, Step 4, applied to the single failing stage.

Alternative considered
Fix the suspicious test first, before any measurement. It loses because, with no flake rate, "suspicious" rests on memory, and a fix without a baseline cannot show that it worked [judgment].

End
I recommend that we run four steps, in this order. Steps 3 and 4 MUST NOT start until the report in Step 1 shows counts for the last 30 runs.

1. Step 1 (Clear, deterministic): turn on retry counting in the CI report. It adds the capability to measure flake rate per test. Test, written before the work: Given a job that fails once and passes on retry, When the run finishes, then the report shows the test name, the commit id, and the retry count.
2. Step 2 (Clear, deterministic): quarantine every test with a fail-then-pass result on the same commit in the last 30 runs. It removes the blocker of red builds on healthy code. Test: Given a test with a same-commit retry in the report, When the CI config builds the gate set, then the test still runs and does not block the merge.
3. Step 3 (Complicated, deterministic): write one root-cause card for the three highest-rate quarantined tests. Card fields: category (race, order dependence, shared data, environment), one log line as evidence, one hypothesis. The analysis is a log comparison across the quarantined tests. Test: Given a root-cause card, When a reviewer reads it, then it names one category and cites one log line.
4. Step 4 (Complicated, deterministic): fix the highest-rate test, test first. It removes the top flake source. Test: Given the fix, When 30 fresh runs execute on the fix branch, then the flake count is 0.
