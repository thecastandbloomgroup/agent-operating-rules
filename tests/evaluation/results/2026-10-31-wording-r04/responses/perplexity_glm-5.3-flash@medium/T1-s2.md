## Headline

Stop treating this as a culture problem: remove the format decision from people and give it to a formatter that runs in CI.

1. The friction exists because format is a preference with no owner, so every reviewer re-litigates it.
2. A tool choice, one CI check, one machine reformat, and one two-week probe end the argument.
3. Adoptions fail in the probe, so run the change as a capped, measured pilot per [18].

## Background

The team disagrees on SQL format. Reviews carry style arguments, so the team blames culture. The request is to fix the friction, not to pick a style first.

## Relevance

Every review today pays a tax in time and in reviewer trust. The fix is cheap and it also sets a pattern for other unowned preferences.

## Information

**Evidence**

Formatting debates are a symptom of an unowned decision, not of a values conflict. [inference]

The strongest evidence for probe-shaped work comes from Cynefin [18], which states two things. First, in Complex domains cause and effect appear only after the fact, so work must start with safe-to-fail probes that carry a measure, a stop condition, and a budget [18]. Whether this team adopts a shared standard is such a domain. Second, in Clear and Confused domains different moves apply, so the first step is to classify or remove uncertainty [18].

**Assumption log**

A1. The repository has CI that runs on each pull request. Why not measured: the material does not state it. Validate by: look for a CI config file. If wrong: run the check in a pre-commit hook instead, which removes the same blocker.

A2. The team uses one SQL dialect. Why not measured: the material does not state it. Validate by: ask the query-writers or scan the repo for dialect-specific syntax. If wrong: give each project its own formatter profile from one shared tool.

A3. The team can free one 30-minute session for the tool decision. Why not measured: meeting norms are unknown. Validate by: propose the session in a team channel. If wrong: run the decision as an async vote on two finalists.

**Alternative considered**

A hand-written style guide applied by human reviewers. It loses because every review stays the enforcement point, so the argument returns with each reviewer. [inference]

## End

I recommend that we remove format from human review and put it under a tool.

1. **Pick the formatter and its rules, in one 30-minute session.** The increment is one config file in the repo. The capability it adds is an owned standard. It is evaluative, domain Complicated. Write the rubric first: score each candidate tool on dialect support (weight 0.4), quality of its default rules (0.2), fit with repo tooling (0.2), update stability (0.2), with pass evidence of each tool formatting ten past SQL files. Highest weighted score wins.
2. **Add the formatter as a CI check.** The increment is one config plus one CI step, sized for one session. The blocker it removes is human enforcement, the root cause. It is deterministic, domain Complicated. Test, written first, in Gherkin form: Given a pull request with an unformatted query, When the lint job runs, Then the job fails and prints only the format diff.
3. **Reformat the whole repository in one machine commit, in one session.** Step 3 MUST NOT start until the test in Step 2 passes. The two steps together have the highest leverage: after them, style comments have nowhere to appear. It is deterministic, domain Clear. Test: Given the full repo, When the formatter runs once, Then a spot check of ten files shows zero manual edits after the commit.
4. **Run a two-week probe on adoption, capped at two weeks.** The increment is a metric review at day 7 and day 14. The blocker it addresses is unknown team acceptance. It is stochastic, domain Complex, per [18]. Acceptance test, written first: metric = style-only comments per review; baseline = the count in the 20 merged pull requests before launch; threshold = half the baseline or fewer; sample size = 20 pull requests after launch. Stop condition: stop the probe if review time grows instead of shrinking. Run Step 4 in parallel with Step 3. Leverage here is a guess [18].

If the probe fails the threshold at the sample size, drop the CI failure mode and keep only the pre-commit hook. Then re-run one more capped probe.

## Follow-up

**Conditions that change the recommendation**

- If A1 is false, replace Step 2 with the pre-commit hook form of the same check.
- If the team ships SQL through a templating layer such as Jinja, the tool must support that layer before Step 2 passes, so Step 1 gains one criterion.
