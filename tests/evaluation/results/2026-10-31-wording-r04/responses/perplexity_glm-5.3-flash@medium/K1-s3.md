## Headline

The connection pool change in release 2026.10.21 caused the latency rise. Revert that config today, then size the pool from the OPS-412 limit and restore the cache TTL.

- Pool acquire, the step where a worker takes a database connection, accounts for 690 ms of the 900 ms request p95.
- The release cut the pool from 50 connections to 8, while 32 worker threads still need connections.
- The cache TTL cut from 300 s to 60 s raised the miss rate from 12% to 31% and added database load.
- The ORM change is not the cause: query p95 stayed flat, and order_lines p95 fell.

## Background

API p95 latency rose from 120 ms to 900 ms after release 2026.10.21, deployed 2026-10-21 at 14:05 UTC. The release touched three parts: the ORM query, the cache TTL, and the database pool settings. Logs, traces, and the diff are attached.

## Relevance

Error rate rose from 0.02% to 0.40%, so customers now see 503 responses on this endpoint. The fix is a config change, so the cost of action today is small.

[1]
8. 96% of the new errors are PoolTimeout, the error raised when a worker waits 5 s and gets no connection.

### Assumption log

A1. Ticket OPS-412 allows more than 24 connections for this service. Why not measured: the ticket is not in the material. Validate by: read OPS-412 before Step 2. If wrong: keep the low pool cap and put PgBouncer, a shared connection pooler, between the API and the database.

A2. The TTL cut to 60 s did not fix a data staleness bug. Why not measured: the diff has no commit message for cache.yaml. Validate by: ask the release author or read git history. If wrong: keep default_ttl_s at 60 s and skip Step 3.

### Alternative considered

The strongest alternative is that the ORM selectinload caused the rise. It loses because per-query p95 stayed flat or fell, and the rise sits in the acquire span, not the query spans.
