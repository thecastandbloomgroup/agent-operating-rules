## Headline

Measure the error rate on a labeled sample first, then fix the top error class with a tested change. The plan has three lines of work: label 50 recent summaries to get a baseline, automate scoring so the number updates weekly, and run one bounded prompt fix against that baseline.

## Background

The tool produces LLM summaries for support agents. Agents report that the summaries are wrong some of the time. No metric exists, so the team cannot see the rate or the type of the errors.

## Relevance

Without a baseline, every prompt change is a guess [inference]. One measured session turns agent opinion into a number, and the number gates each later change.

## Information

**Evidence**

- "Sometimes" does not bound the problem; the rate is unknown, so treat it as material until the sample says otherwise [inference]. Thematic analysis handles this: group the agent complaints into themes, count the sources that support each theme, and keep a source that disagrees [1], [2].
- A judge model can automate the rating. Judge models agree with human raters on evaluation tasks at a rate comparable to human-human agreement, above 80 percent in published tests [3]. High confidence for the direction, moderate for the exact figure, because agreement varies by task type and rubric [3].

**Assumption log**

A1. The complaints point mostly at factual errors or missing details. Why not measured: the request states no error type. Validate by: read 20 flagged summaries with two agents. If wrong: the rubric criteria change, and Steps 2 to 4 shift to the new criteria.
A2. Agent labels are reliable ground truth. Why not measured: no labeled set exists yet. Validate by: have two agents label the same 10 summaries; require agreement on 8 of 10. If wrong: use three labels per summary and majority vote.
A3. The last 30 days contain at least 50 summaries. Why not measured: the request gives no volume. Validate by: count entries in the tool log. If wrong: extend the window to 90 days.

**Alternative considered**

Change the prompt now without a baseline. It loses because no test can show whether the error rate moved, so the team cannot stop or scale the change [judgment].

## End

I recommend that we run five steps, in this order.

1. **Label a 50-summary sample** (Confused domain, evaluative). Increment: label 50 summaries from the last 30 days in one working session. Blocker it removes: unknown error classes and no baseline. Test written first: the rubric states the criteria (factual consistency, completeness, readability), the weights (50, 30, 20), the pass rule (zero factual errors), and the evidence each criterion needs. This step MUST finish first, because later steps depend on its labels.
2. **Publish a weekly error report** (Clear domain, deterministic). Increment: one report that shows the factual error rate, the omission rate, and the count. Blocker it removes: no shared number. Test written first, in Gherkin form [4]: Given 50 labeled summaries with 4 factual errors, When the report runs, Then it shows "8 percent (4 of 50)".
3. **Score every summary with a judge model** (Complicated domain, stochastic). Increment: connect an LLM judge to the pipeline, calibrated on the Step 1 labels. Blocker it removes: manual rating stops at 50. Acceptance test written first: metric = agreement of the judge with agent labels on the factual error flag; baseline = none; threshold = at least 80 percent agreement; sample = the same 50 summaries [3]. Run the trials; accept the judge only when it meets the threshold at that sample size. This step MUST NOT start until Step 1 finishes.
4. **Fix the top error class with a probe** (Complex domain, stochastic). Increment: change one thing, such as add grounding instructions or cap summary length. Blocker it removes: the leading error theme from Step 1. Acceptance test written first: metric = factual error rate on the same 50 summaries; baseline = the Step 1 rate; pass threshold = divide the baseline rate by 2; sample = the same 50; budget = one working session. Cause and effect are visible only after the run, so leverage is a guess; the probe must not exceed its budget. Step 4 MUST NOT start until Step 2 produces the baseline, because the probe needs it.
5. **Collect agent feedback in the tool** (Clear domain, deterministic). Increment: add a one-click "summary wrong" flag that stores the summary, the ticket ID, and the date. Blocker it removes: silent regressions after prompt, model, or product changes. Test written first, in Gherkin form: Given an agent views a summary, When the agent clicks "summary wrong", Then the system stores the summary text, ticket ID, and date. Review top themes weekly, and count supporting reports per theme [1], [2].

## Follow-up

Conditions that change the recommendation:
- If A1 is false, rebuild the rubric around the real error type, then rerun Steps 1 and 2.
- If A2 is false, use three labels per summary and majority vote, which doubles the labeling cost.
- If the judge in Step 3 stays below 80 percent agreement, keep manual weekly sampling instead, because an unchecked judge adds noise.

Open questions:
- What summary volume does the tool produce per week? The answer sets the sample window in A3, but the count check resolves it at no cost.
