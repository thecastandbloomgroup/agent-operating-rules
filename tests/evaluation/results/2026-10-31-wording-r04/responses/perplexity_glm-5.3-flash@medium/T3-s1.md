# Headline

Migrate in stages: issue JWT next to the existing sessions, move clients over, then retire sessions. Treat sign-up conversion as a measurement problem first, because no baseline exists today.

Supporting points:

1. A staged migration keeps session revocation while you test the token path.
2. Conversion work starts with funnel data, so the first change is instrumentation, not redesign.
3. Every step is small, testable, and reverses without a hard cutoff.

# Background

The request has two goals: move the auth service from sessions to JWT, and raise sign-up conversion. The message does not state the current session design, the client inventory, or any funnel metrics. JWT stands for JSON Web Token, a signed token format that a service can verify without a session store [1].

# Relevance

Both goals affect every user and every login. A failed cutover blocks all sign-ins, and a weak sign-up funnel loses users now.

# Information

**Evidence.**

The recommendation rests on these facts:

- JSON Web Token (JWT) is a signed token format with registered claims such as expiry [1].
- A stolen access token cannot be revoked, so short token lifetimes and a revocation path for refresh tokens are part of the standard threat model [2].
- Session state travels today in cookies [3].
- The current stack, traffic level, and funnel data are absent from the material [no source].

The two goals are independent. The migration is engineering risk. The conversion work is an unknown funnel, so it sits in the Confused domain until Step 1 produces data.

- A2. The main sign-up drop-off is form friction, for example too many fields. Why not measured: no funnel data is provided, and measuring costs more than reacting later. Validate by: the funnel events in Step 1. If wrong: Step 4 tests a different change, for example social login.
