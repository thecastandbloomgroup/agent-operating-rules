## Headline

Make the summariser better by measuring its errors first, then grounding its output in the ticket and adding a feedback loop. The plan: (1) label a sample of summaries to find the real error types, (2) fix with one measured change at a time, (3) add a regression test set so quality cannot drop silently.

## Background

The team added an LLM-based summariser to a support tool. Agents report that it is "sometimes wrong". The team has no metrics, so the claim cannot be tested or the fix measured.

## Relevance

Without a measurement, every prompt change is a guess and any improvement can silently reverse. One working session of labeling starts the measurement.

## Information

**Questions a careful reviewer would ask.** What does "wrong" mean here: missing facts, added facts, wrong emphasis, or tone? How often, and on which ticket types? What data does the summariser see? The message answers none of these, so the first action must gather them.

**Error types are known in this area.** Published failure lists for summarisation systems group errors into omission, fabrication, and misweighted importance [inference from reviewed literature, no session source for this tool]. I group agent complaints the same way until the labeling shows otherwise, because the groups do not overlap and cover the whole.

**Evidence plan.** Sample summaries with agent labels gives both a number (error rate with units: errors per summary) and themes with source counts (how many labels support each error theme). When the count and the themes agree, confidence rises.

Assumption log:

- A1. Ticket transcripts are stored and reachable for sampling. Why not measured: the message does not state the ticket system. Validate by: open 10 tickets and check transcript access. If wrong: sample labels from screenshots agents paste instead.
- A2. Weekly volume is at least 100 summaries. Why not measured: no volume data given. Validate by: read the summariser log count for one week. If wrong: extend the sample window to 2 to 4 weeks.
- A3. "Wrong" refers to summary content, not style. Why not measured: the message quotes only "sometimes wrong". Validate by: the labeling rubric includes a style category, so the data resolves this. If wrong: the same sample covers it.

**Alternative considered.** Replace the model or fine-tune it now. This loses because, with no metric and no labeled sample, the team cannot tell whether the change helped, and the cost of a wrong swap is high [judgment].

## End

I recommend that we take these five actions in this order:

1. **Label a sample.** Take 50 summaries, and have 2 agents tag each with one of four error types: omission, fabrication, emphasis, style. This removes the blocker: "sometimes wrong" has no definition. Test (evaluative, rubric first): criteria are error type, weight equal, pass threshold is 80% agreement between the 2 agents, evidence is the tag on each of the 50 items. Domain: Confused. This step runs first because its output decides the rest.

2. **Define the metric and baseline.** Write the acceptance test before changes: metric is factual error rate (fabrication plus omission errors per summary), baseline is the rate from Step 1, pass threshold is a reduction to half the baseline, sample size is 50 summaries. This adds the capability to prove any change helped. Domain: Complicated; the analysis in Steps 1 and 2 picks the practice. Confidence in the baseline: high, because it comes from direct labels [judgment on stability over time].

3. **Ground the summaries.** Run a probe: pass the full ticket transcript with numbered lines, require each summary claim to cite a line number, and show the citations to agents. Cap the probe at 1 week and 50 summaries, stop early if the factual error rate does not drop. This removes the fabrication blocker. Test (stochastic): metric, baseline, threshold, and sample size come from Step 2. Increment stays inside the cap. Domain: Complex; leverage is a guess, so do not commit beyond the cap. Run Steps 3 and 4 in parallel.

4. **Add agent feedback capture.** Put a "wrong" button on each summary that records the error type from the Step 1 rubric. This removes the blocker of permanent silence after rollout. Test (deterministic), written first:

```gherkin
Given a generated summary with a "wrong" button
When the agent clicks the button and picks "fabrication"
Then the log stores summary ID, error type "fabrication", and timestamp
```

Domain: Clear; one known step.

5. **Gate all future changes.** Fix a regression set of 30 summaries with agent labels, and require every prompt or model change to pass the Step 2 threshold on that set before release. This blocks silent quality drops. Test (stochastic): same metric and threshold, sample size 30. Domain: Clear; a best practice applied.

Step 5 MUST NOT start until the Step 1 rubric reaches the 80% agreement threshold. If Step 1 shows that fabrication is not the main error type, drop Step 3 to last and reorder Steps 3 to 5 by the counted share of the dominant error type.

Confidence overall: medium, basis: no session data about the tool, plan rests on standard practice [judgment].

## Follow-up

Conditions that change the recommendation: if volume is under 25 summaries per week (A2 false), merge Steps 3 and 5 into one probe window. If transcripts do not exist in retrievable form (A1 false), grounding in Step 3 is not possible, and the plan shifts to feedback capture plus human review of flag-capable ticket types.
