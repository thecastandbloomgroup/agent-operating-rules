## Headline

Make the summariser measurable, identify its main failure, and test one targeted fix before wider use.

- First, turn agent complaints into a small, traceable test set.
- Next, protect agents from unchecked summaries while measuring the current version.
- Then, accept changes only when a paired test shows fewer errors without losing useful information.

## Background

Your support tool now includes an LLM-based summariser, which generates summaries from support records. Agents report that it is “sometimes wrong,” but you have no metrics. [1]

## Relevance

The first task is to separate harmful factual errors from preferences about wording. Otherwise, a rewrite can sound better without becoming more accurate. [judgment]

## Information

### What counts as better

Use the support record available **when the summary was generated** as the reference. Later messages must not count against an earlier summary. [judgment]

Classify each factual defect once, using this order:

1. **Contradiction:** the summary conflicts with the record.
2. **Unsupported claim:** the record neither supports nor contradicts the claim.
3. **Material omission:** the summary misses information needed for the agent’s next action.

Record style complaints separately. For example, excessive length is not a factual error. [judgment]

Mark a defect **severe** when it changes the apparent resolution, promised action, payment, security status, or required escalation. These are proposed priorities, not measured findings. [judgment]

### Scorecard

| Measure | Definition | Comparison |
|---|---|---|
| Factual failure rate | Summaries with at least one factual defect / summaries reviewed | Current version versus candidate |
| Severe failure count | Summaries with at least one severe defect | Current version versus candidate |
| Required-fact coverage | Required facts included / required facts identified before review | Candidate must not decline |
| Review time | Seconds needed to verify and correct each summary | Candidate must not increase |

Keep random cases separate from complaint cases. Complaint cases test known problems; they do not estimate the overall failure rate. [judgment]

### Assumption log

A1. Agents review summaries before external use. Why not measured: The material does not state it. Validate by: Trace one workflow. If wrong: Stop unchecked external use first.

A2. Support records and generated summaries remain available. Why not measured: The material does not state it. Validate by: Retrieve one matched pair. If wrong: Capture future pairs before evaluation.

A3. An owner can change the summary template or prompt. Why not measured: The material does not state it. Validate by: Inspect the configuration. If wrong: Test through a separate prototype.

### Alternative considered

**Rewrite the prompt immediately:** this is faster, but there is no evidence that the prompt causes the complaints.  
It loses because it provides no baseline and no reliable way to detect regression. [judgment]

**Confidence:** high confidence that measurement must precede acceptance; the reported complaints contain no measured failure pattern. [1]

### 3. Score the current version and choose one fix

**Kind:** Evaluative. **Domain:** Complicated.

**Rubric first:** Use this weighted decision matrix to choose the first failure category to address.

| Criterion | Weight | Evidence required |
|---|---:|---|
| Harm | 50% | Consequence of an agent accepting the defect |
| Frequency | 30% | Defect count within the random sample |
| Correctability | 20% | A reproducible cause and a bounded proposed change |

Score each criterion from 0 to 4. Select the highest weighted category scoring at least 2.5 out of 4. These weights and threshold are proposed defaults. [judgment]

**Increment:** Two reviewers independently score the test set in one session each, then resolve disagreements.

Before reading summaries, reviewers identify required facts from each source record. Then record the four scorecard measures.

**Blocker removed:** The first change targets observed harm, not a guess.

Match the fix to the evidence:

- Missing source text: correct source selection or truncation.
- Claims that exceed the source: require supported facts and explicit uncertainty.
- Missing required facts: use a fixed summary template.
- Correct content but poor usability: change length or structure.

These are candidate responses, not findings about your system. [judgment]

Step 3 MUST NOT start until Step 1 passes. If no category meets the threshold, expand observation instead of changing the model.

### 4. Run one capped comparison

**Kind:** Stochastic. **Domain:** Complex, using a small experiment with limited downside.

**Acceptance test first:**

- **Sample:** The same 30 random cases and up to 10 complaint cases.
- **Trials:** Two fresh outputs per case, per version.
- **Baseline:** The current version under the same inputs.
- **Pass threshold:** At least 50% fewer factual failures in the random sample, with no severe failures.
- **Additional limits:** No lower required-fact coverage and no higher median review time.
- **Complaint cases:** No new severe defect; every targeted defect must disappear in both trials.

These are proposed acceptance thresholds, not established service targets. [judgment]

**Increment:** Change one component and run the comparison offline. Hide version names from reviewers.

**Budget:** One implementation session and one review session per reviewer. Stop when the budget expires or a severe candidate defect appears.

**Capability added:** A measured decision to retain or reject the candidate.

Step 4 MUST NOT start until Step 3 identifies a target. Do not accept the candidate until the full sample passes.

If the baseline has no factual failures, expand the sample rather than claim a reduction. Passing this small test supports a limited rollout, not proof of reliability. [judgment]
