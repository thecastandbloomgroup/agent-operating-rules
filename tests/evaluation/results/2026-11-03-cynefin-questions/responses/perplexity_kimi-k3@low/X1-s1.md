## Headline
Build a measurement baseline first, then improve the summariser with targeted fixes.  
- “Sometimes wrong” is not actionable until errors are typed, counted, and tied to cases [1].  
- The fastest safe path is a small evaluated sample, then one change at a time [judgment].  
- Do not tune prompts or models before a baseline exists, because cause and effect will stay unclear [inference].

## Background
The support tool added an LLM summariser, and agents report occasional errors [1]. No metrics exist, so the team cannot tell frequency, severity, or cause.

## Relevance
Bad summaries can waste agent time and can send wrong answers to customers [judgment]. A baseline turns complaints into decisions about prompt, retrieval, model, or workflow changes.

## Information

Evidence:
- Current state reports “sometimes wrong” and “no metrics,” per the request [1].  
- Error work needs counts by type before optimisation; this is standard evaluation practice [judgment].  
- For LLM output, run-to-run variation is expected, so acceptance needs a threshold and sample size [judgment].

Assumption log:
`A1. Agents can label 200 recent summaries in one week. Why not measured: the material does not state staffing. Validate by: ask for label completion after 3 days. If wrong: cut sample to 100 and extend time.`  
`A2. Each summary links to the source ticket. Why not measured: the material does not state data access. Validate by: open 20 records and check links. If wrong: first fix logging.`  
`A3. Wrong means factual error, missing key fact, wrong action, or unsafe tone. Why not measured: the material gives no rubric. Validate by: label 50 examples and count agreement. If wrong: rewrite the rubric before scoring.`

Alternative considered:
Switch models immediately. It loses because without labels the team cannot prove improvement, and a new model can change cost and failure modes at once [judgment].

## End
I recommend that we run a four-step baseline and fix loop:

1. Create a one-page error rubric with four classes: factual error, missing key fact, wrong next action, unsafe tone.  
   Increment: one rubric and 20 example labels.  
   Blocker: “wrong” has no shared definition.  
   Kind, evaluative. Rubric first: criteria are the four classes, equal weights, pass threshold is 90% label accuracy on sampled tickets, evidence is summary text plus ticket ground truth.  
   Cynefin domain: Clear. Cause and effect are known once the rubric is defined by deduction from policy.

2. Label 200 recent summaries with the rubric.  
   Increment: 200 labelled rows in one spreadsheet.  
   Blocker: no baseline rate or severity ranking.  
   Kind, evaluative. Rubric from Step 1 applies; pass threshold is inter-rater agreement of at least 80% on a 30-item double-checked subset.  
   Cynefin domain: Complicated. An expert can classify the data through analysis; the pattern could break if tickets mix languages or channels.

3. Fix the top failure class only, using the smallest change that matches its cause: retrieval for missing source facts, prompt constraints for wrong action, safety rules for tone.  
   Increment: one change behind a flag for 10% of traffic.  
   Blocker: highest-volume failure keeps reaching agents.  
   Kind, stochastic. Acceptance test first: metric is top-class error rate, baseline comes from Step 2, pass threshold is 30% relative reduction, sample size is 100 treated summaries.  
   Cynefin domain: Complex. LLM output shows its effect after trials, so this is a capped probe with a stop condition of no reduction after 100 trials.

4. Add a weekly scorecard with error rate by class, agent edit rate, escalation rate, and cost per summary.  
   Increment: one dashboard from existing logs.  
   Blocker: regressions return silently after the fix.  
   Kind, deterministic.  
   Given the dashboard reads labelled and production logs, when the weekly job runs, then it shows the four metrics and flags any class that rises more than 20% week over week.  
   Cynefin domain: Clear. The rule is known and repeatable.

Step 3 MUST NOT start until Step 2 passes. If A2 is false, replace Step 1 with repair of summary-to-ticket logging.
