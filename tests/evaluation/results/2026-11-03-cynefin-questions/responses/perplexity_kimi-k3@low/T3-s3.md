## Information

Evidence and artifacts follow.

JWT has two known properties relevant here. Tokens are self-contained and signed, so servers avoid a session store lookup [1]. Tokens cannot be revoked cheaply, because the server trusts the signature until expiry [2].

For comparison: session cookies allow instant revocation through server state. JWTs trade that for stateless scale [judgment].

**Assumption log**

A1. Stack is a standard web app with server-side session storage today. Why not measured: the material does not state it. Validate by: inspect the auth middleware, one file read. If wrong: Step 1 design changes, Steps 3 to 5 stand.

A2. Sign-up conversion lacks a baseline metric today. Why not measured: no analytics data provided. Validate by: query the analytics tool for the last 90 days of funnel events. If wrong: skip Step 5 (already done) and move straight to conversion experiments.

A3. Users tolerate re-login once at cutover. Why not measured: measuring costs more than the decision is worth. Validate by: announce re-login in release notes; watch support tickets for 7 days. If wrong: extend dual-auth window in Step 3.

**Alternative considered**

Keep sessions and add a cache layer instead of migrating: this avoids revocation problems and is cheaper [judgment]. It loses when the service must scale across regions without shared session state, plus mobile clients that prefer bearer tokens. If scale is not the driver, that alternative wins and this plan should stop.

Confidence: high on the JWT properties above, per two primary sources. Low on whether migration is worth doing at all, per A1 and the unknown scale constraint.

## End

I recommend that we take these actions, in order.

1. **Write the JWT design doc before any code change.**
   - Increment: one page covering signing key, expiry, refresh token design, and revocation strategy (short access token plus refresh token [2]).
   - Blocker: removes the risk of shipping a design that cannot be revoked.
   - Kind: evaluative. Rubric first: criteria are revocation ability (weight 40%), mobile support (30%), rollout safety (30%); pass threshold 75%; evidence is the cited spec properties [1], [2]. Kepner-Tregoe matrix against "keep sessions with cache".
   - Domain: Complicated. An expert can pick the design from the spec, so deduction from known rules applies.

2. **Add JWT issuance and verification behind a feature flag, with sessions still active.**
   - Increment: one commit adding token issue at login and a middleware that accepts either auth type.
   - Blocker: enables rollout without a big-bang cutover.
   - Kind: deterministic. Test first in Gherkin:
     - Given a valid login, when the user authenticates, then the service returns a signed JWT and accepts it on protected routes.
   - Domain: Clear. Standards secure the design, so one practice applies [1].

3. **Roll out dual auth, then remove sessions.**
   - Increment: deploy Step 2 to production; monitor 7 days; then flip the flag to JWT-only.
   - Blocker: removes the session store as a dependency.
   - Kind: stochastic. Acceptance test first: metric is error rate on protected routes, baseline from the prior 7 days, threshold equal or lower, sample size equal to one week of traffic.
   - Domain: Complex. Cutover effects show only after trial, so this runs as a capped probe with a stop condition: flip the flag back if error rate rises above baseline.
   - Step 3 MUST NOT start until the test in Step 2 passes.

4. **Measure the sign-up funnel.**
   - Increment: instrument funnel events from landing to confirmed account; one session of analytics setup.
   - Blocker: removes the missing baseline (A2).
   - Kind: deterministic. Test first in Gherkin:
     - Given a visitor who signs up, when each funnel stage completes, then an event fires per stage in the analytics tool.
   - Domain: Clear. One known practice: log the events.
   - Dependency: runs in parallel with Steps 2 to 3, no shared code.

5. **Run one conversion experiment.**
   - Increment: one variant, for example fewer form fields or single sign-on at sign-up.
   - Blocker: converts "better" into a measured change.
   - Kind: stochastic. Acceptance test first: metric is sign-up completion rate, baseline from Step 4, threshold plus 5 percentage points, sample size for 95% confidence given current traffic.
   - Domain: Complex. Effect on user behavior shows only after the trial [judgment]. Stop condition: revert if no lift after the sample size.

If A3 proves false, keep the dual-auth window open another 7 days before the flag flip.
