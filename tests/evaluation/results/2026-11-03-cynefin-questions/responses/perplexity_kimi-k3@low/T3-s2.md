# Headline

Split the work: run the JWT migration as one project and sign-up conversion as a separate measured experiment, because they fail differently.

1. The two asks have different risk: the migration is knowable through analysis, conversion improves only after trials [judgment].
2. The migration should run behind a session-to-token bridge, so active users see no forced logout.
3. Conversion should change only after a baseline exists, because no current rates were supplied.

## Background

The request covers two changes to the auth service: replacing session-based login with JSON Web Tokens (JWT, a signed token the server does not store), and raising the share of visitors who finish sign-up. No code, scale numbers, or current conversion rate was provided.

## Relevance

Tying a growth change to a security-sensitive migration mixes failure modes. A JWT mistake affects every logged-in user; a conversion mistake affects only new visitors. Separate the two.

## Information

### Evidence

1. JWT is a defined standard with standard libraries; the migration is Complicated, not Complex [1].
2. Conversion optimization needs A/B testing, which is Stochastic: a single test commonly runs at 95% confidence with enough traffic, so run length depends on traffic [judgment, no rate supplied].
3. Combining both changes in one release makes rollback ambiguous: a conversion drop and a JWT bug cannot be separated [inference].

### Assumptions

A1. The service uses server-rendered or API clients that can send an Authorization header. Why not measured: no code was shared. Validate by: read the login handler. If wrong: add a cookie transport for tokens, one extra step.

A2. Session invalidation on logout must still work. Why not measured: the material does not state it. Validate by: check for a "sign out everywhere" feature. If wrong: add a token denylist and short token lifetimes.

A3. No existing conversion baseline or analytics events exist for the sign-up funnel. Why not measured: no analytics data was supplied. Validate by: query the event log for sign-up steps. If wrong: skip the baseline step and use the existing funnel data.

### Alternative considered

Doing both in one release: loses because a failure cannot be attributed or safely rolled back [inference].

## End

I recommend that we:

1. **Instrument the funnel first** (Day 1). Adds the baseline all conversion work needs. Classification: deterministic, Clear; cause and effect are known. Test:
```
Given a visitor completes each sign-up step
When events are recorded for 7 days
Then each step shows a count and a step-to-step rate
```

2. **Add JWT issuance beside sessions** (Days 2 to 4). Removes the blocker "tokens do not exist yet" without changing login behavior. Classification: deterministic, Complicated; an expert picks the library and key scheme from known options [1]. Test:
```
Given a valid login
When the session endpoint is called
Then a signed JWT with the user ID is returned and verified against the public key
```
Step 3 MUST NOT start until this test passes.

3. **Route API clients to JWT, keep browsers on sessions** (Days 5 to 7). Removes the risk of mass logout. Classification: deterministic, Clear. Test:
```
Given a request with a valid JWT
When it reaches a protected route
Then access matches the equivalent session request in all cases
```

4. **Session cutoff with rollback flag** (Week 3). Classification: deterministic, Complicated; rollout analysis decides the schedule. Test: traffic on JWT above 99% for 7 consecutive days, then remove session code behind a flag.

5. **Run one capped conversion probe in parallel** (budget: one form change, 2 weeks). Classification: stochastic, Complex; results show only after a trial, so leverage is a guess. Acceptance: metric is sign-up completion rate, baseline from Step 1, pass at +5% relative, 95% confidence, at least 1,000 visitors per arm.

Constants: 7-day observation windows and 1,000-sample arms are [judgment]; adjust to actual traffic.

## Follow-up

Conditions that change this recommendation: if A1 is wrong, add a cookie transport step after Step 3; if A2 is false, remove sessions in Step 4 without a denylist.
