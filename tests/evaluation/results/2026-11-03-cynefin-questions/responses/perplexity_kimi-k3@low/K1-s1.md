# Headline

The latency spike comes from the database connection pool shrinking from 50 to 8 in release 2026.10.21, and the fix is to restore a pool size that matches the 32 workers.

- The `db.pool.acquire` span went from p95 3 ms to 690 ms in traces, so waits at the pool gate nearly all the added latency [traces.txt].
- Logs show 1,800 to 2,400 "pool exhausted" warnings per hour after release, versus zero before [logs.txt].
- Query times barely changed (orders p95: 52 to 58 ms), and DB CPU is 41% peak, so the database itself is healthy [traces.txt].
- The ORM `selectinload` change and lower cache TTL are secondary; they add load inside a pool now too small to carry it.

## Background

After release 2026.10.21, p95 latency rose from 120 ms to 900 ms and errors went from 0.02% to 0.40%. The release changed pool size and timeouts, cache TTL, and the orders query.

## Relevance

96% of the new errors are PoolTimeout failures that return 503s to clients [traces.txt]. Waiting increases customer-facing timeouts and error rate.

## Information

Evidence chain:

1. The pool can hold 8 connections total per service config, but the service runs 4 pods x 8 workers = 32 workers [release.diff]. At 405 requests per second peak with ~30 ms of query work per uncached request, demand exceeds 8 connections at each pod, so workers queue. queuing theory at high utilization explains the nonlinear 87 ms to 912 ms spread in logs [logs.txt] [judgment].
2. Traces show `db.pool.acquire` p95 of 690 ms while all query spans stay near baseline [traces.txt]. DB CPU 41% and only 8 active connections confirm the bottleneck is the client pool, not the database [traces.txt].
3. The cache TTL drop from 300 s to 60 s raised the miss rate from 12% to 31%, which creates about 2.2 times more DB work and holds connections longer [traces.txt, release.diff]. Secondary contributor.
4. The `selectinload` addition adds a second query per request (order_lines p95 26 ms), another secondary contributor [release.diff, traces.txt].

A1. The commit message claims a new DB limit per service justifies max_size 8 (ticket OPS-412). Why not measured: the material does not state the actual server limit. Validate by: ask the DBA or check `max_connections` on orders-db. If wrong on either side: the fix still works, because 8 active connections use 41% CPU, so the server can carry much more.

A2. `max_size` in db.yaml applies per pod, not globally. Why not measured: the material does not state the scope. Validate by: active connections peaked at 8 across the service, which implies the limit is global in effect or per pod with contention dominated; either way 8 is far too small. If wrong: size the per-pod pool at 8 to 12 each, still fixing the issue.

Alternative considered: revert the ORM and cache changes but keep the pool at 8. It loses because acquire waits at the pool gate account for nearly all the added p95 (690 ms of 900 ms), so reverting only the secondary changes would leave the bottleneck in place [traces.txt] [judgment].

## End

3. Restore `default_ttl_s` to 300 and confirm the miss rate returns toward 12%. Deterministic, Clear. Test: at same load as Step 1, cache miss rate is at or below 15%. Depends on Step 1 so pool waits do not mask cache effects.

Run in parallel with Step 1 staging.

Sequencing: start Steps 1, 2, and 4 now. Step 3 follows Step 1. Step 1 production deploy waits on Step 2.
