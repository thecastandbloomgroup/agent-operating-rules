## Headline

Revert the connection pool config in `db.yaml` now; the p95 regression comes from 8 connections starving 32 workers.

- Pool acquire wait rose from 3 ms to 690 ms p95, while query times stayed near flat [2][3].
- The release cut `max_size` 50 to 8 and `acquire_timeout_s` 30 to 5, against 32 concurrent workers [2].
- The TTL cut (300 s to 60 s) tripled the cache miss rate, 12% to 31%, adding load pressure [2][3].
- The `selectinload` change is not the cause; `order_lines` query time fell slightly [3].

## Background

After release 2026.10.21 on 2026-10-21, API p95 rose from 120 ms to 900 ms and error rate from 0.02% to 0.40%. The release changed pool config, cache TTL, and the orders ORM query.

## Relevance

Errors are live now: 96% of them are `PoolTimeout`, and logs show 1,800 to 2,400 pool-exhaustion warnings per hour versus zero before [1]. Each day of delay costs failed customer requests.

## Information

Evidence, tied to each claim:

- `db.pool.acquire` p95 went from 3 ms (window A) to 690 ms (window B). It accounts for about 95% of the total latency increase [3].
- `db.query orders` p95: 52 to 58 ms. `db.query order_lines` p95: 30 to 26 ms. Query speed did not regress [3].
- Active DB connections from this service peaked at 8 in window B, versus 31 in window A, matching the new `max_size: 8` [2][3].
- The service runs 4 pods with 8 workers each, so 32 workers compete for 8 connections per pool boundary [2].
- DB server CPU is 41% peak, so the database has headroom. The 8-connection cap is not protecting the DB [3].
- Cache TTL 300 s to 60 s fits the miss rate rise from 12% to 31%: lower TTL means keys expire sooner [2][3].
- Traffic was flat: 410 versus 405 requests per second peak. Demand did not cause this [3].

Assumption log:

A1. The per-service DB connection limit in ticket OPS-412 allows more than 8 connections. Why not measured: the ticket text is not in the material. Validate by: read OPS-412 or ask the DBA. If wrong: keep max_size 8 and add a queue or reduce workers instead; this still fixes the tail but costs more.

A2. The 5 s acquire timeout is safe to restore to 30 s. Why not measured: no downstream SLA stated. Validate by: check the API timeout budget before deploy. If wrong: keep 5 s and raise max_size only.

Alternative considered: the `selectinload` eager load could have made queries slower and held connections longer. It loses because both query spans stayed flat and the extra query runs inside one acquired connection [3].
