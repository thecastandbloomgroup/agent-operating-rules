## Headline

Adopt one automated SQL formatter, enforce it in CI, and stop all style debate in reviews. Three moves do this.

1. Pick one formatter by a short structured vote.
2. Reformat the codebase once and add a CI check.
3. Make "no style comments without a CI failure" a team norm.

## Background

The team disagrees on SQL formatting. Every review contains style friction. The request is to fix the culture problem, not only the format.

## Relevance

Style arguments consume review time and damage trust. An automated rule removes the topic from human debate.

## Information

Tooling can format SQL deterministically. SQLFluff and sqlfmt both enforce one style and fail builds on violations [1]. This turns a taste dispute into a pass/fail check [judgment]. The cultural fix is the norm change, not the tool. Cynefin guidance says complex social change must run as a small probe with a measure [2].

Assumption log:

A1. The team uses Git with a CI system. Why not measured: the material does not state it. Validate by: check for a CI config file in the repo. If wrong: replace Step 3 with a pre-commit hook, same effect.
A2. All SQL targets one dialect. Why not measured: the material does not state it. Validate by: run the formatter's dialect detection on the repo. If wrong: add per-directory config in Step 2.

Alternative considered: a written style guide that reviewers apply by hand. It loses because humans still choose when to enforce it, so the friction stays [judgment].

## End

I recommend that we take these actions, in order.

1. Hold a 30 minute formatter vote. Increment: one meeting plus a one page comparison of SQLFluff and sqlfmt. Blocker removed: endless opinion loops. Task kind: evaluative. Rubric first: criteria are dialect support (weight 40%), config effort (30%), and editor integration (30%), pass threshold is the top score above 6 of 10, evidence is each tool's documentation [1]. Cynefin domain: Complicated, because an expert can score the options from documentation by deduction.
2. Apply the winner in one commit. Increment: one reformat commit, config file included. Step 2 MUST NOT start until Step 1 records a winner. Blocker removed: mixed existing styles. Task kind: deterministic, test written first:
   - Given the config file and the full SQL directory,
   - When the formatter runs in check mode,
   - Then it exits zero with no files changed.
   Cynefin domain: Clear, because one known practice (run the formatter) fits everyone [1].
3. Add a CI format gate. Increment: one pipeline step, under 20 lines. Step 3 depends on Step 2 passing. Blocker removed: slow drift back into inconsistency. Task kind: deterministic, test written first:
   - Given a pull request with a misformatted SQL file,
   - When the pipeline runs,
   - Then the format job fails and names the file and line.
   Cynefin domain: Clear, cause and effect are known to everyone.
4. Set the review norm as a four week probe. Increment: one line in the review checklist: "no style comments unless CI failed". Blocker removed: social permission to argue about taste. Task kind: stochastic, acceptance test first:
   - Metric: style-only comments across all reviews.
   - Baseline: count from the last four weeks.
   - Threshold: 80% reduction, sample size of at least 20 reviews.
   - Stop condition: revert the norm if review time or defect escapes rise. Budget: one hour per week to collect counts.
   Cynefin domain: Complex, because the norm's effect shows only after a trial, and induction from the baseline could break if review volume changes sharply [2].

## Follow-up

If A1 is false, replace Step 3 with a shared pre-commit hook. If A2 is false, add one config per dialect directory in Step 2.
