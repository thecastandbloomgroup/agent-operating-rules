## Headline

Run an experiment backlog: turn each retrospective into one or two owned, measured actions, and review them first at the next session. first fix the missing loop between talk and change. Then limit how many changes you start. Then change the input format so every voice contributes.

## Background

Your team holds retrospectives, people attend, yet the same problems return. The pattern matches a known failure mode where discussion never converts into tested behaviors [judgment].

## Relevance

Every retrospective without a change costs about one hour per person and erodes trust in the practice. Therefore fixing follow-through protects both time and morale.

## Information

Retrospectives fail mainly at three points: no owner, too many actions, and no review of past actions [judgment]. The Plan-Do-Check-Act cycle closes this loop: a change needs a plan, an owner, and a check against a baseline [1]. Thematically, agile literature reports the same three causes across reviews of retrospective practice (three sources agree, none disagree) [1], [2], [judgment]. Sample size is small because no tool measured your sessions, so confidence is medium (qualitative themes plus common practice).

**Alternative considered.** Stop running retrospectives and use one-on-one feedback instead. This loses because it removes the team's shared problem-solving forum, and the stated problem is follow-through, not forum choice [judgment].

**Assumption log**

A1. The team runs a regular retrospective with a facilitator. Why not measured: the material does not state it. Validate by: read one invitation or calendar entry. If wrong: adapt steps to the actual meeting.

A2. The environment is psychologically safe enough for open proposals. Why not measured: no tool can reach it. Validate by: ask the facilitator in one conversation. If wrong: apply the Follow-up condition.

## End

I recommend that we:

1. **Audit the last three retrospectives** (deterministic, Complicated: cause is knowable from records, by deduction from the no-follow-through rule). Increment: list every action proposed and mark each as done or not done. Blocker removed: unknown baseline.
   Test:
   - Given the notes of the last three retrospectives,
   - When each action is compared with the issue tracker,
   - Then every action carries a status of done, open, or dropped.

2. **Start each retrospective with a five-minute review of prior actions** (deterministic, Clear: one known practice fixes the missing check step). Increment: add a fixed agenda item. Blocker removed: actions were never revisited.
   Test:
   - Given the action list from Step 1,
   - When the next retrospective opens,
   - Then its notes show a status per prior action before new topics begin.

3. **Limit output to two experiments per session, each with one owner, one metric, and a review date** (deterministic, Clear: a work-in-progress limit is standard practice). Increment: one rule added to the facilitator's checklist. Blocker removed: too many parallel changes.
   Test:
   - Given the proposals in a session,
   - When more than two proposals pass the vote,
   - Then only the top two enter the tracker with owner and date fields filled.

4. **Probe silent written input before discussion** (stochastic, Complex: participation shifts are visible only after trials; the pattern could break with a dominant writer). Increment: run a capped probe for three sessions at about one hour each. Blocker removed: loud voices may filter input.
   Test: metric is distinct proposals recorded per session; baseline is the mean of the last three sessions from Step 1; pass threshold is a 50% increase over three sessions.

Steps 2 to 4 MUST NOT start until Step 1 passes. Steps 2 and 3 are ordered before Step 4 because they reduce uncertainty about the probe.
