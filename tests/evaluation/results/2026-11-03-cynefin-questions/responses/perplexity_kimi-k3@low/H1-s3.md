## Background

Checkout returns HTTP 500 for every user since 09:12 today. Ten minutes remain before an executive call. The reader is the on-call engineer and must act alone.

## Relevance

Every minute of full checkout outage is direct revenue loss. A fast rollback restores service before a slow diagnosis does.

## Information

A2. The reader has permission to trigger a rollback and read production logs. Why not measured: the material does not state it. Validate by: attempt the rollback; permission failure appears immediately. If wrong: escalate to whoever holds deploy rights in parallel with Step 2.

**Alternative considered**

The strongest alternative is to diagnose the root cause first (read stack traces, reproduce the 500). It loses because diagnosis time is unbounded and users see zero recovery in the meantime [judgment]. Rollback is reversible and bounded in time.

## End

I recommend that we run these four steps in order.

1. **Rollback the most recent deploy or config change to checkout.**
   - Increment: trigger one rollback in the deployment tool. Done in about two minutes.
   - Blocker removed: the suspected bad change stops serving traffic.
   - Test (deterministic), written first:
     - Given the checkout service with the previous version deployed,
     - When a synthetic request calls the checkout endpoint,
     - Then the response status is 2xx and not 500.
   - Cynefin domain: Chaotic. Harm is happening now and no cause is visible, so the first action stabilises before analysis [1].

2. **Verify recovery and check the deployment timeline (depends on Step 1).**
   - Increment: watch the error rate dashboard for two minutes and pull the deploy log entry nearest 09:12.
   - Blocker removed: confirms or refutes whether the rollback worked (tests A1).
   - Test (deterministic), written first:
     - Given production checkout traffic,
     - When the error-rate dashboard is read two minutes after rollback,
     - Then the 5xx rate is at or below the level recorded before 09:12.
   - Cynefin domain: Clear. Reading a dashboard against a threshold is one known practice; cause and effect are known. It confirms the stabilisation worked.
   - Condition: if the 5xx rate does not drop, the domain is Confused. Page the checkout service owner immediately and treat database, dependency, and network as candidates.

3. **Post a status note to the incident channel and join the exec call.**
   - Increment: send two lines: impact ("checkout down 100% since 09:12"), action ("rollback at 09:1X, recovery verified/pending"), next update time.
   - Blocker removed: the executive audience hears facts, with no speculation.
   - Test (evaluative), written first: rubric is three criteria, equal weight, pass threshold 3 of 3: states impact, states action taken, states next update time.
   - Cynefin domain: Clear. A status note follows one known practice.

4. **Hand off root cause analysis after the call (depends on Step 2 passing).**
   - Increment: diff the rolled-back change and check error logs for the first 500 timestamp.
   - Capability added: data for a fix that can go through normal review and redeploy.
   - Test (deterministic), written first:
     - Given error logs from 09:00 to 09:12,
     - When the earliest unique stack trace is identified,
     - Then it is traced to one line or config key in the rolled-back diff.
   - Cynefin domain: Complicated. An expert reading logs and a diff can find the cause with analysis; leverage estimates become reliable once the analysis is done [1].
