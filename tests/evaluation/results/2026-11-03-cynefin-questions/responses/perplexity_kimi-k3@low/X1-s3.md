## Headline

Add a measured error rubric and a small human eval set before any prompt or model change, because the complaint "sometimes wrong" cannot be fixed without knowing which failure type dominates. First build a grader and 200-case benchmark; then run a root-cause pass; then change only the top failure cause.

## Background

The support tool added an LLM summariser. Agents report errors, but there are no metrics, so the size and type of the problem are unknown. Any change now would be unmeasured.

## Relevance

Random prompt edits without a baseline waste effort and can make things worse with no way to detect it. A cheap eval set converts the complaint into a number within days.

## Information

A1. Ticket volume and summariser traffic are not stated. Why not measured: the material does not state it. Validate by: one week of logs. If wrong: the benchmark sample size scales up or down.

A2. Agents can flag bad summaries with one extra click. Why not measured: the material does not state UI constraints. Validate by: asking one agent. If wrong: pull samples from logs instead.

Assessment [judgment]: summariser error complaints almost always cluster into three types: factual mistakes, missing key details, and wrong tone or length. The fix differs per type, so classification must come before tuning. Strongest alternative considered: swap to a newer model immediately. It loses because it has no baseline, so success or regression is undetectable [judgment].

Confidence: likely (66 to 100%) that a failure-type taxonomy plus eval set finds a dominant fixable cause within two weeks [judgment].

## End

I recommend that we take these four steps.

1. Add a one-click "bad summary" flag in the agent UI. Increment: one flag button writing to the logs. Blocker removed: no data source. Domain: Complicated, because an engineer can analyse the UI and pick the simplest mechanism (deduction from platform docs). Kind: deterministic.
   - Test: Given an open ticket, when the agent clicks the flag, then the ticket ID and summary text appear in the error log.

2. Build a rubric and a human-labelled eval set of 200 summaries. Rubric: factual accuracy (weight 50), completeness of key facts (30), tone and format (20); pass threshold 85 of 100; evidence: the original ticket thread. Blocker removed: no shared definition of "wrong". Domain: Confused, because we cannot answer the Cynefin questions about error cause until we classify failures; this action gathers that data and so goes second. Kind: evaluative, using a weighted rubric per Kepner-Tregoe style scoring [15].

3. Classify the failures from Step 2 into the three types and count each. Increment: one spreadsheet, one afternoon. Blocker removed: unknown root cause. Domain: Complicated, because an expert given labelled data can identify the dominant type (induction from the sample; a new ticket type could break the pattern). Step 3 MUST NOT start until Step 2 is complete [judgment].

4. Run one capped probe targeted at the dominant failure type. Example: for missing facts, add ticket metadata to the prompt. Stochastic test: metric is rubric pass rate; baseline from Step 3; pass threshold plus 10 points; sample size 200 summaries; stop condition is one week or one evaluation cycle. Domain: Complex, because prompt behaviour is visible only after trials, so this is a safe-to-fail probe with a one-week budget. Leverage is a guess. Step 4 MUST NOT start until Step 3 names a failure type.

If A1 shows traffic under 50 summaries a day, reduce the Step 2 eval set to 100 and extend Step 4 to two weeks.
