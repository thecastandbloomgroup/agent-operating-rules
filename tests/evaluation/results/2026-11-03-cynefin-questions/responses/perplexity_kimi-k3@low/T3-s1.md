## Headline

Split this into two parallel workstreams: a deterministic token migration and an experimental conversion program.

1. Session to JWT (JSON Web Token, a signed token format) migration is known engineering work with testable steps.
2. Sign-up conversion is experimental work, because only trials will show which change lifts conversion.
3. The two workstreams share one sign-up flow, so flag boundaries MUST keep them from blocking each other.

## Background

The request covers an auth service that today uses server-side sessions. It also asks for better sign-up conversion in the same pass. No codebase, traffic data, or baseline metrics came with the request.

## Relevance

Token design errors create account-takeover risk, and conversion changes without a baseline produce unverifiable claims. Both failures are expensive to reverse after users depend on the new behaviour.

## Information

JWT trade-offs, per the standards and security guidance:

- JWT is a signed, self-contained token; the server verifies it without a session lookup [1].
- RFC 8725 recommends short token lifetimes and strict algorithm checks, because stolen tokens stay valid until expiry [2].
- OWASP guidance adds refresh token rotation and reuse detection as revocation strategy [3].

One theme emerges from these three sources: statelessness shifts risk from the session store to token lifetime design. Zero sources disagree. Driving claims rest on primary sources [1], [2]; [3] is tertiary and supports only the operational guidance.
