# Headline

Retrospectives fail when they end without owners, limits on work in progress, and follow-through checks, so fix the output loop, not the meeting. First, cap each retro to one or two action items because more items dilute ownership. Second, assign each item a named owner and a deadline because unnamed items never start. Third, review the last retro's items before each new retro because skipped review kills trust in the process.

## Background

The team's retrospectives run with attendance, but no changes follow. The request is how to make retrospectives produce change again.

## Relevance

A retro that produces no change trains people to disengage, so each cycle makes the next one weaker. Fixing the output loop restores the team's main mechanism for self-correction.

## Information

Common causes of retro failure group into three themes [judgment]:

1. Too many action items, so none get done. This matches published retrospective guidance, which advises few, concrete actions per session [1].
2. No named owner or deadline, so items decay after the meeting [judgment].
3. No check on prior items, so the team learns that items are optional [judgment].

One theme that disagrees: some teams act on items but see no effect because the items target symptoms, not process causes [1]. This matters here because the symptom "nothing shifts" can come from either no execution or weak item selection.

Assumption log:

A1. The team uses a standard sprint retro format (what went well, what did not, actions). Why not measured: the material does not state it. Validate by: ask the facilitator for the last retro notes. If wrong: the format change in Step 1 still applies; adjust the wording only.

A2. Items from past retros are not tracked anywhere visible. Why not measured: the material does not state it. Validate by: check the team's board for a retro action column. If wrong: keep Step 3 but shorten it to a two-minute review.

Alternative considered: replace retros with a different forum, for example a monthly improvement meeting. This loses because the retro cadence is not the reported problem; the missing execution loop is, and a new forum inherits the same loop [1].

## End

I recommend that we take these steps in order:

1. **Limit the next retro to one or two action items.** Increment: the next single session. Blocker removed: diluted ownership. Cynefin domain: Clear, because known practice applies directly (deduction from a known rule). Task kind: deterministic.
   - Given a completed retro discussion, When the team selects actions, Then at most two items are recorded.

2. **Assign each item a named owner and a due date before the meeting ends.** Increment: five minutes per item in the same session. Blocker removed: anonymous items that no one starts. Cynefin domain: Clear, one known practice. Task kind: deterministic.
   - Given a selected action item, When the retro closes, Then the item shows one owner name and one date.

3. **Open every later retro with a review of the previous items.** Increment: first ten minutes of the next retro. Depends on Steps 1 and 2; Step 3 MUST NOT start until a retro has produced owned items. Blocker removed: the team's belief that items are optional. Cynefin domain: Clear. Task kind: deterministic.
   - Given the prior retro's item list, When the retro opens, Then each item is marked done, dropped, or carried with a reason.

4. **Run a root-cause probe on one recurring complaint.** Increment: pick the complaint that has appeared in three or more retros, and run one small experiment against its process cause. Blocker removed: items that target symptoms. Cynefin domain: Complex, because the cause shows only after a trial (induction; the pattern breaks if the complaint is situational, not systemic). Budget: one sprint. Stop condition: the complaint appears unchanged in the next retro. Task kind: stochastic.
   - Metric: count of the complaint in retro notes. Baseline: current count over the last three retros. Pass threshold: the complaint is absent in the next retro. Sample size: two retros.

## Follow-up

If A2 is false and items are already tracked, the failure is item quality, so Step 4 moves up to second place.
