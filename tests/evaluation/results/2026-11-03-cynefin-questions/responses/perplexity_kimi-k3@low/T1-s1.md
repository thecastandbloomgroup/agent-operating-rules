## Headline

Automate SQL formatting so the disagreement stops being a human decision.

- Take formatting out of reviews with one enforced config.
- Let a machine apply the style, so no one argues the choice.
- Preserve existing queries through one bulk reformat, not gradual edits.

## Background

The team disagrees on SQL formatting. The disagreement shows up in every review. The request is to fix the friction, not to pick a winning style.

## Relevance

Style debates consume review time that belongs on logic. A formatter removes the debate because the tool decides, not a teammate [judgment].

## Information

Tools such as sqlfluff or sqlfmt apply one style rule set to every file [1]. sqlfluff also lints, so it catches style and rule violations in continuous integration (the automated checks that run on each change) [1]. A one-time bulk reformat avoids mixed styles in the codebase [judgment].

Assumption log:

`A1. The team uses a version control system and can add a continuous integration check. Why not measured: the material does not state it. Validate by: check the repository settings. If wrong: run the format check in code review tooling instead.`

`A2. The team accepts any consistent style once a tool enforces it. Why not measured: the user has not answered. Validate by: propose the default style in one team meeting. If wrong: hold one vote on the tool's style options, then lock the config.`

Alternative considered: a written style guide without a tool. It loses because people interpret guides differently. A formatter gives one deterministic result [judgment].

## End

I recommend that we take these steps:

1. Install sqlfluff. Run it on the full repository to count violations [1]. Given a repository of SQL files, when sqlfluff lint runs, then it prints a violation count and zero errors from the tool itself. Deterministic. Clear domain: one known practice applies, so cause and effect is deduced from the documented tool behavior [1].

2. Adopt the default config in one team meeting, or hold one vote on style options. Rubric first: criteria are tool support (weight 3), readability (2), and diff size from current code (1). Pass threshold: a style named by consensus or majority in that single meeting. Evaluative. Complicated domain: few options exist and the vote decides, deduced from the rubric.

3. Run one bulk reformat commit after Step 2 settles the config. Given the chosen config, when sqlfluff fix runs on every file, then the diff shows only formatting changes and the test suite passes. Deterministic. Clear domain: the tool applies the style deterministically per its documented behavior [1]. Step 3 MUST NOT start until Step 2 names a style.

4. Add a lint check to continuous integration that fails the build on style violations. Given a pull request with unformatted SQL, when the check runs, then the build fails and names the violating lines. Deterministic. Clear domain: enforcement through automation is the standard practice [judgment].

5. Run one retro four weeks later with a single question: did formatting still appear in review comments. Metric: count of review comments about style. Baseline: current reviews, estimated at several per review [no source]. Pass threshold: zero. Sample: all reviews in the four weeks. Stochastic. Complex probe: comment behavior is visible only after the trial, so the result comes from induction. The pattern could break if reviewers use style comments for real logic concerns. Budget: one retro meeting.
