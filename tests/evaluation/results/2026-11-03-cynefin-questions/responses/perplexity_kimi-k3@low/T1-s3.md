# Headline

Automate the decision out of human debate: adopt one SQL formatter, encode its config in the repo, and enforce it in CI so reviews stop arguing about style.

- A formatter with a config file ends the disagreement mechanically, not by consensus.
- CI enforcement moves style checks off reviewers and onto a tool.
- One migration commit reformats all existing SQL so diffs stay clean afterward.

# Background

The team's SQL formatting varies by author. Every review includes style disagreement, which slows reviews and creates friction. The request is to fix the culture problem.

# Relevance

Style debates consume review time and erode trust. A tool-enforced standard removes the disputed question entirely, which changes the culture faster than another discussion would.

# Information

The friction has a fixable cause: style is currently decided by opinion in each review. Evidence from industry practice supports automation. The Google Engineering Practices documentation states that style should be enforced by tooling so reviewers focus on substance [1]. Trunk-based development guides recommend the same for formatting wars [2] [judgment: secondary-source guidance applies here since the symptom is identical].

Tools that resolve this exist and are free. sqlfluff (linter plus formatter) supports most SQL dialects and has a config file. sqlfmt and SQLFluff's `fix` command give deterministic output [judgment]. With a formatter, there is nothing left to argue about, because the tool decides.

Assumption log:

A1. The team uses one main SQL dialect. Why not measured: the material does not state it. Validate by: check the first five files reformatted in Step 2. If wrong: pick the dialect in the sqlfluff config and rerun.

A2. The team has CI or pre-commit hooks, or can add them. Why not measured: the material does not state it. Validate by: check for a `.github/workflows` or `.pre-commit-config.yaml` file. If wrong: add a CI job first, or use editor format-on-save as a fallback.

Alternative considered: write a style guide and agree on it by vote. This loses because agreement on rules does not produce agreement on application, and enforcement still falls on reviewers, which keeps the friction [1].

Confidence: high confidence, the standard cause of and the standard fix for this failure mode match.

# End

I recommend that we take these four actions, in order:

1. Pick sqlfluff and draft its config (dialect, rules, max line length). Task kind: evaluative. Domain: Complicated, because an expert can pick rules from the dialect docs (deduction from known rule). Blocker removed: no shared standard exists. Test first, rubric: config covers dialect, capitalization, and indentation rules (weight 50%), runs without errors on five sample files (50%); threshold 100% of criteria met.

2. Run the formatter once over the whole repo in a single commit with no logic changes. Task kind: deterministic. Step 2 MUST NOT start until Step 1's rubric passes. Domain: Clear, one known practice. Test (Gherkin):
   - Given the config from Step 1 and the current SQL files
   - When sqlfluff fix runs over the repo
   - Then all files pass sqlfluff lint and every query still executes against a dev database with unchanged results

3. Add a CI or pre-commit gate that fails unformatted SQL. Task kind: deterministic. Step 3 MUST NOT start until Step 2's test passes. Domain: Clear. Test (Gherkin):
   - Given a pull request with a formatting violation
   - When the gate runs
   - Then the check fails and names the offending lines

4. Send a one-page note explaining the change and routing future style disputes to the config file, not to people. Task kind: stochastic (team adoption varies). Domain: Complex, effect visible only after trial; probe with budget of one sprint and stop condition of fewer than two style comments per review. Test: acceptance metric written first. Baseline: count style comments per review for the last 10 reviews. Threshold: drop of 80% or more across the next 20 reviews.

# Follow-up

If A2 is false (no CI possible), replace Step 3 with editor format-on-save plus a weekly lint report.

Note: the culture fix is structural, not interpersonal. Nobody has to lose the argument. The tool takes the blame.
