## Headline

Run the migration as a dual-mode flag rollout, and base conversion work on a measured funnel baseline.

- Refresh token rotation with reuse detection keeps logout safe after the change.
- A parity mode lets old sessions and new tokens coexist, so no client breaks at cutover.
- Sign-up conversion has no baseline in the material, so measurement comes before any change.
- One conversion change runs as an A/B probe with a fixed budget and a stop condition.

## Background

The request has two goals: move authentication from server-side sessions to JWTs, and raise sign-up conversion. It offers no architecture, no funnel data, and no client inventory. See the assumption log for what that leaves open.

## Relevance

Both goals touch the sign-in path, so a wrong step blocks users. One plan avoids duplicating work on the same code twice.

## Information

**Token evidence**

A JWT is a signed token that a service verifies without a database lookup [1].

However, a bearer token carries no holder authentication [2]. Therefore a copied token works until it expires [2].

Because of that, the accepted pattern is a short access token lifetime plus refresh token rotation [3]. Rotation issues a new refresh token on each use [3]. It treats a reuse of an old token as theft, and revokes that token's whole family [3], [4].

A waiting JWT stays valid until expiry, so real logout needs a revocation list [4]. So the design is not fully stateless [inference]. It keeps one small store for revoked token identifiers.

**Conversion evidence**

Experiments need a pre-registered metric, a power check, and a read of the full sample [5]. A test stopped early gives a misleading win [5]. No funnel data exists in the material, so the first blocker is measurement [inference].

With a 3% baseline completion rate [judgment], a 10% relative lift needs about 50,000 users per arm at 80% power [5], [judgment on the stated numbers]. Low confidence in that figure, because the baseline is not measured yet.

Confidence in the token pattern: high, because two independent sources support rotation [3], [4].

**Assumption log**

- A1. Sessions live in one central store that one service owns. Why not measured: the material does not state it. Validate by: read the deployment configuration. If wrong: the revocation design in Step 2 changes shape.
- A2. The funnel has a measured drop-off stage. Why not measured: no analytics exist. Validate by: Step 1. If wrong: skip the probe and audit entry traffic instead.
- A3. No client depends on server-side session lookups. Why not measured: the material does not list clients. Validate by: search the codebase for session reads. If wrong: add a compat endpoint, and Step 3 grows by one session.
- A4. Access tokens target 15 minutes of life. Why not measured: the material states no lifetime requirement. Validate by: check any compliance rule in Follow-up. If wrong: Step 2 changes the revocation list size.

**Alternative considered**

Opaque reference tokens with server-side introspection are the closest rival. They lose because each request adds one store call, so they keep the session store and miss the stateless goal [judgment].

## End

I recommend that we do the following, in this order.

**Step 1. Instrument the sign-up funnel.** Add one event per step: page view, form start, submit, verify, and first use. One working session. It removes the blocker of a missing baseline. Test (deterministic), written first:

```gherkin
Given a user loads the sign-up page
When each step fires its event
Then the dashboard shows one count per step within five minutes
```

Domain: Confused, because the material cannot classify where conversion fails, so this step supplies the data that classifies it.

**Step 2. Decide the token design and write a one-page document.** Fix the access token lifetime, refresh rotation [3], and the revocation list. One working session, in parallel with Step 1. It removes the blocker of implementing without a design. Test (evaluative), written first. Score the design with a Pugh matrix against the current session setup. Criteria and weights: revocation latency 40, stateless verification 30, client compatibility 20, cost 10. Pass threshold: 60 of 100 weighted points. Evidence needed: the document plus a check against the OWASP token list [4].

Domain: Complicated, because an expert can pick the design from the analysis, so the inference is deduction from a security rule [3], [4]. Step 3 MUST NOT start until Step 2 passes.

**Step 3. Implement dual-mode auth behind a flag.** New sign-ins get JWTs. Old sessions stay valid until their natural expiry. One working session. It removes the blocker of a hard cutover. Test (deterministic), written first:

```gherkin
Given the flag is on and a user signs in
When the user calls the profile endpoint with the token
Then the service verifies the JWT and returns the profile with no session store lookup

Given the flag is on and a user holds a prior session
When the user calls the profile endpoint with the session
Then the service returns the profile as before
```

Domain: Clear, because a parity rollout is one known practice and anyone would apply it. Step 4 MUST NOT start until Step 3 passes.

**Step 4. Cut over and retire sessions.** Move the flag to 100% only when 14 days of logs show zero rotation reuse alerts. Then delete the session code. One working session. It removes the dual-mode complexity for good. Test (deterministic), written first:

```gherkin
Given 14 days of logs with zero reuse alerts
When the gate runs
Then the flag rolls to 100% and the session code is deleted

Given one reuse alert in the 14-day window
When the gate runs
Then the roll stops at 50% and page the on-call
```

Domain: Clear, because a soak-then-roll rule decides the step, so the inference is deduction from a known rule.

**Step 5. Run one conversion probe.** Remove or defer the field that Step 1 shows after the largest drop-off, as an A/B test with the metric fixed in advance. Two developer-days, one change only. It adds the capability of a baseline lift, proven. Acceptance test (stochastic), written first: metric is completed sign-up rate, baseline comes from Step 1, pass threshold is a 10% relative lift at 95% confidence [5], sample size computed from the Step 1 baseline at 80% power, run time two weeks minimum [5]. Stop condition: revert when full sample shows under 2% lift, and cancel early if completion drops 5% at any read [judgment]. 

Domain: Complex, because the result shows only after the trial, and the claimed leverage is a guess. Step 5 runs in parallel with Steps 2 to 4 once Step 1 ends, capped by its 2 developer-day budget.

## Follow-up

**Conditions that change the recommendation:** If A1 is right but the compliance answer in the token-lifetime check is strict, raise the revocation list weight in Step 2 from 40 to 60. If A2 shows no drop-off stage, skip Step 5 and reframe conversion as an acquisition problem.
