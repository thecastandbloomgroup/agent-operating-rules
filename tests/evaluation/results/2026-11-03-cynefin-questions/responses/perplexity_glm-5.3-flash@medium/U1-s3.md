## Background

The build fails for causes that change between runs. The message gives no logs, no error class, and no build system. The request is to stop the flakiness.

## Relevance

Flakiness costs every developer who waits for a retry. It also hides real defects behind green reruns. [1]

## Information

"Flaky" means a build that fails and passes on the same commit. This definition sets the baseline: runs on one commit must agree. [2]

Fowler lists the causes of non-determinism: lack of isolation, concurrency, uncontrolled inputs, resource leaks, and external dependencies. [2]

Micco's report describes a Google practice: quarantine any test whose failure rate crosses a set threshold. [1]

**Assumptions**

A1. The build runs on a CI server. Why not measured: the message does not state the environment. Validate by: open the CI run history. If wrong: run Step 2 on a local clone instead.

A2. The red rate is between 1% and 50% of runs on one commit. Why not measured: the message gives no rate and no logs. Validate by: count red builds in the last 100 runs on one commit. If wrong: a rate near 100% means a broken build, not flakiness, so debug one failure.

A3. No one changed the test code on purpose in the last week. Why not measured: the message gives no history. Validate by: read the commit log for tests and build config. If wrong: look at that change first, because a direct fix may beat all four steps. [judgment]

**Alternative considered**

Fix the single test that fails most. It loses because no test name is known yet, and a fix without counts leaves the other classes unranked. [judgment]

## End

I recommend that we capture failure data first, then fix causes one class at a time.

**Step 1. Capture and classify. Deterministic. Complicated.**
- Increment: a script that writes one record per failed run: commit, stage, error text, and one cause class from the four classes. Fits one session.
- Blocker: missing data, which blocks every choice below.
- Test, written first:
  ```gherkin
  Given a run that fails
  When the script completes
  Then the record holds commit, stage, error text, and one class
  ```
- Reason for Complicated: analysis of the records picks the practice, so leverage is reliable after the counts exist. This is deduction from the records.

**Step 2. Isolate with reruns. Stochastic. Complex probe.**
- Increment: for the first 20 failed runs after Step 1, rerun the failed stage alone in a clean job.
- Blocker: adds the ability to tell "the test is unstable" from "earlier tests broke it".
- Acceptance test, written first: metric is the isolated rerun pass rate; baseline is 0%, because the sample holds only failed runs; threshold is above 50% at 20 samples; stop at 20 records or at the end of the session.
- Reason for Complex: the result shows only after the trial, so leverage is a guess until the rate is known.

**Step 3. Fix the largest cause class, one class at a time. Deterministic. Complicated.**
- Increment: apply the standard fix for one class, for example fixed test order, or a stubbed service. Fits one session.
- Blocker: removes the top failure class from the build.
- Test, written first:
  ```gherkin
  Given the reproduction case from Step 1
  When the suite runs with the new configuration
  Then the reproduction case passes on every run
  ```
- Reason for Complicated: the class counts from Step 1 choose the fix; this is deduction.

**Step 4. Confirm with a green streak. Stochastic. Clear.**
- Increment: require 20 consecutive green builds on the main branch before closing each fix.
- Blocker: adds the guarantee that merged code keeps passing.
- Acceptance test, written first: metric is the count of red builds in the last 20 runs; baseline is the pre-fix rate from Step 1; pass threshold is zero red builds in 20.
- Reason for Clear: a green-streak gate is a known practice with a known rule, so apply it as one step.

Sequence: Step 2 MUST NOT start until Step 1 produces records. Step 3 MUST NOT start until Step 2 reports. Step 4 MUST NOT start until the test in Step 3 passes.

Condition: if A2 is wrong, replace all four steps with a single-failure debug of the most recent red run.

## Follow-up

- Open question: does the failure appear on CI only, local only, or both? The first two steps do not change, but the answer sets where Step 2 runs.
- Change condition: if the red rate approaches 100% on one commit, treat the build as broken and debug one failure. [judgment]
