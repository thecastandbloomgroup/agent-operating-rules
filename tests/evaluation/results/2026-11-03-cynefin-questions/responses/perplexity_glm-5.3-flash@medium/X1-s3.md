**Headline**

Build a labeled evaluation set from agent corrections first, then measure error types and test prompt fixes against those numbers. The blocker is the absence of ground truth, because no fix can be judged without it. The work runs in four steps: classify the failures, label a test set, run capped prompt probes, and wire agent feedback into the tool. Prompt changes are trials with a stop condition, not a single rewrite.

**Background**

The support tool shows agents a summary written by an LLM (large language model). Agents report that it is sometimes wrong, yet the team has no metrics, so the error rate and the error types are unknown. The request is to make the summarizer better.

**Relevance**

Every wrong summary costs agent time and risks a wrong reply to a customer. Without measurement, a prompt change cannot be told apart from noise, so change attempts will look random to the team.

**Information**

Evidence and findings:

- The request contains no error rate, no error types, and no sample of flagged summaries. Therefore the first artifact is data, not a fix.
- Agent reports are qualitative signals. A fixed set of codes turns them into countable themes, and this is the standard first stage of thematic analysis [3].
- Sample size: 100 labeled pairs gives a 95 percent confidence interval of about plus or minus 6 percentage points when the true error rate is near 10 percent. [judgment]
- Prompt changes show their effect only after trials on real tickets. Cause and effect appear after the trial, so these changes are safe-to-fail probes [18].
- A human review of every summary would catch all errors. It loses because it removes the time savings that motivated the summarizer. [judgment]

Assumption log:

- A1. Agent complaints mean factual errors (a wrong fact or a missing fact), not style. Why not measured: the request does not state the error type. Validate by: tag the last 30 reported cases. If wrong: add style and length metrics to the test set.
- A2. The tool stores both ticket text and summary, so a test set can be built from logs. Why not measured: the material does not describe the storage. Validate by: query the log store. If wrong: rebuild pairs from a sample of past tickets, one extra session.
- A3. Support volume allows collection of 100 labeled pairs within 2 weeks. Why not measured: no volume figure is given. Validate by: query tickets per week. If wrong: cut probe sample size and extend the timeline.

Alternative considered: route every summary through human review before release. It loses because it costs the full agent time saving on every ticket. [judgment]

**End**

I recommend that we run the following steps.

**Step 1. Tag the last 30 flagged summaries and classify the error types.** (Confused; evaluative.) Domain reason: the failure mode is unknown, so this action gathers what is needed to classify, by acting first [18]. Test, written first, as a rubric: 3 codes (wrong fact, missing fact, wrong resolution), weight 40 percent code coverage with no overlap, weight 60 percent two-rater agreement on the same 20 cases, pass threshold at 80 percent agreement, evidence is one tagged line per case.

**Step 2. Build a labeled test set of 100 ticket-and-summary pairs, waiting on Step 1 for the codes.** (Complicated; evaluative.) Domain reason: an expert can derive ground truth from the ticket data by deduction from known records. Test, written first: labeling rubric with weights, factual consistency 50 percent, completeness 30 percent, resolution correctness 20 percent; pass threshold is two-rater agreement on 80 percent of a 20-pair overlap sample. The blocker removed: without this set, no change can be judged.

**Step 3. Probe prompt changes on a 30-ticket sample; MUST NOT start until the test in Step 2 passes.** (Complex; stochastic.) Domain reason: the effect shows only after trials, and leverage is a guess. Two probes: require every claim to quote the ticket text, and cap summary length. Acceptance test, written first: metric is hallucination rate, baseline is the Step 2 rate, pass threshold is a 50 percent relative drop at 30 tickets, and the stop condition is 2 prompt iterations or 10 hours, whichever comes first. If the threshold is not met, keep the best version and hand refunds-and-legal tickets to human review. [judgment]

**Step 4. Add structured agent feedback in the tool; run in parallel with Steps 2 and 3.** (Clear; deterministic.) Domain reason: one known practice, feedback capture with one-click tags, applies to everyone. Deterministic test, written first:

```gherkin
Given an agent views a summary
When the agent applies the tag "wrong fact"
Then the log stores one row with ticket id, tag, and date
```

The added capability: a weekly report of tag counts, which feeds Step 3 with fresh error types, because Step 1 is a one-time sample.

Hedge: if A1 is false and the complaints target style, replace the Step 3 probes with style controls and keep the same tests.

**Follow-up**

Open questions, not blocking:

1. What does the log store for each ticket? (Needed to confirm A2.)
2. How many tickets per week? (Needed to confirm A3.)
3. Can agents edit the summary directly, or only flag it? (Direct edits give free ground truth for Step 2.)

Conditions that change the recommendation: A1 or A3 above.
