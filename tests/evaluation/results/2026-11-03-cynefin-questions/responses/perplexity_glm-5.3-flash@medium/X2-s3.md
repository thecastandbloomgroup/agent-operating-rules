## Headline

A retrospective that produces no change is usually a follow-through failure, not a meeting failure: diagnose the cause with data first, drive one owned action per cycle to done, and only then vary the format.

1. The cause is diagnosable. Sources name the same failure pattern: action items with no owner, no visible list, and no review at the next meeting [1][2].
2. Smaller scope wins. One item, one owner, one cycle beats a long list of unowned ideas [1].
3. Change the format only after follow-through works. Format variety helps stay engaged, but it does not fix a missing feedback loop [2][3].

## Background

The team attends retrospectives, people participate, and no observable change follows. The request asks what to do. This matches a documented pattern in agile practice [1].

## Relevance

Retrospectives carry the adapt half of the team's own feedback loop. When they produce nothing, inspection happens without adaptation, so process debt grows each cycle [3].

## Information

**Evidence**

1. Failure pattern. Symptom: the team names the same problems at every retrospective. Mechanism: when action items are unassigned, or written in a place no one looks at, or never reviewed again, teams rarely complete them [1]. Sources that support the theme: [1], [2]. No source found that disagrees.
2. Remedy pattern. Pick a few items at most, assign an owner, and open the next retrospective by reviewing that list [1][2].
3. Requirement from the team's own process. Teams regularly inspect how they work and adapt. A retrospective with no tracked change delivers neither inspection of outcomes nor adaptation [3].
4. Format matters, second. Participation drops when the format never varies. Varying format is one of several remedies for that symptom, not a cure for missing follow-through [2].

Table 1: failure modes against sources [1][2].

| Failure mode | What it looks like | Source |
|---|---|---|
| No owner | Items exist, nobody acts | [1] |
| No visible list | Items sit in a chat scroll no one reopens | [1] |
| No review | The next retrospective skips the old list | [1][2] |
| Stale format | Same exercise every time, votes feel flat | [2] |

**Assumption log**

A1. The retrospectives run at a regular cadence with the whole team present. Why not measured: the request does not state it. Validate by: ask the team or read the calendar. If wrong: a cadence problem needs a different fix. [inference]

A2. The team can act on its own work process without approval from outside the team. Why not measured: the request does not state it. Validate by: name one process decision the team made without escalation last cycle. If wrong: the blocker sits above the team, so escalate first. [inference]

A3. Action items lack owners and are not tracked. Why not measured: "nothing shifts" points there, but the real cause could be workload or priority [inference]. Validate by: count completed items against raised items for two cycles. If wrong: skip Step 1 of the End and target causes first.

A4. No lasting team conflict sits under the flat outcome. Why not measured: the request gives no sign either way. Validate by: an anonymous three-question pulse survey. If wrong: facilitation alone will not fix it; see Follow-up.

**Alternative considered**

Start with format variety and a facilitator rotation. It loses the first slot because the sources treat participation and follow-through as parallel conditions, not sequential ones [1][2]. Changing the format before the follow-through loop works keeps the meeting long and the outcome flat. [judgment]

## End

I recommend that we take four actions, in this order.

1. **Measure two cycles.** Increment: for the next two retrospectives, record three numbers: items completed from the previous cycle, whether the top concern from last cycle came up again, and a usefulness rating from each participant. Blocker removed: "nothing shifts" becomes a measured fact. Test before the work: the numbers for two cycles exist in a shared visible artifact, stated as percentages. Domain: Complicated, because an expert readout from the data picks where to focus next; the analysis names the practice for Steps 2 and 3.

2. **One item, one owner, one cycle.** Increment: after each retrospective, the team commits to one change, one owner, done before the next retrospective. The next retrospective opens by reviewing that item. Blocker removed: follow-through, which is the adaptation step [1][2]. Test before the work: Given a retrospective has ended and its single action item has an owner, When the next retrospective starts, Then the team reviews that item's status first. Domain: Clear, because the practice is known to everyone and the test checks a single visible behavior [18].

3. **Rotate format and facilitator.** Increment: the facilitator uses a different format from [2] each cycle, and the role rotates. Blocker removed: format fatigue, the participation symptom [2]. Test before the work: the next retrospective uses a format different from the last one. Domain: Clear, one known practice, one step [18].

4. **Retire stale items.** Increment: delete recurring items that have sat unowned or untouched for three cycles. Blocker removed: the ritual of re-listing old complaints, which trains the team to expect no change. Test before the work: no unowned item appears on the list after the next retrospective. Domain: Clear, a single visible deletion [18].

Step 3 follows Step 2, because format change without follow-through repeats the current result.

### Conditions that change this recommendation

- If A1 is false, fix the cadence first, to one review per one or two weeks [3].
- If A2 is false, raise the process blocker with the sponsor before Steps 2 to 4.
- If the measurement in Step 1 shows a 80% or higher completion rate over two cycles, the cause is not follow-through. Re-run the diagnosis on workload or priority. [inference]
- If A4 is false, bring in an experienced outside facilitator and address the conflict outside the retrospective.
