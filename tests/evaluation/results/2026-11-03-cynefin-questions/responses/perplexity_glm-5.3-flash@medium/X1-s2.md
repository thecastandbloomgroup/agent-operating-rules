## Headline

Build an evaluation loop with agent-labeled samples before changing the model. The agents' complaint is real but unmeasured, and "wrong" has many causes.

- You cannot improve a metric you do not have, so measure first.
- Agent labels on a small sample are the ground truth; they take one week to collect.
- Automated per-case scoring lets you fix causes one at a time, with tests.
- A monitor after each release keeps the gains.

## BRIEF

**Background**
The support tool now generates summaries with an LLM. Agents judge the output "sometimes wrong". The request is to make it better. There are no metrics, so the failure rate and the failure types are unknown.

**Relevance**
Unmeasured error erodes agent trust. Agents who distrust the summary stop reading it, so the feature gives no value. Measurement is cheap compared with redesigning the prompt blind.

**Information**

*Analysis.* "Sometimes wrong" can mean at least five distinct things, and they do not overlap: (1) facts not present in the ticket appear in the summary; (2) facts present in the ticket are missing from the summary; (3) a fact is correct but the tone or priority is wrong; (4) the summary reads as incoherent or confusing; (5) the summary is right but not useful for the agent's next step. Grouping all five under one complaint blocks diagnosis, so the first action separates them. This grouping follows standard thematic analysis practice [3], where codes are applied per instance and counted.

The overall problem state cannot be classified yet because no accuracy number exists. Under a framework for decision making in unknown conditions, the first step must then be to gather what is needed to classify [18]. After the ground-truth sample exists, the work becomes two tracks: fix causes found in the sample (each fix is a safe-to-fail probe with a measure and a stop condition), because LLM output varies from run to run and no rule predicts the effect of a prompt change in advance. Ground truth must come from people, because automated scorers of factual consistency agree with human judges only at about 80% or lower at the claim level [S] [19]; automated scores are therefore direction markers, not proof.

*Assumption log.*

- A1. The summariser sees the full ticket text and knowledge-base context. Why not measured: the material does not state the input set. Validate by: read the prompt and retrieval config. If wrong: fixes shift from generation to context retrieval, and the top error will be omission.
- A2. Agents can spend about 10 minutes per day labeling for one week. Why not measured: the user has not answered. Validate by: ask one team lead for a time budget. If wrong: cut the sample to 50 and extend to two weeks.
- A3. Weekly summary volume is at least 100 cases. Why not measured: no tool reached. Validate by: count summaries in the last 7 days. If wrong: stratify by product line to keep variety.

If A1 is false, replace Step 4 with a retrieval fix first.

*Alternative considered.* Tune the prompt now on a few ad hoc examples and skip measurement. It loses because one week of agent labels costs about one person-day and prevents three or more blind tuning rounds; with no metric, a prompt change cannot be told apart from noise.

## End

I recommend that we run the four steps below. Steps 1 and 2 run in one week. Steps 3 and 4 start after that.

1. **Zero in on the failure types (step 1).** Add five fixed labels (hallucination, omission, wrong tone, unclear, not useful) to the summary view. Collect labels on a random sample of 100 summaries for one week, with agent comments. This removes the blocker: complaint types and their rates become known. Test (write before work): Given a labeled sample of 100 summaries, When each label is counted, Then the top two error types cover at least 60% of errors and the count is reproducible by two raters on 20 shared cases (agreement: at least 80%). Kind: evaluative, rubric first: criteria are label fit and rater agreement, weights equal, pass threshold 80% agreement, evidence is the double-rated subset. Domain: Confused, because no accuracy number exists; the reason is that this step classifies the work and decides the rest [18].

2. **Automate the direction marker (step 2).** Build an LLM-as-judge check for factual consistency against the ticket text, and calibrate it on the labeled sample. This removes the blocker: no per-day measurement. Test (write before work): Given the labeled sample, When the judge scores it, Then judge accuracy points to the direction of the human label at 90% for the hallucination label, and misses only over-predict, under-predict, or disagree by type; sample size 100. If the threshold fails at 100, keep human labeling and do not use the judge. Kind: stochastic (LLM output), acceptance test as stated; baseline is human labels, pass threshold 90% on one label at n=100. Domain: Complex, because the effect shows only after a trial; probe budget is two working sessions, stop condition is a fail on the calibration test.

3. **Fix the top error cause (step 3).** Take the leading error type from step 1 and run one change: if hallucination, constrain the prompt to ticket sentences and require source span quotes; if omission, fix retrieval; if tone, add style rules. This adds the capability: the largest measured error rate drops. Test (write before work): Given a fresh random sample of 50 summaries, When the change runs for one week, Then the error rate for the target type falls by at least 30% relative to the step 1 baseline at n=50; otherwise revert. Kind: stochastic, sample size 50, baseline from step 1. Domain: Complex safe-to-fail probe, budget one week and one change at a time, so the effect is attributable. This step MUST NOT start until the step 1 labels are in.

4. **Keep the score visible (step 4).** Add a weekly panel: error rates by type, judge score trend, and sample count. This removes the blocker: regression goes unseen. Test: Given the panel, When a new release ships, Then the weekly hallucination rate and sample count appear within one day of the release. Kind: deterministic, Gherkin as given: Given a week of labeled data, When the panel refreshes, Then it shows all three fields with correct counts (spot-check 10 against tickets). Domain: Clear, one known practice that anyone would apply.

Ordering: steps 1 and 2 run in parallel; step 2 is capped by its two-session budget. Step 3 waits on step 1's labels. Step 4 follows step 2's calibration pass, or ships with human-labeled data only if the judge fails.

## Follow-up

Questions: none; assumptions A1 to A3 cover the unknowns.

Conditions that change the recommendation: if A2 fails, extend labeling to two weeks with n=50; if A3 fails, stratify the sample by product line; if A1 fails, run a retrieval fix as a second step 3 probe.
