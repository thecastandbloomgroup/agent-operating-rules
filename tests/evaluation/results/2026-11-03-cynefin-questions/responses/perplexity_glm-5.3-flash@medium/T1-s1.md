# Response

## Headline

Encode one SQL style in a machine-checkable config and let automation enforce it. This turns a culture debate into a tooling problem, which a team can solve in three working sessions.

Support:

1. A committed config makes the style a fact, not an opinion, and the team owns it [1].
2. Automation checks every change, so no reviewer spends time on format [inference].
3. One batch format of old files keeps blame off any person, because history no longer shows their style [inference].

## Background

The team disagrees on SQL format. Each review restarts the style debate. The request is to fix the pattern, not to pick a side.

## Relevance

Review time spent on format does not go to logic and risk. Without a mechanical rule, the debate returns with every change and every new team member.

## Information

**Evidence**

sqlfluff is a maintained open-source linter and formatter for SQL, and it supports many dialects through configuration [1]. That single fact drives the plan below.

The mechanism that causes the friction is ambiguity: each reviewer holds a private rule set, so each review becomes a negotiation [inference]. When code or a tool states the rule, the negotiation disappears [inference]. This theme rests on the mechanism itself, not on a study, so treat it as judgment from review behavior.

**Assumption log**

A1. Reviews run through pull requests against a repository. Why not measured: the request does not state the review setup. Validate by: look at one repository and its review flow in one session. If wrong: move the check to a local save hook or the shared workspace, and keep the rest of the plan.

A2. The team uses one main SQL dialect, or a small set. Why not measured: the request does not name the dialect. Validate by: scan the code for one session and note dialect markers. If wrong: create one config per dialect; the plan still holds.

A3. The friction is style only, and no deeper dispute hides behind it. Why not measured: no sample of review threads is available. Validate by: read and classify the last ten threads in one session. If wrong: run a team working session before tooling.

**Alternative considered**

A written style guide plus review discipline. It loses because a guide without a machine check still leaves every reviewer as the rule, so the debate returns on every review [judgment].

## End

I recommend that we make the style mechanical in four steps. The order follows the problem kind: gather the missing classification first, then pick, then enforce, then clean up.

1. **Classify the friction.** Read and classify the last ten review threads in one session. Rubric, written first: criterion "style share", weight 70, pass threshold 70 percent of threads, evidence the classified threads; criterion "no dispute about tooling or approach", weight 30, pass threshold 90 percent, evidence the same threads. Blocker: the plan assumed style-only friction (A3). Cynefin: Confused, because the problem kind is not yet visible, so the first action gathers data. Kind: evaluative. If the threshold fails, run a team session on the deeper dispute before Step 2.

2. **Commit one style config.** In one session, compare sqlfluff defaults against the current code, then commit the chosen config file to the repository. Blocker: no agreed rule set. Domain: Complicated, because an expert deduces the choice from data on dialect coverage and rule defaults. Kind: deterministic. Test, written first:

```gherkin
Given the committed config file for the team dialect
When sqlfluff lint runs on one trial file
Then every config rule resolves and the run ends with exit code 0
```

3. **Enforce the check in automation.** In one session, add the formatter check to a pre-commit hook and to continuous integration. This step waits for the config in Step 2. Blocker: enforcement by hand, which is where the friction lives. Domain: Clear, because commit-time format checks are one known practice. Kind: deterministic. Test, written first:

```gherkin
Given a pull request with one unformatted SQL file
When the CI job runs
Then the job fails and names that file
```

4. **Format all existing SQL in one commit.** Run this only after the check in Step 3 passes. Do the whole repository in one session, so no person's past style appears in history. Blocker: old files restart the debate each time a person touches them. Domain: Clear, because a one-time format run is one known practice with a known verification. Kind: deterministic. Test, written first:

```gherkin
Given all SQL files at the old format
When the formatter runs across the repository
Then the diff shows only format changes
Given the test suite runs after the format
Then every test passes
```

Condition that changes this plan: if Step 1 shows several dialects in equal use, add one config per dialect before Step 3.
