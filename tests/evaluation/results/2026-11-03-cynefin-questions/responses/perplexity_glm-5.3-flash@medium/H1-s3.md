## Headline

Roll back the most recent change before 09:12 now, then diagnose if that fails. Supporting points:

1. Harm is active since 09:12 and grows with every failed checkout, so stabilization comes before analysis [18].
2. A change near 09:12 is the most likely cause and rollback is the fastest reversible fix [judgment].
3. If rollback does not apply or does not fix it, check dependencies next: database, payment provider, certificates [judgment].

## Background

Checkout returns HTTP 500 for all users since 09:12. The user is on call and has about ten minutes before an executive call. The request: what to do now.

## Relevance

Every minute of downtime loses orders and damages trust. The executive call needs a short, factual message prepared in the same ten minutes.

## Information

**Evidence**

- Full failure rate since a single point in time points to a change at that time more than to gradual degradation [judgment].
- Rollback of a bad deploy typically restores service in minutes, while a live root cause fix takes longer [judgment].
- A single-step health check of dependencies (database, payment provider, TLS certificate expiry, third-party API status) isolates the failing service in one pass [judgment].

**Assumption log**

- A1. A code or config change near 09:12 caused the 500 errors. Why not measured: no deploy log was provided and no tool access. Validate by: read the deploy and config change timeline for 08:45 to 09:12. If wrong: skip Step 2 and run Step 3 first.
- A2. A rollback path exists and was used recently. Why not measured: the material does not state the deploy system. Validate by: open the deploy tool before 09:12 build and check the "roll back" action. If wrong: use a feature flag off, or fix forward only.
- A3. Dependencies are healthy and reachable from the logs. Why not measured: no tool access. Validate by: one curl per dependency from a production host. If wrong: Steps 1 and 2 waste time, so cap them at five minutes total.

**Alternative considered**

Debug the root cause live instead of rolling back first. It loses: rollback reverses any code or config cause in minutes, while root cause work has no time limit under an active outage [judgment].

## End

I recommend that we run these steps in order, with a total budget of eight minutes before the executive call.

1. **Pull the change timeline (3 min).** Read deploys, config edits, and flag changes from 08:45 to 09:12. This removes the blocker of not knowing what changed and prepares the rollback target. Test, written first:

   ```gherkin
   Given the deploys and config edits from 08:45 to 09:12
   When the timeline is listed
   Then the list shows the latest build and at least one rollback target
   ```

   Domain: Complicated, because an expert reads the deploy log to pick the cause, rather than a guess [18].

2. **Roll back to the last good build (2 min).** This removes the active harm if A1 holds. Step 2 MUST NOT start on a wrong target: use the build from before 09:12. Test, written first:

   ```gherkin
   Given checkout returned 500 since 09:12
   When the last good build serves checkout in production
   Then a test checkout returns 200 and creates a test order
   ```

   Domain: Chaotic, because harm is active and there is no time to analyze; the action stabilizes first, and a wrong rollback is itself reversible [18].

3. **Run the dependency health pass (2 min, only if rollback fails or A1 is false).** Check database connections, payment provider status, and certificate expiry in one pass. This isolates the failing external service. Test, written first:

   ```gherkin
   Given the rollback did not restore checkout
   When one connectivity check runs per dependency
   Then one failing check names the failing service or all pass
   ```

   Domain: Complicated, because the checks and log data determine the failing service by analysis [18].

4. **Send the first status note, then brief the executives (1 min, parallel with Step 3).** Post "checkout is failing, we rolled back, next update at HH:MM", then give the executives the impact, the action taken, and the next check time. This removes the blocker of silence during the call. Test, written first:

   ```gherkin
   Given evidence from Steps 1 to 3
   When the executive call starts
   Then the message states the user impact, the action taken, and the time of the next update
   ```

   Domain: Clear, because the practice is known and applies in one step [18].

Sequencing: Step 2 depends on Step 1 finding a target. Step 3 runs only if Step 2 fails. Step 4 runs regardless.

Hedge: if A1 is false (no change near 09:12), swap the order of Steps 2 and 3.

- Are there incidents with a similar signature in the postmortem history? A match would shorten Step 3.
- Conditions that change the plan: if checkout serves no traffic at all (not just errors), check DNS and certificate expiry before rollback.
