## Headline

The regression comes from the pool change: max_size fell from 50 to 8, so each pod queues its 8 worker threads behind 8 connections, and acquire time grew from 3 ms to 690 ms p95. Support points:

1. The evidence points at connection acquisition, not queries: db.pool.acquire rose 3 to 690 ms p95, while db.query orders and order_lines stayed flat (52 to 58 ms, 30 to 26 ms p95) [traces.txt].
2. Errors match the same cause: 96% of the 0.40% errors in window B are PoolTimeout at the 5 s acquire limit [traces.txt].
3. The cache and ORM changes are secondary: cache.get latency is flat at 2 to 5 ms, and the miss rate rise (12% to 31%) only adds load behind the same pool bottleneck [traces.txt].

## Background

P95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed the ORM layer, the cache TTL, and the connection pool. Logs, traces, and the diff are attached.

## Relevance

Pool exhaustion now causes 503 responses on the orders endpoint, so customer requests fail in production today. The 1800 to 2400 pool exhausted warnings per hour show the fault is continuous, not a traffic spike [logs.txt].

## Information

**Cause analysis, line by line.**

1. Release 2026.10.21 changed max_size from 50 to 8 and acquire_timeout_s from 30 to 5 [release.diff, config/db.yaml].
2. The API runs 4 pods with 8 worker threads each [release.diff, deployment note]. Each pod now serves 8 threads from a pool of 8 connections, so any parallel work exhausts the pool.
3. Pool exhausted warnings were absent on 2026-10-20 and run at 1800 to 2400 per hour on 2026-10-22, consistent with this change and stable traffic (410 to 405 rps peak) [logs.txt][traces.txt].
4. Acquire wait dominates latency: 690 ms of the 900 ms p95 is pool acquire [traces.txt]. That is a 99.7% rise in acquire time against the 3 ms baseline. Therefore pooling, not query work, is the bottleneck.
5. Database capacity is not the constraint: database CPU peak moved only from 38% to 41%, and active connections from this service fell from a peak of 31 to a peak of 8 [traces.txt]. Window A already ran about 31 active connections without exhaustion.
6. The ORM change is not the cause: selectinload added order_lines loading, and order_lines p95 fell from 30 ms to 26 ms [traces.txt][release.diff]. Keep it.
7. The cache change raises load but does not cause the regression: miss rate rose from 12% to 31% because default_ttl_s fell from 300 to 60, while cache.get latency stayed flat [traces.txt][release.diff, cache.yaml]. Missing cache entries now hit the pool more often, so the TTL change amplifies the pool shortage.

**Assumption log.**

A1. The true database connection limit per service in OPS-412 is not 8; the commit set a pod level value instead. Why not measured: the ticket is not in the material. Validate by: reading OPS-412. If wrong: size the pool to the documented limit instead of 50.
A2. The pool is per pod, not shared. Why not measured: the logs show 8 of 8 in use on pods api-1 to api-4 separately, which supports it, and no config states sharing. Validate by: reading the pool initialization code. If wrong: recompute the total pool size across pods.

**Alternative considered.**

Raising acquire_timeout_s back to 30 instead of the pool size. It loses: it turns fast failures into slower waits, so the 503 rate falls only if demand drops, and the traces show supply (8 connections), not patience, is the limit [judgment, from the pool arithmetic above].
