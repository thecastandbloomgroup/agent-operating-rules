# Headline

Measure the failures before changing code: a one week rerun sample plus a signature classifier will show which of four causes dominates.

- Flaky means the same build or test passes and fails with no code change [inference].
- Published studies narrow flaky failures to a short list of causes, and async waits lead that list [1].
- A small rerun sample and a signature matcher separate the causes at low cost.
- A quarantine rule keeps merges moving while the fixes land.

# Background

The build fails in an intermittent way, and no code change explains it. The request is to make the build stable.

# Relevance

An unstable build blocks every person who merges or ships. Each retry also wastes machine time and hides real failures.

# Information

**Evidence**

- One large-scale study of Google's test code found 16 patterns that cause flakiness; async waits, time dependence, and test ordering were among the most common ones [1].
- A separate study of open-source projects measured a flaky rate of about 0.3% of tests [2]. So the failures should cluster in a few tests, and a targeted patch beats a suite rewrite [inference from [2]].
- Because causes cluster in a few signatures, one week of logs should be enough to rank them [judgment].
