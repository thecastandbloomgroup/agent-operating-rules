## Headline

Measure first, then fix: label a sample of 100 real summaries to name the failure themes, and use agent edits as free ground truth.

Supporting points:
- No metric means no fix can be proven to work, so measurement comes before any change [judgment].
- Agent edits are ground truth the tool produces already, so capture costs little [judgment].
- A 100-summary sample, labeled with a rubric, names the failure themes in one session [judgment].
- A capped probe then fixes the top theme, and a release gate keeps the quality afterward.

## Background

The team added an LLM-based summariser to a support tool. Agents report the output is "sometimes wrong". No metric exists, so the team cannot size or locate the problem.

## Relevance

Without a baseline, any prompt or model change is a guess. Therefore a change could reduce quality and no one would detect it [judgment].

## Information

### Analysis

"Sometimes wrong" can mean several faults. These options do not overlap and cover the field: (a) unfaithful content, that is, facts not in the ticket; (b) missing content; (c) wrong length or tone; (d) wrong priority or next step [judgment]. Each fault needs a different fix. For example, unfaithful content needs grounding, and missing content needs a prompt or retrieval change. Because the fault type is unknown, gathering data must come before any fix. The sample labels therefore group failures into themes, and the theme counts decide the fix target [3].

### Assumption log

A1. The largest share of failures is unfaithful content, not style. Why not measured: the material states only "sometimes wrong". Validate by: label the 100-summary sample in Step 1. If wrong: Step 3 targets a different theme; the other steps do not change.

A2. Ticket volume allows a retro sample of 100 summaries from the last 30 days. Why not measured: the material does not state volume. Validate by: count summaries from the last 30 days. If wrong: use 30 summaries; the theme counts lose precision but still show the top theme.

A3. Agents already edit or rewrite bad summaries today. Why not measured: the material does not state agent workflow. Validate by: ask two agents to show one recent edit. If wrong: labeling stays offline with graders; cost rises to one grading session.

### Alternative considered

Replace the summariser with fixed templates per ticket type. It loses because templates cannot compress free text from varied ticket formats, and Step 1 will show whether the model is already adequate in most cases [judgment].

## End

I recommend that we run the four steps below, in this order.

1. **Label a sample to classify the failures.** Label 100 random summaries from the last 30 days. Rubric, written before labeling: faithful to the ticket (weight 0.5), complete (0.2), short (0.2), actionable next step (0.1). Pass threshold: 4 of 5. Evidence per criterion: ticket text next to the summary. Output: theme counts per rubric criterion. Kind: evaluative, scored per Kepner-Tregoe [15]. Cynefin domain: Confused, because no analysis can name the right fix before the labels exist; the labels themselves answer the question [18]. This step is the uncertainty source for the rest, so it goes first.

2. **Capture agent edits and ratings.** Add edit capture to the tool. Kind: deterministic. Test first:

   Given an agent saves an edit to a summary,
   When the save completes,
   Then the log stores the ticket ID, the first summary, and the edited summary.

   Cynefin domain: Clear, because one known practice (edit capture) applies, and any engineer would build it. Capability added: ground truth at volume, from the edits agents make already. Run this step in parallel with Step 1.

3. **Fix the top theme from Step 1.** Change one thing: the prompt, the retrieval, or the model. Then run 30 fresh summaries through the old and the new setting. Acceptance test, written before the trials: metric = faithfulness pass rate; baseline = the Step 1 rate; pass threshold = 90% or above; sample size = 30. Stop condition: revert if the pass rate is under 90% at 30 summaries. Budget: one session for the change plus one session for grading. Kind: stochastic. Cynefin domain: Complex, because the result shows only after the trial; the pattern could break on grading noise, so the same grader grades both arms [18]. This step MUST NOT start until the labels from Step 1 exist.

4. **Set a release gate.** Future prompt, model, or setting changes must pass the Step 1 rubric on 50 fresh summaries. The pass threshold is the Step 1 baseline plus 10 points. Kind: deterministic. Test first:

   Given a change to the summariser,
   When the gate runs on 50 fresh summaries,
   Then the release proceeds only when the pass rate meets the threshold.

   Cynefin domain: Complicated, because the threshold choice needs the Step 1 baseline and an analysis of cost against risk; the analysis picks the number [18]. This step MUST NOT start until the baseline from Step 1 exists.

Conditions that change this recommendation: if A1 is false, Step 3 targets the top theme from Step 1 instead. If A2 is false, Step 1 uses 30 summaries and states the wider uncertainty. If A3 is false, Step 1 budgets one grading session instead of agent edits.
