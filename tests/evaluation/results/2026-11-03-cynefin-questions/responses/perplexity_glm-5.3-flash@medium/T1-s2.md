## Headline

Replace the debate with a decision tool: adopt one SQL formatter, reformat the whole repository once, and enforce it in CI. The style arguments then vanish from reviews, because the tool decides style, not people. Support:

1. A formatter applies every style rule the same way on every file, so reviews stop carrying style disputes [1].
2. A single reformat and an automated check make compliance free for writers and reviewers.
3. The team's acceptance of the tool is a probe that you measure over a 4 week window, not a claim to accept now.

## Background

The team disagrees on the format of its SQL. Every code review carries style arguments. The request is to fix this culture problem.

## Relevance

Each SQL review now spends reviewer time on style instead of logic. A tool enforced rule ends the arguments without a meeting and removes the friction from every later pull request.

## Information

The disagreement is a tooling gap, not a values gap. The team lacks a mechanism that turns style choices into one output, so each review becomes a new vote. SQLFluff parses many SQL dialects, checks rules from a config file, and reformats files from that config [1]. The pre-commit framework runs the same check on each commit, before a pull request exists [2]. Because enforcement is mechanical, the style question leaves the review checklist. High confidence on tool capability comes from the tool documentation [1]. Whether the team accepts the tool's decisions is visible only after a trial.

Assumption log:

- A1. The repository holds one or two SQL dialects, for example PostgreSQL. Why not measured: the material does not state it. Validate by: a SQLFluff scan over all SQL files. If wrong: the config changes, the steps below do not.
- A2. The review platform runs CI checks on pull requests. Why not measured: the material does not state it. Validate by: look for an existing required check configuration. If wrong: rely on the pre-commit hook alone and label compliance in reviews.

Alternative considered: write a house style guide and enforce it through reviewers. It loses because each rule then needs a human argument in each review; a formatter applies the rule without a debate [judgment].

## End

I recommend that we:

1. Inventory the dialects. Run SQLFluff in scan mode over every SQL file and record the dialect errors per file. Blocker removed: the config in Step 2 rests on evidence, not on the loudest voice. Test, written first:
   ```gherkin
   Given the repository with all its SQL files
   When SQLFluff scans each file for a dialect
   Then the scan reports at most two dialects for the whole repository
   ```
   Kind: deterministic. Domain: Complicated, because analysis of the scan output picks the dialect setting.
2. Commit the `.sqlfluff` config and reformat all SQL in one merge commit that carries no other change. Blocker removed: no file ever needs a style discussion again, and no small diff drowns in reformat noise. Test, written first:
   ```gherkin
   Given the committed .sqlfluff config in the repository root
   When SQLFluff reformats every SQL file
   Then a second run of SQLFluff produces an empty change
   ```
   Kind: deterministic. Domain: Clear, because one known practice applies: one mechanical reformat, approved without line comments [1].
3. Enforce the format in CI. Add SQLFluff lint as a required check and add the same rule as a pre-commit hook [2]. Blocker removed: non-compliant files can no longer reach review. Test, written first:
   ```gherkin
   Given an open pull request with a SQL file that breaks the config
   When the CI pipeline runs
   Then the pipeline fails and blocks the merge
   ```
   Kind: deterministic. Domain: Clear, because the practice is standard and one step.
4. Probe the culture change. Count style comments on SQL pull requests for 4 weeks after Step 3, and route every style complaint into a pull request against the config instead of a review debate. Blocker removed: the team sees with data that the friction stopped, so the norm holds. Acceptance test, written first: metric is style comments per SQL pull request, baseline is the count from the 4 weeks before Step 3, pass threshold is at least 80 percent fewer, sample is all SQL pull requests in the window with a minimum of 10 [judgment on the threshold]. Stop condition: two failed config revision rounds in the window end the probe and move the decision to a team vote. Budget: one person, one weekly count. Kind: stochastic. Domain: Complex, because the result is visible only after the trial; the leverage estimate is a guess.

Sequencing: Step 2 MUST NOT start until the test in Step 1 passes. Step 3 MUST NOT start until Step 2 merges. Step 4 starts after Step 3 and runs with a cap of 4 weeks.

## Follow-up

Conditions that change the recommendation: if the scan in Step 1 reports more than two dialects, split the config per directory before Step 2. If A2 is false, replace Step 3 with a documented review rule that requires a reformat pass before approval.
