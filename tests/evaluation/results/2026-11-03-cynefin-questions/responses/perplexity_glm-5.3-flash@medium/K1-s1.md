## Headline

The connection pool change causes the latency regression. Fix the pool config first, then restore the cache TTL.

1. db.pool.acquire p95 rose from 3 ms to 690 ms, so waiting for a connection is 77% of the 900 ms p95 [traces.txt].
2. The release cut pool max_size from 50 to 8 and the acquire timeout from 30 s to 5 s, while the service still runs 32 workers [release.diff].
3. The cache TTL cut from 300 s to 60 s raised the miss rate from 12% to 31%, so more requests hit the starved pool [traces.txt].
4. The ORM change is not the main cause: db.query spans stayed flat and DB CPU rose only from 38% to 41% [traces.txt].

## Background

The API p95 latency rose from 120 ms to 900 ms after the release on 2026-10-21 at 14:05 UTC. The release touched the ORM layer, the cache config, and the pool config. Logs, traces, and the diff were reviewed for this analysis.

## Relevance

Errors rose from 0.02% to 0.40%, and 96% of the errors are 5-second pool timeouts [traces.txt]. Users now see 503s, and every extra hour keeps roughly 2,100 pool-exhaustion events on the books [logs.txt].

## Information

Evidence:

- Pool capacity fell by a factor of 6.25, from 50 to 8, in the same release as the regression [release.diff].
- "Pool exhausted" warnings went from 0 on 2026-10-20 to 1,800 to 2,400 per hour on 2026-10-22 [logs.txt].
- Peak active DB connections from this service were 31 before the release and 8 after, which matches the new cap [traces.txt].
- DB CPU rose only from 38% to 41%, so the database is not saturated. Queuing behind the cap produces the wait [traces.txt].
- The 5 s acquire timeout turns queuing into 503s. Errors at 5,002 to 5,004 ms match the timeout [logs.txt].
- Cache miss rate rose 19 points, from 12% to 31%, because the TTL fell from 300 s to 60 s [traces.txt].
- The ORM change adds little time: the orders query p50 moved from 18 ms to 20 ms and the lines query from 11 ms to 9 ms [traces.txt].

Assumptions:

- A1. The per-service DB connection limit in ticket OPS-412 is at least 64. Why not measured: the ticket is not in the material. Validate by: reading OPS-412 before the config change. If wrong: set the per-pod pool to the limit minus headroom, and queue fewer requests per pod.
- A2. The pool config is scoped per pod, so 4 pods give 32 connections. Why not measured: the material does not state the scope. Validate by: reading the pool library config docs in about 10 minutes. If wrong: the total cap is 8, and the target value in Step 1 must rise further.
- A3. Peak concurrent requests per pod is near 22, because one log line shows 8 in use plus 14 waiters on one pod [logs.txt]. Why not measured: no concurrency metric is in the material. Validate by: one query against the request concurrency metric. If wrong: the pool target in Step 1 changes a little.

Alternative considered: an N+1 query pattern from the new `selectinload` option. It loses because a second query per customer would raise query spans and DB CPU. Both stayed flat [traces.txt].
