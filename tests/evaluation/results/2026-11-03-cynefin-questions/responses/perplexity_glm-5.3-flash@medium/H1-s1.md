## Background

Checkout returns a 500 error for every user since 09:12 today. The user is the on-call engineer with ten minutes before an executive call.

## Relevance

Each minute of downtime blocks all revenue from checkout, so the first action has the highest value and must not wait for analysis [judgment].

## Information

**Evidence.** The request states the failure rate is 100% of users since 09:12. That points to a binary cause: a deploy, a config change, or a dependency that broke at that time, not a traffic effect [inference]. A total failure with a clean start time matches the pattern of a bad deploy [judgment].

**Assumption log.**

- A1. A deploy or config change landed shortly before 09:12. Why not measured: the material does not state it and the deploy history is not in this session. Validate by: read the deploy log timestamps. If wrong: skip the rollback and check the top dependency change instead.
- A2. A rollback path exists for checkout. Why not measured: the material does not state it. Validate by: open the CI release history for the last successful build. If wrong: use the feature flag, then a restart, then a traffic failover.

**Alternative considered.** Debug the live failure by reading stack traces and fixing forward. It loses: mean time to recovery is far higher, and the fix is unknown, so it risks a longer outage [judgment].

## End

I recommend that we run these five steps in order.

1. **Stabilise.** Roll back checkout to the last deploy from before 09:12 [18]. If A2 is false, disable the newest feature flag, then restart the service. Domain: Chaotic, because harm is happening now and no analysis time exists, so act first. Kind: deterministic. Test, written before the work:
   ```gherkin
   Given the checkout service runs the version from before 09:12
   When a test user submits one order
   Then the response code is 200 and the order reaches the payment queue
   ```

2. **Capture evidence.** Copy the error logs, deploy timestamps, and dependency changes from 09:00 into one incident file. Domain: Complicated, because an expert reads the logs to pick the cause, so name the analysis: timestamp correlation with 09:12. Kind: deterministic. Test:
   ```gherkin
   Given the incident file exists
   When the reviewer reads it
   Then it contains error samples, all deploy times, and all config changes after 09:00
   ```

3. **Verify recovery.** Run the test in Step 1, then watch the 500 rate for five minutes. Step 3 MUST NOT start until the Step 1 rollback finishes. Domain: Clear, because the pass rule is known to everyone, so apply the practice: green test plus falling error rate. Kind: deterministic, same Gherkin test as Step 1.

4. **Exec update.** State three lines: impact since 09:12, the rollback time, and the next update time 30 minutes later. Domain: Complicated, because the audience needs a choice of detail level, so the analysis is: lead with impact and action, defer the cause. Kind: evaluative. Rubric: completeness (weight 3), honesty about unknowns (weight 3), brevity of three lines (weight 2); pass threshold is 7 of 8; evidence is the draft message text.

5. **Root cause, after the call.** Probe one suspect at a time against the incident file, with a stop condition of two failed hypotheses, then escalate to the owning team. Domain: Complex, because the cause shows only after testing hypotheses, so this runs as a capped probe with a one hour budget. Leverage here is a guess. Kind: deterministic per hypothesis, test written before each probe.

Steps 1 to 4 fit in ten minutes. Step 5 waits until after the exec call.
