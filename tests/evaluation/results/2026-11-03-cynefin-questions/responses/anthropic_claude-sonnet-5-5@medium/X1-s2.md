## Headline

**Measure the failure first, then change the large language model (LLM) summariser against that measure.**

- Without a baseline, no change can be shown to help, so the first step is a labeled sample.
- Agents need a one-click way to flag a wrong summary, so the signal keeps flowing.
- An automatic check can catch invented names, numbers, and order IDs at no per-run cost.
- Prompt changes are trials, and each trial needs a budget and a pass threshold.

## Background

The support tool shows an LLM summary of each ticket. Agents say it is "sometimes wrong". The team has no metrics, so the error rate, the error types, and the ticket types affected are all unknown.

## Relevance

Agents who distrust a summary reread the full ticket. The tool then adds work instead of saving it. Each unmeasured change risks making this worse without anyone noticing.

## Information

**Evidence**

- Research on abstractive summarisation reports that generated summaries often contain facts that the source text does not support [1].

- Agent feedback is one theme from one source group: "sometimes wrong". Nothing disagrees with it, but it names no error type. Confidence is low, based on one unstructured remark. Labeled examples fix this (see Step 1). Thematic analysis of free-text reasons is the method [2].

- Invented or missing details are the most common error types: likely (66 to 100%) [judgment]. Step 1 tests this.

- Sample size of 100 tickets per variant in Step 4 [judgment]: it is large enough to see a 50% relative drop from a baseline near 20%, and small enough to label in two days.

- Cynefin domains in the End section follow the framework in [3].

**Assumption log**

A1. "Wrong" means invented facts, missing facts, or wrong details, not slow speed or layout. Why not measured: the material does not state it. Validate by: ask three agents for one example each. If wrong: change the reason codes in Step 2 and the rubric in Step 1.

A2. The tool can store ticket text and summaries. Why not measured: no tool can reach the system from here. Validate by: check the database for summary records. If wrong: add storage work before Step 2.

A3. The team can edit the prompt and settings. Why not measured: the material does not state who owns the configuration. Validate by: read the repository and vendor settings. If wrong: replace Step 4 with a change request to the owner.

A4. Two agents can give one hour each for labeling. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: label 25 tickets, not 50, and state the lower confidence.

**Alternative considered**

Swap to a larger model now. It loses because a swap without a baseline cannot show improvement, and it raises cost per ticket [judgment]. Step 4 can include a model swap as one variant.

## End

I recommend that we take these steps, in this order:

1. **Label a baseline sample.** Domain: Confused. The meaning of "wrong" is not yet known, so no cause and effect can be assigned. This step gathers what is needed to classify the rest.
   - Kind: evaluative. Write the rubric first.
   - Increment: two agents score 50 recent summaries against their tickets in one session.
   - Rubric: factual accuracy 40%, completeness 30%, no invented content 20%, usable length 10%.
   - Pass threshold: 80 points per summary.
   - Evidence: each deduction quotes the ticket line that supports it.
   - Blocker removed: the missing baseline and error types.

2. **Add a "Wrong" button with reason codes.** Domain: Clear. Logging feedback is a known practice, so the step follows from a known rule. Kind: deterministic.
   - Increment: one button, four reason codes (invented, missing, wrong detail, other), one stored record.
   - Blocker removed: no ongoing signal.
   - Test, written first:

   ```gherkin
   Given an agent views a ticket summary
   When the agent clicks "Wrong" and picks a reason code
   Then the tool stores ticket ID, summary text, model version, reason code, and time
   ```

3. **Build an unsupported-detail check.** Domain: Complicated. An expert can pick the method from the Step 1 data: exact match, fuzzy match, or a second model as judge. Step 3 MUST NOT start until Step 1 is complete. Kind: deterministic.
   - Increment: a script that flags any name, number, or ID in a summary that is absent from the ticket.
   - Blocker removed: no automatic error signal.
   - Test, written first:

   ```gherkin
   Given a ticket that contains the order ID "A123"
   And a summary that contains the order ID "A124"
   When the check runs
   Then the check flags "A124" as unsupported
   ```

4. **Run a capped prompt trial.** Domain: Complex. The result shows only after the trial. Run it in parallel with Step 2. Step 4 MUST NOT start until Step 1 gives a baseline and Step 3 passes its test. Kind: stochastic.
   - Probe: test up to three variants: quote the ticket line for each fact, lower the randomness setting, or use a fixed template.
   - Metric: share of summaries that score under 80 points or are flagged by the Step 3 check.
   - Baseline: the Step 1 result.
   - Pass threshold: a relative drop of at least 50%, with no fall in the completeness score.
   - Sample size: 100 tickets per variant.
   - Budget: two working days. Stop if no variant beats the baseline by 20% on the first 50 tickets.
   - Leverage is a guess. What could break the pattern: long threads or rare ticket types that the sample lacks.
   - Blocker removed: the error rate itself.
