## Headline

Roll back the latest change now, then send the executives a four-line status before the call.

- Stop the harm first, because every user fails at checkout.
- Get a second person so one of you fixes while the other communicates.
- Give the executives facts, not a root cause you do not yet have.
- Diagnose in depth only if the rollback fails.

## Background

Checkout returns 500 for all users since 09:12. You are the on-call engineer. The executive call starts in ten minutes.

## Relevance

The outage is total, so each minute costs revenue. The call is a fixed deadline, so your status must be ready before it.

## Information

**Evidence**

- Impact: 100% of users fail since 09:12 (your report).
- A sudden total failure at one exact minute points to a change, not to gradual load. This is likely (66 to 100%) [judgment].
- Incident practice puts mitigation before root-cause search, and rollback is the standard first mitigation [3].
- Cynefin treats active harm with no time to analyze as the Chaotic domain, so you act first [1].

**Assumption log**

A1. A deploy or config change went out shortly before 09:12. Why not measured: the material does not state it. Validate by: check the deploy log for changes between 08:45 and 09:12. If wrong: skip Step 1 and start Step 4 now.

A2. A rollback path exists and works. Why not measured: no tool can reach it. Validate by: run the rollback command in dry-run mode. If wrong: disable the changed feature flag instead.

A3. The fault is inside your system, not at a payment provider. Why not measured: the material does not state it. Validate by: read the provider status page. If wrong: the brief states "external dependency", and Step 1 changes to a failover or a message to the provider.

**Alternative considered**

Debug the root cause live before any action. It loses because diagnosis time is unbounded, while a rollback has a known duration [3] and you have ten minutes [judgment].
