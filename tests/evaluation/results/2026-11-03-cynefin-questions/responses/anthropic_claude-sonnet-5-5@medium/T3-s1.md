## Headline

Split this into two projects: migrate auth to JWT first, and run sign-up conversion as separate, measured experiments.

- The two goals touch the same sign-up flow, so shipping them together hides which change caused which result.
- JWT (JSON Web Token, a signed token that carries user claims) removes server-side state but makes revocation harder, so the design needs a decision first.
- Conversion is a measured outcome, so it needs a baseline and a test before any change.
- Both projects start with small, tested increments.

## Background

The request has two goals: replace session-based auth with JWT, and raise sign-up conversion (the share of visitors who finish sign-up). The material gives no code, no metrics, and no reason for the migration. Both goals touch the sign-up and login path.

## Relevance

A auth change can lock users out, and a conversion change can lower sign-ups. Mixing them in one release makes either failure hard to trace and hard to roll back.

## Information

**Evidence**

- A JWT is valid until its expiry claim (`exp`) passes, so a stolen token works until then unless the server keeps a revocation list.

  Source: the JWT specification.

  [1]

- Secure JWT use needs fixed algorithms, short lifetimes, and claim validation.

  Source: the JWT best-practice RFC.

  [2]

- Sessions give instant revocation because the server owns the state. This is the main property you lose.

  Source: the OWASP session guidance.

  [3]

- Access tokens of about 5 to 15 minutes with rotating refresh tokens balance revocation and statelessness. [judgment]
- No conversion number exists in the material, so no conversion claim has a baseline yet. [no source]

**Assumption log**

A1. The reason for the migration is stateless auth across several services or clients. Why not measured: the material does not state it. Validate by: ask the service owner for the one-line reason. If wrong: if there is no such need, the alternative below wins.

A2. The clients are browsers that can hold an httpOnly cookie (a cookie that page scripts cannot read). Why not measured: the material does not state it. Validate by: list the client types from the API gateway logs. If wrong: mobile clients need a different token storage in Step 2.

A3. Sign-up baseline conversion is about 10%. Why not measured: no tool can reach the analytics. Validate by: run Step 1. If wrong: the sample size in Step 4 changes.

A4. Traffic is high enough to finish one experiment in four weeks. Why not measured: the material does not state it. Validate by: read weekly sign-up starts from Step 1. If wrong: use fewer variants or a larger effect target.

**Alternative considered**

Keep sessions in a shared store and spend all effort on conversion. This loses if A1 is true, because stateless verification is the stated purpose of JWT. It wins if A1 is false. [judgment]

## End

I recommend that we take these four actions, in this order:

1. **Measure the sign-up funnel baseline.**
   - Increment: add one event per funnel step (view, start, submit, confirm) and collect one week of data.
   - Blocker removed: no baseline exists, so no conversion change can be judged.
   - Kind: deterministic. Test, written first:
     - Given a visitor completes sign-up
     - When the confirm step finishes
     - Then the four funnel events are stored once each with one shared visitor id
   - Domain: Clear. One known practice applies (event logging), so deduction from a known rule is enough.

2. **Choose the token design.**
   - Increment: score three options (keep sessions, JWT with short access and rotating refresh tokens, JWT with a revocation list) in one document.
   - Blocker removed: revocation and storage are open decisions.
   - Kind: evaluative. Rubric, written first, using a Pugh matrix with sessions as the baseline:

     | Criterion | Weight | Evidence needed |
     |---|---|---|
     | Revocation speed | 3 | Time to block a stolen token, per [1] |
     | Fit with RFC 8725 practices | 3 | Checklist against [2] |
     | Client fit (A2) | 2 | Client list from gateway logs |
     | Operating cost | 2 | Count of new stateful components |

     - Pass threshold: weighted score of at least 70% of the maximum, and no criterion scored 0.
   - Domain: Complicated. An expert can pick the practice from analysis, so the reasoning is deduction.

3. **Add JWT login behind a feature flag, with sessions still active.**
   - Increment: one login endpoint that issues and verifies tokens for flagged users.
   - Blocker removed: no working JWT path exists.
   - Kind: deterministic. Test, written first:
     - Given a flagged user with valid credentials
     - When the user logs in and calls a protected route
     - Then the route returns 200, and the same call with an expired token returns 401
   - Domain: Complicated. The design from Step 2 sets the practice, so the reasoning is deduction.
   - Step 3 MUST NOT start until Step 2 passes its threshold.
   - Later increments (refresh, logout, cutover, session removal) MUST each repeat this test pattern.

4. **Run one sign-up experiment at a time as a safe-to-fail probe.**
   - Increment: one variant, for example fewer form fields, split 50/50.
   - Blocker removed: no evidence shows which change raises conversion.
   - Kind: stochastic. Acceptance test, written first:
     - Metric: confirmed sign-ups divided by sign-up page views.
     - Baseline: the Step 1 value.
     - Pass threshold: an absolute gain of at least 1 point.
     - Sample size: about 14,700 visitors per arm for a 10% baseline, 5% significance, 80% power. [inference] Recompute from the real baseline.
     - Stop condition: end the test if conversion drops 2 points or more for 3 days in a row.
     - Budget: four weeks.
   - Domain: Complex. The result shows only after a trial, so the reasoning is induction. A seasonal traffic shift or a Step 3 auth change could break the pattern. Leverage is a guess.
   - Step 4 MUST NOT start until Step 1 has one full week of data.
   - Step 4 runs in parallel with Step 3. Assign users to variants independently of the auth flag.

## Follow-up

Conditions that change the recommendation:

- If A1 is false, replace Steps 2 and 3 with a shared session store and keep Steps 1 and 4.
- If A2 is false, add a mobile token storage criterion to Step 2.
- If the Step 1 baseline differs from 10%, recompute the Step 4 sample size.
