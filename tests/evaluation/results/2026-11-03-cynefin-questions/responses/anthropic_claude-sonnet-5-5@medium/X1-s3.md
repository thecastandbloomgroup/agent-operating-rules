## Headline

Measure the summariser first, then change it, because no change can be judged without a baseline.

- The team has no metric, so "sometimes wrong" cannot yet be sized or fixed.
- Agent feedback and a scored sample of real tickets will give a baseline within days.
- A prompt change is then tested against that baseline, not against opinion.

## Background

The support tool has a summariser built on a large language model (LLM). Agents report that it is "sometimes wrong". The team has no metrics and asks for an improvement.

## Relevance

Agents who distrust a summary reread the full ticket, so the tool adds work instead of saving it. Each wrong summary also risks a wrong reply to a customer.

## Information

**Evidence**

- Theme: summaries contain errors. Supported by 1 source (the request, current message). No source disagrees. Confidence is low, because there is one source and no count.
- The error rate, the error types, and the cost per error are unknown. [no source]
- Most errors in summaries are likely unsupported claims or missing facts. [judgment]

**Assumption log**

A1. The summariser works on ticket text and the team can read stored inputs and outputs. Why not measured: the material does not state it. Validate by: fetch 10 recent summaries with their tickets. If wrong: Step 2 needs a logging change first.

A2. Agents can give feedback in under 30 seconds per summary. Why not measured: the user has not answered. Validate by: time 5 agents on 5 summaries. If wrong: sample fewer summaries and use a reviewer instead.

A3. The model and prompt are under team control. Why not measured: the material does not state it. Validate by: check the configuration file. If wrong: Step 4 becomes a vendor request.

**Method**

Group the agent notes into themes and count the sources per theme [1].

Each action carries a Cynefin domain, which describes how cause and effect relate in the work [2].

**Alternative considered**

Switch to a larger model now. It loses because the cost is unmeasured, the error types are unknown, and a prompt or input fix is cheaper to try first. [judgment]

## End

I recommend that we take these steps in this order:

1. **Collect failure examples from agents.** Domain: Confused, because the error types are unknown and no expert can classify them yet. Kind: evaluative.
   - Increment: interview 5 agents and collect 30 wrong summaries in one session.
   - Blocker removed: no shared definition of "wrong".
   - Test (rubric first): criteria are error type named (weight 40%), ticket linked (30%), agent consensus (30%). Pass threshold: 70% of the 30 cases score at least 70%. Evidence per criterion: the ticket, the summary, and the agent note.

2. **Add a feedback control and log every summary.** Domain: Clear, because logging and a thumbs-down button are a known practice. Kind: deterministic.
   - Increment: one button plus one stored record per summary.
   - Blocker removed: no metrics exist.
   - Test, written before the work:

   ```gherkin
   Given an agent views a summary of ticket 123
   When the agent presses "wrong" and picks an error type
   Then the log stores the ticket ID, summary text, model version, and error type
   ```

   Step 3 MUST NOT start until this test passes and 3 days of data exist.

3. **Score a sample and set the baseline.** Domain: Complicated, because an analyst can compute the answer from the sample. Kind: evaluative.
   - Increment: score 100 random summaries in one session.
   - Blocker removed: no baseline for faithfulness and completeness.
   - Test (rubric first): faithfulness (weight 60%, no claim absent from the ticket), completeness (30%, all customer asks present), length (10%, under 100 words). Pass: the rubric is applied to all 100 summaries by two scorers, and they agree on at least 80% of items. Evidence: ticket text and summary.

4. **Run a capped prompt probe.** Domain: Complex, because the effect of a prompt change shows only after a trial. Kind: stochastic. Leverage is a guess. [judgment]
   - Increment: one prompt that tells the model to state only facts from the ticket and to write "unclear" otherwise.
   - Blocker removed: unsupported claims in summaries.
   - Test (written first): metric is the faithfulness rate from Step 3. Baseline is the Step 3 result. Threshold is the baseline plus 10 percentage points, with completeness down by no more than 3 points. Sample is 100 tickets per variant. Accept only when both limits hold at that sample size.
   - Budget and stop: one working session. Stop if faithfulness falls 5 points below the baseline in the first 30 tickets.
   - Step 4 MUST NOT start until Step 3 passes. It MAY run in parallel with Step 2 logging after Step 3.

If A3 is false, replace Step 4 with a written change request to the vendor that includes the Step 3 data.

- If the Step 3 baseline is above 95% faithfulness, drop Step 4 and track the metric only.
