## Headline

Measure the summariser first, then fix its most common error with a capped trial.

- Agents say it is "sometimes wrong", but no data shows how often or how.
- A labelled sample of summaries gives a baseline and an error taxonomy.
- Logged agent feedback keeps the measurement running after the sample.
- Each fix ships only if it beats the baseline on a pre-set test.

## Background

The team added a summariser to the support tool. A summariser here is a large language model (LLM, a program that writes text) that shortens a ticket. Agents report that it is "sometimes wrong". The team has no metrics (user message).

## Relevance

An agent who trusts a wrong summary may give a wrong answer to a customer. Without a baseline, no change can be shown to help.

## Information

**Evidence**

- The only evidence is the agents' statement: "sometimes wrong" (user message). The error rate and error types are unknown.
- Agent comments are qualitative data. Group them into themes and count the sources per theme [1].
- A sample of 100 labelled summaries gives a margin of about 8 points at 95% confidence when the true error rate is 20% [inference].
- Confidence in the diagnosis is low, because there are zero measurements so far.

**Assumption log**

A1. The tool stores each summary and its source ticket. Why not measured: the material does not state it. Validate by: query ten recent tickets. If wrong: add logging first and delay Step 1.

A2. Errors are mostly invented facts or omissions, not tone. Why not measured: the material does not state it. Validate by: Step 1 labels. If wrong: change the target of Step 4.

A3. At least 200 tickets per week reach the summariser. Why not measured: the material does not state it. Validate by: count tickets in the last week. If wrong: lengthen the trial window.

**Alternative considered**

The alternative is to switch to a larger model now. It loses because no baseline exists to show a gain, and the cost rises with no proof [judgment].

## End

I recommend that we take these steps in order.

1. **Label a sample of 100 summaries.**
   - Increment: two reviewers score 100 random recent summaries against their tickets.
   - Blocker removed: no one knows the error rate or the error types.
   - Kind: evaluative. Rubric, written first:
     - Faithfulness, weight 50%: every fact appears in the ticket.
     - Completeness, weight 30%: the issue, the request, and the status appear.
     - Usefulness, weight 20%: an agent can act without opening the ticket.
     - Pass threshold: the labelling is done when both reviewers agree on 80% of items.
     - Evidence needed: the full source ticket for each score.
   - Domain: Confused. The error types are unknown, so this step gathers what the other steps need [2].

2. **Log agent feedback.** Step 2 MUST NOT start until Step 1 finishes.
   - Increment: add a "Wrong" button with a reason code to the summary panel.
   - Blocker removed: no ongoing metric exists.
   - Kind: deterministic. Test, written first [3]:
     - Given an agent views the summary of ticket 123
     - When the agent clicks "Wrong" and picks a reason
     - Then the tool stores the ticket ID, summary ID, model version, prompt version, and reason
   - Domain: Clear. Event logging is a known practice that anyone applies.

3. **Run a prompt trial on the top error type from Step 1.** Step 3 MUST NOT start until Step 1 finishes.
   - Increment: change the prompt to target the top error type, then run 200 tickets per variant.
   - Blocker removed: the most common error.
   - Kind: stochastic. Acceptance test, written first:
     - Metric: faithful rate, the share of summaries with no invented or wrong fact.
     - Baseline: the Step 1 rate.
     - Threshold: baseline plus 10 points, and the lower 95% bound is above baseline.
     - Sample size: 200 tickets per variant.
   - Domain: Complex. The result shows only after the trial. Induction from trials decides it, and a shift in ticket mix could break the pattern.
   - Probe budget: one week of effort. Stop if the faithful rate drops 5 points below baseline in the first 50 tickets.

4. **Run a source-link probe in parallel with Step 3.** Step 4 MUST NOT ship until Step 2 is live.
   - Increment: show the ticket sentence behind each summary claim.
   - Capability added: agents verify a claim in one click.
   - Kind: stochastic. Acceptance test, written first:
     - Metric: "Wrong" clicks per 100 summaries.
     - Baseline: the Step 2 rate over the first week.
     - Threshold: a drop of 25% or more.
     - Sample size: 500 summaries.
   - Domain: Complex. Agent behaviour shows only after use, and a change in agent habits could break the pattern.
   - Probe budget: two weeks, one team. Stop if the median time per ticket rises 10%.
