## Headline

I recommend that we raise the connection pool size, because the pool change explains most of the added latency.

- The pool wait (`db.pool.acquire`) grew from 3 ms to 690 ms at p95. That is 687 of the 780 ms rise, or 88% [3].
- The pool shrank from 50 to 8 connections and the acquire timeout from 30 s to 5 s [2].
- The cache TTL cut adds load but is a smaller cause. The ORM change is not a visible cause.
- The database is not the bottleneck: CPU peaked at 41%, and query spans did not slow [3].

## Background

The API p95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed the pool, the cache TTL (time to live), and one ORM query. Logs, a diff, and trace summaries are attached.

## Relevance

The error rate rose from 0.02% to 0.40% [3]. Requests that wait 5 s fail with a 503 error [1]. The fault continues until the config changes.

## Information

**Evidence**

- Traffic is flat: peak requests per second were 410 before and 405 after [3]. Load growth is not the cause.
- Query spans are flat: `db.query orders` p95 went from 52 to 58 ms, and `db.query order_lines` from 30 to 26 ms [3]. The new `selectinload` adds no visible query cost.

- Pool warnings rose from none on 2026-10-20 to 1,800 to 2,400 per hour on 2026-10-22 [1].
- 96% of the errors are `PoolTimeout` [3].
- The cache miss rate rose from 12% to 31% because the TTL fell from 300 s to 60 s [3].

  Each miss sends a query to the pool, so the TTL cut adds pool demand. The `cache.get` span itself is flat at 4 to 5 ms [3].
- Capacity fits the demand badly. Four pods with 8 connections each give 32 connections. The old peak use was 31 [3]. [inference] A 19-point rise in misses pushes demand above 32.
- The commit message ties the pool size to a new database connection limit (ticket OPS-412) [2]. The limit value is not in the material.

**Assumption log**

A1. The database limit allows at least 48 connections for this service. Why not measured: the material does not state the limit. Validate by: read ticket OPS-412 or run `SHOW max_connections`. If wrong: Step 2 uses a smaller pool, and a connection proxy becomes necessary.

A2. The pool is per pod. Why not measured: the logs show "8 of 8" on every pod, but the traces show a service-wide peak of 8 connections [1][3]. Those two facts conflict. Validate by: log the pool config at pod start. If wrong: the sizes in Step 2 apply to the whole service.

A3. The `selectinload` change adds no wait of its own. Why not measured: no trace isolates it. Validate by: the canary in Step 4. If wrong: revert the ORM change.

**Alternative considered**

Revert the whole release. It restores service, but it also drops the new database limit work in OPS-412. The targeted fix keeps that work. Confidence in the pool as the main cause: high, three independent measurements (pool span, error type, flat query spans).
