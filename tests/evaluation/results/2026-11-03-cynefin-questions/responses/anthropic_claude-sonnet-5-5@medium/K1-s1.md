## Headline

Raise the database pool size back to a level the database limit allows, because the pool cap of 8 causes most of the added latency.

- The pool wait explains about 88% of the p95 increase (687 of 780 ms) [3].
- The cache TTL cut adds load on the database, but it does not explain the delay.
- The ORM change did not slow the queries.

## Background

The p95 latency of GET /customers/{id}/orders rose from 120 ms to 900 ms after release 2026.10.21. That release cut the pool max_size from 50 to 8, cut the cache TTL (time to live) from 300 s to 60 s, and added selectinload to one query [2]. The request is to decide what to do.

## Relevance

The error rate is 0.40%, which is 20 times the earlier 0.02% [3]. Each day without a fix keeps 503 errors and slow replies in production.

## Information

**Evidence**

- The p95 of db.pool.acquire rose from 3 ms to 690 ms. The total p95 rose from 120 ms to 900 ms [3].
- The query spans did not change. The orders query went from 52 to 58 ms at p95. The order_lines query went from 30 to 26 ms at p95 [3].
- Traffic is flat: 410 requests per second before, 405 after [3].
- Database CPU went from 38% to 41%, so the database is not the limit [3].
- 96% of the errors are PoolTimeout, with a 5 s wait [3].
- The logs show "8 of 8 connections in use" with 6 to 14 waiters on all four pods [1].
- The pool cap came from ticket OPS-412, which cites a new connection limit per service [2].
- The cache miss rate rose from 12% to 31%, but cache.get latency stayed at 5 ms or less [3].
- Theme: three independent sources (traces, logs, diff) agree on pool exhaustion. No source disagrees.
- Confidence that the pool cap is the main cause: very likely (90 to 100%).
- Held connections explain the loop. [judgment] Each request seems to hold its connection for the whole request. At about 101 requests per second per pod, the load is 0.21 s × 101 ≈ 21 connections. That exceeds 8.
- More cache misses add database work, so they worsen the pool wait. [judgment]

**Data gaps**

- Active connections from the service peaked at 8 in window B, against 31 in window A [3].
- Four pods with a pool of 8 each would show up to 32.
- The logs show 14 waiters on a pod with 8 worker threads [1][2].
- These numbers do not fit one model. Step 1 resolves this.

**Assumption log**

A1. The OPS-412 limit allows at least 12 connections per pod. Why not measured: the material does not state the limit. Validate by: read OPS-412 and the database max_connections. If wrong: Step 2 uses floor(limit / 4), and the team must add a connection pooler or cut worker threads.

A2. The pool size applies per pod. Why not measured: the diff does not say. Validate by: read the live config on one pod. If wrong: the per-pod ceiling in Step 1 changes.

A3. The 60 s TTL has no freshness requirement behind it. Why not measured: no ticket for the TTL is attached. Validate by: ask the config owner. If wrong: keep 60 s in Step 3 and add cache capacity.

**Alternative considered**

Roll back the whole release. It loses because the cache and ORM changes show no latency effect in the spans [3], and a rollback drops the OPS-412 change. It stays as the fallback if Step 2 fails its test.

## End

I recommend that we do these steps in order:

1. **Find the connection ceiling per pod.**
   - Increment: read OPS-412 and the database limit L, then compute floor(L / 4). Also settle the gaps above (31 vs 8, and 14 waiters vs 8 threads).
   - Blocker removed: the safe pool size is unknown.
   - Kind: deterministic. Test:
     - Given OPS-412 states a limit L per service
     - When L is divided by 4 pods
     - Then the written ceiling per pod equals floor(L / 4)
   - Domain: Complicated. An expert deduces the answer from the ticket and the database setting.

2. **Raise the pool on one canary pod.**
   - Increment: set max_size to min(12, ceiling) and acquire_timeout_s to 30 on one pod. Release 2026.10.14 used 12 per pod at most [2].
   - Blocker removed: pool exhaustion, which causes the added wait and 96% of errors.
   - Step 2 MUST NOT start until Step 1 gives the ceiling.
   - Kind: stochastic. Test: the metric is db.pool.acquire p95. The baseline is 3 ms [3]. The pass threshold is 10 ms or less. The sample is 10,000 requests on the canary. Accept only if the threshold holds.
   - Domain: Complicated. The cause is known from analysis, so deduction picks the value.
   - Then roll to all pods. If the test fails, roll back the release.

3. **Restore the cache TTL to 300 s.**
   - Increment: revert one line in config/cache.yaml.
   - Blocker removed: the 31% miss rate adds database load.
   - Kind: stochastic. Test: the metric is the cache miss rate. The baseline is 12% [3]. The pass threshold is 15% or less. The sample is 10,000 requests. Accept only if the threshold holds.
   - Domain: Clear. It reverts to a known setting.
   - Step 3 MAY run in parallel with Step 2. It MUST NOT ship before A3 is checked.

4. **Add a pool wait alert.**
   - Increment: one alert rule on waiters.
   - Capability added: early warning of a repeat.
   - Kind: deterministic. Test:
     - Given a pod pool is at max_size
     - When the waiter count stays above 0 for 60 seconds
     - Then the alert fires
   - Domain: Clear. Alert rules are a known practice.
