## Headline

Treat this as two separate projects: migrate auth to JWT first with no change in user behavior, then test sign-up changes as a measured experiment.

- The two goals have different test types, so one release cannot prove both.
- A JWT migration does not raise sign-up conversion by itself [inference].
- A baseline funnel measure must exist before any conversion claim.
- A migration that changes sign-up at the same time hides the cause of any change in rate.

## Background

The request has two goals: replace server-side sessions with JSON Web Tokens (JWT, signed tokens that carry user identity), and raise sign-up conversion. The material gives no stack, no traffic numbers, and no current conversion rate.

## Relevance

If both changes ship together, a drop in sign-ups has two possible causes. The team cannot tell which one to undo.

## Information

**Evidence**

- A JWT is a signed claim set that a server can check without a lookup [1]. Source type: primary.
- Known JWT attacks include algorithm confusion and weak validation. The best-practice list covers them [2]. Source type: primary.
- A signed token stays valid until it expires, unless the server keeps a deny list. This is why logout and forced sign-out need a design choice [inference].
- Conversion lift needs a baseline. No baseline exists in the material [no source].

**Assumption log**

A1. The service is one web or mobile backend with a server-side session store. Why not measured: the material does not state it. Validate by: read the auth config. If wrong: Step 2 changes to match the real topology.

A2. The current sign-up conversion rate is about 10%. Why not measured: the material does not state it. Validate by: query the existing funnel events. If wrong: the sample size in Step 4 changes.

A3. Funnel events (visit, form start, form submit, account created) can be added in one session. Why not measured: no tool can reach the codebase. Validate by: inspect the sign-up handler. If wrong: Step 1 takes longer and Step 4 waits.

**Alternative considered**

Keep sessions and fix only sign-up. This loses if the reason for JWT is stateless scaling across services. The stated request names JWT, so the migration stays [judgment].

## End

I recommend that we do these steps in order:

1. **Measure the sign-up funnel baseline.**
   - Increment: add four funnel events and read one week of data.
   - Blocker removed: no baseline exists, so no lift can be shown.
   - Kind: deterministic.
   - Domain: Complicated. An analyst can compute the rate from data, by deduction from a known method.
   - Test:
     - Given a visitor completes sign-up
     - When the account is created
     - Then four events with one shared visitor ID are stored

2. **Choose the token design with a rubric.**
   - Increment: one scored comparison of two options, short-lived access token plus refresh token versus opaque token.
   - Blocker removed: the revocation and logout design is undecided.
   - Kind: evaluative.
   - Domain: Complicated. More than one good practice exists, and expert analysis picks one.
   - Rubric (weights sum to 100; pass at 70 or more, with every criterion scored against evidence):
     - Revocation support: 35
     - Attack resistance per [2]: 35
     - Change effort: 30

3. **Build the migration behind a flag, with both methods accepted.**
   - Step 3 MUST NOT start until Step 2 is scored.
   - Increment: issue and verify tokens for login only, with sessions still valid.
   - Blocker removed: the cutover is unsafe without a dual-run period.
   - Kind: deterministic.
   - Domain: Complicated. The practice is known once Step 2 picks the design, by deduction.
   - Test, in Gherkin form [3]:
     - Given a registered user with valid credentials
     - When the user logs in with the flag on
     - Then a signed token is returned and an expired token is rejected

   Sign-up screens MUST NOT change in this step.

4. **Run one sign-up experiment as a capped probe.**
   - Step 4 MUST NOT start until Step 1 gives a baseline. It runs in parallel with Step 3 only on the old flow.
   - Increment: one variant, for example fewer form fields, shown to half of visitors.
   - Blocker removed: no evidence says which change raises conversion.
   - Kind: stochastic.
   - Domain: Complex. The result shows only after the trial, by induction from trials. User behavior shifts by season or traffic source could break the pattern. Leverage is a guess.
   - Acceptance test:
     - Metric: completed sign-ups per visitor.
     - Baseline: from Step 1 (A2 assumes 10%).
     - Threshold: lift of 1 point or more.
     - Sample size: about 14,700 visitors per arm at 80% power and 5% error (computed from A2).
     - Stop condition: halt if the variant rate falls 2 points below baseline.
     - Budget: two weeks of traffic.

5. **Cut over to JWT after Step 3 passes.**
   - Step 5 MUST NOT start until the Step 3 test passes and the dual-run shows no rise in login errors.
   - Increment: switch 10% of logins to tokens.
   - Blocker removed: the old session store stays in use.
   - Kind: deterministic.
   - Domain: Clear. A standard staged rollout applies, by deduction from a known rule.
   - Test:
     - Given the flag is on for 10% of users
     - When 1,000 logins occur
     - Then the login error rate is at or below the baseline rate

If A1 is false, replace Step 2 with a topology review before any design work. If Step 1 shows a baseline above 30%, recalculate the Step 4 sample size.
