## Headline

The pool size cut from 50 to 8 connections per pod caused the slowdown, so restore it first.

- The wait for a database connection explains about 88% of the added p95 latency.
- The query, cache read, and serialize spans did not change, so the ORM change is not the cause.
- The shorter cache lifetime adds load on the pool, so revert it second.

## Background

The API p95 latency (the time under which 95% of requests finish) rose from 120 ms to 900 ms after release 2026.10.21. The release changed the pool size, the cache lifetime (TTL, time to live), and the ORM (object-relational mapper) query. The request is a plan to fix the latency.

## Relevance

The error rate is 0.40%, up from 0.02%, and requests now fail with timeouts. The cause is a configuration change, so the fix is small and fast.

## Information

**Evidence**

- Total p95 rose by 780 ms (120 to 900 ms). The pool acquire span rose by 687 ms (3 to 690 ms), which is 88% of the rise. See traces.txt, window table.
- The p50 shows the same shape: total +162 ms, pool acquire +139 ms (86%). See traces.txt, window table.

- The pool max_size fell from 50 to 8 and the acquire timeout from 30 s to 5 s. See release.diff, config/db.yaml.

- Pods log "8 of 8 connections in use" with up to 14 waiters. So peak demand is at least 22 connections per pod [inference]. See logs.txt, db lines.

- The database query spans are flat: orders p95 52 to 58 ms, order_lines p95 30 to 26 ms. See traces.txt, window table.
- Database CPU is 38% to 41% and traffic is flat (410 to 405 requests per second). The database and the load are not the cause. See traces.txt, footer.
- 96% of errors are PoolTimeout. See traces.txt, footer.
- The cache miss rate rose from 12% to 31%, which is 2.6 times. The TTL fell from 300 s to 60 s. Each miss needs a query, so misses raise pool demand. See traces.txt, cache row, and release.diff, config/cache.yaml.
- The commit message says the pool size matches a new database limit per service (OPS-412). The ticket is not attached. See release.diff, commit note.

**Assumption log**

A1. The database limit in OPS-412 allows at least 22 connections per pod (88 in total). Why not measured: the ticket is not attached. Validate by: read OPS-412. If wrong: size the pool to floor(limit / 4) and add a connection proxy.

A2. The release is the only change between the two windows. Why not measured: the material does not state it. Validate by: compare the deploy log for 2026-10-21 to 2026-10-22. If wrong: the root cause may differ, so redo the span comparison.

**Alternative considered**

Revert the whole release. It loses because the evidence shows the ORM change is neutral [judgment]. A full revert also breaks the database limit work in OPS-412.
