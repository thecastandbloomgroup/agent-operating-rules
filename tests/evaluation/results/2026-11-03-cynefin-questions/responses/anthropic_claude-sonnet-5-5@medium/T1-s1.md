## Headline

I recommend removing the style decision from people and giving it to a tool, because the argument is about taste and taste has no right answer.

- Decide the style once, with a time-boxed vote and a scored choice.
- Apply the style by tool, so no reviewer sets it by hand.
- Enforce the style in an automated check, so a review never has to.
- Measure review comments before and after, so the team sees whether the friction fell.

## Background

The team has no shared SQL style. Each review reopens the argument. The request is to end this friction.

## Relevance

Every style comment costs reviewer time and slows the merge. It also turns a technical review into a personal one.

## Information

**Evidence**

- Review friction comes from style disagreement, per the request. The share of review comments about style is not measured. [judgment]
- SQLFluff, an open-source SQL linter (a tool that flags style problems), also fixes many problems automatically across several SQL dialects.
  See the SQLFluff documentation [1].
- Domain labels in Section End follow the Cynefin framework [2].
- Confidence that automation removes most style comments: low confidence, no local measurement yet. Step 4 measures it.

**Assumption log**

A1. The team reviews SQL by pull request (a proposed change that others read before merge) in git. Why not measured: the material does not state it. Validate by: open the repository history. If wrong: Step 3 moves to the team's own review tool.

A2. Style comments are a large share of review comments. Why not measured: the material does not state it. Validate by: count them in the last 20 pull requests. If wrong: style is not the main friction, so find the real cause first.

A3. The team uses one SQL dialect. Why not measured: the material does not state it. Validate by: ask in the Step 1 meeting. If wrong: Step 2 needs one config per dialect.

A4. The team accepts a tool default when the meeting is time-boxed. Why not measured: the user has not answered. Validate by: the Step 1 vote. If wrong: name one decision owner and let that person choose.

**Alternative considered**

A written style guide, enforced by reviewers. It loses because it keeps style comments inside reviews and still needs someone to decide the rules. [judgment]

## End

I recommend that we take these four actions, in this order.

1. **Choose the tool and rule set in one 45-minute meeting.**
   - Kind: evaluative. Domain: Complicated, because an expert can pick the practice by analysis, which is the scored comparison below.
   - Blocker removed: no agreed style, so no one can end the argument.
   - Increment: score two or three formatters, with the tool default as the starting rule set.
   - Test, written first: a Pugh matrix [3] with weights: dialect support 40, automatic fix 30, check in CI (continuous integration, a server that runs checks on each change) 20, small config 10.
   - Evidence: tool documentation and a trial run on five real files.
   - Pass threshold: a weighted score of 70 of 100. Ties go to the tool default.

2. **Apply the style to the whole repository in one commit.**
   - Kind: deterministic. Domain: Clear, because running a known tool is one known step.
   - Blocker removed: old files would fail the check in Step 3.
   - Increment: add the config, run the formatter, and list the commit in the blame-ignore file.
   - Step 2 MUST NOT start until Step 1 passes its threshold.
   - Test, written first [4]:

     Given the config file from Step 1 is in the repository
     When the formatter runs on every SQL file
     Then a second run changes no file

3. **Add an automated check to every pull request.**
   - Kind: deterministic. Domain: Clear, because wiring a known tool into CI is a standard step.
   - Blocker removed: nothing yet stops unformatted SQL from reaching a review.
   - Increment: add a CI job and a pre-commit hook (a script that runs before each commit).
   - Step 3 MUST NOT start until the test in Step 2 passes.
   - Test, written first:

     Given a pull request contains one badly formatted SQL file
     When the CI job runs
     Then the job fails and names the file

4. **Run a two-sprint probe on one review rule: "No style comments. Change the style only by a pull request to the config."**
   - Kind: stochastic. Domain: Complex, because the result shows only after the team tries the rule. Habits could break the pattern. Leverage is a guess.
   - Blocker removed: old habits keep style talk alive in reviews.
   - Increment: count style comments in the last 20 pull requests (the baseline, which also tests A2). Then announce the rule.
   - Acceptance test, written first: metric is the share of review comments about style. Pass is at most half the baseline share over the next 20 pull requests. Sample size is 20.
   - Budget: one counting session plus two sprints.
   - Stop condition: style comments appear in more than 3 of the first 10 pull requests. Then hold a 20-minute retrospective.
   - Run this probe in parallel with Steps 2 and 3. Take the baseline count before Step 3 goes live.
