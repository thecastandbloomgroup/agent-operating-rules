## Headline

Replace the style debate with an automatic formatter that one short decision selects and CI enforces.

- The friction comes from people judging style by hand, so a tool removes the judgment.
- A single time-boxed decision ends the argument about which style to use.
- A measured trial shows whether review friction falls.

## Background

The team has no shared SQL format. Each review includes style comments. The request is to fix this as a culture problem.

## Relevance

Every review pays this cost now. Each unresolved style opinion also delays real review of the logic.

## Information

Evidence:

- Style disputes come from taste, not from correctness. [judgment]
- A rule that a tool enforces removes the need for people to enforce it. [inference]
- It is likely (66 to 100%) that automated formatting cuts style comments in review. Basis: [judgment], no team data yet.
- The Pugh matrix compares options against a baseline, so it fits the tool choice.

Reference for the method:

Pugh matrix: see [1].

Assumption log:

A1. The team uses pull requests with a CI service. Why not measured: the material does not state it. Validate by: check the repository settings. If wrong: replace Step 3 with a local pre-commit hook.

A2. The SQL lives in repository files. Why not measured: the material does not state it. Validate by: search the repository for `.sql` files. If wrong: Step 2 and Step 3 need an export step.

A3. The team uses one SQL dialect. Why not measured: the material does not state it. Validate by: list the dialects in the last 20 pull requests. If wrong: add dialect support as a rubric gate in Step 1.

Alternative considered: a written style guide with manual enforcement. It loses because people still debate each case in review. [judgment]

## End

I recommend that we take these steps in order:

1. **Choose a formatter.**
   - Kind: evaluative. Domain: Complicated, because an expert can pick the tool from comparison data (deduction from analysis).
   - Increment: one working session. Score three candidate formatters on five sample team files.
   - Blocker removed: no agreed style exists.
   - Test: a Pugh matrix [1] with the baseline "no tool". The criteria and weights are dialect support 30, CI integration 20, configurability 20, team familiarity 20, speed 10.
   - Pass threshold: a weighted score of 70 of 100. Each score needs evidence from the trial run on the sample files.
   - The team accepts the winner without a further vote. Step 2 MUST NOT start until a tool passes.

2. **Format the whole codebase in one commit.**
   - Kind: deterministic. Domain: Clear, because autoformatting is a known practice (deduction from a known rule).
   - Increment: commit the config file and one formatting-only commit.
   - Blocker removed: old files would fail the check in Step 3.
   - Test, written first:

     ```gherkin
     Given the committed formatter config
     When the formatter runs on every SQL file
     Then it reports no changes
     ```

3. **Enforce the format in CI.**
   - Kind: deterministic. Domain: Clear, because a CI check is a known practice (deduction from a known rule).
   - Increment: add one CI job that runs the formatter in check mode.
   - Blocker removed: reviewers enforce style by hand.
   - Test, written first:

     ```gherkin
     Given a pull request with an unformatted SQL file
     When the CI job runs
     Then the job fails and names the file
     ```

   - Step 3 MUST NOT start until the test in Step 2 passes.

4. **Run a probe on review friction.**
   - Kind: stochastic. Domain: Complex, because the effect on people shows only after a trial (induction from trials). The pattern breaks if reviewers keep style comments out of habit. Leverage is a guess.
   - Increment: count style comments on SQL pull requests. Start the baseline count now, in parallel with Steps 1 to 3.
   - Blocker removed: no data shows whether the change works.
   - Acceptance test, written first: the metric is style comments per pull request. The baseline is the last 20 merged pull requests. The threshold is a drop of at least 70%. The sample is the first 20 pull requests after Step 3.
   - Budget: one hour of setup and 15 minutes per week.
   - Stop condition: if the first 10 pull requests show no drop, stop and review the cause.
