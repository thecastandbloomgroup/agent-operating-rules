## Headline

Split this into two tracks: migrate to JWT in three tested steps, and run a capped experiment on sign-up conversion.

- The migration is analyzable work, so experts can plan it up front.
- Sign-up conversion is not predictable, so it needs a measured probe.
- The two tracks must not ship in one release, because the conversion result would be confounded.
- JWT does not raise conversion by itself [judgment].

## Background

The request has two goals: replace server-side sessions with JSON Web Tokens (JWT, a signed token that carries identity claims) in the auth service, and improve sign-up conversion. No code, traffic data, or funnel data came with the request. The plan below therefore rests on logged assumptions.

## Relevance

An auth change affects every user login, so a failed cutover logs everyone out. A conversion change affects revenue. Mixing both in one release hides the cause of any drop.

## Information

**Evidence**

- JWT defines an `exp` claim, so a token stays valid until it expires unless the server keeps state [RFC 7519, Section 4.1.4].

[1]

- Secure JWT use needs algorithm pinning, key checks, and short lifetimes.

[2]

- Sessions revoke at once; stateless JWT does not. This is the main risk of the migration [inference].
- Sign-up conversion gains from one form change are unpredictable until tested [judgment].

**Assumption log**

A1. The service is one web app with cookie sessions in a server-side store. Why not measured: the material does not state it. Validate by: read the auth module and session config. If wrong: Step 2 changes to match the real client types.

A2. Baseline sign-up completion is 20%. Why not measured: no tool can reach the analytics. Validate by: query last 30 days of funnel events. If wrong: recompute the sample size in Step 4.

A3. The site gets at least 2,940 sign-up starts per arm within four weeks. Why not measured: the user has not answered. Validate by: count sign-up starts for the last 28 days. If wrong: extend the test or choose a larger change.

A4. Forced logout of current users is not acceptable. Why not measured: the material does not state it. Validate by: ask the product owner. If wrong: Step 3 can drop the session exchange.

**Alternative considered**

Keep sessions and work only on conversion. This loses because the user asked for JWT explicitly, and the dual-accept plan keeps the rollback cost low [judgment].

## End

I recommend that we do these four steps:

1. **Choose the token design (Complicated, evaluative).**
   - Increment: score two options in one session. Option A is a 15-minute access token plus a rotating refresh token stored on the server. Option B is a long-lived JWT with a denylist.
   - Blocker removed: the revocation gap.
   - Test, written first: a rubric with four criteria. Revocation speed is 40 points. Security fit with the JWT best practices [2] is 25. Build effort is 25. Client impact is 10. Pass threshold: 70 of 100. Evidence per criterion: a threat note, an effort estimate in days, and a client list.
   - Domain: Complicated, because an expert can deduce the answer from known token practice.

2. **Add JWT issue and verify beside sessions, behind a flag (Complicated, deterministic).**
   - Step 2 MUST NOT start until Step 1 passes its threshold.
   - Increment: one login endpoint that returns a token pair, and one check that accepts either a session or a token.
   - Blocker removed: no path exists to run both methods.
   - Test:

   ```gherkin
   Given the flag "jwt_auth" is on
   And a user holds a valid access token
   When the user calls a protected endpoint
   Then the service returns 200
   And a user with an expired token gets 401
   ```

   - Domain: Complicated, because analysis picks the library and key setup, which follow known practice.

3. **Exchange live sessions for tokens, then remove the session store (Complicated, deterministic).**
   - Step 3 MUST NOT start until the test in Step 2 passes.
   - Increment: exchange a session for a token pair on the next request. Remove the store only after 14 days with zero session use.
   - Blocker removed: forced logout of current users (A4).
   - Test:

   ```gherkin
   Given a user holds a valid legacy session
   When the user makes a request
   Then the service returns a token pair
   And the user stays signed in
   ```

   - Domain: Complicated, because the exchange follows from the design in Step 1.

4. **Run one sign-up probe in parallel with Steps 1 to 3 (Complex, stochastic).**
   - Increment: instrument the funnel, then remove one form field for half of new visitors. Change only the form, never the token code.
   - Blocker removed: no measured baseline or cause of drop-off.
   - Test, written first: the metric is sign-up completion rate. The baseline is the measured rate (A2 assumes 20%). The pass threshold is 23% or higher, a 3-point gain. The sample size is 2,940 starts per arm, for 80% power at 5% significance [inference]. Stop condition: end the test if completion falls below 18% with 500 starts per arm. Budget: four weeks and one developer for two days.
   - Domain: Complex, because the result shows only after a trial. Induction from the trial could fail if traffic mix shifts during the test. The leverage of this probe is a guess.

## Follow-up

Open questions: none. Steps 1 and 4 each state the condition that changes them.

- If A1 is false, replace Step 2 with a client inventory first.
- If A3 is false, replace the field removal with a larger change, or extend the test beyond four weeks.
