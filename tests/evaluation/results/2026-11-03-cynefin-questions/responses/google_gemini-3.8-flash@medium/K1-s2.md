### Headline

We must restore database pool capacity and cache retention to eliminate pool acquisition queuing.
First, pool acquisition wait time drives 687 ms of the 780 ms p95 latency increase [1].
Next, cache misses rose from 12% to 31% because the cache time to live dropped from 300 s to 60 s [1], [2].
Finally, connection starvation across the 32 application workers caused pool timeouts and HTTP 503 errors [1], [3].

### Background

Release 2026.10.21 altered object relational mapping queries, reduced cache retention, and shrank database connection limits [2].
Following this release, API p95 latency increased from 120 ms to 900 ms under a steady load of 405 requests per second [1].
Furthermore, HTTP 503 error rates climbed from 0.02% to 0.40% due to pool acquisition timeouts [1], [3].

### Relevance

High latency and database connection timeouts degrade customer checkout flows today.
Therefore, operations must remediate connection starvation before peak traffic causes widespread outages.

### Information

Evidence shows that query execution time is not the root cause of the latency regression [1].
Specifically, database order query p95 latency only changed from 52 ms to 58 ms [1].
In contrast, connection pool acquisition p95 latency increased from 3 ms to 690 ms [1].
This acquisition delay accounts for 88% of the total p95 latency increase [1].

The incident traces to two interacting configuration changes [2].
First, cache `default_ttl_s` decreased from 300 s to 60 s [2].
Because cache retention fell, the cache miss rate rose by 19 percentage points, from 12% to 31% [1].
Consequently, database read traffic increased by a factor of 2.58 [judgment].

Second, `max_size` in `config/db.yaml` decreased from 50 to 8 connections per pod [2].
Each of the 4 API pods runs 8 worker threads, yielding 32 workers in total [2].
When cache misses occur concurrently, all 8 connections per pod saturate [3].
Logs record up to 14 concurrent threads waiting for an available connection [3].
Because `acquire_timeout_s` was lowered from 30 s to 5 s, waiting threads time out and return HTTP 503 responses [2], [3].
Database server central processing unit load remains safe at 41% peak utilization [1].
Therefore, the database server can safely absorb additional connections [judgment].

#### Assumption Log

A2. Redis memory capacity permits returning cache retention to 300 seconds. Why not measured: No tool can reach it. Validate by: Check Redis memory usage metrics in the monitoring dashboard. If wrong: Keep retention at 120 seconds and add memory to Redis.

#### Alternative Considered

The team could revert the object relational mapping change in `app/orm/orders.py` [2].
However, traces prove that `order_lines` query p95 latency actually decreased from 30 ms to 26 ms [1].
Therefore, altering the query layer does not solve the 687 ms pool acquisition bottleneck [1].
