### Background

Last week's release changed the database pool configuration, the cache time-to-live, and the order query [2].
Following that deployment, API p95 latency increased from 120 milliseconds to 900 milliseconds [1].
This response evaluates the telemetry and diff to provide corrective actions.

### Relevance

API latency is 7.5 times above baseline, and error rates increased by twenty times [1].

### Information

This section covers the evidence, assumptions, and alternatives.

First, the traces show that connection acquisition causes the latency spike [1].
In Window B, connection acquisition p95 latency rose from 3 milliseconds to 690 milliseconds [1].
Therefore, connection waiting accounts for 88% of the total 780 millisecond p95 latency growth [1].
Furthermore, pool timeouts cause 96% of the 0.40% error rate in Window B [1].
The database server CPU peak changed only from 38% to 41%, so the database server is not overloaded [1].

Second, the configuration changes caused this starvation [2].
The cache time-to-live dropped from 300 seconds to 60 seconds [2].
Because of this drop, the cache miss rate rose from 12% to 31% [1].
This change caused a 2.58 times increase in database read requests [1].
At the same time, the pool configuration reduced `max_size` from 50 to 8 connections per pod [2].
Each pod runs eight worker threads [2].
When concurrent queries arrive, threads exhaust the eight connections and queue up to five seconds [3].

Third, we log two operational assumptions below:

A1. The database server can support more than 32 total connections. Why not measured: the material does not state the limit in ticket OPS-412. Validate by: inspect ticket OPS-412 in Jira. If wrong: deploy PgBouncer or a connection pooler instead of raising pod pool size.

A2. Reverting cache time-to-live does not violate data freshness requirements. Why not measured: business freshness requirements are not in the release notes. Validate by: check the order domain specification. If wrong: keep time-to-live at 60 seconds and scale the connection pool higher.

Regarding alternative options, we considered rolling back the Object-Relational Mapping (ORM) eager loading change [2].
However, that alternative loses because query execution latency did not cause the spike [1].
Order query p95 latency increased by only 6 milliseconds, while order line query latency decreased by 4 milliseconds [1].
