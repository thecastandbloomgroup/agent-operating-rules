## Headline

Measure the errors first, then test one targeted fix before wider use. [judgment]

- Agents report errors, but the current evidence does not identify their cause or frequency. [1]
- A reviewed sample will distinguish false facts, missing facts, and poor presentation. [judgment]

## Background

The support tool now includes a language-model summariser. Agents describe its output as “sometimes wrong,” but there are no metrics. [1]

## Relevance

Changing the prompt or model now would leave no reliable way to judge improvement. [judgment] Therefore, the first useful deliverable is an error baseline, not a new model. [judgment]

## Information

### Evidence and limits

The supplied material contains one qualitative signal: agents report errors. [1] It contains no examples, error counts, ticket volumes, or model details. [1]

**Confidence in any specific cause is low because the supplied material contains no reviewed examples.**

Track three measures:

- **Error rate:** summaries with at least one false or essential missing fact, divided by summaries reviewed.
- **Severe-error rate:** summaries that could prompt harmful action, disclose private information, or falsely state an important commitment.
- **Review time:** seconds an agent needs to check and correct a summary.

These definitions and all targets, weights, sample sizes, and budgets below are proposed starting points. [judgment]

Count each summary once in the error rate, even when it contains several errors. However, record every error type to guide the fix.

### 1. Create a traceable review sample

**Kind:** Deterministic, meaning fixed inputs have fixed acceptance rules.

**Test first:**

```gherkin
Given a permitted support ticket and its generated summary
When a reviewer opens the review record
Then the record links the summary to the exact source version
```

**Work:** In one session, capture 50 recent ticket-summary pairs across the main support queues.

Record the model version, prompt version, generation time, and source version. Use existing access and retention rules. Keep private ticket content within approved systems.

**Blocker removed:** Reviewers can now check what the summariser actually received.

**Domain:** Clear, by deduction from the known requirement that an audit needs traceable inputs and outputs.

### 2. Establish the baseline and select one error class

**Kind:** Evaluative, meaning reviewers apply a stated rubric.

**Rubric first, using weighted decision analysis:**

| Criterion | Weight | Evidence required |
|---|---:|---|
| Factual accuracy | 50% | Each factual claim matches the source |
| Essential coverage | 30% | Summary includes the issue, current status, and next action when present |
| Usability | 20% | Agent can understand the summary without repair |

Score each criterion as 0, 0.5, or 1: fails, partly meets, or meets. Multiply by its weight.

**Pass threshold:** At least 90 points out of 100, with no severe error. Current scores remain unmeasured because no summaries are available here.

**Work:** After Step 1 passes, review all 50 pairs in one session. Have a second reviewer independently check 10 pairs.

Record each defect as:

1. A false or unsupported fact.
2. An essential fact omitted, excluding facts already counted as false.
3. A presentation defect, excluding factual and coverage defects.

Measure review time on 10 pairs. Resolve reviewer disagreements before calculating the baseline.

Select the most frequent severe error class first. If none exists, select the most frequent remaining error class.

**Blocker removed:** “Sometimes wrong” becomes a measured problem with examples.

**Domain:** Complicated, by deduction through source comparison and rubric analysis.

### 3. Test one targeted change offline

**Kind:** Stochastic, meaning generated output can vary between runs.

**Acceptance test first:**

- **Sample:** 50 fresh tickets, separate from Step 2.
- **Baseline:** The current version’s output on those same tickets.
- **Main metric:** Error rate, as defined above.
- **Pass threshold:** At least 30% fewer erroneous summaries and at least three fewer erroneous summaries.
- **Safety threshold:** Zero severe errors in the candidate outputs.
- **Time threshold:** Median review time does not exceed the current version’s median.

Review outputs without showing reviewers which version produced them.

**Work:** After Step 2 passes, make one change that addresses the selected error class.

For example, require “not stated” when the source lacks a resolution. Use this change only if invented resolutions appear in the baseline.

**Budget:** One four-hour session and 100 generated summaries, split equally between current and candidate versions.

**Stop condition:** Stop the candidate trial when a reviewer finds a severe error. Do not accept the change unless the completed sample meets every threshold.

**Blocker removed:** The team gains evidence that a specific change improves observed quality.

**Domain:** Complex, by induction from a capped trial. New ticket types or later model changes can break the observed pattern.

This is a local acceptance test, not proof of a low production error rate.

### 4. Gate release and preserve rollback

**Kind:** Deterministic.

**Test first:**



**Work:** After Step 3 passes, add the acceptance record and version controls in one session.

Keep summaries as drafts that require agent review before external use or ticket changes. Add an agent error-report control that captures the summary and source versions.

**Blocker removed:** Failed changes cannot silently replace the current version.

**Domain:** Clear, by deduction from fixed release rules.
