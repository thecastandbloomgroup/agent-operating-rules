## Headline

Make the summariser measurable first, then test one targeted fix before expanding its use.

- First, collect real failures instead of treating “sometimes wrong” as one problem.
- Next, judge errors by their harm, not just how well the summary reads.
- Finally, compare a revised version against the current version on cases it has not seen.

## Background

Your support tool now includes an LLM-based summariser, but agents report errors without a measured baseline. [1]  
The request is to improve it, not merely choose another model. [1]

## Relevance

Without examples and error rates, a model change has no reliable success test. [judgment]  
Therefore, the first improvement should make errors visible and prevent unreviewed summaries from driving customer actions. [judgment]

## Information

### Define “wrong”

Use these separate error categories:

| Category | Example | What to measure |
|---|---|---|
| Unsupported claim | Claims that an agent issued a refund | Summaries with claims absent from the ticket |
| Wrong interpretation | Says the issue is resolved when it remains open | Summaries that change the ticket’s meaning |
| Missing essential fact | Omits an unresolved customer request | Summaries missing facts needed for the next action |
| Poor presentation | Repeats details or exceeds the required length | Summaries that fail the agreed format |

These categories and measures are proposed assessment rules, not findings about your tool. [judgment]

Treat invented commitments, wrong customer attribution, and omissions that change the next action as **severe errors**. [judgment]

Measure three outcomes separately:

- **Quality:** failed summaries divided by reviewed summaries, split by error category and severity.
- **Agent effort:** median time to verify and correct a summary, compared with the current version.
- **Operation:** generation failures, response time, and cost per summary, compared with the current version.

These measures prevent a fluent but inaccurate summary from appearing successful. [judgment]

### Assumption log

A1. Agents review summaries before customer use. Why not measured: The material does not state it. Validate by: Inspect one agent workflow. If wrong: Contain automatic use first.

A2. Authorized staff can inspect recent tickets and summaries. Why not measured: The material does not state it. Validate by: Check access to one example. If wrong: Use approved, redacted examples.

### Alternative considered

Replace the model immediately. This loses because no measured baseline exists to show whether the replacement improves accuracy or agent effort. [judgment]

Confidence is high that measurement should precede broad release because the reported problem has no baseline. [judgment]  
Confidence in any specific prompt or model fix remains low because no failure examples are available. [judgment]

### 1. Capture a reproducible baseline

**Kind:** Deterministic.  
**Domain:** Confused, because the failure mechanism is unknown; gather evidence before selecting a cause-and-effect model.

**Test first:**

```gherkin
Given an authorized support ticket with a generated summary
When an authorized reviewer opens its evaluation record
Then the record contains the source snapshot, summary, model version, prompt version, and agent feedback
```

**Work:** In one session, capture 30 recent cases, including agent-reported failures and randomly selected cases.

Keep source snapshots under existing access and retention controls. Record ticket length and language to expose uneven results.

Inspect the workflow from A1. If summaries trigger customer actions without review, require review before further use.

**Capability added:** Reviewers can reproduce errors instead of relying on memory.

### 2. Score errors and select one repair

**Dependency:** Step 2 MUST NOT start until Step 1 passes.

**Kind:** Evaluative.  
**Domain:** Complicated, because expert review can compare summaries with source tickets; use analysis to select the repair.

**Rubric first:** Use a weighted decision matrix.

| Criterion | Weight | Evidence needed |
|---|---:|---|
| Facts match the ticket | 50% | Source passage for each factual claim |
| Essential facts remain | 35% | Reviewer’s list of facts needed for the next action |
| Format supports agent use | 15% | Agreed length, headings, and action fields |

Score each criterion from 0 to 2: fail, partial, pass. Convert the weighted score to a percentage.

**Pass threshold:** At least 90%, with no severe error.

**Work:** In one session, review 10 cases for diagnosis. Reserve the other 20 cases without inspection for Step 3.

Have a second reviewer independently score five diagnostic cases. Resolve differences before fixing the rubric.

Select the most frequent severe error first. If none occurs, select the most frequent failed category.

Choose one repair matched to that evidence. Examples include source-linked claims, explicit unresolved-status fields, or removal of irrelevant input.

**Blocker removed:** “Wrong” becomes a scored failure with a testable repair hypothesis.

### 3. Run a capped comparison

**Dependency:** Step 3 MUST NOT start until Step 2 produces a stable rubric and one repair hypothesis.

**Kind:** Stochastic, because model outputs vary.  
**Domain:** Complex, because the repair needs trials; use induction, which new ticket types or languages can invalidate.

**Acceptance test first:**

- **Sample:** 20 reserved tickets, with three runs per ticket for each version.
- **Baseline:** Current version, assessed under the same rubric.
- **Quality threshold:** Revised version passes at least 54 of 60 outputs and halves baseline failures.
- **Safety threshold:** No severe errors in the revised version.
- **Effort threshold:** Median verify-and-correct time does not exceed baseline.
- **Operational threshold:** Response time and cost remain within limits recorded before the trial.

**Work:** Apply one repair, then compare both versions with their identities hidden from reviewers.

Cap the trial at four staff-hours and a pre-approved generation budget. Stop on any severe error or budget breach.

Accept the repair only after the full sample meets every threshold. Otherwise, retain the baseline and revise the hypothesis.

**Capability added:** Evidence of improvement on unseen cases, rather than a better-looking demonstration.

This small trial does not establish safety across all ticket types. [judgment]

### 4. Gate release and retain rollback

**Dependency:** Step 4 MUST NOT start until Step 3 passes.

**Kind:** Deterministic.  
**Domain:** Clear, because release permissions follow a known gate; use deduction from recorded test results.

**Test first:**

```gherkin
Given a revised summariser and its evaluation results
When any acceptance threshold fails
Then the release gate blocks deployment
```

```gherkin
Given an approved revised summariser
When an operator invokes rollback
Then the support tool restores the previous version
```

**Work:** In one session, configure the release gate, version record, and rollback control.

Release first to a small, named agent group with review required. Continue recording corrections and severe errors.

**Blocker removed:** An untested change cannot silently replace the baseline.

## Follow-up

If the failures cluster in one language or ticket type, narrow the repair and trial to that group.

If input omits essential ticket content, fix input completeness before changing the model.

If live use reveals a severe error, stop the pilot and restore the previous version.
