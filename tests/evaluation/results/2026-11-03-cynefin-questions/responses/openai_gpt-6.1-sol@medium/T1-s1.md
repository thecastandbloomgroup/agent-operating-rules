## Headline

Replace repeated SQL style debates with a shared decision rule, an automatic formatter, and a short trial.

- Give everyone input, but give one named owner responsibility for the final style decision. [judgment]
- Separate formatting preferences from concerns about correctness, performance, and clarity. [judgment]

## Background

You report recurring SQL formatting disputes in code reviews. [1] The request concerns team culture, not just SQL layout.

## Relevance

A formatter alone leaves the team’s decision process unchanged. [judgment] Therefore, address both how the team decides and how reviewers enforce that decision. [judgment]

## Information

**Working diagnosis:** the team lacks an accepted way to resolve low-stakes disagreements. Confidence is low because the evidence contains one account, without review examples. [judgment]

The useful cultural norm is: **everyone gets a voice; not every preference gets a veto.** [judgment]

Use three separate review categories:

| Category | Examples | Decision rule |
|---|---|---|
| Mechanical style | Capital letters, indentation, comma placement | The formatter decides. |
| Engineering concerns | Wrong results, unsafe queries, poor performance | Reviewers provide a concrete example, test, or execution plan. |
| Human clarity | Confusing names, unclear query structure | Explain the reader’s difficulty and propose a specific change. |

This split keeps “the formatter decides” from becoming a reason to dismiss valid engineering concerns. [judgment]

**Assumptions**

A1. The team can name a style owner. Why not measured: The material does not state it. Validate by: Ask the team lead. If wrong: Obtain a sponsor before enforcement.

A2. Most disputes concern mechanical style. Why not measured: The material does not state it. Validate by: Classify ten recent disputed comments. If wrong: Address query clarity or technical standards instead.

**Alternative considered:** require full agreement on a detailed style guide. It loses because it makes agreement on preferences a prerequisite for progress. [judgment]

## End

I recommend that we take these three steps, in order.

### 1. Agree on a one-page decision charter

**Test first, deterministic**

Given a draft charter and a disputed SQL comment,  
When the team applies the charter,  
Then it identifies the comment’s category, decision owner, and appeal route.

**Work:** Hold one 25-minute meeting and approve the charter below. This removes uncertainty about who decides. [judgment]

> Formatting preferences belong in formatter configuration, not individual code reviews.  
> Everyone can propose a preference during the initial decision window.  
> The named style owner decides unresolved mechanical choices.  
> Correctness, performance, and clarity concerns remain valid review topics.  
> Mechanical preferences alone do not block a change that passes the agreed formatter.  
> Revisit the convention after the trial, then only for a documented problem.

Open with: “Different preferences are legitimate. Repeated negotiation in each review is the process we need to change.”

**Domain:** Complicated. Deduction from the category analysis identifies which decisions require technical judgment and which require a shared rule.

**Test first, deterministic**

Start with a small sample. Keep any repository-wide format change separate from functional changes, so reviewers can inspect each independently. [judgment]

**Dependency:** Step 2 MUST NOT start until Step 1 passes its test.

### 3. Run a capped trial of the new review norm

**Acceptance test first, stochastic**

- **Metric:** mechanical-style comments per reviewed SQL change.
- **Baseline:** the last ten reviewed SQL changes.
- **Sample:** the next ten reviewed SQL changes.
- **Proposed pass threshold:** at least 50% fewer mechanical-style comments, with zero changes blocked solely by mechanical preferences.
- **Guardrail:** retain all correctness, performance, and clarity checks.

These thresholds are trial design choices, not proven benchmarks. [judgment]

**Work:** Start the trial in one short session. Cap its duration at two weeks and its administration at 30 minutes.

Use this review response consistently:

> “Does this affect correctness, performance, or clarity? If it is mechanical style, use the formatter result and record any configuration proposal separately.”

Stop the formatter trial if it changes SQL meaning or cannot handle required syntax. Do not treat fewer comments alone as proof of a healthier culture. [judgment]

**Domain:** Complex. Induction from the trial tests whether the norm changes behavior. Unusually simple changes or silent disagreement can break the pattern.

**Dependency:** Step 3 MUST NOT start until Step 2 passes its test. The trial remains unrun; accept it only after collecting the stated sample.
