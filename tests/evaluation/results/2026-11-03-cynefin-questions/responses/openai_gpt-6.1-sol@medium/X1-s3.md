## Background

Agents report that the summariser is “sometimes wrong,” but you have no metrics. [1] This identifies a concern, not its frequency or cause.

## Relevance

Changing the prompt now gives you no reliable way to know whether accuracy improves. [judgment] Therefore, the first improvement should combine limited exposure with a measured baseline.

## Information

### What to measure

Use the **summary** as the measurement unit. Record these measures separately:

| Measure | Definition | Purpose |
|---|---|---|
| Serious error rate | Percentage containing an error that changes the next support action | Primary release measure |
| Unsupported claim rate | Percentage containing a claim absent from the source ticket | Detect invented facts |
| Required-fact omission rate | Percentage missing a fact needed for the next support action | Detect harmful omissions |
| Agent effort | Median seconds to check and correct a summary | Measure practical value |
| Cost and delay | Cost per summary and 95th-percentile response time | Detect operational regressions |

These definitions are proposed, not measured results. [judgment] Count each summary once per measure, even when it contains several errors.

First, separate errors by cause:

1. **Source input:** the model never receives the needed message or receives the wrong ticket.
2. **Generated content:** the source contains the fact, but the summary changes, invents, or omits it.
3. **Display:** the tool shows an outdated summary or associates it with the wrong ticket.

Use the earliest failing stage as the primary cause. This avoids counting the same failure under several causes. [judgment]

### Assumptions

A1. Agents review summaries before customer use. Why not measured: The material does not state it. Validate by: Inspect the workflow. If wrong: Contain automatic use first.

A2. Recent tickets and their summaries remain accessible. Why not measured: No tool can reach them. Validate by: Export one linked record. If wrong: Collect prospective examples.

A3. A support lead can define required facts and serious errors. Why not measured: The material does not state it. Validate by: Review five tickets together. If wrong: Establish the rubric before scoring.

A4. The proposed sample, gates, and trial budget fit your workload. Why not measured: The material does not state it. Validate by: Estimate review time on five tickets. If wrong: Revise them before the trial.

### Alternative considered

An immediate prompt rewrite is faster. However, without a baseline it cannot distinguish improvement from a change in error type. [judgment]

### 3. Run one limited trial against the main failure

**Kind:** Stochastic, meaning outputs vary between runs.

**Acceptance test first:** Use the same 200 tickets for the current version and one candidate.

Proposed release gates are: [judgment]

- Serious error rate falls by at least 50% relative to baseline.
- A 95% confidence interval for the paired error-rate difference stays below zero.
- No candidate summary contains a newly introduced serious error.
- Median agent effort does not increase.
- Cost and response time each increase by no more than 10%.

“Paired” means both versions receive the same tickets. If evidence cannot separate improvement from chance, report the result as inconclusive.

**Increment:** Change only the component responsible for the largest measured failure.

For example, fix missing source messages before changing the prompt. For invented claims, test source-linked statements and an explicit instruction to leave absent facts unknown.

**Blocker removed:** This tests a specific cause instead of changing several components without attribution.

**Domain:** Complex. Induction from a trial tests whether the fix works; different ticket types can break the pattern.

**Budget:** One candidate and at most 200 candidate summaries, plus the planned human review. Treat expected benefit as an estimate.

**Stop condition:** Stop the candidate trial after any newly introduced serious error. Do not enable automatic customer use.
