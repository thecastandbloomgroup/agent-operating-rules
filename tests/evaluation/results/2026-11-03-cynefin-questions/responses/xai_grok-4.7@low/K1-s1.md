Headline
The cut from 50 to 8 pooled connections caused the latency rise.
Acquire wait rose from 3 ms to 690 ms at the 95th percentile.
Query time and database CPU stayed near the old baseline.
Shorter cache life raised misses, but queries did not slow.
The new order-line load is not what made the tail slow.

Background
Release 2026.10.21 went out on 21 October 2026 at 14:05 UTC.
After it, order-read 95th percentile latency rose from 120 ms to 900 ms.
The request is to find the cause and name the next actions.

Relevance
Callers wait longer, and some requests fail with status 503.
The database is not the busy part, so restore the pool today.

Information
This section covers the evidence, the assumptions, and the alternative.

The acquire span is the change that matches the slow requests.
Its 95th percentile rose from 3 ms to 690 ms.
[1]
The full request rose from 120 ms to 900 ms in the same window.
[1]
Therefore 690 ms of the 900 ms tail is time spent on acquire.
[inference]

Order query 95th percentile moved from 52 ms to 58 ms.
[1]

[1]

[1]

[1]

[2]

[2]

[3]

[3]

[1]

[2]

[1]

[1]

The code now loads order lines with the order query.
[2]

[1]

Prior peak connections were 31, against a pool of 50.
[1]
Four pods with eight threads each means 32 workers.
[2]
A pool of 8 per pod has no room for a burst.
[judgment]
Two pods logged 8 connections in use within one second.
[3]
Therefore the service held more than 8 connections at that moment.
[inference]

A1. The peak of 8 connections is a per-pod figure, not a service total. Why not measured: traces.txt says "from this service", but two pods logged 8 in use at once. Validate by: sum connections by pod at 10:14 UTC on 22 October 2026. If wrong: raise the server cap to at least 40 before step 1.

A2. Each request holds one connection for both queries. Why not measured: no hold-time span is in traces.txt. Validate by: add a checkout-duration span for one hour. If wrong: the size target changes, but the wait is still the blocker.

Revert the ORM load and keep the pool at 8.
It loses because the line query got faster while acquire wait rose from 3 ms to 690 ms.
[1]

End
I recommend that we take these four actions.

1. Restore pool max_size from 8 to 50 and reload all four pods.
This removes the acquire queue, which is the largest blocker.
Test, written first:
Given the live pool max size is 8
When max size is 50 and all four pods have reloaded
Then acquire 95th percentile stays under 10 ms for 15 minutes
And pool timeout errors in that window are zero
Kind: deterministic.
Domain: Clear.
Reason: one known practice follows from the acquire span. The inference is deduction.

2. Restore cache default_ttl_s from 60 to 300.
Step 2 MUST NOT start until the test in step 1 passes.
This cuts extra database trips from the miss rise.
Test, written first:
Given cache life is 60 seconds and step 1 has passed
When cache life is 300 seconds
Then miss rate stays under 15% for the next hour
Kind: deterministic.
Domain: Clear.
Reason: miss rate moved with the life cut. The inference is deduction.

3. Read ticket OPS-412 and the server connection cap, then write both numbers in config/db.yaml.
This removes the risk that a later pool edit exceeds the server cap.
Analysis: compare the cap with 40, which is the prior peak of 31 plus headroom.
If the cap is under 40, raise the cap in that same session.
Test, written first. Rubric: cap recorded (weight 50, needs the ticket or server setting), cap at least 40 (weight 50, needs that same source). Pass threshold: 100.
Kind: evaluative.
Domain: Complicated.
Reason: an expert can read the cap from the ticket and the server. The inference is analysis.

4. Add an alert when acquire 95th percentile exceeds 20 ms for 5 minutes.
This catches the next pool squeeze before the tail hits 900 ms.
Step 4 may run in parallel with step 1.
Test, written first:
Given the alert rule is in the staging monitor
When a test series holds acquire at 25 ms for 6 minutes
Then the alert fires once
And it does not fire when the series stays at 5 ms
Kind: deterministic.
Domain: Clear.
Reason: the old acquire baseline was 3 ms. The inference is deduction.

Keep the acquire timeout at 5 s.
A return to 30 s would hide a full pool as long hangs.
Leave the order-line load in place.

Follow-up
If A1 is false, raise the server cap to at least 40 before step 1.
If the step 1 test fails, stop and measure connection hold time before any further pool change.
