Headline
Move auth to short-lived JSON Web Tokens in httpOnly cookies, and measure signup before any form change.
Server logout rules decide if a stateless token is acceptable.
Cookie transport keeps the current browser threat model.
Signup gains need a funnel baseline, not a token change.
A dual-run on login limits the blast radius.

Background
The request is to leave server sessions for JSON Web Tokens and to raise signup conversion.
A JSON Web Token is a signed claim set that a verifier can check from the signature alone.
These goals do not share a cause, so this plan splits them.

Relevance
A token that page script can read raises theft risk next to an httpOnly session cookie.
Therefore logout and revoke behavior must stay intact before any signup form test.

Information
RFC 7519 defines a JSON Web Token as a compact signed set of claims.
A verifier can check that signature without a session read.
[1]

RFC 8725 tells receivers to reject unexpected signing algorithms and to use short expiry.
[2]

A signed token still cannot be deleted on logout before expiry without a server check [judgment].
Signup completion and token format do not share a mechanism [judgment].
The cookie default is 70% likely, because the material does not name the clients.
High confidence applies only to the two RFC claims above, because both are primary texts.

Driving claims for the token shape are the two RFC claims.
Storage choice follows assumption A1, not a second source.

A1. The main client is a browser that already keeps the session in a cookie. Why not measured: The material does not state it. Validate by: Capture one login response and read Set-Cookie. If wrong: Replace the cookie design with a sender-constrained token for native apps.

A2. Logout deletes the server session before the next request. Why not measured: The material does not state it. Validate by: Read the logout handler for a session-store delete. If wrong: A stateless token is closer to current behavior.

A3. Conversion means completed accounts divided by signup page views. Why not measured: The material does not state it. Validate by: Confirm the event names with the product owner. If wrong: Retarget the probe metric.

A4. Policy allows up to 15 minutes before a revoked login dies. Why not measured: The material does not state it. Validate by: Read the session-lifetime rule in the security policy. If wrong: Keep a revoke store and do not drop server state.

Alternative considered: Ship long-lived bearer tokens in page storage and redesign the signup form in one release. It loses because that couples an irreversible client change to an unmeasured funnel [judgment].

End
I recommend that we take these four actions.

1. Test first. Rubric: logout deletes the session within 60 seconds, weight 30, evidence is the logout handler. Password reset kills old sessions, weight 25, evidence is the reset flow. Cookie flags block cross-site request forgery, weight 25, evidence is the Set-Cookie flags. A session list exists per user, weight 20, evidence is the session table. Pass is 80 of 100, and each scored item has evidence. Increment: fill this rubric for one login path and one logout path. Blocker removed: unknown session guarantees. Domain: Complicated, because an expert can pick the practice from this data by deduction from the rubric.

2. Step 2 MUST NOT start until Step 1 passes. Test first. Use a Pugh matrix with the current server session as the datum. Criteria: logout effect within 60 seconds, weight 30. No new page-readable secret, weight 25. No session read on each call, weight 25. Change stays in one service, weight 20. Pass: the winner beats the datum, or we keep sessions. Increment: score three concepts in one session. The concepts are keep sessions, httpOnly cookie token with 15 minute access plus refresh rotation, and a bearer token in page storage. Blocker removed: no chosen token practice. Domain: Complicated, because this analysis selects the practice by deduction from the Step 1 scores.

3. Step 3 MUST NOT start until Step 2 passes. Test first.
Given a test user with a valid password
When the user calls login
Then the response sets an httpOnly Secure cookie
And the cookie value checks as a JSON Web Token
And expiry is at most 15 minutes
And the old session cookie still works
Increment: change only the login route, in one session. Blocker removed: no proven issuer beside the old session. Domain: Clear, because Step 2 leaves one known practice and this step applies it by deduction from that rule.

4. Run this probe in parallel with Steps 1 to 3. Do not order it by claimed gain. Test first. Metric: completed accounts divided by signup page views. Baseline: the rate over the last 14 days, with at least 1,000 page views. Pass for instrumentation: start, submit, verify, and complete are present for 99% of a 50-event sample. Only then change one field or one step. Accept the change only if completion rises by 2 percentage points at 1,000 views and the error rate does not rise. Budget: one form change and one engineer-day. Stop if signup errors rise by 1 percentage point over baseline. Increment: add the four events, then one form probe. Blocker removed: no funnel baseline. Domain: Complex, because the result shows only after the trial, by induction from the 14-day rate. A campaign or a sample under 1,000 can break that pattern.

If A1 is false, replace the Step 2 cookie concept with a sender-constrained token for native apps.
If A4 is false, Step 2 must not pick a design that has no revoke store.
If the 14-day sample is under 1,000 views, keep the instrumentation and do not run the form probe.

Follow-up
No open question. The assumptions above already set the default path.
Conditions that change the recommendation are the three If lines in End.
