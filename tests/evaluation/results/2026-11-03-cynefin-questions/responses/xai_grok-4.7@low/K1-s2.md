Headline
The p95 rise is pool wait, not slow SQL. The acquire span grew from 3 ms to 690 ms and now dominates the 900 ms p95. Query spans and database CPU stayed near the prior baseline. A pool cut from 50 to 8, a 5 s acquire timeout, and a cache TTL cut from 300 s to 60 s explain the queue.

Background
Release 2026.10.21 deployed on 21 October 2026. It changed the pool, the cache TTL, and the order load. Peak rate stayed near 405 requests per second, but p95 latency rose from 120 ms to 900 ms.

Relevance
Order reads are slow, and timeouts now drive most errors. A config change can cut the queue before any ORM rollback.

Information

A2. The new database limit is 8 connections for the whole service. Why not measured: the trace does not define that metric's scope. Validate by: count sessions on the database, grouped by pod. If wrong: restore max_size to 50 per pod instead of adding a pooler.
A3. One session holds the connection for both queries. Why not measured: the diff does not show session scope. Validate by: one trace with connection id on both query spans. If wrong: the hold time is shorter, so a pooler helps less.
Alternative considered: roll back selectinload first. It loses because query time and database CPU did not rise, while acquire time did [3].
