# Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` because it is a fast metadata-only change in Postgres, but check dependent code, views, and foreign keys first since the rename itself does not update them.

- One SQL statement completes the rename in milliseconds (metadata change, no table rewrite).
- Application code and views that reference `user_id` will fail after the rename, so coordinate the deploy.
- Indexes and foreign key constraints keep working automatically because they follow the column by internal ID.

## Background

You are boarding a plane and want the column `user_id` in the `orders` table renamed to `account_id` in a PostgreSQL database. This is a single schema change.

## Relevance

The rename itself is quick and safe, but anything reading the old column name breaks the moment it runs. Doing this right before losing connectivity carries risk if dependent code exists.

## Information

The command:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Evidence and notes:

- Cost: the rename takes only a brief `ACCESS EXCLUSIVE` lock and rewrites no rows, so it finishes in milliseconds even on a large table [inference, well-documented Postgres behavior].
- Automatic: indexes, constraints, triggers on the column, and foreign keys referencing it keep working; they track the column internally, not by name [judgment].
- Not automatic: views, stored functions, and application code that mention `user_id` by name must be updated separately [judgment].
- Check dependents first with: `SELECT * FROM information_schema.views WHERE view_definition ILIKE '%user_id%';`

**Alternative considered:** creating a new column and backfilling (zero-downtime pattern). It loses because it needs a migration, dual writes, and backfill time; overkill for a fast rename when a brief lock is acceptable.
