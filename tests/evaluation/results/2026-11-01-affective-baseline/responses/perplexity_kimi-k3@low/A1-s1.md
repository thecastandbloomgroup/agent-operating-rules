Headline

Pin every dependency in requirements.txt to an exact version, and add automated update checks. 
1. Two build breaks last month trace to unpinned versions.
2. Exact pins make builds reproducible.
3. Automated checks keep security fixes flowing without surprise breaks.

Background

The project keeps all dependencies unpinned in requirements.txt. The build broke twice last month after upstream library releases. The question is whether to pin versions.

Relevance

Each unpinned release is a rerun of last month's outage. Reproducible builds are also a baseline requirement in common secure supply chain guidance [1].

Information

Evidence: two build breaks in one month after library updates (user report, this session). Pinning is the standard defense against this failure mode. NIST guidance on securing software supply chains calls for reproducible builds and identified dependencies [1]. PEP 440 defines the exact pin syntax, for example `requests==2.32.3` [2]. The trade-off: pinned versions miss security patches. Therefore add an automated updater (Dependabot or Renovate, or a scheduled pip-audit run) so updates arrive as tested pull requests instead of silent breakage [3].

Assumption log:

A1. The project uses pip and PyPI packages. Why not measured: the material names requirements.txt only. Validate by: check the repository for setup.py, pyproject.toml, or environment.yml. If wrong: the pin syntax changes but the recommendation stays.

A2. The team has CI that runs the build on pull requests. Why not measured: the material does not state it. Validate by: look for a CI config file, one command. If wrong: add a CI step before the auto-updater, or updates merge untested.

Alternative considered: pin only major versions (for example `requests>=2,<3`). It reduces breakage risk but still allows unreviewed minor releases into the build; the two breaks last month show partial pins did not protect this project, so exact pins win [judgment].

End

I recommend that we take these actions:

1. Pin every direct dependency to its exact version in requirements.txt and commit it. This removes the uncontrolled-update blocker. Cynefin domain: Clear, because pin syntax is a known best practice. Test (deterministic):
Given a fresh virtual environment,
When `pip install -r requirements.txt` runs twice on different days,
Then both installs produce identical package versions and the test suite passes.

2. Generate and commit a lock file with hashes via `pip-compile --generate-hashes` (pip-tools). This adds tamper detection and transitive-dependency pinning. Cynefin domain: Clear, because pip-tools documents a fixed procedure [4]. Test (deterministic):
Given the lock file,
When `pip install --require-hashes -r requirements.txt` runs,
Then installation succeeds and hash verification passes.

3. Enable Renovate or Dependabot for the repository so updates arrive as pull requests. This keeps security patches flowing. Cynefin domain: Clear, because GitHub documents the setup [3]. Test (deterministic):
Given the bot config on the default branch,
When a dependency releases a new version,
Then a pull request opens and CI runs against it.

4. Add a scheduled `pip-audit` job to CI for vulnerability scanning. This covers the security gap of pinned versions. Cynefin domain: Clear, because the tool runs against PyPI advisories directly [5]. Test (deterministic):
Given a pinned dependency with a known advisory,
When the audit job runs,
Then the job fails and names the advisory.

Sequencing: Step 1 first, it stops the next outage. Steps 2, 3, and 4 follow in order. Step 3 MUST NOT merge automatically; updates merge only after the test in Step 1 passes in CI.

If A2 is false, insert a CI build step before Step 3.

Follow-up

Conditions that change the recommendation: if the package is a library published to PyPI, keep requirements.txt pinned for development but use ranges in the package metadata instead.
