# Headline

Yes, pin every dependency with fixed versions in requirements.txt. First, a pinned file makes each build reproducible, so a library update cannot break it [judgment]. Second, two build failures in one month shows the current un-pinned setup already failed twice. Third, a scheduled upgrade process keeps security fixes flowing after pinning.

## Background

Your requirements.txt lists no versions. Upstream releases changed the environment under running builds. The build broke twice last month after library updates.

## Relevance

Each break costs developer time and blocks delivery. Pinning stops this failure mode at its root. It also creates a known baseline for rollback.

## Information

Reproducible builds are a standard practice: a lock or pinned file fixes the environment so builds repeat [1]. Un-pinned installs resolve to the newest release, so two installs at different times produce different artifacts [1]. The local evidence agrees: two failures in about 30 days, both after upstream updates (user report). Numbers and reported history agree, so confidence is high.

Python's native answer is exact pins ("==") in requirements.txt, or a compiled lock file from pip-tools or uv [1]. The strongest alternative is range pins such as ">=1.2,<2". It loses because ranges still resolve to new releases between builds, so builds still differ [judgment].

**Assumption log**

A2. Direct dependencies are the main source of breakage, not transitive ones. Why not measured: the material does not state it. Validate by: run `pip freeze` on a working build and compare. If wrong: freeze all transitive dependencies too.

## End

I recommend that we take these steps:

1. Run `pip freeze` from a known-good environment. Write the output into requirements.txt with one exact pin per line. This removes the blocker of unknown working versions. It is a deterministic action in the Clear domain, because the fix is a known best practice.
   - Given a requirements.txt with no pins, when a developer runs `pip freeze` in the working environment and saves the output, Then every line in requirements.txt contains one "==" version.
2. Add a CI step that builds from a clean environment using only the pinned file. This adds the capability to prove reproducibility. It is deterministic, Clear domain, one known step.
   - Given only the pinned requirements.txt and a clean container, when CI installs and runs the full test suite, Then the build passes with no network-resolved versions.
3. Add a scheduled job, weekly, that creates a pull request with updated pins and runs the test suite. This removes the risk of stale dependencies and missed security fixes. It is stochastic because upstream output varies: accept the update when all tests pass on that pull request; sample size is one full test run per candidate update. Clear-to-Complicated domain; the practice is known, but each update needs its own test pass.
4. Record the last known-good lock in version control so any failed update rolls back in one step. This adds a rollback capability. Deterministic, Clear domain.
   - Given a merged lock file, when a build fails after an update, Then reverting that one file restores the previous passing build.

Step 2 MUST NOT start until the test in Step 1 passes. Steps 3 and 4 can run in parallel after Step 2.

## Follow-up

Conditions that change the recommendation: if A1 is wrong, replace "pip freeze" with the lock command of the actual tool. If A2 is wrong, switch to a fully hashed lock such as `pip-compile --generate-hashes` [1].
