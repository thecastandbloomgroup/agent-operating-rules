## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` now: the rename is instant in Postgres, but first run a dependency check, then fix any view or query that reads `user_id`. Supporting points:

1. The rename is a metadata-only change. It does not rewrite the table, even on a large table [19].
2. Indexes and foreign key constraints on the column stay attached after the rename [19].
3. Views that reference `user_id` do not follow the rename. They break at next use, so check for them first [19].

## Relevance

A dependent object or a running service that reads `user_id` will fail right after the rename. The check below takes seconds and prevents that.

## Information

Run this first to list views that depend on `orders`:

```sql
SELECT DISTINCT source.relname AS dependent_view
FROM pg_depend d
JOIN pg_rewrite r ON r.oid = d.objid
JOIN pg_class source ON source.oid = r.ev_class
JOIN pg_class target ON target.oid = d.refobjid
WHERE target.relname = 'orders'
  AND d.deptype = 'n';
```

Then run the rename:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

The rename takes an exclusive lock on the table only for the instant it changes the catalog entry. Its runtime does not scale with table size [P: 19]. The reverse rename is also instant, so rollback is cheap [inference: from the same metadata-only behavior, 19].
