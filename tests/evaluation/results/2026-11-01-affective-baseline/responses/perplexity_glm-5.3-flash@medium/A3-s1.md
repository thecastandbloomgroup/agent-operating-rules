Yes, turn on gzip; at an average of 400 KB per JSON response, compression cuts the transfer size by a factor of 5 to 10, and it needs no change on the client side.

Gzip works well on JSON text because JSON repeats key names and numeric formats. The cost is CPU time on the server for each compressed response. Support is broad: the HTTP standards define `Accept-Encoding` on the request and `Content-Encoding` on the response [1], and gzip is the one content coding that nearly every client and server ships with.

Here is the reasoning. Your current baseline is 400 KB per response on the wire. Comparable JSON payloads typically compress to 40 to 80 KB with gzip levels 4 to 6 [judgment]. For a client on a 10 Mbit/s link, that change reduces transfer time from about 320 ms to 32 to 64 ms per call, before accounting for connection setup [inference]. The added CPU cost per response stays small at level 4, which is the common default for dynamic content [judgment]. The gain is largest for mobile clients and smallest for callers inside the same data center.

Apply three conditions when you enable it. First, compress only responses above 1 KB, because small bodies gain less than the header overhead costs. Second, do not compress payloads that are already compressed, such as images or zip files. Third, read the client header, not the path, to decide whether to compress.
