# Headline

Pin the versions: put exact pins (`==`) on every direct dependency, and generate a lock file for the transitive (indirect) dependencies.

- Unpinned builds drift: two identical installs can produce different result sets.
- After a pin, an update becomes a deliberate, tested action instead of an accident that ships on its own.
- A lock file keeps the difference between "direct" and "transitive" clean, so updates stay controlled.

# Background

The team keeps a requirements.txt with no versions pinned. The build broke two times last month after a library update [1].

# Relevance

The next build can break again at any time, because any install can pull a new version today. Pinning removes this trigger before the next release.

# Information

Evidence:

- Build breaks: 2 incidents in the last month, seconds after library updates [1]. Baseline for the recommendation: 0 incidents per month, so the measured rate is 2 versus 0, and the gap drives the action.
- Root cause: unpinned requirements let a build resolve to a newer release than the one that passed the last test run. Rebuilds are therefore not reproducible [judgment].
- Direction of evidence: the number (2 breaks after updates) and the theme (uncontrolled resolution) agree, so confidence in the diagnosis is high, based on the reported failure pattern [1] [judgment].

Assumption log:

- A1. The breakages came from a newer resolved version, not from team code that changed the same week. Why not measured: the failure logs are not in the conversation. Validate by: read the two failure logs and check the install lines. If wrong: pinning direct versions still removes the drift path, but add an upper bound review for_conflicting transitive versions.

Alternative considered: leave requirements.txt loose and only pin after a break. This loses, because it keeps the 2 breaks per month as the baseline control and turns every future update into an emergency.

# End

I recommend that we take these four actions:

1. Pin every direct dependency in requirements.txt with `==` and its current working version. Blocker removed: silent version drift on installs. Test (deterministic, write it first):
   ```gherkin
   Given a requirements.txt with one unpinned entry "flask"
   When the install resolves dependencies
   Then every direct entry carries an exact "==" version string
   ```
   Cynefin domain: Clear, because a known best practice applies in one step [2].

2. Generate a lock file with a resolver tool (pip-compile) and install only from it. Blocker removed: uncontrolled transitive (transitive = indirect) dependency drift. Step 2 waits for Step 1. Test (deterministic, write it first):
   ```gherkin
   Given a lock file generated from the pinned direct dependencies
   When a fresh environment installs from the lock file
   Then the installed version set matches the lock file
   ```
   Cynefin domain: Complicated, because choosing the resolver output format needs a short analysis of the tool options [2].

3. Add a CI check that installs from the lock file in a clean environment and runs the test suite before merge. Blocker removed: untested version changes reaching the build. Step 3 waits for Steps 1 and 2. Test (deterministic, write it first):
   ```gherkin
   Given a clean environment and the lock file
   When CI installs and runs the suite before merge
   Then merge proceeds only after the suite passes at 100% of its cases
   ```
   Cynefin domain: Clear, one known step [2].

4. Run a monthly update cycle: bump the pins, run the suite, and pin again the same day. Blocker removed: old pins that accumulate risk over time. Run in parallel with Steps 1 to 3. Probe budget: one session per month. Measure: build breaks per month, baseline 2 [1], pass threshold 0. Stop condition: revert the month's version bump and retry with one library at a time if the suite fails twice in a row. Cynefin domain: Complex, because the effect of each new version set is visible only after the run [2].

# Follow-up

- A1 changes the recommendation only in Step 1's scope: if the logs show a transitive cause, also pin the named transitive packages in the lock file.
- Condition that changes the plan: if the team ships a library to outside users as a package (not an application), switch from exact direct pins to compatible upper and lower bounds, because a library must not-fixed force its own pins on consumers [judgment].
- Questions (question 1 of 3): Was the library that broke the build in last month's two incidents a direct entry in requirements.txt or a transitive one? The answer decides whether Step 1 alone closes both incidents or the lock file carries the fix.
