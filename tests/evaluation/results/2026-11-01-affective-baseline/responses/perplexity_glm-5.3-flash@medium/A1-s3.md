## Headline

Yes, pin exact versions for every package in requirements.txt.

- Exact pins reproduce the last known-good build, so the environment changes only when we decide it changes.
- Unpinned installs pull the newest matching version at build time [1], so the environment can break without a code change.
- Pin transitive dependencies too, because their upgrades enter the build the same way.
- Keep a scheduled, tested upgrade path so pinning does not freeze old, buggy code.

## Background

The requirements.txt has no version pins. Two builds broke last month after a library update [2].

## Relevance

A build can now fail because of another version's release, not because of our code. The same failure will repeat with every update.

## Information

**Evidence**

- pip installs the newest version that satisfies each declared constraint, so an unpinned entry can change between two builds with no change from us [1].
- Two build failures occurred within the last month after a library update [2]. This matches the upgrade mechanism above. The two failures and the mechanism point to the same cause, so confidence is high that exact pinning removes this failure class [3].
- Exact pins and version specifiers have a defined syntax in requirements files [4].

**Assumption log**

**Alternative considered**

Range constraints, for example requiring version 1.4 or higher but below 2.0, instead of exact pins. This loses because ranges still admit new minor versions at build time, and the observed breakages happened when a new version entered the build [2], [3].
