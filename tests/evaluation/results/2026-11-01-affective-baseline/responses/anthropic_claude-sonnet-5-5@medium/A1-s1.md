## Headline

Yes, pin the versions, and pin every package, including the ones your libraries install.

- Unpinned installs fetch the newest release on each build, so any upstream change can break the build.
- An exact lock file makes every build install the same versions.
- Updates then happen on purpose, in a reviewed change, not by surprise.

## Background

Your requirements.txt has no pinned versions. The build broke twice last month after a library update [1]. The request is a decision: pin or do not pin.

## Relevance

The next unpinned build can break again. Each break costs team time and blocks releases.

## Information

Terms used here:
- To pin means to fix a package to one exact version, for example `requests==2.32.3`.
- A transitive dependency is a package that one of your libraries needs.
- A lock file is a requirements file where every package, including transitive ones, is pinned.
- CI means continuous integration, the server that builds and tests each commit.

Evidence:
- Two build breaks in one month, both after a library update, both with unpinned requirements. This is a primary report.

## End

I recommend that we take these steps in order:

1. **Create a lock file.**
   - Increment: in a clean virtual environment built from the last good commit, run `pip freeze > requirements.lock` and commit the file.
   - Blocker removed: unknown versions in each build.
   - Kind: deterministic. Domain: Clear, because pinning is an established best practice.
   - Test, written first:

   ```text
   Given a clean virtual environment built from the last good commit
   When we run pip freeze into requirements.lock
   Then every package line uses "==" with an exact version
   And a fresh install from requirements.lock passes the test suite
   ```

2. **Make CI install only from the lock file.** Step 2 MUST NOT start until the test in Step 1 passes.
   - Increment: change the CI install command to `pip install -r requirements.lock`.
   - Blocker removed: CI still fetches new versions.
   - Kind: deterministic. Domain: Clear, because the change is one known command.
   - Test, written first:

   ```text
   Given requirements.lock is committed
   When CI runs on a new commit
   Then CI installs only from requirements.lock
   And the build passes with no new package versions fetched
   ```

3. **Run a four-week probe of a weekly update routine.** Start it after Step 2. It runs in parallel with later work.
   - Increment: each week, update the lock file in one branch, run the tests, and merge if they pass.
   - Capability added: planned updates, so security fixes still arrive.
   - Kind: stochastic. Domain: Complex, because the effect of the cadence on the team shows only afterward. Leverage is a guess.
   - Budget: 1 hour per week. Stop condition: more than 2 failed update branches in one week. Then switch to a monthly cadence.
   - Acceptance test, written first: metric is builds broken by dependency updates. Baseline is 2 per month [1]. Pass threshold is 0 over 4 weeks. Sample size is 4 weekly update branches.
