## Headline

Yes, pin the versions, and pin the indirect dependencies too.

- Unpinned versions let a library update change the build without a code change, which matches both breaks last month.
- A pinned file makes every build install the same versions, so a failure points to your own change.
- Updates still need to happen, so move them into a scheduled, tested step.

## Background

The project lists libraries in requirements.txt without version numbers. The build broke twice last month after a library update [1]. The question is whether to pin versions.

## Relevance

Each break stops the team until someone finds the cause. Pinning removes that cause at a low cost.

## Information

**Evidence**

- The build broke 2 times in 1 month. The baseline with pinned versions is 0 update-caused breaks [judgment]. Source: user message [1].
- The pip documentation says requirements files can hold the output of `pip freeze` for repeatable installs. This is a vendor source, so it is secondary.

  Source: [2]
- A transitive dependency is a library that your library installs. Pins on direct libraries alone leave transitive dependencies free to change [inference].
- The compatible-release operator (`~=`) allows later patch or minor releases, so it still permits change.

  Source: [3]
- Pinning stops update-caused breaks: very likely (90 to 100%), because both breaks followed an update (see A1).

A2. This is an application, not a library for others to install. Why not measured: the material does not state it. Validate by: check whether the project publishes a package. If wrong: pin in a lock file and keep ranges in the package metadata.

A3. The team has a continuous integration (CI) system that builds on each change. Why not measured: the material does not state it. Validate by: open the CI settings. If wrong: run the Step 1 and Step 3 tests by hand in a clean environment.

**Alternative considered**

Keep versions unpinned and use `~=` ranges. It loses because ranges still admit new releases, and two breaks in one month show the cost [judgment].
