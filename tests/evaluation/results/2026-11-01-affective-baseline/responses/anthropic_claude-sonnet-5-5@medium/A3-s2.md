Yes, turn on gzip for the API, because it should cut each 400 KB response by about 70 to 90% at a small CPU cost.

- Payload size: JSON is repetitive text, so gzip shrinks it well [judgment].
- Cost: compression adds a few milliseconds of CPU per response, which a canary rollout can confirm.
- Risk: the main failure modes are double compression and broken caches, and both have cheap tests.

The API returns JSON with an average size of 400 KB. The question is whether to enable gzip, a lossless compression format defined in RFC 1952, on those responses.

Large responses slow every client on a limited link. At 10 Mbit/s, 400 KB takes about 0.32 s to send. At 60 KB (85% smaller), it takes about 0.05 s [judgment]. Mobile and remote clients gain the most.

On evidence: the HTTP standard lets a server compress a response when the client sends an Accept-Encoding header, and the server then sets Content-Encoding.

The strongest alternative is to shrink the payload itself, for example with pagination or field filtering. That option removes more bytes, but it changes the API contract and needs client changes. Gzip needs none, so it goes first. The two options do not conflict.

I recommend that we:

1. Enable gzip for the application/json content type at the proxy or CDN, with a minimum size of 1 KB and level 5. Increment: one configuration change in staging.
