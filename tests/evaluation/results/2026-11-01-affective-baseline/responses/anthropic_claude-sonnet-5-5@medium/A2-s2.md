## Headline

Run one `ALTER TABLE` statement, but deploy it together with the application code change, and not right before you board.

- The SQL is one line, and it takes a brief exclusive lock on the table [1].
- Application queries that use `user_id` fail the moment the rename commits.
- Views follow the rename, but function bodies and application code do not [judgment].

## Background

The request is to rename `user_id` to `account_id` in the `orders` table of a Postgres database. The material does not name the environment, the Postgres version, or the code that reads the column. The rename itself is simple.

## Relevance

The rename takes effect at once. If you run it in production and then board, any query that still uses `user_id` fails until you return. [judgment]

## Information

Evidence:
- Postgres documents `ALTER TABLE ... RENAME COLUMN` as a metadata change, with no table rewrite. The statement needs an ACCESS EXCLUSIVE lock.

[1]

- Indexes and constraints on the column stay valid after the rename. Their names do not change [inference].

Assumption log:

A1. The database is production, and application code references `user_id`. Why not measured: the material does not state it. Validate by: search the code repository for `user_id`. If wrong: the rename is safe to run at once.

A2. No other table has a foreign key that must also be renamed. Why not measured: no tool can reach the schema. Validate by: run `\d orders` in psql. If wrong: add matching renames for those columns, if wanted.

Alternative considered: add `account_id` as a new column, copy the data, and drop `user_id` later. This route has no downtime, but it takes several steps and a sync trigger. It loses because a rename is one step and the lock is short [judgment].

SQL to run:

```sql
BEGIN;
SET LOCAL lock_timeout = '3s';
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
COMMIT;
```

The `lock_timeout` setting makes the statement fail fast instead of queueing behind a long query.
