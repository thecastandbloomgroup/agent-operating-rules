## Headline

Yes, pin every version in requirements.txt, including indirect libraries.

- Unpinned installs pull the newest release on each build, so any upstream change can break the build [1].
- Exact pins make builds repeat, so a change in versions happens only when the team chooses it [2].
- Pins need a routine for upgrades, otherwise the project falls behind on security fixes.

## Background

The project has a requirements.txt with no pinned versions. The build broke twice last month after a library update [1]. The question is whether to pin the versions.

## Relevance

Each break stops the team from shipping until someone finds the cause. Pinning removes the main cause of these breaks at low cost.

## Information

Evidence:

- Two build breaks in one month, both after library updates (user report, baseline: no breaks stated before) [1].

- pip installs the newest matching release when no version is given. Pinned exact versions give repeatable installs [2].

- Indirect libraries (a transitive dependency is a library that your library needs) also change. A pin on direct libraries alone leaves this risk open [2].

- Confidence that pinning stops this failure type: high confidence. Basis: the failure mechanism is documented [2] and matches the reported pattern [1].
