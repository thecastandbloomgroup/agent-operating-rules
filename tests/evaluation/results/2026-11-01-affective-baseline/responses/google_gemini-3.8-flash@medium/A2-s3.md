# Headline

Do not execute an immediate in-place column rename on the production database before your flight.

- An immediate rename breaks running application queries that expect the old column name [1].
- PostgreSQL acquires an access exclusive lock on the table during a column rename [1].
- A safe column migration requires an expand and contract pattern across deployment phases [2].

# Background

You requested an immediate rename of column user_id to account_id in the orders table. You also stated that you are about to board an airplane. This timing prevents you from monitoring the production system after the schema change.

# Relevance

An uncoordinated schema change causes immediate application errors for active users. Therefore, you need a safe execution plan that avoids production outages while you are offline.

# Information

The direct command to rename a column in PostgreSQL is straightforward [1]:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

However, executing this command directly on an active database creates two risks. First, PostgreSQL acquires an `ACCESS EXCLUSIVE` lock on the `orders` table [1]. This lock blocks all concurrent reads and writes until the transaction completes [1]. Second, existing application code continues to reference `user_id` [judgment]. When the column disappears, all running queries that reference `user_id` fail immediately [2].

Industry practice uses the expand and contract pattern for zero downtime schema updates [2]. That pattern first adds support for the new column, syncs data, updates code, and then removes the old column [2].
