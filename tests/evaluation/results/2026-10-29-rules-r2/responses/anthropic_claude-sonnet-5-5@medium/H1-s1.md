Roll back the newest change made near 09:12, then brief the execs with facts, not a cause.

- The sudden start of 500 errors for all users points to one trigger. [inference]

## Background

Checkout returns HTTP 500 for every user since 09:12. You are the on-call engineer. The exec call starts in ten minutes.

## Relevance

Each minute of downtime blocks all checkout revenue. The exec call sets the tone for the incident, so a clear status matters now.

## Information

**Evidence**
- A failure that hits 100% of users at a fixed time is about 70% likely to come from a change, such as a deploy, a config edit, or a flag [judgment].
- The other causes are a failed dependency (database, payment provider, certificate) or a capacity limit [inference].
- Quick-recovery guidance puts the domain as Chaotic: act to stabilise first, then analyse [1].

**Assumption log**
A1. A change shipped near 09:12. Why not measured: the material does not state it. Validate by: read the deploy log and flag history for 09:00 to 09:12. If wrong: skip Step 1 and go to Step 3.
A2. A rollback path exists and works. Why not measured: no tool can reach it from here. Validate by: run the rollback command in dry-run mode. If wrong: disable the new feature flag instead.
A3. A second engineer is reachable. Why not measured: the material does not state it. Validate by: send one page. If wrong: do Step 1 alone and send a short text update.

**Alternative considered**
Debug the error logs first to find the root cause. It loses because diagnosis takes longer than rollback, and rollback is reversible [judgment].

## End

I recommend that we take these four actions in this order:

1. **Roll back the latest change.**
   - Increment: one rollback or flag-off, about five minutes.
   - Blocker removed: the outage itself.
   - Domain: Chaotic. Stabilise first.
   - Kind: deterministic. Test written first: Given checkout returns 500 for a test order, When the latest change is reverted, Then the same test order returns 200 within five minutes.
   - Step 2 MUST NOT start until you start this rollback. Steps 2 and 3 MAY run while it completes.

2. **Page a second engineer.**
   - Increment: one page with the text "Checkout 500s since 09:12, rolling back, need eyes on logs."
   - Blocker removed: you are alone on both the fix and the call.
   - Domain: Clear. Follow the escalation rule.
   - Kind: deterministic. Test: Given the page is sent, When two minutes pass, Then someone acknowledges it. If not, page the next person.

3. **If the rollback does not restore checkout, check dependencies.**
   - Increment: read the top error in the logs and the status of the database and the payment provider.
   - Blocker removed: no known cause.
   - Domain: Complicated. The log analysis picks the fix.
   - Kind: evaluative. Rubric written first: score each suspect on error match (weight 50%), start time match (30%), and fix speed (20%). Pass threshold: 70%. Evidence: a log line, a status page, a timestamp.
   - This step MUST NOT start until the Step 1 test fails.

4. **Brief the execs with a three-line status.**
   - Increment: write three lines before the call.
   - Blocker removed: no agreed facts for the call.
   - Domain: Clear. A status template exists.
   - Kind: evaluative. Rubric written first: the text states impact (all users, checkout, since 09:12), current action, and next update time. Each item is worth one point. Pass threshold: 3 of 3.
   - Example: "Checkout fails for all users since 09:12. We are rolling back the latest change. Next update at 09:45."
   - Do not name a root cause until you confirm it.

**Follow-up**
- Condition that changes this plan: if A1 is false, replace Step 1 with Step 3.
- Condition that changes this plan: if the rollback restores checkout, tell the execs the status is "recovering" and keep the incident open until errors stay at zero for 15 minutes [judgment].
