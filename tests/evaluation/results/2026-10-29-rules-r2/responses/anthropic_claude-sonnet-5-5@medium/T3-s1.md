## Headline

Run two separate tracks: measure sign-up first, migrate to JWT behind a flag, and test one sign-up change at a time.

- The two goals share the sign-up path, so one release must not carry both changes.
- A JWT (JSON Web Token, a signed token that holds user claims) removes the session lookup but adds a revocation problem, so a design check comes before code.
- The request gives no conversion baseline, so measurement comes first.
- Conversion work is an experiment, so it needs a stop rule and a budget.

## Background

You ask to move the auth service from server sessions to JWT. You also ask to raise sign-up conversion, that is, the share of visitors who finish sign-up. The request gives no stack, no traffic figures, and no current conversion rate.

## Relevance

Both changes touch the login and sign-up path. If both ship together and conversion drops, you cannot tell which change caused the drop.

## End

I recommend that we take these steps in order:

1. **Instrument the sign-up funnel and record a 7-day baseline.**
   - Increment: add three events (page view, form submit, sign-up done).
   - Blocker removed: no baseline exists, so no later result can be judged.
   - Kind: deterministic. Domain: Clear.
   - Test, written first:

   ```gherkin
   Given a visitor opens the sign-up page
   When the visitor submits a valid form
   Then the event "signup_completed" is stored with the visitor id
   And the funnel report shows the rate at each step
   ```

2. **Score the JWT design against the current sessions.**
   - Increment: one Pugh matrix with sessions as the baseline. Include token lifetime, refresh rotation, and the revocation method.
   - Blocker removed: the revocation gap in the design.
   - Kind: evaluative. Domain: Complicated. The analysis in this step picks the practice.
   - Rubric, written first. Score each criterion 0 to 5 with evidence. Weights: revocation speed 30, security 30, rollback 20, latency 10, effort 10. Pass: weighted score of 3.5 or more, and no criterion below 2.
   - Step 3 MUST NOT start until this rubric passes.

3. **Move one endpoint to JWT behind the flag, with both methods accepted.**
   - Increment: the profile endpoint only.
   - Capability added: a safe path with instant rollback.
   - Kind: deterministic. Domain: Complicated.
   - Test, written first:

   ```gherkin
   Given a user with a valid legacy session cookie
   When the user calls the profile endpoint
   Then the service returns 200
   Given a user with a valid JWT
   When the user calls the profile endpoint
   Then the service returns 200
   Given a user with an expired JWT
   When the user calls the profile endpoint
   Then the service returns 401
   ```

4. **Run one safe-to-fail probe: remove one field from the sign-up form.**
   - Increment: one A/B test on one change.
   - Capability added: evidence on what moves conversion. The leverage of this probe is a guess.
   - Kind: stochastic. Domain: Complex.
   - Acceptance test, written first:
     - Metric: sign-up completion rate.
     - Baseline: the Step 1 rate.
     - Pass: a gain of 2 points or more [judgment].
     - Sample size: compute per group from the Step 1 rate, at 80% power and a 5% significance level [judgment].
     - Stop: end the test if the test group falls 3 points below control after 1,000 visitors per group.
     - Budget: 14 days and 10% of traffic.
   - Step 4 MUST NOT start until Step 1 has 7 days of data.
   - Step 4 MUST NOT ship in the same release as a Step 3 change to the sign-up path.
   - Step 4 MAY run in parallel with Steps 2 and 3 when A4 is true.
