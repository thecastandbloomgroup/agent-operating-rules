## Headline

Measure first, then improve: build a small error log and test set before you change the summariser.

- You cannot tell whether a change helps, because the tool has no metrics today (per the query).
- "Sometimes wrong" is vague, so the error types must be named before you pick a fix.
- Agent feedback and a fixed test set are cheap and give a baseline within days.
- Prompt changes come last, as capped trials checked against that baseline.

## Background

Your team added a summariser built on a large language model (LLM) to the support tool. Agents say it is "sometimes wrong". No metric exists, and you want better results.

## Relevance

Each wrong summary can send an agent to the wrong action on a ticket. Without a number, you cannot show that any change helps.

## Information

Evidence:

- Agents report errors, but no rate, type, or severity exists (per the query).
- The output of an LLM varies from run to run [judgment]. One test run is therefore not enough.
- With 100 test tickets and a true error rate of 10%, the 95% interval is about plus or minus 6 points [inference]. That is, 1.96 × √(0.10 × 0.90 / 100) ≈ 0.059.
- Grouping agent comments into themes finds the main error types [3]. Count the sources behind each theme.

Assumption log:

A1. Each summary links to its ticket in storage. Why not measured: the material does not state it. Validate by: query one summary by ticket ID. If wrong: add logging first, in Step 2.

A2. At least 50 agents' comments or flagged cases can be collected in one week. Why not measured: the material does not state ticket volume. Validate by: count summaries made per day. If wrong: extend the Step 1 window.

A3. Wrong facts (names, dates, amounts, actions taken) matter more than style. Why not measured: the user has not answered. Validate by: ask three agents to rank error types. If wrong: change the rubric weights in Step 3.

Alternative considered: switch to a larger model at once. It loses because you cannot measure the gain, and cost rises before you know the error type [judgment].

## End

I recommend that we:

1. **Classify the errors (Confused, evaluative).** Increment: collect 50 summaries that agents call wrong, then label each with an error type. Blocker removed: "sometimes wrong" has no definition. Test: write a rubric first. Criteria are fact error, missing key point, wrong tone, and wrong next action. Weights are 40, 30, 10, 20. The pass threshold is that every case gets one label, and two reviewers agree on at least 80% of the labels. Step 3 MUST NOT start until this test passes [1].

2. **Add a feedback button (Clear, deterministic).** Increment: one "Wrong" button with a reason list on each summary. Blocker removed: no ongoing data. Test, written first:
   - Given an agent views a summary
   - When the agent clicks "Wrong" and picks a reason
   - Then the system stores the summary ID, ticket ID, reason, and time

   Run this step in parallel with Step 1.

3. **Build a test set and a baseline (Complicated, stochastic).** Increment: 100 real tickets with agent-checked facts, run three times on the current prompt. Blocker removed: no baseline. Test, written first: the metric is the share of summaries with at least one fact error. The baseline comes from this step. The pass threshold is a relative cut of at least 50% in Step 4. The sample size is 100 tickets × 3 runs. Use the Step 1 error types to choose the checks, per ISO/IEC 25010 correctness [2].

4. **Run two prompt trials (Complex, stochastic probe).** Increment: change the prompt to quote ticket text for each fact, and add a "not stated" rule. Blocker removed: the fact error rate. Leverage is a guess [judgment]. Budget: two variants, one week. Stop condition: stop if neither variant beats the baseline. Step 4 MUST NOT start until Step 3 gives a baseline. Accept a variant only when it meets the Step 3 threshold.

5. **Track the rate in production (Clear, deterministic).** Increment: a weekly report of "Wrong" clicks per 100 summaries. Blocker removed: no view of drift. Test, written first:
   - Given one week of feedback records
   - When the report runs
   - Then it shows clicks per 100 summaries by error type

   Step 5 MUST NOT start until Step 2 passes.

## Follow-up

Conditions that change the recommendation:

- If A1 is false, add ticket linking before Step 2.
- If A3 is false, change the Step 1 weights and redo the labels.
- If Step 1 shows most errors are missing ticket data, fix the data feed and skip Step 4.
