## Headline

Split this into two projects: migrate authentication to JWT first, then run a measured sign-up conversion experiment, because the two changes share no dependency and mixing them hides regressions.

- The migration is a deterministic infrastructure change with known pass/fail tests.
- Conversion improvement is a stochastic change that needs a baseline and a controlled experiment.
- Bundling them in one release makes it impossible to attribute a metric change to its cause.

## Background

The request combines two unrelated goals: replace session-based authentication with JSON Web Tokens (JWTs), and increase sign-up conversion. No architecture details, traffic numbers, or current conversion data were provided.

## Relevance

Auth changes affect every request and carry security risk. Conversion changes affect revenue. Shipping them together delays both and breaks rollback.

## Information

**Migration design (deterministic).** Issue short-lived access tokens (15 minutes) with refresh tokens, per common practice in RFC 7519 and the OAuth 2.0 Security Best Current Practice [1][2]. Keep the session store alive during a parallel-run phase so you can roll back.

**Risks [judgment].** JWTs cannot be revoked cheaply before expiry, so short access-token lifetimes plus a refresh-token denylist are the standard mitigation. Storing tokens in browser storage raises cross-site scripting exposure; httpOnly cookies for refresh tokens reduce it.

**Conversion work (stochastic).** No baseline was supplied, so the first action is measurement, not redesign. Typical experiment sizes for detecting a 10% relative lift at 80% power need thousands of visitors per variant [3] [inference: exact number depends on the baseline rate].
