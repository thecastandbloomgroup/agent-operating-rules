## Headline

Build a measurement harness before changing the summariser, because "sometimes wrong" gives no target. First, define and sample errors. Next, fix the dominant error class. Then, add guardrails and monitor.

## Background

A support tool now uses an LLM summariser. Agents report it is "sometimes wrong". There are no metrics, so no baseline exists.

## Relevance

Model or prompt changes without a baseline cannot be verified. A wrong change can lower accuracy while appearing to help.

## Information

Three themes emerge from similar deployments:

- Unmeasured LLM outputs drift in quality; human spot checks find only some errors [judgment].
- Error classes in summarisation are usually factual addition, factual omission, and distortion [judgment].
- Fixing the largest class first gives the highest return per change [judgment].

Assumption log:

- A1. Agents can spare time to label summary errors. Why not measured: the material does not state it. Validate by: ask one team lead to confirm a 30 minute per week budget. If wrong: use automated checks plus a smaller sample.
- A2. Conversation logs and summaries are stored and retrievable. Why not measured: the material does not state it. Validate by: run one query against the store. If wrong: add logging first.
- A3. "Wrong" means factual error, not style. Why not measured: the material does not state it. Validate by: inspect the first 20 labelled cases. If wrong: adjust the rubric.

Alternative considered: swap the model or rewrite the prompt now. This loses because no baseline exists, so we cannot tell improvement from regression [judgment].

## End

I recommend that we take these four actions, in order.

1. Build an evaluation set. Sample 200 past conversations with their summaries. This removes the "no baseline" blocker. Test (stochastic): two reviewers label each summary as correct or incorrect per a written rubric; inter-rater agreement is at least 80% on a 50-case overlap. Domain: Clear. Step 2 MUST NOT start until this test passes.

2. Classify the errors. Tag each incorrect case as addition, omission, or distortion. This names the dominant failure mode. Test (evaluative): each case gets one label; a third reviewer resolves disagreements; output is a count per class. Domain: Complicated.

3. Fix the dominant class. For omissions, add key facts to the prompt or retrieve more context. For additions, constrain output to stated facts. Test (stochastic): rerun the 200-case set; the dominant-class error rate drops by at least half versus the Step 1 baseline at the same sample size. Domain: Complex, run as a capped probe: two prompt variants, one week budget, stop if no gain.

4. Add ongoing monitoring. Run an automated fact-check pass on 5% of new summaries each week and alert on error rate above the Step 3 result. Test (deterministic): Given a known-bad summary fixture, When the check runs, Then it flags the case. Domain: Clear.

Steps 3 and 4 can run in parallel once Step 2 finishes.

## Follow-up

If A1 is false, label 50 cases only and accept a wider error range. Step 1 uses judgment-based thresholds; tune them after the first labelling round.
