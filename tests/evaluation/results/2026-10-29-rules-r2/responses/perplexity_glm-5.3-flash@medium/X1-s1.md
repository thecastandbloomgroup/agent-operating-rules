## Headline

Add measurement before changing anything: log agent edits, label a sample of summaries against their tickets, and set a quality threshold, then tune the summariser against that measure. Supporting points:

1. The complaint "sometimes wrong" is a hypothesis, not a cause, so no tuning can distinguish real improvement from noise.
2. Instrumentation plus a labeled sample gives a baseline at a cost of one to two working sessions.
3. Two cheap product fixes, source links and error flagging, work together with measurement because they generate labels for free.

## Background

A support tool now includes a summary produced by an LLM. Agents report that it is sometimes wrong. No metrics exist, so the wrongness has no rate, no type, and no source. The request is to make the summariser better.

## Relevance

Without a metric, any prompt or model change looks good to some agents and bad to others, so the team cannot decide whether to ship it. Measurement also turns agent complaints into specific, fixable cases instead of general distrust. Distrust makes agents ignore the summary, which wastes the feature entirely [judgment].

## Information

**Error categories for support summaries.** A first pass splits "wrong" into four parts that do not overlap and cover the whole:

1. Factuality: the summary states something the ticket does not support, also called a hallucination.
2. Completeness: the summary drops a step, a decision, or a commitment from the ticket.
3. Precision: the summary is correct but too generic to act on.
4. Utility: the summary is accurate but ignores what agents actually need first.

Category 4 comes from qualitative analysis of how agents triage and resolve cases [3], [4]. In support work, the first read matters most because triage decides routing and waiting time [5]. A summary with no factual errors that buries the action item still fails the agent.

**Assumption log.**

- A1. "Wrong" means mostly factuality and completeness errors against the ticket text. Why not measured: the material does not state it. Validate by: label 30 sample summaries together with agents. If wrong: drop the factuality-heavy tests and build the rubric around the categories agents report.
- A2. Ticket history is available as a correct answer source. Why not measured: the material does not state it. Validate by: add ticket and object to the evaluation table. If wrong: construct the eval set from support analyst restatements of the resolution instead.
- A3. Agents edit, rewrite, or ignore the summary, and that behavior is recordable. Why not measured: the material does not state it. Validate by: log whether an agent clicks copy or edit and check for such events. If wrong: run live agent sampling sessions and base the benchmarks on those instead.
- A4. The support team can spend about one working session per week on labeling. Why not measured: measuring costs more than the decision is worth. Validate by: confirm the budget with the team lead. If wrong: shrink the eval set from 50 to 20 cases per round and widen the confidence interval.

**Evidence base.**

- A small labeled set, 50 items, detects only large shifts; detecting a 10 point change in the problem rate with reasonable confidence needs more examples or repeated rounds [judgeestimate based on standard evaluation practice][infer].

## End

I recommend that we:

1. **Instrument the flow first (deterministic, Clear, biggest blocker: no data).** Add logging and a table update.
   - Test first: given a ticket summary the agent edits, when the agent saves the edit or marks the summary as wrong, then a record is added with ticket ID, summary text, edit text, and issue category.
2. **Run a labeling round (evaluative, Complicated).** Sample roughly 100 to 200 ticket summaries at random and weight toward serious errors. Label four dimensions: factual alignment, correctness of claims, completeness of steps, and usefulness.
   - Test (rubric first): each dimension scored 0 to 2 by two reviewers with disagreements flagged; summariser passes the round only at an overall mean label of 1 or higher and a factuality score near 1, reviewed at roughly 95 percent agreement.
3. **Add visible, cheap guardrails (deterministic, Clear).** Show source references for key claims, and add flag and edit UI options.
   - Test first: given a summary with source references available, when it renders, then each core claim shows a link or reference anchor.
4. **Retrain on better prompts or a targeted model (stochastic, Complicated).** Adjust the summariser on slices that failed in step 2, not broadly: add "write only facts stated in the ticket", ask for per-claim source citation, or switch to a focused model for long threads.
   - Acceptance test: run the full labeled set before and after the change; ship the change only if overall agree count and factuality score both reach somewhat higher values with statistical significance on the sample size and reviewed agreement test.
