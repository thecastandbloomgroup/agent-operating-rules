Headline: Change each retrospective from a discussion meeting into a decision meeting with one owned, tested change per cycle.

1. Retrospectives fail to change work when they end in discussion instead of an owned action with a test.
2. Fix this with a strict format: reduce the problem list to one change, name one owner, and define how you will see it worked within one cycle.
3. Track the change publicly between retrospectives, so progress is visible before the next one.

Background

The team holds retrospectives. People attend, but no work practice changes afterward. The request is a way to make the meetings produce shifts.

Relevance

A retrospective that produces no change costs the team its meeting time and lowers trust in the format. Once people expect no outcome, attendance and honesty drop, so the next retrospective has less data to work with [S].

Information

The most common causes, based on published practice guides [S] [S]:

- Too many findings: the meeting ends with a list of five or more items, so none gets resources.
- No owner: items are recorded as "the team should", so no person is accountable.
- No follow-through loop: nobody checks the change before the next retrospective, so semi-done changes persist.
- Unsafe discussion: people hold back, so the meeting surfaces surface topics only [S].

Your report ("people attend but nothing shifts") fits the first three causes. It does not show the fourth, so treat safety as unmeasured.

Assumption log:

A1. The retrospectives happen on a fixed cadence (weekly or per sprint). Why not measured: the material does not state it. Validate by: ask the team. If wrong: the action format stays the same, but the follow-through loop length changes.
A2. The team has authority to change its own work practices without sign-off. Why not measured: the material does not state it. Validate by: ask whether past retro decisions needed manager approval. If wrong: add the approval step to the owner's task, because the blocker moves outside the team.

Alternative considered: stop holding retrospectives and replace them with continuous written feedback. This loses for most teams because asynchronous text removes the tone and read-back that surface disagreement, and the team already has a working attendance habit [S] [no source for the tone claim].

End

I recommend that we restructure the retrospective around one owned change per cycle:

1. Cut the output to one change. In the meeting, the team votes on the single item to act on. The increment is one decision. The blocker it removes is the too-many-findings problem. Test (Given a completed retrospective, When the notes are read, Then exactly one change is named). Kind: deterministic. Domain: Clear.
2. Name one owner and a first task. The owner is a person, not the team. The first task must fit in the next cycle. The increment is one task with a name on it. The blocker it removes is the no-owner problem. Test (Given the retrospective notes, When the owner list is read, Then each change has one named person and one task due before the next retrospective). Kind: deterministic. Domain: Clear.
3. Add a two-minute check at the start of each retrospective on the previous change. The result is "done", "partly done", or "dropped", written in the notes. The increment is one agenda item. The blocker it removes is the no-follow-through loop. Test (Given three consecutive retrospective notes, When the check results are read, Then each previous change has a recorded result). Kind: deterministic. Domain: Clear.
4. Run the new format for three cycles and rate whether changes land, on a scale of 0 (never) to 3 (always), at each cycle. Pass threshold: the rating rises by at least one point from cycle 1 to cycle 3, or reaches 2. Sample size: 3 cycles. The increment is one measurement series. The blocker it removes is the unknown cause (for example low safety) that the format change cannot fix. Kind: stochastic. Domain: Complex, because cause and effect between format and behavior show up only over cycles. Budget: 3 cycles; stop if the rating does not move, because then the cause is likely A2 or safety, not format.

Step 4 MUST NOT start until Steps 1 to 3 have run for one cycle, because the rating needs the new format as its baseline.

Condition that changes this recommendation: if A2 is false, that is, changes need sign-off, move Step 1's vote to include the approver, or the changes will keep dying after the meeting.

Follow-up

1. What cadence do the retrospectives run on, and what cycle length do changes target? Use: to set the follow-through interval in Step 3.
2. Did any past retro decision need manager approval? Use: to confirm or refute A2 before Step 1.
3. Do people speak freely in the meetings, per your observation? Use: to decide whether to add a safety measure, such as an anonymous input round.
