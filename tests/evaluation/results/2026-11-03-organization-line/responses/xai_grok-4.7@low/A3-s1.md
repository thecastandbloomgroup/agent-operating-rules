Turn on gzip for these JSON API responses. A 400 KB body is large enough that transfer cost beats compress cost on slower links. JSON repeats keys, so gzip cuts many such bodies by a large share. Clients that omit gzip still receive the plain JSON. The switch is small, tested, and easy to reverse.

The service sends JSON responses. The average size is 400 KB. The request is whether gzip should be enabled for that traffic.

Each call now moves about 400 KB of JSON. A smaller body lowers bandwidth use and wait time on slower networks.

Gzip is a defined HTTP content coding.
[1]

Gzip often cuts text response size by about 70%.
[2]

JSON is text with repeated keys. [judgment] A 400 KB body at a 70% cut is 120 KB. [inference] Likely (66 to 100%), JSON is close to that text rate, because keys repeat. Medium confidence, one published text rate, no sample from this API. So the size cut is the reason to proceed, and the ratio still needs a local check.

A1. Most clients send Accept-Encoding gzip. Why not measured: the material does not state it. Validate by: count that header in one day of logs. If wrong: those clients keep the full body.

A2. Payloads are plain JSON, not bytes already compressed. Why not measured: the material does not state it. Validate by: open one sample and check Content-Type. If wrong: do not gzip that route.

A3. Calls cross a network where byte count affects wait time. Why not measured: the material does not state it. Validate by: confirm clients are remote, not only same-host. If wrong: leave gzip off.

The strongest alternative is to skip gzip and trust cache plus HTTP/2. That option loses because HTTP/2 does not shrink the JSON entity. Many API responses are also unique, so cache does not remove the 400 KB cost. [judgment]

I recommend that we take the three steps below.

1. Test first. The kind is deterministic.
Given a JSON body near 400 KB and a request with Accept-Encoding gzip,
When the API returns that body,
Then Content-Encoding is gzip, Vary lists Accept-Encoding, and decoded JSON matches the source.
Enable gzip for JSON responses at or above 1 KB.
Set Vary to Accept-Encoding on those responses.
This removes the full 400 KB transfer for clients that accept gzip.
The domain is Clear, because this content coding is a known best practice.

2. Step 2 MUST NOT start until the test in Step 1 passes. Test first. The kind is stochastic.
Metric: compressed bytes divided by raw bytes, plus p95 compress time in milliseconds.
Baseline: the current body near 400 KB, and 0 ms of compress time.
Pass threshold: median ratio at or below 0.40, and p95 time at or below 20 ms.
Sample size: 30 responses.
Measure those 30 responses in one session.
This replaces the unverified ratio with data from this API.
The domain is Complicated, because the ratio needs analysis of this schema.

3. Step 3 MUST NOT start until the Step 2 threshold passes. Test first. The kind is deterministic.
Given a pass on the Step 2 threshold,
When the gzip setting is promoted,
Then live JSON routes at or above 1 KB send gzip to clients that accept it.
Promote the passing gzip setting for those routes in one release.
This keeps the bandwidth cut after the measure.
The domain is Clear, because the pass rule already selects the practice.

If A2 is false, exclude that route from Steps 1 to 3. If Step 2 misses the time threshold, turn gzip off for that route. If A3 is false, stop after Step 1 and leave gzip off.
