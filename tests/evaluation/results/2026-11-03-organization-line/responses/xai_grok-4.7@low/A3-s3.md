Turn gzip on after a sample shows at least a 2:1 size cut. That result is likely, in the 66% to 100% band, for JSON of this size.

First, a 400 KB JSON body is large enough that transfer cost can exceed compress cost. [judgment]

Second, JSON repeats keys, so gzip can store those repeats once.
[1]

Third, a client asks for gzip with Accept-Encoding, and a correct server compresses only then.
[2]

Fourth, a size floor near 1 KB and a moderate level keep small bodies and CPU in bounds. [judgment]

The API returns JSON. The average body is 400 KB. The question is whether gzip should be on.

This choice changes latency, egress cost, and CPU on each response now. A body of 400 KB sits far above common floors near 1 KB. [judgment]

JSON repeats field names across records. Therefore gzip, which encodes repeated strings, can shrink it.
[1]

The exact ratio for this API is not in the material. A cut of 70% to 90% is likely for repetitive JSON. [judgment] That range would turn 400 KB into about 40 KB to 120 KB. [inference]

Encode time at a moderate level is a few milliseconds for this size on one modern core. [judgment] The time to send the extra hundreds of KB is longer on slower links. [judgment] High confidence in the direction, because the size gap is large. The ratio still needs a local sample.

A1. Clients send Accept-Encoding with gzip. Why not measured: the material does not state it. Validate by: read one hour of access logs for that header. If wrong: the change does nothing, because the server must not compress.

A2. Bodies are plain JSON and are not already compressed. Why not measured: the material does not state a content type beyond JSON. Validate by: check Content-Type and the first bytes for a gzip header. If wrong: a second pass wastes CPU and can grow the body.

A3. Responses do not mix a secret with text the caller controls. Why not measured: the material does not state it. Validate by: review response schemas for tokens next to echoed input. If wrong: leave those routes uncompressed, because that mix can leak through compression. [judgment]

The strongest alternative is Brotli alone, or no body compression under HTTP/2. Brotli can be smaller, but older clients lack it and encode cost is higher. [judgment] HTTP/2 compresses headers, not the body.
[2]
Therefore the no-compression option leaves about 400 KB on the wire. Gzip first, with Brotli as a later option, loses less support.
