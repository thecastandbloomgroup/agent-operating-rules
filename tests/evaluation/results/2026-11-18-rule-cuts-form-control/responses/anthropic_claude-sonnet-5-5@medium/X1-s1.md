## Headline

Measure the errors first, then fix the largest error type, and prove each fix with a test.

- No data exists today, so no change can be shown to help.
- Agent reports of "sometimes wrong" cover several different failures, and each failure needs its own fix.
- A small labeled test set lets the team compare every prompt or model change against a baseline.
- Agent feedback built into the tool keeps the measure alive after launch.

## Background

The support tool now has a summariser built on a large language model (LLM). It writes a short summary of each ticket. Agents report that it is "sometimes wrong". The team has no metrics, so nobody knows how often it fails or how.

## Relevance

An agent who cannot trust a summary must read the full ticket. That removes the time the tool should save. Agents may also stop using it.

## Information

Evidence:

- Agent reports are the only evidence today. They are qualitative, from an unknown number of agents [judgment].
- It is likely (66 to 100%) that most errors fall into three or four types, for example a wrong fact, a missing step, or an invented detail [judgment].
- Without a baseline error rate, no claim of "better" can be tested. That is the main blocker.

Assumption log:

- Assumption: the tool stores each ticket and its summary. Why not measured: the material does not state it. Validate by: query the database for last week's summaries. If wrong: add logging first, then wait one week for samples.
- Assumption: two agents can give two hours each for labeling. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: cut the sample from 50 to 25 and accept a wider error margin.
- Assumption: the team can change the prompt and the model setting. Why not measured: the material does not state it. Validate by: read the integration code. If wrong: the probe in Step 4 must target the vendor settings instead.

Alternative considered: switch to a larger model now. It loses because the team has no baseline. A change could not be shown to help, and it would raise cost per ticket [judgment].

## End

I recommend that we:

1. **Label 50 recent summaries to find the error types.**
   - Increment: two agents each score the same 50 randomly sampled summaries in one session.
   - Blocker removed: nobody knows what "wrong" means.
   - Domain: Confused. The cause of the errors is unknown, so this step gathers what is needed to classify the work.
   - Kind: evaluative. Write the rubric before the scoring.
   - Rubric criteria and weights:
     - Factual accuracy, 40%.
     - Completeness of the customer's request, 30%.
     - No invented detail, 20%.
     - Length and tone, 10%.
   - Pass threshold: a summary passes at a score of 80 or more. Each score needs a quoted line from the ticket as evidence.
   - Output: the baseline pass rate and a ranked list of error types.
2. **Add a feedback control and event log to the tool.**
   - Step 2 MUST NOT start until Step 1 is done, because Step 1 names the reason tags.
   - Increment: one "wrong" button per summary with a reason list, plus a log of ticket ID, summary, and agent.
   - Blocker removed: no ongoing metric.
   - Domain: Clear. Logging a click is a known practice that needs only deduction from the spec.
   - Kind: deterministic. The test is written first [1]:
     ```gherkin
     Given an agent views a summary
     When the agent selects "wrong" and the reason "missing step"
     Then the log stores the ticket ID, the summary text, and the reason
     ```
3. **Build a fixed test set of 100 tickets with reference facts.**
   - Step 3 MUST NOT start until Step 1 ranks the error types.
   - Increment: pick 100 tickets that cover the top error types. Agents write the key facts each summary must contain.
   - Blocker removed: no repeatable way to compare versions.
   - Domain: Complicated. Choosing a fair sample needs analysis, and good methods exist.
   - Kind: stochastic, because model output varies per run. The acceptance test is written first:
     - Metric: share of key facts present and correct.
     - Baseline: the current version, run three times on the 100 tickets.
     - Threshold: the new version beats the baseline mean by at least 10 points in all three runs.
     - Sample size: 100 tickets, 3 runs.
4. **Run one probe that fixes the largest error type.**
   - Step 4 MUST NOT start until the test set in Step 3 exists.
   - Increment: change the prompt for the top error type, for example "quote the customer's request first". Run it on the test set.
   - Blocker removed: no evidence that any change helps.
   - Domain: Complex. Model behavior shows its effect only after a trial [2]. The pattern could break if the fix raises a different error type. The leverage is a guess.
   - Safe-to-fail limits: budget of one day, stop if the metric gains less than 5 points, and no release to agents until the threshold in Step 3 is met.
   - Kind: stochastic, with the same acceptance test as Step 3.

If Step 1 shows that the tickets are the problem, for example unclear or very long threads, replace Step 4 with a ticket clean-up probe.

## Follow-up

Conditions that change the recommendation:

- If the pass rate in Step 1 is above 95%, stop at Step 2 and track the feedback.
- If no stored summaries exist, run Step 2 first.
