## Headline

**Measure the summariser first, then change it only against a fixed test.**

- Nobody knows the error rate or the error types, so any change today is a guess.
- A labelled sample and agent flags give a baseline.
- A test harness stops later changes from making summaries worse.
- Prompt changes then run as small probes that must beat the baseline.

## Background

The support tool has a summariser built on an LLM (large language model, a program that writes text from text input). Agents call its summaries "sometimes wrong", per the request message. No metrics exist. The request is to improve the summaries.

## Relevance

Without a baseline, an edit can make summaries worse and nobody will see it. If agents distrust the summary, they read the full ticket, so the tool saves no time [judgment].

## Information

**Evidence**
- One source reports the problem: agents say "sometimes wrong", per the request message. It gives no number, so the error rate is unknown.
- Few error types likely cause most errors (likely, 66 to 100%). Examples are invented facts, missed details, and wrong tone [judgment].
- Step 1 groups the labelled errors into themes and counts the summaries in each theme.

Source for the grouping method:

- Braun and Clarke, thematic analysis [1]

A sample of 50 tickets gives a pass rate within about ±14 points at 95% confidence [inference]. Therefore a small gain needs a second sample to confirm.

**Assumption log**
- Assumption: summaries and source tickets are stored. Why not measured: the material does not state it. Validate by: pull 10 records. If wrong: build logging before Step 1.
- Assumption: "wrong" means a false fact or a missed key fact, not style. Why not measured: the user has not answered. Validate by: ask two agents to review five bad summaries. If wrong: change the rubric weights in Step 1.
- Assumption: the team can edit the prompt and settings. Why not measured: the material does not state it. Validate by: read the tool configuration. If wrong: replace Step 4 with a vendor request.
- Assumption: 50 tickets cover the common ticket types. Why not measured: no metrics exist. Validate by: check the sample against the ticket category counts. If wrong: draw a larger stratified sample.

**Alternative considered:** switch to a larger model now. It loses because it costs more and there is no baseline to show a gain. The cause may also be bad input, not the model [judgment].

## End

I recommend that we:

1. **Label a baseline sample.**
   - Increment: two agents score 50 recent summaries against their tickets in one session, and tag each error type.
   - Blocker removed: no one knows the error rate or the error types.
   - Kind: evaluative. The rubric is written first.

     | Criterion | Weight | Evidence |
     |---|---|---|
     | Accuracy | 50% | Each fact matches the ticket text |
     | Completeness | 30% | Issue, product, and ask are present |
     | Clarity | 20% | Agent can act without opening the ticket |

     A summary passes at a score of 80 or more with zero invented facts.
   - Cynefin domain: Confused [3]. The failure modes are unknown, so this step gathers the data to classify the work.

2. **Add a "wrong summary" flag.** This step can run in parallel with Step 1.
   - Increment: one click records the flag, an optional reason, the ticket ID, and the prompt version.
   - Blocker removed: no ongoing signal exists.
   - Kind: deterministic. Test in Gherkin form [2]:

     ```text
     Given an agent views a summary
     When the agent clicks "wrong summary" and picks a reason
     Then a record stores the ticket ID, reason, and prompt version
     ```
   - Cynefin domain: Clear. Feedback buttons are a known practice, so deduction from that rule applies.

3. **Build the test harness and release gate.** This step MUST NOT start until Step 1 ends.
   - Increment: a script stores the 50 labelled tickets and reports the pass rate.
   - Blocker removed: no way to compare a change with the baseline.
   - Kind: deterministic. Test:

     ```text
     Given 50 stored tickets with human pass or fail labels
     When the script scores the labelled summaries
     Then the pass rate equals the manual count from Step 1
     ```
   - Cynefin domain: Complicated. Analysis of the Step 1 data sets the gate threshold, so this is deduction from that analysis.

4. **Probe one prompt change for the top error type.** This step MUST NOT start until the test in Step 3 passes.
   - Increment: one prompt edit for the most common error theme. An example is "write 'not stated' when the ticket lacks a fact".
   - Blocker removed: the top error type.
   - Kind: stochastic. Acceptance test, written first:
     - Metric: pass rate under the Step 1 rubric.
     - Baseline: the Step 1 pass rate.
     - Threshold: baseline plus 10 points.
     - Sample size: the 50 tickets, three runs each, then 50 new tickets.
   - Cynefin domain: Complex. Induction from trials applies, and model behavior can change with ticket wording or a model update. Leverage is a guess.
   - Stop condition: two prompt versions fail, or two sessions are used.

If Step 1 shows a pass rate of 95% or more, stop after Step 2. The remaining problem is how agents trust the summary, not its accuracy. If errors trace to poor ticket text, replace Step 4 with an input fix.
