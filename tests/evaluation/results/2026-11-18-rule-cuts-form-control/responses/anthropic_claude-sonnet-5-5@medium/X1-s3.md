## Headline

Measure the errors first, then fix the most common error type with a tested change.

- No data exists on the errors, so any fix would be a guess.
- Agent flags and a small reviewed sample give a baseline within days.
- A fixed test set lets each change be accepted or rejected on numbers.
- Changes roll out to a small agent group first, so a bad change does limited harm.

## Background

The support tool has a summariser built on a large language model (LLM). Agents report that it is "sometimes wrong". The team has no metrics, so the error rate, the error types, and the cost of errors are unknown.

## Relevance

An agent who trusts a wrong summary may give a wrong answer to a customer. An agent who distrusts it loses the time the tool should save. Both outcomes get worse as usage grows.

## Information

Evidence:
- The only evidence is the agent report "sometimes wrong". It has no count, no sample, and no error type. [judgment]
- Wrong summaries usually fall into a few types, for example invented facts, omitted facts, and wrong customer intent. [judgment]
- The error rate is unmeasured, so no baseline exists. The first work item creates one.

Assumption log:
- Assumption: the tool can log each summary with its source ticket and model version. Why not measured: the material does not describe the tool. Validate by: ask an engineer to run one query. If wrong: add a logging step before Step 1.
- Assumption: the team can change the prompt and the model setting. Why not measured: the material does not state it. Validate by: check the configuration access. If wrong: Step 4 changes to a vendor request.
- Assumption: about 10 agents will flag errors for two weeks. Why not measured: the user has not answered. Validate by: count active agents. If wrong: use the random sample in Step 2 alone.

Alternative considered: switch to a larger model now. It loses because the cause of the errors is unknown. The change adds cost and may not fix the main error type. [judgment]

## End

I recommend that we take these steps in this order:

1. **Add a flag and a log.** Add a one-click "wrong summary" button with a reason list. Log the summary, the ticket, and the model version.
   - Blocker removed: no error data exists.
   - Kind: deterministic. Domain: Clear. Logging is a known practice, so deduction from a known rule applies.
   - Test, written first:
     - Given an agent views a summary
     - When the agent clicks "wrong summary" and picks a reason
     - Then one record stores the summary, the ticket ID, the reason, and the model version

2. **Label an error sample.** Step 2 MUST NOT start until the test in Step 1 passes. Two reviewers label 50 random summaries and all flagged ones. Group the errors into themes [1].
   - Blocker removed: the error types are unknown.
   - Kind: evaluative. Domain: Complicated. Analysis of the sample picks the practice.
   - Rubric, written first: criteria are theme coverage (weight 40%), reviewer agreement (30%), and a count per theme (30%). Pass at a score of 70% or more. Evidence: the labeled sample, an agreement figure, and the theme counts.

3. **Build the test set and the baseline.** Step 3 MUST NOT start until Step 2 passes. Pick 100 tickets that cover the top themes. Agents write the reference facts. Score today's summaries to get the baseline error rate.
   - Blocker removed: no way to compare changes.
   - Kind: stochastic. Domain: Complicated. The labeled themes from Step 2 guide the choice of tickets.
   - Acceptance test, written first: the metric is the share of summaries with at least one wrong fact. The baseline is measured in this step. A change passes when the rate falls by at least half at 200 summaries. [judgment]

4. **Run one fix as a probe.** Step 4 MUST NOT start until Step 3 sets the baseline. Take the top error theme. Change the prompt, for example by requiring each fact to quote the ticket text. Release it to 10% of agents.
   - Blocker removed: the top error type.
   - Kind: stochastic. Domain: Complex. Cause and effect show only after trials. Induction applies, and a change in the ticket mix could break the pattern. The leverage of this fix is a guess.
   - Probe limits: budget of two weeks and one engineer. Stop if the flag rate rises above the baseline. Keep the change only if it meets the Step 3 threshold.

5. **Repeat for the next theme.** Repeat Step 4 for the second theme, then publish the weekly error rate to the agents.
   - Blocker removed: lost agent trust.
   - Kind: stochastic. Domain: Complex. Same limits as Step 4.
   - Test: the same acceptance test as Step 3.

If the tool cannot log summaries (see the assumption log), insert a logging build before Step 1.
