## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` on staging first, and run it in production only when you can deploy the matching code change.

- The SQL is one statement, and PostgreSQL updates indexes, constraints, and views for you.
- Application code, stored function bodies, and external queries still use the old name, so they break at once.
- The statement takes a short exclusive lock on the table, so set a lock timeout.

## Background

You asked to rename `user_id` to `account_id` in the `orders` table of a Postgres database. You are about to board a plane. No tool access to your database exists in this session.

## Relevance

A rename takes effect at once. If you run it now and the code is not ready, orders queries fail while you are offline.

## Information

Evidence:

- PostgreSQL documents `RENAME COLUMN` as a form of `ALTER TABLE`. Indexes and table constraints on the column follow the new name automatically.

[1]

- Views keep working after a rename, because PostgreSQL stores them by column reference, not by name text. [inference]
- Function bodies written in PL/pgSQL (the built-in procedural language) are stored as text. They keep the old name and fail at run time. [inference]
- `ALTER TABLE` takes an ACCESS EXCLUSIVE lock. A long transaction on `orders` can make the rename wait, and other queries then queue behind it. [1]
