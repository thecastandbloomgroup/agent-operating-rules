## Headline

Yes, pin exact versions of every direct dependency in requirements.txt. Add a lock file for transitive dependencies and pin the interpreter version. Then run a small monthly update probe so the pins do not go stale. This removes the silent upgrade that caused both breaks.

## Background

The project builds from requirements.txt with no versions pinned [1]. A library update broke the build twice last month [1]. The request asks whether to pin.

## Relevance

Each break blocks every person who waits on the build. Pinning costs under one hour [judgment] and removes the trigger for both breaks so far.

## Information

Evidence, with the baseline "a pinned build installs the same package set every time":

pip treats an unpinned name as a range. It resolves the range to the newest release at install time [2].

Therefore a library release changes the next install, and the build changes without a code change [1] [2].

The Python Packaging User Guide advises exact pins for applications [3].
It also notes that pins freeze fixes until someone updates them [3].

A library can change behavior in any release unless it publishes a compatibility contract [4].

Theme from the sources: "exact pins prevent upgrades that the project did not choose." Three sources support it [1] [2] [3]. The guide carries the counterpoint about frozen fixes [3]. Therefore the plan keeps a monthly update probe [3].

Assumption log:

Assumption: a test suite or build check exists that would catch the next break. Why not measured: the user's message does not state it. Validate by: run the checks on the latest commit. If wrong: add a smoke test before Step 4.

Alternative considered: keep loose versions and rely on automatic updates. It loses because a range still resolves to the newest release each time [2], and the resulting changes broke the build twice in one month [1].

## End

I recommend that we take these steps in this order.

1. Pin each direct dependency with "==" and the exact version of the last green build. Increment: edit requirements.txt in one session. Blocker removed: unchosen upgrades from ranges. Test, written before the work, deterministic:

```gherkin
Given requirements.txt from the pinned branch
When CI runs a clean install twice
Then both installs resolve to the same package set and the build passes
```

Domain: Clear. This is deduction from a known rule [2].

2. Run `pip-compile` to produce a lock file with hashes for all transitive dependencies. Commit it, and install from it in CI. Blocker removed: drift inside dependencies that requirements.txt does not name. Test, deterministic:

```gherkin
Given the committed lock file
When a fresh env installs from it with hashes checked
Then the installed set matches the lock and the build passes
```

Domain: Clear. This is deduction from the same rule [2]. This step waits for the test in Step 1, because `pip-compile` reads the pinned file.

3. Pin the interpreter version in a file such as `.python-version` and match it in the CI image. Blocker removed: toolchain drift. Test, deterministic:

```gherkin
Given the version file at the project root
When a CI job starts
Then the job image version equals the file version and the build proceeds
```

Domain: Clear, deduction from the same rule [2]. This step runs in parallel with Step 2.

4. Run a monthly update probe on a branch, with a one hour time budget. Upgrade the pins to current versions, then run the build and the tests. Blocker addressed: pins freeze fixes, so this step keeps the versions current [3]. Acceptance test, stochastic: metric is the count of changed packages with a failed install or test. Baseline is 0 failures on main. Pass threshold is 0 failures across the changed set. Sample size is one full build and test run per month. Stop condition: close the branch without merging when any test fails. Domain: Complex. Each upgrade batch shows its effects only after the trials, so this is a safe-to-fail probe with a fixed budget. Step 4 starts only when Steps 1 and 2 pass their tests.

Confidence in the recommendation: high. It rests on the package manager's own rule for ranges [2], the guide's advice [3], and two breaks recorded last month [1].
