## Headline

Pin the versions. Pin direct dependencies with exact versions and generate a lock file for transitive dependencies. Upgrade on a schedule, one package at a time, with tests first. Unpinned requirements files do not give repeatable builds, so the file alone cannot prevent the breaks you saw.

## Background

The project keeps Python dependencies in requirements.txt with no pins. The build broke twice last month after a library update [3]. The request is a decision: pin or not.

## Relevance

Every unpinned build can install different package versions on different days. The same file can build today and fail tomorrow, so each unpinned build is a new risk.

## Information

pip resolves an unpinned requirement to the newest version that the constraint allows at install time [1]. Therefore an upstream release changes the build environment with no change to your file. Both report breaks followed a library update, so this mechanism matches the observed failure [3]. Pinning with exact versions is the documented method for repeatable installs [1], and pip-compile generates a full lock file from a shorter input file [2].

Uncertainty: high confidence that pinning stops the breaks. The resolver behavior is documented [1], and the failure timeline matches it [3].

## End

I recommend that we pin and lock, then upgrade under control:

1. **Pin direct dependencies (Clear).** Write the exact version of the last known good build for each direct dependency, with "==" [1]. This is one file edit in one session. It removes the blocker where upstream releases change the build without your input. Domain: Clear, because deduction from documented resolver behavior decides it [1].
   ```gherkin
   Given a clean environment with no installed packages
   When the build runs from the pinned requirements.txt
   Then the build succeeds and installs the exact pinned versions
   ```

2. **Generate a lock file (Complicated).** Move direct pins to a requirements.in file and run pip-compile to write a requirements.txt that pins every package in the tree [2]. Commit both files. This removes the blocker from transitive updates, which are invisible in a hand-written file. Dependency: this step MUST NOT start before Step 1 records a known-good set as the baseline. Domain: Complicated, because the compile analysis picks the exact set from the full dependency graph, and the analysis is the required step.
   ```gherkin
   Given requirements.in and pip-tools are installed
   When pip-compile runs from a clean cache
   Then the output file lists a fixed version for every package in the tree
   ```

3. **Build from the lock file in CI (Clear).** Add one CI job that installs from requirements.txt in a fresh environment on every change to a dependency file. This adds the capability to detect a broken pin before it reaches developers. Dependency: this step waits on the output of Step 2. Domain: Clear, because repeat the documented install command is one known step [1].
   ```gherkin
   Given a fresh CI container and a change to requirements.txt or requirements.in
   When the CI job runs the build from the lock file
   Then the job fails on any version conflict or missing package
   ```

4. **Upgrade one package at a time, monthly (Complex).** Raise one direct pin in requirements.in, run the test suite, recompile, and open a review. Stop condition: any test failure reverts that one pin. Budget: one hour per cycle. This removes the blocker where every package ages in place and the gap grows [judgment]. Domain: Complex, because the effect of a new version shows only after the run; the pattern that can break it is a bad interaction between two upgrades in one cycle.

## Follow-up

Conditions that change the recommendation: if the repo already uses a lock file, skip Steps 2 and 3 and audit the pins instead. If no test suite exists, add a smoke import test before Step 4.
