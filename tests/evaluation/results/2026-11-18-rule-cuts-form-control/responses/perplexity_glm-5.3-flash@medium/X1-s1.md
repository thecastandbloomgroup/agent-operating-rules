## Headline

Measure first, then fix: capture agent edits as ground truth, build a rubric and eval set, and run capped prompt probes before touching the model.

- "Sometimes wrong" hides the failure type. Agents lack a way to flag errors, so the signal is unmeasured. [judgment]
- Agent edits of summaries are free labels. Two weeks of capture costs one build session.
- A 30-case eval set with a rubric lets any change be tested before release.
- Guardrail routing keeps weak summaries out of agent view while prompt probes run.

## Background

A large language model (LLM) summariser was added to a support tool. Agents report that summaries are wrong at times. No metrics and no error log exist. The request is to improve the summariser.

## Relevance

Wrong summaries cost agents review time and can pass wrong facts to customers. Without a baseline, any prompt change cannot be shown to help.

## Information

### Evidence

There are no numbers from the tool, so every claim here is calibrated judgment:

- The most common LLM summary failure in support contexts is a fact not present in the ticket (a hallucination), followed by missed facts. Low confidence, one qualitative signal: agent reports only. [judgment]
- Agent edits are a cheaper ground-truth signal than a review workflow, because agents already correct summaries when they are wrong. [judgment]
- Thematic coding of a sample of flagged cases is the standard way to turn "wrong at times" into failure types with counts [3]. Judgment on which theme drives the fix comes after that coding, not before.

Confidence in the plan structure: high. Confidence in the exact failure ranking: low, and the plan does not depend on it.

### Assumption log

- Assumption: agents edit or rewrite summaries in the tool today. Why not measured: the material does not state it. Validate by: check the ticket history field for edits in one session. If wrong: use a one-click "wrong" flag as the capture path.
- Assumption: one working session is about 4 hours. Why not measured: the material does not state it. Validate by: confirm with the team lead. If wrong: split Step 1 into two sessions.
- Assumption: 30 cases give a usable signal per criterion. Why not measured: measuring the needed sample costs more than the decision is worth now. Validate by: re-score with 50 cases in Step 3 if scores are unstable. If wrong: thresholds move, the plan order does not.

### Alternative considered

Fine-tune or swap the model first. It loses because no ground truth or eval set exists, so the result cannot be graded, and the cost is high before the failure type is known. [judgment]

## End

I recommend that we run these five actions in this order. Steps 2 and 3 are sequential. Step 4 runs in parallel with Step 5 after Step 3 passes.

1. **Add edit capture.** Increment: log every agent edit as a diff against the summary, plus a one-click "wrong" flag, in one session. Blocker removed: no ground truth. Test (deterministic, write before the build):
   ```gherkin
   Given a summary shown to an agent
   When the agent saves an edited summary and taps "wrong"
   Then the log stores the original text, the edited text, and the flag
   ```
   Cynefin: Confused. The failure type is unknown, so this step gathers what is needed to classify the rest. [18]

2. **Code the failures and set the rubric.** Increment: code 30 flagged summaries into failure themes with counts, then set weights: faithfulness 0.5, completeness 0.3, length 0.2, pass threshold 0.8. Waits on 2 weeks of capture from Step 1. Blocker removed: unknown failure mode. Test (evaluative, rubric before scoring): two coders label the same 30 cases; pass when they agree on 80% or more of labels. Cynefin: Complicated, the theme counts come from analysis of the coding. [3]

3. **Build the eval set and the judge.** Increment: select 30 ticket-summary pairs spanning the themes, run one LLM judge scored by the rubric, and have a human score 10 of the 30 to check the judge. Blocker removed: no way to grade any change. Test (stochastic, acceptance first): metric is human-judge agreement, baseline is none, pass threshold is 0.7 or higher, sample size is 10 human-scored pairs. Waits on the rubric from Step 2. Cynefin: Complicated, agreement is measured by analysis.

4. **Run two capped prompt probes.** Increment A: prompt includes the full ticket text and the constraint "state only facts from the ticket". Increment B: prompt takes the ticket body only, with less noise. Budget: 2 prompt iterations each, then stop. Blocker removed: faithfulness score below threshold. Test (stochastic, acceptance first): metric is the faithfulness score from Step 3, baseline is the current prompt's score, pass threshold is baseline plus 10 points, sample size is 30. Stop condition: accept the winning probe only when it clears the threshold at that sample size. Cynefin: Complex, cause and effect in prompts is visible only after the run, so these are safe-to-fail probes and their leverage is a guess.

5. **Route low-score summaries as drafts.** Increment: when the judge scores a summary below 0.8, show it as "draft, verify against ticket" with the source lines attached. Waits on the judge from Step 3. Blocker removed: agents act on unverified text. Test (deterministic, write before the build):
   ```gherkin
   Given a generated summary with a judge score of 0.6
   When the summary is opened by an agent
   Then the label reads "draft, verify against ticket" and shows source lines
   ```
   Cynefin: Clear, the rule is known and the action is one step.

Conditions that change this plan: if Step 1 shows zero edits (agents ignore summaries or start from scratch), replace edit capture with the "wrong" flag as the only signal and extend capture to 4 weeks. If the judge fails the 0.7 agreement test, use human scoring on 30 cases until the judge prompt is fixed.
