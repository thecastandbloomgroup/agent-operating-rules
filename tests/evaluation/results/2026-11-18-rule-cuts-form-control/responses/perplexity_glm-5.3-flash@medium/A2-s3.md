## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` in one transaction before departure.

1. The rename changes catalog metadata only, so Postgres does not rewrite the table data [1].
2. The change takes an `ACCESS EXCLUSIVE` lock for under one second on typical schema sizes [inference].
3. The real risk is application code that still names `user_id`, not the database itself.

## Background

The request is to rename one column in one table of a Postgres database. The user is about to board a plane, so the work must fit in one short step plus one verification.

## Relevance

A rename is cheap now and costly later: every new query that uses the old name becomes a break to fix.

## Information

The rename is metadata-only. Postgres rewrites dependency catalogs for views and functions, so they keep working when a column is renamed [1]. Text in application code is not updated by the database.

Assumption: a sub-second `ACCESS EXCLUSIVE` lock is acceptable.
Why not measured: the material does not state table size or traffic.
Validate by: run `SELECT relpages FROM pg_class WHERE relname='orders';` before the change.
If wrong: run the rename in a quiet window instead.

Assumption: the change ships with one code release, so there is no dual-name period.
Why not measured: no deploy plan exists in the material.
Validate by: ask the team whether any job reads `orders.user_id`.
If wrong: delay Step 2 and keep a view with the old name for one release.

Alternative considered: add a new column, copy the data, drop the old one. It loses because the copy rewrites the full table and takes longer than a metadata-only rename [judgment].

## End

I recommend that we:

1. **Run the rename now.**
   - Increment: one transaction with `SET lock_timeout = '5s';` and the `ALTER TABLE` statement above.
   - Blocker removed: the schema still uses the old name.
   - Test (deterministic, in Gherkin form):
     ```
     Given the orders table has a column user_id
     When the rename transaction commits
     Then the table has account_id and no user_id
     ```
   - Cynefin: Clear, because a known rule applies in one step.

2. **Update the code** in the same release. Step 2 MUST NOT ship before Step 1 passes its test.
   - Increment: one search pass for `orders.user_id` and `user_id` in queries on `orders`, then edit each hit.
   - Blocker removed: queries that fail with "column user_id does not exist".
   - Test (deterministic, in Gherkin form):
     ```
     Given the deployed code and the renamed column
     When the app reads and writes an order
     Then no query references user_id and no column error appears
     ```
   - Cynefin: Complicated, because a repository search picks the files; the analysis is a grep over the codebase.

3. **Verify after deploy.** Step 3 MUST NOT start until Step 2 is deployed.
   - Increment: run `\d orders`, one `SELECT account_id FROM orders LIMIT 1;`, and one app call.
   - Blocker removed: silent breakage in a job that was missed by the search.
   - Test (deterministic, in Gherkin form):
     ```
     Given the rename and the code release
     When the probe queries and app calls run
     Then all return without column errors
     ```
   - Cynefin: Clear, because the checks follow directly from the change.

Condition that changes the recommendation: if the quiet-window assumption is wrong, run Step 1 in that window and hold Step 2 until it passes.
