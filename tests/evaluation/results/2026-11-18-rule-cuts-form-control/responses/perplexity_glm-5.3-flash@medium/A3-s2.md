Yes, turn on gzip compression for the API. JSON is text, and gzip reduces JSON to about one quarter to one sixth of its size, so a 400 KB response drops to roughly 70 to 100 KB [judgment]. The CPU cost at compression level 4 is small, about 1 to 3 ms per response at this size [judgment]. The main security risk is the BREACH attack, and standard configuration avoids it by keeping secrets out of compressed bodies [1].

Background: The API returns JSON responses that average 400 KB. The question is whether to enable gzip compression for them.

Relevance: A 400 KB response takes several seconds on a slow mobile link; 80 KB takes under one second. Compression therefore cuts client latency and bandwidth cost per call [comparison against the 400 KB baseline].

Information: Responses that carry "Content-Encoding: gzip" are part of standard HTTP, so server-side compression needs no client change [2]. The change is a documented feature of common reverse proxies such as nginx [3], and it is a Clear domain task: apply the known configuration. Two assumptions apply:

Assumption: clients send "Accept-Encoding: gzip". Why not measured: the request does not state the client mix. Validate by: sample one day of access logs for this header. If wrong: the proxy compresses only when the header is present, so nothing breaks.

Assumption: response bodies do not place secrets next to attacker-controlled input. Why not measured: the request does not describe the response bodies. Validate by: search response builders for reflected user input near tokens or account identifiers. If wrong: exclude those endpoints from compression, or move secrets into headers [1].

Alternative considered: enable brotli instead. Brotli compresses about 15 to 25 percent smaller than gzip at these sizes, but support among programmatic HTTP clients is narrower, so gzip loses on reach, not on ratio [judgment].
