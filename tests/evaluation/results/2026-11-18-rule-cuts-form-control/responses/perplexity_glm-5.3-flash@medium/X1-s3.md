## Headline

Build a measured baseline first, then fix the top error causes with small, tested prompt changes.

1. Log every summary with its ticket text and add a "correct" or "wrong" rating control for agents.
2. Label 100 ticket and summary pairs to measure three error types: wrong fact, missing fact, bad form, plus "other".
3. Run small prompt changes as capped tests against that baseline; keep only changes that cut errors.
4. Review low ratings each week so fixes target real cases.

## Background

A support tool generates ticket summaries with an LLM (a large language model). Agents report that summaries are "sometimes wrong". No metric records how often or how they are wrong.

## Relevance

Without a number, "better" cannot be proven. A fix now is a guess, and the same errors return.

## Information

**Failure modes.** The complaint "wrong" splits into three types that do not overlap, plus a catch-all: statements that the messages show as false or absent; key facts the ticket holds but the summary drops; format or length that blocks a reply; and "other". Nothing reported so far sits outside these four. One client team is the whole population, so the single agent report is the full set of sources at this point. Group the cases with the method in [2].

**Known risk.** LLM summarizers can state facts that the source text does not support [1]. The report "sometimes wrong" therefore has a plausible cause, but a size no one has measured.

**No baseline.** Agent reports are volunteered and not a random sample. They overstate or understate the true rate.

Assumption log:

1. Assumption: the tool logs summary text with the ticket text for over 100 pairs in 90 days. Why not measured: the material does not state the volume. Validate by: count stored pairs for the last 30 days. If wrong: extend the sample window to 180 days before labeling.
2. Assumption: agents can give under 1 hour per week for labeling. Why not measured: no workload data; measuring costs more than the decision is worth. Validate by: ask the team lead for capacity. If wrong: restrict Step 2 to summaries rated "wrong".
3. Assumption: the summarizer prompt is editable. Why not measured: the material does not state it. Validate by: check where the prompt lives. If wrong: Step 3 becomes a vendor escalation with failing cases attached.

Alternative considered: swap the model for a stronger one now. It loses because the error rate is unmeasured; no one can then prove the swap helped [judgment]. Confidence in this path: moderate, because it rests on one team report plus a known failure class [1].

## End

I recommend that we take these steps in this order:

1. **Log pairs and add a rating control.** Increment: one session of tooling work. Blocker removed: no stored pairs for measurement. Test (deterministic), written in Gherkin form (Given, When, Then) [4]:

```gherkin
Given an agent opens a ticket that shows a summary
When the agent selects "correct" or "wrong"
Then the event row stores the ticket ID, the summary text, and the rating
```

   Domain: Clear, the rule is known to everyone and the step is one action [3].

2. **Label 100 pairs from the last 90 days and record the baseline.** Baseline: the starting number this step produces. Use a rubric before scoring:

   | Criterion | Weight | Evidence it needs | Pass line |
   |---|---|---|---|
   | Faithful | 4 | Each statement matches a ticket message | No unmatched statement |
   | Complete | 3 | Root cause, request, and prior actions appear | All three present |
   | Usable | 3 | Format and length fit the reply panel | Fits without edits |

   Two scorers label each pair. A third scorer resolves disagreement. Report the share of pairs with a factual error, with a 90% interval. Blocker removed: no known error type or rate. Increment: two half-day sessions. Domain: Complicated, expert analysis by scorers picks the labels [3]. Step 2 needs the pair storage from Step 1 when logs lack the summary text.

3. **Run three prompt probes.** With the baseline set, change one thing per probe: quote the ticket line next to each fact; forbid facts absent from the ticket; shorten the target. Each probe is safe to fail: stop a probe when its error rate does not fall. Budget: two sessions for all three. Acceptance conditions: metric, share of pairs with a factual error; baseline, the Step 2 value; pass threshold, at least 5 percentage points below that value; sample size, 50 fresh pairs per probe [judgment on threshold]. Accept a change only when the threshold is met at that sample size. Blocker removed: unknown causes of error. Domain: Complex, cause and effect show only after a run, so leverage is a guess [3]. Step 3 MUST NOT start until Step 2 ends.

4. **Route ratings to a weekly fix list.** Increment: a report query plus a 15-minute review. Blocker removed: errors recur without owners. Test (deterministic):

```gherkin
Given one week of ratings
When the lead opens the review list
Then each row shows the ticket ID, the error theme, and the summary text
```

   Domain: Clear, the rule is direct [3].

If the prompt is not editable, per assumption 3, replace Step 3 with a vendor escalation that carries the failing cases and the Step 2 report.
