## Headline

Stop treating the retrospective (retro) as a talk session. Run it as a change process: two owned actions per retro, and a closure review at the start of the next retro.

- Actions that are opened but never owned or reviewed are the common failure mode in published retro practice [1].
- Your own retro notes can confirm the cause within one short session [judgment].
- A cap of two owned, dated actions makes progress visible and reviewable.
- Add an anonymous input probe if people hold back in the room, because psychological safety drives team output [2].

## Background

The team attends retros on a steady basis. The meetings produce no changes to how the team works. The request asks for a fix.

## Relevance

An unproductive retro trains people to expect no change. Over time, attendance and candor drop, so the next retro has less to work with.

## Information

**Themes from the analysis:**

1. Theme: changes die between sessions because no one owns them, dates them, or reviews them later. One source supports it, and no source found disagrees [1]. The published guidance is general; the team's own records are the primary check.
2. Theme: silence in the room reduces retro output. One source supports it, the Google Project Aristotle study, which ranks psychological safety first among team effectiveness factors [2].

Confidence is high for the record check, because it completes within one session and uses the team's own data [judgment]. Confidence for the safety probe is about as likely as not (33 to 66%) that it changes output, because the team's context is unknown.

## End

I recommend that we run four steps in this order.

1. **Classify the failure mode** (Confused, deterministic).
   - Increment: in one 30-minute session, review the last six retro notes.
   - Blocker: no one can say why changes die, so no fix fits.
   - Test (written first):
     - Given the last six retro notes
     - When each opened change gets one tag from {owned and closed, owned and open, unowned, no change recorded}
     - Then the output lists the count per tag and the total
   - Domain reason: the counts classify the failure mode; therefore this step precedes the rest.

2. **Cap and own each change** (Clear, deterministic).
   - Increment: apply the rule at the next retro.
   - Blocker: open changes without an owner or a due date.
   - Test (written first):
     - Given a retro that reaches its decision point
     - When the team records each accepted change with one owner and one due date
     - Then the visible log holds at most two entries, and each entry names both fields
   - Domain reason: a best practice exists in published retro guidance, so the team applies it in one step [1].

3. **Close the loop and measure** (Complicated, stochastic).
   - Increment: review the log at the start of each of the next three retros.
   - Blocker: no feedback shows whether changes survived.
   - Acceptance test (written first): metric = share of logged changes closed by the next retro; baseline = the share from Step 1; threshold = at or above 50 percent; sample = 3 retros.
   - Domain reason: the analysis in Step 1 picks the practice; the leverage estimate is reliable only after that analysis.

4. **Probe for held-back concerns** (Complex, stochastic).
   - Increment: add one anonymous input question before each of the next three retros.
   - Blocker: concerns that never reach the room lower retro output [2].
   - Acceptance test (written first): metric = share of topics first submitted through the anonymous channel; budget = 10 minutes per retro for 3 retros; stop condition = close the channel if use is zero or harmful after three retros.
   - Domain reason: cause and effect show only after the trial; leverage is a guess, so the probe stays small.

Sequencing: Step 1 comes first because its output classifies the problem. Step 2 runs at the next retro. Step 3 MUST NOT start until Step 1 produces the baseline and Step 2 produces the first log entry. Step 4 runs in parallel with Steps 2 and 3, each capped by its budget.

Condition that changes the recommendation: if Step 1 shows changes that are owned and closed, and the same problems return, the blocker is decision durability. In that case, replace Steps 2 and 3 with an audit of whether closed changes actually alter the process.
