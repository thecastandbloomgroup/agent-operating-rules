# Pin the versions, then add a controlled upgrade path

1. Pin exact versions in requirements.txt now. 2. Unpinned builds accept new library releases at install time, so each upstream release reaches your build [2]. 3. Two breakages in one month show that this drift is active today [1]. 4. Pin first, then run a cheap upgrade probe so you can still move forward.

## Background

Dependencies live in requirements.txt with no version specifiers [1]. The build broke twice last month after a library update [1]. The request asks whether to pin the versions.

## Relevance

Every unpinned install can pull a new release. Pinning removes that risk from the next build.

## Information

**Evidence**

- pip accepts the newest release that meets each specifier, and a line without a specifier accepts any release [2]. So an unpinned file has no fixed install input.
- Baseline: the build failed 2 times in one month [1]. With pinning, upstream releases cannot change the install input, so upstream failures drop to 0 [inference]. Failures become possible only when you change the file.
- The closest versioning rule covers only major releases. "Semantic Versioning" says breaking changes belong in a major version [3]. Python packages are not required to follow it, so minor upgrades may still break you [inference].

Confidence: high, because pinning is a documented mechanism [2] and the failure count [1] shows active drift.

**Assumption log**

- Assumption: no lock or hash file exists elsewhere. Why not measured: the repository is not in this conversation. Validate by: search the repo for lock or constraints files. If wrong: pin only the top-level file and keep the rest.
- Assumption: CI runs today, so a probe job can join it. Why not measured: the conversation does not state your CI setup. Validate by: check one CI run history. If wrong: run the probe as a scheduled local job.

**Alternative considered**

Keep unpinned files and add ranges like ">=1.4,<2" on direct deps only. Ranges still let new minor and patch releases enter each install [2], and the transitive deps stay unpinned, so the October failure mode remains [judgment].

## End

I recommend that we pin with a controlled upgrade path, in three steps.

1. **Freeze and commit.** Run pip freeze in the working environment. Commit the output as requirements.txt. Increment: one file, one session. Blocker removed: overflowing upstream releases can no longer reach the build. Test (deterministic, test written first):

   ```gherkin
   Given a clean environment
   When I run pip install -r requirements.txt
   Then every installed package version equals its pinned specifier
   ```

   Cynefin: Clear, because pinned files are the documented best practice for repeatable installs, by deduction [2].

2. **Add a CI install check.** Every push runs pip install from the pinned file plus the test suite. Increment: one CI job. Blocker removed: a broken pinned set now fails in CI, not in a later build. Test (deterministic):

   ```gherkin
   Given the repository and a fresh CI runner
   When CI runs pip install -r requirements.txt and the test suite
   Then the job exits with status 0 and the resolved versions match the file
   ```

   Cynefin: Clear, same known practice, by deduction. Step 2 MUST NOT start until the file in Step 1 is committed, because CI cannot test an empty input.

3. **Run a weekly upgrade probe.** A separate CI job installs the unpinned latest versions, runs the test suite, and reports failures. You then update the pinned file on purpose. Increment: one CI job plus one upgrade runbook note. Blocker removed: upgrades stop as surprise. Test (stochastic): metric = build failures from upstream releases that reach a release unseen; baseline = 2 per month [1]; threshold = 0; sample size = 8 weekly runs. Cynefin: Complex. It is a safe-to-fail probe with a measure, a stop condition, and a budget. Budget: 2 engineer hours per month. Stop condition: suspend the probe if failures from the probe stay unfixed for one week. Leverage is a guess. Step 3 waits on Step 2 passing, because the probe needs the suite in CI.

Condition that changes the recommendation: if pip is not the install tool (first assumption), replace steps 1 and 2 with that tool's lock file and lock check, and keep step 3 with the same probe form.
