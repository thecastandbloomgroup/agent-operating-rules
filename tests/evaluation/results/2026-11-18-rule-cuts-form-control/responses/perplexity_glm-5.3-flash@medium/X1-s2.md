Headline

Measure the failures before changing the model: build an agent-scored audit set, break the error rate down by type, then test fixes against that baseline as capped probes.

- One report, "sometimes wrong", maps to several failure types. False facts, missing points, and wrong emphasis each need a different fix.
- The first gap is data, not model quality. Without an error rate, any change is a guess.
- A 150-item audit set closes that gap in about one week of part-time agent work [judgment].
- Prompt and context changes stay capped probes until the audit set passes.

Background

The support tool now includes an LLM summariser. Agents report that it is sometimes wrong, and the team has no metrics. The request asks to make the tool better.

Relevance

Without a measure, the team cannot tell whether the problem is facts, missing content, or prompt design. The next change to the summariser will repeat that blind risk.

Information

Evidence

Base rates for "mostly right, sometimes wrong" matter here. When humans judge machine text, error types fall into a small set of recurring themes that free-text reports hide. Grouping those themes needs annotated samples; three sources in Section 1 give the same method for this step [5] [3] [4]. The team owns none of the inputs to those methods yet. All numbers in this plan therefore come after Step 1.

This is a Confused situation first. "Make it better" gives no cause and effect between the summariser and agent complaints, so the first action must gather what classifies the problem [18].

Assumption log

Assumption: the tool stores summaries next to the source ticket text. Why not measured: the material for this session does not state it, and no tool in session can reach the tool. Validate by: open the logs for one day and confirm both fields exist. If wrong: agents capture 50 cases by hand, and the Step 1 estimate doubles.

Assumption: agents can label 150 items in one week. Why not measured: no data on team size. Validate by: time two agents as each labels 10 items, then scale the time. If wrong: cut the set to 75 items and raise the confidence interval on each rate.

Assumption: four error types cover the failures: false fact, missing point, wrong emphasis, bad style. Why not measured: no examples exist yet. Validate by: free-label 20 items, then group the labels into themes [5]. If wrong: extend the rubric before Step 2.

Confidence in the action order: high. Basis: the order holds for every mix of error types, so it does not depend on the assumption above [judgment].

Alternative considered

Replace the summariser now with rule-based extraction or a template. This loses: without error-type data the choice is a guess, and templates cannot cover varied tickets [judgment]. The strongest version of this idea reappears as a fix candidate in Step 3, after the data picks the target.

End

I recommend that we run the four steps below in this order [14] [15] [18].

1. Build the audit set (Confused; reason: one action classifies the problem, because without it no other domain is knowable; this is induction from agent judgments).
   - Increment: sample 150 recent summaries at random, stratified by ticket type. Agents score each item on one rubric: false fact (weight 0.5), missing point (0.3), wrong emphasis (0.15), bad style (0.05). Pass means no false fact and no missing point.
   - Blocker removed: "no metrics".
   - Test (before the work): two agents score the same 30 items. Pass: agreement on error type at 0.8 or higher. Fail: rewrite the rubric and rerun.

2. Compute error rates by type (Complicated; reason: deduction, because rates follow from arithmetic on scored data).
   - Increment: one table: error type, count, rate with units of cases per 100 summaries, and two sample quotes per type.
   - Blocker removed: unknown dominance; the table ranks fix targets.
   - Test: Given the 150 scored items, When the rate table is computed, Then each rate equals its count divided by 150, and the rates sum to 100 percent or less, because an item can carry several types.

3. Run capped fixes on the top error type (Complex; reason: the effect of a prompt change is visible only after trials, so this is induction; the stop condition decides what breaks the run).
   - Increment: one change at a time, for example quoting ticket IDs in the prompt or adding the full thread as context.
   - Blocker removed: the dominant failure type from Step 2.
   - Acceptance test (before the work): metric, false-fact rate per 100 summaries. Baseline, the Step 2 rate. Pass threshold, a drop of 5 points or more. Sample size, 50 fresh tickets held out from tuning, plus the audit set unchanged.
   - Cap: stop after 2 iterations or a 2 point regression on the audit set; budget 2 agent-days of scoring.

4. Make the audit set a release gate (Clear; reason: a best practice exists for any deployed text generator, and one step applies it).
   - Increment: every prompt, model, or context change runs the audit set before release; a score at or below the old baseline blocks the change.
   - Blocker removed: silent regression after each fix.
   - Test: Given a failed gate, When no fix has been applied, Then the summariser stays unchanged.

Step 2 MUST NOT start until the Step 1 agreement test passes. Step 3 MUST NOT start until Step 2 produces the baseline. Build Step 4 in parallel from Step 1 annotations.

Condition that changes this plan: if the tool cannot export summaries with ticket text, Step 1 drops to 50 hand-captured cases and Step 2 thresholds go to interim status until the set grows.

Follow-up

Conditions: see the export condition above; see the label-time assumption, which sets the audit set size.
