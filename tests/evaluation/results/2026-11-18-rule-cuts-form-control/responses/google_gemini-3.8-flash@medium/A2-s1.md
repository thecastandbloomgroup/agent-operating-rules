## Headline

Execute the PostgreSQL table alteration command during a maintenance window to rename the column.
First, the standard command changes column metadata without rewriting table data.
Second, dependent views and queries break if callers reference the old column name.
Third, the command takes an exclusive lock that blocks concurrent operations during execution.

## Background

You requested a command to rename the user_id column to account_id in the orders table.
The database engine is PostgreSQL.

## Relevance

## Information

This section covers evidence, assumptions, and alternatives for the database migration.
PostgreSQL provides a command to rename columns in place [1].
The exact statement is ALTER TABLE orders RENAME COLUMN user_id TO account_id;.
This operation updates system catalogs without rewriting data on disk [1].
However, the command acquires an ACCESS EXCLUSIVE lock on the orders table [1].
Therefore, the statement blocks concurrent queries until the transaction completes [1].
For example, running the command inside an active transaction holds the lock until commit [1].

Assumption: The application tolerates a short lock on the orders table. Why not measured: The material does not state it. Validate by: Check database connection counts during off-peak hours. If wrong: Replace Step 2 with a view alias migration to avoid downtime.

Assumption: No external database views depend on the user_id column. Why not measured: The material does not state it. Validate by: Query information_schema.view_column_usage for the orders table. If wrong: Recreate dependent views after renaming the column.

Alternative considered: Add a new column, backfill data, and drop the old column later.
