Establish an evaluation benchmark from real support tickets before you modify the summariser prompt or model.

### Background

You deployed a Large Language Model (LLM) summariser inside your support tool to assist agents. Support agents report that the generated text is sometimes wrong. However, your team currently tracks no quantitative metrics to verify or guide system performance.

### Relevance

Inaccurate summaries cause agent distrust and increase resolution times. Therefore, you must establish baseline measurements immediately to prevent regressions while fixing errors.

### Information

This section covers the analysis of failure modes and evaluation methods. LLM summarisation systems show factual error rates between 5% and 30% in production workflows [1]. Support agents lose trust when tools deliver unverified output without clear error signals [judgment]. 

Assumption: Support agents review text-based customer conversations in English. Why not measured: The material does not state it. Validate by: Inspect five recent support conversation logs. If wrong: The evaluation rubric must expand to support multiple languages.

Assumption: Engineers possess direct database access to extract recent tickets and tool outputs. Why not measured: The material does not state it. Validate by: Query ten records from the production database. If wrong: Step 1 must wait until engineering provisions read permissions.

Alternative considered:
Prompt engineering with immediate few-shot examples was considered. It loses because you cannot measure whether changes improve output quality without an established baseline [judgment].
