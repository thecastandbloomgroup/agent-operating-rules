## Headline

Pin exact dependency versions in your deployment requirements to secure reproducible builds. Pinned dependencies stop unexpected upstream updates from breaking the build. Separation of top-level requirements from locked dependencies preserves upgrade visibility. Automated pull requests enable scheduled package updates without risking unscheduled build failures.

## Background

The project uses unpinned library definitions in requirements.txt. Upstream dependency updates caused two build failures during the previous month.

## Relevance

Unplanned build failures stop your delivery pipeline and waste developer time. Therefore, the team needs deterministic package installation to guarantee predictable releases.

## Information

First, this section covers the evidence for pinned versions. Unpinned packages allow automatic receipt of bug fixes. However, unpinned packages introduce unexpected breaking changes. For example, an upstream release can alter existing function signatures without warning. Pinned versions are virtually certain to eliminate unannounced upstream breakage. See the application assumption in Section 5.2.

Evidence:
- The Python Packaging Authority advises pinned versions for deployment environments [1].
- The repository suffered two build failures in thirty days from unpinned releases [judgment].
- Hermetic dependency management prevents build drift between deployment systems [2].

Section 5.3 Alternative considered:
Keep dependencies unpinned and run daily scheduled test builds. This alternative loses because scheduled tests still permit breaking changes to reach production during deployments [judgment].
