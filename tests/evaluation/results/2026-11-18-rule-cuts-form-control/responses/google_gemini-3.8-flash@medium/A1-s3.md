### Headline

Pin exact dependency versions immediately to stop build failures.

Pinning direct dependencies prevents breaking changes from new third-party releases.
Generating a lockfile ensures reproducible builds across every environment.
Automating scheduled updates allows safe upgrades through continuous integration tests.

### Background

Your team maintains Python code with unpinned dependencies in `requirements.txt`.
The build failed twice in the last thirty days because an upstream package release introduced breaking changes.
You asked whether you should pin the versions in your requirements file.

### Relevance

Broken builds stop your deployment pipeline and consume developer hours on unscheduled fixes.
Because builds fail unpredictably, your team cannot reliably ship software updates to users.

### Information

This section covers the evidence, assumptions, and alternatives.

Unpinned dependencies cause non-deterministic builds because package installers pull the latest package versions by default [1].
In your project, unpinned libraries caused 2 build breaks in the past 30 days [judgment].
Python packaging guidance specifies that applications must pin exact versions for reproducible deployments [1].
Furthermore, teams that adopt lockfiles eliminate build failures caused by unexpected package updates [judgment].
Confidence is high based on reproducible build principles and the recorded build incidents.

Assumption: The repository is an application rather than a public library. Why not measured: The material does not state it. Validate by: Check `setup.py` or `pyproject.toml` for library packaging metadata. If wrong: Pinning exact versions in `requirements.txt` changes to specifying version ranges, while pinning occurs only in test environments.

Alternative considered: Pin major versions only (such as `package>=1.0,<2.0`). This alternative loses because minor and patch releases still introduce regressions and breaking changes that break builds [1].
