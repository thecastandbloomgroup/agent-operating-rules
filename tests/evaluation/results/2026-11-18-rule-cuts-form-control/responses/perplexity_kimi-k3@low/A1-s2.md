## Headline

Yes, pin every dependency to an exact version, because both build breaks last month came from uncontrolled library updates [1].

- Exact pins remove the cause: without pins, pip installs the newest release on every build [2].
- The fix costs little: one command records the versions that work today.
- Updates still happen: they move to a planned cadence with tests before merge.

## Background

Your project keeps all dependencies unpinned in requirements.txt. The build broke twice last month after upstream library updates [1]. The question is whether to pin the versions.

## Relevance

Each unpinned build pulls the newest release, so every upstream release can break the build. Pins convert that random risk into a scheduled task.

## Information

Evidence:

- Two broken builds in about 30 days, each after a library update [1].
- Baseline for comparison: zero unpinned dependencies is the target state, and zero packages are pinned today [1].
- pip installs the newest matching release when the file gives no version [2].

Confidence: high, because the reported cause matches the known mechanism [2] and the fix is standard practice [judgment].

Assumption: The project uses pip with one requirements.txt. Why not measured: the material does not state the toolchain. Validate by: check for pyproject.toml or setup.cfg in the repository. If wrong: the same fix applies, but the file and commands change.

Assumption: The current main branch builds with the installed versions. Why not measured: the material does not state the current build status. Validate by: install and run the test suite in a clean environment. If wrong: fix the build first, then freeze.

Assumption: Continuous integration, that is the automated build and test service, runs on each change. Why not measured: the material does not state it. Validate by: check the CI configuration. If wrong: add CI before Step 4, or updates lose their safety check.

Alternative considered: The strongest alternative is compatible ranges, for example requests>=2,<3. It loses, because any new release inside the range still enters the build untested. That is the failure path that broke the build twice [1, judgment].

## End

I recommend that we:

1. **Pin the current working versions.** Increment: replace requirements.txt with the output of pip freeze, then verify a clean install. Blocker removed: uncontrolled version drift, the cause of both breaks [1]. Task kind: deterministic. Test, written before the work:

   Given the current working environment,
   When pip freeze output replaces requirements.txt,
   Then every package has an exact version, and a fresh virtual environment installs it without error.

   Domain: Clear, by deduction from a known best practice.

2. **Add a clean-install check to CI.** Increment: add one CI job that installs only from the pinned file in a fresh environment. Blocker removed: silent drift between the pinned file and the real build. Task kind: deterministic. Test, written before the work:

   Given a pull request,
   When CI installs from the pinned requirements.txt in a fresh environment,
   Then the install and the test suite pass before merge is allowed.

   Domain: Clear, by deduction from a known best practice. Step 2 MUST NOT start until the test in Step 1 passes.

3. **Select an update tool.** Increment: compare pip-tools and Dependabot in one page [3]. Blocker removed: no controlled path for future updates. Task kind: evaluative. Rubric, written before the work: CI integration weight 40%, hash support weight 30%, team learning cost weight 30%. Pass threshold: 70 of 100. Evidence per criterion: a short trial of each tool. Domain: Complicated, because analysis must pick between two good practices.

4. **Run planned updates as small probes.** Increment: update packages in small batches each week, capped at half a day per week. Blocker removed: security and bug fixes stay applied without surprise breaks. Task kind: stochastic. Acceptance test, written before the work: metric is unplanned build breaks, baseline is two per month unpinned [1], threshold is zero, sample size is one month of weekly updates. Stop condition: revert a batch on the first failure. Domain: Complex, because the effect of a new release is visible only afterward, so leverage here is a guess. Step 4 MUST NOT start until Steps 2 and 3 are done.

## Follow-up

Conditions that change this recommendation: if requirements.txt also serves as install metadata for a published library, keep broad ranges in the package metadata and pin only the lock file used for builds.
