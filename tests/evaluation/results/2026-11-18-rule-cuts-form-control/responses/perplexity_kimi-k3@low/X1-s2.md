# Headline

Measure the summariser before you change it: build a scored test set from real tickets, classify the errors, then fix the dominant error class first.

- "Sometimes wrong" is not actionable; a baseline error rate with an error taxonomy is.
- Most summariser failures cluster in a few classes, so the taxonomy picks the fix.
- Fine-tuning is premature because there is no data to tune on yet.
- A small human review loop keeps quality visible after launch.

# Background

The support tool now has an LLM-based summariser. Agents report it is "sometimes wrong", and no metrics exist. The request is to make it better.

# Relevance

Without a baseline, every change is a guess and regressions go unnoticed. A measurement harness converts agent complaints into ranked defects within days.

# Information

Evidence and labels:

- Abstractive summarisation errors concentrate in hallucination and omission classes; faithfulness failures are the dominant complaint in the literature [1].
- LLM-as-judge metrics correlate acceptably with human judgments for faithfulness when the rubric is explicit, which makes cheap automated scoring feasible [2] [judgment on transfer to this domain].
- "Sometimes wrong" with zero metrics means cause and effect are not visible yet, so the first action is classification, per the Cynefin Confused domain [3].

Assumption log:

Assumption: "Sometimes wrong" means factual errors (wrong facts, invented details), not style issues. Why not measured: the material does not state the failure mode. Validate by: read 30 flagged summaries with an agent. If wrong: the taxonomy in Step 1 still captures the true mode, so only Step 3's fix target changes.

Assumption: At least 200 past summaries with their source tickets can be exported. Why not measured: the material does not state data access. Validate by: run one export query. If wrong: collect live for two weeks before Step 2, delaying the baseline by about 10 working days.

Assumption: Agents can spare 2 hours each for a labeling session. Why not measured: staffing is not stated. Validate by: ask the team lead. If wrong: label with 2 senior agents instead, smaller sample, 70% likely still adequate for the taxonomy.

Alternative considered: fine-tune a model for this domain. It loses because there is no labeled training data, no baseline to beat, and the failure class is unknown; measurement is the prerequisite [judgment].

# End

Blocker removed: we cannot classify the domain or the failure modes. Kind: evaluative. 2. **Build the eval harness.** Step 2 MAY start in parallel with Step 1; its thresholds finish only after Step 1's taxonomy exists. Acceptance test written first: metric is faithfulness score; baseline is the Step 1 sample rate; pass threshold is LLM judge agreement with human labels of at least 80% on the spot check; sample size 200 [2]. If the 200-ticket export assumption is false, replace Step 2's historical scoring with two weeks of live collection and shift Steps 3 and 4 by 10 working days.
