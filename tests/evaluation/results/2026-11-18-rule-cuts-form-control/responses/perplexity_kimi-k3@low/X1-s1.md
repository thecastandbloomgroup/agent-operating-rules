# Headline

No one can improve "sometimes wrong" without measuring it first; start by building a small labeled test set and an error taxonomy, then fix the dominant failure mode. First, define what "wrong" means with agents. Next, measure error rate on real tickets. Then, fix the largest error class, and gate release on the measured rate.

# Background

An LLM summariser was added to a support tool. Agents report it is sometimes wrong. No metrics, test data, or error categories exist.

# Relevance

Changes without a baseline cannot be shown to help or harm. A single measured failure mode gives the highest return on effort.

# Information

Evidence is thin by design, so most claims here are judgment:

- Hallucination and omission are the dominant complaint categories for LLM summarisation of dialogue in the research literature [1]. Only a tertiary-to-secondary base supports this, so local measurement must confirm it.
- A test set of 100 real tickets detects a 10% absolute error reduction with adequate confidence [judgment]. Rule of thumb: a 100-sample binary check bounds the standard error near 5%.
- Manual review of 20 to 30 bad outputs is enough to build an initial error taxonomy [2]. This is standard qualitative practice: themes stabilize fast.

Assumption log:

`Assumption: Tickets and summaries can be sampled and labeled in-house. Why not measured: the material does not state it. Validate by: ask the team lead for export access. If wrong: use synthetic tickets, results less trustworthy.`

`Assumption: "Wrong" means factual errors about the ticket (wrong resolution, invented steps, missed commitments), not style. Why not measured: the user has not defined it. Validate by: the Step 1 taxonomy review with two agents. If wrong: reframe rubric categories before Step 2.`

`Assumption: A human labeler needs about 2 minutes per ticket, so 100 labels cost 3 to 4 hours. Why not measured: no time data exists. Validate by: time the first 10 labels. If wrong: shrink the set to 50 with lower statistical power.`

Alternative considered: swap to a different model immediately. It loses because, without a baseline and error categories, the swap cannot be shown to help, and it confounds prompt, data, and model changes in one step [judgment].

# End

I recommend that we:

1. **Build the error taxonomy from 20 to 30 flagged summaries.** Blocker removed: no shared definition of "wrong". Domain: Complicated, cause and effect are knowable through analysis of real failures. Kind: evaluative. Rubric first: categories are factual error, omission of a customer commitment, wrong resolution state, style; each label needs the ticket as evidence; pass threshold is agreement by two agents on 90% of a 20-sample check.

2. **Create a 100-ticket golden set and measure the baseline error rate.** Depends on Step 1 for category definitions. Blocker removed: no baseline. Domain: Complicated, analysis of labeled data. Kind: evaluative. Rubric per ticket: faithfulness (weight 0.5), completeness of commitments (0.3), correct resolution state (0.2); a ticket fails if any weighted score falls below 0.7. Record errors by category.

3. **Fix the single largest error category with a targeted prompt or context change.** Depends on Step 2 for the ranking. Blocker removed: highest-frequency defect. Domain: Complex, LLM behavior under prompt change is visible only after trials, so run as a capped probe. Budget: two working sessions. Stop condition: no improvement after two iterations. Kind: stochastic. Acceptance test first: metric is category error rate, baseline from Step 2, pass threshold is a 30% relative reduction, sample size is the 100-ticket golden set, three runs to check variance.

4. **Gate every future change on the golden set.** Depends on Step 2. Blocker removed: regressions ship silently. Domain: Clear, a best practice (regression testing) applies directly. Kind: deterministic.

   Given a prompt or model change,
   When the evaluation runs on the 100-ticket golden set,
   Then the total failure rate MUST NOT exceed the Step 3 result.

5. **Add a one-click "summary is wrong" button with a reason dropdown in the agent UI.** Blocker removed: no ongoing error feedback in production. Domain: Complicated, standard instrumentation analysis applies. Kind: deterministic.

   Given an agent views a summary,
   When the agent clicks the flag button and picks a Step 1 category,
   Then the ticket ID, summary, and category MUST be stored for review.

# Follow-up

Conditions that change the recommendation: if the ticket export assumption fails, replace the golden set with synthetic tickets and treat all thresholds as provisional. If Step 2 shows an error rate below 5%, skip Step 3 and invest in Step 5 monitoring instead.
