## Headline

Retro outputs die because actions lack owners, limits, and follow-up, so fix the action pipeline first.

- Run one quick diagnostic to find the real blocker before changing the format.
- Cap each retro at one or two actions with named owners and deadlines.
- Open every retro by scoring the previous actions, so the loop closes.

## Background

Your retrospectives (short team meetings to review work and improve) run but produce no change. Attendance is fine. Follow-through is broken.

## Relevance

A retro that changes nothing trains people to disengage. Each empty cycle lowers trust in the process, so the cost compounds with each sprint.

## Information

**Diagnosis.** The three common causes are mutually exclusive and cover the space:

1. Actions are vague ("communicate better") and untestable.
2. Actions exist but nobody owns them or they exceed team authority.
3. Actions are completed but never reviewed, so nobody sees impact.

Which one applies is unknown. The cheapest test is a five-question anonymous poll, one working session to run.

**Evidence.** Retrospective research and practitioner guidance agree on two themes: committing to few action items (one or two) raises completion, and reviewing prior actions at the next retro raises follow-through [1]. Count of supporting sources: two; no disagreeing source found. These are secondary sources, per Section 5.4 rules.

**Assumption log.**

`Assumption: The team runs retrospectives regularly (every 1 to 4 weeks). Why not measured: the material does not state it. Validate by: ask the facilitator. If wrong: fix cadence first, then apply the steps.`

`Assumption: The team has authority to change its own work process. Why not measured: the material does not state it. Validate by: one question in the poll ("Can the team change this without approval?"). If wrong: route top blocker to the manager each sprint.`

**Alternative considered.** Stop holding retros and use continuous feedback instead. It loses because the failure is in follow-through, not in the meeting format; continuous feedback without ownership fails the same way [judgment].

## End

I recommend that we:

1. **Diagnose once.** Send a five-question anonymous poll today. Blocker removed: unknown cause. Kind: deterministic.
   - Given the poll has the three cause options from the Information section, When at least 70% of the team answers, Then the causes are ranked by vote count.
2. **Limit to one or two actions per retro.** Each action names an owner, a deadline, and a visible test. Blocker removed: vague, unowned actions. Kind: deterministic.
   - Given a retro produces an action, When the meeting ends, Then the action has one owner, one date, and one sentence stating the expected result.
3. **Open each retro with an action review.** Score each prior action: done, dropped (with reason), or in progress. Blocker removed: no visible feedback loop. Kind: evaluative. Rubric: completion rate (weight 1, evidence: action list), pass threshold 60% of actions done within one sprint, per team-improvement guidance [1]. This step MUST NOT start until at least one retro has produced actions under step 2.
4. **Run one retro as a capped probe.** Try one format change (for example, silent writing for ideas, then dot voting) for one retro. Measure action completion versus the prior baseline. Stop condition: revert if completion falls. Budget: one meeting. Cynefin domain: Complex, because team reaction is visible only afterward (induction; the pattern breaks if the prior failure was about authority, not format). Leverage is a guess.
5. **Escalate out-of-reach blockers.** Each sprint, send the top blocker the team cannot fix to the manager, in writing. Blocker removed: actions die at the authority boundary. Kind: deterministic. Cynefin domain: Complicated; practitioner analysis shows constraints sort into team-level and org-level [1].
   - Given the action list, When an action needs approval outside the team, Then it goes in the manager note the same day.

Steps 1 to 3 are Clear domain: cause and effect are known best practices. Step 4 runs in parallel with steps 2 and 3, capped at one meeting.

## Follow-up

Condition that changes the recommendation: if the poll shows most actions die at the authority boundary, drop step 4 and put step 5 first.
