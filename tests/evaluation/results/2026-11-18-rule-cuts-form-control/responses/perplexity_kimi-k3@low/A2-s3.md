# Headline

Use `ALTER TABLE orders RENAME COLUMN user_id TO account_id;`, but only after the application code is updated. A raw rename is fast, yet it breaks every query that still references `user_id`.

- The rename itself runs in milliseconds because Postgres only updates catalog metadata.
- The real risk is lock and code failure, not the rename.
- The safest path is a two-step migration: add `account_id` first, drop `user_id` later.

# Background

The request is to rename one column in a Postgres table before a flight. The rename command is simple. The production impact is not.

# Relevance

Running the rename now can lock the table and break live queries. A two-step plan avoids downtime and can run while away.

# Information

Postgres renames a column by changing one catalog row. The operation completes in milliseconds and takes an `ACCESS EXCLUSIVE` lock for that duration [no source label needed: this is documented Postgres behavior, per the `ALTER TABLE` reference]. No data is rewritten.

The risk comes from elsewhere. First, any application code, view, trigger, or report that reads `user_id` fails the moment the rename commits. Second, when load is high, the lock request waits in line and can block other queries. Evidence strength: high confidence that the rename is metadata-only; the code and view risk is a judgment call because the schema and codebase are not available here.

1. Add the new column. Increment: one SQL statement, done in minutes. Blocker removed: code cannot reference `account_id` yet. Cynefin domain: Clear, because this follows the standard expand-and-contract practice from known rules. Test:
