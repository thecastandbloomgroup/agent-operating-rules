**Headline**
Build the measurement first, then fix the failure mode with the highest rate under a controlled test.
- The report "sometimes wrong" names no failure type, so it cannot guide a change to the prompt or the model.
- A log of generated summaries beside agent final texts creates a quality baseline within 10 working days.
- Changes without a baseline cannot be verified, so the log must come before any fix.

**Background**
The support tool produces a summary of each case with a language model. Agents report that some summaries are wrong, but the reports do not say which kind of wrong. The team has no error metrics and no baseline.

**Relevance**
Every prompt change is unverifiable until a baseline exists. A measured fix also restores agent trust, because each report becomes a counted error instead of an opinion.

**Information**

Analysis. The first blocker is the absence of data, not the model itself [inference]. Summariser errors fall into a small set of classes [judgment]: factual error (the summary states a fact the record does not support), omission (the summary drops a load-bearing item, for example a promised callback), and wrong focus (the summary covers trivia and skips the blocker). The classes do not overlap, and each pair gets one main label, so the set covers the whole. Therefore the work splits into capture, judgment, measurement, and one capped trial; these four parts do not overlap and cover the path from no data to a verified fix.

Assumption log.
- A1. Agents are a reliable judge of summary quality. Why not measured: the material gives no calibration data. Validate by: compare downvotes against edit distance in Step 1. If wrong: replace agent labels with a sampled manual review.
- A2. The tool handles at least 50 cases in 10 working days with a summary and an agent edit. Why not measured: the user gave no volume. Validate by: query the case count once logging starts. If wrong: extend the window to 20 days.
- A3. The three error classes above cover most failures. Why not measured: no taxonomy exists in the material. Validate by: Step 2 labeling, with an "other" box. If wrong: expand the taxonomy before Step 4.

Alternative considered. Remove the summariser and return to manual summaries. It loses because agents pay back the writing time on every case, and the error rate is unknown, so removal has no supporting evidence [inference].

Reason check. The End section listed four domain labels. Two reasons needed correction, so the revised section below states them again in full. Step 1 was labeled Confused with the reason "so data decides the rest"; the reason did not name what is unclassifiable, and it now does. Step 2 was labeled Complicated with the reason "the taxonomy does not yet exist"; a missing taxonomy is not a domain reason, and the reason now names the expertise that the labeling step needs.

**I recommend that we** run the following four steps in order.

1. **Log real pairs (Cynefin: Confused; the failure type and severity remain unclassified, so this step gathers the data needed to classify the problem. Deterministic action.)** Instrument the tool so it stores, for each case, the generated summary, the agent final text, the edit distance, and a timestamp. Increment: logger live in one working session. Blocker removed: no data exists, so no claim about quality can be tested. Test first, in Gherkin form [14]:
   Given a case with a generated summary,
   When the agent saves the final text,
   Then the log stores the pair with the case number and the timestamp.
   Run this step for 10 working days to collect at least 50 pairs.

2. **Label the pairs with a rubric (Cynefin: Complicated; more than one labeling method exists and trained judgment picks the labels, so the rubric plus double review selects the practice through expertise. Evaluative action.)** Build the rubric, then score 50 pairs in one working session. Blocker removed: unclassified agent reports become a ranked list of failure types. Rubric first: criteria are factual accuracy (weight 0.5), completeness (weight 0.3), and focus (weight 0.2); pass threshold is a total score of 0.8; evidence is one mark per item on every pair, plus a second reviewer on a 10-pair sample. Step 2 MUST NOT start before the log in Step 1 holds 50 pairs.

3. **Define the metrics and the acceptance threshold (Cynefin: Clear; the rates follow from labeled counts by a known rule, so the step applies a best practice through deduction. Deterministic action.)** Increment: a one-page metric sheet in one working session. Blocker removed: quality becomes a number, so agent reports can be confirmed or rejected. Test first:
   Given the labeled pairs from Step 2,
   When the pipeline computes the metrics,
   Then it reports the factual error rate, the omission rate, and the focus error rate, each with the sample size.
   Baseline: the rates from Step 2, measured per error type; the goal state is a factual error rate near zero [judgment for the target].

4. **Probe a fix for the top failure mode (Cynefin: Complex; the effect of a prompt change shows only after the trial, so the reason is induction from trials. Stochastic action, capped.)** Increment: one prompt change, tested on the next 50 logged pairs. Blocker removed: the highest-rate error type shrinks. Acceptance test first: metric, factual error rate [15]; baseline, the Step 2 rate [16]; pass threshold, at most half the baseline error count at a sample of 50 pairs [judgment for the threshold]. Budget: two prompt iterations over two weeks. Stop condition: no improvement after two iterations, then re-classify the error type instead of another prompt change. Step 4 MUST NOT start before Step 2 ends.

**Follow-up**
Condition that changes the recommendation: if A1 fails and agent edits do not track agent reports, replace agent labels with a sampled manual review in Step 2 and re-run it monthly.
Condition that changes the recommendation: if A2 fails and 50 pairs need more than 20 days, shorten the metric sheet to the two error types with the highest counts.
Condition that changes the recommendation: if the factual error rate is already below 0.05 per summary after Step 2, the feature performs at a tolerable level, so ship agent-facing feedback buttons instead of prompt work.
