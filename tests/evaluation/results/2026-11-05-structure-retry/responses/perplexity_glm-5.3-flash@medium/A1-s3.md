- The Cynefin framework defines the Complex domain as cause and effect that become visible only after the fact, and it prescribes safe-to-fail probes with measures and budgets that run beside the other work [3].

**End**

I recommend that we pin every version, generate a lock file, gate the merge on it, and run upgrades as capped probes. Actions, in order, with the probe in parallel:

1. Pin each direct dependency with `==` and the exact version in requirements.txt.
   - Increment: one edited file, one session. Blocker removed: a different version set on each install.
   - Kind: deterministic. Test, written first:
     ```gherkin
     Given a clean virtual environment
     When pip install -r requirements.txt runs
     Then pip freeze lists only versions named in requirements.txt
     ```
   - Cynefin domain: Clear. Reason: pip defines the pin rule, so the fix is a deduction from that rule [1].

2. Generate a lock file with `pip-compile` from the direct pins [2]. A lock file is a file that stores the complete resolved version set.
   - Increment: one generated file plus one build command. Blocker removed: uncontrolled transitive dependencies.
   - Kind: deterministic. Test, written first:
     ```gherkin
     Given a clean environment built from the lock file
     When a second clean environment installs the same lock file
     Then the two pip freeze outputs match line for line
     ```
   - Cynefin domain: Complicated. Reason: analysis must pick one tool among pip-compile, Poetry export, and uv; the pattern breaks if the chosen tool resolves a different set than pip installs, and the double-install test above guards against that [2].

3. Add a continuous integration (CI) job that builds from the lock file in a clean environment on every merge.
   - Increment: one pipeline job. Blocker removed: unreviewed version drift entering the main branch.
   - Kind: deterministic. Test, written first:
     ```gherkin
     Given a merge that touches the lock file
     When the CI job builds a clean environment and runs the test suite
     Then the merge fails when either step fails
     ```
   - Cynefin domain: Clear. Reason: an exact-match gate blocks unreviewed updates by a known rule, so this is a deduction.
   - Dependency: Step 3 MUST NOT start until Steps 1 and 2 pass their tests.

4. Run a monthly upgrade as a safe-to-fail probe with `pip-compile --upgrade`, the full test suite, and revert on failure [2].
   - Increment: one upgrade cycle per month. Measure: the count of changed packages per cycle. Budget: one hour. Stop condition: revert on any test failure. Blocker removed: pins that grow stale.
   - Kind: stochastic. Acceptance test, written first, with metric and baseline: metric is the test suite result; baseline is the passing suite on the current pins; threshold is zero failures; sample size is one suite run per cycle.
     ```gherkin
     Given an upgraded lock file
     When the full test suite runs in a clean environment
     Then the upgrade branch merges only when the suite passes
     ```
   - Cynefin domain: Complex. Reason: which upstream version breaks the build becomes visible only after the suite runs, so this is induction from trials; the pattern breaks if a slow or flaky test hides a failure, and the one-hour cap with revert bounds that risk. Leverage here is a guess.
   - Dependency: this probe runs in parallel with Step 3, and it starts only after Step 2 passes [3].

**Follow-up**

Conditions that change the recommendation: if installs come from a pre-built container image or a fully frozen cache, pin that artifact instead, because requirements.txt then adds little on its own. No further questions.
