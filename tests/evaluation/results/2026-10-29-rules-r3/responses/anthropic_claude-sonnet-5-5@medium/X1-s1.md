## Headline

I recommend a measure-first plan: log feedback, label errors, then test one capped prompt change against a baseline.

- Agents report errors, but no number shows how often or what kind, so no change can be judged yet.
- The error types decide the fix, so labeling a sample comes before any change.
- One small, capped test of a prompt change checks the most likely fix at low cost.
- No change ships until it beats the measured baseline.

## Background

Your team added a summariser built on a large language model (LLM) to the support tool. Agents say it is "sometimes wrong". You have no metrics, and the request is to make it better.

## Relevance

An agent who trusts a wrong summary can give a customer wrong advice. An agent who distrusts it loses the time the tool should save.

## Information

**Evidence**

- The query states that no metrics exist, so the error rate is unknown (per the query, no tool output).
- LLM summaries are known to contain invented or unsupported content [1].
- Therefore the likely error types are invented facts, missing facts, and wrong names, numbers or dates. This is a [judgment], at moderate confidence, because no sample has been read yet.
- Only tertiary-level knowledge supports the claim that a "quote exact details" prompt reduces errors, so [no source] exists for its effect here. The probe in Step 4 tests it.

**Assumption log**

A1. The summaries and their source tickets are stored and readable. Why not measured: the material does not state it. Validate by: open five recent tickets. If wrong: Step 2 starts with storage, and Step 1 waits.

A2. Agents mean factual errors, not style, when they say "wrong". Why not measured: the user has not answered. Validate by: the labels from Step 1. If wrong: change the rubric weights in Step 1 and the metric in Step 3.

A3. One team lead can spend two hours on review. Why not measured: the user has not answered. Validate by: ask the lead. If wrong: cut the sample in Step 1 from 50 to 25.

**Alternative considered**

The strongest alternative is to switch to a larger model now. It loses because no baseline exists to show that it helps, and it raises cost per summary [judgment]. Revisit it if the Step 4 probe fails.

## End

I recommend that we take these steps, in this order:

1. **Label a sample of errors.** Cynefin domain [2]: Confused. Kind: evaluative.
   - Increment: one lead reads 50 recent summaries against their tickets and labels each error.
   - Blocker removed: we cannot classify the problem without error types.
   - Rubric, written first: invented fact (weight 40), missing key fact (30), wrong name, number or date (20), other (10). Pass: all 50 labeled, and a second reader agrees on at least 80% of 10 shared items [judgment].
   - Evidence per criterion: a quote from the ticket text next to the summary line.
2. **Add a feedback button and a log.** Cynefin domain: Clear. Kind: deterministic.
   - Increment: add a "Wrong" button with a reason list, and store each click.
   - Blocker removed: no ongoing metric exists.
   - Test, written first (Gherkin [3]):

```gherkin
Scenario: Agent flags a wrong summary
  Given an agent views a summary for a ticket
  When the agent selects "Wrong" and a reason
  Then the system stores the ticket id, summary id, model version, prompt version and reason
```

   Step 3 MUST NOT start until this test passes and Step 1 is complete.

3. **Build a test set and measure the baseline.** Cynefin domain: Complicated. Kind: stochastic.
   - Increment: take 100 tickets, write the key facts for each, and score the current summaries.
   - Blocker removed: no baseline exists.
   - Acceptance test, written first: the metric is the share of summaries with at least one factual error. The baseline is the Step 3 result. The sample size is 100 tickets. The step passes when the baseline is recorded with the rubric from Step 1.
   - Analysis that picks the practice: use the Step 1 error types to choose the key facts to score.

4. **Run a capped prompt probe.** Cynefin domain: Complex. Kind: stochastic. Leverage is a guess.
   - Increment: change the prompt so names, numbers and dates are copied from the ticket, then score the same 100 tickets.
   - Blocker removed: it tests the most likely cause of wrong details.
   - Acceptance test, written first: metric is the error share from Step 3. Pass: at least a 30% relative drop [judgment] at 100 tickets. Budget: one working day. Stop condition: no drop after two prompt versions.
   - Run Step 4 in parallel with Step 2. Step 4 MUST NOT ship to agents until it passes. Then repeat the measure on live feedback from Step 2.
