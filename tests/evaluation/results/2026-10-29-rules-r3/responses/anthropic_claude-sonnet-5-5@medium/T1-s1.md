## Headline

Remove formatting from human review: pick one automated SQL formatter, enforce it in CI, and ban style comments in reviews.

- The dispute is about taste, and no style is objectively right, so a tool should decide it. [judgment]
- A formatter gives the same output for the same input, so it ends the argument.
- A written review rule keeps the old habit from returning.
- A short measured trial shows whether the friction is gone.

## Background

Your team has no shared SQL format. Each review includes style debates. You ask for a fix to the culture problem.

## Relevance

Every style comment costs reviewer time and builds resentment. The friction grows with each pull request (PR) until a rule or a tool ends it.

## Information

Evidence:

- Formatting comments are not a defect signal, so a tool can own them without losing review quality. [judgment]
- Team size, tooling, and the count of style comments per PR are unknown. [no source]

Alternative considered: hold a style-guide workshop and vote on every rule. It loses because people keep arguing and humans enforce the result. A formatter enforces it with no debate. [judgment]

## End

I recommend that we take these steps in order:

1. **Choose one formatter (Complicated, evaluative).** Increment: score three candidates on 10 real files in one session. Candidates are SQLFluff, sqlfmt, and pg_format. Blocker removed: no agreed tool.
   - Rubric (weights sum to 100): dialect support 40, same output on rerun 25, CI and editor support 20, configurability 15.
   - Evidence per criterion: a run on the 10 files.
   - Pass threshold: 75. The highest score wins. The lead breaks ties. Write this rubric before the runs.

2. **Automate it (Clear, deterministic).** Increment: add the formatter to pre-commit and CI, plus one reformat-only commit. Blocker removed: manual enforcement. Step 2 MUST NOT start until Step 1 ends.
   - Test, written first:
     - Given a SQL file with mixed style
     - When the formatter runs twice
     - Then the second run changes nothing
     - And CI fails on an unformatted file

3. **Write the review rule (Clear, deterministic).** Increment: a one-page rule in the repository. Blocker removed: style debate in PRs.
   - Rule text: reviewers MUST NOT comment on formatting. Change the tool config through a PR with lead approval.
   - Test, written first:
     - Given the rule file exists
     - When a new engineer reads it
     - Then they can state who changes style and how

4. **Run a four-week trial (Complex, stochastic probe).** Increment: count style comments per PR. Blocker removed: no proof the culture shifted. Leverage is a guess.
   - Count the baseline in the last 20 merged PRs before Step 2 merges.
   - Acceptance test: style comments per PR fall by at least 80% from the baseline, over at least 20 PRs.
   - Budget: 30 minutes per week. Stop and revisit the rule if the count does not fall after 20 PRs.
   - Run this step in parallel with Steps 2 and 3.

If A3 is false, add a step before Step 1: ask the engineering manager to name the style owner.
