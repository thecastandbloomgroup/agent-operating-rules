## Headline

I recommend that we measure the flake rate first, then fix by cause, because the cause of the failures is not yet known.

- The request gives no logs, so the cause is unknown (see A1 to A3).
- Published data show that flaky tests are common and that a few causes explain most of them.
- A measured rate gives a baseline, so we can prove that each fix works.

## Background

A flaky build passes and fails on the same code. The request states only that the build is flaky. It gives no logs, no failure rate, and no tool names.

## Relevance

Flaky builds hide real defects and waste developer time on reruns. Each unexplained failure also lowers trust in the build signal.

## Information

Evidence:

- Google reported that about 1.5% of all test runs showed a flaky result. [1]

- Google also reported that almost 16% of its tests had some flakiness. [1]

- In a study of 201 fixes, async wait caused 45% of flaky tests, concurrency 20%, and test order 12%. [2]

- Both sources study large code bases, so the rates for your build may differ. [judgment]

- Theme: two sources agree that a small set of causes explains most flakiness. No source in this session disagrees. Confidence is medium, two independent sources.

Alternative considered: add automatic retries to all tests now. It loses because retries hide the cause and raise build time. The flake rate stays unknown. [judgment]

3. **Quarantine the confirmed flaky tests.** Quarantine means to move a test to a separate run that does not block the build. Cynefin domain: Clear, because this is a known practice. Kind: deterministic.

4. **Run a probe on the top cause.** Cynefin domain: Complex, because the effect of a fix shows only after reruns. Kind: stochastic. Leverage is a guess.
