## Headline

Measure before you change: label 50 recent summaries, build a fixed 30-ticket test set, fix the dominant error type, and retest against a set threshold. The support points:

1. "Sometimes wrong" is a data point, not a metric; without a baseline you cannot tell whether a prompt change helps.
2. An error analysis will show which failure type dominates: content not in the ticket, content missing, or content hard to use.
3. A fixed test set turns each prompt change into a pass or fail result at a stated sample size.
4. A report button in the tool keeps data flowing after the first round of fixes.

## Background

You added an LLM summariser to a support tool. Agents report that it is sometimes wrong. No metrics exist, so no one can say how often it fails or in which way. The request is to make it better.

## Relevance

Agent trust in the tool falls while the errors stay unexplained [inference]. A measured baseline lets each change be judged against evidence, so the next prompt edit is not a guess.

## Information

**Taxonomy.** Split summariser failures into three parts that do not overlap [judgment]:

1. Unfaithful: the summary states a fact that is not in the ticket.
2. Incomplete: the summary omits a fact that an agent needs.
3. Unclear: the facts are present but hard to read or use.

This split covers content added, content missing, and content present. Grouping agent comments into themes counts which type dominates [3].

**Evidence.**

- Agents say the tool is "sometimes wrong": 1 source (your message), type unknown. This is a theme with one source; it still matters because it is first-hand use [3].
- Error rate, error type, and baseline: no data exists [no source].
- Stochastic output needs a stated metric, baseline, threshold, and sample size before changes are judged [judgment].
- Probe-first ordering fits settings where cause shows only after the effect [18].

**Assumption log.**

A1. "Wrong" means unfaithful or incomplete content, not style. Why not measured: the material does not state it. Validate by: the Step 1 labels. If wrong: replace Step 3 with a format template change.

A2. Ticket transcripts and summaries are stored and retrievable. Why not measured: no tool access in this session. Validate by: pull 50 pairs from the log. If wrong: log transcripts first; all steps shift one week.

A3. Agents can give 2 hours in one week for labelling. Why not measured: not answered. Validate by: ask the team lead. If wrong: use 25 tickets and a single label per ticket.

**Alternative considered.** Rewrite the prompt now, without measurement. It loses because the output is stochastic: with no baseline and no test set, no one can tell whether the new prompt is better [judgment]. Confidence: medium; no measurement exists yet, and the taxonomy is untested.

## End

I recommend that we run four steps in this order.

1. **Label 50 recent summaries with the taxonomy.** This removes the biggest blocker: the unknown failure mode. Rubric first: criteria are the three error types, weights equal, pass when labelling covers 50 pairs, evidence is the two-agent labels per ticket. Budget: 2 agent-hours. Stop condition: halt if fewer than 20 pairs are retrievable and report A2 as false. Domain: Complex; the dominant error type is a probe outcome, so leverage is a guess. Kind: evaluative.

2. **Build a test set of 30 labelled tickets and a check script.** This adds the capability to reproduce results. Step 2 MUST NOT start before 30 tickets from Step 1 carry two complete labels. Test in Gherkin [14]:

   ```gherkin
   Given the test set of 30 tickets
   When the check script runs twice on the same summaries
   Then it reports the same count of unfaithful, incomplete, and unclear errors both times
   ```

   Domain: Clear; a best practice exists, so apply it. Kind: deterministic.

3. **Change the prompt against the dominant error type.** Add a grounding rule: use only ticket facts, and fill a fixed field list (topic, cause, action taken, next action). Then rerun the test. Step 3 MUST NOT start before the Step 2 script passes. Acceptance test first: metric is the share of error-free summaries, baseline is the Step 1 error rate, threshold is error share cut by half, sample size is n = 30, one prompt version per run. Domain: Complex; one change per test cycle, capped at one run per day. Kind: stochastic.

4. **Add a report button to the tool.** This adds continuous data after the first fix. It runs in parallel with Step 3. Test:

   ```gherkin
   Given a summary shown to an agent
   When the agent clicks report and picks a type
   Then the ticket id, the summary, and the type appear in the log within 1 minute
   ```

   Domain: Clear. Kind: deterministic. Review the flags weekly; cluster them by type [3].
