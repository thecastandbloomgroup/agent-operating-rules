## Headline

Stop solving a culture problem, because the problem is actually missing automation. Enforce one SQL format with a tool, and the review friction ends.

- The team disputes rules that a machine can decide, so a tool that decides them removes the dispute at the source.
- First, pick one formatter with a written rubric, so the choice is a decision, not another debate.
- Second, format the whole codebase once, then check that format in CI.
- Third, run a measured probe on the review norms, so the human habit change is tested, not assumed.

## Background

The team disagrees on how to format SQL. Every code review reopens the debate, so reviews slow down and reviewers spend attention on style. The request is to fix the team culture around this.

## Relevance

Every pull request pays this cost today. One tool change removes the cost and keeps it removed, because the tool produces the same output for the same input [1].

## Information

**Evidence.** A formatter turns a style opinion into a fixed output. The Prettier project built its tool on that design: remove the choices, and people stop arguing about them [1]. sqlfluff supports the major SQL dialects and a configurable rule set, so one tool can cover a team codebase [2]. Theme from qualitative evidence: "removed choice reduces style disputes"; 1 source supports it [1]; no disagreeing source was found in this session [no source]. Comparison against a baseline: today, two team members produce different output for the same query; after the change, their outputs are identical [judgment]. Confidence is high, because the enforcement is deterministic by design, not a social intervention [1].

**Assumption log.**

- `A1. The codebase uses one dominant SQL dialect (PostgreSQL, MySQL, or a cloud warehouse variant). Why not measured: the material does not state it. Validate by: grep the connection strings and file headers in the repo. If wrong: configure per-dialect rules; the recommendation holds.`
- `A2. The team can add dev tooling and a repo config file. Why not measured: the material does not state it. Validate by: ask the repo owner about policy in one message. If wrong: use the editor plugin alone, which is weaker but still removes the debate.`
- `A3. The repo runs CI on pull requests. Why not measured: the material does not state it. Validate by: check for a CI config file in the repo root. If wrong: fall back to the pre-commit hook plus review. See 3.8 in Follow-up.`

**Alternative considered.** Write a style guide by hand and reach consensus in a workshop. It loses because it costs hours per person and still needs manual enforcement in every review [judgment]. The tool path costs one configuration file and enforces itself [1].

## End

I recommend that we:

1. **Select the formatter (Complicated, evaluative).** Increment: in one hour, score two candidates (sqlfluff [2] and one other) against a written rubric: dialect match (weight 40), CI support (30), rule fit to current code (30); pass threshold 7 of 10; store the rubric and the result in the repo. Blocker removed: "which tool" becomes a scored decision. Test written first: `Given two candidates scored on the rubric, When the weights are applied, Then the higher total is chosen and recorded.`
2. **Format the codebase once (Clear, deterministic).** Step 2 MUST NOT start until Step 1 records a choice. Increment: one pull request that runs the tool over every SQL file, reviewed only for the shape of the diff. Blocker removed: existing drift across the repo. Test written first: `Given the pinned config, When the formatter runs on any file twice, Then the output is identical; and Given the repo, When the check runs, Then it reports zero violations.`
3. **Enforce the format (Clear, deterministic).** Step 3 MUST NOT start until the test in Step 2 passes. Increment: add a CI check and a pre-commit hook [3] on SQL files in one working session. Blocker removed: unformatted code can no longer reach a review. Test written first: `Given a pull request with a file that fails the check, When CI runs, Then the build fails and names the file and line.`
4. **Probe the review norms (Complex, stochastic).** Step 4 MUST NOT start before Step 3 runs in CI. Increment: one edit to the review guide that says style is the tool's job; reviewers comment on correctness, performance, and schema design. Blocker removed: reviewers keep authority over what the tool cannot check. Test written first: metric = tool-checkable style comments per review; baseline = count from the last 10 reviews; pass threshold = at least an 80% drop; sample size = the next 10 reviews. Stop condition: if style disputes persist in 3 of 10 reviews, run one 30-minute session to amend the tool config, not the norms. Budget: one doc edit and two weeks. Leverage is a guess, because behavior has no cause and effect you can read in advance [judgment].

## Follow-up

**Conditions that change the recommendation:**

- If A3 is false (no CI), enforcement rests on the hook and on review; the probe in Step 4 then carries more of the load.
- If A1 is false (two or more dialects), use per-dialect rule sets in one config; the four steps stay the same.
