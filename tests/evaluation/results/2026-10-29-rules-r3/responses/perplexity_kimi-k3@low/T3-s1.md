# Headline

Migrate authentication to JWT with short-lived access tokens and rotating refresh tokens, and treat sign-up conversion as a separate measured experiment.

- Split auth migration from conversion work because one changes security state and the other changes funnel behavior [judgment].
- Use access tokens under 15 minutes and refresh tokens under 30 days as a starting baseline [1].
- Keep server-side revocation and logout until token rotation and reuse detection pass [judgment].
- Run sign-up changes as capped A/B probes because attribution is noisy [judgment].

## Background

The request combines an auth architecture change with a growth target. These have different failure modes, owners, and tests.

## Relevance

A weak token design can break logout, password reset, and account takeover defense. A weak sign-up test can report gains that do not persist.

## Information

A1. Stack is a web or SPA first service using an API gateway, PostgreSQL or Redis, and email based sign-up. Why not measured: the material does not state it. Validate by: inspect deployment manifest and one login trace. If wrong: keep session compatibility for one release.

A2. Mobile native clients exist or will exist within 6 months. Why not measured: measuring costs more than this planning pass. Validate by: check mobile repository login flow. If wrong: use browser cookies only and drop native refresh token work.

A3. Current sign-up conversion baseline is unknown. Why not measured: the material does not state it. Validate by: query completed sign-ups divided by sign-up starts for 28 days. If wrong: defer experiment until baseline collection reaches 1,000 starts per arm [judgment].

Claims: JWT is a claims format, not a session store [1]. JWT libraries need strict algorithm, issuer, audience, and expiry checks [2]. Session fixation, CSRF, and cookie rules still apply around login and refresh flows [3]. Conversion lift claims need an experiment baseline; no numeric lift is asserted here [judgment].

Alternative considered: keep sessions and add Redis replication. It loses for cross-service and mobile scale because each request still needs shared session state, while JWT verification can use public keys at the edge [1], [judgment].

Sequencing: Step 2 MUST NOT start until Step 1 threat model passes. Step 4 probes SHOULD run in parallel after Step 3 shadow verification passes, each capped at 5% traffic and 14 days.
