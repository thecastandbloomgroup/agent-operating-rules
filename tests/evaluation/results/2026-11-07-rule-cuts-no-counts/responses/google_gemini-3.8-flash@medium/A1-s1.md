### Headline

We should pin exact package versions in a compiled requirements lockfile immediately.
First, unpinned builds introduce breaking upstream changes without warning.
Second, pinned dependencies ensure repeatable and identical builds across all environments.
Third, automated dependency update tools allow controlled version upgrades with automated tests.

### Background

Your Python project has unpinned dependencies in requirements.txt.
Two upstream library updates broke the build last month.
You asked if the team should pin package versions in requirements.txt.

### Relevance

Broken builds block team delivery and waste engineering time.
Pinning versions restores build reliability today.

### Information

Unpinned dependencies cause non-deterministic builds [judgment].
Upstream package authors release changes that can break existing APIs without notice [1].
The Python Packaging Authority advises applications to pin exact versions for deployment [1].
Furthermore, modern packaging guidelines distinguish abstract dependencies from concrete lockfiles [2].
Concrete lockfiles record the exact version and hash of every transitive dependency [2].
Because of this separation, teams maintain top-level dependencies in one file and compile an exact lockfile for installation [2].

Assumption: The project is an application or service rather than an open-source library.
Why not measured: The material does not state it.
Validate by: Check if the repository contains deployment files or a package build script.
If wrong: Distribute abstract ranges in pyproject.toml and pin versions only for integration tests.

Alternative considered:
Keep dependencies unpinned and run daily integration tests to detect breaks early.
This alternative loses because it still allows random deployment failures during production rollouts [judgment].
