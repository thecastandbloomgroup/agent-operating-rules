## Headline

Measure the summariser first, because the team cannot improve an error rate it has not measured.

- No metric exists, so "sometimes wrong" cannot guide a fix (per the user's message).
- The error types are unknown, so a model or prompt change now would be a guess.
- Agent feedback is the cheapest data source and no tool collects it yet.
- After a baseline exists, small controlled trials can test fixes.

## Background

The team added an LLM-based summariser (a language model that writes ticket summaries) to its support tool. Agents report that it is "sometimes wrong". The team has no metrics and asks for a better summariser.

## Relevance

Agents who distrust summaries will stop using them or will re-read every ticket. Either outcome removes the time saving.

## Information

**Evidence**
- Agents report errors, but no rate, type, or severity is known (per the user's message).
- The team has no metrics (per the user's message).
- Error types in LLM summaries commonly include omissions and invented facts [judgment].
- Agent comments group into themes by thematic analysis [1]. This step is the base of the first action.
- At 100 rated summaries, the 95% margin on a 50% rate is about 10 points [judgment, standard binomial approximation].

**Assumption log**
- Assumption: The tool stores the ticket text and the summary. Why not measured: the material does not state it. Validate by: query 10 recent tickets. If wrong: add storage before Step 2.
- Assumption: Agents will rate summaries during work. Why not measured: the user has not answered. Validate by: pilot with 5 agents for one day. If wrong: sample summaries and ask a reviewer to rate them.
- Assumption: A wrong summary causes no safety harm. Why not measured: the material does not state it. Validate by: ask the support lead. If wrong: add a Chaotic stabilise step (disable the summary for the affected ticket type) before all other steps.

**Alternative considered**
- Switch to a larger model now. It loses because the cost is high and the error cause is unknown [judgment]. A bigger model may not fix omissions that come from the prompt.

## End

I recommend that we:

1. **Label a sample of errors.** Increment: two reviewers rate 50 recent summaries in one session and tag each error as omission, invented fact, wrong attribution, or other.
   - Blocker removed: the error types are unknown.
   - Kind: evaluative. Cynefin: Confused. The first action must gather what is needed to classify the problem. The step gathers facts, so it uses neither deduction nor trials.
   - Rubric, written first:
     - Coverage: at least 90% of errors fit a category (weight 50).
     - Agreement: the two reviewers agree on at least 80% of tags (weight 30).
     - Evidence: each category has at least one ticket example (weight 20).
     - Pass threshold: a weighted score of 80 or more.
   - Step 2 MUST NOT start until this rubric passes.

2. **Add a feedback control.** Increment: add a "wrong summary" button with a reason list that uses the Step 1 categories.
   - Blocker removed: no ongoing data flows from agents.
   - Kind: deterministic. Cynefin: Clear. The task is known practice, so apply deduction from the known rule.
   - Test, written first:

     ```gherkin
     Given an agent views a ticket summary
     When the agent clicks "wrong summary" and picks "invented fact"
     Then the system stores the ticket id, summary id, reason, and time
     ```

3. **Set the baseline.** Increment: rate 100 random summaries with the Step 1 categories and compute the error rate.
   - Blocker removed: no baseline exists to judge any change.
   - Kind: stochastic. Cynefin: Complicated. Analysis picks the sampling method, so the inference is deduction from sampling statistics.
   - Acceptance test, written first:
     - Metric: share of summaries with at least one factual error.
     - Baseline: measured in this step.
     - Pass threshold: the 95% interval is 20 points wide or less.
     - Sample size: 100.
   - Step 4 MUST NOT start until this test passes.

4. **Run one capped prompt probe.** Increment: change one prompt line to require the summary to quote ticket text for each fact. Release it to 10% of agents for 5 working days.
   - Capability added: evidence on whether a prompt change lowers errors. The leverage is a guess [judgment].
   - Kind: stochastic. Cynefin: Complex. The effect shows only after trials. The inference is induction from trials. The pattern could break if ticket types change during the trial.
   - Acceptance test, written first:
     - Metric: error rate from Step 3 ratings.
     - Baseline: the Step 3 result.
     - Pass threshold: a relative drop of 30% or more.
     - Sample size: 100 rated summaries per group.
   - Stop condition: the error rate rises by 5 points, or an agent reports a severe error.
   - Budget: one engineer-day.
   - This probe MAY run in parallel with Step 2.

If the support lead reports safety harm, add a Chaotic step first: disable summaries for the affected ticket type.
