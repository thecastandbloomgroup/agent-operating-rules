## Headline

Measure the error rate first, then fix the most common error type, and block regressions with a fixed test set.

- Measure: no baseline exists, so no change can be shown to help.
- Collect: agents need a one-click way to flag wrong summaries.
- Change: fix the largest error type with a small, capped trial.
- Protect: a frozen test set stops later changes from making summaries worse.

## Background

The team added an LLM-based summariser (a language model that condenses a support ticket) to the support tool. Agents report that it is "sometimes wrong". The team has no metrics, no error taxonomy, and no test set.

## Relevance

Agents who distrust the summaries will stop using them or will re-read every ticket. Either outcome removes the value of the feature.

## Information

**Evidence**

- Agents report errors, but the frequency and type are unknown. [no source]
- Common summariser failures are invented facts, omitted details, and wrong attribution (for example, a customer action credited to an agent). [judgment]
- A sample of 100 summaries gives a margin of about 9 percentage points at 95% confidence for an error rate near 30%. [inference]
- The domain labels below follow the Cynefin framework [1].
- The tests use Gherkin form [2].

**Assumption log**

- Assumption: the summariser input is ticket text the team can export. Why not measured: the material does not state it. Validate by: export 10 tickets with their summaries. If wrong: Step 1 needs a logging change first.
- Assumption: two staff can label 100 summaries in one session. Why not measured: the user has not answered. Validate by: ask two senior agents for two hours. If wrong: label 50 and widen the margin.
- Assumption: privacy rules allow staff to review tickets in the sample. Why not measured: the material does not state it. Validate by: ask the data owner. If wrong: use redacted tickets.

**Alternative considered**

The strongest alternative is to switch to a larger model now. It loses because there is no baseline to show a gain, and cost rises for an unknown benefit. [judgment]

## End

I recommend that we take these steps in order:

1. **Build a baseline.**
   - Increment: pull 100 recent tickets with summaries. Two reviewers label each error by type (invented fact, omission, wrong attribution, wrong status).
   - Blocker removed: no known error rate or error types.
   - Kind: evaluative. Rubric, written first: faithfulness 40%, completeness 30%, actionability 20%, length 10%. Score each 0 to 2. The step passes when both reviewers score all 100 items and each error type has a count.
   - Cynefin: Confused. The failure modes are unknown, so this step gathers what is needed to classify the rest.

2. **Add a "wrong summary" button with a reason list.** Run this step in parallel with Step 1.
   - Increment: one button on the summary panel. Reasons come from the Step 1 labels, or from the four types above until Step 1 ends.
   - Blocker removed: no ongoing metric.
   - Kind: deterministic. Test, written first:
     - Given an agent views a summary
     - When the agent clicks "wrong" and picks a reason
     - Then the system stores the ticket ID, summary ID, reason, and time
   - Cynefin: Clear. A known pattern (a feedback control) applies by deduction.

3. **Run a capped probe on the largest error type.** Step 3 MUST NOT start until Step 1 ends.
   - Increment: change the prompt to target the top error type. For example, require the summary to quote the ticket text for each stated fact. Rerun the same 100 tickets.
   - Blocker removed: the main source of agent distrust.
   - Kind: stochastic. Acceptance test, written first:
     - Metric: share of summaries with that error type.
     - Baseline: the Step 1 count.
     - Threshold: a 30% relative drop, and completeness falls by no more than 10 points.
     - Sample size: 100 tickets, 3 runs each.
   - Budget: one working day. Stop early if the first 30 tickets show no drop.
   - Cynefin: Complex. Prompt effects are known only after trials (induction). The pattern could break on new ticket types or after a model update. The leverage is a guess.

4. **Freeze the labelled set as a release gate.** Step 4 MUST NOT start until Step 1 ends.
   - Increment: store the 100 labelled tickets. Add a script that scores any prompt or model change against them.
   - Blocker removed: later changes can silently make summaries worse.
   - Kind: deterministic. Test, written first:
     - Given the frozen set and a candidate prompt
     - When the script runs
     - Then it prints the error rate per type and fails if any type exceeds its baseline
   - Cynefin: Complicated. Analysis picks the scoring method, and Step 1 supplies the data.

If Step 1 shows an error rate under 5%, I recommend that we skip Step 3 and focus on agent training instead.
