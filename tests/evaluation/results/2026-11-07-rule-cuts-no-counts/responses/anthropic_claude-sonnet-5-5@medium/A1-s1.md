## Headline

Yes, pin every version in requirements.txt, including the libraries that your libraries install.

- Pinning means fixing a library to one exact version, for example `requests==2.32.3`.
- Unpinned installs pick up new releases without a review, and that matches both breaks last month [1].
- A pinned file makes each build repeat the last tested build.
- Pinning adds one cost: a planned routine to update versions.

## Background

The project lists libraries in requirements.txt with no versions. The build broke twice last month after a library update [1]. The question is whether to pin versions.

## Relevance

Each break stops the team until someone finds the cause. Without pins, the next break arrives at a time that no one chooses.

## Information

**Evidence**
- Two build breaks in one month, with zero pinned versions [1].
- Baseline: a pinned build installs the same versions every time. Therefore a new release cannot change a build [judgment].
- Confidence that pinning removes this failure type: high confidence. The basis is the failure pattern in [1] and the install behavior of pip, the Python installer [judgment].

## End

I recommend that we:

1. **Freeze the working set.** Run `pip freeze` in the environment of the last passing build. Save the output as requirements.txt.
   - Blocker removed: builds install different versions on each run.
   - Increment: one file, under one hour.
   - Kind: deterministic.
   - Test, written first:
     - Given a clean virtual environment
     - When we run `pip install -r requirements.txt`
     - Then the install succeeds and the test suite passes
   - Domain: Clear. The rule is known, so deduction applies [2].

2. **Split direct from transitive dependencies.** Create requirements.in with only the libraries that we import. Use pip-tools (`pip-compile`) to generate requirements.txt from it. Step 2 MUST NOT start until the test in Step 1 passes.
   - Blocker removed: no one can tell which pins are deliberate.
   - Increment: one file and one command, under two hours.
   - Kind: deterministic.
   - Test, written first:
     - Given requirements.in lists only direct libraries
     - When we run `pip-compile`
     - Then the output pins the same versions as the file from Step 1
   - Domain: Complicated. More than one tool fits, so we compare pip-tools with Poetry, a project manager, before we choose. Analysis decides.

3. **Make CI install only from the pinned file.** Step 3 MUST NOT start until the test in Step 2 passes.
   - Blocker removed: CI can still resolve new versions.
   - Increment: one CI configuration change.
   - Kind: deterministic.
   - Test, written first:
     - Given a library publishes a new release
     - When CI runs the build
     - Then the installed versions equal the pinned versions
   - Domain: Clear. Deduction from the known install rule.

4. **Schedule a weekly update branch.** A job runs `pip-compile --upgrade`, runs the tests, and opens a pull request. The team merges only when the tests pass. Step 4 MUST NOT start until Step 3 is merged.
   - Capability added: updates happen on our schedule, and a failure stays on a branch.
   - Increment: one scheduled job.
   - Kind: deterministic.
   - Test, written first:
     - Given a newer library version exists
     - When the weekly job runs
     - Then a pull request shows the version change, and the main branch is unchanged
   - Domain: Complicated. We choose the schedule by analysis of release volume and test time.

If the first assumption is false, replace Step 1 with a constraints file and keep ranges in the package metadata.
