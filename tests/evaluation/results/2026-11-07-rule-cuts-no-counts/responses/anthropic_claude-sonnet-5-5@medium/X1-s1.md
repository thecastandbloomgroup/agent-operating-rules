## Headline

I recommend measuring the error first, then fixing the most common error type with a tested change.

- No one knows the error rate or the error types, so every fix is a guess today.
- Agent complaints are evidence of a problem, but they do not show which errors matter.
- A small labelled sample and a feedback flag give a baseline within days.
- A guardrail and a capped prompt trial can then cut the top error type, and the baseline proves it.

## Background

The support tool has an LLM summariser (a model that condenses a ticket thread). Agents say it is "sometimes wrong". The team has no metrics and no definition of "wrong". The request is to make it better.

## Relevance

Agents who distrust summaries reread the full thread, which removes the time saving. A wrong summary can also send a customer a wrong answer.

## Information

**Evidence**

- Agents report errors, but there is no count or category. [no source]
- A sample of 385 summaries gives a 95% confidence interval of about ±5 points on an error rate. This follows from n = 1.96² × 0.25 / 0.05². [inference]
- Two raters must agree before labels count. Cohen's kappa measures agreement beyond chance [1].
- Agent comments group into themes by thematic analysis. [judgment] on the fit here, because the comments are short.
- Cynefin sorts work by how cause and effect relate [2].

**Assumption log**

Assumption: the summary is the only AI output agents see. Why not measured: the material does not state it. Validate by: ask one agent to show a ticket. If wrong: add the other outputs to Step 1.

Assumption: the tool stores ticket text and summary text. Why not measured: no tool can reach the system. Validate by: query ten recent tickets. If wrong: Step 2 must add storage first.

Assumption: a factual error is worse than a style flaw. Why not measured: the user has not answered. Validate by: ask three agents to rank error types. If wrong: change the weights in Step 1.

**Alternative considered**

The strongest alternative is to switch to a larger model now. It loses because without a baseline, no one can tell if it helped. It also raises cost per ticket. [judgment]

## End

I recommend that we take these five steps, in this order:

1. **Classify the failures (sample of 100).** Increment: pull 100 random recent summaries and label each with two raters. Blocker removed: no one knows the error types. Task kind: evaluative. Domain: Confused, because the cause of "wrong" is unknown. Step 1 gathers what is needed to classify the rest.
   - Rubric criteria and weights: invented fact (40%), missing key fact (30%), wrong order or status (20%), unclear wording (10%).
   - Evidence per criterion: the quoted summary sentence next to the quoted ticket sentence.
   - Pass threshold: kappa of at least 0.6 between raters, and each summary has one label. If kappa is lower, rewrite the label definitions and relabel.

2. **Log agent feedback.** Increment: add a one-click "wrong" flag with a reason list on each summary. Blocker removed: no running metric exists. Task kind: deterministic. Domain: Clear, because logging a click is a known practice. Step 2 can run beside Step 1.
   ```gherkin
   Given an agent views a summary
   When the agent clicks "wrong" and picks a reason
   Then the system stores the summary ID, ticket ID, model version, and reason
   ```

3. **Add a source check for the top error type.** Increment: one check for the most common error from Step 1. For example, flag any number, name, or order ID in the summary that is absent from the ticket. Blocker removed: invented facts reach agents. Task kind: deterministic. Domain: Complicated, because analysis of Step 1 picks the check. Step 3 MUST NOT start until Step 1 ends.
   ```gherkin
   Given a summary contains an order ID not found in the ticket text
   When the summary is shown to an agent
   Then the order ID is highlighted as "not in ticket"
   ```

4. **Run a capped prompt trial.** Increment: one prompt change aimed at the top error type, tested on 385 labelled tickets against the current prompt. Blocker removed: no evidence that any change helps. Task kind: stochastic. Domain: Complex, because model output varies and the effect shows only after the trial. Leverage is a guess. Induction could fail if the ticket mix shifts.
   - Metric: share of summaries with a labelled error.
   - Baseline: the rate measured on the same 385 tickets with the current prompt.
   - Pass threshold: a relative drop of 30% [judgment], and no rise in the other error types.
   - Budget: one week and one prompt change. Stop at once if any error type rises by 5 points.
   - Step 4 MUST NOT start until Step 1 gives the baseline.

5. **Set a weekly review.** Increment: a 30-minute review of the Step 2 flag rate and 30 new labelled summaries. Blocker removed: quality drifts unseen. Task kind: evaluative. Domain: Complicated, because trend analysis of known measures guides the next change.
   - Criteria: flag rate (50%), labelled error rate (50%).
   - Pass threshold: both at or below the Step 4 result.
   - Evidence: the logged flags and the new labels.

If assumption three is false, replace the Step 1 weights with the agents' ranking.
