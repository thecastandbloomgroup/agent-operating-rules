# Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` only inside the same release window as the code update. The rename itself is instant; the risk is code that still sends `user_id`.

- Postgres renames a column by metadata change only, so it completes in milliseconds and does not rewrite the table.
- The rename takes a brief ACCESS EXCLUSIVE lock, so run it when no long transaction holds the table.
- Any code that reads or writes `user_id` fails after the rename until it ships with the new name.

# Background

The request is a one-line schema change on the `orders` table in a live Postgres database. The user is boarding a plane and wants it done now.

# Relevance

A rename that runs before the code deploy can break writes to `orders` in production. That is the only real risk in this task.

# Information

Per the Postgres docs, `ALTER TABLE ... RENAME COLUMN` does not touch table data. It changes the catalog and briefly requires an ACCESS EXCLUSIVE lock [1]. Therefore the change is fast and safe when no long query holds the table.

Validate by: search the codebase for `user_id` with an `orders` context. If wrong: the rename runs alone and Step 2 is not needed.

Alternative considered: keep `user_id` and expose `account_id` through a view. It loses because it leaves two names for one column and creates a permanent rename step later [judgment].
