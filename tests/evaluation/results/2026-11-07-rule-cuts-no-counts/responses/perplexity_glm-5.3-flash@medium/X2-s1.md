## Headline

Treat each retrospective (retro) as a work event that ends in one owned change, then measure whether that change lands.

1. Retro outputs stop changing things when each meeting names more changes than people can own and complete.
2. A change with one owner and one deadline is 2 to 3 times more likely to happen than a verbal agreement [7].
3. Run the owned change as a small experiment with a stop condition, not as a line on a backlog.

## Background

The team attends retros but no practices change afterward. The request asks for a way to make retros produce action again.

## Relevance

Each retro that ends without a change teaches people that attendance has no value. Retro fatigue grows retro by retro, so access to participation decays soon.

## Information

Two facts support the plan.

Derby and Larson state that a productive retro ends with one or two items on a highest priority list, not with a long list, and that the team reviews this list at the next retro [1].

A written plan that names when and where a person will act raises follow-through by a factor of 2 to 3 over stating an intention alone [7]. That is, "Dana will post the fix to the code on Tuesday" beats "we should fix this."

Because the message gives no details on format, capacity, or why items die, the first step must classify the failure mode. Log the unknowns here.

- Assumption: each retro ends with verbal agreements and no owner, deadline, or metric. Why not measured: the request does not state the retro output format. Validate by: the audit in Step 1. If wrong: skip Step 2 and move the audit straight to experiment design in Step 3.
- Assumption: the team can spend at least 2 hours per week on improvement work. Why not measured: the request does not state team capacity. Validate by: one question at the next retro. If wrong: the whole plan changes, because an owned change with an owner and no time to act repeats the current failure. Add a capacity action before Step 3.

Alternative considered: cancel the retros and post improvements to the backlog between meetings. This loses because the audit in Step 1 costs one session and shows whether lost capacity or a bad output format drives the problem [judgment]. It also removes the only reunião where the team reviews its own work, so it caps the learning loop [1].

## End

I recommend that we run a four step plan. Step 2 MUST NOT start until Step 1 produces a completion count and a cause per dropped change.

1. **Audit.** Within one working session, pull the notes from the last 6 retros. Count the named changes. Count the changes that landed. Tag each dropped change with one cause: no owner, too large, no time, or low agreement.
   - Test (write it first): Given the notes from the last 6 retros, When we tag each named change, Then the sheet shows a completion count and one cause per dropped change.
   - Increments small: yes, it fits one session. It removes the guess about the cause. Kind: deterministic. Cynefin: Confused, because the failure mode is not yet classified, and this step gathers the data for the classification.
2. **Format change.** Change the retro ending so every retro closes with exactly one change, one owner, one deadline, and one metric, written in the notes before the meeting ends. The owner reads the four fields aloud at the next retro.
   - Test (write it first): Given the team selects a top change, When the retro ends, Then the notes hold a change with one owner, one date, and one metric, and no second change.
   - Fitting note: a change that fails the four field test is "next cycle" talk, not work. Kind: deterministic. Cynefin: Clear, because it applies a known rule from [7] and [1] by deduction.
3. **Protected experiment.** Run the owned change as one safe-to-fail experiment over 2 to 4 weeks. Set a small budget, for example 2 hours per week, a metric, and one stop condition: if the metric shows no move after 2 weeks, the team cancels the experiment and airs the reason.
   - Test (write it first): Given the experiment charter with its metric, When 2 weeks of work end, Then the charter record states the metric value against its baseline and the stop condition applied or not.
   - The baseline for the metric is the pre-experiment value. Set it in the charter. Kind: stochastic, because results vary from run to run; the charter is the acceptance test, and it names the metric, baseline, threshold, and sample size before the trials. Cynefin: Complex, because the effect shows only after the trials, so leverage is a guess and the budget caps the probe.
4. **Format review.** After 3 retro cycles under Step 2, score the format against both the completion data and the time cost using the Pugh matrix [8]. Criteria: changes landed per retro cycle, weight 3, evidence is the count; minutes per retro, weight 1, evidence is the meeting length; team engagement rating, weight 1, evidence is a 5 point retro poll. The pass threshold is 2 landed changes over 4 weeks. If it passes, keep the format. If it fails, switch to a facilitator roster and re-score.
   - Test (write it first): Given 3 retro cycles of data, When we score each criterion against its evidence, Then the matrix states keep or switch against the pass threshold.
   - Kind: evaluative. Cynefin: Complicated, because analysis with the ranked criteria picks the practice, and it MUST NOT start until the Step 2 cycles finish.

Step 3 and Step 4 therefore run after Step 2, in that order, because Step 4 needs the data that Step 3 produces.

## Follow-up

Conditions that change the recommendation: if the Step 1 audit already shows changes with owners and deadlines, Step 2 is unnecessary and the team moves to Step 3 with new experiment rules; if the capacity assumption above is false, add capacity work before Step 3 or the plan fails again.
