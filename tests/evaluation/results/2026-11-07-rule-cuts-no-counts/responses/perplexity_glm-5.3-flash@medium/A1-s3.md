## Headline

Yes, pin every direct dependency in requirements.txt with an exact version. The build broke twice last month, so the current unpinned setup fails the baseline of zero unplanned breaks. A pinned build is reproducible, because pip installs the same versions every run. Add one scheduled upgrade job, so the pins stay current in a controlled way.

## Background

The team runs a Python project with requirements.txt. No version is pinned, and two build breaks followed library updates in the last month.

## Relevance

Each unplanned break costs the team a debugging session and can delay a release. Pinning removes that cost with one small change to one file.

## Information

**Evidence.**

- Two unplanned build breaks in one month [user report]. Baseline for comparison: zero, because a reproducible build must not change between runs.
- pip supports an exact pin in requirements.txt with the `==` operator [1].
- An unpinned build depends on behavior beyond the published interface of each library. Therefore any internal change in a library can break it [3]. This is a qualitative theme from one source; it matches the team's two observed breaks, so confidence rises. Confidence: high, because the team's own failure count agrees with the model.

**Assumption log.**

- Assumption: The project is a deployed application, not a library that other projects install. Why not measured: the user has not answered. Validate by: check whether the package is published to a package index. If wrong: a library uses ranges instead, and the consuming application holds the pins, so the pin target moves out of requirements.txt.
- Assumption: Both breaks came from a dependency update, not from project code, because the dates match the updates. Why not measured: the CI logs are not in this session. Validate by: read the two change sets that triggered the failed builds. If wrong: an own-code defect is the cause, so debug it before Step 1.
- Assumption: requirements.txt is the only dependency file and no lock tool exists. Why not measured: the repository is not in this session. Validate by: list the repository root. If wrong: reuse the existing lock file instead of Step 2.

**Alternative considered.** Pin the direct dependencies loose ("~=") and run CI daily against the newest versions. That option loses: the team still runs every direct update through the build, so the two breaks per month pattern continues.

**Upgrade risk.** A new version can pass the test suite and still fail in production, because a suite cannot cover every runtime path [3]. Step 4 caps this with a budget and a revert rule.

## End

I recommend that we take four actions:

1. **Pin the direct dependencies.** Add one `==` line per direct dependency in requirements.txt [1]. This removes the blocker of silent direct updates. Cynefin: Clear, because "an application pins its dependencies" is a known best practice. Precise pin choice is a deduction from the pip file format. Test (deterministic, write it first):
   ```gherkin
   Given a clean virtual environment
   When "pip install -r requirements.txt" runs twice
   Then both runs report the same version for every package
   ```
2. **Freeze the transitive dependencies.** Generate a lock file, for example with pip-compile [2], and commit it. This removes the blocker of updates that arrive through dependencies of dependencies. Cynefin: Clear, same deduction. Test (deterministic, write it first):
   ```gherkin
   Given the committed lock file
   When the lock file is regenerated
   Then the diff is empty
   ```
3. **Split the test by severity.** Tag the fast unit tests and the slow integration tests. Run the units first, so a broken pin fails in under one minute. This adds the capability of a fast signal. Cynefin: Clear, deduction from standard CI practice.
4. **Schedule one upgrade job per month.** Run the job in a branch: update the pins, run the full suite, then merge or revert. Cynefin: Complex, because the effect of a new library version is only visible after the run. This is induction from trials. What could break the pattern: a change that passes the suite but fails in production. Stop condition: any failing test, then revert. Budget: one branch, two working hours. This is a capped probe, so it is not ordered by leverage. Test (deterministic, write it first):
   ```gherkin
   Given a branch with updated pins
   When the full test suite runs on that branch
   Then the branch merges only if every test passes, otherwise it reverts
   ```

Sequencing. Steps 1 and 2 are first, because they remove the active failure mode. Step 3 MUST NOT start until Step 2 passes its test. Step 4 MUST NOT start until Step 3 exists, because the upgrade job depends on a fast signal.

**Condition that changes the recommendation.** If the first assumption is wrong and the project is a library, replace Steps 1 and 2 with version ranges, and the consumers pin instead.
