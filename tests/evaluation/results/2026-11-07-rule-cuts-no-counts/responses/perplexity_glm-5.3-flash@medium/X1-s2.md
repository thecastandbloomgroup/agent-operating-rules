- Without a rate and a failure type, "sometimes wrong" cannot be compared before and after any change. [judgment]

## Background

The support tool now shows agents an LLM generated summary of each ticket. Agents report errors, but no metric records how often or which kind. The request is to improve the summariser.

## Relevance

Any prompt or model change without a baseline can fix one error type and double another. A one session logging change makes every later change testable in one session.

## End

I recommend that we run the four steps below in this order.

**Step 1. Add structured feedback logging.**
Increment: a one click rating plus a tag menu ("wrong fact", "missing point", "wrong priority", "too long") that stores the thread, the summary, and the tag in one record. Blocker removed: the absence of error data. This is a deterministic coding task; write the test first, make it pass, refactor [14].

Cynefin: Clear. Cause and effect are known: log the event at its source, and the data exists.

**Step 2. Label a failure sample.** This step must not start until Step 1 has recorded at least 30 tagged records.
Increment: code a rating rubric from the tag counts, then have two agents label a sample of 30 records. Blocker removed: unknown failure pattern. Test (evaluative): rubric criteria are tag definitions with weights of 1 each; pass threshold is rater agreement of 70% or higher on 30 records; evidence is each rating with its source quote [15]. Cynefin: Confused. The failure pattern is not yet classifiable, so this step gathers what Step 4 needs.

**Step 3. Build the eval set.**
Increment: select 50 records from the tagged data, with per item human scores for faithfulness, coverage, and length. Blocker removed: no repeatable benchmark. Test (evaluative): rubric first, score against the source thread, two raters. Cynefin: Complicated. The right items come from analysis of the Step 2 labels, and the choice is knowable from that analysis.

**Step 4. Iterate the prompt as capped probes.** Run after Step 3 scores exist; run in parallel with no other dependency.
Increment: two prompt variants per week, for example "state only facts present in the thread" and "quote one source phrase per claim". Blocker removed: no path from labels to fixes. Stochastic acceptance test, written before the runs: metric is human judged faithfulness score; baseline is the Step 3 score; pass threshold is a gain of at least 10 percentage points; sample size is all 50 eval items; budget is two variants per week, stop after three weeks without a pass. Cynefin: Complex. The effect of a prompt change is visible only after the run, so each variant is a safe to fail probe with a stop condition, not a full commit [18].
