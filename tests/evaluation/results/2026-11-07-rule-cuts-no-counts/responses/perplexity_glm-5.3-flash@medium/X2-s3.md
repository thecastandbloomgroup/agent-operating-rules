Headline
Stop holding the retro as a meeting and run it as a loop: select at most two actions with named owners each time, review those actions at the start of the next retro, and run one change as a measured experiment. Supporting points: (1) The cause is not known, so classify why actions die first. (2) Retros without an owner and a review step produce no follow-through [1]. (3) A visible, capped action list makes follow-through checkable. (4) One measured change per cycle tests whether the action actually moves the outcome.

Background
The team holds retrospectives, so the meeting part works. The output stage does not work: people attend, and nothing changes afterward. The request asks for a way to make retrospectives produce real change.

Relevance
Retrospectives are the team's main tool for improvement. When they produce no change, the same blockers repeat every cycle and morale drops. The fix is cheap: it needs less time than the current format, not more.

Information

Cause analysis
Three failure modes explain "meetings happen, nothing changes". They do not overlap, and together they cover the whole space:

1. The retro never produces a concrete action. Talk happens, but no decision results.
2. The retro produces actions, but no one carries them out. Ownership and review are missing.
3. Actions happen, but they are the wrong ones. The team guesses at causes instead of testing them.

The material does not state which failure mode applies, so all three need coverage. Steps 2 and 3 cover modes 1 and 2. Step 4 covers mode 3.

Evidence
- Groups that turn retrospectives into tracked action items complete the loop; the standard practice is: pick a few, make them visible, check them next time [1].
- teams with high psychological safety raise problems that others then act on; safety without action produces talk only [2]. A retro that ends in discussion but no task trains people that speaking changes nothing. [inference]
- Cause and effect in a retro are visible only after the next cycle. That puts mode 3 fixes in the Complex domain: run small probes with a measure and a stop condition [3].

The two-so soft facts (attendance, no change) come from the request. No baseline numbers exist yet, so Step 1 collects them [judgment].

Alternative considered
Add a facilitator or hire an external coach. That fails as the first step because it adds cost before the cause is known, and it does not add an ownership or review structure [judgment].

Confidence
Medium-high confidence that the ownership and review steps are the main gap. Basis: standard practice [1] plus the request's own facts, but the team's data is not yet measured.

End
I recommend that we run these four steps. Steps 3 and 4 wait on Step 2, and Step 2 waits on Step 1.

1. Classify the failure (Confused). First action, because the rest depend on it.
   Increment: in the next retro, put up three columns on the board: "no action chosen", "action chosen, not done", "action done, no effect". Each person puts a mark under the column that matches the last three retros.
   Blocker it removes: we do not know where the loop breaks.
   Test (deterministic, written first):
   Given the three columns on the board,
   When all attendees place a mark,
   Then every retro has marks and the top column names the failure mode.
   Reason for domain: the data does not yet fit any known pattern, so we must gather before we choose. The reason names the inference: acting first.

2. Add a closing rule with owners (Clear).
   Increment: at the end of every retro, the team selects at most two actions, each with one owner and a check date, written on a visible list. One session to set this up, then it runs every retro.
   Blocker it removes: mode 1 and mode 2, "no action" and "no follow-through".
   Test (deterministic, written first):
   Given retro notes from the next two retros,
   When a reviewer reads them,
   Then each retro lists one or two actions, each with one named owner and one check date.
   Reason for domain: a best practice exists; the action is one step. Leverage estimate is reliable. Inference: deduction from the standard practice [1].

3. Review actions at the start of the next retro (Clear). This step MUST NOT start until Step 2 has produced at least two actions.
   Increment: the first five minutes of each retro inspect the previous actions. Done becomes a tick. Not done gets a reason in one sentence.
   Blocker it removes: the missing feedback loop that lets actions disappear without cost.
   Test (deterministic, written first):
   Given an action with an owner and a check date,
   When the next retro starts,
   Then the action appears on the board with a tick or a one-sentence reason.
   Reason for domain: known rule, one step. Inference: deduction [1].

4. Run one change as a measured experiment (Complex). This step waits on the Step 1 column data.
   Increment: pick one blocker theme from Step 2 and design one change. Keep the change under one cycle long.
   Blocker it removes: mode 3, guessing at causes instead of testing them.
   Test (stochastic, written first):
   Metric: one team metric that the team already tracks, for example cycle time in days.
   Baseline: the mean of the last two cycles.
   Pass threshold: the metric improves by 10 percent against the baseline. [judgment]
   Sample size: two cycles. Accept the theme only when the threshold is met at that sample size; otherwise redesign the change and run again, with a budget of three runs.
   Stop condition: stop the probe when the second run fails. Return the result to the retro board.
   Reason for domain: cause and effect show only after the run. Inference: induction from trials; the measure and the stop condition name what breaks the pattern. Leverage is a guess until the first run [3].
