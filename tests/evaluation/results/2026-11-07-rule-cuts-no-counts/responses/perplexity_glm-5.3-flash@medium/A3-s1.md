Turn on gzip compression.

- JSON bodies compress by about 5 to 10 times, so a 400 KB body drops to 40 to 80 KB [inference].
- Compression level 4 keeps the added CPU cost at roughly 10 percent or less on a typical web server [judgment].
- Reverse proxies and web frameworks expose gzip as a setting, so no code change is needed [judgment].

Background
The API returns JSON responses that average 400 KB. The request asks whether to enable gzip compression.

Relevance
Every uncompressed response costs bandwidth for each request. At 10,000 responses per day, the transfer is 4 GB per day, or 1.46 TB per year [inference]. Compression therefore cuts cost and latency without touching application logic.

Information
JSON is repetitive text, and gzip finds repeated patterns well. Measured ratios for JSON bodies commonly fall between 5 and 10 [inference]. Compression runs the CPU on each response, so high levels cost more for a small extra gain. zlib level 4 captures most of the size win at low cost [judgment]. Two risks exist: clients that do not send the "Accept-Encoding: gzip" header, and CPU pressure on a loaded server. Therefore the plan verifies both after the change.

Assumption logs:
- Assumption: Clients connect from outside a data center and bandwidth is metered. Why not measured: the material does not state the deployment. Validate by: read response size and timing from one access log entry. If wrong: on a local 10 GbE cluster the bandwidth case weakens, so set level 1 or leave compression off.
- Assumption: Server CPU has at least 10 percent headroom. Why not measured: the material does not state current load. Validate by: read CPU utilization in monitoring before the change. If wrong: set level 1, or cache compressed variants per response family.
- Assumption: Clients send "Accept-Encoding: gzip". Why not measured: no client census tool is available. Validate by: run one request with curl and count the clients in a sample of access logs. If wrong: skip step 1 and compare the cost of a client update against the bandwidth cost.

Alternative considered: enable Brotli instead of gzip. Brotli loses as the first step because every HTTP client accepts gzip, while Brotli needs a module or library; its extra size gain is about 15 percent [judgment], which does not justify the first change. Brotli stays as a capped probe in step 3.

End
I recommend that we enable gzip and verify it under load:

1. **Enable gzip at level 4 on the reverse proxy for JSON responses, with a 1 KB minimum body size.** This removes the 400 KB per-response bandwidth cost and adds the compression capability. This is a stochastic action, because the traffic sample varies between runs: the metric is average body size and CPU delta, the baseline is 400 KB and the pre-change CPU, the pass threshold is an 80 percent size reduction and a CPU increase at or below 10 percent, and the sample size is 1,000 requests (domain: Complicated, because analysis of the measured data picks the level; leverage is reliable only after the analysis).

3. **Run a Brotli probe on one endpoint, capped at one working session and one rollback script.** This tests whether the client mix supports a further size win. This is a Complex probe, because the gain depends on the client mix, which is visible only after a trial; do not commit the full rollout: the measure is Brotli size versus gzip size, the stop condition is a stop when fewer than 90 percent of sampled clients send "br" or the gain falls under 5 percent, and the budget is one session. Leverage here is a guess.

Step 2 MUST NOT start until the test in step 1 passes on all JSON endpoints. Step 3 can run in parallel with step 2.

Follow-up
Conditions that change this recommendation: if monitoring shows CPU above 90 percent before the change, set level 1 or keep compression off. If responses flow only inside a local cluster with unmetered 10 Gb links, the bandwidth case in the Relevance section weakens, so weigh CPU cost against the smaller latency win.
