## Headline

Build a labeled sample of real summaries first, then fix and verify one error type at a time. The main points:

1. "Sometimes wrong" contains no numbers, so no fix can be ranked or verified yet. [judgment]
2. A one-session labeling task on 100 summaries will produce an error rate and a ranked error list. [judgment]
3. An inline agent feedback button keeps the measure current after the labeling task. [judgment]
4. Each fix is then tested against the labeled baseline with a fixed sample size. [judgment]

## Background

The support tool includes an LLM summariser. Agents report that it is sometimes wrong. No metrics exist for its quality.

## Relevance

Wrong summaries cost agents time on re-checking and can send wrong answers to customers. The next change to the prompt or model is a guess until someone measures the errors. [judgment]

## Information

**Evidence base.** The only input is the agent statement. It forms one theme: "the summary output has errors". One source supports it, so the support is weak as data. It still decides the next step because agents observe every output in live use [judgment]. The reported error sits inside a known failure family for generated text: outputs that are inconsistent with the source, which include added facts and dropped facts [1].

**Error taxonomy to apply.** Prior work on generated text separates errors of faithfulness (false facts) from errors of completeness (true source content with no summary entry) and of form (repetition, wrong length, wrong tone) [1]. The labeling task below scores each sample against these axes. [inference]

**Assumption log.**

- Assumption: summary volume is at least 20 per day. Why not measured: the tool usage data is not in this session. Validate by: count records in the ticket summary table. If wrong: use a larger date range for the sample.
- Assumption: no error log exists today. Why not measured: no tool in this session can read the tool's UI or database. Validate by: ask one agent whether they can flag an error today. If wrong: drop the feedback-button action and analyze the existing log.
- Assumption: a "ticket source text" record exists per summary. Why not measured: the tool's data schema is unknown here. Validate by: read one summary with its ticket side by side. If wrong: faithfulness cannot be judged; cover then only the summary itself and decide replacements instead.
- Assumption: agents can spare the labeling effort in one session. Why not measured: agent capacity is not in the material. Validate by: ask the team lead for 2 hours. If wrong: split the sample across 2 weeks, 10 labels per day.

**Alternative considered.** Rewrite the prompt now with stricter instructions. It loses because a no-metric baseline means a regression stays invisible [judgment], and prompt changes on LLM output show mixed, run-to-run results that need a measured trial.

## End

I recommend that we run these steps in this order:

1. **Label the sample and rank the errors** (Confused, the output decides every later step, so it goes first). Increment: one 2-hour session, 100 recent summaries, 2 people, scores on 3 axes: false facts, missing facts, form issues. Blocker removed: "sometimes wrong" becomes a rate per error type, for example 8 in 100 summaries contain a false fact. Test (evaluative, rubric before scoring): each of 3 axes has a written definition [judgment, based on [1]]; pass when both labelers agree on 80 of 100 with an arbiter settling the rest.
2. **Add an inline feedback button** (Clear, one known pattern applies). Increment: one flag button next to each summary, one weekly report of flags per error type. Blocker removed: the measured error list stops aging after the session in Step 1. This step MUST NOT start until Step 1 has classified the domain as Complex, or Confused; if Complex, run it as a 2-week capped probe: budget 3 engineer-days, stop if flag rate stays under 2% of views, and then investigate why agents do not use it. Its own test: deterministic, Gherkin form.
   ```gherkin
   Given a summary is visible
   When an agent clicks the flag button
   Then one flag record with summary ID, agent ID, and timestamp is stored
   ```
3. **Fix the ranked top error type with one probe** (Complex, results show only after the trial). Increment: one prompt or retrieval change, one error type only. Test (stochastic, acceptance stated before the run): metric is the error rate on the axis from Step 1; baseline is the Step 1 rate; pass threshold is a 30 to 50% relative drop [judgment]; sample size 30 summaries pre and post; accept only when the drop holds at that size. Stop condition: after one trial round, stop and re-label, no further prompt edits.
4. **Ground each summary in its source text** (Complicated, picks a known practice through analysis of ticket structure). Increment: show 3 quoted ticket lines per summary claim. Blocker removed: agents verify a claim in seconds, so the cost of a remaining error drops. Test: deterministic, Gherkin form.
   ```gherkin
   Given a summary with 3 claims
   When the summary renders
   Then each claim shows a quote from the same ticket
   ```

Dependency: Step 3 MUST NOT start until Step 1 has passed. Step 4 can run in parallel with Step 3. This plan changes if the volume assumption is false, then Step 1 uses a wider date range.
