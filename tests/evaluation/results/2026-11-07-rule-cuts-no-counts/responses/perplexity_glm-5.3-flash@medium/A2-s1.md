# Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` after a dependency check. Supporting points:

1. The rename preserves data, indexes, constraints, and foreign keys.
2. Postgres rewires views and internal references, so the main break risk is application code that pins the string "user_id".
3. Do the dependency check first, then the rename, then update code that references the old name.

# Background

The orders table in a Postgres database needs a column rename from user_id to account_id. The request arrives while the user is about to board a plane. The answer must be executable with minimal reading.

# Relevance

A rename is fast but affects every query that names the column. An unchecked rename can stop application queries at the next deploy.

# Information

The rename command is:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Postgres stores the relation to the column internally, so the rename keeps all rows, indexes, constraints, and foreign keys [P, PostgreSQL documentation]. Views that reference the column continue to resolve, because the catalog tracks columns by internal identifier, not by name [S, PostgreSQL documentation on ALTER TABLE].

What breaks instead: application SQL, ORM field mappings, prepared statements, and function bodies that contain the literal name "user_id" [S, PostgreSQL migration practice].

Evidence for the dependency check:

```sql
SELECT object_name(relname), prosrc, definition
```
is not portable, so use this simpler check:

```sql
-- views and functions that mention the old name
SELECT viewname FROM pg_views
WHERE definition LIKE '%user_id%';
```

plus a source search in the codebase for `user_id` inside the orders context.
