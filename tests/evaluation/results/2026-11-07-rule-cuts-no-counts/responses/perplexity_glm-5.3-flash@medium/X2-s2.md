## Headline

Stop producing action lists; run one committed action per retrospective and check it at the next one.
1. Actions fade because no owner, no due date, and no review step exist after the meeting [1].
2. Real causes stay hidden when speaking feels unsafe [2], [3].
3. One action, one owner, one review makes each change visible within one sprint [1].

## Background

You run regular retrospectives: team meetings that review the last work period. People attend, items get listed, and no behavior changes. The request asks for a way to make these meetings produce change.

## Relevance

Each retrospective without result wastes one hour per person and lowers trust in the next meeting. A working improvement loop reuses time the team already spends.

## Information

Three themes in the sources explain a retrospective that produces no change.

**Theme 1: no follow-up loop.** Actions without an owner, a due date, and a review step do not get done. One source supports it and none disagrees [1]. The single source is the standard practice guide for this exact meeting type, so it matters despite its count.

**Theme 2: fear blocks candor.** Psych safety, defined as the shared belief that speaking up carries no penalty, predicts whether people name real problems. Two sources support it and none disagrees [2], [3]. Google's internal study ranked psych safety first among five team dynamics [3].

**Theme 3: many small actions dilute focus.** One source supports it [1]; its format recommends few, concrete actions. None disagrees. It matters because the completion measure in Step 3 depends on a small count.

**Numbers.** The completion baseline is 0 completed actions per meeting [inference from "nothing shifts"]. The pass target is 3 of every 4 actions completed. The evidence is qualitative with one measured baseline; the numbers and themes agree.

**Assumption log**

Assumption: Retro actions go into no system that anyone reviews. Why not measured: the request does not describe the follow-up process. Validate by: read the notes from the last three retrospectives. If wrong: skip the new board and review the existing system.

Assumption: The team can change its own practices without outside approval. Why not measured: the request does not state the team's authority. Validate by: run one small change and watch for a blocker reaction. If wrong: add a sponsor to the review in Step 2.

Assumption: Attendees include the people who do the work. Why not measured: the request does not describe attendance. Validate by: compare the attendee list with the task roster. If wrong: use the anonymous vote (Step 4) before the meeting.

**Alternative considered**

Replace the meeting format with new exercises or a new facilitator. It loses because the reported failure sits in the loop after the meeting, not in the discussion [judgment]; a new format leaves the follow-up gap in place.

## End

I recommend that we run the following four steps, in this order.

**Step 1.** Record exactly one action per retrospective, with one owner and one due date, on a board that everyone sees. This increment fits one working session. It removes the blocker of ownerless items. Kind: deterministic. Test, written first:

```gherkin
Given a retrospective is closing
When the facilitator finalizes the notes
Then exactly one action appears with one owner, one due date, and one board card
```

Domain: Clear, because cause and effect are known and this applies documented practice [1]. Leverage is reliable; it is the largest blocker.

**Step 2.** Open every retrospective with a five-minute review of the prior action, recorded as done, moved, or dropped with one reason. This adds the missing feedback loop. Kind: deterministic. Test, written first:

```gherkin
Given a retrospective starts
When the facilitator reads the last action
Then the team records done, moved, or dropped with one reason
```

Domain: Clear, deduction from known practice [1]. Step 2 MUST NOT start until Step 1 produces the first tracked action.

**Step 3.** Track the completion rate for the next four retrospectives. Metric: completed actions divided by assigned actions, as a percentage. Baseline: 0% [inference]. Pass threshold: 75% or more at a sample size of four meetings. Kind: stochastic, because team behavior varies run to run. Domain: Complicated, because the link between the loop and completion is checked by analysis of the measured rate.

**Step 4.** Probe hidden causes with an anonymous pre-meeting vote: each member sends one top issue by private message before the meeting. Budget: ten minutes per person. Stop condition: two rounds without one agreed action on a voted issue. Kind: stochastic. Metric: new causes that reach discussion per meeting. Baseline: one [judgment]. Pass threshold: two or more at a sample of two rounds. Domain: Complex, because the effect of anonymity appears only after the run; the probes run in parallel with Steps 1 to 3, each capped by its budget. Leverage is a guess.

Hedge: if the completion rate already exceeds 75%, the blocker is item selection instead of the loop; then replace Steps 1 to 3 with an impact and effort filter at the close of each meeting.

## Follow-up

**Condition that changes the recommendation:** if Step 3 shows low trust as the primary cause after four meetings, switch effort from Steps 1 and 2 to repeated Step 4 probes.
