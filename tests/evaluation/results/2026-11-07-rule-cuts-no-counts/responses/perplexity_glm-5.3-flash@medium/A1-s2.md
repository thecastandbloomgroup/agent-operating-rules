## Headline

Yes, pin the versions. Do it in three moves: freeze the working set now, enforce pins in CI, and replace manual pinning with a generated lock file plus a scheduled update window.

## Background

The team keeps unpinned dependencies in requirements.txt. Two builds failed last month after a library released a new version and the build picked it up. The question: pin versions or leave them floating.

## Relevance

Each unpinned build is a silent integration test with a random dependency set. Pinning removes that randomness before the next library release breaks a build again.

## End

I recommend that we take these actions, in this order:

1. **Freeze the current working set.** Run `pip freeze` in a clean environment where the build passes, and commit the exact pinned list to requirements.txt. This removes the repeat-failure blocker today. Domain: Clear, because the command to pin is a known rule. Test (write first, deterministic):

   ```gherkin
   Given a clean virtual environment with python 3.11
   When pip install runs with -r requirements.txt
   Then the resolved versions equal the pip freeze output exactly
   ```

2. **Enforce pins in CI.** Add a CI job that installs from requirements.txt and runs the test suite on every merge. This blocks any future unpinned change to dependency resolution. It waits on Step 1. Domain: Clear, direct rule. Test (deterministic):

   ```gherkin
   Given requirements.txt contains at least one version pin
   When the CI install step runs
   Then no line lacks a pin and the test suite passes
   ```

3. **Split direct and transitive dependencies with pip-tools.** Keep requirements.in with unpinned direct dependencies; generate requirements.txt with `pip-compile`. This adds controlled updates without hand-editing pins. It waits on Step 2. Domain: Complicated, because comparing lock tools (pip-tools, uv, Poetry) needs a short analysis; the analysis is: pick the tool the team already knows. Test (deterministic):

   ```gherkin
   Given requirements.in lists unpinned direct dependencies
   When pip-compile runs
   Then requirements.txt regenerates with pins and no manual edits
   ```

4. **Schedule a monthly update window as a capped probe.** In each window, upgrade one direct dependency at a time, run the test suite, and merge or revert the same day. Budget: one half-day per month; stop condition: two failed upgrades in one window pause the window. This keeps security patches flowing. Domain: Complex, because each upgrade's effect is visible only after the run; the capped budget breaks the pattern of surprise failures. Test (stochastic): metric is the count of failed upgrades carried past the window; baseline is 2 in the last month; pass threshold is 0 carried failures at a sample of 3 monthly windows.

Confidence: high, from two observed failures plus documented install behavior [1][2].
