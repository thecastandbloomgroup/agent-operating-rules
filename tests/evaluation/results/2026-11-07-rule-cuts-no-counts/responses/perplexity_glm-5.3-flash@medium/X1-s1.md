## Headline

Measure before you change: build a labeled error sample, add two metrics from it, and gate any fix on those metrics. Supporting points:

- Label about 100 real summaries against an error taxonomy to replace "sometimes wrong" with counts.
- Track two metrics quarterly: factual error rate and edit rate by agents.
- Add one-click agent feedback, so the sample grows for free.
- Change the prompt or model only after a before-and-after test on the labeled set.

## Background

A support tool uses an LLM-based summariser. Agents rate it as "sometimes wrong". No metrics exist, so the failure rate and failure kinds are unknown. The request is to make the summariser better.

## Relevance

Without counts, any change to the prompt or model cannot be verified. A baseline this week turns opinions into a testable defect rate [judgment].

## Information

The evidence base is one qualitative theme: agents report "sometimes wrong". Thematic analysis with a single source cannot separate failure kinds, so the first step must create the data [3]. A tag of primary or secondary source cannot apply to this report yet; it is first-hand user testimony in this session, tagged `[P]` for what the user reported.

Failure kinds in summarisers typically split into two classes: factual mismatch with the source ticket, and missing or extra content [inference]. The labeled sample decides the real taxonomy.

Assumption log:

- Assumption: agents mean factual errors in summaries, not style. Why not measured: the user has not answered. Validate by: the taxonomy from the labeled sample. If wrong: the taxonomy changes, but Steps 1 and 2 stay valid.
- Assumption: the team can review 100 summaries in one session, about 10 minutes each. Why not measured: summary volume was not stated. Validate by: count summaries for two weeks. If wrong: reduce the sample to 50, or sample every tenth summary.
- Assumption: tickets contain a source text that a summary can be checked against. Why not measured: the user has not answered. Validate by: read 5 tickets next to their summaries. If wrong: groundedness checks cannot run, and Step 2 must use agent feedback only.

Alternative considered: change the prompt or swap the model now. It loses because no baseline exists, so the result cannot be tested against anything [judgment].

## End

I recommend that we run these four actions in this order:

1. **Label a sample of 100 summaries.** Increment: 5 reviewers score 20 summaries each, in one session, against a taxonomy of this draft: factual mismatch, missing content, extra content, wrong tone. Blocker: no baseline. Kind: evaluative. Rubric before scoring, per Pugh matrix form: four criteria weighted equally, pass threshold 80% labeler agreement, evidence is the ticket plus the summary [16]. Cynefin: **Confused**, because the failure kinds are unknown; this step produces the classification, so it comes before leverage ordering [18].
2. **Define two metrics from Step 1.** Increment: compute the factual error rate (labeled factual mismatches divided by 100) and the edit rate (share of summaries agents changed before sending to customers). Blocker: the same no-baseline blocker, output form. This step waits on Step 1. Kind: deterministic. Test first:
   ```
   Given 100 labeled summaries with error counts
   When the metric script runs
   Then it prints one rate per label class, per week, as a percent
   ```
   [14] Cynefin: **Clear**, one step with a known rule, so its leverage estimate is reliable [18].
3. **Add one-click agent feedback.** Increment: a button per summary with the label classes from Step 1, stored with the ticket ID. Blocker: free future sample size. This step MUST NOT start until the metrics in Step 2 are defined. Kind: deterministic. Test first:
   ```
   Given an agent views a summary
   When the agent clicks one feedback label
   Then the label, agent ID, and ticket ID are stored
   ```
   [14] Cynefin: **Clear**, a single known-practice step [18].
4. **Probe one prompt or model change against the baseline.** Increment: adjust one variable (prompt instruction or model), run on 50 new summaries, score with the same rubric. Blocker: reduces the error rate found in Step 1. This step MUST NOT start until the labels in Step 1 agree at 80%. Kind: stochastic. Acceptance test first: metric is factual error rate, baseline is the Step 2 number, pass threshold is a reduction of at least 30% relative [inference], sample size 50. Cynefin: **Complex**, because cause and effect in LLM behaviour appear only after the trial; the probe is capped at one session of work and 50 scored summaries [18].

If the assumption that labels reach 80% agreement fails, run a calibration pass on the taxonomy before Step 4.

## Follow-up

- What is the weekly summary volume? Use it to fix the sampling rate for Step 1.
- Condition that changes the recommendation: if summaries have no source ticket text, replace the groundedness check with agent feedback only, and double the feedback sample.
