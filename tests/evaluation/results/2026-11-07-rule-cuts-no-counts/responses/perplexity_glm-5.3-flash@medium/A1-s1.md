## Headline

Pin the versions in requirements.txt. The evidence supports it because unpinned builds fetch the newest releases, so any upstream break lands in the next build. Pin all dependencies now, then upgrade on a schedule with tests as the gate. This was likely the cause of the two breakages last month, 80% likely [inference].

## Background

The project keeps its Python dependencies in requirements.txt with no version numbers. Two builds failed last month after a library update [1]. The team needs a decision on pinning and a way to keep upgrades safe.

## Relevance

The build is the gate for all changes, so each failure blocks the whole team. Pinning is a one-session change that makes every build reproducible.

## Information

### Evidence

- Two builds broke last month after a library update [1]. This is a primary observation of the effect.
- With pip, a bare package name in a requirements file lets pip choose "the latest available version" each install [2]. So an upstream release changes the build without any local change [1], [2].
- The two facts point to the same pattern. Therefore the probability that pinning removes this failure mode rises above the baseline of no action [inference].
- With no pinning, transitive dependencies are also unpinned by default, so the number of upstream failure paths is larger than the direct list suggests [inference].

Theme: build failure rate falls when the dependency set is fixed. Two sources support this [1], [2]. No source in this session disagrees.

### Assumption log

- Assumption: the breakages came from a new release of a dependency, not from another change. Why not measured: the material does not include the build logs. Validate by: diff the installed versions from the two failed builds against the last good build. If wrong: pinning still helps, but add a version change log to each failure report.
- Assumption: no lock file or tool such as Poetry is already in use. Why not measured: the material does not state the toolchain. Validate by: search the repo for poetry.lock, Pipfile.lock, or uv.lock. If wrong: use the existing lock tool instead of the steps below.

### Alternative considered

Keep requirements.txt unpinned and rely on tests to catch upstream breaks in the build. This loses because the test gate itself is the build that broke, twice in one month [1]. Pinning plus a scheduled upgrade gives the same access to new versions at a lower failure rate [judgment].

## End

I recommend that we do the following, in this order.

1. **Pin the current dependency set.** Increment: in the last working environment, run `pip freeze` and write exact `==` versions into requirements.txt in one session. Blocker removed: unknown versions in the build. Cynefin domain: Clear, because a known best practice applies and the cause of the breaks is known. Write the test first:

   ```gherkin
   Given a requirements.txt where every entry uses "=="
     When "pip install -r requirements.txt" runs twice on clean environments
     Then both "pip freeze" outputs are identical
   ```

   Deterministic. The increment ends in tested, working output.

2. **Split direct from transitive dependencies.** Increment: move direct dependencies to requirements.in, generate requirements.txt with `pip-compile`, and commit both. Blocker removed: pinning by hand hides which dependency the team actually chose. Cynefin domain: Complicated, because analysis of the toolchain picks the practice. Dependency order: Step 2 must not start until the Step 1 test passes.

   ```gherkin
   Given source files requirements.in and requirements.txt
     When a contributor runs "pip install -r requirements.txt" on a clean environment
     Then all installed versions match requirements.txt exactly
   ```

   Deterministic.

3. **Add a scheduled upgrade probe.** Increment: a weekly pipeline job that upgrades, runs the test suite, and opens an upgrade pull request only if tests pass. Cap the budget at 1 pipeline hour per week. Blocker removed: the risk of staying pinned forever while dependencies age. Cynefin domain: Complex, because the value of future upgrades shows only after trials. The pattern breaks if flaky tests flood the team with pull requests. So the stop condition is: disable the probe if it produces no merged upgrade after 12 weeks. Run this probe in parallel with Step 2, not after it.

4. **Record the upgrade policy.** Increment: one README paragraph that states who reviews upgrade pull requests and on what schedule. Blocker removed: unclear ownership of updates. Cynefin domain: Clear, because this is a written rule. Evaluative test first, rubric: reviewer named (weight 40%), schedule stated (weight 40%), rollback step stated (weight 20%), pass threshold 100%, evidence is the merged README diff. Dependency order: Step 4 must not start until Step 3 has run once.

Why this order: Step 1 removes the current failure mode with the smallest change. Step 2 keeps pinning workable for people and tools. Step 3 recovers the upgrade flow that pinning reduces. Do not skip Step 1 to go straight to Step 3.

## Follow-up

Conditions that change this recommendation:

- If a lock tool is already in use, replace Steps 1 and 2 with its own lock command.
- If the test suite takes more than 1 hour, lower the probe to a monthly schedule.
