## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` in a transaction.

- The command is a metadata change and finishes in milliseconds.
- It takes an ACCESS EXCLUSIVE lock, so it waits for other transactions on `orders`.
- Indexes, constraints, and foreign keys on the column keep working after the rename.

## Background

You need one column renamed in a Postgres table before boarding. The request assumes production or a shared database.

## Relevance

A failed rename under lock can block writes to `orders`. The safe form below avoids that.

## Information

Evidence and assumptions:

- Postgres renames are metadata-only, not a table rewrite [1].
- The command takes an ACCESS EXCLUSIVE lock [1].
- Dependent views and application code that reference `user_id` will break after the rename [judgment].

Assumption: this runs against a live database shared with application code. Why not measured: the material does not state it. Validate by: query `pg_stat_activity` for open transactions on `orders`. If wrong: the lock timeout wrapper is harmless overhead.

Assumption: application code is already updated or will be updated now. Why not measured: the material does not state it. Validate by: grep the codebase for `user_id` in the orders context. If wrong: revert with the reverse rename.

Alternative considered: expand-contract (add `account_id`, backfill, dual-write, drop `user_id`). It loses here because you are boarding a plane and need one atomic step, and the rename is fast at metadata level.

## End

I recommend that we:

1. Set a lock guard, then rename in one transaction. Removes the risk of blocking `orders` writes. Clear domain, deduction from documented lock behavior [1].
   ```sql
   BEGIN;
   SET LOCAL lock_timeout = '2s';
   ALTER TABLE orders RENAME COLUMN user_id TO account_id;
   COMMIT;
   ```
   Test (deterministic):
   - Given the orders table has column user_id,
   - When the transaction runs,
   - Then `\d orders` shows account_id and no user_id.

2. Update application code and ORM models from `user_id` to `account_id` for the orders table. Removes runtime errors after the rename. Complicated domain, analysis picks the references to change.
   Test: Given the renamed column, When the app runs its orders queries, Then no `column "user_id" does not exist` errors appear in logs.

3. Check dependent views with `SELECT * FROM information_schema.views WHERE view_definition ILIKE '%user_id%';` and recreate any that reference the old name. Removes silent breakage in reporting. Complicated domain.
   Test: Given views existed on user_id, When recreated with account_id, Then each view query returns rows.

4. Keep the rollback ready: `ALTER TABLE orders RENAME COLUMN account_id TO user_id;`. Adds a one-command recovery path. Clear domain.

Step 2 MUST happen as soon as possible after Step 1 if queries still use the old name. If Step 1 fails on lock timeout, retry in a low-traffic window rather than forcing it.

## Follow-up

Condition that changes the recommendation: if the app cannot be updated today, skip Step 1 and use the expand-contract path instead.
