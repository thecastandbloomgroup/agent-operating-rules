Headline
Measure summariser failure first, then change prompts or models against a fixed gate.
Agents report “sometimes wrong”, but the failure type is unknown, so broad model changes are unsafe [1].
The fastest reliable path is a labelled sample, a quality rubric, automated checks, and a scored offline run.
The first release should improve measurability before it claims quality gains.

Background
The support tool has an LLM summariser. Agents dislike it, and there is no metric baseline [1].

Relevance
Without a baseline, every change risks looking better while hiding faithfulness errors. A small evaluation loop now prevents later rollback.

Information
Evidence limits: the only hard datum is agent dissatisfaction, from the request [1]. The claim “wrong” is unlabelled and cannot separate factual errors, omissions, tone, format, or privacy defects [judgment]. High confidence plan basis: evaluation must precede optimisation because stochastic systems need explicit metrics and trials [judgment].

Assumption: Tickets are accessible in English and contain customer text plus agent notes. Why not measured: The material does not state it. Validate by: Inspect 20 recent tickets. If wrong: Pause sampling and get export rights.

Assumption: Faithfulness is the largest risk because support summaries guide agent actions. Why not measured: Measuring all failure classes costs more than the first decision. Validate by: Label 200 summaries for faithfulness, coverage, format, and privacy. If wrong: Reprioritise the top class.

Assumption: A review pool of two agents per sample is available this week. Why not measured: The user has not answered. Validate by: Ask team lead for two reviewers for one hour. If wrong: Use previous accepted agent summaries as weak labels.

Alternative considered: Replace the summariser model immediately. It loses because no baseline, acceptance threshold, or rollback metric exists, so a bad swap is indistinguishable from noise [judgment].

3. Run a stochastic baseline of 200 summaries with current prompts before any change. Blocker removed: improvement cannot be proven. 4. Change one variable only: prompt, context window, or model. Blocker removed: confounded releases.
