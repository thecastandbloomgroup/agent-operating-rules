## Headline

You cannot improve what you cannot measure, so first build a labeled evaluation set, then measure the summariser against it, then probe fixes.

- "Sometimes wrong" has no metric, so the first action is measurement, not tuning.
- A small golden set of support tickets with reference summaries gives a baseline.
- Fixes are stochastic work: run them as capped trials against that baseline.
- Confidence: high that measurement-first is correct; this is standard LLM evaluation practice [judgment].

## Background

Your support tool includes an LLM-based summariser. Agents report it is "sometimes wrong." No accuracy metric, no error taxonomy, and no baseline exist.

## Relevance

Changing prompts or models without a baseline risks making the tool worse while feeling better. A measurement loop converts a vague complaint into ranked, testable defects.

## Information

Assumptions:

- Assumption: Ticket text and agent notes are accessible for evaluation. Why not measured: the material does not state it. Validate by: export 100 recent tickets in one session. If wrong: use synthetic tickets instead.
- Assumption: "Wrong" includes fact errors, missing key facts, and wrong tone or priority, in unknown proportions. Why not measured: agents gave no taxonomy. Validate by: classify 100 flagged summaries. If wrong: adjust the error categories before fixing.
- Assumption: The team can write a short rubric and label examples. Why not measured: measuring costs more than the decision is worth to confirm now. Validate by: one labeling session. If wrong: use a pairwise preference test instead.

Evidence: no usage or quality data was provided, so the only statement from a source is "sometimes wrong," one source, no disagreement [1]. This is enough to act on because the cost of measurement is low.

Alternative considered: swap in a stronger model immediately. It loses because without a baseline there is no way to know whether it helped, and cost per call may rise with zero verified gain [judgment].

## End

I recommend that we:

1. **Define "wrong" with a rubric** (Evaluative, Confused domain: the complaint is unclassified, so classify first). Write criteria: factual errors, missing key facts, wrong priority or tone. Weights: 50/30/20. Pass threshold: no factual errors and at most one minor miss. Blocker removed: no shared definition of quality.
2. **Build a 100-ticket golden set** (Deterministic, Clear domain: known best practice, one step). Test in Gherkin:
   Given 100 exported tickets,
   When each has a rubric-labeled reference summary,
   Then the set is frozen with a version tag.
3. **Measure the baseline** (Stochastic, Complicated domain: analysis of known failure kinds). Acceptance test: score current output on all 100 tickets, metric = rubric pass rate, report per category. Blocker removed: no baseline. Step 3 MUST NOT start until Step 2 passes.
4. **Probe two cheap fixes in parallel** (Stochastic, Complex domain: prompt changes have unpredictable effects; leverage is a guess). Cap each probe at one working session: (a) constrained prompt with required fields, (b) extract-then-summarize two-step call. Threshold per probe: pass rate improves by at least 10 percentage points on the same 100 tickets, sample size 100.
5. **Add ongoing sampling** (Clear domain, one step): label 20 live summaries per week with the same rubric, track pass rate over time.

If labeling capacity is unavailable, replace Steps 2 to 4 with a pairwise preference test of old vs. new output on 50 tickets.
