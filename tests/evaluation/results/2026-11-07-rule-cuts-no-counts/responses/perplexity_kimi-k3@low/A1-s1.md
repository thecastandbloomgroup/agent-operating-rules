# Headline

Yes, pin every version in requirements.txt.

- Exact pins make installs reproducible, so a new upstream release can no longer change the build by itself.
- Two broken builds last month show the current failure rate already costs more than pins would.
- Pins still move forward deliberately, through automated pull requests gated by the test suite.
- A checksum per package also rejects a downloaded file that changed after the pin was written.

# Background

This project's requirements.txt names packages without versions. pip therefore resolves each name to the newest release at install time. A library update broke the build twice last month.

# Relevance

Each break blocks the team until someone finds the changed package and reverts it. One exact version per line removes this failure class.

# Information

The failure record is two broken builds in one month, per the request [1].

Each break also cost unplanned debug time [judgment].

An unpinned name lets pip pick the newest matching release, so two install runs can produce different environments [2].

The packaging guide states the rule behind this: use exact pins for an application that you deploy [3].

Leave loose ranges only for a library that others install, per the same guide [3].

pip can also verify a SHA256 checksum, that is, a fingerprint of the downloaded file, when the file declares one [4].

Update tools such as Dependabot open one pull request per upstream release, and CI gates the merge [5].

Record the target Python version at the top of the file, because pins are valid for one interpreter line [judgment].

Confidence: high, based on the project's own failure record [1]. The specification guidance points the same way [2].

**Assumptions**

Assumption: this repository is a deployed application, not a library published to a package index. Why not measured: the request does not state it. Validate by: check the repository for packaging metadata or a release pipeline. If wrong: keep loose ranges in the package metadata and pin only the file CI installs.

Assumption: a test suite exists that CI can run. Why not measured: the request mentions builds but not tests. Validate by: list CI jobs in the repository. If wrong: add a minimal smoke test first, or Step 2 has no gate.

Assumption: CI installs from this same requirements.txt. Why not measured: the request does not name the CI setup. Validate by: read the CI file for the pip install line. If wrong: pin the file CI actually uses.

**Alternative considered**

Strongest alternative: leave versions unpinned and repair breaks when they appear. It loses because two breaks per month already exceed the small daily cost of pins [judgment]. A looser range still lets the resolver move without review, so it keeps the same failure mode described above [2].

# End

I recommend that we take three actions, in this order.

**Step 1. Pin versions.** Run the current passing build. Run `pip freeze`. Record each direct dependency with `==` versions in requirements.txt.
Increment: one edit of one file in one session.
Blocker removed: installs stop changing without a change by the team.
Kind: deterministic. Test, write this first:

Domain: Clear. pip documents freeze and pins as the standard workflow, so deduction from a known rule applies.

**Step 2. Automate updates.** Add the update tool that the CI host already supports. Set the test suite as a required status check.
Increment: one small config file in one session.
Blocker removed: pins can otherwise go stale and collect security debt.
Kind: deterministic, because the output is a fixed configuration file. Test, write this first:

When an upstream dependency publishes a release,
Then a pull request opens, CI runs, and a failing suite blocks the merge.
Domain: Complicated. The tool choice needs analysis: pick the tool native to the CI host.

**Step 3. Add checksums.** Regenerate the file so every package carries a SHA256 checksum. Install with `pip install --require-hashes`.
Increment: regenerate one file, change one install flag.
Blocker removed: a replaced package file on an index cannot enter the build.
Kind: deterministic. Test, write this first:
Given requirements.txt lists a checksum per package,
When a downloaded file does not match its checksum,
Then pip refuses the install and names the offending file.
Domain: Clear. pip specifies the flag and the behavior, so deduction applies.

Sequencing: Steps 2 and 3 MUST NOT start until the test in Step 1 passes. Next, Steps 2 and 3 MAY run in either order.

# Follow-up

If the repository publishes a library for others to install, put loose ranges in its package metadata and keep exact pins only in the file CI installs; see the deployed application assumption [3].

If the team prefers Poetry or uv, its built-in lock file replaces Steps 1 and 3 with the same guarantees.
