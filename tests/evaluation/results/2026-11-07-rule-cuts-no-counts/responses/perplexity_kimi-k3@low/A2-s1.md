## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;`. Large tables need a maintenance window because the statement holds a table lock. Application code that reads `user_id` MUST change at the same time.

## Background

A rename of one column in Postgres is requested. The user is boarding a plane, so a fast, self-contained answer is needed.

## Relevance

The rename is one command, but it takes an ACCESS EXCLUSIVE lock and breaks queries that still reference the old name.

## Information

The command [1]:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

Facts [1]:

1. Postgres takes an ACCESS EXCLUSIVE lock for the rename. The operation is fast (metadata only), but concurrent queries wait behind the lock.
2. Indexes and constraints that reference the column keep working. Postgres updates their names automatically.
3. Views and application ORM models that name `user_id` are not updated. They fail after the rename.
4. Run it inside a transaction to roll back safely: `BEGIN; ALTER TABLE ...; COMMIT;`
5. Wrap with a lock timeout so a busy table does not stall: `SET lock_timeout = '5s';` before the ALTER [judgment].

Assumption: dependent application code and views will be updated separately or tolerate the change. Why not measured: the material does not state the deployment setup. Validate by: `grep -r user_id` on the application and `pg_get_viewdef` on views. If wrong: queries fail after the rename; roll back or use a dual-name view.

Alternative considered: add a new column and backfill instead of renaming. It avoids the lock on busy tables but costs a full table rewrite and dual-write logic. It loses because the request is a direct rename and no traffic constraint was given.

## End

I recommend that we:

1. Run `SET lock_timeout = '5s';` then `ALTER TABLE orders RENAME COLUMN user_id TO account_id;` in one transaction. Kind: deterministic. Test (write first):
   ```
   Given the orders table has column user_id
   When the rename executes and COMMIT succeeds
   Then information_schema.columns lists account_id and not user_id
   ```
   Cynefin: Clear, rename is a known Postgres operation.
2. Update ORM models and view definitions that reference `user_id`, then redeploy. Cynefin: Complicated, the grep analysis picks the fix sites. This step MUST NOT run after step 1 if the application cannot tolerate a gap.
3. Verify: `SELECT account_id FROM orders LIMIT 1;` and a smoke test of the read and write path. Test: rubric, criteria are query success and app smoke test, both must pass. Cynefin: Clear, verification follows a known procedure.

## Follow-up

Condition that changes this: if the table is write-heavy and the 5 s lock timeout fails, use the add-column-backfill path instead of a direct rename.
