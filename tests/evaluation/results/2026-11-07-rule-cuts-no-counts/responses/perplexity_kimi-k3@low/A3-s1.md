Yes. Turn on gzip compression for the API. JSON compresses well, and 400 KB responses are large enough to benefit. The only real cost is CPU, which is small at this size.

Three points support this. First, gzip reduces JSON text to roughly 10 to 20 percent of its original size, because JSON repeats keys and whitespace [judgment]. So a 400 KB response becomes about 40 to 80 KB on the wire. Second, smaller responses cut transfer time and bandwidth costs, which matters most for clients on slow networks. Third, the CPU cost of gzip at moderate level (6) is small for 400 KB payloads, typically a few milliseconds per response [judgment].

Why this matters now: if clients call this API often, the bandwidth saving compounds. If the API sits behind a CDN or load balancer, compression can frequently be enabled there with no code change.

Assumption: clients send Accept-Encoding: gzip, or the framework negotiates it. Why not measured: the material does not state it. Validate by: check one client request header. If wrong: compression must still be negotiation-based, so nothing breaks; non-gzip clients get plain JSON.

Assumption: responses are not already compressed or binary-encoded. Why not measured: the material does not state it. Validate by: inspect one response's Content-Encoding header. If wrong: skip compression, because double-compression wastes CPU.

The strongest alternative is switching to a binary format such as Protocol Buffers. That loses here because it changes the API contract and client code, while gzip needs only a server or proxy setting and no client changes.
