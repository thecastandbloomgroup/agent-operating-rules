## Headline

Measure the errors first, then test a source-grounded version before expanding its use.

- First, separate unsupported claims, missing facts, and harmless wording differences.
- Next, compare one revised version against the current version on the same tickets.
- Finally, require agent approval during a small live trial, with explicit stop rules.

## Background

Your support tool now includes an LLM-based summariser, and agents report that it is “sometimes wrong.” No metrics exist yet. [1]

No summaries, logs, or system access accompany the request, so the tests below are proposed, not executed.

## Relevance

“Wrong” does not identify whether the problem comes from missing input, invented facts, or omitted details. Therefore, changing the prompt alone risks treating the wrong cause. [judgment]

## Information

### Define success before changing the model

Use these distinct measures. The proposed definitions and thresholds are starting points, not measured results. [judgment]

| Measure | Definition | Comparison |
|---|---|---|
| Unsupported-claim rate | Summaries containing a factual claim that the supplied ticket does not support | Current versus revised version |
| Required-fact omission rate | Summaries missing a fact needed for the agent’s next action | Current versus revised version |
| High-impact error count | Wrong facts or omissions that change identity, money, security, or escalation decisions | Zero permitted in each trial |
| Agent correction time | Median seconds agents spend correcting a summary | Current versus revised version |
| Response time | Seconds until the summary appears, including the slowest 5% | Current versus revised version |

Count summaries with errors, not just agent complaints. Also record the error category so one summary can reveal several causes. [judgment]

### Diagnose the failure before choosing the fix

Use this order to keep causes separate:

1. **Input failure:** the model never receives the needed source text.
2. **Output failure:** the model receives the text but contradicts, invents, or omits a required fact.
3. **Preference mismatch:** the output is accurate and complete, but its length or wording does not suit agents.

Repair missing input before revising the prompt. For output failures, test source links, explicit uncertainty, and a fixed summary format. [judgment]

### 3. Test one targeted revision offline

**Kind:** Stochastic, because generated summaries vary.

**Acceptance test first:**

- **Sample:** The 20 reserved tickets, with three outputs per ticket from each version: 120 outputs.
- **Baseline:** The recorded current version, using identical ticket input.
- **Primary threshold:** At least 30% fewer summaries with the selected target error.
- **Safety threshold:** Zero high-impact errors and no increase in required-fact omissions.
- **Speed threshold:** The slowest 5% of responses take no more than 20% longer.
- **Decision limit:** This screen does not establish safety for rare errors.

All thresholds are proposed release gates. [judgment]

If the baseline shows no target errors in this sample, treat the comparison as inconclusive, not successful.

**Work:** In one session, test one revision selected from the audit:

- Repair the input pipeline if required text never reaches the model.
- Otherwise, require source references for factual claims and explicit “not stated” fields.
- Use a fixed format: issue, confirmed facts, actions taken, and unresolved items.

Keep facts separate from suggested actions. Treat ticket text as data, not instructions to the summariser. [judgment]

**Capability added:** Evidence that the revision improves the measured failure.

**Domain:** Complex, through induction from a safe-to-fail trial. New ticket types can break the observed pattern.

**Budget and stop:** Cap work at one session and 120 outputs. Stop on any high-impact error; accept nothing without the full sample.

Step 3 MUST NOT start until Step 2 identifies the target error.

### 4. Run an agent-approved live trial

**Kind:** Stochastic.

**Acceptance test first:**

- **Sample:** 50 eligible tickets, randomly split between current and revised versions.
- **Baseline:** Current-version results from the same trial.
- **Quality threshold:** No high-impact errors and no increase in summaries requiring factual correction.
- **Usefulness threshold:** At least 20% lower median correction time.
- **Review:** Agents approve every summary before use.

These are proposed pilot gates, not proof of a production-wide improvement. [judgment]

**Work:** Run one supervised trial session. Record corrections and correction time with a simple agent control.

**Capability added:** Evidence that offline gains help agents in practice.

**Domain:** Complex, through induction from live use. Different agents and ticket types can break the pattern.

**Budget and stop:** Cap the session at two hours or 50 tickets. Stop immediately on a high-impact error.

If the session ends before 50 tickets, record an incomplete trial rather than accept the revision.

Step 4 MUST NOT start until Step 3 passes.
