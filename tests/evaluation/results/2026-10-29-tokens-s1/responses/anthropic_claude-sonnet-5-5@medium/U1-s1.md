## Headline

Measure the flake first, then quarantine the worst test and probe one cause.

- The cause is unknown, so the first step is to classify failures from existing logs.
- A same-commit rerun gives a flake rate that later fixes can beat.
- Quarantine stops the blocked merges today.
- A capped probe tests the most likely cause without a large commitment.

## Background

You report that the build is flaky. That is, the same commit sometimes passes and sometimes fails. The message gives no logs, no CI (continuous integration) tool, and no failure rate.

## Relevance

A flaky build blocks merges and trains the team to ignore red results. Each rerun also costs developer time.

## Information

Evidence:

- At Google, 1.5% of all test runs showed a flaky result. Almost 16% of tests had some flakiness. [1]

- In a study of open-source projects, async wait caused 45% of flaky tests. Concurrency caused 20%. Test order dependency caused 12%. [2]

- Test-level causes are 70% likely to be the main source, not infrastructure. [judgment]

Assumption log:

A1. The build is an automated CI test run. Why not measured: the material does not state it. Validate by: read the pipeline file. If wrong: replace Step 3 with a fix for the actual job type.

A2. Failures are intermittent on the same commit. Why not measured: no tool can reach the CI history. Validate by: Step 1. If wrong: the cause is a real regression, so bisect the commits.

A3. The last 50 run logs are still stored. Why not measured: the material does not state it. Validate by: open the CI history page. If wrong: start with Step 2 and capture logs.

Alternative considered: automatic retry of failed jobs. It hides the flake and adds run time. It also gives no data on the cause. [judgment]

## End

I recommend that we take these steps, in this order:

1. **Classify failures from history.** Pull the last 50 CI runs. Tag each failure by job step and error text. Kind: deterministic. Cynefin: Confused, so this step gathers what we need to classify the rest. It removes the blocker "we do not know where it fails". The increment fits one session.
   ```gherkin
   Given the last 50 CI runs
   When the script groups failures by step and error text
   Then each failure has exactly one group
   And the report lists groups by count
   ```

2. **Measure the flake rate.** Rerun one passing commit 30 times on the failing job. Kind: stochastic. Cynefin: Complicated, because the analysis is known. Step 2 MUST NOT start until Step 1 names the failing job. Metric: failure rate. Baseline: the rate from Step 1. Pass threshold: the 30 runs produce a rate with its 95% interval. Sample size: 30. This removes the blocker "no number to improve".

3. **Quarantine the top flaky test.** Move the test with the most failures to a non-blocking job. Kind: deterministic. Cynefin: Clear, because quarantine is a known best practice. Step 3 MUST NOT start until Step 1 ranks the tests.
   ```gherkin
   Given the top flaky test is in the non-blocking job
   When the blocking job runs 10 times on one commit
   Then that test does not appear in the blocking results
   ```
   This removes the blocker "merges stop on noise".

4. **Probe the order-dependence cause.** Run the suite 20 times with random test order. Kind: stochastic. Cynefin: Complex, so this is a safe-to-fail probe. Budget: 2 working hours. Stop condition: stop at 20 runs or at the budget. Metric: failure rate against the Step 2 baseline. Pass threshold: a drop of at least half. Sample size: 20. Leverage here is a guess. Run Step 4 in parallel with Step 3.
