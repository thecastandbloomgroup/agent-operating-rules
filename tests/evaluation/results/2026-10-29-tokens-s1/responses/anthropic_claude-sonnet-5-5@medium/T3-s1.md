## Headline

Split this request into two linked projects: migrate auth to JWT first, and test sign-up changes as a separate experiment.

- The two goals have different test types, so one plan cannot test both.
- A baseline for sign-up conversion does not exist in the request, so measure it first.
- A migration changes sign-up behavior, so shipping both together hides the cause of any change.
- JWT tokens expire on their own and need a revocation plan that sessions do not need.

## Background

You run an auth service that stores sessions on the server. You want to move to JWT (JSON Web Token, a signed token the client holds). You also want more visitors to finish sign-up. The request gives no stack, no traffic numbers, and no current conversion rate.

## Relevance

Both changes touch the sign-up path. If they ship together, you cannot tell which one moved conversion. A migration error also blocks every user, so it costs more than a form change.

## Information

Evidence:

- A JWT carries an expiry claim called `exp`, and the server does not need a lookup to check it.

  Source: [1]. [P]

- A signed token stays valid until `exp`, so early revocation needs extra design. This is [inference] from the token format.
- The best-practice guide says the server must check the signing algorithm and reject unexpected ones.

  Source: [2]. [P]

- Session logout deletes one server record, so revocation is simple today. [judgment]
- Confidence that the two goals confound each other: high confidence, because both change the same sign-up path. [judgment]
