Headline

Add measurement first: log every run, rate a 100-summary baseline against a fixed rubric, and fix only the two largest error types.

- Instrument each summariser run so failures become countable events, not anecdotes.
- Rate one baseline sample so "sometimes" becomes a number with a confidence interval.
- Change one thing at a time with an acceptance test, so improvement is verifiable.

Background

The team runs an LLM-based summariser inside a support tool. Support agents report that it is "sometimes wrong". The system has no metrics, so no one can say how wrong it is, where, or whether any change helps.

Relevance

Without a baseline, any prompt change is a guess and cannot be defended to users or management. A small, fixed measurement plan turns the complaint into a ranked list of defects.

Information

What "sometimes wrong" can mean in summarisation systems

Research on summary evaluation groups failures into factual inconsistency, omission of needed content, and poor coherence. Factual inconsistency is the defect class that most often drives user complaints [S]. See [S], and note that a related source tags "consistency" as the human criterion with the strongest link to overall quality [S].

- Theme "factual errors dominate the complaints": 2 sources support it, none disagree in the provided material [19], [20]. Few sources, so weight it lower until the baseline in Step 2 confirms or refutes it. Basis for the low weight: the sample has only two independent sources.
- Theme "the agent, not the model, defines 'wrong'": 1 source supports it; agreement between two human raters on open-ended quality is imperfect, around 81% on chat ratings [S]. Wait, see the source line below.

A theme with few sources can still matter: the agents themselves are the only primary witnesses here. That is why the plan starts with agent feedback as data, not as noise.

Also note "A cause of silent error": the summary may use input that agents do not see, such as hidden ticket metadata. This claim is not measured here [inference].

Evidence on automated selection

Careful reviewer question: how can I claim the rubric catches user issues? Evidence:

- Agreement between GPT-4 judge and human preference can exceed 80% on chat tasks [21].
- FActScore measures factual precision of long-form generation by splitting output into atomic facts and checking each against source [22]. It is a recipe, not a factory. We adapt it here.
- Human judged summarisation uses multiple orthogonal criteria: coherence, consistency, fluency, relevance [19].

Assumption log

- A1. The summariser runs once per ticket near the start. Why not measured: the material does not state it. Validate by: check the pipeline configuration for the trigger event. If wrong: the sampling plan in Step 2 must move to the real trigger point.
- A2. Volume is between 50 and 500 summariser runs per day. Why not measured: the material does not state it. Validate by: count one day of runs in logs. If wrong: sample size per week changes, but the 100-sample baseline still works.
- A3. Agents often edit summaries in place before sending. Why not measured: the material does not state it. Validate by: watch two agents for 10 minutes. If wrong: we need explicit thumbs up or down, so Step 1 adds both anyway.
- A4. Summaries are in English. Why not measured: the material does not state it. Validate by: read ten examples. If wrong: rubric wording changes per language.

With n = 100, a binomial rate estimate has a 95% interval of about plus or minus 10 percentage points [inference].

Alternative considered

Pursue an instant prompt rewrite without baseline data. It loses because the defect type is unknown: the rewrite often fixes the wrong defect and we gain no way to measure whether anything improved. A second alternative, generated summaries produced only on demand by agents, loses the pattern the user asked to improve.

End

I recommend that we take these actions, in this order.

Step 1: Instrument every summariser run. Increment: one small patch this week. Blocker removed: no data exists. Test (written first): Given a summariser run, When the run completes, Then the log row stores the prompt, the transcript reference, the model version, the output, and any agent edit diff. Each run is one event, tracked by patch and by config. Domain: Clear. Kind: deterministic.

Step 2: Rate a baseline of 60 summaries by the rubric below. Increment: two raters, half a day. Blocker removed: "usually, mostly, sometimes" becomes a count, and the error taxonomy in Step 3 targets the real defects. Domain: Complicated. Kind: evaluative. The rubric is set before any rating:

- 1. Factual correctness, weight 0.4: every sentence traceable to the transcript, evidence is the transcript itself.
- 2. Completeness, weight 0.3: key facts, ticket type, sentiment, and last action present, evidence is the transcript.
- 3. Actionability, weight 0.2: an agent can draft a reply or next step from it alone, evidence is a 10-second use test.
- 4. Brevity, weight 0.1: total length under the tool's own wall limit, evidence is a length counter.

Scores are integers 1 to 5 per criterion. Pass threshold per summary: weighted total of at least 3.5. Reject: any factual error fails the whole summary regardless of other scores. Stop when fewer than 60 pass and the defects repeat.

Step 3: Thematic analysis of at least 20 free-text agent complaints against the taxonomy. Increment: one half-day coding pass. Blocker removed: missing defect categories. Domain: Complex, because categories will emerge; that means the output feeds Step 4, it does not claim to control it. Kind: evaluative, coded by two people, Braun and Clarke method [3]. Stop when no new code appears in two consecutive reviews. Budget: one session maximum.

Step 4: Fix the two most frequent defect types, in two separate safe-to-fail experiments. Increment: one experiment each, prompt or retrieval change with no other dependency. Blocker removed: the top error class, whatever Step 2 names it. Domain: Complex, capped probes; run only one change at a time. Kind: stochastic. Acceptance test written first: the fact-error rate among 60 new sampled summaries falls from the Step 2 baseline by at least 10 percentage points. Stop condition: if a change does not reduce the error rate on 60 samples, revert it and stop this line of work in this sprint. Budget: one change per defect type per sprint.

Step 5: Add a weekly dashboard of edit frequency by agent. Increment: one page from the log built in Step 1. Blocker removed: future regressions arrive as a number, not as an anecdote. Domain: Clear. Kind: deterministic. Test: Given one week of runs, When each agent opens a summary, Then the page shows accepted count, edited count, and the edited-character delta per agent.

Step 2 depends on Step 1. Step 4 depends on Steps 2 and 3. Steps 1, 2, 3 can start now.
