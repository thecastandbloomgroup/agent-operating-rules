## Background

The team disagrees about SQL format, and those disputes recur in reviews. [1] The request is to change that team behavior, not merely select a style.

## Relevance

A formatter alone does not settle who decides or whether reviewers must respect the decision. [judgment] Therefore, pair automation with a clear agreement about review behavior. [judgment]

## Information

### Proposed team agreement

Use this text as the starting point:

> Everyone gets a voice in the format decision; nobody needs to prefer the final choice.
>
> The configured formatter decides layout, including indentation, capitalization, and line breaks.
>
> Reviewers do not block changes over layout that passes the formatter.
>
> Reviewers still challenge incorrect results, security risks, performance problems, and unclear meaning.
>
> Anyone can propose a style change in the shared policy discussion, outside an active code review.
>
> The named policy owner closes unresolved choices after the agreed comment period.
>
> Apply new format rules to changed SQL only. Keep broad format-only changes separate from functional changes.

This agreement separates three issues: decision authority, mechanical layout, and substantive review. [judgment] It does not require agreement on personal taste. [judgment]

**Suggested review language:** “Does the formatter cover this? If yes, follow its output. If not, is this a correctness concern or a preference?”

A2. The SQL environment supports a suitable formatter. Why not measured: The material does not state it. Validate by: Test representative SQL files. If wrong: Use a short manual checklist temporarily.
