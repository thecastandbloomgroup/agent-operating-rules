## Headline

Treat connection acquisition as the leading bottleneck; test the cache rollback, but do not restore the old pool size blindly.

- Pool-acquire p95 rises from 3 ms to 690 ms, while request p95 rises from 120 ms to 900 ms. [1]
- The smaller pool coincides with more cache misses and new connection-limit requirements. [2]
- The observed eight service connections do not explain the configured capacity across four pods, so verify the live pool scope. [judgment]

## Background

The release changes the connection pool, cache lifetime, and ORM, the database access layer. [2]  
The supplied traces compare 10,000 requests per window before and after that release. [1]

## Relevance

Errors rise from 0.02% to 0.40%; pool timeouts account for 96% of post-release errors. [1]  
Therefore, prioritize connection availability without violating the new database connection limit. [judgment]

**Leading diagnosis:** requests queue for connections after the pool reduction, with extra cache misses adding database demand. [inference]

**Confidence: high for the bottleneck**, based on acquire spans, exhaustion warnings, and timeout errors. [1]  
The logs also show 1,800 to 2,400 exhaustion warnings per hour, against none before release. [3]

**Confidence: medium for the causal split**, because all three changes ship together. [2]  
The evidence does not isolate pool capacity, cache misses, and connection hold time. [judgment]

Do not subtract span percentiles to calculate their exact contribution to request latency. Their percentiles need not represent the same requests. [judgment]

### What needs verification

- **Pool scope:** four pods each have eight worker threads, but observed service connections peak at eight. [2]  
  An eight-connection limit per pod would imply 32 configured connections; per-process pools would imply another total. [inference]
- **ORM effect:** `selectinload(Order.lines)` changes how the application loads related rows. [2]  
  Existing query spans do not establish total queries, rows, or connection hold time per request. [judgment]
- **Database capacity:** CPU rises only from 38% to 41%. [1]  
  That does not establish spare connection capacity or exclude locks and other database waits. [judgment]
