## Headline

Roll back the latest change now, then send the execs a short fact-based status.

- Restore service first, because a rollback is faster than a root-cause search.
- Send the status message while the rollback runs, so the exec call starts with facts.
- Read the logs only if the rollback fails or is not possible.

## Background

Checkout returns HTTP 500 for every user since 09:12. You are the on-call engineer. The exec call starts in about ten minutes. The material does not name a recent deploy, the stack, or the error text.

## Relevance

Each minute of downtime is a minute of lost checkouts. Execs need impact, action, and a next update time more than a cause.

- Scope: 100% of users, since 09:12, per your message.

**Assumption log**

A1. A deploy or config change went live near 09:12. Why not measured: the material does not state it. Validate by: compare the deploy log time with 09:12. If wrong: skip the rollback test and start Step 3 at once.

A2. The rollback is safe, with no irreversible database migration in the last release. Why not measured: no tool can reach the release notes from here. Validate by: scan the last release for migrations. If wrong: disable the new feature flag instead of a full rollback.

**Alternative considered:** find the root cause first. It loses because a diagnosis has no known end time, while a rollback usually takes minutes [judgment].

## End

I recommend that we do these four actions in this order:

1. **Roll back the last change to the checkout service.**
   - Increment: start one rollback to the previous release.
   - Blocker removed: the faulty change.
   - Kind: deterministic.
   - Domain: Chaotic, because the cause is unknown and every user fails now.
   - Test:
     - Given checkout returns 500 for all users
     - When the previous release is deployed
     - Then a test order returns 200 within 5 minutes

2. **Send the status message while the rollback runs.**
   - Increment: one message with impact, start time 09:12, current action, and next update time.
   - Blocker removed: the execs have no facts.
   - Kind: deterministic.
   - Domain: Clear, because incident messages follow a known template.
   - Test:
     - Given the message template
     - When you post it to the incident channel
     - Then it holds all four fields and is posted before the exec call

3. **Diagnose from the logs.**
   - Increment: read the first stack trace in the checkout error log, and check payment and database status pages.
   - Blocker removed: the unknown cause.
   - Kind: evaluative. Rubric: the trace names a failing component (weight 50%), and the failure time matches 09:12 (weight 50%). Pass threshold: 100%.
   - Domain: Complicated, because analysis of the logs finds the cause.
   - Step 3 MUST NOT start until the test in Step 1 fails, or A2 is false.

4. **Preserve evidence and book the review.**
   - Increment: export the logs, freeze deploys, and send one calendar invite.
   - Blocker removed: lost data and repeat failures.
   - Kind: deterministic.
   - Domain: Clear, because a review after an outage is standard practice.
   - Test:
     - Given service is restored
     - When you export logs and send the invite
     - Then the log file exists and the invite has a date
   - Step 4 MUST NOT start until the test in Step 1 passes.

If A1 is false, replace Step 1 with Step 3.

## Follow-up

Condition that changes the recommendation: a rollback that does not restore service in 5 minutes. Then escalate to a second engineer and run Step 3.
