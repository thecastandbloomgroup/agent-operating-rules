## Headline

Measure the flake rate first, then fix the largest cause, because the cause of the flakiness is not yet known.

- The material gives no logs, so the cause is unknown and data comes before any fix.
- Flaky builds are common and usually trace to a few test-level causes.
- A short quarantine step protects the team while the fix is built.

## Background

The request says the build is flaky. A flaky build passes and fails on the same commit with no code change. The material has no logs, no build tool name, and no failure rate.

## Relevance

Each false failure blocks merges and wastes reviewer time. Teams also learn to ignore red builds, so real defects ship.

## Information

Evidence:

- At Google, about 1.5% of all test runs report a flaky result (Micco, 2016) [1].

- At Google, almost 16% of tests show some flakiness (Micco, 2016) [1].

- In an empirical study of flaky tests, the most common root causes were async wait, concurrency, and test order dependency (Luo et al., 2014) [2].

- Test-level causes are likely (66 to 100%) behind this build, with low confidence: the basis is two outside studies and no local data [judgment].

Assumption log:

A1. The build runs on a continuous integration (CI) server, and the same commit passes and fails. Why not measured: the material does not state it. Validate by: rerun one commit 20 times. If wrong: Step 1 changes to find what differs between runs.

A2. Past CI logs for failed runs are readable. Why not measured: no tool can reach them. Validate by: open the last 50 failed runs. If wrong: Step 2 waits on log access.

A3. The cause lies in tests, not in CI hardware. Why not measured: the material does not state it. Validate by: Step 2 groups failures by failing step. If wrong: replace Step 3 with an infrastructure fix.

Alternative considered: retry failed jobs automatically. It is fast, but it hides the cause and raises build time. It loses on the cause, not on the cost [judgment].

## End

I recommend that we take these steps in order:

1. **Measure the flake rate.** Increment: a script that reruns one unchanged commit 20 times and logs each result and failing step. Blocker removed: no data on the failure rate. Kind: deterministic. Domain: Confused, because the cause and the type of cause are unknown, so this step gathers what we need to classify.

   ```text
   Given a commit with no code change
   When the pipeline runs 20 times
   Then a report lists the pass count and the failing step of each failed run
   ```

2. **Group the last 50 failed runs by failing step and error message.** Step 2 MUST NOT start until Step 1 ends. Blocker removed: no named top cause. Kind: evaluative. Domain: Complicated, because analysis of logs finds the cause. Rubric:
   - Share of failures per cause, weight 50%. Evidence: counts from logs.
   - Reproducibility in Step 1 reruns, weight 30%. Evidence: Step 1 report.
   - Fix cost, weight 20%. Evidence: team estimate in hours.
   - Pass threshold: one cause covers at least 50% of failures, with a weighted score of at least 70.

3. **Quarantine the top flaky test.** Move it to a non-blocking job. Step 3 MUST NOT start until Step 2 names the test. Blocker removed: false red builds stop merges. Kind: deterministic. Domain: Clear, because quarantine is a known practice.

   ```text
   Given the top flaky test is tagged as quarantined
   When the blocking pipeline runs
   Then the test does not run and the build result does not depend on it
   ```

4. **Run a probe that fixes the top cause.** Start after Step 2 and run it in parallel with Step 3. Increment: one fix, such as a wait on a condition instead of a fixed sleep. Blocker removed: the root cause. Kind: stochastic. Domain: Complex, because the effect of a fix shows only after reruns. Leverage is a guess. Acceptance test:
   - Metric: pass rate of the fixed test over reruns.
   - Baseline: the Step 1 pass rate.
   - Threshold: 100% pass.
   - Sample size: 100 reruns.
   - Budget: one working session. Stop after two failed fix attempts.

If A3 is false, replace Step 3 and Step 4 with a fix to the CI environment.
