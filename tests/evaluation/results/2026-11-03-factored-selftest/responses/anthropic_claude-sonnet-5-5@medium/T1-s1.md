## Headline

Stop debating SQL style by hand: pick one rule set once, let a formatter enforce it, and remove format comments from review.

- Cause: the friction comes from people judging taste in every review, not from the style itself.
- Fix: a tool decides the format, so no person has to.
- Proof: a two-week pilot measures whether the friction falls.

## Background

The team disagrees on SQL format, and the disagreement appears in every code review. The request is to fix this as a culture problem. The material gives no data on team size, tools, or the number of format comments.

## Relevance

Each format comment costs reviewer time and creates tension. Both costs recur on every pull request, so the fix pays back quickly.

## End

I recommend that we take these four actions in order:

1. **Choose the formatter and the rules in one 45-minute meeting.**
   - Increment: one meeting, one named decider (A3), one decision recorded in the repo.
   - Blocker removed: no one owns the decision, so the debate never ends.
   - Kind: evaluative. Rubric written first. Criteria and weights: dialect support 30, config matches the team's majority style 25, CI and editor support 25, run time under 10 seconds on the repo 20.
   - Scoring: score each criterion 0 to 5 with trial-run evidence. Pass threshold: weighted total of 70 out of 100. Where the team has no majority, use the tool default.
   - Domain: Complicated, because analysis of the options picks the practice.

2. **Commit the formatter config and format the existing SQL in one commit.** This step MUST NOT start until Step 1 passes its rubric.
   - Increment: one config file, one reformat commit, its hash listed in `.git-blame-ignore-revs`.
   - Blocker removed: old files in mixed style keep the dispute alive.
   - Kind: deterministic. Test:
     ```gherkin
     Given the formatter config is committed to the repo
     When the formatter runs twice on the sql directory
     Then the second run changes zero files
     ```
   - Domain: Clear, because running a formatter is a known practice.

3. **Add a CI check that fails on unformatted SQL.** This step MUST NOT start until the test in Step 2 passes.
   - Increment: one CI job that checks changed SQL files.
   - Blocker removed: without enforcement, the style drifts back.
   - Kind: deterministic. Test:
     ```gherkin
     Given a pull request that contains an unformatted SQL file
     When the CI check runs
     Then the check fails and names the file
     ```
   - Domain: Clear, because the CI step is standard.

4. **Run a two-week pilot of the rule "reviewers do not comment on SQL format".** This is a safe-to-fail probe. It runs in parallel with Steps 2 and 3. The baseline count starts now. The rule starts after Step 3.
   - Increment: one rule announced in the team channel, one tally sheet.
   - Blocker removed: the habit of commenting on format continues even with a tool.
   - Kind: stochastic. Metric: format comments per review. Baseline: the mean of the last 20 reviews.
   - Pass threshold: a mean of at most 20% of baseline across the next 20 reviews.
   - Stop condition: median review time rises more than 20%, or two weeks pass. Budget: one hour of setup and five minutes of counting per review.
   - Domain: Complex, because the team's reaction shows only after the rule starts. The leverage of this step is a guess.

- If the pilot misses its threshold, read the remaining comments in the tally and add the missing rules to the config.
