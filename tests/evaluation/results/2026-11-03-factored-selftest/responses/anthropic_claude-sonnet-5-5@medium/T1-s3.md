## Headline

Adopt one automatic SQL formatter and make it the only judge of style, because the friction comes from unsettled rules that people enforce by hand.

- A single recorded decision ends the debate about which style is right.
- A tool and an automatic check move style enforcement from reviewers to the build.
- A review norm keeps formatting comments out of reviews.
- A measured two-week trial shows whether the friction fell.

## Background

The team has no shared SQL format. Each review (a teammate reads a proposed change before it merges) therefore includes style disputes. The request is to end this friction.

## Relevance

Every review that argues about style delays the change under review. The delay repeats on every change until a rule and a tool replace the opinions.

## Information

Evidence:
- The cause is a missing decision plus manual enforcement. This is the best fit for the symptom "friction in every review" [judgment].
- A formatter tool, for example sqlfluff, can both check and fix SQL layout [judgment].
- Formatting comments are likely (66 to 100%) to fall by at least half within two weeks of enforcement [judgment].
- Choosing among several good styles is a Complicated problem, so analysis picks the practice [18].
- A Pugh matrix compares options against a baseline option across weighted criteria [16].

Assumption log:

A1. The team stores SQL in git and reviews it as pull requests. Why not measured: the material does not state it. Validate by: ask one teammate. If wrong: Step 3 changes to match the actual review flow.

A2. The team can run an automatic check on each change (continuous integration, CI). Why not measured: no tool can reach the repository. Validate by: look for a CI config file. If wrong: replace Step 3 with a local pre-commit hook only.

A3. No written style guide exists. Why not measured: the material does not state it. Validate by: search the repository for a guide. If wrong: use the guide as the baseline option in Step 1.

A4. The team has fewer than 15 people. Why not measured: the material does not state it. Validate by: count the repository contributors. If wrong: add a named owner for style decisions in Step 1.

Alternative considered: a written style guide enforced by reviewers. It loses because people apply a guide unevenly, so the friction stays in reviews [judgment].

## End

I recommend that we take these four actions in order.

1. **Decide the style in one 45-minute session.**
   - Increment: run each candidate style on three real queries, then score them in a Pugh matrix [16] with the tool default as baseline.
   - Blocker removed: no agreed rule exists.
   - Kind: evaluative. Test (rubric, written first): criteria are readability on the sample queries (weight 4), diff noise (3), tool support (2), and cost to adopt (1). A candidate wins only if it beats the baseline by 2 weighted points. Otherwise the tool default wins. Evidence for each criterion is the three sample queries.
   - Cynefin: Complicated, because analysis of known options picks the practice.

2. **Reformat all existing SQL in one commit.** Step 2 MUST NOT start until Step 1 records a decision.
   - Increment: add the formatter config and run the fix command once.
   - Blocker removed: old files would fail the new check.
   - Kind: deterministic. Test:
     ```gherkin
     Given the formatter config from Step 1
     When the check command runs on the repository
     Then it reports zero style violations
     ```
   - Cynefin: Clear, because a standard tool run applies a known practice.

3. **Enforce the style in CI and in a pre-commit hook.** Step 3 MUST NOT start until the test in Step 2 passes.
   - Increment: add one CI job and one hook that run the check command.
   - Blocker removed: style depends on human memory.
   - Kind: deterministic. Test:
     ```gherkin
     Given a pull request with one badly formatted SQL file
     When CI runs
     Then the style job fails and names the file
     ```
   - Cynefin: Clear, because CI checks are a standard practice.

4. **Run a two-week probe of the review norm: reviewers do not comment on format.** Run it in parallel with Step 3 once Step 2 passes.
   - Increment: post the norm in the contributing file and count formatting comments per review.
   - Blocker removed: old habits keep style in reviews.
   - Kind: stochastic. Test (written first): the metric is formatting comments per review. The baseline is the count from the last 20 reviews. The pass threshold is a drop of at least 50%. The sample is the next 20 reviews. Stop condition: after 10 reviews with no drop, stop and hold a 15-minute retrospective. Budget: 2 hours in total.
   - Cynefin: Complex, because team behavior shows its response only afterward. The leverage of this probe is a guess.

## Follow-up

Conditions that change the recommendation:
- If A2 is false, replace Step 3 with the pre-commit hook only.
- If the Step 4 probe fails the threshold, replace the norm with a named style owner who settles disputes.
