## Headline

Raise the database pool size back to a level that matches the load, because the pool cap in this release causes the latency rise.

- The span data shows the delay sits in waiting for a connection, not in queries.
- The release cut `max_size` from 50 to 8, so the pool now caps concurrency below demand.
- The cache TTL cut adds database load, but it is a secondary effect.
- The ORM change shows no measurable cost in the query spans.

## Background

API p95 latency rose from 120 ms to 900 ms after release 2026.10.21. That release changed the pool size, the pool timeout, the cache TTL (time to live), and one ORM query. The attached logs, traces, and diff are the evidence.

## Relevance

Error rate is now 0.40%, up from 0.02%. Each hour adds about 2,000 pool exhaustion warnings and more 503 responses, so users see failures now.

## Information

**Evidence**

- Total p95 rose by 780 ms. Pool acquire p95 rose from 3 ms to 690 ms, which is 687 ms of that rise (88%). [1]
- Query spans did not change. The `db.query orders` p95 moved from 52 ms to 58 ms. [1]
- Active database connections from this service peaked at 31 before the release and 8 after it. [1]
- Database CPU rose from 38% to 41%, so the database has spare capacity. [1]
- 96% of errors in window B are `PoolTimeout` after 5 s. [1]
- Pool exhaustion warnings rose from none to 1,800 to 2,400 per hour. [2]
- The diff cut `max_size` from 50 to 8 and `acquire_timeout_s` from 30 to 5. [3]
- The commit note cites a new connection limit per service (ticket OPS-412) but gives no number. [3]
- Cache miss rate rose from 12% to 31%, and `cache.get` latency did not change. The TTL cut from 300 s to 60 s explains the misses. [1]
- At 405 requests per second and about 29 ms of query time per request (p50 sum of two query spans), about 12 connections are busy on average. This is above 8. [inference]
- Confidence that the pool cap is the main cause: high confidence, three independent measurements (span time, connection count, error text).
- The ORM `selectinload` change has no visible cost: `db.query order_lines` p95 fell from 30 ms to 26 ms. [1]

**Assumption log**

A1. The pool limit of 8 applies per pod, so 4 pods hold up to 32 connections. Why not measured: the material does not state the pool scope, and the "8 active" peak in traces suggests a shared pool. Validate by: read the pool library docs and log the pool scope at startup. If wrong: size the shared pool to 40 instead of 10 per pod.

A2. The OPS-412 limit allows at least 40 connections for this service. Why not measured: the material does not state the number. Validate by: read OPS-412 or run `SHOW max_connections` and check the per-service quota. If wrong: set `max_size` to the limit and add a request queue limit or a connection proxy.

**Alternative considered**

Roll back the whole release. It loses because traces point to one setting, and a rollback also undoes the OPS-412 limit work. Keep it as the fallback if Step 2 fails.

## End

1. **Set `max_size` to 10 per pod (40 total) in `config/db.yaml`.** This removes the pool wait, which is 88% of the latency rise. Kind: deterministic. Cynefin: Complicated, because the right size needs the OPS-412 limit check (A2) first. Step 1 MUST NOT start until A2 is confirmed.
