## Headline

Raise the connection pool size first, because the pool cap of 8 per pod causes most of the added latency.

- Pool wait (`db.pool.acquire`) p95 rose from 3 ms to 690 ms, which is 77% of the 900 ms total [1].
- The database itself is not slower: query spans are flat and server CPU rose only from 38% to 41% [1].
- The cache TTL cut from 300 s to 60 s is a smaller, second cause: the miss rate rose from 12% to 31% [1].
- The ORM change is unlikely to be the cause, because `order_lines` query time did not rise [1].

## Background

Release 2026.10.21 cut the pool `max_size` from 50 to 8 and `acquire_timeout_s` from 30 to 5 [2]. It also cut the cache TTL from 300 s to 60 s and added `selectinload` to the orders query [2]. The API runs 4 pods with 8 worker threads each [2]. p95 latency is the time within which 95% of requests finish. A pool is a fixed set of reusable database connections.

## Relevance

Error rate rose from 0.02% to 0.40%, and 96% of those errors are pool timeouts [1]. Requests that wait 5 s return HTTP 503. Every hour adds 1,800 to 2,400 pool warnings [3].

- The change in the diff matches the symptom: the pool shrank from 50 to 8 per pod [2].
- The logs show "8 of 8 connections in use" with 6 to 14 waiters on every pod [3].
- Theme: pool exhaustion. Three sources agree (traces, logs, diff). No source disagrees. Confidence is high.
- Theme: cache effect. One source (traces) shows the miss rate change. The effect size on latency is not measured. Confidence is low.
- Waiter counts (up to 14) exceed the 8 workers per pod [3]. This is unexplained. [inference] Some code path holds or requests two connections at once.

**Assumption log**

A1. The limit in ticket OPS-412 allows at least 64 connections (16 per pod) for this service. Why not measured: the material does not state the limit. Validate by: read OPS-412. If wrong: set the pool to the limit divided by 4 and cut connection hold time.

A2. The 60 s TTL has no business reason that blocks a longer TTL. Why not measured: the diff gives no reason for the TTL change. Validate by: ask the author of the cache config change. If wrong: keep 60 s and rely on the pool fix.

A3. Some request path takes two connections at once. Why not measured: the logs carry no thread or request identifiers. Validate by: check one slow trace for overlapping `db.pool.acquire` spans. If wrong: the pool size fix still holds, but the target size may drop.

**Alternative considered**

Roll back the whole release. It restores 120 ms quickly, but it also reverts the connection limit change from OPS-412 [2]. That change may protect the database. Rollback is the fallback if Step 2 fails.
