## Headline

Choose one SQL style once, name who breaks ties, and let a tool enforce it in the build.

- The conflict is about who decides, not about which style is correct. [judgment]
- A formatter turns style from a debate into a pass or fail check.
- A two-week trial shows whether review friction drops.

## Background

The team disagrees on SQL format. Style comments appear in every review. The request is to fix this as a culture problem.

## Relevance

Each style comment uses review time that could go to correctness. The cost repeats on every pull request.

## Information

**Evidence**

- SQLFluff, a SQL linter (a tool that checks code against rules), also fixes files from one config file. [1]
- Style debates continue when no one owns the decision and no tool enforces it. [judgment]
- It is likely (66 to 100%) that a formatter ends most style comments. Basis: [judgment], no team data yet.
- Domain labels in End follow the Cynefin framework. [2]

**Assumption log**

A1. The team uses one SQL dialect and a git host with CI (continuous integration, an automatic check on each change). Why not measured: the material does not state it. Validate by: read the repo CI config. If wrong: Step 3 uses a pre-commit hook.

A2. A team lead can act as tiebreaker. Why not measured: the user has not answered. Validate by: ask the lead in one message. If wrong: Step 1 uses a majority vote with a fixed deadline.

A3. The dispute is about taste, not correctness. Why not measured: the material does not state it. Validate by: read 10 recent review threads. If wrong: add the correctness rules to the guide in Step 1.

A4. Style comments are a large share of review comments. Why not measured: no tool can reach the review history. Validate by: count them in the last 20 merged pull requests. If wrong: the Step 4 trial shows no gain, so look for another cause.

**Alternative considered**

Keep a written guide and let reviewers enforce it by hand. It loses because the friction stays in the reviews. [judgment]

## End

I recommend that we take these steps:

1. **Decide the style.**
   - Increment: one 30-minute session that scores three candidates and ends with one guide and one named tiebreaker.
   - Blocker removed: nobody owns the decision.
   - Kind: evaluative. Test: a Pugh matrix with the current code as baseline.
   - Criteria and weights: tool support 30, readability on five real queries 30, size of change to existing code 20, dialect coverage 20.
   - Evidence: tool docs, team scores, and the line count from a dry run.
   - Pass threshold: a score of 70 of 100, and readability no worse than the baseline.
   - Candidates:
     - The SQLFluff default rules. [1]
     - A public SQL style guide. [3]
     - The current majority style of the team.
   - Cynefin: Complicated, because analysis picks among several good practices.

2. **Add the formatter config.**
   - Increment: commit the config file and one command that formats a sample file.
   - Blocker removed: the style lives in people's heads.
   - Kind: deterministic. Test, in Gherkin form: [4]

     Given a SQL file with mixed keyword case and indentation
     When the team runs the format command
     Then the file matches the chosen guide
     And a second run changes nothing

   - Cynefin: Clear, because a best practice exists and the effect is known.
   - Step 2 MUST NOT start until Step 1 names the guide.

3. **Enforce the style in CI and reformat once.**
   - Increment: one pull request that adds the check, plus one reformat commit listed in `.git-blame-ignore-revs`.
   - Blocker removed: nothing enforces the style.
   - Kind: deterministic. Test:

     Given a pull request with a SQL file that breaks the guide
     When the CI check runs
     Then the check fails
     And the output names the file and line

   - Cynefin: Clear, because the CI step is a known practice.
   - Step 3 MUST NOT start until the test in Step 2 passes.

4. **Run a two-week trial of the rule "no style comments in review".**
   - Increment: count the style comments in the last 20 merged pull requests now. After Step 3, apply the rule to the next 20.
   - Capability added: evidence on whether the culture changed.
   - Kind: stochastic. Metric: share of review comments about style.
   - Baseline: the count from the last 20 pull requests.
   - Pass threshold: a drop of at least 80% from the baseline, over 20 pull requests.
   - Cynefin: Complex, because team behavior shows its effect only afterward. Leverage is a guess.
   - Budget: 30 minutes of setup and two weeks. Stop early if reviewers report a missed bug caused by the rule.
   - Run the baseline count in parallel with Steps 1 to 3. The rule starts after Step 3.
