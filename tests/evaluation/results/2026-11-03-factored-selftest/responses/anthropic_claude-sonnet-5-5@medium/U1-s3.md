## Headline

Measure the failures first, then fix the most frequent cause, because a flaky build has no single known cause yet.

- Failure data is missing, so the first step is to classify recent failures.
- The most frequent failure signature gets reproduced and fixed before the others.
- A capped probe tests whether parallel runs cause the flakiness.
- A repeated-run test, not one green run, proves the fix.

## Background

The request says the build is flaky. That means the build passes and fails on the same code. The material gives no logs, no build tool, and no failure rate.

## Relevance

Each false failure wastes developer time and hides real defects. Teams also learn to ignore red builds, so real breakage ships.

## Information

Evidence:

- Google reported that about 1.5% of its test runs showed a flaky result. Almost 16% of its tests had some flakiness [1].
- Timing, shared state, and unpinned dependencies are the usual causes. This is likely, but it is a [judgment] for your build.
- Only one source supports the Google figures, and they describe a different system. Treat them as a loose baseline.

Assumption log:

A1. The failures occur on the same commit with no code change. Why not measured: the material does not state it. Validate by: rerun one failed commit five times. If wrong: the cause is a code defect, so skip Step 3.

A2. Logs from the last 50 runs exist on the continuous integration (CI) server. Why not measured: no tool can reach it. Validate by: open the CI history page. If wrong: Step 1 must first collect new runs.

A3. The team can start builds on demand. Why not measured: the user has not answered. Validate by: trigger one manual run. If wrong: Steps 2 to 4 need a scheduled trigger.

Alternative considered: retry failed builds automatically. It hides the cause and keeps the failure rate unknown, so it loses. [judgment]

## End

I recommend that we do these steps in order:

1. **Classify the last 50 runs.** Increment: one table of failures grouped by failing step and error text. Blocker removed: no one knows the failure mix. Domain: Confused, because the cause is not known. Kind: deterministic. Test:
   - Given the logs of the last 50 runs
   - When each failed run is assigned one error signature
   - Then the table lists every failed run once, with a count per signature

2. **Reproduce the top signature.** Increment: a loop that runs the failing step 50 times in the CI environment. Blocker removed: the failure cannot be studied on demand. Domain: Complicated, because analysis of the logs can find the cause. Step 2 MUST NOT start until the table from Step 1 exists. Kind: stochastic. Test:
   - Metric: failures per 50 runs of the failing step.
   - Baseline: the failure rate of that signature in Step 1.
   - Pass threshold: at least one failure in 50 runs.
   - Sample size: 50 runs.

3. **Run a probe with no parallel jobs.** Increment: one branch that runs the build with one job at a time, 30 runs. Blocker removed: unknown link between parallelism and failure. Domain: Complex, because the effect shows only after the runs. Leverage is a guess. Stop condition: stop after 30 runs or 2 hours of CI time. Run it alongside Step 2. Kind: stochastic. Test:
   - Metric: failure rate over the 30 runs.
   - Baseline: the overall rate from Step 1.
   - Pass threshold: zero failures, which supports shared state as a cause.
   - Sample size: 30 runs.

4. **Fix the top cause and verify.** Increment: one change that fixes the signature from Step 2. Blocker removed: the largest source of false failures. Domain: Complicated, because Step 2 gives the cause. Step 4 MUST NOT start until Step 2 reproduces the failure. Kind: stochastic. Test:
   - Metric: failures over repeated runs of the full build.
   - Baseline: the Step 1 rate for that signature.
   - Pass threshold: zero failures.
   - Sample size: 300 runs. Zero failures in 300 runs gives about 95% confidence that the rate is under 1%.

If A1 is false, replace Step 3 with a review of the code change that broke the build.
