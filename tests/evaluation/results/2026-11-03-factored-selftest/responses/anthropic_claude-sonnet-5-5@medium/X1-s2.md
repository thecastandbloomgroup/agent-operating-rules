## Headline

Measure first, then change the prompt: the summariser cannot improve until the team knows what "wrong" means and how often it happens.

- Agents report errors, but no one has named the error types, so any fix is a guess.
- The tool has no feedback log, so progress cannot be seen.
- A labeled test set turns each prompt change into a measured trial.
- The first fix targets the most common error type, not all errors.

## Background

The support tool has a summariser built on a large language model (LLM). Agents say it is "sometimes wrong". The team has no metrics. The request is to make it better.

## Relevance

An agent who distrusts the summary rereads the full ticket, so the tool saves no time. Wrong summaries can also cause wrong replies to customers.

**Assumption log**

A1. Agents can flag a summary inside the tool with one click. Why not measured: the material does not describe the tool. Validate by: ask one developer. If wrong: add a small feedback widget first.

A2. The tool stores each ticket and each generated summary. Why not measured: no tool can reach it. Validate by: query the database for 10 tickets. If wrong: start logging in Step 2 before Step 3.

A3. At least 100 closed tickets are available to label. Why not measured: the material does not state ticket volume. Validate by: count closed tickets from last month. If wrong: lower the sample size and widen the stated error margin.

A4. Two agents can give about two hours each. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: one rater labels, and agreement is not measured.

**Alternative considered**

Switch to a larger model now. It loses because it costs more per call and no baseline exists to show a gain. [judgment]

## End

I recommend that we take these steps in order:

1. **Name the error types.** Increment: two agents label 50 recent summaries as correct or wrong, with a reason and a ticket quote. Blocker removed: no one knows what "wrong" means. Cynefin domain: Confused, because the error types are unknown. Kind: evaluative. Rubric, written first:
   - Category coverage, weight 40: at least 90% of wrong summaries fit one named category. Evidence: the label sheet.
   - Rater agreement, weight 30: the two raters agree on at least 80% of items. Evidence: both label columns.
   - Traceability, weight 30: every label has a ticket ID and a quote. Evidence: the label sheet.
   - Pass threshold: 80 of 100 points.

2. **Add a one-click "wrong" flag with reason codes.** Increment: a button that logs ticket ID, summary, and reason. Blocker removed: no ongoing metric. Cynefin domain: Clear, because logging a click is a known practice. Kind: deterministic. Step 2 MAY run in parallel with Step 1, and it uses the reason codes from Step 1 when they exist. Test:
   - Given an agent views a summary
   - When the agent clicks "wrong" and picks a reason
   - Then one record with ticket ID, summary text, reason, and time is stored

3. **Build a golden set and measure the baseline.** Increment: 100 labeled tickets with reference facts, plus the current correct-rate. Blocker removed: no baseline to compare against. Cynefin domain: Complicated, because Step 1 gives the analysis that picks the label scheme. Kind: evaluative, scored with the Step 1 rubric. Step 3 MUST NOT start until the Step 1 rubric passes. Its output is one number: the share of summaries rated correct.

4. **Run a capped prompt probe on the top error type.** Increment: one prompt change aimed at the most common category from Step 1, run on the golden set. Blocker removed: the first measured improvement. Cynefin domain: Complex, because the effect of a prompt change shows only after a run. Leverage is a guess. Kind: stochastic. Step 4 MUST NOT start until Step 3 reports a baseline. Acceptance test, written first:
   - Metric: share of summaries rated correct, plus the count of invented facts.
   - Baseline: the Step 3 number.
   - Pass threshold: at least 10 percentage points above baseline, and no rise in invented facts.
   - Sample size: 100 tickets, 3 runs each, so 300 summaries.
   - Budget: two working days. Stop after two prompt variants with no pass.
