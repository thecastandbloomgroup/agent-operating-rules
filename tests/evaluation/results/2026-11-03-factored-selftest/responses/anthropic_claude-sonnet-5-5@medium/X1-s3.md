## Headline

Measure first, because the tool has no metrics, and then change the prompt only against a fixed test set.

- Agents report "sometimes wrong", but nobody knows how often or in what way, so any fix is a guess today.
- A small labelled sample gives the baseline and a list of failure types.
- A one-click flag in the tool keeps the data flowing after the first review.
- Prompt changes then run as capped trials that must beat the baseline.

## Background

The team added a summariser based on a large language model (LLM) to its support tool. Agents say its summaries are "sometimes wrong". The team has no metrics and asks for a better summariser.

## Relevance

An agent who cannot trust a summary rereads the full ticket, so the tool adds cost instead of saving time. Without a measure, the team cannot tell whether a change helps or harms.

## Information

**Evidence**
- One qualitative statement exists: agents say the summaries are "sometimes wrong". It has no count, no rate, and no example. Confidence in any cause is low, because only one theme and no numbers exist.
- No baseline error rate exists. Any target rate is a [judgment].
- A larger model usually improves quality, but the gain for this tool is unknown [no source].

**Assumption log**

A1. "Wrong" means factual errors or omissions, not style. Why not measured: the material does not state it. Validate by: read 20 flagged summaries. If wrong: add a style criterion to the rubric in Step 1.

A2. The team can sample real tickets and edit the prompt. Why not measured: the material does not state it. Validate by: ask the tool owner for read access. If wrong: Steps 1 and 3 need a privacy review first.

A3. Two reviewers are available for about two hours. Why not measured: the user has not answered. Validate by: book the time. If wrong: use one reviewer and accept lower confidence.

**Alternative considered**

Switch to a larger model now. It loses because without a baseline the team cannot show a gain, and cost per ticket rises [judgment].

## End

I recommend that we take these steps in order:

1. **Review 50 recent summaries against a rubric (evaluative, Confused).** This removes the blocker that nobody knows the failure types. The domain is Confused because the cause of the errors is unknown. The work fits one session with two reviewers.
   - Criteria and weights: faithfulness to the ticket 40%, completeness of the key facts 30%, usefulness for the next agent action 20%, length 10%.
   - Pass threshold: a summary passes at a weighted score of 80 or more and no faithfulness error.
   - Evidence per criterion: the ticket text, the summary, and a quoted line for each error.
   - Output: the baseline pass rate and a list of failure types with counts.

2. **Add a "wrong summary" button with a reason list (deterministic, Clear).** This adds a continuous measure. The domain is Clear because a feedback button is a known pattern. Step 2 MAY run in parallel with Step 1. The reason list uses the failure types from Step 1 once they exist.
   - Given an agent views a summary
   - When the agent clicks "wrong" and picks a reason
   - Then the tool stores the ticket ID, summary version, and reason [14]

3. **Fix the test set and the acceptance test (stochastic, Complicated).** This removes the blocker that no change can be judged. The domain is Complicated because an analyst can pick the sample and the metric. Step 4 MUST NOT start until Step 3 is done.
   - Metric: share of summaries that pass the Step 1 rubric.
   - Baseline: the Step 1 pass rate.
   - Threshold: the baseline plus 10 points, with no rise in the omission rate. The 10 points is a [judgment].
   - Sample size: 300 tickets, the same tickets for each version.

4. **Run a capped prompt probe (stochastic, Complex).** The domain is Complex because the effect of a prompt change shows only after the trial [18]. The probe changes one thing: the prompt tells the model to use only facts in the ticket and to write "not stated" for a gap.
   - Budget: one working session and 300 tickets.
   - Stop condition: stop when the pass rate falls below the baseline on the first 100 tickets.
   - Leverage is a guess.
   - Accept the change only when the Step 3 threshold is met. If not, run one new probe for the most frequent failure type from Step 1.

If A1 is false, add a style criterion to the rubric and repeat Step 1.

## Follow-up

Open questions: none.

Condition that changes the recommendation: if Step 1 shows a pass rate above 95%, stop at Step 2 and keep monitoring flags.
