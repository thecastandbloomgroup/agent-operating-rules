## Headline

Measure the errors first, then fix the most common error type with tested prompt changes.

- No baseline error rate exists, so the first step is to label 100 real summaries.
- A feedback button in the tool gives a continuing count of wrong summaries.
- A prompt probe, scored against the baseline, tests one fix at a time.
- A release gate stops later changes from making the summariser worse.

## Background

The support tool shows an LLM summary of each ticket. LLM means large language model, a system that writes text from a prompt. Agents say the summaries are "sometimes wrong" (per the query). The team has no metrics.

## Relevance

A wrong summary can send an agent to the wrong action on a customer case [judgment]. Without a number, the team cannot tell whether a change helps.

**Assumption log**

A1. Agents mean factual errors (invented or missing details), not style. Why not measured: the material gives no example. Validate by: Step 1 labels. If wrong: Step 3 targets the style problem found.

A2. The team can log events in the tool and edit the prompt. Why not measured: the material does not state it. Validate by: ask an engineer to log one test event. If wrong: Step 2 uses a shared form.

A3. Policy allows staff to review real tickets. Why not measured: the material does not state it. Validate by: ask the data owner. If wrong: use redacted tickets.

A4. Two agents can spend about two hours on review. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: cut the sample to 50 and widen the error margin.

**Alternative considered**

Switch to a larger model first. It loses because no baseline exists to show a gain, and the cost is higher [judgment]. Revisit it if Step 3 fails.

## End

I recommend that we take these four steps in order.

1. **Label a baseline sample.**
   - Increment: two reviewers score 100 recent summaries against the ticket text and count errors by type.
   - Blocker removed: no one knows the error rate or the main error type.
   - Kind: evaluative.
   - Rubric, written first: functional correctness (weight 50), functional completeness (weight 30), readable in 10 seconds (weight 20).
   - Pass threshold: a score of 80 or more and zero invented facts.
   - Evidence needed: the ticket text, the summary, and two reviewers. A third reviewer settles splits.
   - Domain: Confused, because the cause of the errors is unknown. This step gathers what the team needs to classify the work.

2. **Add a "Wrong summary" button.**
   - Increment: the button offers four reasons (invented fact, missing fact, wrong status, other) and logs each click.
   - Blocker removed: no ongoing signal.
   - Kind: deterministic.
   - Test, written first:
     ```gherkin
     Given an agent views a ticket summary
     When the agent clicks "Wrong summary" and picks "invented fact"
     Then the system stores one event with summary ID, reason, and model version
     ```
   - Domain: Clear, because a known pattern (a feedback button) applies.

3. **Run a prompt probe on the top error type from Step 1.**
   - Increment: test up to three prompt variants in one working day. Example: require the summary to use only facts that appear in the ticket.
   - Blocker removed: the error rate is high and has no tested fix.
   - Kind: stochastic.
   - Acceptance test, written first: the metric is the share of summaries with any wrong or invented fact. The baseline is the Step 1 rate. The pass threshold is half the baseline or less. The sample is 100 new tickets, scored by two reviewers.
   - Stop condition: stop when a variant passes or after three variants fail.
   - Domain: Complex, because the effect of a prompt change shows only after a trial. The leverage is a guess.
   - Step 3 MUST NOT start until Step 1 ends. It runs in parallel with Step 2.

4. **Add a release gate.**
   - Increment: a script runs the labelled tickets three times on any new prompt or model and reports the mean error rate.
   - Blocker removed: later edits can bring errors back without notice.
   - Kind: deterministic.
   - Test, written first:
     ```gherkin
     Given the accepted error rate from Step 3
     When a new prompt version runs on the labelled tickets
     Then the release is blocked if the mean error rate is above the accepted rate
     ```
   - Domain: Complicated, because the team must first analyse run-to-run noise to set the limit.
   - Step 4 MUST NOT start until the Step 3 test passes.

## Follow-up

Conditions that change the recommendation:

- If Step 1 shows an error rate under 5% [judgment], stop after Step 2. More work costs more than it returns.
- If most errors come from long tickets, replace Step 3 with a probe that splits the ticket first.
- If A1 is false, rewrite the Step 3 metric for the style problem.
