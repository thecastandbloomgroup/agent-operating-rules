## Headline

Measure the flake rate first, then fix the largest cause.

- The cause is unknown, so data comes before any fix.
- Flaky builds repeat a few causes, so grouping failures finds the largest one fast.
- Quarantine of the worst test protects the team while the fix is built.

## Background

The report says the build is flaky: the same code sometimes passes and sometimes fails. No logs, project name, or CI (continuous integration, the service that runs builds) were given. The goal is a stable build.

## Relevance

A flaky build wastes reruns. It also teaches people to ignore red results, so real defects pass unnoticed.

## Information

Evidence:

- Google reported that 1.5% of test runs were flaky, and almost 16% of tests had some flakiness. [1]

- Luo et al. found that async wait, concurrency, and test order dependency were leading causes in open source projects. [2]

- Two sources support the theme "a few causes repeat". Neither disagrees. Both are from large code bases, so fit to this build is [judgment].

Assumption log:

A1. The build runs on a CI service, and the logs are readable. Why not measured: the material does not state it. Validate by: open the last CI run. If wrong: Step 1 needs a manual log export.

A2. "Flaky" means one commit gives both pass and fail. Why not measured: the user has not answered. Validate by: rerun one commit twice. If wrong: the problem is a real regression, so skip Steps 2 to 4.

A3. The failures come from tests, not from the build tool. Why not measured: no tool can reach the logs. Validate by: read ten failure logs. If wrong: Step 4 targets a build step, not a test.

A4. The build still works most of the time, so the state is not Chaotic. Why not measured: the material does not state it. Validate by: count passes in the last 50 runs. If wrong: see Follow-up.

Alternative considered: retry every failed job automatically. It loses because it hides the cause and adds build time [judgment]. The flake rate stays unknown.

## End

I recommend that we take these four steps, in this order:

1. **Export the last 50 CI runs to one table.** This removes the blocker "no data to classify". Domain: Confused, because the cause is unknown. Kind: deterministic.
   - Given 50 recorded CI runs
   - When the export script runs
   - Then the table has 50 rows, and each failed row names a test or build step

2. **Rerun the latest passing commit 20 times, as a probe.** This measures the real flake rate. Domain: Complex, because causes show only after the runs. Kind: stochastic. Metric: failure rate. Baseline: the rate from Step 1. Pass threshold: at least 1 failure reproduced. Sample size: 20 runs. Stop at 20 runs or 2 hours. Run it beside Step 3 preparation. Leverage is a guess.

3. **Sort the failures into four causes and name the top one.** Step 3 MUST NOT start until Steps 1 and 2 finish. The causes are test code, product code race, environment, and external service. Domain: Complicated, because log analysis picks the cause. Kind: evaluative.
   - Rubric criteria: log evidence (weight 50), reproduced in Step 2 (30), share of failures (20).
   - Pass threshold: a score of 70 or more.
   - Evidence: log lines, rerun results, and counts from Step 1.

4. **Quarantine the top flaky test and open a fix ticket.** Step 4 MUST NOT start until Step 3 names a test. Move the test to a non-blocking job. Domain: Clear, because quarantine is a known practice. Kind: deterministic.
   - Given the top flaky test is marked quarantined
   - When the blocking build runs 20 times
   - Then the test does not run in the blocking job, and the ticket links to the test

## Follow-up

Condition that changes the recommendation: if A4 is false and the build almost never passes, replace Step 1 with a merge freeze and a rollback to the last green commit.
