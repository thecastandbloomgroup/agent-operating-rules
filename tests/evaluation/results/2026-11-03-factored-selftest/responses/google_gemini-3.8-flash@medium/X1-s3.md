### Headline

Establish an evaluation dataset and error taxonomy from agent feedback before you change the model or prompt.
First, capture agent corrections directly inside the support interface to build a ground-truth benchmark.
Next, measure the current baseline accuracy using a standardized scoring rubric.
Then, test prompt improvements against that benchmark using acceptance thresholds.

### Background

You deployed a Large Language Model (LLM) to summarize customer support tickets [judgment].
Support agents report that the generated summaries are sometimes incorrect [judgment].
Your team does not track accuracy metrics or structured logs for these errors [judgment].

### Relevance

You cannot fix the summarizer without measuring what fails.
A measurement process prevents blind changes that increase agent workload.

### Information

Customer support summarization often fails due to factual hallucination, omission of critical customer issues, or poor formatting [judgment].
Without error categories or quantitative baselines, prompt changes cause regressions [judgment].
Therefore, you must collect structured error data to evaluate model quality [judgment].

#### Assumption Log

A1. Support agents will provide feedback if the feedback tool requires one click. Why not measured: The material does not state it. Validate by: Check feedback submission rates across 50 tickets. If wrong: Conduct brief live interviews with five agents instead.

A2. Summarizer errors stem from prompt instructions or context window truncation rather than model downtime. Why not measured: The material does not state it. Validate by: Inspect ten raw error cases manually. If wrong: Shift focus to infrastructure stability.

#### Alternative Considered

Tune prompt parameters immediately without building an evaluation dataset.
This alternative loses because you cannot measure whether changes fix errors or create new regressions [judgment].

### End

I recommend that we:

1. Add a two-click feedback widget to the agent interface.
This action removes the blocker of missing error data.
Domain: Clear, because best practices for user interface feedback controls are well established.
Test (Deterministic):
Given a generated summary on a resolved ticket
When an agent clicks the thumbs-down button
Then the interface displays error options for factual error, missing detail, and bad formatting.

2. Build an initial evaluation benchmark of fifty historical tickets with human-curated summaries.
This action creates the baseline dataset needed for systematic testing.
Domain: Complicated, because selecting representative tickets requires domain expertise and sampling analysis.
Test (Evaluative):
Use a Kepner-Tregoe rubric with weights: Factual Accuracy (0.50), Core Issue Coverage (0.30), and Brevity (0.20).
A summary passes when its weighted score reaches at least 0.85 out of 1.00 based on expert review.

3. Run an experiment with structured prompt constraints and few-shot examples on the benchmark.
This action adds the capability to prevent factual hallucinations and omissions.
Step 3 MUST NOT start until the test in Step 2 passes.
Domain: Complex, because prompt adjustments produce varied outputs across different conversation styles.
Budget: Cap this probe at twenty engineering hours and three prompt iterations.
Test (Stochastic):
Metric: Factual accuracy score across the fifty benchmark tickets.
Baseline: Current prompt score on the benchmark.
Pass threshold: At least 15% relative improvement over baseline with zero regressions on core issue coverage across fifty tickets.

### Follow-up

If A1 is false, replace Step 1 with a weekly manual audit of forty random tickets by team leads.
