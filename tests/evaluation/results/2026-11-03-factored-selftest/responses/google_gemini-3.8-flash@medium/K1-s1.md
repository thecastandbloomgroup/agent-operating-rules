# Headline

Revert the cache time-to-live and restore the pool timeout to resolve connection starvation.
- Database connection wait time explains 687 milliseconds of the 780 millisecond latency increase.
- The shorter cache time-to-live increased database query volume by 158 percent.
- The reduced connection pool size creates a bottleneck for the 32 application workers.
- The object-relational mapping query changes caused no latency increase.

# Background

Release 2026.10.21 increased the orders endpoint 95th percentile (p95) latency from 120 milliseconds to 900 milliseconds [1].
The release modified query loading, reduced cache expiration duration, and lowered pool limits [2].
The application logged between 1,800 and 2,400 connection pool exhaustion events per hour following deployment [3].

# Relevance

This regression causes 0.40 percent of user requests to fail with gateway timeouts [1].
Therefore, immediate mitigation restores normal order checkout response times for customers.

# Information

This section covers trace evidence, assumption tracking, and the rejected alternative.
First, pool acquisition delay accounts for 88 percent of the added latency [1].
The span grew from 3 milliseconds at p95 to 690 milliseconds at p95 [1].
In contrast, the order lines query p95 dropped from 30 milliseconds to 26 milliseconds [1].
This drop shows that the object-relational mapping (ORM) query change did not cause the regression [judgment].
Next, the cache miss rate climbed from 12 percent to 31 percent [1].
This rise occurred because the cache time-to-live (TTL) dropped from 300 seconds to 60 seconds [2].
At 405 requests per second, database queries surged from 49 queries per second to 126 queries per second [1].
However, database connection pool capacity dropped from 50 connections to 8 connections per pod [2].
The four application pods run 32 worker threads in total, which overwhelmed the smaller pool [2].
The pool timeout also fell from 30 seconds to 5 seconds [2].
Consequently, connection acquisition timeouts caused 96 percent of the failed requests [1].
The findings indicate database connection starvation with high confidence, based on trace and log alignment.
For example, active connections peaked at 8 during Window B, that is, below worker concurrency (see A1) [1].

A1. Ticket OPS-412 set a database connection cap of 8 connections across the entire service. Why not measured: The material does not state it. Validate by: Inspect ticket OPS-412 and database server connection parameters. If wrong: Pods can raise connection pool limits without database reconfiguration.

Alternative considered: Roll back the full release including the ORM query changes.
This alternative loses because the ORM change decreased order lines query latency by 4 milliseconds at p95 [1].
