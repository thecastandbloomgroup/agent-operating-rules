### Headline

Deploy an evaluation harness and grounded prompt changes to eliminate unsupported claims in summaries.
First, a sampled rubric establishes the baseline error rate across historical tickets.
Second, an automated test pipeline blocks prompts that fail factual consistency checks.
Third, in-tool agent feedback captures production errors for continuous evaluation.

### Background

You deployed a Large Language Model summariser into a customer support tool.
Support agents report that generated summaries are wrong without systematic data.
You currently track no quantitative performance metrics for this system.

### Relevance

Inaccurate summaries cause agent errors and slow ticket handling [judgment].
Establishing metrics now prevents customer miscommunication and guides engineering effort [judgment].

### Information

#### Evidence
LLM hallucination rates in abstractive text summarisation often reach 15% to 30% without explicit source grounding [1].
Agent satisfaction drops when errors require manual verification of the entire ticket history [judgment].
A ground-truth evaluation set of 50 to 100 tickets provides statistical significance for prompt testing [2].

#### Assumption log
A1. The support tool stores raw ticket transcripts and agent notes. Why not measured: The material does not state it. Validate by: Check the database schema. If wrong: Export transcripts manually from the ticketing vendor API.
A2. Summarisation failures stem from factual inconsistency rather than formatting issues. Why not measured: The user has not answered. Validate by: Review 20 reported errors with agents. If wrong: Reallocate work to output schema validation.

#### Alternative considered
Fine-tuning a smaller language model was considered.
It loses because prompt engineering with an evaluation harness costs less and solves grounding faster without training overhead [3].

### End

I recommend that we take the following four actions:

1. Create a 50-ticket golden test set and scoring rubric.
   - Test (Evaluative):
     - Rubric:
       - Criterion 1: Factual consistency (source grounding), weight 0.50, requires direct quote match.
       - Criterion 2: Completeness of customer issue, weight 0.30, requires presence of core symptom.
       - Criterion 3: Resolution status accuracy, weight 0.20, requires correct ticket state.
     - Pass threshold: 90% weighted score across 50 sample tickets.
   - Increment: Sample 50 resolved tickets, extract reference summaries, and score current outputs against the rubric in one session.
   - Blocker removed: Removes the lack of baseline accuracy metrics.
   - Cynefin domain: Complicated, because expert inspection is required to score semantic accuracy.

2. Implement an automated continuous evaluation script for factual consistency.
   - Dependency: Step 2 MUST NOT start until the test set in Step 1 passes validation.
   - Test (Deterministic):
     - Given a ticket transcript and a generated summary
     - When the verification script checks claims against the transcript
     - Then the script outputs a binary consistency label for each claim
   - Increment: Write a deterministic Python evaluation script that runs candidate summaries against the 50 golden tickets.
   - Blocker removed: Adds the capability to run regression tests before any prompt deployment.
   - Cynefin domain: Clear, because best practice assertion scripts link directly to inputs.

3. Deploy a grounded chain-of-thought prompt as a safe-to-fail probe.
   - Dependency: Step 3 MUST run against the harness built in Step 2.
   - Test (Stochastic):
     - Metric: Hallucination rate (percentage of summaries with unsupported claims).
     - Baseline: Current prompt error rate measured in Step 1.
     - Pass threshold: Less than 5% hallucination rate.
     - Sample size: 50 golden tickets evaluated across 3 runs (150 total samples).
   - Increment: Update the summariser system prompt to extract facts before generating the final summary, capped at a two-hour test run.
   - Blocker removed: Removes ungrounded generation errors in model output.
   - Cynefin domain: Complex, because prompt variations produce emergent outputs that require empirical probing.

4. Add binary feedback buttons to the support tool interface.
   - Dependency: Step 4 MUST NOT deploy until Step 3 meets its pass threshold.
   - Test (Deterministic):
     - Given an agent views an active summary
     - When the agent clicks the thumbs-down button
     - Then the system records the transcript, summary, and timestamp to the evaluation log
   - Increment: Add thumbs-up and thumbs-down buttons to the UI component in one session.
   - Blocker removed: Removes the lack of ongoing production performance data.
   - Cynefin domain: Clear, because UI telemetry follows established implementation patterns.
