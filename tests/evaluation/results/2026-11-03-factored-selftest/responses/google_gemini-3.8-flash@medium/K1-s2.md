# Headline

Revert the cache time-to-live setting to 300 seconds and increase the database pool size to eliminate connection acquire queueing.
The trace data shows that connection acquire time accounts for 687 ms of the 780 ms latency increase [1].
Lowering the cache time-to-live increased cache misses from 12% to 31%, which increased database query volume [1], [2].
The reduced pool size of 8 connections per pod caused connection starvation during traffic peaks [1], [3].

# Background

Release 2026.10.21 changed the object-relational mapping query, reduced cache time-to-live from 300 to 60 seconds, and lowered database pool size from 50 to 8 [2].
Following deployment, API p95 latency rose from 120 ms to 900 ms, and the error rate rose from 0.02% to 0.40% [1].
The service team requested root-cause identification and corrective actions based on the provided logs, diff, and trace summaries.

# Relevance

The latency degradation violates normal service levels and causes HTTP 503 errors for active users during peak traffic [1], [3].
Fixing this regression restores normal customer latency and prevents connection pool exhaustion [1].

# Information

The trace data isolates the delay to database connection acquisition [1].
In Window A, p95 connection acquire latency was 3 ms [1].
In Window B, p95 acquire latency reached 690 ms, which represents 88% of the total request latency [1].
Individual query durations remained stable; `orders` query p95 changed from 52 ms to 58 ms, and `order_lines` changed from 30 ms to 26 ms [1].
Therefore, the object-relational mapping query modification did not cause the regression [1], [2].

Two changes in Release 2026.10.21 combined to exhaust database connections [2].
First, reducing `default_ttl_s` from 300 to 60 seconds increased the cache miss rate from 12% to 31% [1], [2].
Because misses increased by a factor of 2.58, read traffic to the database more than doubled [1].
Second, `max_size` in `config/db.yaml` decreased from 50 to 8 connections per pod [2].
Each of the 4 pods runs 8 worker threads [2].
With 8 connections per pod and 31% cache misses, waiters rapidly queue up, triggering warnings and 5-second timeouts [1], [3].
The database CPU peaked at 41%, which indicates ample database server headroom [1].

A1. Ticket OPS-412 allows at least 64 total connections to the database for this service. Why not measured: The material does not state it. Validate by: Check ticket OPS-412 in the issue tracker. If wrong: Keep pool size capped to the database maximum and rely on cache retention and connection pooling proxies.

We considered reverting only the object-relational mapping change in `app/orm/orders.py` [2].
This alternative loses because trace metrics show that query execution latency decreased or remained flat after that change [1].
