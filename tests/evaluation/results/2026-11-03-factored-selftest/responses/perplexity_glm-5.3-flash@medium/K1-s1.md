## Headline

The connection pool change is the cause: the release cut max_size from 50 to 8 while the 32 workers stayed unchanged, so workers now queue for connections. Supporting points:

1. Pool acquire time explains the latency: the p95 grew from 3 ms to 690 ms of the 900 ms total, per the attached traces.
2. Pool exhaustion appeared only after the release: warnings went from 0 per hour on 2026-10-20 to 1,800 to 2,400 per hour on 2026-10-22, per logs.txt.
3. The database is not overloaded: CPU moved from 38% to 41% peak, and active connections fell from 31 to 8, per traces.txt.
4. The cache and ORM changes add load but are not the blocker: cache miss rate went from 12% to 31%, and query times stayed near baseline (52 to 58 ms p95).

## Background

The p95 latency of GET /customers/{id}/orders rose from 120 ms to 900 ms after release 2026.10.21, deployed 2026-10-21 14:05 UTC. The user asks for the cause and the fix. The release touched the pool config, the cache TTL, and the ORM query.

## Relevance

Error rate grew from 0.02% to 0.40%, and 96% of the errors are PoolTimeout, per traces.txt. Requests fail after a 5 s wait, so each minute of delay costs about 4 bad requests per 1,000 plus the latency for the rest.

## Information

**Evidence and analysis.** The numbers separate the three changes:

- db.pool.acquire p95: 3 ms in window A, 690 ms in window B [traces.txt] [P]. It makes up 77% of the 690 ms growth of the total wait. Therefore the queue at the pool is the bottleneck, not the queries, cache, or serialization.
- "pool exhausted" warnings per hour: 0 on 2026-10-20, 1,800 to 2,400 on 2026-10-22 [logs.txt] [P]. This is a new behavior after the release.
- Deployment note: 4 pods with 8 worker threads each, 32 workers, unchanged [release.diff] [P]. Because max_size is 8, at most 8 of 32 workers hold a connection at once. The rest wait, and the 5 s acquire timeout turns some waits into 503 responses.
- db.query orders p95: 52 ms in A, 58 ms in B; db.query order_lines p95: 30 ms in A, 26 ms in B [traces.txt] [P]. So the added selectinload in orders.py costs almost nothing here [traces.txt] [P].
- Cache miss rate: 12% in A, 31% in B [traces.txt] [P]. The TTL cut from 300 s to 60 s explains this [release.diff] [P]. More misses put more load behind the pool, so it makes the queue longer, but it is a secondary factor.
- Database CPU peak: 38% in A, 41% in B [traces.txt] [P]. Headroom above 10 times the growth of active connections rules out database saturation as the cause [inference].

The management of this failure sits in the Clear domain: the traces name the blocked span, and the diff names the config change [18].

**Assumption log.**

- A1. The per-service DB connection budget allows at least 40 connections. Why not measured: the material does not state the limit in ticket OPS-412. Validate by: read OPS-412 or ask the DBA. If wrong: raise max_size only to the budget, and cut worker threads instead.
- A2. The TTL cut from 300 to 60 s was not a required limit. Why not measured: the material gives no ticket or reason for cache.yaml. Validate by: ask the change author. If wrong: keep ttl 60 s and raise max_size higher, because more misses mean more acquires.

**Alternative considered.** The ORM change is the strongest alternative suspect, because selectinload adds one query per response to order lines. It loses on the measurement: both query spans stayed at their window A times, and the DB had free CPU and idle capacity, so the extra query did not drive the p95 [traces.txt] [P].

## End

1. **Step 1: confirm the connection budget in OPS-412.** Increment: one DBA check of the per-service limit. Blocker: A1, the risk of exceeding the DB limit. 2. **Step 2: set pool max_size to 40 and acquire_timeout_s to 30 in db.yaml.** Step 2 MUST NOT start before Step 1 passes. Increment: one config line per value, one deploy. Blocker: the acquire queue, which holds 690 ms of the 900 ms p95 [traces.txt] [P]. Test, written first [14]:
   ```gherkin
   Given release 2026.10.21 pool max_size of 8 and a fixed request rate
   ```

   Domain: Clear, because the trace data maps the config directly to the queue [18].

   ```gherkin
   Given a TTL of 60 s and a miss rate of 31%
   ```

   Domain: Clear, same reason as Step 2 [18].

Domain: Complex, because worker behavior after the fix is visible only in the run [18]. Stop condition: if warnings stay above 200 per hour at max_size 40, go back to Step 1 with the new data [judgment].
