## Headline

Redirect the fix away from the ORM query and toward the two config values: the pool now caps the whole service at 8 connections, and the cache TTL cut doubles the load on it. Restore pool capacity to at least 32 connections, raise acquire timeout back to 30 s, and return the cache time to live (TTL) to 300 s.

Supporting points:

- Pool acquire wait grew from 3 ms to 690 ms at the 95th percentile (p95), 687 ms of the 780 ms total increase [3].
- The diff cut pool max_size from 50 to 8 and acquire timeout from 30 s to 5 s [2].
- Traffic, query spans, and database CPU stayed level, so the regression comes from config, not load [3].
- The TTL cut raised the cache miss rate from 12% to 31%, which adds queries under the smaller pool [3].

## Background

The API p95 latency rose from 120 ms to 900 ms after release 2026.10.21, deployed 2026-10-21. The release touched the object relational mapper (ORM) layer, the cache config, and the connection pool. Logs, traces, and the diff are attached.

## Relevance

The error rate moved from 0.02% to 0.40%, and 96% of the new errors are pool timeouts [3]. Three of the regressions are single config values, so a fix needs one edit and one deploy, not new code.

## Information

**Pool saturation is the main mechanism.**

- db.pool.acquire p95 moved from 3 ms to 690 ms, within a total that moved from 120 ms to 900 ms [3].
- Logs show "pool exhausted: 8 of 8 connections in use" with 9 to 14 waiters on all four pods [1]. Warnings run at 1,800 to 2,400 per hour; the baseline was none [1].
- The diff set max_size to 8; the commit message cites ticket OPS-412, a new per-service database connection limit [2].
- The service runs 4 pods with 8 worker threads each, so 32 workers share this pool [2].

**Load and queries did not cause it.**

- Peak requests per second (rps) moved from 410 to 405 [3].
- db.query orders p95 moved 52 to 58 ms; order_lines moved 30 to 26 ms [3]. Therefore the selectinload change did not slow queries; keep it.
- Database CPU peak moved 38% to 41% [3]. The database has headroom; connection supply is the limit.

**The TTL cut adds pressure.**

- default_ttl_s fell from 300 to 60; the miss rate rose from 12% to 31% [3]. Each miss sends a query to the saturated pool.

**Assumption log**

- A1. Ticket OPS-412 sets a per-service connection limit of 32 or more. Why not measured: the ticket is not in the material; the user has not answered. Validate by: open OPS-412 and read the limit. If wrong: cap max_size at the limit minus 2, and put a connection pooler between the service and the database.
- A2. The pool cap is shared across the service. Why not measured: peak active connections in window B equal 8, the new max_size; four pods with min_size 5 each would hold at least 20 connections. Validate by: read per-pod pool metrics for 5 minutes. If wrong: set max_size to 8 per pod; the total still reaches 32.

**Alternative considered**

Revert the whole release, including the selectinload change [2]. It loses because the query spans show no regression: orders 52 to 58 ms and order_lines 30 to 26 ms [3]. The failure evidence points only to the two config files [1] [2].

**Confidence**: high confidence; the diff, the traces, and the logs agree on one mechanism.
