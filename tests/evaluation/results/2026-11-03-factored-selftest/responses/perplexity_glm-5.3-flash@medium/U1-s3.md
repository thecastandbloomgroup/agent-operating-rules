## Headline

Measure the failure pattern for one session, then fix the dominant cause; do not add retries as the first move. Three points support this:

1. A flake's cause shows up only after reproduction data exists, so measurement comes before any repair [18].
2. Most flakes fall into five known modes, so one capture run can rank them [judgment].
3. A quarantine rule with one retry keeps delivery green while the data accumulates [19].

## Background

The build fails and passes on the same code, so the outcome changes between runs with no code change. The message gives no system name, no log, and no failure rate. The goal is a build that is green on every run.

## Relevance

Every failed run blocks merges and lowers trust in green runs; two industry sources state that theme and none sighted disagrees, because each studied large CI fleets [19], [20].

## Information

**Evidence.**

E1. Theme: flaky tests reduce trust in CI and waste engineer time. Two sources support it and none sighted disagrees. Both are large-scale reports from CI fleets, which is why the theme carries weight despite the count [19], [20]. The grouping of failure records by theme follows the source-count method [3].

E2. Five modes cover the flake space; each points to a different fix [judgment]. Basis: these five partition the sources of nondeterminism, so they do not overlap:

1. Shared resources: CPU conflicts, memory limits, disk.
2. Environment setup: versions, containers, credentials.
3. Timing and order: race conditions, test order dependence.
4. External services and clocks: network calls, time zones.
5. Test data and shared state: stale fixtures, cross-test writes.

Baseline: no run data exists yet. Target for the final fix: zero failures across 10 consecutive runs.

**Assumption log.**

- A1. "The build" means the CI pipeline the team merges into. Why not measured: the material does not state the system. Validate by: checking the pipeline name in the repo. If wrong: the steps still apply to any build runner.
- A2. Reruns change the outcome, so the failure is intermittent. Why not measured: no run history is given. Validate by: rerunning the build once. If wrong: the failure is deterministic; use normal debugging and skip the rate work.
- A3. Run logs are retrievable. Why not measured: the material does not state it. Validate by: opening the CI run history. If wrong: Step 1 becomes log capture first.

**Alternative considered.** Add retries to every job now. It loses because it hides real regressions behind green status and ranks no cause; Google's own mitigation pairs retries with quarantine and tracking, not bare retries [19].

## End

**Step 1. Capture run data.** Add a script that runs the build 20 times on one commit. It writes run number, status, duration, and first error line for each run. This removes the blocker: no rankable cause data exists today. Kind: deterministic. Test, written first [14]:

**Step 2. Classify the 20 error records into the five modes in E2.** This adds the capability to rank fixes; without ranks, repair order is a guess. Kind: evaluative. Rubric: criterion 1, each record maps to exactly one mode, weight 0.5; criterion 2, two independent reviewer passes agree on at least 80% of the 20 mappings, weight 0.5; pass threshold is 0.90 total weight; each criterion needs the error line text of its record as evidence. Cynefin: Complicated, because an analyst maps error signatures to modes under fixed rules.

**Step 3. Quarantine the tests named in the timing, order, and data modes.** Move each to a suite with exactly one retry and a tracked item. This removes the blocker: failed runs block merges while real fixes land. Kind: deterministic. Test, written first [14]:

```gherkin
Given a quarantined test fails once on the main pipeline
When the pipeline run finishes
Then the pipeline reports green and names the retry in the log
```

Cap: remove each entry after its fix lands; stop the rule if a regression reaches main while green. Cynefin: Clear, because the retry rule and its check are known to everyone.

**Step 4. Run the order and isolation probe.** Run the failing tests alone 10 times, then in normal order 10 times. Budget: one session or 20 runs, whichever comes first. This separates mode 3 from product defects. Kind: stochastic. Acceptance test, written first: metric is the pass-rate gap; baseline is zero gap; threshold is a gap of 50 percentage points or more at 10 runs per arm. Stop condition: report both rates at the cap. Cynefin: Complex, because the order effect shows up only in the comparison [18].

**Step 5. Fix the top mode by count from Step 2, then re-measure.** Dependency: Step 5 MUST NOT start before Step 2 passes its rubric. Increment: one fix per session. This removes the top blocker that Steps 1 and 2 rank. Kind: stochastic. Acceptance test, written first: metric is flake rate over 10 consecutive runs; baseline is the rate from the Step 1 file; threshold is zero failures at a sample size of 10. Stop condition: revert a fix that does not drop the rate after two attempts. Cynefin: Complex, because the fix's effect appears only in the re-measure; the one-session cap bounds the cost.

Hedge: if A2 is false, replace Steps 3 to 5 with fault isolation on the single failing case; a deterministic failure does not need rate data.
