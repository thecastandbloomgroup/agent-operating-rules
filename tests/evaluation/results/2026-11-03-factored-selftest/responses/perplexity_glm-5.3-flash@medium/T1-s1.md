## Headline

Treat this as a missing automation problem, not a culture problem. Pin one deterministic SQL formatter, enforce it with the machine, and measure what friction remains.

1. A pinned formatter with a fixed config gives the same output from the same input, so per-line format debates have no decision left to make. [judgment]
2. A CI gate makes the rule self-enforcing, so nobody polices it by hand. [judgment]
3. A short measured probe covers the part that tooling cannot: adoption and habit. [judgment]

## Background

The team disagrees on SQL format. Every code review carries friction, and the request is to fix the culture.

## Relevance

The cost is paid in each review now. A machine rule ends the whole dispute class, not one argument at a time. [judgment]

## Information

### Evidence

E1. The friction in review comes from per-line format comments. [judgment]

E2. A deterministic formatter with a pinned config produces byte-for-byte identical output for the same input file. [inference] This is the property of a fixed rule set, so review debates on format have no decision to resolve.

E3. A baseline count of format comments in the last 10 reviews is needed for the probe in Step 4. [judgment]

Probability that per-review format comments drop by at least half within two reviews after enforcement: likely (66 to 100%). [inference] Basis: the rule becomes machine-checked, so non-compliant code cannot reach review. If A3 is false, this probability does not hold.

### Assumption log

A1. The team SQL lives in files under version control. Why not measured: the material does not state it. Validate by: check the repository layout. If wrong: apply the formatter to migration and seed files only; the rest of the plan holds.

A2. The team can run a pre-commit hook and a CI job. Why not measured: no tool can reach their setup. Validate by: read the CI config. If wrong: enforce with a repository-level check bot instead [inference].

A3. Friction comes mainly from format, not from deeper design disagreement. Why not measured: measuring costs more than this decision is worth. Validate by: count format comments versus design comments in the last 10 reviews (E3). If wrong: the formatter removes one cost source, and the plan adds a separate design forum [inference].

### Alternative considered

Publish a style guide and enforce it by human review. It loses because each reviewer must re-read and re-apply the rules in each review, so the debate returns, and the guide drifts. [judgment]

## End

I recommend that we adopt a tool-enforced format standard in four steps.

**Step 1. Pin one formatter.** Add a configuration file with a fixed rule set, for example sqlfluff [S], to the main repository. Blocker removed: no single source of truth for format rules. Test, written first:
Given the pinned configuration file,
When two people run the formatter on one SQL file,
Then both outputs match byte for byte.
Domain: Clear, because a known best practice exists and the step is one action.

**Step 2. Enforce with the machine.** Add a pre-commit hook and a CI gate that fail on unformatted SQL. Step 2 waits until the Step 1 test passes. Blocker removed: rules that depend on memory instead of the machine. Test:
Given a commit with SQL that fails the check,
When the CI gate runs,
Then the job fails and lists the offending files.
Domain: Clear, for the same reason as Step 1.

**Step 3. Document the exceptions.** Keep a one-page note in the repository that lists each deliberate deviation from the default rules. Blocker removed: questions about whether a choice was intent or accident. Test:
Given the one-page note,
When a reviewer sees a deviation in reviewed code,
Then the note explains it, so no meeting is needed.
Domain: Clear. Step 3 awaits Step 2, because exceptions make sense only against an enforced default.

**Step 4. Probe the human part.** Wait for Step 2, then run this probe in parallel with Step 3. Measure format comments per review. Metric: count of format comments per review. Baseline: the count from the last 10 reviews before rollout (E3). Threshold: at review 10 after rollout, the count is half or less of the baseline. Sample: 10 reviews. breached

Budget: one retrospective session. Stop condition: if the count does not reach the threshold, stop the probe and treat the friction as design disagreement, so the plan shifts to a separate design forum [inference]. Domain: Complex, because team behavior shows cause and effect only after the change [18].

Hedge: if A3 fails validation, replace Step 4 with a design-forum arrangement and keep Steps 1 to 3 unchanged.

Confidence: medium; basis is three logged assumptions plus [judgment] from common practice, with the probe in Step 4 as the deciding measure.
