## Headline

Roll back two config values from release 2026-10-21: set the pool max_size back to 50 and the default cache TTL back to 300 s, then watch the dashboards for one day.

1. The pool change is the driver: pool acquire p95 rose from 3 ms to 690 ms, and it holds most of the http p95 rise from 120 ms to 900 ms [3].
2. The database has headroom: peak CPU is 41% versus 38% before, and active connections fell from 31 to 8 [3].
3. The cache TTL cut is a secondary cause: the miss rate rose from 12% to 31% [3].
4. The query did not slow: the order lines query p95 improved from 30 ms to 26 ms, so the ORM change can stay [3].

## Background

P95 latency of GET /customers/{id}/orders rose from 120 ms to 900 ms after release 2026-10-21. The release changed three areas: the ORM query, the cache TTL, and the database pool config. Logs, traces, and the diff are attached.

## Relevance

The error rate rose from 0.02% to 0.40% [3]. Therefore customers now receive failed responses, and 96% of those failures are pool acquire timeouts.

## Information

Evidence from the attached material, one claim per line:

- Pool acquire p95 is 3 ms in window A and 690 ms in window B, per 10,000 sampled requests [3].
- The release cut pool max_size from 50 to 8 and acquire_timeout_s from 30 s to 5 s [2].
- The API runs 4 pods with 8 worker threads each, so 32 workers share 8 connections per pod [2].
- Pool exhausted warnings were absent on 10-20 and run at 1,800 to 2,400 per hour on 10-22 [1].
- Request logs show 503 responses at about 5,000 ms, which matches the 5 s acquire timeout [1].
- Peak DB CPU is 38% in window A and 41% in window B, and peak active connections fell from 31 to 8 [3]. So the pool cap of 8 is too small for the load; the database itself is not the limit.
- The cache TTL fell from 300 s to 60 s [2], and the cache miss rate rose from 12% to 31% [3]. However, both query spans stayed at or below their window A times, so the missing cache entries are not the main driver.

Confidence: high confidence, three independent signals from matched 10,000 request samples on both sides of the release.

Assumption log:

`A1. OPS-412 does not require a pool of 8 for normal operation. Why not measured: the material does not contain the ticket. Validate by: read OPS-412 and the DB connection limit it names. If wrong: set max_size to that limit instead of 50, then rerun the test in Step 1.`

Alternative considered: revert the ORM selectinload change as well. It loses because both query spans are at or better than their pre-release numbers, at 20/58 ms and 9/26 ms versus 18/52 ms and 11/30 ms [3]. See [1] for the supporting config line in the diff.
