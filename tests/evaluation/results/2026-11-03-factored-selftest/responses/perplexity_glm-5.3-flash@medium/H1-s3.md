## Headline

Roll back the most recent change now, verify one checkout succeeds, then send the exec a one-line update. Supporting points:

1. In a total outage with an unknown cause, restore the last known good state first and find the cause after recovery [1].
2. A checkout that fails for every user usually traces to a change made shortly before the failure started [judgment].
3. One verified test order proves recovery to you and gives the exec a fact, not a status guess.

## Background

Checkout returns HTTP 500 for every user since 09:12 today. An on-call engineer has about ten minutes before an exec call. The request is an immediate action plan.

## Relevance

Every minute loses orders and revenue [inference]. The exec call needs a stabilized service and one accurate sentence. Sequence matters more here than completeness.

## Information

Evidence:

- Standard incident practice is to stop user impact first, restore the last known good state, and run root cause analysis after recovery [1].
- Rollback of a bad deploy typically takes minutes; forward debugging has an unbounded duration [judgment].

Assumptions:

- A1. A deploy, config change, or feature flag landed shortly before 09:12. Why not measured: the material contains no change log and no tool reaches the systems. Validate by: read the deploy and change log for 08:30 to 09:12. If wrong: replace Step 1 with a restart of the checkout service and page the service owner, because the cause is not a release, likely a dependency (70% likely a failed deploy lands within the hour before a total outage; [judgment] from common incident patterns).

Alternative considered: debug the stack trace to a root cause before touching anything. It loses because the duration is unknown while the outage costs orders each minute [1] [judgment].

## End

I recommend that we run these four steps in order.

**Step 1, stabilize (Chaotic).** Roll back the last release, config change, or feature flag made before 09:12. If no change exists, restart the checkout service fleet. Do this first whatever its leverage, because it stops user impact. Cynefin: Chaotic, because no cause and effect are visible and the direct act is to restore order.

Test, written first:

**Step 2, verify (Clear).** Send one checkout from outside the service cluster, for example from a laptop. It waits on Step 1. Cynefin: Clear, because one request gives a known pass or fail with the test above.

**Step 4, exec update (Clear).** Send one line: outage window, action taken, result of Step 2, next update time. Test: the message states all four facts and nothing else.

Sequencing: Step 2 must not start until Step 1 finishes. Step 3 must not start until Step 1 begins, because logs may rotate. Step 4 depends on the Step 2 result.

Condition that changes this plan: if Step 1 fails to restore a 200 within ten minutes, skip to Step 4 anyway with "rollback tried, recovery in progress" and page the service owner.
