# Headline

The answer: build a measured baseline before changing anything, then fix the summarizer against one error type at a time, because "sometimes wrong" is not an addressable problem until the errors have types and rates.

1. With no metrics, no change can be tested, so each fix would be a repeat of the current state [judgment].
2. LLM output errors cluster into a small set of types, and counting their rates shows which fix has the largest payoff [1].
3. One working session can produce a labeled sample of past summaries and a written acceptance rubric.
4. After the baseline, each improvement runs as a capped probe against that sample [2].

# Background

The support tool has a new LLM-based summarizer. Support agents report it is "sometimes wrong", and no metrics track the errors. The request is to make it better.

# Relevance

An unreliable summary costs each agent extra checks, so the team wastes time on every ticket. A baseline turns complaints into counts, and counts turn options into decisions [2].

# Information

**Analysis of failure modes.** A careful reviewer would ask: what does "wrong" mean here? LLM summarizer errors fall into four groups that do not overlap and cover the whole: false information the model adds, missing information the source has, wrong answers to the ticket (for example a wrong resolution status), and style or length problems [1]. Agents report only the first three as "wrong"; style alone rarely draws that word [judgment]. Qualitative evidence: the agent group is the one source of the theme "the summaries are sometimes wrong"; no source in the material disagrees with it. The numbers and the themes conflict in one way: no source gives a rate, therefore the scale of the problem is unknown.

**Calibrated uncertainty.** The sample of about 100 summaries likely shows stable rates within roughly 10 percentage points, based on standard survey practice [judgment, no computation in session].

**Assumptions.**

A1. Summaries are read by agents and are not sent to customers as-is. Why not measured: the material does not state it. Validate by: ask the tool owner, five minutes. If wrong: raise the rubric weight for factual accuracy and add a review gate before any display to customers.

A2. The tool produces at least 50 summaries in 14 days. Why not measured: the material does not state the volume. Validate by: one count query on the tool database. If wrong: widen the sample date range before step 3.

A3. Agents accept about 30 minutes of annotation work per session. Why not measured: costs more to test than the decision is worth. Validate by: run step 2 with two agents and check completion. If wrong: cut the sample from 100 to 30 summaries and mark weaker confidence, about as likely as not, on the final rates.

**Alternative considered.** The strongest alternative is to replace the prompt or the model now and ask agents again later. It loses because with no metrics the team cannot tell whether the new version is better, so the complaint cycle repeats and each change costs engineer time with no measured return [judgment].

Test (evaluative; Kepner-Tregoe layout [3]): criteria are the four error types with weights proportional to harm, pass threshold set at 90% of summaries with no false or missing required detail, scoring on 30 summaries; 90% chosen so that only 3 summaries in 30 may fail before the version fails}. 3. **Baseline the current version (version 3). Step: score the same 100 summaries against the rubric and report the rate per error type with its sample size. Test (stochastic): metric is score of summaries with no false detail,  baseline is undefined before this run, pass threshold is a reported rate per type at a minimum sample of 50 scored summaries; report the number even if it is low, because the number, not the pass result, is the deliverable. MUST NOT start until the baseline report (step 3) finishes. Blocker removed: the error type with the highest rate and harm — uncontrolled fixes worked at cross purposes. Test (stochastic, run first): acceptance test states metric is a step 3 rerun of the rated rate on 50 summaries, baseline is the step 3 rate, pass threshold is a 50% relative cut versus the Step 3 rate, and the sample size is 50, and each run is capped at 5 change attempts, so a run that fails twice must stop and switch type. Cynefin: Complex, because cause and effect are visible only in runs with data; leverage for each change target is a guess until the probe measures it [2].**
5. **Add continuous agent ratings (version 5, parallel to steps 1 and 2, only if a developer is free). Step: add a a flag button and a trust flag on each summary, storing agent feedback with the run metadata. Blocker removed: no complaints channel, therefore future regressions stay unmeasured.

Confidence for all five steps: high for the sequence, moderate for the rates, calibrated at 70% for the actual error rates.

If step 1 produces no rate above 2%, replace step 4 with a stop: no change is worth the slot; recalibrate the threshold with a second sample of 300. If summaries reach customers directly (assumption A1), a sixth step with a human gate comes before step 4.

Conditions that change the recommendation: if A1 is false and agents only skim summaries, cut the harm weight on style; if the annotation pass (A3) fails, reduce the sample to 30 in step 3.
