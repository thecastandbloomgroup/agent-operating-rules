# Headline

Measure before changing anything: label 50 recent summaries this week, compute a baseline error rate, then run two capped fixes, then monitor weekly.

- Step 1 classifies the failures, because "sometimes wrong" names no type and no rate [1].
- Step 2 turns the labels into three numbers: wrong facts, missing facts, and tone errors.
- Step 3 runs two bounded probes against the baseline, so each fix is measured, not guessed.
- Step 4 keeps a small weekly sample, so rate changes and regressions stay visible.

# Background

An LLM-based summarizer writes summaries inside the support tool. Agents report that summaries are sometimes wrong [1]. The team has no metrics, so nothing sizes or locates the failures.

# Relevance

Without a baseline, the word "sometimes" is the only evidence. Any prompt or model change is then unmeasurable, so effort goes to the loudest complaint instead of the largest failure type. A 50-summary sample is the cheapest way to direct the next move.

# Information

## Evidence

Agent reports give one theme with one source: "summaries contain errors" [1]. The theme is weak by source count, so it matters because it comes from the tool's own operators. It sets the label set, not the rate.

Numbers and baselines:

- 50 labeled summaries estimate a rate of 25% within about plus or minus 12 percentage points [judgment].
- Lexical overlap scores such as ROUGE track wording, not truth, so they measure coverage of phrases, not correctness of facts [2].
- Human raters weight factual consistency over fluency in summary quality work [3].
  [3]

Therefore this plan counts agent-marked lines as the primary measure. Semantic scores stay out of the first cycle [2] [3].

## Assumption log

A1. "Wrong" means wrong facts, not tone or length. Why not measured: the material does not state it. Validate by: the Step 1 labels. If wrong: replace the Step 3 probes with style and coverage prompts.

A2. Full ticket transcripts are stored and easy to export. Why not measured: the material does not state it. Validate by: pull 5 transcripts before Step 1. If wrong: add a transcript export as Step 0, before everything else.

A3. Two agents label 50 summaries in one 2-hour session. Why not measured: the agent schedule is outside this material. Validate by: time the first batch of 10 labels. If wrong: cut the sample to 25 and accept a wider interval.

## Alternative considered

Switch to a stronger summarization model now. It loses because a gain cannot be proved without a baseline, and because missing transcript context can produce the same symptom at lower cost [judgment].

# End

I recommend that we do the following, in this order:

1. **Label a sample.** Increment: two agents tag 50 recent summaries in one 2-hour session, one tag per line: wrong fact, missing fact, tone, or not wrong. Blocker removed: unknown failure types. Test (evaluative; rubric written before any tag): every tag cites a quote from the ticket, weight 3; tags use only the four values above, weight 2; the two agents agree on at least 80% of tags in 10 double-labeled summaries, threshold 80%, evidence file: the label sheet. Test: pass when all three criteria meet their thresholds. Domain: Confused, because the failure type is unclassified and this output decides the rest [6].
2. **Compute the baseline.** This step MUST NOT start until Step 1 passes. Increment: one script counts three metrics: wrong lines per 100 summarizer lines, missing facts per summary, and the share of summaries with any wrong fact. Blocker removed: "no metrics". Test (deterministic; written first, Gherkin [5]):
   ```gherkin
   Given the label file with 50 summaries
   When the script computes the three metrics
   Then the values match hand counts on 5 summaries
   ```
   Domain: Complicated, because counting labeled data has one clear method [6].
3. **Run two capped probes in parallel.** This step MUST NOT start until Step 2 gives the baseline. Increment: probe A passes the complete transcript to the model (grounding); probe B adds a final pass that deletes any fact not found in the transcript. Budget: 0.5 day each. Measure and stop rule: stop a probe if its wrong rate exceeds the baseline at the mid-point. Acceptance test (stochastic; written first): metric is wrong rate in percent, baseline is Step 2, threshold is at most half of baseline, sample size is 30 summaries per probe [judgment: the half-rate rule is working practice, not a statistical guarantee]. Domain: Complex, because the effect appears only after the run, so each probe is small and capped [6].
4. **Keep a weekly sample.** Increment: 20 sampled summaries per week with the same tags, routed to one report; failures go on a prompt-fix list. Blocker removed: silent rate changes after edits. Test (deterministic; written first, Gherkin [5]):
   ```gherkin
   Given 20 sampled summaries for the week
   When the script computes the three metrics
   Then the report shows each metric with its 4-week trend
   ```
   Domain: Clear, because sample and track is a known practice for services, and it is one step [6] [judgment].

If A1 is false and tone or missing actions lead the labels, swap the Step 3 probes for style and coverage prompts, and keep everything else.

# Follow-up

Open questions (the recommendation above uses the most likely answer for each):

1. Does "wrong" also mean missed ticket field updates and action items? Purpose: widen the Step 1 tag set if so.
2. What volume of summaries does the tool produce per day? Purpose: set the share for the Step 4 sample.
3. Is there a flag button on summaries today? Purpose: reuse it for the Step 4 routing if it exists.

Condition beyond the hedge above: if Step 1 shows no one failure type above about 40% of tags, treat the fixes as Complex overall and run three probes instead of two.
