# Headline

Roll back the last change now, before diagnosing, then join the exec call with three facts and a next-update time.

- Stabilize first: with every user failing, recovery beats root cause on cost per minute.
- Verify recovery with one probe request after the rollback propagates.
- Capture the change record while the outage is fresh; it supports diagnosis.
- The exec call needs only: what is down, what was done, when the next update comes.

# Background

Checkout returns HTTP 500 to every user since 09:12, about 50 minutes before this response. The on-call engineer has ten minutes before the exec call. The request asks what to do now.

# Relevance

Every minute of a total checkout outage multiplies failed orders and blocked users [judgment]. So the first action removes the failure, not the unknown cause.

# Information

Evidence. The failure is total and time-bounded: 100% of users, one start time, 09:12 [user report]. A failure that is total and starts at one instant points to a recent change more often than to traffic load, because load grows gradually [judgment]. In the Chaotic domain, the rule is to stabilize first and analyze later [18].

Assumptions:

A1. A deploy or config change landed near 09:12. Why not measured: no deploy log exists in this session. Validate by: open the deploy list now. If wrong: rollback does nothing harmful; continue from the change record and logs.

A2. A rollback mechanism or feature flag exists. Why not measured: the request does not state the tooling. Validate by: check the deploy tooling in the next two minutes. If wrong: replace Step 1 with traffic reduction and instance restart probes.

Alternative considered: diagnose the root cause first, then fix. It loses because mean time to recovery, not root cause depth, limits revenue loss in a total outage [judgment].

# End

I recommend that we take these four actions.

**Step 1. Roll back the last deployment, or turn off its feature flag.** Increment: one rollback command, complete in ten minutes. Blocker removed: the error source stops, because the newest change is out of the path. This step is the priority; Steps 2 to 4 run after it is underway. Cynefin domain: Chaotic, because cause and effect are not visible yet, so the action only stabilizes. Test (write it as the probe, then run it):

**Step 3. Rank candidate causes against the record from Step 2.** Increment: one ranked list of at most three candidates, complete in one working session. Blocker removed: the need for a fix that survives the next deploy. This step MUST NOT start before the note in Step 2 exists. Cynefin domain: Complicated, because analysis of the diff and logs picks the cause. **Step 4. Send the exec call note.** Increment: three sentences, complete in two minutes. Blocker removed: exec uncertainty, because the call happens with the state in the open. Cynefin domain: Clear, because the format is fixed. Test:

```gherkin

```

# Follow-up

Conditions that change this plan: if A2 is false, replace Step 1 with a rolling restart plus traffic reduction probe. If the Step 1 probe already passes before any rollback, skip Step 1 and put Step 3 first.
