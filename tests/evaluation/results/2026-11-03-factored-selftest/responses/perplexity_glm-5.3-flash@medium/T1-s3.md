## Headline

The friction is not a culture problem; it is a tooling gap, and the fix is automation, not agreement. Three points:
1. Reviewers argue because each person applies style rules by hand, so a diff from person A fails the rules of person B.
2. One formatter (sqlfluff) applies one rule set to every file, so style never appears in a diff for debate.
3. The change is small: one config file, one CI step, and one reformat commit.

## Background

The team formats SQL by hand and there is no shared rule. Each review contains style comments, and nobody accepts another person's style. The request is to fix the friction.

## Relevance

Each review spends minutes on style instead of logic. The fix stops that cost within one week and does not depend on people changing their habits.

## Information

**Evidence:**
- Teams argue about style because humans apply rules inconsistently. A linter applies the same rules to every file, so the output is consistent by construction. See [A1] for the pipeline assumption. This consistency claim rests on the tool's design: a formatter parses the SQL and writes it back by one rule set. Its rule set is written into a config file that all contributors share. [judgment]
- The strongest driver here is the reviewer's experience, not the style rule itself. Each of these three themes has one source: calendar friction in reviews, style comments blocking useful logic comments, and distrust between reviewers. Remove the style comments as a class, so the review holds only logic comments. [inference]

**Assumption log:**
- A1. The team merges code through pull requests that run an automated pipeline. Why not measured: no repository access in this session. Validate by: open the pipeline config and look for a lint step. If wrong: run the format check as a required review checklist item.
- A2. The existing SQL corpus is large but reformat-O-options-compatible. Why not measured: no repository access in this session. Validate by: run the formatter on a copy of one schema folder and read the diff. If wrong: reformat one folder per sprint instead of all folders at once.
- A3. The tool must match the team's SQL dialect (for example Postgres or BigQuery). Why not measured: the material does not state the dialect. Validate by: ask the data lead, one question. If wrong: set the dialect in the config before Step 1.

**Alternative considered:**
A team meeting to agree on written style rules loses. People drift from a written rule within weeks, style comments return, and the meeting turns into the debate it was meant to end. [judgment]

## End

I recommend that we enforce one formatter with a machine, not with a vote. Follow these steps.

**Step 1: Add the formatter gate to the pipeline.**
- Increment: add a `sqlfluff lint --dialect <team-dialect>` step to the pipeline config, in one working session.
- Blocker it removes: it removes the debate venue, because a non-compliant diff never reaches a human reviewer.
- Test (write first, Gherkin):
  ```gherkin
  Given a pull request that contains SQL with two leading spaces per keyword line
  When the pipeline runs the lint step on the branch
  Then the pipeline run fails before any human review starts
  ```
- Cynefin domain: Clear, because cause and effect are known to everyone and a best practice (deterministic) exists.

**Step 2: Reformat the existing SQL in one commit.**
- Increment: one person runs `sqlfluff fix` on the whole corpus and opens one reformat-only pull request, in one working session.
- Dependency: Step 2 MUST NOT start until the test in Step 1 passes, so the reformat commit is checked by the same gate.
- Blocker it removes: it removes the mixed-style codebase, which is the base cause of the trust problem in reviews.
- Test (write first, Gherkin):
  ```gherkin
  Given the branch that contains only reformat changes
  When the reviewer compares the diff against a grep for changed keywords
  Then no line changes a keyword, table name, or value, and the pipeline passes
  ```
- Cynefin domain: Clear, because the fix is mechanical and its output is fully checkable (deterministic).

**Step 3: Add a local hook so writers see the error before the push.**
- Increment: add a pre-commit hook or an editor format-on-save command that runs the same rule set, in one working session.
- Dependency: Step 3 MAY start with Step 2, but the hook's rule set MUST match the config from Step 1.
- Blocker it removes: it adds the capability to surface errors in seconds instead of in a failed pipeline run minutes later.
- Test (write first, Gherkin):
  ```gherkin
  Given a local working tree that contains one SQL file with a bad line break
  When the developer tries to commit that file
  Then the commit is blocked and the hook prints the fix command
  ```
- Cynefin domain: Clear, because one command produces one known result (deterministic).

**Follow-up:**
1. Which SQL dialect does the team use? The answer sets the config value in Step 1; it does not change the plan.
2. If sqlfluff cannot parse a stored database object such as a vendor query, exclude that path in the config and add a carved-out test for it.
3. This recommendation changes if the pipeline does not exist (A1). Then use a required review checklist item, with the same Gherkin logic applied by a reviewer instead.
