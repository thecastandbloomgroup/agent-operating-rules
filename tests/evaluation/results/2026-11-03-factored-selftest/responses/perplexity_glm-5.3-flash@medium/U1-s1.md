## Headline

The build fails in some runs and passes in others; the fix is to measure the failures first, quarantine the unstable tests, and then repair the top cause. 

- Run the failing job 10 times and collect every failure message.
- Quarantine the tests that fail without a code change, so the build result can be trusted again.
- Classify the failures by cause, then fix the cause with the highest count.

## Background

The request states one fact: the build is flaky. "Flaky" means the same code passes the build sometimes and fails sometimes. No logs, configuration, or environment details are provided.

## Relevance

A flaky build blocks releases and hides real defects. Teams then run the build again until it passes, and the failure signal is lost [1].

## Information

Google reports that flaky tests were a main source of lost trust in its builds, and that it first quarantines them, then fixes causes in ranked order [1]. That pattern matches this situation, so the plan below follows it [1].

The strongest alternative is to configure the job to run again until it passes. It loses because it masks defects and raises the false-pass rate [1].

Assumption log:

- A1. The failing build runs in a shared pipeline, not on one desk machine. Why not measured: the material does not state where the build runs. Validate by: read one failure log for host names and worker details. If wrong: test the local cache and tool versions instead of the pipeline.
- A2. Flaky tests cause the failures, not the build script. Why not measured: the material does not state the failure type. Validate by: classify the failure messages after Step 1. If wrong: the fix targets the script, versions, and dependency downloads instead.

## End

I recommend that we:

1. **Collect failure data.** Increment: run the failing job 10 times on one host and save every failure message. Blocker removed: no data about the cause exists. Write the test first. Test: metric is pass rate; baseline is unknown; pass threshold is one failure signature that repeats in 3 of 10 runs, or 10 of 10 passes, which refutes A2; sample size is 10 runs. Budget: 10 runs, one evening. Stop condition: a signature repeats 3 times. Cynefin: Complex [2], because the cause becomes visible only after the runs.

2. **Quarantine the unstable tests.** Increment: add each test that fails without a code change to a quarantine list and merge that change today.   
   ```gherkin
   Given a test on the quarantine list
   When the pipeline runs
   Then the pipeline result does not change when that test fails
   ```
   Cynefin: Clear [2], because a standard practice exists for this step [1].

3. **Classify the failures.** Increment: group the messages from Step 1 into cause classes and rank them one table row per class. Step 3 must not start until Step 1 ends. Blocker removed: without a ranking, the fix order is a guess. Write the rubric first. Test: rubric criteria are frequency count and fix cost, weights are 0.6 and 0.4, pass threshold is the class with the highest weighted score, evidence is failure messages plus code that matches each class. Cynefin: Complicated [2], because test expertise picks the class.

4. **Fix the top cause.** Increment: change exactly one thing that targets the top class from Step 3. Step 4 must not start until Step 3 ends. Blocker removed: removes the largest cause of failed runs, as measured by the class count. Write the test first. Test (Gherkin) [3]:
   ```gherkin
   Given the fix for the top cause class
   When the job runs 20 times
   Then the job passes 20 of 20 runs
   ```
   Cynefin: Complicated [2], because Step 3 names the cause and expertise picks the change.

If Step 1 produces 10 passes with no repeat, A2 is wrong. In that case, replace Steps 3 and 4 with instrumentation of the host: record disk space, memory, and network errors on every run.
