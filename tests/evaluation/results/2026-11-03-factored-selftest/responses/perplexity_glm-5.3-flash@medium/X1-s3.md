# Headline

You cannot make the summarizer better until "sometimes wrong" becomes a number, so the first fix is a labeled sample of past summaries, not a prompt change. Support for this:

1. Agent complaints have no error classes, so no one can rank the problems.
2. Two agents and one working session can label 100 past summaries and produce a baseline error rate.
3. A capped probe then fixes the top error class and measures the drop against that baseline.
4. A one-click complaint button keeps the baseline current after the probe.

# Background

The support tool now generates conversation summaries with an LLM (a large language model, software that generates text). Agents report that summaries are "sometimes wrong". The team has no metrics and no complaint log.

# Relevance

Without a baseline, no change can be tested, so each prompt edit is a guess. A baseline also sets the target for any later vendor or model swap.

# Information

**Evidence.**

Factual non-faithfulness is a top measured failure class for generated news summaries; human judges marked a large share of model summaries as not faithful to the source [1]. Automatic metrics track human judgment poorly, so agent labels are the right instrument here [2]. [Judgment: wrong facts are 60% likely to be the dominant class in these complaints.] Baseline: overall error rate today is unknown, count of measurements is 0.

**Assumption log.**

A1. "Wrong" means wrong facts or missing key content, not style. Why not measured: the request does not state it. Validate by: sort the Step 1 labels. If wrong: swap the Step 3 constraint for length and format rules.

A2. Past conversations and their summaries are stored and retrievable. Why not measured: no tool access in this session. Validate by: pull a 100-conversation sample. If wrong: label new summaries for one week first.

A3. Label work of about 100 items fits one session for two agents. Why not measured: no cost data. Validate by: assign 25 items per agent. If wrong: cut the sample to 50 and widen the confidence range.

**Alternative considered.**

Change the prompt now and skip measurement. It loses because LLM output varies run to run, so there is no baseline that can show whether the error rate dropped.

# End

I recommend that we run the four steps below. Domains follow the Cynefin framework [3].

**Step 1 (Confused). Label the sample.** Increment: two agents code 100 summaries into four classes: wrong fact, missing content, wrong emphasis, style; 20 items are coded by both [judgment]. Blocker: the unknown error ranking, which hides every later choice. Test (evaluative, rubric first): the rubric is the class guide with an example per class, weight 0.4, plus agreement on the 20 shared items, weight 0.6; the pass threshold is agreement of 80% or more; the evidence is the label sheet. Domain: Confused, because the labels decide all later steps. This class split is MECE at the deciding level: one cause per complaint, one class per item.

**Step 2 (Complicated). Build the baseline.** Increment: a short script that reads the label sheet and prints four error rates per 100 summaries. Blocker: no numbers, so no target for fixes. Test (deterministic, Gherkin):

```gherkin
Given a label sheet with 5 hand-checked rows
When the script computes the rates
Then the output matches the hand calculation
```

Domain: Complicated, because a known analysis turns labels into rates. Step 2 MUST NOT start until the Step 1 test passes.

**Step 3 (Complex). Probe a fix for the top class.** Increment: on the Step 2 ranking, add one constraint to the summarizer, for example "name only people, products, and dates named in the conversation", and run it on the next 50 summaries. Blocker: the top error class from Step 2. Test (stochastic, written before the run): metric, wrong-fact rate; baseline, the Step 2 rate; threshold, a relative drop of 30% or more; sample, 50 summaries; stop condition, if the threshold fails after 50, revert and probe the next class. Budget: 2 agent-hours of label review. Domain: Complex, because the effect is visible only after the run. Step 3 MUST NOT start until Step 2 prints the baseline.

**Step 4 (Clear). Add a complaint button.** Increment: a one-click "report a summary error" button that stores the conversation ID, the summary, and one class from the Step 1 list. Blocker: no complaint channel, so drift goes unseen. Test (deterministic, Gherkin):

```gherkin
Given an open summary in the tool
When the agent clicks the button and picks one class
Then the system stores the ID, the summary, and the class
```

Domain: Clear, because one known step exists. Step 4 runs in parallel with Step 3 once the class list exists.

# Follow-up

Conditions that change the recommendation:

- If A1 is false and agents mean style, replace the Step 3 constraint with length and format rules and keep the same test shape.
- If A2 is false, run Step 1 on new summaries for one week and pick the sample later.
- If the LLM cannot read attachments, add an "attachment not covered" class in Step 1 [judgment].
