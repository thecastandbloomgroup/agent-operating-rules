## Headline

Treat the flaky build as a data problem first: measure the failures, then fix the top cause.

1. Flakiness has more than one cause, so diagnosis comes before repair [1].
2. Tests that use time, order, or shared state cause most flakes [1].
3. A capped probe limits cost while the cause stays unclear [2].

## Background

A build pipeline fails without a clear pattern, and no logs, error messages, or history were provided. The cause is unknown, so the work starts with measurement.

## Relevance

Flaky builds hide real defects and slow every merge. Long-running flakiness also trains the team to ignore red builds [1].

## Information

Evidence:

- A 2014 study of 201 real flaky tests found top causes: async waits, concurrency, and test order dependence [1].
- Environment and resource limits also appear as common causes in industry reports [judgment].
- Median time to fix a flake often exceeds the time to detect it, because reproduction is hard [judgment].

Assumption log:

A1. The build runs in a CI system that keeps logs. Why not measured: the material does not state it. Validate by: open the CI job history. If wrong: Step 1 changes to local repeat runs.
A2. "Flaky" means failures without code changes on the same commit. Why not measured: the material does not state it. Validate by: search for red builds on unchanged commits. If wrong: treat as a real regression instead.
A3. The team can rerun failed jobs and script data collection. Why not measured: no tool access was given. Validate by: try one scripted rerun. If wrong: collect data by hand.

Alternative considered: enable automatic retry of failed jobs and skip diagnosis. It is faster, but it hides the cause. It loses because flakes then grow without limit, because nothing fixes them [1].

## End

I recommend that we:

1. Collect 30 days of build history with one script. This removes the visibility blocker. Test first: Given the CI job history, When the script runs, Then it outputs a table of failures per test and per commit. Domain: Clear, because log extraction is a known recipe.
2. Classify each failure by pattern using a rubric: async wait (weight 3), concurrency (3), test order (2), environment (2); pass threshold: every failure gets one category with a log excerpt as evidence. This depends on Step 1. Domain: Complicated, because expert analysis maps logs to causes [1].
3. Fix the most frequent category with a fix to one test or resource. Test first: run the flaky test 100 times; baseline is its current failure rate; pass at 0 failures in 100 runs. Domain: Complex, because the cause may move after the fix [2]. Budget: half a session.
4. Add a quarantine rule for tests that fail the Step 3 test. Test first: Given a test added to the quarantine list, When the build runs, Then the build stays green and the quarantined test still runs separately. Domain: Clear, because quarantine is a standard practice [1].

Step 2 MUST NOT start until the script in Step 1 runs. Step 3 MUST NOT start until Step 2 names a top category.

## Follow-up

If A2 is wrong, replace Step 3 with a standard regression fix. Condition that changes the plan: one single test causes over 80% of flakes, then skip to Step 3.
