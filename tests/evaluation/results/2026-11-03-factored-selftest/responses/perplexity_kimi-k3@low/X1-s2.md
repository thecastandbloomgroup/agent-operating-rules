# Headline

The team cannot improve the summariser until it can measure it, so the first move is a small evaluation harness, then failures are fixed by category. Agents saying "sometimes wrong" is a symptom with no data, and any model or prompt change without measurement is guesswork. The work splits into three MECE parts: measure the errors, classify the errors, and fix the largest class first. This fits known LLM evaluation practice [1].

## Background

The support tool now uses an LLM summariser, and agents report it is wrong at times. There is no metric, no sample of failures, and no definition of "wrong". The request is to make it better.

## Relevance

Without a metric, every change is unverifiable and agents lose trust. A measured, classified failure set turns "sometimes wrong" into a fixable backlog.

## Information

**Assumptions**

`A1. Agent conversations and their summaries can be logged and reviewed. Why not measured: the material does not state it. Validate by: check tool settings for a log or export. If wrong: add logging first; the rest waits.`

`A2. A sample of 100 past conversations is reachable within privacy rules. Why not measured: the material does not state it. Validate by: request the export. If wrong: use 50 synthetic or anonymised cases; lower confidence in results.`

`A3. "Wrong" means factual error against the source conversation. Why not measured: the user has not defined it. Validate by: interview 3 agents for 15 minutes each. If wrong: add criteria such as tone or missing actions to the rubric.`

**Evidence**

- LLM output varies per run, so single examples mislead; evaluation needs a labelled sample and a score [1, tertiary basis for method, P for the eval concept].
- Faithfulness errors (summary claims not in the source) are a known, measurable failure class for summarisers [2].
- [judgment] 100 labelled cases is enough to rank failure classes with rough confidence; 30 is the floor for a first pass.

**Alternative considered**

Switch to a stronger model first: this is the fastest change, but it loses because without a metric there is no way to know it helped, and prompt or retrieval fixes are often cheaper [judgment].

| Failure class (expected) | Detection | Likely fix |
|---|---|---|
| Fabricated fact | claim absent from source | stricter prompt, cite spans |
| Missed action item | rubric check | extraction step before summary |
| Wrong priority | agent rubric score | few-shot examples |

## End

I recommend that we:

1. **Build the evaluation set** (deterministic, Clear domain, best practice applies). Pull 100 past conversations plus their summaries (A1, A2). Blocker removed: no shared ground truth. Given 100 exported conversation/summary pairs, When a reviewer labels each summary against the rubric in step 2, Then at least 90 pairs carry a pass/fail label.
2. **Write the scoring rubric** (evaluative, Complicated domain, criteria choice needs the agent interviews). Criteria and weights: faithfulness 50%, completeness 30%, usefulness 20%. Pass threshold: 85% of samples pass. Evidence per criterion: quotes from the source conversation. Interview 3 agents first (A3). Blocker removed: "wrong" is undefined. Step 1 labels depend on this rubric, so run step 2's interviews in parallel and finalise before scoring.
3. **Classify every failure** (evaluative, Complicated). Tag each failed sample with one class from the table above. Blocker removed: fixes are currently undirected. Test: every failed sample has exactly one class tag; two reviewers agree on 90% of tags.
4. **Run one bounded fix probe on the largest class** (stochastic, Complex domain, cause and effect known only after the probe, so cap it: one working session, one change). Change only the prompt or add a span-citation requirement. Metric: pass rate. Baseline: from step 1. Threshold: plus 10 percentage points at n=100, or stop and revert. Step 4 MUST NOT start until step 3 reports.
5. **Add the harness to CI** (deterministic, Clear). Re-score on every prompt or model change. Blocker removed: regressions ship silently. Given a prompt change in a pull request, When CI runs the eval on the frozen 100-case set, Then the run fails if the pass rate drops below the step 4 result.

## Follow-up

Conditions that change the recommendation: if A1 fails, add a logging step before step 1. If agents define "wrong" as tone, not facts (A3 false), rebalance rubric weights in step 2.
