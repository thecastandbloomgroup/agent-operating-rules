# Headline

The release cut the database connection pool from 50 to 8 with a 5 s timeout, and that change caused the latency spike. Restore the pool settings first.

- Pool acquire time rose from 3 ms to 690 ms at p95, which explains almost all of the 900 ms p95 [1].
- The cache TTL cut from 300 s to 60 s raised the miss rate from 12% to 31%, adding load [1].
- The ORM change is not the cause, because query times stayed flat at 52 ms to 58 ms p95 [1].
- About 96% of the new errors are PoolTimeout, which matches the logs and the diff [2] [3].

## Background

The API p95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed three things: pool config, cache TTL, and the orders query. Logs, traces, and the diff are attached.

## Relevance

The service now returns 503s at a 0.40% error rate, up from 0.02% [1]. Each pool acquisition block stalls user requests for up to 5 s.

## Information

**Evidence.**

The dominant span change is `db.pool.acquire`: 3 ms to 690 ms at p95, while total p95 went from 120 ms to 900 ms [1]. All other spans stayed flat. For example, `db.query orders` moved only from 52 ms to 58 ms p95 [1].

Active database connections from this service peaked at 8 after the release, versus 31 before [1]. The diff shows `max_size: 50` changed to `8`, and `acquire_timeout_s: 30` changed to `5` [3]. The commit message ties this to ticket OPS-412, a new DB connection limit per service [3]. The API runs 4 pods with 8 workers each, so 32 workers compete for a small pool [3].

Logs confirm this. Pool exhausted warnings were zero per hour on 2026-10-20 and 1,800 to 2,400 per hour on 2026-10-22 [2]. Two PoolTimeout errors appear with 503 responses at about 5,004 ms [2].

The cache change is a secondary factor. The TTL fell from 300 s to 60 s, so the miss rate rose from 12% to 31% [1] [3]. Each miss adds a pool acquisition, which worsens the contention.

The ORM `selectinload` change adds a second query, but `db.query order_lines` is only 26 ms at p95 [1]. It does not drive the regression. However, it slightly raises time each connection is held, so it adds pressure at the margin [judgment].

**Assumption log.**

A1. The pool limit of 8 applies per service, not per pod. Why not measured: the material does not state the scope. Validate by: read the db client config loader code. If wrong: each pod allows 8 connections, so 32 in total, and the contention cause shifts to per-worker demand exceeding 8 per pod.

A2. The OPS-412 limit of 8 connections is a policy, not a hard database failure. Why not measured: the ticket text is not attached. Validate by: read ticket OPS-412 and test 31 connections against orders-db. If wrong: keep pool size limited and instead reduce worker count per pod.

**Alternative considered.**

Reduce the number of worker threads to match the 8-connection pool. This loses because throughput at 405 requests per second needs 32 workers, and query work itself is only about 60 ms per request, so the bottleneck is connection supply, not worker count [1].

## End

I recommend that we:

1. **Revert `config/db.yaml`: set `max_size: 50` and `acquire_timeout_s: 30`.** This removes the dominant blocker, pool starvation. Domain: Clear, because the prior values are a known good practice, and Window A proves they work at this load. Deterministic test, written first:
   - Given release 2026.10.21 config under 405 requests per second,
   - When the config is reverted to pool size 50 and a 30 s timeout,
   - Then `db.pool.acquire` p95 is below 10 ms, total p95 is below 150 ms, and PoolTimeout errors are zero over 10,000 requests.
2. **Restore `default_ttl_s: 300` in `config/cache.yaml`.** This removes the secondary blocker, excess misses hitting the pool. Domain: Clear, as with Step 1. Deterministic test:
   - Given the restored pool,
   - When TTL is set back to 300 s under the same load,
   - Then cache miss rate returns to about 12% plus or minus 3 points, and total p95 is at or below 120 ms.
   - Step 2 SHOULD deploy with Step 1 in one release, so verification compares Window A to Window C directly.
3. **Verify the real limit in ticket OPS-412 with the database team.** If a hard per-service limit exists, size each pod's pool as limit divided by 4 pods, and reduce workers per pod to match. Domain: Complicated, because the correct value needs analysis of the actual database constraint. Evaluative test: a Kepner-Tregoe comparison of options (50 per service, 8 per pod, fewer workers) against the criteria of total connections, p95 latency, and throughput, with a pass threshold of p95 at or below 150 ms and zero PoolTimeout errors.
4. **Keep the `selectinload` change, but add an alert.** Alert on pool exhausted warnings above 100 per hour and on `db.pool.acquire` p95 above 20 ms. Domain: Clear, because alerting thresholds are a standard practice. Deterministic test:
   - Given the monitoring configuration,
   - When a synthetic load triggers 200 pool warnings in one hour,
   - Then an alert fires within 10 minutes.
