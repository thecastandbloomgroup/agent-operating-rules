# Headline

The 8-connection pool limit in release 2026.10.21 starves the 32 API workers, so revert the pool config, then the cache TTL, and treat the ORM change as minor. The traces show pool acquire time rose from p95 3 ms to 690 ms, while every query span stayed flat, and the commit message confirms the pool change was intentional but wrong-sized [1]. Rollback restores latency immediately because this is a known-reversible config change.

## Background

Latency on GET /customers/{id}/orders rose from p95 120 ms to 900 ms after the 2026.10.21 release. The release changed the pool size, the cache TTL, and the ORM query for order lines. Logs show thousands of pool-exhausted warnings per hour and PoolTimeout errors [2].

## Relevance

The error rate is now 0.40%, with 96% of errors being PoolTimeout [3]. Customer-facing 503s will persist and grow until the pool is fixed.

## Information

Evidence for the pool as the root cause:

1. The API runs 32 workers (4 pods x 8 threads), but the pool now permits only 8 connections per pod [1]. At 405 requests/s, workers block on `db.pool.acquire`, which rose from p95 3 ms to 690 ms [3].
2. All query spans stayed flat: `db.query orders` p95 went 52 to 58 ms, `db.query order_lines` went 30 to 26 ms [3]. Therefore the ORM `selectinload` change added no latency.
3. DB server CPU stayed flat at 38 to 41% peak, so the database has spare capacity [3].
4. Active DB connections from this service fell from 31 at peak to 8, which confirms the pool cap, not DB pressure, throttles throughput [3].
5. Cache misses rose from 12% to 31% because the TTL fell from 300 s to 60 s [1]. This adds load to the starved pool but is the secondary cause, because its effect flows through the pool.
6. Pool-exhausted warnings went from zero per hour on 2026-10-20 to 1,800 to 2,400 per hour on 2026-10-22 [2].

The commit for db.yaml says the change matches a "new DB connection limit per service" (ticket OPS-412) [1]. That limit is 8 connections per service per the commit, but the traffic math shows 8 cannot serve 32 workers at 405 requests/s with 20 to 60 ms queries. The alternative considered: raise the pool only slightly (e.g., to 16) to respect OPS-412. It loses, because the service peaked at 31 active connections pre-release and DB CPU is only 41%, so the DB can absorb more than 16; a partial fix keeps p95 above baseline.

Validate by: read OPS-412 and confirm the intended limit with the ops owner. If wrong: if a hard limit of 8 per pod is real, replace Step 1 with a per-pod pool of 8 plus worker count reduction, and re-test.`
