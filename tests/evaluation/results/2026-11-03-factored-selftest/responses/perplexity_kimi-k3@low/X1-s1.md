## Headline

Measure first, then change one thing: classify errors, capture data, score a baseline, probe one fix against it.

- First, "sometimes wrong" is not actionable, so Step 1 classifies real failures into a taxonomy.
- Next, every summary must produce traceable data, because no later analysis is possible without logs.
- Then, a golden set with a calibrated judge turns quality into a number with a confidence interval.
- Finally, one capped probe against the top failure class keeps only changes that beat the baseline.

## Background

The support tool includes a summariser built on a large language model (LLM). Agents report it is "sometimes wrong". No metrics, logs, or labeled error examples exist.

## Relevance

Without a baseline, every change is unverifiable and regressions stay invisible. This plan produces a measured error rate in about two weeks [judgment].

## Information

**Evidence and term definitions**

Faithfulness means every claim in the summary is supported by the ticket text. Completeness means the summary contains the issue, the actions taken, and the resolution. A hallucination is a claim with no support in the ticket. A golden set is a fixed set of tickets with human-approved reference summaries. A judge is an LLM that scores summary quality against a rubric.

Two reviewers labeling the same examples need a reliability bar. Cohen's kappa is a chance-corrected agreement score between two reviewers; 0.70 marks substantial agreement [1].

An LLM judge agrees with human preferences at roughly 80 percent in controlled comparisons, so calibrate it against human labels before its scores count [2].

The Cynefin framework orders the work: gather data to classify an unknown domain first, and treat later changes as probes [3].

Expect one or two failure classes to dominate the error count; the Step 1 taxonomy tests this [judgment]. The 30 percent improvement threshold in Step 5 is a target, not a measurement [judgment].

**Assumption log**

A1. Factual errors (hallucination or omission) dominate "wrong", not style complaints. Why not measured: the material does not state it. Validate by: the Step 1 taxonomy. If wrong: the taxonomy still captures the real classes, and Step 5 targets the new top class.

A2. Agents can flag or edit summaries inline, so a feedback signal can be captured. Why not measured: the material does not state it. Validate by: inspect the agent view for one hour. If wrong: replace inline capture with a weekly manual review of 20 summaries.

A3. Volume is at least 100 summaries per week, so a 100-item golden set reflects production. Why not measured: the material does not state it. Validate by: count summaries in the ticket system. If wrong: extend the collection window or accept a wider confidence interval.

A4. Ticket text can be stored and processed for evaluation under current data terms. Why not measured: the material does not state it. Validate by: one question to the data owner. If wrong: run all evaluation on de-identified exports only.

**Alternative considered**

The strongest alternative is to tune the prompt directly from agent anecdotes and ship it. It loses because no baseline or eval set exists to verify the change, so regressions stay invisible [judgment]. Switching models loses for the same reason: the measurement gap remains.

## End

I recommend that we run five steps, with Steps 2 and 3 in parallel.

**Step 1. Build the failure taxonomy.** Domain: Confused, because the failure mix is unknown and this step gathers what is needed to classify the problem.

- Increment (one working session): interview 5 agents for 30 minutes each and pull 50 flagged ticket-and-summary pairs.
- Define the classes: hallucination, omission, misattribution, format error, other.
- Removes: the blocker that "sometimes wrong" has no counted meaning.
- Kind: deterministic. Test written first, in Gherkin:

Given 50 flagged pairs and the written taxonomy,
When two reviewers label every pair independently,
Then each pair has one agreed label and Cohen's kappa is at least 0.70 [1].

**Step 2. Instrument the summariser.** Domain: Clear, because logging is a known best practice with one standard form.

- Increment (one working session): add one log record per summary and an accept, edit, or reject control in the agent view.
- Adds: every summary carries ticket identifier, prompt version, model version, raw output, agent decision, and final text.
- Kind: deterministic. Test written first, in Gherkin:

Given the summariser produces a summary for a ticket,
When the agent accepts, edits, or rejects it,
Then the log entry stores all six fields listed above.

**Step 3. Build the golden set and rubric.** Domain: Complicated, because more than one good rubric exists; the Step 1 class counts pick the rubric weights.

- Increment (one working session, two reviewers): take 100 random resolved tickets and write a reference summary for each.
- Write the rubric: faithfulness and completeness, each scored 0 or 1, with quoted ticket lines as evidence.
- Adds: the fixed yardstick for every later measurement.
- Kind: deterministic. Test written first, in Gherkin:

Given 100 randomly sampled resolved tickets,
When two reviewers write reference summaries and the rubric,
Then the golden set holds 100 items, each with a reference summary and both labels.

**Step 4. Score the baseline.** Domain: Clear, because running a fixed harness on a fixed set is a known best practice.

- Increment (one working session): run the judge over the golden set against current production output.
- Kind: stochastic. Acceptance test written first:
- Metric: faithfulness error rate and completeness error rate.
- Gate: the judge MUST reach at least 85 percent agreement with human labels on 40 double-scored items before its scores count [2].
- Baseline: current production output. Sample size: 100, giving a 95 percent confidence interval of about ±10 points.
- Pass: a published baseline number with its interval.
- Removes: the blocker that quality is anecdote, not a number.

**Step 5. Probe one fix.** Domain: Complex, because the effect of a prompt or context change is visible only afterward; run it as a safe-to-fail probe with a budget.

- Increment: one prompt or context change aimed at the top failure class from Step 1. Budget: 3 working sessions.
- Kind: stochastic. Acceptance test written first:
- Metric: error rate of the top class. Baseline: the Step 4 number for that class.
- Threshold: relative reduction of at least 30 percent at n = 100 [judgment], with no regression over 3 points on the other metric.
- Stop condition: revert after two failed iterations or one regression trip.
- Adds: a verified improvement, or a documented negative result.

Sequencing: Step 4 MUST NOT start until the Step 3 test passes. Step 5 MUST NOT start until Steps 1 and 4 pass. Steps 2 and 3 MAY run in parallel. The order follows the Cynefin rules: the Confused step comes first, the Complex probe comes last and stays capped [3].

## Follow-up

Conditions that change the recommendation:

- If A4 is false, replace content logging in Step 2 with hashed identifiers and run all evaluation on de-identified exports.
- If Step 1 shows the top class is missing context (the model never receives key ticket fields), replace the Step 5 prompt probe with a retrieval fix probe.
