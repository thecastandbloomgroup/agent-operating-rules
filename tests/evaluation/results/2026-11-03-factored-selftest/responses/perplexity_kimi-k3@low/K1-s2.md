# Headline

The 900 ms p95 is caused by the connection pool shrink (50 to 8 across 32 workers per pod), not by the ORM change; revert the pool settings first.

1. The pool acquire span explains the latency: it grew from 3 ms p95 to 690 ms p95, while query times stayed flat [3].
2. The cache TTL cut (300 s to 60 s) raised the miss rate from 12% to 31%, adding load the small pool cannot serve [3].
3. The ORM change did no harm: order_lines query time fell from 30 ms to 26 ms p95, so selectinload is fine [3].
4. Reverting pool size and timeout restores the prior capacity and removes the 503 rate of 0.40% [3].

# Background

Release 2026.10.21 on 2026-10-21 changed three things: pool max_size 50 to 8, acquire timeout 30 s to 5 s, cache TTL 300 s to 60 s, and added selectinload on order lines [2]. After it, p95 rose from 120 ms to 900 ms, with roughly 1,800 to 2,400 pool exhaustion warnings per hour [1][3].

# Relevance

PoolTimeout errors now fail about 1 in 250 requests, against 1 in 5,000 before [3]. Left alone, this risks SLA breaches and client retries that add more load on the pool.

# Information

First, the arithmetic. Four pods with 8 workers each give 32 concurrent workers [2]. With max_size 8 per pod, worker demand per pod (8) equals total pool capacity, so there is no headroom for cache misses that lengthen each connection hold. Traces show active DB connections capped at 8 in window B against 31 in window A, at equal request rates (410 vs 405 RPS) [3]. DB CPU is normal at 41% [3]. That is a queueing bottleneck, not a slow database [judgment].

Second, the TTL cut. Miss rate rose from 12% to 31%, because 60 s TTL expires entries before most repeat reads [judgment, inferred from [2][3]]. At 405 RPS peak, this sends roughly 77 more queries per second to the DB ([calculated from [3]]) through an 8-connection pool.

Third, the counterevidence. The commit message cites a new DB connection limit per service from ticket OPS-412 [2]. Active connections peaked at 8 in B, so the API respected that limit, but the limit shrinks capacity and the release arrived with it rather than after traffic shaping [judgment].

Alternative considered: tune selectinload or the queries first. It loses because db.query spans are nearly unchanged between windows (52 to 58 ms p95), so the ORM diff cannot explain a 780 ms p95 increase [3].
