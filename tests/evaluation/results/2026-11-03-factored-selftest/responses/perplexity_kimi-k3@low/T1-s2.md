## Headline

Adopt one automatic SQL formatter, enforce it in CI, and remove style decisions from human review.

- A formatter answers layout questions deterministically, so reviewers discuss logic instead [judgment].
- One bulk reformat aligns every existing file without per-file debate.
- A CI gate rejects nonconforming SQL, so the rule persists without human policing.
- The Go project ended the same style conflict this way at scale [2].

## Background

The team disagrees on SQL formatting, and it causes friction in every review [1]. The request is to fix the conflict itself, not only the style. The durable fix removes the formatting decision from people and gives it to a tool.

## Relevance

Review time spent on layout is time not spent on correctness. Ending the style debate also ends the recurring interpersonal friction it produces [judgment].

## Information

**Evidence.** Formatter automation resolved an identical community-wide style dispute in Go. Its author reports that the imposed style displeased everyone equally, which ended the debates [2]. SQLFluff is a mature open source SQL linter and formatter with per-dialect configuration [3]. Git can ignore the bulk reformat commit in blame, so history stays readable [4]. Uncertainty: likely (IPCC term, 66 to 100%) that review friction drops. High confidence, one documented precedent at scale plus team-reported evidence [1] [2].

**Assumption log.**

`A1. The team uses a mainstream SQL dialect supported by SQLFluff. Why not measured: the material does not state it. Validate by: check connection strings or the data platform console. If wrong: swap the tool, not the approach; see Follow-up.`

`A2. Reviews happen as pull requests in version control with CI available. Why not measured: the material does not state it. Validate by: inspect the repository settings. If wrong: run the formatter as a commit hook instead of CI.`

`A3. No regulatory constraint fixes the SQL layout. Why not measured: the material does not state it. Validate by: ask the team lead once. If wrong: encode the required layout in the config.`

**Alternative considered.** A written style guide enforced in reviews loses. That is the current failing arrangement, because human enforcement of taste is the friction source [judgment].

## End

I recommend that we take four steps. Steps 1 to 3 are sequential. Step 4 runs in parallel with Steps 1 and 2.

1. Add a `.sqlfluff` config naming the dialect. Increment: one config file, one session. Blocker removed: there is no single agreed style. Cynefin domain: Clear, because a documented best practice exists [3]. Test first (deterministic, Gherkin):
   - Given a repo with the config and a deliberately misformatted query
   - When `sqlfluff lint` runs, then `sqlfluff fix` runs
   - Then lint reports the violations and fix corrects them
2. Run `sqlfluff fix` over all SQL in one commit. Record its hash in `.git-blame-ignore-revs`. Increment: one commit. Blocker removed: existing files conflict with the new rule. Cynefin domain: Clear, because it is a mechanical transform. Step 2 MUST NOT start until the test in Step 1 passes. Test first (deterministic, Gherkin):
   - Given the passing config from Step 1
   - When the reformat commit lands
   - Then `sqlfluff lint` exits with code 0 on the whole tree
3. Add a CI job that runs `sqlfluff lint` on each pull request. Increment: one pipeline step. Capability added: permanent, impartial enforcement. Cynefin domain: Clear, because CI gating is standard practice. Step 3 MUST NOT start until the test in Step 2 passes. Test first (deterministic, Gherkin):
   - Given a pull request containing a style violation
   - When the CI job runs
   - Then the build fails and names the violating lines
4. Time-boxed ratification. Announce the defaults and collect objections. Cynefin domain: Complex, because team reaction is visible only afterward, so this is a capped probe. Metric: blocking objections per reviewer. Baseline: friction in every current review [1]. Stop condition: blocking objections from at least 40% of reviewers within five working days. Budget: five working days. Otherwise the defaults stand.
