# Headline

Without metrics, "sometimes wrong" cannot be fixed directly, so the path is to define what "wrong" means, measure it, then improve. First, build a small error taxonomy from real ticket summaries. Second, set a baseline with a scoring rubric on a fixed sample. Third, change one cause at a time (prompt, context inputs, or post-checks) and re-measure. Fourth, keep a human check loop until the error rate meets target.

# Background

A support tool now uses an LLM to summarize tickets or chats. Agents report that summaries are occasionally wrong, and no measurements exist. The request is to improve the summarizer.

# Relevance

No baseline means no way to tell improvement from noise. "Wrong" also covers many failure types, and fixes differ by type.
