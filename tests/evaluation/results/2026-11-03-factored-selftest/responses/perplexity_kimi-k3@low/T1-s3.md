# Headline

The fix is to pick one automated SQL formatter and one review rule, because formats enforced by tools end format debates by people. First, the team votes on a tool once, then a pre-commit hook applies it, and then reviews cover logic only. This turns a values argument into a configuration file. Culture follows the tooling change [judgment].

# Background

The team disagrees on SQL style. Every review carries arguments about format instead of logic. The request is to fix the culture problem, not the syntax.

# Relevance

Each review cycle spends time on format debates. This cost repeats on every pull request until a tool owns the decision.

# Information

Evidence:

- Automated formatters remove style debates. This is a documented team-level result in the Go ecosystem, where `gofmt` ended layout arguments [1].
- Linters and formatters in pre-commit or CI checks enforce style at machine speed, so no reviewer pays for it [2].
- The root cause is ambiguous ownership of the style decision. When no rule is written down, each reviewer becomes the rule [judgment].

Confidence: likely (66 to 100%). Basis: one secondary source on Go, plus the mechanism is the same for SQL [1].

Assumption log:

`A1. The team uses git with pull request reviews. Why not measured: the material does not state it. Validate by: check if a repo host exists. If wrong: replace the pre-commit step with a shared editor config.`

`A2. The team will accept one binding vote. Why not measured: the user has not answered. Validate by: run the vote in one meeting. If wrong: escalate to the engineering manager for a ruling.`

`A3. A formatter exists for the team's SQL dialect. Why not measured: the material does not name the database. Validate by: test sqlfmt or SQLFluff on one file in one hour. If wrong: use SQLFluff rules as a written spec only.`

Alternative considered:

Writing a style guide by consensus. It loses because guides without automation drift, and each review reopens the debate [2].

# End

I recommend that we:

1. Run one binding 30-minute vote on a formatter: sqlfmt, SQLFluff, or pgFormatter. This removes the blocker "no single owner of the style decision." Test: **Given** the team in one meeting, **When** each person casts one ranked vote, **Then** one formatter is recorded in a decision file. Domain: Clear, because the vote mechanism is a known best practice. Deterministic.

2. Configure the chosen formatter on the worst SQL file in the repo. This removes the blocker "no working config." Test: **Given** the chosen formatter and one existing SQL file, **When** the formatter runs, **Then** the file reformats and its query returns identical results. Domain: Complicated, because the config needs syntax analysis of the dialect. Deterministic. Step 2 MUST NOT start until Step 1 passes.

3. Add the formatter as a pre-commit hook and a CI check. This adds the capability "style enforced without a human." Test: **Given** a commit with unformatted SQL, **When** the developer commits, **Then** the hook reformats or blocks the file. Domain: Clear, because hooks are a known best practice. Deterministic. Step 3 MUST NOT start until Step 2 passes.

4. Write one review rule: "format comments are formatter bugs, not author bugs." This removes the blocker "reviewers still debate style." Test: rubric with one criterion, weight 100%: zero format comments per pull request, threshold 90% over the next 20 pull requests, evidence is the comment log. Domain: Complex, because reviewer behavior is visible only after the change. Capped probe: budget two weeks, stop condition is two pull requests with repeated format disputes. Evaluative.

5. Bulk-format the repo in one pull request before the rule takes effect. This removes the blocker "every future diff is noisy." Test: **Given** the full repo, **When** the formatter runs on all SQL files, **Then** the test suite passes unchanged. Domain: Clear, because a one-time reformat is a known practice. Deterministic. Step 5 SHOULD merge the same day as Step 3.

If A3 is false, replace Steps 2, 3, and 5 with a one-page written style spec enforced by the Step 4 rule alone.

# Follow-up

Conditions that change the recommendation: no git or review flow (see A1), no formatter for the dialect (see A3).
