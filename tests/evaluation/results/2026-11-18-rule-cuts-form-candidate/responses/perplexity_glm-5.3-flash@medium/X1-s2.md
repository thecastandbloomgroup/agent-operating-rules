# Headline

Measure before you change the summarizer, because nobody can name the failing pattern. First, score a sample of 100 summaries against a written rubric. Second, rank the failure modes by frequency and by cost. Third, add an automatic check that compares each summary sentence to the ticket text. Fourth, retune the prompt or model and rerun the same test.

# Background

The support tool has an LLM-based summarizer. Agents report errors that occur sometimes, and no metrics exist. The task is to make the summarizer better.

# Relevance

Without measurements, any prompt change tests whether agents like it more, not whether summaries are correct. Therefore this plan builds a small evaluation loop in two working sessions.

# Information

Evidence and sources:

- A second LLM used as a judge approximates human judgment when the task has clear criteria and a fixed procedure [3]. Treat this as unverified for your case until step 3 measures it.

**Step 3: Add an automatic faithfulness check.**
The check splits a summary into single claims, then compares each claim to the ticket text [2]. Before coding, write the test: metric is agreement between the check and the human labels, baseline comes from step 2, threshold is 90% agreement, sample size is 100. Stop condition: stop and fall back to manual review if agreement is below threshold. Budget: one session.

**Step 4: Change the prompt, then rerun the rubric.**

Kind: stochastic. Cynefin: Complex, because model behavior shows effects only after the run, and the probe is capped at 50 items.

**Step 5: Run weekly monitoring.**
Keep the automatic check in the pipeline. Alert when weekly faithfulness drops below 0.95 on a sample of 20. Increment: one session of wiring.
Kind: deterministic. Cynefin: Clear, because the best practice is pipeline alerting on a fixed threshold [judgment]. Step 5 runs in parallel with step 4 after step 3 passes.
