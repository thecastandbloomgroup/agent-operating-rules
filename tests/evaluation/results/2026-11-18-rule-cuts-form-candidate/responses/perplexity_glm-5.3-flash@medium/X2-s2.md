Headline
Your retrospectives fail because they do not produce owned action items that are checked later. Fix this in four steps.

First, gather data on why past action items did not happen. Second, cap each retrospective at one action item with an owner. Third, change the format for two retrospectives and measure the effect. Fourth, review progress at the start of every retrospective.

Background
The team holds retrospectives at a regular cadence. People attend, but the team's process does not change. The request asks for a way to make retrospectives lead to change.

Relevance
A retrospective that produces no changes wastes one meeting per cycle. It also teaches the team that speaking up does nothing, so attendance and honesty drop over time [1].

Information
The purpose of a retrospective is to inspect the way of working and plan one improvement [1]. Three claims drive the advice.

Claim 1: the cause of failure is not yet known. The fix depends on the cause. The team may lack owner assignment, or lack follow-up, or the format may suppress ideas. Because each cause needs a different strict fix, the first step is to classify it [judgment].

Claim 2: converging on one owned action item is accepted practice with high leverage. See Derby and Larsen, who state that retrospective outcomes end with action items that the team then tracks [1].

Claim 3: changing behavior is a probe, not a plan. People respond to a new format in ways you cannot predict, so the change needs a measure and a stop condition [judgment].

Assumptions:

Assumption: past retrospectives produced written action items. Why not measured: the material does not state it. Validate by: check the notes of the last retrospective. If wrong: start from an empty list in Step 1 and adjust.

Assumption: the team is small enough (5 to 12 people) for one shared facilitator to run the steps. Why not measured: the material does not state it. Validate by: confirm headcount before Step 2. If wrong: split Step 3 into two groups.

Assumption: the blocker is process, not interpersonal conflict. Why not measured: the material does not state it. Validate by: Step 1 blocker question. If wrong: reduce the depth of Steps 2 to 4 and run a separate trust session first.

Alternative considered: replace retrospectives with a continuous improvement channel. It loses because written input shows fewer causes than a facilitated discussion, where people build on each other's points [1], and because Step 1 tests the cheaper fix first.

End
I recommend that we run the grader... (no) I recommend that we act in four steps, in this order.

Step 1. Classify the failure cause. Increment: at the next retrospective, list every action item from the last three retrospectives, mark each done or not done, and ask each person to name one blocker in one sentence. Blocker removed: we do not know why changes did not happen. Test (evaluative). Rubric: cause is classified when (a) every action item has a status, weight 40 percent; (b) at least 80 percent of the team names one blocker, weight 60 percent; pass threshold is both scores at or above their weights; evidence is the written list and the blocker sentences. Technical kind: evaluative, because the output is a judgment. Cynefin: Confused, because the failure cause is not yet classified and the answer decides the rest of the plan.

Step 2. Cap each retrospective at one action item. Increment: write the rule (one item, one owner, one due date) into the retrospective template and apply it at the next retrospective. Blocker removed: scattered action items with no owner wait forever. Test (deterministic, Gherkin). Given the retrospective ends and produces at least one proposed change, when the facilitator closes the meeting, then the notes show one action item, one owner, and one due date. Write this test before the meeting. Technical kind: deterministic. Cynefin: Clear, because owner assignment is a known rule from retrospective practice [1].

Step 3. Probe a format change. Increment: run two retrospectives with silent writing first, then group the notes, then vote. Blocker removed: some members speak little, so the current format collects few real problems. Test (stochastic). Acceptance test: metric is the count of blocker notes written by each member; baseline is the notes per member in Step 1; pass threshold is median notes per member at least 1.5 times the baseline; sample size is two retrospectives. Stop condition: keep the old format if the threshold is not met after two runs. Technical kind: stochastic. Cynefin: Complex, because the effect of a format change shows only after the run; each probe is capped at one retrospective.

Step 4. Review past commitments at the start of every retrospective. Increment: add the first ten minutes to every retrospective, where the team checks the last action item as done or not done. Blocker removed: action items carried no later check, so they lapsed. Test (deterministic, Gherkin). Given a retrospective starts and the last action item has an owner, when the team checks its status, then the notes record done or not done with a reason if not done. Step 4 MUST NOT start before Step 2 passes its test, because there is no item to check without a cap and owner. Technical kind: deterministic. Cynefin: Clear, because the check is a known rule [1].

Sequence: Step 1 is first and its result may change Step 3. If Step 1 shows the blocker is interpersonal, replace Step 3 with a team health session before Step 4.
