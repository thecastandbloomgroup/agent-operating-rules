## Headline

Yes, your team should pin exact versions in requirements.txt.

- An unpinned file lets the installer resolve versions at build time, so two builds of the same file can install different code [judgment].
- A pinned file installs the same versions every time, so a library update happens only when you decide it [judgment].
- The task is small: one freeze command, one CI check, and a short update procedure [judgment].

## Background

The project has an unpinned requirements.txt. A library update broke the build twice last month. The request asks whether to pin versions.

## Relevance

Every new install repeats the same risk, so the break can return at any build. Pinning closes that gap before the next update.

## Information

**Evidence**

- Package installers resolve unpinned requirements at install time, so the resolved set changes when a registry serves a new version [judgment].
- With no pinned file, an update reaches production without a test run, as happened in the two breaks you describe [judgment]. A return of this failure is very likely (90 to 100%) over a year of builds with no pin [judgment].
- Pinning does not remove the need to update packages; it moves each update into a tested, deliberate change [judgment].
