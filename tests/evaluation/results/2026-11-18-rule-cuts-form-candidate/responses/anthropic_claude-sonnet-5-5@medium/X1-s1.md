## Headline

We cannot improve the summariser until we measure it, so first build a small labeled baseline and then fix the largest error type.

- Agents report "sometimes wrong", but no data shows how often or in what way.
- A labeled sample of real tickets gives the baseline and shows which error type to fix first.
- A feedback button and a frozen test set keep the gains measurable after the first fix.
- A prompt change is the cheapest first fix, and it runs offline before any agent sees it.

## Background

The support tool now uses an LLM (large language model, a program that writes text) to summarise tickets. Agents say the summaries are "sometimes wrong". The team has no metrics, so the size and type of the errors are unknown.

## Relevance

Agents who distrust the summaries reread the full ticket, so the tool saves no time. Wrong summaries can also lead to wrong replies to customers.

## Information

Evidence:

- Summaries written by LLMs often contain content that the source text does not support. This is the best-known failure type.
  [1]
- Most errors likely fall in two or three types, such as invented details or missing status (likely, 66 to 100%) [judgment].
- No error rate exists for this tool today [no source].

Assumption log:

- Assumption: the tool stores each ticket and its summary. Why not measured: the material does not state it. Validate by: query the database for ten recent tickets. If wrong: start with Step 2 and wait two weeks for data.
- Assumption: 100 labeled summaries are enough to rank error types. Why not measured: measuring more costs more than the decision is worth. Validate by: check that the top type has at least 15 cases. If wrong: label 100 more.
- Assumption: agents or leads can give two hours to labeling. Why not measured: the user has not answered. Validate by: ask the support lead. If wrong: label 50 summaries and lower the confidence level.

Alternative considered: switch to a larger model or fine-tune (train further on your own data) now. It loses because without a baseline we cannot show that it helps. It also costs more than a prompt change [judgment].

## End

I recommend that we take these four actions, in this order:

1. **Label a baseline sample.**
   - Increment: two reviewers label 100 random recent summaries in one session. They score 20 of them twice to check agreement.
   - Blocker removed: we do not know the error rate or the error types.
   - Domain: Confused. We cannot yet tell which causes drive the errors, so this step gathers what we need to classify.
   - Kind: Evaluative. The rubric is written first.
   - Rubric criteria and weights: Faithfulness 40 (no claim absent from the ticket). Completeness 30 (issue, steps taken, status, next action). Actionability 20 (an agent can act without opening the ticket). Brevity 10.
   - Pass threshold: a summary passes at a score of 80 or more and no faithfulness failure.
   - Evidence needed: the ticket text next to the summary, with the failing sentence marked and typed.
   - Output: the baseline error rate and a ranked list of error types.

2. **Add a "wrong summary" button.** This step MAY run in parallel with Step 1.
   - Increment: one button that logs the ticket ID, the summary, and a reason chosen from a short list.
   - Blocker removed: agents have no way to report errors, so no live data exists.
   - Domain: Clear. A standard feedback pattern exists, and we apply it by deduction.
   - Kind: Deterministic. The test is written first:
     - Given an agent views a summary
     - When the agent clicks "wrong summary" and picks a reason
     - Then the system stores the ticket ID, the summary text, the reason, and the time

3. **Freeze a regression set.** Step 3 MUST NOT start until Step 1 is done.
   - Increment: save the 100 labeled tickets with a script that scores any new prompt or model against them.
   - Blocker removed: no repeatable way to compare versions.
   - Domain: Clear. Fixed inputs and fixed labels follow known practice.
   - Kind: Deterministic. The test is written first:
     - Given the frozen set of 100 labeled tickets
     - When the script runs on the current summariser
     - Then it prints the same error rate as the Step 1 baseline

4. **Probe a prompt fix for the top error type.** Step 4 MUST NOT start until the test in Step 3 passes.
   - Increment: change the prompt to target the top type from Step 1. For example, tell the model to state only facts found in the ticket.
   - Blocker removed: the largest source of wrong summaries.
   - Domain: Complex. We see the effect only after the trial, so this is a safe-to-fail probe. The leverage is a guess. Induction from trials could break if the new prompt shifts errors to another type.
   - Budget: one working session. Stop condition: the error rate does not fall after two prompt versions.
   - Kind: Stochastic. The acceptance test is written first:
     - Metric: share of summaries that fail the Step 1 rubric.
     - Baseline: the Step 1 rate.
     - Threshold: a relative drop of at least 25%, and no other error type rises by more than 2 points [judgment].
     - Sample size: the frozen 100 tickets plus 100 new ones, run three times each.
     - Accept the change only when the threshold is met at that sample size.
   - Agents see the new prompt only after it passes.

If the labeled sample shows no dominant error type, replace Step 4 with a probe of a different model on the same test.
