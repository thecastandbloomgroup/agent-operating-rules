Yes, turn on gzip for the API. The savings are large and the cost is small.

- JSON is repetitive text, so gzip very likely shrinks a 400 KB response to about 40 to 100 KB [judgment].
- The smaller body cuts transfer time, most on slow mobile links.
- The CPU cost is small and you can measure it before full rollout.
- The risk is configuration, not design: double compression and cache mix-ups are the usual faults.

This matters now because 400 KB is a large payload. At 10 Mbit/s, 400 KB takes about 0.32 s to transfer. A 60 KB body takes about 0.05 s [inference]. Every call pays this cost.

Evidence and assumptions follow. The size reduction of 85% (400 KB to 60 KB) is an estimate for typical JSON [judgment]. It is very likely (90 to 100%) that the reduction exceeds 60%, because JSON repeats key names. Gzip at level 5 or 6 adds CPU load, which you must measure [no source].

Assumption: the body is plain-text JSON, not already compressed. Why not measured: the material does not state it. Validate by: run `curl --compressed -sI` against one endpoint and read the headers. If wrong: the gain falls and the recommendation changes.

Assumption: clients send `Accept-Encoding: gzip`. Why not measured: no tool can reach the client logs. Validate by: count the header in the access logs for one day. If wrong: the clients that omit it gain nothing.

Assumption: no proxy or CDN (content delivery network) already compresses the response. Why not measured: the material does not describe your network path. Validate by: compare response headers at the origin and at the edge. If wrong: skip Step 1 and check the edge setting.

The strongest alternative is Brotli, a newer compression format. It gives smaller files than gzip at high levels, but it costs more CPU per request and some older clients lack support. Gzip loses only if the Step 2 test fails, so start with gzip [judgment].

I recommend that we take these steps in order:

1. Enable gzip on staging for `application/json` responses. Use level 5, a minimum size of 1 KB, and the header `Vary: Accept-Encoding`. This step removes the largest blocker: no compression exists today. Cynefin domain: Clear, because the setting is a known best practice. The test, written first, is deterministic:

   When a client sends a request with the header "Accept-Encoding: gzip"
   Then the response carries "Content-Encoding: gzip" and "Vary: Accept-Encoding"
   And the decoded body equals the uncompressed body byte for byte

2. Measure the effect on staging with a replay of 10,000 real requests. This step adds the evidence for the CPU and latency trade-off. Cynefin domain: Complicated, because analysis of the measurements picks the compression level. The test is stochastic. The metric is bytes sent, p95 latency, and CPU use. The sample size is 10,000 requests. Step 2 MUST NOT start until the test in Step 1 passes.
