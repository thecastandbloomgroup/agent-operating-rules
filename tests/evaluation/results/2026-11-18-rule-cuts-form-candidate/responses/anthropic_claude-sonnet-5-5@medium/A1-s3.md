## Headline

Yes, pin every version, including indirect dependencies, and update them on a schedule.

- Unpinned versions let the newest release install on each build, so any library update can break the build.
- Pinning only the libraries you name leaves their own dependencies free to change, so pin the full tree.
- Pins need a routine for updates, otherwise the project falls behind on security fixes.

## Background

The file requirements.txt lists the Python libraries that the project installs. No entry has a fixed version. The build broke twice last month after a library update [1].

## Relevance

Each unpinned build can break without any change in your code. The next break is likely to cost the same time as the last two.

## Information

**Evidence**

- Two build breaks in one month after library updates is the baseline for this decision [1].
- The pip tool supports exact pins with the `==` operator and hash checking with `--require-hashes` [2].
- The pip-tools program compiles a short input list into a full pinned file, including indirect dependencies [3].
- Pinning direct dependencies stops update-caused breaks in those libraries: very likely (90 to 100%) [judgment].
- Pinning only direct dependencies leaves indirect ones free to change. An indirect dependency (also called a transitive dependency) is a library that your libraries need.
