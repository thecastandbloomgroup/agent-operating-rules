## Headline

Yes, pin every version, and update the pins on a schedule you control.

- Unpinned installs take the newest release on each build, so an upstream change breaks your build without any change from you [2].
- Two breaks in one month is the baseline to beat, per the user's message [1].
- Pins alone go stale, so a scheduled update job keeps them current.

## Background

The project lists its Python libraries in requirements.txt with no version numbers. Pinning means fixing a library to one exact version, for example `requests==2.32.3`. The build broke twice last month after a library update [1].

## Relevance

Each break stops the team until someone finds the cause. Pinning turns a surprise failure into a planned change.

## Information

- A tool can compile a short list of direct libraries into a full pinned list, including transitive dependencies (libraries that your libraries need) [3].
- Pinning is very likely (90 to 100%) to stop this type of break on the main branch [judgment].
