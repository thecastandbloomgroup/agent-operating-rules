## Headline

Run `ALTER TABLE orders RENAME COLUMN user_id TO account_id;`, but only when the application code that reads `user_id` ships in the same release.

- The statement is one line, and Postgres updates indexes, constraints, and views for you [1].
- Application queries, ORM mappings (code that maps tables to objects), and function bodies that name `user_id` break at once.
- The rename takes a short exclusive lock on the table, so a failed deploy blocks all orders traffic.
- Because you board now, the safest time to run it is after you land.

## Background

You asked to rename `user_id` to `account_id` in the `orders` table of a Postgres database. You have little time before your flight. The material does not say what reads this column.

## Relevance

A rename is instant for the data but not for the code. A mismatch between code and schema stops order queries, so the timing matters more than the statement.

## Information

Evidence:
- Postgres stores column references in indexes, constraints, and views by column position, so the rename follows them. Index and constraint names keep the old text [1].
- `RENAME COLUMN` takes an ACCESS EXCLUSIVE lock. That lock blocks every other query on the table until the rename commits [1].
- Code and stored function text that name `user_id` are not rewritten. Failure is very likely if any such code exists [judgment].
