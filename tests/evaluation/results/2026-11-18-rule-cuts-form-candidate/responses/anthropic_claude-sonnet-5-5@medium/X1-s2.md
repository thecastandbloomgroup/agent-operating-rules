## Headline

I recommend that we measure the summariser's errors first, then fix the most common error type and test the fix against a baseline.

- No fix can be judged today, because the team has no error rate and no error categories.
- A labelled sample of 100 summaries gives a baseline within about ±10 points (95% confidence).
- A permanent feedback button keeps the measure alive after the first fix.
- Each prompt or model change then passes or fails one written test.

## Background

The support tool now shows a summary of each ticket, written by a large language model (LLM). Agents report that the summary is "sometimes wrong". The team has no metrics, so nobody knows how often it fails or how.

## Relevance

An agent who reads a wrong summary may give a wrong reply to a customer. Trust in the tool also drops when errors stay unmeasured.

## Information

**Evidence**

- Abstractive summarisers add content that the source text does not support. Research documents this for neural models [1].
- Unsupported content is likely (66 to 100%) the largest error category here [judgment].
- Omission of key facts, such as the current ticket status, is the next most common category [judgment].
- An LLM can score summaries after humans label a first set. Judge scores matched human ratings in over 80% of cases in one study [2].
- With 100 labelled summaries, the 95% margin on an error rate is at most ±9.8 points. That is 1.96 × √(0.25 / 100) [inference].

**Assumption log**

`Assumption: The tool stores each ticket text and its generated summary. Why not measured: the material does not state it. Validate by: read 10 records from the database. If wrong: add logging first, and Step 1 starts one session later.`

`Assumption: The tool creates at least 100 summaries per week. Why not measured: the material does not state it. Validate by: count last week's summaries. If wrong: label all available summaries and widen the stated margin.`

`Assumption: Two agents can label 70 summaries each in one session (about 2 minutes each). Why not measured: measuring costs more than the decision is worth. Validate by: time the first 10 labels. If wrong: split the work over two sessions.`

**Alternative considered**

Switch to a larger model now. It loses because, without a baseline, the team cannot show that the new model is better, and it costs more per summary [judgment].

## End

I recommend that we take these four steps in order:

1. **Audit a sample of 100 summaries.**
   - Increment: two agents label 100 recent summaries, with 20 shared to check agreement.
   - Blocker removed: nobody knows the error rate or the error types.
   - Kind: evaluative. Write the rubric before the work.
     - Criteria and weights: facts match the ticket (40), key information kept (30), status and next action correct (20), length and clarity (10).
     - Pass threshold: a summary passes at score 80 or more with no wrong fact.
     - Evidence: the full ticket text for each criterion.
     - Output: the major error rate (call it B) and a count per error type: unsupported fact, omission, wrong status, wrong name or number.
   - Cynefin domain: Confused. The cause of the errors is unknown, so this step gathers the data to classify the work. This step comes first because its output decides the rest.

2. **Add a "Wrong summary" button.**
   - Increment: one button and one reason list in the agent screen.
   - Capability added: a live error signal from agents.
   - Kind: deterministic. The test:

     ```text
     Given an agent views a ticket summary
     When the agent selects "Wrong summary" and picks a reason
     Then the system stores the ticket ID, summary text, model version, reason, and time
     ```

   - Cynefin domain: Clear. A known best practice exists, so apply it by deduction. This step does not depend on Step 1. Run it in parallel.

3. **Build a test harness from the labelled tickets.**
   - Increment: a script that runs the summariser on the 100 labelled tickets and reports the major error rate.
   - Blocker removed: no repeatable way to compare changes.
   - Kind: deterministic. The test:

     ```text
     Given the 100 labelled tickets from Step 1
     When the script runs the current summariser on them
     Then the script reports a major error rate within 5 points of B
     ```

   - Cynefin domain: Complicated. Analysis picks the scoring method (human labels first, an LLM judge later [2]). Deduction from the Step 1 rubric guides the work.
   - Step 3 MUST NOT start until Step 1 gives the labels.

4. **Probe one fix for the top error type.**
   - Increment: up to three prompt variants. Examples: a fixed summary layout with the sections "issue", "steps tried", "status", and "next action", plus an instruction to use only ticket text.
   - Blocker removed: the largest error type from Step 1.
   - Kind: stochastic. Write the acceptance test first.
     - Metric: major error rate on the 100 labelled tickets.
     - Baseline: B from Step 1.
     - Pass threshold: half of B or lower, in three repeat runs.
     - Sample size: 100 tickets per run.
   - Cynefin domain: Complex. Cause and effect show only after the trial, so this is a safe-to-fail probe. Leverage is a guess. Induction from trials drives it, and a model update or a new ticket type could break the pattern.
   - Budget: two working sessions. Stop when three variants fail the test.
   - Step 4 MUST NOT start until the Step 3 test passes.

## Follow-up

**Open questions:** none.

**Conditions that change the recommendation**

- If B is below 5%, skip Step 4. Instead, show a link to the source ticket beside each summary.
- If the data in Step 1 does not exist, add logging first.
- If a variant passes Step 4, release it to a small group of agents. Watch the Step 2 button for one week.
