Headline
Measure error types before any model change. Agents call summaries wrong, and the team has no metric. Therefore a model swap cannot show a gain. First, label a small set of real tickets. Next, set a factual-error baseline and fix only the largest class.

Background
The support tool now writes summaries with a large language model (LLM). Agents say those summaries are sometimes wrong. The team has no metric for that claim. The request is to make the summariser better.

Relevance
A wrong summary can send an agent to the wrong next step. Without a number, a change can release and still fail the same cases.

Information
This section covers the evidence, the assumptions, and the alternative.

The request states that agents find summaries wrong and that no metric exists.
[1]

Human checks document unfaithful content in abstractive news summaries.
[2]

Word-overlap scores do not track factual consistency well.
[3]

Human consistency ratings also disagree with many automatic scores.
[4]

Therefore the first measure is a human error code, not a new model.
[judgment]

Those studies use news text, not support tickets. The support rate can differ from the news rate.
[judgment]

Assumption: The input is a support ticket thread, not a call transcript. Why not measured: The material does not state it. Validate by: Open ten recent summary jobs and record the input type. If wrong: Use the real input in Step 1.

Assumption: Wrong means a fact error or a missing fact that changes the next agent action. Why not measured: The material does not state it. Validate by: Ask three agents to code five bad summaries. If wrong: Change the rubric before Step 2.

Assumption: At least 40 closed tickets with summaries exist. Why not measured: The material does not state it. Validate by: Count stored summary records. If wrong: Use every stored ticket and do not treat the rate as stable.

Alternative considered: Replace the LLM this week. It loses because there is no baseline, so a gain cannot be shown.

End
I recommend that we do these four steps in this order.

Step 1 is first because the work is Confused.

Test, evaluative. Rubric name: Support summary error review. Criteria and weights: source faithfulness 50%, missing next-step fact 30%, unsafe tone or policy miss 20%. Pass threshold: the same primary code from two raters on at least 32 of 40 items. Evidence: source text, summary text, and one reason code per rater.

In one session, export 40 closed tickets from the last 30 days and apply that rubric. This removes the unknown error class. Domain: Confused. Reason: acting first. The cause is not visible, so the labels are what classify the work.

Step 2 MUST NOT start until the Step 1 agreement test passes.

Test, deterministic.
Given 40 tickets with two reason codes each,
When the count script runs,
Then it prints the percent of each primary code and the number of rater conflicts.

In one session, write that script and store the baseline table. This removes the missing numeric baseline. Domain: Complicated. Reason: deduction from the counts. The counts pick the error class. More than one fix practice exists.

Step 3 MUST NOT start until Step 2 prints a top error class.

Test, stochastic. Metric: percent of summaries with the top error code from Step 2. Baseline: that Step 2 percent. Pass threshold: 10 percentage points below the baseline. Sample size: 30 new tickets, two raters, same rubric. Stop if any other code rises by 5 points.

In one session, change only the prompt line that targets the top class. Score 30 tickets. Do not release the prompt. Budget: one prompt version and 30 tickets. This adds a measured probe of one fix. Domain: Complex. Reason: induction from the trial. Cause shows only after the score. The pattern breaks if the top class comes from bad source text, not from the prompt.

Step 4 can start after Step 1. It does not wait on Step 3.

Test, deterministic.
Given the stored labels from Step 1,
When the score command runs,
Then it reprints the Step 2 baseline rates with zero difference.

In one session, save the labels and add that score command. This adds one score for every later change. Domain: Clear. Reason: deduction from a known rule. A fixed labeled set is the practice for regression checks.

If the ticket-count assumption is false, use every stored ticket and do not treat the rate as stable. If the top class is a tool bug, skip Step 3 and fix that tool path instead.
