Headline

Pin every direct dependency in requirements.txt, because two build breaks in one month show the current risk. First, unpinned versions let any upstream release change your build without warning. Second, breaks that appear after a library update confirm this cause. Third, pinning with a regular update routine keeps fixes current while builds stay stable.

Background

The project has a requirements.txt with no version pins. The build failed twice last month after upstream library updates.

Relevance

Each unpinned dependency is a recurring source of surprise failures. Pinning removes this class of failure at low cost.

Information

Two breaks in one month trace to upstream releases, per your report [judgment]. The standard practice is to pin exact versions for the runtime environment and to use a lock file or a tool such as pip-tools for transitive dependencies [1]. A full pin set records every transitive dependency, so a rebuild installs identical code [1][S, cited below].
