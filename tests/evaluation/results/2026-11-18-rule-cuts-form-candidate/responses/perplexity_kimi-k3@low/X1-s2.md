# Headline

You cannot improve the summariser until you measure it, so the first move is to build a small evaluation loop and then act on what fails.

- "Sometimes wrong" is an anecdote; a sampled error audit turns it into a measurable error rate and error types.
- Most LLM quality fixes (prompt edits, better context, length limits) are cheap once failure modes are known [judgment].
- A fixed test set prevents regressions: without it, each fix can silently break other cases.
- Full automation is premature until the error rate and its causes are quantified.

# Background

A support tool now includes an LLM-based summariser, and agents report it is "sometimes wrong". No metrics, test set, or failure log exist, so neither the size nor the type of the problem is known. The request is to make it better.

# Relevance

Changing prompts or models without measurement risks regressions that agents will detect before you do. A two-to-three-day measurement effort de-risks every later change.

## Evidence and analysis

- No error rate exists today [no source], so improvement is unverifiable.
- LLM summariser errors typically fall into classes: hallucination, omission of key facts, wrong entity, wrong tone [judgment]. The fix differs per class: hallucination improves with grounding in retrieved ticket text; omission improves with a checklist prompt.
- An acceptance test (per the stochastic task kind) needs: a metric (percent of summaries rated correct by a human), a baseline (measured in Step 3), a pass threshold (for example 90% correct, to be confirmed after baseline), and a sample size (100 summaries gives roughly plus or minus 8 percentage points at 95% confidence [judgment, standard binomial sampling]).

## Alternative considered

Swap to a different model or vendor first. It loses because without a test set there is no way to know if the new model is better, and it costs more than a prompt fix [judgment].

# End

I recommend that we run this five-step plan, in order.

1. **Add logging of input and output pairs.** Deterministic, Complicated domain (a known engineering practice applies). Test written first: Given a resolved ticket, When the summariser runs, Then the raw ticket text and the summary are stored with a shared identifier. Increment: one logging change shipped and verified on live traffic.
2. **Interview three agents and tag their complaints.** Evaluative, Complicated domain. Write a rubric first: error classes hallucination, omission, wrong entity, other; each complaint gets exactly one class. This removes the blocker of an undefined word, "wrong".
3. **Build a baseline test set of 100 sampled summaries and score them.** Stochastic measurement, Complicated domain. Metric: percent rated correct by two human raters. This becomes the regression suite every later change must pass.
4. **Run one safe-to-fail fix per dominant error class as a capped probe.** Complex domain: cause and effect are visible only after the trial, so cap each probe at one working session. Test written first: rerun the prompt change on the 100-item test set; accept only if the correct rate rises by at least 5 points and no other error class worsens.
5. **Add a weekly pass/fail report on 30 fresh summaries.** Deterministic, Clear domain. Step 5 MUST NOT start until the test set in Step 3 exists. Test: Given the weekly sample, When scored, Then the report shows the pass rate and triggers an alert below the threshold.

# Follow-up

Conditions that change the recommendation: if logging is impossible for privacy reasons, replace Step 1 with manual collection of 100 tickets; if two error classes tie in Step 2, run two probes in parallel within the same budget.
