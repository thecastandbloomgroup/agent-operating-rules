## Headline

Measure the summariser before changing it, then fix the largest measured failure cause.

1. "Sometimes wrong" is not actionable, so first convert it into a labeled sample with an error taxonomy.
2. Summariser output is stochastic, so every change needs an acceptance test with a baseline and a sample size.
3. Prompt, retrieval, and model changes each fix different failure classes, so order the fixes by measured cause.
4. The cheapest reliable gain is usually better source context, because grounding errors dominate support summarisation [judgment].

## Background

A support tool now includes a summariser built on a large language model (LLM). Agents report errors, but no measurements exist. The request is to make the summariser better.

## Relevance

Acting without metrics risks spending effort on changes that do not reduce the errors agents see. Without a baseline, no later improvement is provable.

## Information

First, the evidence available: the agent reports are the only signal. They show errors exist but give no rate, class, or cause [no source]. Three facts from practice inform the plan. LLM output varies from run to run, so single examples cannot prove a fix worked [judgment]. Support summaries fail in two main classes: fabrication, where the summary states things not in the ticket, and omission, where the summary drops required facts [judgment]. Grounded summaries, generated from retrieved ticket text, fail less on fabrication than summaries generated from memory of the conversation [judgment].

Assumption: A log of at least 200 past summaries with their source tickets exists. Why not measured: the material does not state it. Validate by: check the tool's storage for summary records. If wrong: capture new traffic for two weeks before Step 2, and shift the timeline by two weeks.

Assumption: Agents can label summaries during normal work. Why not measured: the material does not state it. Validate by: ask one team to label for one day and measure the time cost. If wrong: use a sample of 100 summaries labeled offline instead.

Alternative considered: tune the prompt immediately and ship it. This loses because prompt tuning without a labeled test set optimises against anecdotes, not against the measured error classes [judgment].

## End

I recommend that we take these actions:

1. Add a feedback capture to the tool: a one-click "wrong" flag with an optional note on each summary. This removes the blocker that no error data exists. Deterministic. Test first: Given a displayed summary, When an agent clicks "wrong", Then the flag, note, summary, and source ticket persist together. Clear domain: the path from click to stored record is known deduction from a standard logging practice.

2. Sample 200 flagged or randomly selected summaries and label each: correct, fabrication, omission, or wrong tone. This adds the capability to rank failure causes. Evaluative, because labeling is a judgment. Rubric first: each summary scored against its source ticket on four criteria weighted evenly: factual accuracy, completeness, actionability, tone; pass threshold 90% correct; evidence is the source ticket text. Complicated domain: analysis of the labels picks the fix, induction from the sample; a biased sample would break the pattern, so keep the random sample alongside flagged ones.

3. Run the acceptance test on the current summariser: metric is correct rate on the labeled rubric, baseline is the current system, pass threshold is set after the baseline run, sample size is 200. Stochastic. Complicated domain: the result decides which fix class to fund, deduction from measured rates.

4. Fix the largest measured failure class. If fabrication dominates, ground the prompt in retrieved ticket text and require quoting the source. If omission dominates, add a required-fields checklist to the prompt. Stochastic. Rerun the Step 3 test and accept only when the correct rate rises by the threshold at a sample of 200. Complex domain: causes are visible only after trials, so treat this as a capped probe with a stop condition of two iterations and a budget of two working sessions. Leverage is a guess.

5. Add the acceptance test to the release pipeline so every prompt or model change reruns it. Deterministic. Test first: Given a prompt change, When the release runs, Then the measured correct rate on the 200-case set gates deployment. Clear domain: a known regression-test practice. Step 5 MUST NOT start until the test in Step 3 passes, because the gate needs a trusted baseline.

Sequence: 1 and 2 in parallel, then 3, then 4, then 5.

If the log assumption is false, delaying Steps 2 and 3 by two weeks changes the timeline, not the plan.
