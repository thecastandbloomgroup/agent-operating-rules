## Headline

Treat SQL formatting as a team agreement problem, then let a tool handle layout. [judgment]

- Give one person authority to resolve formatting disputes through a fair, time-limited process. [judgment]
- Separate layout preferences from correctness and readability concerns. [judgment]
- Test the agreement before making it permanent. [judgment]

## Background

Your team disagrees about SQL format, and those disputes create friction in every review. [1] The request concerns team behavior, not just indentation.

## Relevance

A formatter alone does not decide whose preferences count or how people can challenge a rule. [judgment] Therefore, address the decision process before enforcing the tool.

## Information

**Working diagnosis:** the team lacks an accepted way to settle low-risk preferences. [inference] Confidence is low because the account describes the conflict, but not its causes.

The proposed agreement separates three concerns:

- **Layout:** let the formatter control indentation, spacing, keyword case, and line breaks.
- **Meaning:** keep human review for query results, performance, security, and database compatibility.
- **Readability:** permit concrete concerns about names, query structure, and comments, without reopening layout preferences.

This separation is a proposed boundary, not a finding about your team. [judgment]

**Assumptions**

A1. A team lead can own the temporary agreement. Why not measured: The material does not state it. Validate by: confirm ownership. If wrong: obtain a sponsor before rollout.

A2. An available formatter supports your SQL dialect. Why not measured: The material does not state it. Validate by: check five representative queries. If wrong: postpone automation.

**Alternative considered:** vote on a detailed style guide. It gives everyone a voice, but preserves many preference decisions and their enforcement burden. [judgment]

## End

I recommend that we complete these three actions, with the third treated as a limited experiment.

### 1. Publish a temporary review agreement

**Kind:** deterministic. **Domain:** Clear, because a written rule defines the permitted review behavior.

**Test first**

```gherkin
Given a review comment concerns only formatter-controlled layout
When the author uses the agreed formatter
Then the comment cannot block approval
```

**Action:** Hold one 30-minute team session and publish a one-page agreement.

This removes uncertainty about decision rights. Use this proposed text:

> The formatter controls layout, not personal preference. Human review covers meaning, safety, performance, and readability.
>
> Explain readability concerns with a concrete example. Do not block approval over formatter-controlled layout.
>
> Record style proposals in one shared list. The named owner decides them at the scheduled review, not inside individual code reviews.
>
> Apply the agreement equally, regardless of seniority.

Give each person one chance to name a practical constraint. The owner then closes unresolved preference choices for the trial. [judgment]

### 2. Configure one formatter without changing the whole repository

**Dependency:** Step 2 MUST NOT start until Step 1 has a named owner and published agreement.

**Kind:** deterministic. **Domain:** Clear, because one configuration produces the required layout.

**Test first**

```gherkin
Given five representative queries in the team's SQL dialect
When the formatter runs twice with the shared configuration
Then the second run produces no further changes
And all five queries pass the project's existing SQL checks
```

**Action:** Spend one session configuring a compatible formatter with its default layout rules.

This removes manual layout enforcement. Add the same command to local development and the automated checks.

Inspect the first changes for unexpected edits. Keep bulk reformatting separate from functional changes so reviewers can distinguish them. [judgment]

If A2 fails, stop this step rather than imposing an incompatible tool.

### 3. Run a bounded trial of the agreement

**Dependency:** Step 3 MUST NOT start until Step 2 passes its test.

**Kind:** stochastic. **Domain:** Complex, because the effect on team behavior becomes visible only after use.

**Acceptance test first**

- **Baseline:** count format-only blocking comments in the previous 10 SQL reviews.
- **Sample:** the next 10 SQL reviews.
- **Metric:** format-only blocking comments per review.
- **Pass threshold:** zero such comments, with every participant able to name a route for concrete readability concerns.
- **Stop condition:** pause enforcement if the formatter breaks supported SQL or suppresses a concrete correctness concern.
- **Budget:** cap administration at 60 minutes, excluding normal review work.

**Action:** Run the trial, record results, and hold a 15-minute decision session.

This tests whether the agreement reduces friction without silencing useful review. Its benefit remains a hypothesis, not a measured result.

Accept the agreement only after the sample meets the threshold. Otherwise, revise the failed boundary rather than debating every style choice again.

## Follow-up
