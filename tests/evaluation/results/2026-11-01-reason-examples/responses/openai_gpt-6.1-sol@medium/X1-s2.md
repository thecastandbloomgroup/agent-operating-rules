## Headline

Improve the summariser by measuring its errors first, then testing one targeted change offline.

- Use ticket facts, not agent satisfaction alone, to judge accuracy. [judgment]
- Compare each change with the current summariser before release. [judgment]
- Keep agents responsible for checking summaries until the tests support a wider trial. [judgment]

## Background

Agents report that the summariser is “sometimes wrong,” but no metrics exist. [1] The available evidence does not identify the error types, frequency, or causes. [1]

## Relevance

Therefore, a prompt change now would lack a measured basis. [judgment] A small, source-linked test can establish what fails without exposing customers to an untested change. [judgment]

## Information

### Define “better”

Use these measures first. They separate false statements, missing facts, and agent effort. [judgment]

| Measure | Definition | Comparison |
|---|---|---|
| Factual error rate | Percentage of summaries containing a false or unsupported claim | Candidate versus current summariser |
| Essential omission rate | Percentage missing a fact needed for the agent’s next action | Candidate versus current summariser |
| Serious error count | Errors that risk harmful action, financial loss, or private-data exposure | Candidate must have zero |
| Correction time | Median seconds agents need to make a summary usable | Candidate versus current summariser |

Record each error beside the source passage and the correction. This makes “wrong” specific enough to diagnose. [judgment]

Treat unsupported claims separately from contradictions. For example, an invented refund promise differs from an incorrect refund amount. [judgment]

**Confidence:** Low confidence in any specific cause, because the only evidence is an unmeasured agent report. [1]

### Assumption log

A1. Authorised reviewers can access ticket records and saved summaries. Why not measured: The material does not state it. Validate by: Check one record. If wrong: Establish approved access before sampling.

A2. Agents can judge which facts support the next action. Why not measured: The material does not state it. Validate by: Review three tickets together. If wrong: Add a support specialist as reviewer.

### Alternative considered

Replace or fine-tune the model immediately. This loses because no evidence yet separates model faults from missing context or unclear instructions. [judgment]

## End

I recommend that we complete these three actions in order. The sample sizes, budgets, and thresholds below are proposed pilot limits. [judgment]

### 1. Create a source-linked test set

**Kind:** Deterministic.  
**Domain:** Clear, because fixed record requirements allow direct checks.

**Test first:**

```gherkin
Given 30 authorised support tickets and their saved summaries
When the test set passes its record checks
Then every record links the summary to its exact source context
And every record includes model version and available prompt settings
And access follows the support tool's privacy controls
```

**Action:** In one session, select 30 tickets at random from a defined recent period.

Save the exact context the summariser received, not just the full ticket. Record unavailable settings rather than inventing them.

**Capability added:** A repeatable comparison set that can reveal missing input as well as faulty output. [judgment]

**Budget:** 60 minutes. If access prevents completion, resolve access before continuing.

### 2. Measure the current summariser and identify the main fault

Step 2 MUST NOT start until Step 1 passes.

**Kind:** Stochastic, because the sampled tickets and agent assessments vary.  
**Domain:** Complex, because actual failure patterns emerge through observation.

**Acceptance test first:**

- **Baseline:** Saved outputs from the current summariser; no prior measured error rate exists.
- **Sample:** All 30 tickets from Step 1.
- **Metrics:** The four measures above, plus error count by cause.
- **Pass threshold:** Complete assessments for 30 of 30 summaries, with source evidence for every error.
- **Review check:** A second agent checks every serious error and every disputed assessment.

**Action:** Have an agent correct each summary while recording time and errors.

For each error, assign one cause:

1. The required fact was absent from the supplied context.
2. The context contained the fact, but the summary misstated or omitted it.
3. The ticket itself lacked a supported answer.

Keep uncertain causes marked “unresolved” rather than forcing a category.

**Blocker removed:** The team gains a measured problem instead of a general complaint. [judgment]

**Probe limits:** Cap this session at two hours. Stop any affected automatic action if reviewers find a serious error. [judgment]

This sample gives an initial direction, not proof of safety against rare errors. [judgment]

### 3. Test one change against fresh tickets

Step 3 MUST NOT start until Step 2 passes.

**Kind:** Stochastic.  
**Domain:** Complex, because the change’s effect appears only after a trial.

**Acceptance test first:**

- **Baseline:** Current summariser outputs on the same fresh tickets.
- **Sample:** 30 fresh tickets, each processed by both versions.
- **Accuracy threshold:** At least 50% fewer summaries with factual errors.
- **Zero-error exception:** If the baseline has zero factual errors, the candidate must also have zero.
- **Other thresholds:** Zero serious errors; no higher essential omission rate.
- **Effort threshold:** Median correction time must not exceed the baseline.
- **Review method:** Hide version labels from reviewers.

**Action:** Change only the part implicated by the most common supported cause.

- For missing context, supply the missing source fields.
- For unsupported claims, require source-backed statements and explicit unknowns.
- For missing answers, show “not established” instead of an inferred answer.

**Capability added:** Evidence that one targeted change improves quality without increasing agent work. [judgment]

**Probe limits:** Keep the candidate offline. Cap the session at three hours and stop upon a serious candidate error.

Accept the candidate only if every threshold passes. If it fails, retain the current version and use the new errors to choose the next change.
