## Information

**Working diagnosis:** formatting decisions lack a shared decision process, so each review becomes another vote. [judgment]

Low confidence in this diagnosis: the evidence contains one report and no review records. Therefore, avoid treating this as proof of poor attitudes.

Distinguish three kinds of feedback:

- **Formatting:** spacing, capitalization, indentation, and line breaks.
- **Readability:** names, query structure, and explanations.
- **Correctness:** results, database behavior, security, and performance.

Use these boundaries in the policy below. A formatter should settle the first category, not silence the other two. [judgment]

## End

I recommend that we take these three steps, in order.

### 1. Write a one-page review agreement

**Kind:** Deterministic.  
**Domain:** Clear, because the document has explicit acceptance criteria.  
**Increment:** One 30-minute session.  
**Blocker removed:** Nobody knows which feedback requires a change.

**Test, before the work:**

```gherkin
Given a proposed SQL review agreement
When the team checks its contents
Then it defines formatting, readability, and correctness feedback
Then it names one temporary formatting decision owner
Then it defines an exception path and a review date
```

Use this core agreement:

> The formatter decides routine SQL formatting. Reviewers do not block changes over personal formatting preferences.
>
> Correctness and readability concerns remain valid. Explain the concrete problem and suggest a change.
>
> Discuss proposed formatting rules outside active reviews. The temporary owner decides unresolved rules and records the reason.
>
> Apply the same rules regardless of author or seniority.

Have the repository owner confirm the agreement. Do not present that approval as proof of team trust. [judgment]

### 2. Make the default executable

**Dependency:** Step 2 MUST NOT start until Step 1 passes its document check.

**Kind:** Deterministic.  
**Domain:** Complicated, because compatibility tests must identify a formatter that supports the team’s SQL dialect.  
**Increment:** One setup session on a branch.  
**Capability added:** Authors and reviewers can apply the same rules.

**Test, before the work:**


Compare available formatters through the compatibility test, not a preference poll. [judgment]  
Commit one configuration and a short command for local use. Add an automated check when repository permissions allow.

Keep the first change small. Do not combine a repository-wide reformat with functional changes. [judgment]

### 3. Run a capped review trial

**Dependency:** Step 3 MUST NOT start until Step 2 passes.

**Kind:** Stochastic, because reviewer behavior varies.  
**Domain:** Complex, because the effect on team behavior appears only after a trial.  
**Increment:** One review session, capped at 45 minutes.  
**Capability added:** Evidence about whether the agreement reduces conflict. Leverage remains a guess. [judgment]

**Acceptance test, before the trial:**

- **Baseline:** Count formatting-only exchanges in three recent SQL reviews.
- **Sample:** Review three small SQL changes under the agreement.
- **Metric:** Count formatting-only exchanges and policy breaches.
- **Pass threshold:** Zero blocking formatting-only exchanges; all three reviews preserve correctness and readability feedback.
- **Stop condition:** Stop if the formatter changes query behavior or someone uses the agreement to dismiss substantive feedback.
- **Budget:** At most 45 minutes; no production rollout.

Record observations without ranking or blaming teammates. If fewer than three reviews finish, record an incomplete trial, not a pass.
