## Headline

Make the summariser measurable first, then test one targeted fix before expanding its use.

- Define “wrong” with a short review rubric, rather than treating every complaint as the same failure.
- Compare the current and revised summariser on the same support cases.
- Keep agents in control until the revised version passes a quality and effort test.

## Background

Agents report that the summariser is “sometimes wrong,” but you have no metrics. [1]  
The report identifies a problem, but it does not establish its frequency, severity, or cause. [inference]

## Relevance

Without a baseline, a prompt change can improve some summaries while harming others without detection. [judgment]  
Therefore, the next useful result is a measured baseline and a tested fix, not an untested rewrite. [judgment]

## Information

### Define the failure before choosing the fix

Use three distinct review criteria. These weights are proposed starting points, not measured business priorities. [judgment]

| Criterion | Weight | Evidence required |
|---|---:|---|
| Factual accuracy | 60% | Each factual claim matches the source conversation |
| Required coverage | 25% | The summary preserves the issue, current status, and agreed next action, when present |
| Usability | 15% | An agent can understand the summary without correcting its structure or wording |

Score each criterion as **0: fails, 1: partly meets, or 2: meets**.  
Calculate the weighted score out of 100.

Use **90/100 with no severe error** as the initial acceptance threshold. [judgment]  
A severe error invents a commitment, reverses a key fact, or reveals restricted information. [judgment]

Also measure:

- **Error rate:** percentage of summaries with a factual error or missing required information.
- **Severe-error rate:** percentage of summaries with a severe error.
- **Agent review time:** seconds needed to approve or correct a summary.

Review time prevents a quality gain that merely transfers more work to agents. [judgment]

### Match the fix to the observed failure

These are candidate fixes, not findings about your system. [judgment]

| Observed failure | First change to test |
|---|---|
| Relevant source text never reaches the model | Repair input selection or truncation |
| Source text reaches the model, but the summary invents facts | Require source references and explicit “not stated” outputs |
| The summary omits required information | Use fixed fields for issue, status, and next action |
| The summary mixes speakers or dates | Preserve speaker labels and timestamps in the input |

Do not change the model, prompt, and input pipeline together. That prevents a useful comparison of which change caused the result. [judgment]

**Confidence:** low confidence about the cause, because no examples, logs, or measured outcomes are available.

### 3. Run a capped, paired comparison

**Kind:** Stochastic.  
**Domain:** Complex, because the change’s effect becomes visible only through a trial.

**Acceptance test first:**

- **Sample:** 50 untouched cases, with one current-version and one revised-version summary per case.
- **Baseline:** The current version’s scores on those same cases.
- **Primary threshold:** At least 20% fewer error-bearing summaries than the baseline.
- **Safety threshold:** Zero severe errors in the revised summaries.
- **Coverage threshold:** The revised version’s average coverage score must not fall below the baseline.
- **Effort threshold:** Median agent review time must not exceed the baseline by more than 10%.

These are pilot thresholds, not proven business tolerances. [judgment]  
If the baseline has zero errors, this sample cannot demonstrate the proposed error reduction.

**Action:** Implement only the selected change in a test version. Compare both versions with reviewers unaware of version identity.

**Budget:** One four-hour session, at most 100 generated summaries.  
**Stop condition:** Stop for a severe error, an access violation, or the budget limit.
