# Headline

Treat the flaky build as a diagnostic problem: stabilize a reproduction first, then classify the cause, then fix one cause at a time.

- Flaky builds fall into four MECE cause classes: timing/concurrency, environment differences, shared state between runs, and dependency nondeterminism [judgment].
- Stabilizing a reproducible failure removes the largest blocker: invisible causes.
- The recommendation is domain-agnostic because the build system and language are not stated (see assumptions A1 to A3).

# Background

The build fails intermittently (flaky) rather than deterministically. No build tool, language, error output, or failure frequency was provided. The task is to move from "fails sometimes" to a diagnosed, fixable cause.

# Relevance

Flaky builds erode trust in the build signal. Teams then ignore build failures, so real defects pass through [judgment]. Fixing flakiness now protects every future change.

# Information

## Cause classes (MECE)

1. **Timing and concurrency**: race conditions, unordered parallel steps, network timeouts. Typically shows as failures under load or on fast machines.
2. **Environment differences**: machine state, timezone, locale, tool versions that drift between agents (a "agent" is one build machine or container).
3. **Shared state**: leftover build artifacts, caches, database residue, or port/file collisions between runs.
4. **Dependency nondeterminism**: unpinned versions, live network calls, tests that query external services.

A theme across practitioner sources: shared caches and tests that depend on wall-clock time or the network are the most reported flaky-build causes (three common categories, reported repeatedly in industry guidance) [1] [2]. Baseline comparison: a build that fails under 1% of runs is typical; one that fails over 5% of runs blocks merges [judgment].

## Assumption log

A1. You control the build pipeline and can re-run it on demand. Why not measured: the material does not state it. Validate by: trigger one manual re-run. If wrong: add a step to get pipeline access first.

A2. The failure is nondeterministic, not a slowly degrading deterministic fault. Why not measured: the material does not state it. Validate by: run the same commit twice; differing results confirm nondeterminism. If wrong: treat as a normal bug, skip Step 1 probe.

A3. Failure rate is above 5% of runs, making diagnosis economical. Why not measured: not stated. Validate by: count failures over 20 runs. If wrong (below 1%): schedule the work later; keep the quarantine steps.

## Alternative considered

The strongest alternative is "upgrade all build tools and dependencies at once, hoping the flake disappears". It loses because it changes many variables at once, so no cause is identified and the flake can return unseen [judgment].
