## Headline

The pool size change caused the latency rise. Restore `max_size` toward 50 and `acquire_timeout_s` toward 30 first.

1. Trace data shows `db.pool.acquire` p95 rose from 3 ms to 690 ms while query times stayed flat [3].
2. The diff lowered `max_size` from 50 to 8, but 32 workers need connections concurrently [2].
3. The added `selectinload` and the shorter cache TTL add load but are secondary causes [2][3].

## Background

Release 2026.10.21 touched the ORM layer, the cache config, and the pool config. After deploy, endpoint p95 rose from 120 ms to 900 ms [3].

## Relevance

Pool timeouts now cause 0.40% of requests to return 503 [3]. Each hour of delay extends customer-facing errors.

## Information

Evidence:

- `db.pool.acquire` p95: 3 ms in Window A versus 690 ms in Window B [3].
- Query spans are flat: `db.query orders` p95 is 52 ms versus 58 ms; `order_lines` is 30 ms versus 26 ms [3].
- Active database connections peaked at 31 before the release. The new limit of 8 is 74% below that observed peak [3][2].
- 1,800 to 2,400 "pool exhausted" warnings per hour after release, versus zero before [1].
- Cache miss rate rose from 12% to 31% because TTL fell from 300 s to 60 s [2][3]. This raises query volume, so it amplifies pool contention.
- Database CPU is flat at 38% versus 41%, so the server is not saturated [3].

Assumption log:

`A1. Ticket OPS-412 states a real per-service database connection limit, but its value is not in the material. Why not measured: the material does not state it. Validate by: read OPS-412 or ask the DBA. If wrong (limit below 50): keep pool at that limit and reduce worker count to match.`

`A2. The selectinload change is a deliberate feature, not an accident. Why not measured: no commit message explains it. Validate by: check the pull request for app/orm/orders.py. If wrong: revert it.`

Alternative considered: blame the ORM change (`selectinload`). It loses because both query spans are flat, and 96% of errors are pool acquire timeouts [3]. The ORM change adds one extra connection hold per miss, so it amplifies but does not cause the failure [judgment].

## End

I recommend that we:

1. **Raise `pool.max_size` to 50 and `acquire_timeout_s` to 30, then deploy.** Blocker removed: 32 workers cannot share 8 connections. Domain: Clear, because the trace shows acquire wait as the single dominant span and the prior config is known to work [3]. Test (deterministic, write first):
   - Given release 2026.10.14 traffic replayed at 410 requests per second,
   - When the new config runs for 30 minutes,
   - Then `db.pool.acquire` p95 is below 10 ms and `PoolTimeout` count is zero.

2. **Confirm the limit in OPS-412 before Step 1 reaches production.** Blocker removed: risk of exceeding a real database cap. Domain: Complicated, because two valid pool sizes exist and the ticket decides between them. Test (evaluative): rubric weight 100% on the stated per-service connection limit in OPS-412. If the limit is below 50, set `max_size` to that limit and reduce worker threads so workers per pod do not exceed the pool. Step 1 MUST NOT ship to production until this check passes.

3. **Restore `cache.default_ttl_s` to 300.** Blocker removed: miss rate of 31% adds avoidable queries against a small pool. Domain: Clear, because the prior TTL is known to give a 12% miss rate. Test (deterministic):
   - Given Window B traffic replayed,
   - When the TTL is 300 s,
   - Then cache miss rate is at or below 15%.

4. **Probe the `selectinload` change with a capped canary.** Blocker removed: unknown memory and row-fetch cost on large order sets. Domain: Complex, because its effect on tail latency shows only under live traffic. Budget: one pod, 2 hours. Stop condition: pod p95 200 ms above fleet p95. Test (stochastic): metric is endpoint p95, baseline is the control pods, pass threshold is parity within 10%, sample size is 10,000 requests. Leverage is a guess.

5. **Add a deploy gate on pool config.** Capability added: a config check that blocks `max_size` below the worker count per pod. Domain: Clear, because the rule is mechanical. Test (deterministic):
   - Given a db.yaml with `max_size` below workers per pod,
   - When the gate runs in continuous integration,
   - Then the deploy fails with a named error.

Steps 2 and 3 can run in parallel with Step 1's staging test. Step 4 runs in parallel after Step 1. If A1 is false (limit below 50), Step 1 uses the OPS-412 limit and the worker-count change in Step 2.

## Follow-up

Conditions that change the recommendation: a hard database limit below 50 connections (see A1). Open question: what value does OPS-412 state? The answer sets the final `max_size`.
