# Headline

Build a measured quality loop before tuning anything: a test set, an error taxonomy, and an acceptance threshold for the summariser.

- No baseline exists, so no fix can be verified [judgment].
- "Sometimes wrong" hides distinct failure types that need distinct fixes.
- LLM output varies by run, so only sampled testing gives a valid pass or fail signal.
- Instrumentation changes little user-visible behavior, so risk stays low.

# Background

The support tool now includes an LLM-based summariser for tickets. Agents report it is "sometimes wrong", but no metrics or error records exist. The request is to improve it without a clear definition of "better".

# Relevance

Without a baseline, any change cannot be proven to help and could hurt. A short instrumentation sprint converts a complaint into an engineering problem that a team can close.

# Information

## Evidence

- "Sometimes wrong" is one qualitative report with no count, so severity is unknown [no source]. One source theme, no disagreeing source.
- LLM summarisation output varies from run to run [judgment]. Therefore stochastic testing with a stated sample size applies.
- Agent feedback is the cheapest proxy for ground truth because agents already read every ticket [judgment].

## Assumption log

`A1. The summariser output is visible to agents next to the source ticket. Why not measured: the material does not state it. Validate by: open the tool and check one ticket. If wrong: add a review step before agents see summaries.`

`A2. The team can deploy code changes to the support tool within one week. Why not measured: the material does not state it. Validate by: ask the owning engineer. If wrong: shift all steps to the platform team's backlog.`

`A3. At least 200 tickets per week flow through the tool. Why not measured: the material does not state it. Validate by: query ticket database for last four weeks. If wrong: extend the sampling window in Step 4.`

## Alternative considered

Fine-tune or rewrite the prompt immediately. It loses because with no test set there is no way to know whether accuracy rose or a new failure type appeared [judgment].

# End

I recommend that we:

1. Classify the complaint scope first, Cynefin domain Confused, because the failure types are not visible yet. This is a one-hour working session. Interview the three agents, write down every "wrong" example from the last week, and group them into an initial error taxonomy (missing facts, wrong facts, wrong tone, other). This removes the blocker of not knowing what "wrong" means. The analysis picks the taxonomy. Blocker this step ingests only: we cannot classify the domain further without it.

   Deterministic test, written first:
   Given at least 20 recent tickets,
   When the session ends,
   Then 95% of reviewed tickets carry one taxonomy label and the team agrees on the label set.

2. Add a logging hook that stores for every summary: ticket text, model version, prompt version, summary, and a one-tap agent rating (correct or wrong plus taxonomy label). Cynefin domain Clear, because one known practice (structured logging) covers it. This adds the capability to measure. One working session.

   Deterministic test, written first:
   Given a new ticket is summarised,
   When the agent taps a rating,
   Then one row appears in the log with ticket ID, prompt version, summary, and rating.

3. Build a fixed test set of 100 tickets sampled across issue types, each with a human-written gold summary. This depends on Step 1 for the taxonomy and MUST NOT start until Step 1 passes. Cynefin domain Complicated, because sampling strategy needs analysis of the ticket mix. This becomes the baseline for every future change.

   Evaluative test, written first. Rubric per ISO/IEC-style criteria: factual accuracy weight 50, coverage of key points weight 30, brevity weight 20. Pass needs each ticket scored by one agent against the rubric. Threshold: all 100 tickets carry both a gold summary and a rubric score for the current model output.

4. Run the baseline measurement, Cynefin domain Complex as a capped probe with budget of one working session, because the true error rate is knowable only after measurement. Leverage claim is a guess at this stage.

   Stochastic test, written first: metric is rubric score from Step 3. Sample size 100. Baseline is undefined, so this run sets it. Pass condition for the project overall: error share below 5% on the 100-ticket set.

5. Apply one fix to the largest error class from Step 4, such as a prompt change or an added source-passage requirement, in parallel with ongoing logging. Cynefin domain Complex, capped at one prompt iteration per trial, because the effect of prompt changes is visible only afterward.

   Stochastic test, written first: same metric and sample size as Step 4. Pass when the rubric score rises by at least 10 points at the same 100-ticket sample size. Reject the change when the threshold is not met.

Steps 1 to 3 run in sequence. Step 4 runs twice: before any fix and after each fix. Step 5 repeats per fix and MUST NOT ship a change that fails its test.

# Follow-up

- Condition that changes the plan: if A3 is false, raise the sampling window so the test set still reaches 100 tickets.
- Condition that changes the plan: if agents resist one-tap rating in Step 2, use a weekly sample-review of 50 summaries instead.
