# Headline

The pool size cut from 50 to 8 caused the latency spike; it leaves 24 of 32 workers queued on connections. Cache misses tripled because TTL fell from 300 s to 60 s, which deepens the queue. I recommend that we roll back the pool size to 50 in the new release, then re-tune the cache and the DB connection limit together.

# Background

P95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed pool config, cache TTL, and the orders query. Logs, traces, and the diff are attached.

# Relevance

The service now returns 503 errors under load. Each hour of delay costs about 0.40% of requests failing, per traces.txt.

# Information

**Evidence**

1. db.pool.acquire p95 rose from 3 ms to 690 ms between windows A and B [1]. Query and serialize spans stayed flat, so the bottleneck is pool wait, not slower queries.
2. The pool holds 8 connections while 32 workers run across 4 pods [2]. Little's law predicts queueing: at 405 rps with 690 ms wait time, roughly 280 requests queue behind 8 connections [judgment].
3. Peak DB connections from this service fell from 31 to 8 [1]. The database has headroom: CPU peak was 41% [1].
4. Cache miss rate rose from 12% to 31% because default TTL fell from 300 s to 60 s [1][2]. More misses mean more pool demand per request.
5. The selectinload change splits the query into two, but each query is fast: 58 ms and 26 ms p95 [1]. It adds one connection hold per miss, a secondary effect.

**Assumptions**

A1. The "new DB connection limit per service" in OPS-412 reflects a real constraint, not an error. Why not measured: the material states a ticket number but no limit value. Validate by: ask the DBA for the limit. If wrong: the pool can return to 50 with no negotiation.

A2. If there is a real limit, it applies per service, so 50 across 4 pods is the baseline to negotiate against, since release 2026.10.14 used 31 peak connections. Why not measured: the diff gives no limit value. Validate by: confirm in OPS-412. If wrong: redistribute pool size across pods.

**Alternative considered**

Raise the pool to 32 (one per worker). It loses because cache misses still need 2 connection holds at times, and release 2026.10.14 ran healthy at a 31-peak pool with 120 ms p95 [1].

# End
