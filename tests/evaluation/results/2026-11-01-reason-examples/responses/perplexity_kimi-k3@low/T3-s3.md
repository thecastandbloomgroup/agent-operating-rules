# Headline

Split the request in two: run the session-to-JWT migration as a tested code change, and run sign-up conversion as a small measured experiment with its own stop condition.

1. The migration is a deterministic engineering task with a verifiable test.
2. Conversion work is a separate stochastic task because no baseline or target exists [judgment].
3. The two tasks share no dependency, so teams can run them in parallel.
4. No stack, baseline metric, or JWT threat model was given, however the recommendation proceeds on stated assumptions.

# Background

The request asks for two things: replace session-based authentication with JSON Web Tokens (JWT, a signed token that a client sends on each request), and improve sign-up conversion. No framework, user data store, or conversion metric appears in the request.

# Relevance

Both items affect the login path, which is the highest-traffic surface of the product. A wrong migration breaks every logged-in user, so evidence and tests must come first.

# Information

## Evidence and assumptions

- JWT removes per-request session storage lookups. The size of that saving is [judgment] because the request gives no load data.
- JWT adds risks: no simple server-side revocation and token theft risk. Mitigations are short token lifetimes and refresh-token rotation. [judgment]
- No conversion baseline or target appears in the request, so no improvement target can be proved.

Assumption log:

`A1. The service is a standard web API with a database-backed session store. Why not measured: the material does not state it. Validate by: one scan of the auth module. If wrong: Step 1 design changes, Steps 3 to 4 still hold.`

`A2. Sign-up means the form-to-account-success rate in existing analytics. Why not measured: the material does not state it. Validate by: query the analytics events table. If wrong: Step 5 picks a different funnel step, probe design is unchanged.`

`A3. Users can tolerate a one-time re-login at cutover. Why not measured: the user has not answered. Validate by: support ticket policy check. If wrong: add a silent token exchange step before cutover.`

## Alternative considered

The strongest alternative is to keep sessions and only scale the session store, for example with a shared cache. It loses on coupled scope: the migration is already requested, and a cache layer adds a component without removing the per-request lookup [judgment]. It remains the fallback if Step 2's design review finds unacceptable revocation requirements.

# End

I recommend that we take these five actions in this order.

1. **Inventory the auth surface.** List every endpoint that reads the session, and every store of session state. This removes the blocker of unknown blast radius. Cynefin domain: Clear, because each endpoint scan has one known method. Kind: deterministic. Test, written first:
   - Given the service source code and route table,
   - When the inventory runs,
   - Then every session-read call appears in the list, checked by a static search for the session API that returns zero unlisted hits.

2. **Write the JWT design, one page.** Cover signing algorithm, key rotation, token lifetime in minutes, refresh flow, and revocation list. This removes the blocker of an undefined security model. Cynefin domain: Complicated, because several valid designs exist and analysis must pick one; the analysis is this design review. Kind: evaluative. Rubric first: criteria are revocation support (weight 40%), key rotation safety (30%), integration cost (30%); pass threshold 80 on weighted score; evidence is the design section answering each criterion. Step 2 MUST NOT start implementation; it waits for the rubric score.

3. **Implement JWT login behind a feature flag, with dual-read.** Accept both session and JWT during transition. This unblocks safe rollout. Cynefin domain: Clear, because flag-based rollout is a known practice. Kind: deterministic. Test, written first:
   - Given a valid session cookie and the flag off,
   - When a request hits a protected endpoint,
   - Then the endpoint returns 200, and with the flag on and a valid JWT it also returns 200, and with an expired JWT it returns 401.
   Step 3 MUST NOT merge until the tests in Step 2's rubric pass.

4. **Cut over and delete the session path.** Flip the flag for all traffic, then remove session code after one re-login window. This removes the blocked capability of stateless auth. Cynefin domain: Clear, because the cutover steps are known once tests pass. Kind: deterministic. Test, written first:
   - Given the flag fully on for 7 days,
   - When error rate and login success rate are compared with the 7-day baseline before the flip,
   - Then login success rate stays within 1 percentage point of the baseline, and session-store reads are zero.
   Step 4 depends on Step 3 passing at 100% traffic for one week.

5. **Run one sign-up conversion probe, capped.** Ship one change to the sign-up form, for example fewer fields, behind an A/B split. This is a Complex task, because the effect on users shows only after the trial, so leverage here is a guess. Run it in parallel with Steps 3 and 4 with a budget of one iteration. Kind: stochastic. Acceptance test, written first: metric is the account-created rate per form view; baseline is the current 4-week rate measured in Step 2's timeline; pass threshold is a relative lift of 10%; sample size is 2,000 views per arm or two weeks, whichever comes first; stop condition is a drop greater than 5% at 500 views per arm.

# Follow-up

Conditions that change the recommendation:

1. If A1 is false (for example a server-rendered monolith), replace Steps 3 and 4 with a framework-native token library and keep the same test pattern.
2. If A2 is false (a different funnel step is "sign-up"), rerun Step 5 against that step with the same thresholds.
3. If any login path needs instant revocation of single users (for example payments compliance), hold at Step 2 and re-score using the session-plus-cache alternative.

Questions (answers change Step 5 and A3):

1. What is the current sign-up conversion rate and its main drop-off step? The answer sets the probe's baseline and target.
2. Is a forced re-login of all users acceptable at cutover? The answer decides whether Step 4 needs a silent session-to-JWT exchange first.
