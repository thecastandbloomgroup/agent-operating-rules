# Headline

Adopt one automated SQL formatter with a checked-in configuration, and the formatting disputes stop because the tool decides, not the people.

1. The friction comes from an undecided style choice, not from culture [judgment].
2. An auto-formatter removes the decision from review, so no one argues for or against a style.
3. Enforcement in continuous integration makes the style costless to follow and free to review.
4. The real culture work is one team decision: pick the tool and accept its output.

# Background

The team disagrees on SQL formatting, and reviewers raise it in every review. The request asks to fix the culture problem.

# Relevance

Style disputes consume review time and create personal friction. An automated decision ends them at the source, usually within one week.

# Information

**Evidence.** Studies of code review find that style comments are the most common review friction and add no defect detection [1] [2]. Formatters ended analogous disputes in other languages: Go ships `gofmt` as the single standard, and its designers report that format arguments in Go reviews largely vanished [3]. Baseline comparison: zero team decisions today versus one team decision after adoption [judgment].

**Reframe.** Disagreement over taste is normal and healthy. The failure mode is leaving taste decisions to individuals during review. That is a process gap, not a character flaw in the team [judgment].

**Assumption log.**

A1. The team writes standard SQL against one main dialect. Why not measured: the material does not state it. Validate by: ask which database the team uses. If wrong: pick a formatter with dialect support, for example sqlfluff, or run one per dialect.

A2. Code review happens in a shared platform with CI (continuous integration) available. Why not measured: the material does not state it. Validate by: check the repository for a CI configuration file. If wrong: enforce with a pre-commit hook instead.

A3. At least one team member can configure tooling. Why not measured: the material does not state it. Validate by: confirm in the team channel. If wrong: pair with a colleague or contractor for Step 2.

A4. Existing SQL files can be reformatted in one bulk commit. Why not measured: the material does not state repository size. Validate by: run the formatter on one directory first. If wrong: reformat per directory over several sessions.

**Alternative considered.**

Write a style guide document by consensus instead. This loses because guides rely on memory and reviewers still judge compliance by eye, so the same disputes return [1]. A formatter enforces the same decision at zero review cost.

Confidence: likely (over 66%) that tooling ends the disputes, based on the gofmt precedent and review-friction research. The residual risk is a team member who keeps style comments after adoption; Step 5 addresses that.

# End

I recommend that we take these five steps, in order.

1. **Pick the formatter (decision, evaluative).** Book one 45-minute team session. Rubric first, weighted Kepner-Tregoe style [4]: dialect support 40%, configurability 20%, CI integration 20%, team familiarity 20%. Candidates: sqlfluff, sqlfmt, pgFormatter. Pass threshold: one tool scores over 70 out of 100 and no veto. Evidence per criterion: each tool's documentation and a 5-minute trial on a real query. Cynefin domain: Complicated, because analysis of known options picks the practice. Blocker removed: the open style question.

2. **Configure and apply (deterministic).** Commit a formatter configuration file, then bulk-format all SQL in one commit. Gherkin test, written first:
   - Given a clone of the repository,
   - When the formatter runs in check mode,
   - Then it exits with zero violations.
   Cynefin domain: Clear, because the formatter documentation gives one command for each action. Blocker removed: inconsistent existing files. Step 2 MUST NOT start until Step 1 passes.

3. **Enforce in CI (deterministic).** Add a CI job that fails pull requests with unformatted SQL. Gherkin test:
   - Given a pull request with a style violation,
   - When CI runs,
   - Then the job fails with a message that names the fix command.
   Cynefin domain: Clear, because every CI platform documents status checks. Blocker removed: relying on reviewer memory. Step 3 MUST NOT start until Step 2 passes.

4. **Rewrite the review norm (evaluative).** Update the review guide with one line: formatting comments are out of scope because the formatter owns style. Rubric: the guide contains the rule (50%) and the team lead confirms it aloud in the next review (50%); pass at 100%. Cynefin domain: Clear, because one norm with one owner is a known practice. Blocker removed: the social opening for style debate.

5. **Probe the residual friction (stochastic probe).** Track formatting comments per review for four weeks. Acceptance test stated first: metric is style comments per pull request, current baseline measured in week zero [to be measured], pass threshold is under 5% of reviews, sample size is all reviews in the four weeks. Cynefin domain: Complex, because the effect on team behavior shows only after the trial [judgment]. Budget: the tracking takes five minutes per week. Stop condition: if the threshold fails at week four, run one retrospective on why, not a new tool debate.

If A1 is false and the team uses two dialects, replace Step 2 with one configuration per dialect and run both checks in Step 3.

# Follow-up

Condition that changes the recommendation: if a team member rejects any automated formatter on principle, Steps 1 and 4 become the whole intervention, and the dispute moves from style to team governance.
