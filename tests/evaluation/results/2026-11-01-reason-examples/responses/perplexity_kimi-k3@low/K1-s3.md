## Headline

The pool size cut (50 to 8) in config/db.yaml is the root cause, made worse by the cache TTL cut (300 s to 60 s); restore the pool size and TTL.

1. Pool rejections are the bottleneck: db.pool.acquire rose from p95 3 ms to 690 ms, while query times stayed flat [2][3].
2. The new pool admits 8 connections for 32 worker threads, so up to 24 threads wait per pod [1][2].
3. The TTL cut raised the cache miss rate from 12% to 31%, increasing demand on the smaller pool [3].
4. The ORM change is not the cause: both order and order_lines query times are unchanged [3].

## Background

API p95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed the pool config, cache TTL, and the ORM query. Logs, traces, and the diff cover 2026-10-20 (before) and 2026-10-22 (after).

## Relevance

Each hour the release runs, the service returns about 0.40% errors, almost all pool timeouts [3]. The risk grows at any traffic peak above 405 requests per second.

## Information

Evidence, quantitative:

- Pool acquire p95 rose from 3 ms to 690 ms; this span alone explains most of the 900 ms total [3, traces.txt].
- Cache miss rate rose from 12% to 31% after TTL dropped from 300 s to 60 s [2][3].
- Pool exhaustion warnings: none on 2026-10-20, then 1,800 to 2,400 per hour on 2026-10-22 [1, logs.txt].
- Active DB connections peaked at 8 after the release, against 31 before [3].
- Query times are stable: orders p95 52 ms before, 58 ms after; order_lines 30 ms before, 26 ms after. Therefore the selectinload change did not slow the path [3].
- Throughput is flat (410 vs 405 requests per second), so the change is not from higher load [3].

The arithmetic: 32 workers per instance set, but only 8 connections per pod. When a worker waits on a query and another cache-missed request arrives, it queues. With acquire_timeout_s cut from 30 to 5, queued requests fail after 5 s instead of waiting [2, release.diff]. So three of the four config changes point in the same direction.

Assumption log:

A1. The OPS-412 ticket limit of 8 connections per service was correct, but the app-level pool setting of 8 per pod (4 pods, 32 connections possible intent) was misread. Why not measured: the material does not state the ticket terms. Validate by: read ticket OPS-412 and the DB max_connections setting. If wrong: keep pools at 8 per pod and instead reduce concurrency or add capacity.

A2. Cache TTL of 60 s was not a deliberate freshness requirement. Why not measured: the diff commit message covers only db.yaml. Validate by: ask the release owner. If wrong: keep TTL at 60 s and raise pool size only.

Alternative considered: blame the ORM selectinload change and revert it. It loses because both query spans are unchanged between windows (58 ms vs 52 ms p95) and DB CPU is flat at 38% to 41%; the load the queries create is not the problem, connection supply is [3].
