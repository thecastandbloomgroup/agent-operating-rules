Headline

Split this work into two streams: a deterministic JWT migration with rollout gates, and a separate capped experiment for sign-up conversion.

1. The migration is a known-pattern change; run it stepwise with a rollback flag.
2. The conversion goal has no metric or baseline, so it needs a probe, not a commitment.
3. Doing both in one release couples a security change to a UX guess and blocks rollback of either.

Background

The auth service currently uses server sessions. The request asks to move to JWT (JSON Web Tokens) and to improve sign-up conversion in the same effort.

Relevance

Coupling these changes means a conversion regression could force a rollback of the security migration, or vice versa. Separating them protects both.

Information

Evidence and assumptions:

- A1. Session store exists and token invalidation on logout matters. Why not measured: the material does not state it. Validate by: read the session module and logout endpoint. If wrong: Step 3 below changes.
- A2. No stated conversion metric or baseline. Why not measured: the material does not state it. Validate by: query analytics for sign-up completion rate. If wrong: probe in Step 4 uses the real baseline.
- JWT best practice: short-lived access tokens plus refresh tokens, per the OAuth 2.0 guidance [1]. Storing tokens in cookies mitigates XSS theft compared with localStorage [2].
- Refresh token rotation limits replay risk [1].
- Alternative considered: keep sessions and only improve conversion. It loses because the user explicitly wants the JWT migration [judgment].

End

I recommend that we:

1. Inventory the session code and write contract tests for login, logout, and refresh. Blocker removed: no regression safety net. Test (deterministic): Given a valid credential, When login is called, Then a session-independent response schema is returned. Cynefin: Clear, because the endpoints have one known behavior each.
2. Implement JWT issue and verify behind a feature flag, with refresh rotation per [1]. Blocker removed: sessions block stateless scaling. Test (deterministic): Given the flag on, When a request carries a valid token, Then access is granted; Given an expired token, Then a 401 is returned. Cynefin: Clear, because the library docs give one verification path.
3. Run dual-auth (session and JWT) for one deploy, then cut over when Step 2 tests pass and error rate stays under 0.1% of requests. Blocker removed: no safe rollback. Test (deterministic): Given the cutover, When traffic runs one hour, Then error rate versus the prior week differs by less than 0.1%. Step 3 MUST NOT start until Step 2 tests pass. Cynefin: Complicated, because analysis of logs picks the cutover moment.
4. Run one safe-to-fail probe on sign-up (for example, fewer form fields). Metric: completion rate; baseline from analytics; threshold: +5% relative at n = 2,000 visitors; budget: two weeks; stop condition: completion drops 3%. Cynefin: Complex, because the effect on users shows only after a trial. Leverage here is a guess.

Follow-up

- Open question: what is the current sign-up completion rate? The answer sets the probe baseline in Step 4.
