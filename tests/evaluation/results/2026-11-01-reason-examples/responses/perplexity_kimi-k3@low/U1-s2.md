# Headline

Isolate the failing tests, then collect failure data before any fix, because a flaky build without data gets random fixes.

- A "flaky" build fails without code changes, so the first blocker is no failure evidence.
- Retry and quarantine stop the bleeding, but only measured root-cause fixes reduce flakiness.
- Three assumptions below stand in for missing context (see Section 5.2 in Information).

## Background

The report is one sentence: the build sometimes passes and sometimes fails. No CI system, language, test suite, or failure rate was given. A workaround is needed until details arrive.

## Relevance

A flaky build erodes trust in every signal the pipeline sends. Teams then merge broken code or re-run jobs blindly. Fixing it restores the pipeline as a gate.

## Information

**Evidence**

- Typical CI flakiness rates above 1% of runs correlate with developers ignoring failures [1]. This is tertiary only; treat it as a starting baseline, not a target.
- No failure logs, failure rate, or test list was provided, so root cause is unknown [judgment].

**Assumption log**

A1. The build runs on a hosted CI system with re-run and test-history features. Why not measured: the material does not state it. Validate by: ask which CI system is in use. If wrong: Step 1 changes tool, not order.

A2. Flakiness comes from tests, not infrastructure. Why not measured: no logs were provided. Validate by: check whether failures cluster in the same tests. If wrong: shift Steps 3 and 4 to agent or network fixes.

A3. The team can change the pipeline. Why not measured: the material does not state it. Validate by: check repository permissions. If wrong: escalate before Step 1.

**Alternative considered**

Re-run failed jobs automatically and move on. This loses because it hides the failure signal and does not reduce the failure rate [judgment], and it costs compute on every flake [1].

## End

I recommend that we:

1. **Tag each failure with its test name and log in a shared list.** Blocker removed: no failure data. Domain: Clear, because every CI system exposes a failure log per run. Test (deterministic):
   - Given one week of builds,
   - When each failure is logged with test name and timestamp,
   - Then the list shows a failure rate per test with units of failures per 100 runs.
2. **Quarantine the top offenders**: mark them non-blocking but still run them. Blocker removed: red builds block merges. Domain: Complicated, because the quarantine threshold needs analysis of the Step 1 data. Test (deterministic):
   - Given the failure-rate list from Step 1,
   - When tests above 5 failures per 100 runs are quarantined,
   - Then the main pipeline passes on unchanged code for 20 consecutive runs. Step 2 MUST NOT start until Step 1 finishes.
3. **Fix the most common root cause found in the Step 1 logs** (timing waits, shared state, or network calls). Blocker removed: the dominant flake source. Domain: Complicated, because log analysis picks the practice. Test (deterministic):
   - Given a fixed test,
   - When it runs 100 times on one change set,
   - Then zero failures occur.
4. **Add a flake metric to the weekly report.** Blocker removed: no guard against regression. Domain: Clear, because a failure-rate chart is one standard practice. Test (deterministic):
   - Given four weeks of data,
   - When the report runs,
   - Then the overall flake rate is stated and stays under 1 per 100 runs.

## Follow-up

Open question 2: what is the current failure rate per 100 runs? The answer sets the quarantine threshold in Step 2.
