# A flaky build gets a fix sequence: classify the failures first, then quarantine, then fix, then verify

Support points:

1. Most flaky builds trace to three failure classes: order dependence, shared state, and timing waits [judgment].
2. Classification decides the fix practice, so it comes before any edit [1].
3. Quarantine restores merge reliability today, while fixes land over the next sessions.
4. A repeat-run check proves each fix with a pass rate, not with a single rerun.

## Background

The request states two words: the build is flaky. No logs, no tool names, and no failure samples are in the material. A flaky build means: the same code passes and fails across runs [no source].

## Relevance

Flaky runs block merges and hide real regressions behind random noise [1]. The quarantined tests stay merged because the gate ignores them, so fix speed matters.
