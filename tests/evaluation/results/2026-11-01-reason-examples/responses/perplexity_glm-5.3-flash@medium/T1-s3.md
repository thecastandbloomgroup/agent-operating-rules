Headline

The reviewer friction is a tooling gap, not a values dispute about format. Format choices have no measurable output, so debate between people has no winner. The fix is to move the decision from people to a formatter plus a merge gate. Four moves: commit one formatter config, gate merges on it, trial it once, and end format comments in review.

Background

The team writes SQL without a shared format. Each review reopens the debate, and no one accepts another person's style [per the request]. The debate repeats because the decision has no owner.

Relevance

Every future SQL review spends the same time on format until a gate exists. The first gate merges that time out of the next Pull Request.

Information

Evidence and analysis:

- Formatting taste is subjective, so human review cannot settle it. A formatter gives the same output for the same input, so it settles it by construction [1]. [inference]
- An anti pattern here is a style guide with manual enforcement. It keeps the same debate in every review, because each reviewer re-applies the rules by hand [2]. [judgment]
- Trial structure: one sprint of use, then one adjustment pass. The effect of a rule set on reviewer acceptance shows only after use [3]. [inference]

Assumption log:

- A1. The repos use one SQL dialect, or one dialect each. Why not measured: the material does not name the database. Validate by: list dialects in the repo config. If wrong: set one formatter config per repo.
- A2. A CI pipeline with required checks exists. Why not measured: the request does not say. Validate by: check the pipeline settings. If wrong: use a pre-commit hook as the gate instead.
- A3. Reviewers will accept a rule they did not pick. Why not measured: no tool can reach it. Validate by: the trial in Step 3. If wrong: run a vote on the two or three disputed rules only.

Alternative considered

Adopt a written style guide and enforce it by review. It loses because it keeps the per-review debate; the gate ends it once [judgment].

End

I recommend that we:

1. Commit a formatter config (SQLFluff or equal) with the dialect and rules locked. Blocker removed: no single format exists. Classification: deterministic. Test, written first:

   ```gherkin
   Given a .sql file in the repo
   When the formatter runs twice on it
   Then the two outputs match and the lint check passes
   ```

   Domain: Clear, because the tool returns one output for one input, per its specification [1].

2. Add a lint step to CI that blocks merge on format errors. Depends on Step 1: the config must exist first. Blocker removed: nothing enforces the format. Classification: deterministic. Test:

   ```gherkin
   Given a Pull Request with an unformatted .sql file
   When the lint step runs
   Then the build fails with the rule name in the output
   ```

   Domain: Clear, because the gate applies one known rule to every merge.

3. Run the new format on a branch of real queries for one sprint. Measure disputed rules. Adjust the config once, then lock it. Blocker removed: untested rules erode trust in the gate. Classification: stochastic, because reviewer reaction varies. Acceptance test, written first: metric = disputed rules; baseline = the full disagreement at start [judgment]; pass threshold = fewer than 3 disputed rules [inference]; sample = 20 formatted queries. Domain: Complex, so this is a capped probe: budget 5 working days, stop when the threshold fails twice. Run it in parallel with Step 4.

4. Publish one review rule: no comment on format; the gate owns it. Add it to the Review template. Depends on Step 3: publish only the locked config. Blocker removed: reviewers relitigate format from habit. Classification: stochastic, because comment behavior is human. Acceptance test: metric = comments on format per SQL Pull Request; baseline = the current count, measured over the last 10 SQL Pull Requests [inference]; pass threshold = 0 at that sample [judgment]. Domain: Complex, so cap it: check at a review of 10 Pull Requests, stop and revisit if comments persist.

Follow-up

Conditions that change the recommendation:

- If A2 is false, replace Step 2 with a pre-commit hook plus a check.
- If the repos mix dialects, set one config per repository.
- If the trial keeps the same disputed rules, replace Step 3 config choices with a team vote.
