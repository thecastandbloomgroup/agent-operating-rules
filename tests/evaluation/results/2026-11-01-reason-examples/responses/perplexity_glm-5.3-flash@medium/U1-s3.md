## Headline

Label each failure as flaky or real with a rerun check, quarantine the worst tests, then fix root causes. Do not mask failures with silent retries.

Supporting points:
1. The request gives no failure data, so the flake rate and the causes are unknown.
2. A rerun and count probe turns unknown failure modes into measured data.
3. Quarantine restores trust in the main branch while fixes proceed.
4. Fixes target the top tests by measured flake rate, not by guesswork.

## Background

The build fails in ways that do not repeat. The request includes no logs, no CI tool name, and no failing test names.

## Relevance

A flaky build erodes trust in the branch gate. Developers then ignore red builds, and real faults merge. Google reports this pattern and manages it at scale with rerun detection and quarantine [1].

## Information

Evidence the plan depends on:
- Rerun-based detection and quarantine are the core practice Google reports for flaky tests at large scale [1].
- A test that fails only sometimes is stochastic, so counting failures across many runs is the only direct measure of flake rate [judgment].
- One clean rerun does not prove a test is stable, because a flaky failure can pass on retry [inference]. This is why the probe counts over many runs.

Assumption log:
- A1. Failures come from test flakiness, not from a broken shared dependency. Why not measured: the material does not include logs. Validate by: read the last failing job's log. If wrong: the fix targets infrastructure, not tests.
- A2. The CI system can rerun a failed job or test on demand. Why not measured: the CI tool is not stated. Validate by: check the CI config for a retry or rerun option. If wrong: rerun failing tests twice inside one job script.
- A3. The main branch merges only on green. Why not measured: the material does not state branch rules. Validate by: read the branch protection settings. If wrong: quarantine loses part of its value.

Confidence: high for the overall plan because it follows one documented large-scale practice [1]; both plan and sequence depend on A2.

Alternative considered: silent retries, where every failed job reruns until green with no label. It loses because an unlabelled retry hides real faults and delays root cause work [1].

## End

I recommend that we take these actions, in this order:

1. **Label failures with a rerun probe** (stochastic test, Cynefin: Confused). Increment: configure each failed test to rerun up to 9 times, and record the pass count per test. Blocker removed: the unknown flake rate, which blocks every later step. Test first, as an acceptance test: metric, labeled share of failures; baseline, 0%; pass threshold, 95% labeled; sample size, 30 CI runs. Stop condition: end the probe after 30 runs or one week, whichever comes first. Cause and effect: we cannot tell the domain yet, so this probe first classifies the problem [3].

2. **Quarantine tests above the threshold** (deterministic test, Cynefin: Clear). Increment: move every test with 3 or more failures in the 30-run sample out of the required path. Blocker removed: red main branches that do not indicate real faults. Test written first:

   ```gherkin
   Given a test with 3 or more failures in the 30-run window
   When the CI gate runs
   Then the test is excluded from the required path
   And the build passes without it
   ```

   Cause and effect: one written rule decides the outcome for everyone [2]. This step MUST NOT start before the probe in Step 1 has 30 recorded runs.

3. **Fix the top three quarantined tests** (deterministic test, Cynefin: Complicated). Increment: for each test, run a root cause review, then apply one fix, such as replacing sleep waits with event waits. Blocker removed: the largest source of false failures. More than one practice can fit, so the review picks one per test [2]. Each fix ships with its own Given, When, Then test that fails before the fix and passes after. This step MUST NOT start before the probe in Step 1 has 30 recorded runs.

4. **Publish a flake rate report on every run** (deterministic test, Cynefin: Clear). Increment: add a report job that lists each test with its pass rate over the last 30 runs. Blocker removed: invisible regressions after the fixes. Test written first:

   ```gherkin
   Given a finished CI run
   When the report job runs
   Then it lists each test with its pass rate over the last 30 runs
   ```

   Cause and effect: a fixed reporting rule, applied by the CI worker. This step can run in parallel with Step 2 and Step 3.

## Follow-up

Conditions that change the recommendation: if A2 is false, replace Step 1 with manual reruns of failing tests inside one job script. If A1 is false, stop quarantine work and fix the shared dependency first, because retrying cannot fix it.
