## Background

The team runs retrospectives, and people attend. Agreed changes do not reach the work, so the meeting now costs one team hour and returns nothing [per your query]. The request asks for a way to make the meeting produce shifts again.

## Relevance

Every wasted retro also weakens trust in the format, so attendance is the next thing at risk [judgment]. A working loop pays back within 3 cycles because shipped changes remove work rather than discuss it [judgment].

## Information

The failure has three candidate modes. They do not overlap, and together they cover the whole path from talk to shift [judgment]:

1. No action is agreed; the retro produces talk only.
2. An action is agreed, but it has no named owner or no date, so it is unassignable.
3. An action has an owner and a date, but the owner is blocked, and the block never surfaces because nothing reviews it.

Your report sets the baseline at zero changes shipped in recent cycles [per your query]. Therefore the first question is which mode holds, because mode 1 needs a tighter discussion, mode 2 needs a closing step, and mode 3 needs a status review. One count over past retro records answers this in one hour [judgment]. We assume the records exist; A1 covers the risk.

**Alternative considered**

## End

I recommend that we classify the failure, probe a tight loop, and review status in that order.

1. **Classify the failure mode.** This week, review the last 6 retro documents in one working session. Score each document against this rubric; the method follows Kepner-Tregoe decision analysis [15]:
   - Action written (weight 0.4). Evidence: the document holds at least one action line.
   - Owner named (weight 0.3). Evidence: a person is named per action.
   - Shipped (weight 0.3). Evidence: the product or process shows the change done.
   - Scoring: 1 present, 0 absent. Pass threshold: a retro passes at 1.0. The count mode is the output; the criterion with the most zeros names the failure mode.
   - Blocker it removes: a fix aimed at the wrong step.
   - **Confusion**, because the query does not say which step fails, and this review produces the classification that the rest depends on.

2. **Probe a tight loop.** For 3 retros, end each one with exactly one change, one named owner, and a date within 7 days. Metric: changes shipped per cycle. Baseline: zero, per your report. Pass threshold: at least 1 shipped in 2 of 3 cycles. Sample size: 3 retros. Budget: 3 retros, no more. Stop condition: no owner assigned in the first 2 retros. **Complex**, because the effect on team behavior shows only after a trial [18]; the listed leverage is a guess.
   Step 1 MUST finish before this probe starts, because the mode found there changes the probe detail.

3. **Open each retro with the last retro's change.** Start this step with the first probe retro; it MUST NOT run before Step 2 because the status depends on it. Write and pass the test before the first use:
   ```gherkin
   Given the change with owner and date from the last retro
   When the next retro opens review
   Then the team marks that change done or not done,
   and records a new date or a block reason when not done
   ```
   **Clear**, because the practice is one fixed step for every retro.

4. **Conditional step: replace the format if the probe fails.** If Step 2 misses its threshold, run cause analysis on one incident per retro: ask "why" up to 5 times, then choose the change from the last "why". Test: the chosen change answers the last "why"; evidence is the written note; pass is yes or no. **Complicated**, because expertise picks the cause, and more than one good practice fits each incident.
