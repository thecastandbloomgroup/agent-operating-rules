# Headline

Migrate the auth service to short-lived JWT access tokens with rotating refresh tokens, and roll the token change out behind a flag while you fix sign-up conversion with measured A/B probes; do not bundle the two changes into one release. Supporting points:

1. JWT migration has a known, testable path; conversion improvement does not, so conversion needs a baseline first.
2. The two changes must ship separately, because a combined release cannot show which change caused a metric move.
3. State alone, JWT cannot be revoked before expiry, so the design needs refresh rotation and a revocation check.
4. Both requests lack inputs, so the plan below runs on logged assumptions and three listed questions.

# Background

The auth service today keeps state server-side in sessions. The request adds two goals: move to JWT, and improve the rate at which sign-ups complete.

# Relevance

Tokens change the security model, and a bad token design locks users out or lets stolen tokens live too long. Conversion is unmeasured, so any change today cannot be validated.

# Information

**What JWT changes.** A JWT is a signed, self-contained token that carries claims [1]. Because the token is self-contained, the server can verify it without a session store, hence the migration benefit. The same property is the cost: the server cannot revoke it before expiry, so the standard answer is a short access token life, a refresh token with rotation, and a revocation check at issue time [2].

**What conversion needs.** No baseline data exists in the material. Theme from the source guidance: validated conversion work requires a measured baseline and one variable per test [2]. Sources that agree: [2]. Any design without that baseline rests on [judgment] only.

**Alternative considered.** Keep sessions and only fix sign-up. This loses on the stated goal, and it wins if the service is single browser client with one instance, because sessions are revocable and simpler [judgment]. The migration is about as likely as not (50%) to be required rather than chosen for style; the questions in Follow-up settle this.

**Assumption log.**

- A1. Web browsers are the main client. Why not measured: the material does not state it. Validate by: read the client list in the service config. If wrong: mobile clients need secure token storage, and Step 3 changes. Unlikely to flip the plan, roughly 80% likely correct [judgment].
- A2. No SSO or external identity provider exists behind the service. Why not measured: the material does not state it. Validate by: search the code for IdP configuration. If wrong: wrap the provider session with tokens instead of replacing it.
- A3. Sign-up conversion is not measured today. Why not measured: no analytics output was provided. Validate by: query the funnel in Step 1. If wrong: skip the baseline task.

# End

I recommend that we run these steps:

1. **Measure the funnel baseline.** Increment: one analytics query, one session of work. Blocker removed: unvalidated conversion claims. Cynefin: Confused, because no data exists to classify the conversion problem. Test (stochastic, state before work): metric is the sign-up completion rate. Baseline: today, unknown, recorded in Step 1. Pass threshold: rate recorded with a 95% interval half-width of 5 percentage points or less. Sample: 300 funnel entries.
2. **Build the token service.** Increment: issue and verify tokens for one endpoint. Blocker removed: no token path exists. Cynefin: Complicated, because more than one good practice exists (rotation plus denylist), and analysis picks between them [2]. Test (deterministic, Gherkin, write first, per [14]):
   ```gherkin
   Given a user with a valid refresh token
   When the user presents it at the rotate endpoint
   Then the service issues an access token that expires in 15 minutes
   And the service marks the old refresh token as used
   ```
3. **Roll out tokens behind a flag.** Increment: dual runtime, one client cohort on tokens. Blocker removed: forced logout of all users. This step MUST NOT start until Step 2 passes its test. Cynefin: Clear, one known practice: keep both runtimes valid and move cohorts [2]. Test (deterministic, Gherkin, write first):
   ```gherkin
   Given the flag routes cohort B to tokens
   When a cohort A user reopens the app
   Then the session survives and no re-login is required
   ```
4. **Run two conversion probes in parallel.** Increment: probe 1 removes every optional form field; probe 2 adds one social sign-in button. Blocker removed: untested conversion guesses. Cynefin: Complex, because the effect on completers shows only after a trial, so each probe is safe to fail with a budget [18]. Test (stochastic, per probe, state before work): metric is the sign-up completion rate from Step 1. Baseline: the see Step 1 value. Pass threshold: a 2 percentage point lift [judgment]. Sample: 2,000 sign-ups per arm. Budget: 4 weeks. Stop condition: completion drops 2 points, revert the probe.

Steps 2 and 3 can run while Step 1 collects data. Ship no joint release of Steps 3 and 4.

# Follow-up

Questions (answers set the design in Steps 1 and 3):

1. Which client types call the auth service? Answer decides cookie versus header token storage. Applies to Step 3.
2. Is an SSO or external identity provider in the path? Answer decides whether to replace or wrap sessions. Applies to Step 2.
3. How many sign-ups per week reach the funnel? Answer decides whether a 2,000-per-arm sample is reachable within 4 weeks. Applies to Step 4.

Condition that changes the recommendation: if Question 1 and 2 reveal a single browser client with no SSO, replace Steps 2 and 3 with an access audit of the session store, because the migration then adds cost with no reach.
