## Background

The request covers two systems: the sign-in path, which uses server-side sessions, and the sign-up page, which has a stated conversion problem. Conversion means the share of visitors who finish sign-up. The material provided contains no code, no traffic data, and no funnel metrics.

## Relevance

Both changes touch the same sign-in and sign-up path. A bad cutover can lock users out, and a guess at the conversion cause can waste a whole sprint.

## Information

**Evidence.** A JWT is a signed token that carries claims such as a user id and an expiry [1]. Verification is local, so the auth service needs no shared session store [1, inference]. RFC 9700 requires refresh tokens for public clients to be one-time use or sender-constrained [2]. A 15 minute access token balances token exposure against re-sign-in cost [judgment]. Storing tokens in an HttpOnly secure cookie keeps them out of page scripts [judgment]. No material describes the sign-up funnel, so every cause claim in the conversion track is [judgment].

**Confidence.** The migration plan: high confidence, because it rests on two published standards plus a capped probe before any commit. The conversion cause: not known, and Step 1 below decides it.

Issue an access token with a 15 minute expiry [judgment], rotate refresh tokens on use [2], and verify signatures at the gateway. This removes the shared session store dependency, so the auth service can scale without shared state.
   ```gherkin
   Given a sign-in with valid credentials
   When the token endpoint responds
   Then the access token verifies and expires after 15 minutes
   And reuse of a rotated refresh token is rejected
   ```
   Step 3 waits on this step.

3. **Probe JWT with one cohort (Complex, stochastic).** The effect on real traffic shows only after the run, so the leverage estimate here is a guess. Route a capped 5% of new sign-ins to JWT, with a budget of one week. This proves the path under real load before any commit. Acceptance test: metric, sign-in failure rate; baseline, the current session failure rate; pass, no more than baseline plus 0.2 percentage points; sample size, 2,000 probe sign-ins. Stop condition: roll the cohort back the day a breach appears. Step 4 waits for a pass at full sample size.

4. **Cut over (Clear, deterministic).** One known practice applies: enable at 100% traffic, keep session validation for one refresh cycle, then disable the session store in the next release. This completes the migration and ends the dual-path cost.
   ```gherkin
   Given the flag is set to 100% and 24 hours pass
   Then session writes equal zero
   And the sign-in failure rate stays at or below the baseline
   ```

5. **Fix conversion by selection, then capped experiments (split: 5a evaluative, 5b Complex).** Part 5a: score the funnel drop points on a rubric before any design work. Criteria and weights: drop size 0.4, visitor volume 0.3, build effort 0.3; evidence, the dashboard from Step 1; pass threshold, a total score of 3 or more out of 5, Kepner-Tregoe layout [judgment]. Part 5b: launch at most three bounded probes, each capped at one week and 10% of traffic [judgment], and never at the same time as a JWT probe on the same step. Acceptance test per probe: metric, sign-up success rate; baseline, the Step 1 dashboard; pass, a rise of at least 0.2 percentage points; sample size, 5,000 visits per probe [judgment]. This targets the measured blocker instead of the assumed one.

Condition that changes this plan: if Step 1 shows no drop point above 10% of visitors at any step, stop the conversion track, because the page is not the problem. If A3 is false, extend the probe window to four weeks and keep the sample bar fixed.
