**Background**

The user reports p95 API latency of 900 ms, up from 120 ms, after release 2026.10.21. The attached logs, traces, and diff cover the ORM layer, cache config, and connection pool.

**Relevance**

Error rate is up 20 times to 0.40%, and 96% of errors are pool timeouts [1]. Fixing the pool returns both latency and errors to baseline in one config change.

**Information**

First, the evidence. The traces show the regression sits in db.pool.acquire. Its p95 rose from 3 ms to 690 ms; every other span moved by 5 ms or less [1]. The logs support this with 1,800 to 2,400 "pool exhausted" warnings per hour on 2026-10-22, versus none on 2026-10-20 [2]. The diff names the change: max_size 50 to 8, timeout 30 s to 5 s [3]. Therefore 32 workers now share 8 connections per pod.

Second, the database is not the constraint. Peak CPU was 38% before and 41% after [1]. Peak active connections fell from 31 to 8 because the pool caps them [1]. So the pool, not the server, is the bottleneck.

Third, a secondary contributor. Cache TTL fell from 300 s to 60 s [3], and the miss rate rose from 12% to 31% [1]. This adds database reads and waiters, because each miss sends one query into the pool. cache.get latency stayed flat at 2 to 5 ms, so the cache itself adds no latency.

Confidence: high. Three independent measurements agree; traces, logs, and the diff point to the same cause.
