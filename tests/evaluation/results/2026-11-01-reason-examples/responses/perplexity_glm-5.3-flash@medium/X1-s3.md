## Headline

Track errors before changing the prompts: add reason codes, a weighted rubric, a frozen test set, and a weekly score.

1. The agent report "sometimes wrong" has no numbers behind it, so step one captures the error types.
2. A weighted rubric turns those tags into criteria, weights, and a pass threshold.
3. A frozen test set makes that score repeatable across prompt versions.
4. Prompt fixes then run as small tests against a measured baseline.

## Background

A language model (LLM) now writes a summary for each support ticket. Agents judge the summaries as "sometimes wrong". The request states that no metrics exist.

## Relevance

Without a number, each prompt edit is a guess [judgment]. A shared error score also shows agents that their reports change results, which protects trust in the tool [judgment].

## Information

**Quantitative evidence**: none exists yet, because no metric was captured. This gap makes the first step a measurement step [judgment].

**Qualitative evidence**: the agent report is one statement with no detail, so thematic grouping of error tags is needed [3]. Strong judge models show high agreement with human raters on open-text quality, so judge-assisted scoring can support human labels, not replace them [1].

**Quality criteria**: ISO/IEC 25010 lists accuracy among software quality characteristics, and the rubric below maps that set to summarisation [2].

**Domain law**: where an effect shows only after a trial, the work is Complex and needs a capped probe with a measure and a stop condition [3].

**Confidence**: high confidence that the measure-first order is correct, because three facts point the same way: no metrics exist, the agent report lacks detail, and prompt edits are hard to check once agents adapt around them [judgment].

### Assumption log

A1. Summaries are read by agents only, not passed to customers. Why not measured: the material does not state it. Validate by: check one ticket view in the tool. If wrong: accuracy becomes the first fix target and the customer team is informed.

A2. Agents will tag at least 20 summaries in 10 working days. Why not measured: the material gives no tag volume. Validate by: count tags after 5 days. If wrong: swap Step 1 for a weekly review of 20 random summaries.

A3. The ticket queue holds 60 cases that fit the test set within the time. Why not measured: the material gives no ticket volume. Validate by: sample one week of ticket counts. If wrong: cut the set to 30 tickets and accept a wider uncertainty range.

### Alternative considered

Switch the summariser off until metrics exist. It loses because agents then lose the summary value, and measurement needs live outputs [inference].

## End

I recommend that we run four steps in this order.

**Step 1: capture error types.** Add five one-click reason codes to the summary panel: fact wrong, detail missing, too long, wrong focus, other. This removes the blocker that no error taxonomy exists, so agents can report "wrong" in a form a count can use. Kind: stochastic. Test, written first: metric = share of flagged summaries that carry a code; baseline = 0%; pass threshold = 70%; sample size = 20 flags; budget = 50 tags or 10 working days, whichever comes first. Cynefin: Confused, because the request does not say which error type dominates, and this step gathers the data needed to classify the problem [3].

**Step 2: write the scoring rubric.** Criteria and weights: factual accuracy 0.4, completeness 0.25, focus 0.15, length 0.1, tone 0.1. Pass threshold: 4 of 5 points. Each criterion names its evidence, for example "fact wrong" tag counts for accuracy [2]. Weights are a judgment until the Step 1 tags arrive [judgment]. This removes the blocker that "wrong" has no agreed definition between agents. Kind: evaluative, and the rubric itself is the test, written before any scoring, in the Kepner-Tregoe form [4]. Score 50 tagged outputs with it. Cynefin: Complicated, because more than one weighting fits and analysis must pick one. This step waits on Step 1.

**Step 3: freeze the test set and automate the score.** Select 60 tickets, label the key facts per ticket, and freeze the pairs as a test set. A judge model scores each run against the rubric, and 20 outputs get human checks each month [1]. This adds the capability of a weekly score that any prompt version can repeat. Kind: deterministic. Test, written first:

```gherkin
Given the frozen set of 60 labelled tickets
When a prompt version runs on the set
Then the report shows scores for all five criteria within 10 minutes
```

Cynefin: Clear, because a frozen set plus a script is one known practice [6]. This step waits on the rubric in Step 2.

**Step 4: fix prompts as capped probes.** Target the theme with the highest tag count first, then the next, per thematic grouping [5]. Run the changed prompt on the 60-ticket set. Pass threshold: the fact-error rate falls by one third from the Step 3 baseline, at sample size 60. Budget: two prompt versions before a revert. This removes the largest Q: blocker, the dominant error type itself. Kind: stochastic. Cynefin: Complex, because the effect of a wording change shows only after the run [3]. Step 4 waits on Steps 2 and 3.

Confidence in the method: high, because frozen test sets with human labels are standard practice for text quality [1]. Confidence about which fix matters most: low until Step 1 ends.

- If A1 is false, factual accuracy becomes the top weight in Step 2 and a customer-facing check joins Step 4.
