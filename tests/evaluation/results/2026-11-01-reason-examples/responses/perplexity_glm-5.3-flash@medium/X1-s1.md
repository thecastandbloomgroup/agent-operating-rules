**Headline**

Improve the summariser by measuring it first: label 100 past summaries by error type, then require grounded output and a weekly machine review.

1. An audit of 100 past summaries turns "sometimes wrong" into five counted error rates, and it sets the baseline.
2. A grounded output format links each claim to ticket text, so added facts become detectable.
3. A judge model scored against the human labels keeps the check running after release.
4. A two-week capped agent-feedback probe catches error types that the labels miss.

**Background**

The team added an LLM summariser to the support tool. Agents report that summaries are "sometimes wrong", and no metrics exist. The request is to make the summariser better.

**Relevance**

Without a baseline, every prompt change is a guess, and the next change can erase the last gain. The audit set is the cheapest step that makes quality countable.

**Information**

Three research results shape this plan. First, LLM summaries contain factual errors even when the text reads well [1]. Second, common automatic metrics, such as ROUGE, agree poorly with human judgment of summary quality, so hand labels must set the truth [3]. Third, an LLM judge agrees with human labels in over 80% of cases on benchmark tasks with a defined scale [2]. The error categories used below are: wrong fact, missing fact, added fact, wrong tone or format. The split covers the report of "wrong" without overlap [judgment].

Assumption log:

- A1. "Sometimes wrong" means mostly factual errors, with tonal or omissions reporting errors elsewhere. Why not measured: the material does not state it, and no tool can reach agent intent. Validate by: the Step 1 audit. If wrong: the weights in the Step 1 rubric change to match the top category. Current guess on category mix: about as likely as not (no data yet; the audit replaces this guess).
- A2. A sample of 100 past ticket-summary pairs exists or can be drawn. Why not measured: the material does not state ticket volume or data access. Validate by: attempt the draw at the start of Step 1. If wrong: run the audit on 30 pairs and require 25 of 30 reviewer agreements.
- A3. Agents can give two hours per week during the probe. Why not measured: the material does not state agent workload. Validate by: track time on the first 10 labels. If wrong: cut the probe budget in half.

Alternative considered. An extractive summariser that copies whole ticket sentences is the strongest alternative. It loses a judged comparison: it cannot join information across tickets, and it still needs the same labeled threshold to prove that it is better [judgment].

**End**

I recommend that we run the four steps below, in this order, with each test written before the work.

**Step 1. Label an audit set (Confused, evaluative).** Label 100 past ticket-summary pairs in one working session. Rubric:

- Criteria and weights: wrong fact 0.4, missing fact 0.3, added fact 0.2, tone or format 0.1.
- Pass threshold: two reviewers assign the same category on 80 of 100 pairs.
- Evidence per criterion: the labeled row, with ticket ID, summary quote, and category.

Domain: Confused, because the counted categories decide every later step, and cause and effect cannot be read yet.

**Step 2. Ground the output format (Clear, deterministic).** Change the output spec: every factual claim cites the ticket text it came from, and missing data prints a fixed marker line. Test:

Given a ticket with three facts
When the summariser runs
Then each claim line names the ticket text it came from
And the marker line prints when the data is absent

The test checks structure only, so the same input always produces the same pass or fail. Domain: Clear, because one known practice exists: cite the source per claim.

**Step 3. Add a judge harness (Complicated, stochastic).** Build an automated review that scores each summary against its ticket text, using the same categories. Acceptance test written first: metric = agreement with the 100 human labels; baseline = Step 1 counts; pass threshold = 80% agreement; sample size = 100 pairs. Benchmark results put this threshold within reach [2]. Domain: Complicated, because more than one judge setup fits, and analysis of the sampled agreement picks one.

**Step 4. Probe agent feedback live (Complex, stochastic).** Add a one-click flag button that writes category and ticket ID into the audit set, then run a two-week live trial. Measure flags per 100 summaries per week. Stop condition: stop and re-label if flags per 100 exceed 15 after week one. Budget: 2 agent hours per week. Domain: Complex, because the effect on live quality shows only after the trial, and the leverage here is a guess.

Sequencing: Step 3 MUST NOT start until the Step 1 label set passes its threshold. Step 4 MUST NOT start until the Step 2 format change is live. Run none of these on the full traffic until Step 3 passes.

Condition that changes this plan: if the audit shows tone or format errors above the weight of wrong facts, replace Step 2 with a style guide plus a tone-only rubric at the same pass threshold.
