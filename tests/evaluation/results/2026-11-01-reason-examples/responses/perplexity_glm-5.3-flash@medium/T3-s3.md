## Headline

Migrate behind a dual-run flag with short-lived access JWTs and a refresh token, and treat sign-up conversion as separate measured probes, not as one bundled change.

- Dual-run keeps every old session valid during rollout, so rollback is one config change.
- Access tokens live 15 minutes or less, which bounds the damage window of a stolen token [2].
- Conversion probes wait for funnel baseline data, so they test real drop-off causes, not guesses.

## Background

The request covers two systems: the auth service, which moves from server-side sessions to JWT, and sign-up conversion. The material provides no stack detail, no traffic data, and no funnel data. The plan assumes a typical web backend, and the questions in Follow-up list what to confirm.

## Relevance

A wrong token design can lock every user out, so the migration carries the highest cost of failure. Conversion changes without a baseline cannot show a real lift, so measurement comes first there.

## Information

Evidence and analysis:

- A session keeps state on the server, so logout and revocation act at once [1].
- A JWT is a signed token the client holds; the server verifies it without a lookup [2].
- Because a JWT stays valid until its expiry, the lifetime must be short to bound the window after theft [2].
- OWASP also recommends renewal of the session ID after a privilege change [1].
- A 15 minute access token plus a refresh token is a common practice for web and API clients [judgment].
- Drop-off causes depend on user behavior, so their effect shows only after a live trial [judgment].
- Drop-off answers come from grouping the reason data into themes; thematic analysis is the standard method here [3].

Assumption log:

A1. The service is a web backend with browser or SPA clients, and no mobile apps hold session IDs. Why not measured: the material does not state the stack. Validate by: read the repo and the client inventory. If wrong: the rollout gains a mobile app release cycle, about 1 to 2 weeks.
A2. No sign-up funnel analytics exist yet. Why not measured: the user has not answered. Validate by: query the analytics system for the last 90 days. If wrong: skip Step 1 and move straight to Step 5.
A3. A 15 minute access lifetime fits the service's operations. Why not measured: it depends on ops data the material omits. Validate by: count failed refresh requests in a one week trial. If wrong: change one config value, so the plan holds.

Alternative considered:

A big-bang cutover with long-lived tokens is the strongest alternative. It loses because logout would leave a stolen token valid for weeks [1].

## End

I recommend that we take the following five steps, in this order.

1. Instrument the sign-up funnel with four events: page view, submit, email verify, completion. This adds measurement and classifies the conversion problem. Test:
   ```gherkin

   When a test user finishes sign-up
   Then the dashboard records four events with one shared user ID
   ```
   Domain: Confused, because no data exists yet to classify the drop-off causes.

2. Pick the token design with a scored rubric in one working session. This removes the revocation blocker before any code changes. Rubric: revocation control (weight 3), client impact (weight 2), build effort (weight 1); threshold: the winner leads by 2 points; evidence: [1] and [2]. Domain: Complicated, because several good designs fit and analysis must pick one.

3. Build the JWT path behind a flag: issue, verify, and refresh endpoints. This adds the new capability beside the old one. Test:
   ```gherkin
   Given the JWT flag is on for the account
   When the user signs in with valid credentials
   Then the service returns an access token and a refresh token
   And the old session cookie also stays valid
   ```
   Domain: Clear, because each step follows one known library practice. Deterministic: the test runs first, then the code, then refactor.

4. Roll out to 5 percent, then 50 percent, then 100 percent of traffic, and keep sessions alive for one expiry cycle after. Test: Given 5 percent of traffic on JWT, when the rollback command runs, then all logins return to sessions with zero new lockouts. Domain: Clear, because staged rollout is one known practice. Dependency: Step 4 MUST NOT start until the test in Step 3 passes.

5. Run two conversion probes in parallel with Steps 2 to 4, each capped at 10 percent of traffic and 10 engineering hours. Probe A removes form fields. Probe B moves email verification to after first use. Test: completion rate rises at least 10 percent relative over the Step 1 baseline, with n = 1,000 sessions per arm. Domain: Complex, because the effect shows only after the trial, so these are safe-to-fail probes and the leverage is a guess. Dependency: Step 5 MUST NOT start until the Step 1 dashboard shows a baseline.
