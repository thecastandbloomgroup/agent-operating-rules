## Headline

Roll back the most recent checkout change now, verify recovery with one test purchase, then give the exec call the timeline. The supporting points:

1. Restore service before diagnosis. Mitigation comes first in an outage [1].
2. The most recent change is the first suspect in a sudden full-user failure [1].
3. One test purchase verifies recovery in under a minute.
4. The exec call needs four facts, not root cause.

## Background

Checkout returns HTTP 500 to every user since 09:12. The on-call window is ten minutes before an executive update. The task is to restore service and to report.

## Relevance

Each minute of downtime loses revenue and user trust. The exec call needs an accurate status in ten minutes.

## Information

Evidence:

- Practice from Google SRE: during an emergency, stop the bleeding first, then diagnose [1].
- Sudden failures for all users follow a change far more often than any random fault. Confidence: high, based on the standard on-call practice to check the last change first [1] [judgment].
- A full rollback of a named service runs in minutes. A root-cause search of a 500 spike typically runs for hours without a known trigger [judgment].

Assumptions:

A1. A deploy or config change touched checkout near 09:12. Why not measured: ten minutes leaves no time to scan the change log before acting. Validate by: run the deploy history command for this service, 60 seconds. If wrong: skip the rollback and start the log triage in Step 2.

A2. The rollback is safe and loses no order data. Why not measured: no time for a full diff of the last release. Validate by: read the last change note, 30 seconds. If wrong: shift traffic to the last known-good version instead of a destructive revert.

Alternative considered: keep the broken version live and search for the root cause first. It loses because diagnosis takes hours with no known trigger, and a rollback takes minutes [judgment].
