## Headline

Stop asking people to agree: install one SQL formatter, enforce it in the pipeline, and move reviews to logic only.

- A formatter turns style from a per-review debate into a config file.
- CI enforcement removes the format check from reviewers, so the friction has no place to live.
- A written review rule makes format comments out of scope.
- A four-week probe measures whether the friction falls.

## Background

The team disagrees on SQL formatting, and every review carries format arguments. The request asks to fix this culture problem.

## Relevance

Review time spent on style is time not spent on logic and data risk. Repeated friction also slows merges and pushes people to skip reviews.

## Information

Evidence and analysis:

- Baseline: the request states format friction occurs in every review. That is the number to beat.
- The mechanism: a formatter applies one style without reviewer effort, so the disputed object leaves the review [inference].
- Cultural change shows its effect only after a trial, because behavior shifts after the norm becomes visible in daily work [18].

Assumption log:

A1. The team stores SQL in one shared repository with a CI pipeline. Why not measured: the request does not state it. Validate by: check the repo root for a pipeline file. If wrong: Step 3 becomes a pre-commit hook plus a merge checklist.
A2. The team uses one SQL dialect across the repo. Why not measured: the request does not state it. Validate by: run the formatter's dialect detection on five files. If wrong: weight dialect support triple in Step 1 and ship one config per directory.
A3. "Culture problem" means the recurring review friction the request describes, not a wider conflict. Why not measured: asking costs a meeting the fix can run without. Validate by: one five-minute team question. If wrong: escalate to the team lead for a broader review, because a formatter alone will not solve it.

Alternative considered: hold a meeting and agree on a written style guide without a tool. It loses because eye-based checking is the current failure mode; a guide changes nothing about enforcement [inference].

## End

I recommend that we enforce style with a tool and probe the review norm.

1. Adopt one formatter and one dialect through a scored decision.
   - Increment: complete a Pugh matrix in one session [16]. Criteria and weights: dialect support (3), auto-fix share (3), CI support (2), rule documentation (1). Pass threshold: one candidate wins against the "manual review" baseline.
   - Blocker removed: the "which tool" debate, closed by scoring instead of opinion.
   - Test, written first (evaluative): score each candidate on evidence from a trial run on five real files, then rank.
   - Kind: evaluative. Cynefin domain: Complicated, because more than one tool fits and analysis must pick one.

2. Format every SQL file once with the chosen config.
   - Increment: one commit that reformats all SQL files.
   - Blocker removed: the backlog of mixed styles; after it, new diffs show only logic.
   - Test, written first (deterministic, Gherkin [14]):
     Given the config file at the repo root
     When the formatter runs a second time on the same file
     Then no line changes
   - Kind: deterministic. Cynefin domain: Clear, because the tool manual gives one procedure per run.

3. Block unformatted SQL in CI and pre-commit. Step 3 MUST NOT start until the test in Step 2 passes.
   - Increment: one CI job plus one pre-commit hook.
   - Blocker removed: reliance on reviewer memory; the check moves to the pipeline.
   - Test, written first (deterministic, Gherkin [14]):
     Given a commit with a file that fails the format check
     When the CI job runs
     Then the merge is blocked and the message shows the fix command
   - Kind: deterministic. Cynefin domain: Clear, because the check either passes or fails.

4. Run a four-week probe on the review norm, in parallel with Steps 2 and 3, capped at a 2 hour budget.
   - Increment: add one line to the review template: "format comments are out of scope; the formatter owns style."
   - Capability added: reviewer attention moves to logic and data.
   - Test, written first (stochastic): metric is format-only comments per 10 reviews; baseline is "nearly every review" per the request; pass threshold is below half the baseline; sample size is 10-review units across 4 weeks.
   - Stop condition and budget: if the count has not fallen by week 4, stop the probe and hold a 30-minute team review of the rule.
   - Kind: stochastic. Cynefin domain: Complex, because the effect on review behavior shows only after a trial, so the leverage estimate is a [judgment] guess [18].

Confidence: high confidence, because the request names format as the only reported friction, and the pipeline removes that check from people.

## Follow-up

Conditions that change the recommendation: if A2 is false, ship one config per directory and re-score in Step 1. If A1 is false, replace the CI job with a hook and a merge checklist. If A3 is false, stop at Step 1 and hand the broader issue to the team lead.
