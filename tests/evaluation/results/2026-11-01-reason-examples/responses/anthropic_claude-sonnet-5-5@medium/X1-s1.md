## Headline

We should measure the summariser's errors first, then fix the most common error type with a tested change.

- Nobody knows today how often or how the summaries fail, so any fix is a guess.
- A labelled sample of real summaries gives the first error rate and error types.
- A one-click "wrong summary" button keeps the measure running after the sample.
- Prompt or design changes ship only when they beat the measured baseline.

## Background

The team added a summariser to its support tool. It uses a large language model (LLM), a program that writes text from a prompt. Agents say the summaries are "sometimes wrong". The team has no metrics (per the user's query).

## Relevance

Agents act on the summary, so a wrong summary can send a customer a wrong answer. Without a number, the team cannot tell whether a change helps or harms.

## Information

**Evidence**

- One source says the summaries are "sometimes wrong": the agents, as relayed in the user's query. No source disagrees. No number backs it. Confidence in any error rate is therefore low (one statement, zero measurements).
- LLM text generators are known to invent facts and to omit facts from the source text [1].
- An LLM can grade outputs at over 80% agreement with human graders in one benchmark study [3]. This must be checked on your data before use.
- The likely error types are invented facts, missing facts, and wrong outcomes. This is a [judgment] and Step 1 tests it.

**Assumption log**

A1. Agents read the summary and act on it without reading the full ticket. Why not measured: the material does not state it. Validate by: ask three agents to describe their last five tickets. If wrong: the cost of an error is lower, so Step 4 gets a smaller budget.

A2. The tool stores each ticket text and each summary. Why not measured: no tool can reach your system from here. Validate by: query the store for one day of records. If wrong: add logging before Step 1.

A3. Two agents can label 50 summaries in one working session. Why not measured: the material does not state staff capacity. Validate by: ask two agents for two hours. If wrong: cut the sample to 30 and lower confidence.

**Alternative considered**

Switch to a larger model or fine-tune now. It loses because there is no baseline to show a gain, and the cost is higher [judgment]. Revisit it after Step 3 if prompt changes fail.

## End

I recommend that we take these four actions in this order:

1. **Label a sample of 50 recent summaries.**
   - Increment: two agents compare each summary with its ticket and assign an error type: invented fact, missing fact, wrong outcome, or none.
   - Blocker removed: we do not know the error rate or the error types.
   - Kind: evaluative. Write the rubric before the work.
     - Criteria and weights: each label cites a quote from the ticket (50%); each error type comes from the fixed list (30%); the two labelers agree (20%).
     - Pass threshold: weighted score of at least 0.8, and agreement on at least 80% of cases.
     - Evidence needed: ticket text, summary text, and the quote.
   - Domain: Confused, because we cannot yet tell which error type dominates.
   - Step 3 MUST NOT start until this rubric passes.

2. **Add a "wrong summary" button with a reason list.**
   - Increment: one button in the agent screen. It saves the summary ID and the reason.
   - Blocker removed: there is no ongoing signal from agents.
   - Kind: deterministic. Test first:
     - Given an agent views a summary
     - When the agent clicks "wrong summary" and picks the reason "invented fact"
     - Then the store holds one record with the summary ID and that reason
   - Domain: Clear, because the same logging pattern works in any support tool.

3. **Build a baseline report from the labels.**
   - Increment: a script that reads the 50 labels and prints the error rate for each error type.
   - Blocker removed: no baseline exists to judge any change.
   - Kind: deterministic. Test first:
     - Given the 50 labelled cases from Step 1
     - When the script runs twice
     - Then both reports are identical and show a rate for each error type
   - Domain: Complicated, because several measures fit (human labels, LLM judge, text overlap) and analysis must pick one. Start with human labels. Compare any LLM judge to them [3].

4. **Run a capped probe of one prompt change.**
   - Increment: change the prompt to target the top error type from Step 3. For example, require a quote from the ticket for each stated fact, and write "not stated" for missing items.
   - Blocker removed: no tested fix exists.
   - Kind: stochastic. Test first:
     - Metric: share of summaries with at least one labelled error.
     - Baseline: the Step 3 rate.
     - Pass threshold: at least 30% lower (relative) than baseline.
     - Sample size: 100 summaries, labelled as in Step 1.
   - Budget and stop: one week and 10% of tickets. Stop if the error rate rises 5 points or agents report slower handling.
   - Domain: Complex, because the effect on agents shows only after a trial. Leverage is a guess.
   - Step 4 runs in parallel with Step 2. It MUST NOT be accepted until Step 3 gives the baseline.

If A2 is false, insert a logging step before Step 1. If Step 1 finds under 5% errors, stop and keep the current prompt.
