## Headline

Stop debating SQL style by hand: pick one standard once, then let a tool enforce it.

- The friction comes from people judging style in each review, so removing style from review removes the friction.
- A one-time team decision ends the disagreement, because a tool applies the same rule to everyone.
- A measured trial shows whether the culture changed.

## Background

The team has no shared SQL format. Each review repeats the same style argument. The request is to fix this as a culture problem.

## Relevance

Every review that argues about layout delays the work and wears down trust. Fixing this now stops the cost from compounding.

## Information

**Evidence**

1. The user states that style friction occurs in every review. This is one source, with no source that disagrees (user request, current message).
2. Automation removes most style comments: likely (66 to 100%) [judgment].
3. A style rule enforced by a tool does not depend on the reviewer's mood or rank [judgment].

**Assumption log**

A1. The team reviews SQL in pull requests on a shared git host with CI (automated checks on each change). Why not measured: the material does not state it. Validate by: look at the repository settings. If wrong: replace Step 4 with a local pre-commit hook.

A2. A formatter exists for the team's SQL dialect. Why not measured: the material does not name the dialect. Validate by: run the candidate tool on 10 real files. If wrong: pick another tool, or write a short guide and drop Steps 2 to 4.

A3. The team lead can make the decision binding. Why not measured: the user has not answered. Validate by: ask the lead before the session. If wrong: ask the repository owner to approve the result.

A4. Style comments are the main friction. Why not measured: no review data is in the material. Validate by: count style comments in the last 30 merged pull requests. If wrong: Step 5 shows no drop, so diagnose again.

**Alternative considered**

Write a style guide and rely on reviewers to apply it. This loses because a guide has no enforcement, so the same debate returns in each review [judgment].

## End

I recommend that we take these five actions in this order:

1. **Choose one style in a 45-minute session.**
   - Blocker removed: no agreed standard exists.
   - Kind: evaluative. Rubric written first: criteria and weights are fit with current code (40), formatter support (30), readability of the longest queries (20), and dialect support (10). The pass threshold is 70 of 100. Evidence is a count of matching files in a sample of 20, a tool run, and a read of 3 long queries.
   - Cynefin: Complicated [1], because more than one good style exists and the rubric picks one.
   - The lead MUST confirm the decision is binding before the session starts.

2. **Commit the formatter configuration and a golden file (a saved correct output).**
   - Blocker removed: the style is not yet executable.
   - Kind: deterministic. Test written first:
     - Given the chosen configuration and a sample query in mixed style
     - When the formatter runs on it
     - Then the output equals the golden file, and a second run changes nothing
   - Cynefin: Clear [1], because the tool documentation gives one setting for each rule.
   - Step 2 MUST NOT start until Step 1 passes the threshold.

3. **Reformat all existing SQL in one separate commit.**
   - Blocker removed: old files fail the new rule.
   - Kind: deterministic. Test written first:
     - Given the reformat commit is listed in the git ignore-revs file
     - When a developer runs git blame
     - Then each line shows its original author
   - Cynefin: Clear [1], because one known command does the work.
   - Step 3 MUST NOT start until the test in Step 2 passes.

4. **Add a CI check that fails on unformatted SQL.**
   - Blocker removed: no one enforces the rule.
   - Kind: deterministic. Test written first:
     - Given a pull request with one unformatted SQL file
     - When CI runs
     - Then the check fails and names that file
   - Cynefin: Clear [1], because the CI documentation gives one step for this check.
   - Step 4 MUST NOT start until Step 3 is merged. Gherkin form follows [2].

5. **Run a 30-pull-request probe on the new review rule: "no style comments, the tool decides".**
   - Capability added: evidence that the culture changed.
   - Kind: stochastic. Acceptance test written first: the metric is style comments per merged pull request. The baseline is the count from the last 30 merged pull requests (A4). The pass threshold is a drop of at least 80% from baseline. The sample size is the next 30 merged pull requests.
   - Cynefin: Complex [1], because team reaction shows only after the trial. The leverage of this step is a guess.
   - Budget: 30 minutes per week. Stop condition: stop if false CI failures delay two merges.
   - The baseline count MAY start now. The trial MUST NOT start until Step 4 passes.

If A2 is false, replace Steps 2 to 4 with a short written guide and keep Step 5.
