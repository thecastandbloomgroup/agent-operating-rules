## Headline

Migrate to JWT first with no visible change, and run one capped sign-up experiment after cutover.

- The two goals touch the same sign-up path, so a combined release hides the cause of any conversion change.
- The migration is deterministic work, so tests can prove it.
- The conversion work is uncertain, so it needs a measured experiment.
- The baseline conversion rate is unknown, so measure it first.

## Background

The request has two goals. First, replace sessions (the server stores login state and the browser holds an ID) with JWT (JSON Web Token: a signed token that carries login claims). Second, raise sign-up conversion (the share of sign-up visitors who finish sign-up). The material gives no code, no analytics, and no current rate.

## Relevance

The sign-up flow ends by creating a login. A change to login therefore changes sign-up. This is likely (66 to 100%) [judgment]. A mixed release would make the conversion result unreadable.

## Information

Evidence:

- A JWT defines an expiry claim, and the token stays valid until that time. A stolen token therefore works until expiry unless the server keeps a revocation list [1].

- A secure JWT service must pin the allowed signing algorithm and validate every claim [2].

- Sessions revoke at once by deleting the server record. JWT does not. Short access tokens plus server-stored refresh tokens close this gap [judgment].

- Conversion has no baseline in the material. Any lift claim is [no source] until Step 1 finishes.

Assumption log:

A1. The service has one server-side session store and browser clients. Why not measured: the material does not state it. Validate by: read the session configuration. If wrong: add mobile token storage work to Step 3.

A2. Analytics can report visits and completions per sign-up step. Why not measured: no tool can reach the analytics. Validate by: run one funnel query for the last 28 days. If wrong: Step 1 grows to add event tracking.

A3. Instant logout and ban are required. Why not measured: the user has not answered. Validate by: ask the product owner one yes/no question. If wrong: drop refresh-token revocation from Step 3.

Alternative considered: keep sessions and only improve conversion. It loses because the user asked for the migration, and the cost of sessions is unmeasured [judgment]. A second alternative is to ship both changes together. It loses because it confounds the conversion measure.

## End

1. **Measure the sign-up baseline.** Increment: one funnel report for 28 days, with drop-off per step. Blocker removed: no baseline, so no lift can be judged. 2. **Lock current behavior in tests.** Increment: tests for login, logout, expiry, and ban, run green on the existing service. Blocker removed: no proof that the migration keeps behavior. Domain: Clear, because the current service shows one known result for each case. Kind: deterministic. Step 3 MUST NOT start until these tests pass. Test written first:

   ```text
   Given a user holds a valid login
   When the user logs out
   Then the old login is rejected on the next request
   ```

3. **Build JWT behind a feature flag.** Increment: issue and verify 15-minute access tokens and rotating refresh tokens, then canary at 5% of traffic. Blocker removed: sessions block the stateless design. Domain: Complicated, because more than one token design fits and RFC 8725 analysis [2] picks one. Kind: deterministic. Cutover to 100% MUST NOT happen until the Step 2 tests pass on JWT. Test written first:

   ```text
   Given a token signed with the algorithm "none"
   When the token reaches a protected route
   Then the service returns 401
   ```

   ```text
   Given a banned user holds a refresh token
   When the user asks for a new access token
   Then the service refuses
   ```

4. **Run one capped sign-up experiment.** Increment: one change to the weakest step found in Step 1, tested in an A/B test (users split at random into two groups). Blocker removed: no evidence on what raises conversion. Domain: Complex, because the effect on users shows only after a trial. Leverage is a guess. Kind: stochastic. The live phase MUST NOT start until Step 3 has run at 100% for 3 days with no rise in login errors. Budget: 2 weeks and one change. Stop condition: stop early if completions fall more than 5% relative to control. Acceptance test written first:
   - Metric: completed sign-ups divided by sign-up visitors.
   - Baseline: the Step 1 rate.
   - Pass threshold: a 5% relative lift at 95% confidence.
   - Sample size: from a power calculation at 80% power on the Step 1 baseline.

If A3 is false, remove refresh-token revocation from Step 3. If Step 1 shows no drop-off at the final step, move the experiment before Step 3.
