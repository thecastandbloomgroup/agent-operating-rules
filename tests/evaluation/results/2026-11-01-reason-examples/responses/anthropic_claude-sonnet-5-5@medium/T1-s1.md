## Headline

**Fix the missing decision, not the culture: pick one SQL style once and let a tool enforce it.**

- The friction comes from an open question, not from bad people. [judgment]
- A formatter removes style from human review, so reviewers talk about logic.
- A two-week trial with a measure shows whether the change works.

## Background

SQL (Structured Query Language) is the code your team writes for databases. Team members hold different formatting preferences. Each pull request (a proposed code change that others review) triggers the same style arguments.

## Relevance

Every style comment costs reviewer time and adds tension. The cost repeats in each review until the team settles the question.

## Information

**Evidence**

- SQLFluff is a SQL linter (a tool that checks style) and formatter. Its documentation states that it supports many SQL dialects and can fix files automatically. [1]
- A rule that a program enforces ends most style comments. This is likely (66 to 100%). [judgment]
- Style choices are mostly arbitrary, so consistency matters more than which style wins. [judgment]
- The sources are one vendor document and my assessment. No team data exists yet. The trial in Step 4 produces that data.

**Assumption log**

A1. The team uses pull requests with a shared repository. Why not measured: the material does not state it. Validate by: look at the last five merged changes. If wrong: replace Step 3 with a pre-commit hook on each laptop.

A2. The team uses one SQL dialect. Why not measured: the material does not state it. Validate by: list the database engines in the repository. If wrong: set one formatter config for each dialect.

A3. One person has the authority to break a tie. Why not measured: the user has not answered. Validate by: ask the team lead in Step 1. If wrong: use a majority vote with a fixed time limit.

A4. Style comments are the main source of review friction. Why not measured: no tool can reach the review history from here. Validate by: count style comments in the last 20 merged pull requests. If wrong: the trial in Step 4 shows a small drop, and the real cause needs a separate review.

**Alternative considered**

The alternative is a written style guide with reviewers who enforce it by hand. It loses because people apply rules unevenly, so the arguments continue. [judgment]

## End

I recommend that we take these four actions in order:

1. **Decide the style in one 30-minute session.**
   - Blocker removed: the open question behind every argument.
   - Kind: evaluative. Rubric (Pugh matrix [pairwise scoring against criteria]): tool can enforce it (weight 50), produces small diffs (30), close to existing code (20).
   - Pass threshold: a score of at least 70 of 100. Evidence: the SQLFluff rule list and a trial run on five existing files. The team lead breaks ties.
   - Cynefin domain: Complicated, because several styles fit and a short analysis picks one.

2. **Write the formatter config and run it once on the repository.**
   - Blocker removed: no machine-readable definition of the style.
   - Kind: deterministic. Commit the reformat alone, so it does not mix with other changes.
   - Test, written first:
     - Given a SQL file with mixed case keywords and tabs
     - When a developer runs the fix command
     - Then the file matches the agreed style, and a second run changes nothing [2]
   - Cynefin domain: Clear, because the tool documentation gives one setting for each rule.
   - Step 2 MUST NOT start until Step 1 ends.

3. **Add an automatic check to every pull request.**
   - Blocker removed: style depends on reviewers.
   - Kind: deterministic. Test, written first:
     - Given a pull request that contains a badly formatted SQL file
     - When the automatic check runs
     - Then the check fails and names the file and line
   - Cynefin domain: Clear, because the CI vendor manual gives one way to add a check.
   - Step 3 MUST NOT start until the test in Step 2 passes.

4. **Run a two-week probe on the review rule: "reviewers do not comment on SQL format".**
   - Capability added: reviews focus on logic.
   - Kind: stochastic. Metric: style comments for each pull request.
   - Baseline: the count from the last 20 merged pull requests (see A4). Pass threshold: a drop of at least 80%. Sample size: the next 20 pull requests.
   - Stop condition: review time rises, or two people report that the rules block their work. Budget: two weeks and one hour of setup.
   - Cynefin domain: Complex, because the effect on team behavior shows only afterward. Leverage here is a guess.
   - Run Step 4 in parallel with Steps 2 and 3. Accept the rule only when the threshold is met at 20 pull requests.

Cynefin classes follow Snowden and Boone. [3]

If A1 is false, replace Step 3 with a pre-commit hook.
