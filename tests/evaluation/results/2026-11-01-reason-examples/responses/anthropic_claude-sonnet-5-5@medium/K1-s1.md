## Headline

Raise the database pool size first, because the 8-connection pool caused most of the slowdown.

- The wait for a pool connection explains about 88% of the p95 increase.
- The shorter cache TTL raised the cache miss rate and added load on the pool.
- The ORM change does not explain the slowdown.

## Background

API p95 latency rose from 120 ms to 900 ms after release 2026.10.21. That release cut the pool from 50 to 8 connections, cut the acquire timeout from 30 s to 5 s, cut the cache TTL from 300 s to 60 s, and added `selectinload` to the orders query.

## Relevance

The error rate rose from 0.02% to 0.40%, and customers now receive 503 responses. Each hour without a fix adds 1,800 to 2,400 pool exhaustion events.

## Information

**Evidence**

- The p95 total rose by 780 ms. The p95 pool wait rose by 687 ms (3 to 690 ms), which is 88% of the rise.

  Source: traces.txt, table.
  - Reference: [1]

- Query and serialize spans did not change. The p95 of `db.query orders` moved from 52 to 58 ms.

  Source: traces.txt, table.
  - Reference: [1]

- All four pods (4 of 4) report "8 of 8 connections in use" with up to 14 waiters. Two requests failed with 503 after 5 s.

  Source: logs.txt, lines 10:14:02 to 10:14:12.
  - Reference: [2]

- Pool exhaustion warnings went from none on 2026-10-20 to 1,800 to 2,400 per hour on 2026-10-22.

  Source: logs.txt, closing note.
  - Reference: [2]

- The release set `max_size` to 8 and `acquire_timeout_s` to 5. It also set `default_ttl_s` to 60.

  Source: release.diff, config sections.
  - Reference: [3]

- The cache miss rate rose from 12% to 31%, a rise of 19 points. Each miss needs a database connection. The cache read time did not change.

  Source: traces.txt, table.
  - Reference: [1]

- Load is the same (410 vs 405 requests per second). Database CPU is 38% vs 41%. The database has spare capacity, so the limit sits in the pool.

  Source: traces.txt, footer.
  - Reference: [1]

- Theme: pool starvation. Three independent sources support it (logs, traces, diff). No source disagrees. Confidence: high, three independent sources.

- One conflict exists. The logs show 8 connections on each of 4 pods (32 in total). The traces show 8 active connections for the service. The pool is likely per pod, and the trace figure is per pod. [inference]

- The `selectinload` change is not a cause. The `order_lines` query already ran before the release, and its p95 fell from 30 to 26 ms. [inference]

**Assumption log**

A1. The new database limit in OPS-412 is at least 32 connections for the service. Why not measured: the material does not state the limit. Validate by: read ticket OPS-412 or run `SHOW max_connections` for the service role. If wrong: Step 1 uses a smaller pool, or a connection pooler replaces it.

A2. No business need requires the 60 s TTL. Why not measured: the material does not state the reason for the change. Validate by: ask the author of the TTL commit. If wrong: keep 60 s and accept a higher miss rate, which makes Step 1 more important.

**Alternative considered**

Roll back the whole release. It loses because the config changes cover 88% of the delay, the rollback also removes the OPS-412 change, and the `selectinload` change shows no harm.

## End

I recommend that we take these actions in order:

1. **Set the pool size per pod so that 4 pods × `max_size` fits the database limit from A1. Use 16 if the limit allows it.** Deploy to one canary pod. This removes the main blocker, the pool wait. Domain: Complicated, because the limit and the load set the size, and analysis must pick it.

   Kind: stochastic. Write the test first.
   - Metric: p95 of `db.pool.acquire` on the canary.
   - Baseline: 3 ms in window A.
   - Pass threshold: 10 ms or less.
   - Sample size: 10,000 requests.
   - Step 2 MUST NOT start until this test passes.

2. **Restore `default_ttl_s` to 300, if A2 holds.** This adds back the cache hit rate and cuts the load on the pool. Domain: Clear, because the config before the release is known to work.

   Kind: deterministic. Write the test first.

   ```text
   Given the cache config with default_ttl_s 300
   When the API stores the key orders:customer:55120
   Then the cache entry has ttl=300
   ```

3. **Roll out the Step 1 and Step 2 config to all 4 pods, then add an alert on any "pool exhausted" warning.** This adds early detection of a repeat. Domain: Clear, because the alert rule has one known practice.

   Kind: deterministic. Write the test first.

   ```text
   Given the alert rule on the "pool exhausted" warning
   When a test pod logs one "pool exhausted" warning
   Then the on-call channel receives one alert within 60 seconds
   ```

   Step 3 MUST NOT start until the test in Step 1 passes.

If A1 is false, replace Step 1 with a connection pooler in front of the database, or lower the worker threads per pod to match the limit.
