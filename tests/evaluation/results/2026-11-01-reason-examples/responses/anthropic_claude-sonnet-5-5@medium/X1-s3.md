## Headline

Measure the summariser's errors first, then fix the most common error type with a controlled trial.

- Without a metric, no change can be shown to help, so measurement comes first.
- "Sometimes wrong" covers several failure types, so a labeled sample must split them.
- Logging and agent feedback give a continuous signal at low cost.
- Each fix runs as a small trial with a stop condition.

## Background

The support tool has an LLM summariser (a model that condenses a ticket thread into a short text). Agents report that it is "sometimes wrong". The team has no metrics, and the material does not say what "wrong" means.

## Relevance

Agents who distrust a summary reread the full thread. That removes the time the tool should save. [judgment]

**Assumption log**

A1. Agents can label 50 summaries in one session. Why not measured: the material does not state agent capacity. Validate by: ask one team lead for a 30-minute slot. If wrong: shrink the sample to 25 and widen the error bounds.

A2. The tool can store input, output, and model version. Why not measured: no tool can reach the codebase. Validate by: read the summariser's call site. If wrong: add a logging wrapper before Step 2.

A3. A 10% agent split is possible. Why not measured: the material does not describe the rollout system. Validate by: check for a feature flag. If wrong: run the trial with one volunteer team.

**Alternative considered**

Swap to a larger model now. It loses because the failure types are unknown, so a swap cannot be judged and raises cost. [judgment]

## End

I recommend that we take these four actions in order:

1. **Label a sample of 50 recent summaries by failure type.**
   - Increment: two agents label 50 summaries as correct or wrong, with a type for each wrong one.
   - Blocker removed: we do not know what "wrong" means.
   - Domain: Confused, because the request does not say which failure types occur.
   - Kind: evaluative. Write the rubric first.
   - Rubric: criteria are factual accuracy (weight 50%), completeness (30%), and attribution (20%). Pass is 4 of 5 per summary on every criterion. Evidence is the source thread beside the summary.
   - Step 2 MUST NOT start until the labels exist.

2. **Log every summary and agent reaction.**
   - Increment: store input ID, output, model version, prompt version, and a thumbs up or down with an edit flag.
   - Blocker removed: no continuous metric exists.
   - Domain: Clear, because the logging fields follow one known practice.
   - Kind: deterministic. The test is:

   Given an agent opens a ticket summary

   When the agent clicks thumbs down

   Then a record with output, model version, prompt version, and the rating is stored

3. **Fix a metric and a baseline from Steps 1 and 2.**
   - Increment: define the error rate as wrong summaries divided by all labeled summaries. Compute the baseline.
   - Blocker removed: no pass threshold exists.
   - Domain: Complicated, because an analysis of Step 1 types picks the metric.
   - Kind: stochastic. Acceptance test: metric is error rate, baseline is from Step 1, threshold is half the baseline, sample size is 200 labeled summaries.
   - Step 4 MUST NOT start until this baseline is recorded.

4. **Run one prompt change as a trial on the most common failure type.**
   - Increment: change the prompt for the top type. Show it to 10% of agents for one week.
   - Capability added: a tested way to improve.
   - Domain: Complex, because the effect on agents shows only after use. Leverage is a guess.
   - Kind: stochastic. Use the Step 3 test. Budget is one week and one prompt change. Stop if the thumbs-down rate rises 20% above baseline.
   - Run Step 4 in parallel with Step 2 once Step 3 is done. Keep the change only when the threshold holds at 200 summaries.
