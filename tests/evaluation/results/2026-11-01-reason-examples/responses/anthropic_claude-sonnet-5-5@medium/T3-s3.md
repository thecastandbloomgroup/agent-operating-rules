## Headline

Split the request into two pieces of work: migrate to JWT (JSON Web Token) first, and test sign-up changes separately.

- The migration is deterministic work with known acceptance criteria.
- Sign-up conversion is an experiment, so its result varies from run to run.
- The two changes must not ship together, because the migration would confound the conversion result.
- No baseline conversion rate exists in the request, so measure it first.

## Background

The request asks for two changes to the auth service. The first replaces server-side sessions with JWT. The second raises the share of visitors who finish sign-up. The request gives no stack, client types, or current conversion rate.

## Relevance

Both changes touch the sign-up and login path. If they ship together, a drop or gain in conversion has no clear cause.

## Information

**Evidence**

- A JWT is valid until its `exp` claim passes, so logout and password change need extra design [1]. Source type: primary.
- Best practices for algorithm choice and claim validation exist in a separate standard [2]. Source type: primary.
- Sign-up conversion has no known link to the token format. [inference]
- Sample size for the probe: a two-proportion test with 80% power, 5% significance, a 10% baseline, and a 2-point gain needs about 3,800 users per arm. [judgment, computed with the standard formula]

**Assumption log**

A1. The service is one web app with a server-side session store. Why not measured: the material does not state it. Validate by: read the session configuration. If wrong: for mobile clients, change the token storage design in Step 2.

A2. Baseline conversion is 10%. Why not measured: no tool can reach the analytics data. Validate by: run the funnel query in Step 1. If wrong: recompute the sample size in Step 4.

A3. The product needs server-side logout and revocation. Why not measured: the user has not answered. Validate by: ask the product owner for one yes or no. If wrong: drop the refresh-token store in Step 3.

**Alternative considered**

Keep sessions and only improve sign-up. This option has the lowest risk. It loses because the request asks for the migration, and A1 gives no technical reason to refuse it. [judgment]

## End

I recommend that we take these four actions in this order:

1. **Measure the sign-up baseline.**
   - Increment: add or confirm funnel events for each sign-up step, and run one query for the last 30 days.
   - Blocker removed: Step 4 has no baseline without it.
   - Kind: deterministic.
   - Domain: Clear, because one known practice exists for funnel events.
   - Test:
     - Given a test user who completes sign-up
     - When the funnel query runs
     - Then it counts one event for each step, in order

2. **Choose the token design.**
   - Increment: score three options in one written decision record: sessions, short-lived JWT with refresh rotation, and JWT with a revocation list.
   - Blocker removed: Step 3 has no design without it.
   - Kind: evaluative.
   - Domain: Complicated, because several designs fit and analysis must pick one.
   - Rubric (Pugh matrix [3], sessions as the baseline): revocation support (weight 3), security per [2] (weight 3), client fit (weight 2), build effort (weight 1). Pass threshold: the winner scores at least 3 points above the baseline. Evidence: cited standards and A1 to A3.

3. **Build the JWT path behind a feature flag.**
   - Increment: issue and verify an access token with a 15-minute life, and keep the session path active.
   - Blocker removed: the service cannot leave sessions without it.
   - Kind: deterministic.
   - Domain: Complicated, because the design from Step 2 fixes the cause and effect.
   - Test, written first:
     - Given a valid user with the flag on
     - When the user logs in and later calls a protected route with an expired token
     - Then the route returns 401 and a valid refresh returns a new token
   - Step 3 MUST NOT start until Step 2 passes its threshold.

4. **Run one capped sign-up probe.**
   - Increment: change one element, for example the number of form fields, for 5% of traffic.
   - Capability added: evidence on what moves conversion.
   - Kind: stochastic.
   - Domain: Complex, because the effect on users shows only after a trial.
   - Leverage is a guess. Budget: two weeks, one engineer-day.
   - Stop condition: stop if conversion falls more than 2 points below baseline, or at 3,800 users per arm.
   - Acceptance test: metric is sign-up completion rate. Baseline comes from Step 1. Pass threshold is a gain of at least 2 points. Sample size is 3,800 users per arm.
   - Step 4 MUST NOT start until Step 1 gives a baseline.
   - Step 4 MUST NOT run in the same release window as the Step 3 rollout.

If A3 is false, remove the revocation list from Step 2 and shorten Step 3.

## Follow-up

Conditions that change the recommendation:

- If A1 is false, add a client-storage review to Step 2.
- If Step 1 shows a baseline far from 10%, recompute the sample size.
