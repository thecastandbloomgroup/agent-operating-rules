## Headline

Split this into two jobs: migrate to JWT first with no sign-up change, then run one measured test to lift sign-up conversion.

- The migration has a known design, so a test can prove it works.
- The conversion work has an unknown outcome, so it needs an experiment with a baseline.
- Changing both at once hides which change moved the sign-up rate [judgment].
- Sessions allow instant revocation and plain JWTs do not, so the design must restore revocation.

## Background

The request has two goals: move authentication from server-side sessions to JSON Web Tokens (JWT), and raise sign-up conversion. The material gives no code, client list, or funnel data. A JWT is a signed token that carries identity claims, as defined in RFC 7519.

## Relevance

Both goals touch the sign-up path, because new users are logged in right after sign-up. A mixed release makes any drop in conversion hard to trace.

## Information

**Evidence**

1. A JWT is self-contained and signed, so servers need no session lookup [1].
2. Best practice for JWT covers algorithm choice, validation, and short token life [2].
3. Revocation is the main cost of leaving sessions. Short access tokens plus a server-side refresh token list solve it [judgment].
4. Change one variable at a time to read a conversion result [judgment].
5. Cause and effect in a user-behavior change show only afterward, so it is a Complex domain [3].

**Assumption log**

A1. All clients are first-party web or mobile apps. Why not measured: the material does not state it. Validate by: list the clients in the repository. If wrong: add an OpenID Connect review before Step 2.

A2. The sign-up flow already emits funnel events. Why not measured: no tool can reach the analytics. Validate by: query the last 7 days of events. If wrong: Step 1 must add them.

A3. Baseline sign-up completion is 20%. Why not measured: the material does not state it. Validate by: Step 1 query. If wrong: recompute the sample size in Step 4.

A4. Weekly sign-up starts exceed 3,000. Why not measured: the material does not state it. Validate by: count starts in Step 1. If wrong: replace the A/B test with five moderated user sessions.

**Alternative considered**

Do both changes in one release. It ships sooner, but it confounds the conversion result and raises rollback risk [judgment]. It loses.

## End

I recommend that we take these five actions in this order:

1. **Inventory and baseline (Confused, because the clients, the funnel events, and the baseline are unknown).**
   - Increment: list every session reader and writer, and query the 7-day sign-up funnel.
   - Blocker removed: the unknowns in A1 to A4.
   - Kind: deterministic. Test, written first:
     - Given the repository and the analytics store
     - When the inventory and funnel query run
     - Then every session call site is listed and baseline completion is recorded with its sample count

2. **Build JWT issue and validate behind a flag (Complicated, because token storage and revocation have several good designs and analysis picks one).**
   - Increment: one login endpoint issues a 15-minute access token and a rotating refresh token, following RFC 8725 [2].
   - Blocker removed: no token path exists.
   - Kind: deterministic. Test, written first:
     - Given a user with a valid login and the flag on
     - When the user calls a protected endpoint with a valid, an expired, and a revoked token
     - Then only the valid token succeeds
   - Step 2 MUST NOT start until Step 1 is done.

3. **Canary rollout with dual accept (Complicated, because rollout order depends on the client list from Step 1).**
   - Increment: accept sessions and JWT together, then move 5% of logins to JWT.
   - Blocker removed: the risk of a full cutover.
   - Kind: deterministic. Test, written first:
     - Given 5% of logins use JWT
     - When a user logs in, refreshes, and logs out
     - Then logout revokes the refresh token and error rate stays within the Step 1 baseline
   - Step 3 MUST NOT start until the Step 2 test passes.

4. **Conversion probe (Complex, because the effect of a form change on new users shows only after a trial; leverage is a guess).**
   - Increment: one A/B test of one change, such as removing one optional sign-up field.
   - Blocker removed: no evidence on what lifts conversion.
   - Kind: stochastic. Acceptance test, written first:
     - Metric: sign-up completion rate.
     - Baseline: the Step 1 value (20% under A3).
     - Threshold: a gain of 2 percentage points.
     - Sample size: about 6,500 sign-up starts per arm, at 80% power and 5% significance.
   - Stop condition: end the test if completion falls 2 points below baseline.
   - Budget: 4 weeks.
   - Design and instrument the test in parallel with Step 3. The traffic split MUST NOT start until the Step 3 canary shows no change in sign-up errors.

5. **Retire sessions (Clear, because the rule is one known step: remove code that has no traffic).**
   - Increment: delete session auth after 14 days with zero session logins.
   - Blocker removed: two auth paths to maintain.
   - Kind: deterministic. Test, written first:
     - Given the JWT rate is 100% for 14 days
     - When the session code is removed
     - Then the full login test suite passes
   - Step 5 MUST NOT start until Step 3 reaches 100%.

If A1 is false, add an OpenID Connect review before Step 2.
