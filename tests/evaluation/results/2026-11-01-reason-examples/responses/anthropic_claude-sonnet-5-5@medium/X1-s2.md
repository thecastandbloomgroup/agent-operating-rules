## Headline

We should measure the error rate first, then fix the most common error type with small, tested changes.

- No baseline exists, so no change can be called an improvement yet.
- Agent reports are the cheapest source of error data, so the tool should capture them at one click.
- The fix depends on the error type, which is unknown, so prompt changes run as capped trials.

## Background

The team added a summariser based on a large language model (LLM) to the support tool. Agents say it is "sometimes wrong" (per the request, current message). The team has no metrics. The request is to improve it.

## Relevance

Agents who distrust a summary reread the full ticket, which removes the time saving. Without numbers, the team cannot tell whether a change helps or harms.

## Information

**Evidence**

- Theme: "sometimes wrong". One source supports it (the request). No source disagrees. The theme gives no rate and no error type. Confidence: low, one source, no measurement.
- Impact of errors on agent time: [judgment] distrust leads to rereading.
- Cynefin sorts work by how cause and effect relate [1]. It guides the labels in the End section.

**Assumption log**

A1. The tool stores the ticket text, the summary, and the prompt version. Why not measured: the material does not state it. Validate by: read one stored record. If wrong: add logging before Step 2.

A2. "Wrong" means a false fact, a missing key fact, or a wrong status. Why not measured: the user has not answered. Validate by: ask two agents to label five summaries. If wrong: change the rubric in Step 1.

A3. The team can change the prompt and route 10% of traffic to a variant. Why not measured: the material does not state it. Validate by: ask the engineer who owns the integration. If wrong: replace Step 3 with an offline test on the labelled set.

**Alternative considered**

Switch to a larger model now. It loses because the cause of the errors is unknown, so the cost is unjustified [judgment]. Step 3 can include a model change as one variant if the error type points to it.

## End

I recommend that we take these four actions, in this order.

1. **Label a sample and build an error list.** Confused: the request does not say what "wrong" means or how often it happens.
   - Increment: in one session, agents label 50 recent summaries as correct or wrong, with an error type.
   - Blocker removed: no baseline and no error types.
   - Kind: evaluative. The rubric is written first.
   - Rubric: criteria are factual accuracy (weight 50%), key facts kept (30%), correct status (20%). A summary passes at a weighted score of 80% or more. Evidence per criterion: the ticket text, side by side with the summary.
   - Output: a baseline error rate (the margin is at most 14 points at 95% confidence with 50 items) and a ranked error list.
   - Step 3 MUST NOT start until this output exists.

2. **Add a one-click "wrong summary" flag.** Clear: because adding a button and a log field follows a known practice.
   - Increment: a button that stores the ticket ID, the summary, the prompt version, and an optional reason.
   - Blocker removed: no ongoing metric.
   - Kind: deterministic. The test is written first [2].

   ```gherkin
   Given an agent views a ticket with a summary
   When the agent clicks "wrong summary"
   Then the system stores the ticket ID, summary, and prompt version
   ```

3. **Run a capped trial of one prompt change.** Complex: because the effect of a prompt change shows only in live use. Leverage is a guess.
   - Increment: the change targets the top error type from Step 1. Example: "quote the ticket for every fact". Route 10% of tickets to it.
   - Blocker removed: unknown fix.
   - Kind: stochastic. The acceptance test is written first.
   - Metric: wrong-flag rate plus labelled error rate. Baseline: Step 1 and Step 2 data. Threshold: a relative drop of 30% or more. Sample size: 200 summaries per arm.
   - Budget: two weeks. Stop at once if the variant's flag rate exceeds the baseline by 10 points.
   - Run in parallel with Step 2 once Step 1 is done.

4. **Freeze the labelled set as a regression check.** Complicated: because more than one scoring method fits, and a comparison of human and automatic scoring must pick one.
   - Increment: store the 50 labelled items. Score each future prompt on them using the Step 1 rubric.
   - Blocker removed: no way to check a change before release.
   - Kind: evaluative. A change passes if its rubric score is not below the baseline.
   - Step 4 MUST NOT start until Step 1 ends.

If A1 is false, add logging first and move Step 2 to the front. If A3 is false, replace Step 3 with an offline run on the Step 4 set.
