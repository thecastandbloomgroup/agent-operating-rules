# Headline

Increase the database connection pool size and restore the cache time to live to reduce latency.
The connection acquisition delay accounts for 687 ms of the 780 ms latency increase at the 95th percentile [1].
Lowering the cache time to live increased database request volume because the cache miss rate rose from 12% to 31% [1].
The object-relational mapping query changes did not degrade database execution speed [1].

# Background

Last week's release changed the database connection pool, cache configuration, and query preloading [2].
After the deployment, the application programming interface 95th percentile latency rose from 120 ms to 900 ms [1].
HTTP 503 error rates rose from 0.02% to 0.40% because connection acquisition timed out after 5 seconds [1], [3].

# Relevance

Customer requests fail and experience slow responses during peak traffic periods [1].
You need to remove the connection bottleneck to restore service performance.

# Information

The trace data shows that connection pool acquisition delay drives the latency increase [1].
Specifically, connection acquisition latency at the 95th percentile increased from 3 ms to 690 ms [1].
Meanwhile, query execution times remained stable across both versions [1].
Database query execution for orders took 52 ms in window A and 58 ms in window B [1].
Query execution for order lines took 30 ms in window A and 26 ms in window B [1].
Therefore, the query preloading change in the object-relational mapping layer is not the cause [1], [2].

Two configuration changes created connection starvation [2].
First, the database connection pool maximum size per pod dropped from 50 to 8 [2].
Second, the cache time to live dropped from 300 seconds to 60 seconds [2].
This cache change increased the cache miss rate from 12% to 31% [1].
Higher cache misses sent more queries to the database while pool capacity was restricted [1], [2].
Consequently, worker threads queued for database connections and timed out after 5 seconds [1], [3].

### Assumptions

A1. The database server can support at least 40 concurrent connections from this service. Why not measured: the material does not state database server capacity limits. Validate by: inspect ticket OPS-412 or query `max_connections` on `orders-db.internal`. If wrong: use an external connection pooler such as PgBouncer.

A2. Reverting the cache time to live to 300 seconds does not violate data freshness requirements. Why not measured: product specifications are not provided. Validate by: check the order update frequency in the product specification. If wrong: keep time to live at 60 seconds and increase pool capacity further.

### Alternative Considered

Reverting the object-relational mapping preloading change (`selectinload`).
This alternative loses because order line queries ran faster in window B than in window A (26 ms versus 30 ms at the 95th percentile) [1].
