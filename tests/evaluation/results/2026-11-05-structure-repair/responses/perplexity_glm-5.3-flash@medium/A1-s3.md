## Headline

Pin the versions: requirements.txt should use exact `==` pins, and a generated lock file should pin the full dependency tree. Three supporting points:
1. An unpinned requirement accepts every new upstream release into each install, so two breaks in one month is the expected outcome of the current setup [1].
2. Exact pins with `==` make each install reproducible, and the pin list then records one tested set of versions [1].
3. A lock file pins the transitive dependencies that exact direct pins do not control [2].

## Background

The project installs Python libraries from requirements.txt with no version pins. A library update broke the build twice last month. The request asks whether to pin the versions.

## Relevance

Each unpinned install takes whatever release is newest at install time [1]. So the same file produces different builds on different days, and the next release can break the build again at any time.

## Information

Evidence:
- The pip requirements file format defines exact pins with `==` and treats an unpinned name as a bare requirement with no version constraint [1].
- The pip-tools documentation states that `pip-compile` resolves and pins the full dependency tree, including transitive dependencies, into one file [2].
- User report from this conversation: two build failures in one month, both after a library update. Therefore the observed failure rate confirms the unpinned risk [1].

Assumptions:
- A1. The project installs dependencies with pip from requirements.txt. Why not measured: the material does not state the installer. Validate by: read the build script or container file. If wrong: the pin syntax changes, the principle holds.
- A2. Some breakage came from transitive dependencies rather than only direct ones. Why not measured: the conversation contains no error logs. Validate by: read the two build logs and the diff of changed versions. If wrong: direct pins still fix the direct path, and Step 2 fixes the transitive path.

Alternative considered: ranged pins such as `package>=2.0,<3`. This loses because new patch releases still enter the build without review [2]. Review effort then lands on unplanned build failures instead of planned upgrades.

## End

I recommend that we pin every direct dependency, lock the full tree, and gate the build on an exact match. Actions, in order:

1. Pin each direct dependency with `==` and its exact version in requirements.txt.
   - Increment: one edited file, one session. Blocker removed: different versions on each install.
   - Kind: deterministic. Test, written first:
     ```gherkin
     Given a clean virtual Python environment
     When the build runs pip install -r requirements.txt, then pip freeze
     Then every frozen line matches a line in requirements.txt
     ```
   - Cynefin domain: Clear. Reason: pip defines the pin rule, so the fix follows by deduction from that rule [1].

2. Generate a fully pinned lock file with `pip-compile` from the direct pins [2].
   - Increment: one generated file plus one command in the build. Blocker removed: uncontrolled transitive dependencies.
   - Kind: deterministic. Test, written first:
     ```gherkin
     Given a clean environment built from the lock file
     When a second clean environment installs the same file
     Then both pip freeze outputs match line for line
     ```
   - Cynefin domain: Complicated. Reason: more than one lock tool exists, so analysis picks one; a wrong tool choice, not the method, is what could break the pattern.

3. Add a continuous integration job that builds from requirements.txt in a clean environment on every merge.
   - Increment: one pipeline job. Blocker removed: version drift entering the main branch without review.
   - Kind: deterministic. Test, written first:
     ```gherkin
     Given a merge request with changed dependencies
     When the job runs the clean build and the test suite
     Then the merge fails when the build or the suite fails
     ```
   - Cynefin domain: Clear. Reason: an exact-match gate blocks unreviewed updates by deduction from the pin rule.
   - Step 3 MUST NOT start until the file edits in Steps 1 and 2 pass their tests.

4. Upgrade pins monthly with `pip-compile --upgrade`, run the full test suite, and revert on failure.
   - Increment: one upgrade session per month, capped at one hour. Blocker removed: pins growing stale over time.
   - Kind: deterministic. Test, written first:
     ```gherkin
     Given the upgraded lock file
     When the full test suite runs in a clean environment
     Then the upgrade merges only on a passing suite, and the team reverts otherwise
     ```
   - Cynefin domain: Complex. Reason: the effect of an upstream version shows only after the probe, so each upgrade is a safe-to-fail trial with a stop condition and a one hour budget [3]. Leverage is a guess.

## Follow-up

Conditions that change the recommendation: if installs come from a pre-built container image or a frozen cache, pinning requirements.txt adds little on its own, so pin the image or cache instead. No open questions.
