# Headline

The solution to SQL format disputes is a machine-checked style guide, not a consensus vote. An automated formatter removes the dispute from human review. A short style guide covers what the formatter cannot check. A pilot on one project proves the approach before a team-wide rollout.

## Background

The team cannot agree on SQL formatting. Every review now contains format feedback instead of logic feedback. The request is to end this friction.

## Relevance

Format debates consume review time and create conflict without improving code quality. A tool that enforces one format ends the debate because the tool decides, not a person.

## Information

Style disagreements are a known failure mode in code review. Google Engineering Practices documentation states that teams should derive style rules from an authoritative guide and enforce them with tools rather than personal judgment [1]. No source disagrees (one source, secondary).

Automated formatters exist for SQL and are in wide use. SQLFluff lints and auto-fixes SQL and supports many dialects [2]. dbt Labs publishes a SQL style guide that pairs with a formatter [3]. Both are free. License cost is $0 [2][3].

A formatter alone will not fix this. The root cause is that people treat format preference as a question of taste. The fix must change the rule source from "per person" to "a config file voted on once, then frozen".

A2. The team uses a supported SQL dialect. Why not measured: the material does not state it. Validate by: run SQLFluff parse on three existing files. If wrong: fall back to sqlfmt with manual rules.

A3. Someone can own the roll-out for about 4 to 6 hours in week one [judgment]. Why not measured: team capacity is unknown. Validate by: ask a lead to confirm one owner. If wrong: extend the timeline, the plan still holds.

Alternative considered: hold a team meeting to agree on formatting rules by vote. It loses because votes create winners and losers, and a human still enforces the rules in review, so the friction continues [1].

## End

I recommend that we take these four actions.

1. **Adopt the dbt SQL style guide as the written rule, verbatim, in a one-hour meeting.** This removes the blocker "no shared source of truth". Cynefin domain: Clear, because a published guide exists and needs no analysis. Test (evaluative): rubric is adoption by majority vote in one meeting, threshold 60% yes, evidence is the recorded vote [3].

2. **Write the SQLFluff config before the code change.** This adds the capability of machine enforcement. Cynefin domain: Clear, because the mapping from guide to config is documented [2]. Test (deterministic):
Given the team repository on a branch,
When SQLFluff lint runs with the new config on three existing SQL files,
Then it reports violations in at least one file and exits nonzero.

3. **Run a one-week pilot on one project.** Cause and effect for team acceptance are visible only after the trial, so this is a safe-to-fail probe. Cynefin domain: Complex. Budget: one project, one week. Stop condition: more than one developer asks to revert. Measure: count of format comments in pilot reviews versus the prior week, target equal to zero.

4. **Add SQLFluff to CI so checks run on every commit.** This removes the blocker "humans enforce format". Cynefin domain: Clear after Step 2 passes, because config already exists. Step 4 MUST NOT start until the test in Step 2 passes. Test (deterministic):
Given a commit with a format violation,
When CI runs,
Then the build fails and names the violated rule.

If A1 is false, replace Step 4 with a pre-commit hook that runs the same lint.
