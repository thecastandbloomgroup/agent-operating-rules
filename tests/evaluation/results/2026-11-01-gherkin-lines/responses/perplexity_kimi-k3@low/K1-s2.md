## Headline

The latency rise comes from the database connection pool cut from 50 to 8, so revert the pool configuration first and verify with traces. Three supporting points follow.

1. The pool change explains 800 ms of the 900 ms p95: db.pool.acquire rose from 3 ms to 690 ms p95, while query time stayed flat [2].
2. The cache TTL cut (300 s to 60 s) tripled miss rate from 12% to 31%, which raises demand for connections [2].
3. The ORM change is about as likely as not a minor amplifier: it holds each connection through the order_lines query, but peak DB connections rose only from 31 at a pool of 50, so reverting the pool alone is sufficient [2].

## Background

P95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed three things: pool config, cache TTL, and the orders ORM query [1], [2], [3]. The request is to diagnose and say what to do.

## Relevance

Error rate rose from 0.02% to 0.40%, and 96% of errors are PoolTimeout [3]. Each reverted day costs roughly 1,800 to 2,400 "pool exhausted" warnings and about 1 order per 250 failing [1], [3].

## Information

Evidence, in order of cause weight:

1. Pool size cut from 50 to 8, and acquire timeout from 30 s to 5 s [2]. Peak concurrent need is 31 connections [2]. With only 8 per pod, 32 workers queue. Queue time is the entire regression: db.pool.acquire p95 went from 3 ms to 690 ms [3].
2. Cache TTL cut from 300 s to 60 s [2]. Miss rate rose from 12% to 31% [3]. More misses mean more requests hold a connection, so this compounds the pool shortage.
3. The selectinload change adds a second query per request, but db.query spans stayed flat or improved (order_lines 30 ms to 26 ms p95) [2], [3]. It lengthens connection hold time a little. It is not the driver.
4. DB CPU is flat at 38% to 41% peak [3], so the database has headroom for 50 connections per pod, as before the release.

The commit cites OPS-412, a new per-service DB connection limit [2]. At 4 pods × 50 = 200 connections, the old config breaches that limit if it is real. Validate OPS-412 before a full revert.

Assumption log:

`A1. The OPS-412 limit either does not exist or permits more than 50 connections per service. Why not measured: not in attached material. Validate by: read OPS-412 and confirm with DB current max_connections. If wrong: raise max_size to the allowed value (for example 40/pod) and extend acquire timeout to 15 s instead of full revert.`

Alternative considered: keep pool at 8 and restore cache TTL. This loses because peak demand is 31 connections and 8 cannot serve 405 requests/s whose handlers each need a connection; traces show acquire at 690 ms p95 regardless of query speed [judgment, based on 3].
