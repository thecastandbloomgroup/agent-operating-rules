## Headline

The summariser cannot improve without a measured baseline, so the first work is evaluation, not tuning.

- Agents report errors but there is no error taxonomy, so nobody knows what "wrong" means.
- A labelled sample of summaries with scores gives a baseline and a target.
- An automated harness then turns each fix into a repeatable measurement.

## Background

An LLM summariser was added to a support tool. Agents say it is "sometimes wrong". No metrics, no error categories, and no test set exist. The request is to make it better.

## Relevance

Changes without measurement cannot be confirmed or rejected. Each prompt or model change risks fixing one error type and adding another.

## Information

Evidence: there are zero quantitative measures of summariser quality [no source, per the request itself]. The phrase "sometimes wrong" covers at least three distinct error classes [judgment]:

1. Factual errors: the summary states things the ticket does not say (hallucination).
2. Omissions: the summary drops required facts, for example dates or error codes.
3. Format errors: wrong length, wrong tone, missing fields.

These classes need different fixes. Prompt edits help format and omission. Retrieval of the full ticket text helps factual errors. Model choice sits under all three [judgment].

A1. The summariser receives the full ticket text, not a truncated version. Why not measured: the material does not state it. Validate by: log inputs for one day. If wrong: fix input pipeline before any prompt work.

A2. Agents can spend 30 minutes per week on labelling. Why not measured: the user has not answered. Validate by: ask the team lead. If wrong: use two staff members for a smaller labelled set.

A3. Volume is at least 50 summaries per day. Why not measured: the material does not state it. Validate by: count log entries for one day. If wrong: extend the evaluation window to reach n=100.

Alternative considered: switch to a larger model immediately. This loses because there is no baseline to prove the gain, the cost is unknown, and a model change cannot fix a broken input pipeline (A1).

## End

I recommend that we:

1. **Build a scored sample (deterministic, Clear).** Collect 100 recent ticket-summary pairs. Have two agents score each on a rubric: factual accuracy 40%, completeness 40%, format 20%. Pass threshold for the system: mean score at least 4 of 5, no factual error above 5% of samples. This removes the blocker "no baseline".
   Test:
   ```
   Given 100 labelled pairs,
   When the rubric is applied,
   Then each pair has accuracy, completeness, and format scores recorded.
   ```

2. **Classify errors (evaluative, Complicated).** Group every failed sample into the three error classes above. Adds the capability of targeted fixes. Step 2 MUST NOT start until Step 1 passes.
   Test: rubric as in Step 1; each failure carries exactly one class label, agreed by both scorers on a 20-sample overlap with at least 80% agreement.

3. **Build an automated harness (stochastic, Complicated).** Script the summariser over the 100 labelled tickets. Metric: mean rubric score from an LLM judge, validated against the human scores from Step 1. Baseline: current system score. Pass threshold: judge agrees with humans within ±0.3 points on the mean over n=100. Adds the capability of repeatable measurement. Step 3 MUST NOT start until Step 2 passes.

4. **Fix the largest error class, one change per run (stochastic, Complex).** Prompt or retrieval change targeting the top class from Step 2. Safe-to-fail probe: run against the harness, budget two working sessions per change. Stop condition: no gain over baseline after two sessions, then revert. Pass threshold: mean score rises by at least 0.3 points at n=100 against the Step 3 baseline. Leverage is a guess because cause and effect in prompt changes appear only after the run.

5. **Add a standing quality check (deterministic, Clear).** Sample 20 summaries per week, score with the Step 1 rubric, alert when the mean falls below 4. Adds the capability of regression detection.
   Test:
   ```
   Given a week of production summaries,
   When 20 are sampled and scored,
   Then a report with the mean score is produced, and an alert fires below 4.
   ```

If A1 proves false, replace Step 4 with an input-pipeline fix and rerun Step 3.
