## Headline

Retrospectives fail when actions lack owners, deadlines, and follow-up; run one experiment per sprint and check results first.

- Actions without owners and deadlines do not get done [judgment].
- Reviewing last actions first creates accountability and closes the loop [judgment].
- One small commitment beats a long list nobody remembers [judgment].

## Background

Your team meets regularly but the same problems stay. Attendance is good, yet decisions do not turn into changes in daily work.

## Relevance

Meetings cost roughly one hour per person per sprint [judgment]. When nothing changes, trust in the process falls and attendance will follow.

## Information

Common causes, from practice experience [judgment]:

1. Lists are too long. Teams pick five or more items. None get done.
2. No owner is named. Shared responsibility means no responsibility.
3. Actions live in a tool nobody opens again.
4. The retro never reviews the previous retro. The loop is open.
5. The same complaints repeat because the cause sits outside team control.

Assumption log:

`A1. Actions are recorded but not tracked to completion. Why not measured: the material does not state it. Validate by: check the last three retro notes for open items. If wrong: focus on cause 5 instead.`

`A2. The team controls its own process and tools. Why not measured: the material does not state it. Validate by: ask the team which one blocker needs management approval. If wrong: escalate the external blocker first.`

Alternative considered: stop retrospectives and rely on 1:1 feedback. It loses because shared problems need a shared forum [judgment], and 1:1s hide systemic patterns.

## End

I recommend that we:

1. Start the next retro by reviewing the previous actions. Increment: 10 minutes at the start of the meeting. Blocker removed: the open feedback loop. Domain: Clear, because a best practice exists. Deterministic test, written first:
   - Given the last retro's action list,
   - When the retro begins,
   - Then each item is marked done, dropped, or carried over with a reason.
2. Commit to exactly one change per retro, with one owner and one date. Increment: pick one item by dot vote before the meeting ends. Blocker removed: overload and missing ownership. Domain: Clear. Deterministic test:
   - Given the voted items,
   - When the retro ends,
   - Then the top item has a named owner and a deadline in writing.
3. Make the change visible daily. Increment: add the single action as a ticket on the team board. Blocker removed: forgotten actions. Domain: Clear. Deterministic test:
   - Given a committed retro action,
   - When the sprint board is viewed,
   - Then the action appears as a ticket with owner and status.
4. Run a four-week trial as a safe-to-fail probe. Budget: four retros. Measure: percent of committed actions completed. Stop condition: less than 50% complete after four weeks, then change the format. Domain: Complex, because the effect of the new format is visible only afterward. Stochastic test, written first: metric is completion rate, baseline is current rate, pass threshold is 80% over four retros, sample size is four actions minimum.

Sequencing: Steps 1 to 3 happen in the next retro. Step 4 MUST NOT start until its acceptance test is written. If A2 is false, replace Step 2 with escalating the external blocker to management in the same session.

## Follow-up

Conditions that change the recommendation: if the real blocker sits outside team control (A2 false), the retro format is not the problem and escalation comes first. If A1 is false and actions are tracked but nothing improves, change the retro format itself (for example, run a root-cause session using the "5 Whys" technique [1]).
