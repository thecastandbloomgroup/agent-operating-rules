## Headline

This request bundles two unrelated efforts, so split them: run the JWT (JSON Web Token) migration as a bounded, tested project, and run sign-up conversion as separate, small probes. First, the migration carries security risk that conversion work would blur. Second, conversion gains need evidence, and no baseline metric exists in the request. Third, mixing the two in one changeset makes rollback and attribution unreliable.

## Background

The request asks to replace session-based authentication in the auth service with tokens, and at the same time to improve how many visitors finish sign-up. No codebase, team size, timeline, or current conversion rate appears in the request, so several assumptions below fill those gaps.

## Relevance

Auth changes touch every authenticated path, so errors there lock users out at scale. Conversion work affects growth directly, yet its causes are not visible without measurement. Doing them as one effort doubles risk and makes results unreadable.

## Information

Evidence and assumptions:

- A1. The service is a standard web stack with session state held server-side. Why not measured: the material does not state it. Validate by: list the session read points in the code. If wrong: Step 1 scoping changes.
- A2. Token signing keys can be rotated and the platform supports two parallel auth checks during migration. Why not measured: the material does not state it. Validate by: a one-hour spike that issues a token beside a session. If wrong: add Step 0 for key management before anything ships.
- A3. No sign-up funnel baseline (visits to completed sign-ups) exists today. Why not measured: the material does not state it, and no tool can reach it here. Validate by: pull 30 days of funnel events. If wrong: skip Step 4 and run conversions probes now.
- Dual-run auth (accept both session and token during transition) is standard practice for this migration, because an abrupt cut makes rollback a full redeploy [judgment].
- Funnel drop-off causes vary per product, so no single fix wins in advance; small measured probes beat one large redesign [judgment, based on theme from [1]].

Strongest alternative: do both in one project to save coordination. It loses because a conversion change touching sign-up flows sits next to auth token logic, and a single rollback then kills both.

## End

I recommend that we run these five actions in this order:

1. Map every session read and write in the auth service into one document (deterministic; increment: one list of endpoints and middleware; blocker removed: unknown blast radius; Clear, cause and effect are known).
   - Given the endpoint inventory, When the session middleware list is compared with code, Then every session touchpoint appears in the document.
2. Add token issue and verify beside the existing session checks, with both accepted and metrics counting which path authenticates each request (deterministic; blocker removed: unsafe cutover; Complicated, because key and expiry design needs analysis; depends on Step 1).
   - Given a logged-in user, When a token is issued, Then a request with that token authenticates, and a tampered token returns 401.
3. Cut each client to tokens only, one client at a time, then remove session code after two weeks at zero session-path requests (deterministic; blocker removed: dual-state debt; Clear; Step 3 MUST NOT start before the dual-run metric in Step 2 shows stable token success rates).
4. Baseline the sign-up funnel with 30 days of events before any change (deterministic data task; blocker removed: no way to attribute wins; Clear; parallel with Steps 1 to 3 is fine because it touches metrics only).
   - Given 30 days of events, When funnel stages are joined, Then a conversion rate per step is computed with sample sizes.
5. Run two capped, parallel conversion probes, one week each, against the Step 4 baseline (stochastic; Complex, because drop-off causes show only after trials; budget: one week and one variant each; stop condition: no lift or a data-quality fault).
   - Test: metric is sign-up completion rate, baseline from Step 4, pass threshold 10% relative lift at a 95% confidence check, sample size at least 1,000 visitors per arm; accept only at that sample size.

If A2 is false, insert a key-management increment before Step 2.
