## Headline

Measure the errors first, then fix the most common error type with a controlled test.

- No one can improve "sometimes wrong" until it has a count, so logging comes first.
- Agent reviews of real cases show which error types matter, so review comes second.
- A fixed test set gives a baseline, so every change gets a pass or fail result.
- One small trial on a single error type limits the risk of a bad change.

## Background

The team added a summariser based on a large language model (LLM) to the support tool. Agents report that it is "sometimes wrong". The team has no metrics, and the request is to improve it.

## Relevance

Agents who distrust the summary will reread the full ticket. That removes the time the tool should save. A wrong summary can also send a wrong answer to a customer.

## Information

**Evidence.** The material gives no error rate, no volume, and no error examples. Therefore no number here is measured.

- Errors in LLM summaries usually cluster in a few types, such as missing facts, invented facts, wrong names or numbers, and wrong ticket status. This is 70% likely [judgment].
- The error types will come from agent comments. Thematic analysis groups comments into themes and counts the sources behind each theme [2].
- The work is classed by Cynefin domain, which describes how cause and effect relate [1].

**Assumption log**

A1. The team can change the prompt and log each summary. Why not measured: the material does not state it. Validate by: ask one engineer. If wrong: Step 1 grows and Step 4 waits.

A2. The team handles at least 300 tickets per week. Why not measured: the material does not state it. Validate by: count tickets in the last four weeks. If wrong: lengthen the trial in Step 4.

A3. Agents will give feedback if it takes one click. Why not measured: the user has not answered. Validate by: check the flag rate after one week. If wrong: sample summaries for review instead.

**Alternative considered.** Switch to a larger model now. It loses because no baseline exists, so the team cannot show that it helps. It also raises cost, which is [judgment].

## End

I recommend that we take these steps in order:

1. **Log every summary and add a one-click flag.** Increment: store ticket ID, model version, prompt version, summary text, and flag with reason. Blocker removed: no data exists. Domain: Clear, because logging is a known practice. Kind: deterministic. Test, written first:
   - Given an agent views a summary for ticket 123
   - When the agent clicks "Wrong" and picks a reason
   - Then one record holds ticket 123, both versions, the summary, and the reason

2. **Review flagged cases and interview agents.** Step 2 MUST NOT start until Step 1 holds 50 flagged summaries. Increment: read 50 flags and talk to 5 agents in one session. Blocker removed: unknown error types. Domain: Complicated, because analysis of the cases picks the fix. Kind: evaluative. Rubric, written first:
   - Criteria: share of errors per type (weight 50%), harm to the customer (30%), ease of fix (20%).
   - Pass threshold: one type holds at least 30% of weighted errors.
   - Evidence: the coded flags, with themes counted per source and any dissenting agent noted [2].

3. **Build a test set and measure the baseline.** Step 3 MUST NOT start until Step 2 names the error types. Increment: select 100 past tickets and have two reviewers mark errors on their summaries. Blocker removed: no baseline. Domain: Complicated, because the labelling method is known. Kind: stochastic. Acceptance test, written first:
   - Metric: share of summaries with at least one factual error.
   - Baseline: this step produces it.
   - Pass threshold: reviewer agreement of at least 80%.
   - Sample size: 100 tickets.

4. **Run a capped trial on the top error type.** Step 4 MUST NOT start until Step 3 passes. Increment: change the prompt for the top error type and serve it to 50% of agents. Blocker removed: no proof that a fix works. Domain: Complex, because the effect shows only after real use. The leverage of this step is a guess. Kind: stochastic. Acceptance test, written first:
   - Metric: flag rate per 100 summaries.
   - Baseline: the Step 3 rate.
   - Pass threshold: a 25% relative drop.
   - Sample size: 300 summaries per arm.
   - Budget: two weeks.
   - Stop condition: the flag rate rises 5 points above baseline.

If A1 is false, replace Step 4 with a vendor request for prompt access. If Step 2 finds no dominant type, run Step 4 on the two largest types in turn.
