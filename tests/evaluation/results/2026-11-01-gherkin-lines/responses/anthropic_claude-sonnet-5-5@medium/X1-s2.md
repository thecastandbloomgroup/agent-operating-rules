## Headline

Measure the summariser first, then change it: build a feedback log and a scored test set before any prompt or model change.

- No metric exists, so no change can be shown to help.
- Agent complaints are vague, so the error types must be named before a fix is chosen.
- A small labelled test set makes each later change a cheap, repeatable experiment.

## Background

The team added a summariser built on an LLM (large language model, a program that generates text). Agents report that it is "sometimes wrong" (per the request, user message). No metrics, logs of errors, or error types exist. The request is to improve it.

## Relevance

Agents who distrust a summary reread the full ticket, so the tool may add work instead of saving it [judgment]. Each unmeasured change risks making the summaries worse without anyone knowing.

## Information

**Evidence**

- Agents report errors, but the material gives no rate, no examples, and no error types (user message). Confidence in any cause is low.
- Omitted facts and invented details are the likely main error types for LLM summaries [judgment].
- A second LLM can score summaries as a judge. Reported agreement with human raters exceeds 80% on chat tasks [2]. This supports a scorer, but only after a check against your own raters.
- The Cynefin framework separates work where cause and effect are known from work where they appear only afterward [1]. Here the cause of errors is unknown, so the first step gathers data.

**Assumption log**

A1. The summariser works on support tickets and the tool can store each summary with its source ticket. Why not measured: the material does not state it. Validate by: ask an engineer to query one stored record. If wrong: add storage to Step 2.

A2. Agents will tag a bad summary if the tag takes one click. Why not measured: the user has not answered. Validate by: count tags after one week. If wrong: sample summaries for review instead.

A3. Two reviewers can label 100 tickets in one working session each. Why not measured: the material does not state staff time. Validate by: time the first 10 labels. If wrong: cut the set to 50.

**Alternative considered**

Switch to a larger model or fine-tune now. It loses because without a baseline nobody can show a gain, and the cost is higher [judgment].

## End

I recommend that we take these four steps, in this order:

1. **Classify the failures (Confused: the cause of errors is unknown).** Increment: collect 50 summaries that agents call wrong, and label each error type. Blocker removed: no one knows what "wrong" means. Kind: evaluative.
   - Rubric criteria and weights: error type is named from a fixed list (40%); the source ticket sentence is quoted as proof (40%); two reviewers agree (20%).
   - Pass threshold: at least 80% weighted score on every summary.
   - Evidence: the ticket text, the summary, and both reviewer labels.

2. **Add a feedback tag and a log (Clear: standard logging practice applies).** Increment: add a one-click "wrong summary" tag with a reason list. Store summary, ticket ID, prompt version, and model version. Blocker removed: no ongoing data. Kind: deterministic. Step 2 can run in parallel with Step 1.
   - Given an agent views a summary
   - When the agent clicks "wrong" and picks a reason
   - Then one record stores the tag, reason, ticket ID, prompt version, and model version

3. **Build a scored test set (Complicated: expert analysis picks the scoring method).** Increment: label 100 tickets and compute the baseline error rate. Blocker removed: no baseline. Kind: stochastic. Step 3 MUST NOT start until Step 1 ends, because the error list defines the labels.
   - Metric: share of summaries with no factual error, per two reviewers.
   - Baseline: measured in this step.
   - Pass threshold: two reviewers agree on at least 80% of items. Only then is the baseline accepted.
   - Sample size: 100 tickets.

4. **Run one prompt probe (Complex: the effect of a prompt change appears only after a run).** Increment: change the prompt to require facts to come only from the ticket, in a fixed layout. Score it on the test set. Blocker removed: no evidence on what works. Leverage is a guess. Kind: stochastic. Step 4 MUST NOT start until Step 3 gives a baseline.
   - Metric: share of summaries with no factual error.
   - Baseline: Step 3 result.
   - Pass threshold: a relative error cut of 30% [judgment].
   - Sample size: the same 100 tickets.
   - Budget: one working session and one prompt version. Stop if the error rate rises. Ship only on a pass.
