## Headline

**Restore database connection capacity first, because the 8-connection pool explains most of the latency rise.**

- The pool change from 50 to 8 connections per pod explains 687 ms of the 780 ms p95 rise (p95 means the 95th percentile). That is 88% [3].
- The cache time-to-live (TTL, how long an entry stays valid) cut from 300 s to 60 s raises database demand. It is a second cause.
- The ORM change (object-relational mapper, the code layer that builds queries) is not a measured cause. Query spans stayed flat.

## Background

The API p95 latency for `GET /customers/{id}/orders` rose from 120 ms to 900 ms after release 2026.10.21. The release changed the pool size, the cache TTL, and one query. The task is to find the cause and choose the next actions.

## Relevance

The error rate is now 0.40%, up from 0.02%. Of these errors, 96% are pool timeouts that return HTTP 503 to users [3].

## Information

**Evidence**

- The pool max_size fell from 50 to 8, and the acquire timeout fell from 30 s to 5 s [1].
- Pool acquire p95 rose from 3 ms to 690 ms [3].
- The query spans did not move. Orders p95 went from 52 ms to 58 ms. Order lines p95 went from 30 ms to 26 ms [3].
- Database CPU went from 38% to 41%, so the database is not the bottleneck [3].
- The logs show "8 of 8 connections in use" on all four pods, with up to 14 waiters [2].
- Peak load is the same: 410 and 405 requests per second [3].
- The cache miss rate rose from 12% to 31% [3].
- Connection demand follows Little's law: connections in use equal request rate times hold time [4].
- Before the release, 31 connections ran at 410 requests per second, so each request held a connection for about 76 ms [3].
- The new capacity is 4 pods times 8 connections, which is 32. Demand of 31 against capacity of 32 is 97% utilization. Queues grow fast at that level [inference].
- The higher miss rate adds queries, so it raises demand further [inference].
- The commit says the pool matches a new database limit (OPS-412) [1]. The limit value is not in the material.

**Assumption log**

A1. The trace figure "8 active connections" is per pod, not per service. Why not measured: the trace file does not state the scope. Validate by: read the per-pod pool gauge. If wrong: the capacity figure of 32 changes, and Step 2 needs a new size.

A2. The cache is read before each database query, so a miss adds one orders query. Why not measured: the code path is not in the diff. Validate by: read the cache call site. If wrong: Step 3 gains less than stated.

A3. The OPS-412 limit allows at least 44 connections for this service. Why not measured: the material does not state the limit. Validate by: Step 1. If wrong: use the condition in the End section.

**Alternative considered**

Revert the whole release. It is a safe rollback, but it also removes the limit change from OPS-412 and gives no evidence about which change matters. It loses because a one-pod config change tests the cause with less risk [judgment].

## End

3. **Restore `default_ttl_s` to 300 in a separate release.** Step 3 MUST NOT start until Step 2 passes, so the two effects stay separate. This cuts database demand because the miss rate falls toward 12%. First ask the OPS-412 owner why the TTL changed. Cynefin domain: Complicated, because the reason for the change is unknown. Kind: stochastic. Test, written first:
   - Metric: cache miss rate.

4. **Run a probe on the query change, in parallel with Steps 2 and 3.** Deploy the old query (no `selectinload`) on one canary pod for one day. This adds the capability to rule the change in or out. Cynefin domain: Complex, because the effect on connection hold time shows only after the run. Leverage is a guess: query spans were flat, so the gain is likely small. Kind: stochastic. Test, written first:

   - Sample size: 10,000 sampled requests.
   - Keep the change if the hold time drops by less than 10%.

If L is below 44 (A3 is false), replace Step 2 with Step 3 first. Then add a connection pooler (a proxy that shares database connections) before you raise `max_size`. If L is 32, pool size alone cannot fix the problem.
