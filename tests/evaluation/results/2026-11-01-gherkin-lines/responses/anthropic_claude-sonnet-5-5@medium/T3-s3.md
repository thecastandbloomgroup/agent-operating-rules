## Headline

Do the migration and the conversion work as two separate tracks, and measure the sign-up baseline first.

- The two goals share one flow (sign-up and login), so a change in one can distort the measure of the other.
- JWT (JSON Web Token) is a known design with known risks, so analysis and a staged cutover are enough.
- Conversion gains are not predictable, so run small capped experiments.
- A baseline measured before any change is the only way to tell which change moved the numbers.

## Background

The request has two goals: replace server-side sessions with JWT in the auth service, and raise the sign-up conversion rate. The material gives no stack, no traffic data, and no current conversion rate. Both goals touch the sign-up and login path.

## Relevance

If both ship together without a baseline, a drop or rise in conversion has no clear cause. A rollback of one change would also undo the other.

## Information

**Evidence**

- A JWT is a signed token that the server can check without a store lookup [1].

- A signed token stays valid until it expires, so early revocation needs extra design such as short expiry, refresh tokens, or a deny list [2].

- Session cookies allow instant server-side revocation, and the guidance for them differs from the guidance for tokens [3].

- Required sample size is 14,700 per arm. This is a calculation, not a measurement. It assumes a 10% baseline, a 1-point absolute gain, 5% significance, and 80% power [judgment].

- Confidence that the migration is routine work: medium confidence, because the stack is unknown (A1).

**Assumption log**

A1. The service is a web app with a server-side session store. Why not measured: the material does not state it. Validate by: read the auth config. If wrong: Step 2 changes its rubric inputs.

A2. Current sign-up conversion is near 10%. Why not measured: no tool can reach the analytics data. Validate by: run Step 1. If wrong: the sample size in Step 4 changes.

A3. Traffic reaches 14,700 sign-up starts per arm within four weeks. Why not measured: the material does not state it. Validate by: count last month's sign-up starts. If wrong: Step 4 needs a larger effect target or a longer run.

A4. No rule requires instant logout of all devices. Why not measured: the user has not answered. Validate by: ask the security owner. If wrong: choose a deny list or keep sessions in Step 2.

**Alternative considered**

Keep sessions and work only on conversion. This loses because the user asked for the migration explicitly. Opaque tokens with a server store are a second option. Step 2 scores that option against JWT.

## End

I recommend that we take these four actions in this order:

1. **Measure the sign-up funnel baseline.** The increment: add event tracking for each sign-up step and collect one week of data. The blocker removed: no baseline exists, so no result can be judged. Cynefin domain: Clear, because the method is standard practice. Kind: deterministic. Test:

   Given a visitor who starts sign-up
   When the visitor completes or leaves each step
   Then one event per step appears in the funnel report with the visitor's anonymous ID

2. **Choose the token design.** The increment: score JWT with short expiry and refresh tokens, JWT with a deny list, and opaque tokens. Use a Pugh matrix [16] against the current sessions. The blocker removed: the revocation risk in A4. Cynefin domain: Complicated, because expert analysis picks among several good practices. Kind: evaluative. Rubric, written first:
   - Revocation speed, weight 40%. Evidence: a measured logout test.
   - Security fit with guidance [2], weight 30%. Evidence: a checklist result.
   - Change effort, weight 20%. Evidence: an estimate in working days.
   - Operating cost, weight 10%. Evidence: a store-load estimate.
   - Pass threshold: the winner scores at least 70% and beats sessions.

   Step 3 MUST NOT start until this rubric yields a winner.

3. **Ship the chosen design behind a feature flag with dual-read.** The increment: the service accepts both session and token for one login route. The blocker removed: the all-at-once cutover risk. Cynefin domain: Complicated, because Step 2 supplies the analysis. Kind: deterministic. Test, written first:

   Given a user with a valid token and the flag on
   When the user calls a protected route
   Then the service returns 200 and creates no session record

   Given a user whose token expired
   When the user calls a protected route
   Then the service returns 401

   Step 3 MUST NOT start until Step 2 passes.

4. **Run one capped sign-up experiment.** The increment: test one change to the sign-up form, such as fewer fields. The blocker removed: unknown cause of drop-off. Cynefin domain: Complex, because the effect shows only after users respond. Leverage is a guess. Kind: stochastic. Acceptance test, written first:
   - Metric: sign-up completion rate.
   - Baseline: the Step 1 result.
   - Pass threshold: a gain of at least 1 point.
   - Sample size: 14,700 per arm.
   - Stop condition: stop at four weeks or when completion falls 2 points below baseline.

   Step 4 MUST NOT start until Step 1 has one full week of data. Step 4 MAY run in parallel with Steps 2 and 3. Assign users by random split that does not depend on the login method.

If A4 is false, replace the JWT options in Step 2 with sessions or a deny list.
