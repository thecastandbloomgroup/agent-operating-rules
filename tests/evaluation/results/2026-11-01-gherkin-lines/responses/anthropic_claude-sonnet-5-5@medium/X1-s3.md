## Headline

**Measure the summary errors first, then change the summariser against a fixed test set.**

- The team has no baseline, so no change can be shown to help.
- "Sometimes wrong" names no error type, so the fix is not yet known.
- Support agents already see every error, so a flag button gives data at low cost.
- One controlled trial then tests the most likely fix.

## Background

The support tool now has a summariser built on an LLM (large language model, a program that generates text). Support agents report that it is "sometimes wrong". The team has no metrics and no error log. The request is to make the summariser better.

## Relevance

A wrong summary can send a support agent to the wrong action on a customer ticket. Without a measure, each change is a guess, and the team cannot tell progress from noise.

## Information

**Evidence**
- Source: the user query. One statement, from support agents: "sometimes wrong". No numbers exist. Confidence in any cause is low, based on one unquantified statement.
- No theme can be counted yet, because no source disagrees or agrees in detail [no source].
- A test set of 100 tickets gives a 95% interval of about plus or minus 10 points at a 50% error rate [inference, from the normal approximation for a proportion].
- Common error types in LLM summaries are invented facts, missed facts, and wrong emphasis [judgment].

**Assumption log**

A1. The errors are mixed types, and no single type causes most of them (likely). Why not measured: the material does not state it. Validate by: label 50 summaries by error type (Step 1). If wrong: the probe in Step 4 targets the dominant type.

A2. The tool stores the ticket text and the summary. Why not measured: no tool can reach the system. Validate by: ask an engineer to open one record. If wrong: Step 2 first adds the storage.

A3. Two support agents can label 50 summaries in one session. Why not measured: the user has not answered. Validate by: time the first 10 labels. If wrong: cut the sample to 30 and widen the stated interval.

**Alternative considered**
- Switch now to a larger model. It loses because no baseline exists to show a gain, and the cost is higher [judgment].

**Cynefin note**
- Cause and effect for the errors are unknown, so the overall problem is Confused [1]. The first action gathers data to classify it.

## End

I recommend that we:

1. **Label a sample of 50 recent summaries.**
   - Increment: two support agents label each summary as correct or wrong. They add an error type: invented fact, missed fact, or wrong emphasis.
   - Blocker removed: no baseline and no known error type.
   - Kind: evaluative.
   - Cynefin: Confused, because the cause of the errors is unknown.
   - Rubric (written first):
     - Criterion 1, factual accuracy, weight 60%. Evidence: each claim in the summary matches the ticket text.
     - Criterion 2, completeness, weight 30%. Evidence: the customer request and the open issue appear.
     - Criterion 3, label agreement, weight 10%. Evidence: the two agents agree on at least 80% of labels.
     - Pass threshold: criterion 3 passes. Otherwise the labels are not trusted and the agents repeat the session.

2. **Add a "wrong summary" button with reason codes.**
   - Increment: a button that logs ticket ID, summary text, reason code, and model version.
   - Blocker removed: no ongoing error data.
   - Kind: deterministic.
   - Cynefin: Clear, because logging a user flag is a known practice.
   - Test:
     ```gherkin
     Given a support agent views a summary
     When the agent clicks "wrong summary" and picks a reason
     Then the log holds the ticket ID, summary, reason, and model version
     ```
   - Step 2 MAY run in parallel with Step 1.

3. **Build a gold set of 100 labeled tickets and a scoring script.**
   - Increment: the 50 labels from Step 1, plus 50 more from the Step 2 flags and random tickets. The script outputs the share of summaries with at least one factual error.
   - Blocker removed: no repeatable way to compare two versions.
   - Kind: deterministic.
   - Cynefin: Complicated, because the sampling method needs analysis to avoid bias.
   - Test:
     ```gherkin
     Given the gold set and a file of 100 summaries
     When the script runs
     Then it prints the error share with its 95% interval
     ```
   - Step 3 MUST NOT start until Step 1 passes its rubric.

4. **Run one capped probe: force the summary to quote the ticket.**
   - Increment: change the prompt so each fact in the summary carries a short quote from the ticket. Run it on the gold set.
   - Blocker removed: the unknown effect of grounding on invented facts.
   - Kind: stochastic.
   - Cynefin: Complex, because the effect shows only after the trial. The leverage is a guess.
   - Acceptance test (written first):
     - Metric: share of summaries with at least one factual error.
     - Baseline: the Step 3 result for the current prompt.
     - Pass threshold: a drop of at least 15 points.
     - Sample size: 100 tickets.
   - Budget: one working session. Stop and discard if the drop is under 15 points.
   - Step 4 MUST NOT start until the Step 3 script passes its test.
