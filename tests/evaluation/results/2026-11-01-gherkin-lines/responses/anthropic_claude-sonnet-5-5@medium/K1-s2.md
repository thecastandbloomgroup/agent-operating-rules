## Headline

Restore the connection pool size first, because the pool cap of 8 causes most of the slowdown.

- Pool wait time (`db.pool.acquire`) rose from 3 ms to 690 ms at p95, which covers most of the 780 ms rise [3].
- The release cut `max_size` from 50 to 8 and the acquire timeout from 30 s to 5 s [2].
- The cache TTL cut (time to live: how long an entry stays) is a smaller second cause, because cache misses rose from 12% to 31% [3].
- The ORM change does not slow queries: the `db.query orders` p95 moved from 52 ms to 58 ms [3].

## Background

The p95 latency of `GET /customers/{id}/orders` rose from 120 ms to 900 ms after release 2026.10.21. The release changed the pool size, the cache TTL, and the ORM query. The service runs 4 pods with 8 worker threads each [2].

## Relevance

The error rate rose from 0.02% to 0.40% [3]. Users now see 503 errors after a 5 s wait [1]. Every hour of delay adds more failed requests.

## Information

**Evidence**

- Pool wait p95 rose from 3 ms to 690 ms (p50: 1 ms to 140 ms) [3].
- Logs show "8 of 8 connections in use" with 6 to 14 waiters per pod, and 1,800 to 2,400 warnings per hour on 2026-10-22 against none on 2026-10-20 [1].
- Active DB connections peaked at 31 before and 8 after, so the cap limits throughput [3].
- Database CPU moved from 38% to 41%, so the database is not the bottleneck [3].
- Of the errors, 96% are `PoolTimeout` [3].
- Traffic is flat (410 against 405 requests per second), so load does not explain the rise [3].
- Query spans for `order_lines` and `serialize` are unchanged [3].
- The cache miss rate rose from 12% to 31% after the TTL fell from 300 s to 60 s [3]. More misses mean more queries, and each query holds a connection. The size of this effect is [judgment].
- Confidence that the pool is the main cause: high confidence, three independent sources (traces, logs, diff).
- Supporting source: the commit message says the pool was lowered "to match the new DB connection limit" (ticket OPS-412) [2]. The limit value is not stated.

**Assumption log**

A1. The new database limit allows at least 12 connections per pod (48 in total). Why not measured: the material does not state the limit. Validate by: ask the database owner, or run `SHOW max_connections` and check the role limit. If wrong: set the pool to the limit divided by 4 and cut workers to match.

A2. The "8 connections" in the trace is a per-pod peak. Why not measured: the trace does not say whether it is per pod or per service. Validate by: compare the pool metrics of one pod. If wrong: the pool sizing in Step 2 still holds, but the baseline changes.

**Alternative considered**

Roll back the whole release. It loses because the cache and ORM changes are not the main cause [3]. A rollback also reverts the pool change that ticket OPS-412 requested [2], and it could break the new database limit. Use rollback only if A1 proves false and no safe pool size exists.
