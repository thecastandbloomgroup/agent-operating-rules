## Headline

Remove the style choice from human review: pick one style once, then enforce it with a tool.

- The friction comes from people judging style by hand in every review, so the tool takes that judgment away.
- A one-time, time-boxed decision ends the debate better than open talk, because it has an owner and a deadline.
- A short trial with a measure shows whether the change works before the team commits.

## Background

The team disagrees on SQL format, and each review repeats the argument. The request is to fix this as a culture problem. No style guide, tool, or review data was provided.

## Relevance

Every review that debates style delays the merge and hides real defects. A rule enforced by a tool costs the team nothing after setup.

## Information

**Evidence**

- SQLFluff is a linter (a tool that checks code against rules). It checks and auto-fixes SQL style from a shared config file, per its documentation.

**Assumption log**

A1. The team reviews SQL through pull requests (proposed changes that others review). Why not measured: the material does not state it. Validate by: ask one team member. If wrong: replace the CI step with a pre-commit check only.

A2. No style guide exists today. Why not measured: the material does not state it. Validate by: search the repository for a style file. If wrong: use that guide as the baseline in Step 2.

A3. The team has CI (continuous integration: automated checks on each change). Why not measured: no tool can reach it. Validate by: look for a pipeline file. If wrong: add a pre-commit hook only.

**Alternative considered**

The alternative is a written style guide enforced by reviewers. It loses because people apply it unevenly, and each review reopens the debate [judgment].

## End

I recommend that we do these steps in order:

1. **Measure the baseline.** In one session, count style comments in the last 20 reviews. This removes the lack of data for the trial. Kind: deterministic. Domain: Clear, because counting comments has a known method.

   Given 20 merged pull requests with comments

   When we tag each comment as style or not style

   Then we record one number: style comments per review

2. **Decide the style once.** Hold one 45-minute meeting. Score the candidate styles in a Pugh matrix, using the most common current style as the baseline. This removes the open debate. Kind: evaluative. Domain: Complicated, because analysis of sample queries picks the practice.
   - Rubric criteria: matches existing code (weight 40), the tool can enforce it (weight 30), readability on five sample queries (weight 30).
   - Evidence: counts from Step 1 and the SQLFluff rule list.
   - Pass threshold: the top style scores above the baseline. If two styles tie, the team lead decides on the spot.

3. **Add the formatter to pre-commit and CI.** Configure SQLFluff with the Step 2 style. This removes manual style checks. Kind: deterministic. Domain: Complicated, because the config needs expert setup. Step 3 MUST NOT start until Step 2 has a decision.

   Given a SQL file that breaks the chosen style

   When a developer commits it or opens a pull request

   Then the check fails and shows the fix

4. **Run a four-week trial of the "no style comments" rule.** Reviewers raise no style points. Anyone who wants a style change opens a pull request on the config file. This tests the culture change. Kind: stochastic. Domain: Complex, because team response shows only afterward. Leverage here is a guess [judgment]. Step 4 MUST NOT start until the test in Step 3 passes.
   - Metric: style comments per review, from Step 1.
   - Pass threshold: 20% or less of the baseline.
   - Sample size: 20 reviews.
   - Budget: one hour of setup and four weeks.
   - Stop condition: after 10 reviews, stop if the count has not fallen, or if most of the team vetoes.

If A1 is false, replace the CI part of Step 3 with a pre-commit check only.

## Follow-up

Conditions that change the recommendation:
- If Step 1 shows fewer than 0.5 style comments per review, the problem is perception, not volume. Replace Step 4 with a team talk.
- If the trial stops at 10 reviews, return to Step 2 and rescore.
