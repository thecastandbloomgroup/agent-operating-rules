## Headline

Do the migration and the conversion work as two separate releases, so each result stays measurable.

- The migration is a known problem with several good designs, so pick the design first.
- The conversion work is an experiment, so test one change against a measured baseline.
- A shared release would confound the two results, because an auth change can itself alter sign-up completion.

## Background

The request has two goals. First, replace server-side sessions in the auth service with JSON Web Tokens (JWT, signed tokens that carry user claims) [1]. Second, raise sign-up conversion, that is, the share of visitors who finish sign-up. The material gives no stack details and no funnel data.

## Relevance

Both goals touch the sign-up and login path. A mistake in either one blocks new users, so the order of work protects revenue.

## Information

**Evidence**

- A JWT is a signed set of claims [1].
- Best current practice requires an explicit algorithm check and validation of issuer and audience [2].
- A signed token stays valid until it expires, unless the server keeps a deny list. [inference]
- Therefore, short access tokens plus rotating refresh tokens are the usual compromise. [judgment]
- The classification of the work follows the Cynefin framework [3].

**Assumption log**

A1. The service is a web app with a server-side session store and browser clients. Why not measured: the material does not state it. Validate by: read the auth service config. If wrong: Step 2 changes the token storage design.

A2. Sign-up funnel events are not tracked today. Why not measured: no tool can reach the analytics. Validate by: search the codebase for sign-up events. If wrong: shorten Step 3.

A3. Baseline sign-up conversion is 10%. Why not measured: no tool can reach the analytics. Validate by: query one week of funnel data. If wrong: recompute the sample size in Step 4.

A4. Logout and account bans must take effect within one minute. Why not measured: the user has not answered. Validate by: ask the product owner. If wrong: drop the deny list in Step 1.

**Alternative considered**

Keep sessions and do only the conversion work. This loses because the user asked for the migration. Also, server-side sessions revoke access at once. [judgment]

## End

I recommend that we:

1. **Choose the token design.** Increment: a one-page decision record. Blocker removed: no agreed design for expiry, refresh, and revocation. Kind: evaluative. Test, written first as a Kepner-Tregoe rubric [4]:
   - Criteria and weights: revocation speed 40, conformance with [2] 30, rollout risk 30.
   - Pass threshold: 70 of 100 for the chosen option.
   - Evidence: A4 answer, a checklist run against [2], and a rollback plan.

   Domain: Complicated, because experts can analyse the options and this step is that analysis.

2. **Instrument the sign-up funnel.** Increment: events for form view, submit, and success. Blocker removed: no baseline for Step 4. Kind: deterministic. Test, written first:

   ```gherkin
   Given a visitor opens the sign-up form
   When the visitor submits valid details
   Then the events view, submit, and success each record once
   ```

   Domain: Clear, because event tracking has a known best practice. This step can run in parallel with Step 1.

3. **Ship JWT issuance behind a flag for new logins.** Step 3 MUST NOT start until Step 1 passes its threshold. Increment: issue and verify tokens for 5% of logins, with sessions as fallback. Blocker removed: no working token path. Kind: deterministic. Test, written first:

   ```gherkin
   Given a user holds an access token past its expiry
   When the user calls a protected endpoint with a valid refresh token
   Then the service returns a new access token and rotates the refresh token
   ```

   Domain: Complicated, because the design from Step 1 sets the correct practice.

4. **Run one sign-up probe after Step 3 reaches 100%.** Step 4 MUST NOT start until Step 2 shows one week of data and the auth cutover is stable. Increment: remove one optional form field for half of the visitors (an A/B test). Kind: stochastic. Test, written first:
   - Metric: sign-up completion rate.
   - Baseline: the Step 2 value, assumed 10% (A3).
   - Pass threshold: a gain of 2 points.
   - Sample size: about 3,600 visitors per arm, at 5% error and 80% power. [inference]
   - Budget: two weeks.
   - Stop condition: stop early if completion in the test arm falls 2 points below the baseline.

   Domain: Complex, because the effect of a form change shows only after real users act. The leverage of this probe is a guess.

If A4 is false, drop the deny list in Step 1 and use plain short-lived tokens.

- If A3 is false by more than 5 points, recompute the sample size before Step 4.
