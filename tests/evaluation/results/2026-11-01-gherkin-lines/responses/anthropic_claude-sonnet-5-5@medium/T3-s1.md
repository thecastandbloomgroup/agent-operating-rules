## Headline

Migrate to JWT in a staged rollout and test one sign-up change separately, so each result stays measurable.

- The two goals have different test types: the migration is deterministic and the conversion work is stochastic.
- A JWT (JSON Web Token, a signed token that carries user claims [1]) removes the session store lookup but makes instant logout harder.
- Sign-up conversion needs a baseline first, because the material gives none.
- Both changes on the same users at the same time would confound the conversion result.

## Background

The request has two parts. The first part moves the auth service from server-side sessions to JWT. The second part raises the share of visitors who finish sign-up. The material states no stack, no traffic, and no current conversion rate.

## Relevance

Auth changes can lock users out, and a lockout lowers conversion. So the two goals interact, and the order of work matters.

## Information

Evidence:

- JWT is a signed claim format. Its own specification defines it.

  RFC 7519 defines the token format [1].

- Known JWT attacks include weak algorithm choice and missing claim checks.

  RFC 8725 lists best practices that counter them [2].

- A server-side session can be ended at once by deleting it. A stateless JWT stays valid until it expires.

  The OWASP session guidance covers server-side invalidation [3].

- A short access token (15 minutes) with a rotating refresh token limits that exposure. [judgment]
- A sign-up test of 5% baseline and a 1 point absolute gain needs about 8,000 users per arm, at 80% power and 5% significance. [judgment]
- No source states our current baseline. [no source]
