## Headline

Measure the failures first, then quarantine the flaky tests, then fix the top cause.

- The same code gives different results, so the cause stays unknown until failures are grouped.
- A few causes explain most flakiness, so grouping finds the fix with the most effect.
- Quarantine keeps the team unblocked while the fixes proceed.
- A repeated-run test with a pass threshold proves each fix.

## Background

The request says only that the build is flaky. A flaky build passes and fails on the same code. The material gives no logs, no tool names, and no failure rate. This response therefore assumes a typical continuous integration (CI) setup and gives a plan that works without more detail.

## Relevance

Each false failure blocks merges and wastes reviewer time. Teams also learn to ignore red builds, so real defects pass unnoticed.

## Information

Evidence:

- Google reported that 1.5% of its test runs showed a flaky result.

  [1]

- Google also reported that about 16% of its tests show some flakiness.

  [1]

- Luo et al. studied flaky-test fixes in open-source projects. Async waits caused 45%, concurrency 20%, and test order 12%.

  [2]

- Confidence is medium. Two sources agree on direction, but they come from different settings.

Assumptions:

A1. The build is a CI build that fails at random on unchanged code. Why not measured: the material does not state it. Validate by: rerun one failed job on the same commit. If wrong: the cause is a code change, so skip this plan and bisect.

A2. Test code causes most failures, not CI infrastructure. Why not measured: no tool can reach the logs. Validate by: Step 1 groups the errors. If wrong: replace Step 3 with a runner fix.

A3. At least 50 recent run logs are available. Why not measured: the material does not state it. Validate by: list the runs in the CI dashboard. If wrong: collect new runs first, at a cost of one day.

Alternative considered: retry failed tests automatically. It loses because it hides the flake rate and slows the build [judgment].

## End

I recommend that we take these four actions in order.

1. Export the last 50 main-branch runs and group each failure by test name and error text.
   - Blocker removed: nobody knows whether tests or infrastructure fail.
   - Kind: deterministic.
   - Domain: Confused, because the cause is unknown and this output classifies the later steps [18].
   - Test, written first:

     Given 50 run logs from the main branch

     When the script groups failures by test and error

     Then each failure appears once and the group counts sum to the total failures [14]

2. Quarantine every test that both passed and failed on one commit. Step 2 MUST NOT start until the test in Step 1 passes.
   - Blocker removed: false red builds stop merges.
   - Kind: deterministic.
   - Domain: Clear, because quarantine is a known best practice.
   - Test, written first:

     Given test T passed and failed on the same commit

     When the quarantine job runs

     Then T runs in a non-blocking job and the main build excludes T

3. Fix the largest failure group from Step 1. Reproduce it locally 20 times before the change. Step 3 MUST NOT start until the test in Step 1 passes.
   - Blocker removed: the largest source of red builds.
   - Kind: stochastic.
   - Domain: Complicated, because the Step 1 report and local reproduction pick the fix.
   - Test, written first: the metric is failures per run of the fixed tests. The baseline is the Step 1 rate. The threshold is 0 failures. The sample is 100 consecutive runs.

4. Run a probe: execute the suite 20 times on a branch with random test order. Run it in parallel with Steps 2 and 3, after Step 1.
   - Capability added: it finds hidden order dependence.
   - Kind: stochastic.
   - Domain: Complex, because order effects show only after the runs. The leverage is a guess.
   - Budget: 20 CI runs. Stop if any run takes more than twice the normal time.
   - Test, written first: the metric is the count of distinct new failing tests. The baseline is the Step 1 list. The sample is 20 runs. Accept the finding when a new failing test repeats in at least 2 runs.
