## Headline

I recommend that we stop debating style and let a formatter decide, after one timeboxed vote on its settings.

- The friction comes from taste disputes, which have no correct answer, so a tool must settle them [judgment].
- A formatter enforced in CI removes style from review.
- One reformat commit gives everyone the same starting point.
- A four-week trial with a measure shows whether the culture changed.

## Background

The team has no shared SQL format. Each review includes style comments. The request is to end this friction.

## Relevance

Every review that debates style delays real feedback on logic. The cost repeats with each pull request until the team sets one rule.

## Information

**Evidence.** No team data was provided, so this analysis rests on judgment.

- Style disputes are about preference, not correctness [judgment].
- A rule enforced by a tool is less personal than a rule enforced by a colleague [judgment].
- Confidence that tool enforcement cuts style comments by half or more: likely (66 to 100%), based on judgment only.

**Domain.** Choosing a style is Complicated: experts can compare the options [1]. Changing team behavior is Complex: the effect shows only afterward [1].

**Assumption log**

A1. The team uses pull requests and has CI. Why not measured: the material does not state it. Validate by: look for a CI config file in the repo. If wrong: Step 2 uses a pre-commit hook instead.

A2. The team uses one SQL dialect in one repo. Why not measured: the material does not state it. Validate by: list the SQL folders. If wrong: configure one formatter profile per dialect.

A3. One person, such as the team lead, can break ties. Why not measured: the user has not answered. Validate by: ask the lead for five minutes. If wrong: Step 1 goes to the lead's manager.

**Alternative considered.** Write a prose style guide and enforce it in review. It loses because reviewers stay the enforcers, so the friction stays [judgment].

## End

I recommend that we take these steps, in this order:

1. **Choose the style in one 45-minute session.** Kind: evaluative. Domain: Complicated, because the options can be compared by analysis. This removes the blocker that no rule exists. Score each option with a Kepner-Tregoe layout [3]. Write the rubric before the session:
   - Criteria and weights: enforceable by a tool (40), matches most existing code (30), readable diffs (20), low setup cost (10).
   - Evidence: a formatter run on five real files per option.
   - Pass threshold: a weighted score of 70 out of 100.
   - If no option passes, the formatter's default settings win. The tie-break owner is the person named in A3.

2. **Add the formatter to CI as a required check.** Kind: deterministic. Domain: Clear, because the practice is standard. This removes the human enforcer. Step 2 MUST NOT start until Step 1 ends. Test, written first [2]:

   Given a pull request with a SQL file that breaks the chosen style
   When the CI format check runs
   Then the check fails and names the file

   Given a pull request with a SQL file that follows the style
   When the CI format check runs
   Then the check passes

3. **Reformat the whole repo in one commit with no logic changes.** Kind: deterministic. Domain: Clear. This gives all branches one baseline. Step 3 MUST NOT start until the test in Step 2 passes. Add the commit to the blame-ignore list so history stays readable. Test:

   Given the main branch with all existing tests passing
   When the reformat commit is applied
   Then all tests still pass and the CI format check passes on every SQL file

4. **Run a four-week trial of the rule "reviewers do not comment on format".** Kind: stochastic. Domain: Complex, because team reaction is visible only afterward. Treat it as a safe-to-fail probe. Count the baseline in parallel with Step 1, using the last 20 reviews. Leverage is a guess. Acceptance test, written first:
   - Metric: style comments per review.
   - Baseline: the count from the last 20 reviews.
   - Pass threshold: a 50% drop or more.
   - Sample size: 20 reviews after Step 3.
   - Budget: five minutes per week to count.
   - Stop condition: if the count is not lower after 10 reviews, hold a 30-minute retro and change the rule.

If A1 is false, replace the CI check in Step 2 with a pre-commit hook.
