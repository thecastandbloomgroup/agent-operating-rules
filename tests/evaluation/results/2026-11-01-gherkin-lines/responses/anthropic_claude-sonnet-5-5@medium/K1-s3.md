## Headline

Raise the database pool size, which the release cut from 50 to 8, and then restore the cache time to live (TTL).

- The pool cap is the main cause: wait time for a connection (`db.pool.acquire`) explains 139 of the 162 ms rise in median latency.
- The cache TTL cut is a second cause, because the miss rate rose from 12% to 31%.
- The ORM change (object-relational mapper, the code layer that builds database queries) is not a cause, because query times did not change.
- The fix is a config change that can be tested in one session.

## Background

The p95 latency (the time under which 95% of requests finish) of `GET /customers/{id}/orders` rose from 120 ms to 900 ms after release 2026.10.21. The release changed the pool, the cache TTL, and the ORM query. The attached logs, traces, and diff are the evidence.

## Relevance

The error rate rose from 0.02% to 0.40%. Users now get 503 responses after a 5 s wait. Each hour of delay adds more failed requests.

## Information

**Evidence**

- Median `db.pool.acquire` rose from 1 ms to 140 ms. The p95 rose from 3 ms to 690 ms [2].
- Median total latency rose from 48 ms to 210 ms, so the pool wait explains 139 of 162 ms (86%) [2].
- Query spans did not change. `db.query orders` p95 went from 52 ms to 58 ms [2].
- Database server CPU went from 38% to 41%. The database has spare capacity [2].
- Traffic did not change: 410 requests per second before, 405 after [2].
- The diff cut `max_size` from 50 to 8 and `acquire_timeout_s` from 30 to 5 [3].
- Pool warnings were absent on 2026-10-20. They ran at 1,800 to 2,400 per hour on 2026-10-22 [1].
- 96% of the errors in window B are `PoolTimeout` [2].
- The cache miss rate rose from 12% to 31% after the TTL fell from 300 s to 60 s [2]. Misses add database queries, so they raise pool demand.
- Peak service connections in window A were 31. The new cap of 8 per pod is far below that demand [2].
- The ORM change does not explain the delay. The `order_lines` query already ran before the release, and its p95 fell from 30 ms to 26 ms [2].
- Confidence that the pool cap is the main cause: high, three independent sources (traces, logs, diff).
- Confidence that the cache TTL is a secondary cause: likely. The `cache.get` span is unchanged, so the effect is indirect. [judgment]
- The ticket text says the pool was lowered to match a new database connection limit [3]. The limit value is not in the material.

**Assumption log**

A1. The new database limit allows at least 40 connections for this service (4 pods of 10). Why not measured: the material does not state it. Validate by: read ticket OPS-412 or ask the database owner. If wrong: use the stated limit and add a connection pooler.

A2. The pool size of 8 applies per pod. Why not measured: the traces do not label the scope of the connection count. Validate by: read the pool metrics per pod. If wrong: the cap is 8 for the whole service, and the new size must still reach about 40.

**Alternative considered**

Roll back the whole release. It loses because it also reverts the ORM change, which causes no harm. The old pool size of 50 may also break the new database limit from OPS-412 [3].
