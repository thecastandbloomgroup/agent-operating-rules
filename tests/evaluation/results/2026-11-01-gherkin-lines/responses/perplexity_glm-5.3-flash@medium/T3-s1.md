# Headline

Migrate to short-lived JWTs with a revocable refresh-token store, run both token formats in parallel until each client passes the old tests, and treat sign-up conversion as a measured experiment, not a redesign.

1. A stateless access token cannot be deleted server-side, so a refresh-token store must exist before cut-over to keep logout working.
2. A dual-run behind a flag lets each client switch only after it passes the login, refresh, and logout tests.
3. Funnel instrumentation comes before any sign-up change, so a lift is measurable against a baseline instead of a guess.

# Background

The request asks for two changes together: replace server-side sessions with JWTs, and raise sign-up conversion. The material gives no data on the current auth design, no client list, and no funnel metrics.

# Relevance

Token format touches every request path, so a wrong cut-over is costly to reverse. Sign-up changes without a baseline cannot show any lift, because there is nothing to compare against.

# Information

**Evidence**

A JWT carries claims that a verifier checks with a key [1]. A verifier can therefore accept it without a session lookup. Because the token holds its own claims, no server action can delete it before it expires [1]. So logout and credential loss need a server-side deny mechanism for refresh tokens. No quantitative data exists in the material, so the plan starts with measurement and analysis rather than with a fix [judgment].

**Assumption log**

- A1. Current sessions allow server-side logout. Why not measured: the material does not state the auth design. Validate by: read the logout handler in the auth service code. If wrong: the refresh store becomes a hard requirement rather than a design choice; the plan holds.
- A2. All clients are first-party and can ship an update on schedule. Why not measured: the material does not list clients. Validate by: list clients and their release cycles. If wrong: extend the dual-run by one release cycle per outside client.
- A3. No funnel metrics exist today. Why not measured: the material provides none. Validate by: check the analytics event list. If wrong: skip the instrumentation step and set the baseline from existing data.
- A4. Sign-up traffic is under a few thousand sessions per week. Why not measured: no data provided. Validate by: query sign-up events after the instrumentation step. If wrong: the reach the sample size in a shorter window [judgment].

**Alternative considered**

Keep sessions and change only the sign-up flow. It loses because the migration is an explicit request, and with a refresh store both formats give the same logout behavior, so the security trade-off that favors sessions disappears [judgment].

# End

I recommend that we run these five steps. Step 5 runs in parallel with Steps 2 and 3 once it has a baseline from Step 4.

1. **Token design decision record** (evaluative, Complicated, because analysis must pick one practice among several good ones). Increment: a one-page decision record, one working session. Blocker: nothing can be built until token lifetimes, key rotation, and revocation policy are decided. Test: write the rubric first. Criteria and weights: logout support 0.4, request-path cost 0.2, rollout risk 0.2, key-rotation safety 0.2. Pass threshold: one option leads by at least 2 points on a 10-point scale in a Pugh matrix [2].

2. **Refresh-token store with rotation and deny-list** (deterministic, Clear, because one known step applies standard practice). Blocker: adds revocable logout to a stateless design. Test:
```gherkin
Given a valid refresh token
When the client sends it to the token refresh endpoint
Then the service returns a new access token and marks the used token denied
```
Step 3 MUST NOT start until Step 1 passes this test.

3. **Dual-run behind a flag, one client at a time** (deterministic, Complicated, because the per-client analysis decides the switch order). Blocker: removes the format change from one risky cut-over. Test per client:
```gherkin
Given a client switched to the JWT path
When it completes login, refresh, and logout
Then no session record is read or written
```

4. **Instrument the sign-up funnel** (deterministic, Clear, because one known step applies standard practice). Increment: one event per funnel step, one working session. Blocker: no baseline exists, so any later lift is unmeasurable. Test:
```gherkin
Given a new visitor
When each funnel step completes
Then one event with the step name reaches analytics
```

5. **Capped A/B probe on the top drop-off step** (stochastic, Complex, because cause and effect are visible only after the run, so leverage is a guess). Metric: conversion rate of that step. Baseline: Step 4 data. Threshold: 5 percent relative lift at 95% confidence. Sample size: set after Step 4 (3,000 sessions per variant) [judgment]. Stop condition: a drop of more than 2 percentage points. Budget: 4 weeks or 2 variants, whichever ends first.

# Follow-up

**Condition that changes the recommendation:** if A1 is false and logout must be instant, add an edge-checked deny-list for access tokens before Step 3.
