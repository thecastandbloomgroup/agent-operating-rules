## Headline

Restore the connection pool capacity first; the pool downgrade in release 2026.10.21 caused the latency rise. Support:

- Pool wait grew from 3 ms to 690 ms at p95 (the 95th percentile), and 690 ms is 77% of the 900 ms request total [1].
- Database supply is not the constraint: CPU moved from 38% to 41% and request rate stayed flat at 410 to 405 per second [1].
- Cache miss rate rose from 12% to 31%, but cache read spans stayed at 2 to 5 ms, so the cache adds database load, not latency per request [1].
- ORM query spans stayed flat at 52 to 58 ms p95, so the ORM change is not the cause [1].

## Background

The p95 latency of `GET /customers/{id}/orders` rose from 120 ms to 900 ms after release 2026.10.21, deployed 2026-10-21 14:05 UTC [1] [3]. The release changed three areas: the connection pool (a fixed set of reuseable database connections), the cache time to live (TTL), and one ORM (object relational mapper) query that loads order lines [3].

## Relevance

Error rate rose from 0.02% to 0.40%, and 96% of errors are pool timeouts, so customers see failures now [1]. Logs show 1,800 to 2,400 pool exhausted warnings per hour against none before the release [2].

## Information

The three release changes split the case into three non overlapping parts: pool config, cache config, ORM query. Compare each against the pre release baseline, window A [1].

**Pool.** Acquire wait rose from 3 ms to 690 ms p95, and PoolTimeout errors are 96% of all errors [1]. Logs show "pool exhausted: 8 of 8" on three pods within 7 seconds, with 6 to 14 waiters each [2]. The deployment runs 4 pods with 8 worker threads each, so 32 workers now share pools capped at 8 connections per pod [3]. Therefore demand for connections exceeds the cap whenever requests hold connections longer, because each waiting worker adds queue time.

**Cache.** TTL fell from 300 s to 60 s, and miss rate rose from 12% to 31% [1] [3]. Cache spans stayed flat, so each miss costs little directly [1]. However, each miss adds a database read, which lengthens the time a worker holds its connection and feeds the pool queue. Confidence: high, three independent measurements agree [1] [2] [3].

**ORM.** The added `selectinload` did not raise query spans: orders query p95 moved 52 to 58 ms, order lines p95 30 to 26 ms, and database CPU stayed low [1]. Keep the change.

**Assumption log**

A1. The pool limit applies per pod. Why not measured: the diff does not state the config scope. Validate by: read the config loader or one boot log. If wrong: the service wide pool is 8 connections total, and step 1 sets a larger total instead. Per pod is very likely (90 to 100%), because three separate pods each report their own "8 of 8 in use" at the same time [2].

A2. Ticket OPS-412 defines a service wide connection limit for the database. Why not measured: the ticket is not attached. Validate by: read OPS-412. If wrong: the guard in step 3 uses the real limit instead.

**Alternative considered**

The ORM `selectinload` change caused the slowdown. It loses because query spans did not rise and database CPU stayed at 38 to 41%, so the database shows no extra work [1].

## End

I recommend that we recover capacity in four steps.

1. **Raise the pool (Clear).** Write the test first, then change `max_size` from 8 to 16 and `acquire_timeout_s` from 5 to 30 in `config/db.yaml`; deploy to one pod, and deploy to all four within one hour.
   Given 405 requests per second and 16 connections per pod
   When p95 of `db.pool.acquire` is measured over 1,000 requests
   Then p95 acquire is under 10 ms and the PoolTimeout count is zero.
   This removes the pool queue behind 77% of the latency and the timeout errors. Clear domain: cause and effect are known from traces and logs, so a one step config fix applies [5].

2. **Restore the TTL (Clear).** Change `default_ttl_s` from 60 to 300 in `config/cache.yaml` in the same deploy window.
   Given `default_ttl_s` at 300
   When 1,000 requests run against keys with a 5 minute reuse pattern
   Then the miss rate is at or below 15%.
   This cuts database reads per request, which shortens connection hold time. Clear domain: the effect follows from step 1 evidence [5].

3. **Add a limit guard (Complicated).** Add a boot check that fails startup when pods times `max_size` exceeds the OPS-412 limit. Step 3 waits until OPS-412 is read, because step 1, step 2 do not. 
   Given pods times `max_size` above the OPS-412 limit
   When the config loader boots
   Then startup fails with a message that names the limit.
   This prevents a repeat at the next release. Complicated domain: the correct guard needs analysis of the ticket before the practice is chosen [5].

4. **Verify the ORM change (Clear).** Run one profile with SQL statement counting, and keep `selectinload` when it passes.
   Given a customer with 50 orders and 10 lines per order
   When `orders_for_customer` runs with statement counting on
   Then exactly 2 SQL statements run and order query spans stay under 60 ms p95.
   This confirms the ORM change is safe to keep. Clear domain: a direct measurement answers it [5].

Steps 1 and 2 start now. Step 4 runs after step 1 passes.
