## Headline

Stop the culture problem by mechanizing the style choice: a pinned formatter plus a CI gate removes style from human review.

1. A tool applies one style to every SQL file, so no human judges style again.
2. A CI gate rejects unformatted SQL before a reviewer sees it.
3. One team decision about the config replaces a debate in every review.
4. A measurement probe confirms the review friction actually falls.

## Background

The team disagrees on the way to format SQL. The same style arguments reopen in each code review. The request is to remove this friction, which the material frames as a culture problem.

## Relevance

Review time now buys style edits, not logic checks. A mechanized rule ends the debate within one or two working sessions.

## Information

The style debate is a deterministic policy question, so a tool can decide it instead of the reviewers. [judgment] Rules like these work only when they are enforced, not when they are written down. [judgment] The Cynefin framework sorts problems by how cause and effect relate, and here the fix path is Clear or Complicated, not Complex. [18]

Assumption log:

A1. The team keeps SQL in one shared repository. Why not measured: the material does not state it. Validate by: open the repository. If wrong: use a pre-commit hook instead of CI.
A2. Reviews happen as pull requests. Why not measured: the material does not state it. Validate by: read three closed reviews. If wrong: run the check locally before each commit.
A3. The team can change CI configuration. Why not measured: the material does not state it. Validate by: check who owns the CI file. If wrong: ship the check as a local script first.

Alternative considered: publish a written style guide with no tool. It loses because humans still check style by hand, so the debate stays in every review. [judgment]

## End

I recommend that we take five actions.

**Step 1. Pick the tool and config.** [15]
- Increment: in one 45-minute session, format three sample files with two candidate tools, score the results, and commit the winning config file.
- Blocker removed: the team has no single source of truth for style.
- Kind and test (evaluative). Rubric: readability (weight 0.4), diff size against current code (weight 0.3), dialect support (weight 0.3). Evidence per criterion: the printed diff. Pass threshold: total score of 4 of 5 or more, plus a majority vote.
- Domain: Complicated, because analysis of the diffs picks among good practices.
- Write the rubric before the session. Run it, then commit.

**Step 2. Format the codebase once.**
- Increment: in one session, run the pinned tool on every SQL file and merge one "style only" pull request.
- Blocker removed: mixed style across the files makes every diff noisy.
- Test (deterministic), written first:

```gherkin
Given the pinned config file
When the formatter runs twice on every SQL file
Then the second run changes zero bytes
```

- Domain: Clear, because the steps are known to everyone with the tool in hand.

**Step 3. Add a CI gate.**
- Increment: in one session, add the format check to CI so it fails the build on unformatted SQL.
- Blocker removed: reviewers checking style by hand.
- Test (deterministic), written first:

```gherkin
Given a pull request with one unformatted SQL file
When CI runs the format check
Then the build fails and prints the formatter command
```

- Domain: Clear, because cause and effect are known to everyone.
- Sequencing: Step 3 MUST NOT start until the pull request in Step 2 merges.

**Step 4. Move style out of the review scope.**
- Increment: in one session, add two lines to the contribution guide that mark style comments as out of scope and point to the config file.
- Blocker removed: reviewers keep debating by habit.
- Test (deterministic), written first:

```gherkin
Given the updated contribution guide
When a reviewer reads the review scope section
Then the text names format checks as automated and out of scope
```

- Domain: Clear, because it is one known edit with a fixed acceptance criterion.

**Step 5. Probe: measure the friction change.**
- Increment: count style comments per pull request for the last 20 merged pull requests (baseline), then for 20 pull requests after the gate. [A2]
- Blocker removed: the claim "friction is fixed" has no measure.
- Kind and test (stochastic). Metric: style-related review comments per pull request. Baseline: the count from the 20 pull requests before the gate. Pass threshold: the count falls to 1 or fewer per 10 pull requests. Sample size: 20 pull requests after the gate.
- Stop condition and budget: if style comments do not fall after those 20 pull requests, reopen the config in one session, then stop.
- Domain: Complex, because team behavior shows cause and effect only afterward. The leverage estimate here is a guess. Run this probe in parallel with nothing; it runs after the gate because the baseline needs the gate in place.

Step 1 MUST run first because the config file is the single source of truth for every later step.

## Follow-up

Conditions that change the recommendation: if A1 is false, replace Steps 2 and 3 with a pre-commit hook in Step 2. [A1] If A2 is false, change the Step 5 measure to commit-review notes. [A2]
