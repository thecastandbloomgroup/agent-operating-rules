## Headline

The summariser has no measured error types, so first collect agent edits and label a sample, then publish two error rates, then make one fix and prove it on a fixed sample.

- Support points: "sometimes wrong" cannot improve while it is one word instead of labelled classes.
- A sample of 50 summaries gives a baseline in one to two weeks at a low cost.
- One change at a time, judged against the same labels, prevents silent regression.
- Agent edits are free ground truth, so capture them before anything else.

## Background

A support tool now generates summaries with an LLM. Agents report it is "sometimes wrong" with no examples or counts.

The request is to make it better, and no metrics exist.

## Relevance

Without error types, any prompt change is a guess. A labeled sample turns "sometimes wrong" into two numbers that a fix can move.

## Information

Thematic view of the material: one theme, "the output is wrong", from the agent group, with count 1; no source in the material splits it into classes [3].

Claims that the plan depends on, all without a source for this tool:

1. The most common LLM summary faults are added facts and missing facts [judgment].
2. A 50-item labeled sample is enough to rank the fault classes [judgment].
3. An unmeasured prompt change can reduce quality as easily as raise it [judgment].

## End

I recommend that we take these steps in this order. Step 2 MUST NOT start before step 1 stores logs. Steps 3 and 4 MUST NOT start before step 2 labels all 50 items.

**Step 1. Capture ground truth.**
- Increment: in one session, log ticket ID, generated summary, and agent edits, and add a one-click "wrong fact" flag.
- Capability added: every edit and flag becomes a labeled example at zero extra effort.
- Kind: deterministic. Test, written first (per Gherkin [14]):
  ```gherkin
  Given a closed ticket with a summary
  When an agent edits the summary or clicks the flag
  Then the log stores the ticket ID, the old summary, the new summary, and the flagged fact
  ```
- Cynefin: Clear, because the effect of logging is known to everyone.

**Step 2. Label a sample of 50.**
- Increment: two people label 50 random summaries against the ticket with a three-class taxonomy: added fact, missing fact, other.
- Blocker removed: "wrong" becomes ranked classes.
- Kind: evaluative. Rubric, written first: three classes at equal weight, weighted disagreement score based on class match; each label needs the ticket line as evidence; pass at 80% labeler agreement; reject the taxonomy and re-design if agreement is below 80%.
- Cynefin: Complicated, because each label needs analysis of summary against ticket.

**Step 3. Publish two metrics.**
- Increment: a one-page table with the added-fact rate and the missing-fact rate at n=50, with dates.
- Blocker removed: the team can see which rate is higher and set a target.
- Kind: deterministic. Test, written first:
  ```gherkin
  Given the labeled sample from step 2
  When the report is generated
  Then it shows both rates, the sample size 50, and the window dates
  ```
- Cynefin: Clear, because counting labeled items has a known best procedure.

**Step 4. Make one fix and prove it.**
- Increment: one change only. If missing facts lead the table, pass more ticket text. If added facts lead, add a source-quoting rule to the prompt.
- Blocker removed: the top error class falls, verified instead of assumed.
- Kind: stochastic. Acceptance test, written first: metric is the added-fact rate for the quoting fix or the missing-fact rate for the context fix; baseline is the step 3 rate; pass threshold is a rate below baseline with the other rate not higher; sample size is 100 fresh summaries; accept only at that size.
- Cynefin: Complex, because the effect of a prompt change shows only afterward [18]. This is a safe-to-fail probe, capped at one change and 100 samples [18].

**Step 5. Keep the loop running.**
- Increment: each month, label 25 fresh summaries and compare against the step 3 baseline.
- Blocker removed: a rejected change cannot re-enter the tool unnoticed.
- Kind: stochastic. Acceptance test, written first: metric is either rate; baseline is the step 3 value; pass is at or below baseline; sample size is 25; two failed cycles trigger a new step 4.
- Cynefin: Clear, because repeating a defined measurement has a known procedure.
