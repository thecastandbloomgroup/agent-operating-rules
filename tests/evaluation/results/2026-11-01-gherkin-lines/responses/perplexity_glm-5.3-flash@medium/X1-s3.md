## Headline

Instrument the tool, audit a sample, set a baseline, then fix one measured error cause and re-test; do not touch the prompt before the audit.

- No metrics exist today, so every prompt change is a guess with no way to check the result.
- Five steps over about 3 to 4 weeks produce an error rate, a cause ranking, and one repaired cause.
- Prompt changes run as capped probes until the audit shows the largest cause.

## Background

An LLM summariser was added to a support tool. Agents report incorrect summaries. No measurements exist. The request is to improve the summariser.

## Relevance

A wrong summary costs each agent time to verify and repair, on every ticket. Without a baseline, no change can show whether it helped.

## End

I recommend that we run five steps. Each step names its task kind, its test, and its Cynefin domain, which classifies the problem by how cause and effect behave. [18]

**Step 1. Add a rating control with a wrong-reason picker.** Kind: deterministic. Domain: Clear, because it is one known practice with a visible result. Increment: one control, three categories (factual error, missing fact, style), stored with ticket ID, in one session. Blocker: it removes the missing signal for "wrong". Test, written before the work, in Given-When-Then form: [14]

```gherkin
Given an agent opens a summary
When the agent selects a wrong-reason category
Then the tag, ticket ID, and timestamp are stored in the log
```

**Step 2. Audit 50 sampled summaries.** Kind: evaluative. Domain: Complicated, because expert analysis of the sample picks the dominant failure. Run in parallel with Step 1; it needs no agent tags. Increment: score 50 summaries against their source tickets, in one session. Blocker: it produces the cause ranking and the baseline rate. Rubric, written before scoring: factual accuracy weight 0.5, completeness of key facts and actions weight 0.3, style weight 0.2; pass is 4.0 of 5.0 per summary; two reviewers score each criterion against ticket text; agreement target is 80%.

**Step 3. Set the metrics and baseline.** Kind: stochastic. Domain: Complicated, because the thresholds need analysis of the Step 2 result. Increment: record three numbers, in one session: factual errors per 100 summaries, missing-fact rate per 100, and agent rating rate. Blocker: it turns opinion into a number that later changes must beat. Acceptance test, written first: metric is factual errors per 100; baseline is the Step 2 result; pass threshold for any later change is a drop of 10 or more per 100; sample size is 50.

Step 3 MUST NOT start before Step 2 concludes. Step 4 MUST NOT start before Step 3 states the baseline.

**Step 4. Fix the top error cause and re-test.** Kind: stochastic. Domain: Complex, because cause and effect in LLM output appear only after the run, so this is a safe-to-fail trial: small, measured, with a stop condition. Increment: add the top error examples to the prompt or the retrieval step, then re-audit 50 fresh summaries. Blocker: it removes the largest measured cause. Budget: one week, one engineer. Stop condition: no drop after one cycle, revert to the prior prompt. Acceptance: the drop in factual errors per 100 meets the Step 3 threshold at n=50.

**Step 5. Label low-trust summaries.** Kind: deterministic. Domain: Clear, because cause and effect are known to everyone: a label above a summary tells the agent to check. Increment: one display rule, in one session. Blocker: it caps the harm to agents while the error rate stays above threshold. Test, written first:

```gherkin
Given the rolling factual error rate is above 5 per 100
When an agent opens a summary
Then the label "verify against the ticket" shows above the summary
```
