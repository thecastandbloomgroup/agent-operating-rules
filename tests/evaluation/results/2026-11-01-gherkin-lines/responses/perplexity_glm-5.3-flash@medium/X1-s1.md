## Headline

Add measurement first, then fix the two failure modes that measurement exposes: build a truth set, rate the current summaries against it, and gate the output so a failed check yields no summary instead of a wrong one.

1. "Sometimes wrong" has no meaning until we count the error types and their rates.
2. The current summary failures fit three groups: untrue statements, missing facts, and poor length or form [inference from common LLM failure modes, to be confirmed by labeling].
3. Truth is available in the ticket itself: every summary statement can be checked against the source messages.
4. A gated output ("no summary") removes the harm of wrong summaries before any model change is proven.

## Background

The support tool now generates summaries with an LLM. Agents report wrong summaries, with no detail and no metrics. The request is to make the summariser better.

## Relevance

Without measurement, any prompt or model change is a guess and cannot be verified. A wrong summary also costs agents trust: after a bad start they probably skip the feature.

## Information

Evidence and analysis:

- The complaints contain a taxonomy of errors. Thematic analysis of user feedback is a standard method: group statements into themes, count sources per theme, and look for disagreement [3], [5]. Agents are primary sources here: they saw the failures. So step 1 labels real cases and counts themes.
- The cause-effect pattern for this work is Complex: the effect of a prompt change is visible only after a run [18]. Therefore fixes must be safe-to-fail probes with a measure, a stop condition, and a budget.
- The ticket text is a primary ground truth per case. A statement check against the source messages converts a judgment task into a verification task.
- Confidence in the plan shape: high, per the Cynefin rule for unclassifiable work [18]. Confidence in which fix will work: low until step 1 data exists [judgment].

Assumption log:

- A1. "Wrong" covers untrue statements, missing facts, and poor form. Why not measured: no data yet. Validate by: the error count in step 1. If wrong: the taxonomy below changes, the process does not.
- A2. The support tool stores conversations and exposes them for a sample export. Why not measured: the material does not state it. Validate by: attempt an export of 50 conversations. If wrong: build the export first; all steps shift by one session.
- A3. Agents can spare about 0.5 hours each for a review session. Why not measured: the user has not answered. Validate by: ask one agent. If wrong: use the requester's own review time in one session.

Alternative considered: replace the LLM with extractive summarisation that copies sentences from the ticket. It loses on likely utility: it cannot merge context that sits in separate messages, and omission rates probably stay high [inference]. It remains a fallback if probe fixes fail.

## End

I recommend that we take these five steps.

1. **Label and count the errors (Confused).** Import 40 conversations from the last month and label each summary as correct, untrue, incomplete, or poor form, with a one-line reason. The output decides every later step, and the domain is unknown today. Test written first (evaluative): rubric with three criteria, weights 0.5 faithfulness, 0.3 coverage, 0.2 form, pass at kappa agreement of 0.6 or more between two raters on a shared set of 10 items. This is the confused-classification step, so it goes first.

2. **Add a verification gate (Clear, high leverage, run in parallel from step 1).** After each generated summary, run a second pass that checks each statement against the ticket messages. If a check fails, output "No summary available". This removes the largest blocker now: a wrong summary reaches agents. Test written first (deterministic):

   ```gherkin
   Given a summary with one statement not present in the ticket
   When the verification pass runs
   Then the output is "No summary available"
   ```

   Clear domain: cause and effect are known and the step is one scripted pass.

3. **Build the truth set fixture (Complicated).** Pick 20 conversations, write a reference summary for each from the full ticket, and store them as a versioned test fixture. The analysis that picks the practice here is the sampling of cases across error types found in step 1, so step 3 needs the labels from step 1. Test written first (deterministic):

   ```gherkin
   Given the fixture file at version 1
   When the fixture pipeline runs on the same 20 conversation IDs
   Then the output file matches the committed fixture byte for byte
   ```

4. **Define the acceptance test (Complicated).** Metric: share of summaries over the truth set with zero untrue statements. Baseline: the step 1 rate on the current prompt. Threshold: 90% over 40 samples, then 90% over 200 samples next quarter. This test must pass before any fix is accepted. Test written first (stochastic): metric, baseline, threshold, and sample size are all stated above; sample size 40 per evaluation run.

5. **Probe the top error type with a prompt or retrieval fix (Complex).** Based on step 1 counts, change one variable: an instruction against invention, or inclusion of the full ticket in context. This is a safe-to-fail probe, so do not commit the full increment. Cap: two rounds, one week, one engineer-session each. Measure: error rate on the truth set, acceptance by step 4's test. Stop condition: no reduction to at most 50% of baseline after two rounds; then the fallback alternative in Information applies. Leverage is a guess until step 1 data exists.

Dependencies: steps 3 and 4 must not start before step 1 labeling ends. Step 5 must not start before step 4 defines its threshold. Step 2 needs step 1 only to tune its false-rejection limit.
