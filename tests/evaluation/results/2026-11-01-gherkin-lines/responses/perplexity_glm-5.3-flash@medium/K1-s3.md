Restore the pool settings from release 2026.10.14; the pool config caused the latency rise, not the ORM change.

- The db.pool.acquire span grew from 3 ms to 690 ms at p95, and that span is 77% of the 900 ms request time [3].
- The diff cut pool max_size from 50 to 8 while each pod runs 8 worker threads, so threads queue for connections [2].

## Background

API p95 latency rose from 120 ms to 900 ms after release 2026.10.21 on 2026-10-21 [3]. The request asks for a fix. Logs, traces, and the release diff are attached.

## Relevance

The error rate rose from 0.02% to 0.40%, and 96% of the errors are pool timeouts that fail after 5 s [3]. Customers now see 503 responses on the main orders route [1].

### Evidence

2. The config change matches the mechanism. The diff lowers max_size from 50 to 8 and acquire_timeout_s from 30 to 5 [2]. The deployment note states 4 pods with 8 workers each, unchanged [2].
3. The timing matches. Pool warnings went from none on 2026-10-20 to 1,800 to 2,400 per hour on 2026-10-22, one day after deploy [1]. PoolTimeout errors appear with 8 of 8 connections in use and 9 to 14 waiters [1].

6. The ORM change added one extra query type but both query spans stayed fast [3]. No action on it.

Confidence: high. Config diff, span data, and logs agree on one mechanism [2] [3] [1].
