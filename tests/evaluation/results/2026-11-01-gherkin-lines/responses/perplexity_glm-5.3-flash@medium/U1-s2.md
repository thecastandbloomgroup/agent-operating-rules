## Headline

Measure the failure pattern first, then fix by cause type; do not guess fixes.

- A flaky build has causes in three non-overlapping groups: resources, time dependence, and shared state. [judgment]
- A fix without a measured failure rate cannot show that it worked, because flaky builds pass sometimes by chance. [judgment]
- A sample of 20 reruns separates a stable suite from a flaky one at a usable confidence. [judgment]

## Background

The build fails and passes with no code change. The request is to make it trustworthy again.

## Relevance

A red build blocks every merge and hides real failures inside noise. Each day of guessing costs a full pipeline run per guess. [judgment]

## Information

**Evidence.** Flaky builds break into three cause groups [judgment]:

1. Resources: memory limits, disk space, port conflicts, parallel job contention.
2. Time dependence: timeouts, race conditions, ordering, network latency.
3. Shared state: leftover files, dirty databases, tests that depend on earlier tests.

Look for one theme first: scan the logs of the last failing runs for one error class that repeats. A single theme with a repeat count above 5 of 20 runs points to one cause group. [judgment]

**Assumption log.**

- A1. The build is a CI pipeline, not a local build. Why not measured: the material does not state it. Validate by: run the build command locally once. If wrong: Steps 1 and 2 shift to a local run loop.
- A2. CI logs from past runs are still readable. Why not measured: no tool reach in this session. Validate by: open the last 5 failed run logs. If wrong: replace log scan with fresh reruns only.
- A3. Failures are not caused by one broken commit. Why not measured: no commit metadata in the material. Validate by: check whether green and red runs share one commit. If wrong: revert that commit and skip Step 4.

**Alternative considered.** Skip measurement and fix the most recent error directly. It loses because a flaky fix without a baseline failure rate cannot show the fix worked. [judgment]

## End

I recommend that we run four steps in this order.

1. **Stabilise the pipeline (Chaotic, because no cause is visible yet and flow must return first).** Add auto-retry capped at 2 reruns, and tag rerun events so they do not hide the real failure rate. Increment: one CI config change, one working session. Blocker removed: merges blocked by red. Test, written first:

   ```gherkin
   Given a pipeline step that fails on its first run
   When the pipeline executes the step
   Then the step reruns at most 2 times
   And the run record shows the rerun count
   ```

2. **Classify the cause (Confused, because the domain is not yet clear).** Rerun the failing suite 20 times and record per-run status, error class, and duration. Increment: one 20-run batch with a written log. Blocker removed: no data to pick a fix. Test, written first: metric is failure rate per error class; baseline is 0%; threshold is a completed table with 20 of 20 runs and a readable log for each; sample size is 20. Stop if after 10 runs the log is unreadable in more than 2 runs, and repair logging first. This step MUST NOT start before Step 1 passes its test.

3. **Quarantine the worst tests (Clear, because the practice is known: isolate confirmed flaky tests).** Move each test with a rerun failure rate above 10% into a quarantine list so main stays green. Increment: one quarantine list plus one config entry, one working session. Blocker removed: green-but-trustworthy main restored while fixes proceed. Test, written first:

   ```gherkin
   Given the rerun table from Step 2
   When a test shows a failure rate above 10 percent
   Then the test joins the quarantine list
   And main ignores it until the list entry is removed
   ```

   This step depends on the Step 2 table.

4. **Fix one cause at a time (Complex, because cause and effect are visible only after the fix).** Pick the top error class, fix one suspected cause, and rerun 20 times. Budget: 2 working sessions per fix, capped at 2 fixes in this cycle. Test, written first: metric is failure rate over 20 fresh runs; baseline is the Step 2 rate; pass threshold is a rate below 5%; sample size is 20. Stop the fix and move to the next class if the threshold is not met.

If Step 2 shows the errors cluster in the resource group, replace Step 4 with a limit increase on jobs and memory, and test it with the same 20-run sample. [judgment]

## Follow-up

Open question: does the build also fail on a local repeat run? The answer only splits Step 2 into a local loop or a CI loop, and the plan above covers both.

Conditions that change the recommendation: if A3 is wrong and one commit causes the failures, revert the commit and skip Step 4.
