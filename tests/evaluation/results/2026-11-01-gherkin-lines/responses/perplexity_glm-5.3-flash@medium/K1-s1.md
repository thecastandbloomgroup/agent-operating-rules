## Headline

Roll back the pool and cache settings from the 2026-10-21 release; the pool config change caused the latency rise.

- The release cut pool `max_size` from 50 to 8 and `acquire_timeout_s` from 30 to 5 [2].
- The acquire wait p95 rose from 3 ms to 690 ms, 77% of the 900 ms request p95 [3].
- Pool exhausted warnings rose from 0 per hour to 1,800 to 2,400 per hour [1].
- Query times stayed flat, so the ORM change is not the driver [3].

## Background

The API p95 latency rose from 120 ms to 900 ms after the release on 2026-10-21 [3]. Here "p95" means the 95th percentile latency. The release touched the DB pool config, the cache config, and the ORM query [2]. Three artifacts support this analysis: logs [1], the release diff [2], and traces [3].

## Relevance

The error rate rose from 0.02% to 0.40%, and 96% of those errors are pool timeouts [3]. Each timed-out request waits 5 s and returns 503 [1]. Fix this before the next weekly peak.

## Information

**Findings.** First, the pool change is the main shift. `max_size` fell from 50 to 8, and the per-service connection limit ticket OPS-412 drove it [2]. Next, acquire spans grew to 690 ms at p95, against 3 ms before [3]. Log waiters ran from 6 to 14 per pod [1]. Peak active connections fell from 31 to 8, so the cap, not demand, now binds [3]. Database CPU stayed low: 38% to 41% peak [3]. So the DB has headroom and the wait is client-side. Second, the cache change adds pressure. The default TTL fell from 300 s to 60 s [2], and the miss rate rose from 12% to 31% [3]. Third, the ORM change is harmless to latency. The orders query p95 moved from 52 ms to 58 ms, and the order_lines p95 fell from 30 ms to 26 ms [3]. Last, the capacity math: 4 pods with 8 worker threads each [2]. The new cap allows 8 connections per pod, and old peak demand was 31 connections across 4 pods, about 8 per pod [3]. So the cap sits at old peak demand with zero headroom, and any burst queues behind it.

**Assumption log.**

A1. The DB connection limit behind OPS-412 is about 32 connections per service. Why not measured: the material does not state it. Validate by: read OPS-412. If wrong: set per-pod `max_size` to floor(limit / 4) instead of keeping 8.

A2. Acquires beyond 8 threads per pod come from work outside request threads, such as background jobs. Why not measured: the artifacts do not name the holders. Validate by: trace acquire holders for one hour. If wrong: shorten holds by reading the cache before the DB session opens [judgment].

A3. A TTL of 300 s restores the miss rate to near 12%. Why not measured: the deploy has not run. Validate by: miss rate after deploy. If wrong: DB demand stays higher, but 41% CPU peak leaves headroom [3].

Confidence is high on the pool as the main cause, because the diff, logs, and traces agree [judgment].

**Alternative considered.** The ORM `selectinload` change (two statements per request) as the cause. It loses because the order_lines query p95 fell from 30 ms to 26 ms [3].

## End

I recommend that we run these steps in order:

**Step 1.** Deploy a config rollback of the two cache and pool values today.

1. Increment: set `acquire_timeout_s` to 30 s in `config/db.yaml` and `default_ttl_s` to 300 s in `config/cache.yaml`.
2. Blocker: removes the 5 s stalls and cuts DB demand from cache misses.
3. Test (deterministic):
```gherkin
Feature: roll back pool and cache settings
  Scenario: pre-release values are live
    Given the config deploy finishes and health checks pass
    When the config endpoint reports pool and cache values
    Then acquire_timeout_s reads 30 and default_ttl_s reads 300
  Scenario: no timeout storm under pool saturation
    Given the rollback is live
    When 8 requests hold free pool connections at once and 20 more arrive
    Then requests wait for a free connection and fewer than 1 in 100 requests returns 503
```
4. Domain: Clear, because the prior values are known good and the change is one step [2].

**Step 2.** Read OPS-412 and set the pool size to match the real limit.

1. Increment: if the built-in limit above 32, set per-pod `max_size` to floor(limit / 4); if 32 or below, keep 8. Wait for Step 1 to be live.
2. Blocker: adds headroom at the cap, the largest latency blocker.
3. Test (deterministic):
```gherkin
Scenario: pods match the derived cap
  Given the limit value L from OPS-412
  When each pod applies max_size
  Then every pod reports floor(L / 4) and 4 pods times max_size does not exceed L
```
4. Domain: Complicated, because analysis of the ticket must pick the value first.

**Step 3.** If the limit stays at 32, file a capacity request with the demand number.

1. Increment: one ticket that requests a higher per-service limit, with this requirement: start only after the Step 2 limit value is known.
2. Blocker: the cap equals old peak demand of 31 connections with zero headroom [3].
3. Test (deterministic):
```gherkin
Scenario: the request cites demand
  Given the limit is 32 and window A peak demand is 31
  When the capacity request is filed
  Then it states 31 peak connections, the proposed limit, and OPS-412
```
4. Domain: Clear, because filing one ticket against a stated number is one step.

**Step 4.** Monitor for two hours, capped.

1. Increment: run the acceptance trial after Steps 1 and 2 are live.
2. Blocker: proves the latency return; no other step does this.
3. Test (stochastic): metric p95, baseline 900 ms, pass threshold 150 ms or less, sample 10,000 requests; also PoolTimeout count 0 and pool exhausted warnings 10 per hour or fewer. Stop condition: warnings above 10 per hour after Step 2. Budget: two hours.
4. Domain: Complex, because the combined effect of Steps 1 to 3 is not provable in advance; run it as a capped, safe-to-fail probe [5].

If Step 4 fails its stop condition, run the A2 holder trace before further config changes.

## Follow-up

Conditions that change the recommendation:

- If OPS-412 shows a limit of 64 or more, set `max_size` to 16 per pod and drop Step 3 (A1 wrong in a favorable way).
- If the A2 trace shows acquires outside request threads, add a holder fix before Step 2's new value.
- If the miss rate stays above 25% at TTL 300 s, accept it (CPU headroom) and rerun the trial once.

Open questions: none; the artifacts answer or the assumptions above cover the rest.
