### Headline

Build an evaluation set from real support tickets to measure summary errors before changing the model prompt.
First, a gold standard benchmark establishes your error baseline [judgment].
Next, error taxonomy categorisation separates factual hallucinations from omitted details [judgment].
Finally, targeted prompt updates address the verified primary failure mode [judgment].

### Background

You deployed a Large Language Model (LLM) summariser in your customer support tool [inference].
Support agents report that generated summaries are sometimes incorrect, but your team tracks no quality metrics [inference].
You requested a plan to improve the summariser output [inference].

### Relevance

Inaccurate summaries create agent errors and slow ticket resolution time [judgment].
Without baseline metrics, changes to the summariser risk introducing new errors without detecting them [judgment].

### Information

Customer support summarisation requires factual accuracy and completeness to prevent agent error [judgment].
Because agents report errors without data, you must quantify error types before modifying prompts or models [judgment].
A benchmark of 50 to 100 historical tickets provides sufficient statistical power to detect major error categories [1].
Furthermore, human-in-the-loop evaluation remains the primary standard for summarisation quality in customer service [2].

#### Assumptions

A1. Support agents can annotate ticket summaries during normal shifts. Why not measured: The material does not state it. Validate by: Ask the team lead for two hours of agent time. If wrong: Engineering must label the benchmark tickets instead.

A2. Production ticket logs are accessible for sampling. Why not measured: The material does not state it. Validate by: Query the database for 100 recent closed tickets. If wrong: Generate synthetic support dialogues for the initial baseline.

#### Alternative Considered

Prompt engineering directly in production: We could rewrite the system prompt immediately with stricter guardrails. This option loses because without a test set, you cannot verify whether the new prompt reduces errors or creates new omissions [judgment].

### End

I recommend that we:

1. Create an evaluation dataset of 50 closed support tickets with agent-verified reference summaries.
   - Increment: Extract 50 diverse closed tickets and draft reference summaries in one session.
   - Capability: Establishes a permanent evaluation baseline for all future summarisation changes.
   - Domain: Complicated, because selecting representative tickets requires domain knowledge of support categories.
   - Test (Evaluative):
     - Rubric criteria: Representative ticket distribution across categories (weight: 0.4), complete reference summaries (weight: 0.4), verified accuracy by a senior agent (weight: 0.2).
     - Pass threshold: Score of 0.85 out of 1.0.

2. Run an error taxonomy audit on current summariser outputs against the evaluation dataset.
   - Dependency: Step 2 MUST NOT start until Step 1 passes.
   - Increment: Evaluate current model outputs across the 50 tickets and record error counts by category.
   - Blocker: Removes the lack of quality metrics by identifying whether errors stem from hallucination, omission, or formatting.
   - Domain: Complicated, because categorising semantic errors requires structured analysis.
   - Test (Evaluative):
     - Rubric criteria: Error classification into hallucination, omission, or extraneous detail (weight: 0.5); inter-annotator agreement above 80% (weight: 0.5).
     - Pass threshold: 100% of errors classified into defined buckets with root-cause notes.

3. Update the summariser system prompt with explicit constraints that target the highest frequency error category from Step 2.
   - Dependency: Step 3 MUST NOT start until Step 2 passes.
   - Increment: Add negative constraints and few-shot examples to the prompt in one configuration session.
   - Capability: Directly suppresses the primary cause of agent dissatisfaction.
   - Domain: Complex, because LLM output distributions respond non-linearly to prompt changes.
   - Test (Stochastic):
     - Metric: Summary error rate across the evaluation dataset.
     - Baseline: Error rate measured in Step 2.
     - Pass threshold: Error rate reduces by at least 30% relative to baseline.
     - Sample size: 50 evaluation tickets across 3 independent runs.

4. Implement a binary feedback mechanism in the support tool interface for live agent ratings.
   - Dependency: Step 4 MAY run in parallel with Step 3.
   - Increment: Add thumbs-up and thumbs-down buttons with a one-click error tag to the summary widget.
   - Blocker: Removes the lack of ongoing production quality monitoring.
   - Domain: Clear, because adding feedback buttons to an existing user interface follows standard software patterns.
   - Test (Deterministic):
     - Given a support agent views a generated summary
     - When the agent clicks thumbs-down and selects an error reason
     - Then the system logs the ticket identifier, prompt version, summary text, and error reason to the analytics table
