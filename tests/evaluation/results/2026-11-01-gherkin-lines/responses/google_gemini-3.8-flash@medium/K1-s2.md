# Headline

Revert the cache time-to-live to 300 seconds and increase the database connection pool acquire timeout to eliminate connection queueing.

- Database connection acquisition latency accounts for 687 ms of the 780 ms latency increase [1].
- Lowering cache time-to-live from 300 seconds to 60 seconds increased cache misses by 2.58 times [2].
- Reducing the pool size to 8 connections per pod created a pool exhaustion bottleneck under the increased cache miss load [1], [2].
- Shortening the acquire timeout from 30 seconds to 5 seconds caused 96% of the new 503 errors [1], [2].

# Background

Release 2026.10.21 deployed on October 21, 2026 changed database pool size, cache time-to-live, and object-relational mapping queries [2].
Following this release, API p95 latency increased from 120 ms to 900 ms, and the error rate increased from 0.02% to 0.40% [1].
The team requested diagnostic analysis and remediation steps based on attached logs, traces, and release diffs.

# Relevance

Customer requests now fail with 503 errors during traffic peaks due to connection timeouts [3].
Immediate remediation restores latency to historical baselines and avoids service-level agreement violations.

# Information

Traces show that `db.pool.acquire` p95 latency rose from 3 ms to 690 ms between Window A and Window B [1].
In contrast, total query execution time remained flat: `orders` query p95 rose from 52 ms to 58 ms, while `order_lines` query p95 dropped from 30 ms to 26 ms [1].
Therefore, query execution in the database is not the cause of the latency increase [judgment].

The latency increase stems from connection contention [judgment].
In `config/cache.yaml`, `default_ttl_s` was reduced from 300 seconds to 60 seconds [2].
This change caused the cache miss rate to jump from 12% to 31% [1].
Because cache misses increased by 2.58 times, database request volume rose accordingly [judgment].

Concurrently, `config/db.yaml` reduced `max_size` from 50 to 8 connections per pod [2].
Across four pods with eight worker threads each, 32 worker threads now compete for 32 total connections [2].
Logs record 1,800 to 2,400 pool exhaustion events per hour in Window B, compared to none in Window A [3].
Furthermore, `acquire_timeout_s` fell from 30 seconds to 5 seconds [2].
When threads wait longer than 5 seconds, the application throws `PoolTimeout` errors, which account for 96% of all request failures [1], [3].

### Assumptions

A1. The Redis cache host has sufficient memory to retain entries for 300 seconds without evictions.
Why not measured: The material does not state Redis memory metrics.
Validate by: Check `used_memory` and eviction counts in Redis metrics.
If wrong: Keep time-to-live at 120 seconds and scale Redis memory allocation.

A2. Ticket OPS-412 allows at least 48 total database connections for this service.
Why not measured: Ticket OPS-412 text is not present in the material.
Validate by: Read ticket OPS-412 in the issue tracker.
If wrong: Maintain `max_size` at 8 connections per pod and rely on cache offload.

### Alternative Considered

The alternative was reverting the object-relational mapping change in `app/orm/orders.py` that added `selectinload(Order.lines)`.
This alternative loses because `order_lines` query p95 latency decreased from 30 ms to 26 ms [1].
Therefore, the eager loading optimization did not cause the latency regression [judgment].
