### Background

Release 2026.10.21 changed the object-relational mapping query, the cache time-to-live, and database connection pool settings [3].
API p95 latency rose from 120 milliseconds to 900 milliseconds after deployment [1].
The team requested diagnostic analysis and remediation actions to resolve the latency regression.

### Relevance

The API currently fails user requests with 503 errors during steady traffic [2].
Prolonged connection queueing risks cascading failures across dependent services if traffic increases.

### Information

Traces show that `db.pool.acquire` p95 latency increased from 3 milliseconds to 690 milliseconds [1].
Therefore, connection wait times cause 88 percent of the total latency regression [judgment].
In contrast, individual database queries did not slow down [1].
Order query p95 latency changed from 52 milliseconds to 58 milliseconds [1].
Order line query p95 latency dropped from 30 milliseconds to 26 milliseconds [1].
This confirms that the eager loading change in the mapping layer is not the bottleneck [judgment].

The regression stems from two interacting configuration changes [3].
First, `config/cache.yaml` lowered `default_ttl_s` from 300 seconds to 60 seconds [3].
Consequently, the cache miss rate rose from 12 percent to 31 percent [1].
This miss rate increase sent 2.58 times more read traffic to the database pool [judgment].

Second, `config/db.yaml` reduced `max_size` from 50 connections to 8 connections [3].
The four API pods run 32 worker threads in total [3].
Under eight connections per pod, workers exhaust the pool and queue for connections [2].
Furthermore, `acquire_timeout_s` dropped from 30 seconds to 5 seconds [3].
Waiters that exceed 5 seconds fail with 503 errors, raising error rates from 0.02 percent to 0.40 percent [1].
