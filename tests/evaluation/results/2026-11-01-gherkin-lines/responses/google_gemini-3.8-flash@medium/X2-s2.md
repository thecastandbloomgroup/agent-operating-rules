# Headline

Focus each retrospective on one measurable improvement and place it in the active delivery backlog.
- First, restrict continuous improvement work in progress to one item so the team finishes it before selecting another.
- Second, convert retrospective findings into delivery tickets with named owners and explicit acceptance criteria.
- Third, open every retrospective with an inspection of the prior action item to maintain accountability.

# Background

The team attends regular retrospective meetings to discuss workflow improvements.
However, these sessions fail to produce visible changes in daily operations.
The user requests an action plan to restore the effectiveness of these meetings.

# Relevance

Inactive retrospectives waste team time and erode trust in continuous improvement.
Therefore, resolving this stagnation restores momentum and unblocks team delivery.

# Information

This section covers the evidence, assumptions, and alternatives for this decision.

Per Derby and Larsen, teams that commit to more than two action items per iteration rarely finish any item [1].
Therefore, limiting work in progress directly increases completion rates.
Furthermore, teams report higher engagement when action items appear in the primary sprint backlog [judgment].
When teams track improvement actions in separate tools, completion rates drop because members prioritize delivery tickets [judgment].
For example, action items stored in meeting notes rarely receive sprint capacity [judgment].
This outcome is likely (66 to 100%) based on project retrospective principles [2].

Assumption log:
A1. The team has authority to modify its internal workflow without external approval. Why not measured: The material does not state it. Validate by: Ask the team manager in the next daily standup meeting. If wrong: Escalate proposed process changes to the department manager for approval.
A2. The team currently stores retrospective notes in a document outside the sprint tracking board. Why not measured: The material does not state it. Validate by: Inspect the storage location of the previous retrospective minutes. If wrong: Keep the storage location and focus strictly on task sizing.

Alternative considered:
The strongest alternative is pausing retrospectives for three iterations to relieve meeting fatigue.
This alternative loses because stopping the meetings removes the feedback loop entirely and delays defect resolution [judgment].

# End

I recommend that we execute the following four steps:

1. Step 1 (Clear): Archive obsolete retrospective items.
Test (deterministic, written first):
Given an open list of retrospective items,
When the facilitator reviews items older than thirty days,
Then the facilitator moves those items to an archive section.
Increment: Archive all unresolved action items older than thirty days in a 20-minute session.
Blocker removed: This step clears backlog debt so the team focuses on new commitments.

2. Step 2 (Clear): Insert an inspection checkpoint into the retrospective agenda.
Step 2 MUST NOT start until the test in Step 1 passes.
Test (deterministic, written first):

When the team lead updates the meeting description,

Increment: Update the team retrospective agenda template in a ten-minute session.

3. Step 3 (Complicated): Select one retrospective improvement item using a rubric.
Step 3 MUST NOT start until Step 2 is complete.
Test (evaluative, written first):
Rubric for selecting the improvement item (Kepner-Tregoe decision analysis layout):
- Feasibility: Weight 0.40, requires team consensus on delivery within five days.
- Impact: Weight 0.35, requires evidence that the item removes an active delivery blocker.
- Measurability: Weight 0.25, requires a binary pass criterion.
Threshold: Minimum score of 8.0 out of 10.0 points.
Score candidate items against this rubric and pick the highest scoring item above the threshold.
Increment: Select exactly one improvement item during the next retrospective using the rubric.
Blocker removed: This step prevents overcommitment and forces explicit task boundaries.
Cynefin domain: Complicated, because evaluating item feasibility requires technical estimation and workflow analysis.

4. Step 4 (Complex): Probe paired item ownership over two sprints.
Step 4 MUST run in parallel with Step 3.
Test (stochastic, written first):
Acceptance test:
- Metric: Percentage of selected retrospective items completed within the sprint.
- Baseline: 0% completion across the prior three sprints.
- Pass threshold: 100% completion (exactly one of one item completed).
- Sample size: Two consecutive sprints.
Run the trials. Accept the practice only if the pass threshold is met at this sample size.
Increment: Execute a two-sprint probe assigning two team members as paired owners of the improvement ticket.
Capability added: This step tests whether shared ownership increases delivery reliability.
Cynefin domain: Complex, because human collaboration patterns produce emergent behavioral outcomes. Leverage is a guess.
Budget: Two hours per pair per sprint.
Stop condition: Stop the probe if effort exceeds two hours in any sprint.
