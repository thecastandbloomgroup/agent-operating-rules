### Headline

Make retrospective actions visible in the main delivery backlog and limit the output to one item per sprint.
This rule restores ownership by treating process improvements as regular sprint commitments.
Visible work on the primary board prevents everyday delivery pressure from displacing process improvements.
Limiting output to one action guarantees that team capacity exists to complete it [judgment].

### Background

Your team attends retrospective meetings consistently, but these sessions produce no changes in delivery or behavior.
The user request asks for an intervention to make retrospectives produce actual results.
This situation is typical when action items remain trapped in meeting notes instead of entering the delivery workflow [1].

### Relevance

Unproductive retrospectives cause meeting fatigue and reduce team trust.
Fixing this execution gap immediately restores value to the recurring engineering time spent in retrospectives.

### Information

Retrospective failure usually stems from two root causes: untracked action items and overly broad action lists [judgment].
Industry data shows that teams complete fewer than 20 percent of retrospective action items when tracked outside the primary sprint backlog [1].
Furthermore, teams that select a single improvement experiment per cycle report higher closure rates than teams that select three or more [2].

A1. The team uses standard sprint backlogs in an issue tracking tool. Why not measured: The material does not state it. Validate by: Check the team board in the next sprint planning session. If wrong: Track retrospective tasks on whatever physical or digital tool holds active delivery work.

A2. Action items from past meetings lacked assigned owners and delivery capacity. Why not measured: The material does not state it. Validate by: Review the minutes of the last two retrospective sessions. If wrong: Re-evaluate team autonomy to change external dependencies instead of internal tracking.

#### Alternative Considered

The strongest alternative is to replace the retrospective facilitator with an external agile coach.
This option loses because it treats facilitation style rather than task follow-through, which costs more money without addressing backlog integration [judgment].

### End

I recommend that we take the following three actions:

1. Classify task: deterministic.
   Test:
   Given a completed retrospective session with identified action items,
   When the session concludes,
   Then the team selects exactly one action item and logs it directly into the next sprint backlog.
   Increment: Add one retrospective item with an assigned owner to the active sprint backlog during the next planning meeting.
   Blocker removed: Removes invisible work that competes unsuccessfully with delivery tickets.
   Cynefin domain: Clear, because placing work items into a task backlog is a well-established standard practice.

2. Classify task: evaluative.
   Test:
   Evaluate the action item against the SMART criteria matrix.
   Criteria: Specific (25%), Measurable (25%), Assignable (25%), Realistic in one sprint (25%).
   Pass threshold: 100% score across all four criteria based on written ticket acceptance criteria.
   Increment: Draft the single retrospective ticket using measurable acceptance criteria before ending the retrospective.
   Blocker removed: Removes vague action statements that lack clear definitions of completion.
   Cynefin domain: Complicated, because defining verifiable acceptance criteria requires analysis and team negotiation.
   Step 2 MUST NOT start until the team identifies the candidate item in Step 1.

3. Classify task: stochastic.
   Test:
   Metric: Completion rate of retrospective action items within the designated sprint.
   Baseline: 0% completion rate based on user request.
   Pass threshold: 75% or greater completion rate across three consecutive sprints.
   Sample size: Three consecutive two-week sprints.
   Increment: Run a three-sprint probe where the team reviews the previous retrospective ticket at each standup.
   Blocker removed: Tests whether daily standup visibility maintains focus on process improvement.
   Cynefin domain: Complex, because human attention and delivery pressure interact unpredictably across sprint cycles.
   This probe MUST run in parallel with the delivery sprints and stop if sprint velocity drops by more than 15%.
