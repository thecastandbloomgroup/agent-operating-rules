## Headline
Measure fault types on a fixed case set before any change to the summary tool.
Agents report faults, but the team has no count of those faults.
A summary can fail in separate ways, so one fix will miss some faults.
A scored sample sets a baseline, and the same sample tests the next change.

## Background
The support tool now uses a large language model (LLM) to write case summaries.
Agents say those summaries are sometimes wrong.
The team has no metric for that fault.

## Relevance
A wrong summary can send an agent to the wrong next step.
Therefore a measured fault rate should come before time spent on a change.

## Information
This section covers the evidence, the assumptions, and the alternative.

Research on abstractive summaries finds that models add facts that are not in the source.
[1]

The request states that agents call the output wrong and that no metrics exist.
[2]

A change with no baseline cannot show a gain.

The share of each fault type is unknown.

Next, the assumption log follows.

A1. Readers are agents, not customers. Why not measured: The material does not state it. Validate by: Ask who reads the summary. If wrong: Hold any live prompt change.

A2. Wrong means a fact error, not tone or length. Why not measured: The material does not state it. Validate by: Collect two agent examples. If wrong: Add those criteria before the count.

A3. Old case text can be opened next to the summary. Why not measured: The material does not state it. Validate by: Open one old case. If wrong: Log inputs before any score.

A4. Thirty cases fit in one work session. Why not measured: The material does not state it. Validate by: Time the first five labels. If wrong: Use 15 cases and note a wider error band.

The strongest alternative is to rewrite the prompt now.
It loses because the fault type is unknown, so the rewrite can target the wrong fault.

## End
I recommend that we follow these four steps.

1. Domain: Confused, because the cause pattern is not known yet.
Kind: evaluative, that is, the output is a judgment.
Test, written first.
Rubric weights: invented fact 40%, missed fact 40%, wrong label 20%.
Evidence for invented fact: a summary phrase with no support in the case.
Evidence for missed fact: a promise, product, or status in the case that the summary omits.
Evidence for wrong label: a priority, product, or sentiment that does not match the case.
Pass mark: two reviewers agree on at least 24 of 30 cases.
Then, in one session, label 30 cases with that rubric.
This removes the blocker of an undefined fault.
Step 2 MUST NOT start until this pass mark is met.

2. Domain: Clear, because a count of labeled items has one accepted method.
Kind: deterministic.
Test, written first.
Given 30 cases with labels from Step 1.
When counts are made for each fault type.
Then the sheet lists three rates in counts per 30, plus the date.
This removes the blocker of no baseline.
The increment is one count sheet in the same session.

3. Domain: Complex, because a prompt effect shows up only after a trial.
Kind: stochastic.
Test, written first.
Metric: invented-fact count per 30 cases.
Baseline: the Step 2 rate.
Pass threshold: a drop of at least 3 cases out of 30.
Sample size: the same 30 cases.
Budget: one session and one prompt variant.
Stop if the invented-fact count does not drop, or if missed facts rise by 3 or more.
Then run one probe: require each summary claim to point to a case line.
This is a safe-to-fail probe, not a full rollout.
Leverage is a guess, because the domain is Complex.
Step 3 MUST NOT start until Step 2 has stored the baseline.
If invented facts are fewer than 3 of 30, aim this probe at the largest fault from Step 2.

4. Domain: Clear, because a weekly count uses the same method as Step 2.
Kind: deterministic.
Test, written first.
Given a new set of 30 cases each week.
When the same rubric is applied.
Then the sheet shows the three rates next to the Step 2 baseline.
This adds a repeat check so a later change can be compared.
The increment is one weekly sheet template.
Step 4 can run in parallel with Step 3.
Step 4 MUST NOT start until Step 2 has a stored baseline.

## Follow-up
If A1 is false, do not run Step 3 on live customer text.
Replace it with a hold until invented facts are 0 of 30 on a fresh sample.
If A3 is false, stop after the input check and store the missing text first.
