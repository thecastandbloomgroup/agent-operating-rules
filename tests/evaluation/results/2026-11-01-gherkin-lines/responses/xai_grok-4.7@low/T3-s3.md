Headline

Keep cookie sessions until a short-lived token passes logout tests, and test signup apart from that work.

Map the current session path before any token code ships.
Store any new token where page script cannot read it.
Keep logout working before the session store is removed.
Change signup in a small probe with a stop rule.

Background

The request asks for a move from sessions to JSON Web Token (JWT) and a higher signup completion rate.
JWT means a signed set of claims that a recipient can check from the token itself [2].
No code or completion metric is in the material, so the plan assumes a browser app with cookie sessions and proceeds.

Relevance

An HttpOnly cookie is not available to script APIs, so page script cannot read it [1].
A signup change in the same release hides which change moved completion [3].

Information

This section covers the evidence, the assumptions, and the alternative.

HttpOnly is a cookie flag that blocks non-HTTP API access to that cookie [1].
A JWT represents claims that travel with the token [2].
Therefore a JWT login can skip a session lookup on each call [inference].
Whether logout must survive store removal is answered by the Step 1 inventory, not by this note.
A signup test must change one factor so the result has a cause [3].

A1. The main client is a browser. Why not measured: The material does not state it. Validate by: list clients in the service repo. If wrong: use the client secure store in Step 3.
A2. Auth today is a server session in a cookie. Why not measured: The material does not state it. Validate by: find the session middleware in one search. If wrong: skip the dual-cookie slice and extend the inventory.
A3. Higher conversion means a higher share of signup starts that create an account. Why not measured: The material does not state it. Validate by: read the analytics event dictionary. If wrong: set the probe metric to that definition.
A4. A wrong auth switch costs more than a one-week delay. Why not measured: The material does not state it. Validate by: compare last incident cost with one week of engineering. If wrong: merge Steps 2 and 3 into one flagged slice.
A5. The signup form has one optional field. Why not measured: The material does not state it. Validate by: read the signup form. If wrong: remove one required field that support can collect after signup.

The strongest alternative is a full switch to a bearer JWT in script storage in one release.
It loses because script storage skips the HttpOnly control [1].

1. Map the live auth path in one page. Domain: Confused, because the material does not show cause and effect yet. The increment is that one page. It removes the blocker of an unknown session design.

2. Score three token options on one rubric. Domain: Complicated, because more than one good practice exists and the score picks one. The increment is the scored sheet only. It removes the blocker of an untested storage choice.

Rubric, written first. Kind: evaluative.

Pass threshold: the top option scores at least 70, and theft resistance scores at least 30.
Evidence: the Step 1 inventory and one option sheet.
Options: keep the server session; short-lived JWT in an HttpOnly cookie plus a revocation list; bearer JWT in script storage.

A revocation list is a store that marks a token invalid.
Step 3 MUST NOT start until the test in Step 2 passes.

3. Add one login path that sets a short-lived token cookie beside the session. Domain: Clear, because Step 2 has picked the practice and this step applies it. The increment is one login handler and one protected read. It adds dual checks so a flag restores the old path.

Test, written first. Kind: deterministic.
Given a test user and the feature flag on,
When login succeeds,
Then the response sets an HttpOnly cookie, the session cookie still works, and script cannot read the token cookie.
Given the flag off,
When login succeeds,
Then only the session cookie is set.

4. Run one signup probe with a hard budget. Domain: Complex, because the effect shows only after the trial, so leverage is a guess. Budget: 5 engineering days. Stop if the signup error rate is 1 percentage point above the control arm. The increment is removal of one optional signup field. It adds a measured completion change and does not touch token code.

Step 4 MAY run in parallel with Steps 2 and 3.

Test, written first. Kind: stochastic.
Metric: signup completion rate.
Baseline: the control arm rate in the same window.
Pass threshold: the treatment rate is at least 2 percentage points above the baseline.
Sample size: 400 completed attempts per arm.
Accept the change only when the sample size is met and the threshold holds.
