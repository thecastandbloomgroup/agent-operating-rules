Headline

Measure error types on a labeled sample before any change to the summariser.

- The error report has no rate, so the failure type is unknown.
- A ticket sample can split errors into types that do not overlap.
- Prompt and model changes start only after a baseline count exists.

Background

The support tool now adds a summary from a large language model. Agents say the summary is sometimes wrong. The tool has no metrics for those errors.

Relevance

Agents read these summaries during live support. A wrong summary can send the next reply off the ticket facts, so a baseline is the first fix.

Information

The request states that agents call summaries sometimes wrong and that no metrics exist.
[1]

Abstractive summaries can add facts that are not in the source text.
[2]

However, the share of each error type in this tool is not known. High confidence, the request states zero metrics. Therefore a labeled sample comes before a prompt change. A sample of 30 cases can show a common error in one work session. [judgment]

A1. Agents read the summary before they reply. Why not measured: the material does not state the workflow. Validate by: ask two agents how they use one summary. If wrong: score the real use, not the reply.

A2. Wrong means a fact error, a missing ask, or a bad next step. Why not measured: the material does not state the error type. Validate by: the labels in Step 1. If wrong: keep only the types that appear.

A3. Thirty cases can be labeled in one work session. Why not measured: team size is not in the material. Validate by: time the first five labels. If wrong: stop at fifteen cases for the first rate.

A4. The tool can set temperature to 0. Why not measured: the material does not state model settings. Validate by: read the summariser config. If wrong: use the stochastic rule in Follow-up.

The strongest alternative is to rewrite the prompt from agent stories now. It loses because those stories do not show which error is most common. A change can then miss the main error. [judgment]

End
