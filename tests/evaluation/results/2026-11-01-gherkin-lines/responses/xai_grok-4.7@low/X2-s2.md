Headline
Close the action loop before you change the retrospective format.
Attendance is already in place, so it is not the blocker.
Unowned actions are the likely blocker.
A review at the start of the next meeting closes that loop.
A new format does not close it.

Background
A retrospective is a regular meeting where the team inspects its work and picks a change.
The team still meets, but the work does not change afterward.
The request is to restore a path from that meeting to a real shift.

Relevance
A meeting that ends with no closed action teaches the team that talk will not matter.
The next retrospective can test a smaller loop with no extra people.

Information
This section covers the evidence, the assumptions, and the alternative.
Per the Scrum Guide, the team addresses the most impactful improvements as soon as possible [1].
Derby and Larsen name "decide what to do" as one phase of the retrospective [2].
A decision with no owner and no later review does not change the work [judgment].
The material shows attendance without a shift.
Follow-through is likely (66 to 100%) the gap.
The basis is that report, plus the two method sources, with no action log in hand [judgment].
Follow-through means the team finishes or drops each action.
The evidence does not include the team notes.
Therefore the next lines are assumptions.

A1. Recent retrospectives left actions with no later status review. Why not measured: the material does not state it. Validate by: mark each action in the last four notes as done, open, or dropped. If wrong: measure the result those actions were meant to change.

A2. The team can change at least one rule in its own process. Why not measured: the material does not state it. Validate by: name one rule the team sets with no outside approval. If wrong: the one action is a request to the person who controls the rule.

A3. The notes match what people will say about the real blocker. Why not measured: the material does not state it. Validate by: ask one quiet member in private whether the notes match that blocker. If wrong: repair safety before you add process rules.

The strongest alternative is to replace the retrospective with a board of small experiments.
It loses because a new board still needs an owner and a review [judgment].
The missing review is the blocker, not the meeting name [judgment].

End
I recommend that we take these five steps.

1. Build one status sheet from the last four retrospective notes.
Domain: Confused, because the cause is not yet visible, so this step gathers the facts that classify the stall.
Task kind: deterministic, that is, the same notes give the same sheet.
Test first:
Given four retrospective notes,
When each action is marked done, open, dropped, or missing,
Then the sheet lists owner, due date, and status for every action.
Increment: one working session to build the sheet.
Blocker removed: no shared picture of whether actions close.
This step comes first because later steps use its label.

2. Score the sheet and label the stall.
Domain: Complicated, because more than one cause fits, and the rubric picks the practice.
Task kind: evaluative, that is, the output is a judgment.
Rubric first, in Kepner-Tregoe form.
Must: a private check agrees that the notes match the real blocker.
If that must fails, label the stall as safety, and stop Steps 3 and 4.
Want 1, weight 40: prior actions have a recorded status. Evidence: the status column. Score 0 or 40.
Want 2, weight 40: the top action has one owner and one due date. Evidence: those two fields. Score 0 or 40.
Want 3, weight 20: at least one action sits inside team control. Evidence: a yes or no on control. Score 0 or 20.
The pass threshold is 70 points.
A score of 70 or more means the label is follow-through.
Increment: 30 minutes to score the sheet.
Blocker removed: choice of the wrong fix.
Step 2 MUST NOT start until the test in Step 1 passes.

3. If the label is follow-through, put a status review first on the agenda.
Domain: Clear, because a status review at the start is a known practice.
Task kind: deterministic.
Test first:
Given one open action from the last retrospective,
When the next retrospective starts,
Then the first 10 minutes record that action as done, open, or dropped.
Increment: one edit to the agenda template in the same session as Step 2.
Blocker removed: new topics start before old actions close.
Step 3 MUST NOT start until Step 2 gives the follow-through label.

4. Limit the next retrospective to one action record.
Domain: Clear, because the record rules are known once the label is follow-through.
Task kind: deterministic.
Test first:
Given the follow-through label,
When the retrospective ends,
Then exactly one action has one owner, one due date, and one result the team can see.
Increment: write that record before the meeting ends.
Blocker removed: a long list that nobody owns.
Step 4 MUST NOT start until Step 3 is in the agenda.
If A2 is false, replace that record with one request to the person who controls the rule.

5. Probe whether a closed action changes the work.
Domain: Complex, because that link shows up only afterward.
Task kind: stochastic, that is, the result can vary from run to run.
Test first:
Metric: count of work changes the team can name and tie to a closed action.
Baseline: the count from a 15-minute check in this same week.
Pass threshold: 1 or more.
Sample size: one retrospective cycle.
Increment: do not commit a format change from this probe.
Blocker removed: doubt about whether closed actions change the work.
Budget: 15 minutes for the baseline, and 10 minutes at the next retrospective.
Run the baseline in parallel with Steps 1 and 2.
Cap that check at 15 minutes.
Stop if the team cannot name one change tied to the action.
Then return to the rubric.
The full check MUST NOT start until the Step 4 action is due.
If A1 is false, replace Steps 3 and 4 with a measure of results for actions that already close.
