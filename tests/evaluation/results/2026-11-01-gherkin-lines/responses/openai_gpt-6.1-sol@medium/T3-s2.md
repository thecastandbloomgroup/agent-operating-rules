## Background

The request combines a security change with a product goal: replace sessions with JSON Web Tokens (JWTs) and improve sign-up conversion. [1]

No repository, system details, or conversion data accompanies the request. [1]

## Relevance

JWT design requires explicit security choices, including token validation rules. [2]  
Separately, changing auth and sign-up together makes failures harder to attribute. [judgment]

## Information

**Auth scope.** JWT is a token format, not a complete replacement for session management. [2]  
The design still needs decisions about token storage, expiry, renewal, revocation, and logout. [judgment]

First, establish whether the target uses browser cookies, bearer tokens, or different approaches for different clients. [judgment]  
Next, define how existing sessions survive the transition and how deployment can return to the current system. [judgment]

**Conversion scope.** No supplied evidence identifies where users leave sign-up or why. [1]  
Therefore, selecting a change such as fewer fields, delayed verification, or social sign-in would rest on an untested assumption. [judgment]

Measure the path from sign-up start to account creation, verification, and first useful action. [judgment]  
Track abuse and account quality alongside conversion so an increase does not hide worse outcomes. [judgment]

**Alternative considered:** Rewrite auth and simplify sign-up in one release.  
It loses because it combines security risk with an unmeasured product change and weakens fault isolation. [judgment]

The following tests define proposed work; no repository inspection or test execution has occurred.
