## Headline

Run one `ALTER TABLE orders RENAME COLUMN user_id TO account_id` statement, but only when the application code that reads `user_id` ships in the same window.

- The rename changes only catalog metadata, so it finishes fast [1].
- Every query that still names `user_id` fails the moment the rename commits.
- The statement needs a short exclusive lock, so set a lock timeout.

## Background

The request is to rename one column in the `orders` table of a Postgres database. The sender boards a plane soon. The material does not name the Postgres version, the environment, or the client code.

## Relevance

A rename takes seconds, but a missed dependent breaks live queries at once. A failure during a flight has no fast fix, so timing matters more than the command.

## Information

Evidence:
- `ALTER TABLE ... RENAME COLUMN` renames the column in the catalog and does not rewrite table data [1].
- Indexes, constraints, and foreign keys follow the new name on their own [1].
- Application SQL, ORM mappings, and function bodies stored as text keep the old name. They fail after the rename [judgment].
- The statement takes an ACCESS EXCLUSIVE lock on the table, which blocks other queries until it commits [1].

Statement:

```sql
BEGIN;
SET LOCAL lock_timeout = '3s';
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
COMMIT;
```

Assumption: the target is a production database with a live application. Why not measured: the material does not state it. Validate by: ask the owner of the environment. If wrong: skip Step 3 and run the statement at once.

Assumption: the application code still uses `user_id`. Why not measured: no tool can reach the code. Validate by: search the code base for `user_id`. If wrong: the code is ready and Step 3 shrinks to the statement alone.

Alternative considered: add `account_id` as a new column, copy the data, and drop `user_id` later. It is safer for live traffic but needs several deploys, so it loses for a plain rename [judgment].

## End

I recommend that we do the following, in this order:

1. Find the dependents of `user_id`. Search the code base and run `SELECT proname FROM pg_proc WHERE prosrc ILIKE '%user_id%';` to list functions. This removes the risk of a missed dependent.
   - Kind: evaluative. Cynefin: Complicated, by deduction from analysis of the code and the catalog.
   - Test (rubric): pass at 100% of weight when every hit is either updated in a ready change or marked as not used.

2. Run the transaction above on a staging copy. This proves the statement works.
   - Kind: deterministic. Cynefin: Clear, by deduction from a known rule [1].
   - Test:
     ```text
     Given a staging copy of the orders table with a user_id column
     When the rename transaction runs
     Then the orders table has account_id and no user_id
     ```
   - Step 3 MUST NOT start until this test passes.

3. Run the same transaction on production in the same window as the code release. Do this after the flight if nobody can watch it.
   - Kind: deterministic. Cynefin: Clear, by deduction from a known rule.
   - Test:
     ```text
     Given the application release that reads account_id is live
     When the rename transaction commits on production
     Then a test order saves and reads back with account_id
     ```

4. Keep a rollback statement ready: `ALTER TABLE orders RENAME COLUMN account_id TO user_id;`.
   - Kind: deterministic. Cynefin: Clear, by deduction from a known rule.
   - Test:
     ```text
     Given the rename has run on staging
     When the rollback statement runs
     Then the orders table has user_id again
     ```

If the application is not live yet, replace Step 3 with a direct run at once.
