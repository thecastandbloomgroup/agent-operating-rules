## Headline

Measure the summariser first, then fix its most common error with a tested change.

- No one knows the error rate today, so any change is a guess.
- Agents can tell us what is wrong if the tool asks them at the moment of error.
- A fixed test set lets us prove that a change helps before release.

## Background

The team added a summariser based on a large language model (LLM) to the support tool. Agents report that it is "sometimes wrong" [1]. The team has no metrics and asks for a better summariser.

## Relevance

Agents who distrust the summary re-read the full ticket. That removes the time the tool should save. A wrong summary can also send a wrong answer to a customer.

## Information

Evidence:
- The user states that agents report errors and that no metrics exist [1].
- Summary errors usually fall into a few types: wrong fact, missing fact, invented fact. [judgment]
- The top two error types are likely to cover most errors (66 to 100%). [judgment]

Assumption log:

Alternative considered: switch to a larger model now. It loses because the cause is unknown, and a model change costs more than a prompt change. [judgment]

## End

I recommend that we:

1. **Measure the baseline error rate and error types.**
   - Increment: five agents rate 100 recent summaries against the ticket text in one session.
   - Blocker removed: no metric exists. The domain is Confused, because we cannot yet tell which error types occur. This step gathers what we need to classify the work.
   - Kind: evaluative. The rubric is written before rating. Criteria and weights: factual accuracy 50, key issue and status included 30, no invented content 20.
   - Pass threshold: a score of 80 or more out of 100. Evidence: ticket text next to the summary, two raters per summary.
   - Output: the pass rate (the baseline) and a count of each error type.

2. **Add a thumbs-down button with a reason list to the summary.**
   - Step 2 MUST NOT start until Step 1 gives the error types, because they fill the reason list.
   - Increment: one button and one stored record per click.
   - Blocker removed: no ongoing signal. The domain is Clear, because logging feedback is a known practice (deduction from a known rule).
   - Kind: deterministic. The test is written first:
     - Given an agent views a summary
     - When the agent clicks thumbs-down and picks a reason
     - Then the system stores the ticket ID, summary, reason, and time

3. **Run a capped probe that fixes the top error type with a prompt change.**
   - Step 3 MUST NOT start until Step 1 is done.
   - Increment: up to three prompt variants, tested on the same 100 tickets.
   - Blocker removed: the most common error. The domain is Complex, because the effect of a prompt change shows only after a trial (induction from trials). The pattern can break if the 100 tickets do not represent real traffic. Leverage is a guess.
   - Kind: stochastic. The acceptance test is written first. Metric: pass rate from the Step 1 rubric. Baseline: the Step 1 result. Threshold: at least 15 points above baseline. Sample: 100 tickets.
   - Budget: two working days. Stop if no variant meets the threshold after three tries.

4. **Make the 100 rated tickets a release gate for every prompt or model change.**
   - Step 4 MUST NOT start until Step 3 yields a passing variant or stops.
   - Increment: a script that runs the set and prints the pass rate.
   - Blocker removed: silent regressions. The domain is Complicated, because analysis picks the pass margin (deduction from the Step 1 data).
   - Kind: deterministic. The test is written first:
     - Given the saved set of 100 tickets and the baseline pass rate
     - When the script runs on a new prompt
     - Then it prints the pass rate and exits with failure if the rate is below baseline

Steps 2 and 3 run in parallel after Step 1.

If Step 1 shows that most errors come from truncated long tickets, replace Step 3 with a change that splits long tickets before summary.
