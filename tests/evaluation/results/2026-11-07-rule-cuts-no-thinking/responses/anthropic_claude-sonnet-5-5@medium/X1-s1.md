## Headline

Measure the summariser first, then change it, because "sometimes wrong" cannot be fixed until it is counted.

- No baseline exists, so no change can be shown to help.
- Agents hold the knowledge of what "wrong" means, so their labels are the cheapest data source.
- Fixes depend on the error type, for example invented facts, missing facts, or wrong tone.
- A feedback button keeps the measure running after the first audit.

## Background

The team added a summariser based on a large language model (LLM) to the support tool. Agents report that it is "sometimes wrong". The team has no metrics and asks for an improvement.

## Relevance

Agents who distrust a summary reread the full ticket, so the tool adds work instead of saving it. Wrong summaries in a customer record can also cause wrong replies.

## Information

Evidence:
- Agents report errors, but no count exists (per the request) [no source].
- Most summary errors in LLM tools fall into a few types: invented facts, omitted facts, and wrong status [judgment].
- A sample of 100 summaries gives a 95% interval of about ±10 points on an error rate near 50%, and about ±6 points near 15% (binomial arithmetic) [inference].

Assumption log:

- `Assumption: the tool stores the ticket text and the summary. Why not measured: no tool can reach the system from here. Validate by: query one record. If wrong: add logging before Step 1.`
- `Assumption: the model prompt can be changed by the team. Why not measured: the material does not state it. Validate by: ask the owner. If wrong: Step 4 changes to a vendor request.`

Alternative considered: switch to a larger model now. It loses because no baseline exists to show a gain, and the cost rises for every ticket [judgment].

## End

I recommend that we do these steps in order:

1. **Label a sample of 100 recent summaries.**
   - Increment: two agents label each summary, in one session, as correct or wrong, with an error type.
   - Blocker removed: no baseline and no error taxonomy.
   - Kind: evaluative. Rubric first. Criteria and weights: factual accuracy 50%, completeness of the customer issue 30%, correct status and next step 20%. Pass: a summary scores at least 80% and has no invented fact. Evidence: the full ticket text. Also report agreement between the two labelers.
   - Cynefin: Complicated. Deduction from expert review sorts the errors into types.

2. **Log agent feedback in the tool.**
   - Increment: one "wrong" button with a short error-type menu.
   - Blocker removed: no continuing measure.
   - Kind: deterministic. Test first:
     - Given an agent views a summary
     - When the agent presses "wrong" and picks "invented fact"
     - Then the system stores the ticket ID, summary version, and error type
   - Cynefin: Clear. A known pattern applies, and the cause and effect are direct.

3. **Replay the summariser on 200 labeled tickets to set the baseline.**
   - Increment: one scripted run that scores each summary against the Step 1 rubric.
   - Blocker removed: no number to beat.
   - Kind: stochastic. Metric: share of summaries that pass the rubric. Baseline: the Step 1 rate. Threshold: the script matches the agent labels on at least 90% of cases. Sample: 200.
   - Cynefin: Complicated. Analysis picks the scoring method.
   - Step 3 MUST NOT start until Step 1 ends.

4. **Run one capped probe on the most common error type.**
   - Increment: one prompt change, for example "quote the customer's request, and write only facts from the ticket".
   - Blocker removed: the largest error type from Step 1.
   - Kind: stochastic. Metric: error rate on the same 200 tickets. Baseline: the Step 3 rate. Threshold: a drop of at least 30% with no rise in omissions. Sample: 200. Budget: one working day. Stop if two prompt variants fail.
   - Cynefin: Complex. Induction from trials. Leverage is a guess. The pattern breaks if the error type differs on new ticket kinds.
   - Step 4 MUST NOT ship until Step 2 is live to watch the effect.

If Step 1 shows an error rate under 5%, replace Step 4 with a monthly check from the Step 2 feedback.
