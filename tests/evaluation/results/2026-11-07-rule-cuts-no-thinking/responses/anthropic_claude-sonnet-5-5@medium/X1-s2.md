## Headline

Measure the summariser first, then change it: the agents' "sometimes wrong" must become a counted error type and a baseline score.

- Without a metric, no change can be shown to help or harm.
- The errors are likely concentrated in a few types, so one targeted fix can remove most of them.
- Agents already see the errors, so their labels are the cheapest data source.
- Prompt and model changes are experiments, so each needs a sample size and a threshold.

## Background

The support tool has a summariser built on a large language model (LLM, a text-generating model). Agents report that it is "sometimes wrong". No metrics exist, and the request is to improve it.

## Relevance

An agent who trusts a wrong summary may give a wrong answer to a customer. An agent who distrusts it stops using it, so the feature loses its value.

## Information

**Evidence**

- Agents report errors, but the count and type are unknown [no source].
- Error types in summaries usually fall into a few groups: invented facts, missing key facts, wrong order of events, and wrong tone [judgment].
- LLM judges agree with human raters on more than 80% of comparisons in one study [1]. Use a judge only after it is checked against agent labels [inference].

**Assumption log**

Assumption: Agents can label 100 recent summaries in one session. Why not measured: the material does not state agent capacity. Validate by: ask one team lead to book the time. If wrong: label 50 summaries and widen the error margin.

Assumption: The tool stores ticket text and summary text. Why not measured: no tool can reach the system. Validate by: query the database for ten recent tickets. If wrong: Step 2 must add logging first.

Assumption: The main failure is faithfulness, that is, summaries that state things the ticket does not say. Why not measured: no labels exist. Validate by: Step 1. If wrong: the probe in Step 4 targets the top error type from Step 1 instead.

**Alternative considered**

The strongest alternative is to switch to a larger model now. It loses because without a baseline nobody can show it is better. It also raises cost per ticket [judgment].

## End

I recommend that we take these steps in order:

1. **Label 100 recent summaries with agents.**
   - Increment: one working session with two agents who score the same summaries.
   - Blocker removed: nobody knows what "wrong" means.
   - Kind: evaluative. Rubric, written first: faithfulness (weight 50%), completeness of key facts (30%), usefulness for the next action (20%).
   - Evidence per criterion: the original ticket text beside the summary.
   - Pass threshold: at least 90 summaries scored, and the top three error types counted.
   - Cynefin domain: Confused. We cannot yet classify the problem, so this step gathers the data to do so.

2. **Add a one-click "wrong summary" button with a reason list.**
   - Increment: one button, one stored record per click.
   - Blocker removed: no ongoing signal exists.
   - Kind: deterministic. Test, written first:
     - Given an agent views a summary
     - When the agent clicks "wrong" and picks a reason
     - Then the system stores the ticket ID, summary ID, reason, and time
   - Cynefin domain: Clear. Feedback buttons are a known practice, so apply it by deduction.

3. **Turn the labels into a fixed test set and a baseline score.**
   - Increment: the 100 labeled summaries become a frozen set.
   - Blocker removed: no number exists to compare against.
   - Kind: stochastic, because LLM output varies between runs.
   - Acceptance test, written first: the metric is the share of summaries rated faithful. The baseline is the Step 1 result. The threshold is set after Step 1. The sample size is 100 tickets, run three times each.
   - Step 3 MUST NOT start until Step 1 is complete.
   - Cynefin domain: Complicated. Analysis of the labels picks the metric, so this is deduction from the data.

4. **Run one capped probe against the top error type.**
   - Increment: one prompt change, for example "state only facts found in the ticket".
   - Blocker removed: no evidence that any change helps.
   - Kind: stochastic. Acceptance test, written first: the faithful share rises by at least 10 points over the Step 3 baseline on the 100-ticket set, over three runs.
   - Budget: one working day. Stop condition: two failed prompt variants.
   - Step 4 MUST NOT start until the Step 3 baseline exists. Step 4 MAY run in parallel with Step 2.
   - Cynefin domain: Complex. Cause and effect show only after trials. The pattern breaks if the 100 tickets do not represent real traffic. Leverage is a guess.

If Step 1 shows that missing facts, not invented facts, are the top error, replace the Step 4 prompt change with a longer input window or a ticket-field extraction step.
