Turn on gzip for these JSON responses. A 400 KB JSON body is large enough that transfer time dominates on typical links. JSON text compresses well because keys and syntax repeat. CPU cost stays acceptable when a size floor is set and latency is measured. Skip gzip only when a proxy already compresses the body or the CPU is already full.

The API returns JSON, a text data format. The average response is 400 KB. The request is whether gzip, a common HTTP compression method, should be on.

A 400 KB body adds delay on mobile networks and on long links. Compression cuts bytes before they leave the server, so the same answer arrives sooner.

HTTP defines gzip as a content coding that clients name in Accept-Encoding. [1]
Accept-Encoding is the request header that names accepted compression.
The gzip format stores DEFLATE compressed data. [2]
Repetitive JSON often shrinks to about 10 to 30 percent of its size. [judgment]
Therefore a 400 KB body often falls near 40 to 120 KB. [inference]
That byte cut removes more delay than typical encode time adds on slower links. [judgment]
However, a mixed secret and caller-controlled text can leak under compression plus TLS. [3]
This risk does not remove the byte savings for normal JSON.

Assumption: clients send Accept-Encoding with gzip. Why not measured: The material does not state it. Validate by: read one production request header. If wrong: those clients get no savings.

Assumption: no proxy already compresses these bodies. Why not measured: The material does not state it. Validate by: check Content-Encoding on one live response. If wrong: a second gzip pass wastes CPU.

Assumption: spare CPU exists at the current load. Why not measured: The material does not state it. Validate by: read CPU percent for one minute. If wrong: turn gzip off or lower the effort.

The strongest alternative is to shrink field names and leave gzip off. That alternative loses because the schema change is larger work. Also, 400 KB still crosses the wire until that change ships. [judgment]
