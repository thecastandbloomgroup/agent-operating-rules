The API serves JSON. Average response size is 400 KB [1]. The open choice is whether gzip is on for those bodies.

This choice matters now because each call moves hundreds of kilobytes. A smaller body lowers latency and egress cost before other API work.

The size figure comes from the request [1]. No compressed sample is in the material. Therefore the shrink ratio is [judgment], not a measurement. Text JSON with repeated names usually falls to a fraction of raw size under gzip [judgment]. The exact fraction needs a local sample. HTTP defines Accept-Encoding and Content-Encoding for this negotiation [2].

Gzip is the coding named for that path [3]. A known risk remains when one body holds a secret and attacker-chosen text [4]. In that case compression can leak the secret. Whether these routes have that mix is not in the material.

Assumption: Clients send Accept-Encoding with gzip. Why not measured: The material does not state it. Validate by: Count that header on 100 live calls. If wrong: Only matching clients gain, and others keep the raw body.

Assumption: Bodies are not already compressed. Why not measured: The material does not state it. Validate by: Check Content-Encoding on 20 routes. If wrong: A second pass wastes CPU and can grow the body.

Assumption: Bodies do not place a secret beside attacker-chosen text. Why not measured: The material does not state it. Validate by: Review routes that echo user input next to tokens. If wrong: Those routes stay uncompressed [4].

Assumption: Median client delay is at least 5 ms. Why not measured: The material does not state it. Validate by: Read the latency tier from existing metrics. If wrong: Skip gzip where delay is under 5 ms and CPU is full.

The strongest alternative is Brotli on every response. It loses because dynamic Brotli uses more CPU than gzip at a low level [judgment]. Some clients also lack Brotli, so coverage is narrower [judgment].
