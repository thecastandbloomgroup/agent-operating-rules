Headline
A retrospective changes the work only when one owned action is written down and the next session checks it.
People attend, but attendance is not a decision.
An action without an owner and a date is forgotten before the next session.
Several actions at once split attention, so none of them finish.
Therefore the next session must open on the last action, not on a new list.

Background
A retrospective is a regular meeting where the team inspects how it works. The team still holds these meetings, and people attend. The request is how to make the meetings change the work.

Relevance
Each cycle with no closed action teaches the team to ignore the session. The next retrospective is the cheapest place to stop that habit.

Information
The Scrum Guide says the team picks the most helpful changes and addresses the most impactful ones soon [1].
The same guide lets the team place that change on the next sprint backlog, so the change enters the plan [1].
A sprint is a fixed cycle of one month or less [1].
Derby and Larsen say the session must decide what to do [2].
The same book treats that decision as a small experiment with a later check [2].
A missing owner leaves no person to carry the change [judgment].
Therefore a review at the next session is the control that makes the experiment real [judgment].

Assumption: The team writes few or no actions with owners. Why not measured: The material does not state it. Validate by: Read the notes from the last three sessions. If wrong: Keep the review step, and look for a blocked owner instead of a missing owner.

Assumption: Sessions occur at least once every two weeks. Why not measured: The material does not state it. Validate by: Check the team calendar. If wrong: Use the next planned session, and do not add a new cadence.

Alternative considered: Add a new facilitator and keep the same open discussion. This loses because a better discussion can still end with no checked action [judgment].

End
I recommend that we take these steps.

Step 1. Test first. Rubric: owner present (weight 40%), check date present (weight 30%), result reviewed next time (weight 30%). Pass threshold: 70% of the weight, from the written notes, not from memory.
This step is evaluative.
Domain: Complicated. Reason: deduction from these three criteria picks the practice.
Increment: score the last three sessions in one sitting of 30 minutes.
Blocker removed: unknown cause of no change.
Step 2 MUST NOT start until this score exists.

Step 2. Test first.
Given the score shows a missing owner or a missing date,
When the next session ends,
Then the notes name one action, one owner, and one check date.
This step is deterministic.
Domain: Clear. Reason: one owner and one date is a known rule, so apply it.
Increment: write that one line before people leave.
Blocker removed: actions that nobody owns.
Step 3 MUST NOT start until this line exists.

Step 3. Test first.
Given the previous notes name one action,
When the next session starts,
Then the owner states done, not done, or blocked before any new topic.
This step is deterministic.
Domain: Clear. Reason: the check is a fixed step in a known sequence.
Increment: the first five minutes of that session.
Blocker removed: actions that nobody reviews.
Step 4 MUST NOT start until Step 3 has a result for one action.

Step 4. Test first. Metric: actions closed. Baseline: zero closed actions in the last three sessions, per the first assumption. Pass threshold: at least one of two actions closed. Sample size: two sessions.
This step is stochastic.
Domain: Complex. Reason: induction from two trials. A constraint outside the team can break the pattern.
Increment: run the one-action rule for two sessions only. Budget: two sessions. Stop if both actions stay open.
Blocker removed: doubt that the rule changes the work.
Leverage of this probe is a guess.

Follow-up
If the Step 1 score is at least 70%, owners already exist.
If actions still do not close, replace Step 2.
The replacement is a five-minute check of capacity for the owner.
