## Headline

Rename the column now with one ALTER TABLE statement, then update every view, function, and application query that still names the old column.

- The rename is a metadata-only change, but it takes an ACCESS EXCLUSIVE lock, so keep the transaction short [1].
- The rename does not update views, functions, or generated code that references the old name [1].
- Application code and the database change must ship together, or queries start to fail.

## Background

You asked to rename the column `user_id` in the `orders` table of a PostgreSQL database. The task is a schema change, so dependent code decides whether it is safe.

## Relevance

A rename that skips dependent code breaks read paths at the next query. The fix is small, but the release order decides the failure mode.

## Information

**Analysis**

PostgreSQL applies the rename in place. The statement is:

```sql
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
```

The change itself is fast. However, it locks the table against all other access until the transaction ends. Therefore keep other statements out of that transaction [1].

PostgreSQL does not track the rename into views or stored functions. They keep working through the old positional or search-path behavior, so check them before the release [1].

Run the change inside a transaction with a check after it, like this:

```sql
BEGIN;
ALTER TABLE orders RENAME COLUMN user_id TO account_id;
SELECT column_name FROM information_schema.columns
  WHERE table_name = 'orders' AND column_name = 'account_id';
COMMIT;
```

If the SELECT returns a row, the rename landed. If not, run `ROLLBACK;` and the schema returns unchanged.

**Alternative considered**

A zero-downtime expand-and-contract release (add the new column, dual-write, drop the old one). It loses here because a rename is reversible in seconds and the schema has no stated dual-write need [judgment].
