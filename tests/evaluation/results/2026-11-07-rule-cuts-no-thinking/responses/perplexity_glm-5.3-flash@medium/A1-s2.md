## Background

The repository has a requirements.txt with no pinned versions. The build broke twice last month after a library update.

## Relevance

Unpinned dependencies fail without any change to your code. Pinning converts an unpredictable failure into a reviewed, tested change.

## Information

First, the evidence. An install without pins reads each requirement as an open range, for example `flask>=2.0`. So each fresh install can take a newer release than the one that passed your tests. Your team saw two such failures in one month [1]. That is the baseline for the recommendation: two broken builds per month.

Next, the assumption log:

`Assumption: this repository is an application, not a reusable library. Why not measured: the material does not state it. Validate by: check the repository readme for a published package. If wrong: pin direct dependencies in an upper-bounded range instead, and treat the lock file as the reproducible artifact.`

Then, the alternative considered. Pinning only the transitive packages, or using loose ranges with a lock file, loses because direct dependencies drive the API your code calls. A new direct release changes your surface first.

## End

I recommend that we take four actions.

1. **Pin the direct dependencies.** Change requirements.txt to one exact `package==version` line per direct dependency, at the versions that passed the last green build. This removes the silent-update blocker.
   - Kind: deterministic. Domain: Clear, because the rule "pin what you depend on" is known and applies in one step.
   - Test, written before the work:
     ```
     Given requirements.txt lists one pin for each direct dependency
     When we run pip install -r requirements.txt in a clean environment
     Then no package installs a version newer than its pin
     ```
2. **Create a lock file for the transitive tree.** Generate a full freeze of the clean install with `pip freeze > requirements-lock.txt`, and install from it in CI. This removes the transitive-update blocker. Step 2 MUST NOT start until the test in Step 1 passes.
   - Kind: deterministic. Domain: Complicated, because the analysis of the resolved tree picks the practice; the tool does the work after the choice.
   - Test:
     ```
     Given requirements-lock.txt exists and is committed
     When a clean install runs from the lock file
     Then the installed tree matches the file, package by package
     ```
3. **Add a CI gate on dependency changes.** Run the test suite on every pull request that touches a requirements file, and block merge on failure. This adds the capability of a checked update instead of a blind one. Step 3 depends on Step 1 for the pins it reads.
   - Kind: deterministic. Domain: Clear.
   - Test:
     ```
     Given a pull request changes requirements.txt
     When CI runs
     Then the full test suite runs and a failure blocks the merge
     ```
4. **Run a gated update cycle as a probe.** Update one dependency per week, run the test suite, and record which packages fail. Measure broken builds per month against the baseline of two [1]. Accept at zero broken builds over eight weeks. Budget: two hours of review per week. Stop condition: three weeks in a row with failures above one build per week. Leverage here is a guess, because future library behavior is not yet visible.
   - Kind: stochastic. Domain: Complex, because the effect of each new release shows only after the test run; the probe watches for a changing failure pattern.
   - Acceptance test, written before the trials:
     ```
     Given eight weekly update runs
     When we count broken builds per month
     Then the count meets the threshold of zero (baseline: two per month [1], sample size: eight)
     ```

Ordering check: no step is Chaotic or Confused. Steps 1 to 3 are Clear or Complicated, ordered by leverage. Step 4 is a Complex probe, capped by its budget, and it MUST NOT run until Steps 1 and 2 give it a stable baseline.

If the assumption is false and this is a reusable library, replace Step 1's exact pins with upper-bounded ranges and keep Steps 2 to 4 unchanged.
