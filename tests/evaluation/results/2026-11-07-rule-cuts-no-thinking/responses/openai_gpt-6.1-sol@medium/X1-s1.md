## Headline

Make the summariser measurable before changing its model, and test one targeted fix against the current version.

- Keep agents in control while the error rate remains unknown. [judgment]
- Separate wrong facts, missing facts, and poor usefulness so each problem has a distinct measure. [judgment]
- Accept changes only after a paired test on the same support tickets. [judgment]

## Background

Agents report that the large language model (LLM) summariser is “sometimes wrong,” but the team has no metrics. [1]  
The request includes no ticket examples, generated summaries, or test results.

## Relevance

Without examples and a baseline, the team cannot tell whether a change improves summaries. [judgment]  
Therefore, the first increment should produce evidence, not a model replacement. [judgment]

## Information

### Measures

Use these proposed definitions and thresholds as an initial test contract, not as established industry standards. [judgment]

| Measure | Definition | Purpose |
|---|---|---|
| Incorrect-summary rate | Summaries with at least one contradicted or unsupported claim, divided by summaries reviewed | Measures factual error |
| Major-omission rate | Summaries that omit a fact needed for the agent’s next action, divided by summaries reviewed | Measures completeness |
| Severe-error count | Errors about identity, money, account access, or an action the customer must take | Tracks higher-impact errors |
| Usable-summary rate | Summaries an agent accepts without factual correction or a major addition, divided by summaries reviewed | Measures practical value |

A claim is supported only when the ticket text available at generation time supports it. [judgment]  
Do not penalise a summary for facts that arrive later. [judgment]

Keep two test groups separate: randomly selected recent tickets and reported failures.  
The first estimates recent performance; the second checks known failure cases. [judgment]

## End

I recommend that we complete these four steps, with no automatic customer-facing release.

### 1. Make summaries review-only

**Kind:** Deterministic.  
**Domain:** Clear, because deduction from the review rule determines whether an unapproved summary can reach a customer.  
**Increment:** One configuration change, capped at one engineering hour.  
**Blocker removed:** Unreviewed summaries can otherwise affect customers before the team measures errors. [judgment]

**Test, before work:**

```gherkin
Given a generated summary without agent approval
When a customer-facing action uses that summary
Then the tool blocks the action until an agent approves it
```

Apply the gate, verify the test, and retain a working review-only flow.  
If this gate already exists, verify it rather than rebuild it.

### 2. Create a versioned test pack

**Kind:** Deterministic.  
**Domain:** Complicated, because analysis of the generation inputs determines which evidence each summary can use.  
**Increment:** One test-pack export, capped at two engineering hours.  
**Capability added:** Repeatable comparisons against identical ticket evidence. [judgment]

**Test, before work:**

```gherkin
Given 40 randomly selected recent tickets and up to 10 reported failures
When the test pack exports each example
Then each example includes its generation-time text, summary, model, and instruction version
```

Store only approved data in an access-controlled location.  
Record the selection date and keep the two groups separate.

Step 2 MUST NOT start until Step 1 passes.  
If version details are unavailable, record that gap and capture them for subsequent summaries.

### 3. Run one paired improvement probe

**Kind:** Stochastic.  
**Domain:** Complex, because induction from trials tests whether one change reduces errors.  
Ticket mix or model variation can break the observed pattern.  
**Increment:** One candidate against the current version, using the test pack.  
**Budget:** At most 100 generated summaries and four reviewer-hours.  
**Capability added:** Evidence for accepting or rejecting one change. [judgment]

**Acceptance test, before work:**

- **Baseline:** Current-version scores on the same tickets.
- **Sample:** 40 recent tickets, plus up to 10 reported failures.
- **Primary threshold:** At least 25% fewer incorrect summaries among recent tickets, with at least two fewer incorrect summaries.
- **Safety threshold:** Zero severe errors from the candidate across both groups.
- **Completeness threshold:** No increase in major omissions among recent tickets.
- **Usefulness threshold:** No decrease in usable summaries among recent tickets.

These are proposed screening thresholds, not proof of production safety. [judgment]

First, review current summaries against their ticket evidence using the definitions above.  
Next, count errors by cause: missing input, unsupported claim, contradiction, or omission.  
Select the most frequent cause and change only one relevant component.

For example, test explicit source references when unsupported claims dominate. [judgment]  
Hide version names from reviewers and vary summary order.

Stop when the budget expires or a severe candidate error appears.  
Reject the candidate unless every threshold passes.  
If the baseline contains fewer than two incorrect summaries, expand the baseline before claiming an improvement.

Step 3 MUST NOT start until Step 2 passes.

### 4. Add the accepted cases to a release gate

**Kind:** Deterministic.  
**Domain:** Clear, because deduction from recorded acceptance results determines whether release is permitted.  
**Increment:** One release check, capped at two engineering hours.  
**Blocker removed:** A later change can otherwise bypass the agreed test. [judgment]

**Test, before work:**

```gherkin
Given a candidate without a passing evaluation record
When the team attempts to release that candidate
Then the release check blocks it
```

Require the test-pack version, candidate version, scores, and reviewer approval in the release record.  
Verify both a blocked release and an authorised release.

Step 4 MUST NOT authorise a candidate until Step 3 passes.  
Keep human review after release; this small test does not establish an unattended-use safety rate. [judgment]

## Follow-up

If incorrect summaries remain rare but agents still reject them, investigate usefulness rather than optimise factual accuracy alone. [judgment]  
If required facts never reach the model, fix the input before changing the model. [judgment]
