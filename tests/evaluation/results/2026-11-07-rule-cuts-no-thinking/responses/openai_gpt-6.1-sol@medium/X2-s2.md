## Background

Your team attends retrospectives, but you report that nothing changes afterward. [1] Attendance therefore does not establish that the meetings improve work. [judgment]

## Relevance

Another discussion format does not address a failure to act on decisions. [judgment] The next retrospective should test the path from discussion to a concrete change. [judgment]

## Information

First, distinguish these possible failure points:

| Failure point | Evidence to seek | Response |
|---|---|---|
| Choice | Broad goals such as “communicate better” | Specify one observable change |
| Ownership | Nobody accepts the next action | Name one owner |
| Authority | The action needs approval outside the team | Name the decision-maker and request |
| Follow-through | Nobody checks the action or its effect | Start the next meeting with evidence |

These are diagnostic possibilities, not findings about your team. [judgment]

Do not treat every unfinished action as an effort problem. An owner without time or authority cannot resolve the constraint alone. [judgment]

**Assumption:** The team can test one small work change. **Why not measured:** The material does not state it. **Validate by:** Confirm permission before the test. **If wrong:** Seek the required decision before launching it.

**Alternative considered:** Change the retrospective format or facilitator first. This loses because it does not directly repair the path from decisions to action. [judgment]

### 2. Create one bounded change test

Step 2 MUST NOT start until Step 1 produces its record.

**Test first, deterministic:**
```gherkin
Given the action record
When the team writes one change-test card
Then it states the change, owner, permission, measure, budget, and stop condition
```

Use 15 minutes of the next retrospective to complete one card. For example:

> For five working days, add one named reviewer to each new review request.  
> Owner: one named team member.  
> Measure: requests still awaiting review after one working day.  
> Baseline: the previous five working days.  
> Budget: five minutes per day.  
> Stop: end after five days, or sooner if the change delays urgent work.

Use the team’s actual bottleneck rather than this example. The card removes vague commitments and limits the cost of an unsuccessful test. [judgment]

**Domain: Complex**, because the effect requires induction from a trial. Workload changes can break the observed pattern, so leverage remains a guess. [judgment] Run only this capped test, not a permanent rollout.
