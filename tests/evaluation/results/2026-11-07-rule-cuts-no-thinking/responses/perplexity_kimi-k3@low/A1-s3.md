## Background

Your requirements.txt lists no versions. A library update broke the build twice last month. The decision is whether to pin versions.

## Relevance

Unpinned builds resolve to the newest library version each time. Therefore any upstream release can break the build without any code change on your side.

## Information

Evidence: two build failures last month came from library updates, per the user message [P].

A pinned file, for example `requests==2.32.3`, forces the same version at each install, so failures from upstream releases stop [judgment].

Pip freezes only direct dependencies in requirements.txt. Transitive dependencies, those your libraries pull in, still float. Tools such as `pip-compile` or hashes with `pip --require-hashes` close that gap [judgment].

Unpinning trades stability for easy updates. A monthly review job, for example Dependabot or a scheduled `pip list --outdated`, recovers the update path [judgment].

Assumption: the team can run a monthly dependency review. Why not measured: the material does not state it. Validate by: ask one teammate to own the first review. If wrong: replace the manual review with Dependabot.

Alternative considered: pin nothing and accept breakage. It loses because breakage already cost two build cycles last month and costs are unbounded.
