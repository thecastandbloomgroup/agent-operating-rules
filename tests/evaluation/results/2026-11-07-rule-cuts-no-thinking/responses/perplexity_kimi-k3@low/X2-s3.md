# Headline

Retrospectives stop producing change when actions lack owners, deadlines, and follow-through checks. The fix is a decision-bounded format with one to three owned actions per session. A review of the last three retrospectives shows where the pipeline breaks. A two sprint trial tests whether the new format restores change.

# Background

The team runs retrospectives. People attend, but no process or outcome changes follow, therefore the meetings feel hollow. The request is for a practical way to restart change.

# Relevance

Broken retrospectives cost meeting time and erode trust, so the rest of the improvement system degrades. Fixing them restores the team's main mechanism for self-correction.

# Information

Agile literature identifies the common failure causes: too many actions, no assigned owner, no review of prior actions, and actions outside the team's authority. The number and impact of completed action items is the standard health metric for a retrospective practice [1].

Assumption: the team is a software team using Scrum or a similar sprint cycle. Why not measured: the query does not state it. Validate by: ask the requester. If wrong: adapt step timing to the team's actual review cadence.

Assumption: the team holds authority over actions inside its own process. Why not measured: the query does not state it. Validate by: the facilitative review in Step 2. If wrong: route system-level issues to management instead of the action list.

Alternative considered: stop running retrospectives entirely. This loses because the team then has no structured improvement loop at all, so the underlying problems persist [judgment].

# End

I recommend that we:

1. Cap each retrospective at one to three actions, each with a named owner and a due date. Increment: one facilitated session. Blocker removed: diffusion of responsibility, the largest known failure cause [1]. Kind: deterministic. Test, deterministic: Given the session ends, When the action list is recorded, Then each action has one owner and one date. Domain: Clear, because this is a best practice with known cause and effect.

2. Open each retrospective with a ten-minute review of the prior action list. Increment: a standing agenda item. Blocker removed: no feedback loop on whether actions completed. Kind: deterministic. Test, deterministic: Given the session starts, When the previous list is read, Then each item is marked done, in progress, or dropped with a reason. Domain: Clear, deduction from the feedback-loop principle.

3. Audit the last three retrospectives before the next one. Count actions recorded, owned, and completed. Increment: a 30 minute review of notes and tickets. Blocker removed: diagnosis of which stage breaks. Kind: evaluative. Rubric first: completion rate (weight 50%), ownership rate (30%), scope inside team authority (20%); pass threshold: below 60% completion signals a follow-through failure. Domain: Complicated, analysis of past records. This step precedes Step 1 because it confirms the diagnosis.

4. Run the new format for two sprints as a safe-to-fail probe. Metric: action completion rate. Baseline: the rate measured in Step 3. Pass threshold: two or more of three actions completed per sprint, across at least two sprints. Stop condition: zero completion after two sprints. Budget: two sprints, no format changes mid-trial. Kind: stochastic. Domain: Complex, leveraged claimed improvement is uncertain, therefore capped by the two sprint budget.

Steps 1 and 2 start after Step 3 finishes. Step 4 MUST NOT start until Step 3 produces the baseline rate.

If the audit shows most failures are system-level issues outside team authority, redirect Step 1 actions to a manager escalation channel instead of the team list.
