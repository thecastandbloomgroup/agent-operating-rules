# Headline

Yes, pin the versions in requirements.txt.

- Two build breaks last month already show the cost of unpinned dependencies [judgment].
- Python packaging guidance recommends pinned versions with hashes for deployed applications [1].
- Pinning makes builds reproducible, so the same environment builds anywhere.
- A scheduled update process replaces the risk that unpinned installs create.

## Background

The team has a requirements.txt with no pinned versions. Two builds broke last month after a library update, so deployment currently accepts unplanned upstream change.

## Relevance

Each unpinned build can pull a new library release without review. The team absorbs the breakage at the worst time, that is, during a build or deploy.

## Information

Python packaging guidance states that applications should pin exact versions, and that hash checking adds protection against tampering [1]. Reproducible installs, meaning the same input gives the same environment, remove the class of failure seen last month [1]. Pip supports exact pins (`package==1.2.3`) and per-file hash lists [1].

The alternative is to cap versions with ranges such as `package<2.0`. Caps reduce breakage risk but keep builds unreproducible, because pip can still pick different versions at install time. Caps also failed here indirectly, because nothing was written at all.

Assumption: requirements.txt installs the production application, not a published library. Why not measured: the material does not state it. Validate by: check whether the file also packages the software for others. If wrong: use compatible ranges in library metadata instead, and pin only in a separate lock file.

## End

I recommend that we pin versions and add a controlled update process.

1. Pin every direct and transitive dependency in requirements.txt with exact versions, and add hashes.
   - Kind: deterministic. Domain: Clear, because a known best practice applies by direct rule [1].
   - Blocker removed: unreproducible builds.
   - Test:
     ```
     Given a clean virtual environment,
     When pip installs from the pinned requirements.txt twice,
     Then both installs report identical package versions and hash checks pass.
     ```
2. Record the two last-month breakages in a short incident note, with the library and version that caused each.
   - Kind: evaluative. Domain: Clear, because the record exists and the extraction is one step.
   - Blocker removed: no memory of which libraries drift.
   - Test: the note names the library, the old version, and the new version for each breakage. Pass threshold: both incidents complete.
3. Add a monthly update step that upgrades one dependency, runs the test suite, and opens a review before merge.
   - Kind: evaluative. Domain: Complicated, because the choice of which dependency to update first needs judgement; pick the one that broke last month.
   - Blocker removed: pins growing stale and insecure [judgment].
   - Test: rubric: tests pass (weight 60%), no new security advisory on the new version (weight 40%), pass threshold 90 of 100.
4. Remove pins one at a time only if a library proves unstable under pinning. Step 4 MUST NOT start until Steps 1 to 3 pass.

## Follow-up

If the application is a published library rather than a deployed service, replace Step 1 with compatible ranges in package metadata and keep the pinned file as a lock for testing.
