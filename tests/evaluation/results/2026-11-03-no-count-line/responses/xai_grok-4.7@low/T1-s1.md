Background
The team has no shared format for SQL (Structured Query Language). Because of that gap, reviews fight over layout. The request is to stop that fight.

Relevance
The next review will repeat the same fight until a machine owns layout. A pipeline rule stops that repeat on the next change.

Information
The request states that format disagreement causes friction in every review [1].

A team needs one format rule, not personal habits [2].

Therefore that rule has to sit in one place the whole team runs.

More than one formatter can be a sound practice, so a short trial has to pick one [3].

A1. The SQL in the repo parses with a common formatter. Why not measured: the material does not state the dialect. Validate by: run two formatters on 10 files. If wrong: Step 1 picks a dialect tool, and later steps stay.

A2. A continuous integration pipeline exists or can be added in one session. Why not measured: the material does not state the toolchain. Validate by: open the pipeline files. If wrong: use a pre-commit hook in Step 3.

The strongest alternative is a style guide with no machine check. It loses because the team already does not agree, so another guide leaves the same review fight [1].

End
I recommend that we do these five steps.

1. Evaluative test first. Criteria and weights: dialect fit 40, pipeline fit 30, config in the repo 20, and 10 files formatted in under 5 minutes 10. Pass threshold: 70 of 100. Evidence: a score sheet from the trial. Increment: score two formatters in one session. Blocker removed: a choice with no trial. Domain: Complicated, because a trial must pick among sound practices. Later steps need this result.

2. Deterministic test first.
Given the winning config,
When the formatter runs twice on the 10 trial files,
Then the second run changes nothing.
Increment: commit that config and those 10 files in one session. Blocker removed: no shared rule in the repo. Domain: Clear, because the team applies the practice Step 1 picked. Step 2 MUST NOT start until the Step 1 score passes 70.

3. Deterministic test first.
Given a change that breaks the format,
When the pipeline check runs,
Then the check fails and names the file.
Increment: add one check job in one session. Blocker removed: unformatted SQL still reaches review. This is the largest blocker among the Clear steps. Domain: Clear, because a failing check is the known way to hold a format rule. Step 3 MUST NOT start until the test in Step 2 passes.

4. Deterministic test first.
Given the check passed,
When a reviewer comments,
Then the comment does not ask for a format change.
Increment: add the rule to the review guide in one session. Blocker removed: style debate after a green check. Domain: Clear, because the rule follows the check. Step 4 MUST NOT start until the test in Step 3 passes.

5. Stochastic test first. Metric: share of review comments that only ask for format. Baseline: that share in the last 20 reviews. Pass threshold: at or below half the baseline. Sample size: the next 20 reviews. Increment: count those comments only. Do not add rules in this step. Blocker: it is unknown whether debate falls after the check. Domain: Complex, because behavior shows the cause only afterward. Leverage here is a guess. Budget: one repository and two weeks. Stop if people bypass the check more than twice. Step 5 MUST NOT start until the test in Step 3 passes.
