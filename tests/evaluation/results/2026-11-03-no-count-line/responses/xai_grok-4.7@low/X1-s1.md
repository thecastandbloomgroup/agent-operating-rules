Background
The support tool now adds summaries from a large language model, called an LLM here.
Agents say some summaries are wrong, and the team has no error metric.
The request is to make that summarizer better.

Relevance
A model or prompt change can cost more and still be wrong. [judgment]

Information
Abstractive summaries often state facts that are not in the source.
ROUGE is a word-overlap score for summaries.
Such scores match human fact judgments poorly [1].
Therefore the team needs a human fact score before it shops for a model. [judgment]
The request states no model name, volume, or error log. [no source]
The main error type is not known.
Confidence is low: the request has no examples.

A1. Summaries cover support tickets or chats that agents read. Why not measured: the material does not state it. Validate by: open one live case with the product owner. If wrong: relabel the sample to the real input and output.

A2. The main defect is an invented or wrong fact, not tone. Why not measured: the material does not state the error type. Validate by: the tag test in Step 1. If wrong: change rubric weights before Step 4.

A3. Fifty real cases can be reviewed in one week. Why not measured: no access rule is in the material. Validate by: a data-owner yes or no before Step 3. If wrong: use redacted cases and do not ship a model change.

The strongest alternative is to change the model or the prompt now.
It loses because no baseline exists, so a win cannot be told from noise. [judgment]
