**Kind:** Evaluative.  
**Domain:** Confused, because the report does not distinguish factual errors, missing facts, stale inputs, or unclear presentation.

**Test first: weighted review rubric**

| Criterion | Weight | Evidence |
|---|---:|---|
| Factual support | 50% | Source passage for each factual claim |
| Required-fact coverage | 30% | Reviewer’s source-based fact list |
| Clear status and next action | 20% | Source status compared with summary |

### 2. Add a minimal safety barrier

**Kind:** Deterministic.  
**Domain:** Clear, because the acceptance checks concern visible workflow behavior, not uncertain model quality.

**Test first:**

```gherkin
Given an agent views a generated summary
When the agent opens the ticket
Then the source conversation remains accessible

Given a generated summary contains an error
When the agent reports the error
Then the report records the ticket and summary version

Given a summary has not received agent approval
When a customer response is sent
Then the system does not insert that summary automatically
```

**Increment:** Add the missing controls in one session, or disable the unsafe automatic path until they exist.

**Blocker removed:** Agents can inspect, reject, and report faulty summaries. These controls reduce exposure without claiming better model accuracy. [judgment]

Step 2 follows Step 1 unless A2 is false. In that case, suspend automatic use before Step 1.

### 3. Test one targeted correction offline

**Kind:** Stochastic.  
**Domain:** Complex, because the effect of a prompt or model change requires observation.

**Acceptance test first:**

- **Baseline:** Current version on the same source snapshots.
- **Sample:** 50 fresh tickets, with two outputs per version per ticket.
- **Threshold:** Zero serious errors, fewer unsupported claims, and no loss of required-fact coverage.
- **Review:** Hide version labels from reviewers.

These are proposed pilot thresholds, not proof of a low production error rate. [judgment]

**Increment:** After Step 1, change only the largest confirmed defect’s suspected cause.

For example, repair missing source input before changing the prompt. If inputs are complete, test a prompt that requires source-supported facts and explicit unknowns. [judgment]

**Capability added:** Evidence that one correction improves the measured defect.

**Budget:** One work session and at most 200 generated summaries. Stop on any serious candidate error. Do not promote an incomplete test.

Step 3 requires Step 2’s tests to pass. The expected benefit remains a guess until this probe completes.

### 4. Check usefulness with agents

**Kind:** Stochastic.  
**Domain:** Complex, because agent behavior determines the practical benefit.

**Acceptance test first:**

- **Baseline:** Current-version task time and quality.
- **Sample:** 40 ticket tasks, randomly split equally between versions.
- **Threshold:** At least 15% lower median task time, zero serious errors, and no lower required-fact coverage.
- **Measure:** Include inspection and correction time, not just generation time.

These are proposed screening thresholds; this small pilot does not establish production safety. [judgment]

**Increment:** Run one supervised session after Step 3 passes.

**Capability added:** Evidence that factual improvements also help agents.

**Budget:** One session, capped at 40 tasks. Stop immediately for a serious error. If the sample remains incomplete, keep the candidate restricted.
