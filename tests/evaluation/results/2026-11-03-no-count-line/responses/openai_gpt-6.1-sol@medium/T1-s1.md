I recommend that we take these three steps.

### 1. Agree on how decisions work

**Kind:** Deterministic. **Domain:** Clear, because the output is a short policy with explicit acceptance criteria.

**Test first:**

```gherkin

When the team applies the policy
```

In one 30-minute session, name one maintainer as the decider and give each team member a chance to state constraints.

Publish a short policy:

> The formatter governs SQL appearance. Human review addresses substantive concerns.  
> Anyone can propose a rule change with an example and its practical impact.  
> The maintainer decides after hearing affected people.  
> Discuss the code and its effects, not the author's competence or taste.

This removes unclear authority without requiring everyone to prefer the result. [judgment] Apply the same policy to senior and junior staff.

### 2. Make the rule executable

**Dependency:** Step 2 starts after Step 1 passes.

**Kind:** Deterministic. **Domain:** Complicated, because compatibility requires analysis of the SQL dialect and any template syntax.

**Test first:**


In one working session, check formatter support against the repository’s actual syntax.

Configure one formatter, pin its version, and add one shared command. Add an automated check if permissions allow.

Keep any initial reformat separate from functional changes. This separates format changes from code behavior during review. [judgment]

If no formatter passes the test, do not force adoption. Use a minimal written rule until compatibility work succeeds.

### 3. Run a bounded trial, not a permanent decree

**Dependency:** Step 3 starts after Step 2 passes.

**Kind:** Stochastic, because review behavior varies. **Domain:** Complex, because the cultural effect becomes visible only after the trial.

**Acceptance test first:**

- **Metric:** Percentage of reviews containing a disputed cosmetic comment.
- **Baseline:** Measure the previous ten SQL reviews.
- **Sample:** Observe the next ten SQL reviews.
- **Pass threshold:** Reduce that percentage by at least half, with zero formatter-caused failures in existing checks.
- **Status:** Not measured; acceptance remains pending.

Run the trial for at most two weeks, with two staff-hours reserved for process adjustments. These limits and thresholds are proposed decision rules. [judgment]

Stop if formatting changes SQL behavior or breaks templates. If fewer than ten reviews occur, record insufficient evidence rather than declaring success.

At the final review, hear from each participant about unresolved friction. Keep the process only after the acceptance test passes.

The expected cultural benefit remains a hypothesis, not a promised result. [judgment]
