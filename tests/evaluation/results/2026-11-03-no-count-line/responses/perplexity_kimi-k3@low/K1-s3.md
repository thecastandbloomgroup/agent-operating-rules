## Headline

The release cut the database pool from 50 to 8 connections per pod, and requests now wait about 690 ms just to get a connection [1].

- The wait for a connection rose from 3 ms to 690 ms at p95, which is 88% of the added latency [2].
- Cache misses rose from 12% to 31%, so more requests need the database at the same time [2].
- The database itself is not the bottleneck: query times stayed flat and its CPU peaked at 41% [2].
- Roll back the cache and pool config now, then resize the pool against the OPS-412 limit [1].

## Background

Release 2026.10.21 deployed on 2026-10-21 and changed the pool config, the cache TTL (time to live), and the ORM (object-relational mapper) query for orders [1]. The endpoint p95 (95th percentile) latency rose from 120 ms to 900 ms, and errors rose from 0.02% to 0.40% [2]. The pool change cites ticket OPS-412, a new connection limit per service, but the diff does not state its value [1].

## Relevance

At the 405 requests per second peak, a 0.40% error rate fails about 97 requests per minute [2]. Almost all of these failures (96%) are pool timeouts, so the errors stop only when the queue stops [2].

## Information

What changed, and what each change did. Before and after values come from the diff [1].

| Change | Before | After | Observed effect |
|---|---|---|---|
| Pool max per pod | 50 | 8 | p95 wait for a connection: 3 ms to 690 ms [2] |
| Pool acquire timeout | 30 s | 5 s | Slow requests now fail as 503 after 5 s [3] |
| Cache TTL | 300 s | 60 s | Miss rate: 12% to 31% [2] |
| ORM loads order lines | lazy | eager batch | Line query p95: 30 ms to 26 ms [2] |

Attribution. Total p95 rose by 780 ms, and the connection wait rose by 687 ms, so the queue explains 88% of the added latency [2]. Query spans, serialization, and cache lookups stayed flat, so no other span explains the rise [2]. Pool-exhausted warnings confirm this: zero on 2026-10-20, and 1,800 to 2,400 per hour on 2026-10-22 [3].

Why the pool queues. Each pod runs 8 workers and now has 8 connections, with zero headroom [1]. Peak load is about 101 requests per second per pod [2]. If a request holds its connection for most of its 210 ms p50 duration (A2), demand is about 21 connections per pod, per Little's law [4]. Supply is 8, so the model predicts about 13 waiters. Logs show 6 to 14 waiters, so the model matches [3]. Database CPU peaked at 41%, so the server has spare capacity [2].

The ORM change. It adds one batched query for order lines, and its spans stayed flat, so it is not a cause [2]. The old code loaded order lines lazily, so the new eager batch is an improvement worth keeping [inference].

Confidence: high, because three independent records (diff, traces, logs) agree on the cause and on its size.

Assumption log:

`A1. The limit of 8 applies per pod, and the reported peak of 8 active database connections is a per-pod metric. Why not measured: the material shows "8 of 8" on several pods but never states the metric scope. Validate by: query the database for per-application connection counts. If wrong: the pool is service-wide, so Step 3 designs a shared pooler instead of per-pod sizing.`

`A2. Requests hold a connection for most of the request, not only during queries. Why not measured: the traces have no connection-hold span. Validate by: add a hold-time span or read the session lifecycle code. If wrong: Step 4 becomes optional, because burst load alone would explain the queue.`

`A3. Ticket OPS-412 allows a temporary return to 50 connections per pod. Why not measured: the ticket is not in the material. Validate by: read OPS-412 before Step 1. If wrong: use the hedge in Step 1 and rely on the TTL revert first.`

Alternative considered. Keep the release and only raise the pool back to 50. This loses because the 60 s TTL keeps misses at 31%, about 2.6 times the baseline database demand, so the service sits near the OPS-412 cap with no margin [2]. If the cap is real, raising the pool is not possible at all, so the TTL revert and the hold-time fix are needed anyway.
