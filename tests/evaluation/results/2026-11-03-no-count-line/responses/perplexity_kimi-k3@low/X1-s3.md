# Headline

Build a measurement loop first, then improve the summariser against a tested quality bar.

- "Sometimes wrong" has no severity, rate, or failure type. Measurement defines the problem.
- The summariser is stochastic. Fixes must be proven by trials against a baseline, not by inspection.
- A small set of labeled cases becomes the regression suite for every later change.

# Background

The support tool has an LLM-based summariser. Agents report errors, but no metrics exist. The request is to improve the output.

# Relevance

Without a baseline, any change can make some errors better and others worse with no way to know. A measured baseline protects agents and gives a pass test for each fix.

# Information

Evidence is limited to the agent reports provided in the conversation.

- Claim: the summariser sometimes fails. Source: agent feedback, type unknown [no source].
- Claim: hallucinated facts are a known failure mode of LLM summarisation, so errors are expected, not anomalous [judgment].

Assumption log:

A1. Failures are factual errors, omissions, or wrong tone, not tool outages. Why not measured: the material does not state it. Validate by: sample 50 recent summaries with agents. If wrong: replace the labeling schema in Step 1.

A2. At least 50 recent summary and transcript pairs are retrievable. Why not measured: the material does not state it. Validate by: query the support database once. If wrong: collect summaries prospectively for one week before Step 2.

A3. No organisation quality bar exists for summaries. Why not measured: the user has not answered. Validate by: one question below. If wrong: adopt the existing bar in the rubric.

Alternative considered: replace the summariser with a different model or vendor. It loses because no baseline exists to prove the replacement is better, so the swap buys risk without evidence [judgment]. Model swaps remain an option after the metric exists.

Confidence: likely. Basis: agent reports are consistent in direction; failure type and rate are unmeasured.

# End

I recommend that we:

1. Collect 50 random recent summaries with their transcripts and label each error by type. This removes the "no data" blocker and produces the failure taxonomy. (Evaluative; rubric first: error types factual, omission, tone; a summary passes only with zero factual errors.) Cynefin Confused: the failure class is unknown, so this step classifies the problem. Test:

   Given 50 labeled summaries,
   When error types are counted,
   Then the dominant type accounts for at least 30% of errors, or more cases are sampled.

2. Rate 100 summaries with an agent-reviewed binary quality score. This adds the baseline error rate. (Stochastic; measure: error rate, baseline unknown, threshold set after measurement, n=100.) Cynefin Complicated: the measurement method is fixed and knowable. Step 2 MUST NOT start until Step 1 delivers the taxonomy.

3. Change the highest-frequency failure mode with one targeted fix, for example a stricter prompt with grounded citations to the transcript. This adds an improvement lever. (Stochastic; measure: error rate, baseline from Step 2, pass at a 30% relative reduction, n=100 trials.) Cynefin Complex probe: cause and effect of prompt changes are unpredictable, so cap at 10 prompt variants and stop if no variant passes in two sessions.

4. Add the labeled cases plus the rating step as a regression gate on every future change. This adds permanent protection against silent degradation. (Deterministic.) Cynefin Clear: regression gating is standard practice. Test:

   Given a candidate prompt or model,
   When the gate runs on the labeled suite,
   Then deployment is blocked when the error rate exceeds the Step 3 rate.
