## Headline

Fix the flaky build in four steps: measure the failures, quarantine the worst tests, fix the top cause, and add monitoring.

1. Flaky tests dominate intermittent failures at scale: at Google, 84% of pass-to-fail transitions involved a flaky test [1].
2. The causes cluster: async wait, concurrency, and order dependency explain 77% of flaky tests in a Microsoft study [2].
3. Fixes differ by cause, so classification of the last 20 failures comes before any fix.

## Background

The build fails intermittently, and the report includes no logs, failure rate, or tool names (see A1). The usual cause is a small set of flaky tests [1]. A flaky test passes or fails without any code change; quarantine excludes it from the gating result while it gets fixed.

## Relevance

A signal that fails at random teaches people to ignore red builds, so real regressions pass unnoticed. Therefore, restoring a trustworthy signal is the fast win; the deep fixes follow.

## Information

**Evidence**

- Prevalence: Google measured almost 16% of its tests as flaky, and 84% of pass-to-fail transitions involved a flaky test [1].
- Baseline for prevalence: at that scale, new code regressions explain a minority of intermittent failures.
- Causes: a Microsoft study of its flaky tests found three dominant causes [2].
- Baseline for causes: async wait, that is, waiting on asynchronous work, caused 45%; concurrency 20%; order dependency 12%. The top three cover 77% of cases, so a three-category plan covers most fixes.
- Replication: an independent study of open-source projects found the same top causes [3].
- Therefore, confidence is high that these three categories dominate: high confidence, two independent studies agree.
- Transfer: these figures come from large organizations. Treat them as priors for this build, not as measurements [judgment].

**Assumption log**

A1. "Flaky" means intermittent continuous integration (CI) failures caused mostly by non-deterministic tests. Why not measured: the material does not state it. Validate by: check whether any of the last 20 failed runs passed on re-run without a code change. If wrong: failures are deterministic; drop Steps 2 to 4 and debug the single failing step.

A2. CI logs for at least 20 recent runs are retained. Why not measured: the material does not state it. Validate by: open the CI history page. If wrong: enable log retention first; Step 1 waits about one week for data.

A3. The team can edit and merge test code without another team's approval. Why not measured: the material does not state it. Validate by: check repository ownership. If wrong: send quarantine requests to the owning team; Step 2 slips by their response time.

**Alternative considered**

Strongest alternative: automatically re-run failed jobs until they pass. It restores a green badge within minutes; however, it hides the failure signal, raises compute cost per run, and lets the flaky set grow. Google mitigates through detection, quarantine, and fixing, not through retries alone [1].

## End

I recommend that we run four steps in this order.

Tests use Gherkin, a Given/When/Then format [4].

Domains use the Cynefin names, that is, how cause and effect relate in the work [5].

1. Classify the last 20 failed runs.
   - Domain: Complicated, because causes are knowable from log analysis and several good taxonomies exist; this step uses the Lam categories [2].
   - Kind: evaluative. Rubric first. Use six categories: async wait, concurrency, order dependency, external service, infrastructure, product bug. Each failure gets one category. Pass threshold: 20 of 20 classified. Evidence: one log excerpt per failure.
   - Do: pull the last 20 failed runs and tag each with a category (one session).
   - Removes: the absence of data on what fails and why.

2. Quarantine the top offenders. Step 2 MUST NOT start until the rubric in Step 1 passes.
   - Domain: Clear, because a best practice exists: quarantine with an owner and an expiry date.
   - Kind: deterministic. Test first:
     Given a quarantined test fails
     When the pipeline runs
     Then the result stays green, and the failure appears in the quarantine report
   - Do: quarantine the smallest set of tests that covers at least 50% of flaky failures.
   - Removes: a red signal that nobody trusts.

3. Fix the largest root-cause category.
   - Domain: Complicated when Step 1 names async wait or order dependency, because known practices exist. If Step 1 names concurrency, treat this step as a Complex probe: cap it at one session with a stop condition.
   - Kind: stochastic. Acceptance test first. Metric: failure rate of the fixed tests. Baseline: the rate from Step 1. Threshold: zero failures. Sample size: 100 consecutive CI runs.
   - Do: apply the matching practice, for example replace fixed sleeps with polling on a condition.
   - Removes: the dominant root cause.

4. Add a weekly flakiness report and a quarantine expiry policy.
   - Domain: Clear, because scheduled reporting is a standard practice.
   - Kind: deterministic. Test first:
     Given the weekly schedule triggers
     When the report job runs
     Then it posts each test's failure rate for the last 7 days and the quarantined count
   - Do: add one scheduled job and one policy: no test stays quarantined beyond 15 working days.
   - Removes: silent regrowth of the flaky set.

## Follow-up

Conditions that change the recommendation: if A1 is wrong, drop Steps 2 to 4 and debug the single failing step. If Step 1 names infrastructure as the top cause, replace Step 3 with a runner or network fix.
