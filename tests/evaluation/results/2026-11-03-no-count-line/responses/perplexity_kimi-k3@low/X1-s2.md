## Headline

Measure first, then fix the largest error class.

- "Sometimes wrong" becomes actionable only when errors are sorted into a taxonomy: a named list of error types.
- A sample of 100 scored summaries bounds the error rate to about ±6 percentage points when the true rate is near 10% [judgment].
- For factuality errors, the highest-leverage fix is grounding: each summary claim links to its source message [judgment].
- A one-click agent rating converts every future summary into evaluation data, so quality stops depending on anecdotes.

## Background

The support tool uses an LLM (large language model) to summarise ticket threads. Agents say the summary is "sometimes wrong". No metrics exist, so the error rate and error types are unknown [1].

## Relevance

Agents who stop trusting the summary will stop reading it, so the feature loses its value. Every change made without a baseline is a guess, because improvement cannot be told apart from chance.

## Information

**Evidence**

- Agents report one theme: the summary is "sometimes wrong". One source supports it and no source disagrees [1]. A single vague theme cannot rank fixes. Therefore Step 1 converts complaints into types.
- Hallucination, a summary statement that is not in the source thread, is documented across model families and sizes [2].
- An LLM judge, an LLM that scores another LLM's output, matches human-to-human agreement levels on some benchmarks. So it can pre-screen outputs, with human spot checks [3].
- Sampling arithmetic: at a 10% true error rate, 100 samples give a 95% confidence interval of about ±6 percentage points [judgment]. A confidence interval is the range the true rate falls in with 95% probability.

**Assumption log**

- A1. The summariser condenses ticket threads for agent handoff or context. Why not measured: the material does not state it. Validate by: read the prompt template in the tool. If wrong: the taxonomy labels change, the four steps do not.
- A2. The tool stores the thread text with each summary, or can log it. Why not measured: the material does not state it. Validate by: inspect the database schema. If wrong: add a logging step before Step 2, which delays Step 2 by one session.
- A3. Volume is at least 100 summaries per two weeks. Why not measured: the material does not state it. Validate by: count rows in the summaries table. If wrong: extend the sampling window until 100 pairs exist.
- A4. Two senior agents can give one half-day for a workshop. Why not measured: the user has not answered. Validate by: send one calendar invitation. If wrong: Step 1 slips, and later steps slip with it.
- A5. The team can edit the prompt and rerun the summariser. Why not measured: the material does not state it. Validate by: locate the prompt in code or configuration. If wrong: Step 3 becomes a vendor request or a post-processing filter, with the same budget.

**Alternative considered**

Strongest alternative: swap in a stronger model now. It loses because no baseline exists to judge the swap, and prompt or grounding defects follow the new model [judgment]. Hallucinations occur across model families, so a swap alone does not remove the likely dominant error [2].

## End

I recommend that we take four steps: define error types, measure a baseline, probe one fix, and make feedback permanent.

**Step 1: Build the error taxonomy.** Kind: evaluative. Domain: Complicated, because expert agents can classify cause and effect through analysis.
- Test (written first), rubric: five types, each with a one-line definition and one example. The types are hallucination, omission, misattribution, wrong status, other. Both agents code the same 20 summaries. Pass threshold: kappa, a rater-agreement score from -1 to 1, of 0.7 or higher [judgment].
- Increment: in one half-day workshop, two senior agents code 50 recent summaries with the rubric.
- Blocker removed: "we do not know what wrong means".

**Step 2: Score the baseline.** Kind: evaluative. Domain: Complicated, because the method is known statistics.
- Test (written first), protocol: stratify the sample by week, then report a rate per error type with 95% confidence intervals. Pass when every type has a rate.
- Increment: two raters score 100 pairs of thread plus summary in one session, with 20 shared pairs for the agreement check.
- Blocker removed: "we cannot rank fixes".
- Step 2 MUST NOT start until Step 1 passes its kappa threshold.

**Step 3: Probe one grounding fix.** Kind: stochastic. Domain: Complex, because the effect of a prompt change is visible only after the trial. Run it as a capped probe; its leverage is a guess.
- Test (written first), acceptance test: metric is the error rate of the dominant type on the frozen Step 2 sample. Baseline is the Step 2 rate. Pass threshold: 50% relative reduction, and no other type rises by more than 2 percentage points. Sample size: the same 100 pairs. Stop condition: less than 30% relative reduction after three prompt variants. Budget: three variants.
- Increment: rewrite the prompt so each claim cites the ID of the message it came from. Pre-screen all 100 outputs with an LLM judge, and have humans spot-check 20.
- Blocker removed: "the dominant error class".
- Step 3 MUST NOT start until Step 2 reports its rates. Deploy to production only after the probe passes.

**Step 4: Add one-click agent feedback.** Kind: deterministic. Domain: Clear, because event logging is a known best practice.
- Test (written first), Gherkin:

```text
Given an agent views a summary
When the agent selects "wrong" and picks "omission"
Then the event is stored with summary ID, agent ID, error type, and timestamp
```

- Increment: add a "wrong" button with the five error types, and store the event.
- Blocker removed: "quality depends on anecdotes".
- Step 4 MAY run in parallel with Step 3, because it has no dependency on the probe.

Steps 1 and 2 come first because they shrink the uncertainty that Step 3 would otherwise spend its budget on.

## Follow-up

Conditions that change the recommendation:

- If A2 is false, insert a one-session logging step before Step 2.
- If Step 2 shows the dominant type is omission, replace the Step 3 grounding probe with a fixed-schema probe: issue, status, next action, open questions.
- If Step 3 hits its stop condition, escalate to an extractive-then-abstractive pipeline: quote the thread first, then write.
