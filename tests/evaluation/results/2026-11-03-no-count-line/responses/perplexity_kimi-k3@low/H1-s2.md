# Background

Checkout returns HTTP 500 (a server error code) for every user, starting at 09:12 [1]. You are the on-call engineer, and the exec call starts in ten minutes. The plan below fits those ten minutes.

# Relevance

Checkout downtime blocks revenue for all users at once. The exec call needs facts, so the last two minutes of the plan produce the update.

# Information

**Evidence**

- A sharp start time with a 100% error rate points to one change or one dead dependency, not slow capacity loss. Baseline: capacity problems raise latency before they raise errors [judgment].
- In the Cynefin framework (a model that classifies work by how knowable cause and effect are), an outage with unknown cause is Chaotic: act to stabilise, then sense [2].
- Incident practice: one declared channel, a second responder, timed updates [3].

**Assumption log**

A1. A deploy or config change on the checkout path went live within an hour before 09:12. Why not measured: the material does not state it. Validate by: open the change log and compare timestamps (one minute). If wrong: skip Step 1 and run Step 3 first.

A2. A rollback (restore of the previous version) completes in under five minutes. Why not measured: the material does not state it. Validate by: the deploy tool shows the last rollback duration. If wrong: run Step 3 in parallel with the slow rollback.

A3. One cause explains the 500s. Why not measured: measuring costs more than the decision is worth in the first ten minutes. Validate by: the 5xx rate (the family of server error codes) after Step 1. If wrong: split the responders and treat each failing dependency as its own probe.

**Alternative considered**

Diagnose the logs first, then fix the root cause directly. It loses because diagnosis time is unbounded in a Chaotic domain, while a rollback has a known duration and restores service [2].
