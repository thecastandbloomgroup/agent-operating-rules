## Headline

The pool config change (max_size 50 to 8) causes the latency spike; revert it, then revert the cache TTL.

1. The time moved almost entirely into connection wait: pool acquire p95 rose from 3 ms to 690 ms [1].
2. The 8-connection pool serves 32 worker threads, so threads queue and hit the 5 s timeout [2].
3. The TTL drop (300 s to 60 s) raised the cache miss rate from 12% to 31%, adding DB load [1].
4. The ORM change is not the cause: both DB query spans are unchanged or faster [1].

## Background

p95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed the DB pool, the cache TTL, and the ORM query. Error rate rose from 0.02% to 0.40%, with 96% of errors from PoolTimeout [1].

## Relevance

The service now returns 503s at peak and 900 ms p95, against demand of about 405 requests per second. A revert restores latency within one deploy.

The math: 8 connections per pod versus 8 worker threads per pod leaves zero headroom. One slow cache-miss request holds a connection, and waiters stack up. Before the change, peak active connections were 31 across 4 pods, which fits the old limit of 200 (4 pods × 50). The database CPU is stable at 38% to 41% [1], so the database is not the bottleneck. The selectinload change adds an order_lines query, but that span is fast (9 ms p50) and unchanged between windows [1]. Therefore the ORM change is benign with respect to this regression.

A1. The DB connection limit in ticket OPS-412 permits reverting to max_size 50. Why not measured: the material does not state the limit. Validate by: read ticket OPS-412 or ask the platform team. If wrong: keep max_size at 8 and compensate with a larger in-process queue plus a per-request query budget, latency will stay above baseline.

A2. The 5-minute cache TTL had no documented reason to change. Why not measured: the diff gives no commit message for cache.yaml. Validate by: check the change history. If wrong: keep the 60 s TTL; Step 2 alone still restores most of the latency.

### Alternative considered

Keep the 8-connection pool and raise concurrency elsewhere (more pods or fewer cache misses). This loses because logs show zero pool headroom: every saturation event shows 8 of 8 in use with 6 to 14 waiters [2]. Adding pods multiplies DB connections, which conflicts with OPS-412.
