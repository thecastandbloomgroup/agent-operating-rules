## Background

Checkout returns HTTP 500 for every user since 09:12. That is near total failure of a revenue path [judgment]. You are on call and have 10 minutes before an executive call. This is a Chaotic situation per Cynefin: act to stabilise before analysis [18].

## Relevance

Every minute of full checkout failure costs revenue and trust. Rollback of the last deploy restores service in minutes in most teams [judgment].

## Information

No telemetry is available in the request. The 100% failure rate and sharp onset at 09:12 point to a recent deploy, config change, or failed shared dependency such as the payment gateway or database [judgment]. A 100% blast radius argues for rollback over forward fixing, because a fix takes longer to find than a revert takes to run [judgment].

Assumption log:

- A1. A deploy or config change happened near 09:12. Why not measured: no tool access in this session. Validate by: check the deploy log, one command. If wrong: skip rollback, go to Step 3 probe.
- A2. A rollback mechanism exists and is fast, under 5 minutes. Why not measured: the material does not state it. Validate by: check the runbook or CI tool now. If wrong: replace Step 2 with feature flag disable or scaling.

Strongest alternative: forward fix the bug first. It loses because mean time to find root cause exceeds rollback time [judgment], and you can diagnose after the site is green.

## End

I recommend that we:

1. **Revert the latest deploy or config change now** (Chaotic: this acts to restore order before cause is known). Increment: run the standard rollback command. Blocker removed: the 500s themselves. Test (deterministic): Given the rollback completes, When a synthetic checkout request runs, Then it returns HTTP 200. Test (evaluative): rubric, no unverified cause stated, one owner named, one update time given; all pass or revise.
