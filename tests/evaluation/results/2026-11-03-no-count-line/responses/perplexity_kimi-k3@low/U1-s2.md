## Headline

Treat the flaky build as a measurement problem. Measure the rate, reproduce it under a budget, classify the cause, then fix and verify against a numeric threshold.

1. Measure first, because the failure rate and the failing step are unknown, and every later step depends on them.
2. Classify with a rubric, because flaky causes form a small known set, led by timing, concurrency, and order dependence [1].
3. Verify against a threshold, because one green run does not rule out an intermittent fault (step 5).

## Background

The build fails without a clear pattern. Flaky here means the same commit passes and fails with no code change. The request gives no logs, no system name, and no history, so this plan starts with evidence and stays correct for any single cause.

## Relevance

A flaky build trains the team to ignore red results, so real defects reach production [judgment]. The problem is common: Google reported in 2016 that about 16% of its tests showed some flakiness [2].

## Information

Evidence that drives the plan:

- A peer-reviewed study of flaky-test fixes ranks asynchronous waits, concurrency, and test-order dependence as the most common causes [1]. This sets the rubric classes in step 3.
- Google's report puts flakiness at about 16% of tests in a large industrial pipeline [2]. This supports a systematic fix.
- Arithmetic: with zero failures in N runs, the 95% upper bound on the true rate is about 3 divided by N [inference]. This sets the sample sizes in steps 2 and 5.

Assumption log:

A1. The continuous integration (CI) system keeps a history of at least 50 runs. Why not measured: the material does not state it. Validate by: open the CI dashboard. If wrong: step 1 uses 50 local runs instead.

A2. Flaky means intermittent; the same commit both passes and fails. Why not measured: the material does not state it. Validate by: re-run one failed commit once. If wrong: the failure is deterministic; replace steps 2 to 5 with standard debugging.

A3. At least one failing log is reachable today. Why not measured: the material does not state it. Validate by: open the latest failed run. If wrong: turn on verbose logs, then start step 1.

A4. The team can trigger CI runs on demand. Why not measured: the material does not state it. Validate by: trigger one manual run. If wrong: run steps 2 and 5 locally in the same container image.

Alternative considered: quarantine the flaky step or add automatic retries now. This loses because retries mask the cause, and quarantine deletes the failure signal that step 1 measures [judgment].

## End

I recommend that we run five steps in the order below. Step 2 runs in parallel with step 1. Each step names its Cynefin domain, that is, how predictable cause and effect are in that work.

1. **Measure the baseline.** Pull the last 50 CI runs. Compute the failure rate per pipeline step.
   - Increment: one script or spreadsheet, done in one session.
   - Blocker removed: there is no data on where or how often the build fails.
   - Kind: deterministic (same input, same output). Test first, in Given, When, Then form:
   - Given the CI history for the last 50 runs,
   - When the script labels each run as pass or fail per step,
   - Then each step shows a failure rate in percent and names the top failing step.
   - Cynefin: Clear, because one best practice exists for this check.
2. **Reproduce the failure, as a capped probe.** Trigger the same commit in a loop.
   - Increment: one repeat-run job, done in one session.
   - Blocker removed: there is no fresh failing log to analyze.
   - Kind: stochastic (output varies per run). Acceptance test first:
   - Metric: failures per run. Baseline: the rate from step 1.
   - Sample size and budget: 20 runs.
   - Pass: capture at least one failing log, or record 20 clean runs. Twenty clean runs bound the true rate under 15% [inference].
   - Stop condition: stop at 3 failures or 20 runs.
   - Cynefin: Complex, because cause and effect for an intermittent fault appear only afterward. Leverage is a guess here, so the probe stays capped.
3. **Classify the cause.** Score each distinct failing log against the rubric. Step 3 MUST NOT start until step 1 or step 2 yields at least one failing log.
   - Increment: one scored rubric per failure signature, done in one session.
   - Blocker removed: the cause has no name, so no fix can target it.
   - Kind: evaluative (the output is a judgment). Write the rubric first, then score.
   - Classes (MECE, that is, no overlap and full coverage): timing or race, order dependence, shared state, external service, resource limit, environment drift. The first three dominate in published data [1].
   - Criteria, weights, and required evidence [judgment]:
   - Log signature, 30%: quoted error lines.
   - Repetition pattern, 30%: the pass and fail matrix from step 2.
   - Environment correlation, 20%: agent and time metadata.
   - Sensitivity to the last change, 20%: the result with the suspect change reverted.
   - Pass threshold: one class reaches 70% of weighted points. On a tie, collect 10 more runs and score again.
   - Cynefin: Complicated, because analysis of the evidence selects the cause. Leverage is reliable once the rubric scores.
4. **Fix the named cause.** Apply the standard fix for the winning class. Examples: replace fixed sleeps with condition waits, isolate shared fixtures, stub network calls. Step 4 MUST NOT start until step 3 passes its threshold.
   - Increment: one change plus one regression test, done in one session. Write the test first, watch it fail, then change the code.
   - Blocker removed: the defect itself.
   - Kind: deterministic. Test first:
   - Given the code path that step 3 named,
   - When the change replaces the unsafe pattern,
   - Then the new regression test passes, and the old error signature no longer appears in a forced run of that path.
   - Cynefin: Complicated, because the rubric in step 3 picks the right practice.
5. **Verify the fix.** Re-run the full pipeline N times. Step 5 MUST NOT start until step 4 merges.
   - Increment: one batch of N runs plus a one-line report.
   - Blocker removed: there is no proof the fix worked.
   - Kind: stochastic. Acceptance test first:
   - Metric: failed runs out of N. Baseline: the rate p from step 1.
   - Sample size: N = ceil(ln(0.05) / ln(1 - p)). Examples: 29 runs at p = 10%, 14 runs at p = 20% [inference].
   - Pass threshold: 0 failures in N runs. On any failure, return to step 3 with the new log.
   - Cynefin: Clear, because a fixed threshold check is a known procedure.

## Follow-up

Conditions that change the plan:

- If the same commit fails every time (A2 false), stop this plan. Use standard debugging for a deterministic failure.
- If step 1 shows a rate under 2%, extend step 5 to one week of scheduled runs instead of one batch.

Open questions (the plan already assumes the answers in A1 to A4):

1. Which CI system runs the build? The answer sets the script syntax for step 1.
2. When did the flakiness start, and what merged just before? The answer shortens step 3.
