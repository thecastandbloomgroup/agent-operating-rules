# Headline

The latency regression comes from the new database pool config, which cuts pool size from 50 to 8 while the service runs 32 workers. Restore the pool size and acquire timeout. Keep the ORM change, because it reduced query time. Consider restoring the cache time to live (TTL) of 300 seconds, because the lower TTL raised the cache miss rate and adds pressure to the pool.

# Background

Last week's release 2026.10.21 changed three things: the ORM query, the cache TTL, and the pool config. After the deploy, p95 latency rose from 120 ms to 900 ms and the error rate rose from 0.02% to 0.40% (traces.txt, Window A versus Window B).

# Relevance

Each request holds a pool connection from acquire to response. With 8 connections for 32 workers, requests queue and then fail after the 5 second acquire timeout. Traffic did not rise, so demand is not the cause.

# Information

**Evidence.**

1. The diff set `pool.max_size: 8` (was 50) and `acquire_timeout_s: 5` (was 30) (release.diff, config/db.yaml).
2. The `db.pool.acquire` span rose from p95 3 ms to 690 ms. Query spans stayed near baseline, so the database is not slow (traces.txt, span table).
3. Active database connections from this service peaked at 8 in Window B, versus 31 in Window A. DB CPU stayed at 38 to 41% peak. So the server has spare capacity and OPS-412's stated limit does not appear to bind at 31 connections (traces.txt) [inference].
4. Logs show 1,800 to 2,400 "pool exhausted" warnings per hour and repeated PoolTimeout errors after 5 seconds. Zero such warnings occurred on 2026-10-20 (logs.txt).
5. The cache miss rate rose from 12% to 31% because the diff cut TTL from 300 to 60 seconds (release.diff, config/cache.yaml; traces.txt). This raises the rate of connections requested, a secondary pressure.
6. The ORM change to `selectinload(Order.lines)` kept query times at or below baseline (18/52 ms for orders; 9/26 ms p50/p95 for lines). It is not the cause [judgment].

**Alternative considered.** Restore only the cache TTL. It reduces connection demand, but acquire p95 of 690 ms and 14 waiters at 8 connections show the pool itself is undersized. The pool fix wins.

**Assumption log.**

Validate by: query `SHOW max_connections;` and the connection count per service on orders-db.internal. If wrong: set pool size to the highest value the server budget allows (for example 32, one per worker) instead of 50.
