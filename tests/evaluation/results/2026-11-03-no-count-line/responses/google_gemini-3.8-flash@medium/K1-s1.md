### Headline

Restore the cache expiration time and raise the database connection pool size to eliminate queue delays.
Database connection acquire latency accounts for 687 ms of the 780 ms latency increase [3].
A reduced cache expiration time increased database query volume by 158 percent [3].
The reduced pool size caused connection starvation across all application worker threads [1], [2].

### Background

Release 2026.10.21 changed the database pool size, the cache expiration time, and the object-relational mapping query [2].
Following that release, 95th percentile request latency increased from 120 ms to 900 ms [3].
In the same period, database pool timeout errors rose to 0.38 percent of all requests [3].

### Relevance

Users currently experience slow responses and service errors on customer order endpoints [1], [3].
Fixing connection starvation restores normal latency and prevents request failures.

### Information

Traces show that 95th percentile database connection acquire latency rose from 3 ms to 690 ms [3].
This acquire delay explains 88 percent of the total 780 ms latency increase [3].
The query execution times changed by less than 6 ms across both queries [3].
Therefore, query execution time did not cause the latency increase [judgment].

The latency increase stems from two interacting changes in release 2026.10.21 [2].
First, cache default expiration dropped from 300 s to 60 s [2].
Because the cache expires faster, the cache miss rate rose from 12 percent to 31 percent [3].
This higher miss rate increased database traffic by 158 percent [3].
Second, the database pool maximum size per pod dropped from 50 to 8 [2].
Each of the 4 pods runs 8 worker threads [2].
When all 8 connections are busy, incoming worker requests must wait [1].
The logs record 1,800 to 2,400 pool exhaustion events per hour in release 2026.10.21, compared to zero before [1].
Furthermore, acquire timeout dropped from 30 s to 5 s [2].
Because threads wait longer than 5 s during traffic spikes, requests fail with status 503 [1].

The alternative considered was rolling back the entire release, including the object-relational mapping change.

Therefore, a full rollback removes a beneficial query optimization [judgment].
