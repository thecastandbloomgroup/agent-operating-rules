# Headline

Roll back the pool config: the release cut pool size from 50 to 8 and the timeout from 30 s to 5 s, so workers wait for connections, not for the database. Three points:
1. Pool acquire took 690 ms of the 900 ms total p95 in window B, up from 3 ms in window A [2].
2. The database is healthy: CPU stayed near 41% peak, so lower pool limits made things worse, not better [2].
3. The cache TTL cut from 300 s to 60 s raised the miss rate from 12% to 31%, which added load to the small pool [2].

# Background

The API p95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release changed the pool config, the cache TTL, and the ORM query. Logs, traces, and the diff are attached.

# Relevance

Error rate rose to 0.40%, and 96% of errors are pool timeouts, so customers now see 503 responses, not only slow ones [2]. This is an availability issue, not only a speed issue.

# Information

The evidence splits the three changes into separate effects (MECE):

**Pool config is the main driver.** `db.pool.acquire` p95 rose from 3 ms to 690 ms, while `db.query` spans stayed flat at 52 to 58 ms [2]. Logs show 1,800 to 2,400 "pool exhausted" warnings per hour, up from zero, plus 5 s timeout errors [1]. Peak active connections fell from 31 to 8 while database CPU stayed at 38% to 41%, so the old headroom was safe [2]. Seven of eight workers on each pod therefore wait for one connection at peak, because 32 workers in total share pools capped at 8 per pod [3].

**Cache TTL adds DB load but is not the driver.** The miss rate rose from 12% to 31%, and `cache.get` latency is flat at 2 to 5 ms [2]. More misses mean more queries, so this magnifies pool pressure.

**The ORM change is not the driver.** The `selectinload` option adds a second query, but `db.query order_lines` p95 fell from 30 ms to 26 ms, and it stays inside one session [2]. No evidence supports reverting it.

Assumption log:

- A1. The OPS-412 per service connection limit allows at least 24 per pod. Why not measured: the ticket is not attached. Validate by: read the ticket and the database `max_connections` setting. If wrong: set the pool to the allowed total split across 4 pods.
- A2. `pool.max_size` applies per pod, not per service. Why not measured: the diff and driver docs are not attached. Validate by: check the client library docs or count connections from one pod. If wrong: the true per service cap is 8, so the fix needs a proxy or a shared pool.

Alternative considered: reverting the ORM `selectinload` change. It loses because the query spans measured flat across both windows [2].
