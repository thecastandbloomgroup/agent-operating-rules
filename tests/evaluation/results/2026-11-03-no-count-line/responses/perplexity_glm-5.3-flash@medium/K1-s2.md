## Headline

The p95 rise comes from the connection pool change, not the ORM: revert the cache TTL, restore pool headroom within the new database limit, and confirm with a load test.

- The p95 for `db.pool.acquire` went from 3 ms to 690 ms, while the p95 for the database queries moved by 6 ms or less [3 traces].
- Pool exhaustion went from 0 warnings per hour to 1,800 to 2,400, right after `max_size` dropped from 50 to 8 per pod [1 logs] [2 diff].
- The cache TTL change from 300 s to 60 s raised the miss rate from 12% to 31%, which adds database load [3 traces] [2 diff].
- The new `selectinload` line is not the driver: the `order_lines` query p95 dropped from 30 ms to 26 ms [3 traces].

## Background

The API p95 latency rose from 120 ms to 900 ms after release 2026.10.21. The release touched the connection pool, the cache TTL, and the ORM query for orders. Logs, traces, and the diff are attached [1] [2] [3].

## Relevance

The 503 errors are live: 96% of the current errors are `PoolTimeout`, so customers fail at 0.40% of requests [3]. The fix is config-only and can land today.

## Information

**Evidence.** The traces break the p50 request into spans [3]:

| Span | A p50 ms | B p50 ms | Change |
|---|---|---|---|
| `db.pool.acquire` | 1 | 140 | +139 |
| `db.query orders` | 18 | 20 | +2 |
| `db.query order_lines` | 11 | 9 | -2 |
| `cache.get` | 2 | 2 | 0 |
| `serialize` | 6 | 6 | 0 |
| http.request (total) | 48 | 210 | +162 |

Queue time, not query time, is the added cost. Each pod has 8 worker threads [2]. At a peak of 405 requests per second over 4 pods, each pod serves about 101 requests per second. The p50 request holds a connection for about 70 ms after it acquires one (210 ms total minus 140 ms of waiting). Demand is therefore about 7.1 concurrent holds against 8 connections, or 89% used [judgment from 3]. Queueing delay grows steeply near full use, and the p95 acquire span of 690 ms matches that [judgment]. The database itself has room: CPU sat at 41% at peak, versus 38% before [3].

Two themes come from the qualitative review:

- Pool saturation from the smaller pool. Supported by 2 sources (logs, traces) [1] [3]. No source disagrees.
- More database work from the shorter cache TTL (miss rate 31% versus 12%). Supported by 2 sources (traces, diff) [2] [3]. This is the smaller factor, because query spans stayed flat; it drives p50, not p95.

Confidence in the diagnosis: high confidence, three independent sources agree (logs, diff, traces).

**Assumption log.**

`A1. The database limit behind ticket OPS-412 allows about 32 connections for this service, so a pool of 50 per pod would exceed it. Why not measured: the ticket is not attached and the material does not state the limit. Validate by: read OPS-412 and the database max_connections setting. If wrong: set max_size directly to 16 per pod and skip the budget analysis.`

`A2. A request holds its connection for the whole post-acquire part of the request. Why not measured: the traces show spans, not connection hold intervals. Validate by: query the pool's in-use and waiting metrics, or add a hold-time span. If wrong: the pool size is still the binding constraint, so the same fix applies, and the TTL revert gains more weight.`

**Alternative considered.** Revert `db.yaml` fully to `max_size: 50` and `acquire_timeout_s: 30`. It loses because the commit records a deliberate limit reduction to match ticket OPS-412 [2], so 50 per pod (200 total over 4 pods) may exceed the database budget [inference]. Another alternative, blaming `selectinload`, loses because both query spans stayed flat or improved [3].

## End

I recommend that we:

1. **Compute the connection budget (Complicated, because limits from two sources need analysis before a value is picked).** Increment: read ticket OPS-412 and the database `max_connections`, and write one table that lists the budget and the per-pod share. Blocker removed: it decides a safe `max_size`. Test, written before the work:
   ```gherkin
   Given OPS-412 and the database max_connections
   When the budget is computed
   Then the chosen max_size times 4 pods is at or below the budget minus 20% headroom
   ```
2. **Apply the pool config (Clear, because step 1 sets the values and this is one config edit).** Step 2 MUST NOT start until step 1 is done. Increment: set `max_size` per the budget (16 per pod is the first candidate) and set `acquire_timeout_s` back to 30. Blocker removed: it clears the acquire queue and the 503 `PoolTimeout` errors. Test:
   ```gherkin
   Given traffic at 405 requests per second
   When requests acquire pool connections
   Then the p95 acquire span is under 10 ms
   ```
3. **Revert the cache TTL (Clear, because one value returns to a known-good setting).** Increment: set `default_ttl_s` back to 300. Blocker removed: it cuts the miss rate toward 12%, which lowers the p50 and the database load. Test:
   ```gherkin
   Given a warm cache
   When 10,000 requests run
   Then the miss rate is under 15% and the p50 total is under 60 ms
   ```
4. **Load test before full rollout (Complex, because load behavior emerges; this is a capped probe with a measure and a stop condition).** Increment: run a canary or a stage test at 410 requests per second for 30 minutes. Blocker removed: it confirms the fix against the pre-release baseline. Acceptance: p95 at or under 150 ms and error rate at or under 0.05%, over at least 10,000 sampled requests. Budget and stop condition: 2 hours total; revert the pool change if p95 goes over 300 ms after 1 hour.

## Follow-up

Condition that changes the recommendation: if A1 is false and the database budget allows more, raise `max_size` to 16 per pod in step 2 without further analysis. If A2 is false, keep step 4 but add a hold-time span first, because shortening the hold is then the larger lever.
