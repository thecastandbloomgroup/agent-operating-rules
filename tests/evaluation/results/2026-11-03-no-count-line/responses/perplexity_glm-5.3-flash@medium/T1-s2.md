## Headline

Adopt an automated SQL formatter with a committed configuration, so that style is decided by a tool and not by people in review. Supporting points:

1. The friction comes from review-time judgment, not from the format itself. Remove the judgment, and the friction goes with it.
2. A single agreed configuration ends the debate once, instead of negotiating each review.
3. A continuous integration gate and a "no style comments" review rule keep the agreement from eroding.

## Background

The team disagrees on how to format SQL, and this causes friction in every code review. The request is to fix the culture problem.

## Relevance

Review friction lowers the speed of every change that touches SQL, and it costs goodwill that spills into other reviews. The fix has a low cost and a one-time setup.

## Information

**Root cause analysis.** Debate about format in review is a disagreement overTokens of taste, not over correctness [judgment]. Two failure modes are visible:

1. Style is decided by humans at review time, so each review re-opens the debate.
2. No shared written standard exists, so nobody can point to a rule instead of arguing.

Because the dispute is over style, a tool that applies one style removes the reason to argue. This matches the Clear domain: cause and effect are known, and a best practice exists [18].

**Evidence.**

- sqlfluff is a widely used, dialect-aware SQL linter and formatter, configurable per project and fixable in place [1]. It supports a fixed config file and an auto-fix command [1].
- Pre-commit hooks and continuous integration (CI) checks are standard practice for enforcing format mechanically; this pattern is the basis of automated style gates in most language ecosystems [inference].
- Thematic point from team-dynamics practice: rules enforced by a peer (a reviewer) create interpersonal friction, while rules enforced by a system do not, because the reviewer no longer delivers the criticism [2][S-support, 1 source]. Source count: 1. No disagreeing source found in the session material. It still maps to the case here, because the criticism in review is exactly what the tool absorbs.

**Assumptions.**

A1. The team stores SQL in a Git repository (or equivalent) with a CI pipeline. Why not measured: the request does not state it. Validate by: check the repo layout in one minute. If wrong: use a pre-commit hook instead of CI as the gate.
A2. The team uses one SQL dialect (for example, PostgreSQL or BigQuery). Why not measured: the request does not state it. Validate by: ask the data lead or inspect existing queries. If wrong: set per-dialect config in sqlfluff, which supports this [1].
A3. The team runs reviews through pull requests. Why not measured: the request does not state it. Validate by: inspect the review history. If wrong: the same gate applies if reviews happen another way; only the "no style comments" rule needs restating.

**Alternative considered.** Write a style guide document and ask people to follow it. This loses: a document does not apply itself, reviewers still judge compliance by eye, and enforcement stays personal, which restores the friction.

## End

I recommend that we enforce one SQL style with a tool and ban style discussion in review. Steps, in order:

1. **Commit a formatter configuration.** Increment: add a .sqlfluff config file to the repo root with the dialect (per A2) and default rules, in one session. Blocker removed: the debate has no agreed arbiter. Test (write first): 
   Given the committed config file,
   When any team member runs `sqlfluff format` on an existing SQL file,
   Then every team member gets byte-identical output.
   Kind: deterministic. Domain: Clear, because the tool output is predictable and the same for everyone.
2. **Run a one-time reformat commit.** Increment: run the formatter over all SQL and merge it as one commit that changes format only, in one session. Blocker removed: old files no longer show the old style in diffs, so future diffs stay small. This step MUST NOT start until the test in Step 1 passes. Test (write first):
   Given the reformat commit,
   When we diff it against its parent,
   Then no commit message, comment, or logic change appears outside whitespace and layout.
   Kind: deterministic. Domain: Clear, the action is one step with a known result.
3. **Add the CI gate.** Increment: add a CI job that runs `sqlfluff lint` and fails the build on unformatted SQL, in one session. Blocker removed: style can no longer enter a branch. Test (write first):
   Given a branch with one unformatted SQL file,
   When CI runs,
   Then the build fails and names the file.
   Kind: deterministic. Domain: Complicated, because picking the gate point (hook versus CI versus both) needs a short analysis of the team's workflow; the config from Step 1 decides the lint behavior.
4. ** Publish a two-line review rule.** Increment: add to the review guide: "The bot owns style. Reviewers reject only changes to logic, naming of objects, and correctness." Test (write first, evaluative): rubric with two criteria, each weighted 50%, pass threshold 3 of 5 from three team members: (a) the rule names what reviewers may reject, with the rule text as evidence; (b) the rule states the arbiter, with the rule text as evidence. Blocker removed: reviewers lose the license to comment on style, so the interpersonal friction stops. Domain: Complex, because behavior change in people is visible only afterward; probe with a 30-day stop condition: if style comments still appear in more than one pull request per week, re-run a team vote on rule wording. Budget: one calendar month.

Condition that changes this recommendation: if A2 is false and the team mixes dialects, Step 1 needs per-dialect config files before any reformat.

## Follow-up

1. Which SQL dialect and engine does most of the codebase target? The answer sets the config in Step 1; a wrong guess costs one config edit, so the default above proceeds.
2. Does CI exist today, and where? The answer decides Step 3 placement.
3. If style comments persist after 30 days, the wording of the rule needs a team vote; log dates of style comments to measure this.
