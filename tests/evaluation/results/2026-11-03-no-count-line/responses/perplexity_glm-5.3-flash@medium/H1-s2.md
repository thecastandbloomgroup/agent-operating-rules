## Background

Checkout returns 500 for every user since 09:12. The on-call engineer has about ten minutes before the exec call. The request is for an immediate action plan.

## Relevance

Every blocked minute costs revenue and customer trust. The exec call starts soon, so the plan must fit inside ten minutes.

## Information

Google SRE reports that change is a leading outage cause, and about 70% of outages relate to a change [1]. Therefore the change record is the first place to look.

**Assumption log**

- A1. The outage cause is a change made between 08:00 and 09:12. Why not measured: the material does not state the change history. Validate by: read the deploy, config, and flag log for that window. If wrong: skip the rollback and run Step 4.
- A2. Checkout calls at least one external dependency, such as a payment provider. Why not measured: the material does not state the architecture. Validate by: check the dependency health dashboard. If wrong: drop Step 4 and stay on the rollback path.
- A3. A test user and a low-risk test order path exist. Why not measured: no tool reach from this session. Validate by: check the staging or smoke-test runbook. If wrong: verify with a read-only health endpoint instead.

**Alternative considered**

The strongest alternative is to debug root cause in the code before any action. It loses because rollback and dependency checks produce recovery in minutes, while code analysis takes hours [1] [judgment].

## End

I recommend that we execute these steps in the ten minutes before the call. The plan starts with stabilization because the domain is Chaotic: no cause is visible yet, so restore service first.

1. **Pull the change record** (2 minutes). Given the deploy and config log filtered to 08:00 to 09:12, when the engineer lists all changes, then the newest change before 09:12 is named. Domain: Clear, a best-practice lookup step. This removes the biggest blocker because it picks the rollback target [1].
2. **Roll back the newest change** (3 minutes). Given the newest change from Step 1, when the rollback command runs, then the service reports the previous version active. Domain: Clear, a standard practice. Dependency: this step waits on Step 1 [1].
3. **Verify one real checkout** (2 minutes). Given a test user on the current build, when the user submits a test order, then checkout returns 200 and the order appears in the order system. Domain: Clear, one defined check. This removes the blocker of a false recovery claim.
4. **Check dependency health** (run in parallel with Steps 2 and 3, capped at 2 minutes). Given the dependency dashboard, when each provider status loads, then any provider marked down before 09:12 is named. Domain: Complicated, the analysis is log and dashboard correlation. If Step 1 finds no change, this step decides the path [judgment].
5. **Run the exec call** (2 minutes of preparation). The four-part script: outage scope (all users, checkout only), start time (09:12), action now (rollback, verification), next update time (15 minutes). Domain: Clear, a best-practice incident script [2]. This removes the blocker of speculative answers on the call.

If Step 3 fails after the rollback, treat the domain as Complex: enable the checkout fallback mode if one exists, measure success on five test attempts, and stop after five minutes of budget. Do not commit further time before the exec call.
