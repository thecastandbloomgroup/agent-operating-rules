## Headline

1. The regression comes from the pool fix in this release: `db.yaml` lowered `max_size` from 50 to 8, while the API runs 32 worker threads, so most workers wait for a connection.
2. The 5 s `acquire_timeout` turns the waits into errors.
3. The slower cache TTL (300 s to 60 s) adds load, but traces show cache misses cost little, so it is a secondary cause.
4. The ORM change (`selectinload`) is not the cause: query spans stayed flat.

## Background

The request describes a p95 jump from 120 ms to 900 ms after release 2026.10.21 [judgment: from the query]. That release changed the pool config, the cache config, and the ORM. Logs, traces, and the diff are attached for analysis.

## Relevance

Error rate rose 20 times, from 0.02% to 0.40%, and 96% of errors are pool timeouts [traces.txt]. Customers now see 503 responses, so a config revert is urgent.

## Information

**Evidence:**

1. Pool exhaust warnings: 0 per hour on Oct 20, 1800 to 2400 per hour on Oct 22 [logs.txt]. This is a new behavior, so the cause is inside this release window.
2. The release set `max_size: 8` and `acquire_timeout_s: 5` [release.diff, config/db.yaml]. Because the service runs 32 workers, 8 connections serve 4 threads of demand at peak, so workers queue.
3. The wait is in `db.pool.acquire`: p95 3 ms before, 690 ms after [traces.txt]. It explains about 75% of the 780 ms p95 increase [inference: 690 ms of 780 ms in the same trace table].
4. Database health is good: peak CPU 38% to 41%, and `db.query` spans changed little (18 to 20 ms p50) [traces.txt]. The database is not the bottleneck. So the queue forms from client-side starvation, per item 3.
5. Cache TTL dropped from 300 s to 60 s [release.diff]. Miss rate rose from 12% to 31% [traces.txt]. Therefore each miss adds one extra query of about 55 ms average [traces.txt: order + lines spans]. This is a modest contributor.

**Assumptions:**

A1. The per-service DB connection limit in OPS-412 is 40 or higher. Why not measured: the ticket is not in the material. Validate by: read OPS-412 or the DB server config. If wrong: set `max_size` to that limit minus headroom, everything else holds.

**Assumption validation note:** the old setting `max_size: 50` ran without connection-limit errors [release.diff, traces window A]. This supports A1 at high confidence, because window A used up to 31 connections [traces.txt].

**Alternative considered:** scale the database instead of the pool. It loses: DB CPU is 41% at peak and query spans are flat, per item 4. The bottleneck sits between the workers and the DB, not at the DB.
