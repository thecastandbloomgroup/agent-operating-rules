## Headline

Build the measurement first, then tune the summariser against a measured baseline. The plan has four parts:
- Label a sample of summaries to classify the error types.
- Score a fixed eval set to record the baseline.
- Capture agent flags in the tool so the signal keeps growing.
- Tune the prompt or model as capped probes that must beat the baseline.

## Background

An LLM-based summariser sits in the support tool. Agents say its output is "sometimes wrong". The team has no metrics and has asked to make it better.

## Relevance

Without a baseline, a change to the prompt or model cannot be verified. Because the error type is unknown, the team also risks fixing the wrong problem first.

## Information

**Evidence**

- Agents report that summaries are sometimes wrong (user conversation, one source). Theme: "errors exist, error type unknown". Count of supporting sources: 1. No disagreeing source in the material.
- Numbers: zero metrics tracked, zero labeled samples [inference].
- Confidence in the failure mix is low; basis: one qualitative source and no measurements. The labeling step will raise it.

**Assumption log**

- A1. "Wrong" means factual errors or missing facts in the ticket summaries. Why not measured: the user has not answered. Validate by: the labeling step below. If wrong: replace the error taxonomy in Step 1 and rerun.
- A2. Ticket text and generated summaries can be exported for review. Why not measured: the material does not state it. Validate by: check the tool export or ask the tool admin. If wrong: Step 1 runs inside the tool on live tickets, at half the sample size.
- A3. Agents can name examples of summaries they disliked. Why not measured: the user has not answered. Validate by: ask two agents to point at examples in history. If wrong: Step 1 samples random summaries instead of flagged ones.

**Alternative considered**

Fine-tune or swap the model now. It loses because, without a baseline, a gain of unknown size cannot be shown, and a fix for the wrong problem cannot be ruled out [judgment].

## End

I recommend that we complete the four steps below, in this order.

1. **Classify the failure modes.** (Confused, evaluative [18].) Increment: label 30 agent-flagged summaries and 30 unflagged ones with error categories, in one session. Blocker removed: the unknown error type. Rubric first: criteria = the category list; weights = equal; pass = 80% agreement between two raters; evidence = rater marks per summary. Categories: wrong fact, missing fact, wrong tone, stale data, other [5]. Domain is Confused, because the failure mode is unknown and its output decides the next steps.

2. **Record the baseline.** (Complicated, evaluative.) Increment: select 50 summaries with their ticket text as a fixed eval set, score them, and record the mean per category, in one session. Rubric first: criteria = faithfulness (weight 50%), completeness (30%), readability (20%); scale 1 to 5; pass = mean of 4 or higher; evidence = scores from two raters, with a third rater for disagreements; layout per Kepner-Tregoe [15]. Blocker removed: there is no way to tell better from worse. Domain is Complicated, because expert analysis of the scores picks the practice to change. This step has the highest leverage, since it unblocks every tuning decision.

3. **Capture agent feedback.** (Clear, deterministic.) Increment: add a thumbs-down button and a reason list to the summary card, in one session. Reason list: wrong fact, missing fact, other. Blocker removed: agent reports stay anecdotal and fade from memory. Test, written first [14]:
   ```
   Given a summary is shown to an agent
   When the agent selects "thumbs down" and picks a reason
   Then the tool stores the ticket ID, the summary ID, the reason, and a timestamp
   ```
   Domain is Clear, because a known best practice applies: log the complaint where it happens.

4. **Tune against the baseline.** (Complex, stochastic.) Increment: one prompt change per trial, capped at 3 trials or one engineer week, whichever comes first. Acceptance test, written first: metric = error count on the eval set; baseline = the Step 2 result; pass = error count drops by 40% or more at n = 50 rated summaries; stop condition = two failed trials. Blocker removed: unmeasured prompt edits. Domain is Complex, because the effect of a prompt change shows only in the result, so each trial is a probe with a budget, not a commitment. Leverage is a guess until the first trial runs. Step 4 MUST NOT start until Step 2 records the baseline.

Steps 3 and 4 do not depend on each other, so the team can run them in parallel once Steps 1 and 2 are done.

## Follow-up

- If Step 1 shows invented ticket details as the top category, make the first probe a grounding instruction that quotes ticket lines, before any model change.
- If A2 is false, Step 1 needs 10 working days to collect summaries first, so the plan slips by about a week [judgment].
