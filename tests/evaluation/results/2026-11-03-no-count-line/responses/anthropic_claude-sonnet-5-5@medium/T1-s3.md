## Headline

Replace the style argument with one decision, one formatter, and one automated check, so reviews stop carrying the debate.

- The friction exists because no rule settles style and people enforce taste by hand.
- A tool that formats code removes the need for a human opinion in review.
- A time-boxed team decision gives the rule legitimacy, so the culture follows the tool.
- A measured baseline shows whether the friction actually falls.

## Background

The team has no shared SQL format. Each review repeats the same style debate. The request is to fix this as a culture problem.

## Relevance

Every review that debates style delays merges and wears down trust. The cost repeats with each pull request (a proposed code change that peers review).

## Information

**Evidence**

- Formatters such as SQLFluff lint and fix SQL against a configured rule set [3]. This is the basis for automating the rule.
- The decision step is a Complicated problem: experts can compare the options by analysis [1].
- Style comments take reviewer time and add no defect findings. [judgment]
- An automated check is likely (66 to 100%) to remove most format comments. Confidence is medium. The basis is general practice, with no data from this team. [inference]

**Assumption log**

A1. The team reviews SQL in pull requests and has a CI (automated build) pipeline. Why not measured: the material does not state it. Validate by: ask one teammate. If wrong: Step 3 changes to a pre-commit hook.

A2. The team uses one SQL dialect. Why not measured: the material does not state it. Validate by: check the repository for dialect settings. If wrong: Step 1 must score dialect support per dialect.

A3. The team has about 10 people or fewer. Why not measured: the material does not state it. Validate by: count the review participants. If wrong: Step 1 needs a named decision owner.

**Alternative considered**

The strongest alternative is a written style guide with no tool. It loses because people must enforce it by hand, so the same review friction stays. [judgment]

## End

I recommend that we take these five actions in order. Step 5 runs in parallel with the others.

1. **Decide the style rule in one 45-minute session.** (Evaluative. Complicated: analysis can pick among known good practices [1].)
   - Blocker removed: no agreed rule exists.
   - Increment: score two or three formatter options and pick one. The team accepts the winner, and the decision owner breaks any tie.
   - Rubric (pass threshold 70 of 100):
     - Diff readability, weight 30, evidence: the same three real queries formatted by each option.
     - CI enforcement support, weight 30, evidence: tool documentation [3].
     - Dialect support, weight 20, evidence: the tool's dialect list.
     - Size of the one-time change, weight 20, evidence: count of lines changed in a trial run.

2. **Apply the chosen formatter to the whole repository in one commit.** (Deterministic. Clear: a known best practice applies.)
   - Step 2 MUST NOT start until Step 1 passes its threshold.
   - Blocker removed: old files keep the old styles.
   - Test, written first [2]:

     Given the formatter configuration is committed
     When the formatter runs over all SQL files
     Then a second run changes zero files

3. **Add a CI check that fails on unformatted SQL.** (Deterministic. Clear: the check is a standard feature.)
   - Step 3 MUST NOT start until the test in Step 2 passes.
   - Blocker removed: nothing enforces the rule.
   - Test, written first [2]:

     Given a pull request with one badly formatted SQL file
     When the CI pipeline runs
     Then the style check fails and names that file

4. **Add one line to the review guide: reviewers do not comment on format that the tool accepts.** (Deterministic. Clear: the acceptance criterion is fixed.)
   - Blocker removed: reviewers still argue style by habit.
   - Test, written first [2]:

     Given the review guide is merged
     When a reviewer opens the guide
     Then the guide contains the rule and links to the formatter configuration

5. **Run a two-week probe on style comments.** (Stochastic. Complex: team behavior shows its effect only afterward [1]. Leverage is a guess.)
   - Blocker removed: no one knows if the friction fell.
   - Start now with a baseline: count format comments in the last 20 pull requests. Budget: 30 minutes.
   - Metric: share of review comments about format.
   - Pass threshold: at least an 80% drop from the baseline, over 20 new pull requests.
   - Stop condition: if the share rises after week one, hold a 30-minute retro and re-open Step 1.

If A1 is false, replace Step 3 with a pre-commit hook and keep the same test.
