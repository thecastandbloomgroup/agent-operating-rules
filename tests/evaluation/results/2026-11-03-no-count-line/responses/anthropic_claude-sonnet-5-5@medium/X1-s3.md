## Headline

Measure the summariser's errors first, then change the prompt and keep the change only if the measured error rate falls.

- No metrics exist today, so no change can be proved to help.
- Agents need a cheap way to report wrong summaries, so data starts to flow.
- A fixed test set (the "golden set") lets the team compare each change with the baseline.
- Prompt changes are the cheapest fix to try first, but their effect is unknown until tested.

## Background

The support tool uses an LLM (large language model, a program that writes text) to summarise tickets. A ticket is one customer support case. Agents report that summaries are "sometimes wrong". The team has no metrics, and the request is to improve quality.

## Relevance

An agent who trusts a wrong summary may give a wrong answer to a customer. An agent who stops trusting the tool loses the time the tool should save.

## Information

**Evidence**

- The team has no error rate, no logs of flagged summaries, and no baseline (per the user's message). [judgment: the baseline is unknown, not zero]
- LLM summaries can contain invented or unsupported statements. A survey covers this failure mode (see the next line).
- Ji et al. describe it as hallucination in text generation [1].
- The cause is about as likely as not to be the prompt, rather than the ticket text or the model. Basis: low confidence, no data. [judgment]
- It is likely (66 to 100%) that the errors fall into a few types, such as omitted facts and invented facts. [judgment]

**Assumption log**

A1. The tool stores each summary and its source ticket. Why not measured: the material does not state it. Validate by: ask an engineer to query ten records. If wrong: add logging to Step 2 before Step 1 starts.

A2. "Wrong" means factual errors or missing facts, not style. Why not measured: the user has not answered. Validate by: Step 1 labels. If wrong: add a style criterion to the rubric.

A3. The team can edit the prompt and the model settings. Why not measured: the material does not state it. Validate by: change a test prompt in a staging copy. If wrong: replace Step 4 with a vendor request.

A4. The team can get 100 past tickets and two agent reviewers for one session each. Why not measured: the material does not state it. Validate by: ask the support lead. If wrong: reduce the sample sizes and lower the confidence level.

**Alternative considered**

Switch to a larger model at once. It loses because cost and gain are unknown, and without a baseline the team cannot prove the switch helped. [judgment]

## End

I recommend that we:

1. **Label 50 recent summaries (evaluative; Cynefin: Confused).** The domain is Confused because the error types are unknown.
   - Blocker removed: nobody knows what "sometimes wrong" means.
   - Increment: two agents each score the same 50 summaries in one session. They tag every error by type.
   - Test (rubric, ISO/IEC 25010 criteria [2]), written before the work:
     - Functional correctness, weight 50%. Evidence: each stated fact appears in the ticket.
     - Functional completeness, weight 30%. Evidence: each key fact in the ticket appears in the summary.
     - Functional appropriateness, weight 20%. Evidence: an agent can act on the summary without reading the ticket.
     - Pass threshold for a summary: 80 of 100 points. The step passes when both reviewers finish all 50 summaries and the error types are counted.
   - Output: the baseline error rate and an error type list.

2. **Add a "Wrong" button with a reason list (deterministic; Cynefin: Clear).** The domain is Clear because logging a click is a known practice. Step 2 MAY run in parallel with Step 1.
   - Blocker removed: no ongoing data.
   - Increment: one button, one reason list, one log table.
   - Test, written before the work [3]:
     ```gherkin
     Given an agent views a summary of ticket 123
     When the agent clicks "Wrong" and selects the reason "invented fact"
     Then the log stores the ticket ID, the summary text, the model version, the reason, and the time
     ```

3. **Build the golden set and a scoring script (deterministic; Cynefin: Complicated).** The domain is Complicated because an expert can choose the ticket mix by analysis of the Step 1 error types. Step 3 MUST NOT start until Step 1 passes.
   - Blocker removed: no fixed way to compare changes.
   - Increment: 100 tickets, each with a list of key facts written by an agent, and a script that scores a summary against the list.
   - Test, written before the work:
     ```gherkin
     Given a golden set of 100 tickets with agent-written key facts
     When the script scores the current summaries
     Then it outputs the share of summaries with an invented fact and the share with a missing key fact
     And the invented-fact share is within 10 points of the Step 1 baseline
     ```

4. **Run a prompt probe (stochastic; Cynefin: Complex).** The domain is Complex because the effect of a prompt change shows only after a run [4]. Leverage is a guess. Step 4 MUST NOT start until the test in Step 3 passes.
   - Blocker removed: unknown effect of prompt changes.
   - Increment: up to three prompt variants. For example, require every fact to come from the ticket, and allow "not stated" for gaps.
   - Budget: two working days. Stop condition: stop when three variants fail the test below.
   - Test, written before the work:
     - Metric: share of golden-set summaries with at least one invented fact.
     - Baseline: the Step 3 result.
     - Pass threshold: a relative fall of at least 30% [judgment], with no fall in the missing-fact score.
     - Sample size: 100 tickets, three runs each.
   - Accept a variant only when it meets the threshold at that sample size.
   - If all variants fail, replace the probe with a model change test on the same golden set.
