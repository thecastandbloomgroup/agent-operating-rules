## Background

The team has no agreed format for SQL (Structured Query Language). Every code review includes style arguments. The request is to fix this as a culture problem.

## Relevance

Each review that debates style delays the merge and wears down trust. The cost repeats with every pull request until a rule and a tool settle it.

## Information

- Style disputes continue because no one holds the authority to close them. [judgment]
- Style rules that a tool enforces need no human opinion in review. [inference]

## End

I recommend that we take these five actions in order.

1. **Choose one style in a 45-minute session.**
   - Blocker removed: no one has authority to end the debate.
   - Increment: compare three candidates: the formatter's default, a published SQL style guide, and the current majority style. The tech lead decides if the group has no consensus by minute 40.
   - Kind: evaluative. Cynefin: Complicated, because several good styles exist and a Pugh matrix [2] picks one.
   - Test (written first), Pugh matrix with the formatter default as baseline:
     - Criteria and weights: formatter support (3), diff readability (3), match with current code (2), adoption cost (2).
     - Evidence: a sample of five real queries formatted in each style.
     - Pass threshold: the winner scores above the baseline total.

2. **Configure the formatter with the chosen style.**
   - Blocker removed: the style exists only as opinion.
   - Increment: add one config file to the repository.
   - Kind: deterministic. Cynefin: Clear, because formatters apply a known best practice.
   - Test:
     - Given a file with mixed style
     - When the formatter runs
     - Then the output matches the chosen style
     - And a second run changes nothing

   Step 2 MUST NOT start until Step 1 names a winner.

3. **Add a formatter check to the review pipeline.**
   - Blocker removed: reviewers enforce style by hand.
   - Increment: one pipeline job that fails on unformatted SQL.
   - Kind: deterministic. Cynefin: Clear, because the pipeline pattern is standard.
   - Test:
     - Given a pull request with unformatted SQL
     - When the pipeline runs
     - Then the job fails and names the file
     - And a formatted pull request passes

   Step 3 MUST NOT start until the test in Step 2 passes.

4. **Reformat all existing SQL in one isolated commit.**
   - Blocker removed: old files would fail the new check.
   - Increment: one commit that contains only formatting changes.
   - Kind: deterministic. Cynefin: Clear, because the tool does the whole change.
   - Test:
     - Given the repository before the commit
     - When the formatter runs on all SQL files
     - Then query results and tests are unchanged
     - And the Step 3 check passes on every file

   Step 4 MUST NOT start until the Step 3 test passes.

5. **Run a 30-day probe on review friction.** Start the baseline count now, in parallel with Steps 1 to 4.
   - Capability added: evidence that the change worked.
   - Increment: count style comments per review.
   - Kind: stochastic. Cynefin: Complex, because team response is visible only afterward. Leverage is a guess.
   - Test (written first):
     - Metric: style comments per review.
     - Baseline: the count from the last 20 reviews.
     - Pass threshold: at least an 80% drop.
     - Sample size: 20 reviews after Step 4.
   - Budget: 30 minutes of counting. Stop condition: if the drop is under 40% after 20 reviews, hold a short retrospective to find the cause.

If A3 is false, stop after Step 1 and re-diagnose the friction before you build the pipeline.
