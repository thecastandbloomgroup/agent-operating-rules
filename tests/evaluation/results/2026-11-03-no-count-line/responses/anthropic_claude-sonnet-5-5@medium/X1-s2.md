## Headline

Measure the summariser first, then fix its most common error, because "sometimes wrong" cannot be improved until it is counted.

- No data exists today, so the first step is to label a sample of summaries and name the error types.
- Agents need a cheap way to flag bad summaries, so the data keeps coming after the sample.
- A fixed test set turns each change into a measured result instead of an opinion.
- One small, capped trial on the top error type then tests a fix without risking all tickets.

## Background

The support tool now includes a summariser built on a large language model (LLM). Agents report that it is "sometimes wrong". The team has no metrics, no error categories, and no test set. The request is to improve it.

## Relevance

Agents who distrust the summary stop reading it, so the feature loses its value. A wrong summary can also send a customer the wrong answer. Both costs grow with ticket volume.

## Information

**Evidence.**
- The only evidence is the agent statement "sometimes wrong" (1 source group, from the request). It gives no rate, no error type, and no severity. Confidence in any specific cause is low, because there is no measurement.
- With 100 labeled summaries, the 95% margin on an error rate is about 10 points at a 50% rate [inference]. This is enough to find large problems and too coarse for small gains.
- Typical LLM summary errors are invented facts, missed key details, wrong customer sentiment, and mixed-up ticket parts. This list is a starting hypothesis [judgment], not a finding.

**Assumption log.**

A1. Agents can label a summary as right or wrong by reading the ticket. Why not measured: the material does not state it. Validate by: ask two agents to label the same 20 summaries and compare. If wrong: replace Step 1 with a labeling guide first.

A2. Ticket text and the stored summary are available for export. Why not measured: no tool can reach the system. Validate by: export 10 pairs. If wrong: Step 1 waits for logging to be added.

A3. Data rules allow agents to review ticket text. Why not measured: the user has not answered. Validate by: ask the data owner. If wrong: use redacted tickets only.

A4. The team can change the prompt or model settings. Why not measured: the material does not state it. Validate by: check the deploy process. If wrong: Step 4 becomes a vendor request.

**Alternative considered.** Switch at once to a larger model. It loses because the error types are unknown, so a gain cannot be measured. It also adds cost that has no baseline [judgment].

## End

I recommend that we take these steps, in this order:

1. **Label a sample (Step 1).**
   - Increment: export 100 recent ticket and summary pairs. Two agents label each pair and tag each error type. Group the tags into themes [2].
   - Blocker removed: nobody knows what "wrong" means.
   - Domain: Confused [1], because the failure types are unknown. This step gathers what is needed to classify.
   - Kind: evaluative. Rubric, written first:
     - Faithfulness (weight 50%): every claim appears in the ticket.
     - Completeness (30%): the customer's request and the current status appear.
     - Usefulness (20%): an agent can act without opening the ticket.
     - Pass: a summary passes when faithfulness is met and the weighted score is 80% or higher.
     - Evidence: the ticket text, quoted per criterion.
   - Output: the baseline pass rate and a ranked list of error types.

2. **Add a flag button (Step 2).**
   - Increment: one click marks a summary "wrong" with a reason code. The flag stores the ticket ID.
   - Blocker removed: no ongoing data.
   - Domain: Clear, because logging a flag is a known practice.
   - Kind: deterministic. Test, written first [3]:

   ```text
   Given an agent views a ticket with a summary
   When the agent clicks "wrong" and picks a reason
   Then the flag, reason, and ticket ID are stored
   ```

   - Step 2 MAY run in parallel with Step 1.

3. **Build the fixed test set (Step 3).**
   - Increment: keep the 100 labeled pairs from Step 1 as a test set. Add a script that scores any summariser version on it.
   - Blocker removed: no way to compare versions.
   - Domain: Complicated, because the scoring method needs analysis to pick.
   - Kind: stochastic. Acceptance test, written first:
     - Metric: share of summaries that pass the Step 1 rubric.
     - Baseline: the Step 1 pass rate.
     - Threshold: two scoring runs agree within 5 points.
     - Sample size: 100 pairs, 2 runs.
   - Step 3 MUST NOT start until Step 1 is complete.

4. **Probe a fix for the top error type (Step 4).**
   - Increment: change the prompt to target the top error type from Step 1. For example, require each claim to quote the ticket. Run it on the test set, then on 10% of live tickets for one week.
   - Capability added: a measured improvement.
   - Domain: Complex, because the effect of a prompt change shows only after the trial. The leverage is a guess [judgment].
   - Kind: stochastic. Acceptance test, written first:
     - Metric: pass rate on the rubric.
     - Baseline: the Step 3 score.
     - Threshold: at least 10 points above baseline.
     - Sample size: 200 live summaries plus the 100-pair test set.
   - Budget: one week and one engineer.
   - Stop condition: stop at once if the flag rate rises above the baseline flag rate from Step 2.
   - Step 4 MUST NOT start until the Step 3 test passes. Accept the change only when the threshold is met.

If A1 is false, replace Step 1 with a labeling guide and a 20-pair agreement check.

## Follow-up

**Open questions:** none.

**Conditions that change the recommendation:**
- If the Step 1 pass rate is already 95% or higher, skip Step 4 and keep only the flag button.
- If one error type covers 70% or more of the failures, fix that one first, before any model change.
