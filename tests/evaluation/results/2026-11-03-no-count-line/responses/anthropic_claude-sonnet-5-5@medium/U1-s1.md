## Headline

Measure the failure pattern first, then contain the worst flaky tests while a capped probe finds the cause.

- Data: no failure history is available, so the first step is to collect it.
- Cause: published studies show a few causes explain most flakiness, so clustering failures is cheap and informative.
- Containment: quarantined tests stop blocking the team while the cause is found.
- Fix: a controlled rerun probe tests the likeliest cause before any large change.

## Background

The build passes and fails on the same code. This is called flaky behavior. The request gives no logs, no CI (continuous integration) system name, and no failure rate. So this response gives a method that works on any CI system.

## Relevance

Flaky builds waste reruns and hide real defects. Each ignored red build trains the team to distrust the signal.

## Information

**Evidence**

- Google reported that about 1.5% of its test runs were flaky. Almost 16% of its tests showed some flakiness [1].
- A study of 201 fixed flaky-test commits found three top causes. Async wait caused 45%, concurrency 20%, and test order dependency 12% [2].
- Therefore the cause is likely (66 to 100%) inside the tests or their ordering, not the compiler. [judgment]

**Alternative considered**

## End

I recommend that we take these four steps, in this order.

1. **Export the last 50 CI run results, one row per test per run.** This is one session of work. It removes the blocker that no data exists. Kind: deterministic. Domain: Confused, because the cause is unknown and the data decides the class.
   - Given a CI history with 50 runs
   - When the export script runs
   - Then a file lists test name, result, commit, and error text for every run

2. **Group the failures by test name and error text, then rank the groups.** This removes the blocker of not knowing where to look. Step 2 MUST NOT start until the test in Step 1 passes. Kind: evaluative. Domain: Complicated, because analysis of the data can pick the target.
   - Criteria and weights: failure count 40, repeat rate on the same commit 30, number of builds blocked 30.
   - Pass threshold: a weighted score of 70 out of 100 selects a group as the target.
   - Evidence: the export file from Step 1 for each criterion.

3. **Move the top-ranked flaky tests to a separate non-blocking CI job.** This adds a stable main build. Step 3 MUST NOT start until Step 2 names the targets. Kind: deterministic. Domain: Clear, because quarantine is a known practice.
   - Given the target tests from Step 2 are listed in the quarantine file
   - When the main build runs
   - Then the main build skips them and the quarantine job runs them

4. **Run a probe on the top target: 100 runs in fixed order and 100 runs in random order.** This tests the order-dependence cause from [2]. Run it in parallel with Step 3. Stop at 200 runs or two hours. Kind: stochastic. Domain: Complex, because the cause shows only after the runs. Leverage is a guess.
   - Metric: failure rate per mode.
   - Baseline: the failure rate from Step 1.
   - Threshold: random order fails at least 5 percentage points more than fixed order.
   - Sample size: 100 runs per mode.
