## Headline

Measure the error rate first, then fix the largest error type, because the tool has no data today.

- Agents report "sometimes wrong", but nobody knows how often or in what way.
- Without a baseline, no change can be shown to help.
- A feedback signal in the tool keeps the measurement running after the first audit.
- Each fix is tested against the baseline before release.

## Background

The support tool has an LLM (large language model) summariser. Agents say its summaries are "sometimes wrong". The team has no metrics. The request is to make it better.

## Relevance

An agent who trusts a wrong summary may give a wrong answer to a customer. An agent who distrusts the tool stops using it. Both outcomes waste the investment.

## Information

**Evidence**

- Abstractive summarisers (models that write new text instead of copying) are known to add content that the source does not support [1].
- The error rate of this tool is unknown. [no source]
- A sample of 400 summaries gives a margin of about ±5 points at 95% confidence. [inference] (1.96² × 0.25 ÷ 0.05² ≈ 384)
- The "serious error" threshold in Step 3 is an assessment. [judgment]

**Assumption log**

A1. The tool stores each summary and its source ticket. Why not measured: the material does not state it. Validate by: ask an engineer to pull ten records. If wrong: add logging before Step 1.

A2. The tool can host a feedback button. Why not measured: the material does not state it. Validate by: check the front-end code for an extension point. If wrong: collect feedback in a form outside the tool.

A3. Two reviewers can label 400 summaries in about two days. Why not measured: no tool can reach reviewer capacity. Validate by: time the first 20 labels. If wrong: reduce the sample and widen the margin.

**Alternative considered**

Switch to a larger model now. It loses because without a baseline nobody can show that it helps, and the cost may buy nothing. [judgment]

## End

I recommend that we take these steps in order:

1. **Audit a sample (Confused).** Draw 400 random summaries. Two reviewers label each one against its source. The rubric has four criteria: faithful to source (weight 40%), complete on the customer's issue (30%), correct on names, numbers, and dates (20%), and clear (10%). Each criterion is scored 0 to 2 against the source text. A summary with a faithfulness or accuracy score of 0 is a "serious error". Group the errors into types and count each type. The increment is one report with the baseline serious-error rate and a ranked error list. The blocker removed is that nobody knows the error rate or its causes. The test is evaluative: the rubric is written before labeling, and the pass threshold is a reviewer agreement of at least 80% on a shared set of 40. The domain is Confused, because the error causes are unknown and this step classifies them.

2. **Add an agent feedback button (Clear).** The increment is a "wrong summary" button with four reason codes, logged with the summary ID. The blocker removed is that there is no ongoing signal. The test is deterministic:
   - Given an agent views a summary
   - When the agent clicks "wrong summary" and selects a reason
   - Then the tool stores the summary ID, the reason, and a timestamp
   
   The domain is Clear, because a standard feedback pattern exists [2].

3. **Run a capped probe on the top error type (Complex).** Step 3 MUST NOT start until Step 1 delivers the ranked error list. Change one thing that targets the top error type, for example the prompt or the input format. Run it on the same 400 tickets. The blocker removed is the largest error type. The test is stochastic. The metric is the serious-error rate. The baseline is the Step 1 value. The pass threshold is a relative drop of one third or more [judgment]. The sample size is 400. The budget is two working days. The stop condition is three variants without a pass. Leverage here is a guess. The domain is Complex, because the effect of a prompt change is visible only after the run.

4. **Show the source beside the summary (Clear).** The increment is a link from each summary to the ticket lines it covers. The capability added is fast agent verification. The test is deterministic:
   - Given a summary exists for a ticket
   - When an agent opens the summary
   - Then the tool shows a link to the source messages
   
   The domain is Clear, because the change is a known interface pattern. Run Step 4 in parallel with Step 3.

5. **Track the rate after release (Clear).** Step 5 MUST NOT start until Step 2 is live. The increment is a weekly report of the feedback rate per 100 summaries. The blocker removed is that quality can drop unseen. The test is deterministic:
   - Given feedback events exist for the week
   - When the report job runs
   - Then it shows the count of "wrong summary" clicks per 100 summaries
   
   The domain is Clear, because the calculation is a plain count.

Step 3 changes go live only if the test passes. If A1 is false, add summary and source logging before Step 1.

## Follow-up

- If reviewer agreement stays under 80%, rewrite the rubric before any fix.
