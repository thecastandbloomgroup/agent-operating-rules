## Headline

Raise the connection pool size first, because the pool cut from 50 to 8 per pod causes most of the delay.

- Pool wait (span `db.pool.acquire`) rose by 687 ms at p95, which is 88% of the 780 ms rise. [1]
- The database itself is not slower: query p95 moved from 52 to 58 ms, and server CPU from 38% to 41%. [1]
- The shorter cache TTL (time to live) raised the miss rate from 12% to 31%, which adds load on the pool. [2]
- The ORM change (object-relational mapper) is a minor factor on this evidence, so test it after the pool fix. [1]

## Background

Release 2026.10.21 changed three things. It cut `max_size` from 50 to 8, cut `acquire_timeout_s` from 30 to 5, and cut the cache TTL from 300 to 60 s. It also added `selectinload` (eager load of order lines) to the orders query. [2]

The API runs 4 pods with 8 worker threads each. P95 latency went from 120 ms to 900 ms. [1]

## Relevance

The error rate rose from 0.02% to 0.40%, and 96% of the errors are `PoolTimeout`. [1] Each of these requests ends as a 503 after 5 s. [3]

## Information

**Evidence**

- The pool is full on every pod: "8 of 8 connections in use", with 6 to 14 waiters. [3]
- Pool-full warnings went from none on 2026-10-20 to 1,800 to 2,400 per hour on 2026-10-22. [3]
- Peak load is flat: 410 requests per second before, 405 after. Load is not the cause. [1]
- Cache miss rate rose from 12% to 31%, which is 2.6 times more cache misses and so more database work. [1]
- The commit message says the cut matches a new DB connection limit (OPS-412). The limit value is not in the material. [2]
- Confidence that the pool cut is the main cause: very likely (90 to 100%). Basis: three independent measurements agree (span delta, log warnings, error type). [1]

Waiters per pod (up to 14) exceed the 8 worker threads. This suggests that something else asks for connections. [inference]

**Assumption log**

A1. The OPS-412 limit allows at least 32 connections for this service (4 pods x 8 workers). Why not measured: the material does not state it. Validate by: read OPS-412 or ask the database team. If wrong: set the pool to limit divided by 4 pods, and add a pool proxy.

A2. The pool size applies per pod. Why not measured: the traces show 8 active connections in total, but the logs show 8 of 8 on each pod. Validate by: read the pool metric per pod. If wrong: the total is smaller than assumed, and the fix is still the same.

A3. The business does not require the 60 s TTL. Why not measured: the material does not state it. Validate by: ask the owner of the cache change. If wrong: keep 60 s and size the pool for the higher miss rate.

**Alternative considered**

Roll back the whole release. It restores all three settings at once. It loses because it also removes the OPS-412 change, which may break the new connection limit. [judgment]

   - This probe runs in parallel with Steps 2 and 3.
