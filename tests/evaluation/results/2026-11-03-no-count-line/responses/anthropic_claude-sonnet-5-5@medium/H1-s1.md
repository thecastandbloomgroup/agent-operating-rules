## Headline

Roll back the newest change now, then brief the executives with three facts.

- Stabilise first, because a rollback (a return to the previous version) is the fastest reversible fix.
- Communicate second, because executives need impact, status, and a next-update time, not a cause.
- Diagnose third, and only if the rollback fails.
- Get a second engineer in now, so one person does not hold the whole incident.

## Background

Checkout returns HTTP 500 (a server error code) for every user since 09:12. The on-call engineer has ten minutes before an executive call. The cause is unknown.

## Relevance

Every minute of downtime is lost checkout revenue. The executive call is a fixed deadline, so the first ten minutes must both start recovery and prepare a clear message.

## Information

Evidence:

- About 70% of outages follow a change to a live system, so a recent change is the first suspect [1].
- Every user fails from one start time, 09:12. This pattern points to a shared component, not a user-specific fault [judgment].
- The cause is not visible yet, so Cynefin classes the situation as Chaotic until service returns [2].

Assumption log:

A1. A deploy or config change happened near 09:12. Why not measured: the material does not state it. Validate by: check the deploy log for changes from 08:45 to 09:12. If wrong: skip Step 1 and start Step 3.

A2. A rollback path exists and takes under 5 minutes. Why not measured: no tool can reach it. Validate by: read the last deploy's rollback command. If wrong: use a feature flag or a traffic switch instead.

A3. A status channel exists for the executives. Why not measured: the material does not state it. Validate by: open the incident channel. If wrong: send a direct message to the call host.

Alternative considered: find the root cause before any action. It loses because diagnosis time has no upper bound, while a rollback is quick and reversible [judgment].

## End
