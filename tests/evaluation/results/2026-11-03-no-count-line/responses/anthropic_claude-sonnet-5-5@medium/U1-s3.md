## Headline

Measure the flake rate first, then quarantine the worst test and probe the root cause.

- The cause is unknown, so the first step is to collect run history.
- Known causes of flaky tests are few, so a short list of hypotheses covers most cases.
- A quarantine keeps the main branch green while the fix proceeds.

## Background

The message says only that the build is flaky. A flaky build passes and fails on the same code. The query gives no logs, no tool names, and no failure rate.

## Relevance

Each false failure blocks merges and wastes reruns. Teams that rerun by habit also stop trusting real failures.

## Information

Evidence:

- In a study of 201 fixed flaky-test commits in open-source projects, async waits caused 45% of cases. High confidence, one large study. [1]
- The same study found concurrency caused 20% and test order dependency caused 12%. [1]
- Practitioner guidance says to quarantine a non-deterministic test and fix it, not ignore it. [2]
- Two sources support the theme "few causes dominate". No source found disagrees. [judgment] The study covers open-source code, so the shares for this build may differ.

Assumption log:

A1. The failure is a test failure in continuous integration (CI), the automated build service. Why not measured: the material does not state it. Validate by: read the last failed CI log. If wrong: replace Step 2 with a check of the build tooling.

A2. CI keeps at least 50 past runs. Why not measured: no tool can reach it. Validate by: open the CI history page. If wrong: start with Step 2 and collect new runs.

A3. The same commit both passes and fails. Why not measured: the user has not answered. Validate by: rerun one failed commit. If wrong: the cause is a code change, not a flake.

Alternative considered: add automatic retries to every job. This hides the flake rate and delays the fix, so it loses. [judgment]

## End

I recommend that we do these steps in order:

1. Collect the last 50 CI runs and list each failure by test name and commit.
   - Increment: one table, built in one session.
   - Blocker removed: no one knows which test fails.
   - Kind: deterministic. Domain: Confused, because the cause is not yet visible.
   - Test:
     - Given 50 past CI runs
     - When the failures are grouped by test name
     - Then each failure appears in exactly one row, and the row count equals the failure count
2. Rerun the top failing test 30 times on one unchanged commit.
   - Increment: one scripted loop.
   - Blocker removed: A3 is unconfirmed.
   - Kind: stochastic. Domain: Complicated, because analysis of the logs picks the cause.
   - Test: the metric is the failure count in 30 runs. The baseline is 0 failures. The flake is confirmed at 1 or more failures. The sample size is 30.
   - Step 2 MUST NOT start until the table in Step 1 passes its test.
3. Quarantine that test, that is, move it to a non-blocking job.
   - Increment: one configuration change.
   - Blocker removed: false failures block merges.
   - Kind: deterministic. Domain: Clear, because quarantine is an established practice. [2]
   - Test:
     - Given the quarantined test still fails on a rerun
     - When the main job runs
     - Then the main job passes and the quarantine job reports the failure
   - Step 3 MUST NOT start until Step 2 confirms the flake.
4. Run a probe on the likely cause: replace fixed sleeps with explicit waits, then rerun.
   - Increment: one test file.
   - Blocker removed: the root cause is open.
   - Kind: stochastic. Domain: Complex, because the cause shows only after the change. Leverage is a guess.
   - Budget: 2 hours. Stop condition: stop if 100 reruns still show failures, then test order next.
   - Test: the metric is the failure rate over 100 runs. The baseline is the rate from Step 2. The pass threshold is 0 failures. The sample size is 100.
   - This probe MAY run in parallel with Step 3.

If A1 is false, replace Step 2 with a check of the build tooling.
