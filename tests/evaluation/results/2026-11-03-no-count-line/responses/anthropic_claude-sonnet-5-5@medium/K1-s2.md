## Headline

Raise the database pool limit first, because the pool change in the release causes most of the slowdown.

- Pool wait explains the latency: `db.pool.acquire` p95 rose from 3 ms to 690 ms, which is 690 of the 780 ms added.
- The ORM change and the cache change are minor causes, because query times did not move and the cache span stayed flat.
- The 5 s acquire timeout turns waits into 503 errors.
- One fact is open: the real database connection limit (see A1).

## Background

Release 2026.10.21 cut the pool `max_size` from 50 to 8 and the acquire timeout from 30 s to 5 s. It also cut the cache TTL (time to live, how long an entry stays valid) from 300 s to 60 s, and added `selectinload` to the orders query. API p95 latency rose from 120 ms to 900 ms. A pool is a set of reusable database connections.

## Relevance

The error rate is 0.40% today, against 0.02% before the release. It stays at this level until the pool limit changes. Each day adds failed order requests.

## Information

**Evidence**

- Pool wait p95 rose from 3 ms to 690 ms (traces.txt, window A and B table). [3]
- Query spans are flat: `db.query orders` p95 went from 52 ms to 58 ms (traces.txt, same table). [3]
- Database CPU peaked at 38% before and 41% after, so the database is not saturated (traces.txt, last lines). [3]
- Of the errors, 96% are `PoolTimeout` after 5 s (traces.txt, error rate line). [3]
- Pool warnings rose from none on 2026-10-20 to 1,800 to 2,400 per hour on 2026-10-22 (logs.txt, note). [1]
- The commit says the pool size was lowered to match a new database connection limit (release.diff, OPS-412 commit message). [2]
- Cache miss rate rose from 12% to 31%, but `cache.get` p95 stayed at about 5 ms (traces.txt, table). [3]
- Cause confidence: very likely (90 to 100%) that the pool change drives the latency. The basis is three independent measurements: span timing, error type, and warning counts.
- Cache theme: all three files agree the TTL change raises misses. No source says it raises latency. The extra misses add query load, but query p95 is flat. [judgment]
- The ORM change adds a second query. Its p95 (26 ms) is below the old value (30 ms), so this change is not a cause (traces.txt). [3]
- Waiters reach 14 on a pod with 8 threads (logs.txt, 10:14:07 line). [1]
  - A pod with 8 threads should not queue more than 8 requests for connections.
  - A request may hold more than one connection. [inference]

**Assumption log**

**Alternative considered**

Roll back the whole release. It restores the old speed fast, but it also drops the OPS-412 limit change. The database may reject connections. Rollback is the fallback if Step 2 fails.
