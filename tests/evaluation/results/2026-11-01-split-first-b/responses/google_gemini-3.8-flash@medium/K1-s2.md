### Headline

Revert the cache time-to-live to 300 seconds and adjust connection pool parameters to resolve database contention.
Connection acquisition time accounts for 687 milliseconds of the 780 millisecond latency increase.
Lowering the cache time-to-live increased database query volume by raising cache misses from 12% to 31%.
The reduced pool size of eight connections per pod cannot handle the resulting query volume.

### Background

Application p95 latency rose from 120 ms to 900 ms following the deployment of release 2026.10.21 [2].
The deployment modified the database connection pool, the cache configuration, and the query loader [2].
Errors increased to 0.40% because connection pool acquisitions timed out after 5 seconds [3].

### Relevance

Current latency degrades user experience and triggers HTTP 503 error spikes [1].
Fixing the pool starvation immediately restores throughput and prevents service failures.

### Information

Traces show that `db.pool.acquire` p95 duration rose from 3 ms to 690 ms [3].
This change explains 88% of the total 780 ms latency increase [3].
In contrast, database query execution times remained stable [3].
The `db.query orders` p95 changed from 52 ms to 58 ms [3].
The `db.query order_lines` p95 decreased from 30 ms to 26 ms [3].
Therefore, the object-relational mapping (ORM) change did not cause the regression [inference].

However, the cache miss rate rose from 12% to 31% after reducing time-to-live (TTL) to 60 seconds [2].
This higher miss rate increased query traffic to the database pool [1].
Concurrently, configuration updates lowered pool `max_size` from 50 to 8 per pod [2].
Each pod runs 8 worker threads, so slight traffic bursts exhaust all 8 connections [2].
Logs record up to 14 waiting threads per pod and over 1,800 exhaustion warnings hourly [1].
In addition, cutting `acquire_timeout_s` from 30 to 5 seconds caused 503 failures [1].
Confidence level: high confidence, three independent measurements in logs, diffs, and traces.
