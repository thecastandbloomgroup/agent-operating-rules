### What to measure

Use the source ticket as the reference, not whether the summary sounds convincing. [judgment]

Track these separate dimensions:

| Dimension | Definition | Measure |
|---|---|---|
| Factual errors | Claims that contradict the ticket or lack support | Percentage of summaries with an error |
| Required facts | Facts agents need for the next support action | Percentage of required facts retained |
| Restricted content | Information that access rules prohibit in the summary | Number of violations |
| Agent effort | Time needed to check and correct the summary | Median seconds per summary |

Mark an error **severe** when it changes the next support action or violates an access rule. [judgment]

Record the ticket reference, model version, prompt version, supplied context, summary, reviewer labels, and correction. [judgment] Use approved storage and existing access controls. [judgment]

### 3. Test one targeted fix against the current version

**Kind:** Stochastic.  
**Domain:** Complex, because the effect on unseen tickets becomes visible only after a trial.

**Acceptance test first:**

- **Metrics:** The four dimensions above.
- **Baseline:** Current-version results on the same test tickets.
- **Sample:** 30 fresh tickets, excluded from diagnosis.
- **Pass threshold:** At least 30% fewer summaries with factual errors, with no new severe errors.
- **Guardrails:** Required-fact retention cannot decrease; median correction time cannot increase.
- **Budget:** One two-hour experiment; no live deployment.

These thresholds are provisional pilot gates, not measured business requirements. [judgment]

Step 3 MUST NOT start until Step 2 identifies the most frequent actionable cause.

Change only one element:

- For missing input, correct the supplied ticket context.
- For incorrect use of available input, require source-linked claims.
- For unclear requirements, define required facts and an explicit “not stated” response.

Choose only the matching change. Hide version names from reviewers and vary the review order.

**Increment:** One candidate and a paired comparison report.  
**Capability added:** Evidence that a specific change improves unseen cases.  
**Stop condition:** Reject the candidate after any new severe error or access violation.

If the baseline has no factual errors, expand the sample instead of claiming a reduction. [judgment] Even a passing pilot does not establish safety for rare errors. [judgment]
