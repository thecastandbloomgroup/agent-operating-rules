Headline

Retrospectives fail when they end as discussion, so convert each one into a tracked experiment.
- Give every selected change one owner, one due date, and one visible test.
- Open the next retrospective by judging the last change before new topics.
- If people still do not speak, run a small safety probe with a stop rule.

Background

The team meets, but the same issues return. The pattern points to weak closure, weak memory, or low safety [judgment]. The useful move is to treat the retrospective as a system that must produce delta, not as a meeting that must produce talk [judgment].

Relevance

A repeated ritual without change teaches people that input has no effect. That lowers trust and attendance quality over time [judgment].

Information

Evidence is limited to the symptom in the request, so the mechanism is inferred. Three failure modes fit the symptom and are mutually exclusive enough to act on: no ownership after the meeting, no review of prior actions, and fear of naming the real constraint [judgment]. The baseline is zero completed changes per retrospective. The target is one completed, verified change per sprint for four sprints [judgment].

A1. Team cadence is sprint or iteration based. Why not measured: the material does not state it. Validate by: ask for the last four retrospective notes. If wrong: use the actual cadence length for due dates.

A2. One facilitator exists. Why not measured: the material does not state it. Validate by: check who ran the last two sessions. If wrong: assign a rotating facilitator before Step 1.

A3. Main blocker is follow-through, not topic quality. Why not measured: no notes were provided. Validate by: count prior action items closed. If wrong: shift effort to problem selection.

Alternative considered: stopping retrospectives saves time, but it removes the only regular feedback loop and hides causes [judgment].

End

I recommend that we run the next four retrospectives as a measured change loop with these actions:

1. Close each retrospective with one change only. Increment: write one card with owner, due date, and evidence of done; this removes the no-owner blocker; test: test first in Gherkin form.
Given the retrospective has ended,  
When the card is written,  
Then it names one accountable owner, one date, and one observable result.  
Domain: Clear, because the practice is standard and cause and effect are known.

2. Open the next retrospective with the previous card. Increment: spend ten minutes on status, evidence, and keep or drop; this restores memory; test: test first in Gherkin form.
Given one card from the last session exists,  
When the next session starts,  
Then the first agenda item records done, not done, or blocked with a reason.  
Domain: Clear, because a known checklist removes recurrence.

3. If Steps 1 and 2 show cards are done but issues persist, run one safety probe. Increment: one anonymous three-question pulse plus one round-robin pass; budget: 20 minutes; stop condition: stop if names are requested or results are debated; this tests low safety without blame; test: acceptance test first, metric is percent reporting “safe to raise a hard topic,” baseline from first pulse, pass threshold is 60% or a 15-point rise, sample size is all attendees for two rounds. Domain: Complex, because cause and effect appear only after the probe, so the probe is capped.

Step 2 MUST NOT start until Step 1 has created a card. Step 3 SHOULD start only after two cycles of Steps 1 and 2. If A3 is false, replace action selection in Step 1 with ranking by repeat frequency.

Follow-up

Conditions that change the recommendation: use a shorter cycle if the team works weekly; escalate to a manager only if the same blocker repeats for four cycles and is outside team control. References: none.
