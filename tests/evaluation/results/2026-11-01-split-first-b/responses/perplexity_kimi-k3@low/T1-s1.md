Headline
SQL formatting wars end with one automated formatter, one config file, and a pre-commit hook, not with a style debate.
- Formatting disputes are taste-based, so discussion cannot resolve them; tooling can [judgment].
- An automated formatter removes the topic from reviews because the output is deterministic.
- A one-time team vote on the config builds commitment, then the tool enforces it from then on.

Background
The team disagrees on SQL formatting and it causes friction in every code review. The request is to fix the culture problem, not just the style. No database type, team size, or formatter already in place is known.

Relevance
Review friction slows delivery and erodes goodwill each sprint. Removing one recurring dispute source compounds over every future review.

Information
Evidence:
- Harold Abelson: "Programs must be written for people to read, and only incidentally for machines to execute" [1]. Readability matters, but which style matters less than consistency.
- Industry practice: teams that adopt an opinionated formatter (Prettier for JavaScript, Black for Python) stop having format disputes because the tool decides [2].
- Theme from team-work research: norms that members vote on get followed more than norms imposed from above (one supporting source) [3].

Assumptions:
- A1. SQL dialect is unknown; assume a common one (PostgreSQL, MySQL, or similar). Why not measured: the material does not state it. Validate by: ask in the first team session. If wrong: only the choice of tool changes, the approach stays.
- A2. Code is reviewed through a tool that allows pre-commit hooks or CI checks. Why not measured: the material does not state it. Validate by: check the repository setup. If wrong: enforce at CI instead of pre-commit.

Alternative considered: write a team style guide without auto-formatting. It loses because memory and discipline enforce it, so disputes return within months [judgment].

End
I recommend that we take these steps:
1. Pick a formatter by brief vote (sqlfluff for lint plus format, or the dbt-geneerated SQLFluff if dbt is in use). Increment: one meeting with three live demos. Blocker removed: the open question of which tool. Test (evaluative: rubric of dialect support 40%, rule coverage 30%, editor integration 30%, pass at majority yes): score each tool in the meeting, treat as evaluative because no further data exists. Domain: Complicated, because options are knowable through one analysis session.
2. Have the team vote on the config rules once, in the same session. Increment: one vote per contested rule. Blocker removed: taste disputes. Test (stochastic): every active member votes, pass at simple majority, sample size equals team size. Domain: Clear, because majority vote is the best practice for tying taste decisions.
3. Run the formatter once on the whole codebase and commit the result alone. Increment: one commit, no other changes. Blocker removed: noisy diffs that hide real changes. Test (deterministic):
   Given the formatted code, When all existing tests or queries run, Then results match the pre-format run. Domain: Clear, refactor with no behavior change.
4. Add a pre-commit hook and a CI check that fails on unformatted SQL. Increment: one hook file, one CI step. Blocker removed: human enforcement in reviews. Test (deterministic):
   Given a commit with unformatted SQL, When the hook runs, Then the commit is rejected with a fix command. Domain: Clear, standard hook setup.
5. Add a review rule: comments on format are off-limits, exceptions go to a config-change proposal. Increment: one line in the review checklist. Blocker removed: format comments in review threads. Test (stochastic): zero format-only comments across the next 20 SQL reviews, against the current baseline where they occur every review. Domain: Complex, because behavior shifts are only visible after the norm is in place; cap the probe at 20 reviews and stop if the count is not dropping by review 10.

Step 3 MUST NOT start until the vote in Step 2 finishes. Steps 4 and 5 run in parallel after Step 3 passes. If A2 is false, replace Step 4 with a CI-only check.
